# 사전 학습 노트 — Claude Code 설정과 워크플로우 (conf 30-39 범위)

이 문서는 이 주제를 처음 접하는 사람을 위한 것입니다. Claude Code가 무엇인지 모른다는 전제에서 시작해, 필요한 개념을 하나씩 쌓아 올립니다.

---

## 0. 출발점: Claude Code란 무엇인가

Claude Code는 Anthropic이 만든 **터미널에서 동작하는 AI 코딩 에이전트**입니다. 채팅창에 코드를 붙여넣고 답변을 받아 다시 붙여넣는 방식이 아니라, 에이전트가 **직접 파일을 읽고 쓰고, 셸 명령을 실행하고, 검색을 수행**합니다.

이 때문에 두 가지 새로운 관심사가 생깁니다.

1. **컨텍스트 관리** — 모델이 한 번에 볼 수 있는 텍스트 양(컨텍스트 윈도우)은 유한합니다. 에이전트가 파일 수십 개를 읽으면 그 내용이 전부 대화에 쌓입니다.
2. **권한 관리** — 에이전트가 임의의 셸 명령을 실행할 수 있으므로, 무엇을 허용할지 통제해야 합니다.

이 노트의 대부분은 이 두 축을 중심으로 전개됩니다.

---

## 1. 컨텍스트 윈도우와 그 관리

### 1.1 컨텍스트 윈도우(Context Window)

LLM은 매 요청마다 "지금까지의 대화 전체"를 다시 읽습니다. 이 전체를 담는 그릇이 컨텍스트 윈도우이고, 크기는 토큰(token) 단위로 제한됩니다.

여기서 파생되는 세 가지 실질적 문제:

- **비용**: 대화가 길수록 매 턴 처리해야 할 토큰이 늘어나 요금과 지연시간이 커집니다.
- **오염(pollution / noise)**: 지금 하려는 작업과 무관한 옛 내용이 잔뜩 섞이면 모델의 판단이 흐려집니다.
- **한계 초과**: 윈도우가 가득 차면 앞부분이 잘리거나 요약되면서 정보가 손실됩니다.

### 1.2 신선한 세션(Fresh Session)

세션(session)은 하나의 이어지는 대화 단위입니다. 새 세션을 시작하면 컨텍스트가 비워집니다.

핵심 전략: **탐색/토론 단계와 구현 단계를 서로 다른 세션으로 나눈다.**

탐색 단계에서는 수십 번의 질의응답, 폐기된 아이디어, 읽다 만 파일 내용이 쌓입니다. 그 상태에서 구현을 시작하면 모델은 "이미 버려진 아이디어"까지 참조하며 흔들립니다. 대신 탐색 결과를 **문서로 고정**한 뒤, 새 세션에서 그 문서만 읽히면 컨텍스트는 깨끗하고 정보는 보존됩니다.

### 1.3 서브에이전트(Subagent)

서브에이전트는 **메인 대화와 분리된 컨텍스트를 가진 별도의 에이전트 인스턴스**입니다. 메인 에이전트가 작업을 위임하면, 서브에이전트가 자기만의 컨텍스트에서 일하고 **최종 결과만** 메인에게 돌려줍니다.

동작 그림:

```
[메인 대화]  ── 위임 ──▶  [서브에이전트: 파일 40개 읽기, grep 20회 ...]
      ▲                                    │
      └──── "인증 설정은 config/auth.ts에 있음" (요약 결과만) ─────┘
```

메인 컨텍스트에 들어가는 것은 마지막 한 줄짜리 결론뿐입니다. 파일 40개의 원문은 서브에이전트 안에서 소모되고 사라집니다.

**Explore 서브에이전트**는 이 용도에 특화된 읽기 전용 탐색 에이전트입니다. "이 기능이 어디 구현돼 있지?", "레거시 인증 흐름이 어떻게 돌아가지?" 같은 **넓은 범위의 조사**에 씁니다.

### 1.4 위임할 때와 직접 할 때

| 작업 성격 | 권장 방식 | 이유 |
|---|---|---|
| 넓은 조사 (파일 수십 개 읽기, 전체 탐색) | 서브에이전트 위임 | 산출물이 크고 대부분 버려짐 |
| 좁은 실행 (파일 1개에 필드 1개 추가) | 메인에서 직접 실행 | 위임 오버헤드가 작업보다 큼 |

전형적인 조합: **넓은 조사는 서브에이전트에 위임 → 결론만 받음 → 좁은 수정은 메인에서 직접 수행.** 이것이 "철저함"과 "컨텍스트 효율" 사이의 균형점입니다.

반대로, 조사 자체를 건너뛰고 "그럴듯해 보이는 파일"에 바로 손대는 것은 효율이 아니라 도박입니다. 이해를 줄이는 것과 출력을 줄이는 것은 다릅니다.

또 하나 주의할 점: **플랜 모드(Plan Mode)** 는 파일을 바꾸기 전에 계획을 세워 검토받는 모드인데, 이것은 *컨텍스트 소모 문제를 해결해 주지 않습니다.* 조사 과정에서 읽은 파일 내용은 플랜 모드에서도 그대로 메인 컨텍스트에 쌓입니다. 게다가 설정 파일 한 줄 고치는 사소한 작업까지 플랜 모드로 감싸면 절차만 무거워집니다. 컨텍스트 절약 수단은 플랜 모드가 아니라 서브에이전트입니다.

## 2. 요구사항 도출과 스펙 기반 개발

### 2.1 AskUserQuestion 도구

`AskUserQuestion`은 Claude Code가 **사용자에게 선택지가 있는 질문을 던지는** 도구입니다. 에이전트가 혼자 추측하는 대신, 결정적인 갈림길에서 사람에게 물어봅니다.

사용자가 "이 기능을 만들고 싶은데, AskUserQuestion으로 나를 상세히 인터뷰해 줘"라고 요청하면, 에이전트는 요구사항을 캐내는 **대화형 요구사항 도출(interactive requirements elicitation)** 진행자가 됩니다.

### 2.2 왜 인터뷰가 필요한가

"지원 티켓 검색 기능을 만들어 줘" 같은 한 줄 요청에는 결정되지 않은 사항이 수십 개 숨어 있습니다.

- **랭킹(ranking)**: 결과를 어떤 순서로 보여줄 것인가? 최신순? 관련도순? 우선순위 가중치?
- **필터링(filtering)**: 상태·담당자·기간·태그 중 무엇으로 걸러낼 수 있어야 하는가?
- **실패 모드(failure mode)**: 검색 인덱스가 다운되면? 결과가 0건이면? 쿼리가 너무 길면? 타임아웃은?

이런 항목이 정해지지 않은 채 구현에 들어가면 에이전트는 "일반적인 관행"으로 빈칸을 채웁니다. 그럴듯하지만 실제 요구와 어긋난 코드가 나옵니다. 질문 두세 개만 답하고 나머지를 모델의 추정에 맡기는 것도 같은 결과를 낳습니다.

**DB 스키마만 던져주면 되지 않나?** 안 됩니다. 스키마는 데이터의 *모양*(필드 이름, 타입, 관계)을 알려줄 뿐, *비즈니스 의도*는 담고 있지 않습니다. 필드 이름과 타입에서 "고객사 티켓을 우선 노출한다" 같은 규칙을 추론할 수는 없습니다.

### 2.3 명세서(Spec)와 스펙 기반 개발

**Spec-driven development**: 대화로 도출한 요구사항을 **독립적으로 완결된 명세 문서**로 먼저 고정하고, 그 문서를 기준으로 구현하는 방식입니다.

좋은 스펙의 요건:

- **자립적(self-contained)** — 이 문서만 읽으면 구현할 수 있어야 합니다. "아까 대화에서 말한 그거"에 의존하면 안 됩니다.
- **구체적** — 관련 파일 경로와 인터페이스(함수 시그니처, 타입, 엔드포인트)를 명시합니다.
- **결정 사항이 빠짐없이 기록됨** — 랭킹 규칙, 필터 목록, 에러 처리 정책까지.

왜 "대화 기록(transcript)"으로는 부족한가: 대화 기록은 길고, 순서가 뒤섞이고, 중간에 뒤집힌 결정이 그대로 남아 있으며, 새 세션으로 옮길 수 없습니다. 스펙은 그 대화의 **정제된 결과물**입니다.

전체 흐름:

```
한 줄 요청
  → AskUserQuestion 인터뷰 (랭킹·필터·실패 모드까지 전부 확정)
  → 자립형 스펙 문서 작성 (파일·인터페이스 명시)
  → 새 세션 시작
  → 스펙만 읽히고 구현에 집중
```

## 3. 효과적인 버그 수정 프롬프팅

### 3.1 에지 케이스(Edge Case)

정상 경로가 아닌 경계 조건에서만 나타나는 상황입니다. 예: 값이 `null`, 빈 리스트, 0, 음수, 아주 긴 문자열, 유니코드 문자.

예시 상황: 레거시 고객 데이터를 새 스키마로 옮기는 마이그레이션 스크립트에서, `middle_name`이 `null`인 레코드가 **빈 문자열로 변환되어야 하는데 아예 누락**되고 있습니다.

### 3.2 구체적 예시로 지시하기 (Few-shot / 테스트 케이스 제공)

가장 효과적인 수정 요청은 **입력과 기대 출력을 나란히 보여주는 것**입니다.

```
입력:
  { "first_name": "Kim", "middle_name": null, "last_name": "Lee" }

기대 출력:
  { "first_name": "Kim", "middle_name": "", "last_name": "Lee" }

현재는 이 레코드가 결과에서 통째로 빠집니다.
```

이렇게 주면 모델은 (1) 어느 필드인지, (2) 어떤 조건인지, (3) 무엇이 정답인지를 추측 없이 알게 됩니다. 게다가 이 예시는 그대로 회귀 테스트로 굳힐 수 있습니다.

비효율적인 대안들과 그 이유:

- **모호한 신고** ("null 관련 버그가 있어") — 어느 필드인지, 정답이 무엇인지 알 수 없어 엉뚱한 곳을 고칩니다.
- **전면 재작성 / 언어 교체** — 한 줄짜리 조건 분기 문제에 스크립트 전체를 다른 언어로 다시 쓰는 것은 비용만 크고 해결을 보장하지 못합니다.
- **광범위한 예외 삼키기** — 변환 함수 전체를 `try/except`로 감싸 오류 레코드를 조용히 건너뛰면, 증상(에러 로그)만 감추고 원인(데이터 유실)은 그대로입니다. 오히려 유실이 눈에 안 보이게 됩니다.

원칙: **증상이 아니라 원인을 고치고, 정확히 무엇이 정답인지 예시로 보여준다.**

## 4. 권한 시스템

### 4.1 왜 권한이 필요한가

에이전트가 셸을 쓸 수 있다는 것은 `rm -rf`도 실행할 수 있다는 뜻입니다. Claude Code는 기본적으로 위험한 동작 전에 **사용자에게 확인 프롬프트**를 띄웁니다. 하지만 CI 같은 자동화 환경에는 답할 사람이 없으므로, 미리 규칙으로 정해두어야 합니다.

### 4.2 `--allowedTools`와 패턴 매칭

`--allowedTools`는 **프롬프트 없이 자동 승인할 도구/명령을 지정**하는 CLI 옵션입니다.

```bash
claude -p "run the migration script" --allowedTools "Bash(npm run migrate)"
```

형식은 `도구이름(인자패턴)`입니다. `Bash(...)` 안의 문자열이 실행될 명령과 대조됩니다.

**핵심 규칙 — 끝에 붙은 별표는 접두사 매칭(prefix matching)입니다.**

| 패턴 | 매칭되는 것 |
|---|---|
| `Bash(npm run migrate)` | 정확히 `npm run migrate` 만 |
| `Bash(npm run migrate*)` | `npm run migrate`, `npm run migrate-cleanup`, `npm run migrate:dev`, `npm run migrateEverything` … |

`*`는 "그 뒤에 무엇이 오든 상관없음"을 뜻합니다. 따라서 `Bash(npm run migrate*)`로 써 두면 의도하지 않은 `npm run migrate-cleanup`까지 **프롬프트 없이 자동 실행**됩니다. 정확히 한 명령만 허용하려면 **별표를 빼야** 합니다.

혼동하기 쉬운 오해들:

- 이 패턴은 정규표현식이 아니라 **글로브(glob) 스타일 와일드카드**입니다. 정규식의 `*`(앞 문자 0회 이상 반복)나 교차(alternation)와는 의미가 다릅니다.
- `acceptEdits` 같은 다른 권한 모드가 `--allowedTools`의 매칭 폭을 몰래 넓히지 않습니다. "migrate라는 단어를 포함하면 매칭" 같은 규칙도 존재하지 않습니다.
- 매칭 방식을 바꾸는 마법의 플래그(`--bare` 등) 같은 것은 없습니다. 넓어진 원인은 패턴 그 자체입니다.

### 4.3 권한 모드(Permission Mode)

권한 모드는 "규칙에 안 잡힌 요청이 들어왔을 때 어떻게 할지"를 정하는 전역 태도입니다.

| 모드 | 동작 | 적합한 곳 |
|---|---|---|
| 기본(대화형) | 미승인 동작마다 사용자에게 확인 프롬프트 | 사람이 앞에 앉아 있는 로컬 개발 |
| `acceptEdits` | 파일 쓰기·일반 파일시스템 명령을 자동 승인 | 신뢰하는 작업을 빠르게 반복할 때 |
| `dontAsk` | 프롬프트를 띄우지 않음. `permissions.allow` 규칙이나 내장 읽기 전용 명령 세트에 없는 것은 **즉시 거부** | 사람이 없는 CI/CD, 잠금 환경 |

`dontAsk`가 자동화에 맞는 이유: 비대면(non-interactive) 환경에서 프롬프트가 뜨면 프로세스가 **무한 대기**에 빠집니다. `dontAsk`는 애초에 묻지 않고 거부하므로 실행이 즉시 중단되고, CI 잡은 명확히 실패합니다. "허용 목록 + 그 외 전부 거부"라는 화이트리스트 보안 모델이기도 합니다.

각 대안이 "읽기 전용 최소 집합만 허용, 그 외에는 중단" 요구를 못 맞추는 이유:

- `acceptEdits`는 **쓰기 작업을 자동 승인**하므로 요구와 정반대입니다.
- **턴 수 제한**(`--max-turns 1`)은 에이전트가 몇 번 왕복할지를 제한할 뿐, *어떤* 명령을 실행할 수 있는지는 전혀 통제하지 못합니다. 1턴 안에서도 위험한 명령이 실행될 수 있습니다.
- **프롬프트 + 짧은 타임아웃**은 무의미한 대기 시간을 만들고, 타임아웃이 어긋나면 파이프라인이 블로킹됩니다. 애초에 물어보지 않게 만드는 것이 옳습니다.

### 4.4 `permissions.allow`와 내장 읽기 전용 명령 세트

- `permissions.allow`: 설정 파일(`settings.json`)에 적어두는 허용 규칙 목록. `--allowedTools`와 같은 패턴 문법을 씁니다.
- **내장 읽기 전용 명령 세트**: `ls`, `cat`, `grep` 처럼 상태를 바꾸지 않는다고 판단되는 명령들. 별도 승인 없이 허용되는 기본 안전 집합입니다.

`dontAsk`는 정확히 이 두 집합만 통과시키고 나머지를 막습니다.

## 5. 메모리와 CLAUDE.md

### 5.1 CLAUDE.md란

`CLAUDE.md`는 Claude Code가 **세션 시작 시 자동으로 읽어 들이는 지침 파일**입니다. 매번 반복해서 알려줘야 할 프로젝트 규칙을 여기에 적어둡니다.

```markdown
# 프로젝트 규칙
- 커밋 전 항상 `npm run lint`를 실행할 것
- 테스트는 vitest를 사용
```

계층 구조 (여러 곳에 있을 수 있고 모두 합쳐집니다):

| 위치 | 범위 | Git 공유 |
|---|---|---|
| `~/.claude/CLAUDE.md` | 사용자 전역 (내 모든 프로젝트) | 안 됨 (개인 머신) |
| `<프로젝트>/CLAUDE.md` | 프로젝트 (팀 공유용) | 커밋하면 공유됨 |
| `<프로젝트>/CLAUDE.local.md` | 프로젝트, 개인 전용 | 보통 `.gitignore` 대상 |
| `.claude/rules/*.md` | 규칙 파일 모음 | 커밋하면 공유됨 |

### 5.2 `@` 임포트 문법

`CLAUDE.md` 안에서 `@경로` 라고 쓰면, Claude Code가 **그 파일의 내용을 실제로 읽어 컨텍스트에 넣습니다**. 단순한 링크가 아니라 진짜 삽입입니다.

```markdown
See @README for project overview and @package.json for available npm commands.
```

이렇게 쓰면 `README`와 `package.json`의 **내용 전체**가 세션에 로드됩니다.

### 5.3 임포트를 피하는 방법 — 백틱

문제: 파일 경로를 **사람이 읽으라고 언급만** 하고 싶은데, `@`를 쓰면 자동으로 임포트됩니다. 큰 파일이면 컨텍스트가 낭비됩니다.

해결: **백틱으로 감싸 인라인 코드 스팬으로 만듭니다.**

```markdown
과거 결정 배경은 `@docs/legacy-notes.md` 파일을 참고하세요. (필요할 때만 직접 열어보세요)
```

임포트 파서는 **마크다운 코드 스팬(백틱으로 감싼 인라인 코드)과 펜스드 코드 블록(``` 로 감싼 블록) 안의 내용을 건너뜁니다.** 그래서 백틱 안의 `@경로`는 리터럴 텍스트로 남고, 사람에게는 화면에 그대로 보입니다. 이것이 공식 문서가 안내하는 방식입니다.

통하지 않는 방법들:

- `@ docs/legacy-notes.md` (`@`와 경로 사이에 공백) — 공식적으로 보장된 이스케이프 방식이 아닙니다.
- `@@docs/legacy-notes.md` (`@` 두 번) — Claude Code에 그런 이스케이프 문법은 없습니다.
- `<!-- @docs/legacy-notes.md -->` (HTML 주석) — 주석은 렌더링 시 **보이지 않습니다.** "사람에게 보여주는 안내"라는 목적 자체가 무너집니다.

### 5.4 `/memory` — 무엇이 실제로 로드됐는지 확인하기

`/memory`는 **현재 세션에 어떤 메모리 파일이 실제로 로드되어 있는지 보여주는 슬래시 명령어**입니다. `CLAUDE.md`, `CLAUDE.local.md`, 규칙 파일 목록과 그 내용을 확인할 수 있습니다.

전형적인 활용 상황: 같은 저장소·같은 브랜치인데도 한 사람의 Claude는 "커밋 전 린터 실행" 규칙을 지키고, 다른 사람의 Claude는 그 규칙을 아예 언급조차 하지 않는 경우.

규칙 문구가 모호한지 따지기 **전에**, 그 규칙이 애초에 로드되긴 했는지부터 확인해야 합니다. 두 사람이 각각 `/memory`를 실행해 목록을 비교하면 몇 초 만에 판가름 납니다. 흔한 원인:

- 한쪽의 `CLAUDE.md`가 `.gitignore`에 걸려 있어 애초에 받아지지 않음
- 파일이 서로 다른 디렉터리에 있어 로딩 범위 밖
- 한쪽의 `CLAUDE.local.md`가 프로젝트 규칙을 덮어쓰고 있음
- 실행 위치(작업 디렉터리)가 달라 프로젝트 메모리가 잡히지 않음

무관하거나 우선순위가 낮은 요인들: OS 재부팅은 아무 상관 없습니다(설정 변경은 새 세션이면 반영됩니다). git 이력 삭제 후 재클론은 과도하고 느립니다. Claude Code 버전 차이보다 로컬 메모리 로딩 누락일 확률이 훨씬 높으므로 진단 순서상 뒤입니다.

**일반 원칙: 지시가 안 먹히면 "지시가 나쁜가"보다 "지시가 도착했는가"를 먼저 확인한다.**

## 6. 슬래시 명령어(Slash Command)

### 6.1 개념

슬래시 명령어는 **자주 쓰는 프롬프트를 이름 붙여 저장해 둔 것**입니다. `/release-notes` 라고 입력하면 저장된 지시문이 실행됩니다.

정의 방법은 간단합니다: 디렉터리에 마크다운 파일 하나를 만들면 **파일 이름이 곧 명령어 이름**이 됩니다.

`.claude/commands/release-notes.md`:

```markdown
마지막 태그 이후의 커밋 로그를 읽고,
사용자 관점에서 릴리스 노트를 작성해줘.
Breaking change는 맨 위에 별도 섹션으로 분리할 것.
```

→ `/release-notes` 로 호출됩니다.

### 6.2 스코프: 프로젝트 vs 사용자

| 위치 | 스코프 | 누가 쓸 수 있나 |
|---|---|---|
| `<프로젝트>/.claude/commands/이름.md` | 프로젝트 | 저장소를 클론한 **모든 사람** |
| `~/.claude/commands/이름.md` | 사용자(전역) | **내 머신의 나만**, 대신 내 모든 프로젝트에서 |

`~`(틸데)는 홈 디렉터리를 뜻하며, 여기 둔 설정은 그 개인 머신 밖으로 나가지 않습니다.

### 6.3 팀 배포 — Git이 곧 배포 채널

"팀 전원이 `git pull`만 하면 자동으로 명령어를 갖게 하고 싶다"의 정답은 명확합니다.

**프로젝트의 `.claude/commands/release-notes.md`에 저장하고 그 파일을 저장소에 커밋한다.**

버전 관리 시스템이 배포 메커니즘 역할을 합니다. 팀원이 `git pull` 하면 파일이 함께 내려오고, 별도 설치 절차 없이 `/release-notes`가 즉시 동작합니다.

실패하는 대안들:

- 그 파일을 `.gitignore`에 넣으면 애초에 원격에 올라가지 않아 아무에게도 전달되지 않습니다.
- 팀 리드의 `~/.claude/`에 두면 팀 리드 개인 머신 안에만 존재합니다(그 사람의 모든 프로젝트에는 적용되지만, 남에게는 전달되지 않습니다).
- 팀원에게 파일을 각자 복사하라고 하는 것은 "수동 설치 없이"라는 요구 자체를 위반합니다.

## 7. 스킬(Skill)

### 7.1 스킬이란

스킬은 슬래시 명령어보다 한 단계 더 구조화된 **재사용 가능한 절차 패키지**입니다. 디렉터리 하나에 `SKILL.md` 파일을 두는 형태입니다.

```
.claude/skills/explore-alternatives/SKILL.md     ← 프로젝트 스코프
~/.claude/skills/explore-alternatives/SKILL.md   ← 사용자 전역 스코프
```

`SKILL.md`는 **프론트매터(frontmatter)** — 파일 맨 위의 `---` 사이에 들어가는 YAML 메타데이터 — 로 동작을 설정합니다.

```markdown
---
name: explore-alternatives
description: 여러 아키텍처 대안을 비교한 뒤 하나를 추천한다
context: fork
---

경쟁하는 접근 방식을 3개 이상 도출하고,
각각의 트레이드오프를 검토한 뒤 최종 권고안 하나를 제시하라.
```

### 7.2 `context: fork` — 스킬을 서브에이전트에서 실행하기

`context: fork`를 지정하면 그 스킬은 **메인 대화가 아니라 별도의 서브에이전트 안에서 실행**됩니다.

- 중간 과정(브레인스토밍, 후보 비교, 폐기된 안, 주고받는 탐색 대화)은 **전부 서브에이전트 컨텍스트에 머무릅니다.**
- 메인 대화에는 **최종 반환 결과만** 올라옵니다.

이것이 앞서 1.3절에서 본 서브에이전트 위임을, 스킬 정의 수준에서 선언적으로 켜는 방법입니다. 탐색적이고 장황한 작업(대안 브레인스토밍, 대규모 조사, 리서치)에 적합합니다.

### 7.3 다른 프론트매터 옵션들과의 구분

혼동하기 쉬운 옵션들을 정리합니다. **이들은 컨텍스트 분리와 무관합니다.**

| 옵션 | 하는 일 | 컨텍스트 분리? |
|---|---|---|
| `context: fork` | 서브에이전트에서 실행, 결과만 반환 | **예** |
| `user-invocable: false` | 사용자가 직접(슬래시 명령 등으로) 호출하지 못하게 막음. 모델만 내부적으로 사용 | 아니요 |
| `disable-model-invocation: true` | 반대로, 모델이 알아서 자동 호출하지 못하게 막음. 사람이 직접 칠 때만 발동 | 아니요 |
| `paths: **/*` | 어떤 파일 경로에서 이 스킬이 관련되는지 지정하는 매칭 패턴 (활성화 조건) | 아니요 |

정리하면 `user-invocable`과 `disable-model-invocation`은 **"누가 호출할 수 있는가"** 를, `paths`는 **"언제 관련되는가"** 를, `context`는 **"어디서 실행되는가"** 를 다룹니다. 네 가지는 서로 다른 축입니다.

## 8. 헤드리스 실행과 자동화

### 8.1 `claude -p` (print / 헤드리스 모드)

`-p`(또는 `--print`)는 Claude Code를 **대화형 UI 없이 한 번 실행하고 결과를 출력한 뒤 종료**하게 만듭니다. 스크립트, cron 잡(야간 배치), CI 파이프라인, 봇에서 쓰는 형태입니다.

```bash
claude -p "run the migration script" --allowedTools "Bash(npm run migrate)"
```

### 8.2 주요 CLI 옵션과 그 실제 효과

각 옵션이 **정확히 무엇을 하고, 무엇을 하지 않는지**를 아는 것이 중요합니다.

| 옵션 | 하는 일 | 흔한 오해 |
|---|---|---|
| `-p / --print` | 비대화형 1회 실행 | — |
| `--allowedTools` | 자동 승인할 도구/명령 패턴 지정 | 패턴 끝 `*`는 접두사 매칭이라 범위가 넓어짐 |
| `--max-turns` | 에이전트가 돌 수 있는 최대 턴(왕복) 수 제한 | **보안 통제 수단이 아님.** 어떤 명령을 실행할지는 제어 못 함. 늘린다고 PR 댓글을 스스로 읽어오지도 않음 |
| `--output-format` | 출력 형식 (`text`, `json`, `stream-json`) | 형식만 바꿀 뿐, **없던 로직을 만들어주지 않음** |
| 권한 모드 설정 | `dontAsk` / `acceptEdits` 등 | 4.3절 참조 |

`--max-turns`의 용도는 폭주 방지와 비용 상한이지 권한 통제가 아닙니다. `--output-format`의 `stream-json`은 결과를 점진적으로 흘려보내는 것일 뿐, "기존 댓글과 대조해서 중복을 거른다" 같은 판단 로직은 여전히 **누군가 짜야 합니다.**

### 8.3 상태 없음(Statelessness) 문제

헤드리스 실행은 기본적으로 **매번 아무것도 기억하지 못한 채 시작**합니다. 이것이 자동화 봇의 대표적 함정입니다.

**시나리오**: PR에 새 커밋이 올라올 때마다 리뷰 봇이 재실행됩니다. 작성자가 null 체크 누락을 아직 고치지 않았으므로, 봇은 매번 같은 결함을 새로 발견하고 **같은 인라인 댓글을 중복 게시**합니다.

원인은 명확합니다. 봇은 자신이 이전 실행에서 이미 그 지적을 했다는 사실을 **모릅니다.** 코드는 그대로이니 결함도 그대로 검출되는 것이 당연합니다.

### 8.4 해결책 — 이전 결과를 컨텍스트에 주입하기

**해결의 핵심: 이전 실행의 발견 사항(prior findings)을 새 실행의 프롬프트/컨텍스트에 넣어주고, 중복을 제외하라고 명시적으로 지시한다.**

```bash
PRIOR=$(gh pr view "$PR" --json comments -q '.comments[].body')

claude -p "이 PR의 변경 사항을 리뷰하라.

아래는 이전 실행에서 이미 보고한 지적 사항이다:
---
$PRIOR
---
위 목록에 이미 존재하는 지적은 다시 보고하지 말고,
새로 발견된 사항만 보고하라."
```

일반화하면: **상태 없는 에이전트에게 상태가 필요하면, 그 상태를 명시적으로 넘겨줘야 한다.** 모델이 알아서 이전 실행을 기억하거나 PR 댓글을 조회해 주지 않습니다.

작동하지 않는 접근들:

- **턴 수를 늘린다** — 봇이 알아서 PR 댓글을 읽으러 가지 않습니다. 필요한 것은 턴이 아니라 정보와 지시입니다.
- **세션 지속성을 끈다** — 기억을 더 지우는 방향이므로 중복이 줄기는커녕 정반대입니다.
- **출력 형식을 바꾼다** — 대조·필터링 로직이 저절로 생기지 않습니다.

## 9. 전체를 관통하는 원칙 정리

1. **컨텍스트는 유한한 자원이다.** 크고 버려질 산출물(대규모 조사)은 서브에이전트로 격리하고 결론만 받는다.
2. **단계 사이에는 문서를 둔다.** 대화 기록이 아니라 자립형 스펙이 단계 간 전달 매체다.
3. **모호함을 남기지 않는다.** 인터뷰로 요구사항을, 입출력 예시로 버그 정의를 확정한다.
4. **권한은 화이트리스트로.** 자동화 환경에서는 묻지 말고 거부(`dontAsk`)하고, 패턴은 필요한 만큼만 좁게 쓴다.
5. **팀 공유는 저장소를 통해.** 프로젝트 `.claude/` 디렉터리에 두고 커밋하면 그것이 곧 배포다.
6. **상태 없는 실행에는 상태를 주입한다.** 기억이 필요하면 명시적으로 넘긴다.
7. **진단은 "전달됐는가"부터.** 지시가 안 먹히면 지시문을 의심하기 전에 로딩 여부를 확인한다.
8. **옵션의 실제 의미를 안다.** 이름이 그럴듯하다고 원하는 일을 해주지 않는다(`--max-turns`, `--output-format`, `paths`).

## 10. 용어 사전 (Glossary)

| 영어 용어 | 한국어 설명 |
|---|---|
| **Context Window** | 모델이 한 번에 처리할 수 있는 텍스트 총량. 토큰 단위로 제한되며, 다 차면 정보가 잘리고 비용·지연이 증가한다. |
| **Token** | 모델이 텍스트를 세는 단위. 대략 단어 조각 하나. |
| **Context Pollution / Noise** | 현재 작업과 무관한 내용이 컨텍스트에 쌓여 모델 판단을 흐리는 현상. |
| **Session** | 하나의 이어지는 대화 단위. 컨텍스트가 유지되는 범위. |
| **Fresh Session** | 컨텍스트가 비어 있는 새 대화 세션. 단계 전환 시 노이즈를 끊기 위해 사용한다. |
| **Subagent** | 메인 대화와 분리된 자체 컨텍스트를 가진 보조 에이전트. 작업을 위임받아 수행하고 결과만 반환한다. |
| **Explore Subagent** | 넓은 범위의 코드 탐색·조사에 특화된 읽기 전용 서브에이전트. |
| **Direct Execution** | 위임 없이 메인 에이전트가 직접 수행하는 것. 좁고 확실한 작업에 적합. |
| **Broad Investigation** | 넓은 조사. 파일 수십 개를 읽어 흐름을 파악하는 단계. 위임 대상. |
| **Narrow Implementation** | 좁은 구현. 파일 하나에 필드 하나 추가 같은 작은 수정. 직접 실행 대상. |
| **Plan Mode** | 파일을 변경하기 전에 계획을 먼저 세우고 검토받는 모드. 컨텍스트 소모를 줄여주지는 않으며, 사소한 단일 수정에까지 쓰면 과잉이다. |
| **AskUserQuestion** | Claude Code가 사용자에게 선택지 있는 질문을 던지는 도구. 요구사항 인터뷰에 사용. |
| **Requirements Elicitation** | 요구사항 도출. 모호한 요청을 질문으로 파고들어 구체적 결정 사항으로 바꾸는 과정. |
| **Spec (Specification)** | 명세서. 무엇을 만들지 확정해 적은 문서. |
| **Self-contained Spec** | 자립형 명세서. 그 문서만 읽고도 구현 가능한, 외부 대화 맥락에 의존하지 않는 스펙. |
| **Spec-driven Development** | 스펙을 먼저 확정하고 그것을 기준으로 구현하는 개발 방식. |
| **Transcript** | 대화 기록 원문. 길고 정제되지 않아 스펙을 대체할 수 없다. |
| **Interface** | 인터페이스. 함수 시그니처·타입·엔드포인트 등 모듈 간 계약. 스펙에 명시해야 할 항목. |
| **Schema** | 데이터의 구조 정의(필드 이름·타입·관계). 데이터 모양은 알려주지만 비즈니스 의도는 담지 않는다. |
| **Ranking** | 검색 결과의 정렬·순위 규칙. |
| **Filtering** | 결과를 조건으로 걸러내는 규칙. |
| **Failure Mode** | 실패 모드. 시스템이 잘못될 수 있는 방식(타임아웃, 0건, 인덱스 다운 등)과 그때의 동작. |
| **Edge Case** | 에지 케이스. null, 빈 값, 0, 경계값 등 정상 경로 밖의 조건. |
| **Few-shot Prompting** | 구체적인 입력–출력 예시를 함께 제시해 모델의 동작을 유도하는 프롬프팅 기법. |
| **Test Case** | 입력과 기대 출력의 쌍. 버그를 모호함 없이 전달하는 가장 좋은 형식이자 회귀 방지 수단. |
| **Migration Script** | 기존 데이터를 새 스키마 형태로 변환해 옮기는 스크립트. |
| **`claude -p` / Headless Mode** | 대화형 UI 없이 1회 실행 후 종료하는 실행 방식. 스크립트·CI·봇용. |
| **Non-interactive Environment** | 비대면 환경. 권한 프롬프트에 답할 사람이 없는 CI 등의 실행 환경. |
| **CI Runner** | CI 파이프라인에서 작업을 실행하는 머신/프로세스. 사람이 상주하지 않는다. |
| **`--allowedTools`** | 프롬프트 없이 자동 승인할 도구/명령 패턴을 지정하는 CLI 옵션. |
| **Prefix Matching** | 접두사 매칭. 패턴 끝의 `*`로 인해 해당 문자열로 *시작하는* 모든 명령이 매칭되는 방식. |
| **Glob / Wildcard** | `*` 등을 쓰는 단순 패턴 매칭 문법. 정규표현식과 다르다. |
| **Regex Alternation** | 정규식의 `|` 를 이용한 택일 표현. `--allowedTools`가 쓰는 방식이 *아니다*. |
| **`Bash(...)`** | 셸 명령 실행 도구에 대한 권한 패턴 표기 형식. |
| **Auto-approve** | 자동 승인. 프롬프트 없이 실행이 허용되는 것. |
| **Permission Mode** | 권한 모드. 규칙에 없는 요청을 만났을 때의 기본 대응 방식. |
| **`dontAsk`** | 프롬프트 없이, 허용 규칙과 내장 읽기 전용 세트 밖의 모든 것을 즉시 거부하는 권한 모드. 자동화 환경용. |
| **`acceptEdits`** | 파일 쓰기 등 일반 작업을 자동 승인하는 권한 모드. 읽기 전용 잠금 요구와는 상충한다. |
| **`permissions.allow`** | 설정 파일에 기록하는 허용 규칙 목록. |
| **Built-in Read-only Command Set** | `ls`, `cat`, `grep` 등 상태를 바꾸지 않아 기본 허용되는 내장 명령 집합. |
| **`--max-turns`** | 에이전트의 최대 턴(왕복) 수 제한. 폭주·비용 방지용이며 권한 통제 수단이 아니다. |
| **`--output-format`** | 출력 형식 지정(`text` / `json` / `stream-json`). 형식만 바꾸며 로직을 추가하지 않는다. |
| **`stream-json`** | 결과를 JSON 이벤트로 점진적으로 흘려보내는 출력 형식. |
| **`CLAUDE.md`** | Claude Code가 세션 시작 시 자동으로 읽는 프로젝트/사용자 지침 파일. |
| **`CLAUDE.local.md`** | 개인 전용 메모리 파일. 보통 Git에서 제외되며 팀에 공유되지 않는다. |
| **`.claude/rules/`** | 규칙 파일들을 모아두는 디렉터리. |
| **Memory (Claude Code)** | 세션에 자동 로드되는 지침 파일들의 총칭. |
| **`@` Import** | `CLAUDE.md` 등에서 `@경로`로 다른 파일의 *내용 전체*를 컨텍스트에 불러오는 문법. |
| **Code Span** | 백틱으로 감싼 인라인 코드. 임포트 파서가 건너뛰므로 `@` 임포트를 막는 데 쓰인다. |
| **Fenced Code Block** | 백틱 세 개로 감싼 코드 블록. 역시 임포트 파싱에서 제외된다. |
| **Literal Text** | 해석되지 않고 글자 그대로 남는 텍스트. |
| **`/memory`** | 현재 세션에 실제로 로드된 메모리 파일들을 확인하는 슬래시 명령어. 지침 로딩 문제 진단용. |
| **Slash Command** | `/이름` 으로 호출하는 저장된 프롬프트. `.claude/commands/이름.md` 파일로 정의한다. |
| **Project Scope** | 프로젝트 범위. `<프로젝트>/.claude/` 에 두어 저장소를 공유하는 모두에게 적용되는 설정. |
| **User Scope / Global Scope** | 사용자(전역) 범위. `~/.claude/` 에 두어 그 개인 머신의 모든 프로젝트에 적용되나, 남에게 공유되지 않는다. |
| **`.gitignore`** | Git이 추적하지 않을 파일을 지정하는 목록. 여기에 넣으면 팀에 공유되지 않는다. |
| **Skill** | `SKILL.md`로 정의하는 재사용 가능한 절차 패키지. 프론트매터로 동작을 설정한다. |
| **`SKILL.md`** | 스킬 정의 파일. 스킬 디렉터리 안에 위치한다. |
| **Frontmatter** | 마크다운 파일 최상단 `---` 사이의 YAML 메타데이터 블록. |
| **`context: fork`** | 스킬을 서브에이전트에서 실행해 중간 과정을 격리하고 최종 결과만 메인 대화로 반환하게 하는 설정. |
| **`user-invocable: false`** | 사용자가 직접 호출하지 못하게 막는 설정(모델 내부 전용). 컨텍스트 분리와 무관. |
| **`disable-model-invocation: true`** | 모델의 자동 호출을 막고 사람이 직접 부를 때만 실행되게 하는 설정. 컨텍스트 분리와 무관. |
| **`paths:`** | 스킬이 어떤 파일 경로에서 관련되는지 지정하는 매칭 패턴. 활성화 조건이지 실행 위치 설정이 아니다. |
| **Statelessness** | 상태 없음. 헤드리스 실행이 매번 아무 기억 없이 시작하는 성질. |
| **Session Persistence** | 세션 지속성. 이전 실행의 상태를 이어받는 기능. 끄면 기억이 더 사라진다. |
| **Prior Findings** | 이전 실행에서 보고된 발견 사항. 중복 방지를 위해 새 실행 컨텍스트에 주입한다. |
| **Contextual Deduplication** | 이전 결과를 컨텍스트에 넣고 "중복은 제외하라"고 지시해 반복 출력을 막는 기법. |
| **Inline Comment (PR)** | PR의 특정 코드 줄에 다는 댓글. 봇이 중복 게시하기 쉬운 대상. |
| **PR (Pull Request)** | 코드 변경 사항을 병합하기 위해 올리는 요청. 리뷰가 붙는 단위. |
