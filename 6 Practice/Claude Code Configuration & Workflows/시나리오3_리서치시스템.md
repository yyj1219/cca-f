# 시나리오3_리서치시스템

## 질문 1

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : An engineer maintaining this system asks Claude Code to trace how the coordinator routes tasks. Discovery output (file listings, grep results) is rapidly consuming the main context window. What should the engineer do?


**A(정답).** Delegate the search to the Explore subagent, which holds the verbose output in its own context and returns a summary.

**설명**

정답이다. Explore는 코드베이스 검색과 분석에 최적화된 내장 읽기 전용 서브에이전트로, 별도의 컨텍스트 윈도우에서 동작하기 때문에 원본 파일 목록과 검색 결과가 메인 대화에 유입되지 않고, 정제된 요약만 돌아온다. 이를 통해 메인 컨텍스트를 실제 유지보수 작업을 위해 보존할 수 있다.

**B.** Run /compact after each discovery phase so the accumulated search output is summarized within the same session.

**설명**

압축(compaction)은 복구 메커니즘일 뿐 격리 메커니즘이 아니다. 방대한 출력이 먼저 메인 컨텍스트에 유입되고, 요약 과정에서 파일 경로나 정확한 일치 결과 같은 세부 정보가 손실될 위험이 있다. 탐색 작업을 위임하면 오염 자체를 애초에 막을 수 있는데, 이는 반복적으로 정리하는 것과 다르다.

**C.** Switch to plan mode so the investigation proceeds read-only and produces a plan instead of verbose output.

**설명**

플랜 모드는 Claude가 변경을 수행할 수 있는지 여부를 통제하는 것이며, 탐색 출력이 어디에 쌓이는지와는 무관하다. 메인 세션에서 읽기 전용으로 조사를 진행해도 동일한 파일 목록과 검색 결과가 그대로 메인 컨텍스트 윈도우를 채운다.

**D.** Use /clear once the window fills, then restate the findings gathered so far and continue the investigation.

**설명**

대화를 지우면 누적된 노이즈뿐 아니라 지금까지 파악한 이해까지 모두 사라져, 엔지니어가 창이 찰 때마다 수동으로 findings를 다시 구성해야 한다. 이는 탐색 출력을 처음부터 메인 컨텍스트 밖에 두는 것이 아니라 증상을 반복적으로 처리하는 방식일 뿐이다.

### 전반적인 설명

Claude Code의 Explore 서브에이전트는 바로 이런 실패 양상을 위해 존재한다. 코드베이스 탐색은 본질적으로 대용량 작업이다. 라우팅 경로를 추적한다는 것은 디렉터리를 글롭하고, 호출 지점을 grep하고, 대부분 다시 참조되지 않을 파일 내용을 읽는 일이다. 모든 서브에이전트가 자신만의 컨텍스트 윈도우에서 실행되기 때문에, 검색을 Explore에 위임하면 그 원본 출력 전체가 서브에이전트의 컨텍스트에 쌓이고 메인 대화는 관련 요약만 받게 된다. Explore는 빠르고 읽기 전용인 에이전트이며(Write와 Edit는 거부됨), Claude는 작업에 맞춰 문서화된 철저함 수준(quick, medium, very thorough)을 선택한다. 또한 연구에 집중하기 위해 CLAUDE.md 파일은 건너뛴다.

여기서의 핵심 사고 모델은 예방과 복구의 차이다. /compact와 /clear는 방대한 출력이 이미 메인 윈도우를 가득 채운 뒤에 작동한다. 압축은 손실이 있는 요약이라서(정확한 숫자, 경로, 세부 사항이 누락될 수 있다) 위험하고, 지우기는 학습된 컨텍스트를 완전히 버린다. 플랜 모드는 이와는 별개의 축이다. 세션을 읽기 전용으로 만들고 승인된 플랜 뒤로 편집을 미루지만, 탐색 출력의 모든 바이트는 여전히 메인 컨텍스트에 쌓인다. 서브에이전트로의 위임만이 유용한 결론을 유지하면서 노이즈를 메인 대화 밖에 두는 유일한 방법이다. 내장 Explore 에이전트와 대용량 작업을 위임해 요약만 반환받는 일반적인 패턴에 대해서는 Claude Code의 Subagents 문서를 참고하라.

## 질문 2

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : Claude Code's implementation of the citation normalizer for the report generator keeps mishandling edge cases (missing authors, duplicate DOIs) despite several rewrites of the prose specification. Which refinement approach most reliably drives progressive improvement?

**A.** Add the full citation formatting specification to CLAUDE.md so every session loads the rules automatically.

**설명**

오답이다. CLAUDE.md는 규칙이 컨텍스트에 존재하도록 보장할 뿐, 그 규칙은 여전히 Claude가 일관되지 않게 해석할 수 있는 프롬프트 형태의 지침으로 남는다. 모호한 스펙을 지속적으로 로드하는 것만으로는 점진적 개선에 필요한 검증과 실패 피드백을 제공하지 못한다.

**B.** Rewrite the specification with IMPORTANT markers on the edge-case rules so the model prioritizes them.

**설명**

오답이다. 강조 표시는 주변 텍스트에 대한 상대적 우선순위만 높일 뿐, 프롬프트 규칙 자체의 근본적인 모호성을 해결하지 못한다. 시나리오는 이미 프롬프트 개선이 실패했음을 보여주므로, 더 강한 강조 표현이라고 해서 정확성을 이끌어내는 구체적인 피드백 루프가 생기지는 않는다.

**C.** Switch to plan mode so the approach is reviewed and approved before any code is written.

**설명**

오답이다. 플랜 모드는 실행 전에 크거나 아키텍처적으로 모호한 변경의 범위를 정하는 데 도움이 되지만, 여기서 문제는 특정 엣지 케이스에 대한 정확성 격차이며 구현 방식이 불명확한 것이 아니다. 검토된 플랜이 있어도 무언가가 검증하기 전까지는 엣지 케이스 동작이 여전히 확인되지 않은 채로 남는다.

**D(정답).** Write a test suite for expected behavior and edge cases first, then share failing test output to iterate.

**설명**

정답이다. 테스트 주도 반복은 모호한 기대치를 구체적이고 검증 가능한 목표로 전환한다. 테스트가 엣지 케이스를 명시적으로 인코딩하고, 각 실패한 테스트는 Claude에게 다음에 무엇을 고쳐야 하는지에 대한 정확하고 명확한 피드백을 제공한다. 이는 프롬프트를 다시 해석하는 또 한 번의 시도가 아니라 측정 가능한 수렴을 만들어낸다.

### 전반적인 설명

이런 유형의 문제에 권장되는 기법은 테스트 주도 반복이다. 구현에 앞서 예상 동작, 알려진 엣지 케이스(저자 누락, 중복 DOI), 그리고 성능 요구 사항을 명확히 규정하는 테스트 스위트를 작성한다. 그런 다음 Claude가 테스트를 기준으로 구현하게 하고, 매 라운드마다 실패한 테스트 출력을 공유한다. 각 실패는 무엇이 여전히 잘못되었는지를 정확하고 기계적으로 확인 가능한 형태로 알려주므로, 요구 사항을 또 다르게 바꿔 말하는 것보다 훨씬 실행 가능하다.

여기서의 사고 모델은 프롬프트 스펙은 해석되지만 테스트는 검증된다는 것이다. 스펙을 반복적으로 다시 작성해도 엣지 케이스 처리가 계속 일관되지 않게 나온다면, 병목은 주의력이나 강조의 문제가 아니라 요구 사항에 실행 가능한 근거(ground truth)가 없다는 점이다. 테스트가 바로 그 근거를 제공하며, 실패를 기반으로 반복하면 수렴이 일어난다. 진행 상황이 측정 가능하기 때문이다. 즉 실패 집합이 매 회차마다 줄어들고, 회귀는 즉시 잡힌다.

오답 선택지들은 각각 다른 문제를 다룬다. IMPORTANT 같은 강조 표시는 다른 지침에 상대적으로 배분되는 예산일 뿐이며 규칙 자체의 모호성을 없애지 못한다. 플랜 모드는 크고 여러 파일에 걸친 변경이거나 여러 아키텍처 방식이 경쟁할 때 가치가 있지만, 정확성 격차가 있는 독립적인 정규화 모듈은 커밋 전 설계로부터 이득을 얻지 못하며 검증으로부터 이득을 얻는다. CLAUDE.md를 통해 스펙을 로드하면 매 세션마다 규칙이 컨텍스트에 있음을 보장하지만, 그 규칙은 여전히 모델이 확률적으로 따르는 가이드일 뿐, 실패를 잡아내는 검사가 아니다.

테스트 주도 워크플로에 대한 안내는 Claude Code 모범 사례(best practices)와 일반 워크플로(Common workflows) 문서를 참고하라.

## 질문 3

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : While building the coordinator's prompts, a developer wrote the team's citation formatting and report structure conventions into ~/.claude/CLAUDE.md, but teammates report their Claude Code sessions never apply them. What should the developer do?

**A.** Add the conventions to the committed .claude/settings.json so every teammate's sessions apply them.

**설명**

오답이다. settings.json은 권한이나 도구 설정 같은 구성 정보를 담는 파일이며, 프롬프트 형태의 지침이나 컨벤션을 담는 곳이 아니다. 그곳에 컨벤션을 커밋해도 Claude Code가 이를 CLAUDE.md 내용처럼 가이드로 취급하지는 않는다.

**B(정답).** Move the conventions into a project-level CLAUDE.md at the repository root and commit it to version control.

**설명**

정답이다. ~/.claude/CLAUDE.md는 사용자 수준 메모리로, 해당 개발자의 머신에만 적용되며 저장소를 통해 배포되지 않는다. 프로젝트 수준 CLAUDE.md는 팀 공유 지침을 위한 문서화된 메커니즘으로, 팀원이 클론하거나 풀할 때 저장소와 함께 전달된다.

**C.** Copy the conventions into ./CLAUDE.local.md in the repository so each teammate's sessions load them automatically.

**설명**

오답이다. CLAUDE.local.md는 개인적인 프로젝트별 지침을 위한 것으로, .gitignore를 통해 버전 관리 대상에서 제외되는 것이 원칙이다. 팀 전체가 공유해야 하는 컨벤션에는 맞지 않는 위치다.

**D.** Have each teammate run /memory at the start of a session to import the developer's user-level conventions.

**설명**

오답이다. /memory는 로컬 머신에 로드된 메모리 파일을 보고 편집하는 명령이며, 다른 사용자의 홈 디렉터리 파일을 가져올 수 없다. 팀원들의 세션은 해당 개발자의 ~/.claude/CLAUDE.md를 전혀 보지 못하므로, /memory가 가져올 대상 자체가 없다.

### 전반적인 설명

Claude Code 메모리는 범위(scope)별로 구성되며, 그 범위가 누구에게 전달되는지를 결정한다. ~/.claude/CLAUDE.md 파일은 사용자 수준 메모리로, 개발자의 홈 디렉터리에 있으며 그 개발자가 모든 프로젝트에서 시작하는 모든 세션에 로드되고, 문서에는 "본인만 공유"되는 것으로 명시되어 있다. 저장소 밖에 위치하기 때문에 git이 이를 인식하지 못하며, 프로젝트 작업을 푸시해도 이 파일은 배포되지 않는다. 여기서의 사고 모델은 두 축의 구분이다. 홈 디렉터리는 개인용, 저장소는 공유용이며, 팀 전체가 따라야 할 것은 버전 관리가 전달할 수 있는 저장소 안에 있어야 한다.

해결책은 인용 및 보고서 컨벤션을 프로젝트 수준 CLAUDE.md(저장소 루트 또는 .claude/CLAUDE.md)에 두고 커밋하는 것이다. 그러면 모든 팀원이 클론하거나 풀한 후 별도의 머신별 설정 없이 동일한 컨벤션을 자동으로 로드한다. 오답 선택지들은 각각 공유 체인을 끊는다. CLAUDE.local.md는 개인용 프로젝트별 메모를 위해 존재하며 .gitignore에 속해야 한다. .claude/settings.json은 커밋되는 파일이지만 권한과 도구 설정을 구성할 뿐 지침 프롬프트 역할을 하지 않는다. 그리고 /memory는 세션이 이미 로드한 메모리 파일에 대한 로컬 진단 및 편집 명령이지, 다른 사용자의 홈 디렉터리 구성을 가져오는 메커니즘이 아니다.

메모리 위치와 각각의 공유 범위에 대한 전체 설명은 Manage Claude's memory 문서를, JSON 설정 파일에 무엇이 들어가야 하는지는 Claude Code settings 문서를 참고하라.

## 질문 4

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : A developer copies a team's draft-report project skill to ~/.claude/skills/draft-report/ to customize it personally. They want to invoke their variant as /report-helper while leaving the team's /draft-report command untouched. What should they do?

**A.** Restart Claude Code so the session re-reads the frontmatter and registers /report-helper as the command.

**설명**

오답이다. 스킬 디렉터리는 로컬 세션 동안 감시되므로, 일반적인 경우 재시작 없이도 변경 사항이 반영된다. 더 근본적으로는, 재시작을 하더라도 /report-helper가 작동하지는 않는다. 개인 스킬에서는 프런트매터의 name 필드가 명령어 이름이 되지 않기 때문이다.

**B(정답).** Rename the personal skill directory to ~/.claude/skills/report-helper/, keeping SKILL.md inside it.

**설명**

정답이다. 개인 스킬과 프로젝트 스킬의 슬래시 명령어는 스킬의 디렉터리 이름에서 파생되므로, report-helper라는 이름의 디렉터리는 /report-helper를 만들어낸다. 이름을 바꾸면 개인용 draft-report 스킬이 팀의 동명 프로젝트 스킬을 덮어쓰는 이름 충돌 문제도 함께 해소된다.

**C.** Move the variant into the project's .claude/skills/report-helper/ directory so the new command is recognized.

**설명**

오답이다. 변형본을 프로젝트 범위에 두면 개인화의 목적 자체가 무의미해진다. 프로젝트 스킬은 버전 관리에 커밋될 수 있어 결국 팀원들에게도 나타나게 되기 때문이다. 개인 워크플로는 ~/.claude/skills/ 아래에 별도의 디렉터리 이름으로 두어야 한다.

**D.** Set name: report-helper in the SKILL.md frontmatter, which changes the command that invokes the skill.

**설명**

오답이다. 개인 스킬과 프로젝트 스킬에서는 프런트매터의 name 필드가 표시 라벨만 바꿀 뿐, 호출 가능한 명령어를 바꾸지는 않는다. 명령어는 여전히 /draft-report로 남고, 개인 스킬이 이름 충돌 시 우선권을 가지므로 팀의 프로젝트 스킬을 계속 가리게 된다.

### 전반적인 설명

Claude Code 스킬은 SKILL.md 파일을 담은 디렉터리이며, 개인 스킬(~/.claude/skills/)과 프로젝트 스킬(.claude/skills/) 모두에서 호출 가능한 슬래시 명령어는 프런트매터의 어떤 필드가 아니라 디렉터리 이름에서 파생된다. ~/.claude/skills/report-helper/SKILL.md에 있는 스킬은 /report-helper로 호출된다. 프런트매터의 name 필드는 표시 라벨만 바꿀 뿐 명령어 결정에는 전혀 관여하지 않는다.

디렉터리 이름은 여기서 두 가지 역할을 한다. 명령어를 결정하는 것 외에도 충돌 해소 규칙을 좌우한다. 서로 다른 레벨의 스킬이 같은 이름을 공유할 때 우선순위는 enterprise > personal > project 순으로 적용된다. 따라서 개인용 draft-report 스킬은 팀의 프로젝트 스킬을 조용히 덮어쓰게 되며, 이 때문에 개인 변형본에는 공유 이름을 재사용하지 말고 별도의 디렉터리 이름을 부여하라는 것이 문서화된 패턴이다.

다른 선택지들은 핵심 메커니즘을 놓치고 있다. 프런트매터를 편집하면 라벨만 바뀔 뿐 명령어 문제와 가림(shadowing) 문제가 그대로 남는다. 재시작은 불필요하다. 스킬 디렉터리는 로컬 세션 중 감시되기 때문이다(재시작이 필요한 경우는 세션 시작 시 최상위 스킬 디렉터리 자체가 존재하지 않았을 때뿐이다). 그리고 재시작으로는 표시 라벨을 명령어로 바꿀 수 없다. 변형본을 프로젝트 범위로 옮기면 명령어는 작동하지만, 커밋되어 공유될 수 있는 위치에 개인 워크플로를 두게 되어, 정작 개인화하려던 대상인 팀원들에게 영향을 주게 된다. 명령어 이름 결정과 우선순위 규칙에 대해서는 Claude Code 스킬 문서를 참고하라.

**QUESTION** : Subagent prompt templates in this system live as *.prompt.md files scattered across a dozen packages. Conventions for writing these templates should load automatically whenever one is edited. What is the most maintainable configuration?

**A.** Add a CLAUDE.md beside the templates in every package directory, keeping each copy synchronized as conventions change.

**설명**

하위 디렉터리의 CLAUDE.md 파일은 디렉터리에 종속되어 트리 탐색을 통해 로드되므로, 열두 곳에 흩어진 위치를 다루려면 열두 개의 중복 파일이 필요해진다. 컨벤션이 바뀔 때마다 모든 곳에 동일하게 반영해야 하는데, 이것이 바로 경로 범위 규칙이 피하려는 유지보수 부담이다.

**C(정답).** Add a .claude/rules/ file with a paths frontmatter glob matching **/*.prompt.md so the conventions load for those files.

**설명**

정답이다. .claude/rules/의 경로 범위 규칙은 글롭 패턴을 기준으로 활성화되며, 트리 상 위치와 무관하게 일치하는 파일을 다룰 때만 로드된다. 중앙에서 관리되는 단 하나의 파일로 흩어진 모든 템플릿을 커버할 수 있으며, 내용을 중복하거나 무관한 세션에 로드하지 않는다.

**D.** Package the conventions as a skill in .claude/skills/ that developers invoke before editing any template file.

**설명**

스킬은 필요할 때 호출하는 워크플로이므로, 누군가 스킬을 호출하는 것을 기억할 때만 컨벤션이 적용된다. 일치하는 파일이 편집될 때마다 항상 적용되어야 하는 컨벤션에는 자동 로딩이 필요하며, 이는 경로 범위 규칙이 제공하고 스킬은 제공하지 않는 기능이다.

### 전반적인 설명

여기서 결정적인 요소는 파일이 어디에 위치하는가와 메커니즘이 어떻게 활성화되는가의 차이다. 하위 디렉터리 CLAUDE.md 파일은 디렉터리 탐색으로 발견된다. Claude Code는 해당 디렉터리의 하위 트리 안에서 작업할 때 이를 로드한다. 이 모델은 단일 폴더가 소유하는 컨벤션에는 잘 맞지만, 동일한 컨벤션이 여러 패키지에 흩어진 파일에 적용되어야 할 때는 무너진다. 위치마다 사본이 하나씩 필요해지고, 각 사본이 독립적으로 틀어지기 때문이다.

.claude/rules/의 경로 범위 규칙은 이 모델을 뒤집는다. 하나의 마크다운 파일이 YAML 프런트매터에 경로 글롭(예: **/*.prompt.md)을 선언하면, 트리 어디에 있든 일치하는 파일을 Claude가 다룰 때마다 규칙이 활성화된다. 규칙은 정확히 한 곳에서 관리되며, 시작 시점이 아니라 조건에 따라 로드되기 때문에 템플릿을 전혀 건드리지 않는 세션의 컨텍스트 윈도우를 잡아먹지 않는다. Anthropic의 모노레포 가이드는 이 트레이드오프를 명확히 규정한다. 디렉터리 소유자가 자신의 코드와 함께 컨벤션을 관리하는 경우에는 디렉터리별 CLAUDE.md를 사용하고, 동일한 규칙이 여러 흩어진 경로에 적용되는 경우에는 경로 범위 규칙을 사용한다.

다른 선택지들은 메커니즘을 잘못 사용하고 있다. 루트 CLAUDE.md를 통해 모든 것을 로드하는 방식은 동작하지만 컨벤션을 무조건적으로 만들어 모든 세션에 컨텍스트를 추가한다. 문서는 바로 이런 이유로 좁게 관련된 지침을 경로 범위 규칙으로 옮기라고 권장한다. 스킬은 컨벤션을 선택적으로 만드는데, 이는 일치하는 파일이 편집될 때마다 항상 적용되어야 하는 것에는 맞지 않는 계약이다. 스킬은 필요할 때 실행하는 작업 워크플로를 위해 설계된 것이지, 상시 적용되는 컨벤션을 위한 것이 아니다. ## 질문 7

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : A report-generation skill's SKILL.md declares allowed-tools: Write. Files are written without prompts on the invoking turn, but after the user's next message, Write calls prompt again. How should the team handle pre-approval on later turns?

**A.** Rewrite the allowed-tools field as a YAML list rather than a plain string, which makes the grant persist across subsequent turns.

**설명**

오답이다. allowed-tools 필드는 공백으로 구분된 문자열, 쉼표로 구분된 문자열, 또는 YAML 리스트를 받아들이며, 모든 형식이 동일하게 동작한다. 어떤 문법을 쓰더라도 승인 상태가 호출된 턴을 넘어 지속되지는 않는다. 턴 단위 범위는 이 메커니즘에 내재된 특성이다.

**B(정답).** Re-invoke the skill on each turn that writes report files, since the allowed-tools grant clears when the user sends the next message.

**설명**

정답이다. allowed-tools가 부여하는 사전 승인은 스킬이 실행되는 턴에만 적용된다. 사용자가 다음 메시지를 보내면 승인 상태가 초기화되어 Write는 다시 일반적인 권한 동작으로 돌아간다. 스킬을 다시 호출하면 그 새로운 턴에 대해 승인이 다시 적용된다.

**C.** Approve each Write prompt manually, since Write requires interactive confirmation on every call and cannot be pre-approved through frontmatter.

**설명**

오답이다. Write는 기본적으로 권한이 필요하지만, 스킬 프런트매터의 allowed-tools가 바로 이를 사전 승인하는 메커니즘이며, 그래서 호출된 턴에는 프롬프트가 나타나지 않았다. 시나리오 자체가 사전 승인이 정상적으로 동작했음을 보여준다.

**D.** Keep the skill's instructions loaded in the conversation after execution so the permission grant stays active on follow-up turns.

**설명**

오답이다. 스킬 지침은 호출된 턴 이후에도 대화 컨텍스트에 남아있을 수 있지만, 사용자가 다음 메시지를 보내면 권한 승인은 여전히 초기화된다. 승인의 유효 기간은 턴에 묶여 있으며, 지침이 컨텍스트에 남아있는지 여부와는 무관하다.

### 전반적인 설명

SKILL.md 프런트매터의 allowed-tools 필드는 턴 단위로 범위가 정해지는 사전 승인이다. 스킬을 호출한 턴 동안에는 목록에 있는 도구를 권한 요청 없이 사용할 수 있게 하지만, 그 이상은 아니다. 사용자가 다음 메시지를 보내면, 스킬의 지침이 여전히 컨텍스트에 남아있더라도 승인은 초기화된다. 스킬을 다시 호출하면 그 새로운 턴에 대해 승인이 다시 적용된다. 이 설계는 상승된 권한을 세션 전체에 걸친 상시 예외로 남기지 않고, 스킬의 워크플로가 실제로 실행되는 순간에만 단단히 묶어둔다.

allowed-tools가 무엇이고 무엇이 아닌지에 대한 사고 모델도 짚어둘 만하다. 이는 제한이 아니다. 목록에 넣지 않은 도구는 세션의 일반 권한 설정에 따라 여전히 호출 가능하며, 우선순위를 가지는 deny나 ask 규칙을 무효화하지도 않는다. 스킬이 활성화된 동안 도구를 제거해야 한다면 disallowed-tools 필드가 그 역할을 하며, 이 제한 역시 다음 사용자 메시지에서 초기화된다. Read, Grep, Glob 같은 도구는 기본적으로 권한이 필요하지 않으므로 목록에 넣어도 크게 달라지는 것은 없다. 이 승인이 가장 중요한 경우는 평소 프롬프트를 띄우는 Write, Edit, Bash 같은 도구들이다.

오답 선택지들은 각각 잘못된 해결 방향을 제시한다. Write는 분명히 사전 승인될 수 있다(프롬프트 없이 진행된 첫 번째 턴이 이를 증명한다). 그러니 수동 승인으로 되돌아가는 것은 이미 작동하는 메커니즘을 포기하는 것이다. allowed-tools가 허용하는 문법들(공백 구분, 쉼표 구분, YAML 리스트)은 기능적으로 동등하므로 형식을 바꿔도 아무것도 달라지지 않는다. 그리고 승인의 만료는 스킬 지침이 계속 로드되어 있는지와 무관하므로, 컨텍스트에 남겨둔다고 해서 승인이 연장되지는 않는다. 프런트매터 동작과 어떤 도구에 권한이 필요한지에 대해서는 Claude Code Skills 문서와 tools 레퍼런스를 참고하라.

**설명**

Don't ask 모드는 명시적으로 사전 승인되지 않은 도구를 모두 자동으로 거부하는데, 이는 프롬프트에서 절대 멈춰서는 안 되는 무인 CI 파이프라인에 적합하다. 대화형 수정 세션에서는 편집을 가속화하기보다 오히려 막아버리게 된다.

**B.** Use plan mode, which has Claude explore the code and propose the fix before any source file is modified.

**설명**

플랜 모드는 플랜이 승인되기 전까지 읽기 전용으로 유지되므로, 변경 이후가 아니라 이전에 검토 단계를 추가하는 것이다. 스택 트레이스가 명확한 작고 잘 이해된 수정에 대해서는, 문서에 계획 수립이 이득 없이 오버헤드만 추가한다고 명시되어 있다.

**C(정답).** Use accept edits mode, which auto-approves file edits in the working directory for after-the-fact review.

**설명**

정답이다. acceptEdits는 인라인 승인 없이 Claude가 파일을 생성하고 편집하도록 하고, 흔한 파일 시스템 명령도 실행하도록 허용하는 문서화된 모드다. 이는 개발자가 각 편집을 일일이 승인하기보다 결과로 나온 diff를 검토하고 싶어하는, 범위가 명확하고 잘 이해된 수정에 부합한다.

**D.** Use bypass permissions mode, which skips every permission check so the edit lands with no gating at all.

**설명**

Bypass permissions는 편집 승인뿐 아니라 모든 권한 검사를 제거하며, 격리된 컨테이너나 가상 머신 안에서만 사용하도록 권장된다. 범위가 명확한 한 줄짜리 수정에서 승인 프롬프트를 건너뛰는 데 필요한 것보다 훨씬 광범위하다.

### 전반적인 설명

Claude Code의 권한 모드는 매 작업마다 프롬프트에 답하는 대신, 각 행동 범주가 어느 정도의 마찰을 감당해야 하는지를 한 번에 결정할 수 있게 해준다. Accept edits(acceptEdits)는 작업 디렉터리 안에서의 파일 생성과 편집, 그리고 mkdir, mv, rm 같은 흔한 파일 시스템 명령을 자동 승인하는 반면, 다른 행동은 일반적인 권한 검사를 그대로 받는다. 이 프로파일은 잘 이해된 변경을 직접 실행하는 경우에 부합한다. 위험이 낮고 범위가 명확하며, 의미 있는 검토는 각 키 입력 수준의 편집이 아니라 결과로 나온 diff에서 이루어진다.

다른 모드들은 서로 다른 트레이드오프를 만든다. 플랜 모드는 제안된 플랜을 승인하기 전까지 Claude를 읽기 전용으로 유지한다. 모범 사례 가이드는 이를 불확실한 접근 방식, 여러 파일에 걸친 변경, 낯선 코드에 국한해서 사용하도록 권장하며, diff를 한 문장으로 설명할 수 있는 경우에는 계획 수립을 건너뛰라고 명시한다. Don't ask 모드는 무인 파이프라인을 위해 설계되었다. 사전 승인되지 않은 것은 프롬프트 없이 모두 자동 거부되므로, 대화형 세션에서는 편집이 가속화되기보다 막히게 된다. Bypass permissions는 모든 검사를 완전히 비활성화한다. 이는 acceptEdits가 이미 좁게 해결하는 문제를 위해 모든 안전 경계를 거래하는 것이며, Anthropic은 격리된 환경에서만 이를 실행하도록 권고한다.

어떤 모드를 선택하든, 직접 실행 후에는 여전히 검증으로 마무리해야 한다. 성공을 단언하는 대신 Claude에게 관련 테스트를 실행하고 결과를 보여달라고 요청하라. Permission modes와 Claude Code best practices를 참고하라.

### 전반적인 설명

-p(--print) 플래그는 Claude Code를 비대화형으로 실행하게 하지만, 그것만으로는 완전한 무인 실행 전략이 되지 못한다. 권한 처리는 별도의 계층이다. MCP의 --permission-prompt-tool이나 Agent SDK의 canUseTool 콜백처럼 권한 호스트가 구성된 경우, 승인이 필요한 모든 도구 호출은 그 호스트로 라우팅되며 실행은 그 응답을 기다린다. CI 환경에는 그 호스트 뒤에 응답할 무언가가 없으므로, 세션 자체는 헤드리스임에도 실행이 멈추게 된다.

다른 접근 방식들은 잘못된 계층을 대상으로 삼기 때문에 실패한다. stdin에 긍정 응답 텍스트를 흘려 넣어도 승인은 표준 입력을 통해 흐르지 않으므로 권한 호스트에 도달하지 못한다. 출력 형식을 바꾸는 것은 결과 직렬화에만 영향을 주고 승인 흐름에는 영향을 주지 않는다. -p를 제거하는 것은 응답할 사람이 없는 환경에 대화형 세션을 다시 들여옴으로써 상황을 더 악화시킨다. 무인 실행을 위한 전체 구성은 Headless mode와 CLI 레퍼런스를 참고하라.

### 전반적인 설명

여기서의 사고 모델은 CLAUDE.md가 매뉴얼이 아니라 컨텍스트라는 것이다. 그 내용은 모든 세션에 로드되고, 모든 줄이 다른 모든 줄과 모델의 주의를 두고 경쟁한다. 이것이 Anthropic이 각 파일을 대략 200줄 이하로 간결하게 유지하도록 권장하는 이유다. 문서화된 모범 사례는 테스트 지침과 선호하는 테스트 러너를 포함하면서, 긴 튜토리얼, 자명한 관행, 그리고 Claude가 코드 자체에서 추론할 수 있는 세부 사항은 명시적으로 제외하는 것이다. 300줄짜리 프레임워크 튜토리얼은 바로 이 가이드가 막고자 하는 실패 양상이다. 실제로 증상을 고쳐줄 두 가지 사실(어떤 러너를 호출해야 하는지, 픽스처 라이브러리가 어디에 있는지)이 아무것도 더해주지 않는 자료 속에 묻혀 있다.

효과적인 개선안은 생성 과정에서 현재 잘못되고 있는 부분을 정확히 명시한다. 러너 명령, 픽스처 위치, 그리고 좋은 테스트의 기준을, 이상적으로는 모델이 실행하고 반복할 수 있는 실행 가능한 성공/실패 검사 형태로 표현한다. 튜토리얼 내용을 더 추가하는 것은 주의력 문제를 해결하기보다 심화시킨다. 지침을 슬래시 명령으로 옮기는 것은 항상 관련 있는 표준을 선택적 단계로 바꿔버려서, 누군가 잊을 때마다 조용히 실패한다. 규격에 맞지 않는 테스트 작성을 막는 PreToolUse 훅은 강제일 뿐 교육이 아니다. 나쁜 결과물이 반영되는 것을 막을 수는 있지만, 모델은 여전히 좋은 결과물을 만드는 데 필요한 정보가 부족하므로 생성 품질 자체는 개선되지 않는다. 훅은 모델에게 무엇을 알려주었든 관계없이 정책이 반드시 지켜져야 할 때만 적합한 수단이다.

CLAUDE.md에 무엇이 들어가야 하는지는 Claude Code best practices를, 크기 가이드와 메모리 파일 로딩 방식은 Manage Claude's memory를, 결정적 강제가 적합한 경우는 Hooks 문서를 참고하라.

## 질문 11

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : The codebase is a monorepo where each subagent lives in its own package with a package-level CLAUDE.md, and shared standards files sit in a top-level standards/ directory. How should maintainers pull only the standards relevant to their subagent into their package's CLAUDE.md?

**A.** Consolidate all standards files into the root CLAUDE.md so every package inherits the complete set through the additive loading hierarchy.

**설명**

루트 CLAUDE.md는 저장소 어디서든 모든 세션에 로드되므로, 관련성과 무관하게 모든 패키지가 모든 표준을 짊어지게 된다. 이는 선택적 포함이라는 목표를 무너뜨리고, 지금 작업 중인 서브에이전트에 적용되지 않는 지침에 컨텍스트를 낭비하게 된다.

**B.** List each needed standards file's path wrapped in backticks in the package's CLAUDE.md so Claude opens it on demand during the session.

**설명**

백틱은 임포트와 정반대의 효과를 낸다. 임포트 파싱은 마크다운 코드 스팬과 펜스드 코드 블록을 건너뛰므로, 백틱으로 감싼 경로는 그대로 리터럴 텍스트로 취급되어 임포트되지 않는다. 이런 식으로 경로를 언급하는 것만으로는 파일이 열리지 않는다. 실제 임포트는 해당 경로를 담은 CLAUDE.md가 로드될 때 확장된다.

**C.** Copy the text of each relevant standards file directly into every package's CLAUDE.md so no package depends on files outside its own directory.

**설명**

표준 텍스트를 복제하면 드리프트가 생긴다. 공유 표준을 수정할 때마다 각 사본에 수동으로 반영해야 하며, 사본들은 결국 서로 어긋나게 된다. 임포트는 각 패키지가 적용할 항목을 선택할 수 있게 하면서도 단일한 진실의 원천을 유지시켜 준다.

**D(정답).** Add @path imports (for example @../../standards/citations.md) in each package's CLAUDE.md, referencing only the standards files that package needs.

**설명**

이것이 문서화된 메커니즘이다. CLAUDE.md 안의 @path 임포트는 참조된 파일을 컨텍스트로 확장하며, 상대 경로는 임포트하는 파일의 위치를 기준으로 해석된다. 각 패키지 관리자는 자신의 서브에이전트에 적용되는 표준만 정확히 선택하는 반면, 표준 자체는 하나의 권위 있는 위치에 그대로 남는다.

### 전반적인 설명

Claude Code의 @path 임포트 문법은 CLAUDE.md가 다른 파일을 끌어오도록 해주며, 그 파일들은 참조하는 파일과 함께 확장되어 컨텍스트에 로드된다. 모노레포에서는 이것이 패키지별 CLAUDE.md와 자연스럽게 짝을 이룬다. 공유 표준은 중앙 디렉터리에 한 번만 존재하고, 자신의 코드를 실제로 규율하는 컨벤션이 무엇인지 아는 각 패키지의 관리자가 그중 필요한 것만 임포트한다. 반드시 기억해야 할 세부 사항은, 상대 임포트 경로가 작업 디렉터리가 아니라 임포트를 포함한 파일의 위치를 기준으로 해석된다는 점이다. 그래서 패키지 파일 안의 @../../standards/citations.md는 그 패키지의 위치를 기준으로 해석된다.

여기서 중요한 경계가 두 가지 있다. 첫째, 임포트는 조직화 메커니즘이지 컨텍스트 축소 메커니즘이 아니다. 임포트된 파일은 이를 참조하는 CLAUDE.md가 로드될 때마다 확장되며 그 내용이 컨텍스트 윈도우를 차지한다. 따라서 여기서 얻는 이점은 유지보수성과 선택성이며, 토큰 절약이 아니다. 둘째, 임포트 파싱은 코드 스팬과 펜스드 블록을 건너뛴다. 이는 백틱으로 감싼 경로가 의도적으로 리터럴 텍스트로 남겨지는 이유다. 이 기능은 문서가 임포트를 유발하지 않고 경로를 언급할 수 있도록 존재하며, 바로 이 때문에 백틱 방식은 포함 메커니즘으로 작동하지 않는다. 임포트는 재귀도 가능하지만 최대 네 단계까지만 허용된다.

각 패키지에 표준 텍스트를 복제하는 것은 하나의 권위 있는 파일을 여러 개의 어긋나는 사본으로 바꾸는 것이며, 모든 것을 루트 CLAUDE.md로 끌어올리는 것은 선택성을 완전히 포기하는 것이다. 로딩 계층은 가산적(additive)이며 루트 파일은 모든 세션에 도달하기 때문이다. 임포트 문법과 해석 규칙은 Manage Claude's memory를, 패키지별 패턴은 Claude Code in large codebases를 참고하라.

## 질문 12

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : A refactoring task begins with a discovery phase that lists hundreds of call sites with surrounding context, filling the main context window before the design and implementation phases even start. Which approach best preserves context for the later phases?

**A.** Split the work across separate sessions, recording discovered call sites in CLAUDE.md so each new session reloads the findings at startup.

**설명**

CLAUDE.md는 지속적인 프로젝트 컨벤션을 위한 것이며, 작업별로 존재하는 수백 개의 호출 지점을 임시로 쌓아두는 곳이 아니다. 게다가 그곳에 적은 모든 내용은 이후 모든 세션의 컨텍스트에 로드된다. 이 방식은 작업을 조각내고, 결국 모든 대화를 탐색 데이터로 부풀리게 된다.

**B.** Enable plan mode for the discovery phase, since read-only exploration keeps its findings out of the conversation context.

**설명**

플랜 모드는 Claude를 읽기 전용 조사로 제한하고 승인용 플랜을 만들어내지만, 그것이 생성하는 탐색 출력은 여전히 메인 대화에 축적된다. 이는 변경이 이루어지는지 여부를 통제하는 것일 뿐, 방대한 탐색 출력이 어디에 쌓이는지를 통제하지는 않는다.

**C(정답).** Delegate the discovery phase to the Explore subagent, which searches in its own context and returns a summary to the main conversation.

**설명**

정답이다. Explore는 파일 탐색과 코드 검색을 위한 내장 읽기 전용 서브에이전트다. 방대한 작업을 별도의 컨텍스트 윈도우에서 수행하고 간결한 요약만 돌려주므로, 메인 대화는 설계와 구현 단계를 위한 용량을 그대로 유지할 수 있다.

**D.** Run discovery in the main conversation and invoke /compact after each batch of files to keep the context window from overflowing.

**설명**

압축은 방대한 출력이 이미 메인 컨텍스트를 소비한 이후에 이력을 요약하는 것이며, 반복적인 요약은 이후 단계가 의존하는 구체적인 호출 지점 세부 사항을 누락시킬 위험이 있다. 이는 탐색 출력을 애초에 메인 대화 밖에 두는 것이 아니라 증상을 관리하는 것일 뿐이다.

### 전반적인 설명

Explore 서브에이전트는 정확히 이런 상황을 위해 존재한다. 이는 Claude Code에 내장된, 파일 탐색과 코드 검색, 코드베이스 탐색을 위한 빠른 읽기 전용 에이전트이며, 모든 서브에이전트가 그렇듯 자신만의 컨텍스트 윈도우에서 동작한다. 수백 개의 호출 지점 목록은 그 격리된 컨텍스트에 쌓이고, 정제된 요약만 메인 대화로 넘어온다. 따라서 메인 세션은 컨텍스트 예산을 거의 온전히 유지한 채 설계와 구현 단계에 도달하며, 바로 이 단계에서 컨텍스트를 유지하는 것이 일관성을 위해 가장 중요하다.

여기서의 사고 모델은 컨텍스트 간의 업무 분담이다. 대규모 부수 작업(광범위한 검색, 로그 처리, 테스트 출력)은 다시 볼 필요가 없을 트랜스크립트를 가진 서브에이전트에 위임하고, 메인 대화는 서로 쌓여가는 결정과 편집을 위해 남겨둔다. 이는 사후에 보완하는 것과는 근본적으로 다르다. /compact를 반복적으로 실행하는 것은 이미 윈도우를 소비한 이력을 요약하는 것이며, 각 요약 과정은 탐색이 포착하려 했던 정확한 세부 사항을 조용히 누락시킬 수 있다. findings를 CLAUDE.md에 임시 저장하는 것은 항상 로드되는 컨벤션 파일을 스크래치패드처럼 오용하는 것이며, 이후 모든 세션을 부풀린다. 플랜 모드는 Claude가 무엇을 할 수 있는지(편집 없는 조사)를 바꿀 뿐, 방대한 출력이 어디에 축적되는지는 바꾸지 않는다. 플랜 모드에서의 탐색도 여전히 메인 컨텍스트를 채운다.

Explore와 일반적인 서브에이전트 위임 패턴이 어떻게 탐색 결과를 메인 대화 밖에 유지하는지는 Claude Code의 Subagents 문서를 참고하라.
