# 사전 학습 노트 — 컨텍스트 관리와 신뢰성 (Context Management & Reliability)

이 문서는 이 주제를 전혀 모르는 사람이 처음부터 읽고 이해할 수 있도록 쓴 개념 정리입니다.
LLM(대형 언어 모델) 기반 에이전트 시스템을 설계할 때 반복해서 등장하는 개념들을 주제별로 묶어 설명합니다.

---

## 0. 큰 그림: 왜 "컨텍스트 관리"와 "신뢰성"이 한 묶음인가

LLM은 매 호출마다 **컨텍스트 윈도우(context window)** 라는 고정 크기의 입력 공간에 들어간 텍스트만 볼 수 있습니다.
사람처럼 "기억"하는 게 아니라, 매번 필요한 내용을 통째로 다시 넣어 줘야 합니다.

여기서 두 가지 문제가 동시에 생깁니다.

1. **공간 문제** — 넣을 수 있는 양이 유한하다. 넘치면 뭔가를 버려야 한다.
2. **주의(attention) 문제** — 공간에 들어가 있어도 모델이 그 정보를 실제로 활용한다는 보장이 없다.

이 두 문제 때문에 정보가 조용히 사라지고, 그 결과 시스템이 **틀린 답을 자신 있게** 내놓습니다.
즉 컨텍스트 관리는 곧 신뢰성(reliability) 문제입니다.

여기에 하나 더, 에이전트가 사람 대신 판단을 내리는 순간 **"언제 스스로 하고, 언제 사람에게 넘길 것인가"** 라는
운영 원칙(에스컬레이션)이 필요해집니다. 이것도 신뢰성의 일부입니다.

이 노트는 크게 다음 주제를 다룹니다.

- 컨텍스트 윈도우와 토큰 예산
- 멀티 에이전트 구조 (오케스트레이터 / 서브에이전트 / 코디네이터)
- 서브에이전트 출력 설계 (요약, 메타데이터, 충돌 보고)
- 프롬프트 구조화와 Lost in the Middle
- 대화 요약, 압축(compaction), 영속성(persistence)
- 에러 처리와 재시도 전략
- 사람에게 넘기는 기준(에스컬레이션)과 어조/공감
- 모델 신뢰도 보정(calibration)과 임계값 라우팅

## 1. 컨텍스트 윈도우와 토큰 예산

### 1.1 토큰(token)

LLM은 글자가 아니라 **토큰** 단위로 텍스트를 처리합니다. 토큰은 대략 단어 조각입니다.
영어 기준 대략 1토큰 ≈ 4글자, 한국어는 더 잘게 쪼개집니다.

비용과 속도가 모두 토큰 수에 비례하므로, "토큰을 아낀다"는 말은 곧 "돈과 시간과 정확도를 아낀다"는 뜻입니다.

### 1.2 컨텍스트 윈도우(context window)

한 번의 모델 호출에 넣을 수 있는 토큰의 최대치입니다.
시스템 프롬프트 + 대화 기록 + 도구 출력 + 첨부 문서 + 모델이 생성할 답변이 **모두 이 안에** 들어가야 합니다.

윈도우가 100만 토큰이라 해도 무한이 아닙니다. 로그 덤프, 파일 전문(全文), 검색 결과 같은 것은
놀라울 정도로 빠르게 윈도우를 채웁니다.

### 1.3 컨텍스트 예산(context budget)

실무에서는 윈도우 크기를 그냥 쓰는 게 아니라, 용도별로 **예산을 배분**합니다.

```
전체 200,000 토큰 예산 예시
├─ 시스템 프롬프트 / 규칙        2,000
├─ 영속 팩트 블록                 500
├─ 대화 요약                    3,000
├─ 검색·도구 결과              40,000
├─ 참조 문서                  100,000
└─ 출력 여유분                 20,000
```

예산을 넘기면 다음 중 하나가 일어납니다.

- 호출 자체가 실패한다.
- 앞부분(또는 뒷부분) 내용이 잘려 나간다(truncation).
- 파이프라인이 임의로 일부 입력을 **통째로 버린다(drop)**.

마지막 경우가 가장 위험합니다. 에러가 안 나고, 결과물에서 특정 내용이 그냥 없어지기 때문입니다.

### 1.4 다운스트림(downstream) 에이전트

여러 에이전트를 파이프라인으로 연결하면, 앞 단계 출력이 뒤 단계 입력이 됩니다.
앞 단계 5개가 각각 "약간 장황"하면, 뒤 단계에서는 그것이 5배로 곱해져 폭발합니다.

**핵심 규칙: 컨텍스트 예산은 생산자(producer) 쪽에서 지켜야 한다.**
소비자(consumer) 쪽에서 "알아서 잘 읽어라"라고 요구하는 것으로는 해결되지 않습니다.

## 2. 멀티 에이전트 아키텍처 기본 용어

### 2.1 역할 구분

| 역할 | 설명 |
|---|---|
| **메인 에이전트(main agent)** | 사용자와 직접 대화하고, 전체 목표를 유지하며, 최종 판단을 내리는 주체 |
| **오케스트레이터(orchestrator)** | 여러 서브에이전트를 실행하고 그 결과를 모아 다음 단계로 넘기는 조율자 |
| **코디네이터(coordinator)** | 오케스트레이터와 거의 같은 뜻. 서브에이전트 결과를 받아 조정·결정하는 상위 주체 |
| **서브에이전트(subagent)** | 좁고 구체적인 하위 작업을 자기 자신의 별도 컨텍스트에서 수행하는 하위 실행 단위 |
| **종합 단계(synthesis step)** | 여러 서브에이전트 결과를 하나의 답/문서로 통합하는 단계 |

### 2.2 서브에이전트가 존재하는 진짜 이유: 컨텍스트 격리

서브에이전트의 가장 큰 가치는 "병렬 처리"가 아니라 **컨텍스트 격리(context isolation)** 입니다.

서브에이전트는 자기만의 컨텍스트 윈도우를 가집니다.
그 안에서 파일 500개를 열고 grep 결과 3만 줄을 봐도, **메인 에이전트의 컨텍스트는 전혀 오염되지 않습니다.**
메인 에이전트는 서브에이전트가 최종적으로 반환한 **요약본만** 받습니다.

```
[메인 에이전트]  ← 요약 300토큰 ←  [서브에이전트 A]  ← 원시 출력 40,000토큰
                 ← 요약 300토큰 ←  [서브에이전트 B]  ← 원시 출력 35,000토큰
                 ← 요약 300토큰 ←  [서브에이전트 C]  ← 원시 출력 50,000토큰
```

### 2.3 위임의 방향 규칙

이것이 이 주제에서 가장 중요한 설계 원칙 중 하나입니다.

> **토큰을 많이 소모하지만 결론이 짧은 작업 → 서브에이전트에게 위임**
> **전체 맥락을 알아야 하는 고수준 판단·종합 → 메인 에이전트가 직접 수행**

**서브에이전트에 적합한 일**
- 여러 디렉터리를 전수 검색(exhaustive search)
- 대량 로그 파싱
- 문서 수십 건 훑어서 관련 부분만 추출
- 즉, **verbose output(장황한 출력)을 만들어내는 저수준 탐색**

**메인 에이전트가 직접 해야 하는 일**
- 마이그레이션 전략 수립
- 아키텍처 판단
- 상충되는 정보 사이의 최종 결정
- 즉, **전체 그림을 봐야 하는 고수준 종합(synthesis)**

이 방향이 **거꾸로** 되면(탐색을 메인이 하고 종합을 서브에게 위임) 최악입니다.
메인 컨텍스트는 쓰레기 토큰으로 가득 차고, 정작 종합을 맡은 서브에이전트는 전체 맥락을 못 봅니다.

### 2.4 위임을 아예 안 하는 것도 답이 아니다

"전부 하나의 에이전트 컨텍스트 안에서 처리한다"는 선택은 소규모에서는 단순해서 좋지만,
20만 줄 코드베이스 같은 규모에서는 컨텍스트 예산을 금방 초과하고 정보 손실이 발생합니다.

### 2.5 단계 간 핸드오프(phase handoff)

작업을 phase 1 → phase 2로 나눠 진행할 때, phase 2 에이전트가 phase 1 결과를 알아야 합니다.
이때 선택지는 세 가지이고, 정답은 항상 가운데입니다.

| 방식 | 결과 |
|---|---|
| 원본 대화록(raw transcript) 전부 전달 | 토큰 폭발, 비용 증가, 주의 분산. 격리의 이점이 사라짐 |
| **핵심 발견을 간결한 요약으로 종합해 초기 프롬프트에 주입** | ✅ 토큰 절약 + 맥락 유지 |
| 아무것도 전달 안 함 | phase 2가 phase 1 작업을 중복 재발견. 자원 낭비 |

**grounded(기반을 둔)** 라는 표현은 "후속 에이전트가 앞 단계의 사실 위에서 작업하는 상태"를 뜻합니다.
근거 없이 시작하면 에이전트는 가정을 지어내고, 그것이 곧 **환각(hallucination)** 으로 이어집니다.

또한 "서브에이전트가 질문할 때까지 기다린다"는 수동적 방식은 나쁩니다.
에이전트는 모르는 걸 모른다고 인지하지 못한 채 그냥 진행해 버리는 경향이 있기 때문입니다.
**필요한 맥락은 처음부터 밀어 넣는(push) 것이 원칙입니다.**

## 3. 서브에이전트 출력 설계

서브에이전트가 "무엇을, 어떤 형태로" 반환하는지가 시스템 전체 품질을 결정합니다.

### 3.1 출력 스키마(output schema)를 정하라

서브에이전트에게 자유 서술을 허용하면 대개 이런 걸 반환합니다.

> "먼저 A 디렉터리를 살펴봤습니다. 거기에서 몇 가지 흥미로운 패턴을 발견했는데, 이는
> B와 관련이 있어 보였고, 그래서 다시 C를 확인했더니… (단락 5개 더)"

이 **추론 서술(reasoning narrative)** 은 대부분 상위 에이전트에게 불필요합니다.
상위 에이전트가 필요한 건 **결론과 근거**뿐입니다.

권장 출력 형태:

```json
{
  "key_facts": ["2023년 개정으로 X 조항이 적용 제외됨"],
  "citations": [
    {"source": "Smith v. Jones, 2023", "locator": "p.14"}
  ],
  "relevance_score": 0.82,
  "conflicts": []
}
```

- **key facts**: 핵심 사실만
- **citations**: 인용/출처
- **relevance score**: 관련성 점수 — 상위 단계가 정렬·필터링에 사용
- 추론 과정은 **제외**

이렇게 하면 서브에이전트 8개의 출력을 합쳐도 컨텍스트 예산 안에 들어옵니다.

### 3.2 잘못된 대안들

- **먼저 도착한 것만 쓰고 나머지 버리기** — 정보 유실. 도착 순서는 중요도와 무관.
- **에이전트 수를 늘려 주제를 잘게 나누기(단, 여전히 전체 추론을 반환)** — 총 토큰은 줄지 않고 오히려 늘어남.
- **소비자가 두 번에 나눠 읽기(two passes)** — 한 번 호출의 입력 한계 자체는 그대로. 구조적 해결이 아님.

**원칙: 출력량 문제는 출력을 만드는 쪽에서 줄여야 한다.**

### 3.3 출처 메타데이터(source metadata)를 함께 실어라

숫자 하나만 넘기면 상위 단계가 그것을 판단할 수 없습니다.

나쁜 출력:
```
TAM: 480억 달러
```

좋은 출력:
```
TAM: 480억 달러
  - 출처: Gartner "Industry X Market Sizing"
  - 발행일: 2021-03
  - 방법론: 하향식(top-down), 상위 20개사 매출 기반 추정
  - 지역 범위: 북미만
```

왜 필요한가:

- **발행일(publication date)** — 어느 수치가 최신인지 판단하려면 필수. 없으면 오래된 수치(outdated figure)를 인용하는 사고가 납니다.
- **방법론(methodology)** — 하향식 추정치와 상향식 실측치는 애초에 **비교 가능(comparable)** 하지 않습니다. 방법이 다르면 숫자 차이는 오류가 아니라 정의 차이일 수 있습니다.
- **범위/정의** — 지역, 기간, 포함 항목.

여기서 나오는 개념이 **TAM(Total Addressable Market, 총 유효 시장)** 입니다.
어떤 제품이 이론상 도달 가능한 시장 전체 규모를 뜻하며, 정의와 방법론에 따라 몇 배씩 달라지는 대표적인 "맥락 없이는 무의미한 숫자"입니다.

잘못된 대안:
- 여러 출처를 **평균 내기** — 서로 다른 시점·방법의 수치를 평균하면 의미 없는 숫자가 되고, 최신성도 사라집니다.
- **가장 큰 값을 고르기** — 정확성과 무관한 편향된 규칙.
- **검색 과정을 더 자세히 설명하기** — 필요한 건 에이전트가 어떻게 찾았는지가 아니라, **찾아낸 데이터 원본의 속성**입니다.

### 3.4 충돌 보고(conflict reporting)와 책임 분리

서브에이전트가 서로 모순되는 데이터를 발견했을 때(예: 같은 분기 영업비용이 두 스프레드시트에서 다름),
서브에이전트가 해야 할 일은 **판단이 아니라 보고**입니다.

**옳은 처리:**
```
영업비용 (2024 Q2)
  - 값 A: 1,240,000 (출처: FY24_ops_final.xlsx, 시트 "Summary")
  - 값 B: 1,187,500 (출처: Q2_close_v3.xlsx, 시트 "Actuals")
  - 상태: 불일치. 조정(reconciliation)은 코디네이터가 수행할 것.
```

**하면 안 되는 일:**
- **누락(omit)** — 불일치한다는 이유로 항목을 빼면, 상위 단계는 문제가 있다는 사실조차 모릅니다. 가장 나쁜 선택.
- **자체 재계산(recompute from first principles)** — 서브에이전트에게 부여되지 않은 권한 행사. 환각과 왜곡의 원천.
- **파일 수정 시각(timestamp)만 보고 한쪽 버리기** — 검증되지 않은 가정. 최근에 열어 저장만 한 파일이 최신 수치라는 보장은 없습니다.

여기 깔린 원칙이 **관심사의 분리(separation of concerns)** 입니다.

> 서브에이전트: 수집 · 1차 분석 · 출처 기록 · **투명한 보고**
> 코디네이터: 조정(reconciliation) · 우선순위 결정 · 최종 종합

**침묵으로 문제를 숨기지 말고, 불확실성을 위로 올려라(surface uncertainty upward).**

## 4. 프롬프트 구조화와 Lost in the Middle

### 4.1 Lost in the Middle 현상이란

LLM은 긴 입력에서 **맨 앞과 맨 뒤**의 정보를 잘 기억하고, **중간**에 놓인 정보는 놓치는 경향이 있습니다.
성능을 위치별로 그리면 U자 곡선이 나옵니다.

```
회상률
 높음 │■                                      ■
      │ ■                                   ■
      │   ■                              ■
 낮음 │      ■■■■■■■■■■■■■■■■■■■■■■■■
      └──────────────────────────────────────
       앞부분          중간부분          뒷부분
```

이것은 버그가 아니라 트랜스포머 어텐션의 알려진 특성입니다.
**컨텍스트에 넣었다고 해서 모델이 그것을 사용한다는 보장은 없습니다.**

전형적인 증상: 4개 서비스의 조사 메모를 순서대로 이어 붙인 긴 문서에서,
**두 번째(가운데) 서비스의 근본 원인만 결과물에서 반복적으로 빠진다.**

### 4.2 완화 방법

**(1) 프론트로딩(front-loading) — 핵심 요약을 맨 앞에**

```markdown
## 요약: 서비스별 근본 원인
- auth-service: JWT 만료 시각 검증 누락
- billing-service: 커넥션 풀 고갈
- notify-service: 재시도 폭주로 인한 self-DDoS
- search-service: 인덱스 재구축 중 읽기 타임아웃

---

## 상세: auth-service
(로그와 상세 메모…)

## 상세: billing-service
...
```

핵심 결론이 모두 맨 앞(가장 잘 읽히는 위치)에 들어가고,
상세 내용은 명확한 **헤딩(headings)** 아래 구조화됩니다.

**(2) 구조화 마크업**

마크다운 헤딩, XML 태그(`<service name="billing">…</service>`), 명확한 구분선은
모델에게 "여기가 하나의 독립된 단위"라는 신호를 줍니다.

**(3) 중요 정보를 끝에도 반복 배치**

앞과 뒤 모두 회상률이 높으므로, 결정적 지시사항을 마지막에 한 번 더 놓는 것도 유효합니다.

### 4.3 효과 없는 대응

- **모든 걸 줄바꿈 없는 한 단락으로 합치기** — 구조가 사라져 상황이 더 나빠집니다. 길이를 줄이는 것과 구조를 없애는 것은 다릅니다.
- **문서 끝에 "중간 부분을 주의 깊게 보세요"라고 써 두기** — 구조적 어텐션 문제를 문장 한 줄로 고칠 수 없습니다.
- **입력 순서를 매번 무작위로 바꾸기** — 어느 항목이 희생되는지 무작위로 바뀔 뿐, 여전히 가운데 것은 누락됩니다.

**원칙: 프롬프트 엔지니어링은 "부탁"이 아니라 "배치"다.**

## 5. 요약, 압축, 영속성

### 5.1 러닝 서머리(running summary)와 정보 손실

긴 대화를 유지하기 위해 몇 턴마다 지금까지 내용을 요약하고, 원문 대신 요약을 컨텍스트에 유지하는 기법입니다.
토큰은 아끼지만, 요약을 반복하면 **디테일이 점점 일반화**됩니다.

```
원본:  "페니실린 알레르기가 있고, 22일에 예약을 원합니다"
1차:   "페니실린 알레르기, 22일 예약 희망"
3차:   "약물 알레르기 있음, 이번 달 예약 희망"
5차:   "환자가 몇몇 알레르기가 있고 곧 예약을 원함"
```

이것을 **손실 압축(lossy compression)** 또는 **요약 드리프트(summarization drift)** 라고 부릅니다.
"페니실린"이 "몇몇 알레르기"가 되는 순간, 의료 시스템에서는 이것이 안전 사고가 됩니다.

### 5.2 영속 팩트 블록(persistent facts block)

해결책은 요약 빈도를 조절하는 것이 아니라, **절대 잃으면 안 되는 사실을 요약 대상에서 빼는 것**입니다.

구조화된 팩트 블록을 별도로 유지하고, 매 프롬프트마다 **요약본 바깥에** 그대로 주입합니다.

```
=== 확정 사실 (변경 금지, 원문 그대로 유지) ===
- 알레르기: 페니실린
- 요청 예약일: 22일
- 환자 ID: 88213
=============================================

=== 대화 요약 ===
환자가 정기 검진 일정 변경을 문의 중이며 …
```

특징:
- 요약 파이프라인을 **통과하지 않는다** → 절대 흐려지지 않음
- 구조화되어 있어 프로그램이 검증·재사용 가능
- 매 호출마다 그대로 재주입됨

이것은 대화 메모리를 **"흐릿해도 되는 것"과 "정확해야 하는 것"으로 분리**하는 상태 관리(state management) 패턴입니다.

### 5.3 잘못된 대안

- **요약 빈도 낮추기** — 압축 시점을 미룰 뿐, 압축이 일어나는 순간 같은 손실이 발생.
- **사용자에게 매번 재확인 요청** — UX 악화. 내부 정보 손실이라는 원인은 그대로.
- **요약을 아예 안 쓰고 전체 원문을 사람이 검토** — 자동화의 목적 자체를 포기.

### 5.4 컴팩션(compaction)과 스크래치패드(scratchpad)

**컴팩션**이란 길어진 세션의 대화 기록을 요약으로 대체해 컨텍스트 공간을 되찾는(reclaim) 동작입니다.
(코딩 에이전트 도구의 `/compact` 같은 명령이 대표적입니다.)

컴팩션도 요약이므로 **손실이 발생합니다.** 파일 덤프의 세부 내용, 명령어 출력의 구체적 수치는 대개 살아남지 못합니다.

그래서 **순서가 중요합니다.**

> **1. 현재 단계의 핵심 발견을 스크래치패드 파일에 먼저 기록한다(persist).**
> **2. 그런 다음에 컴팩션한다.**

**스크래치패드 파일**이란 작업 중 발견한 것을 적어 두는 별도의 파일(예: `notes/phase1-findings.md`)입니다.
**durable(지속 가능한, 영속적인)** 저장소라는 표현은 "세션이 끝나거나 컨텍스트가 날아가도 남아 있는 곳"을 뜻합니다.

이것을 **컨텍스트 → 디스크 오프로딩**이라고 볼 수 있습니다.
컨텍스트 윈도우는 RAM, 파일은 디스크라고 생각하면 직관적입니다. RAM을 비우기 전에 저장하는 게 당연합니다.

나쁜 대안:
- **기록 없이 바로 컴팩션** — 복구 불가능한 손실. "나중에도 접근할 수 있겠지"라는 믿음은 틀렸습니다.
- **세션을 완전히 종료하고 참조 없이 새로 시작** — 지금까지 작업을 통째로 버리는 것.
- **컨텍스트가 완전히 고갈될 때까지 방치** — 성능 저하, 강제 truncation, 환각 증가.

## 6. 에러 처리와 재시도 전략

### 6.1 오류의 두 종류

| 구분 | 일시적 오류 (transient) | 지속적/구조적 오류 (systematic) |
|---|---|---|
| 예시 | HTTP 503 Service Unavailable, 네트워크 타임아웃, 순간 rate limit | 인증 실패(401/403), 잘못된 자격증명, 권한 부족, 잘못된 설정 |
| 성질 | 원인이 스스로 사라짐 | 환경이 바뀌지 않으면 영원히 실패 |
| 올바른 처리 | **로컬 재시도(local retry)** | **상위로 에스컬레이션** |

**503(Service Unavailable)** 은 서버가 일시적으로 처리 불가 상태라는 신호입니다.
1초 뒤 재시도하면 성공하는 경우가 흔합니다.

**자격 증명 로테이션(credential rotation)** 은 보안상 주기적으로 비밀키·토큰을 새 값으로 교체하는 관행입니다.
새 값이 어떤 환경에 **전파(propagate)** 되지 않으면 그 환경은 계속 실패합니다.
이건 재시도로 절대 해결되지 않습니다. 사람이나 시스템이 자격증명을 배포해야 합니다.

### 6.2 올바른 조합

> 일시적 오류 → 서브에이전트가 조용히 로컬 재시도로 해결. 코디네이터를 귀찮게 하지 않는다.
> 지속적 오류 → **시도 내역(what was attempted)을 첨부해** 코디네이터에게 에스컬레이션.

"시도 내역 첨부"가 중요한 이유: 코디네이터가 같은 실패를 반복하지 않고 바로 원인 계층(자격증명 배포)을 조치할 수 있게 해 줍니다.

에스컬레이션 보고 예시:
```
실패: metrics-store 쿼리
증상: 2분간 반복 401 Unauthorized
시도: 지수 백오프로 6회 재시도, 모두 동일 오류
추정 원인: 자격증명 로테이션이 이 환경에 미전파
필요 조치: 환경 변수 METRICS_TOKEN 갱신 (에이전트 권한 밖)
```

### 6.3 재시도 기법: 지수 백오프(exponential backoff)

일시적 오류 재시도 시, 간격을 점점 늘리며 재시도합니다.

```python
delays = [1, 2, 4, 8]   # 초
for attempt, d in enumerate(delays):
    try:
        return call()
    except TransientError:
        sleep(d + random.uniform(0, 0.5))   # jitter: 동시 재시도 몰림 방지
raise EscalateToCoordinator("6.2절 형식으로 보고")
```

반드시 **최대 재시도 횟수(retry budget)** 를 둡니다.

### 6.4 안티패턴

- **무한 재시도(indefinitely)** — 자원 낭비, 무한 루프, 다른 작업까지 지연. 반드시 상한이 필요합니다.
- **모든 오류를 즉시 에스컬레이션** — 코디네이터가 병목이 됩니다. 서브에이전트가 스스로 처리할 수 있는 건 스스로 처리해야 자율성의 의미가 있습니다.
- **거꾸로 매핑** (일시적 오류는 올리고, 구조적 오류는 계속 재시도) — 최악의 조합.

## 7. 사람에게 넘기는 기준 (Human Escalation)

에이전트가 사람에게 넘기는 것을 **에스컬레이션(escalation)** 이라 합니다.
너무 자주 하면 자동화 가치가 없고, 너무 안 하면 위험합니다. 기준이 필요합니다.

### 7.1 에스컬레이션해야 하는 경우

**(1) 사용자가 명시적으로 사람을 요청했을 때 — 최우선**

"실제 사람과 얘기하고 싶다", "봇 말고 사람" 같은 직접적 요구가 있으면
**작업이 아무리 쉬워도, AI가 처리할 수 있어도, 즉시 사람에게 넘깁니다.**

하면 안 되는 것:
- 이유를 캐묻기 ("왜 사람을 원하시나요?") — 이미 불만인 고객에게 마찰을 더함
- 먼저 처리해 보겠다고 제안하고, 고객이 다시 요구하면 그때 넘기기 — 명시적 의사 위반
- "간단하니까"라며 절차 안내를 강행하기 — 가장 나쁜 거부적 태도

원칙: **사용자의 명시적 선호는 효율성보다 우선한다.**

**(2) 정책에 규정이 없을 때 (policy silence)**

문서화된 정책이 어떤 상황을 **전혀 다루지 않는다면**, 에이전트는 그 공백을 스스로 메워선 안 됩니다.

예: 정책에 "자사 웹사이트가 구매 후 14일 내 가격을 내리면 차액 조정"만 있고,
경쟁사 가격 매칭에 대해서는 **한 마디도 없는데** 고객이 경쟁사 가격 매칭을 요구한 경우.

가능한 오답 세 가지 모두 "공백을 스스로 메우는" 행동입니다.
- **유추(analogy)로 승인** — 자사 조항을 확장 해석. 권한 밖.
- **명시가 없으니 금지된 것으로 간주하고 거절** — 이것도 자의적 해석. "언급 없음 ≠ 금지".
- **증거를 받아 독자적으로 승인** — 절차를 추가해도 승인 권한이 없다는 사실은 그대로.

정답: **에스컬레이션.** 정책 공백은 사람이 메워야 할 정책 결정 사항입니다.

> "명시되지 않음(silent)"과 "금지됨(prohibited)"은 다르다.

**(3) 도구·권한이 없을 때, 위험이 크거나 되돌릴 수 없을 때**

### 7.2 에스컬레이션하면 안 되는 경우

**단계 수가 많다는 이유만으로는 에스컬레이션하지 않습니다.**

예: 계량기 재측정 → 일할 계산(prorated) 크레딧 → 요금제 조정으로 이어지는 3단계 청구 정정.
**모든 단계가 정책에 명시되어 있고, 각 단계를 실행할 도구가 있다면** 그냥 직접 처리합니다.

- **일할 계산(prorated)**: 기간에 비례해 금액을 나누어 계산하는 방식.
  예를 들어 30일 요금제를 12일만 썼다면 12/30만큼만 청구/환급.

에스컬레이션 트리거는 **복잡도(complexity)가 아니라**:
- 정책의 모호함/공백
- 도구나 권한의 부재
- 사용자의 명시적 요청
- 위험·비가역성

"단계가 여러 개라 사람이 봐야 한다"는 논리를 받아들이면 자동화가 성립하지 않습니다.
반대로 "이 업무 카테고리는 복잡도 규칙에서 원천 면제"라는 식의 절대적 범주화도 잘못된 논리입니다.
판단 기준은 **정책이 커버하는가 + 도구가 있는가** 이지, 업무 종류가 아닙니다.

### 7.3 어조 인식과 공감 (tone acknowledgment)

사용자가 **짜증 난 어조(irritated tone)** 로 메시지를 보냈지만,
① 긴급성이 없고 ② 에이전트가 직접 처리 가능하며 ③ 사람을 요구하지 않았다면?

가장 좋은 응답은 **세 가지를 동시에** 합니다.

1. **감정 인정(acknowledge)** — "기다리시게 해서 번거로우셨겠습니다."
2. **즉시 처리 가능함을 알림** — "예약 변경은 지금 바로 처리해 드릴 수 있습니다."
3. **원하면 사람 연결 가능함을 제안(offer)** — "직원과 통화를 원하시면 바로 연결해 드리겠습니다."

이것이 왜 최선인가:
- 감정을 무시하고 기계적으로 처리만 하면 불만이 커집니다.
- 짜증 났다는 이유만으로 **자동 에스컬레이션**하면 인적 자원을 낭비하고 처리도 늦어집니다. 어조는 에스컬레이션 트리거가 아닙니다.
- "정말 사람이랑 얘기 안 하셔도 되나요?"라고 **되묻는 것**은 요청하지도 않은 절차를 추가하는 비효율입니다.

핵심 구분:
> **어조(tone)** 는 공감으로 대응한다.
> **명시적 요청(explicit request)** 은 행동으로 대응한다.
> 어조를 요청으로 오해해서 마음대로 에스컬레이션하지 않는다.

**offer(제안)** 와 **ask for confirmation(확인 요청)** 의 차이도 중요합니다.
제안은 사용자에게 선택지를 열어 주면서 흐름을 막지 않고, 확인 요청은 사용자를 멈춰 세웁니다.

## 8. 신뢰도 보정(Calibration)과 임계값 라우팅

### 8.1 신뢰도 점수(confidence score)란

모델이 자기 출력에 대해 내놓는 "이게 맞을 확률" 추정치입니다. 보통 0~1 사이 값입니다.
문서 추출 시스템이라면 필드마다("발행일", "총액") 별도 점수가 나옵니다.

### 8.2 보정(calibration)의 정의

모델이 **잘 보정되었다(well-calibrated)** 는 것은:

> 신뢰도 0.9라고 말한 예측들을 모아 보면, 실제로 그중 약 90%가 맞다.
> 신뢰도 0.6이라고 말한 예측들은 실제로 약 60%가 맞다.

즉 **신뢰도 점수와 실제 정답률(observed accuracy)이 일치**하는 상태입니다.
이걸 그래프로 그린 것이 **신뢰도 다이어그램(reliability diagram)** 이고, 이상적이면 y=x 대각선이 됩니다.

### 8.3 미스캘리브레이션(miscalibration)

- **과신(overconfidence)**: 0.95라고 했는데 실제 정답률 78% → 실제보다 자신을 과대평가
- **과소평가(underconfidence)**: 0.6이라고 했는데 실제 정답률 90% → 실제보다 자신을 과소평가

두 현상이 **동시에** 나타나면(높은 점수가 낮은 정확도, 낮은 점수가 높은 정확도),
점수와 정확도가 **역관계(inversely related)** 인 심각한 상태입니다.

```
정답률
100% │
     │        ● 0.6점수 → 90%
 90% │
     │                        ● 0.95점수 → 78%
 78% │
     └──────────────────────────────────
        0.6                     0.95     신뢰도 점수
        (기울기가 음수 = 완전히 뒤집힘)
```

이것은 결코 정상 동작이 아닙니다. "낮은 점수가 높은 정확도에 대응하는 것이 원래 그렇다"는 주장은 틀렸습니다.

### 8.4 임계값 라우팅(threshold routing)

자동화 시스템에서 흔한 패턴입니다.

```
if confidence >= THRESHOLD:
    자동 승인
else:
    사람 검토(human review)로 라우팅
```

이 방식은 **점수가 정확도와 단조적으로 비례한다는 가정**에 전적으로 의존합니다.
그 가정이 깨지면(역관계) 임계값 규칙은 **정확한 항목을 사람에게 보내고, 틀린 항목을 자동 통과**시킵니다.
즉 최악의 방향으로 작동합니다.

### 8.5 역관계를 발견했을 때 할 일

**올바른 결론:**
점수가 미스캘리브레이션되어 있고 해당 구간에서 정확도와 역관계이므로,
**원시 점수(raw score)를 그대로 "X 미만은 사람 검토" 임계값에 쓰면 안 되며, 추가 조사가 필요하다.**

추가 조사에서 볼 것들:
- 특정 필드 유형이나 문서 유형에서만 나타나는 현상인가? (혼동 변수)
- 표본 크기가 통계적으로 유의한가?
- 재보정(recalibration)으로 고칠 수 있는가?

**재보정 기법** (참고): Platt scaling, isotonic regression, temperature scaling 등
검증 세트를 이용해 원시 점수를 실제 확률에 맞게 사후 변환하는 방법들.

**잘못된 대응:**
- **임계값만 0.96으로 올리기** — 근본 원인(역관계)은 그대로. 정확한 항목까지 대량으로 사람 검토에 보내 비용만 폭증.
- **필드 수준 신뢰도 체계를 전부 폐기하고 모든 필드를 사람 검토로** — 과잉 반응. 자동화 이점을 전부 포기.
- **"원래 그런 것"이라며 그대로 사용** — 잘못된 라우팅을 계속 유지.

핵심 교훈:
> **자기 보고 신뢰도는 검증 없이 신뢰하지 말라.**
> 임계값을 정하기 전에 반드시 점수 대 실제 정답률을 측정하라.

## 9. 전체를 관통하는 원칙 정리

1. **컨텍스트는 유한한 자원이다.** 예산을 정하고, 생산자 쪽에서 지켜라.
2. **컨텍스트에 넣는 것과 모델이 사용하는 것은 다르다.** 위치와 구조가 중요하다(Lost in the Middle).
3. **위임의 방향**: 장황한 저수준 탐색은 아래로, 고수준 종합은 위에서.
4. **단계 간에는 원본이 아니라 요약을 넘긴다.** 단, 아무것도 안 넘기지도 않는다.
5. **잃으면 안 되는 사실은 요약 파이프라인 밖에 둔다** (영속 팩트 블록).
6. **컨텍스트를 버리기 전에 디스크에 먼저 저장한다** (스크래치패드 → 컴팩션 순서).
7. **불확실성과 충돌은 숨기지 말고 출처와 함께 위로 올린다.**
8. **일시적 오류는 스스로, 구조적 오류는 시도 내역과 함께 위로.** 무한 재시도는 금지.
9. **에스컬레이션 트리거는 복잡도가 아니라** 정책 공백·권한 부재·사용자의 명시적 요청이다.
10. **어조는 공감으로, 요청은 행동으로** 대응한다.
11. **자기 보고 신뢰도는 측정으로 검증한 뒤에만 자동화 규칙에 쓴다.**

## 10. 용어 사전 (Glossary)

### 컨텍스트 관련

| 영어 용어 | 한국어 설명 |
|---|---|
| **token** | 모델이 처리하는 텍스트의 최소 단위. 비용·속도·용량이 모두 토큰 수에 비례 |
| **context window** | 한 번의 모델 호출에 넣을 수 있는 토큰의 최대 크기 |
| **context budget** | 컨텍스트 윈도우를 용도별로 나눠 배정한 계획. 초과 시 잘림이나 누락 발생 |
| **truncation** | 예산 초과로 입력의 일부가 잘려 나가는 것 |
| **drop** | 파이프라인이 특정 입력(예: 서브에이전트 결과 하나)을 통째로 버리는 것 |
| **verbose output** | 파일 덤프, 로그, grep 결과처럼 부피만 크고 정보 밀도는 낮은 출력 |
| **downstream agent** | 파이프라인에서 앞 단계의 출력을 입력으로 받는 뒤쪽 에이전트 |
| **context isolation** | 서브에이전트가 별도 컨텍스트를 가져 상위 컨텍스트를 오염시키지 않는 성질 |
| **Lost in the Middle** | 긴 입력의 중간에 위치한 정보를 모델이 잘 활용하지 못하는 현상 |
| **front-loading** | 핵심 요약을 프롬프트 맨 앞에 배치해 회상률을 높이는 기법 |
| **headings / structured markup** | 마크다운 헤딩·XML 태그 등으로 입력을 구획해 모델의 인식을 돕는 것 |
| **compaction** | 길어진 대화 기록을 요약으로 대체해 컨텍스트 공간을 되찾는 동작 |
| **reclaim (context space)** | 컨텍스트 공간을 다시 확보하는 것 |
| **scratchpad file** | 발견 사항을 적어 두는 작업용 별도 파일 |
| **durable / persistence** | 세션이 끝나도 남는 지속적 저장. 컨텍스트는 휘발성, 파일은 영속성 |
| **running summary** | 대화가 진행되는 동안 몇 턴마다 갱신되는 누적 요약 |
| **summarization drift / lossy compression** | 요약을 반복할수록 구체적 사실이 점점 흐려지는 정보 손실 현상 |
| **persistent facts block** | 절대 잃으면 안 되는 사실을 요약 밖에 구조화해 두고 매 프롬프트에 재주입하는 영역 |
| **state management** | 대화·작업 상태를 어디에 어떤 형태로 보관할지 설계하는 것 |

### 멀티 에이전트 관련

| 영어 용어 | 한국어 설명 |
|---|---|
| **main agent** | 사용자와 대화하고 전체 목표와 최종 판단을 담당하는 주 에이전트 |
| **orchestrator** | 여러 서브에이전트를 실행·조율하고 결과를 모으는 상위 주체 |
| **coordinator** | 오케스트레이터와 동의어. 서브에이전트 결과를 받아 조정·결정 |
| **subagent** | 좁은 하위 작업을 자기 컨텍스트에서 수행하는 하위 실행 단위 |
| **delegation** | 작업을 서브에이전트에게 위임하는 것 |
| **synthesis (step)** | 여러 결과를 하나의 답·문서로 통합하는 단계 |
| **handoff** | 한 단계·에이전트에서 다음으로 결과를 넘기는 것 |
| **raw transcript** | 에이전트 실행의 원본 대화록 전체. 그대로 넘기면 토큰 폭발 |
| **grounded** | 후속 에이전트가 앞 단계의 실제 발견 사실 위에서 작업하는 상태 |
| **injection (into prompt)** | 요약이나 사실 블록을 프롬프트에 삽입하는 것 |
| **separation of concerns** | 역할 분리. 서브는 수집·보고, 코디네이터는 조정·결정 |
| **output schema** | 서브에이전트가 반환해야 할 출력의 정해진 구조 |
| **key facts / citations / relevance score** | 축약된 구조화 출력의 3요소: 핵심 사실 / 출처 인용 / 관련성 점수 |
| **reasoning narrative** | 에이전트의 단계별 추론 서술. 대개 상위에는 불필요 |
| **conflict reporting** | 상충되는 데이터를 판단하지 않고 출처와 함께 투명하게 보고하는 것 |
| **reconciliation** | 상충 데이터를 조정해 하나로 정리하는 작업. 코디네이터의 역할 |
| **annotation** | 각 값에 출처·조건을 붙여 표시하는 것 |
| **hallucination** | 모델이 근거 없는 내용을 사실처럼 생성하는 현상 |

### 데이터 메타데이터 관련

| 영어 용어 | 한국어 설명 |
|---|---|
| **source metadata** | 데이터의 출처, 발행일, 방법론, 범위 등 부가 정보 |
| **publication date** | 자료의 발행 일자. 최신성 판단의 근거 |
| **methodology** | 수치가 산출된 방법(하향식/상향식, 표본, 정의 등) |
| **comparable** | 서로 비교 가능한 상태. 방법론과 범위가 같아야 성립 |
| **outdated figure** | 더 최신 자료가 있음에도 인용된 낡은 수치 |
| **TAM (Total Addressable Market)** | 총 유효 시장. 제품이 이론상 도달 가능한 시장 전체 규모 |
| **first principles (recompute from)** | 근본 원리로부터 직접 재계산하는 것. 서브에이전트에겐 대개 권한 밖 |

### 에러 처리 관련

| 영어 용어 | 한국어 설명 |
|---|---|
| **transient error** | 일시적 오류. 재시도하면 성공할 가능성이 높음 (예: 503, 타임아웃) |
| **503 Service Unavailable** | 서버가 일시적으로 요청을 처리할 수 없다는 HTTP 상태 코드 |
| **systematic / non-transient failure** | 환경이 바뀌지 않으면 계속 실패하는 구조적 오류 (예: 잘못된 자격증명) |
| **credential rotation** | 보안상 자격증명을 주기적으로 새 값으로 교체하는 관행 |
| **propagation** | 교체된 자격증명·설정이 각 환경에 실제로 반영·전파되는 것 |
| **local retry** | 서브에이전트가 상위에 알리지 않고 자체적으로 재시도하는 것 |
| **exponential backoff** | 재시도 간격을 1s, 2s, 4s… 로 늘려 가는 재시도 전략 |
| **jitter** | 재시도 시각을 무작위로 흩뿌려 동시 재시도 폭주를 막는 기법 |
| **retry budget** | 최대 재시도 횟수·시간의 상한 |
| **escalate (with what was attempted)** | 시도 내역을 첨부해 상위 주체에게 넘기는 것 |

### 운영·정책 관련

| 영어 용어 | 한국어 설명 |
|---|---|
| **human escalation** | 사람(상담원·관리자)에게 사건을 넘기는 것 |
| **escalation trigger** | 에스컬레이션을 발동시키는 조건 |
| **documented policy** | 문서화된 공식 지침 |
| **policy silence** | 정책이 해당 상황을 전혀 다루지 않는 공백 상태. "금지"와 다름 |
| **by analogy** | 다른 조항을 유사하다는 이유로 확장 적용하는 것. 권한 밖의 위험한 해석 |
| **policy coverage** | 정책이 해당 사안을 명시적으로 다루고 있는 정도 |
| **step count** | 처리에 필요한 단계 수. 그 자체로는 에스컬레이션 사유가 아님 |
| **prorated** | 일할 계산. 사용 기간에 비례해 금액을 나누어 산정 |
| **tone acknowledgment** | 사용자의 감정·어조를 인지하고 언급하는 것 |
| **offer to escalate** | 사람 연결을 선택지로 제시하는 것 (강제하거나 되묻는 것과 다름) |
| **explicit request** | 사용자가 말로 분명히 밝힌 요구. 효율성보다 우선 |

### 신뢰도·평가 관련

| 영어 용어 | 한국어 설명 |
|---|---|
| **confidence score** | 모델이 자기 출력에 부여한 정답 확률 추정치 (0~1) |
| **calibration** | 신뢰도 점수가 실제 정답률과 일치하도록 맞추는 것 |
| **well-calibrated** | 0.9라고 한 예측이 실제로 약 90% 맞는 상태 |
| **miscalibration** | 점수와 실제 정답률이 어긋난 상태 |
| **overconfidence / underconfidence** | 과신(점수 > 실제) / 과소평가(점수 < 실제) |
| **inversely related** | 점수가 높을수록 정확도가 낮아지는 역관계. 심각한 미스캘리브레이션 |
| **observed accuracy** | 검증 데이터에서 실제로 측정된 정답률 |
| **reliability diagram** | 신뢰도 구간별 실제 정답률을 그린 보정 상태 진단 그래프 |
| **routing threshold** | 자동 처리와 사람 검토를 가르는 신뢰도 기준값 |
| **raw score** | 재보정을 거치지 않은 모델의 원시 점수 |
| **recalibration** | Platt scaling, isotonic regression 등으로 점수를 실제 확률에 맞게 사후 보정하는 것 |
| **human review** | 자동 처리하지 않고 사람이 직접 확인하는 경로 |
| **stratified sampling** | 문서 유형 등 하위 집단별로 나누어 표본을 뽑는 검증 기법 |
| **validation set** | 모델 성능·보정 상태를 측정하는 데 쓰는 별도 데이터 집합 |
