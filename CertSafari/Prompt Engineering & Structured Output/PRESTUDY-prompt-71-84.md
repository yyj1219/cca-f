# 사전 학습 노트: 프롬프트 엔지니어링과 구조화된 출력

이 문서는 이 주제를 처음 접하는 사람을 위한 개념 정리입니다. LLM(대규모 언어 모델)이 무엇인지 정도만 알고 있어도 읽을 수 있도록, 필요한 배경부터 하나씩 쌓아 올립니다.

---

## 0. 배경: 이 분야는 무엇을 다루는가

**LLM(Large Language Model, 대규모 언어 모델)** 은 앞의 텍스트를 보고 다음에 올 토큰(단어 조각)을 확률적으로 예측하는 모델입니다. Claude, GPT 같은 것들이 여기에 속합니다.

핵심적으로 기억해야 할 성질이 두 가지 있습니다.

1. **모델은 학습되어 고정되어 있고, 우리가 바꿀 수 있는 것은 "입력"뿐이다.** 모델의 가중치를 재학습시키지 않고 원하는 동작을 얻어내려면 입력 텍스트(=프롬프트)를 잘 설계해야 합니다. 이것을 **프롬프트 엔지니어링(Prompt Engineering)** 이라고 부릅니다.
2. **모델은 "그럴듯한" 것을 생성하지 "참인" 것을 생성하지 않는다.** 이 성질에서 환각(hallucination), 산술 오류, 자기 검토의 한계 같은 문제가 전부 파생됩니다.

이 노트는 크게 네 갈래를 다룹니다.

- 예시로 모델을 가르치는 법 (Few-shot prompting)
- 출력 형태를 기계적으로 강제하는 법 (Tool use / JSON Schema / Structured Output)
- 프롬프트를 고쳤을 때 정말 좋아졌는지 재는 법 (Evaluation)
- 여러 에이전트를 조합해 시스템을 만드는 법 (Agent architecture)

## 1. 컨텍스트 윈도우와 토큰: 모든 제약의 출발점

### 1.1 토큰(Token)

모델은 글자가 아니라 **토큰** 단위로 텍스트를 처리합니다. 토큰은 대략 단어보다 작은 조각입니다(영어 기준 평균 4글자 안팎). 요금과 속도가 전부 토큰 개수에 비례하므로, "프롬프트를 길게 쓴다"는 것은 곧 "돈과 시간을 더 쓴다"는 뜻입니다.

### 1.2 컨텍스트 윈도우(Context Window)

모델이 한 번의 요청에서 볼 수 있는 토큰의 최대 개수입니다. 시스템 프롬프트 + 대화 이력 + 이번 입력 + 생성할 출력이 모두 이 창 안에 들어가야 합니다.

여기서 흔한 오해가 하나 있습니다.

> "컨텍스트 윈도우가 크니까 다 넣으면 되지 않나?"

**아닙니다.** 창에 들어간다는 것과 모델이 그 내용을 고르게 잘 활용한다는 것은 다른 문제입니다.

### 1.3 Lost in the Middle (중간 정보 소실)

긴 컨텍스트를 넣으면 모델은 **맨 앞과 맨 뒤의 정보는 잘 활용하지만 중간에 위치한 정보는 놓치는 경향**이 있습니다. 이 현상을 "Lost in the Middle"이라고 부릅니다. 어텐션(attention)이 긴 입력 전체에 고르게 분산되지 않기 때문입니다.

따라서 컨텍스트를 무작정 채우면 다음이 한꺼번에 나빠집니다.

- **비용 증가**: 입력 토큰만큼 과금
- **지연 시간(Latency) 증가**: 처리할 토큰이 많아짐
- **정확도 하락**: 중간 정보 소실, 주의 분산, 모순된 결론

이것을 통틀어 **컨텍스트 과부하(context overload)** 라고 부릅니다.

### 1.4 max_tokens 파라미터

API 요청에 넣는 설정값으로, **모델이 생성할 수 있는 출력 토큰의 최대 개수**를 제한합니다.

혼동하지 말아야 할 점:

- `max_tokens`는 **출력 길이 상한**일 뿐입니다.
- 입력(프롬프트)의 품질, 모델의 추론 능력, 일반화 성능과는 **아무 관계가 없습니다.**
- 이 값을 키운다고 모델이 "더 깊이 생각"하지 않습니다. 단지 더 길게 쓸 수 있게 될 뿐입니다.

```json
{
  "model": "claude-...",
  "max_tokens": 1024,
  "messages": [{"role": "user", "content": "..."}]
}
```

## 2. 예시로 가르치기: Zero-shot / One-shot / Few-shot

### 2.1 세 가지 방식

| 방식 | 예시 개수 | 설명 |
|---|---|---|
| Zero-shot | 0개 | 지시문만 주고 시킨다. "다음 티켓의 우선순위를 정하라." |
| One-shot | 1개 | 입력-출력 예시를 하나만 보여준다. |
| Few-shot | 보통 3~5개 | 여러 개의 입력-출력 쌍을 보여준다. |

**Few-shot prompting(퓨샷 프롬프팅)** 은 프롬프트 안에 "이런 입력이면 이런 출력"이라는 예시를 몇 개 넣어, 모델이 그 패턴을 따라 하도록 유도하는 기법입니다. 모델을 재학습시키는 것이 아니라, 단지 입력 안에 예시를 두는 것이므로 **In-Context Learning(문맥 내 학습)** 이라고도 부릅니다.

```
분류 규칙: 서비스 중단 여부와 영향 범위로 우선순위를 정한다.

입력: "결제 서버 전체 다운, 전 고객 결제 불가"
출력: P1

입력: "로그인 화면 오타 발견"
출력: P4

입력: "특정 브라우저에서만 장바구니 버튼 미작동"
출력: P3

입력: "{여기에 실제 티켓}"
출력:
```

### 2.2 왜 예시가 효과가 있는가

지시문(instruction)만으로는 "우선순위가 높다"의 기준이 사람마다, 상황마다 다릅니다. 예시는 **경계선이 어디에 그어져 있는지**를 구체적으로 보여줍니다. 특히 분류(classification) 작업에서 응답의 **일관성(consistency)** 을 크게 높여줍니다.

### 2.3 예시는 몇 개가 적절한가 — 3~5개

실무 경험칙은 **3~5개**입니다. 이유는 양쪽 극단이 모두 실패하기 때문입니다.

**너무 적을 때 (0~1개)**
- 모델이 일반적 패턴을 추출할 근거가 부족합니다.
- 특히 예시 하나가 "가장 어려운 예외 케이스"이면 최악입니다. 모델은 그 극단적 사례를 기준선으로 착각해서, 평범한 입력마저 그 사례처럼 취급하는 편향이 생깁니다.

**너무 많을 때 (수십 개)**
- 토큰 비용과 지연 시간이 늘어납니다.
- Lost in the Middle로 중간 예시가 무시됩니다.
- 그리고 아래 2.5의 **과적합/암기** 문제가 발생합니다.

### 2.4 예시를 어떻게 고르는가 — 다양성(Diversity)

개수보다 중요한 것이 **선택 기준**입니다.

- **다양성(diverse)**: 서로 다른 클래스, 서로 다른 유형을 고르게 덮어야 합니다. 5개가 전부 P1 사례라면 모델은 "전부 P1"이라고 답하게 됩니다.
- **대표성(representative)**: 실제 들어올 입력 분포를 반영해야 합니다.
- **경계 조건(edge case)을 의도적으로 포함**: 애매해서 사람도 헷갈렸던 경계 사례를 넣으면, 모델이 그 경계선을 어디에 그어야 하는지 배웁니다.

> **Edge case(예외/경계 케이스)** 란: 정상 범위의 가장자리에 있어 판단이 갈리는 입력. 예) "장애는 아니지만 성능이 심하게 느림" 같은 티켓.

**무작위 선택(random sampling)은 왜 나쁜가?** 언뜻 "선택 편향(selection bias)을 피한다"고 들리지만, 예시 5개짜리 표본에서는 무작위가 오히려 위험합니다.
- 희귀 클래스나 중요한 경계 케이스가 통째로 빠질 수 있습니다.
- 품질이 낮거나 그 자체로 애매한 과거 데이터가 뽑혀 들어와 잘못된 패턴을 가르칠 수 있습니다.
- 클래스 분포가 우연히 심하게 치우칠 수 있습니다.

즉 few-shot 예시 선택은 **의도적인 큐레이션(curation)** 작업이지, 통계 표본 추출이 아닙니다.

### 2.5 과적합(Overfitting)과 암기(Memorization)

**과적합**은 원래 머신러닝 용어로, 모델이 학습 데이터의 일반적 규칙 대신 개별 사례 자체를 외워버려 새로운 데이터에서 성능이 떨어지는 현상입니다. 프롬프트에서도 같은 일이 일어납니다.

전형적인 증상:

- 프롬프트에 넣어둔 20개 입력에 대해서는 완벽하게 맞춘다.
- 그런데 그 20개와 **비슷하지만 똑같지는 않은** 새 입력이 오면 성능이 뚝 떨어진다.

이것은 모델이 **판단 규칙(decision rule)을 배운 것이 아니라 입력-출력 문자열 쌍을 매칭하는 법을 배웠다**는 신호입니다. 예시가 너무 많고 서로 겹치면, 모델 입장에서는 "규칙을 추론"하는 것보다 "가장 비슷한 예시를 찾아 그대로 흉내내는" 편이 더 쉬운 전략이 되어버립니다.

### 2.6 일반화(Generalization)를 회복하는 법

해법은 예시를 더 넣는 것이 **아니라 줄이는 것**입니다.

- 예시 개수를 소수(3~5개)로 줄인다.
- 남길 예시는 **밑에 깔린 결정 규칙이 눈에 보이도록** 고른다. 즉 "이 세 개를 보면 규칙이 무엇인지 자연스럽게 유추된다"는 조합을 만든다.
- 필요하다면 예시와 함께 **규칙을 명시적 문장으로도 적는다.**

나쁜 방향의 예:
- 새 실패 사례가 나올 때마다 그 입력-출력 쌍을 계속 프롬프트에 덧붙이기 → 프롬프트가 무한히 커지고, 암기가 심해지고, Lost in the Middle까지 겹칩니다. 이것은 근본 원인(규칙이 드러나지 않음)을 고치지 않고 증상만 덮는 방식입니다.
- 예시를 전부 빼고 지시문 한 줄만 남기기(zero-shot) → 규칙이 복잡하거나 경계 케이스가 있는 분류에서는 정확도와 일관성이 떨어집니다.

**요약: 예시의 목적은 "사례를 다 덮는 것"이 아니라 "규칙을 드러내는 것"입니다.**

## 3. 도구 사용(Tool Use)과 구조화된 출력

### 3.1 왜 구조화된 출력이 필요한가

모델의 기본 출력은 자유 형식 텍스트입니다. 하지만 애플리케이션은 파싱 가능한 데이터를 원합니다. "청구서에서 총액과 품목을 뽑아 DB에 넣어라" 같은 작업에서 자유 텍스트를 정규식으로 파싱하는 것은 매우 취약합니다.

그래서 **Tool Use(도구 사용)** 기능을 사용합니다. 도구를 하나 정의하고 그 도구의 입력 형식을 **JSON Schema**로 선언하면, 모델은 그 스키마를 만족하는 JSON을 만들어 도구를 "호출"합니다. 실제로 도구를 실행할 필요조차 없습니다. 스키마에 맞는 JSON을 얻는 것 자체가 목적일 수 있습니다. 이 용법을 **구조화된 데이터 추출(Structured Data Extraction)** 이라고 부릅니다.

### 3.2 JSON Schema 기초

JSON Schema는 "이 JSON은 이런 모양이어야 한다"를 기술하는 표준입니다.

```json
{
  "name": "extract_invoice",
  "description": "청구서에서 품목과 총액을 추출한다",
  "input_schema": {
    "type": "object",
    "properties": {
      "line_items": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "description": { "type": "string" },
            "amount": { "type": "number" }
          },
          "required": ["description", "amount"]
        }
      },
      "order_total": { "type": "number" },
      "phone_number": { "type": ["string", "null"] }
    },
    "required": ["line_items", "order_total"]
  }
}
```

주요 키워드:

- `type`: 값의 자료형 (`string`, `number`, `integer`, `boolean`, `object`, `array`, `null`)
- `properties`: 객체가 가질 수 있는 필드 정의
- `required`: **반드시 존재해야 하는** 필드 이름 목록
- `enum`: 값이 지정된 후보 중 하나여야 함 (예: `"enum": ["P1","P2","P3","P4"]`)
- `items`: 배열 원소의 스키마
- `type: ["string", "null"]`: 문자열 **또는** null 허용 (nullable)

### 3.3 스키마가 보장하는 것 vs 보장하지 못하는 것 — 핵심 구분

이것이 이 주제 전체에서 가장 중요한 개념입니다.

**구문적 유효성(Syntactic Validity)** — 스키마가 보장함
- JSON 문법이 깨지지 않음
- 필드 타입이 맞음 (`amount`가 문자열이 아니라 숫자임)
- `required` 필드가 빠지지 않음
- `enum` 값이 후보 밖으로 나가지 않음

**의미적 정확성(Semantic Correctness)** — 스키마가 **보장하지 못함**
- 값이 원본 문서에 실제로 있던 값인가 (사실성)
- 필드들끼리 **논리적/산술적으로 앞뒤가 맞는가**
- 비즈니스 규칙을 지키는가 (예: 할인율은 총액보다 클 수 없다, 종료일은 시작일보다 뒤여야 한다)

**구체적인 예:**

```json
{
  "line_items": [
    {"description": "위젯 A", "amount": 500},
    {"description": "위젯 B", "amount": 440}
  ],
  "order_total": 980
}
```

품목 합계는 940인데 `order_total`은 980입니다. 그런데 이 JSON은 **스키마 검증을 완벽히 통과합니다.** 두 값 모두 유효한 `number`이고, 필수 필드도 다 있기 때문입니다.

이 불일치는 **스키마가 잡을 수 없는 의미적 오류(semantic error)** 입니다.
- 구문 오류(syntax error)가 **아닙니다.** 문법도 타입도 정상입니다.
- `required` 제약을 더한다고 막히지 **않습니다.** `required`는 "있느냐 없느냐"만 볼 뿐 값들 사이의 계산 관계를 보지 않습니다.
- `tool_choice` 설정을 바꾼다고 해결되지 **않습니다.** 도구 선택 방식과 산술 검증은 무관합니다.
- 일시적인 샘플링 잡음이라 무시해도 되는 것도 **아닙니다.** LLM은 원래 산술에 약하고 문서에서 잘못된 숫자를 집어올 수 있으므로 반복적으로 발생합니다.

### 3.4 다운스트림 검증(Downstream Validation)

그러므로 의미적 검증은 **모델 밖, 애플리케이션 코드에서** 해야 합니다. "다운스트림"은 모델의 응답을 받은 이후 단계라는 뜻입니다.

```python
def validate_invoice(data, tolerance=0.01):
    calculated_total = sum(item["amount"] for item in data["line_items"])
    if abs(calculated_total - data["order_total"]) > tolerance:
        return {
            "ok": False,
            "reason": "total_mismatch",
            "calculated_total": calculated_total,
            "stated_total": data["order_total"],
        }
    return {"ok": True}
```

이런 검증에 실패한 레코드는 자동 통과시키지 말고 재시도하거나 사람 검토로 보냅니다.

**설계 원칙: 스키마는 "형태"를 강제하고, 애플리케이션 코드는 "의미"를 검증한다.** 두 층은 서로를 대체할 수 없습니다.

### 3.5 required 필드가 환각을 유발하는 문제

원본 문서에 **없을 수도 있는 정보**를 `required`로 지정하면 심각한 부작용이 생깁니다.

상황: 지원 이메일에서 고객 전화번호를 뽑는 스키마인데, 오래된 이메일 상당수에는 전화번호가 아예 없습니다. 그런데 `phone_number`를 `required: string`으로 선언했습니다.

결과: 모델은 스키마를 만족시켜야 하므로 **그럴듯해 보이는 가짜 전화번호를 지어냅니다.** 이것이 **환각(hallucination)** 입니다. 스키마가 사실상 "빈칸을 채워라"라고 강요한 셈입니다.

**올바른 해법: 해당 필드를 선택적(optional)이고 nullable로 만든다.**

```json
{
  "properties": {
    "phone_number": {
      "type": ["string", "null"],
      "description": "문서에 전화번호가 명시된 경우에만 채운다. 없으면 null."
    }
  },
  "required": ["customer_name"]
}
```

- `required` 목록에서 빼면 → 필드를 아예 생략할 수 있습니다 (optional).
- `type`에 `"null"`을 함께 허용하면 → 명시적으로 `null`을 반환할 수 있습니다 (nullable).
- `description`에 "없으면 null"이라고 적어주면 모델이 의도를 더 정확히 이해합니다.

이러면 모델에게 **"모른다"고 말할 수 있는 합법적인 출구**가 생기고, 환각의 구조적 원인이 사라집니다.

**잘못된 대안들과 그 이유:**

- *도구 정의를 통째로 없애고 산문으로 부탁하기*: 환각은 줄 수 있으나 출력이 다시 자유 텍스트가 되어 파싱 안정성과 추출 정밀도를 잃습니다. 구조화의 이점을 통째로 버리는 것은 과잉 대응입니다.
- *`required`를 유지한 채 타입을 지역번호 `enum`으로 바꾸기*: 여전히 반드시 채워야 하므로, 모델은 이제 "후보 중에서 가짜 지역번호를 고르게" 될 뿐입니다. 근본 원인(필수 제약)이 그대로입니다.
- *`required`를 유지하고 `phone_number_confidence` 같은 신뢰도 필드를 추가하기*: 여전히 가짜 번호를 생성해야 하고, 스키마만 복잡해집니다. 또한 LLM이 스스로 매긴 신뢰도 점수는 잘 보정(calibrate)되어 있지 않아 신뢰하기 어렵습니다.

**일반 원칙: 스키마의 필수 제약은 "반드시 존재하는 정보"에만 건다. 부재 가능성이 있는 정보를 필수로 걸면 모델은 거짓말로 그 제약을 만족시킨다.**

### 3.6 원본 문서 내부의 충돌 처리

앞의 3.3은 모델이 계산을 틀린 경우였습니다. 이번에는 **원본 문서 자체가 서로 모순되는** 경우입니다.

상황: 임대차 계약서 1페이지 요약 조항에는 월세 $1,800, 4페이지 지급 일정표에는 $1,850. 둘 다 문서에 실제로 적혀 있고, 둘 다 깔끔하게 추출되는 유효한 숫자입니다.

이때 추출 시스템이 임의로 하나를 고르면 안 됩니다. 어느 쪽이 맞는지는 **법적/계약적 판단**이며 데이터 파이프라인이 내릴 결정이 아닙니다.

**모범 사례 — 충돌을 데이터로 표현하고 사람에게 넘긴다:**

```json
{
  "monthly_rent_candidates": [
    {"value": 1800, "source": "요약 조항, p.1"},
    {"value": 1850, "source": "지급 일정표, p.4"}
  ],
  "conflict_detected": true
}
```

그리고 `conflict_detected: true`인 레코드는 자동 처리 흐름에서 빼내 **사람이 확인/조정(human reconciliation)** 하도록 라우팅합니다. 이 패턴을 **Human-in-the-Loop(사람 개입)** 이라고 부릅니다.

**해서는 안 되는 처리들:**

- *더 상세해 보이는 섹션의 값을 택하기*: "상세한 섹션이 더 정확할 것"이라는 것은 시스템의 근거 없는 추측입니다.
- *두 값을 평균 내기 ($1,825)*: 문서 어디에도 없는 숫자를 만들어내는 것이므로 그 자체가 환각이며, 계약 금액으로는 명백히 틀린 값입니다.
- *먼저 나온 값만 취하고 뒤의 값을 조용히 버리기*: 충돌이 있었다는 사실 자체가 소실되어, 나중에 문제를 추적할 수도 없습니다. 데이터 손실이며 감사(audit) 불가능합니다.

**원칙: 모호할 때 추측하지 말고, 모호하다는 사실을 출력에 명시적으로 표현하라(fail loudly, not silently).**

### 3.7 tool_choice: 도구 호출 강제하기

`tool_choice`는 모델이 도구를 호출할지 말지를 제어하는 API 파라미터입니다.

| 값 | 동작 |
|---|---|
| `{"type": "auto"}` | 모델이 알아서 판단. 도구를 호출할 수도, 그냥 텍스트로 답할 수도 있음. 기본값. |
| `{"type": "any"}` | 등록된 도구 중 **아무거나 하나는 반드시** 호출해야 함. |
| `{"type": "tool", "name": "tag_document"}` | **지정한 그 도구를 반드시** 호출해야 함. |
| `{"type": "none"}` | 도구를 호출하지 않음. |

`any`와 `{"type":"tool", ...}` 두 가지를 묶어 **강제 도구 선택(Forced Tool Selection)** 이라고 부릅니다.

**언제 강제하는가:** "모든 입력 문서는 반드시 태깅되어야 한다"처럼 **구조화된 출력이 필수 요구사항**일 때입니다. `auto`로 두면 모델이 도구를 호출하지 않고 일반 텍스트로 답해버릴 수 있고, 그러면 파이프라인이 깨집니다. 즉 `auto`와 강제 모드의 차이는 **출력 형식을 보장하느냐 마느냐**의 차이입니다.

## 4. Extended Thinking (확장 추론)

### 4.1 무엇인가

**Extended Thinking**은 모델이 최종 답변을 내놓기 전에 내부적으로 추론 과정을 길게 전개하도록 하는 기능입니다. 이 추론에 쓰이는 토큰을 **thinking token(추론 토큰)** 이라 하고, 얼마나 쓸지를 **thinking budget(추론 예산)** 또는 **effort 수준**으로 설정합니다.

수학, 복잡한 코드 작성, 다단계 판단처럼 한 번에 답하기 어려운 작업에서 정확도를 올려줍니다.

### 4.2 tool_choice와의 호환 제약

중요한 API 제약이 있습니다.

> **Extended Thinking은 `tool_choice`가 `auto` 또는 `none`일 때만 사용할 수 있습니다. 강제 도구 선택(`any`, 또는 특정 도구 이름 지정)과는 함께 쓸 수 없으며, 함께 요청하면 API 에러가 발생합니다.**

즉 `any`도 강제 선택의 일종이므로 호환되지 않습니다. `any`가 예외적으로 허용된다는 식의 이해는 틀립니다.

**충돌이 났을 때 무엇을 포기할 것인가?** 두 기능을 동시에 쓸 수 없으므로 하나를 버려야 하는데, **시스템의 핵심 요구사항이 무엇인지**를 기준으로 판단합니다.

- 요구사항이 "모든 문서가 예외 없이 태깅되어야 한다"라면, 도구 강제는 그 요구사항을 보장하는 유일한 수단이므로 **강제를 유지하고 Extended Thinking을 끕니다.**
- `auto`로 바꾸면 에러는 사라지지만 모델이 도구를 건너뛸 수 있으므로 요구사항이 깨집니다. 에러를 없애려다 기능을 잃는 셈입니다.

또한 `input_schema` 안에 `thinking_mode` 같은 필드를 넣어 제약을 우회한다는 발상은 성립하지 않습니다. `input_schema`는 **도구가 받을 인자의 모양**을 기술하는 곳이지 API 동작을 바꾸는 곳이 아니며, 그런 필드는 존재하지도 않습니다. 스키마 내용은 API 파라미터 검증에 아무 영향을 주지 않습니다.

### 4.3 Extended Thinking이 해결하지 못하는 것

Extended Thinking은 **더 오래, 더 깊이 생각하게** 해줍니다. 하지만 **누구의 관점에서 생각하는지는 바꾸지 못합니다.** 이 한계가 5장의 주제로 이어집니다.

## 5. 에이전트 아키텍처: 생성자와 검증자의 분리

### 5.1 에이전트와 서브에이전트

**에이전트(Agent)** 는 LLM이 도구를 사용하며 여러 단계에 걸쳐 작업을 수행하는 구성입니다. **서브에이전트(Subagent)** 는 상위 에이전트가 특정 하위 작업을 맡기려고 띄우는 별도의 에이전트 인스턴스로, 보통 자기만의 컨텍스트와 도구 집합을 가집니다.

### 5.2 자가 검토(Self-Review)는 왜 잘 안 되는가

흔한 설계: 코드를 생성한 다음, **같은 대화(세션) 안에서** "끝내기 전에 네 작업을 다시 읽고 실수를 지적하라"고 지시하는 것.

관찰되는 현상: 이 자가 검토는 문제를 거의 찾아내지 못하고, 나중에 새로운 리뷰어가 보면 문제가 발견됩니다.

**원인은 확증 편향(Confirmation Bias) / 자기 일관성 편향(Self-Consistency Bias)** 입니다.

모델은 코드를 생성하면서 그 설계 결정들을 이미 채택했고, 그 근거가 대화 이력에 그대로 남아 있습니다. 다음 토큰을 예측할 때 모델은 앞선 컨텍스트와 **일관되게** 이어가려는 강한 경향이 있습니다. 방금 스스로 정당화한 선택을 이제 와서 부정하는 것은 그 일관성을 깨는 방향이므로, 확률적으로 불리합니다. 결과적으로 모델은 자기 결정을 재확인하는 쪽으로 기울고 비판을 회피합니다.

**흔한 오해들:**

- *"명령문 대신 질문형으로 바꾸면 된다"* → 문장 형식은 편향의 원인이 아닙니다. 원인은 컨텍스트 공유입니다.
- *"파일을 다시 읽을 권한이 없어서 그렇다"* → 생성자는 자기가 방금 쓴 내용을 컨텍스트에 갖고 있고, 보통 파일 읽기 도구도 있습니다. 접근성 문제가 아닙니다.
- *"Extended Thinking이 꺼져 있어서 그렇다"* → 4.3에서 본 대로, 켜도 같은 세션에서는 같은 편향이 유지됩니다.
- *"self-review 지시를 더 엄격하게 쓰면 된다"* → 프롬프트 문구를 강화해도 오염된 컨텍스트 자체가 남아 있는 한 편향은 사라지지 않습니다.
- *"같은 세션에서 두 번 검토하게 하면 된다"* → 같은 편향된 컨텍스트에서의 반복일 뿐이고, 오히려 첫 검토 결론까지 컨텍스트에 쌓여 편향이 강화됩니다. 비용만 두 배가 됩니다.

### 5.3 해법: 생성자-검증자 분리 (Generator-Evaluator Separation)

**독립된 두 번째 인스턴스**를 띄워서 검토하게 합니다. 핵심 조건은 그 인스턴스가 **생성 세션의 대화 이력에 접근하지 못하는 것(fresh context)** 입니다.

새 인스턴스는 코드가 어떤 논리로 쓰였는지, 어떤 근거로 정당화되었는지 모릅니다. 오직 결과물만 보고 판단하므로, 코드가 실제로 요구사항을 만족하는지 편향 없이 평가할 수 있습니다. 이것이 소프트웨어 공학에서 작성자와 리뷰어를 분리하는 이유와 정확히 같은 원리입니다.

```
[생성자 세션]  코드 작성  ──▶  산출물(diff/파일)
                                    │
                        (대화 이력은 전달하지 않음)
                                    ▼
[리뷰어 세션]  백지 상태에서 산출물만 보고 검토
```

이것은 프롬프트 문구 조정이 아니라 **아키텍처 수준의 변경**입니다. 그래서 근본적으로 효과가 있습니다.

### 5.4 리뷰 서브에이전트의 권한 설계 — 최소 권한 원칙

리뷰 전용 서브에이전트는 코드를 **분석만 하고 절대 수정하면 안 된다**는 제약을 가지는 경우가 많습니다. 이를 어떻게 보장할까요?

에이전트 설정에는 보통 **`tools` 필드**가 있어서, 그 에이전트가 쓸 수 있는 도구 목록을 지정합니다.

대표적인 도구들:

| 도구 | 성격 | 하는 일 |
|---|---|---|
| `Read` | 읽기 전용 | 파일 내용 읽기 |
| `Grep` | 읽기 전용 | 파일 내용 패턴 검색 |
| `Glob` | 읽기 전용 | 파일 경로 패턴 검색 |
| `Edit` | 쓰기 | 파일 수정 |
| `Write` | 쓰기 | 파일 생성/덮어쓰기 |
| `Bash` | **사실상 쓰기** | 임의의 셸 명령 실행 |

**올바른 설정: `tools`를 읽기 전용 도구만으로 명시적으로 제한한다.**

```yaml
name: code-reviewer
tools: Read, Grep, Glob
```

`Edit`, `Write`는 물론이고 **`Bash`도 반드시 제외해야 합니다.** Bash가 있으면 `sed -i`, `echo > file`, `rm` 같은 명령으로 얼마든지 파일을 바꿀 수 있기 때문입니다. "Bash는 파일을 읽는 데만 쓸 것"이라는 가정은 성립하지 않습니다. Bash는 읽기 도구가 아니라 **임의 실행 권한**입니다.

**잘못된 대안들:**

- *`tools` 필드를 비워두고(=부모의 모든 도구 상속) 프롬프트로 "Edit/Write 쓰지 마"라고 지시하기*: 이것은 **소프트 제약(soft constraint)** 입니다. 모델이 지시를 어기거나, 프롬프트 인젝션으로 우회되거나, 단순히 헷갈리면 파일이 수정됩니다. 지시는 보장이 아닙니다.
- *수정 권한을 주되 매 수정마다 수동 승인을 받게 하기*: 사람이 실수로 승인할 수 있고, 승인 피로(approval fatigue)로 무비판적 클릭이 발생합니다. 무엇보다 "수정 불가"라는 요구를 **구조적으로 보장하지 못합니다.**

**원칙: 하드 제약(도구 자체를 주지 않음) > 소프트 제약(프롬프트로 부탁함).** 이것이 보안의 **최소 권한 원칙(Principle of Least Privilege)** 입니다. 필요한 최소한의 권한만 부여하면, 위반이 "일어나지 않기를 바라는" 것이 아니라 **애초에 불가능해집니다.**

### 5.5 대규모 리뷰의 분할: Map-Reduce 패턴

상황: 60개 파일을 건드린 리팩토링 diff를 리뷰어 인스턴스 하나에 통째로 넣었더니, 파일마다 **서로 모순되는 지적**이 나옵니다.

원인은 1.3의 컨텍스트 과부하입니다. 입력이 너무 커서 모델의 주의가 분산되고, 앞부분에서 세운 기준을 뒷부분에서 잊거나 다르게 적용합니다.

**해법: 리뷰를 두 단계로 나눈다 (계층적 리뷰 / Multi-pass Review).**

1. **파일별 패스 (per-file pass) — Map 단계**
   각 파일을 독립적으로, 작은 컨텍스트에서 검토합니다. 지역적(local) 버그, 스타일, 로직 오류를 정밀하게 잡습니다. 병렬 실행도 가능합니다.

2. **통합 패스 (integration pass) — Reduce 단계**
   개별 결과와 인터페이스 변경 요약을 모아, **파일 간 일관성(cross-file consistency)** 을 검토합니다. 함수 시그니처 변경이 모든 호출부에 반영되었는지, 계약이 깨진 곳은 없는지 같은 것들입니다.

지역적 문제와 전역적 문제는 성격이 다르므로 서로 다른 패스에서 다루는 것이 맞습니다.

**잘못된 대안들:**

- *컨텍스트 윈도우만 더 키우기*: diff가 들어가긴 하지만 Lost in the Middle과 주의 분산은 그대로입니다. "담을 수 있다"가 "잘 볼 수 있다"를 뜻하지 않습니다.
- *같은 전체 diff를 두 번 돌려 공통으로 나온 지적만 채택하기*: 과부하 자체가 해결되지 않으므로 두 실행 모두 부정확합니다. 비용만 두 배가 되고, 한 번만 발견된 진짜 버그는 버려집니다.
- *커밋을 잘게 나눠 최신 커밋만 매번 전부 리뷰하기*: 개별 커밋은 잘 보게 되지만, 60개 파일에 걸친 **전체 리팩토링의 맥락**과 파일 간 일관성은 영원히 검토되지 않습니다.

## 6. 프롬프트 평가와 회귀 테스트

### 6.1 왜 필요한가

프롬프트는 코드와 비슷합니다. 고치면 좋아질 수도 있지만, 다른 곳이 망가질 수도 있습니다. 그런데 프롬프트는 동작이 확률적이라 "읽어보고 괜찮은지" 판단하는 것이 특히 불가능합니다. 프롬프트를 바꿨다면 **측정해야 합니다.**

### 6.2 분류 성능의 기본 지표

어떤 항목을 "문제 있음"으로 지적하는 시스템(코드 리뷰 봇, 스팸 필터 등)을 생각합시다.

| | 실제로 문제 있음 | 실제로 문제 없음 |
|---|---|---|
| **문제 있다고 지적** | True Positive (TP) | **False Positive (FP)** |
| **지적 안 함** | False Negative (FN) | True Negative (TN) |

- **False Positive(거짓 양성 / 오탐)**: 문제가 없는데 문제라고 지적한 것. 사용자가 가장 짜증내는 오류이며, 오탐이 많으면 사람들이 시스템 전체를 무시하기 시작합니다.
- **False Negative(거짓 음성 / 미탐)**: 진짜 문제를 놓친 것.
- **False Positive Rate(오탐율)**: 문제없는 항목 중 잘못 지적된 비율.
- **Precision(정밀도)**: 지적한 것들 중 실제로 맞았던 비율 = TP / (TP + FP).
- **Recall(재현율)**: 실제 문제들 중 찾아낸 비율 = TP / (TP + FN).

### 6.3 Held-out 데이터셋과 골든 데이터셋

**Held-out set(격리 평가 세트)** 은 프롬프트를 개선할 때 **보지 않고 따로 떼어둔** 평가 전용 데이터입니다. 개발 중에 보면서 튜닝한 데이터로 성능을 재면, 그 데이터에 맞춰 조정한 결과를 자기가 채점하는 셈이라 점수가 부풀려집니다.

**Golden dataset / Ground truth(정답 데이터)** 는 각 입력에 대해 **정답이 이미 확정되어 있는** 데이터입니다. 예를 들어 과거 PR들과, 그 PR에서 실제로 유효했던 지적/오탐이었던 지적 기록.

### 6.4 회귀 테스트(Regression Testing) 절차

프롬프트를 고친 뒤 전체 배포 전에 밟아야 할 표준 절차:

1. 정답이 알려진 held-out 데이터셋을 준비한다.
2. 수정된 프롬프트를 그 데이터셋 전체에 대해 실행한다.
3. 오탐율, 정밀도 등 **정량 지표**를 계산한다.
4. 목표 기준(예: 오탐율 5% 이하)을 만족하는지 확인한다.
5. 기존에 잘 되던 케이스가 망가지지 않았는지(회귀 여부)도 함께 본다.
6. 통과하면 배포한다.

**전형적인 시나리오:** 코드 리뷰 에이전트의 "성능 제안" 카테고리가 오탐이 너무 많아 일시 비활성화했고, 판단 기준을 구체적이고 검증 가능한 규칙으로 다시 썼습니다. 이제 팀 전체에 다시 켜도 될까요? → **다시 켜기 전에 held-out PR 세트로 돌려보고 오탐율이 실제로 목표치까지 떨어졌음을 데이터로 확인해야 합니다.**

**부적절한 검증 방식들:**

- *규칙을 명확하게 썼으니 검증 없이 바로 켠다*: 프롬프트 문구가 명확하다는 것과 모델이 그 문구대로 행동한다는 것은 별개입니다. 검증 없는 배포는 추측입니다. 게다가 새 규칙이 다른 유형의 오탐이나 미탐을 만들었을 수도 있습니다.
- *시니어 엔지니어 한 명이 소수의 과거 PR을 눈으로 훑어보고 판단한다*: 표본이 작고(통계적으로 무의미), 편향되어 있으며(오탐을 냈던 케이스만 봄 → 미탐은 전혀 확인 안 됨), 주관적이고, 정량 지표가 없어 "얼마나 좋아졌는지" 말할 수 없습니다.
- *오탐을 신고한 엔지니어의 PR에만 켜서 파일럿한다*: 실제 운영 환경에서 검증되지 않은 것을 돌리는 것이고, 한 사람의 코드는 다양성이 없으며, 그 사람에게 테스트 부담을 떠넘깁니다. 과거 데이터로 오프라인 측정하면 될 일을 굳이 프로덕션에서 할 이유가 없습니다.

**원칙: 사람의 인상(impression)이 아니라 재현 가능한 정량 지표로 판단한다.**

## 7. Message Batches API와 custom_id

### 7.1 배치 처리란

수천~수만 건의 요청(예: 문서 대량 번역)을 실시간으로 하나씩 보내는 대신, **한 번에 묶어서 제출하고 나중에 결과를 받아오는** 방식입니다. Anthropic의 **Message Batches API**가 이 역할을 하며, 실시간 API보다 저렴하고 대량 처리에 적합합니다. 대신 즉시 응답하지 않고 시간이 걸립니다.

### 7.2 custom_id: 결과와 요청을 다시 이어붙이는 열쇠

배치는 결과가 **제출한 순서대로 돌아온다는 보장이 없습니다.** 그래서 각 요청에 개발자가 직접 붙이는 식별자가 필요한데, 그것이 **`custom_id`** 입니다. 결과를 받으면 `custom_id`를 보고 원래 어떤 요청의 답인지 매칭(correlate)합니다.

```json
{
  "requests": [
    {
      "custom_id": "doc-2026-report_final",
      "params": {
        "model": "claude-...",
        "max_tokens": 1024,
        "messages": [{"role": "user", "content": "다음 문서를 한국어로 번역: ..."}]
      }
    }
  ]
}
```

### 7.3 custom_id의 형식 제약

`custom_id`에는 엄격한 문자 제한이 있습니다.

**허용되는 문자:**
- 영문 대소문자 `a-z`, `A-Z`
- 숫자 `0-9`
- 하이픈 `-`
- 언더스코어 `_`

**길이 제한:** 최대 64자.

**추가로:** 하나의 배치 안에서 `custom_id`는 **중복될 수 없습니다(고유해야 함).**

허용되지 않는 문자를 쓰면 배치 제출 시 **유효성 검사 에러(validation error)** 로 거부됩니다. 대표적으로 금지되는 것들:

| 예시 | 문제 |
|---|---|
| `doc/2026/report:final` | 슬래시 `/`, 콜론 `:` 불가 |
| `doc#2026#report#final#v2` | 샵 `#` 불가 |
| `doc 2026 report final v2` | 공백 불가 |
| `doc-2026-report_final` | **유효함** (영숫자, 하이픈, 언더스코어만 사용) |

"추적하기 편하다", "눈으로 읽기 좋다" 같은 이유는 API 규격을 바꿔주지 않습니다. **의미 있는 정보를 넣고 싶다면 허용된 문자만으로 인코딩해야 합니다.** 예: 날짜와 구획을 하이픈/언더스코어로만 구분한 `doc-20260315-report_final-v2`.

## 8. 전체를 관통하는 설계 원칙 정리

이 주제 전체에서 반복되는 사고방식을 다섯 줄로 정리하면 다음과 같습니다.

1. **더 많이 넣는 것이 더 좋은 것이 아니다.** 예시도, 컨텍스트도, diff도 — 양이 늘면 비용·지연·부정확이 함께 늘어난다. 선별과 분할이 답이다.
2. **형태의 보장과 내용의 보장은 다르다.** 스키마는 구문을 보장할 뿐, 의미·산술·사실성은 애플리케이션 코드가 검증해야 한다.
3. **모델에게 "모른다"고 말할 출구를 줘라.** 출구가 없으면 모델은 제약을 만족시키기 위해 거짓을 만들어낸다(필수 필드 → 환각).
4. **모호할 때는 추측하지 말고 드러내라.** 충돌 플래그를 세우고 사람에게 넘기는 것이 조용히 하나를 고르는 것보다 항상 낫다.
5. **부탁(soft)이 아니라 구조(hard)로 보장하라.** 프롬프트로 "하지 마"라고 하는 대신 도구를 주지 않는다. 같은 세션에서 반성시키는 대신 독립된 인스턴스를 띄운다. 감으로 판단하는 대신 held-out 세트로 측정한다.

## 9. 용어 사전 (Glossary)

### 프롬프트 기법

- **Prompt Engineering (프롬프트 엔지니어링)**: 모델을 재학습하지 않고 입력 텍스트 설계만으로 원하는 동작을 끌어내는 기술.
- **Zero-shot**: 예시 없이 지시문만으로 작업을 시키는 방식.
- **One-shot**: 입력-출력 예시를 하나만 제공하는 방식.
- **Few-shot Prompting (퓨샷 프롬프팅)**: 프롬프트에 소수(보통 3~5개)의 입력-출력 예시를 넣어 패턴을 학습시키는 기법.
- **In-Context Learning (문맥 내 학습)**: 가중치 변경 없이 프롬프트 안의 예시만으로 모델이 작업 패턴을 파악하는 현상.
- **Diverse Examples (다양성 있는 예시)**: 서로 다른 클래스와 유형을 고르게 덮는 예시 집합. few-shot 품질의 핵심.
- **Edge Case (경계/예외 케이스)**: 정상 범위의 가장자리에 있어 판단이 갈리는 입력. 의도적으로 예시에 포함시켜야 경계선이 학습된다.
- **Decision Rule (결정 규칙)**: 분류 판단의 밑에 깔린 원리. 예시는 이 규칙이 드러나도록 골라야 한다.
- **Overfitting (과적합)**: 규칙 대신 개별 사례를 외워버려, 비슷하지만 새로운 입력에서 성능이 떨어지는 현상.
- **Memorization (암기)**: 과적합의 프롬프트 버전. 입력-출력 문자열 매칭에 의존하게 되는 것.
- **Generalization (일반화)**: 학습에 쓰이지 않은 새 입력에도 올바르게 대응하는 능력. 예시를 줄이고 규칙을 드러내면 개선된다.
- **Selection Bias (선택 편향)**: 표본을 고르는 방식 때문에 생기는 치우침. 다만 few-shot에서는 무작위 추출이 이를 해결해주지 않는다.

### 컨텍스트와 파라미터

- **Token (토큰)**: 모델이 텍스트를 처리하는 최소 단위. 비용과 지연의 계산 기준.
- **Context Window (컨텍스트 윈도우)**: 한 요청에서 모델이 볼 수 있는 최대 토큰 수. 시스템 프롬프트·이력·입력·출력이 모두 포함된다.
- **Context Overload (컨텍스트 과부하)**: 입력이 지나치게 커져 정확도·비용·지연이 모두 나빠지는 상태.
- **Lost in the Middle**: 긴 컨텍스트에서 중간에 위치한 정보를 모델이 상대적으로 놓치는 현상.
- **max_tokens**: 모델이 생성할 수 있는 출력 토큰 수의 상한. 추론 품질이나 일반화와는 무관하다.
- **Latency (지연 시간)**: 요청부터 응답까지 걸리는 시간. 입출력 토큰 수에 비례해 증가한다.

### 도구 사용과 구조화된 출력

- **Tool Use (도구 사용)**: 모델이 미리 정의된 도구를 스키마에 맞는 인자와 함께 호출하도록 하는 기능. 구조화된 출력을 얻는 수단이기도 하다.
- **tool_use (응답 블록)**: 모델이 도구를 호출하겠다고 반환하는 응답 형태. 스키마를 만족하는 JSON을 담고 있다.
- **Structured Output / Structured Data Extraction (구조화된 출력/데이터 추출)**: 자유 텍스트가 아니라 정해진 스키마의 JSON 형태로 결과를 받아내는 방식.
- **JSON Schema**: JSON의 구조·타입·필수 여부를 기술하는 표준 명세.
- **input_schema**: 도구가 받을 인자의 모양을 기술하는 JSON Schema 필드. API 동작을 바꾸는 곳이 아니다.
- **required (필수 필드)**: 스키마에서 반드시 존재해야 하는 필드 목록. 값의 존재만 강제하고 값들 사이의 관계는 검증하지 않는다.
- **optional (선택 필드)**: `required` 목록에 없어 생략 가능한 필드.
- **nullable (null 허용)**: `type: ["string", "null"]`처럼 명시적으로 null을 반환할 수 있는 필드. 환각 방지의 핵심 장치.
- **enum**: 값이 미리 정한 후보 목록 중 하나여야 한다는 제약.
- **Syntactic Validity (구문적 유효성)**: JSON 문법, 타입, 필수 필드 존재 등 형태 차원의 정확성. 스키마가 보장한다.
- **Semantic Correctness (의미적 정확성)**: 값의 사실성, 필드 간 산술·논리 일관성, 비즈니스 규칙 준수. 스키마가 보장하지 못한다.
- **Semantic Error (의미적 오류)**: 스키마는 통과하지만 의미상 앞뒤가 안 맞는 오류. 예) 품목 합계 940 ≠ 총액 980.
- **Downstream Validation (후속 검증)**: 모델 응답을 받은 뒤 애플리케이션 코드에서 수행하는 의미 수준 검증.
- **calculated_total vs stated_total**: 개별 항목을 직접 합산한 값과 문서/모델이 제시한 총액. 둘을 비교하는 것이 대표적인 다운스트림 검증.
- **Hallucination (환각)**: 모델이 근거 없는 정보를 그럴듯하게 지어내는 현상. 필수 필드 강제, 모호성 강제 해소가 주된 유발 요인.
- **conflict_detected**: 원본 문서 내 값들이 서로 충돌할 때 출력에 세우는 플래그. 자동 처리에서 제외하고 사람에게 넘기기 위한 신호.
- **Human-in-the-Loop (사람 개입)**: 자동 처리가 확신할 수 없는 케이스를 사람 검토로 라우팅하는 설계 패턴.
- **Human Reconciliation (사람의 조정)**: 충돌한 데이터를 사람이 확인해 최종 값을 결정하는 절차.

### tool_choice와 Extended Thinking

- **tool_choice**: 도구 호출 여부와 방식을 제어하는 API 파라미터.
- **auto**: 모델이 도구 호출 여부를 스스로 결정. 도구를 건너뛸 수 있으므로 출력 형식이 보장되지 않는다.
- **any**: 등록된 도구 중 아무거나 하나는 반드시 호출. 강제 도구 선택의 일종.
- **tool (named tool)**: `{"type":"tool","name":"..."}` 형태로 특정 도구를 반드시 호출하게 하는 설정.
- **none**: 도구를 호출하지 않도록 하는 설정.
- **Forced Tool Selection (강제 도구 선택)**: `any` 및 특정 도구 지정을 아우르는 개념. 구조화된 출력이 필수일 때 사용한다.
- **Extended Thinking (확장 추론)**: 최종 답변 전에 내부 추론을 길게 전개하는 기능. `tool_choice`가 `auto` 또는 `none`일 때만 사용 가능하며, 강제 도구 선택과 함께 쓰면 API 에러가 난다.
- **Thinking Budget / Effort (추론 예산/노력 수준)**: Extended Thinking에 할당하는 토큰 양. 늘려도 동일 세션의 확증 편향은 해소되지 않는다.

### 에이전트 아키텍처

- **Agent (에이전트)**: LLM이 도구를 사용해 여러 단계 작업을 수행하는 구성.
- **Subagent (서브에이전트)**: 상위 에이전트가 하위 작업을 위해 띄우는 별도 인스턴스. 고유한 컨텍스트와 도구 집합을 가진다.
- **tools 필드**: 에이전트가 사용할 수 있는 도구 목록을 명시하는 설정. 여기서 뺀 도구는 애초에 사용할 수 없다.
- **Read / Grep / Glob**: 각각 파일 읽기, 내용 검색, 경로 검색을 하는 읽기 전용 도구.
- **Edit / Write**: 파일을 수정·생성하는 쓰기 도구.
- **Bash**: 임의의 셸 명령을 실행하는 도구. 읽기용으로 보이지만 실질적으로 파일 수정이 가능하므로 읽기 전용 에이전트에서는 반드시 제외한다.
- **Principle of Least Privilege (최소 권한 원칙)**: 작업에 꼭 필요한 최소한의 권한만 부여하는 보안 원칙.
- **Hard Constraint (하드 제약)**: 시스템 구조상 위반이 불가능한 제약. 예) 도구를 주지 않음.
- **Soft Constraint (소프트 제약)**: 프롬프트 지시처럼 모델이 어길 수 있는 제약. 보안 경계로 신뢰할 수 없다.
- **Permission Mode (권한 모드)**: 도구 실행 전 수동 승인 등을 요구하는 설정. 승인 피로 때문에 하드 차단의 대체재가 되지 못한다.
- **Generator (생성자)**: 결과물을 만들어내는 인스턴스/역할.
- **Evaluator / Reviewer (검증자/리뷰어)**: 결과물을 검토하는 인스턴스/역할.
- **Generator-Evaluator Separation (생성자-검증자 분리)**: 생성과 검증을 서로 다른 인스턴스에 맡기는 아키텍처 원칙.
- **Self-Review / Self-Correction (자가 검토/자가 수정)**: 같은 세션에서 모델이 자기 출력을 검토하는 방식. 확증 편향 때문에 효과가 제한적이다.
- **Confirmation Bias (확증 편향)**: 이미 내린 결정을 지지하는 방향으로 판단이 기우는 경향.
- **Self-Consistency Bias (자기 일관성 편향)**: 모델이 앞선 컨텍스트와 일관되게 이어가려다 자기 오류를 부정하지 못하는 현상.
- **Fresh Context / Fresh Reviewer (백지 컨텍스트/새 리뷰어)**: 생성 세션의 이력에 접근하지 않는 독립 인스턴스. 편향 없는 검토의 전제 조건.
- **Separation of Concerns (관심사의 분리)**: 서로 다른 책임을 별도 구성 요소로 나누는 설계 원칙.
- **Multi-pass Review (다단계 리뷰)**: 리뷰를 여러 패스로 나누어 수행하는 구조.
- **Per-file Pass (파일별 패스)**: 각 파일을 독립적으로 검토해 지역적 문제를 잡는 단계(Map).
- **Integration Pass (통합 패스)**: 파일 간 일관성과 인터페이스 정합성을 검토하는 단계(Reduce).
- **Cross-file Consistency (파일 간 일관성)**: 여러 파일에 걸친 변경이 서로 모순 없이 맞물리는 성질.
- **Map-Reduce**: 큰 작업을 나눠 처리(Map)한 뒤 결과를 합쳐 정리(Reduce)하는 패턴.

### 평가와 품질 관리

- **Prompt Evaluation (프롬프트 평가)**: 프롬프트 변경의 효과를 정량 지표로 측정하는 활동.
- **Regression Testing (회귀 테스트)**: 변경이 기존에 잘 되던 것을 망가뜨리지 않았는지 확인하는 테스트.
- **Held-out Set (격리 평가 세트)**: 튜닝에 사용하지 않고 따로 떼어둔 평가 전용 데이터.
- **Golden Dataset / Ground Truth (정답 데이터)**: 각 입력의 정답이 확정되어 있는 기준 데이터셋.
- **Known Findings (기지의 결과)**: 과거 데이터에 대해 이미 확인된 정답 라벨.
- **False Positive (거짓 양성/오탐)**: 문제가 없는데 문제라고 지적한 오류.
- **False Negative (거짓 음성/미탐)**: 실제 문제를 놓친 오류.
- **False Positive Rate (오탐율)**: 문제없는 항목 중 잘못 지적된 비율.
- **Precision (정밀도)**: 지적한 것 중 실제로 맞은 비율.
- **Recall (재현율)**: 실제 문제 중 찾아낸 비율.
- **Failure Mode (실패 유형)**: 시스템이 잘못되는 특정 방식. 개선책이 새로운 실패 유형을 만들지 않는지 확인해야 한다.

### 배치 API

- **Message Batches API**: 대량 요청을 묶어 비동기로 처리하는 API. 실시간 호출보다 저렴하다.
- **custom_id**: 배치 내 각 요청을 식별하기 위해 개발자가 부여하는 문자열. 결과와 원본 요청을 매칭하는 데 사용된다. 영문자·숫자·하이픈(`-`)·언더스코어(`_`)만 허용되며 최대 64자, 배치 내에서 고유해야 한다.
- **Correlate (매칭/연관 짓기)**: 반환된 결과를 `custom_id`로 원래 요청과 이어붙이는 작업.
- **Validation Error (유효성 검사 에러)**: 규격에 맞지 않는 요청이 API 단계에서 거부되는 오류.
