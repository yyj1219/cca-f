## 0. 먼저 알아야 할 대전제: LLM은 "기억"이 없다

대규모 언어 모델(LLM)은 요청 한 번마다 **그 요청에 담겨 온 텍스트만** 봅니다. 이전 요청에서 무슨 일이 있었는지 서버가 알아서 기억해 주지 않습니다.

- 대화가 이어지는 것처럼 보이는 이유는, 클라이언트(우리 코드)가 **지금까지의 대화 전체를 매번 다시 보내주기** 때문입니다.
- 이 "매번 다시 보내는 텍스트 뭉치"를 **컨텍스트(context)** 라고 하고, 한 번에 담을 수 있는 최대 분량을 **컨텍스트 윈도우(context window)** 라고 합니다.

이 한 문장이 이 문서 전체를 관통합니다: **모델은 컨텍스트에 들어 있는 것만 안다.** 뒤에 나오는 "도구 결과가 사라져 같은 도구를 또 부른다", "서브에이전트가 형제 에이전트의 결과를 모른다", "서버리스 컨테이너에서 세션 재개가 안 된다" 같은 문제는 전부 이 원리의 다른 얼굴입니다.

## 1. Messages API와 도구 사용(Tool Use)의 원리

### 1.1 Messages API 기본 구조

Anthropic의 Messages API는 `messages`라는 배열을 받습니다. 배열의 각 원소는 `role`(`"user"` 또는 `"assistant"`)과 `content`를 가집니다. `content`는 단순 문자열일 수도 있고, **블록(block)들의 배열**일 수도 있습니다.

블록의 종류:

| 블록 타입 | 누가 만드나 | 의미 |
|---|---|---|
| `text` | 모델 / 사용자 | 평범한 텍스트 |
| `tool_use` | 모델(assistant) | "이 도구를 이런 인자로 실행해 줘"라는 요청 |
| `tool_result` | 우리 코드(user role) | 도구를 실제로 실행한 결과 |

### 1.2 stop_reason

API 응답에는 `stop_reason` 필드가 있어, 모델이 왜 말을 멈췄는지 알려줍니다.

- `end_turn` — 할 말을 다 했음. 대화 한 턴이 끝남.
- `tool_use` — 도구를 부르고 싶어서 멈춤. **우리 코드가 도구를 실행해 결과를 돌려줘야** 다음이 진행됨.
- `max_tokens` — 출력 토큰 한도에 걸림.

즉 `stop_reason == "tool_use"`는 "공이 너에게 넘어갔다"는 신호입니다.

### 1.3 tool_use_id — 요청과 결과를 잇는 끈

모델이 만든 각 `tool_use` 블록에는 고유한 `id`가 붙습니다. 우리가 결과를 돌려줄 때 `tool_result` 블록의 `tool_use_id`에 **그 id를 그대로** 적어야, 모델이 "이 결과는 내가 아까 요청한 그 호출의 답"이라고 짝지을 수 있습니다.

`tool_use_id`는 **호출 하나를 식별하는 값일 뿐**입니다. 훅끼리 결과를 주고받는 것과는 아무 관계가 없고, 여러 훅이 같은 값을 공유하도록 사람이 맞춰줘야 하는 설정값도 아닙니다.

### 1.4 에이전틱 루프(Agentic Loop)

"모델이 도구를 쓰면서 스스로 일을 끝낼 때까지 반복"하는 구조를 에이전틱 루프라고 합니다. 직접 짜면 이렇게 생겼습니다.

```python
messages = [{"role": "user", "content": "config.yaml 읽고 문제 있으면 알려줘"}]

while True:
    resp = client.messages.create(model=..., tools=TOOLS, messages=messages)

    # (1) 모델이 만든 블록 전체를 그대로 히스토리에 append — text만이 아니라 tool_use도!
    messages.append({"role": "assistant", "content": resp.content})

    if resp.stop_reason != "tool_use":
        break  # end_turn 등 -> 루프 종료

    # (2) 요청된 도구들을 실제로 실행
    results = []
    for block in resp.content:
        if block.type == "tool_use":
            output = run_tool(block.name, block.input)
            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,   # 반드시 원래 id
                "content": output,
            })

    # (3) 결과를 user role로 히스토리에 append
    messages.append({"role": "user", "content": results})
```

### 1.5 가장 흔한 버그: 히스토리에서 tool_use / tool_result를 빠뜨리기

위 코드에서 (1)과 (3)을 생략하고 **모델의 `text` 블록만** 히스토리에 넣으면 어떤 일이 벌어질까요?

- 모델 입장에서는 자기가 파일을 읽었다는 사실도, 읽은 내용도 컨텍스트에 없습니다.
- 그래서 다음 반복에서 **똑같은 도구를 똑같은 인자로 다시 호출**합니다. 무한 루프처럼 보이는 증상이 여기서 나옵니다.

기억할 규칙:

- API가 알아서 히스토리를 관리해 주지 않습니다. **컨텍스트 관리는 전적으로 개발자 책임**입니다.
- API가 토큰 절약을 위해 몇 턴마다 `tool_use` 블록을 자동으로 지우거나, 컨텍스트를 몰래 초기화하는 동작 같은 것은 **없습니다**.
- 도구가 멱등(idempotent)인지 아닌지는 API의 재호출 여부와 무관합니다. 멱등성은 "같은 입력으로 여러 번 실행해도 결과가 같은가"라는 도구 자체의 성질일 뿐입니다.

## 2. Client SDK vs Agent SDK

두 SDK는 추상화 수준이 다릅니다.

### 2.1 Client SDK (Anthropic API 클라이언트)

- 하는 일: HTTP로 Messages API를 호출해 주는 얇은 라이브러리.
- 도구 목록도, 도구의 실제 구현도, 위 1.4의 while 루프도 **전부 개발자가 작성**해야 합니다.
- `stop_reason`을 직접 검사하고, 도구를 실행하고, `tool_result`를 직접 append합니다.
- 장점: 완전한 제어. 단점: 보일러플레이트가 많고, 히스토리 관리 실수(1.5)가 나기 쉽습니다.

### 2.2 Agent SDK (Claude Agent SDK)

- 하는 일: 에이전트 하나를 통째로 제공.
- **내장 도구(built-in tools)** 를 기본 탑재합니다 — 파일 읽기/쓰기, 파일 검색, 셸(Bash) 실행, 웹 검색, 서브에이전트 호출 등.
- **에이전틱 루프를 내부에서 자동 실행**합니다. 개발자는 `stop_reason`을 볼 필요도, `tool_result`를 손으로 붙일 필요도 없습니다.
- 그 밖에 훅, 세션 관리, 서브에이전트, 권한 제어 같은 상위 기능을 함께 제공합니다.

### 2.3 선택 기준

"파일을 읽고, 셸 명령을 돌리고, 다 될 때까지 반복하되, **루프를 손으로 짜기는 싫다**" → Agent SDK.
"모델 호출만 필요하고 도구 실행 흐름을 내가 완전히 통제하고 싶다" → Client SDK.

주의: Client SDK도 `stop_reason`을 정상적으로 돌려줍니다. Client SDK로 도구 루프를 못 만드는 게 아니라, **직접 만들어야** 할 뿐입니다.

## 3. 훅(Hook) 시스템

### 3.1 훅이란 무엇이고 왜 존재하나

훅은 **에이전트 실행 과정의 특정 시점에 우리 코드가 끼어들 수 있게 해주는 콜백**입니다.

존재 이유의 핵심은 **결정론(determinism)** 입니다.

- 프롬프트에 "환불 전에 반드시 신원을 확인해라"라고 적는 것은 **확률적(probabilistic)** 통제입니다. 대부분 지켜지지만 실패율이 0은 아닙니다.
- 훅에 `if not verified: block()` 이라고 코드로 적는 것은 **결정론적(deterministic)** 통제입니다. 100% 지켜집니다.

따라서 "지켜지지 않으면 되돌릴 수 없는 일"(금전 이동, 데이터 삭제, 규정 준수 사안)은 프롬프트가 아니라 훅으로 막아야 합니다. "시스템 프롬프트에 이미 써 뒀으니 훅은 낭비"라는 생각이 위험한 이유가 이것입니다. 환불처럼 **금전적이고 되돌리기 어려운(hard to reverse)** 작업은 단 한 번의 누락만으로도 복구 불가능한 컴플라이언스 결함이 됩니다.

반대로 문장 다듬기처럼 실패해도 영향이 작은 일은 프롬프트 지시로 충분합니다. 즉 **작업의 되돌릴 수 없음(irreversibility)과 피해 규모**가 판단 기준입니다.

### 3.2 주요 훅 이벤트(라이프사이클)

| 훅 이벤트 | 실행 시점 | 대표 용도 |
|---|---|---|
| `SessionStart` | 세션이 시작될 때 한 번 | 초기 컨텍스트 주입, 환경 정보 안내 |
| `UserPromptSubmit` | 사용자가 프롬프트를 보낼 때마다 | 프롬프트 검사, 참고 정보 덧붙이기 |
| `PreToolUse` | 도구가 **실행되기 직전** | 실행 차단(block), 입력값(`tool_input`) 검사·수정 |
| `PostToolUse` | 도구가 **실행된 직후, 결과가 모델에 가기 전** | 출력 정규화, 잘라내기, 마스킹 |

시점이 중요합니다. **입력을 손보려면 `PreToolUse`, 출력을 손보려면 `PostToolUse`** 입니다. 도구 결과 형식을 통일하고 싶은데 `PreToolUse`를 쓰면 시점이 맞지 않습니다.

### 3.3 matcher — 훅을 어떤 도구에 걸 것인가

훅을 등록할 때 `matcher`를 지정합니다.

```python
HookMatcher(matcher="refund_customer", hooks=[my_callback])
```

핵심 규칙: **`matcher`는 오직 "도구 이름"만 매칭합니다.** 문자열 또는 정규식으로 도구 이름을 거를 뿐입니다.

- 도구의 **인자 값**(예: `category`가 특정 값일 때만)으로 필터링하는 기능은 matcher에 없습니다.
- `refund_customer.*category=restricted` 같은 정규식을 써도 인자를 걸러주지 않습니다.
- `argument_matcher` 같은 별도 필드도 존재하지 않습니다.

그럼 인자 조건은 어디에? → **콜백 함수 안에서 직접 검사**합니다.

### 3.4 훅 콜백이 받는 데이터: input_data

콜백에는 `input_data`(딕셔너리)가 전달되며, 그 안의 `tool_input`에 도구로 넘어갈 인자가 그대로 들어 있습니다.

```python
async def block_restricted_refund(input_data, tool_use_id, context):
    args = input_data["tool_input"]
    if args.get("amount", 0) > 500 and args.get("category") == "restricted":
        return {
            "hookSpecificOutput": {
                "hookEventName": "PreToolUse",
                "permissionDecision": "deny",
                "permissionDecisionReason": "제한 카테고리의 $500 초과 환불은 차단됩니다.",
            }
        }
    return {}   # 아무것도 반환하지 않으면 그대로 진행
```

정리하면 **"어느 도구인가"는 matcher가, "그 도구의 인자가 어떤 값인가"는 콜백 내부 조건문이** 담당합니다. `PreToolUse` 훅이 도구 인자를 볼 수 없다는 말은 사실이 아닙니다 — `input_data["tool_input"]`으로 전부 볼 수 있습니다.

### 3.5 PostToolUse 반환 필드들

`PostToolUse` 훅은 도구가 낸 결과를 바꿔서 모델에게 보낼 수 있습니다. 이때 쓰는 필드가 서로 역할이 다릅니다.

| 필드 | 역할 | 적용 범위 |
|---|---|---|
| `updatedToolOutput` | 도구 출력을 **교체(replace)** | **내장 도구 + MCP 도구 모두** — 표준·범용 필드 |
| `updatedMCPToolOutput` | 도구 출력을 교체 | **MCP 도구 전용**, 레거시 필드 |
| `additionalContext` | 기존 출력에 **정보를 덧붙임** (교체 아님) | — |
| `systemMessage` | 사용자 UI에 안내 메시지 표시 | 모델에게 가는 도구 출력이 아님 |

따라서 MCP 도구와 내장 도구를 **한 훅으로 함께 처리**하려면 `updatedToolOutput`을 씁니다. `updatedMCPToolOutput`은 MCP 도구에만 적용되므로 내장 도구 출력을 바꾸지 못합니다.

`additionalContext`와 `systemMessage`는 "덮어쓰기"가 아니라는 점이 중요합니다. 원래 출력은 그대로 남습니다.

### 3.6 결정론적 출력 정규화(Output Normalization) 예시

서로 다른 도구가 같은 개념을 다른 형식으로 돌려주는 상황을 생각해 봅시다.

- `inventory_lookup` → 숫자 코드 `0 / 1 / 2` (재고 있음 / 부족 / 없음)
- `warehouse_lookup` → 문자열 `"in-stock" / "low-stock" / "out-of-stock"`

모델이 어느 도구가 답했든 **하나의 일관된 어휘**로 추론하게 하려면, 두 도구 모두에 매칭되는 `PostToolUse` 훅에서 결과를 같은 문자열 레이블 집합으로 매핑한 뒤 `updatedToolOutput`으로 돌려주면 됩니다.

```python
LABELS = {0: "in-stock", 1: "low-stock", 2: "out-of-stock"}

async def normalize_stock(input_data, tool_use_id, context):
    raw = input_data["tool_response"]
    normalized = LABELS.get(raw, raw)  # 숫자면 변환, 문자열이면 그대로
    return {"hookSpecificOutput": {
        "hookEventName": "PostToolUse",
        "updatedToolOutput": normalized,
    }}
```

같은 목적을 프롬프트로 달성하려 하면(세션 시작 시 매핑표를 안내, 매 턴 변환하라고 상기) 확률적 통제가 되어 결정론적 보장이 되지 않습니다.

### 3.7 훅 체이닝(Chaining) — 여러 훅이 같은 결과를 순차 가공할 때

같은 도구에 `PostToolUse` 훅을 둘 이상 걸었다고 합시다. 예: (a) 결과 행 수를 잘라내는 훅, (b) 타임스탬프를 ISO 8601로 바꾸는 훅. 최종 출력은 "잘렸고 **또한** 정규화된" 상태여야 합니다.

여기서 반드시 확인할 것은 **두 번째 훅이 첫 번째 훅의 `updatedToolOutput`을 입력으로 받아 이어서 작업하는 구조인가**입니다.

- 파이프라인처럼 이어지면: `원본 → 훅A → 훅B → 최종` 으로 두 변환이 모두 살아남습니다.
- 두 훅이 각각 **원본만** 보고 독립적으로 돌면, 마지막에 반환된 값만 채택되어 **앞선 변환이 유실**됩니다.

혼동하기 쉬운 오해들:

- 타임아웃 값이 훅 충돌을 해결하지 않습니다. 늦게 끝난 훅의 출력을 무시하는 규칙 같은 것은 없습니다.
- 훅 이름의 알파벳 순서로 실행 순서가 정해지지 않습니다.
- `tool_use_id`를 맞춰야 훅이 합성되는 것도 아닙니다(3.3 참고).

## 4. 세션(Session) 관리

### 4.1 세션이란

세션은 **하나의 대화 흐름 전체**(주고받은 메시지, 도구 호출과 결과, 읽은 파일 내용 등 누적된 컨텍스트)를 담는 단위입니다. 각 세션에는 고유한 **세션 ID**가 부여되고, 대화 기록(transcript)은 보통 로컬 디스크에 파일(예: `.jsonl`)로 저장됩니다.

세션이 있어서 "어제 하던 조사"를 오늘 이어서 할 수 있습니다.

### 4.2 세션을 되살리는 세 가지 방식

| 방식 | 의미 | 특징 |
|---|---|---|
| **Continue** (`claude --continue`, `continue_conversation=True`) | **현재 디렉터리의 가장 최근** 세션을 이어감 | ID 몰라도 됨. 하지만 "최근"이 누구 것인지 특정 불가 |
| **Resume** (`claude --resume <id\|name>`, `resume=<id>`) | **지정한 그 세션**을 이어감 | 정확한 대상 지정. 여러 세션이 공존해도 안전 |
| **Fork** (`fork_session=True`) | 기존 세션 상태를 **복사해 새 분기**를 만듦 | 원본은 보존, 갈래를 나눠 실험할 때 |

인자 없이 `claude --resume`만 실행하면 **세션 선택기(session picker)** 라는 대화형 UI가 떠서 사람이 목록에서 골라야 합니다. 반대로 `claude --resume payment-retry-bug`처럼 이름이나 ID를 인자로 주면 선택기를 거치지 않고 곧바로 그 세션이 열립니다. 세션 선택기는 사람이 터미널에서 쓰는 UI이므로, 자동화된 백엔드 서비스가 프로그래밍적으로 쓸 수단이 아닙니다.

### 4.3 max_turns와 error_max_turns

`max_turns`는 에이전트가 한 실행에서 돌 수 있는 **최대 대화 턴 수** 상한입니다. 폭주와 비용 폭발을 막는 안전장치입니다. 이 상한에 걸려 멈추면 `error_max_turns` 상태로 종료됩니다.

중요한 점: **`error_max_turns`는 "접근이 틀렸다"는 뜻이 아니라 단지 "예산이 떨어졌다"는 뜻**입니다. 이미 수행한 분석은 세션에 그대로 남아 있습니다.

그래서 올바른 대응은:

1. 그 세션의 ID로 **resume** 하고,
2. 후속 요청에 **더 큰 `max_turns`** 값을 준다.

이러면 읽은 파일과 중간 결론을 모두 보존한 채 남은 작업을 이어서 끝냅니다. 처음부터 다시 돌리거나(분석 폐기), 새 세션에 읽었던 파일 목록을 손으로 다시 적는 것은 낭비입니다. 단순히 이어 하면 되는 상황에서 fork까지 할 이유도 없습니다.

### 4.4 다중 사용자 환경: 왜 continue가 아니라 resume인가

한 리포지토리 디렉터리에서 여러 사용자가 각자 장기 대화를 진행하고, 백엔드 서비스가 몇 시간 뒤 특정 사용자의 대화를 이어가야 하는 상황을 봅시다.

- `continue`(가장 최근 세션)를 쓰면, **다른 사용자가 방금 만든 세션**을 잘못 집어 대화가 섞입니다.
- `fork_session=True`를 매 요청마다 쓰면 매번 새 분기가 생겨 한 사용자의 대화가 이어지지 않고, "최신 세션"을 복사하는 것이라 역시 사용자 간 혼선이 납니다.
- 정답 구조: 세션 생성 시 발급된 **세션 ID를 사용자별로 DB에 저장**해 두었다가, 그 사용자의 후속 요청이 오면 저장해 둔 ID로 **resume** 합니다.

즉 **세션 ID를 애플리케이션이 추적·소유**하는 것이 다중 사용자 세션 관리의 기본입니다.

### 4.5 상태 비저장(Stateless) 환경: 세션이 아예 안 통할 때

서버리스 파이프라인처럼 각 단계가 **매번 새로 뜨고 곧 사라지는 컨테이너**에서 실행되고, 이전 컨테이너의 로컬 디스크에 접근할 수 없다면?

세션 재개의 전제가 무너집니다. resume도 fork도 continue도 **모두 로컬 디스크에 트랜스크립트 파일이 존재해야** 동작합니다. 세션 ID만 들고 가봐야 읽을 파일이 없습니다.

이때의 해법은 세션 기능이 아니라 **애플리케이션 레벨 상태 전달**입니다.

1. 앞 단계가 끝나면 **핵심 결과·결론만 추출**해 외부 저장소나 파이프라인 변수(application state)에 저장한다.
2. 다음 컨테이너에서는 **새 세션을 시작**하고, 그 결과를 **첫 프롬프트에 함께 넣어** 준다.

이는 3장 서두의 "모델은 컨텍스트에 있는 것만 안다"의 직접적 응용입니다. 전달 수단이 없으면 직접 텍스트로 넣어 주는 것이 유일한 방법입니다.

## 5. 서브에이전트(Subagent)

### 5.1 서브에이전트란

서브에이전트는 **자기 자신의 독립된 컨텍스트 윈도우를 가진 별도의 에이전트**입니다. 메인 에이전트(코디네이터)가 특정 하위 작업을 위임하면, 서브에이전트가 그 작업을 수행하고 **요약된 결과만** 상위로 돌려줍니다.

얻는 이점:

- **컨텍스트 격리(Context Isolation)**: 서브에이전트가 파일 50개를 뒤져도 그 원시 내용이 코디네이터의 컨텍스트를 오염시키지 않습니다. 결론만 올라옵니다.
- **병렬화**: 독립적인 하위 작업을 동시에 돌릴 수 있습니다.
- **역할 특화**: 각 서브에이전트마다 다른 시스템 프롬프트, 다른 도구 집합, 다른 모델을 줄 수 있습니다.

### 5.2 AgentDefinition의 주요 필드

서브에이전트는 정의(AgentDefinition)로 기술됩니다. 자주 나오는 필드:

- `description` — 이 에이전트가 무엇을 하는지. 코디네이터가 언제 부를지 판단하는 근거.
- `prompt` / 시스템 프롬프트 — 이 에이전트의 역할과 지침.
- `tools` — **허용된 도구 배열**. 여기 없는 도구는 쓸 수 없습니다.
- `disallowedTools` — 명시적으로 금지할 도구 목록.
- `model` — 사용할 모델(추론 능력·비용 선택).
- `maxTurns` — 이 에이전트의 최대 턴 수.
- `background` — 백그라운드(비동기)로 실행할지 여부.

### 5.3 능력은 "도구"로 결정된다 — 가장 중요한 원리

에이전트가 무엇을 **할 수 있는지**는 모델 크기나 실행 방식이 아니라 **어떤 도구를 가졌는가**로 결정됩니다.

예: `lead-investigator`는 스스로 하위 조사관을 만들 수 있어야 하고, `final-summarizer`는 절대 하위 에이전트를 만들면 안 된다고 합시다.

- 서브에이전트를 생성하는 행위 자체가 **서브에이전트 호출 도구(Agent 도구)** 를 쓰는 일입니다.
- 그러므로 `lead-investigator`의 `tools`에는 그 도구를 **포함**시키고, `final-summarizer`의 `tools`에서는 **제외**하거나 `disallowedTools`에 넣습니다.

이것이 구조적 강제(enforcement)입니다. 반면 다음은 통제 수단이 되지 못합니다.

- **모델 크기**: 큰 모델이라 위임이 가능하고 작은 모델이라 불가능한 게 아닙니다. 능력 차이는 추론 품질이지 권한이 아닙니다.
- **`background: true`**: 비동기 실행 방식일 뿐, 도구 권한을 부여하지 않습니다.
- **`maxTurns`를 낮추기**: 턴이 적어도 **첫 턴에 곧바로** 서브에이전트를 만들 수 있습니다. 권한 차단이 아니라 실행 예산 제한일 뿐이라 확실한 보장이 안 됩니다.

일반화하면: **권한은 도구 목록(allow/deny)으로, 예산은 maxTurns로** 통제합니다. 둘을 바꿔 쓰면 안 됩니다.

### 5.4 중첩(Nesting) 깊이

Claude Code는 서브에이전트가 또 다른 서브에이전트를 만드는 **중첩 서브에이전트**를 지원합니다. 다만 무한 재귀와 토큰 비용 폭발을 막기 위해 하드 리밋이 있습니다.

- **최대 5레벨** 깊이까지 중첩 가능하며, **메인 에이전트를 1레벨로 포함**해서 셉니다.
- 즉 메인 → 자식 → 손자 → … 로 내려갈 수 있고, 5레벨을 넘길 수 없습니다.
- 각 레벨은 독립된 컨텍스트 윈도우를 갖고, 상위에는 요약 결과만 올립니다.

"서브에이전트는 어떤 경우에도 다른 에이전트를 못 만든다"는 것은 옛 제약이며 현재는 사실이 아닙니다. 반대로 도구만 있으면 무제한 중첩된다는 것도 사실이 아닙니다 — 가드레일로 5레벨 제한이 걸립니다.

### 5.5 컨텍스트는 자동으로 상속되지 않는다

**서브에이전트는 부모나 형제 에이전트의 대화 맥락을 자동으로 물려받지 않습니다.** 각자 깨끗한 상태(clean state)에서 시작합니다.

전형적인 실패 사례: 코디네이터가 `web-researcher`를 돌려 자료 10건을 모은 뒤, `synthesis` 서브에이전트에게 "방금 완료된 조사를 바탕으로 보고서를 써라"라고만 지시하는 경우. `synthesis`는 "방금 완료된 조사"가 무엇인지 **볼 방법이 없어서** 일반론만 새로 지어냅니다.

해결책은 단 하나: **코디네이터가 `web-researcher`의 결과를 `synthesis`의 프롬프트에 직접 넣어 준다**(명시적 주입).

효과가 없는 대안들:

- 더 큰 모델로 교체 — 존재하지 않는 정보를 추론해 낼 수는 없습니다.
- `maxTurns` 증가 — 이미 끝난 조사를 처음부터 다시 하게 만드는 낭비이고, 분업의 목적에 어긋납니다.
- 검색 도구를 똑같이 부여 — 마찬가지로 중복 수행입니다.

## 6. 오케스트레이션 패턴

### 6.1 Hub-and-Spoke Coordinator 패턴

중앙의 **코디네이터(허브)** 가 모든 서브에이전트(스포크)와의 통신·상태·에러 처리를 중앙집중적으로 관장하는 구조입니다.

```
        ┌──────────────┐
        │ Coordinator  │  ← 로깅, 에러 처리, 결과 취합
        └──┬───┬───┬───┘
           │   │   │
        ┌──▼┐ ┌▼─┐ ┌▼──┐
        │ A │ │ B│ │ C │   ← 서로 직접 통신하지 않음
        └───┘ └──┘ └───┘
```

핵심 원칙: **스포크끼리 코디네이터를 우회해 직접 데이터를 주고받지 않는다.**

서브에이전트 둘이 공유 파일이나 공유 DB로 직접 결과를 주고받으면, 코디네이터는 무슨 일이 오갔는지 모르고, 한쪽이 실패해도 감지하지 못합니다. 이것이 **가시성(visibility) 상실**입니다. 공유 큐를 직접 폴링하고 완료 후에만 알리는 방식도 중간 실패에 대한 실시간 가시성을 떨어뜨립니다.

올바른 교정: **모든 에이전트 간 통신을 코디네이터를 경유하도록 라우팅**해서, 코디네이터가 중간 결과를 로깅하고 실패를 일관되게 처리하게 만듭니다.

(서브에이전트 둘을 하나로 합치고 에러 처리 책임까지 넘기는 것은 코디네이터의 본래 역할을 없애는 것이므로 이 패턴과 어긋납니다.)

### 6.2 코디네이터는 평가자이기도 하다 — 갭 평가와 타깃 재위임

코디네이터는 단순 전달자가 아닙니다. 취합된 결과가 **원래 요구 범위를 다 채웠는지 평가(evaluate for gaps)** 하는 책임이 있습니다.

예: '공급망 사이버 보안의 신종 위험' 보고서에 랜섬웨어는 충실한데 원래 범위였던 **제3자 공급업체 위험**이 빠졌다면?

올바른 흐름: **갭 식별 → 그 부분만 타깃 쿼리로 재위임 → 자료 보강 → synthesis 재실행.**

- 미완성인 채 최종본으로 발행 — 부적절.
- 새 자료 없이 어조만 고쳐 쓰기 — 빠진 정보는 채워지지 않음.
- 전체 파이프라인을 처음부터 재시작 — 잘 된 부분까지 버리는 토큰·시간 낭비.

이 "생성 → 평가 → 부족분 보강 → 재생성" 순환이 오케스트레이션의 품질을 만듭니다.

### 6.3 작업 분해 패턴 고르기: Prompt Chaining vs Orchestrator-Workers

| 패턴 | 구조 | 언제 쓰나 |
|---|---|---|
| **단일 패스(single-pass)** | 한 번의 프롬프트로 끝 | 작업이 작고 단순, 외부 탐색 불필요 |
| **Prompt Chaining** | 미리 정해진 고정 단계를 순차 실행 (A→B→C) | 단계 수와 순서를 **사전에 알 수 있을 때** |
| **Orchestrator-Workers** | 오케스트레이터가 중간 결과를 보고 **다음 하위 작업을 동적으로 생성**해 워커에 분배 | 필요한 단계 수·탐색 경로를 **사전에 알 수 없을 때** |

판단 기준은 하나입니다: **작업 단계를 미리 확정할 수 있는가?**

예: "이 라이브러리 취약점이 대규모 애플리케이션 어딘가에서 실제로 악용 가능한가?" — 시작 시점에 호출 지점(call sites)이 어디인지, 도달 가능한지(reachability), 이미 어떤 완화 조치가 있는지 **전부 미지**입니다. 검색을 한 번 돌려야 다음에 무엇을 조사할지 정해집니다. 이런 경우는 **Orchestrator-Workers**가 맞습니다.

이때 잘못된 선택들:

- Prompt Chaining으로 고정 3단계(스캔→패치→검증)를 박아 넣기 — 탐색 범위가 동적으로 변하는 상황에 대응 못 함. 단계 수를 고정한다고 모든 호출 지점을 찾는 게 보장되지도 않음.
- CVE 설명만 읽고 코드베이스를 보지 않은 채 단일 패스로 판단 — 특정 애플리케이션에서의 실제 악용 가능성은 코드를 봐야만 알 수 있음.

### 6.4 Attention Dilution과 Map-Reduce식 분할

**Attention Dilution(주의력 분산)**: 컨텍스트에 너무 많은 내용을 한꺼번에 넣으면, 모델의 주의가 넓게 퍼져 세부 사항을 놓치고 결과물이 뭉뚱그려집니다. 컨텍스트 윈도우에 "들어가긴 한다"와 "잘 처리된다"는 다른 문제입니다.

예: 모노레포에서 40개 파일을 건드린 PR을 한 번의 패스로 리뷰하면, 미묘한 파일 간(cross-file) 문제를 놓치고 코멘트가 일반론이 됩니다.

해법은 **분할 정복(divide and conquer) / Map-Reduce 구조**입니다.

1. **Map 단계**: 각 파일을 **독립적으로** 분석해 파일별 발견 사항(findings)을 뽑는다. 각 패스의 컨텍스트가 작아 세밀해집니다.
2. **Reduce / 통합 단계**: 원본 40개 파일이 아니라 **요약된 findings만** 모아 파일 간 연관성을 분석한다.

효과 없는 시도들:

- 파일 순서 무작위화 — 여전히 40개를 한 컨텍스트에 넣으므로 근본 문제 그대로, 비결정성만 증가.
- 앞쪽 파일 우선순위 부여 — 뒤쪽 파일의 리뷰 품질이 무너짐.
- **Temperature 상향** — temperature는 토큰 선택의 무작위성(다양성/창의성)을 조절하는 샘플링 파라미터일 뿐, 컨텍스트 과부하나 주의력 분산과 무관하며 오히려 환각 위험을 키움.

### 6.5 초대형 스케일: 오케스트레이션을 대화 밖으로 빼기 (Workflow 도구)

서브태스크가 수백 개(예: 파일 단위 200개 마이그레이션)라면, 코디네이터가 턴마다 몇 개씩 위임하는 방식으로는 감당이 안 됩니다.

- 대화 컨텍스트가 위임 기록으로 폭발하고,
- 턴 수 한계에 부딪히며,
- 지연 시간과 토큰 비용이 기하급수로 늘어납니다.

이때는 **Workflow 도구**를 써서 오케스트레이션 로직 자체를 **런타임이 대화 바깥에서 실행하는 스크립트**로 옮깁니다. 반복·배치 처리는 결정론적 스크립트가 돌리고, 대화에는 최종 결과만 돌아옵니다. 대화 컨텍스트 소비를 최소화하면서 대규모 자동화를 안정적으로 수행하는 방식입니다.

대안들이 부족한 이유:

- 서브에이전트 하나가 한 컨텍스트 윈도우 안에서 200개를 순차 처리 — 컨텍스트 오버플로와 주의력 분산으로 실패.
- `maxTurns`만 키워 턴 안에서 200번 위임 — 토큰 낭비와 지연, 컨텍스트 오버헤드 미해결.
- 코디네이터를 여러 개로 쪼개 각자 파이프라인 유지 — 코디네이터 간 상태 동기화·중복 작업이라는 새 복잡성 발생.

## 7. 전체를 관통하는 판단 원칙 정리

1. **모델은 컨텍스트에 있는 것만 안다.** 히스토리 누락, 서브에이전트 컨텍스트 미상속, 서버리스 상태 유실은 모두 같은 원리의 변주다.
2. **되돌릴 수 없는 일은 프롬프트가 아니라 코드(훅)로 막는다.** 프롬프트는 확률적, 훅은 결정론적.
3. **시점이 곧 훅의 선택이다.** 입력 통제 = `PreToolUse`, 출력 통제 = `PostToolUse`.
4. **권한은 도구 목록으로, 예산은 maxTurns로.** 서로 대체할 수 없다.
5. **필터링의 층을 구분한다.** 도구 이름은 matcher, 인자 값은 콜백 내부 로직.
6. **컨텍스트가 커질수록 나눠라.** Map-Reduce, 서브에이전트 격리, 그리고 초대형 규모면 대화 밖 Workflow로.
7. **단계를 미리 알면 체이닝, 모르면 오케스트레이터-워커.**
8. **중앙 허브를 우회하는 통신은 가시성을 죽인다.**
9. **재개(resume)는 맥락 보존의 기본기.** 다만 로컬 디스크가 없으면 성립하지 않는다.
10. **코디네이터는 취합자이자 평가자다.** 갭을 찾아 표적 재위임한다.

## 8. 용어 사전 (Glossary)

| 영어 용어 | 한국어 설명 |
|---|---|
| **Messages API** | Anthropic의 대화 요청 API. `messages` 배열을 보내고 모델 응답을 받는다. |
| **context / context window** | 모델에게 한 번에 전달되는 텍스트 전체 / 그 최대 용량. |
| **content block** | 메시지 내용의 단위. `text`, `tool_use`, `tool_result` 등. |
| **tool_use** | 모델이 "이 도구를 이 인자로 실행해 달라"고 요청하는 블록. |
| **tool_result** | 도구를 실제 실행한 결과를 모델에 돌려주는 블록. 대응하는 `tool_use_id` 필수. |
| **tool_use_id** | 개별 도구 호출을 식별하는 고유 ID. 요청과 결과를 짝짓는 용도일 뿐. |
| **stop_reason** | 모델이 멈춘 이유. `tool_use`(도구 필요), `end_turn`(완료), `max_tokens` 등. |
| **agentic loop** | 모델 호출 → 도구 실행 → 결과 반환을 작업 완료까지 반복하는 구조. |
| **idempotent / non-idempotent** | 같은 입력으로 여러 번 실행해도 결과가 같은가 여부. 도구 자체의 성질. |
| **Client SDK** | Anthropic API를 감싼 얇은 클라이언트. 도구 루프를 직접 구현해야 함. |
| **Agent SDK (Claude Agent SDK)** | 내장 도구와 에이전틱 루프를 자동 제공하는 상위 SDK. |
| **built-in tools** | Agent SDK가 기본 제공하는 도구들(파일 읽기/쓰기, Bash, 검색 등). |
| **MCP (Model Context Protocol)** | 외부 도구·데이터 소스를 에이전트에 연결하는 표준 프로토콜. |
| **MCP server** | MCP로 도구를 제공하는 외부 프로세스/서비스. |
| **hook** | 에이전트 실행의 특정 시점에 실행되는 사용자 코드 콜백. |
| **HookMatcher** | 훅을 어떤 도구에 걸지 지정하는 등록 객체. `matcher`는 **도구 이름만** 매칭. |
| **matcher** | 도구 이름 매칭용 문자열/정규식. 도구 인자 값으로는 필터링 불가. |
| **PreToolUse** | 도구 실행 **직전** 훅. 실행 차단이나 입력값 검사·수정에 사용. |
| **PostToolUse** | 도구 실행 **직후** 훅. 결과가 모델에 가기 전 출력 가공에 사용. |
| **SessionStart** | 세션 시작 시 한 번 실행되는 훅. |
| **UserPromptSubmit** | 사용자가 프롬프트를 제출할 때마다 실행되는 훅. |
| **input_data** | 훅 콜백이 받는 데이터 객체. `tool_input`에 도구 인자가 들어 있음. |
| **tool_input** | 도구로 전달될 인자들. `PreToolUse`에서 검사·수정 가능. |
| **updatedToolOutput** | 도구 출력을 교체하는 표준 필드. **내장 도구와 MCP 도구 모두**에 적용. |
| **updatedMCPToolOutput** | MCP 도구 전용 레거시 출력 교체 필드. 내장 도구에는 적용 안 됨. |
| **additionalContext** | 기존 출력에 정보를 **덧붙이는** 필드. 교체가 아님. |
| **systemMessage** | 사용자 UI에 보여주는 안내 메시지. 모델용 도구 출력이 아님. |
| **hook chaining** | 여러 훅을 파이프라인처럼 연결해, 뒤 훅이 앞 훅의 결과를 이어받아 가공하는 것. |
| **deterministic guarantee** | 코드로 100% 보장되는 통제. 프롬프트 기반 확률적 통제와 대비. |
| **programmatic gate / guardrail** | 코드로 강제하는 차단 장치. 불가역적 작업에 필수. |
| **output normalization** | 서로 다른 도구의 응답 형식을 하나의 일관된 규격으로 통일하는 것. |
| **session** | 하나의 대화 흐름 전체(메시지·도구 결과·읽은 파일 등 누적 맥락) 단위. |
| **session ID** | 세션을 식별하는 고유 값. 정확한 재개를 위해 애플리케이션이 저장·추적해야 함. |
| **transcript** | 디스크에 저장되는 세션 대화 기록 파일(예: `.jsonl`). |
| **resume** (`--resume <id\|name>`) | 지정한 특정 세션을 이어서 재개. 인자를 주면 선택기를 건너뜀. |
| **continue** (`--continue`, `continue_conversation`) | 현재 디렉터리의 **가장 최근** 세션을 이어감. 대상 특정 불가. |
| **fork_session** | 기존 세션을 복사해 새로운 분기를 만드는 옵션. 원본 보존. |
| **session picker** | `--resume`을 인자 없이 실행하면 뜨는 대화형 세션 선택 UI. 사람용. |
| **max_turns / maxTurns** | 실행 가능한 최대 대화 턴 수 상한. 폭주·비용 방지용 예산 제한. |
| **error_max_turns** | `max_turns` 상한에 걸려 중단된 상태. 접근 실패가 아니라 예산 소진. |
| **stateless / serverless** | 실행마다 상태가 초기화되는 환경. 로컬 세션 파일에 의존할 수 없음. |
| **application state** | 세션 기능 밖에서 애플리케이션이 직접 저장·전달하는 결과 데이터. |
| **subagent** | 자체 컨텍스트를 가진 별도 에이전트. 작업을 위임받고 요약 결과만 반환. |
| **AgentDefinition** | 서브에이전트의 정의(설명, 프롬프트, tools, model, maxTurns 등). |
| **tools / disallowedTools** | 허용 도구 배열 / 금지 도구 목록. 에이전트의 **권한**을 결정. |
| **subagent-invocation tool (Agent tool)** | 다른 서브에이전트를 생성·호출하는 도구. 이 도구 유무가 위임 권한을 결정. |
| **background** | 에이전트를 비동기로 실행하는 옵션. 권한과는 무관. |
| **nesting depth** | 서브에이전트 중첩 깊이. 메인 포함 **최대 5레벨**. |
| **context isolation** | 서브에이전트가 독립 컨텍스트를 가져 상위를 오염시키지 않는 성질. |
| **coordinator** | 서브에이전트들을 지휘·취합·평가하는 중앙 에이전트(허브). |
| **hub-and-spoke** | 모든 통신이 중앙 허브를 경유하는 아키텍처 패턴. |
| **visibility** | 코디네이터가 하위 작업의 진행·실패를 관측할 수 있는 정도. |
| **targeted re-delegation** | 누락된 범위만 골라 다시 위임하는 보완 전략. |
| **prompt chaining** | 사전에 정해진 고정 단계를 순차 실행하는 분해 패턴. |
| **orchestrator-workers** | 중간 결과에 따라 하위 작업을 **동적으로 생성**해 워커에 분배하는 패턴. |
| **task decomposition** | 큰 작업을 하위 작업으로 나누는 설계 행위. |
| **attention dilution** | 컨텍스트가 과대해져 모델 주의가 분산되고 세부를 놓치는 현상. |
| **map-reduce (divide and conquer)** | 개별 단위 분석 → 요약 결과만 통합 분석하는 2단계 처리 구조. |
| **temperature** | 토큰 샘플링의 무작위성 조절 파라미터. 컨텍스트 문제와 무관. |
| **Workflow tool** | 오케스트레이션 로직을 대화 밖 스크립트로 옮겨 런타임이 실행하게 하는 도구. 초대형 배치용. |
| **reachability** | 취약한 코드가 실제 실행 경로에서 도달 가능한지 여부. |
| **call site** | 특정 함수·라이브러리가 실제로 호출되는 코드상의 지점. |
