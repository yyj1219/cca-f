# 사전 학습 노트: 프롬프트 엔지니어링과 구조화된 출력 (29~42 범위)

이 문서는 해당 범위가 다루는 개념을 **아무 배경지식 없이** 읽어도 이해할 수 있도록 처음부터 설명합니다.
주제는 크게 다섯 덩어리입니다.

1. LLM이란 무엇이며 어떤 제약 속에서 동작하는가 (컨텍스트 창, 토큰, stateless)
2. 프롬프트를 잘 쓰는 법 (XML 태그 구조화, 명시적 기준, 예시 제공)
3. 구조화된 출력과 스키마 설계 (JSON, enum, tool_choice, 검증)
4. 오류가 났을 때 고치는 법 (오류 피드백 재시도, 자기 수정, 오류 분류)
5. 대량 처리와 에이전트 아키텍처 (Batches API, 서브에이전트, 오케스트레이션)

## 1. 기초: LLM은 무엇이고 어떻게 동작하는가

### 1.1 LLM (Large Language Model, 대규모 언어 모델)

LLM은 "지금까지 주어진 텍스트 다음에 올 말"을 확률적으로 이어 쓰는 모델입니다.
Claude, GPT 같은 것이 여기에 속합니다. 중요한 성질은 다음과 같습니다.

- **텍스트를 넣으면 텍스트가 나온다.** 넣는 텍스트를 프롬프트(prompt)라고 부릅니다.
- **확률적이다.** 같은 입력에도 매번 조금씩 다른 출력이 나올 수 있습니다. 그래서 "형식을 지켜라"라고 말로만 시키면 잘 지키다가도 가끔 어깁니다.
- **모르는 것도 그럴듯하게 만들어낸다.** 이것을 환각(hallucination)이라고 합니다. 설계할 때 항상 고려해야 하는 위험입니다.

### 1.2 토큰(Token)

모델은 글자를 그대로 보지 않고 **토큰**이라는 조각 단위로 봅니다.
영어 기준 대략 4글자 = 1토큰, 한국어는 글자당 토큰이 더 많이 듭니다.

- API 요금은 보통 "입력 토큰 수 + 출력 토큰 수"로 과금됩니다.
- 따라서 프롬프트에 쓸데없는 내용을 중복해서 넣으면 **돈이 그만큼 더 나갑니다.**

### 1.3 컨텍스트 창 (Context Window)

모델이 한 번의 요청에서 볼 수 있는 **입력 + 출력 토큰 총량의 상한**입니다.
예를 들어 20만 토큰짜리 컨텍스트 창이라면, 프롬프트와 답변을 합쳐 20만 토큰을 넘길 수 없습니다.

- 아주 긴 문서(예: 300페이지 계약서)를 통째로 넣으면 이 한도를 넘겨 요청 자체가 거절됩니다.
- 해결책은 **청킹(chunking)** 입니다. 문서를 의미 단위로 잘라 여러 요청으로 나눠 처리하고, 결과를 나중에 합칩니다.

### 1.4 max_tokens 와 컨텍스트 창의 차이 (아주 자주 헷갈림)

| 항목 | 뜻 | 무엇을 제한하나 |
|---|---|---|
| **컨텍스트 창** | 모델이 한 번에 다룰 수 있는 전체 용량 | 입력 + 출력 **합계** |
| **max_tokens** | 요청 파라미터. "답변을 최대 몇 토큰까지 쓸지" | **출력(생성)만** |

즉 **입력 문서가 너무 길어서 생긴 문제를 `max_tokens`를 줄여서 고칠 수는 없습니다.**
`max_tokens`를 줄이면 답변이 중간에 잘릴(truncation) 뿐, 입력이 짧아지지 않습니다.
- 입력이 길어서 생긴 문제 → 입력을 자른다(청킹).
- 답변이 중간에 끊겨서 생긴 문제 → `max_tokens`를 늘린다.

### 1.5 API는 상태를 기억하지 않는다 (Stateless)

Messages API 같은 LLM API는 기본적으로 **무상태(stateless)** 입니다.
서버가 "아까 그 문서"를 기억하고 있지 않습니다.

- 대화가 이어지는 것처럼 보이는 이유는, 클라이언트가 **이전 메시지 전체를 매 요청마다 다시 보내기 때문**입니다.
- 그러므로 "아까 준 문서를 참고해서 고쳐줘"라고만 보내면, 그 문서를 다시 첨부하지 않는 한 모델은 문서를 볼 수 없습니다.
- 이 사실은 뒤에 나오는 **자기 수정 재시도** 설계의 핵심 전제입니다.

### 1.6 동기(synchronous) vs 비동기(asynchronous)

- **동기 호출**: 요청을 보내고 응답이 올 때까지 기다린다. 보통 수 초 내에 응답. 채팅처럼 사람이 기다리는 상황에 적합.
- **비동기 호출**: 요청을 큐에 넣어두고, 나중에 결과를 찾아간다. 즉시성이 없는 대신 저렴하거나 대량 처리에 유리.

**지연 시간(latency)** 은 요청부터 응답까지 걸리는 시간을 말합니다. 실시간 사용자 경험에서 가장 중요한 지표입니다.

## 2. 프롬프트 구조화하기

### 2.1 왜 구조가 필요한가

프롬프트가 길어지고, 서로 다른 성격의 내용(지시문, 규칙, 예시, 검사 대상 데이터)이 섞이면
모델이 "어디까지가 규칙이고 어디부터가 데이터인지" 헷갈립니다.
그 결과 **교차 오염(cross-contamination)** 이 발생합니다. A 범주에 쓰라고 준 규칙을 B 범주에 적용해버리는 현상입니다.

### 2.2 XML 태그로 경계를 만들기

Claude는 학습 과정상 XML 스타일 태그로 구분된 프롬프트를 특히 잘 따릅니다.
각 영역을 **의미 있는 고유한 이름의 태그**로 감싸면 경계가 명확해집니다.

```xml
<security_criteria>
  - 사용자 입력이 검증 없이 SQL 문자열에 들어가면 지적한다.
  - 하드코딩된 비밀키를 지적한다.
  <severity_examples>
    critical: 인증 우회가 가능한 경우
    low: 로그에 사용자 ID가 남는 경우
  </severity_examples>
</security_criteria>

<correctness_criteria>
  - 반환 타입이 문서와 다르면 지적한다.
  <severity_examples>
    high: null을 반환할 수 있는데 호출부가 처리하지 않음
  </severity_examples>
</correctness_criteria>

<style_criteria>
  ...
</style_criteria>
```

핵심 원칙:

- **태그 이름은 내용과 일치하게** 짓습니다. `<section1>`보다 `<security_criteria>`가 훨씬 낫습니다.
- **중첩(nesting)** 으로 계층을 표현할 수 있습니다. 위 예시처럼 규칙 안에 예시를 넣습니다.
- 태그 이름을 프롬프트 뒷부분에서 참조할 수 있습니다. "`<security_criteria>`에 정의된 기준만 사용하라."

### 2.3 구조화의 잘못된 대안들 (왜 안 좋은지 이해하기)

- **긴 줄글 한 단락으로 쓰기**: 문장 구조만으로 경계를 표현하려는 시도. 긴 컨텍스트에서 범주 경계가 흐려지고 규칙이 섞입니다.
- **헤더 없는 하나의 불릿 목록**: 항목 순서만으로 소속 범주를 암시하는 방식. 모델이 추측해야 하므로 오염 위험이 큽니다.
- **모든 범주의 전체 규칙을 각 섹션마다 통째로 반복**: 섹션을 자립적으로 만들려는 의도지만, 토큰을 낭비하고(비용 증가) 같은 규칙이 여러 곳에 있어 오히려 혼란을 키웁니다. 경계 문제는 **반복이 아니라 구획화**로 푸는 것이 정석입니다.

## 3. 명시적 기준 vs 모호한 지시

### 3.1 배경 용어: 거짓 양성과 정밀도

- **거짓 양성 (False Positive, 오탐)**: 문제가 아닌 것을 문제라고 지적하는 것.
- **거짓 음성 (False Negative, 미탐)**: 진짜 문제를 놓치는 것.
- **정밀도 (Precision)**: 지적한 것 중 진짜 문제의 비율. `진짜 문제 / 전체 지적 수`
- **재현율 (Recall)**: 존재하는 문제 중 잡아낸 비율.

오탐이 많으면 **알림 피로도(notification fatigue)** 가 생깁니다.
개발자가 "또 사소한 트집이겠지"라며 도구의 출력을 아예 무시하기 시작하면, 그 도구는 사실상 죽은 것입니다.
따라서 자동 리뷰 도구에서는 **정밀도를 올리는 것**이 종종 최우선 과제가 됩니다.

### 3.2 모호한 지시가 만드는 문제

"주석이 정확한지 확인하라(check that comments are accurate)" 같은 지시는 왜 나쁠까요?
"정확하다"의 기준이 없기 때문입니다. 모델은 문구가 조금 어색한 것도 "정확하지 않음"으로 판단해 지적합니다.

특히 다음 표현들은 **기준을 모델의 주관에 떠넘기는 모호한 지시**입니다.

- "높은 확신이 있을 때만(highly confident)" → 얼마가 높은 것인지 정의가 없음
- "충분히 중요하다고 판단되면(significant enough)" → 중요함의 기준이 없음
- "사소한 표현 차이는 무시하라(trivial wording)" → 사소함의 기준이 없음
- "신뢰도가 90%를 넘으면" → LLM이 산출하는 자기 확신도는 교정(calibration)되어 있지 않아 신뢰할 수 없는 숫자임
- "개선될 수 있는 모든 것(could plausibly be improved)" → 사실상 무한대로 지적하게 만들어 오탐을 극대화

### 3.3 명시적 기준(Explicit Criteria)으로 바꾸는 법

좋은 기준은 **객관적으로 참/거짓을 판정할 수 있는 조건**이어야 합니다.
그리고 그 조건을 보여주는 **구체적인 예시**가 붙어야 합니다.

나쁜 지시:
```
주석이 정확한지 확인하라.
```

좋은 지시:
```
주석이 동작에 대해 구체적인 주장을 하고 있고, 그 주장이 코드가 실제로 하는 일과
모순될 때만 지적하라.
예: docstring에 "returns None"이라고 적혀 있는데 함수가 항상 값을 반환하는 경우.
표현 방식이나 문체에 대한 지적은 하지 않는다.
```

차이의 핵심은 판정 절차가 **검증 가능(verifiable)** 하다는 점입니다.
"주석의 주장"과 "코드의 실제 동작"을 비교하면 참/거짓이 결정됩니다. 취향이 개입할 여지가 없습니다.

### 3.4 원칙 요약

- 주관적 판단어("중요한", "확신하는", "적절한")를 **관찰 가능한 조건**으로 치환한다.
- 무엇을 지적할지뿐 아니라 **무엇을 지적하지 말지**도 명시한다.
- 조건마다 구체 예시를 하나씩 붙인다.

## 4. 예시로 출력 형식 고정하기 (Few-shot / Worked Examples)

### 4.1 Zero-shot vs Few-shot

- **Zero-shot**: 예시 없이 말로만 지시하는 것. "다음 네 필드를 포함해서 답해라."
- **Few-shot**: 원하는 입력→출력 쌍을 몇 개 보여주는 것.
- **Worked example (모범 예시)**: 완성된 형태의 출력 예시를 그대로 보여주는 것.

모델은 **설명보다 패턴을 훨씬 잘 따릅니다.**
"필드 4개를 넣어라"라고 글로 쓰면 가끔 하나를 빼먹지만,
필드 4개가 항상 같은 순서로 등장하는 예시를 2~3개 보여주면 그 형태를 그대로 재현합니다.

### 4.2 예시를 잘 만드는 법

```
<example>
location: src/auth/session.py:42
issue: 세션 토큰이 만료 검사 없이 사용됨
severity: high
suggested_fix: 사용 전 expires_at을 현재 시각과 비교하는 가드를 추가
</example>

<example>
location: src/utils/log.py:17
issue: 디버그 로그에 사용자 이메일이 남음
severity: low
suggested_fix: 이메일을 마스킹하거나 로그 레벨을 낮춘다
</example>
```

- **모든 필드를 항상 같은 순서로** 배치합니다. 순서 자체가 학습되는 패턴입니다.
- **엣지 케이스를 예시에 포함**시킵니다. 예를 들어 `severity`가 누락되는 문제가 있다면, 빠뜨리기 쉬운 **low severity 사례**를 예시에 반드시 넣습니다. 그래야 모델이 "심각도가 낮아도 필드는 쓴다"는 것을 배웁니다.
- 예시는 실제 출력과 형식이 완전히 동일해야 합니다.

### 4.3 효과가 약한 대안들

- **"출력을 스스로 다시 확인하라"고 지시하기**: 추상적인 자기 점검 요구는 형식 일관성을 근본적으로 보장하지 못합니다.
- **끝에 "심각도 필드를 잊지 마세요"라고 덧붙이기**: 한 필드의 누락만 조금 줄일 뿐, "issue와 fix가 한 문장으로 뭉쳐지는" 구조 붕괴는 못 막습니다.
- **max_tokens를 늘리기**: 잘림 때문이 아니라 형식 미준수 때문에 생긴 문제이므로 무관합니다.

## 5. 구조화된 출력(Structured Output)과 스키마 설계

### 5.1 구조화된 출력이란

모델의 답을 자유로운 문장이 아니라 **JSON처럼 프로그램이 바로 파싱할 수 있는 형태**로 받는 것입니다.
문서에서 정보를 뽑아 데이터베이스에 넣는 추출 파이프라인(extraction pipeline)에 필수적입니다.

```json
{
  "account_number": "1234-5678",
  "usage_details": {
    "meter_reading": 4821,
    "billing_period": "2026-04"
  },
  "billing_address": "서울시 ...",
  "service_address": "서울시 ..."
}
```

### 5.2 스키마(Schema)

스키마는 "이 JSON은 어떤 필드를 어떤 타입으로, 어떤 계층에 가져야 하는가"를 정의한 규격입니다.
JSON Schema가 대표적인 표기법입니다.

```json
{
  "type": "object",
  "properties": {
    "usage_details": {
      "type": "object",
      "properties": {
        "meter_reading": { "type": "number" }
      },
      "required": ["meter_reading"]
    }
  }
}
```

### 5.3 중첩(Nesting)과 부모 객체(Parent object)

JSON은 객체 안에 객체를 넣을 수 있습니다. 이를 중첩이라고 합니다.
`meter_reading`이 `usage_details` 안에 들어가야 하는데 `billing_address` 안에 들어갔다면,
**값 자체는 맞지만 위치가 틀린 것**입니다. 이런 실수를 "잘못된 부모 객체 아래 중첩되었다"고 표현합니다.

### 5.4 스키마 검증(Schema Validation)

모델의 출력을 스키마와 대조해서 규격을 지켰는지 확인하는 단계입니다.
Python이라면 `jsonschema`, `pydantic` 같은 라이브러리를 씁니다.

- 검증에 실패하면 **어떤 필드가 어떻게 잘못됐는지 오류 메시지**가 나옵니다.
- 이 오류 메시지는 뒤에 나오는 **오류 피드백 재시도**의 재료가 됩니다.

### 5.5 enum (열거형)

필드가 가질 수 있는 값을 미리 정해진 목록으로 제한하는 것입니다.

```json
{ "governing_law": { "enum": ["California", "New York", "Delaware"] } }
```

장점은 값이 정규화되어 후속 처리가 쉬워진다는 것입니다.
문제는 **현실이 목록보다 지저분하다**는 것입니다.

### 5.6 enum의 가장 중요한 설계 원칙: "모름"을 표현할 수 있게 하라

계약서에서 준거법(governing_law)을 뽑는다고 합시다. 현실은 셋 중 하나입니다.

1. 명시적으로 적혀 있다.
2. 두 사법권에 걸쳐 모호하게 암시된다.
3. 아예 언급이 없다.

enum에 구체적인 사법권 이름만 있으면, 2번과 3번에서도 모델은 **억지로 하나를 골라야 합니다.**
이것이 바로 환각을 강제하는 구조입니다. 출력은 형식상 유효하지만 내용은 거짓입니다.

해결책은 **탈출구(escape hatch) 값을 enum에 추가**하는 것입니다.

```json
{ "governing_law": { "enum": ["California", "New York", "Delaware", "unclear"] } }
```

이제 모델은 확신이 없을 때 `"unclear"`를 선택할 수 있고,
파이프라인은 "확실히 식별된 데이터"와 "사람이 확인해야 할 데이터"를 깔끔하게 나눌 수 있습니다.
`"unknown"`, `"not_stated"`처럼 상황을 더 세분화한 값을 두어도 좋습니다.

### 5.7 나쁜 대안들과 그 이유

- **필드를 boolean으로 바꾸기**: "사법권이 언급되었는가 예/아니오"만 남기면 **어느 사법권인지라는 핵심 정보를 잃습니다.** 모호성을 없애려다 유용성을 버리는 것입니다.
- **모든 값을 `ambiguous_California`처럼 접두사 붙여 복제하기**: enum 크기가 2배가 되어 복잡해지고, **아예 언급이 없는 경우**를 표현할 값이 여전히 없습니다.
- **강제로 고르게 만들기**: 문제를 악화시킬 뿐입니다. (다음 절 참조)

### 5.8 tool_choice

모델이 도구(tool)를 호출하는 방식을 제어하는 파라미터입니다. 대표적인 값은 다음과 같습니다.

| 값 | 의미 |
|---|---|
| `{"type": "auto"}` | 모델이 도구를 쓸지 말지 스스로 결정 |
| `{"type": "any"}` | 반드시 도구 중 하나를 호출해야 함 |
| `{"type": "tool", "name": "..."}` | 지정한 도구를 반드시 호출 |

구조화된 출력을 얻는 흔한 방법이 "출력 스키마를 도구로 정의하고 `tool_choice`로 강제 호출하게 하는 것"입니다.

**주의할 점**: `tool_choice`는 *형식*을 강제하는 도구이지, *데이터 부족* 문제를 해결하지 못합니다.
정보가 없는 상황에서 `{"type": "any"}`로 강제하면 모델은 억지로 값을 지어내게 됩니다.
즉 **모호성 문제의 해법은 강제(tool_choice)가 아니라 스키마에 "unclear" 같은 값을 두는 것**입니다.

## 6. 오류 처리: 무엇을 재시도로 고칠 수 있고 무엇은 못 고치는가

### 6.1 오류 피드백 재시도 (Error-Feedback Retry)

출력이 잘못되었을 때, **무엇이 왜 잘못되었는지를 알려주면서 다시 요청**하는 기법입니다.

```
1차 요청 → 출력 → 스키마 검증 실패
        → 오류 메시지를 프롬프트에 넣어 재요청 → 수정된 출력 → 검증 통과
```

같은 프롬프트를 그대로 다시 보내는 단순 재시도(blind retry)와는 다릅니다.
같은 입력에는 대체로 같은 실패가 반복되므로, **오류 정보를 되먹임(feedback)하는 것이 핵심**입니다.

### 6.2 실패 원인 분류: 재시도로 고칠 수 있는가?

파이프라인 운영에서 가장 중요한 판단은 **"이 실패는 어떤 종류인가"** 입니다.

| 분류 | 설명 | 올바른 대응 |
|---|---|---|
| **처리/형식 오류 (processing / formatting error)** | 정보는 문서에 있고 모델도 제대로 읽었으나, JSON 구조·키 위치·필드명이 틀림 | **오류 피드백 재시도로 해결 가능.** 사람이나 새 문서 불필요 |
| **원본 데이터 부재 (source data absent)** | 필요한 정보가 그 문서 어디에도 없음 (예: 전화번호가 인쇄되어 있지 않음) | **다른 원본 문서가 필요.** 재시도는 무의미하고, 오히려 환각을 유발 |
| **문서 미제공 (document not supplied)** | 정보가 다른 문서(예: 연례 서한)에만 있는데 그 문서를 넣지 않음 | **해당 문서를 파이프라인에 공급**해야 함 |
| **의미/정책 모호성 (semantic ambiguity)** | 값은 있지만 그 값이 옳은지 판단하려면 정책·업무 기준이 필요 (예: 청구서에 주소가 하나뿐인데 그게 서비스 주소인지 우편 주소인지 알 수 없음) | **사람에게 에스컬레이션(human escalation)** 하거나 판정 규칙을 먼저 정의 |

핵심 직관: **모델은 존재하지 않는 정보를 만들어낼 수 없습니다(만들어내면 그게 환각입니다).**
따라서 재시도가 의미 있는 경우는 오직 "정보는 있는데 배치/형식만 틀린" 경우입니다.

### 6.3 자기 수정(Self-Correction) 요청에 무엇을 담아야 하는가

앞서 본 대로 API는 무상태입니다. 그러므로 후속 요청에는 **세 가지를 모두** 넣어야 합니다.

1. **원본 문서** — 값을 잃어버리지 않기 위해. 이게 없으면 모델은 구조를 고치면서 값을 지어낼 수 있습니다.
2. **직전의 실패한 출력(JSON)** — 무엇을 고칠 대상인지 명시.
3. **구체적인 수정 지침 / 검증 오류 메시지** — 무엇이 왜 틀렸고 어떻게 되어야 하는지.

```
<original_document>
... 접수 문서 원문 ...
</original_document>

<previous_output>
{"guardian": {"date_of_birth": "1990-03-11"}, "patient": {...}}
</previous_output>

<validation_error>
date_of_birth는 guardian이 아니라 patient 객체 아래에 있어야 합니다.
</validation_error>

위 오류를 반영하여 스키마에 맞는 JSON을 다시 출력하세요.
```

세 가지 중 무엇이 빠지면 어떻게 되는지 이해해 두는 것이 중요합니다.

- **오류 코드만 보내기**: 모델이 이전 대화를 기억한다고 잘못 가정한 것. 무상태 환경에서는 문서도 이전 출력도 없어 아무것도 못 합니다. 게다가 코드만으로는 어떻게 고칠지 알 수 없습니다.
- **원본 문서 없이 실패 JSON만 보내기**: 구조는 고칠 수 있어도, 값의 근거가 없어 다른 필드를 유실하거나 값을 왜곡할 위험이 있습니다.
- **원본 문서 없이 스키마만 새로 설명하기**: 추출 대상 데이터 자체가 사라지므로 작업이 불가능합니다.

## 7. Message Batches API (대량 비동기 처리)

### 7.1 무엇인가

수천~수만 건의 요청을 **한 번에 묶어서 비동기로** 처리하는 API입니다.

- **가격**: 표준 동기 호출 대비 약 **50% 할인**. (프리미엄이 붙는 것이 아니라 더 쌉니다.)
- **처리 시간**: 보장된 반환 시간이 없습니다. 수 분에서 최대 **24시간**까지 걸릴 수 있습니다.
- **용도**: 야간 배치 요약, 대량 분류, 데이터셋 백필, 평가 실행 등 **지금 당장 답이 필요 없는** 작업.

### 7.2 언제 쓰면 안 되는가

**사용자가 화면 앞에서 기다리는 모든 것** — 라이브 채팅, 자동완성, 대화형 어시스턴트.
채팅에서 사용자가 참아줄 수 있는 지연은 길어야 수 초인데, 배치는 그 범위를 훨씬 초과합니다.
비용이 싸다는 이유로 실시간 대화를 배치로 돌리면 답변이 몇 시간 뒤 도착해 제품이 성립하지 않습니다.

정리: **배치가 라이브 채팅에 부적합한 이유는 가격이 아니라 지연 시간(latency)입니다.**

### 7.3 custom_id — 가장 중요한 개념

배치의 각 요청에는 개발자가 직접 붙이는 고유 식별자 `custom_id`가 있습니다.

```json
{"custom_id": "doc-00042", "params": {"model": "...", "messages": [...]}}
{"custom_id": "doc-00043", "params": {"model": "...", "messages": [...]}}
```

**배치 결과는 제출한 순서대로 돌아온다는 보장이 없습니다.**
내부적으로 요청들을 병렬 처리하기 때문에 완료된 순서나 임의의 순서로 결과 파일에 기록될 수 있습니다.

따라서 결과를 원본과 짝지을 때 **배열 위치(index)로 zip하면 안 됩니다.**

```python
# 잘못된 방법 - 결과가 뒤섞여 엉뚱한 문서에 요약이 붙는다
for doc, res in zip(documents, results):
    doc.summary = res.text

# 올바른 방법 - custom_id로 매칭
by_id = {r.custom_id: r for r in results}
for doc in documents:
    doc.summary = by_id[doc.id].text
```

이 순서 미보장은 **요청 건수와 무관합니다.** "1,000건을 넘으면 순서가 바뀐다" 같은 임계값은 존재하지 않습니다.

### 7.4 결과 유형(result type)과 오류

배치 결과의 각 항목에는 결과 유형이 붙습니다. 대표적으로:

- `succeeded` — 정상 처리
- `errored` — 오류 발생. 안에 오류 객체가 들어 있음
- `canceled` — 취소됨
- `expired` — 처리 기한 내에 완료되지 못함

`errored` 항목의 대표적인 오류가 **`invalid_request_error`** 입니다.
이는 **클라이언트 측 입력 문제(4xx 계열)** 를 뜻합니다. 예를 들어 문서가 컨텍스트 창을 초과한 경우입니다.

중요한 성질: **입력을 고치지 않고 똑같이 다시 보내면 똑같이 실패합니다.**
배치 API가 오류 요청을 알아서 재시도해 주지도 않습니다.

### 7.5 배치 오류 복구의 정석

20,000건 중 일부가 컨텍스트 초과로 실패했다면:

1. 결과 파일에서 `errored` 항목을 찾아 **`custom_id`로 어떤 문서가 실패했는지 식별**한다.
2. **그 문서들만** 작은 청크로 분할한다(원인 해결).
3. **실패한 것들만** 새 배치로 다시 제출한다.

이미 성공한 수만 건을 다시 돌리는 것은 시간과 비용의 낭비입니다.
또한 실패했다고 영구 폐기할 이유도 없습니다. 청킹이라는 전처리로 충분히 처리 가능하기 때문입니다.
그리고 앞서 본 대로 `max_tokens`를 줄이는 것은 입력 길이 문제와 무관합니다.

## 8. 에이전트와 서브에이전트 아키텍처

### 8.1 에이전트란

LLM이 도구(파일 읽기, 명령 실행, 검색 등)를 사용하며 여러 턴에 걸쳐 스스로 작업을 수행하는 시스템입니다.

- **상위(부모, parent) 에이전트**: 전체 작업을 조율하는 쪽.
- **서브에이전트(subagent)**: 부모가 특정 작업을 위임해 실행시키는 별도의 에이전트 인스턴스.

### 8.2 컨텍스트 격리 (Context Isolation)

서브에이전트는 **완전히 새롭고 비어 있는 컨텍스트**로 시작합니다.
부모의 대화 이력, 방금 무슨 파일을 고쳤는지, 왜 그렇게 고쳤는지는 **자동으로 전달되지 않습니다.**

전달되는 것은 오직 **호출 시 넘긴 `prompt` 문자열** 뿐입니다.

그래서 "코드 생성 직후 리뷰 서브에이전트를 불렀는데 어떤 파일이 왜 바뀌었는지 모르더라"는 현상은
버그가 아니라 **설계상 당연한 동작**입니다. 해결책은 프롬프트에 필요한 맥락을 명시적으로 적어 넣는 것입니다.

```
# 나쁜 호출
prompt: "방금 작성한 코드를 리뷰해줘"

# 좋은 호출
prompt: """
다음 파일들이 변경되었습니다:
- src/auth/session.py (세션 만료 검사 추가)
- src/auth/token.py (토큰 서명 알고리즘을 HS256에서 RS256으로 변경)

변경 이유: 만료된 토큰이 통과되는 보안 이슈(#412) 수정.
`git diff HEAD~1` 로 변경 내용을 확인하고, <security_criteria>에 정의된 기준으로 리뷰하세요.
"""
```

혼동하기 쉬운 다른 설정들:

- **`model` 오버라이드**: 어떤 LLM 모델로 실행할지 바꾸는 설정일 뿐, 프롬프트 전달을 막지 않습니다.
- **`tools` 필드 미설정**: 도구 사용 권한에 영향을 줄 수는 있어도, 프롬프트 텍스트를 받는 것 자체를 막지는 않습니다.

### 8.3 세션 재개(Resume)와 독립적 검토(Independent Review)

**세션 재개**는 이전에 실행했던 세션을 그 대화 이력째로 이어서 실행하는 것입니다.
`resume`하면 **이전 대화, 추론 과정, 도구 호출 기록이 그대로 보존됩니다.** 지워지지 않습니다.

여기서 중요한 개념이 **자기 검토의 한계(self-review limitation)** 와 **확증 편향(self-confirmation bias)** 입니다.
자기가 방금 작성한 코드를 자기가 검토하면, "왜 이렇게 짰는지"에 대한 정당화 논리를 이미 갖고 있기 때문에
같은 실수를 다시 못 보고 지나칠 가능성이 높습니다.

따라서 **진정한 독립 검토는 이전 생성 맥락이 전혀 없는 새 인스턴스**로 수행해야 합니다.
"설정을 재사용하려고 같은 세션을 재개해서 자기 diff를 리뷰시키는 것"은 독립 검토가 아닙니다.
겉으로는 다른 요청 같아도, 편향의 원천인 이전 컨텍스트가 그대로 살아 있기 때문입니다.

정리:
- 독립 검토가 필요하다 → **새 서브에이전트를 새 컨텍스트로 띄우고, 필요한 맥락만 프롬프트로 준다.**
- 이어서 작업해야 한다 → resume이 적합하다.

### 8.4 전용 서브에이전트로 오탐 줄이기

특정 종류의 검토(예: 네이밍 규칙)를 전담하는 서브에이전트를 두는 설계가 있습니다. 구성 요소는 셋입니다.

1. **격리된 컨텍스트 창** — 다른 리뷰 주제의 내용이 섞여 판단을 흐리지 않게 합니다.
2. **맞춤형 시스템 프롬프트** — 판정 기준을 명시적으로 못 박습니다.
3. **최소 권한 도구 접근 (least privilege)** — 그 작업에 필요한 도구만 줍니다. 보안 원칙이자, 엉뚱한 행동을 줄이는 장치이기도 합니다.

전형적인 문제 상황: 한 파일 안에 여러 세대의 레거시 네이밍 스타일이 섞여 있습니다.
새 헬퍼 함수가 그중 한 레거시 스타일을 따랐다면, "파일 내 우세한 스타일과 다르다"는 이유로 지적됩니다.
이는 유용하지 않은 오탐입니다. 판단 기준이 **파일의 지역적 관행**이었기 때문입니다.

해결의 핵심은 시스템 프롬프트로 **기준점을 옮기는 것**입니다.

```
파일 내에 이미 존재하는 레거시 스타일 편차는 무시한다.
프로젝트의 표준 네이밍 규칙(canonical naming standard) 위반만 지적한다.
```

이러면 지역적 혼재로 인한 오탐은 줄어들면서, 진짜 표준 위반은 계속 잡힙니다.
다만 **모든 오탐을 없앨 수는 없다**는 점을 인정하는 것도 좋은 설계 태도입니다.

비교되는 열등한 접근들:
- 네이밍 지적을 전부 끄기 → 오탐과 함께 **진짜 결함(genuine defect)도 사라집니다.**
- 오탐을 그냥 낮은 심각도로 계속 보고하기 → 노이즈는 여전하고 알림 피로도는 해결되지 않습니다.
- "신뢰도 90% 이상일 때만" → 모델의 자기 확신도는 신뢰할 수 있는 척도가 아닙니다.

### 8.5 파일별 검토(Per-file pass)의 한계와 교차 파일 통합 단계

**파일별 검토 패스**는 파일 하나씩 독립적으로 리뷰하는 방식입니다. 병렬화가 쉽고 컨텍스트가 작아 효율적입니다.
그러나 **파일 간 상호작용을 볼 수 없다는 근본적 한계**가 있습니다.

두 파일이 서로 의존하고 문제의 뿌리가 두 파일에 걸친 하나의 데이터 흐름(data flow)일 때,
각 파일 검토는 각자 자기 파일 안에서만 말이 되는 서로 충돌하는 수정안을 냅니다.

올바른 해법은 **교차 파일 통합 패스(cross-file integration pass)** 를 별도 단계로 두는 것입니다.
두 파일을 함께 놓고 실제 데이터 흐름을 보며 **하나의 일관된 권고안**을 도출합니다.

잘못된 해법들:
- 재실행해서 "더 확신에 찬 말투"의 권고를 채택 → 말투는 정확성의 근거가 아닙니다. 근본 원인(파일 간 맥락 부재)이 그대로입니다.
- 리뷰 편의를 위해 두 소스 파일을 하나로 병합 → 리뷰 도구의 한계 때문에 실제 코드 구조를 훼손하는 본말전도입니다.
- 원래 생성자에게 중재를 맡김 → 8.3의 자기 검토 편향 문제를 그대로 안고 있습니다.

### 8.6 규모 확장: 워크플로 오케스트레이션

200개 파일이 바뀐 대규모 마이그레이션처럼, 단일 대화에서 **턴 바이 턴(turn-by-turn)으로 위임**하기엔 너무 큰 작업이 있습니다.

턴 바이 턴 위임의 한계:
- 각 위임과 결과 요약이 부모 대화의 컨텍스트에 계속 쌓여 **컨텍스트 창을 잠식**합니다.
- 순차적이라 처리량(throughput)이 낮고 지연이 누적됩니다.

정석적인 해결책은 **오케스트레이션을 코드로 옮기는 것**입니다.
스크립트나 워크플로 도구가 다수의 서브에이전트를 **병렬로 생성·조율**하고, 각 결과를 수집해 집계합니다.

```python
# 개념 예시
results = run_parallel([
    spawn_review_agent(prompt=make_prompt(f)) for f in changed_files
], max_concurrency=10)
report = aggregate(results)
```

이 방식의 장점:
- 각 서브에이전트가 **깨끗한 작은 컨텍스트**를 갖는다.
- 병렬 실행으로 총 소요 시간이 크게 준다.
- 재시도, 실패 처리, 집계 로직을 **결정적인 코드로** 제어할 수 있다.

열등한 대안들:
- **확장 사고(extended thinking)를 늘려 한 모델이 200개를 다 보게 하기**: 사고 시간을 늘려도 컨텍스트 창 한계와 정보 과부하는 해결되지 않습니다.
- **20개만 샘플링해서 나머지를 추정**: 검토하지 않은 180개의 독립적 결함을 놓칩니다. 코드 리뷰의 목적 자체와 어긋납니다.
- **단일 서브에이전트가 한 대화에서 200개를 순차 처리**: 컨텍스트 초과, 후반부 품질 저하, 환각 증가가 발생합니다.

## 9. 전체를 관통하는 설계 원칙 정리

1. **모델에게 판단 기준을 떠넘기지 말고 명시하라.** 모호한 형용사는 오탐의 원천이다.
2. **경계는 구조로 표현하라.** XML 태그로 구획하고, 반복 복사로 때우지 마라.
3. **형식은 설명보다 예시로 고정하라.** 엣지 케이스 예시를 반드시 포함하라.
4. **스키마에 "모름"을 위한 자리를 만들어라.** 강제 선택은 환각을 부른다.
5. **모델은 없는 정보를 만들 수 없다.** 재시도로 고칠 수 있는 실패와 없는 실패를 구분하라.
6. **재시도에는 원본 + 실패 출력 + 구체 피드백을 모두 넣어라.** API는 기억하지 않는다.
7. **위치가 아니라 식별자로 매칭하라.** 비동기 결과의 순서는 보장되지 않는다.
8. **지연 시간 요구에 맞는 API를 골라라.** 싸다고 실시간에 배치를 쓰지 마라.
9. **컨텍스트는 자동으로 전달되지 않는다.** 서브에이전트에게는 프롬프트로 명시하라.
10. **독립 검토는 깨끗한 컨텍스트에서만 가능하다.** 재개된 세션은 편향을 그대로 물려받는다.
11. **규모가 커지면 대화가 아니라 코드로 오케스트레이션하라.**

## 10. 용어 사전 (Glossary)

| 영어 용어 | 한국어 설명 |
|---|---|
| **Token** | 모델이 텍스트를 처리하는 최소 단위 조각. 과금과 길이 제한의 기준 |
| **Context Window** | 한 요청에서 모델이 다룰 수 있는 입력+출력 토큰 총량의 상한 |
| **max_tokens** | 모델이 **생성**할 출력의 최대 토큰 수. 입력 길이와는 무관 |
| **Truncation** | 토큰 한도에 걸려 출력이 중간에 잘리는 현상 |
| **Chunking** | 긴 입력을 작은 조각으로 나누어 여러 요청으로 처리하는 기법 |
| **Stateless** | 서버가 이전 요청을 기억하지 않는 성질. 매 요청에 필요한 맥락을 다시 보내야 함 |
| **Latency** | 요청부터 응답까지 걸리는 지연 시간 |
| **Synchronous / Asynchronous** | 응답을 기다리는 동기 호출 / 나중에 결과를 찾아가는 비동기 호출 |
| **Hallucination** | 근거 없는 내용을 그럴듯하게 지어내는 현상 |
| **Prompt** | 모델에 넣는 입력 텍스트 전체 |
| **XML Tags** | `<name>...</name>` 형태로 프롬프트 영역의 경계를 명확히 하는 구조화 기법 |
| **Cross-contamination** | 한 범주의 규칙·예시가 다른 범주에 잘못 적용되는 현상 |
| **Explicit Criteria** | 객관적으로 참/거짓 판정이 가능한 명확한 기준 |
| **Vague Instruction** | "중요한", "확신하는" 등 판단을 모델의 주관에 맡기는 모호한 지시 |
| **False Positive** | 문제가 아닌 것을 문제라고 지적하는 오탐 |
| **False Negative** | 실제 문제를 놓치는 미탐 |
| **Precision** | 지적한 것 중 진짜 문제의 비율 |
| **Notification Fatigue** | 오탐이 잦아 사용자가 도구의 출력을 아예 무시하게 되는 현상 |
| **Zero-shot** | 예시 없이 지시문만으로 작업을 시키는 방식 |
| **Few-shot / Worked Example** | 원하는 출력의 완성 예시를 프롬프트에 넣어 형식을 고정하는 방식 |
| **Structured Output** | 자유 문장이 아니라 JSON 등 파싱 가능한 형태로 결과를 받는 것 |
| **Schema** | 출력 JSON이 가져야 할 필드·타입·계층의 규격 정의 |
| **Schema Validation** | 출력이 스키마를 지켰는지 검사하는 단계 |
| **Nesting / Parent Object** | JSON 객체 안에 객체를 넣는 계층 구조 / 그 상위 객체 |
| **Enum** | 필드가 가질 수 있는 값을 정해진 목록으로 제한하는 스키마 요소 |
| **Escape Hatch Value** | `"unclear"`, `"unknown"`처럼 모호·부재 상황을 표현하기 위해 enum에 두는 값 |
| **tool_choice** | 모델의 도구 호출 방식을 제어하는 파라미터 (`auto`, `any`, 특정 도구 지정) |
| **Error-Feedback Retry** | 무엇이 왜 틀렸는지 알려주며 다시 요청하는 재시도 기법 |
| **Self-Correction** | 모델이 피드백을 받아 자기 출력을 스스로 고치는 것 |
| **Processing / Formatting Error** | 정보는 맞게 읽었으나 구조·위치·형식이 틀린 오류. 재시도로 해결 가능 |
| **Human Escalation** | 정책·의미 판단이 필요해 사람에게 넘기는 절차 |
| **Extraction Pipeline** | 문서에서 정형 데이터를 뽑아내는 자동화 처리 흐름 |
| **Message Batches API** | 대량 요청을 비동기로 처리하는 API. 약 50% 저렴하나 최대 24시간 소요 |
| **custom_id** | 배치 각 요청에 부여하는 고유 식별자. 결과 매칭의 유일하게 안전한 기준 |
| **invalid_request_error** | 클라이언트 입력 문제로 발생하는 4xx 계열 오류. 입력을 고쳐야 해결됨 |
| **Result Type** | 배치 결과 항목의 상태 (`succeeded`, `errored`, `canceled`, `expired`) |
| **Agent / Subagent** | 도구를 쓰며 스스로 작업하는 LLM 시스템 / 상위 에이전트가 위임한 하위 인스턴스 |
| **Context Isolation** | 서브에이전트가 부모의 대화 이력 없이 빈 컨텍스트로 시작하는 성질 |
| **Resume (Session)** | 이전 세션을 대화 이력째로 이어서 실행하는 것. 맥락이 지워지지 않음 |
| **Independent Review** | 이전 생성 맥락이 없는 새 인스턴스로 수행하는 검토 |
| **Self-Confirmation Bias** | 자기가 만든 결과를 자기가 검토할 때 생기는 확증 편향 |
| **Least Privilege** | 작업에 꼭 필요한 최소한의 도구·권한만 부여하는 원칙 |
| **Canonical Standard** | 프로젝트 전역의 공식 표준 규칙 (지역 관행과 대비되는 기준점) |
| **Per-file Pass** | 파일 하나씩 독립적으로 검토하는 단계. 파일 간 상호작용은 볼 수 없음 |
| **Cross-file Integration Pass** | 여러 파일을 함께 놓고 데이터 흐름을 검토해 단일 권고를 내는 단계 |
| **Data Flow** | 값이 함수·파일·모듈을 거쳐 흘러가는 경로 |
| **Orchestration** | 여러 에이전트·작업의 실행 순서와 병렬성을 조율하는 것 |
| **Turn-by-turn Delegation** | 대화 턴마다 하나씩 수동으로 작업을 위임하는 방식. 규모 확장에 부적합 |
| **Workflow Tool** | 스크립트로 다수 서브에이전트를 병렬 조율하는 실행 도구 |
| **Extended Thinking** | 모델이 답하기 전 더 오래 추론하도록 하는 기능. 컨텍스트 한계를 늘려주지는 않음 |
| **Throughput** | 단위 시간당 처리할 수 있는 작업량 |
