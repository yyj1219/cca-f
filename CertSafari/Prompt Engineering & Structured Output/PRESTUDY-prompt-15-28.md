# 사전 학습 노트 — 프롬프트 엔지니어링과 구조화된 출력

이 문서는 해당 주제를 처음 접하는 사람을 위한 개념 정리입니다. LLM(대규모 언어 모델)을 실제 제품 파이프라인에 넣었을 때 마주치는 문제들과, 그것을 다루는 표준적인 기법들을 바닥부터 설명합니다.

---

## 0. 먼저 알아야 할 기본 그림

### LLM이란 무엇인가

LLM(Large Language Model)은 텍스트를 입력받아 그다음에 올 법한 텍스트를 확률적으로 생성하는 모델입니다. 중요한 성질 세 가지:

1. **결정론적이지 않다.** 같은 입력을 두 번 줘도 다른 출력이 나올 수 있습니다. 그래서 "세션마다 판단이 달라진다(inconsistent between sessions)"는 현상이 자연스럽게 발생합니다.
2. **입력에 없는 것은 만들어낼 수 없다(정직하게는).** 억지로 만들면 그것이 환각(hallucination)입니다.
3. **자기 자신의 확신도를 객관적으로 계산하지 못한다.** 이것이 뒤에 나오는 "신뢰도 지시어가 안 먹히는 이유"의 근본 원인입니다.

### 프롬프트란 무엇인가

프롬프트(prompt)는 모델에게 주는 입력 텍스트 전체입니다. 보통 두 부분으로 나뉩니다.

- **시스템 프롬프트(system prompt)**: 역할, 규칙, 정책 등 대화 전체에 걸쳐 유지되는 지시.
- **사용자 메시지(user message)**: 이번 요청의 구체적 내용(처리할 문서, 질문 등).

프롬프트 엔지니어링은 "모델을 재학습하지 않고, 입력 텍스트만 고쳐서 원하는 동작을 얻어내는 일"입니다.

### 파이프라인이란 무엇인가

실무에서 LLM은 혼자 쓰이지 않고 **파이프라인**의 한 부품으로 들어갑니다.

```
원본 문서(PDF/스캔본) → 전처리 → 프롬프트 조립 → LLM 호출
    → 출력 파싱 → 스키마 검증 → 비즈니스 규칙 검증 → 저장/전달
                              ↘ 실패 시 재시도(retry) 또는 사람에게 이관(escalation)
```

이 문서에서 다루는 개념들은 대부분 이 그림의 어느 칸에 속하느냐로 정리됩니다.

## 1. 프롬프트 설계 기법

### 1.1 지시(Instruction)만 주는 방식 — Zero-shot

예시 없이 "무엇을 하라"만 서술하는 방식입니다.

```
문서에서 모든 인용(citation)을 추출하라. 인용은 본문 안에 있을 수도 있고,
번호가 매겨진 참고문헌 목록에 있을 수도 있다.
```

**언제 충분한가**: 작업이 단순하고, 모델이 이미 그 패턴을 잘 알고 있을 때.

**언제 부족한가**: 작업이 **여러 단계의 연결(추적)**을 요구할 때. 예를 들어 본문의 위첨자 `¹`을 보고 → 문서 끝의 참고문헌 목록으로 가서 → 1번 항목을 찾아 → 그것을 인용으로 기록하라는 작업은 "그럴 수 있다"는 한 줄 설명만으로는 모델이 실제 절차를 수행하지 못하는 경우가 많습니다. 지시는 "존재를 알려줄" 뿐, "절차를 보여주지" 않기 때문입니다.

### 1.2 Few-shot 프롬프팅

프롬프트 안에 **입력 → 출력 예시를 몇 개** 넣어주는 기법입니다. 모델 가중치를 바꾸지 않고, 문맥(context)만으로 패턴을 알려주므로 **in-context learning**이라고도 부릅니다.

```
[예시 1 — 본문 내 인용 형식]
입력: "선행 연구는 이를 뒷받침한다 (Smith, 2019)."
출력: [{"author": "Smith", "year": 2019}]

[예시 2 — 참고문헌 목록 형식]
입력 본문: "선행 연구는 이를 뒷받침한다¹."
입력 참고문헌: "1. Smith, J. (2019). Title..."
출력: [{"author": "Smith", "year": 2019, "marker": 1}]
   ← 위첨자 1이 목록의 1번 항목으로 연결되는 과정을 그대로 보여준다
```

**핵심 포인트**: few-shot 예시의 가치는 "이런 것도 있다"는 정보가 아니라, **매핑 과정(어떻게 연결되는지)을 시연**한다는 데 있습니다. 여러 입력 형식(variant)이 섞인 데이터를 다룰 때는, **각 형식마다 최소 한 개씩** 예시를 넣는 것이 정석입니다.

### 1.3 Chain-of-Thought(CoT)를 곁들인 Few-shot

예시에 **정답만** 넣는 대신, **왜 그 정답인지 짧은 근거(rationale)**를 함께 넣는 방식입니다.

```
[예시]
게시물: "그 사건 얘기가 나올 때마다 정말 신나 죽겠네요."
결정: 사람 검토로 이관(escalate)
근거: 민감한 사건에 대한 반어적 표현으로, 실제 태도가 조롱인지 자조인지
      텍스트만으로 판별 불가 → 판단 유보하고 사람에게 넘긴다.
```

**왜 근거가 중요한가**: 정답 라벨만 반복해서 보여주면 모델은 표면적 패턴(특정 단어의 존재 등)을 흉내 낼 뿐입니다. 근거를 보여주면 모델은 **판단의 기준선 자체**를 학습하므로, 예시에 없던 새로운 사례에도 적용할 수 있게 됩니다. 이것이 **일반화(generalization)**입니다.

정리하면, 좋은 few-shot 예시 하나의 구성은:

| 구성 요소 | 설명 |
|---|---|
| 입력 텍스트 | 실제 현장에서 나올 법한, 노이즈가 있는 진짜 사례 |
| 결정/출력 | 무엇으로 판정했는지 |
| 근거 | 왜 그렇게 판정했는지, 특히 **왜 다른 그럴듯한 선택지를 이겼는지** |

### 1.4 어떤 예시를 골라야 하는가

모호한 경계선 판단(borderline case)이 문제인 상황에서:

- **경계선 사례를 골라야 한다.** 명백히 문제없는 사례를 10개 넣어도, 애매한 사례를 어떻게 가를지에 대한 정보는 0에 가깝습니다. 마찬가지로 가장 극단적인 위반 사례 1개도 경계선을 그리는 데 도움이 되지 않습니다. **경계선의 위치를 알려면 경계선 근처의 점을 보여줘야 합니다.**
- **실제 사례를 골라야 한다.** 읽기 쉽게 정제·이상화한 가짜 사례는 실전의 지저분함(오타, 중복 키워드, 맥락 부족)을 담지 못해 일반화에 도움이 안 됩니다.
- **개수는 적게(보통 2~4개).** 예시는 토큰을 소비하고, 너무 많으면 오히려 특정 예시에 과적합(overfit)되거나 프롬프트가 산만해집니다.
- **정책 문서 전체를 각 예시마다 반복 삽입하는 것은 낭비.** 정책은 지시부에 한 번 쓰고, 예시는 예시 역할만 하게 둡니다.

### 1.5 신뢰도 지시어(Confidence Language)의 함정

"확신하는 것만 보고하라(only report issues you are confident about)", "확신도 80% 이상만 출력하라" 같은 지시는 실무에서 거의 효과가 없습니다.

**이유**: 모델에게는 자기 출력의 정확도를 측정하는 내부 계기판이 없습니다(**calibration**, 교정 능력의 한계). "80%"라는 숫자를 줘도 모델이 비교할 대상 자체가 없으므로 그냥 문장을 흉내 낼 뿐입니다.

**그러면 무엇을 해야 하는가 — 명시적 범위 정의(Explicit Scoping)**:

주관적 판단을 모델에게 위임하지 말고, **객관적으로 판정 가능한 규칙**으로 바꿔 씁니다.

```
[이 카테고리에 포함되는 것 — Inclusion]
- 사용자 입력이 SQL 쿼리 문자열에 직접 연결(concatenate)되는 경우
- 검증되지 않은 경로 문자열이 파일 열기 함수에 전달되는 경우

[이 카테고리에서 제외되는 것 — Exclusion]
- 파라미터 바인딩을 사용하는 쿼리
- 테스트 코드 내부의 하드코딩된 문자열
```

이렇게 하면 모델은 "내가 얼마나 확신하나?"가 아니라 "이 항목이 목록에 있나?"를 판단하게 되고, 이는 훨씬 안정적입니다.

**실패한 시도에서 배워야 할 교훈**: 어떤 지시가 안 먹혔을 때,
- 같은 지시를 대문자로 강조하거나 어조를 세게 바꾸는 것,
- 같은 지시에 숫자만 붙이는 것,
- 같은 지시를 시스템 프롬프트에서 사용자 메시지로 옮기는 것

은 모두 **근본 원인(지시 자체가 모호하다는 것)을 건드리지 않은 표면 수정**입니다. 원인이 "모호함"이면 해법은 "구체화"여야 합니다.

### 1.6 정밀도(Precision)와 재현율(Recall)

- **정밀도(Precision)**: 시스템이 "문제다"라고 신고한 것 중 실제로 문제인 비율. 낮으면 **오탐(false positive)**이 많습니다.
- **재현율(Recall)**: 실제 문제들 중 시스템이 잡아낸 비율. 낮으면 **누락(false negative)**이 많습니다.

"노이즈가 많은 카테고리"란 보통 정밀도가 낮은 카테고리를 뜻합니다. 정밀도를 올리는 정석은 위 1.5의 포함/제외 기준 명시입니다.

## 2. 구조화된 출력(Structured Output)

### 2.1 왜 구조화가 필요한가

LLM의 기본 출력은 자유 형식 텍스트입니다. 하지만 프로그램이 소비하려면 정해진 형태(JSON 등)여야 합니다. 그래서 출력 형식을 강제하는 장치가 필요합니다.

### 2.2 JSON Schema

JSON 데이터의 "형태"를 기술하는 표준 명세입니다.

```json
{
  "type": "object",
  "properties": {
    "amount": { "type": "number" },
    "currency": { "type": "string", "enum": ["USD", "EUR", "KRW"] },
    "transaction_type": { "type": "string", "enum": ["deposit", "withdrawal"] }
  },
  "required": ["amount", "currency", "transaction_type"]
}
```

스키마가 표현할 수 있는 것:
- 필드의 **데이터 타입**(number, string, boolean, array, object)
- **필수 필드(required)** 여부
- 허용값 목록(**enum**), 숫자 범위(minimum/maximum), 문자열 패턴(pattern, 정규식)
- 중첩 구조, 배열 원소의 타입

### 2.3 Tool Use를 통한 스키마 강제

Claude API 등에서는 "도구(tool)"를 정의하면서 그 입력 형태를 `input_schema`로 지정합니다. 모델이 그 도구를 호출하면, 호출 인자가 해당 스키마 형태로 생성됩니다. 즉 **도구 호출을 구조화 출력의 수단으로 사용**하는 패턴입니다.

```json
{
  "name": "record_transaction",
  "description": "PDF 내역서에서 추출한 거래 한 건을 기록한다.",
  "input_schema": { "...위의 스키마..." }
}
```

관련 옵션들:

- **`tool_choice`**: 모델이 도구를 쓸지 말지 결정하게 둘지(`auto`), 반드시 어떤 도구를 부르게 할지(`any` 또는 특정 도구 지정)를 제어합니다. **호출 여부만 강제할 뿐, 인자 값의 내용이 옳은지는 보장하지 않습니다.**
- **strict mode**: 출력이 스키마 구조를 한 치도 어기지 않도록 강제하는 모드입니다. 이것도 **구조**의 문제이지 **내용**의 문제가 아닙니다.

### 2.4 스키마 검증이 잡아주는 것과 못 잡는 것 — 가장 중요한 구분

| | 잡아준다 | 못 잡는다 |
|---|---|---|
| 필드가 빠졌는가 | O | |
| 타입이 맞는가(숫자 자리에 문자열) | O | |
| enum에 없는 값인가 | O | |
| 값이 **원본 문서의 실제 내용과 일치하는가** | | X |
| 두 필드 사이의 **의미적 정합성** | | X |

#### 구문/구조 오류(Schema Violation) vs 의미론적 오류(Semantic Error)

- **스키마 위반**: `amount`가 없다, `amount`에 `"삼천"`이 들어왔다 → 검증기가 에러를 냅니다.
- **의미론적 오류**: `amount`는 정상적인 숫자 `50000`이고 필수 필드도 다 있는데, **원본에는 입금(deposit)인데 출금(withdrawal)으로 라벨링**되었다. 또는 원본이 EUR인데 통화 기호를 잘못 읽어 USD로 기록되었다.

두 번째 경우 **스키마 검증은 아무 불평 없이 통과합니다.** 이것이 구조화 출력의 근본적 한계입니다.

**전형적인 오답 패턴 3가지** — 의미론적 오류를 만났을 때 다음은 모두 틀린 진단입니다.
- "스키마 위반이다" → 아니다. 타입도 필수 조건도 다 만족했다.
- "strict mode를 켜면 된다 / 스키마를 더 잘 짜면 된다" → 아니다. JSON Schema는 원본 문서를 읽지 않으므로 원본 대비 정확성을 검증할 방법이 없다.
- "`tool_choice`로 강제하면 된다" → 아니다. 호출 여부와 인자 내용의 진위는 별개다.
- "`max_tokens`를 늘리면 된다" → 아니다. 잘림(truncation) 문제가 아니다(2.6 참고).

### 2.5 해법: 의미론적/비즈니스 검증 계층(Cross-check)

스키마 검증 **뒤에** 별도의 검증 단계를 둡니다. 이것은 LLM이 아니라 보통 평범한 코드로 씁니다.

```python
def cross_check(record, source_text):
    # 통화 기호와 금액 표기를 대조
    if record["currency"] == "USD" and "€" in source_text:
        raise SemanticError("통화 기호 불일치")
    # 거래 유형과 부호 대조
    if record["transaction_type"] == "deposit" and record["amount"] < 0:
        raise SemanticError("입금인데 금액이 음수")
```

**원칙**: 구조 검증(스키마)과 의미 검증(비즈니스 규칙)은 서로 다른 계층이며, 둘 다 필요합니다.

### 2.6 `max_tokens`와 잘림(Truncation)

`max_tokens`는 모델이 한 번의 응답에서 **생성할 수 있는 최대 출력 토큰 수**입니다. 이 한도에 도달하면 응답이 문장 중간에서 끊깁니다(truncation). 증상은 명확합니다: **JSON이 닫히지 않은 채 끝남, 배열이 중간에서 잘림, 파싱 에러.**

따라서 다음의 경우는 `max_tokens`와 **무관**합니다:
- JSON이 완전한 형태로 나왔는데 값이 틀린 경우 (→ 의미론적 오류)
- 원본에 정보가 없어서 빈 값이 나온 경우 (→ 데이터 부재)
- 합계가 안 맞는 경우 (→ 원본 데이터 오류이거나 계산 오류)

### 2.7 필드 세분화(Granularity) 설계

출력 스키마의 각 필드를 **얼마나 잘게** 기록할지는 나중의 분석 능력을 결정합니다.

예: 코드 검토 어시스턴트가 발견 항목마다 `detected_pattern` 필드를 기록한다고 할 때,

- **거친 범주(coarse)**: `"security"`
- **구체적 트리거(fine-grained)**: `"regex:sql_concat_v3"`, `"function:eval"`, `"decorator:@app.route_without_auth"`

**왜 세분화가 중요한가 — 피드백 루프**: 개발자가 경고를 **기각(dismiss)**하는 행동은 오탐의 신호입니다. 하지만 `"security"`로만 기록해두면 "보안 경고 기각률 40%"라는 사실만 남고, **어떤 규칙이 범인인지 알 수 없습니다.** 구체적 규칙 단위로 기록하면 "`regex:sql_concat_v3`의 기각률이 90%"라는 식으로 **원인을 격리(isolate)**하여 그 규칙만 수정할 수 있습니다.

**흔한 잘못된 반론**:
- "대시보드가 렌더링하기 쉬우려면 값 종류가 적어야 한다" → 세밀한 데이터는 나중에 **집계(group by)**해서 거칠게 만들 수 있지만, 거친 데이터를 나중에 세밀하게 되돌릴 수는 없습니다. 표현 편의를 위해 데이터 해상도를 버리는 것은 잘못된 설계입니다.
- "심각도(severity) 필드로 분석하면 된다" → 심각도는 "얼마나 위험한가"이지 "어떤 규칙이 발동했는가"가 아니므로 원인 추적에 쓸 수 없습니다.

**일반 원칙**: 로그와 메타데이터는 **나중에 물어볼 질문을 답할 수 있는 해상도로** 기록하라. 집계는 나중에 해도 되지만, 기록하지 않은 정보는 영원히 복구되지 않는다.

## 3. 재시도(Retry)와 실패 처리

### 3.1 재시도 루프란

검증에 실패하면 오류 내용을 모델에게 알려주고 다시 시도하게 하는 패턴입니다.

```python
for attempt in range(MAX_RETRIES):
    result = call_model(prompt)
    error = validate(result)
    if error is None:
        return result
    prompt += f"\n이전 시도의 오류: {error}. 수정해서 다시 출력하라."
raise ExtractionFailed()
```

### 3.2 재시도가 고칠 수 있는 것

- 일시적인 형식 오류(JSON 문법 깨짐, 필드 누락)
- 모델의 우발적 실수, 부주의로 인한 오독
- 지시를 한 번 놓친 경우

즉 **모델 측의 교정 가능한(correctable) 실수**입니다.

### 3.3 재시도가 절대 고칠 수 없는 것 — 재시도의 한계

#### (a) 원본에 정보가 존재하지 않는 경우 (Data Absence)

스캔된 서식에서 필요한 필드가 검은 마커로 가려져(**redacted**) 있다면, 모델은 그 값을 읽을 수 없습니다. 100번 재시도하며 상세한 오류 피드백을 줘도 빈 값만 반복됩니다. **없는 정보는 복구할 수 없습니다.** 억지로 채우게 만들면 그것은 환각(hallucination)이며 더 나쁩니다.

#### (b) 원본 데이터 자체가 모순된 경우 (Source Data Error)

은행 내역서의 개별 거래 합계와 명시된 총액이 안 맞는데, 조사해보니 **발급 은행이 실제로 산술 오류를 냈다**면, 모델은 원본에 적힌 숫자를 정확히 추출하고 있는 것입니다. 검증 규칙은 계속 실패하고, 재시도는 컴퓨팅 비용만 태웁니다. 계속 재시도하면 모델이 "합이 맞게" 숫자를 조작하도록 유도하는 셈이 되어 더 위험합니다.

### 3.4 올바른 대응: 실패의 종류를 구분하라

| 실패 원인 | 올바른 대응 |
|---|---|
| 모델의 형식 오류 / 우발적 실수 | 피드백과 함께 재시도 |
| 프롬프트 설계 미비(형식 변형 미대응 등) | 프롬프트/예시 개선 |
| 원본에 정보 부재 | 재시도 중단, 필드를 `null`로 두고 사람 검토로 이관 |
| 원본 데이터 모순 | 재시도 중단, 원본 데이터 이슈로 플래그하고 사람에게 이관 |

**절대 하면 안 되는 것**:
- 무한 재시도 (비용 낭비 + 환각 유도)
- 문제를 감지하는 검증 필드를 스키마에서 삭제해 **증상을 숨기기** (예: 합계 불일치가 싫다고 `statement_total` 필드를 제거) — 검증 파이프라인의 존재 이유를 무너뜨립니다
- 처리하기 어려운 입력 형식을 아예 **거부(reject)**해서 요구사항을 포기하기

### 3.5 사람 검토로의 이관(Escalation)

자동화가 판단할 수 없거나 위험한 경우 사람에게 넘기는 것은 **실패가 아니라 설계된 안전장치**입니다. 콘텐츠 중재, 재무 대조, 개인정보 추출 등에서는 "판단 유보 → 사람"이 정답인 경로가 반드시 존재해야 합니다.

## 4. 동기 API vs 배치 API, 그리고 SLA 계산

### 4.1 Messages API (동기, synchronous)

요청을 보내면 그 자리에서 응답을 기다리는 방식입니다.
- **장점**: 지연 시간(latency)이 짧고, 스트리밍으로 토큰이 생성되는 즉시 받을 수 있음.
- **용도**: 사용자가 화면 앞에서 기다리는 실시간 대화, 챗봇, 코드 어시스턴트.
- **단점**: 대량 작업에는 비효율적이고 비쌉니다.

### 4.2 Message Batches API (비동기, asynchronous)

많은 요청을 하나의 묶음(batch)으로 제출하고, 나중에 결과를 받아가는 방식입니다.

핵심 성질:
- **최대 24시간 이내 처리**를 목표로 하는 처리 시간 창(SLA). 더 빨리 끝날 수도 있지만 최악의 경우 24시간까지 걸릴 수 있다고 봐야 합니다.
- **동기 API 대비 약 50% 저렴**합니다.
- 즉시 응답이 없으므로 **지연 시간에 관대한(latency-tolerant)** 작업에만 적합합니다.

### 4.3 어느 쪽을 고를 것인가

판단 기준은 딱 두 가지입니다.

1. **누군가 결과를 기다리고 있는가?** 기다린다면 동기, 아니면 배치 후보.
2. **비용이 중요한가?** 중요하고 지연 허용되면 배치.

예: 매일 밤 40,000개 모듈에 대해 테스트 케이스를 생성하고, 개발자는 다음 날 아침에 보면 되며, 비용 효율이 최우선 → **Batches API**가 정답입니다. 지연 허용 + 대량 + 50% 절감이 모두 맞아떨어집니다.

**주의해야 할 잘못된 근거들**:
- "요청이 수백 건 넘으면 배치가 **필수**다" → 그런 강제 규칙은 없습니다. 선택 기준은 지연 허용 여부와 비용입니다.
- "야간 작업이니 총 소요 시간을 최소화해야 하므로 동기 + 스트리밍" → 아무도 안 기다리는데 벽시계 시간을 줄일 이유가 없습니다.
- "순차 실행이 완료를 보장한다" → 40,000건 순차 호출은 엄청난 시간과 비용, 타임아웃 위험만 낳습니다.

### 4.4 SLA와 최악의 경우(Worst-case) 대기 시간 계산

배치를 주기적으로 제출하는 파이프라인의 총 소요 시간은 두 조각입니다.

```
총 소요 시간 = (문서가 다음 배치 제출까지 대기하는 시간) + (배치 처리 시간)
```

최악의 경우, 문서는 **직전 배치가 막 떠난 직후**에 도착합니다. 그러면 제출 주기 전체를 기다려야 합니다.

```
T_대기(최악) = T_제출주기
T_처리(최악) = T_배치최대실행시간
```

따라서 SLA를 지키려면:

```
T_제출주기 + T_배치최대실행시간 ≤ T_SLA
∴ T_제출주기(최대) = T_SLA − T_배치최대실행시간
```

**구체적 예**: SLA가 수집 후 48시간, 배치 최대 처리 시간이 24시간이라면

```
최장 제출 주기 = 48 − 24 = 24시간
```

- 6시간이나 12시간 주기도 SLA는 만족하지만, "**가장 긴** 간격"을 묻는다면 답이 아닙니다.
- 48시간 주기는 최악의 경우 48 + 24 = 72시간이 되어 SLA를 위반합니다. **마감 시간을 그대로 제출 주기로 쓰면 안 됩니다** — 처리 시간을 뺀 나머지가 대기 예산입니다.

## 5. LLM 기반 코드 검토 아키텍처

### 5.1 문제: 큰 입력을 한 번에 주면 생기는 일

60개 파일에 걸친 변경(diff)을 단일 모델 호출에 통째로 넣으면:
- **주의력 분산**: 입력이 길어질수록 모델은 특정 부분에 대한 집중도를 잃습니다.
- **Lost in the middle**: 긴 컨텍스트의 중간 부분 정보가 앞뒤보다 덜 활용되는 현상.
- 결과적으로 **파일 간 모순되는 검토 결과**(A 파일에서는 이렇게 하라 하고, B 파일에서는 반대로 지적)가 나옵니다.

**컨텍스트 윈도우를 키우는 것만으로는 해결되지 않습니다.** 넣을 수 있는 양(용량)과 실제로 잘 활용하는 능력(주의력)은 다른 문제입니다.

### 5.2 해법: 분할 정복(Divide and Conquer) 검토 아키텍처

역할을 두 계층으로 나눕니다.

**1단계 — 파일별 검토(Per-file pass)**
- 각 파일을 하나씩, 별도의 호출로 검토합니다.
- 잡는 것: 그 파일 **안에서 완결되는** 문제 — 문법 오류, 로컬 로직 오류, 네이밍, 미사용 변수, 파일 내 예외 처리 누락.
- 한계: **각 파일을 격리해서 판단하므로 파일 밖의 사실은 모릅니다.**

**2단계 — 교차 파일 통합 검토(Cross-file integration pass)**
- 파일 경계를 넘나들며 **데이터 흐름과 인터페이스 사용**을 추적합니다.
- 잡는 것: 모듈 A의 함수 시그니처가 바뀌었는데 호출부인 모듈 B, C가 일관되게 갱신되지 않은 문제, 타입 계약 불일치, 순환 의존, 설정 값의 앞뒤 불일치.

이 구조는 map-reduce와 같은 형태입니다: 각 파일을 개별 처리(map)한 뒤, 전체를 아우르는 일관성 검사(reduce)를 별도로 수행합니다.

### 5.3 왜 다른 대안들이 부족한가

- **파일별 검토를 두 번 하기 / 같은 파일을 두 번 읽기**: 격리 판단이라는 구조적 한계는 그대로입니다. 모듈 A를 아무리 여러 번 읽어도 모듈 B의 잘못된 호출은 시야에 없습니다.
- **A와 B만 한꺼번에 읽기**: 임시방편입니다. 모듈 C와의 불일치는 여전히 놓칩니다. 교차 파일 분석의 정식 메커니즘을 대체하지 못합니다.
- **동일한 검토를 두 번 돌려 교집합만 남기기**: 근본 원인(컨텍스트 과부하)이 그대로이므로 두 번 다 틀릴 수 있습니다.
- **생성기(코드를 작성한 LLM) 자신에게 자체 검토를 맡기기**: 생성기는 자기 의도를 "기억한다"고 여기지만, 컨텍스트 유실과 환각으로 신뢰할 수 없습니다. 무엇보다 자기가 만든 오류를 자기가 발견하는 데는 편향이 있습니다. **검증은 생성과 독립적인 단계여야 합니다.**
- **최근 커밋만 검토하기**: 누적된 변경 사이의 상호작용을 놓칩니다.

### 5.4 일반 원칙

> 격리된 검사는 격리된 문제만 잡는다. 관계에서 발생하는 문제는 관계를 보는 단계가 따로 있어야 잡힌다.

이 원칙은 코드 검토뿐 아니라 2.5의 "구조 검증과 의미 검증은 별개 계층"과 같은 사고방식입니다.

## 6. 에이전트와 도구(Tool) 설계

### 6.1 에이전트란

LLM이 여러 도구(함수) 중 어떤 것을 어떤 인자로 호출할지 스스로 결정하며 여러 단계를 진행하는 구성입니다. 예: `search_docs`(문서 검색)와 `search_code`(코드 검색)를 모두 가진 에이전트.

### 6.2 도구 정의의 구성 요소

```json
{
  "name": "search_code",
  "description": "소스 코드 저장소에서 심볼, 함수, 설정 값의 실제 정의 위치를 찾는다.",
  "input_schema": { "type": "object", "properties": { "query": {"type": "string"} } },
  "input_examples": [ ... ]
}
```

- **name**: 도구 식별자. 명확해야 하지만, 이름만으로 모든 모호성이 해소되지는 않습니다.
- **description**: 자연어 설명. 모델이 도구 선택의 1차 근거로 삼습니다.
- **input_schema**: 인자의 구조(2.3 참고).
- **input_examples**: 이 도구를 **언제, 어떤 요청에 대해** 어떤 인자로 부르는지 보여주는 예시. 도구 정의 안에 넣는 few-shot입니다.

### 6.3 도구 선택이 흔들리는 문제

"레이트 리밋(rate limit)이 어디에 정의되어 있나?"는 문서에도, 코드에도 답이 있을 수 있는 **모호한 요청**입니다. 이런 경우 에이전트는 세션마다 다른 도구를 고르게 됩니다.

**효과적인 해법 — `input_examples`에 근거를 담은 예시 넣기**:

```
요청: "레이트 리밋이 어디에 정의되어 있나?"
선택: search_code
이유: "어디에 정의(defined)되어 있는가"는 실제 값의 소스 위치를 묻는 것이므로,
      설명 문서보다 코드 저장소가 정답을 담고 있다.
      (정책이나 사용자 대상 한도 자체를 묻는다면 search_docs를 택한다.)
```

여기서도 **선택 + 근거**라는 1.3의 원칙이 그대로 적용됩니다. 예시가 "왜 다른 그럴듯한 선택지를 이겼는지"를 담아야 새로운 모호한 요청에도 일반화됩니다.

**덜 효과적인 대안들**:
- **설명에 형용사를 더 붙이기**: 장황해질 뿐 판단 기준을 주지 못합니다.
- **이름을 더 구별되게 바꾸기**: `search_docs`/`search_code`는 이미 충분히 구별됩니다. 문제는 이름 혼동이 아니라 **경계 기준의 부재**입니다.
- **하드코딩된 라우팅(항상 A를 먼저 호출하고 실패 시 B로 폴백)**: 에이전트의 추론을 없애버리고, 코드 검색이 명백히 맞는 상황에서도 불필요한 호출과 지연을 발생시킵니다.

## 7. 전체를 관통하는 사고 틀

이 주제 영역의 문제들은 대체로 다음 네 가지 질문으로 정리됩니다.

**Q1. 이 실패의 원인은 어느 계층에 있는가?**
프롬프트 설계 / 모델의 우발적 실수 / 출력 구조 / 출력 의미 / 원본 데이터 / 시스템 아키텍처. 원인 계층과 다른 계층을 수정하면 절대 고쳐지지 않습니다.

**Q2. 지시로 충분한가, 예시가 필요한가?**
단순 사실 전달이면 지시. 다단계 절차나 경계선 판단이면 근거를 곁들인 예시.

**Q3. 이 검증은 구조를 보는가, 의미를 보는가?**
스키마는 구조만. 의미는 별도의 교차 검증 규칙이 필요합니다.

**Q4. 재시도가 이걸 고칠 수 있는가?**
모델의 실수면 예. 원본의 부재나 모순이면 아니오 → 중단하고 사람에게.

그리고 공통 안티패턴:
- 증상을 숨기기(검증 필드 삭제, 어려운 입력 거부)
- 근본 원인과 무관한 파라미터 만지기(`max_tokens`, 컨텍스트 크기, 메시지 위치)
- 같은 접근을 더 세게/더 여러 번 반복하기
- 데이터 해상도를 편의를 위해 버리기

## 8. 용어 사전 (Glossary)

| English | 한국어 설명 |
|---|---|
| Prompt | 모델에게 주는 입력 텍스트 전체 |
| System prompt | 역할·규칙 등 대화 전반에 적용되는 지시 영역 |
| User message | 이번 요청의 구체적 내용이 담기는 영역 |
| Zero-shot | 예시 없이 지시만으로 작업을 시키는 방식 |
| Few-shot prompting | 프롬프트에 입력→출력 예시를 몇 개 넣어 패턴을 알려주는 기법 |
| In-context learning | 가중치 변경 없이 문맥에 넣은 예시만으로 동작이 바뀌는 현상 |
| Chain-of-Thought (CoT) | 최종 답뿐 아니라 중간 추론 과정/근거를 함께 다루는 방식 |
| Rationale | 예시에 붙이는 "왜 그렇게 판단했는지"에 대한 짧은 근거 |
| Generalization | 예시에 없던 새로운 사례에도 학습한 판단 기준을 적용하는 능력 |
| Borderline case | 어느 쪽으로도 판정 가능한 경계선상의 애매한 사례 |
| Ambiguous request | 여러 도구·경로 중 어느 쪽으로도 처리 가능한 모호한 요청 |
| Confidence language | "확신하는 것만 보고하라" 같은 주관적 신뢰도 지시어. 효과가 거의 없음 |
| Calibration | 모델이 자기 출력의 정확도를 실제 확률과 맞게 추정하는 능력. LLM은 약함 |
| Explicit scoping | 포함/제외 기준을 구체적 규칙으로 명시해 범위를 정의하는 것 |
| Inclusion / Exclusion criteria | 카테고리에 넣을 것과 뺄 것을 나열한 기준 목록 |
| Precision | 신고한 것 중 실제로 맞는 비율. 낮으면 오탐이 많음 |
| Recall | 실제 문제 중 잡아낸 비율. 낮으면 누락이 많음 |
| False positive | 오탐. 문제가 아닌데 문제라고 신고한 것 |
| Structured output | 프로그램이 소비할 수 있게 정해진 형식(JSON 등)으로 출력을 강제하는 것 |
| JSON Schema | JSON 데이터의 타입·필수 여부·허용값 등 구조를 기술하는 표준 |
| Schema validation | 출력이 스키마의 구조 규칙을 지켰는지 검사하는 것. 구조만 검사 |
| Schema violation | 필드 누락, 타입 불일치 등 구조 규칙 위반 |
| Semantic error | 구조는 완벽하지만 값의 의미가 원본과 다른 오류. 스키마로는 못 잡음 |
| Semantic accuracy | 추출값이 원본 문서의 실제 내용과 부합하는 정도 |
| Cross-check rule | 필드 간 또는 필드와 원본 간 정합성을 대조하는 비즈니스 검증 규칙 |
| Tool use | 모델이 정의된 도구(함수)를 호출하게 하는 기능. 구조화 출력 수단으로도 쓰임 |
| input_schema | 도구 호출 인자의 구조를 정의하는 JSON Schema |
| input_examples | 도구 정의 안에 넣는 사용 예시. 도구 선택과 인자 구성을 시연 |
| tool_choice | 도구 호출 여부/대상을 강제하는 옵션. 인자 값의 정확성은 보장 안 함 |
| Strict mode | 스키마 구조 준수를 엄격히 강제하는 모드. 의미 오류는 못 막음 |
| max_tokens | 응답에서 생성 가능한 최대 출력 토큰 수. 초과 시 응답이 잘림 |
| Truncation | 토큰 한도로 출력이 중간에서 끊기는 현상. JSON 미완결이 전형적 증상 |
| Retry loop | 검증 실패 시 오류 피드백과 함께 다시 호출하는 패턴 |
| Feedback retry | 무엇이 틀렸는지 알려주며 재시도하는 방식 |
| Data absence | 원본에 정보가 물리적으로 존재하지 않는 상태(예: 마커로 가려짐) |
| Redacted | 문서에서 정보가 검게 가려져 읽을 수 없게 처리된 상태 |
| Source data error | 원본 문서 자체에 오류·모순이 있는 상태. 재시도로 해결 불가 |
| Hallucination | 근거 없는 내용을 사실처럼 생성하는 현상 |
| Escalation | 자동 판단이 어려운 건을 사람 검토로 넘기는 것 |
| Messages API | 요청 즉시 응답을 받는 동기식 API. 저지연, 실시간용 |
| Message Batches API | 대량 요청을 묶어 비동기 처리하는 API. 최대 24시간, 약 50% 저렴 |
| Latency-tolerant | 결과가 늦게 나와도 문제없는 성질. 배치 처리의 전제 조건 |
| SLA (Service Level Agreement) | 서비스 수준 약속. 예: "수집 후 48시간 내 결과 전달" |
| Worst-case latency | 최악의 경우 총 소요 시간. 대기 시간 + 처리 시간으로 계산 |
| Ingestion | 문서가 파이프라인에 수집·투입되는 시점 |
| Wall-clock time | 실제 경과한 시계 시간 |
| Per-file pass | 파일을 하나씩 격리해서 검토하는 단계. 파일 내부 문제만 잡음 |
| Cross-file integration pass | 파일 경계를 넘어 데이터 흐름과 인터페이스를 추적하는 검토 단계 |
| Function signature | 함수의 이름·매개변수·반환 타입 등 호출 계약 |
| Runtime mismatch | 시그니처와 호출부가 어긋나 실행 중 발생하는 불일치 오류 |
| Context window | 모델이 한 번에 받아들일 수 있는 최대 토큰 양 |
| Lost in the middle | 긴 입력의 중간부 정보가 상대적으로 덜 활용되는 현상 |
| Divide and conquer | 큰 작업을 쪼개 처리한 뒤 통합하는 전략 |
| Self-review | 생성한 주체가 스스로 검토하는 것. 편향과 컨텍스트 유실로 신뢰도 낮음 |
| Agent | 도구 선택과 다단계 실행을 스스로 결정하는 LLM 구성 |
| Routing | 요청을 적절한 처리 경로(도구, 대기열 등)로 보내는 것 |
| Granularity | 데이터를 얼마나 잘게 기록하는지의 수준(해상도) |
| Detected pattern | 검토 시스템이 무엇을 근거로 항목을 감지했는지 기록하는 필드 |
| Dismissal | 개발자가 시스템 경고를 무시·기각하는 행동. 오탐의 신호 |
| Isolate (a rule) | 문제를 일으키는 특정 규칙을 데이터로 정확히 짚어내는 것 |
