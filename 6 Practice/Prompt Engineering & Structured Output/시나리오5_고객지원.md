# 시나리오5_고객지원

## 질문 1

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : Before calling process_refund, the agent produces a structured dispute record. Validation fails: refund_amount is 85.00 but the extracted disputed line items sum to 70.00, and order_date is not ISO 8601. What should the retry request contain?

**A.** Resubmit the original prompt with a general reminder appended to double-check amounts and date formats.

**설명**

일반적인 리마인더는 오류 피드백이 아니라 모호한 지시일 뿐이다. 구체적으로 어떤 값이 충돌했는지, 어떤 필드가 형식을 위반했는지 알려주지 않는다. 재시도가 빠르게 수렴하려면 구체적인 검증 오류가 필요하다.

**B.** Resubmit the original prompt unchanged, relying on regeneration to produce a valid record.

**설명**

아무런 피드백 없이 재제출하면 재시도가 표적화된 수정이 아니라 다시 한번 무작위로 시도하는 것에 불과해진다. 모델은 무엇이 잘못되었는지에 대한 신호가 전혀 없으므로 동일한 산술 오류와 형식 오류가 다시 발생할 가능성이 높다.

**C(정답).** Include the source conversation and order data, the failed record, and the two specific validation errors.

**설명**

이것은 오류 피드백을 포함한 재시도 패턴이다. 모델은 자신이 생성한 결과, 정확히 무엇이 잘못되었는지, 그리고 수정 시 참조해야 할 원본 자료를 모두 확인할 수 있다. 이 세 가지가 모두 제공되면 보통 한두 번의 재시도로 이런 형식 및 산술 불일치를 해결할 수 있다.

**D.** Send only the two validation errors plus a firmer instruction to comply, omitting the failed record and source data.

**설명**

오류만으로는 충분하지 않다. 실패한 결과물이 없으면 모델은 어떤 값을 수정해야 하는지 알 수 없고, 원본 데이터가 없으면 환불 금액이나 항목 내역을 다시 근거로 삼을 수 없다. 더 강한 어조의 지시는 수정을 이끌어낼 실질적인 정보를 추가로 제공하지 않는다.

### 전반적인 설명

검증-재시도 루프는 구조화된 출력에 대한 표준적인 신뢰성 패턴이다. 모델이 생성하고, 코드가 스키마와 비즈니스 규칙에 따라 검증하며, 실패하면 피드백과 함께 다시 프롬프트를 보낸다. 재시도를 효과적으로 만드는 것은 그 구성 요소다. 모델에는 세 가지가 필요하다. 올바른 값을 다시 도출할 수 있게 해주는 원본 자료(대화 내용과 주문 데이터), 무엇을 수정해야 하는지 알 수 있게 해주는 실패한 결과물, 그리고 맹목적인 재생성이 아니라 표적화된 수정이 되도록 하는 구체적인 오류("refund_amount는 85.00이지만 항목 합계는 70.00입니다. order_date는 ISO 8601 형식이어야 합니다")다. 여기서 두 오류 모두 재시도로 해결 가능한 종류다. 모델이 다시 확인할 수 있는 산술 불일치와 다시 포맷할 수 있는 형식 위반이다. 필요한 정보가 원본 자료에 전혀 없는 경우에만 재시도가 무의미해진다.

핵심 개념은 피드백 없는 재시도는 단순한 재추출일 뿐이며 실패 확률이 거의 변하지 않는다는 것이다. 실패한 결과물이나 원본 데이터를 빼면 모델이 문제가 되는 값을 찾거나 다시 근거를 세울 수 없게 되며, "다시 확인하라"는 식의 일반적인 리마인더는 구체적인 기준과 구체적인 오류가 대체하고자 하는 바로 그 모호한 지시에 해당한다. 실무에서는 이 루프를 의미론적 자체 검증 필드(명시된 합계와 계산된 합계를 함께 추출하고 충돌 플래그를 두는 방식)와 결합해, 이런 불일치를 환불 도구가 호출되기 전에 기계적으로 탐지하도록 하는 것이 좋다.

## 질문 2

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : You add a verification pass that checks each drafted resolution against refund and escalation policy before it executes, routing risky drafts to a human. How should the verifier's output be designed for calibrated routing?

**A.** Return a single approve or reject verdict per draft so the routing logic stays deterministic and simple to implement.

**설명**

이것은 틀렸다. 단순한 승인/거부 판정은 라우팅에 필요한 보정(calibration) 신호를 버리는 것이다. 발견 항목별 신뢰도와 심각도가 없으면 플래그가 붙은 모든 초안이 동일하게 취급되어, 저위험 초안까지 사람이 검토하게 되고 실제로 위험한 초안에 대한 임계값은 조정할 수 없다.

**B.** Have the same session that drafted the resolution re-check it and flag anything it now judges a likely policy violation.

**설명**

이것은 틀렸다. 자신의 생성 컨텍스트 내에서 검토하는 모델은 그 추론을 그대로 유지하고 있어 자신의 결정에 이의를 제기할 가능성이 낮다. 그런 컨텍스트가 없는 독립적인 검증 단계가 자체 검토로는 합리화되어 넘어가는 문제를 잡아낸다.

**C.** Instruct the verifier to report only high-confidence, high-severity policy violations so routing receives an already-filtered signal.

**설명**

이것은 틀렸다. 발견 단계 자체에 필터링을 지시하면 라우팅이 확인하기도 전에 불확실한 발견 항목이 억제되어 재현율(recall)이 낮아진다. Claude는 이런 지시를 문자 그대로 따르는 경향이 있어, 경계선상의 위험한 초안이 조용히 승인되어 버린다.

**D(정답).** Have the verifier report every potential issue with a confidence level and severity for each, applying routing thresholds downstream.

**설명**

이것이 정답이다. 발견과 필터링을 분리하면 재현율과 라우팅 정밀도를 모두 유지할 수 있다. 검증자는 눈에 띄는 모든 것을 드러내고, 각 항목에는 신뢰도와 심각도가 함께 붙어 있어 후속 단계가 어떤 초안에 사람의 검토가 필요한지 판단하는 데 사용할 수 있다.

### 전반적인 설명

여기서의 설계 원칙은 발견(finding)과 필터링(filtering)을 분리하는 것이다. 검증 단계는 서로 반대 방향으로 작동하는 두 가지 별개의 역할을 갖는다. 잘못될 수 있는 모든 것을 알아채는 것(포괄성)과, 조치를 취할 만큼 중요한 것을 판단하는 것(필터링)이다. 이 두 역할이 하나의 프롬프트로 뭉쳐지면 "고신뢰도 위반만 보고하라"와 같은 지시가 문자 그대로 실행된다. 모델은 여전히 철저히 조사하지만 불확실한 발견 항목을 억제해버리고, 그런 항목은 라우팅 로직에 아예 도달하지 못한다. 리뷰 형태의 하네스에 대한 Anthropic의 가이드는 이 점을 명확히 하고 있다. 모델에게 불확실하거나 심각도가 낮은 항목을 포함해 발견한 모든 문제를 보고하도록 요청하고, 각 항목에 신뢰도와 추정 심각도를 함께 붙여 후속 단계가 순위를 매기고 라우팅할 수 있게 하라는 것이다. Prompting Claude Sonnet 5를 참고하라.

핵심 개념은 2단계 파이프라인이다. 1단계는 재현율을 최대화하고 각 발견 항목에 자체 보고된 신뢰도와 심각도를 주석으로 붙인다. 2단계는 코드에서 임계값을 적용하는데, 이렇게 하면 조정 가능하고 감사 가능하며 일관성이 유지된다. 고객지원 에이전트의 경우, 신뢰도는 낮지만 심각도가 높은 정책 우려가 있는 환불 초안은 여전히 사람에게 라우팅될 수 있고, 심각도가 낮은 형식상의 문제는 자동 승인될 수 있다는 뜻이다. 검증자 내부에서 미리 필터링해버리면 이런 임계값이 보이지 않게 되고 조정할 수 없게 된다. 같은 세션에서의 자체 검토는 다른 방식으로 실패한다. 모델은 초안을 만들어낸 추론을 그대로 지니고 있어 자신의 결론을 확인하는 경향이 있으며, 이것이 독립적인 검증 인스턴스가 더 미묘한 문제를 잡아내는 이유다. 단순한 승인/거부 판정은 가장 취약한 설계인데, 라우팅을 전부 아니면 전무가 아니라 보정된 방식으로 만들어주는 등급화된 신호를 버리기 때문이다.

## 질문 3

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : Alongside live conversations, the team runs a nightly audit that re-scores every resolved ticket for policy compliance. To capture the Message Batches API's 50% discount, how should these two workloads be split across APIs?

**A.** Submit live conversations as batches with a synchronous fallback triggered whenever a batch has not completed within a few minutes.

**설명**

이 설계는 배치 제출 비용을 지불한 후 종종 동기 호출 비용을 또다시 지불하게 되어, 신뢰할 수 있는 비용 절감 없이 복잡성과 지연만 늘어난다. 지연 시간 보장이 없기 때문에 폴백이 자주 발동될 가능성이 높으며, 결국 실시간 워크로드는 추가 장치가 덧붙은 채로 실질적으로 동기 방식으로 남게 된다.

**B.** Submit both workloads as batches, since most batches finish in under an hour and polling can surface results quickly.

**설명**

대부분의 배치가 한 시간 이내에 완료되는 것은 맞지만, 지연 시간에 대한 SLA는 없으며 처리에 최대 24시간이 걸릴 수 있다. 실시간 대화 중인 고객은 보장이 없는 시간 창을 기다릴 수 없으므로, 일반적인 배치 처리 속도와 무관하게 실시간 상호작용은 동기 방식으로 유지되어야 한다.

**C(정답).** Submit the nightly ticket audit as a batch and keep live customer conversations on synchronous Messages API calls.

**설명**

이것이 정답이다. 야간 감사는 지연 시간에 관대하고 논블로킹 방식이므로 최대 24시간까지 걸리는 배치 API의 처리 시간 창에 문제없이 들어맞고 50% 할인을 받을 수 있다. 실시간 대화는 고객이 실제로 기다리고 있으므로 동기 응답이 필요한 블로킹 워크로드다.

**D.** Keep both workloads synchronous, because batch results can return out of input order and cannot be reliably matched to tickets.

**설명**

배치 결과가 입력 순서와 다르게 반환될 수 있는 것은 사실이지만, API는 각 결과를 원래 요청으로 상관시킬 수 있도록 custom_id 필드를 제공한다. 순서 문제는 이미 해결된 문제이며, 야간 감사에서 50% 절감 효과를 포기할 이유가 되지 않는다.

### 전반적인 설명

Message Batches API는 지연 시간을 비용과 교환한다. 요청은 비동기로 처리되며 대부분의 배치는 한 시간 이내에 완료되지만, 지연 시간 SLA 없이 처리에 최대 24시간이 걸릴 수 있고, 그 대가로 표준 요금 대비 50% 할인을 받는다. 따라서 결정 기준은 "누가 기다리고 있는가"이다. 이미 해결된 티켓에 대한 야간 컴플라이언스 감사는 전형적인 배치 워크로드다. 아무도 기다리지 않는 오프라인 논블로킹 작업이므로 비동기 완료를 감내할 수 있고, 물량이 많아 할인 효과가 의미 있다. 실시간 고객 상담은 정반대의 성격을 갖는다. 고객이 매 턴마다 기다리고 있으므로 동기 방식 Messages API 호출을 사용해야 한다.

순서 관련 반론은 API의 설계를 잘못 이해한 것이다. 배치 내 각 요청은 custom_id(1~64자)를 가지고 있어, 배치가 processing_status: "ended" 상태가 되었을 때 .jsonl 파일로 도착하는 결과를 원래 티켓으로 정확히 매핑할 수 있다. 실시간 트래픽에 배치와 폴백을 혼합하는 방식은 안티 패턴이다. 어떤 시점에서도 완료 보장이 없기 때문에 동기 폴백이 실제 경로가 되어버리는 경향이 있으며, 이 아키텍처는 배치 제출 비용과 동기 호출 비용을 모두 지불하면서 지연 시간까지 추가로 부담하게 된다. 실시간 트래픽을 일반적인 한 시간 이내 완료 시간에 걸 경우, 흔히 발생하는 결과를 보장으로 오해하는 것이다. 분포의 꼬리는 하루 전체에 달한다.

문서화된 사용 사례, 지연 시간 특성, custom_id 상관 메커니즘에 대해서는 공식 Batch processing 가이드를 참고하라.

## 질문 4

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : In testing, the request "my order arrived broken" sometimes triggers an immediate process_refund and sometimes a lookup_order investigation first. Detailed prompt instructions have not made the behavior consistent. What change most reliably fixes this?

**A(정답).** Add 3-5 examples of ambiguous requests, each showing the chosen tool sequence with a rationale for rejecting the plausible alternative.

**설명**

이것이 정답이다. 표적화된 퓨샷(few-shot) 예시는 프롬프트 문구로는 전달하기 어려운 판단 기준을 전달한다. 선택된 행동과 함께 경쟁 관계의 행동이 왜 기각되었는지에 대한 근거를 보여주면 결정 경계 자체를 가르치게 되어, 모델이 단어 패턴을 매칭하는 것이 아니라 새로운 모호한 표현에도 일반화할 수 있게 된다.

**B.** Add examples showing only the final tool call for each request type, keeping them short so they do not dilute the system prompt.

**설명**

입력과 도구 호출만 짧게 짝지은 예시는 형식만 보여줄 뿐 판단 기준은 보여주지 못한다. 왜 한 행동이 다른 그럴듯한 대안보다 선택되었는지 설명하는 근거가 없으면 모델이 일반화할 원칙이 없으므로, 예시가 간결해도 새로운 모호한 요청에 대한 불일치는 계속된다.

**C.** Add ten or more examples covering every request phrasing the team has logged so the agent can match new messages to prior cases.

**설명**

이는 퓨샷 프롬프팅을 교육 메커니즘이 아니라 조회 테이블처럼 다루는 것이다. 표적화 없는 양적 확대는 컨텍스트를 불필요하게 늘리고 정작 중요한 예시의 신호를 희석시키며, 로그에 없던 표현에는 여전히 실패한다. 진짜 모호함을 겨냥한 소수의 예시가 더 잘 일반화된다.

**D.** Add examples of clear-cut requests only, since ambiguous cases would teach the model conflicting patterns it cannot generalize from.

**설명**

이는 표적화의 방향이 반대다. 명확한 사례는 모델이 이미 잘 처리하는 경우다. 퓨샷 예시의 가치는 바로 모호함을 해결하는 방법을 보여주는 데 있다. 근거가 잘 구성된 모호한 예시는 서로 충돌하지 않으며, 오히려 어려운 사례에 일관된 결정 규칙이 적용되는 모습을 보여준다.

### 전반적인 설명

여기서의 실패는 형식 문제가 아니라 판단 경계 문제다. "주문한 물건이 파손되어 도착했다"는 정말로 모호한 표현이다. 즉시 환불이 타당할 수도 있고, 먼저 조사가 필요할 수도 있다. "환불 전에 조사하라" 같은 프롬프트 규칙은 목표를 서술할 뿐, 경계선상의 사례를 결정하는 추론 자체를 전달하지는 못한다. 상세한 지시에도 여전히 일관되지 않은 동작이 나온다면, 이는 규칙에서 예시로 전환해야 한다는 신호로 문서화되어 있다.

모호함에 대한 효과적인 퓨샷 설계에는 두 가지 특성이 있다. 첫째는 표적화다. 소수의 예시(Anthropic 문서는 최상의 결과를 위해 3~5개를 권장하며, 잘 선택된 소수의 예시가 대량 커버리지보다 낫다고 명시한다)를 에이전트가 흔들리는 요청에 정확히 겨냥해야 한다. 둘째는 명시적인 추론이다. 각 예시는 선택된 도구 호출 순서와 함께, 왜 그럴듯한 대안이 기각되었는지 설명하는 근거를 짝지어야 한다. 예를 들어 "'파손'이 배송 손상을 의미할 수 있고 주문 정보가 필요할 수 있으므로 먼저 lookup_order를 호출한다. 즉시 환불하면 잘못된 처리로 이어질 위험이 있다"와 같은 식이다. 이 근거가 있어야 모델이 표면적 패턴을 외우는 것이 아니라 본 적 없는 표현에도 규칙을 일반화할 수 있다. Anthropic 문서는 또한 예시가 관련성 있고 다양하며 구조화되어 있어야 한다고(<example> 태그로 감싸는 등) 권장한다. 그래야 우연한 상관관계를 가르치지 않으면서 엣지 케이스를 다룰 수 있다.

각 대안은 이 두 특성 중 하나를 놓치고 있다. 로그 기반의 대량 예시는 과거 표현의 커버리지를 최적화하지만 주의력을 저하시키고 새로운 표현에는 실패한다. 명확한 사례만 사용하는 방식은 모델이 도움이 필요 없는 곳에 예시 예산을 소비한다. 형식만 있는 도구 호출 쌍은 형식은 고정시키지만 실제로 가르쳐야 할 판단력은 빠져 있다. 예시에 대한 Anthropic의 프롬프트 엔지니어링 가이드와 Increase output consistency를 참고하라.

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : In pilot testing, a same-session self-review step approves drafts containing subtle policy misapplications; the agent's reasoning shows it considered and dismissed each concern during generation. What change most directly addresses this limitation?

**A(정답).** Route each draft, along with the case data, to a separate Claude instance that lacks the generation session's reasoning.

**설명**

이것이 정답이다. 생성자의 추론을 전혀 보지 않은 새 인스턴스는 결함 있는 초안을 만들어낸 근거들에 얽매이지 않으므로, 사례 데이터에 대해 그 자체의 판단으로 해결 방안을 평가할 수 있다. Anthropic의 가이드는 바로 이런 독립성을 위해 생성된 결과물을 검토할 때 별도의 인스턴스나 새로운 컨텍스트를 사용할 것을 권장한다.

**B.** Add stronger self-critique instructions telling the same session to challenge its own conclusions before responding.

**설명**

이것은 틀렸다. 여기서 설명된 실패는 구조적인 문제다. 세션은 각 결정을 정당화한 추론을 그대로 유지하고 있어서 그 결정을 재확인하는 쪽으로 기울지, 이의를 제기하는 쪽으로는 잘 가지 않는다. 더 강한 문구를 쓴다고 해서 세션에 내재된 공유 컨텍스트로 인한 편향이 사라지지는 않는다.

**C.** Generate two drafts within the same session and release a response only when both drafts reach matching conclusions.

**설명**

이것은 틀렸다. 두 초안 모두 동일한 대화 이력과 동일한 추론 컨텍스트에서 만들어지므로, 바로 그 컨텍스트가 합리화한 오적용에 대해 서로 동의할 가능성이 높다. 상관관계가 있는 시도들 간의 일치는 독립적인 검증이 아니다.

**D.** Enable extended thinking during the generation turn so the agent deliberates more thoroughly before finalizing each draft.

**설명**

이것은 틀렸다. 더 깊은 숙고라 해도 여전히 오류를 만들어낸 것과 동일한 추론 경로 안에서 이루어지므로, 에이전트는 이미 기각했던 우려에 대해 동일한 결론에 계속 얽매이게 된다. 하나의 컨텍스트 안에서 더 많이 생각하는 것으로는 독립적인 시각을 얻을 수 없다.

### 전반적인 설명

여기서 나타나는 실패 양상은 자체 검토의 잘 알려진 약점이다. 답을 생성한 모델은 그 답을 만들어낸 추론 컨텍스트를 그대로 유지하고 있으며, 여기에는 우려를 고려했다가 스스로 그 우려를 떨쳐버린 순간들도 포함된다. 같은 세션에 그 결과를 검토하라고 요청하면, 진정으로 다시 검토하기보다는 동일한 정당화 논리를 다시 따라가는 경향을 보인다. 이는 사람의 코드 리뷰에서 나타나는 "저자 맹점"과 유사하며, 에이전트의 추론 과정에서 우려가 제기되었다가 기각되는 모습이 나타나면서도 자체 검토 단계는 여전히 초안을 승인하는 관찰된 동작과도 일치한다.

더 효과적인 아키텍처는 독립적인 검토 인스턴스다. 즉, 초안 해결 방안과 관련 사례 데이터는 전달받지만 생성자의 추론은 전혀 전달받지 않는 두 번째 Claude 호출이다. 이 컨텍스트에는 사전에 형성된 결론이 전혀 없으므로 처음부터 근거를 바탕으로 초안을 평가해야 하며, 이는 공유 컨텍스트로 인한 편향을 줄여 미묘한 정책 오적용을 잡아낼 가능성을 높인다. Claude 워크플로우에 대한 Anthropic의 가이드는 생성된 결과물을 검증할 때 별도의 인스턴스나 새로운 컨텍스트를 사용하는 것을 지지한다. 이때의 대가는 해결 방안마다 추가되는 추론 호출 한 번이며, 이는 잘못된 환불이나 잘못 적용된 정책의 비용에 비하면 보통 저렴하다.

오답들은 모두 동일한 근본적인 이유로 실패한다. 검증을 오염된 컨텍스트 안에 그대로 두기 때문이다. 확장 사고는 동일한 추론 경로를 따라 숙고를 심화시킬 뿐이고, 자체 비판 지시는 편향된 당사자에게 스스로를 단속하라고 요청하는 것이며, 한 세션에서 두 초안을 생성하는 방식은 정확성이 아니라 일관성만을 입증하는 상관관계 있는 출력을 만들어낸다. 확인 루프를 끊는 것은 노력의 강도가 아니라 컨텍스트의 독립성이다.

생성된 결과물을 별도의 인스턴스가 검토하도록 권장하는 Claude Code Best Practices와, 검증을 별개의 단계로 구성하는 방법을 다루는 Chain complex prompts를 참고하라.

## 질문 6

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : The agent extracts a structured dispute record before calling lookup_order. The purchase_date field always passes schema validation, yet values arrive as "yesterday", "early last week", or "03/04/2025", and order lookups fail or return the wrong orders. What is the most effective fix?

**A.** Tighten the schema by adding minLength and maxLength constraints so malformed date strings are rejected at validation.

**설명**

구조화된 출력은 JSON Schema의 일부만 지원하며, minLength와 maxLength 같은 문자열 제약은 지원되지 않으므로 이 스키마는 강제 효과 없이 요청 오류만 발생시킬 수 있다. 길이를 제약할 수 있다 해도 "yesterday" 같은 상대적 표현을 절대 날짜로 변환할 수는 없다.

**B.** Post-process the extracted dates with a natural-language date-parsing library that converts whatever text the model returned.

**설명**

파싱 라이브러리는 추출된 문자열만 독립적으로 처리하며 모델이 가진 대화 맥락이 없으므로, "early last week" 같은 모호한 표현이나 03/04/2025 같은 모호한 숫자 형식은 신뢰성 있게 파싱되지 않는다. 전체 대화를 볼 수 있는 추출 시점에 모델이 정규화하도록 하는 것이 결과물을 이후에 수정하는 것보다 더 정확하다.

**C(정답).** Add prompt normalization rules: resolve relative dates against the current date provided in context and output ISO 8601.

**설명**

이것이 정답이다. 스키마는 필드가 올바른 형태의 문자열인지만 강제할 수 있다. "yesterday"나 "early last week"를 절대 날짜로 변환하는 것은 모델만 수행할 수 있는 의미론적 변환이며, 이를 일관되게 수행하려면 명시적인 규칙과 기준 날짜가 모두 필요하다. 스키마와 함께 프롬프트에 명시된 정규화 규칙이 바로 이 공백을 메운다.

**D.** Set the sampling temperature to zero so the model formats the date field identically on every extraction.

**설명**

온도(temperature)는 토큰 선택의 무작위성을 제어할 뿐, 모델이 따라야 할 날짜 표기 규칙을 정의하지는 않는다. 명시된 정규화 규칙이 없으면 모델은 고객이 사용한 형식을 그대로 반복할 것이고, 단지 그 반복이 더 결정적일 뿐이다.

### 전반적인 설명

여기서 핵심 구분은 스키마가 보장하는 것과 표현할 수 없는 것 사이의 차이다. 구조화된 출력이나 도구 정의에 붙은 JSON 스키마는 형태를 제약한다. 필드가 존재할 것, 문자열일 것, JSON이 문법적으로 유효할 것 등이다. 의미에 대해서는 아무것도 말해주지 않는다. "yesterday"가 절대 날짜로 해석되었는지, 03/04/2025가 4월 3일인지 3월 4일인지, 값이 lookup_order가 필터링할 수 있는 형식인지 여부는 알 수 없다. 이 의미론적 계층은 프롬프트에 속한다. 목표 표기법(ISO 8601, YYYY-MM-DD)을 명시하고, 상대적 표현을 해석할 기준이 되는 현재 날짜를 모델에 제공하며, 모호한 숫자 형식에 대한 명확화 규칙을 지정해야 한다. 필드의 스키마 설명에 규칙을 반복해 적고 예시 매핑("yesterday"가 계산된 절대 날짜가 되는 예)을 보여주면 이를 강화할 수 있으며, 이는 도구 정의에서 형식에 민감한 파라미터를 자세히 설명하라는 Anthropic의 가이드와도 일치한다.

이 수정을 스키마 쪽으로 밀어넣으려는 시도는 두 가지 이유로 실패한다. 첫째, 구조화된 출력은 JSON Schema의 일부만 지원한다. minLength, maxLength 같은 문자열 제약은 지원되지 않으며 400 오류를 유발할 수 있다. 둘째, 검증이 작동하더라도 그것은 거부만 할 뿐, 상대적 표현을 날짜로 변환하는 방법을 모델에 가르쳐주지 않는다. 날짜 라이브러리로 후처리하는 방법은 문제를 대화를 전혀 보지 못한 구성 요소로 옮기는 것이므로, 모델이 직접 해석할 수 있었던 표현을 추측해야 하게 된다. 그리고 온도 조정은 표기 규칙이 아니라 샘플링 분산을 바꾸는 것이다. 명시된 규칙이 없는 모델은 온도가 0이어도 고객의 표현을 그대로, 단지 더 일관되게 반영할 뿐이다. 기억해야 할 핵심 개념은 스키마는 구조를 강제하고, 프롬프트는 정규화 의미론을 담당하며, 신뢰할 수 있는 파이프라인은 이 둘을 함께 사용한다는 것이다.

**C(정답).** Route questionable refund decisions to an independent review instance that starts without the generator's reasoning context.

**설명**

이것이 정답이다. 같은 세션에서의 검토는 원래 결정을 이끌어낸 모든 추론을 그대로 유지하므로, 모델은 그 결론을 다시 도출해야 할 판단이 아니라 이미 확정된 것으로 취급한다. 그런 생성 컨텍스트가 없는 독립적인 인스턴스는 사람의 동료 검토(peer review)와 마찬가지로 새로운 시각을 제공하며, 의심스러운 결정에 이의를 제기할 가능성이 훨씬 높다.

**D.** Trigger context compaction before the review step so the summarized history frees the agent to reconsider its earlier refund reasoning.

**설명**

압축(compaction)은 컨텍스트 예산을 관리하기 위해 이력을 요약하는 것이며, 결정의 근거를 확실하게 제거하는 방법이 아니다. 요약본은 보통 검토가 문제 삼아야 할 결론을 그대로 보존한다. 격리는 별도의 인스턴스에서 검토를 실행함으로써 달성되는 것이지, 같은 세션 내에서의 손실이 있는 요약으로 달성되지 않는다.

### 전반적인 설명

여기서 설명된 패턴은 문서화된 자체 검토의 한계다. 모델이 자신이 생성한 결과물을 같은 세션 내에서 검토할 때, 컨텍스트 윈도우에는 그 결정을 이끌어낸 추론의 전체 흐름이 여전히 담겨 있다. 모델의 관점에서 그 결론은 이미 정당화된 것이므로, 검토 단계는 결론을 다시 도출하기보다는 확인하는 쪽으로 기우는 경향이 있다. 이것이 같은 세션 내의 자체 비판이 기계적인 점검(누락된 필드, 형식, 체크리스트 대비 완전성)에는 잘 작동하지만, 경계선상의 환불 같은 판단 문제는 거의 뒤집지 못하는 이유다. 형식상의 공백을 잡아내는 데는 이전 추론과의 모순이 필요 없지만, 결정을 뒤집으려면 그런 모순이 필요하다.

유용한 개념적 비유는 하나의 세션 안에서의 자체 검토가 동료 검토보다는 저자가 자신의 초안을 직접 교정하는 것에 더 가깝다는 것이다. 저자의 가정을 그대로 공유하기 때문이다. 이것이 같은 세션 안에서 적용하는 해법들이 효과가 없는 이유이기도 하다. 온도를 낮추는 것은 샘플링 노이즈를 바꿀 뿐 기존 추론에 대한 고정 편향을 바꾸지 않으며, 압축은 근거를 확실히 제거하기보다 이력을 요약할 뿐이고, 추가적인 도구 접근은 검토가 이미 가지고 있는 사실을 다시 가져올 뿐이다. 문제는 생성 컨텍스트 자체의 존재이므로, 해법은 구조적이어야 한다. 그 컨텍스트를 전혀 본 적 없는 검토자에게 결정을 보내는 것이다.

아키텍처 측면에서, 이것이 검토 파이프라인이 생성자의 추론 없이 시작하는 독립적인 인스턴스로 초안을 라우팅하는 이유이며, 이는 사람의 동료 검토가 작동하는 방식과 닮아 있다. 에이전트 설계에 대한 Anthropic의 가이드는 Building Effective Agents에서 이 평가자(evaluator) 패턴을 다루며, Subagents는 별도의 컨텍스트가 정확히 이런 종류의 격리를 제공하는 방법을 설명한다.

## 질문 8

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : You define three triage tools, one per request category (returns, billing, account), and set tool_choice to "any" so intake always yields structured output. Billing disputes are occasionally triaged through the returns tool. What is the right fix?

**A.** Set tool_choice to "none" on the first turn so the model states the category in text before a structured tool call is compelled.

**설명**

"none" 모드는 어떤 도구 사용도 막아버리므로, 첫 턴이 구조화된 출력이 아니라 자유 텍스트를 생성하게 되어 인테이크(intake) 설계 자체가 무너진다. 프롬프트 형식의 사전 분류도 이후의 도구 선택을 고정시키지 않으므로, 다음 턴에서 잘못된 라우팅이 여전히 발생할 수 있다.

**B.** Force a single named triage tool with tool_choice type "tool" so misclassification between schemas can no longer occur on any request.

**설명**

단일한 이름 있는 도구를 강제하면 모든 요청을 하나의 스키마로 라우팅함으로써 선택 오류를 제거할 뿐이다. 요청이 실제로 세 가지 범주에 걸쳐 있으므로, 반품과 계정 문제는 강제된 스키마에 억지로 끼워 맞춰지게 되어, 간헐적인 오분류가 체계적인 오분류로 바뀌게 된다.

**C.** Change tool_choice to "auto" so the model deliberates over the request before committing itself to one of the triage tools.

**설명**

"auto" 모드는 숙고 과정을 추가하지 않는다. 단지 모델이 도구를 호출하는 대신 일반 텍스트로 응답하는 것을 허용할 뿐이다. 이는 인테이크가 항상 구조화된 출력을 생성한다는 보장을 희생시키면서도, 모델이 범주를 구분하는 능력은 전혀 개선하지 못한다.

**D(정답).** Sharpen the tool descriptions to separate the categories, since "any" compels a tool call but leaves the choice of tool to the model.

**설명**

이것이 정답이다. tool_choice "any"는 제공된 도구 중 하나가 호출된다는 것만 보장할 뿐, 어떤 도구가 호출될지에는 영향을 주지 않는다. 도구 선택은 도구 정의 자체에 의해 결정되므로, 범주 경계를 명확히 구분하는 설명이야말로 구조화된 출력 보장을 유지하면서 스키마 간 오분류를 고치는 메커니즘이다.

### 전반적인 설명

tool_choice 파라미터에는 문서화된 네 가지 모드가 있으며, 각각 서로 다른 질문에 답한다. auto(도구가 제공되었을 때의 기본값)는 모델이 도구를 호출할지 여부 자체를 결정하게 한다. any는 모델이 제공된 도구 중 하나를 반드시 호출하도록 요구하지만, 그중 무엇을 선택할지는 의도적으로 모델에 맡긴다. {"type": "tool", "name": ...}는 호출을 하나의 이름 있는 도구로 고정한다. none은 도구 사용을 완전히 막는다. 핵심 개념은 두 축으로 이루어진 결정이라는 것이다. 하나의 축은 도구 호출이 일어날지를 제어하고, 다른 축은 어떤 도구가 호출될지를 제어한다. any는 첫 번째 축만 고정하는데, 이것이 바로 여러 개의 추출 스키마가 존재하고 요청 유형을 사전에 알 수 없을 때 올바른 설정인 이유다.

any가 설정되면, "어떤 도구가 호출되는가"라는 두 번째 축은 도구 정의에 의해 결정된다. description 필드는 모델의 주된 선택 신호다. 트리아지 도구의 설명이 모호하거나 서로 겹치면, 모델은 billing dispute와 returns 같은 인접한 범주를 혼동한다. 이 문제의 해법은 각 도구가 무엇을 다루는지, 무엇을 다루지 않는지, 언제 인접 도구보다 우선되어야 하는지를 명시하는 도구 정의에 있는 것이지, 이미 제 역할을 다하고 있는 tool_choice 설정에 있는 것이 아니다.

오답들은 각각 한 축을 깨뜨려 다른 축을 억지로 메우려 한다. 단일한 이름 있는 도구를 강제하는 것은 간헐적인 오분류를 세 범주 중 두 범주에 대한 확실한 스키마 불일치로 바꾸는 것이다. auto나 none으로 전환하는 것은 이 설계의 목적이었던 구조화된 출력 보장을 포기하는 것이며, 어느 모드도 모델이 범주를 구분하는 능력을 향상시키지 못한다. 각 모드의 문서화된 동작과 도구 설명 작성 가이드에 대해서는 Implement tool use와 tool use overview를 참고하라.

## 질문 9

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : An engineer proposes routing the support agent's entire multi-turn, tool-driven resolution loop through the Message Batches API for a latency-tolerant email ticket queue, accepting slower replies in exchange for the 50% discount. What should you recommend?

**A.** Adopt batches but attach ticket sequence metadata to every request, since results returned out of order cannot otherwise be reassembled.

**설명**

순서 문제는 이미 해결된 상관관계 문제다. 각 배치 요청은 모든 결과를 원본 요청에 다시 매핑하는 custom_id를 가지고 있다. 순서 메타데이터를 추가해도 실제 장애물, 즉 도구 결과를 요청 중간에 다시 넣어 다음 턴을 이어갈 수 없다는 문제는 해결되지 않는다.

**B.** Adopt the proposal unchanged, since the email queue's tolerance for slow replies satisfies the only requirement batch processing imposes.

**설명**

지연 시간에 대한 관대함은 배치 채택을 위한 필요 조건이지 충분 조건이 아니다. 각 작업 단위는 단일 요청-응답 교환 안에 들어맞아야 하는데, 에이전트의 도구 기반 루프는 그렇지 않다. 이 제안을 그대로 채택하면 모든 대화가 첫 번째 tool_use 응답에서 멈춰버릴 것이다.

**C(정답).** Keep the resolution loop on synchronous calls, since each batch request yields one response and cannot return tool results for continued turns.

**설명**

이것이 정답이다. Message Batches API는 각 요청을 한 번 보내면 끝나는 단일 Messages 호출로 처리하며, tool_use 응답을 가로채 MCP 도구를 실행하고 그 결과를 모델에 돌려주어 계속 이어갈 수 있는 메커니즘이 없다. 에이전트의 해결 흐름은 여러 차례의 도구 요청-응답 라운드에 의존하므로, 큐가 얼마나 지연에 관대한지와 무관하게 동기 API를 유지해야 한다.

**D.** Strip the MCP tool definitions from each batch request, since the Message Batches API rejects any request that declares tools.

**설명**

배치 요청은 도구 정의를 포함한 핵심 Messages API 파라미터를 동일하게 받아들이므로, 제거할 것이 없다. 실제 공백은 요청된 도구가 처리 중에 실행되어 다음 턴을 위해 결과를 돌려받을 방법이 없다는 것이며, 도구를 제거하면 에이전트가 티켓을 해결하는 능력도 함께 마비될 것이다.

### 전반적인 설명

여기서 가져야 할 핵심 개념은 배치 요청이 비동기 처리를 위해 제출되는 단일하고 독립적인 Messages API 호출이라는 것이다. 요청이 들어가면 결국 결과 파일에 하나의 응답이 나온다. 중간에 개입하는 하네스는 없다. 일반적인 에이전틱 루프에서는 코드가 각 응답을 검사하고, tool_use 정지 신호를 보면 MCP 도구(lookup_order나 process_refund 같은)를 실행하고, 그 결과를 대화에 추가한 뒤 모델을 다시 호출한다. Message Batches API는 그런 가로채기를 위한 어떤 훅도 제공하지 않으므로, 멀티턴 도구 호출 워크플로우는 하나의 배치 요청 안에서 완료될 수 없다. 이 한계는 지연 시간과는 무관하다. 하루 종일 기꺼이 기다릴 수 있는 큐라 해도 그 루프를 실행할 수는 없으며, 이것이 바로 루프를 동기 방식으로 유지해야 한다는 타당한 권장 사항의 이유다.

이것이 배치와 동기 방식 사이의 결정에 두 가지 독립적인 관문이 있는 이유다. 첫째, 워크로드가 논블로킹이고 지연에 관대한가(배치는 보통 한 시간 이내에 끝나지만 SLA 없이 최대 24시간이 걸릴 수 있다)? 둘째, 각 작업 단위가 단일 요청-응답 교환 안에 들어맞는가? 야간 감사와 대량 추출은 두 관문을 모두 통과하지만, 고객이 얼마나 기다릴 의향이 있는지와 무관하게 상호작용적인 도구 기반 해결 흐름은 두 번째 관문에서 실패한다.

오답들은 흔한 반쪽짜리 지식을 반영한다. 도구 정의는 배치 요청 파라미터에서 완전히 유효하다. 문제가 되는 것은 요청 중간의 도구 실행이 들어갈 자리가 없다는 것이다. 그리고 결과가 입력 순서와 다르게 반환되기는 하지만, 필수인 custom_id 필드가 정확히 각 결과를 원본 요청으로 상관시키기 위해 존재하므로 순서는 배치 사용을 막는 요인이 결코 아니다. 비동기 처리 모델, 지연 시간 특성, 결과 상관 관계에 대해서는 Message Batches 문서를 참고하라.

**QUESTION** : Human support staff dismiss roughly a third of the agent's escalations as unnecessary, but case-by-case transcript review has not revealed why. What change makes the dismissal problem systematically analyzable?

**A.** Add a prompt instruction telling the agent to escalate only when genuinely necessary and to avoid borderline cases.

**설명**

이것은 틀렸다. "필요할 때만 에스컬레이션하라" 같은 모호한 지침은 주관적이며 일관되지 않은 동작을 낳는다. 팀이 어떤 에스컬레이션 트리거가 문제인지도 모르는 상태에서 수정을 시도하는 것이므로, 이는 기각 패턴을 분석 가능하게 만들 수 없다.

**설명**

이것이 정답이다. 각 에스컬레이션을 유발한 요청 특성을 구조화된 필드로 기록하면 각 기각이 그룹화하고 집계할 수 있는 데이터 포인트가 된다. 패턴별 기각률을 집계하면 정확히 어떤 트리거가 불필요한 에스컬레이션을 유발하는지 드러나므로, 추측이 아니라 가장 문제가 되는 요인을 표적으로 프롬프트를 수정할 수 있다.

**D.** Have the agent attach a self-rated confidence score to each escalation and suppress those below a fixed threshold.

**설명**

이것은 틀렸다. 자체 평가 신뢰도는 보정이 잘 되어 있지 않으며, 억제는 에스컬레이션을 설명하는 것이 아니라 걸러낼 뿐이다. 신뢰도가 낮은 에스컬레이션을 자동으로 버리는 것은 실제로 사람이 필요한 경우까지 숨길 위험이 있으며, 이는 에스컬레이션 경로가 존재하는 목적과 상충한다.

### 전반적인 설명

여기서의 근본적인 설계 원칙은 구조화된 발견 항목이 결정 자체뿐 아니라 그 결정이 발생한 이유도 함께 담아야 한다는 것이다. detected_pattern 필드는 에스컬레이션 스키마에 애플리케이션 차원에서 추가하는 것으로, 에이전트가 에스컬레이션할 때 어떤 요청 특성이 그 결정을 유발했는지(예: 정책 상한에 가까운 환불 금액, 모호한 주문 상태, 명백한 고객의 불만 표현 등) 기록한다. 이제 모든 에스컬레이션이 기계가 읽을 수 있는 트리거를 갖게 되므로, 기각은 더 이상 일화가 아니라 그룹화할 수 있는 행(row)이 된다. 한 패턴으로 유발된 에스컬레이션이 70%의 비율로 기각되는 반면 다른 패턴은 5%만 기각된다면, 프롬프트 기준을 어디에서 강화해야 하는지 정확히 알 수 있고, 정확한 트리거는 그대로 둘 수 있다.

이는 피드백 루프의 사고 방식이다. 먼저 출력을 계측하고, 측정된 증거를 바탕으로 동작을 바꾸는 것이다. 다른 대안들은 모두 이 계측 단계를 건너뛴다. "필요할 때만 에스컬레이션하라"는 모호한 지시는 전형적인 모호한 기준 안티패턴이며, 맹목적이고 일관성 없이 행동을 바꾼다. 검토자의 자유 텍스트 메모는 에이전트의 실제 트리거가 아니라 사람의 인상을 기록하며, 비정형 텍스트는 실질적인 규모에서 집계에 저항한다. 자체 평가 신뢰도 임계값은 에스컬레이션을 진단하기보다 걸러내며, 신뢰도가 낮은 에스컬레이션을 자동으로 억제하는 것은 에스컬레이션 경로가 제공해야 할 안전장치를 조용히 제거한다.

기술적으로는, 발견 항목이 이미 JSON 스키마(엄격한 도구 사용이든 API의 구조화된 출력 지원이든)를 통해 출력되고 있다면 이런 필드를 추가하는 것은 간단하다. 그 필드는 스키마에 하나의 필수 속성으로 더해지고 생성 시점에 채워진다. 이런 필드의 형태를 스키마가 어떻게 보장하는지는 Structured outputs를 참고하되, 스키마는 구조를 보장할 뿐이고 그 필드의 진단적 가치는 후속 집계에서 나온다는 점을 기억해야 한다.

## 질문 11

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : A nightly batch classifies 5,000 resolved support transcripts for quality auditing. When the batch ends, 120 entries in the results file carry a result type of errored. How should the pipeline recover the missing classifications?

**A.** Resubmit the entire 5,000-transcript batch as a new submission and deduplicate the classifications after both result files arrive.

**설명**

전체 배치를 재제출하면 이미 성공한 수천 건의 요청을 다시 처리하게 되어 그 비용을 두 번 지불하고, 이후 조정해야 하는 중복 출력까지 만들어낸다. 실패한 요청만 선별적으로 재제출하는 것이 문서화된 실패 처리 패턴이다.

**B.** Use the batch's request_counts metadata to determine which transcripts failed and queue those entries for resubmission.

**설명**

배치 객체의 request_counts 필드는 집계 메타데이터다. 몇 건이 성공, 오류, 만료되었는지는 알려주지만 어떤 건인지는 알려주지 않는다. 개별 실패를 식별하려면 결과 파일을 읽고 각 항목의 custom_id를 사용해야 한다.

**C(정답).** Filter the results file for errored entries, map each one's custom_id back to its transcript, and resubmit only those requests.

**설명**

이것이 정답이다. 오류가 발생한 항목을 포함한 모든 결과 행에는 개발자가 지정한 custom_id가 들어 있으므로, 파이프라인은 정확히 어떤 트랜스크립트가 실패했는지 식별하고 그 120건만 담은 새 배치를 구성할 수 있다. 이렇게 하면 성공한 4,880건의 분류에 대해 다시 비용을 지불하지 않는다.

**D.** Read the message id inside each errored result to identify the affected transcripts, then rerun those through the synchronous API.

**설명**

오류가 발생한 결과에는 error 객체만 있고 Message는 없으므로 읽을 message id가 존재하지 않는다. 성공한 결과에서도 모델이 생성한 message id는 원본 트랜스크립트와 아무런 관계가 없다. 상관 관계를 맺어주는 메커니즘은 개발자가 제공한 custom_id이다.

### 전반적인 설명

Message Batches API는 의도적으로 "보내고 잊어버리는" 방식으로 설계되어 있다. requests 배열을 제출하고, processing_status가 ended가 될 때까지 폴링한 뒤, .jsonl 결과 파일을 다운로드한다. API는 여러분의 도메인 객체에 대해 아무것도 알지 못하므로, 결과를 여러분의 데이터에 다시 연결하는 계약은 각 요청에 지정하는 custom_id이다. 결과 파일의 모든 행은 결과가 어떻든 그 custom_id를 succeeded, errored, canceled, expired 중 하나인 result 객체의 type과 함께 그대로 돌려준다.

이런 설계 덕분에 부분 실패를 저렴하게 처리할 수 있다. 복구 워크플로우는 결과 파일에서 성공하지 않은 항목을 필터링하고, 각 custom_id를 원본 트랜스크립트로 해석한 뒤, 그 요청들만 담은 새 배치를 제출하는 것이다. 이렇게 하면 50% 배치 할인을 그대로 유지하면서 120건의 재시도에만 비용을 지불하고, 성공한 결과는 전혀 건드리지 않는다.

다른 접근법들은 각 산출물이 실제로 제공하는 것을 잘못 이해하고 있다. 전체 배치를 재제출하면 모든 것을 다시 처리하게 되어 후속 단계에서 중복 제거가 강제된다. 모델이 생성한 message id는 성공한 succeeded 결과의 Message 안에만 존재하며 오류 항목에는 전혀 존재하지 않는다. 이는 응답을 식별할 뿐 여러분의 트랜스크립트를 식별하지 않는다. 그리고 request_counts는 배치 수준의 원격 측정 데이터로 진행 상황을 모니터링하는 데 유용하지만, 결과의 개수만 셀 뿐 어떤 개별 요청이 실패했는지는 알려줄 수 없다.

실패 처리 워크플로우와 결과 타입에 대해서는 Batch processing을, custom_id가 각 요청에 어떻게 정의되는지에 대해서는 Create a Message Batch 레퍼런스를 참고하라.

## 질문 12

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : The agent extracts order IDs reliably from plain requests but often selects the wrong one in forwarded threads and pasted receipts that quote IDs from earlier orders. Detailed instructions have not helped. What is the most effective change?

**A.** Lower the sampling temperature so the agent processes every message format in a deterministic, uniform way.

**설명**

온도는 토큰 선택의 다양성에 영향을 줄 뿐, 낯선 문서 구조 안에서 관련 식별자를 고르는 방법을 모델이 알고 있는지와는 무관하다. 온도를 낮추면 동일한 형식 의존적 오류가 더 반복적으로 나타날 뿐, 더 정확해지지는 않는다.

**B(정답).** Add a few targeted examples showing which order ID to extract from each message format, with brief rationale for each.

**설명**

퓨샷 예시는 상세한 지시로도 다양한 입력 구조에 대한 일관된 처리를 이끌어내지 못할 때 문서화된 해법이다. 포워딩된 스레드와 붙여넣은 영수증에서 인용된 여러 ID 중 올바른 ID를 선택한 예시를 근거와 함께 보여주면, 모델은 각 구조에 맞는 판단을 배우게 되고, 단순히 예시를 반복하는 것이 아니라 새로운 형식 변형에도 일반화한다.

**C.** Add a preprocessing step that uses regular expressions to pull order identifiers from messages before the agent reads them.

**설명**

정규 표현식은 주문 ID 형식과 일치하는 모든 문자열을 찾아낼 수 있지만, 포워딩된 스레드와 영수증은 이전 주문에서 인용된 여러 ID를 포함하고 있다. 고객이 실제로 묻고 있는 것이 어느 ID인지 판단하는 것은 메시지에 대한 의미론적 판단이며, 패턴 매칭으로는 할 수 없다.

**D.** Rewrite the instruction with stronger emphasis, telling the agent to scan the entire message for identifiers before acting.

**설명**

프롬프트 문구를 더 강조하는 것은 실질적인 내용을 추가하지 않고 강조만 더할 뿐이다. 문제 설명에서 이미 상세한 지시가 실패했다고 명시되어 있으며, 더 강한 문구도 고객의 현재 주문 ID를 이전 주문에서 인용된 ID와 구별하는 방법을 보여주지 못하므로 불일치는 계속된다.

### 전반적인 설명

이것은 퓨샷 프롬프팅이 추가적인 지시 개선보다 더 나은 성과를 내는 전형적인 사례다. 입력이 구조적으로 다른 형태(단순 문장, 인용된 헤더가 있는 포워딩된 이메일, 붙여넣은 영수증 표)로 도착할 때, 어려움의 본질은 모델에 규칙이 없다는 것이 아니라, 어떤 프롬프트 규칙으로도 각 구조에서 관련 값이 어디에 위치하는지, 또는 인용된 여러 후보 중 어느 것이 고객이 의미하는 것인지 나열할 수 없다는 것이다. 형식마다 하나씩, 입력과 올바른 추출 결과, 짧은 근거를 보여주는 2~4개의 소규모 예시 세트는 그 판단을 직접적으로 보여준다. 그러면 모델은 본 적 없는 형식에도 그 패턴을 일반화하는데, 이는 다양한 문서 구조에서의 추출에 대해 예시가 갖는 문서화된 강점 그대로다.

기억해야 할 핵심 개념은, 지시는 행동을 추상적으로 서술할 뿐이고 예시는 그것을 실제로 구현한다는 것이다. 이미 상세한 지시가 존재하는데도 입력 형태에 따라 출력이 여전히 일관되지 않다면, 더 많거나 더 강한 지시를 추가하는 것은 거의 효과가 없다. 강조는 올바른 처리가 어떤 모습인지에 대한 새로운 정보를 전달하지 않기 때문이다. 샘플링 온도도 마찬가지로 본질과 무관하다. 그것은 출력의 변동성을 제어할 뿐, 인용된 스레드 안에서 어떤 주문 ID가 관련 있는지에 대한 모델의 이해와는 무관하다. 그리고 정규 표현식 전처리는 이 문제의 절반만 해결한다. 패턴은 메시지 안의 모든 후보 ID를 찾아낼 수 있지만, 인용된 여러 ID 중 어느 것이 고객의 현재 요청과 일치하는지 판단할 수는 없다. 그 판별이 바로 예시가 가르치는 판단력이다.

효과적인 예시를 구성하는 방법에 대해서는 Use examples (multishot prompting) to guide Claude's behavior를 참고하라.
