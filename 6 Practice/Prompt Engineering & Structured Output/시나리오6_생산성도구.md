# 시나리오6_생산성도구

## 질문 1

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : A pipeline extracts metadata from legacy service manifests. The schema marks deprecation_date as required, but many older manifests never record one, and the model fills the field with plausible dates. Which change prevents the fabrication?

**A.** Add a system prompt rule stating that the model must never output a deprecation date that does not appear in the manifest text.

**설명**

프롬프트 지시는 값을 구조적으로 요구하는 스키마를 무력화할 수 없다. 매니페스트에 날짜가 없어도 모델은 여전히 스키마에 유효한 무언가를 내놓아야 한다. 지시는 잘해야 조작 가능성을 낮추는 정도이며, required 필드 제약은 계속해서 그것을 강제한다.

**B(정답).** Declare deprecation_date nullable with type ["string", "null"] and omit it from required so the model can return null for missing dates.

**설명**

이 답이 정답인 이유는, null 옵션이 없는 required 필드는 모델이 값의 부재를 정직하게 보고할 방법을 남기지 않아 스키마에 맞는 값을 만들어내게 만들기 때문이다. 필드를 nullable이면서 선택적으로 만들면 모델에게 날짜 누락을 정당하게 표현할 방법이 생기고, 조작을 유발하는 구조적 압박이 제거된다.

**C.** Add a pattern constraint restricting deprecation_date to the manifests' ISO date format so fabricated values fail schema validation.

**설명**

조작된 날짜는 보통 형식이 올바르기 때문에, 패턴 제약은 실제 날짜와 마찬가지로 조작된 날짜도 그대로 통과시킨다. 형식을 강화해도 값의 형태만 제한할 뿐, 날짜가 없다는 것을 표현할 정당한 방법은 여전히 없으므로 조작 압박은 그대로 남는다.

**D.** Re-run each affected extraction with the fabricated date and a correction instruction included in the retry prompt.

**설명**

오류 피드백을 활용한 재시도는 형식이나 구조적 실수에는 효과가 있지만, 소스에 아예 존재하지 않는 정보에는 효과가 없다. 매니페스트에는 근거로 삼을 폐기 예정일이 없고 스키마는 여전히 값을 요구하므로, 재시도는 또 다른 조작을 낳을 수밖에 없다.

### 전반적인 설명

스키마는 단순히 출력의 형태를 기술하는 것을 넘어, 모델이 낼 수 있는 답변의 전체 공간을 정의한다. Structured Outputs를 사용하면 required 필드는 선언된 타입으로 반드시 존재하도록 보장되는데, 이 보장은 양날의 검이다. 소스 문서에 실제로 필요한 값이 없을 때 모델은 그 필드를 비워둘 수 없으므로, 스키마상 유일하게 합법적인 방법은 그럴듯한 값을 지어내는 것뿐이다. 이 조작은 부주의한 생성 때문이 아니라 스키마 설계 자체에서 비롯된다. 여기서 가져가야 할 사고 모델은, "이 정보는 여기에 존재하지 않는다"를 포함한 소스의 모든 실제 상태가 스키마 안에서 합법적으로 표현될 수 있어야 한다는 것이다.

Anthropic이 지원하는 JSON Schema 하위 집합은 바로 그런 표현 방법을 제공한다. "type": ["string", "null"]과 같은 union 타입을 사용하면 필드에 명시적으로 null을 담을 수 있고, required 목록에서 필드를 제외하면 그 필드는 선택적이 된다. 이 둘은 서로 다른 설계 선택이다. required이면서 nullable인 필드는 키는 반드시 존재하게 하면서 진실한 null 값은 허용하는 반면, 선택적 필드는 완전히 생략될 수 있다. 어느 쪽이든 모델은 데이터가 없을 때 정직하게 답할 방법을 얻게 되며, 이는 이 실패 유형에 대해 문서화된 예방책이다.

다른 접근법들은 증상만 건드릴 뿐이다. 형식 패턴은 값의 형태만 조일 뿐이며, 지어낸 날짜는 구문상 실제 날짜와 구별되지 않는다. 오류 피드백을 통한 재시도는 수정 가능한 오류에는 강력하지만, 정보가 소스에 아예 없는 경우에는 효과가 없다고 문서에 명시되어 있다. 수정이 근거로 삼을 것이 매니페스트에 전혀 없기 때문이다. 추측을 금지하는 프롬프트 규칙은 값을 요구하는 확고한 구조적 제약과 확률적 지시를 맞세우는 셈인데, 결국 제약이 이겨서 조작된 날짜가 계속 흘러나가게 된다. 지원되는 nullable 및 선택적 필드 메커니즘은 Structured outputs 문서를, 프롬프트 전용 기법 대신 스키마 강제에 의존해야 하는 시점은 Increase output consistency 문서를 참고하라.


## 질문 2

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : Prose rules telling the agent whether a legacy code pattern is safe to auto-modernize keep failing on patterns the rules never anticipated. How should the team change the prompt so the judgment transfers to unanticipated patterns?

**A.** Add the examples once in a calibration session so the model's learned behavior persists and future sessions handle new patterns.

**설명**

이 답이 오답인 이유는 프롬프트 내용이 모델을 학습시키거나 세션 간에 유지되지 않기 때문이다. Few-shot 예시는 요청의 컨텍스트 안에 존재하는 동안에만 동작에 영향을 준다. 이는 프롬프팅 기법일 뿐, 가중치 업데이트가 아니다.

**B.** Add an example for every known legacy pattern so the model can match each incoming case to its nearest documented example.

**설명**

이 답이 오답인 이유는 예시를 조회 테이블처럼 취급하기 때문이다. Few-shot 프롬프팅은 다양하고 근거가 잘 갖춰진 소수의 예시로부터 일반화를 이끌어내는 방식으로 동작하며, 최근접 일치를 빠짐없이 다루는 방식으로 동작하지 않는다. 알려진 패턴마다 예시를 쌓아 올리는 것은 컨텍스트만 비대하게 만들 뿐, 예상하지 못한 사례를 다루는 데는 도움이 되지 않는다.

**C(정답).** Add contrasting safe and unsafe examples with reasoning shown, so the model generalizes the decision boundary to novel patterns.

**설명**

이 답이 정답이다. 안전한 경우와 안전하지 않은 경우를 대조하고 각 판단이 내려진 이유를 설명하는 few-shot 예시는 사례 목록이 아니라 판단 경계를 가르친다. 모델은 그렇게 시연된 판단을 새로운 패턴에도 적용하며, 이것이 바로 예시가 예상치 못한 입력에서 프롬프트 문구보다 더 나은 성능을 내는 이유다.

**D.** Remove the prose rules and rely on well-chosen examples alone, since demonstrations fully replace explicit decision criteria.

**설명**

이 답이 오답인 이유는 예시가 명시적 기준을 대체하는 것이 아니라 보완하는 역할을 하기 때문이다. 효과적인 프롬프트는 명확한 규칙과 시연을 결합한다. 기준을 제거하면 예시가 무엇을 보여주는지 뒷받침하는 운영상의 정의가 사라지게 된다.

### 전반적인 설명

Few-shot 프롬프팅에 대한 흔한 오해는, 예시가 모델이 정확히 또는 유사하게 일치하는 항목을 찾아보는 사례 테이블처럼 작동한다는 것이다. 실제로 이 기법은 그렇게 동작하지 않는다. 입력, 판단, 그리고 그 판단의 근거를 각각 보여주는 3~5개의 대조적인 예시 집합은 판단 경계를 시연한다. 모델은 그 경계를 추상화하여 예시가 전혀 보여주지 않은 입력에도 적용한다. Anthropic의 가이드는 예시를 관련성 있고 다양하게 구성하라고 강조하는데, 이는 모델이 부수적인 표면적 특징이 아니라 의도된 패턴을 포착하도록 하기 위함이다.

이것이 바로 상세한 프롬프트 문구 지시가 일관되지 않은 결과를 낼 때 few-shot 예시가 문서상 권장되는 해결책인 이유다. 프롬프트 문구는 목표를 명명할 뿐이지만, 실제로 작업된 예시는 판단력을 전달한다. Increase output consistency 문서에 따르면, 원하는 출력과 판단을 보여주는 것이 일관성 측면에서 추상적인 지시보다 더 효과적이다.

다른 접근법들은 각각 메커니즘상의 이유로 실패한다. 알려진 패턴을 모두 다루는 방식은 예시를 검색 키처럼 취급하는 것이라 여전히 새로운 패턴을 다루지 못하며, 오히려 정말 중요한 예시의 신호를 희석시킨다. 프롬프트 예시는 요청이 끝난 후에는 유지되지 않는다. 모델의 가중치나 이후 세션에 어떤 변화도 생기지 않는다. 그리고 예시는 명시적 기준을 대체하지 않는다. 가장 강력한 프롬프트는 구체적인 규칙(어떤 패턴이 자동 현대화 대상이고 어떤 것이 검토가 필요한지)과, 그 규칙이 모호한 영역에서 적용되는 모습을 보여주는 시연을 함께 사용한다. 예시가 프롬프트 내에서 지시와 어떻게 어우러지는지는 prompt engineering overview와 prompt templates and variables 문서를 참고하라.


## 질문 3

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : The team commits to delivering batch-generated codebase analysis reports within 30 hours of an engineer's request, using the Message Batches API. Which TWO statements about batch submission cadence are accurate? (Select TWO.)

**A(정답).** Requests must be submitted within 6 hours of arrival, since batch processing alone can consume 24 of the 30 hours.

**설명**

이 답이 정답이다. 최악의 경우 처리 시간이 24시간이고 지연에 대한 SLA가 없으므로, 통제 가능한 유일한 여유는 요청이 도착한 시점과 배치가 제출되는 시점 사이의 시간이며, 이는 30에서 24를 뺀 6시간이다.

**B(정답).** Submitting accumulated requests every 4 hours caps the worst case at 28 hours: 4 of accumulation plus 24 of processing.

**설명**

이 답이 정답이다. 제출 직후 도착한 요청은 다음 배치까지 최대 4시간을 기다리며, 여기에 최악의 경우 처리 시간 24시간을 더하면 28시간이 되어 30시간 약속 대비 2시간의 여유가 남는다.

**C.** Submitting batches overnight shortens processing time enough that a 12-hour accumulation window still meets the commitment.

**설명**

이 답이 오답이다. Anthropic은 지연에 대한 보장을 제공하지 않으며, 비혼잡 시간대에 처리가 더 빨라진다는 내용도 문서화하지 않았다. 따라서 12시간 누적에 최악의 경우 처리 시간 24시간을 더하면 36시간이 되어 약속을 위반하게 된다.

**D.** Accumulating requests into one daily batch is safe because most batches complete far sooner than the 24-hour maximum.

**설명**

이 답이 오답이다. SLA 계획은 일반적인 동작이 아니라 최악의 경우 한계치를 기준으로 세워야 한다. 요청은 하루 단위 제출까지 거의 24시간을 기다린 뒤 처리에 다시 최대 24시간이 걸릴 수 있어, 최악의 경우 거의 48시간에 이른다.

### 전반적인 설명

Message Batches API는 지연을 비용과 맞바꾼다. 50% 할인을 제공하지만 요청을 비동기적으로 처리하며 최대 24시간의 처리 시간이 걸리고 지연에 대한 SLA는 없다. 이 설계상의 선택은, 배치 위에 구축되는 전달 약속이라면 평균이 아니라 최악의 경우를 기준으로 계획되어야 함을 의미한다. 여기서 사고 모델은 단순한 산술이다: 제출 가능 시간 = 외부 SLA - 24시간. 30시간 약속의 경우, 요청 도착과 배치 제출 사이에 최대 6시간의 여유만 남는다.

고정된 제출 주기는 이 예산을 실제 운영 일정으로 바꾼다. 4시간마다 제출하면, 가장 운이 나쁜 요청(제출 직후 도착한 요청)은 4시간을 기다린 뒤 최대 24시간의 처리 시간을 거치므로 총 28시간이 되어 여유가 유지된다. 6시간 이하의 어떤 주기도 성립하며, 4시간 주기는 실패한 요청의 재시도나 재제출을 위한 여유를 추가로 확보해 두는 것일 뿐이다.

실패하는 접근법들은 한 가지 결함을 공유한다. 보장된 한계치 대신 낙관을 대입한다는 것이다. 비혼잡 시간대에 처리가 빨라진다는 내용은 문서화되어 있지 않으므로, 야간 제출도 여전히 최대 24시간의 처리 시간을 그대로 마주한다. 12시간 누적은 최악의 경우를 36시간으로 밀어올린다. 마찬가지로 "대부분의 배치는 일찍 끝난다"는 전제로 계획하는 것은, 하루 단위 주기가 일부 요청을 종단 간 거의 48시간에 노출시킨다는 사실을 무시하는 것이며, 약속은 바로 예측할 수 없는 그 요청들에서 깨진다. 문서화된 처리 시간과 비동기 모델에 대해서는 Batch processing 문서를 참고하라.


## 질문 4

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : The team adds a second Claude instance to review generated refactors, seeding it with the generator's full session transcript so it understands intent. The reviewer approves nearly everything, echoing the generator's justifications. What change restores effective review?

**A(정답).** Pass the reviewer only the code changes and the original task requirements, excluding the generation transcript.

**설명**

이 답이 정답인 이유는, 두 번째 인스턴스의 가치가 단순히 별도 프로세스라는 데서 오는 것이 아니라 컨텍스트 격리에서 온다는 점이다. 검토자가 생성자의 추론 과정을 보게 되면 결함을 낳은 것과 같은 합리화를 그대로 물려받게 된다. 이 전사 기록을 주지 않으면 코드와 요구사항만을 근거로 한 독립적인 판단을 하도록 강제할 수 있다.

**B.** Instruct the reviewer to identify at least three issues in every change it examines.

**설명**

발견 항목 수를 할당하는 방식은 진정한 검토가 아니라 잡음을 만들어낸다. 문제없는 변경에서는 억지로 문제를 만들어내게 하고, 결함이 있는 변경에서는 검토자가 생성자의 추론에 동조하는 상태를 깨는 데 아무런 역할도 하지 못한다.

**C.** Upgrade the reviewer to a more capable model while keeping the full transcript available for context.

**설명**

모델 성능은 여기서 실패의 원인이 아니다. 검토자가 생성자의 추론을 읽는 한, 더 강력한 모델이라 해도 그 정당화를 반박하기보다 받아들이는 경향을 보이므로 확증 편향은 그대로 남는다.

**D.** Enable extended thinking on the reviewer so it deliberates longer over the transcript before approving.

**설명**

동일하게 편향된 입력에 대해 더 오래 고민한다고 해서 독립성이 생기지는 않는다. Extended thinking은 더 깊은 추론을 제공하지만, 검토자는 여전히 생성자의 근거에 고정되어 있으며, 이것이 바로 변경 사항을 그대로 승인하게 만드는 원인이다.

### 전반적인 설명

두 번째 Claude 인스턴스가 생성자가 놓친 문제를 잡아내는 이유는 컨텍스트 격리에 있다. 검토자는 코드를 만들어낸 추론 과정 없이 도착하므로, 그 추론에 녹아든 합리화를 물려받을 수 없다. 이미 어떤 접근이 옳다고 결론 내린 모델은 그 결론을 방어하려 하지만, 결과물과 요구사항만을 평가하는 새로운 인스턴스에는 그런 애착이 없다. 이는 사람이 하는 피어 리뷰와도 닮아 있다. 저자가 코드가 괜찮은 이유를 설명하는 것 자체가, 좋은 리뷰어가 diff를 읽을 때 제쳐두어야 하는 것이다.

검토자에게 전체 생성 전사 기록을 제공하는 것은 이 속성을 조용히 무너뜨린다. 구성 자체는 여전히 두 인스턴스 아키텍처처럼 보이지만, 정보 측면에서는 사실상 자기 검토로 되돌아간 것이다. 검토자는 각 결정이 왜 내려졌는지를 읽고, 예상대로 그 정당화를 그대로 반복한다. 해결책은 검토자에게 주어지는 입력을 코드 변경 사항과 원래 작업 요구사항(그리고 관련 테스트나 명세)으로 제한하는 것이며, 이것이 바로 제2의 의견을 진정으로 독립적으로 만든다.

더 강력한 모델이나 extended thinking 모두 이 문제를 해결하지 못한다. 둘 다 동일하게 오염된 컨텍스트 위에서 작동하기 때문이다. 생성자의 근거에 대해 더 많은 성능이나 더 많은 숙고를 더해도 검토는 여전히 그 근거에 고정되어 있다. 리뷰마다 고정된 개수의 발견 항목을 요구하는 것은 그 자체로 안티패턴이다. 이는 정교한 판단을 할당량으로 대체하여, 실제 결함 탐지를 개선하지 못한 채 문제없는 코드에 억지로 지적사항을 만들어낸다. 멀티 Claude 워크플로에 대한 Anthropic의 가이드는 한 인스턴스가 코드를 작성하고 별도의 인스턴스가 이를 검증하도록 권장하는데, 이는 정확히 검증자의 컨텍스트를 깨끗하게 유지하기 위함이다. Claude Code: Best practices for agentic coding를 참고하라.


## 질문 5

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : Despite a system prompt that lists required sections and formatting rules in detail, the agent's legacy-module overviews vary: prose one run, bullets the next, sometimes with sections missing. Which change most reliably produces consistently structured overviews?

**A(정답).** Add three to four example overviews wrapped in XML tags that demonstrate the exact expected sections and structure.

**설명**

이 답이 정답이다. 상세한 지시만으로는 일관되지 않은 출력이 나올 때, 잘 구성된 예시는 문서상 권장되는 해결책이다. 목표 형식을 설명하는 대신 모델에게 정확히 보여주기 때문이며, Anthropic은 일관성 확보에 있어 예시로 제약을 두는 것이 추상적인 지시보다 더 효과적이라고 명시하고 있다. 예시를 XML 태그로 감싸면 지시와 명확히 구분된다.

**B.** Set the temperature to zero so the model formats every overview deterministically instead of sampling varied structures.

**설명**

temperature는 토큰 샘플링의 변동성에 영향을 줄 뿐, 모델이 요구되는 구조를 이해하는 방식에는 영향을 주지 않는다. 낮은 temperature는 개별 응답을 더 예측 가능하게 만들 수 있지만, 형식에 대한 모델의 해석이 충분히 구체화되지 않았다면 입력과 실행마다 여전히 흔들리게 된다.

**C.** Rewrite the formatting instructions with stronger emphasis, marking each required section as IMPORTANT and repeating the rules at the end of the prompt.

**설명**

시나리오는 이미 상세한 지시가 존재하는데도 출력이 여전히 일정하지 않다고 명시하고 있다. 강조와 반복을 추가하는 것은 이미 실패하고 있는 동일한 채널을 강화하는 것일 뿐이다. 지시는 형식을 문장으로 설명하지만 예시는 그것을 직접 보여주며, 이것이 바로 예시가 여기서 더 신뢰할 수 있는 해결책인 이유다.

**D.** Prefill the assistant turn with the first section heading so the response is forced to begin in the required layout.

**설명**

프리필은 시작 토큰만 고정할 뿐, 여러 섹션으로 구성된 문서를 중간과 끝까지 일관되게 유지하지는 못한다. 프리필된 제목을 지나면 모델은 다시 문장 지시를 해석하는 상태로 돌아가므로, 팀이 겪고 있는 섹션 간의 흔들림이 그대로 이어지게 된다.

### 전반적인 설명

여기서 실패 유형은 전형적이다. 문장 지시는 형식을 설명하지만, 매 실행마다 모델은 그 설명을 다시 해석해야 하고 그 해석은 매번 달라진다. Few-shot 예시는 목표를 직접 시연함으로써 이 간극을 메운다. Anthropic의 가이드는 예시를 출력 형식, 어조, 구조를 조정하는 가장 신뢰할 수 있는 방법 중 하나로 꼽으며, 일관성에 관한 가이드에서는 예시로 제약을 두는 것이 추상적인 지시보다 더 효과적이라고 명시적으로 밝히고 있다. 권장되는 방식은 실제 사용 사례를 반영하는 관련성 있고 다양한 소수(대략 3~5개)의 예시를 <example> 또는 <examples> 태그로 감싸, 모델이 시연과 지시를 구분할 수 있도록 하는 것이다.

여기서의 사고 모델은 다음과 같다. 지시는 모델이 적용해야 할 규칙을 정의하고, 예시는 모델이 매칭하고 일반화할 수 있는 패턴을 정의한다. 신뢰성 측면에서 둘이 충돌할 때는 구체적인 시연에 대한 패턴 매칭이 이긴다. 이것이 바로 상세한 지시가 이미 고치지 못한 형식 흔들림을, 강조를 더하거나 규칙을 반복하는 것으로는 거의 고칠 수 없는 이유다. temperature 같은 샘플링 조절 장치는 한 번의 실행 내에서 무작위성을 줄일 뿐, 충분히 구체화되지 않은 형식을 명확하게 만들지는 못한다. 어시스턴트 턴을 프리필하는 것도 시작 토큰만 고정할 뿐, 여러 섹션으로 구성된 문서의 나머지 부분은 여전히 동일하게 가변적인 해석에 맡겨진다. 요구사항이 사람이 읽는 일관된 구조의 문서가 아니라 기계가 엄격하게 파싱해야 하는 JSON이라면, 올바른 대응은 구조화된 출력(structured outputs)이나 JSON 스키마를 사용하는 tool use로 넘어가는 것이다. 필요한 형태를 갖춘 사람이 읽는 개요 문서라면, 목표를 겨냥한 예시가 문서상 권장되는, 가장 마찰이 적은 해결책이다.

See Increase output consistency and Prompt engineering best practices.


## 질문 6

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : An engineer measures that every batch the team has submitted so far finished in under an hour, and proposes routing the agent's interactive codebase-exploration requests through the Message Batches API to capture the 50% discount. How should you respond?

**A.** Approve the move but submit each interactive request as its own single-request batch so small batches complete quickly enough for live use.

**설명**

배치 크기가 지연 보장을 만들어주지는 않는다. 단일 요청 배치라 해도 동일하게 최대 24시간의 시간 범위 안에서 비동기로 처리된다. 이 설계는 배치 관리 오버헤드를 추가하면서도 블로킹 워크로드와의 근본적인 불일치는 해결하지 못한다.

**B(정답).** Keep interactive requests on the synchronous API, since batches carry no latency guarantee and can take up to 24 hours to complete.

**설명**

이 답이 정답이다. 인터랙티브 요청은 블로킹 방식이다. 엔지니어가 결과를 기다리고 있는데, 대부분의 배치가 한 시간 안에 끝난다 해도 문서상 보장되는 것은 지연 SLA 없는 최대 24시간의 처리 시간뿐이다. 테스트에서 관찰된 빠른 완료는 사람이 기다리고 있는 워크로드에서 믿고 의지할 수 있는 근거가 되지 못한다.

**C.** Approve the move and add a polling loop that surfaces results to the engineer as soon as the batch's processing status becomes ended.

**설명**

폴링은 결과가 준비되었을 때를 정확히 감지하지만, 준비되는 데 걸리는 시간을 제한하는 데는 아무런 역할을 하지 못한다. 엔지니어는 여전히 보장 없는 최대 24시간의 처리 시간에 노출되며, 이는 인터랙티브 세션에서는 받아들일 수 없다.

**D.** Route requests to batch first with an automatic synchronous retry whenever a batch has not completed within a fixed timeout window.

**설명**

이 하이브리드 방식은 두 경로의 최악의 상황을 동시에 보장한다. 느린 요청은 모두 타임아웃을 다 채운 뒤 결국 동기식의 전체 비용까지 지불하게 되므로, 할인은 지연이 우연히 낮았을 때만 실현된다. 블로킹 워크로드는 배치 처리 시간에 운을 걸기보다 그냥 동기식 API에 머무는 것이 낫다.

### 전반적인 설명

Message Batches API에 대한 판단 기준은 일반적인 성능이 아니라 보장에 있다. Anthropic은 대부분의 배치가 한 시간 이내에 끝난다고 문서화하고 있지만, 계약상 보장되는 유일한 한계는 처리에 최대 24시간이 걸릴 수 있으며 그 이후에는 완료되지 않은 배치가 만료된다는 것뿐이다. 배치 크기나 시간대에 관계없이 지연 SLA는 존재하지 않는다. 이 비대칭성이 설계상 트레이드오프의 전부다. 응답성 보장을 50% 비용 절감과 맞바꾸는 것이며, 이것이 바로 이 API가 지연에 민감하지 않은 작업(야간 감사, 대량 분석, 대규모 평가)에는 맞지만 사람이 직접 기다리는 어떤 작업에도 맞지 않는 이유다.

이 상황에서의 제안은 전형적인 신뢰성 오류를 범한다. 관찰된 동작으로부터 보장을 추정하는 것이다. 한 달 동안 배치가 한 시간 이내에 끝났다는 사실은, 고부하 시기에 도착해 20시간이 걸리는 배치에 대해서는 아무것도 알려주지 않는다. 탐색 중인 엔지니어는 그런 지연을 감당할 수 없다. 폴링은 완료 여부만 감지할 뿐 완료를 앞당기지 못한다. 단일 요청 배치도 여전히 동일한 최대 24시간의 큐에 들어간다. 동기식 폴백을 갖춘 배치 우선 설계는 실패한 배치 시도에 대한 비용을 지불하고, 모든 느린 요청의 지연에 타임아웃을 추가하며, 배치가 우연히 빨랐을 때만 절감 효과를 실현하므로 할인 효과를 예측할 수 없게 만들면서 동시에 인터랙티브 경험을 저해한다.

건전한 아키텍처는 지연 요구사항에 따라 명확히 나누는 것이다. 블로킹되는 인터랙티브 트래픽은 동기식 Messages API 호출에 그대로 두고, 하루 전체의 처리 시간을 감당할 수 있는 워크로드만 배치로 옮긴다. 문서화된 완료 시간과 적절한 사용 사례는 Batch processing 문서를 참고하라.


## 질문 7

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : The agent scans legacy modules and flags "risky code" for engineers to review. Despite the prompt instruction "only flag genuinely risky code," flags are noisy and vary between runs on identical modules. What prompt change most improves accuracy?

**A.** Limit each run to fewer legacy modules so the agent can examine the remaining ones more thoroughly.

**설명**

문제는 모듈당 주의력 부족이 아니라 정의되지 않은 판단 경계에 있다. 동일하게 모호한 기준으로 더 적은 코드를 스캔해도 똑같이 일관되지 않은 판단이 나올 뿐이며, 그저 더 작은 범위에서 벌어지는 것뿐이다.

**B.** Have the agent attach a self-rated confidence score to each flag so engineers can filter out the weak ones.

**설명**

모델이 스스로 보고하는 확신도는 정확도가 떨어지므로, 이를 기준으로 걸러내는 것은 잡음을 제거하는 것이 아니라 순서만 재배열하는 것이다. 엔지니어는 여전히 일관되지 않은 발견 항목들을 걸러내야 하며, 근본적인 판단은 여전히 근거 없는 상태로 남는다.

**C(정답).** Define explicit criteria naming the specific code conditions to flag and the patterns to leave unreported.

**설명**

"진정으로 위험한"과 같은 모호한 표현은 실행마다 다르게 해석된다. 플래그를 달아야 할 구체적인 조건과 그렇지 않은 패턴을 명확히 명명하면 모델이 실제로 적용할 수 있는 판단 규칙이 생기며, 이것이 잡음과 실행 간 편차를 실제로 줄이는 방법이다.

**D.** Strengthen the instruction to say the agent must be absolutely certain before it ever reports a finding.

**설명**

주관적인 지시를 강화하는 것은 운영상의 내용을 더하지 않고 강조만 더할 뿐이다. "절대적으로 확실한"이라는 표현도 "진정으로 위험한"만큼이나 해석의 여지가 열려 있으므로 불일치는 그대로 남는다.

### 전반적인 설명

"진정으로 위험한 코드만 플래그하라"와 같은 지시는 운영상의 내용을 담고 있지 않기 때문에 실패한다. 모델은 후보 발견 항목을 무엇에 대조해 검증해야 할지 알 수 없으므로, 실행마다 그 문구를 다시 해석하게 된다. 신뢰할 수 있는 해결책은 모호한 목표를 명시적이고 검증 가능한 기준으로 바꾸는 것이다. 예를 들어 "도달 가능한 경로에서 null이 될 수 있는 값을 역참조하는 함수에만 플래그를 단다"와 같은 조건과, "스타일상의 중복이나 주석 처리된 코드는 플래그하지 않는다"와 같은 제외 목록을 함께 두는 것이다. 이렇게 하면 막연한 느낌이 모델이 매번 동일하게 적용할 수 있는 루브릭으로 바뀌며, 이것이 바로 명시적 기준이 더 강한 형용사보다 일관되게 더 나은 성능을 내는 이유다.

Anthropic의 가이드도 이를 반영한다. Claude는 모델이 스스로 추론해야 하는 의도보다는, 정확한 출력 제약이 있는 명확하고 명시적인 지시에 가장 잘 반응하며, 효과적인 프롬프트 작업은 주관적인 표현이 아니라 구체적이고 측정 가능한 성공 기준에서 시작한다. Claude prompting best practices와 Define success criteria 문서를 참고하라.

다른 대안들은 각각 근본 원인을 놓친다. "절대적으로 확실한"으로 강화하는 것은 하나의 주관적 기준을 다른 주관적 기준으로 바꾸는 것일 뿐, 모델에게는 여전히 적용할 규칙이 없다. 모델이 스스로 매긴 확신도 점수는 정확도가 떨어지므로, 이를 기준으로 정렬하거나 걸러내는 것은 잡음이 있는 발견 항목의 순서를 뒤섞을 뿐 제거하지는 못한다. 그리고 스캔 범위를 줄이는 것은 오류가 주의력의 한계에서 온다고 가정하는 것인데, 실제로는 정의되지 않은 판단 경계에서 오는 것이므로, 더 적은 모듈에 동일하게 결함 있는 판단을 적용해도 똑같이 불일치한 결과가 나온다.


## 질문 8

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : This team's agent runs a validation-retry loop: when a structured extraction fails schema or business-rule validation, the failure is fed back for self-correction. Retry budgets are being exhausted on failures that never resolve. Which retry-policy change should the team make?

**A(정답).** Bypass retries when the required information is simply not present in the source file being analyzed.

**설명**

이 답이 정답인 이유는 자기 수정이 모델이 자신의 출력을 소스에 다시 근거하여 검토하는 데 의존하기 때문이다. 소스 파일에 원래부터 그 정보가 없었다면 아무리 재시도해도 그 정보를 만들어낼 수 없으므로, 이 루프는 수렴하지 못한 채 예산만 소모한다. 이런 경우는 null 처리나 에스컬레이션 경로로 보내야 한다.

**B.** Bypass retries when per-item counts fail to sum to the stated total reported elsewhere in the file.

**설명**

산술적 불일치는 재시도로 해결 가능한 유형이다. 오류 피드백에 불일치 내용이 명확히 적혀 있으면 모델이 소스와 개별 값을 다시 대조 검토할 수 있기 때문이다. 이런 경우는 보정된 첫 시도에서 해결되는 경우가 많으므로, 재시도를 건너뛰는 것은 이 패턴의 강점을 낭비하는 것이다.

**C.** Bypass retries when a date field arrives in a format the schema's pattern constraint rejects.

**설명**

형식 오류는 재시도로 해결 가능한 전형적인 실패 유형이므로, 여기서 재시도를 건너뛰는 것은 쉽게 얻을 수 있는 성과를 버리는 것이다. 재시도 프롬프트에 구체적인 검증 오류가 포함되어 있으면 모델은 소스에서 이미 찾아낸 값을 다시 형식화할 수 있으며, 이런 문제는 대개 한두 번의 시도 안에 해결된다.

**D.** Bypass retries when a value was placed under the wrong field name in an otherwise valid structure.

**설명**

값이 잘못된 위치에 놓이는 것과 같은 구조적 오류는 재시도로 해결 가능하므로 루프 안에 그대로 두어야 한다. 재시도 요청에 소스, 실패한 추출 결과, 그리고 구체적인 오류가 포함되어 있으면 모델은 다음 시도에서 값을 올바른 필드로 재배치할 수 있다.

### 전반적인 설명

검증-재시도 패턴이 효과적인 이유는 검증 실패를 목표가 명확한 수정 작업으로 바꾸어주기 때문이다. 모델은 추출 대상이었던 소스, 자신이 만들어낸 출력, 그리고 거부된 패턴이나 맞지 않는 합계와 같은 구체적인 오류를 받는다. 이 세 가지가 모두 주어지면 모델은 문제가 된 값을 소스에 다시 근거하여 수정할 수 있으며, 이것이 바로 형식 오류, 구조적 오류(값이 잘못된 필드에 들어간 경우), 산술적 불일치가 대개 한두 번의 재시도로 해결되는 이유다.

이 패턴의 한계는 정보의 가용성에 있다. 재시도는 모델이 볼 수 있는 자료 안에 정답이 존재할 때만 도움이 된다. 필요한 정보가 소스 파일에 없거나, 제공되지 않은 외부 문서에만 존재한다면, 재시도할 때마다 동일하게 불가능한 작업이 반복된다. 모델은 다시 실패하거나, 더 나쁘게는 스키마를 만족시키기 위해 그럴듯한 값을 조작해낸다. 설계자는 재시도에 앞서 검증 실패를 분류해야 한다. 재시도로 해결 가능한 실패는 시도 횟수에 제한을 둔 오류 피드백 루프로 보내고, 정보 부재로 인한 실패는 null 결과, 선택적/nullable 필드, 또는 사람이 검토하는 대기열로 즉시 보내야 한다. 이러한 분류는 또한 진정으로 선택적인 데이터를 스키마에서 nullable로 만들어야 하는 이유이기도 하다. 그렇게 해야 모델이 조작을 강요받는 대신 부재를 정직하게 보고할 방법을 갖게 된다.

JSON Schema 검증이 에이전트 출력과 어떻게 통합되는지는 Agent SDK structured outputs 문서를 참고하라.


## 질문 9

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : The agent's structured code findings are supposed to carry a detected_pattern annotation, requested through prompt instructions, but many findings omit it and false-positive aggregation keeps breaking. What change guarantees the annotation appears in every finding?

**A.** Lower the sampling temperature to zero so the model emits the annotation deterministically each run.

**설명**

temperature는 토큰 샘플링의 변동성을 조절할 뿐, 스키마 준수를 보장하지 않는다. temperature를 0으로 설정하면 출력이 더 반복 가능해지지만, 스키마가 요구하지 않는 필드를 포함해야 한다는 구조적 의무를 만들어내지는 못한다.

**B.** Set additionalProperties to true on the finding object so the annotation field is always permitted.

**설명**

추가 속성을 허용하는 것은 어떤 필드가 반드시 나타나야 한다는 것을 요구하지 않으므로, 누락은 계속될 것이다. 게다가 Anthropic이 지원하는 JSON Schema 하위 집합에서는 스키마로 제약되는 객체에 대해 additionalProperties가 false여야 하므로, 이 설정 자체가 지원되지 않는다.

**C.** Restate the annotation instruction in the system prompt and again at the start of every user turn.

**설명**

프롬프트 지시는 모델이 그 필드를 포함할 가능성을 높여주지만 여전히 확률적일 뿐, 모든 발견 항목에 필드가 존재함을 보장하지 못한다. 시나리오에서 나타난 간헐적인 누락은, 이 경우 지시를 강조하는 것만으로는 충분하지 않다는 직접적인 증거다.

**D(정답).** Define detected_pattern in each finding's JSON schema and include it in the required list.

**설명**

Structured output는 스키마 자체에 표현된 필드에 대해서만 보장을 제공한다. detected_pattern을 스키마 필드로 만들고 required로 지정하면 스키마를 따르는 모든 발견 항목이 그 값을 반드시 가지게 되며, 이는 프롬프트 지시만으로는 제공할 수 없는 정확한 보장이다.

### 전반적인 설명

여기서 가져가야 할 사고 모델은, structured output이 Claude가 만들어내는 결과물의 형태를 강제하지만, 그 강제는 스키마가 실제로 선언한 필드에 대해서만 적용된다는 것이다. 발견 항목 스키마가 detected_pattern을 정의하고 이를 required 목록에 넣으면, 스키마를 따르는 모든 추출 결과는 그 값을 반드시 가져야 한다. 모델이 단순히 그것을 빠뜨릴 수 있는 실행은 없다. 문장으로만 요청된 것은 이 보장 밖에 있다. 모델은 보통 이를 따르지만 그 준수는 확률적이며, 이것이 바로 이 어노테이션이 간헐적으로 나타났던 정확한 이유다.

이 구분은 이 필드가 지원하려는 오탐(false-positive) 워크플로에서 중요하다. detected_pattern별로 기각된 발견 항목을 집계하는 작업은 모든 레코드에 그 필드가 존재해야만 제대로 동작한다. 데이터에 공백이 있으면 분석이 우연히 어노테이션된 탐지 행동 쪽으로 조용히 편향된다. 이 필드를 지시에서 스키마로 옮기면, 최선을 다하는 수준의 어노테이션이 신뢰할 수 있는 분석 차원으로 바뀐다.

오답들은 각각 특징적인 이유로 실패한다. 지시를 더 강조해서 반복하는 것은 구조적인 문제를 프롬프트의 압박으로 풀려는 전형적인 패턴이며, 실패율을 줄일 뿐 없애지는 못한다. additionalProperties를 true로 설정하는 것은 필드를 허용하는 것과 요구하는 것을 혼동한 것이며, 문서화된 스키마 하위 집합은 어떤 경우든 제약된 객체에 대해 additionalProperties가 false여야 한다고 요구한다. temperature 조정은 샘플링의 무작위성을 다스릴 뿐 구조적 의무를 다스리지 않으므로, 결정론적 디코더라 해도 선택적 필드를 결정론적으로 빠뜨릴 수 있다. 스키마로 선언된 필드, required, additionalProperties가 어떻게 상호작용하는지는 Structured outputs 문서를 참고하라.
