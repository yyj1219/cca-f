# 2. 예시로 가르치기: Zero-shot / One-shot / Few-shot

이 장에서 다루는 것:

- Zero-shot / One-shot / Few-shot의 정의와 언제 무엇을 쓸지
- 왜 예시가 지시문보다 잘 먹히는가 (In-Context Learning)
- 좋은 예시를 고르는 법: 다양성, 대표성, 경계 조건, 적정 개수
- 예시로 출력 형식을 고정하기 (Worked Example)
- 퓨샷이 듣지 않는 경우: 편향, 위치 편향, 과적합/암기
- Extended Thinking(확장 추론)과 예시의 관계

---

## 2.1 세 가지 방식

| 방식 | 예시 개수 | 설명 |
|---|---|---|
| Zero-shot (제로샷) | 0개 | 지시문만 주고 시킨다. "다음 티켓의 우선순위를 정하라." |
| One-shot (원샷) | 1개 | 입력-출력 예시를 하나만 보여준다. |
| Few-shot (퓨샷) | 보통 3~5개 | 여러 개의 입력-출력 쌍을 보여준다. |

**Few-shot prompting(퓨샷 프롬프팅)** 은 모델을 재학습(fine-tuning)시키지 않고, 프롬프트 안에 "이런 입력이면 이런 출력"이라는 견본(shot)을 몇 개 넣어 원하는 동작을 유도하는 기법입니다. 모델의 가중치를 바꾸는 것이 아니라 단지 입력 안에 예시를 두는 것이므로 **In-Context Learning(문맥 내 학습)** 이라고도 부릅니다.

여기에 한 가지 개념을 더 구분해 둡니다.

- **Worked example (모범 예시)**: 입력-출력 쌍이 아니라, **완성된 형태의 출력 예시**를 그대로 보여주는 것. 형식 고정에 특히 유효합니다.

```
분류 규칙: 서비스 중단 여부와 영향 범위로 우선순위를 정한다.

입력: "결제 서버 전체 다운, 전 고객 결제 불가"
출력: P1

입력: "로그인 화면 오타 발견"
출력: P4

입력: "특정 브라우저에서만 장바구니 버튼 미작동"
출력: P3

입력: "{여기에 실제 티켓}"
출력:
```

퓨샷이 특히 강한 영역은 세 가지입니다.

- **출력 형식 고정**
- **레이블 일관성 확보**
- **말로 설명하기 어려운 애매한 판정 기준 전달**

## 2.2 왜 예시가 효과가 있는가

모델은 프롬프트 안의 패턴을 인식해 그 패턴을 이어갑니다. "입력이 이렇게 생기면 출력은 이렇게 생긴다"는 규칙성을 예시에서 읽어내 새 입력에도 적용합니다.

핵심은 이것입니다. **모델은 설명보다 패턴을 훨씬 잘 따릅니다.**

- 지시문(instruction)만으로는 "우선순위가 높다"의 기준이 사람마다, 상황마다 다릅니다. 예시는 **경계선이 어디에 그어져 있는지**를 구체적으로 보여줍니다.
- "필드 4개를 넣어라"라고 글로 쓰면 가끔 하나를 빼먹지만, 필드 4개가 항상 같은 순서로 등장하는 예시를 2~3개 보여주면 그 형태를 그대로 재현합니다.

특히 분류(classification) 작업에서 응답의 **일관성(consistency)** 을 크게 높여줍니다. 말로 설명하기 힘든 기준도 예시 세 개면 전달되는 경우가 많습니다.

---

## 2.3 예시는 몇 개가 적절한가 — 3~5개

실무 경험칙은 **3~5개**입니다. 이유는 양쪽 극단이 모두 실패하기 때문입니다.

**너무 적을 때 (0~1개)**

- 모델이 일반적 패턴을 추출할 근거가 부족합니다.
- 특히 예시 하나가 "가장 어려운 예외 케이스"이면 최악입니다. 모델은 그 극단적 사례를 기준선으로 착각해서, 평범한 입력마저 그 사례처럼 취급하는 편향이 생깁니다.

**너무 많을 때 (수십 개)**

- 토큰 비용과 지연 시간이 늘어납니다.
- Lost in the Middle로 중간 예시가 무시됩니다.
- 그리고 2.6의 **과적합/암기** 문제가 발생합니다.

## 2.4 예시를 어떻게 고르는가 — 다양성(Diversity)

개수보다 중요한 것이 **선택 기준**입니다.

- **다양성(diverse)**: 서로 다른 클래스, 서로 다른 유형을 고르게 덮어야 합니다. 5개가 전부 P1 사례라면 모델은 "전부 P1"이라고 답하게 됩니다. 길이(짧은 것/긴 것), 언어, 문서 형태, 도메인, 그리고 **정보가 놓인 위치**까지 폭넓게 섞습니다.
- **대표성(representative)**: 실제 들어올 입력 분포를 반영해야 합니다.
- **경계 조건(edge case)을 의도적으로 포함**: 애매해서 사람도 헷갈렸던 경계 사례를 넣으면, 모델이 그 경계선을 어디에 그어야 하는지 배웁니다.

> **Edge case(예외/경계 케이스)** 란: 정상 범위의 가장자리에 있어 판단이 갈리는 입력. 예) "장애는 아니지만 성능이 심하게 느림" 같은 티켓.

**무작위 선택(random sampling)은 왜 나쁜가?** 언뜻 "선택 편향(selection bias)을 피한다"고 들리지만, 예시 5개짜리 표본에서는 무작위가 오히려 위험합니다.

- 희귀 클래스나 중요한 경계 케이스가 통째로 빠질 수 있습니다.
- 품질이 낮거나 그 자체로 애매한 과거 데이터가 뽑혀 들어와 잘못된 패턴을 가르칠 수 있습니다.
- 클래스 분포가 우연히 심하게 치우칠 수 있습니다.

즉 few-shot 예시 선택은 **의도적인 큐레이션(curation)** 작업이지, 통계 표본 추출이 아닙니다.

## 2.5 예시로 출력 형식을 고정하기 (Worked Example)

형식을 고정하고 싶을 때는 **실제 출력과 완전히 동일한 모양**의 예시를 보여줍니다.

```
<example>
location: src/auth/session.py:42
issue: 세션 토큰이 만료 검사 없이 사용됨
severity: high
suggested_fix: 사용 전 expires_at을 현재 시각과 비교하는 가드를 추가
</example>

<example>
location: src/utils/log.py:17
issue: 디버그 로그에 사용자 이메일이 남음
severity: low
suggested_fix: 이메일을 마스킹하거나 로그 레벨을 낮춘다
</example>
```

지켜야 할 규칙:

- **모든 필드를 항상 같은 순서로** 배치합니다. 순서 자체가 학습되는 패턴입니다.
- **엣지 케이스를 예시에 포함**시킵니다. 예를 들어 `severity`가 누락되는 문제가 있다면, 빠뜨리기 쉬운 **low severity 사례**를 예시에 반드시 넣습니다. 그래야 모델이 "심각도가 낮아도 필드는 쓴다"는 것을 배웁니다.
- 예시는 실제 출력과 형식이 완전히 동일해야 합니다.

### 효과가 약한 대안들 (형식 붕괴를 못 막는 것들)

| 대안 | 왜 부족한가 |
|---|---|
| "출력을 스스로 다시 확인하라"고 지시 | 추상적인 자기 점검 요구는 형식 일관성을 근본적으로 보장하지 못합니다. |
| 끝에 "심각도 필드를 잊지 마세요" 덧붙이기 | 한 필드의 누락만 조금 줄일 뿐, "issue와 fix가 한 문장으로 뭉쳐지는" 구조 붕괴는 못 막습니다. |
| `max_tokens` 늘리기 | 잘림 때문이 아니라 형식 미준수 때문에 생긴 문제이므로 무관합니다. |

## 2.6 퓨샷이 듣지 않는 경우

예시를 넣었는데 오히려 나빠지는 상황들입니다. 원인은 대부분 **모델이 우리가 의도하지 않은 것까지 배웠기 때문**입니다.

### (1) 의도치 않은 상관 패턴 (spurious pattern / few-shot example bias)

모델은 우리가 **의도한 패턴만** 배우지 않습니다. 예시 집합에 우연히 공통된 다른 특징이 있으면, **그것까지 규칙으로 착각해서 배웁니다.**

> 문서 분류 프롬프트에 예시 5개를 넣었는데, 5개가 전부 우연히 "100단어 미만의 영어 이메일"이었다. 배포 후 짧은 영어 이메일은 잘 분류되지만, **예시 없던 이전 프롬프트에서는 잘 되던** 긴 문서와 다른 언어 문서가 오분류되기 시작했다.

모델이 배운 것은 "이렇게 분류해라"만이 아니라 "이 작업은 짧은 영어 텍스트에 대한 것이다"였습니다. **해결책은 예시의 다양화(diversify)입니다** (2.4 참고).

주의할 오해들:

- 편향된 예시를 **복제해서 개수만 늘리는 것**은 편향을 강화할 뿐입니다. 토큰만 낭비합니다.
- 예시 추가 직후에 발생한 성능 저하를 "모델 드리프트(model drift, 모델 자체가 시간에 따라 변하는 현상)" 탓으로 돌리는 것은 인과 오판입니다. 변경 시점과 저하 시점이 일치하면 원인은 그 변경입니다.
- "퓨샷은 분류 작업에 안 맞는다"는 것도 사실이 아닙니다. 오히려 분류 일관성을 높이는 대표적 기법입니다.

### (2) 위치 편향 (position bias)

> 논문에서 '표본 크기'와 '통계적 방법'을 추출하는 도구가, `Methodology`라는 제목이 붙은 섹션에서는 잘 뽑아내지만 같은 정보가 `Results`나 `Discussion` 문장 속에 제목 없이 묻혀 있으면 `null`을 반환한다.

원인은 컨텍스트 부족도, 검색 순서 문제도 아닙니다. 모델이 **"헤딩(제목) 아래에 있어야 그 정보다"** 라는 편향을 학습한 것입니다.

올바른 해결책: **레이블된 섹션에서 뽑는 예시와, 문장 속에 묻혀 있는 정보를 뽑는 예시를 둘 다** 프롬프트에 제공합니다.

비교를 위한 오답 유형과 이유:

- **컨텍스트 창(context window) 늘리기**: 컨텍스트 창은 모델이 한 번에 볼 수 있는 토큰의 최대 길이입니다. 텍스트가 잘려서 못 읽는 게 원인이라면 유효하지만, 여기서는 읽었는데 **못 알아본** 것이므로 무관합니다.
- **해당 섹션 없는 문서를 파이프라인에서 제외**: 문제를 푸는 게 아니라 시스템의 적용 범위를 임의로 줄이는 회피입니다.
- **Methodology 먼저 검색하고 없으면 다른 섹션으로 폴백(fall back)**: 폴백은 "어디를 볼지"의 순서 문제를 다룰 뿐입니다. 다른 섹션을 보게 해도 그 안의 비구조적 문장에서 여전히 추출하지 못합니다.

### (3) 과적합(Overfitting)과 암기(Memorization)

**과적합**은 원래 머신러닝 용어로, 모델이 학습 데이터의 일반적 규칙 대신 개별 사례 자체를 외워버려 새로운 데이터에서 성능이 떨어지는 현상입니다. 프롬프트에서도 같은 일이 일어납니다.

전형적인 증상:

- 프롬프트에 넣어둔 20개 입력에 대해서는 완벽하게 맞춘다.
- 그런데 그 20개와 **비슷하지만 똑같지는 않은** 새 입력이 오면 성능이 뚝 떨어진다.

이것은 모델이 **판단 규칙(decision rule)을 배운 것이 아니라 입력-출력 문자열 쌍을 매칭하는 법을 배웠다**는 신호입니다. 예시가 너무 많고 서로 겹치면, 모델 입장에서는 "규칙을 추론"하는 것보다 "가장 비슷한 예시를 찾아 그대로 흉내내는" 편이 더 쉬운 전략이 되어버립니다.

### (4) 일반화(Generalization)를 회복하는 법

해법은 예시를 더 넣는 것이 **아니라 줄이는 것**입니다.

- 예시 개수를 소수(3~5개)로 줄인다.
- 남길 예시는 **밑에 깔린 결정 규칙이 눈에 보이도록** 고른다. 즉 "이 세 개를 보면 규칙이 무엇인지 자연스럽게 유추된다"는 조합을 만든다.
- 필요하다면 예시와 함께 **규칙을 명시적 문장으로도 적는다.**

나쁜 방향의 예:

- 새 실패 사례가 나올 때마다 그 입력-출력 쌍을 계속 프롬프트에 덧붙이기 → 프롬프트가 무한히 커지고, 암기가 심해지고, Lost in the Middle까지 겹칩니다. 이것은 근본 원인(규칙이 드러나지 않음)을 고치지 않고 증상만 덮는 방식입니다.
- 예시를 전부 빼고 지시문 한 줄만 남기기(zero-shot) → 규칙이 복잡하거나 경계 케이스가 있는 분류에서는 정확도와 일관성이 떨어집니다.

> **요약: 예시의 목적은 "사례를 다 덮는 것"이 아니라 "규칙을 드러내는 것"입니다.**

## 2.7 Extended Thinking (확장 추론)과 예시의 관계

### 무엇인가

**Extended Thinking**은 모델이 최종 답변을 내놓기 전에 내부적으로 추론 과정을 길게 전개하도록 하는 기능입니다. 이 추론에 쓰이는 토큰을 **thinking token(추론 토큰)** 이라 하고, 얼마나 쓸지를 **thinking budget(추론 예산)** 또는 **effort 수준**으로 설정합니다.

수학, 복잡한 코드 작성, 다단계 판단처럼 한 번에 답하기 어려운 작업에서 정확도를 올려줍니다.

### tool_choice와의 호환 제약

중요한 API 제약이 있습니다.

> **Extended Thinking은 `tool_choice`가 `auto` 또는 `none`일 때만 사용할 수 있습니다. 강제 도구 선택(`any`, 또는 특정 도구 이름 지정)과는 함께 쓸 수 없으며, 함께 요청하면 API 에러가 발생합니다.**

즉 `any`도 강제 선택의 일종이므로 호환되지 않습니다. `any`가 예외적으로 허용된다는 식의 이해는 틀립니다.

**충돌이 났을 때 무엇을 포기할 것인가?** 두 기능을 동시에 쓸 수 없으므로 하나를 버려야 하는데, **시스템의 핵심 요구사항이 무엇인지**를 기준으로 판단합니다.

- 요구사항이 "모든 문서가 예외 없이 태깅되어야 한다"라면, 도구 강제는 그 요구사항을 보장하는 유일한 수단이므로 **강제를 유지하고 Extended Thinking을 끕니다.**
- `auto`로 바꾸면 에러는 사라지지만 모델이 도구를 건너뛸 수 있으므로 요구사항이 깨집니다. 에러를 없애려다 기능을 잃는 셈입니다.

또한 `input_schema` 안에 `thinking_mode` 같은 필드를 넣어 제약을 우회한다는 발상은 성립하지 않습니다. `input_schema`는 **도구가 받을 인자의 모양**을 기술하는 곳이지 API 동작을 바꾸는 곳이 아니며, 그런 필드는 존재하지도 않습니다. 스키마 내용은 API 파라미터 검증에 아무 영향을 주지 않습니다.

### Extended Thinking이 해결하지 못하는 것

Extended Thinking은 **더 오래, 더 깊이 생각하게** 해줍니다. 하지만 **누구의 관점에서 생각하는지는 바꾸지 못합니다.**

예시와의 관계도 같은 맥락입니다. 추론 예산을 늘려도 모델이 **모르는 판정 기준**이나 **원하는 출력 형식**은 알아낼 수 없습니다. 그런 것은 예시가 가르치는 영역입니다.

- 기준·형식이 불명확해서 틀린다 → **퓨샷 예시**로 해결
- 기준은 알지만 계산·다단계 추론이 어려워 틀린다 → **Extended Thinking**으로 해결
