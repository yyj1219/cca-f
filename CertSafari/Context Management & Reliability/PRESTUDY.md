# 1부. 공통 기초

## 0. 큰 그림: 왜 "컨텍스트 관리"와 "신뢰성"이 한 묶음인가

LLM은 두 가지 구조적 한계를 가집니다.

1. **컨텍스트 윈도우가 유한하다.** 모델이 한 번에 볼 수 있는 텍스트 양에는 상한이 있습니다.
   대화가 길어지거나 도구 호출 결과가 쌓이면 반드시 무언가를 버려야 합니다. → **컨텍스트 관리**
2. **모델의 출력은 확률적이고, 스스로의 정확도를 모른다.** 그럴듯하지만 틀린 답(환각,
   Hallucination)을 자신 있게 내놓습니다. → **신뢰성(Reliability)**

여기서 두 가지 문제가 동시에 생깁니다.

1. **공간 문제** — 넣을 수 있는 양이 유한하다. 넘치면 뭔가를 버려야 한다.
2. **주의(attention) 문제** — 공간에 들어가 있어도 모델이 그 정보를 실제로 활용한다는 보장이 없다.

이 두 문제 때문에 정보가 조용히 사라지고, 그 결과 시스템이 **틀린 답을 자신 있게** 내놓습니다.
즉 컨텍스트 관리는 곧 신뢰성 문제입니다.

여기에 하나 더, 에이전트가 사람 대신 판단을 내리는 순간 **"언제 스스로 하고, 언제 사람에게
넘길 것인가"** 라는 운영 원칙(에스컬레이션)이 필요해집니다. 이것도 신뢰성의 일부입니다.

이 두 축에서 파생되는 실무 주제가 이 노트의 나머지 부분입니다.

- 컨텍스트 윈도우 절약 기법과 그 부작용
- 멀티 에이전트에서의 정보 합성(Synthesis)과 출처 추적성
- 에러 처리와 복구를 위한 구조화된 페이로드 설계
- 정확도 평가: 집계 지표의 함정과 세분화 평가
- 신뢰도 점수(Confidence Score)의 교정 문제
- 이관(Escalation) 판단 기준의 설계

## 1. LLM, 토큰, 컨텍스트 윈도우

### 1.1 LLM이란

LLM(Large Language Model, 대규모 언어 모델)은 텍스트를 입력받아 다음에 올 텍스트를
예측·생성하는 모델입니다. Claude, GPT 같은 모델이 여기에 해당합니다.
우리가 "AI가 대화한다"고 느끼는 것은, 실제로는 **매번 대화 전체를 다시 입력해서 다음 문장을
생성**하는 과정의 반복입니다. LLM은 기억 장치가 따로 없고, "지금 눈앞에 보이는 글자들"만 봅니다.

### 1.2 토큰(Token)

**토큰**은 모델이 텍스트를 처리하는 최소 단위이자 과금 단위입니다. 대략 단어 조각 하나 정도의
크기입니다.

- 영어 기준 1토큰 ≈ 4글자, 1토큰 ≈ 0.75단어
- 한국어는 글자당 1~2토큰 정도로 더 많이 소비됩니다

비용과 속도가 모두 토큰 수에 비례하므로, "토큰을 아낀다"는 말은 곧 **"돈과 시간과 정확도를
아낀다"** 는 뜻입니다.

### 1.3 컨텍스트 윈도우(Context Window)

**컨텍스트 윈도우**는 한 번의 모델 호출에 넣을 수 있는 토큰의 최대치입니다.
시스템 프롬프트 + 대화 기록 + 도구 출력 + 첨부 문서 + 모델이 생성할 답변이 **모두 이 안에**
들어가야 합니다.

예: 컨텍스트 윈도우가 20만 토큰인 모델은, 시스템 프롬프트 + 대화 기록 + 파일 내용 + 도구 출력
전부 합쳐서 20만 토큰을 넘을 수 없습니다.

컨텍스트 윈도우는 **고정된 크기**입니다. 대화 도중에 저절로 줄어들거나 늘어나지 않습니다.

**핵심 성질:**

1. **컨텍스트 안에 없는 것은 모델에게 존재하지 않는다.** 모델은 "기억"하지 않습니다.
   매 요청마다 전달된 텍스트만 봅니다.
2. **유한하다.** 20만 토큰이든 100만 토큰이든 끝이 있습니다. 넘어가면 잘리거나(truncation)
   요청 자체가 실패합니다(Context Window Exceeded).
3. **비용이 든다.** API 요금은 대개 입력 토큰 수 × 단가입니다. 쓸데없는 내용을 넣으면 그대로 돈입니다.
4. **지연 시간(Latency)이 늘어난다.** 입력이 길수록 응답이 느려집니다.
5. **주의력(attention)이 희석된다.** 컨텍스트에 넣은 내용이 많을수록, 그중 특정 한 줄에 모델이
   집중할 확률은 떨어집니다. 관련 없는 정보가 많을수록 모델이 핵심을 놓칩니다.

대화가 길어지면 오래된 내용이 창 밖으로 밀려나거나 잘려나갑니다(**truncation, 절단**).
그러면 모델은 그 내용을 "잊어버립니다". **잊었다는 사실조차 인지하지 못하고, 그럴듯한 답을
지어내기도 합니다.**

그래서 "컨텍스트에 무엇을 넣고 무엇을 뺄 것인가"를 설계하는 일이 하나의 공학 분야가 되었고,
이를 **컨텍스트 엔지니어링(Context Engineering)** 이라 부릅니다.

### 1.4 컨텍스트 윈도우를 키우면 다 해결되나?

**아닙니다.** 더 큰 컨텍스트 윈도우는 도움이 되지만 근본 해결책이 아닙니다.

- **비용**: 입력 토큰만큼 요금이 붙습니다. 매 턴 20만 토큰을 보내면 비용이 선형으로 증가합니다.
- **지연 시간**: 입력이 길수록 응답이 느려집니다.
- **Needle-in-a-Haystack 문제 (건초더미 속 바늘)**: 컨텍스트가 매우 길면 모델이 그 안의 특정
  사실을 정확히 찾아내는 능력이 떨어집니다. 창 안에 있어도 "못 보는" 일이 생깁니다.
- **모델 파라미터 수가 늘어난다고 입력에 없는 정보를 알 수는 없습니다.** 컨텍스트에서 이미
  잘려 나간 사실은 어떤 모델로도 복원되지 않습니다.

따라서 큰 창에 다 넣는 것보다, **넣을 것을 고르는 설계**가 중요합니다.

> **큰 컨텍스트 윈도우는 컨텍스트 설계를 대체하지 못합니다.**

### 1.5 최대 출력 토큰(Max Output Tokens)과의 혼동 주의

`max_tokens`(최대 출력 토큰)은 **모델이 한 번에 생성할 답변의 길이 상한**입니다. 이것을 늘려도:

- 입력으로 들어갈 수 있는 과거 대화의 양은 늘어나지 않습니다.
- 이미 컨텍스트에서 밀려난 정보를 되살려 주지도 않습니다.

## 2. 무상태성(Stateless)과 messages 배열

### 2.1 무상태란

**무상태(Stateless)** 란 서버가 이전 요청에 대한 정보를 전혀 기억하지 않는다는 뜻입니다.
Claude API를 포함한 표준 LLM API 서버는 무상태입니다. 즉:

- 모델은 **서버 쪽에 대화 내역을 저장하지 않습니다.**
- 매 API 호출마다 클라이언트(개발자의 애플리케이션)가 **필요한 모든 맥락을 직접 다시 보내야** 합니다.
- 요청에 포함되지 않은 정보는 모델 입장에서 **존재하지 않는 정보**입니다.

```python
# 잘못된 이해: "모델이 알아서 기억하겠지"
client.messages.create(model="...", messages=[{"role": "user", "content": "아까 말한 그 좌석으로 예약해줘"}])
# → 모델은 "아까"가 무엇인지 전혀 모름. 그 대화가 요청에 없기 때문.

# 올바른 방식: 대화 전체를 매번 다시 보냄
messages = [
    {"role": "user", "content": "비즈니스석으로 알아봐줘"},
    {"role": "assistant", "content": "비즈니스석 조회 결과입니다..."},
    # ... 중간 대화들 ...
    {"role": "user", "content": "아까 말한 그 좌석으로 예약해줘"},
]
client.messages.create(model="...", messages=messages)
```

### 2.2 messages 배열

API 요청의 `messages` 파라미터는 대화 기록을 담는 배열입니다. 각 원소는 `role`(`user` 또는
`assistant`)과 `content`를 가집니다. **이 배열이 곧 모델이 볼 수 있는 세계의 전부입니다.**

### 2.3 흔한 오해: 세션 ID

개발자가 자기 앱에서 만든 `session_id`를 요청에 함께 보내면서
"API가 알아서 이전 대화를 찾아 붙여주겠지"라고 가정하는 실수가 흔합니다.

그 결과: 사용자가 세션을 재개하면 어시스턴트가 이전에 논의한 위험 감수 성향,
투자 목표 같은 것을 "잊어버린" 것처럼 보입니다.
실제로는 잊은 게 아니라 **애초에 전달받은 적이 없습니다.**

세션 ID는 **당신의 애플리케이션이 만든 값**입니다. API는 그 값의 의미를 모릅니다.

### 2.4 올바른 구현

대화 이력은 **애플리케이션이 저장하고, 매 요청마다 `messages` 배열에 실어 보냅니다.**

```python
# 1) 앱의 DB에서 이 세션의 이전 대화를 불러온다 (resolve)
history = db.load_messages(session_id)
# history = [
#   {"role": "user",      "content": "은퇴 자금을 모으고 싶어요"},
#   {"role": "assistant", "content": "위험 감수 성향은 어떠신가요?"},
#   {"role": "user",      "content": "보수적인 편입니다"},
# ]

# 2) 이전 이력 + 새 메시지를 함께 보낸다
response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    messages=history + [{"role": "user", "content": new_user_message}],
)

# 3) 이번 턴도 DB에 저장해서 다음 재개에 대비한다
db.append_messages(session_id, new_user_message, response.content)
```

**왜 다른 방법들은 해결책이 아닌가:**

- **컨텍스트 윈도우가 더 큰 모델로 교체** → 창 크기 문제가 아닙니다. 데이터가 애초에 요청에
  담기지 않았습니다. 창을 아무리 키워도 없는 것은 보이지 않습니다.
- **새 메시지를 짧게 쓰기** → 보내지도 않은 과거를 모델이 "회상"할 방법은 없습니다.
- **사용자에게 매번 다시 말해달라고 요청** → 앱이 저장하고 다시 보내면 완전히 해결되는 문제를
  사용자에게 떠넘기는 것입니다. 시스템의 책임을 사용자에게 전가하는 잘못된 설계입니다.

**핵심 결론:** "모델에 내장된 대화 메모리"라는 것은 존재하지 않습니다. 대화의 연속성은
**애플리케이션(개발자)이 책임지고 관리**하는 것입니다.

### 2.5 부수적 함의

무상태이기 때문에 대화가 길어질수록 매 요청의 토큰 수가 계속 증가합니다.
이것이 압축과 스크래치패드가 필요한 근본 이유이기도 합니다.
(반복되는 앞부분을 캐싱하는 프롬프트 캐싱 같은 기법도 이 성질에서 나옵니다.)

## 3. 에이전트, 도구, 멀티 에이전트 아키텍처

### 3.1 에이전트와 도구

**에이전트(agent)** 는 LLM에게 "도구(tool)"를 쥐여 주고, 목표를 준 뒤, 스스로 판단해서 도구를
호출하고 결과를 보고 다음 행동을 결정하게 만든 시스템입니다. 즉 LLM + 도구 + 목표로 구성된
실행 단위입니다.

- **도구(Tool / Function Calling):** 모델이 호출할 수 있는 외부 함수. 예: `web_fetch(url)`,
  `crm_lookup(contact_id)`, `get_logs(service, minutes)`. 모델은 함수를 직접 실행하지 않고
  "이 함수를 이 인자로 불러 줘"라는 JSON을 출력하며, 실제 실행은 여러분의 코드가 합니다.
  실행 결과(도구 출력)는 다시 컨텍스트에 넣어 모델에게 돌려줍니다.
- **루프(Agent Loop):** 모델 출력 → 도구 실행 → 결과를 컨텍스트에 추가 → 다시 모델 호출.
  이 반복이 에이전트의 심장입니다. **반복할수록 컨텍스트가 계속 불어난다는 점이 중요합니다.**

### 3.2 역할 구분

한 에이전트가 모든 일을 하면 컨텍스트가 금방 터지고 역할도 뒤섞입니다. 그래서 흔히 이렇게 나눕니다.

| 역할 | 설명 |
|---|---|
| **메인 에이전트(main agent)** | 사용자와 직접 대화하고, 전체 목표를 유지하며, 최종 판단을 내리는 주체 |
| **오케스트레이터(orchestrator)** | 여러 서브에이전트를 실행하고 그 결과를 모아 다음 단계로 넘기는 조율자 |
| **코디네이터(coordinator)** | 오케스트레이터와 거의 같은 뜻. 서브에이전트 결과를 받아 조정·결정하는 상위 주체 |
| **서브에이전트(subagent)** | 좁고 구체적인 하위 작업을 자기 자신의 별도 컨텍스트에서 수행하는 하위 실행 단위 |
| **합성/종합 에이전트(synthesis agent)** | 여러 서브에이전트 결과를 하나의 최종 산출물(보고서 등)로 합치는 역할 |
| **스폰(spawn)** | 코디네이터가 서브에이전트를 새로 생성/실행하는 행위 |

### 3.3 서브에이전트가 존재하는 진짜 이유: 컨텍스트 격리

서브에이전트의 가장 큰 가치는 "병렬 처리"가 아니라 **컨텍스트 격리(context isolation)** 입니다.

서브에이전트는 자기만의 컨텍스트 윈도우를 가집니다. 그 안에서 파일 500개를 열고 grep 결과
3만 줄을 봐도, **메인 에이전트의 컨텍스트는 전혀 오염되지 않습니다.**
메인 에이전트는 서브에이전트가 최종적으로 반환한 **요약본만** 받습니다.

```
[메인 에이전트]  ← 요약 300토큰 ←  [서브에이전트 A]  ← 원시 출력 40,000토큰
                 ← 요약 300토큰 ←  [서브에이전트 B]  ← 원시 출력 35,000토큰
                 ← 요약 300토큰 ←  [서브에이전트 C]  ← 원시 출력 50,000토큰
```

구체적 예시:

```
[메인 에이전트 컨텍스트]           [서브에이전트 컨텍스트]
 - 사용자 요청                       - grep 원시 출력 4,000줄
 - 계획                       →      - 필터링 과정
 - "테스트 파일 1,203개, 주로  ←      - 정리
    tests/ 와 src/**/__tests__/"
```

원시 출력은 서브에이전트가 끝나면 함께 사라집니다. 메인 컨텍스트는 깨끗하게 유지됩니다.

**언제 쓰는가**: 출력이 크고, 그 출력의 원시 형태를 나중에 다시 볼 일이 없으며, 결론만 필요할 때.
(대량 검색, 저장소 전수 탐색, 여러 문서 스캔 등)

**하지 말아야 할 대안들**:
- 메인에서 파일 5만 개를 하나씩 읽어보기 → 비용·시간 폭발, 컨텍스트 초과.
- 사용자에게 목록을 직접 붙여넣어 달라고 요청 → 자동화의 목적 자체를 훼손.
- 원시 출력을 "혹시 나중에 필요할까 봐" 대화에 그냥 남기기 → 오염 문제를 그대로 방치.

### 3.4 다운스트림(downstream) 에이전트와 병렬 실행

여러 에이전트를 파이프라인으로 연결하면, 앞 단계 출력이 뒤 단계 입력이 됩니다.
앞 단계 5개가 각각 "약간 장황"하면, 뒤 단계에서는 그것이 5배로 곱해져 폭발합니다.

> **핵심 규칙: 컨텍스트 예산은 생산자(producer) 쪽에서 지켜야 한다.**
> 소비자(consumer) 쪽에서 "알아서 잘 읽어라"라고 요구하는 것으로는 해결되지 않습니다.

코디네이터가 서브에이전트 여러 개를 **병렬(parallel)** 로 돌리는 경우가 많습니다.
예: 경쟁사 3곳의 가격 페이지를 각각 다른 서브에이전트가 수집.
이때 **일부만 실패하는 상황(partial failure, 부분 실패)** 이 반드시 생깁니다. 2개는 성공, 1개는 실패.
이에 대한 처리는 [17장](#17-구조화된-실패-보고와-부분-결과), [18장](#18-부분-실패의-투명한-전달-커버리지-주석)에서 다룹니다.

각 서브에이전트는 자체 컨텍스트 윈도우를 가지므로, 작업을 나누면 전체가 다룰 수 있는 정보량이
늘어납니다. 대신 서로의 컨텍스트를 볼 수 없으므로 **주고받는 데이터의 형식이 매우 중요**해지고,
**정보가 단계를 건널 때마다 손실될 위험**이 생깁니다.
