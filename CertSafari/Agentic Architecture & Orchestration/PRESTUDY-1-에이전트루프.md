# 1. 에이전트 루프와 Messages API

## 이 장에서 다루는 것

- Messages API의 기본 구조 — `messages` 배열, `role`, 콘텐츠 블록
- API가 무상태(stateless)라는 사실과 그로부터 나오는 모든 규칙
- `tool_use` / `tool_result` 왕복의 정확한 절차와 `tool_use_id` 짝맞춤
- 병렬 도구 호출(한 턴에 여러 도구)
- `stop_reason` — 루프의 신호등, 그리고 `max_tokens` 누락 버그
- 에이전틱 루프 직접 구현하기 (파이썬 골격)
- 도구 실행 실패 처리 — `is_error`
- 정지 메커니즘: `stop_reason` vs 고정 반복 상한(서킷 브레이커)
- 모델 중심 제어 흐름 vs 애플리케이션 하드코딩
- 책임 분담, 그리고 Client SDK vs Agent SDK
- 흔한 함정과 오해 총정리

## 1. Messages API의 기본 구조

### 1.1 messages 배열과 role

API 요청 본문의 핵심은 `messages` 배열입니다. 각 원소는 `role`과 `content`를 가집니다.

- `role: "user"` — 사람(또는 외부 환경)이 모델에게 주는 입력
- `role: "assistant"` — 모델이 낸 출력
- `system` — 별도 최상위 필드로 주는 전역 지시문. 대화 맨 앞에서 모델의 성격/규칙을 정합니다.

대화는 반드시 user → assistant → user → assistant … 로 **역할이 교대**되어야 합니다.

요청 전체의 모양은 이렇습니다.

```json
{
  "model": "claude-...",
  "system": "너는 인시던트 대응 도우미다.",
  "tools": [ ],
  "max_tokens": 4096,
  "messages": [
    { "role": "user",      "content": "결제 서비스가 느려요." },
    { "role": "assistant", "content": [ ] },
    { "role": "user",      "content": [ ] }
  ]
}
```

### 1.2 Messages API는 무상태(Stateless)다

**API는 상태를 기억하지 않습니다.** 서버는 이전 대화를 저장하지 않으며, 매 요청마다 클라이언트가 **지금까지의 전체 `messages` 배열**을 다시 보내야 합니다. 보내지 않은 것은 모델이 알 수 없습니다. "대화 맥락"이란 곧 이 배열입니다.

이 한 문장이 뒤에 나오는 거의 모든 규칙의 뿌리입니다. 히스토리를 덮어쓰면 안 되는 이유도, `tool_result`를 배열에 append 해야 하는 이유도, 컨텍스트 관리가 전적으로 개발자 책임인 이유도 전부 여기서 나옵니다.

### 1.3 content는 "블록의 배열"이다

`content`는 그냥 문자열일 수도 있지만, 도구를 쓰는 순간부터는 **콘텐츠 블록(content block)의 배열**이 됩니다.

| 블록 타입 | 누가 만드나 | 의미 |
|---|---|---|
| `text` | 모델 / 사용자 | 평범한 텍스트 |
| `tool_use` | 모델(assistant) | "이 도구를 이 인자로 실행해 달라"는 요청 |
| `tool_result` | 애플리케이션(우리 코드, user 역할로) | 도구를 실제로 실행한 결과를 모델에게 되돌려 주는 것 |

**중요:** 한 assistant 응답 안에 `text` 블록과 `tool_use` 블록이 **동시에** 들어올 수 있습니다. 모델이 "먼저 고객 정보를 조회하겠습니다"라는 설명 텍스트를 쓰면서 동시에 도구 호출을 요청하는 것이 정상입니다. 이 사실이 뒤에 나오는 종료 조건 이야기의 핵심입니다.

### 1.4 tool_use 블록과 tool_result 블록의 모양

```json
{
  "type": "tool_use",
  "id": "toolu_01A09q90qw90lq917835lq9",
  "name": "get_customer",
  "input": { "customer_id": "C-1024" }
}
```

`id`는 이 호출을 식별하는 값입니다. 결과를 돌려줄 때 이 id로 짝을 맞춥니다.

```json
{
  "type": "tool_result",
  "tool_use_id": "toolu_01A9",
  "content": "133,200 KRW"
}
```

### 1.5 tool_use_id — 요청과 결과를 잇는 끈

**`tool_use_id` 짝맞춤은 절대 규칙입니다.** 모델이 요청한 각각의 `tool_use`에는 그와 **같은 id를 가진 `tool_result`가 정확히 하나씩** 있어야 합니다. 임의로 여러 결과를 하나의 id로 합치거나, 일부만 응답하면 API 검증 오류가 나거나 모델이 맥락을 잃습니다.

`tool_use_id`는 **호출 하나를 식별하는 값일 뿐**입니다. 훅끼리 결과를 주고받는 통로도 아니고, 여러 훅이 같은 값을 공유하도록 사람이 맞춰줘야 하는 설정값도 아닙니다.

### 1.6 tool_result는 "새로운 user 메시지" 안에 넣는다

가장 자주 틀리는 부분입니다. 도구를 실행한 뒤 그 결과를 넣는 위치는 **정해져 있습니다.**

> `tool_use`를 담고 있던 assistant 메시지 **바로 뒤에**, **새로운 `role: "user"` 메시지**를 추가하고, 그 `content` 배열 안에 `tool_result` 블록을 넣는다.

```json
[
  { "role": "user",      "content": "고객 C-1024의 환불을 처리해 줘" },
  { "role": "assistant", "content": [
      { "type": "text", "text": "먼저 고객 정보를 확인하겠습니다." },
      { "type": "tool_use", "id": "toolu_01", "name": "get_customer",
        "input": { "customer_id": "C-1024" } }
  ]},
  { "role": "user", "content": [
      { "type": "tool_result", "tool_use_id": "toolu_01",
        "content": "{\"name\":\"홍길동\",\"verified\":true}" }
  ]},
  { "role": "assistant", "content": [ ... 다음 추론 ... ] }
]
```

왜 하필 `user`일까요? 모델 입장에서 도구 실행은 **자기가 한 일이 아니라 외부 세계가 해 준 일**입니다. 외부 세계에서 들어오는 모든 입력은 `user` 역할로 표현하는 것이 이 API의 규약입니다.

도구를 쓰는 대화가 `messages` 배열에 **누적**되는 순서를 다시 정리하면 이렇습니다.

```
[1] user       : "지난 1시간 CPU 메트릭 좀 가져와줘"
[2] assistant  : tool_use  (name="fetch_metrics", input={...})     ← 모델이 도구 호출을 요청
[3] user       : tool_result (tool_use_id=..., content="cpu: 87%") ← 실행 결과를 되돌려줌
[4] assistant  : "CPU가 87%로 높습니다. ..."                        ← 결과를 해석한 답변
```

핵심은 **[3]단계에서 `tool_result`를 배열에 "추가(append)"해야 한다는 것**입니다.

**하지 말아야 할 것들:**

- `tool_use`를 담았던 assistant 메시지 안을 고쳐 쓰거나 대체하기 — assistant 메시지는 모델이 실제로 생성한 기록이므로 조작하면 대화 흐름이 깨집니다.
- HTTP 헤더에 결과를 넣기 — 도구 결과는 요청 **본문(body)**의 `messages` 배열 안에 있어야 합니다. 헤더는 인증/버전 같은 전송 메타데이터용입니다.
- 대화 맨 앞 `system` 메시지에 넣기 — `system`은 전역 규칙용이며, 특정 `tool_use`와 짝지어지지 않습니다.

## 2. 병렬 도구 호출 (Parallel Tool Use)

모델은 **한 번의 응답(한 턴) 안에서 여러 개의 `tool_use` 블록**을 낼 수 있습니다. 서로 독립적인 조회라면 굳이 순차로 할 이유가 없기 때문입니다.

예: 가격 계산에 환율 조회와 세율 조회가 둘 다 필요하다 → 모델이 한 턴에 두 개의 `tool_use`를 낸다.

이때 애플리케이션 루프가 해야 할 일:

1. 응답 안의 **모든** `tool_use` 블록을 찾는다.
2. **전부** 실행한다 (가능하면 동시에).
3. 각각에 대해 **개별 `tool_result` 블록**을 만든다. 각 블록은 자기 `tool_use_id`를 가진다.
4. 이 `tool_result` 블록들을 **하나의 user 메시지 content 배열에 모두 담아** 다음 요청으로 보낸다.

```python
tool_results = []
for block in response.content:
    if block.type == "tool_use":
        output = run_tool(block.name, block.input)
        tool_results.append({
            "type": "tool_result",
            "tool_use_id": block.id,      # 개별 매칭
            "content": output,
        })

messages.append({"role": "assistant", "content": response.content})
messages.append({"role": "user", "content": tool_results})  # 한 턴에 전부
```

**하지 말아야 할 것들**

- 두 결과를 하나의 `tool_result`로 합치기 → id 매핑 파손, API 검증 오류.
- 대화를 두 갈래로 쪼개서 각각 따로 보내기 → 모델이 두 결과를 종합할 수 없음. 하나의 연관된 스레드 안에서 함께 전달해야 함.
- 첫 번째만 실행하고 나머지 무시 → 데이터 누락으로 작업 실패. **"턴당 도구 하나"라는 제약은 존재하지 않습니다.**

## 3. `stop_reason` — 루프의 신호등

응답 객체에는 `stop_reason` 필드가 있습니다. 모델이 **왜 생성을 멈췄는지**를 알려주며, 이것이 **턴 종료를 판별하는 공식 신호**입니다. 루프의 계속/종료 판단은 전적으로 이 값에 달려 있습니다.

| 값 | 의미 | 루프가 해야 할 일 |
|---|---|---|
| `tool_use` | 모델이 도구 실행을 요청하며 멈춤. 응답 안에 `tool_use` 블록이 들어 있음 | 도구를 실행 → `tool_result`를 붙여 **계속** |
| `end_turn` | 모델이 할 말을 다 하고 자연스럽게 턴을 마침. 더 요청할 도구가 없음 | 루프 **종료**, 결과 반환 |
| `max_tokens` | **출력 토큰 상한에 걸려 문장 중간에 잘림** | 미완성! 이어쓰기 요청하거나 `max_tokens`를 늘려 재시도 |
| `stop_sequence` | 지정한 정지 문자열이 나와서 멈춤 | 종료 신호. 상황에 따라 처리 |

즉 `stop_reason == "tool_use"`는 **"공이 너에게 넘어왔다"**는 신호입니다.

### 3.1 흔한 버그 ① — `end_turn`을 "계속" 조건에 넣기

`stop_reason in ("tool_use", "end_turn")`을 continue 조건으로 삼는 코드는 잘못된 코드입니다. `end_turn`은 작업이 **이미 끝났다**는 신호이므로, 그 위에서 루프를 계속 돌리면 끝난 작업에 대해 계속 요청을 보내게 됩니다(불필요한 비용, 무한 루프 위험).

### 3.2 흔한 버그 ② — `max_tokens`를 `else`로 흘려보내기

코드가 `tool_use`와 `end_turn` 두 가지만 분기하고 나머지는 `else`(= 종료)로 처리하는 것이 **가장 흔한 버그**입니다.

```python
if resp.stop_reason == "tool_use":
    ...도구 실행...
else:                      # max_tokens 도 여기로 떨어진다
    return resp            # 잘린 미완성 응답을 "완성품"으로 취급
```

이러면 **잘린 보고서를 최종 결과로 오인하고 에이전트를 조기 종료**합니다. 예외도 안 나고 조용히 데이터가 손실되므로 발견하기 어렵습니다. 그러므로 반드시 명시적으로 분기하십시오.

```python
if resp.stop_reason == "max_tokens":
    raise TruncatedResponse("응답이 잘림 — 이어쓰기 또는 상한 조정 필요")
```

### 3.3 `stop_reason` 관련 사실 정정

- `max_tokens`는 Messages API가 반환하는 **정식 표준 값**입니다. 그 자체로 미처리 예외나 크래시를 일으키지 않습니다.
- 잘못된 폴백이 있다고 해서 응답을 버리고 첫 요청부터 다시 보내는 일은 일어나지 않습니다.
- 코드를 고치지 않는 한 다음 요청의 `max_tokens` 값이 **자동으로 늘어나지 않습니다.**
- `end_turn`은 첫 번째 요청에서만 나오는 값이 아닙니다. 도구 결과를 받은 뒤의 턴을 포함해 **작업이 완료되는 어느 턴에서든** 반환될 수 있습니다.
- `end_turn`은 과금 경계(billing boundary)와 아무 상관이 없으며, 이 값을 지나쳐 계속한다고 토큰이 중복 청구되는 개념도 없습니다.
- `end_turn`과 `tool_use`는 계정 종류와 무관하게 모두 유효한 표준 값입니다. 둘 중 하나만 나오는 계정 같은 것은 없습니다.

### 3.4 왜 "텍스트가 있으면 끝"은 틀린 판단인가

"마지막 텍스트 블록이 비어 있지 않으면 끝났다"는 방식은 **부수 효과(side effect)에 의존하는 추론**입니다. 앞서 봤듯 모델은 도구를 요청하면서도 설명 텍스트를 함께 낼 수 있으므로, 텍스트의 유무와 `stop_reason`은 함께 움직이지 않습니다. 텍스트를 기준으로 판단하면 도구를 더 써야 할 시점에 루프가 조기 종료되어 작업이 미완으로 끝납니다.

또한 콘텐츠 블록의 **개수**로도 완료를 판단할 수 없습니다. API는 개수로 완료 여부를 알려주지 않으며, 블록 수는 응답마다 자유롭게 달라집니다.

**교훈:** 명세로 제공되는 신호(`stop_reason`)가 있으면 그것을 쓰고, 관측 가능한 부산물로 상태를 추측하지 마십시오.

### 3.5 도구 없이 바로 끝나는 것도 정상이다

첫 번째 응답이 `stop_reason: "end_turn"`이고 `tool_use` 블록이 하나도 없는 경우가 있습니다. 이는 **버그가 아닙니다**. 모델이 도구 없이도 충분히 답할 수 있는 간단한 질문이라면, 도구를 한 번도 호출하지 않고 즉시 완료하는 것이 정상이며 올바른 동작입니다.

관련된 잘못된 믿음들:

- "API가 첫 응답의 `end_turn`을 거부하고 재전송을 요구한다" → 그런 동작 없습니다.
- "도구가 필요 없으면 API가 가짜(placeholder) `tool_use` 블록을 끼워 넣는다" → 그런 동작 없습니다.
- "정식 완료로 인정하려면 최소 1회 도구 왕복을 강제해야 한다" → 그럴 필요 없습니다. 오히려 불필요한 호출을 만드는 나쁜 설계입니다.

## 4. 에이전틱 루프 직접 구현하기

"모델이 도구를 쓰면서 스스로 일을 끝낼 때까지 반복"하는 구조를 **에이전틱 루프(agentic loop)**라고 합니다.

### 4.1 루프의 흐름

```
1. 사용자 메시지 + tools 정의를 모델에 보낸다
2. 응답을 받는다
3. 응답의 stop_reason 을 본다
   - "tool_use"  → 모델이 도구를 부르고 싶다는 뜻
                   → 도구를 실제로 실행하고
                   → 그 결과를 tool_result 블록으로 대화에 추가하고
                   → 1번으로 돌아간다
   - "end_turn"  → 모델이 할 말을 다 했다는 뜻 → 루프 종료
4. 최종 답변을 사용자에게 전달
```

### 4.2 `tool_use` → `tool_result` 왕복의 정확한 절차

`stop_reason: "tool_use"`를 받았을 때 루프가 해야 할 일은 정해져 있습니다.

1. 응답 안의 `tool_use` 블록에서 도구 이름과 인자, 그리고 **`tool_use_id`**를 꺼낸다.
2. 해당 도구를 실제로 실행한다.
3. 실행 결과를 `tool_result` 블록으로 만든다. 이때 반드시 **같은 `tool_use_id`를 태그로 붙인다.**
4. 어시스턴트의 원래 응답과 이 `tool_result`를 대화 이력에 이어 붙인다.
5. **업데이트된 전체 대화**를 다시 API에 보낸다.

### 4.3 기본 골격 (Python)

```python
messages = [{"role": "user", "content": "이 프로젝트의 중복 코드를 리팩토링해 줘"}]

while True:
    resp = client.messages.create(
        model="claude-...",
        system="당신은 리팩토링 에이전트입니다.",
        tools=TOOLS,
        messages=messages,
    )

    # (1) 모델이 만든 블록 전체를 그대로 히스토리에 append — text만이 아니라 tool_use도!
    messages.append({"role": "assistant", "content": resp.content})

    if resp.stop_reason != "tool_use":
        break                      # end_turn 등 → 종료의 공식 신호

    # (2) 요청된 도구들을 실제로 실행
    results = []
    for block in resp.content:
        if block.type == "tool_use":
            output = run_my_tool(block.name, block.input)   # 내 코드가 실행
            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,   # 반드시 원래 id로 짝 맞추기
                "content": output,
            })

    # (3) 결과를 user role로 히스토리에 append
    messages.append({"role": "user", "content": results})
```

### 4.4 가장 흔한 버그 ① — 히스토리에서 tool_use / tool_result를 빠뜨리기

위 코드에서 (1)과 (3)을 생략하고 **모델의 `text` 블록만** 히스토리에 넣으면 어떻게 될까요?

- 모델 입장에서는 자기가 파일을 읽었다는 사실도, 읽은 내용도 컨텍스트에 없습니다.
- 그래서 다음 반복에서 **똑같은 도구를 똑같은 인자로 다시 호출**합니다. 무한 루프처럼 보이는 증상이 여기서 나옵니다.

기억할 규칙:

- API가 알아서 히스토리를 관리해 주지 않습니다. **컨텍스트 관리는 전적으로 개발자 책임**입니다.
- API가 토큰 절약을 위해 몇 턴마다 `tool_use` 블록을 자동으로 지우거나, 컨텍스트를 몰래 초기화하는 동작 같은 것은 **없습니다**.
- 도구가 멱등(idempotent)인지 아닌지는 API의 재호출 여부와 무관합니다. 멱등성은 "같은 입력으로 여러 번 실행해도 결과가 같은가"라는 도구 자체의 성질일 뿐입니다.

### 4.5 가장 흔한 버그 ② — 이력을 덮어쓰기

도구 실행 결과를 돌려줄 때 기존 `messages` 배열을 **`tool_result` 하나로 대체(replace)** 해버리는 버그입니다.

```python
# 잘못됨 — 이력을 통째로 날림
messages = [{"role": "user", "content": [tool_result]}]

# 올바름 — 기존 이력에 덧붙임
messages.append({"role": "user", "content": [tool_result]})
```

이력을 덮어쓰면 무슨 일이 생기는가:

- 원래 사용자의 질문([1])이 사라진다 → 무엇을 위한 결과인지 모른다.
- 모델이 왜 그 도구를 호출했는지 담긴 `tool_use`([2])가 사라진다 → 결과의 의도와 맥락을 잃는다.
- 결국 모델은 **이 결과가 무엇에 대한 답인지 해석할 수 없어** 엉뚱하거나 무의미한 응답을 내놓는다.

그리고 API가 무상태이므로 **서버가 알아서 이전 대화를 다시 불러와 채워주는 일은 없습니다.** 다음도 모두 사실이 아닙니다.

- `tool_result` 블록에 첫 호출의 세션 토큰이 필요해서 인증 오류가 난다 → 그런 메커니즘 없음.
- `tool_result`가 자동으로 시스템 프롬프트로 변환되어 이후 턴의 지침을 영구히 바꾼다 → 그런 동작 없음.
- 서버 측 저장소에서 전체 대화를 자동으로 다시 가져온다 → 무상태이므로 불가능.

### 4.6 그 밖의 흔한 잘못된 구현

- 도구를 실행한 뒤 결과를 **애플리케이션 로그 파일에만** 쓰고 이전 대화를 그대로 재전송 → 모델은 결과를 전혀 모르므로 진행이 막히거나 같은 도구 호출을 반복합니다.
- `tool_use` 블록을 받고도 "모델이 어떤 출력을 기대하는지 텍스트로 설명해 줄 때까지" 기다림 → `tool_use` 블록에는 이미 도구 이름과 인자가 다 들어 있습니다. 즉시 실행하면 됩니다.
- `tool_use` 블록만 이력에 넣고 `tool_result` 없이 원래 프롬프트만 다시 보냄 → 요청된 도구 호출에 대한 응답이 없어서 API 오류가 나거나 대화가 진행되지 않습니다.

## 5. 도구 실행이 실패했을 때 — `is_error`

도구 실행 중 예외가 나면 두 가지 선택지가 있습니다.

1. 루프를 즉시 강제 종료 (Hard Fail)
2. 실패 내용을 `tool_result` 블록에 담고 `"is_error": true`를 붙여 **모델에게 돌려주고 계속 진행**

일반적으로 **2번이 더 나은 설계**입니다. 에이전트의 핵심 강점이 **모델 주도 추론(model-driven reasoning)**에 있기 때문입니다. 오류 내용을 대화 맥락에 넣어주면 Claude는

- 잘못된 파일 경로였구나 → 경로를 고쳐 재시도
- 인자 타입이 틀렸구나 → 다른 인자로 재시도
- 이 도구로는 안 되겠구나 → 다른 도구나 우회 전략 선택

같은 **자율적 복구(recovery)**를 스스로 수행할 수 있습니다.

```python
results.append({
    "type": "tool_result",
    "tool_use_id": block.id,
    "is_error": True,
    "content": "FileNotFoundError: config/build.yaml 을 찾을 수 없습니다.",
})
```

`is_error`에 대한 오해 정정:

- `is_error`는 **도구 실행 결과의 실패 여부**를 표시할 뿐, 모델 응답의 완료 상태를 나타내는 `stop_reason`을 대체하거나 그 확인을 없애 주지 않습니다. 둘은 완전히 다른 층위의 신호입니다.
- Messages API는 `is_error` 필드가 없다고 해서 대화를 자동 종료하지 않습니다.
- 오류를 돌려준다고 해서 다음 시도의 성공이 보장되지도 않고, 도구의 내부 호출 제한(rate limit)이 초기화되지도 않습니다.

## 6. 정지 메커니즘: `stop_reason` vs 고정 반복 상한

**올바른 주 정지 조건은 `stop_reason`입니다.** `end_turn`(또는 `stop_sequence`)이 오면 멈추고, `tool_use`면 계속합니다. 이것이 "모델이 목표를 달성했다"는 유일한 신뢰 가능한 신호입니다.

반대로 **"정확히 5회 반복하면 무조건 종료" 같은 고정 반복 상한(Fixed Iteration Cap)을 주 정지 메커니즘으로 삼으면 안 됩니다.**

> `stop_reason`이 아직 `tool_use`인데 상한에 걸려 루프가 끊기면, 모델이 아직 추론을 끝내지 못한 작업을 강제로 포기하게 됩니다. 결과물은 미완성 상태로 남습니다.

복잡한 조사 작업은 필요한 도구 호출 횟수를 미리 알 수 없습니다. 어떤 질문은 2회로 끝나고 어떤 질문은 30회가 필요합니다.

**그렇다고 상한을 아예 두지 말라는 뜻은 아닙니다.** 고정 상한은 **안전 가드레일 / 서킷 브레이커(circuit breaker)**로서는 반드시 필요합니다. 모델이 같은 도구를 무의미하게 반복 호출하는 무한 루프에 빠질 때 비용 폭주를 막아주기 때문입니다. 역할 구분이 핵심입니다.

| 목적 | 사용할 장치 |
|---|---|
| 정상 종료 판단 | `stop_reason` (`end_turn` / `stop_sequence`) |
| 비정상 상황의 비상 정지 | 반복 상한 — 걸렸다는 사실을 **로그로 남기고 경고 처리** |

### 6.1 흔한 오해 바로잡기

- Messages API에 "총 도구 호출 5회"라는 하드 리밋은 **없습니다**. 상한은 개발자가 코드에서 정하는 값입니다.
- 특정 반복 횟수 이후에 `tool_result` 블록 추가가 차단되는 규칙 같은 것도 **없습니다**.
- 반복 상한을 설정한다고 해서 이후 요청에서 `tools` 파라미터가 자동으로 빠지지도 **않습니다**. 그런 자동 동작은 존재하지 않습니다.

## 7. 모델 중심 제어 흐름 vs 애플리케이션 하드코딩

에이전트 루프에서 "다음에 무엇을 할지"를 **누가** 결정하느냐가 아키텍처의 핵심 갈림길입니다.

### (A) 모델 중심 (Model-driven / Dynamic)

애플리케이션은 `tool_result`를 대화에 덧붙여 그대로 모델에게 되돌려 줄 뿐입니다. 모델이 갱신된 맥락을 읽고 스스로 "도구를 더 쓸까(`tool_use`), 답을 마무리할까(`end_turn`)"를 판단합니다.

- 장점: 중간 발견에 **적응(adapt)**한다. 로그를 봤더니 디스크 문제 같으면 메트릭 대신 디스크 도구를 부르는 식.
- 단점: 비결정론적. 같은 입력에도 경로가 달라질 수 있다.
- 예: DB 조회 결과가 0행이면 더 넓은 필터로 재시도할지, 그냥 요약으로 마무리할지를 **모델이** 판단하게 하려면 `tool_result`를 그대로 되돌려 주기만 하면 됩니다.

### (B) 애플리케이션 하드코딩 (Deterministic / Static)

코드에 `if rows == 0: 다시 조회` 같은 규칙을, 혹은 "로그 확인 → 메트릭 확인 → 재시작"처럼 고정된 순서를 박아 둡니다. 이전 단계 결과가 무엇이든 다음 단계는 정해져 있습니다.

- 장점: 예측 가능, 감사(audit)하기 쉬움, 저렴함.
- 단점: 중간 결과를 반영하지 못하는 **고정된 트리(fixed tree)**. 예상 밖 상황을 못 다룸.

### 같은 성격의 안티패턴들

겉으로는 LLM을 쓰지만 제어권은 코드에 있는 사례들입니다.

- 애플리케이션이 행 개수를 검사해 **하드코딩된 프롬프트 템플릿 두 개 중 하나**를 고르기.
- 가능한 쿼리 개선안을 미리 다 계산해 두고 **행 개수를 키로 하는 룩업 테이블**에서 꺼내기.
- 외부 **룰 엔진**이 다음 도구를 정하고 Claude에게는 승인만 받기.

### 부수적 사실

- (A)에서도 `stop_reason` 검사는 **필수**입니다. 도구 호출 여부를 알아야 루프를 돌 수 있기 때문입니다.
- (A)라고 해서 사용 가능한 도구를 전부 한 턴에 몰아 부르지 않습니다 — 필요한 것만 골라 부릅니다.
- (A)와 (B)는 도구 호출과 반환값이 다르므로 **대화 기록 자체가 완전히 달라집니다.**

## 8. 책임 분담 — 누가 무엇을 하는가

저수준 API를 직접 쓸 때 역할을 명확히 정리합시다.

| 주체 | 하는 일 |
|---|---|
| Anthropic API (모델) | 어떤 도구를 어떤 인자로 부를지 **결정하고 JSON으로 요청**만 함 |
| 내 애플리케이션 | 그 요청을 받아 **실제로 도구를 실행**하고, 결과를 `tool_result`로 되돌려 주고, 루프를 계속 돌림 |

즉 API는 절대 클라이언트 측 코드를 대신 실행하지 않습니다. 다음은 모두 **존재하지 않는 메커니즘**입니다.

- Anthropic 서버가 내 사내 티켓팅 시스템이나 지식베이스 API를 대신 호출해 주는 것
- 응답 생성 도중 Anthropic이 내 웹훅 URL을 동기적으로 콜백해서 도구를 대신 실행해 주는 것
- API가 내 런타임에 정의된 동명의 함수를 원격으로 감지해 자동 바인딩·실행해 주는 것

이 책임을 대신 져 주는 것이 바로 상위 계층의 Agent SDK입니다. 저수준 API를 직접 쓰기로 했다면 루프·재시도·에러 처리·컨텍스트 관리 전부가 내 몫입니다.

## 9. Client SDK vs Agent SDK

두 SDK는 추상화 수준이 다릅니다.

### 9.1 Client SDK (Anthropic API 클라이언트)

- 하는 일: HTTP로 Messages API를 호출해 주는 **얇은 라이브러리**.
- 도구 목록도, 도구의 실제 구현도, 4장의 while 루프도 **전부 개발자가 작성**해야 합니다.
- `stop_reason`을 직접 검사하고, 도구를 실행하고, `tool_result`를 직접 append합니다.
- 장점: 완전한 제어. 단점: 보일러플레이트가 많고, 히스토리 관리 실수(4.4/4.5)가 나기 쉽습니다.

### 9.2 Agent SDK (Claude Agent SDK)

- 하는 일: **에이전트 하나를 통째로 제공.**
- **내장 도구(built-in tools)**를 기본 탑재합니다 — 파일 읽기/쓰기, 파일 검색, 셸(Bash) 실행, 웹 검색, 서브에이전트 호출 등.
- **에이전틱 루프를 내부에서 자동 실행**합니다. 개발자는 `stop_reason`을 볼 필요도, `tool_result`를 손으로 붙일 필요도 없습니다.
- 그 밖에 훅, 세션 관리, 서브에이전트, 권한 제어 같은 상위 기능을 함께 제공합니다.

### 9.3 선택 기준

| 상황 | 선택 |
|---|---|
| "파일을 읽고, 셸 명령을 돌리고, 다 될 때까지 반복하되 **루프를 손으로 짜기는 싫다**" | Agent SDK |
| "모델 호출만 필요하고 도구 실행 흐름을 내가 완전히 통제하고 싶다" | Client SDK |

주의: Client SDK도 `stop_reason`을 정상적으로 돌려줍니다. Client SDK로 도구 루프를 **못 만드는 게 아니라 직접 만들어야** 할 뿐입니다.

## 10. 한 장 요약 — 절대 규칙 체크리스트

1. API는 **무상태**다. 매 요청마다 전체 `messages`를 다시 보낸다.
2. 모델 응답의 `content` **블록 전체**(text + tool_use)를 assistant 메시지로 append한다.
3. `tool_result`는 **새 `user` 메시지**의 content 배열에 넣고, 기존 이력에 **append**한다(replace 금지).
4. 각 `tool_use`에는 **같은 `tool_use_id`를 가진 `tool_result`가 정확히 하나** 대응한다.
5. 한 턴에 여러 `tool_use`가 오면 **전부 실행해 하나의 user 메시지에 모아** 돌려준다.
6. 루프 분기는 오직 **`stop_reason`**으로 한다. 텍스트 유무·블록 개수로 추측하지 않는다.
7. `max_tokens`를 **명시적으로 분기**한다. `else`로 흘려보내면 잘린 응답을 완성품으로 오인한다.
8. 도구 실패는 `is_error: true`로 **모델에게 돌려주어** 자율 복구를 유도한다.
9. 반복 상한은 **주 정지 조건이 아니라 서킷 브레이커**다. 걸리면 로그·경고를 남긴다.
10. 도구 실행은 **내 애플리케이션의 책임**이다. API는 요청만 할 뿐 대신 실행해 주지 않는다.
