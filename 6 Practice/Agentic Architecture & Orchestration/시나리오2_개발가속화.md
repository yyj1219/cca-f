# 시나리오2_개발가속화

## 질문 1

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : A coordinator delegates work to an API-extraction subagent and a documentation-writing subagent. The extraction subagent hits an unrecoverable parsing failure mid-task. In a hub-and-spoke design, how should this failure be handled?

**A.** Have the extraction subagent notify the documentation subagent directly so it can adapt its plan around the missing analysis.

**설명**

서브에이전트 간 직접 통신은 모든 에이전트 간 통신이 코디네이터를 거치는 허브-스포크 패턴을 깨뜨린다. 서브에이전트는 격리된 컨텍스트에서 실행되며 형제 에이전트에게 메시지를 보낼 채널이 없고, 최종 결과만 부모에게 반환된다.

**B.** Have the extraction subagent return an empty result marked successful so the workflow continues without interruption.

**설명**

오류를 조용히 빈 성공으로 숨기면 코디네이터가 실패를 알지 못하게 되고, 정상적으로 결과가 없는 경우와 추출 단계가 고장난 경우를 구분할 수 없게 된다. 이는 후속 의사결정을 왜곡하는 것으로 문서화된 안티패턴이다.

**C.** Terminate the entire workflow immediately so no downstream subagent operates on incomplete extraction output.

**설명**

단일 실패로 전체 워크플로를 중단하는 것은 모든 부분 진행 상황을 버리게 되므로 문서화된 안티패턴이다. 코디네이터는 대개 부분적인 결과로 계속 진행하면서 누락된 부분을 표시할 수 있으며, 그렇게 하면 모든 것을 잃지 않을 수 있다.

**D(정답).** Return the error with context to the coordinator, which can retry, delegate elsewhere, or continue with partial results.

**설명**

허브-스포크 아키텍처에서는 코디네이터가 오류 처리와 라우팅을 담당하므로, 해결할 수 없는 실패는 충분한 컨텍스트와 함께 코디네이터로 올라가 합리적인 복구 결정을 내릴 수 있게 한다. 이렇게 하면 실패가 계속 눈에 보이는 상태로 유지되며, 워크플로를 가장 넓게 조망하는 컴포넌트가 대응 방식을 선택할 수 있다.

### 전반적인 설명

허브-스포크 토폴로지는 코디네이터에게 세 가지 책임을 부여한다: 작업 분해와 위임, 결과 집계, 오류 처리. 서브에이전트는 서로 절대 직접 통신하지 않으며, 실패 보고를 포함한 모든 메시지는 허브를 거쳐 흐른다. 이것은 형식을 위한 형식이 아니다. 코디네이터만이 전체 워크플로를 조망할 수 있는 유일한 컴포넌트이므로, 실패한 추출 작업을 재시도할지, 다른 서브에이전트로 재라우팅할지, 아니면 나머지 파이프라인이 부분 결과로 계속 진행하도록 하고 누락으로 받아들일지를 오직 코디네이터만이 판단할 수 있다. 모든 것을 한 지점으로 라우팅하면 시스템에 관측성과 일관된 복구 로직을 위한 단일 지점도 생긴다.

이러한 설계는 서브에이전트가 실제로 동작하는 방식으로도 뒷받침된다. 각 서브에이전트는 매번 새로 시작하는 격리된 컨텍스트에서 실행되며, 최종 메시지만 부모에게 반환된다. 따라서 서브에이전트에게는 자신의 오류를 형제 에이전트에게 전달할 메커니즘이 전혀 없으며, 형제 에이전트는 그 오류를 절대 볼 수 없다. 올바른 패턴은 구조화된 오류를 반환하는 것이며, 이상적으로는 실패 유형, 시도한 작업, 부분 결과를 포함해야 한다. 그래야 코디네이터가 추측이 아니라 합리적인 판단을 내릴 수 있다.

나머지 두 가지 접근 방식은 잘 알려진 안티패턴이다. 단일 실패로 전체 워크플로를 종료하는 것은, 누락된 범위를 표시한 채 점진적으로 성능을 낮추는 방식이 가치를 보존할 수 있는 상황에서 이미 완료된 작업을 버리는 결과를 낳는다. 실패를 조용히 성공으로 표시한 빈 결과를 반환하는 것은 더 나쁘다. 이는 고장난 단계를 정상적인 빈 결과와 구분할 수 없게 만들어, 문서 작성 서브에이전트가 누락된 데이터를 기반으로 결과물을 만들어내는데도 누구도 문제가 생겼다는 사실을 알지 못하게 된다. 서브에이전트의 컨텍스트 격리와 결과 반환이 실제로 어떻게 동작하는지는 커스텀 서브에이전트 만들기 문서를 참고하라.


## 질문 2

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : Two days ago you ran a long named session that analyzed twelve files while diagnosing a race condition. Since then a teammate modified two of those files; the rest of the analysis remains valid. What should you do when continuing the work?

**A(정답).** Resume the session and name the two modified files, directing Claude to re-read them before relying on its earlier analysis.

**설명**

이것이 정답인 이유는 세션이 파일시스템이 아니라 대화 기록을 지속시키기 때문에, 두 파일의 이전 내용이 여전히 복원된 컨텍스트에 남아 있기 때문이다. 변경된 파일을 명시적으로 지정하고 다시 읽도록 지시하면 오래된 정보를 정정하면서 나머지 10개 파일에 대한 유효한 분석은 그대로 유지할 수 있다.

**B.** Resume the session and immediately run /compact so summarization removes the outdated file contents from the restored history.

**설명**

압축(compaction)은 컨텍스트 공간을 절약하기 위해 대화를 압축할 뿐, 어떤 파일 내용이 오래되었는지 알지 못하며 최신 버전으로 교체하지도 않는다. 오래된 읽기 결과를 바탕으로 만든 요약은 오래된 결론을 압축된 형태로 그대로 이어갈 뿐이다.

**C.** Discard the session and start a fresh one, because modifying any previously read file invalidates the entire resumed context.

**설명**

도구 결과가 상당히 오래되었을 때는 새로 시작하는 것이 맞는 선택이지만, 여기서는 12개 파일 중 2개만 변경되었고 나머지 분석은 여전히 유효하다. 세션을 버리는 것은 대상 파일만 다시 읽도록 지시했다면 보존할 수 있었을 유용한 조사 컨텍스트를 낭비하는 것이다.

**D.** Resume the session without extra instructions, since resumption restores a filesystem snapshot that refreshes stale file reads.

**설명**

이것은 틀린 이유가 세션은 파일시스템 스냅샷이 아니라 대화를 저장하기 때문이다. 파일 내용은 Claude가 실제로 읽을 때만 컨텍스트에 들어오므로, 변경된 파일에 대한 이전 읽기 결과는 당시 그대로 대화 기록에 남아 있다.

### 전반적인 설명

여기서 핵심 사고 모델은 세션이 파일시스템 스냅샷이 아니라 대화 기록이라는 점이다. 세션을 재개하면 SDK는 프롬프트, 모든 도구 호출, 모든 도구 결과, 모든 응답을 기록된 그대로 복원한다. 파일 내용은 Claude가 실제로 읽는 순간에만 그 기록에 들어오므로, 이후에 파일을 수정해도 이전의 읽기 결과가 소급되어 갱신되지는 않는다. 따라서 재개된 세션에는 이틀 전 모습 그대로의 두 파일이, 컨텍스트 내 다른 모든 것과 동일한 신뢰도로 담겨 있다.

분석 대상 파일 중 극히 일부만 변경되었으므로, 재개와 새로 시작하기 사이의 문서화된 트레이드오프는 재개 쪽에 유리하다. 이전 조사의 대부분은 여전히 유효하며 다시 만들려면 비용이 크다. 신뢰할 수 있는 패턴은 에이전트에게 변경 사항을 알리는 것이다. 재개 프롬프트에서 변경된 파일을 명시하고, 이전 결론에 의존하기 전에 그 파일들을 다시 읽도록 지시한다. 이렇게 하면 오래된 근거만 정교하게 교체하면서 나머지 컨텍스트는 보존할 수 있다. 반대의 경우, 즉 분석 대상 코드의 상당 부분이 변경된 경우에는 세션을 버리고 구조화된 요약으로 새 세션을 시작하는 편이 더 나은 선택이 된다.

다른 접근 방식들은 메커니즘 자체에서 실패한다. 자동 갱신을 기대하는 것은 세션이 유지하지 않는 파일시스템 스냅샷을 가정하는 것이다. /compact를 실행하면 기록이 압축되지만 현재 내용과 오래된 내용을 구분할 방법이 없으므로, 오래된 읽기 결과를 정정하는 대신 그대로 압축해 넘길 뿐이다. 세션 지속성이 실제로 무엇을 저장하는지는 Agent SDK의 세션(Sessions) 문서를, 파일 수정이 이전 읽기 결과를 갱신하지 않는 이유는 프롬프트 캐싱(Prompt caching) 문서를 참고하라.


## 질문 3

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : A documentation subagent's prompt concatenates code excerpts from twelve files, with all file paths listed together at the end. Its generated docs often attribute behavior to the wrong files. How should the handoff be restructured?

**A.** Number the excerpts sequentially and rely on their order matching the order of the appended file path list.

**설명**

위치 기반 대응은 취약하다. 모델은 긴 프롬프트 전반에 걸쳐 분리된 두 시퀀스를 세어서 정렬해야 하며, 순서 변경이나 누락이 하나라도 있으면 이후 모든 매핑이 조용히 어긋난다. 이는 귀속 관계를 암묵적으로만 남길 뿐 명시적으로 만들지 않는다.

**B(정답).** Wrap each excerpt in a delimited block, such as XML tags, pairing the code content with a separate subtag holding its file path.

**설명**

이것이 정답인 이유는 각 콘텐츠 조각을 다운스트림 에이전트의 컨텍스트에 들어가는 시점에 해당 메타데이터와 구조적으로 결합시키기 때문이다. 모델은 더 이상 어떤 경로가 어떤 발췌문에 속하는지 추론할 필요가 없으므로, 프롬프트 길이나 발췌문 순서와 무관하게 귀속 관계가 유지된다.

**C.** Add a system prompt instruction telling the subagent to verify every attribution against the path list before writing documentation.

**설명**

프롬프트 지시는 확률적인 준수만 제공하며, 근본적인 입력 구조는 여전히 모델이 발췌문-경로 매핑을 스스로 재구성하도록 강요한다. 주의하라고 요청하는 것으로는 모델에게 부족한 구조적 연결 관계를 만들어줄 수 없다.

**D.** Move the file path list to the top of the prompt so the model processes the mapping before reading any of the excerpts.

**설명**

목록의 위치를 바꾸면 매핑이 놓이는 자리는 달라지지만 콘텐츠와 메타데이터는 여전히 물리적으로 분리된 상태로 남으므로, 모델은 여전히 분리된 목록을 12개의 발췌문과 머릿속으로 연결해야 한다. 위치에 따른 주의 효과는 구조적 연결 문제를 해결하지 못한다.

### 전반적인 설명

한 에이전트가 다른 에이전트에게 컨텍스트를 넘길 때, 받는 쪽은 오직 자신의 프롬프트 안에 있는 것만 보며, 그것도 포맷된 그대로 본다. 콘텐츠(코드 발췌문)와 메타데이터(파일 경로)가 서로 연결되지 않은 두 개의 덩어리로 도착하면, 모델은 그 연관 관계를 스스로 재구성해야 하고, 발췌문이 여러 개일 경우 그 재구성은 충분히 자주 실패하여 체계적인 오귀속을 낳는다. 해법은 지시가 아니라 구조에 있다. 각 발췌문에 콘텐츠와 출처를 함께 담는 자체 구분 블록을 부여하는 것이다. 예를 들어 <document_content>와 <source> 하위 태그를 담은 <document> 래퍼가 그것이다. 이는 Anthropic이 다중 문서 프롬프트에 권장하는 패턴으로, 명시적인 구분자가 콘텐츠, 메타데이터, 지시 사항 사이의 경계를 모델에게 명확하게 만들어주기 때문이다. Prompt templates and variables를 참고하라.

내재화할 만한 사고 모델은 이것이다: 작성자의 머릿속에만 존재하는 연관 관계(세 번째 발췌문은 세 번째 경로와 연결된다)는 모델이 받는 연관 관계가 아니다. 구조화된 형식은 암묵적인 관계를 명시적인 관계로 바꾼다. 그래서 경로 목록을 프롬프트 맨 위로 옮기는 것이 도움이 되지 않는 것이다. 초두 효과는 주의를 어디에 기울일지에 영향을 주지만, 매핑 자체는 여전히 분리되어 있고 추론이 필요하다. 발췌문에 번호를 붙이고 목록 순서에 의존하는 것도 똑같이 암묵적 매핑 문제이며, 오히려 더 취약하다. 하나라도 빠지거나 순서가 바뀌면 그 뒤의 모든 귀속이 어긋나기 때문이다. 그리고 귀속을 재확인하라는 시스템 프롬프트 지시는 어디까지나 프롬프트 수준의 지침일 뿐, 입력 자체가 어떤 경로가 어떤 발췌문에 속하는지 전혀 명시하지 않았다는 사실을 바꾸지는 못한 채 확률만 개선한다.

같은 원칙은 더 큰 규모에서도 적용된다. Claude가 출처 기반 출력을 네이티브로 지원할 때는, 문서가 각자의 source 및 메타데이터 필드를 가진 개별 콘텐츠 블록으로 제공되는데, 이는 Citations에 설명되어 있다. 내장된 인용 기능을 쓰든 직접 만든 XML 블록을 쓰든 설계 원칙은 동일하다. 모든 콘텐츠 단위를 그 출처와 물리적으로 함께 배치하여, 귀속 관계가 절대 모델의 추론에 의존하지 않도록 하는 것이다.


## 질문 4

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : A pull request touches 16 files. A single review pass over all of them produces detailed feedback on the first few files, shallow comments on the rest, and identical code patterns judged differently across files. How should this review be restructured?

**A.** Run the identical full-PR review three separate times and report only the findings that appear in at least two of the runs.

**설명**

일관성이 없는 여러 패스에 대해 합의 필터링을 적용하면 실제 문제를 억제하게 된다. 한 번의 희석된 패스에서만 발견된 진짜 버그가 폐기될 수 있기 때문이다. 또한 각 개별 패스가 왜 얕고 서로 모순되는지에 대한 근본 원인은 고치지 못한 채 비용만 세 배로 늘린다.

**B(정답).** Chain the review: analyze each file individually for local issues, then run a separate pass over cross-file interactions.

**설명**

이러한 프롬프트 체이닝 구조는 근본 원인, 즉 한 패스가 많은 파일을 다뤄야 할 때 발생하는 주의 분산을 해결한다. 파일별 패스는 로컬 이슈에 대한 일관된 깊이를 보장하고, 별도의 통합 패스는 타입 불일치나 계약 불일치 같은 파일 간 문제를 잡아낸다.

**C.** Move the review to a model tier with a larger context window so all 16 files can be evaluated together in one pass.

**설명**

설명된 증상은 컨텍스트 윈도우에 콘텐츠가 들어가지 못해서 생긴 것이 아니라, 한 패스 안에서 많은 파일에 주의가 너무 얇게 분산되어 생긴 것이다. 더 큰 윈도우는 더 많은 텍스트를 담을 수 있게 해줄 뿐, 주의의 일관성이나 깊이를 개선하지는 못한다.

**D.** Enable extended thinking for the review pass so the model deliberates more thoroughly before commenting on each of the 16 files.

**설명**

확장된 사고(extended thinking)는 단일 작업에 대한 추론 깊이를 더해주지만, 한 패스가 16개 파일에 주의를 나누어야 한다는 사실 자체는 바꾸지 못한다. 이 불일치는 숙고 부족이 아니라 작업 구조에서 비롯된 것이므로, 동일한 분산 패턴이 그대로 지속된다.

### 전반적인 설명

큰 변경 사항 집합을 단일 패스로 리뷰하면 특징적인 방식으로 실패한다. 모델은 일부 파일에는 깊은 분석을 하고 다른 파일에는 얕은 처리만 하며, 기준을 일관되지 않게 적용해 한 파일에서는 어떤 패턴을 지적하면서 다른 곳의 동일한 코드는 그냥 승인한다. 근본 메커니즘은 주의 분산이다. 하나의 추론 패스가 한 번에 많은 파일을 다뤄야 할 때, 개별 파일 어느 것도 지속적인 초점을 받지 못하고, 입력 초반에 내려진 판단이 이후 파일까지 안정적으로 이어지지 않는다.

해법은 작업의 형태에 맞는 프롬프트 체이닝 구조다. 리뷰에는 두 가지 서로 다른 종류의 발견 사항이 있다. 한 파일 안에서만 보이는 로컬 이슈와, 타입 불일치, 순환 의존성, 데이터 흐름 불일치처럼 파일들을 가로질러야만 보이는 통합 이슈다. 리뷰를 파일별 패스와 이어지는 별도의 파일 간 통합 패스로 체이닝하면 각 관심사에 집중된 컨텍스트를 줄 수 있다. 각 파일별 패스는 하나의 파일을 온전한 주의력으로 리뷰하여 일관된 깊이를 만들어내고, 통합 패스는 그 결과들과 파일 간 관계를 바탕으로 작업한다. 체이닝은 또한 중간 출력을 검토할 수 있게 해주므로, 파일별 결과를 통합 단계가 소비하기 전에 검증하거나 기록할 수 있다. Anthropic의 프롬프팅 가이드는 작업을 순차적인 호출로 나누는 이 근거를 정확히 설명한다. 중간 출력을 검토해야 하거나 특정 파이프라인 구조를 강제해야 할 때 여전히 유용하다는 것이다(Anthropic prompt engineering documentation 참고).

다른 대안들은 모두 문제를 잘못 진단한다. 더 큰 컨텍스트 윈도우는 용량 문제를 다룰 뿐 주의의 질을 다루지 못한다. 파일들은 이미 다 들어가 있고, 단지 모두가 동일한 정성으로 처리되지 않은 것뿐이다. 일관성 없는 세 번의 패스에 대한 다수결 투표는 단 한 번만 드러난 실제 발견 사항을 폐기하면서 비용을 세 배로 늘린다. 확장된 사고는 한 패스 안에서 추론을 깊게 만들지만, 16개 파일에 걸쳐 하나의 패스가 분산된다는 구조적 문제는 그대로 남긴다. 내재화해야 할 엔지니어링 직관은 이것이다. 출력 품질이 입력 내 위치에 따라 달라진다면, 단순히 컴퓨팅 자원을 더하지 말고 작업 자체를 재구성하라.


## 질문 5

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. **QUESTION** : This team embeds the Agent SDK to automate large refactors. The main agent, configured with allowedTools of Read, Grep, and Glob, ignores repeated prompt instructions to delegate analysis work to the defined subagents. Which change enables delegation?

명확한 설명은 작업이 서브에이전트와 얼마나 잘 매칭되는지를 개선하지만, 매칭은 위임이 가능해진 이후에만 의미가 있다. Task 도구가 없으면, 설명이 얼마나 정교하든 메인 에이전트는 어떤 서브에이전트도 생성할 수 없다.

**설명**

서브에이전트는 Task 도구를 통해 생성되므로, allowedTools에 Task가 없는 코디네이터는 지시 사항과 무관하게 위임할 메커니즘이 전혀 없다. Task를 추가하면 프롬프트가 사용하라고 요구하는 그 기능이 복원된다.

**C.** Add each subagent's name to the main agent's allowedTools so it can invoke them directly.

**설명**

서브에이전트는 자신의 이름을 가진 도구로 호출되지 않는다. 위임은 항상 Task 도구를 거쳐 흐르므로, allowedTools에 서브에이전트 이름을 나열해도 호출 경로가 생기지 않는다.

**D.** Strengthen the delegation instructions in the system prompt and repeat them in CLAUDE.md.

**설명**

프롬프트 지시는 지침일 뿐 기능이 아니다. 에이전트는 이미 위임하라는 지시를 받고 있다. 실패의 원인은 도구 설정이 그것을 실행할 방법을 제공하지 않는다는 것이며, 더 강한 문구로는 누락된 도구를 만들어낼 수 없다.

### 전반적인 설명

Claude Agent SDK에서 서브에이전트로의 위임은 모델이 직접 수행하는 행동이 아니라 특정 도구 호출을 통해 일어난다. 코디네이터가 Task 도구 호출을 발생시키면, 하니스가 해당 서브에이전트를 생성하여 자체 격리된 컨텍스트에서 실행시키고 최종 메시지를 반환한다. 즉 서브에이전트를 생성하는 것은 Read나 Bash와 마찬가지로 allowedTools가 통제하는 기능이다. Task가 목록에 없으면 에이전트에게는 서브에이전트를 만들어낼 수 있는 행동이 문자 그대로 존재하지 않으므로, 결국 스스로 작업을 처리하게 되며, 이것이 바로 팀이 관찰한 현상이다.

여기서 유용한 사고 모델은 기능 설정과 프롬프트 지침을 엄격히 분리하는 것이다. 프롬프트는 모델이 무엇을 시도할지를 형성하고, 도구 목록은 무엇을 할 수 있는지를 정의한다. 에이전트가 프롬프트가 요구하는 행동을 계속 취하지 못한다면, 먼저 확인해야 할 것은 그 행동이 애초에 가능한지 여부다. 그래서 AgentDefinition의 설명을 다시 쓰거나 시스템 프롬프트와 CLAUDE.md에서 지시를 강화하는 것으로는 이 실패를 고칠 수 없다. 그런 수단들은 설정에 존재하지 않는 기능을 둘러싼 확률적 행동을 조정할 뿐이다. 마찬가지로 서브에이전트는 자신의 이름을 가진 도구로 절대 호출되지 않는다. 각 AgentDefinition의 이름과 설명은 코디네이터가 Task를 호출할 때 어떤 서브에이전트를 요청할지 알려줄 뿐이다.

Task가 있으면 코디네이터는 하나의 응답 안에서 여러 Task 호출을 동시에 발생시켜 독립적인 서브에이전트들을 병렬로 실행할 수도 있는데, 이는 대규모 코드베이스에 걸쳐 분석 작업을 펼쳐나가는 표준 패턴이다. Task 메커니즘, AgentDefinition 설정, 컨텍스트 격리가 어떻게 맞물리는지는 공식 문서인 Subagents in the SDK를 참고하라.

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. **QUESTION** : Prompts that generate module documentation include eight formatting constraints. Despite repeated emphasis, every run violates one or two of them, and which constraints slip varies. How should the workflow be restructured to reliably satisfy all constraints?

**A.** Restate the constraints at both the top and bottom of the prompt and flag the most frequently violated ones as IMPORTANT.

**설명**

반복과 강조는 일부 규칙의 우선순위를 다른 규칙에 비해 높일 뿐이며, 시나리오 자체가 이미 반복된 강조로도 위반이 사라지지 않았음을 보여준다. 단일 패스가 여러 제약 조건을 동시에 충족해야 할 때는, 어떻게 강조하든 일부는 누락된다.

**B(정답).** Chain the work: generate the documentation draft first, then run a second pass that checks each constraint and rewrites violations.

**설명**

이것은 문서화된 자기 교정 체이닝 패턴이다. 첫 번째 호출은 콘텐츠 생성에 집중하고, 두 번째 호출은 초안을 제약 목록과 대조해 검토하고 누락을 고치는 일에만 전념한다. 생성과 검증을 분리하면 어느 단계도 전체 제약 부담을 한꺼번에 다룰 필요가 없어지는데, 이는 정확히 관찰된 실패 양상을 해결한다.

**설명**

CLAUDE.md는 강제가 아니라 지침이므로, 그 안의 지시 사항도 일반 프롬프트 지시와 마찬가지로 여전히 확률적이다. 제약을 옮기는 것은 어디에 기술되는지를 바꿀 뿐, 단일 생성 패스가 그 모든 것을 얼마나 신뢰성 있게 준수하는지는 바꾸지 못한다.

**D.** Enable extended thinking for the generation request so the model deliberates over the full constraint list before writing.

**설명**

확장된 사고는 어려운 문제에 대해 추론 깊이를 더해주지만, 여기서의 실패 원인은 추론 부족이 아니라 단일 패스 안에서의 제약 과부하다. 또한 여전히 발생하는 위반을 잡아낼 검증 단계는 전혀 제공하지 않으면서 토큰 비용만 늘린다.

### 전반적인 설명

이 상황은 프롬프트 체이닝을 촉발하는 전형적인 사례다. 여러 제약 조건을 동시에 담은 단일 요청은 지시 사항을 얼마나 강조하든 신뢰성 있게 한두 개를 놓치게 된다. 사고 모델은 이렇다. 각 생성 패스에는 한정된 주의 예산이 있으며, 콘텐츠 생산과 여덟 개 규칙 감시가 한 패스 안에서 경쟁하면 준수 여부는 확률적이 된다. 체이닝은 작업을 서로 다른 책임을 가진 순차적 호출로 나눈다. 첫 호출은 초안을 생성하고, 두 번째 호출은 그 초안과 제약 목록을 받아 오직 검토와 재작성만 수행한다. 검증 패스는 콘텐츠를 동시에 작성하지 않으므로 제약 조건을 하나씩 확인할 수 있고, 살아남은 위반은 발견되어 수정될 가능성이 훨씬 높아진다.

이것은 Anthropic이 체이닝된 워크플로에 대해 문서화한 자기 교정 패턴이며, 모델이 내부적으로 더 많은 다단계 작업을 처리하게 되어도 왜 체이닝이 여전히 가치를 지니는지를 보여준다. 한 패스가 모든 것을 잘 처리하기를 바라는 대신, 중간 출력을 검토하고 특정 파이프라인 구조를 코드로 강제할 수 있게 해주기 때문이다. 이 시험 자료 다른 곳에서도 파일별 분석 후 파일 간 통합 패스를 거치는 것과 같은 형태가 등장하지만, 제약 준수 체인은 그 자체로 별개의 응용이다.

대안들은 모두 작업을 단일 패스에 남겨둔다. 규칙을 반복하고 IMPORTANT로 표시하는 것은 강조 예산을 소모할 뿐 규칙들 사이의 우선순위만 재조정한다. 제약 조건을 CLAUDE.md로 옮기는 것은 전달 표면을 바꿀 뿐, CLAUDE.md의 내용은 모델이 확률적으로 따르는 지침이며 강제 메커니즘이 아니다. 확장된 사고는 어려운 문제에 대한 추론을 심화시키지만, 관찰된 실패는 추론 격차가 아니다. 전담 검증 단계가 없으면 간헐적인 누락은 여전히 그대로 결과물에 반영된다. 체이닝의 근거는 Anthropic의 프롬프트 엔지니어링 가이드를 참고하라.

**C.** Run all five pipeline steps in parallel so the irrelevant steps consume less wall-clock time overall.

**설명**

병렬 실행은 지연 시간을 줄이지만, 초기 발견 사항이 불필요하다고 보여줄 단계에도 여전히 노력을 쏟게 되며, 고정된 계획에 포함되지 않았던 단계를 추가할 수도 없다. 또한 하나의 발견이 다음 질문을 결정하는, 진단이 흔히 갖는 순차적 의존성을 무시한다.

**D.** Keep the five-step chain but reorder it so the most diagnostic checks execute before the less informative ones.

**설명**

고정된 시퀀스를 재정렬해도 근본적인 한계는 바뀌지 않는다. 단계들은 어떤 근거도 존재하기 전에 선택된 것이므로, 나중 단계는 초기 발견 사항이 실제로 보여주는 것과 여전히 무관할 수 있다. 프롬프트 체이닝은 예측 가능한 워크플로에 적합하며, 결과에 따라 경로가 드러나는 조사에는 맞지 않는다.

### 전반적인 설명

작업 분해를 선택하는 핵심 규칙은 워크플로의 구조를 그 불확실성 프로필에 맞추는 것이다. 프롬프트 체이닝(고정된 순차 파이프라인)은 모든 단계를 사전에 알 수 있을 때 잘 작동한다. 매번 동일한 리뷰 템플릿, 동일한 추출 단계, 동일한 검사 항목이 그 예다. 그 가치는 재현성과 안정성이다. 동적 적응형 분해는 전체 범위를 알 수 없고 각 단계가 이전 단계에서 드러난 것에 의존할 때 작동하는데, 이는 간헐적 버그 조사의 본질적인 형태다. 초기 발견(예를 들어 실패가 특정 배포 시점과 상관관계가 있다는 것)이 다음 하위 작업을 결정하며, 미리 작성된 어떤 스크립트도 그것을 담아낼 수 없었을 것이다.

사고 모델은 이렇다. 고정 파이프라인은 근거가 존재하기 전에 내려진 결정을 코드화하는 반면, 적응형 분해는 근거가 도착할 때까지 각 결정을 미룬다. 그래서 파이프라인에 분기를 더 붙이거나, 단계를 재정렬하거나, 병렬화하는 것이 모두 같은 방식으로 실패하는 것이다. 이들은 계획이 중간 결과에서 자연스럽게 드러나야 하는 작업에 미리 확정된 계획을 계속 맡겨둔다. 추가 분기는 무한한 실패 모드의 공간을 뒤쫓고, 재정렬은 여전히 눈을 감고 선택된 단계를 실행하며, 병렬화는 아예 실행되지 않아야 할 작업의 소요 시간만 줄여준다. 트레이드오프는 반대 방향으로도 작동한다. 항상 동일한 측면을 검사하는 리뷰처럼 진짜로 예측 가능한 워크플로에 적응형 분해를 적용하면, 아무 이득 없이 유연성 오버헤드를 지불하고 재현성을 희생하게 된다.

Anthropic의 에이전트 설계 가이드는 미리 정의된 코드 경로를 가진 워크플로와 스스로 프로세스를 동적으로 지휘하는 에이전트 사이에 정확히 이 경계선을 긋는다. Building Effective Agents와 Chain complex prompts를 참고하라.


## 질문 8

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : Your project CLAUDE.md tells Claude to ignore the generated/ directory during analysis. When a developer delegates codebase research to the built-in Explore subagent, its findings repeatedly reference generated files. What is the correct fix?

**A(정답).** Restate the exclusion rule in the delegation prompt, because the Explore subagent skips CLAUDE.md files.

**설명**

이것이 정답인 이유는 내장된 Explore와 Plan 서브에이전트가 조사를 빠르고 저렴하게 유지하기 위해 CLAUDE.md 파일과 부모 세션의 git 상태를 의도적으로 건너뛰기 때문이다. 서브에이전트에게 반드시 전달되어야 하는 규칙은 위임 프롬프트라는 채널을 통해 명시적으로 전달해야 한다.

**설명**

규칙을 어느 메모리 위치에 두는지 바꿔도 도움이 되지 않는다. Explore는 사용자 수준 파일을 포함한 CLAUDE.md 계층 전체를 건너뛰기 때문이다. 규칙은 여전히 서브에이전트의 컨텍스트에 전혀 들어가지 못한다.

**C.** Mark the rule as IMPORTANT in the project CLAUDE.md so it carries into the subagent's isolated context.

**설명**

강조는 실제로 로드된 콘텐츠들 사이에서 규칙이 주의를 얼마나 잘 차지하는지에만 영향을 준다. Explore가 CLAUDE.md를 전혀 로드하지 않으므로, 그 파일 안에서 아무리 강조해도 전달될 수 없다.

**D.** Have the parent session filter references to generated/ out of Explore's findings after the subagent returns.

**설명**

사후 필터링은 원인이 아니라 증상만 다룬다. Explore는 여전히 생성된 파일에 검색 노력을 쏟고 그 파일들을 근거로 결론을 내릴 수 있으므로, 반환된 요약을 정리하는 것으로는 신뢰할 수 있는 조사 결과를 만들어내지 못한다. 제외 규칙은 서브에이전트가 검색을 시작하기 전에 전달되어야 한다.

### 전반적인 설명

Claude Code의 서브에이전트는 격리된 컨텍스트 윈도우에서 실행되지만, 그 컨텍스트에 담기는 내용은 에이전트 유형에 따라 달라진다. 대부분의 내장 및 커스텀 서브에이전트는 시작 시 전체 CLAUDE.md 계층과 git 상태 스냅샷을 로드한다. 내장된 Explore와 Plan 서브에이전트는 문서화된 예외로, 설계상 둘 다 건너뛴다. 이는 빠른 읽기 전용 조사가 대부분 필요 없는 프로젝트 메모리의 토큰 비용을 지불하지 않도록 하기 위함이다. Anthropic은 또한 어떤 에이전트가 이를 건너뛰는지 바꿀 수 있는 프런트매터 필드나 에이전트별 설정이 없다고 명시하므로, 이 동작은 재구성으로 우회할 수 없다.

가져가야 할 사고 모델은 위임 프롬프트가 부모에서 서브에이전트로 향하는 신뢰할 수 있는 채널이라는 것이다. 메인 대화는 전체 CLAUDE.md 컨텍스트를 가지고 Explore의 결과를 읽으므로, 대부분의 프로젝트 규칙은 서브에이전트 자체에 전달될 필요가 없다. 그러나 검색 중 어떤 디렉터리를 건너뛸지처럼 규칙이 실제로 서브에이전트 자신의 동작을 통제해야 하는 경우, 문서의 지침은 위임 시 Claude에게 주는 프롬프트에서 그것을 다시 명시하라는 것이다. 서브에이전트가 반환한 후 결과를 필터링하는 것은 실패하는데, 조사 자체가 이미 제외 대상 파일들을 대상으로 수행되었기 때문이다. 규칙을 다른 메모리 위치로 옮기거나 강조로 증폭시키는 것도 같은 근본 이유로 실패한다. 컨텍스트에 전혀 로드되지 않은 콘텐츠는 그 안에서 동작하는 에이전트에 영향을 줄 수 없다.

각 서브에이전트 유형이 시작 시 무엇을 로드하는지에 대한 전체 설명은 Create custom subagents와 Subagents in the SDK를 참고하라.


## 질문 9

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : Despite a CLAUDE.md rule stating "never push directly to main," logs show Claude Code occasionally pushed to main during long autonomous refactoring sessions. The team needs this rule to hold on every run. What should they implement?

**A.** Package the rule into an Agent Skill whose description triggers whenever Claude performs git operations.

**설명**

스킬도 여전히 모델이 읽고 따르는 지시 사항이므로, CLAUDE.md와 동일한 확률적 준수를 그대로 물려받는다. 규칙을 git 작업에 한정하면 관련성은 개선되지만 위반을 불가능하게 만들지는 못한다.

**B.** Move the rule to the top of CLAUDE.md, mark it IMPORTANT, and restate it in every session's first prompt.

**설명**

강조와 반복은 다른 지시 사항에 비해 그 규칙의 우선순위를 높이지만, CLAUDE.md는 여전히 모델이 확률적으로 따르는 지침일 뿐이다. 시나리오는 프롬프트 지시가 이미 간헐적으로 실패했음을 보여주며, 이 변화는 실패 모드를 없애는 것이 아니라 확률만 바꿀 뿐이다.

**C(정답).** Add a PreToolUse hook that inspects Bash commands and rejects any push targeting the main branch.

**설명**

이것이 정답인 이유는 PreToolUse 훅이 도구 호출이 실행되기 전에 코드로서 실행되므로, 모델이 무엇을 의도하든 위반하는 푸시는 절대 실행될 수 없기 때문이다. 훅은 지시 기반 접근으로는 불가능한 결정적인 보장을 제공한다.

**D.** Require every session to run in plan mode so proposed git operations are reviewed before execution.

**설명**

플랜 모드는 읽기 전용 조사 단계이며, 팀이 계획을 승인하고 실행이 시작되면 플랜 모드의 어떤 부분도 이후 main으로의 푸시를 막지 못한다. 또한 하나의 규칙을 다루기 위해 모든 작업에 큰 마찰을 부과하면서도 여전히 사람이 문제를 포착하는 데 의존한다.

### 전반적인 설명

이 문제는 프롬프트 지침과 프로그래밍적 강제 사이의 핵심 구분을 시험한다. CLAUDE.md, 스킬, 세션 프롬프트 어디에 있든 자연어 지시로 표현된 것은 컨텍스트 내의 다른 모든 지시와 모델의 주의를 두고 경쟁하며, 준수 여부는 확률적이다. 대개는 따르지만 간혹 그렇지 않다. 규칙에 실질적인 결과(main 브랜치 보호, 금액 한도, 민감한 작업 전 신원 확인)가 걸려 있을 때 "대개"는 용인할 수 있는 보장이 아니며, 프로덕션에서 관찰된 간헐적 위반은 정확히 지시 기반 강제가 보이는 예상된 실패 양상이다.

PreToolUse 훅은 강제 모델 자체를 완전히 바꾼다. 이것은 일치하는 모든 도구 호출 전에 실행되는 코드다. 훅은 Bash 명령을 검사할 수 있으며, 거부 결정을 반환하거나 종료 코드 2로 종료함으로써 그 호출을 차단하여 절대 실행되지 않게 할 수 있다. 모델은 훅을 건너뛰거나 잊거나 재해석할 수 없다. 그래서 사고 모델은 다음과 같다: 지시는 요청이고, 훅은 관문이다. 엔지니어링상의 트레이드오프는 훅이 경직되어 있고 유지보수가 필요하다는 것이므로, 위반이 절대 용납될 수 없는 소수의 규칙에만 훅을 예약해두고, CLAUDE.md와 스킬은 유연성이 중요한 관례와 선호를 담당해야 한다.

CLAUDE.md 규칙을 강화하거나 Agent Skill로 옮기는 것은 강제를 계속 지시 쪽에 두는 것이므로 실패율이 0보다 큰 채로 남는다. 플랜 모드를 의무화하면 계획 단계에 사람의 검토가 추가되지만, 플랜 모드는 읽기 전용 조사이며 실행이 시작된 이후의 명령을 가로채지 않는다. 이는 하나의 확률적 안전장치(모델의 준수)를 다른 확률적 안전장치(사람의 경계)로 바꾸는 것일 뿐이다.

PreToolUse 매처와 차단 결정이 어떻게 동작하는지는 Claude Code hooks reference와 Get started with Claude Code hooks를 참고하라.


## 질문 10

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : Two subagents researching a legacy module report different default values for the same timeout setting, each drawn from a different internal document. How should their findings reach the main agent that is drafting the documentation?

**A.** Have each subagent apply credibility heuristics to select the single most likely value and return only that one, keeping the handoff record concise.

**설명**

이것은 틀린 이유가 서브에이전트 수준에서 임의로 하나의 값을 선택하면 메인 에이전트가 필요로 하는 정보가 파괴되기 때문이다. 불일치 자체가 의미 있는 발견이며, 서브에이전트가 조용히 한 값을 버리면 충돌 사실도 패배한 쪽의 출처도 이후 단계에서 복구할 수 없다.

**B.** Have the main agent automatically adopt the value from whichever source document was modified most recently and silently discard the older finding.

**설명**

이것은 틀린 이유가 최신성만으로는 정확성이 보장되지 않으며, 오래된 값을 조용히 버리면 문서를 검토하는 사람에게 충돌 사실이 숨겨지기 때문이다. 날짜는 차이를 해석하는 데 유용한 메타데이터이지만, 조정 과정에 참고할 정보일 뿐 한 출처의 주장을 자동으로 삭제하는 근거가 되어서는 안 된다.

**C(정답).** Return both values in a structured record that flags the conflict and attributes each to its source, deferring reconciliation to the main agent.

**설명**

이것이 정답인 이유는 신뢰할 수 있는 출처들 사이의 충돌하는 값은 서브에이전트 수준에서 임의로 해결하기보다는 각 출처 문서에 귀속시킨 채로 보존해야 하기 때문이다. 메인 에이전트는 불일치를 조정하는 데 필요한 더 넓은 컨텍스트를 가지고 있으며, 구조화된 기록은 핸드오프 전 과정에서 주장과 출처의 매핑을 온전히 유지시켜준다.

**D.** Re-run both subagents against a shared prompt instructing them to cross-check each other until they converge on one agreed value.

**설명**

이것은 틀린 이유가 불일치는 서브에이전트의 추론이 아니라 출처 문서 자체에서 비롯된 것이므로, 반복 실행으로는 실제로 충돌하는 출처들을 합의시킬 수 없기 때문이다. 또한 토큰과 지연 시간을 낭비하면서도 여전히 적절한 귀속과 함께 충돌을 드러내는 데 실패한다.

### 전반적인 설명

여러 에이전트가 서로 다른 출처에서 정보를 수집할 때, 핸드오프 형식이 귀속 정보와 불일치가 집계 과정에서 살아남는지를 결정한다. 신뢰할 수 있는 패턴은 콘텐츠와 메타데이터를 별도의 짝지어진 필드로 유지하는 구조화된 기록이다. 각 값은 그 출처 문서 이름과, 이상적으로는 날짜나 리비전 표시와 함께 이동한다. Anthropic의 프롬프팅 가이드는 다중 문서 입력에 대해 동일한 원칙을 반영하며, 문서 콘텐츠와 출처 메타데이터를 명확히 구분된 별도의 필드(예를 들어 <source> 요소와 함께 있는 <document_content> 요소)에 유지하여 모델이 어떤 메타데이터가 어떤 콘텐츠에 속하는지 추측할 필요가 없도록 하라고 권장한다. 이 구조는 Prompt templates and variables를 참고하라.

충돌하는 값은 그 구조 안에서 특별한 처리를 받아야 한다. 신뢰할 수 있는 두 출처가 서로 다르다는 것을 발견한 서브에이전트는 승자를 고르는 대신 충돌 사실을 표시하고 각 값을 출처에 귀속시켜야 한다. 조정 결정은 전체 작업을 조망하는 코디네이팅 에이전트의 몫이기 때문이다. 이 역할 분담이 바로 이 패턴이 잘 작동하는 이유다. 서브에이전트는 좁은 시야를 가진 수집자이고, 메인 에이전트는 한 문서가 오래되었는지, 그 차이가 시간적인 것인지(정당하게 시간에 따라 변한 값), 아니면 문서에 그 불일치를 팀이 고쳐야 할 사항으로 표시해야 하는지를 판단하는 데 필요한 출처 간 컨텍스트를 가지고 있다.

거부된 접근 방식들은 모두 정보를 너무 일찍 무너뜨린다. 서브에이전트 수준의 신뢰도 추측과 자동 최신성 규칙 모두 부분적인 시야로 되돌릴 수 없는 선택을 하며, 에이전트를 수렴할 때까지 재실행하는 것은 출처 수준의 불일치를 에이전트 수준의 비일관성으로 잘못 진단하여 신뢰할 수 있는 답을 내지 못한 채 토큰만 소모한다.

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. **QUESTION** : An Agent SDK harness receives a coordinator response containing three tool_use blocks, each spawning a read-only code analysis subagent; the coordinator states it will delegate file edits after reviewing the findings. How should the harness handle this batch?

**A.** Execute the three calls strictly in the order the tool_use blocks appear, because the model emitted them in the sequence it expects them to complete.

**설명**

이것은 틀린 이유가 문서에서 런타임이 도구 호출을 나타난 순서대로 실행할 것을 요구하지 않는다고 명시하기 때문이다. 순차 실행을 강제하면 세 개의 독립적인 분석 작업이 병렬로 얻을 수 있는 지연 시간 이점을 버리게 된다.

**설명**

**설명**

이것은 틀린 이유가 문서에서 별도의 도구 결과에 대해 별도의 사용자 메시지를 보내는 것을 명시적으로 경고하고 있기 때문이다. 이런 방식으로 결과를 조금씩 흘려주면 기대되는 턴 구조가 깨지고, 이후 모델이 병렬 도구 호출을 배치하지 않도록 학습시키게 된다.

**D(정답).** Run the three analysis calls concurrently and return all three tool_result blocks together in the next user message.

**설명**

이것이 정답인 이유는 API가 하나의 응답에 담긴 여러 도구 호출에 대해 실행 순서를 규정하지 않으며, 독립적인 읽기 전용 작업은 병렬로 실행해도 안전하기 때문이다. 일치하는 모든 tool_result를 하나의 사용자 메시지에 함께 반환하는 것이 문서화된 패턴이며, 그 이후 코디네이터는 분석 결과를 프롬프트에 명시적으로 포함시켜 편집 서브에이전트를 생성할 수 있다.

### 전반적인 설명

Claude가 stop_reason: "tool_use"를 담은 응답을 반환할 때, 그 응답은 한 번에 여러 개의 tool_use 블록을 담을 수 있다. 여기서 따라오는 중요한 설계 포인트는 API가 실행 순서에 대해 아무런 규정을 두지 않는다는 것이다. API는 요청된 호출들의 배치를 하니스에 넘겨주고 스케줄링은 전적으로 각자의 코드에 맡긴다. 동시에, 순차적으로, 또는 혼합 전략으로 실행할 수 있으며, 올바른 선택은 각 호출의 성격에 따라 달라질 뿐 응답에 블록이 나타나는 순서와는 무관하다. 독립적인 읽기 전용 작업(검색, 분석, 요약)은 어떤 호출도 다른 호출의 입력을 손상시킬 수 없으므로 동시 실행에 이상적인 대상이다.

이 패턴의 나머지 절반은 결과를 어떻게 되돌리는가이다. 모든 tool_use 블록에 대해 하니스는 그 tool_use_id를 참조하는 정확히 하나의 tool_result를 반환해야 하며, 그 tool_result 블록들은 모두 다음 사용자 메시지 하나에 함께 담겨야 한다. 문서는 별도의 결과에 대해 별도의 사용자 메시지를 보내는 것을 명시적으로 안티패턴으로 지목한다. 이는 왕복 횟수를 늘릴 뿐만 아니라, 이후 턴에서 모델이 호출을 배치하지 않도록 학습시킨다.

의존적인 편집 단계가 나중 턴에 속하는 데는 이유가 있다. 서브에이전트는 자신을 생성한 프롬프트에 담긴 내용만 보는 격리된 인스턴스이므로, 편집 서브에이전트는 그 분석 결과가 코디네이터에게 반환되고 코디네이터가 그것을 새로운 위임에 명시적으로 기록한 이후에만 그 결과를 바탕으로 동작할 수 있다. 분석을 직렬화하면 병렬 처리가 제공하는 지연 시간 이점을 낭비하게 되며, 턴당 하나의 호출이든 결과당 하나의 메시지든 결과를 조금씩 흘려주는 것은 처리량과 모델의 배치 행동 모두를 시간이 지남에 따라 저하시킨다.

문서화된 동작은 Parallel tool use와 Subagents in the SDK를 참고하라.

**설명**

### 전반적인 설명

서브에이전트의 설명을 넓히는 것은 유혹적이지만 잘못된 선택이다. 이는 표적화된 수정을 시스템 전체의 손상과 맞바꾸는 것인데, 모호하거나 중복되는 설명이야말로 비슷한 서브에이전트들 사이의 잘못된 라우팅을 일으키는 원인이며, 호출 자체는 여전히 실패할 수 있는 매칭에 의존한다. agents 설정에서의 순서는 라우팅 신호가 전혀 아니므로, 서브에이전트를 앞에 두어도 아무것도 바뀌지 않는다. background 필드는 Claude가 이미 Agent 도구 호출을 발생시킨 이후에 그 호출이 비동기로 실행되는지 동기로 실행되는지만 통제할 뿐, 호출 자체를 발생시키지는 못한다.

자동 호출이 어떻게 작동하는지, 명시적 이름 지정이 어떻게 특정 서브에이전트를 강제하는지, AgentDefinition에서 사용 가능한 필드는 Subagents in the SDK를 참고하라.

**설명**

**D.** Delegate all tasks to subagents so the main conversation stays minimal, since context isolation always outweighs the cost of a fresh subagent start.

**설명**

### 전반적인 설명

이 문제는 확률적 준수를 만들어내는 프롬프트 지시와, 고정된 생명주기 지점에서 실행되어 결정적인 보장을 제공하는 훅 사이의 핵심적인 아키텍처 구분에 달려 있다. CLAUDE.md의 모든 줄은 다른 모든 지시 사항과 모델의 주의를 두고 경쟁하므로, 잘 배치되고 강조된 규칙조차도 간혹 건너뛰어질 수 있다. 규칙이 절대 건너뛰어져서는 안 될 때, 그것은 프로세가 아니라 코드에 속해야 한다.

여기서 Stop 이벤트가 적절한 제어 지점인 이유는 Claude가 턴을 끝내려고 하는 정확한 시점에 발동되기 때문이다. 그 이벤트에 등록된 커맨드 훅은 테스트 스위트를 실행할 수 있고, 테스트가 실패하면 문서화된 차단 신호인 종료 코드 2로 종료할 수 있다. 턴은 거부되고, 훅의 stderr 출력이 컨텍스트로 Claude에게 반환되어, 대개는 별다른 프롬프트 없이도 실패를 읽고 코드를 고치도록 이끈다. 종료 코드의 의미에 유의해야 한다. 오직 코드 2만 차단하며, 종료 0은 정상적으로 계속되고, 대부분의 다른 0이 아닌 코드는 차단하지 않는 오류로 기록될 뿐이다. 그래서 실패 시 1로 종료하는 훅은 아무것도 강제하지 못한 채 조용히 실패하게 된다.

오답들은 모두 강제를 잘못된 쪽에 남겨둔다. CLAUDE.md를 강화하는 것과 스킬을 추가하는 것 모두 규칙을 모델이 해석하는 지시 사항으로 남겨둔다. PostToolUse 훅은 도구 호출이 완료된 후에 실행되므로, 피드백을 컨텍스트에 되돌려줄 수는 있지만 그 호출을 되돌리거나 턴의 종료를 통제할 수는 없다. 프로덕션에 가져가야 할 사고 모델은 이렇다. 훅은 루프를 결정적으로 감시하고 통제하며, 프롬프트는 모델이 무엇을 시도할지를 형성한다. 생명주기 이벤트와 종료 코드 동작은 Claude Code hooks를, 강제가 모델이 아니라 Claude Code 자체에 있어야 하는 이유는 Claude Code permissions를 참고하라.
