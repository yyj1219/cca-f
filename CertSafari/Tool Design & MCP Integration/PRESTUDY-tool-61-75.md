# 사전 학습 노트: 도구 설계와 MCP 통합 (tool 61-75 대비)

이 문서는 해당 범위에서 다루는 개념을 **아무런 배경지식이 없는 상태**에서 읽어도 이해할 수 있도록 처음부터 설명합니다. 크게 다섯 갈래입니다.

1. Claude Code의 코드 탐색 도구들 (Read / Grep / Glob / Bash / Edit)
2. MCP(Model Context Protocol) 서버 설정 — 범위(scope), 환경 변수, 인증
3. MCP 도구의 오류 계약(error contract)과 재시도 의미론
4. 멀티 에이전트(코디네이터 - 서브에이전트) 오류 처리와 에스컬레이션
5. 도구 설명(description) 작성법과 도구 선택 정확도

## 0. 먼저 알아야 할 큰 그림

### 0.1 LLM 에이전트란
Claude Code 같은 **에이전트**는 사람이 말로 요청하면, 스스로 "어떤 도구를 어떤 인자로 호출할지" 판단해 실행하고, 결과를 보고 다음 행동을 정하는 프로그램입니다. 사람이 코드를 짜서 흐름을 고정하는 게 아니라 **모델이 매 턴마다 결정**합니다. 이것이 이 범위 전체의 전제입니다.

여기서 두 가지 결론이 따라옵니다.

- 모델이 판단하려면 **정보가 텍스트로 주어져야** 합니다. 도구 이름, 설명, 오류 메시지가 곧 모델의 유일한 판단 근거입니다.
- 모델의 작업 기억(컨텍스트 윈도우)은 **유한**합니다. 쓸데없는 정보를 넣으면 정말 필요한 정보가 밀려납니다.

### 0.2 컨텍스트 윈도우(Context Window)
모델이 한 번에 "볼 수 있는" 텍스트의 총량입니다. 토큰(token, 대략 단어 조각) 단위로 셉니다. 지금까지의 대화, 읽은 파일 내용, 도구 결과가 전부 여기에 쌓입니다.

한도를 넘으면 오래된 내용이 잘려나가거나 요약되고, 그러면 모델이 앞서 본 것을 "잊습니다". 또한 토큰은 비용이자 지연시간입니다. 그래서 **"필요한 것만, 필요할 때 읽는다"** 가 에이전트 작업의 기본 원칙입니다.

## 1. 코드베이스 탐색 도구

Claude Code가 파일을 다루는 기본 도구는 네 가지입니다. 각각 잘하는 일이 다릅니다.

### 1.1 Glob — 파일 "이름/경로" 찾기
- **무엇인가**: 파일 경로 패턴으로 파일 목록을 얻는 도구입니다. 파일 안을 열어보지 않습니다.
- **왜 있는가**: "이런 이름의 파일들이 어디에 있지?"를 가장 싸게 답하기 위해서입니다. 결과가 경로 목록뿐이라 토큰을 거의 안 씁니다.
- **패턴 문법(글로브 패턴)**
  - `*` : 경로 구분자(`/`)를 제외한 임의의 문자열
  - `**` : 디렉토리 경계를 넘어 재귀적으로 매칭 (하위 폴더 전체)
  - `?` : 임의의 한 글자
  - `{a,b}` : a 또는 b
- **예시**

```
**/*.test.tsx     → 어느 깊이의 폴더든 .test.tsx로 끝나는 파일
**/*.spec.tsx     → .spec.tsx로 끝나는 파일
**/*Test.tsx      → 파일명이 Test.tsx로 끝나는 파일 (예: LoginTest.tsx)
src/**/*.{ts,tsx} → src 아래 모든 ts/tsx
```

- **언제 쓰나**: 명명 규칙이 여러 개로 섞여 있고(예: `.test.tsx`, `.spec.tsx`, `Test.tsx`), 폴더가 깊게 중첩되어 있고, **내용은 볼 필요 없이 경로 목록만** 필요할 때. 패턴이 여러 개면 그냥 여러 번 호출하면 됩니다.
- **한계**: 파일 "안에 무엇이 들었는지"는 전혀 모릅니다. 그건 Grep의 일입니다.

### 1.2 Grep — 파일 "내용" 검색
- **무엇인가**: 정규식(regex)으로 파일 내용을 검색하는 도구입니다. 내부적으로 ripgrep 기반이라 대형 저장소에서도 빠릅니다.
- **주요 옵션**
  - `pattern` : 찾을 정규식
  - `glob` / `type` : 검색 대상 파일을 좁히는 필터 (`*.ts`, `py` 등)
  - `output_mode` : 결과 형태
    - `files_with_matches` (기본): 매치된 **파일 경로만** 반환 — 가장 저렴
    - `content` : 매치된 **줄 자체**를 반환 — 실제 코드를 봐야 할 때
    - `count` : 파일별 **매치 개수**만 반환
  - `-n` : 줄 번호 표시, `-i` : 대소문자 무시
  - `-A` / `-B` / `-C` : 매치 줄의 뒤/앞/양쪽 문맥 줄 수
  - `multiline` : **여러 줄에 걸친 매치 허용** (아래 별도 설명)
- **출력 모드는 "철저함"의 차이가 아니다**: `count`, `content`, `files_with_matches`는 **같은 검색 결과를 다른 형태로 보여줄 뿐**입니다. 모드를 바꾼다고 더 깊게/더 넓게 찾아주지 않습니다. 이 점을 헷갈리면 안 됩니다.

#### 1.2.1 멀티라인(multiline) 모드
기본적으로 grep 계열 도구는 **한 줄씩** 검사합니다. 패턴이 줄바꿈을 넘어가면 절대 매치되지 않습니다.

문제가 되는 전형적인 코드:

```js
throw new Error("insufficient " +
                "permissions for this resource");
```

여기서 `insufficient permissions`는 소스 텍스트상 한 줄에 연속으로 존재하지 않습니다(`" +` 와 줄바꿈, 공백이 끼어 있음). 그래서 단일 라인 패턴으로는 절대 안 잡힙니다.

해결책은 **multiline 모드를 켜는 것**입니다. 이 모드에서는 `.`이 줄바꿈에도 매칭되고, 패턴이 줄 경계를 넘어갈 수 있습니다.

```
pattern:  insufficient[\s"+]*permissions
multiline: true
```

기억할 것: "찾았는데 일부가 안 잡힌다 + 문자열이 여러 줄로 쪼개져 있다" → **도구를 바꾸는 게 아니라 Grep의 multiline을 켠다.** Glob(경로 검색)이나 파일 전체 Read로 바꾸는 것은 문제의 성격과 무관합니다.

### 1.3 Read — 파일 내용 읽기
- **무엇인가**: 특정 파일의 내용을 컨텍스트로 가져옵니다. `offset`/`limit`로 일부 구간만 읽을 수도 있습니다.
- **비용**: 가장 비쌉니다. 파일 전체가 토큰으로 들어옵니다.
- **원칙**: **어디를 읽어야 할지 이미 알 때만** 사용합니다. 탐색용이 아닙니다. 디렉토리를 Read로 지정해서 재귀 목록을 얻는 용도가 아니며(그건 Glob), 저장소 전체를 Read하는 것은 컨텍스트 낭비의 전형입니다.

### 1.4 Bash — 셸 명령
- **무엇인가**: 임의의 셸 명령 실행(빌드, 테스트, git 등).
- **주의**: 파일 검색/읽기/편집에는 **전용 도구가 더 낫습니다**. `find`나 `ls -R`로 목록을 뽑고 하나씩 열어보는 방식은 느리고, 토큰을 쓰고, 결과가 구조화되지 않습니다. Bash는 "전용 도구가 못 하는 일"에 씁니다.

### 1.5 점진적 탐색 전략 (Incremental Exploration)

처음 보는 코드베이스에서 "로그인 요청이 HTTP 라우트 핸들러부터 DB 호출까지 어떻게 흐르는가" 같은 **호출 체인 추적**을 해야 할 때의 표준 절차입니다.

1. **프로젝트 문서 먼저 읽기**: `CLAUDE.md`, `AGENTS.md`, `README.md` 등이 있으면 먼저 읽습니다. 아키텍처 개요, 폴더 구조, 관례가 압축적으로 적혀 있어 **적은 토큰으로 큰 지도**를 얻습니다.
   - `CLAUDE.md`: Claude Code가 세션 시작 시 자동으로 참고하는 프로젝트 지침 파일. 빌드 명령, 코딩 컨벤션, 아키텍처 설명 등을 적어둡니다.
   - `AGENTS.md`: 같은 목적의 도구 중립적 규약 파일.
2. **진입점 찾기**: Grep으로 `login`, `/auth/login`, 라우트 등록 코드 등을 검색해 라우트 핸들러 위치를 특정합니다.
3. **호출 체인 따라가기**: 찾은 파일의 import/require 문을 보고, 다음 계층(컨트롤러 → 서비스 → 리포지토리 → DB)의 파일만 **하나씩 순서대로** 읽습니다.
4. 목표에 도달할 때까지 2-3을 반복합니다.

이 전략의 핵심은 **"넓게 싸게 좁힌 뒤, 좁게 비싸게 읽는다"** 입니다.

반대로 하면 안 되는 것들과 그 이유:
- 저장소 전체/`src` 전체를 미리 Read → 컨텍스트를 다 소진하고, 정작 필요한 정보가 밀려남.
- 파일 크기(단어 수)가 큰 순서로 읽기 → 파일 크기와 관련성은 아무 상관이 없음. 큰 파일이 자동 생성 파일이거나 데이터 파일일 수도 있음.
- 최근 수정 시각 순으로 읽기 → 최근 수정과 "로그인 흐름"은 무관. 최근에 만진 게 CSS일 수도 있음.

이런 접근들은 공통적으로 **근거 없는 가정(heuristic)** 위에 서 있고, 목표와 인과관계가 없습니다.

### 1.6 Edit과 "편집 전 읽기(read-before-edit)" 규칙

- **Edit 도구**: 파일 안의 `old_string`을 `new_string`으로 **정확히 일치하는 문자열 치환**합니다. 정규식이 아니라 **리터럴 문자열 매칭**입니다(그래서 정규식 메타문자 이스케이프 같은 개념이 애초에 적용되지 않습니다).
- **read-before-edit 규칙**: Edit을 호출하려면 그 파일을 **이 세션에서 먼저 Read**해야 합니다. 왜 이런 제약이 있을까요?
  - 모델이 파일 내용을 추측해서 덮어쓰는 사고를 막기 위해서입니다.
  - 그리고 **동시성(concurrency) 제어**를 위해서입니다. 도구는 "내가 읽었을 때의 파일 상태"를 기억해 둡니다.

#### 낙관적 동시성 제어 (Optimistic Concurrency Control)
데이터베이스에서 온 개념입니다. 잠금을 걸지 않고 일단 진행하되, **쓰기 시점에 "내가 읽은 이후로 바뀌었는가"를 검사**합니다. 바뀌었으면 실패시키고 다시 읽게 합니다.

Edit도 같습니다. 시나리오:

1. Claude가 세션 초반에 `config.yaml`을 Read함.
2. 동료가 별도 에디터에서 그 파일을 손으로 수정하고 저장함(디스크 내용 변경).
3. Claude가 예전에 본 문자열을 `old_string`으로 삼아 Edit 호출 → **실패**.

원인은 "파일이 Claude의 마지막 읽기 이후 디스크에서 변경되었다"는 것이고, 정답 복구 절차는 **파일을 다시 Read해서 최신 내용을 확인한 뒤, 갱신된 텍스트를 기준으로 Edit을 재시도**하는 것입니다.

잘못된 대응들:
- `old_string`의 모든 문자를 이스케이프 → Edit은 리터럴 매칭이므로 무의미.
- 파일을 버리고 Write로 처음부터 재생성 → **동료의 수정 사항을 파괴**합니다. 데이터 손실.
- "세션 내 두 번째 Edit은 원래 실패한다"고 믿고 Bash 치환으로 전환 → 사실이 아닌 가정이고, 안전장치를 우회하는 나쁜 습관.

## 2. MCP 서버 설정

### 2.1 MCP란 무엇인가
**Model Context Protocol(MCP)** 은 AI 에이전트가 외부 시스템(GitHub, 데이터베이스, 사내 API 등)에 연결하기 위한 **개방형 표준 프로토콜**입니다.

구조는 이렇습니다.

- **MCP 서버**: 어떤 기능을 도구(tool)로 노출하는 프로그램. 예: GitHub MCP 서버는 `create_issue`, `list_prs` 같은 도구를 제공.
- **MCP 클라이언트**: Claude Code 같은 호스트. 서버에 연결해 도구 목록을 받아오고, 모델이 호출하면 서버에 요청을 보냄.

MCP가 존재하는 이유: 연결 대상마다 제각각의 통합 코드를 짜는 대신, **한 번 표준을 지키면 어떤 에이전트에도 붙는** 구조를 만들기 위해서입니다.

### 2.2 전송 방식(Transport)
- **stdio**: 서버를 로컬 프로세스로 실행하고 표준 입출력으로 통신. 설정에 `command`와 `args`(실행 인자 배열)를 적습니다.
- **HTTP / SSE**: 원격 서버에 네트워크로 연결. 이때 인증 정보는 보통 HTTP **헤더**(`Authorization` 등)로 보냅니다.

stdio 설정 예:

```json
{
  "mcpServers": {
    "my-api": {
      "command": "node",
      "args": ["./server.js", "--region", "${API_REGION:-us-east-1}"],
      "env": { "LOG_LEVEL": "info" }
    }
  }
}
```

HTTP 설정 예:

```json
{
  "mcpServers": {
    "github": {
      "type": "http",
      "url": "https://api.example.com/mcp",
      "headers": { "Authorization": "Bearer ${GITHUB_TOKEN}" }
    }
  }
}
```

### 2.3 설정 범위(Scope)

같은 MCP 서버라도 **어디에 등록하느냐**에 따라 누가, 어디서 쓸 수 있는지가 달라집니다. 네 가지를 구분해야 합니다.

| 범위 | 저장 위치 | 공유 대상 | 적용 프로젝트 |
|---|---|---|---|
| **Local(로컬)** | `~/.claude.json` 안, **해당 프로젝트 경로 아래** | 나만 (커밋 안 됨) | 그 프로젝트 하나만 |
| **Project(프로젝트)** | 저장소 루트의 `.mcp.json` (버전 관리 대상) | 팀 전체 | 그 저장소 |
| **User(사용자)** | `~/.claude.json` 사용자 전역 영역 | 나만 | 내 **모든** 프로젝트 |
| **Enterprise(관리형)** | 조직이 배포하는 관리 설정 | 조직 전체 | 정책으로 강제 |

혼동 포인트를 정리하면:

- **Local과 User는 둘 다 `~/.claude.json`에 들어가서 헷갈립니다.** 차이는 "프로젝트 경로에 묶여 있는가"입니다. Local은 특정 프로젝트 디렉토리 항목 아래 저장되어 그 프로젝트에서만 보이고, User는 전역이라 모든 프로젝트에서 보입니다.
- **Project 범위만 파일이 저장소에 커밋되어 팀과 공유**됩니다.
- Enterprise는 조직 차원의 정책 배포 수단이지, "서버를 한 프로젝트로 한정하는 유일한 방법" 같은 것이 아닙니다.

선택 기준 예:
- 아직 불안정한 실험용 서버를, 나만, 지금 프로토타이핑 중인 그 프로젝트에서만 쓰고 싶다 → **Local**. (팀에 노출 안 되고, 내 다른 프로젝트도 오염 안 됨)
- 팀 전원이 같은 서버를 써야 한다 → **Project**.
- 내가 모든 프로젝트에서 늘 쓰는 개인 도구 → **User**.

### 2.4 환경 변수 확장 (Environment Variable Expansion)

설정 파일에 실제 값을 박아 넣지 않고 **환경 변수 참조**를 쓸 수 있습니다. 셸(POSIX)과 같은 문법입니다.

- `${VAR}` : 환경 변수 `VAR`의 값으로 치환. 없으면 오류가 나거나 빈 값이 됩니다.
- `${VAR:-default}` : `VAR`이 설정되어 있으면 그 값, **설정되어 있지 않거나 비어 있으면 `default` 문자열**로 치환.

핵심 동작 예:

```json
"args": ["--region", "${API_REGION:-us-east-1}"]
```

`API_REGION`이 설정되지 않은 머신에서는 서버가 실제로 받는 값은 **문자열 `us-east-1`** 입니다. 빈 문자열도, 파싱 실패도, `${API_REGION:-us-east-1}`이라는 리터럴 텍스트도 아닙니다. 그게 기본값 문법의 존재 이유입니다.

또 하나: 이 확장은 **`env` 블록 전용이 아닙니다.** `command`, `args`, `url`, `headers` 등 설정 값 전반에 적용됩니다.

### 2.5 시크릿을 커밋하지 않고 팀과 설정 공유하기

전형적 요구사항: "GitHub MCP 서버 설정을 저장소에 체크인해야 하는데, 팀원마다 개인 액세스 토큰(PAT)이 다르고, 실제 시크릿은 절대 커밋되면 안 된다."

정답 패턴:

1. **Project 범위**로 `.mcp.json`에 서버를 등록해 저장소에 커밋한다.
2. 인증 헤더 값에 **환경 변수 참조**를 쓴다: `"Authorization": "Bearer ${GITHUB_TOKEN}"`
3. 각 팀원은 자기 셸 환경(`.zshrc`, `.env`, 시크릿 매니저 등)에 `GITHUB_TOKEN`을 설정한다.
4. 연결 시점에 각자의 로컬 환경 값이 주입된다.

이렇게 하면 저장소에는 **변수 이름만** 들어가고 시크릿은 절대 들어가지 않으며, 팀원은 아무 파일도 손으로 고칠 필요가 없습니다.

피해야 할 안티패턴:
- 리터럴 토큰을 설정 파일에 붙여넣고 커밋 → **시크릿 유출**. 최악입니다. 게다가 한 사람의 토큰을 팀이 공유하면 감사 추적(누가 무엇을 했는가)도 깨집니다.
- `.mcp.json`을 `.gitignore`에 넣기 → "설정을 저장소에 체크인해야 한다"는 요구사항 자체를 포기하는 것. 팀원들이 각자 설정을 재현해야 하고 표류(drift)합니다.
- 각 팀원이 플레이스홀더를 자기 토큰으로 손수 치환 → 수동 작업이 반복되고, 실수로 커밋될 위험이 항상 남습니다.

### 2.6 동적 인증: `headersHelper`

문제 상황: 어떤 사내 MCP 서버는 **연결할 때마다 새로 발급되는 토큰**을 요구합니다. 예를 들어 Kerberos 기반 토큰은 수명이 짧고 매번 갱신해야 하며, OAuth 인가 서버가 개입하지 않습니다.

- **정적 `headers`는 부적합**합니다. 값이 고정이라 만료되면 사람이 파일을 고쳐야 합니다.
- **`oauth` 블록**(`authServerMetadataUrl` 등)은 **OAuth 인가 서버가 존재할 때** 쓰는 것입니다. Kerberos 영역(realm)은 OAuth 메타데이터를 제공하지 않으므로 맞지 않습니다.

해결책이 **`headersHelper`** 입니다.

- **무엇인가**: 서버에 연결할 때마다 Claude Code가 실행하는 **외부 스크립트**를 지정하는 설정 항목.
- **동작**: 스크립트가 실행되어 토큰을 새로 발급받고, **결과 헤더를 JSON으로 stdout에 출력**합니다. Claude Code가 그 JSON을 읽어 요청 헤더로 사용합니다.
- **왜 좋은가**: 토큰 발급 로직(kinit, 사내 SDK, 시크릿 매니저 조회 등)을 스크립트에 캡슐화할 수 있고, **매 연결마다 신선한 값**이 보장되며, 설정 파일에는 시크릿이 남지 않습니다.

개념 예시:

```json
{
  "mcpServers": {
    "internal": {
      "type": "http",
      "url": "https://internal.example.com/mcp",
      "headersHelper": "/usr/local/bin/get-kerberos-headers.sh"
    }
  }
}
```

스크립트가 출력해야 하는 형태:

```json
{"Authorization": "Bearer eyJhbGciOi..."}
```

정리: **정적이면 `headers`, OAuth면 `oauth` 블록, 매번 새로 계산해야 하면 `headersHelper`.**

## 3. MCP 도구의 오류 계약(Error Contract)과 재시도 의미론

### 3.1 도구 결과와 `isError`
MCP 도구 호출 결과에는 성공/실패를 나타내는 `isError` 불리언이 있습니다.

- `isError: false` (또는 없음): 정상 결과.
- `isError: true`: 호출이 실패했음. 이때 `content`의 텍스트 블록에 실패 이유를 담습니다.

중요한 원칙: **도구가 요청된 일을 하지 못했다면 반드시 `isError: true`** 여야 합니다. 필수 인자가 빠져서 아무 일도 못 했는데 "기술적으로는 호출이 반환됐으니 성공"이라고 처리하면, 에이전트는 실패를 성공으로 오인하고 잘못된 데이터 위에서 다음 단계를 진행합니다.

### 3.2 구조화된 오류 필드 (관례적 확장)
`isError`만으로는 "무엇을 해야 하는가"를 알 수 없습니다. 그래서 많은 도구가 **추가 필드**를 함께 반환하는 관례를 씁니다. 대표적으로:

- **`errorCategory`** : 오류의 성격 분류
  - `"validation"` — 요청 자체가 잘못됨 (필수 인자 누락, 형식 오류, 범위 초과 등)
  - `"transient"` — 일시적 장애 (타임아웃, 연결 리셋, 429 rate limit, 503 등)
  - `"permission"` — 권한/인증 부족 (401, 403)
  - `"not_found"` — 대상이 없음 등
- **`isRetryable`** : **동일한 요청을 그대로 다시 보내면 성공할 가능성이 있는가**

`errorCategory`와 `isRetryable`은 MCP 코어 명세가 강제하는 필드가 아니라 도구 설계 관례이지만, 에이전트가 올바른 복구 행동을 고르게 하는 사실상의 표준 패턴입니다.

### 3.3 `isRetryable`의 정확한 의미 — 가장 자주 틀리는 지점

`isRetryable: true`가 뜻하는 것은 **"입력을 하나도 바꾸지 않고 그대로 다시 보내도 성공할 수 있다"** 입니다. "언젠가는 어떻게든 해결될 수 있다"가 아닙니다.

그래서 카테고리별로 값이 정해집니다.

| errorCategory | isRetryable | 이유 / 에이전트가 할 일 |
|---|---|---|
| `validation` | **false** | 요청이 잘못됐다(malformed). 같은 요청은 100번 보내도 100번 실패. **입력을 고쳐서** 새 요청을 보내야 함 |
| `transient` | **true** | 서버/네트워크 쪽 일시 장애. 잠시 기다렸다 같은 요청을 보내면 성공할 수 있음 |
| `permission` | 보통 **false** | 권한이 없다. 재시도가 아니라 권한 획득이나 에스컬레이션이 필요 |

**필수 인자 누락 사례**: `customer_id`가 빠졌다면 이는 `validation` 오류이고 `isRetryable`은 **false**여야 합니다. "에이전트가 나중에 제대로 채워줄 수도 있으니 true"라는 논리는 틀렸습니다. 그건 재시도(retry)가 아니라 **수정 후 재요청(correct and resubmit)** 이고, `isRetryable: true`는 에이전트에게 "그대로 다시 보내라"는 잘못된 신호를 줘서 무의미한 반복 실패를 유발합니다.

카테고리를 `transient`로 바꾸는 것도 답이 아닙니다. 인자 누락은 시간이 지난다고 저절로 낫는 문제가 아니므로, 오류의 성격을 왜곡해 잘못된 대기·재시도 행동을 부릅니다.

### 3.4 Rate limit(429)의 올바른 오류 응답

**429 Too Many Requests**는 서버가 "요청이 너무 잦다"며 잠시 거절하는 상태 코드입니다. 요청 자체는 정상이고, 잠시 후면 성공합니다. 전형적인 **일시적(transient)** 오류입니다.

데이터 웨어하우스가 가끔 429를 던지는 `run_report` 도구라면 이렇게 반환합니다.

```json
{
  "isError": true,
  "errorCategory": "transient",
  "isRetryable": true,
  "content": [{
    "type": "text",
    "text": "Data warehouse is rate-limiting requests (HTTP 429). Retry after a short backoff."
  }]
}
```

이러면 에이전트는 "재시도 가능한 일시 오류"임을 알고, **자신의 유한한 백오프 전략**을 적용합니다.

관련 개념:
- **백오프(backoff)**: 재시도 전에 기다리는 것. **지수 백오프(exponential backoff)** 는 대기 시간을 1s, 2s, 4s, 8s처럼 배로 늘려, 이미 과부하인 서버를 더 때리지 않게 합니다.
- **지터(jitter)**: 대기 시간에 무작위 편차를 더해, 여러 클라이언트가 동시에 재시도하는 쏠림(thundering herd)을 막습니다.
- **유한한 재시도(bounded retry)**: 최대 횟수/최대 총 시간을 정해두고, 넘으면 포기하고 상위로 알립니다. 무한 재시도는 시스템을 멈추게 하는 장애 패턴입니다.

여기서 도구 작성자와 에이전트의 역할 분담이 중요합니다. **도구는 "이건 일시적이고 재시도 가능하다"는 사실만 정확히 알려주고, 얼마나 기다리고 몇 번 시도할지는 에이전트가 결정**합니다. 도구가 무한 대기를 강요하지 않습니다.

잘못된 응답 설계들:
- `permission` + `isRetryable: false` → 원인을 오진해서, 재시도하면 될 일을 포기하게 만듦.
- `validation` + `isRetryable: true` → 자기모순. 게다가 "날짜 범위를 줄이라"는 지시는 429의 실제 원인(속도 제한)과 무관.
- 구조화된 필드 없이 본문에 "try again later"라고만 적기 → 에이전트가 자연어를 해석해 추측해야 하고, 기계적으로 신뢰할 수 없습니다. **기계 판독 가능한 필드**가 있어야 일관된 행동이 나옵니다.

### 3.5 왜 오류 메시지는 구체적이어야 하는가

"모든 실패에 대해 똑같이 `isError: true` + `"Operation failed"` 만 반환하면 도구 작성자 입장에서 인터페이스가 단순하다"는 주장이 있을 수 있습니다. 하지만 이건 **작성자의 편의를 위해 소비자(에이전트)의 능력을 파괴하는** 설계입니다.

에이전트가 실패 후 고를 수 있는 행동은 크게 셋입니다.

1. **재시도(retry)** — 일시적 오류일 때
2. **입력 수정 후 재요청(adjust input)** — 검증 오류일 때
3. **에스컬레이션(escalate)** — 권한 문제 등 스스로 못 푸는 경우, 사람이나 상위 에이전트에게 넘김

동일한 일반 메시지만 오면 이 셋 중 무엇을 골라야 하는지 판단할 **근거가 전혀 없습니다.** 그 결과 에이전트는 아무거나 추측하거나, 무의미하게 반복하거나, 그냥 멈춥니다. 이것이 균일한 오류 메시지에 대한 가장 강력한 아키텍처적 반론입니다.

(참고로, "MCP 명세가 고유 진단 문자열을 요구한다", "모든 `isError: true`에 스택 트레이스를 포함해야 한다", "상수 문자열이 프로토콜 최대 콘텐츠 길이를 초과시킨다" 같은 주장은 프로토콜 사실이 아닙니다. 진짜 문제는 규격 위반이 아니라 **에이전트의 복구 판단 불가**입니다.)

좋은 오류 메시지가 담아야 할 것:
- 무엇이 실패했는가 (어떤 작업/어떤 리소스)
- 왜 실패했는가 (분류 + 구체적 원인)
- 무엇을 하면 되는가 (재시도 가능 여부, 수정해야 할 인자 이름 등)

## 4. 멀티 에이전트: 코디네이터와 서브에이전트

### 4.1 구조
복잡한 작업은 **코디네이터(coordinator, 오케스트레이터)** 가 전체 계획을 세우고, 각 하위 작업을 **서브에이전트(subagent)** 에게 위임하는 형태로 나눕니다.

이 구조의 이점은 **관심사의 분리**와 **컨텍스트 격리**입니다. 서브에이전트가 수십 개 파일을 뒤지며 만든 잡다한 중간 산출물이 코디네이터의 컨텍스트를 오염시키지 않고, 결론만 올라옵니다.

### 4.2 캡슐화(Encapsulation) 원칙 — 무엇을 위로 올릴 것인가

핵심 원칙: **로컬에서 해결된 문제는 위로 보고하지 않는다. 최종 결과만 보고한다.**

예시: 코디네이터가 서브에이전트에게 3단계 데이터 마이그레이션(extract → transform → load, 즉 ETL)을 위임했습니다. load 단계에서 DB 연결 리셋(알려진 일시적 오류)이 두 번 났지만, 서브에이전트 자체 재시도로 **세 번째 시도에서 성공**했습니다.

이때 올바른 보고는 **성공 결과 요약**입니다. 마이그레이션은 완료됐고, 중간의 일시적 실패는 서브에이전트 안에서 이미 해결됐습니다. 코디네이터가 알아야 할 것은 "작업이 끝났다"는 사실입니다.

잘못된 보고들:
- `isError: true`로 실패 보고 → **사실이 아닙니다.** 작업은 성공했습니다. 코디네이터가 불필요하게 롤백하거나 중복 실행할 수 있습니다.
- "자격 증명이 만료된 것 같으니 새 크리덴셜을 달라"고 에스컬레이션 → 원인 오진입니다. 연결 리셋은 인증 실패가 아니고, 애초에 세 번째 시도가 성공한 것이 그 증거입니다.
- load 단계를 빼고 extract/transform만 완료로 보고 → **거짓 보고**입니다. 실제로 완료된 작업을 누락시켜 코디네이터가 잘못된 상태를 갖게 만듭니다.

물론 무조건 침묵하라는 뜻은 아닙니다. 재시도 사실을 **부가 정보로 간략히 덧붙이는 것**은 관측(observability)에 도움이 됩니다. 다만 **최종 상태는 성공**이어야 합니다.

### 4.3 에스컬레이션(Escalation) — 언제 위로 올릴 것인가

에스컬레이션은 **서브에이전트가 자기 권한과 재시도 한도 안에서 더 이상 할 수 있는 게 없을 때** 상위로 문제를 넘기는 행위입니다.

예시: 문서 번역 서브에이전트가 `translate_text` 도구를 호출했는데 연결 타임아웃. 로컬 재시도 정책은 **일시적 오류에 대해 최대 2회 자동 재시도** 후 에스컬레이션. 두 번째 재시도도 타임아웃.

이 시점에서 로컬 재시도 한도가 소진되었으므로, 올바른 행동은 **재시도를 멈추고 코디네이터에게 실패를 전파**하는 것입니다. 그리고 전파할 때는 코디네이터가 판단할 수 있도록 **충분한 정보를 함께** 보냅니다.

- `errorCategory` (여기서는 `transient`)
- 허용된 로컬 시도 전부에서 타임아웃이 지속되었다는 사실
- **어떤 텍스트가 번역되지 않은 채 남았는지** (부분 진행 상태)

세 번째 항목이 중요합니다. 코디네이터가 다른 도구로 우회하거나, 남은 부분만 다시 시도하거나, 사람에게 알릴 수 있으려면 **어디까지 됐는지**를 알아야 합니다.

잘못된 대응들:
- **조작된 결과 반환**: 이전 성공 호출의 캐시 응답을 진짜 번역인 척 조용히 반환 → 절대 안 됩니다. 워크플로 중단을 피하려다 **틀린 데이터를 시스템에 주입**합니다. 이런 오류는 나중에 훨씬 큰 비용으로 발견되고, 에이전트에 대한 신뢰 자체를 무너뜨립니다. "조용히(silently)"라는 단어가 나오면 거의 항상 나쁜 설계입니다.
- **무한 재시도 + 카운터 리셋**: 재시도 한도를 두는 이유(자원 낭비 방지, 장애 조기 감지) 자체를 무효화합니다. 서브에이전트가 영원히 멈춰 있고, 코디네이터는 이유도 모른 채 기다립니다.
- **오류 재분류**: 타임아웃을 권한 실패로 바꿔서 보고 → 코디네이터가 존재하지 않는 접근 제어 문제를 고치려 들게 만듭니다. 반복된 타임아웃은 네트워크/가용성 문제이지 접근 권한 문제가 아닙니다. **관측한 오류의 성격을 그대로 보고하는 것**이 원칙입니다.

### 4.4 정리: 로컬 처리 vs 에스컬레이션 판단표

| 상황 | 서브에이전트의 행동 |
|---|---|
| 일시적 오류, 재시도 한도 내 | 로컬 재시도 |
| 일시적 오류, 재시도로 결국 성공 | **성공 보고** (내부 재시도는 노출 불필요) |
| 일시적 오류, 재시도 한도 소진 | **에스컬레이션** — 카테고리 + 지속 사실 + 부분 진행 상태 포함 |
| 검증 오류 | 입력을 스스로 고칠 수 있으면 수정 후 재요청, 아니면 에스컬레이션 |
| 권한 오류 | 즉시 에스컬레이션 (재시도 무의미) |
| 어떤 경우든 | **거짓/조작된 결과 반환 금지** |

## 5. 도구 설명(Tool Description) 설계

### 5.1 도구 설명이 왜 중요한가
모델은 도구의 소스 코드를 보지 않습니다. 오직 **도구 이름, 설명, 입력 스키마(JSON Schema)** 만 보고 다음 두 가지를 결정합니다.

1. **어떤 도구를 부를 것인가** (도구 선택)
2. **어떤 인자를 넣을 것인가** (인자 생성)

따라서 도구 설명은 문서가 아니라 **프롬프트이자 API 계약**입니다. 설명이 부실하면 모델은 추측하고, 추측은 틀립니다.

### 5.2 좋은 설명이 담아야 할 요소

1. **무슨 일을 하는가** — 한 문장으로 명확히.
2. **입력 형식(input format)** — 각 인자의 정확한 형태. 예: "city 인자는 도시 이름 문자열, 여러 단어면 공백을 그대로 유지 (예: `San Francisco`). 필요 시 `City, Country` 형식."
3. **예시 호출(example query)** — 구체적 예시 하나가 추상적 설명 열 줄보다 강력합니다. 모델은 예시를 그대로 모방합니다.
4. **범위 밖(out of scope)** — 이 도구가 **하지 않는 일**을 명시. 예: "현재 및 예보 날씨만 제공. 과거 기후 기록 조회는 이 도구의 범위가 아님."
5. **다른 도구와의 경계** — 언제 다른 도구를 써야 하는지.
6. **오류/제약 조건** — 지원 지역, 길이 제한 등.

### 5.3 사례 1: 인자 왜곡과 범위 혼동

문제: 설명이 `"Get weather for a location."` 한 줄뿐이다. 결과적으로
- 모델이 여러 단어로 된 도시 이름(`San Francisco`)을 뭉개거나 잘못 변형함 → **입력 형식이 명시되지 않았기 때문**.
- 사용자가 과거 기후 보고서를 원할 때도 이 도구를 부름 → **범위 경계가 명시되지 않았기 때문**.

가장 직접적인 해결책은 **설명을 확장**하는 것입니다: 입력 형식 명시 + 예시 쿼리 포함 + 과거 조회는 범위 밖임을 명시. 세 가지가 각각 위의 두 실패에 정확히 대응합니다.

개선 예:

```
Get current and forecast weather for a location.

Input: `location` is a city name as a plain string. Keep multi-word
names intact with spaces, e.g. "San Francisco". Optionally disambiguate
with "City, Country", e.g. "Paris, France".

Example: location = "San Francisco"

Out of scope: historical climate records or long-term climate averages.
For those, use `get_climate_history` instead.
```

효과 없는 대안들:
- 검증을 전부 런타임 오류 핸들러로 미루기 → 오류는 **호출한 뒤에야** 발생합니다. 사전에 막을 수 있는 실패를 사후 처리로 미루는 것은 왕복(round trip)과 토큰만 늘립니다. 런타임 검증은 필요하지만 **설명을 대체하지 못합니다.**
- 설명을 더 줄이기 → 정보 부족이 원인인데 정보를 더 없앱니다. 정반대 방향.
- 이름을 무작위 고유 문자열로 변경 → 의미 충돌은 사라지겠지만 **의미 자체가 사라져서** 모델이 언제 이 도구를 써야 하는지 전혀 알 수 없게 됩니다. 이름은 의미론적 신호이지 충돌 회피용 ID가 아닙니다.

### 5.4 사례 2: 유사한 도구 간 모호성 제거 (Disambiguation)

문제: `analyze_content`(붙여넣은 텍스트 요약)와 `analyze_document`(업로드된 문서 요약)의 한 줄 설명이 거의 동일하다. 모델이 붙여넣은 웹 기사 텍스트에 대해 자꾸 `analyze_document`를 부른다.

원인: 두 설명의 **의미론적 거리**가 너무 가깝습니다. 모델은 임베딩 공간에서 사실상 구별할 수 없는 두 선택지를 놓고 사실상 동전을 던지고 있습니다.

해결책: **각 도구의 설명을 다시 써서, 기대하는 입력 유형을 명시하고, 다른 도구가 적용되는 경우를 함께 적는다.**

```
analyze_content:
  Summarizes raw text supplied directly in the request (pasted text,
  copied article bodies, chat transcripts). Input is a plain string.
  If the user has uploaded a file or given a document ID, use
  `analyze_document` instead.

analyze_document:
  Summarizes an uploaded document referenced by document ID
  (PDF, DOCX, TXT files). Input is a document identifier, not text.
  If the user pasted the text inline, use `analyze_content` instead.
```

이 패턴을 **상호 참조(cross-reference)** 또는 경계 명시라고 부릅니다. 각 설명이 자기 영역만 말하는 게 아니라 **경계선의 반대편도 가리켜** 주기 때문에, 모델이 어느 쪽인지 즉시 판별할 수 있습니다.

효과 없는 대안들:
- 한쪽에 "더 유능한 옵션"이라는 홍보성 문구를 길게 추가 → 모델을 한쪽으로 편향시킬 뿐, **구별 기준**을 주지 않습니다. 오히려 이미 과잉 선택되는 도구를 더 밀어줍니다.
- 한쪽 도구를 아예 삭제 → 그 도구가 필요한 실제 사용 사례가 처리 불가능해집니다. 문제(모호성)를 기능 상실로 바꾸는 것.
- 샘플링 온도(temperature) 올리기 → 온도는 출력의 무작위성을 조절하는 값입니다. 높이면 선택이 **더 예측 불가능**해집니다. 정확도를 원하는 상황에서 정확히 반대 방향입니다.

### 5.5 도구 설계 일반 원칙 요약

- 이름은 **의미가 드러나게**, 동사_명사 형태로 (`create_issue`, `run_report`).
- 설명에는 **입력 형식 + 예시 + 범위 밖 + 이웃 도구와의 경계**.
- 스키마에 필수/선택, 타입, 열거값, 형식(날짜 등)을 정확히 선언.
- 오류는 **분류 가능하고 행동 지침이 담기게**.
- 비슷한 도구가 둘 이상이면 반드시 상호 배타적 조건을 명시.

## 6. 용어 사전 (Glossary)

**MCP (Model Context Protocol)** — AI 에이전트가 외부 시스템과 도구를 주고받기 위한 개방형 표준 프로토콜.

**MCP Server** — 도구/리소스를 MCP 규격으로 노출하는 프로그램. stdio(로컬 프로세스) 또는 HTTP(원격)로 연결.

**MCP Client / Host** — 서버에 연결해 도구를 사용하는 쪽. Claude Code가 여기 해당.

**stdio transport** — 서버를 로컬 프로세스로 띄우고 표준 입출력으로 통신하는 방식. `command`, `args`로 설정.

**`.mcp.json`** — 저장소 루트에 두는 프로젝트 범위 MCP 설정 파일. 버전 관리 대상이며 팀과 공유됨.

**`~/.claude.json`** — 사용자 홈의 Claude 설정 파일. User 범위 항목과, 프로젝트 경로별 Local 범위 항목이 함께 들어감.

**Local scope (로컬 범위)** — `~/.claude.json` 안의 **특정 프로젝트 경로 아래** 저장. 나에게만, 그 프로젝트에서만 유효. 커밋되지 않음.

**Project scope (프로젝트 범위)** — `.mcp.json`에 저장. 커밋되어 팀 전체가 공유.

**User scope (사용자 범위)** — `~/.claude.json` 전역에 저장. 나에게만, 내 모든 프로젝트에서 유효.

**Enterprise / managed scope** — 조직이 배포·강제하는 관리형 설정.

**Environment variable expansion (환경 변수 확장)** — 설정 값 안의 `${VAR}`를 실제 환경 변수 값으로 치환하는 기능.

**`${VAR:-default}`** — VAR이 미설정/빈 값이면 `default` 문자열을 사용하는 기본값 문법. `args`, `headers`, `url` 등 어디서나 동작.

**PAT (Personal Access Token)** — 개인 액세스 토큰. 사용자별 API 자격 증명. 절대 저장소에 커밋하면 안 됨.

**`headers`** — MCP HTTP 연결 시 보낼 정적 HTTP 헤더 맵.

**`headersHelper`** — 매 연결마다 실행되어 헤더 JSON을 stdout으로 출력하는 외부 스크립트 경로. 짧은 수명의 동적 토큰(예: Kerberos)에 적합.

**`oauth` block / `authServerMetadataUrl`** — OAuth 인가 서버가 존재할 때 인증 흐름을 자동 발견·수행하도록 하는 설정. OAuth 서버가 없는 환경(Kerberos 등)에는 부적합.

**Kerberos** — 티켓 기반의 사내 네트워크 인증 프로토콜. 발급 토큰의 수명이 짧아 매 연결 갱신이 필요.

**`isError`** — MCP 도구 결과에서 실패 여부를 나타내는 불리언. 작업을 수행하지 못했으면 `true`.

**`errorCategory`** — 오류의 성격 분류 필드(관례). `validation`, `transient`, `permission` 등.

**`isRetryable`** — **입력을 바꾸지 않고 동일 요청을 그대로 재시도했을 때 성공 가능성이 있는가**를 나타내는 불리언.

**Validation error (검증 오류)** — 요청 자체가 잘못됨(필수 인자 누락, 형식 오류 등). 요청이 malformed하므로 `isRetryable: false`. 입력을 고쳐 재요청해야 함.

**Transient error (일시적 오류)** — 타임아웃, 연결 리셋, 429 등 시간이 지나면 해소되는 장애. `isRetryable: true`.

**Permission error (권한 오류)** — 인증/인가 부족(401, 403). 재시도로 해결되지 않으며 에스컬레이션 대상.

**HTTP 429 (Too Many Requests)** — 요청 속도 제한. 대표적 일시적 오류.

**Rate limiting (속도 제한)** — 서버가 단위 시간당 요청 수를 제한하는 것.

**Backoff (백오프)** — 재시도 전에 대기하는 것. **Exponential backoff**는 대기 시간을 배로 늘려가는 방식.

**Jitter (지터)** — 백오프 대기 시간에 무작위 편차를 더해 동시 재시도 쏠림을 방지하는 기법.

**Bounded retry (유한 재시도)** — 최대 횟수/시간 한도를 둔 재시도. 무한 재시도는 장애 패턴.

**Error contract (오류 계약)** — 도구가 실패 시 어떤 형태의 정보를 어떤 의미로 반환할지에 대한 약속.

**Coordinator agent (코디네이터)** — 전체 작업을 계획하고 하위 작업을 서브에이전트에 위임하는 상위 에이전트.

**Subagent (서브에이전트)** — 위임받은 하위 작업을 자기 컨텍스트에서 수행하고 결과만 보고하는 에이전트.

**Escalation (에스컬레이션)** — 스스로 해결할 수 없는 문제를 상위 에이전트나 사람에게 넘기는 것. 오류 카테고리, 시도 이력, 부분 진행 상태를 함께 전달해야 함.

**Encapsulation (캡슐화)** — 서브에이전트가 내부에서 해결한 일시적 실패를 상위에 노출하지 않고 최종 결과만 보고하는 원칙.

**Partial progress (부분 진행 상태)** — 실패 시 "어디까지 완료됐는지"에 대한 정보. 에스컬레이션 시 반드시 포함.

**ETL (Extract, Transform, Load)** — 데이터를 추출·변환·적재하는 3단계 데이터 파이프라인.

**Context window (컨텍스트 윈도우)** — 모델이 한 번에 다룰 수 있는 토큰의 총량. 유한하며 비용과 직결.

**Token (토큰)** — 모델이 텍스트를 처리하는 최소 단위. 대략 단어 조각.

**Glob** — 파일 경로 패턴으로 파일 목록만 얻는 도구. 내용은 보지 않음.

**Glob pattern (`**`, `*`, `?`)** — `**`는 하위 디렉토리 재귀, `*`는 경로 구분자 제외 임의 문자열, `?`는 한 글자.

**Grep** — 정규식으로 파일 **내용**을 검색하는 도구(ripgrep 기반).

**`output_mode`** — Grep 결과 형태: `files_with_matches`(경로만), `content`(매치 줄), `count`(개수). 검색 범위나 철저함을 바꾸지 않음.

**Multiline mode (멀티라인 모드)** — Grep이 줄 경계를 넘어 매칭할 수 있게 하는 옵션. `"a " + "b"` 처럼 문자열이 여러 줄로 쪼개진 경우에 필요.

**Read** — 특정 파일 내용을 컨텍스트로 가져오는 도구. 가장 비싸므로 위치를 아는 상태에서만 사용.

**Bash** — 셸 명령 실행 도구. 파일 탐색/편집에는 전용 도구가 우선.

**Edit** — 파일 내 `old_string`을 `new_string`으로 **리터럴 문자열** 치환하는 도구. 정규식이 아님.

**Read-before-edit** — Edit 전에 반드시 해당 파일을 Read해야 하는 안전 규칙.

**Optimistic concurrency control (낙관적 동시성 제어)** — 잠금 없이 진행하되, 쓰기 시점에 "읽은 이후 변경 여부"를 검사해 충돌 시 실패시키는 방식. Edit 실패의 원리.

**`CLAUDE.md` / `AGENTS.md`** — 프로젝트의 아키텍처·규약·명령어를 적어두는 에이전트용 지침 파일. 새 코드베이스 탐색의 첫 진입점.

**Incremental exploration (점진적 탐색)** — 문서 → Grep으로 진입점 특정 → 호출 체인 따라 필요한 파일만 순차 Read하는 저비용 코드 이해 전략.

**Call chain (호출 체인)** — 라우트 핸들러 → 컨트롤러 → 서비스 → 리포지토리 → DB처럼 요청이 거쳐가는 함수/모듈의 연쇄.

**Tool description (도구 설명)** — 모델이 도구 선택과 인자 생성에 사용하는 유일한 근거 텍스트. 입력 형식, 예시, 범위 밖, 이웃 도구와의 경계를 담아야 함.

**Disambiguation (모호성 제거)** — 유사한 도구들의 설명에 기대 입력 유형과 상호 배타적 사용 조건을 명시해 오선택을 막는 기법.

**Out of scope (범위 밖)** — 도구가 처리하지 **않는** 일을 설명에 명시하는 것. 잘못된 도구 호출을 직접 차단.

**Cross-reference (상호 참조)** — 도구 설명에서 "이 경우엔 다른 도구 X를 쓰라"고 가리켜 주는 서술.

**Input schema (입력 스키마)** — 도구 인자의 타입·필수 여부·형식을 선언한 JSON Schema.

**Temperature (샘플링 온도)** — 모델 출력의 무작위성 조절 파라미터. 높이면 다양해지지만 정확도는 떨어짐. 도구 선택 정확도 개선 수단이 아님.

**Fabricated / cached fallback result (조작된 결과)** — 실패를 감추려 가짜나 오래된 캐시 값을 성공인 양 반환하는 것. 금지되는 안티패턴.
