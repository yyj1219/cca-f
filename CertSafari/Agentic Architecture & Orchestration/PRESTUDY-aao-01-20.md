# 사전학습 노트: 에이전틱 아키텍처와 오케스트레이션 (1~20 범위)

이 문서는 Claude Agent SDK, Claude Messages API, Claude Code CLI를 한 번도 다뤄본 적 없는 사람을 대상으로, 관련 개념을 밑바닥부터 설명합니다. 순서는 학습하기 좋은 순서이며, 원문 자료의 순서와는 다릅니다.

---

## 0. 큰 그림: LLM, 도구, 그리고 "에이전트"

### 0.1 LLM은 스스로 아무것도 실행하지 못한다

대규모 언어 모델(LLM, Large Language Model)은 텍스트를 입력받아 텍스트를 출력하는 함수입니다. 파일을 읽거나, 데이터베이스를 지우거나, HTTP 요청을 보내는 능력은 모델 자체에 없습니다. 모델이 할 수 있는 최선은 **"나는 이런 작업을 이런 인자로 하고 싶다"고 말하는 것**뿐입니다.

### 0.2 도구(Tool)와 에이전트(Agent)

- **도구(Tool)**: 모델이 호출을 "요청"할 수 있는, 개발자가 정의한 기능. 이름, 설명, 입력 스키마(JSON Schema)로 정의합니다. 예: `get_customer`, `process_refund`, `web_search`.
- **에이전트(Agent)**: 목표를 받아서, 스스로 어떤 도구를 어떤 순서로 쓸지 판단하며, 결과를 보고 다음 행동을 다시 결정하는 반복 루프를 도는 LLM 시스템.

즉 "에이전트"란 특별한 모델이 아니라, **모델 + 도구 실행 코드 + 반복 루프**의 조합입니다. 이 루프를 **에이전틱 루프(agentic loop)**라고 부릅니다.

### 0.3 계층 구조 이해하기

이 주제 영역에는 세 가지 층위가 나오고, 자꾸 섞여서 헷갈리므로 먼저 구분해 둡시다.

| 층위 | 무엇인가 | 대표 개념 |
|---|---|---|
| **Messages API (저수준)** | Anthropic이 제공하는 HTTP API. 메시지 배열을 보내고 응답을 받습니다. 루프는 내가 직접 짭니다. | `messages`, `role`, `content` 블록, `tool_use`, `tool_result`, `stop_reason` |
| **Claude Agent SDK (중간)** | 루프, 훅, 서브에이전트, 권한 등을 대신 관리해 주는 라이브러리 | 훅(Hooks), 서브에이전트, `AgentDefinition`, `maxTurns` |
| **Claude Code CLI (최상위)** | 터미널에서 쓰는 대화형 도구 | 세션, `--resume`, `/fork`, `/clear`, `/compact`, `.claude/agents` |

## 1. Messages API의 기본 구조

### 1.1 messages 배열과 role

API 요청 본문의 핵심은 `messages` 배열입니다. 각 원소는 `role`과 `content`를 가집니다.

- `role: "user"` — 사람(또는 외부 환경)이 모델에게 주는 입력
- `role: "assistant"` — 모델이 낸 출력
- `system` — 별도 최상위 필드로 주는 전역 지시문. 대화 맨 앞에서 모델의 성격/규칙을 정합니다.

대화는 반드시 user → assistant → user → assistant … 로 **역할이 교대**되어야 합니다.

### 1.2 content는 "블록"의 배열이다

`content`는 그냥 문자열일 수도 있지만, 실제 도구 사용 흐름에서는 **콘텐츠 블록(content block)의 배열**입니다. 블록에는 타입이 있습니다.

- `text` — 일반 텍스트
- `tool_use` — assistant가 "이 도구를 이 인자로 실행해 달라"고 요청하는 블록
- `tool_result` — 도구 실행 결과를 모델에게 되돌려 주는 블록

**중요:** 한 assistant 응답 안에 `text` 블록과 `tool_use` 블록이 **동시에** 들어올 수 있습니다. 모델이 "먼저 고객 정보를 조회하겠습니다"라는 설명 텍스트를 쓰면서 동시에 도구 호출을 요청하는 것이 정상입니다. 이 사실이 뒤에 나오는 종료 조건 이야기의 핵심입니다.

### 1.3 tool_use 블록의 모양

```json
{
  "type": "tool_use",
  "id": "toolu_01A09q90qw90lq917835lq9",
  "name": "get_customer",
  "input": { "customer_id": "C-1024" }
}
```

`id`는 이 호출을 식별하는 값입니다. 결과를 돌려줄 때 이 id로 짝을 맞춥니다.

### 1.4 tool_result는 "새로운 user 메시지" 안에 넣는다

가장 자주 틀리는 부분입니다. 도구를 실행한 뒤 그 결과를 넣는 위치는 다음과 같이 **정해져 있습니다.**

> `tool_use`를 담고 있던 assistant 메시지 **바로 뒤에**, **새로운 `role: "user"` 메시지**를 추가하고, 그 `content` 배열 안에 `tool_result` 블록을 넣는다.

```json
[
  { "role": "user",      "content": "고객 C-1024의 환불을 처리해 줘" },
  { "role": "assistant", "content": [
      { "type": "text", "text": "먼저 고객 정보를 확인하겠습니다." },
      { "type": "tool_use", "id": "toolu_01", "name": "get_customer",
        "input": { "customer_id": "C-1024" } }
  ]},
  { "role": "user", "content": [
      { "type": "tool_result", "tool_use_id": "toolu_01",
        "content": "{\"name\":\"홍길동\",\"verified\":true}" }
  ]},
  { "role": "assistant", "content": [ ... 다음 추론 ... ] }
]
```

왜 하필 `user`일까요? 모델 입장에서 도구 실행은 **자기가 한 일이 아니라 외부 세계가 해 준 일**입니다. 외부 세계에서 들어오는 모든 입력은 `user` 역할로 표현하는 것이 이 API의 규약입니다.

**하지 말아야 할 것들:**

- `tool_use`를 담았던 assistant 메시지 안을 고쳐 쓰거나 대체하기 — assistant 메시지는 모델이 실제로 생성한 기록이므로 조작하면 대화 흐름이 깨집니다.
- HTTP 헤더에 결과를 넣기 — 도구 결과는 요청 **본문(body)**의 `messages` 배열 안에 있어야 합니다. 헤더는 인증/버전 같은 전송 메타데이터용입니다.
- 대화 맨 앞 `system` 메시지에 넣기 — `system`은 전역 규칙용이며, 특정 `tool_use`와 짝지어지지 않습니다.

### 1.5 stop_reason: 모델이 왜 멈췄는가

응답 객체에는 `stop_reason` 필드가 있습니다. 이것이 **턴 종료를 판별하는 공식 신호**입니다.

| 값 | 의미 |
|---|---|
| `"end_turn"` | 모델이 할 말을 마쳤고, 추가 도구 요청이 없음 → 루프를 종료해도 됨 |
| `"tool_use"` | 모델이 도구 실행을 요청했음 → 도구를 실행하고 결과를 넣어 다시 호출해야 함 |
| `"max_tokens"` | 출력 토큰 한도에 걸려 잘림 |
| `"stop_sequence"` | 지정한 정지 문자열이 나옴 |

## 2. 에이전틱 루프 직접 구현하기

### 2.1 기본 골격

```python
messages = [{"role": "user", "content": "이 프로젝트의 중복 코드를 리팩토링해 줘"}]

while True:
    response = client.messages.create(
        model="claude-...",
        system="당신은 리팩토링 에이전트입니다.",
        tools=TOOLS,
        messages=messages,
    )
    messages.append({"role": "assistant", "content": response.content})

    if response.stop_reason == "end_turn":
        break                      # ← 종료의 공식 신호

    # stop_reason == "tool_use" 인 경우
    results = []
    for block in response.content:
        if block.type == "tool_use":
            output = run_my_tool(block.name, block.input)   # 내 코드가 실행
            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": output,
            })
    messages.append({"role": "user", "content": results})   # ← user 역할
```

### 2.2 왜 "텍스트가 있으면 끝"은 틀린 판단인가

"마지막 텍스트 블록이 비어 있지 않으면 끝났다"는 방식은 **부수 효과(side effect)에 의존하는 추론**입니다. 앞서 봤듯 모델은 도구를 요청하면서도 설명 텍스트를 함께 낼 수 있으므로, 텍스트의 유무와 `stop_reason`은 함께 움직이지 않습니다. 텍스트를 기준으로 판단하면 도구를 더 써야 할 시점에 루프가 조기 종료되어 작업이 미완으로 끝납니다.

또한 콘텐츠 블록의 **개수**로도 완료를 판단할 수 없습니다. API는 개수로 완료 여부를 알려주지 않으며, 블록 수는 응답마다 자유롭게 달라집니다.

**교훈:** 명세로 제공되는 신호(`stop_reason`)가 있으면 그것을 쓰고, 관측 가능한 부산물로 상태를 추측하지 마십시오.

### 2.3 Messages API를 직접 쓸 때의 책임 분담

저수준 API를 직접 쓸 때 누가 무엇을 하는지 명확히 정리합시다.

| 주체 | 하는 일 |
|---|---|
| Anthropic API (모델) | 어떤 도구를 어떤 인자로 부를지 **결정하고 JSON으로 요청**만 함 |
| 내 애플리케이션 | 그 요청을 받아 **실제로 도구를 실행**하고, 결과를 `tool_result`로 되돌려 주고, 루프를 계속 돌림 |

즉 API는 절대 클라이언트 측 코드를 대신 실행하지 않습니다. 다음은 모두 존재하지 않는 메커니즘입니다.

- Anthropic 서버가 내 사내 티켓팅 시스템이나 지식베이스 API를 대신 호출해 주는 것
- 응답 생성 도중 Anthropic이 내 웹훅 URL을 동기적으로 콜백해서 도구를 대신 실행해 주는 것
- API가 내 런타임에 정의된 동명의 함수를 원격으로 감지해 자동 바인딩·실행해 주는 것

이 책임을 대신 져 주는 것이 바로 상위 계층의 Agent SDK입니다. 저수준 API를 직접 쓰기로 했다면 루프·재시도·에러 처리 전부가 내 몫입니다.

## 3. 서브에이전트와 멀티 에이전트 구조

### 3.1 서브에이전트란

**서브에이전트(subagent)**는 상위 에이전트가 특정 하위 작업을 맡기기 위해 띄우는 별도의 에이전트입니다. 자체 컨텍스트(대화 기록)를 가지며, 작업이 끝나면 결과 요약을 상위에게 돌려주고 사라집니다.

이렇게 나누는 이유:

- **컨텍스트 격리** — 하위 작업의 수많은 중간 로그가 상위 에이전트의 컨텍스트를 오염시키지 않음
- **단일 책임** — 각 에이전트가 하나의 관심사만 담당해 프롬프트가 짧고 정확해짐
- **병렬 처리 가능** — 독립적인 작업을 동시에 돌릴 수 있음

### 3.2 AgentDefinition과 .claude/agents

서브에이전트는 정의(definition)를 가집니다. 대체로 다음을 담습니다.

- `description` — 이 에이전트를 언제 쓰는지 (상위 에이전트가 선택할 때 참고)
- `prompt` — 이 에이전트의 시스템 프롬프트
- `tools` — 사용 가능한 도구 목록
- `model` — 사용할 모델

정의 방식은 두 가지입니다.

1. **프로그래밍 방식**: SDK 옵션에 `AgentDefinition` 객체로 전달
2. **파일시스템 방식**: 프로젝트의 `.claude/agents/` 디렉터리에 마크다운 파일로 저장 (프론트매터에 메타데이터, 본문에 프롬프트)

`.claude/agents`는 **정의를 저장·공유하는 장소**일 뿐이라는 점을 기억하세요. 이 위치에 둔다고 해서 에이전트끼리 실시간으로 상태를 공유하거나 메시지를 주고받게 되지는 않습니다.

### 3.3 Task 호출과 병렬 실행

상위 에이전트가 서브에이전트를 띄우는 행위는 하나의 도구 호출(흔히 `Task` 도구)로 표현됩니다. 여기서 병렬성의 핵심 규칙이 나옵니다.

> **하나의 assistant 응답(턴) 안에 여러 개의 도구 호출 블록을 넣으면, 런타임이 그것들을 동시에 실행한다.**

반대로 한 턴에 하나씩 호출하고 결과를 기다린 뒤 다음 턴에 또 하나를 호출하면, 구조적으로 **직렬**이 됩니다. 아무리 옵션을 조정해도 이 흐름은 병렬이 되지 않습니다.

```
[직렬] 턴1: Task(A) → 결과 대기 → 턴2: Task(B) → 결과 대기 → 턴3: Task(C)
[병렬] 턴1: Task(A), Task(B), Task(C) 를 한 응답에 함께 발행 → 셋이 동시 실행 → 결과 일괄 수신
```

병렬화를 방해하는 흔한 오해:

- **여러 에이전트를 하나로 합치기** — 동시성이 아니라 그냥 하나의 긴 직렬 작업이 됩니다. 게다가 관심사 분리라는 설계 이점도 잃습니다.
- **세션 저장 비활성화(`persistSession: false`)** — 트랜스크립트를 디스크에 남길지 여부의 설정일 뿐, 호출 흐름의 직렬/병렬과 무관합니다.
- **`maxTurns` 증가** — 각 에이전트가 돌 수 있는 최대 턴 수의 상한일 뿐입니다. 상한을 올린다고 실행이 빨라지거나 겹치지 않습니다.

### 3.4 코디네이터-서브에이전트 (허브 앤 스포크)

가장 기본적인 멀티 에이전트 형태입니다.

```
            ┌──────────────┐
            │ 코디네이터   │  (Hub)
            └──┬───┬───┬───┘
               │   │   │
          ┌────┘   │   └────┐
       [스타일]  [보안]  [커버리지]   (Spokes)
```

특징:

- 통신은 **수직적**입니다. 코디네이터 ↔ 각 서브에이전트만 오갑니다. 스포크끼리는 직접 대화하지 않습니다.
- 서브에이전트 호출은 **일회성(one-shot)**입니다. 작업을 맡기고, 최종 요약만 돌려받습니다.

**허브 앤 스포크의 설계 원칙: 공통 관심사는 허브에 모은다.**

에러 처리, 로깅 포맷, 재시도 정책, 속도 제한 백오프(rate-limit backoff) 같은 **횡단 관심사(cross-cutting concern)**를 각 서브에이전트가 제멋대로 구현하면 시스템 전체가 일관성을 잃습니다. 로그 포맷이 제각각이라 모니터링이 안 되고, 재시도 정책이 달라 어떤 에이전트는 API 한도를 계속 때립니다. 이를 코디네이터로 **중앙화(centralize)**하면 하나의 규칙으로 모든 서브에이전트 통신이 관리됩니다.

잘못된 대안들:

- 재시도와 로깅을 아예 없애기 — 관측 가능성과 복원력을 모두 버리는 것입니다.
- 동일한 로직을 각 서브에이전트 프롬프트에 복사·붙여넣기 — 파편화는 그대로이고 유지보수만 나빠집니다.
- 다른 에이전트를 감시하는 감시자 에이전트를 하나 더 두기 — 오케스트레이션은 원래 허브의 책임인데, 불필요한 계층을 덧붙여 책임을 흐립니다.

### 3.5 Agent Teams (에이전트 팀)

코디네이터-서브에이전트 패턴의 한계는 명확합니다. 일회성이고, 단방향이며, 요약만 오갑니다. 여러 에이전트가 **장기간에 걸쳐 서로 직접 메시지를 주고받으며** 공유 작업 목록을 함께 조율해야 한다면 이 모델로는 부족합니다.

**Agent Teams**는 이런 요구를 위한 패턴입니다.

- **에이전트 간 메시징(inter-agent messaging)**: 피어 투 피어로 직접 주고받음
- **여러 협력 세션의 중앙 관리**: 팀 전체 상태를 한 곳에서 관리

| | 코디네이터-서브에이전트 | Agent Teams |
|---|---|---|
| 통신 방향 | 수직, 단방향(위임→요약) | 수평, 양방향 |
| 지속성 | 일회성 태스크 | 장기 세션에 걸친 지속 협업 |
| 적합 상황 | 독립적 하위 작업 분담 | 상호 조율이 계속 필요한 공동 작업 |

참고로, 서브에이전트에게서 Agent 도구를 뺏는 것(중첩 생성 금지)은 단순한 **제약 설정**이지 협업 기능이 아닙니다. 또 한 에이전트의 `maxTurns`를 늘려 여러 참여자를 흉내 내게 하는 것도 실제 독립 에이전트 간 통신이 아닙니다.

### 3.6 에이전트 사이로 데이터를 넘기는 방법: 구조화가 답이다

멀티 에이전트에서 자주 나오는 문제: 검색 에이전트와 문서 분석 에이전트가 조사한 결과를, 종합(synthesis) 에이전트가 보고서로 쓰는데 **출처가 자꾸 뒤바뀝니다.** 어떤 주장에 엉뚱한 URL이나 페이지 번호가 붙습니다.

원인은 전달 형식입니다. 자유 형식 산문으로 넘기면 본문 내용과 메타데이터(URL, 문서명, 페이지)가 한 덩어리로 섞이고, 모델은 어느 문장이 어느 출처에서 왔는지 문맥으로 "추측"해야 합니다. 추측은 틀립니다.

**해결: 콘텐츠와 메타데이터를 분리한 구조화된 항목으로 넘긴다.**

```json
[
  {
    "claim": "2024년 3분기 이탈률이 12% 감소했다",
    "source_url": "https://example.com/report-q3",
    "document_name": "Q3 Retention Report",
    "page": 14
  },
  {
    "claim": "신규 온보딩 흐름 도입 후 활성화율이 개선되었다",
    "source_url": "https://example.com/blog/onboarding",
    "document_name": null,
    "page": null
  }
]
```

이렇게 하면 문장과 출처가 **자료 구조 수준에서 묶여 있으므로** 모델이 짝을 잃을 여지가 구조적으로 사라집니다.

피해야 할 대안:

- 요약만 넘기고 종합 에이전트가 원본을 다시 가져오게 하기 — 이미 한 일을 반복하는 것이라 비용과 지연만 늘어납니다.
- 채팅체 원문 그대로 복사 — 문구가 정확해도 구조가 없으면 귀속은 여전히 추측입니다.
- 모든 출처의 텍스트를 하나의 연속된 산문으로 합치기 — 출처 경계가 아예 사라져 오귀속이 더 심해집니다.

## 4. 훅(Hooks): 코드 수준의 결정론적 통제

### 4.1 훅이란 무엇이고 왜 필요한가

**훅(hook)**은 에이전트 실행 생애주기의 특정 시점에 자동으로 실행되는 내 코드입니다. 모델이 아니라 런타임이 호출하므로, **모델의 판단과 무관하게 반드시 실행됩니다.**

이것이 훅의 존재 이유입니다. 시스템 프롬프트에 "업무 시간 외에는 삭제하지 마"라고 아무리 강하게 써도, LLM은 **확률적(probabilistic)**으로 동작합니다. 대부분 따르지만 100%는 아닙니다. 긴급해 보이는 문구, 예외적인 표현, 환각 등으로 규칙을 어길 수 있습니다. 훅은 **결정론적(deterministic)**입니다. 조건에 맞는 도구 호출이면 모델이 무슨 생각을 했든 무조건 검사됩니다.

| | 시스템 프롬프트 | 훅 |
|---|---|---|
| 성격 | 확률적 — 준수 **가능성**에 영향 | 결정론적 — 매번 강제 실행 |
| 작동 위치 | 모델의 생성 과정 | 코드 런타임 |
| 보장 수준 | "대체로" | "항상" |
| 적합 용도 | 스타일, 어조, 선호 방침 | 보안, 컴플라이언스, 순서 강제 |

주의할 오해들:

- SDK 런타임이 시스템 프롬프트의 자연어 규칙을 자동으로 권한 검사 코드로 번역해 주지 **않습니다.** 두 방식은 기능적으로 전혀 다릅니다.
- 훅이 `deny`를 반환하면 **실제 도구 실행 자체가 차단됩니다.** 화면 표시만 바뀌고 뒤에서 실행되는 것이 아닙니다.

### 4.2 주요 생애주기 훅

| 훅 | 발화 시점 | 대표 용도 |
|---|---|---|
| `UserPromptSubmit` | 사용자가 프롬프트를 제출한 순간 | 입력 검증, 컨텍스트 주입 |
| `PreToolUse` | 도구가 실행되기 **직전** | 인자 검증·수정, 실행 차단 |
| `PostToolUse` | 도구 실행이 **끝난 후** | 결과 검사, 로깅, 후처리 |
| `SubagentStop` | 서브에이전트가 작업을 마칠 때 | 결과 집계, 완료 감지, 로깅 |
| `Stop` | 메인 에이전트가 턴을 마칠 때 | 최종 검증, 마무리 처리 |
| `Notification` | 권한 요청 등 알림 이벤트 발생 시 | 사용자 알림 전달 |

시점을 헷갈리지 않는 요령: 이름의 `Pre`/`Post`/`Stop`이 그대로 시점입니다. **`PreToolUse`는 실행 전이므로 결과를 미리 볼 수 없고**, `PostToolUse`는 실행 후이므로 실행을 막을 수 없습니다.

### 4.3 PreToolUse: 인자 검증·정규화·차단

`PreToolUse` 훅은 세 가지 일을 할 수 있습니다.

1. **통과(allow)** — 그대로 실행하게 둔다
2. **수정(updatedInput)** — 도구에 전달될 입력을 바꿔서 실행하게 한다
3. **거부(deny)** — 실행 자체를 막고, 사유를 모델에게 알려준다

응답 형태는 대략 다음과 같습니다.

```python
def pre_tool_use(tool_name, tool_input):
    if tool_name != "process_payment":
        return {"permissionDecision": "allow"}

    # 1) 정규화: "$1,250.00" 도 1250.0 도 모두 float 로
    raw = tool_input["amount"]
    amount = float(str(raw).replace("$", "").replace(",", "")) if isinstance(raw, str) else float(raw)

    # 2) 정규화된 값으로 임계값 검사
    if amount > COMPLIANCE_THRESHOLD:
        return {
            "permissionDecision": "deny",
            "permissionDecisionReason": f"금액 {amount}이(가) 컴플라이언스 한도를 초과했습니다.",
        }

    # 3) 통과: 정규화된 입력으로 갱신
    return {
        "permissionDecision": "allow",
        "updatedInput": {**tool_input, "amount": amount},
    }
```

**설계 원칙: 정규화와 그 정규화된 값에 대한 검증은 같은 훅 안에서 한다.**

왜 나누면 안 될까요?

- 정규화는 `PreToolUse`, 검증은 `PostToolUse`로 나누면 — 검증 시점에는 **이미 결제가 실행된 뒤**입니다. 사후 확인은 사전 차단이 아닙니다.
- `PreToolUse` 훅 두 개로 나누면 — 훅 간 실행 순서와 `updatedInput`의 전파 시점에 의존하게 됩니다. 두 번째 훅이 정규화 이전 값을 보게 될 위험이 있으므로, 순서에 의존하지 않는 단일 훅이 더 안전하고 결정론적입니다.

일반화하면: **판단에 필요한 값의 생성과 그 값에 대한 판단은 같은 원자적 단위 안에 두어라.**

### 4.4 하드 게이팅: 호출 순서 강제하기

"환불하기 전에 반드시 고객 신원을 확인하라" 같은 순서 규칙을 100% 보장하려면, 프롬프트가 아니라 **하드 게이트(hard gate)**가 필요합니다.

```python
def pre_tool_use(tool_name, tool_input, session_state):
    if tool_name == "process_refund" and not session_state.get("verified_customer_id"):
        return {
            "permissionDecision": "deny",
            "permissionDecisionReason": "get_customer로 신원 확인을 먼저 수행하세요.",
        }
    return {"permissionDecision": "allow"}
```

핵심 아이디어는 **선행 단계의 성공을 세션 상태에 기록해 두고, 후행 도구의 훅에서 그 상태를 확인**하는 것입니다. 상태가 없으면 거부하고, 거부 사유를 모델에게 알려 주면 모델은 스스로 순서를 바로잡아 다시 시도합니다.

효과 없는 대안들:

- 프롬프트에 "must"를 넣고 두 번 반복하기 — 여전히 확률적입니다.
- 컨텍스트 윈도우 키우기 — 지시를 기억하느냐의 문제가 아니라 준수 보장의 문제입니다.
- 매 티켓마다 순서를 상기시키는 메시지 주입 — 역시 확률 조정일 뿐 하드 차단이 아닙니다.

### 4.5 훅의 예외 처리와 Fail-Closed 원칙

훅은 내 코드이므로 예외를 던질 수 있습니다. 훅이 외부 검증 서비스를 호출하는데 그 서비스가 타임아웃되어 예외가 처리되지 않은 채 밖으로 전파되면, **에이전트 세션 전체가 죽습니다.** 깔끔한 거부 대신 크래시가 나는 것입니다.

두 가지를 함께 지켜야 합니다.

1. **방어적 훅 작성**: 훅 내부에서 예외를 `catch`하여 절대 밖으로 전파시키지 않는다.
2. **Fail-Closed**: 검증을 수행할 수 없는 상태라면 **거부(`deny`)**한다.

```python
def pre_tool_use(tool_name, tool_input):
    if tool_name != "process_refund":
        return {"permissionDecision": "allow"}
    try:
        ok = verification_service.check(tool_input, timeout=5)
    except TimeoutError:
        return {
            "permissionDecision": "deny",
            "permissionDecisionReason": "검증 서비스 장애로 확인할 수 없어 환불을 보류합니다.",
        }
    return {"permissionDecision": "allow" if ok else "deny"}
```

**Fail-Closed vs Fail-Open**

- **Fail-Closed(실패 시 차단)**: 검증 불가 → 거부. 보안·컴플라이언스의 기본값. 가용성은 조금 잃지만 안전성은 지킵니다.
- **Fail-Open(실패 시 허용)**: 검증 불가 → 허용. 서비스 장애 시간 동안 **모든 검증이 우회**됩니다. 공격자에게는 "검증 서비스를 죽이면 게이트가 열린다"는 뜻이 됩니다.

같은 맥락에서 나쁜 대응들:

- 타임아웃을 몇 시간으로 늘리기 — 예외는 안 나지만 에이전트가 무기한 대기(hang)합니다. 빠른 실패 + 명확한 거부가 낫습니다.
- 장애 동안 훅을 아예 제거하기 — 무검증 실행을 허용하는 것으로, 통제를 포기하는 것과 같습니다.

### 4.6 SubagentStop: 병렬 서브에이전트 결과 집계

여러 서브에이전트를 병렬로 띄웠을 때, "각자 정말 끝났는가"와 "각자 무엇을 찾았는가"를 알아야 최종 종합을 할 수 있습니다. 이를 위한 전용 훅이 `SubagentStop`입니다. 각 서브에이전트가 자기 작업을 마치는 시점에 발화하므로, 완료 시점마다 결과를 로깅하거나 공용 저장소에 모을 수 있습니다.

다른 훅이 왜 안 되는지도 시점으로 설명됩니다.

- `Notification` — 권한 요청 같은 알림 이벤트용이며 조사 결과 데이터를 나르지 않습니다.
- `PreToolUse` — 실행 **전**이므로 아직 존재하지 않는 결과를 미리 볼 수 없습니다.
- `UserPromptSubmit` — 최초 프롬프트 제출 시점이므로 아직 서브에이전트가 시작도 하지 않았습니다.

## 5. 작업 분해(Decomposition)와 워크플로우 패턴

에이전트 시스템을 설계할 때 "이 일을 어떻게 쪼갤 것인가"가 핵심 결정입니다. 세 가지 축을 구분해야 합니다.

### 5.1 고정 프롬프트 체인 (Fixed Prompt Chain)

**정의:** 정해진 단계를 정해진 순서로, 앞 단계의 출력이 뒤 단계의 입력이 되도록 이어 붙인 구조.

**적합 조건:**
- 단계 수와 순서가 **사전에 완전히 알려져** 있음
- 데이터에 따라 **분기하지 않음**
- 단계 간에 **순차적 의존성**이 있음

**예:** 신규 고객 온보딩 — 계정 레코드 생성 → 기본 권한 부여 → 환영 메일 발송. 어떤 계정이든 항상 같은 3단계입니다.

**장점:** 예측 가능, 디버깅 쉬움, 오버헤드 적음, 비용 예측 가능.

### 5.2 병렬화 (Parallelization / Fan-out · Fan-in)

**정의:** 서로 의존하지 않는 하위 작업들을 **동시에** 실행하고, 결과를 모아 하나로 합치는 구조.

```
                ┌─→ [분류]     ─┐
입력 ──(fan-out)─┼─→ [감정 분석] ─┼─(fan-in)→ 종합 결과
                └─→ [요약]     ─┘
```

**적합 조건:** 하위 작업들이 **서로의 결과를 필요로 하지 않을 때**.

**예:** 지원 티켓 분류 — 카테고리 분류, 감정 추출, 요약 생성. 셋 중 어느 것도 다른 것의 결과를 기다릴 필요가 없습니다.

**핵심 논거:** 독립적인 작업을 순차 실행하면 지연 시간(latency)만 누적됩니다. 병렬 실행은 전체 소요 시간을 가장 느린 작업 하나의 시간으로 줄입니다.

**중요한 구분:** 고정된 3단계라고 해서 자동으로 "고정 프롬프트 체인"이 되는 것이 아닙니다. 체인은 **순차 의존**이 있을 때의 패턴입니다. 단계가 고정되어 있고 **의존이 없다면** 병렬화가 맞습니다.

**Fan-in의 중요성:** 병렬 실행 후 결과를 각각 따로 내보내면 사용자는 파편화된 답을 받습니다. 반드시 하나로 **종합(synthesis)**해서 일관된 단일 응답을 만들어야 합니다.

**적용 예 — 다중 관심사 요청:** 고객 메시지 하나에 "배송 지연", "쿠폰 미적용", "계정 해지" 세 가지가 섞여 있고 각각 별도 도구가 있다면, 메시지를 세 관심사로 분할 → 세 조사를 동시 실행 → 결과를 하나의 답변으로 종합하는 것이 가장 빠르면서도 일관됩니다.

이런 상황에서 하지 말아야 할 것:
- 고객에게 티켓을 세 개로 나눠 다시 보내 달라고 하기 — 자동화 능력을 포기하고 사용자 경험을 해칩니다.
- 하나만 처리하고 나머지를 무시하기 — 다른 요청도 각각 원인 파악과 조치가 필요합니다.
- 하나 처리하고 답한 뒤 후속 메시지를 기다리기 — 독립 작업을 직렬화해 불필요하게 느려집니다.

### 5.3 적응형 분해 / 동적 오케스트레이션 (Adaptive Decomposition / Dynamic Orchestrator)

**정의:** 다음에 무엇을 할지가 **직전 단계에서 발견한 내용에 따라 실행 중에 결정**되는 구조. 오케스트레이터가 새 하위 작업을 동적으로 생성하고 우선순위를 매깁니다.

**적합 조건:**
- 필요한 단계 수·경로를 **사전에 알 수 없음**
- 탐색적(exploratory) 문제
- 발견 내용이 다음 행동을 결정함

**예 1 — 사기 조사:** 플래그된 계정의 거래 내역을 조회하고, 거기서 발견되는 의심 패턴에 따라 다음에 볼 레코드가 달라집니다.

**예 2 — 장애 원인 분석:** 모호한 알림 메시지만 있고 어느 서비스가 원인인지 모릅니다. 볼 로그·서비스·코드 경로의 수를 미리 정할 수 없습니다. 각 단계에서 나온 단서(오류 코드, 로그 패턴)를 해석해 다음 조사 대상을 만들어 내야 합니다.

이런 상황에서 부적절한 선택들:
- 단일 프롬프트로 즉시 근본 원인을 말하게 하기 — 근거 없는 추측, 즉 환각을 유도합니다.
- 고정된 5단계 체인을 무조건 완주하기 — 상황 변화에 적응하지 못하고, 불필요한 단계를 돌거나 필요한 조사를 놓칩니다.
- "DB → 캐시 → 로드밸런서" 같은 고정 순서 — 원인이 그 목록 밖(서드파티 API, 인증 서비스 등)에 있으면 영원히 찾지 못합니다.

### 5.4 세 패턴 선택 요약

| 조건 | 선택 |
|---|---|
| 단계 고정 + 순차 의존 있음 | 고정 프롬프트 체인 |
| 단계 고정 + 의존 없음 | 병렬화 (fan-out / fan-in) |
| 단계를 사전에 알 수 없음 | 동적 오케스트레이터 / 적응형 분해 |

**핵심 원칙:** 동적 오케스트레이션이 "더 안전한 기본값"이 아닙니다. 예측 가능한 워크플로우에 동적 구조를 쓰면 계획 오버헤드, 비용, 비결정성만 늘어납니다. 반대로 탐색적 문제에 고정 체인을 쓰면 답을 아예 못 찾습니다. **제어 흐름의 성질에 맞는 패턴을 고르는 것**이 설계입니다.

## 6. 에이전트 프롬프트 설계

### 6.1 과잉 명세(Over-specification)의 함정

서브에이전트 프롬프트를 이렇게 쓰는 경우가 흔합니다.

> "1단계: 상위 5개 기사를 검색한다. 2단계: 각각을 연다. 3단계: 게시일을 추출한다. 4단계: 표로 반환한다."

문제가 생깁니다. 가장 유용한 출처에 게시일이 아예 없어도 억지로 표를 만들고, 6개 출처가 더 나은 답을 주는 상황에서도 5개에 갇힙니다. 에이전트가 **환경의 가변성에 적응할 수 없게** 되기 때문입니다.

여기서 단계를 10단계로 더 잘게 쪼개는 것은 상황을 **악화**시킵니다. 명세가 촘촘할수록 예외 상황에 대한 적응력은 더 떨어집니다. 숫자만 5에서 6으로 바꾸거나, "추출한 날짜를 재확인하라"는 단계를 하나 더 붙이는 것도 경직된 구조 자체를 그대로 두므로 근본 해결이 아닙니다.

### 6.2 목표 지향 프롬프팅 (Goal-Oriented Prompting)

대신 **목표(goal)와 품질 기준(quality bar)** 중심으로 씁니다.

> "이 질문에 답하는 데 필요한, 신뢰할 수 있고 관련성 높은 출처를 찾으세요. 각 주장에 대해 검증 가능한 내용만 보고하고, 확인할 수 없는 정보는 그렇다고 표시하세요. 출처가 몇 개여야 하는지는 질문의 성격에 따라 판단하세요."

이렇게 하면 에이전트가 상황에 맞게 5개든 6개든 고르고, 게시일이 없으면 다른 메타데이터로 신뢰도를 설명합니다.

### 6.3 언제 절차를 지시하고 언제 목표를 지시하는가

- **절차를 명시**: 순서가 정말 고정되어 있고, 벗어나면 안 되는 규정이 있는 경우
- **목표를 명시**: 최선의 경로가 상황에 따라 달라지고, 판단이 필요한 경우

다만 **"반드시 지켜져야 하는 규칙"은 프롬프트에 쓰는 것으로 끝내지 말고 훅으로 강제하십시오** (4장 참조). 프롬프트는 방향을 주는 도구이지 보증 장치가 아닙니다.

## 7. Claude Code CLI: 세션과 상태 관리

### 7.1 세션(Session)과 트랜스크립트(Transcript)

CLI에서 대화를 시작하면 **세션**이 만들어지고, 고유한 **세션 ID**가 붙습니다. 그 대화의 전체 기록을 **트랜스크립트(transcript)**라고 합니다.

**가장 중요한 사실: 트랜스크립트는 중앙 서버가 아니라 실행 머신의 로컬 디스크에 저장됩니다.** (일반적으로 `~/.claude/` 아래) 즉 세션 기록은 그 머신에 묶인 파일입니다.

### 7.2 --resume: 이전 세션 이어가기

```bash
claude --resume <session-id>
```

이 명령은 세션 ID에 해당하는 **로컬 트랜스크립트 파일을 찾아 읽어** 대화를 이어갑니다. 파일을 찾지 못하면 이전 기록 없이 새 세션처럼 동작합니다.

### 7.3 재개가 실패하는 두 가지 대표 원인

**(1) 머신이 다르다 — 파일이 그 머신에 없다**

CI 환경에서 자주 겪는 문제입니다. 일회성(ephemeral) 빌드 머신에서 세션을 만들었다가, 다른 워커에서 같은 세션 ID로 `--resume`을 하면 완전히 빈 세션이 나옵니다. 원본 머신의 트랜스크립트 파일이 새 워커로 복사된 적이 없기 때문입니다. 컨테이너·VM이 종료되면 그 디스크는 함께 사라지거나 분리됩니다.

해결하려면 **트랜스크립트 파일이나 세션 상태 아티팩트를 명시적으로 저장·전달**해야 합니다 (CI 아티팩트, 공유 볼륨 등).

**(2) 작업 디렉터리가 다르다**

같은 머신이라도, CLI는 **실행된 작업 디렉터리(working directory)를 기준으로 프로젝트 컨텍스트와 세션 기록을 관리**합니다. 세션 저장소가 프로젝트 경로별로 분리되어 있기 때문에, 다른 디렉터리에서 같은 세션 ID로 `--resume`을 하면 해당 경로 기준 저장소에서 기록을 못 찾아 빈 세션이 됩니다.

세션 ID가 확실히 맞는데도 기억이 없다면, **원래 세션을 시작했던 디렉터리에서 실행했는지 가장 먼저 확인**하십시오.

**재개 실패의 원인이 *아닌* 것들:**

- CI 환경이라 대화형 세션 재개가 금지된다 — 그런 정책은 없습니다.
- 세션 이름이 너무 길어 조회가 실패했다 — 조회 실패는 파일 부재가 원인입니다.
- 재개할 때 준 프롬프트가 원본과 달랐다 — 새 지시를 줘도 이전 기록은 유지되어야 정상입니다.
- 최대 턴 수나 예산 한도 초과로 끝났다 — 한도로 종료돼도 트랜스크립트는 남습니다. 기록이 통째로 없어지지 않습니다.
- 원래 실행자의 도구 권한이 부족했다 — 권한은 세션 기록의 저장·재개와 무관합니다.

### 7.4 fork_session

기존 세션을 **복제해서 새로운 분기 세션을 만드는** 옵션입니다. 원본을 건드리지 않고 갈라져 나가는 기능이며, 머신 간 재개를 막는 기능과는 아무 관련이 없습니다.

### 7.5 대화형 세션의 슬래시 명령어

터미널 세션 안에서 대화 상태를 조작하는 명령들입니다. 이름이 비슷해 헷갈리므로 **무엇이 보존되고 무엇이 사라지는지**로 구분하세요.

| 명령 | 하는 일 | 원본 대화 |
|---|---|---|
| `/fork [name]` | 지금까지의 대화를 그대로 복사한 **분기 세션**을 만들고 그쪽으로 전환 | **그대로 보존됨** |
| `/resume` | 이전에 저장된 기존 세션을 선택해 다시 불러옴 | 현재 세션을 복제하지는 않음 |
| `/clear` | 컨텍스트를 완전히 비우고 처음부터 시작 | **추론 흐름이 사라짐** |
| `/compact` | 대화 기록을 요약으로 압축해 토큰 절약 | 원본 상세 내용이 요약으로 대체됨 |

**활용:** 버그를 조사하다가 "다른 가설도 한번 시험해 보고 싶은데 지금까지의 추론은 잃기 싫다"면 `/fork`가 정확히 그 용도입니다. 복사본에서 자유롭게 탐색하고, 아니면 원본으로 돌아오면 됩니다.

`/clear`나 `/compact`는 **탐색을 분기하는 도구가 아닙니다.** 전자는 맥락을 버리고, 후자는 압축할 뿐 별도의 복사본을 만들지 않습니다. `/resume`도 기존 세션을 다시 여는 것이지 현재 세션을 제자리에서 복제하지 않습니다.

## 8. 자주 나오는 설정 값 정리

| 설정 | 의미 | 하는 일 / 하지 않는 일 |
|---|---|---|
| `maxTurns` | 에이전트가 돌 수 있는 최대 대화 턴 수 상한 | 폭주 방지용 안전장치. **속도를 높이거나 병렬성을 만들지 않음** |
| `persistSession` | 세션 트랜스크립트를 디스크에 저장할지 여부 | 저장 여부만 결정. **호출 흐름의 직렬/병렬과 무관** |
| `fork_session` | 재개 시 원본을 복제해 분기 세션 생성 | 원본 보존용. **머신 간 재개를 막는 기능이 아님** |
| `permissionDecision` | 훅이 반환하는 판정: `allow` / `deny` | `deny`면 실제 도구 실행이 차단됨 |
| `updatedInput` | 훅이 도구 입력을 수정해서 넘길 때 쓰는 필드 | `PreToolUse`에서 정규화된 값을 전달 |
| `stop_reason` | 모델이 왜 멈췄는지를 알려주는 응답 필드 | 루프 종료 판단의 공식 신호 |

## 9. 관통하는 설계 원칙 다섯 가지

1. **명세된 신호를 쓰고, 부산물로 추측하지 마라.** (`stop_reason` vs 텍스트 유무)
2. **반드시 지켜야 하는 것은 코드로 강제하라.** 프롬프트는 확률, 훅은 결정론.
3. **실패할 때는 닫히는 쪽으로 실패하라(Fail-Closed).** 그리고 실패가 세션 전체를 무너뜨리지 않게 하라.
4. **구조가 정확도를 만든다.** 메타데이터와 콘텐츠를 분리하면 모델이 추측할 필요가 없어진다.
5. **제어 흐름의 성질에 맞는 분해 패턴을 골라라.** 고정+의존이면 체인, 고정+독립이면 병렬, 미지수면 동적.

## 10. 용어 사전 (Glossary)

### API / 프로토콜

| 영어 용어 | 설명 |
|---|---|
| **Messages API** | Anthropic이 제공하는 저수준 대화 API. 메시지 배열을 주고받으며, 도구 실행 루프는 개발자가 직접 구현한다. |
| **content block** | 메시지 `content` 배열의 원소. `text`, `tool_use`, `tool_result` 등의 타입을 가진다. |
| **tool_use** | 모델이 "이 도구를 이 인자로 실행해 달라"고 요청하는 콘텐츠 블록. assistant 메시지에 담긴다. |
| **tool_result** | 도구 실행 결과를 모델에게 돌려주는 콘텐츠 블록. 대응하는 `tool_use`가 있던 assistant 메시지 **바로 뒤의 새 user 메시지**에 담는다. |
| **tool_use_id** | `tool_use`와 `tool_result`를 짝지어 주는 식별자. |
| **stop_reason** | 모델이 응답을 멈춘 이유를 알려주는 응답 필드. `end_turn`, `tool_use`, `max_tokens`, `stop_sequence`. |
| **end_turn** | `stop_reason` 값 중 하나. 도구 요청 없이 턴을 마쳤음을 뜻하며, 에이전틱 루프 종료의 표준 신호. |
| **role** | 메시지의 화자 구분. `user`(외부 입력) / `assistant`(모델 출력) / `system`(전역 지시). |
| **system prompt** | 모델의 역할·규칙을 정하는 전역 지시문. 확률적으로 영향을 줄 뿐 강제력은 없다. |
| **direct integration** | 상위 SDK 없이 Messages API를 직접 호출하는 방식. 도구 실행과 루프 관리 책임이 전부 애플리케이션에 있다. |

### 에이전트 / 오케스트레이션

| 영어 용어 | 설명 |
|---|---|
| **agentic loop** | 모델 호출 → 도구 요청 감지 → 도구 실행 → 결과 반환 → 재호출을 종료 신호까지 반복하는 제어 루프. |
| **subagent** | 상위 에이전트가 하위 작업을 위임하는 별도 에이전트. 자체 컨텍스트를 가지며 결과 요약을 돌려준다. |
| **coordinator** | 서브에이전트들을 지휘하는 상위 에이전트. 허브 앤 스포크의 허브. |
| **hub-and-spoke** | 중앙 코디네이터(허브)가 여러 서브에이전트(스포크)와만 통신하는 구조. 공통 관심사를 허브에 중앙화한다. |
| **Agent Teams** | 에이전트끼리 직접 메시지를 주고받고, 여러 협력 세션을 중앙 관리하는 패턴. 장기 협업에 적합. |
| **inter-agent messaging** | 에이전트 간 직접 메시지 교환. 코디네이터를 거치지 않는 수평적 통신. |
| **AgentDefinition** | 서브에이전트의 정의 객체. 설명, 시스템 프롬프트, 사용 가능 도구, 모델 등을 담는다. |
| **.claude/agents** | 서브에이전트 정의를 마크다운 파일로 저장하는 프로젝트 디렉터리. 정의 저장소일 뿐 실시간 상태 공유 기능은 아니다. |
| **Task call** | 서브에이전트를 실행시키는 도구 호출. 한 응답 안에 여러 개를 넣으면 병렬 실행된다. |
| **one-shot subtask** | 한 번 위임하고 최종 요약만 받는 일회성 하위 작업 형태. |
| **cross-cutting concern** | 로깅, 에러 처리, 재시도, 백오프처럼 여러 컴포넌트에 공통으로 걸치는 관심사. 중앙화 대상. |
| **rate-limit backoff** | API 호출 한도에 걸렸을 때 대기 시간을 늘려 가며 재시도하는 전략. |

### 워크플로우 패턴

| 영어 용어 | 설명 |
|---|---|
| **task decomposition** | 큰 작업을 여러 하위 작업으로 쪼개는 설계 활동. |
| **fixed prompt chain** | 정해진 단계를 정해진 순서로 이어 붙인 구조. 단계가 고정되고 앞 출력이 뒤 입력이 되는 순차 의존 상황에 적합. |
| **parallelization** | 서로 독립적인 하위 작업을 동시에 실행하는 패턴. 지연 시간을 크게 줄인다. |
| **fan-out** | 하나의 입력을 여러 독립 하위 작업으로 분배하는 단계. |
| **fan-in** | 병렬 실행된 결과들을 하나로 모아 종합하는 단계. |
| **synthesis** | 여러 출처·에이전트의 결과를 하나의 일관된 산출물로 통합하는 작업(또는 그 역할의 에이전트). |
| **adaptive decomposition** | 앞 단계에서 발견한 내용에 따라 다음 하위 작업이 결정되는 분해 방식. |
| **dynamic orchestrator** | 실행 중에 새 하위 작업을 생성하고 우선순위를 매기는 오케스트레이터. 탐색적 문제에 적합. |
| **over-specification** | 프롬프트에 절차를 지나치게 세밀히 못 박아 환경 변화에 적응하지 못하게 만드는 문제. |
| **goal-oriented prompting** | 절차 대신 목표와 품질 기준을 제시해 에이전트의 판단 여지를 남기는 프롬프트 설계. |
| **quality bar** | 결과가 만족해야 할 품질 기준. 절차를 대체하는 판단 근거로 쓴다. |
| **attribution** | 각 주장이 어느 출처에서 왔는지 정확히 귀속시키는 것. |
| **structured entries** | 콘텐츠와 메타데이터(URL, 문서명, 페이지)를 필드로 분리한 형태의 데이터. 귀속 정확도를 높인다. |

### 훅 / 통제

| 영어 용어 | 설명 |
|---|---|
| **hook** | 에이전트 생애주기의 특정 시점에 런타임이 자동 실행하는 개발자 코드. |
| **PreToolUse** | 도구 실행 직전에 발화하는 훅. 인자 검증·정규화·실행 차단에 쓴다. |
| **PostToolUse** | 도구 실행이 끝난 후 발화하는 훅. 실행을 막을 수는 없다. |
| **SubagentStop** | 서브에이전트가 작업을 마칠 때 발화하는 훅. 완료 감지와 결과 집계에 쓴다. |
| **Stop** | 메인 에이전트가 턴을 마칠 때 발화하는 훅. |
| **UserPromptSubmit** | 사용자가 프롬프트를 제출한 시점에 발화하는 훅. |
| **Notification** | 권한 요청 등 알림 이벤트에 대응하는 훅. 작업 결과 데이터를 나르지 않는다. |
| **permissionDecision** | 훅이 반환하는 판정 값(`allow` / `deny`). `deny`면 도구 실행이 실제로 차단된다. |
| **updatedInput** | `PreToolUse` 훅이 수정된 도구 입력을 전달할 때 쓰는 필드. |
| **deterministic** | 결정론적. 같은 조건이면 항상 같은 결과. 훅·코드 수준 통제의 성질. |
| **probabilistic** | 확률적. 대체로 따르지만 보장은 없음. 프롬프트 기반 통제의 성질. |
| **hard gate** | 조건을 만족하지 못하면 실행을 코드 수준에서 무조건 막는 관문. |
| **fail-closed** | 검증 불가·장애 시 **차단**하는 원칙. 보안·컴플라이언스의 기본값. |
| **fail-open** | 검증 불가·장애 시 **허용**해 버리는 위험한 동작. 장애 중 통제가 우회된다. |
| **normalization** | 형식이 제각각인 입력(`"$1,250.00"` / `1250.0`)을 하나의 표준 타입으로 통일하는 작업. |
| **compliance threshold** | 규정 준수를 위해 넘어서면 안 되는 기준값. |
| **guardrail** | 에이전트가 넘지 못하게 막는 안전 경계. 훅이 대표적 구현 수단. |

### CLI / 세션

| 영어 용어 | 설명 |
|---|---|
| **session** | 하나의 연속된 대화 단위. 고유한 세션 ID를 가진다. |
| **session ID** | 세션 식별자. `--resume`에 넘겨 특정 대화를 되살린다. |
| **transcript** | 세션의 전체 대화 기록. 중앙 서버가 아닌 **실행 머신의 로컬 디스크**에 저장된다. |
| **--resume** | 세션 ID로 이전 대화를 이어가는 CLI 옵션. 로컬 트랜스크립트 파일을 읽는다. |
| **working directory** | CLI가 실행된 디렉터리. 프로젝트 컨텍스트와 세션 저장소의 기준이 되므로, 다르면 재개가 실패한다. |
| **ephemeral build machine** | CI에서 작업마다 새로 만들어지고 끝나면 사라지는 일회성 머신. 디스크가 보존되지 않아 세션 재개가 깨진다. |
| **fork_session** | 재개 시 원본 세션을 복제해 분기 세션을 만드는 옵션. |
| **/fork [name]** | 대화형 세션에서 지금까지의 대화 복사본을 만들고 그쪽으로 전환하는 명령. 원본은 보존된다. |
| **/resume** | 저장된 기존 세션을 골라 다시 불러오는 명령. |
| **/clear** | 현재 컨텍스트를 완전히 비우는 명령. 이전 추론 흐름이 사라진다. |
| **/compact** | 대화 기록을 요약으로 압축해 토큰을 절약하는 명령. 분기를 만들지는 않는다. |
| **persistSession** | 세션 트랜스크립트를 디스크에 남길지 결정하는 설정. |
| **maxTurns** | 에이전트가 수행할 수 있는 최대 대화 턴 수 상한. |
| **context window** | 모델이 한 번에 볼 수 있는 토큰 한계. 지시 준수 보장과는 다른 문제다. |
