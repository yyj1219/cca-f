# 1. 지침 파일: CLAUDE.md와 .claude/rules/

**이 장에서 다루는 것**

- `CLAUDE.md`가 무엇이고 무엇을 담는가
- CLAUDE.md의 위치별 계층(개인/프로젝트/하위 디렉터리/로컬/관리형 정책)과 병합 규칙
- 로딩 규칙: 시작 시 즉시 로드 vs. 온디맨드(지연) 로딩
- `@` 임포트 문법과, 임포트하지 않고 경로만 언급하는 법(백틱)
- AGENTS.md, `claudeMdExcludes`, `/init`, `/memory`
- CLAUDE.md의 한계(토큰 비용, 준수율 하락, 강제력 없음)
- `.claude/` 디렉터리 구조와 `.claude/rules/` 규칙 파일
- YAML 프론트매터와 `paths` — 조건부 로딩의 핵심
- Glob 패턴 문법 전체 (`*`, `**`, `?`, `{a,b}`)와 대표적 실패 유형
- 규칙 로드 순서·충돌 처리, 심볼릭 링크를 통한 규칙 공유
- 디렉터리별 CLAUDE.md vs. 경로 범위 규칙 선택 기준
- 자주 나오는 함정과 잘못된 통념 정리

## 1.1 CLAUDE.md란 무엇인가

`CLAUDE.md`는 **Claude에게 주는 프로젝트 지침서**입니다. 마크다운 평문으로 자연어로 쓰며, Claude Code가 세션을 시작할 때 자동으로 읽어 컨텍스트에 넣습니다. 사람이 신입에게 건네는 "우리 팀 규칙 문서"에 해당합니다.

덕분에 매번 "우리는 pnpm 씁니다", "탭 대신 스페이스입니다"라고 타이핑할 필요가 없어집니다.

전형적으로 담는 내용:

- 빌드/테스트/린트 명령어 (`npm run test:unit`, `pytest -q`, `make test`)
- 커밋 메시지 형식 (예: Conventional Commits)
- 코드 스타일 규칙, 금지 사항
- 아키텍처 설명, 디렉터리 구조
- 자주 쓰는 명령어 모음

```markdown
# 프로젝트 개요
결제 백엔드 서비스. Node 20, TypeScript, PostgreSQL.

# 명령어
- 빌드: `npm run build`
- 테스트: `npm test`
- 린트: `npm run lint`

# 컨벤션
- 커밋 메시지는 Conventional Commits 형식을 따른다.
- 모든 API 핸들러는 zod 스키마로 입력을 검증한다.
- 패키지 매니저는 pnpm만 사용한다. npm/yarn 금지.
- src/legacy/ 는 수정 금지.
- 새 의존성 추가 전 반드시 상의할 것.
```

## 1.2 위치별 계층 구조

`CLAUDE.md`는 한 개가 아니라 **여러 위치에 동시에 존재할 수 있고, 각각 적용 범위가 다릅니다.**

| 위치 | 이름 / 성격 | 적용 범위 | 버전 관리 |
|---|---|---|---|
| `~/.claude/CLAUDE.md` | 개인(글로벌) 지침 | 그 사용자의 **모든** 프로젝트 | 커밋 안 됨 (개인 머신에만 존재) |
| `<프로젝트 루트>/CLAUDE.md` | 프로젝트 지침 | 그 저장소에서 작업하는 **모든 사람** | 보통 git에 커밋 |
| `<하위 디렉터리>/CLAUDE.md` | 서브디렉터리 지침 | 해당 하위 트리 작업 시 | 보통 커밋 |
| `CLAUDE.local.md` | 개인 로컬 오버라이드 | 그 **프로젝트 하나**에서 본인만 | 보통 `.gitignore` |
| 관리형 정책(managed policy) CLAUDE.md | 조직/엔터프라이즈 수준 | IT가 배포, 개인이 편집 불가 | 조직 관리 |
| `.claude/rules/*.md` | 규칙 파일 모음 | (뒤 절 참조) | 커밋하면 공유됨 |

**이들은 서로를 대체하지 않고 병합(merge)됩니다.** 하위 파일이 있다고 해서 상위 파일이 무시되는 일은 없습니다.

> 참고: "Claude가 절대 무시할 수 없는 특별 등급"이 CLAUDE.md 안에 존재하는 것은 아닙니다. managed policy 계층은 조직이 배포·통제하는 파일이라는 의미이지, 모델이 기술적으로 절대 어길 수 없는 오버라이드 계층이라는 뜻이 아닙니다(1.8 참조).

### 개인 글로벌 파일의 함정 — 반드시 알아야 할 사고 시나리오

> `~/.claude/CLAUDE.md`(개인 글로벌 파일)에 적은 규칙은 **그 사람의 머신에만** 있습니다. git으로 공유되지 않습니다.

전형적인 사고 흐름:

- 팀원 A, B, C가 각자 자기 `~/.claude/CLAUDE.md`에 "커밋은 이렇게, 테스트는 이렇게"를 적어 두었다.
- 세 사람 모두 Claude가 규칙을 잘 지키는 것처럼 보인다.
- 저장소 루트의 `CLAUDE.md`는 사실 **빈 파일**이다. 아무도 눈치채지 못한다.
- 신입 D가 저장소를 clone 한다. 저장소 파일은 다 받았지만 A/B/C의 홈 디렉터리 파일은 받을 수 없다.
- D의 Claude는 규칙을 하나도 모른다.

**교훈: 팀 공통 규칙은 반드시 저장소에 커밋되는 프로젝트 `CLAUDE.md`에 적어야 합니다.** 개인 글로벌 파일은 "나만의 취향"(답변 언어, 개인 단축 습관, 편집기 취향)에만 씁니다.

이 시나리오에서 함께 알아둘 사실:

- `CLAUDE.md`는 세션이 시작될 때 **디스크에서 직접 읽습니다.** 머신별 캐시를 수동 재빌드해야 하는 구조가 아닙니다. 파일을 고치면 다음 세션에 반영됩니다.
- git은 확장자에 따라 파일을 골라서 체크아웃하지 않습니다. `.md`만 조용히 빠지는 일은 없습니다.
- 빈 파일은 토큰을 거의 쓰지 않으므로 "토큰 한도 초과로 드롭됐다" 같은 설명도 성립하지 않습니다.

또한 **팀 공용 규칙을 `CLAUDE.local.md`에 복사해 두면** 같은 내용이 두 번 로드되어 컨텍스트만 낭비됩니다. 중복은 이득이 아니라 비용입니다.

## 1.3 로딩 규칙 — 시작 시 로드 vs. 온디맨드 로드

Claude Code를 실행한 디렉터리를 **작업 디렉터리(working directory, cwd)** 라고 합니다.

**세션 시작 시 즉시 로드되는 것**
- 작업 디렉터리의 `CLAUDE.md`
- 그 **상위(ancestor) 경로들**을 루트까지 거슬러 올라가며 발견되는 모든 `CLAUDE.md`

**세션 시작 시 로드되지 않는 것**
- 작업 디렉터리 **하위(subdirectory)** 의 `CLAUDE.md`
  → Claude가 그 하위 디렉터리 안의 파일을 실제로 읽거나 수정할 때 비로소 컨텍스트에 추가됩니다. 이를 **온디맨드 로딩(on-demand loading)** 또는 **지연 로딩(lazy loading)** 이라고 부릅니다.

| 위치 | 로드 시점 | 공유 범위 |
|---|---|---|
| 프로젝트 루트 `CLAUDE.md` | 세션 시작 시 **항상** | Git 커밋 → 팀 전체 |
| 하위 디렉터리 `some/dir/CLAUDE.md` | Claude가 그 디렉터리 **안의 파일을 읽을 때** | Git 커밋 → 팀 전체 |
| `CLAUDE.local.md` | 위와 같으나 개인용 | Git 제외 → 본인만 |
| `~/.claude/CLAUDE.md` | 모든 프로젝트에서 | 본인 기기 전체 |

### 구체적 예시

```
repo/
├── CLAUDE.md                              (A)
└── services/
    └── billing/
        ├── CLAUDE.md                      (B)
        └── reports/
            └── CLAUDE.md                  (C)
```

`services/billing/`에서 Claude Code를 실행했다면:

- **시작 즉시 로드**: A(상위 조상), B(작업 디렉터리) → 둘이 병합되어 적용
- **로드 안 됨**: C. `reports/` 안의 파일을 읽는 순간에야 로드됨

**왜 이렇게 설계했는가?** 거대한 모노레포에는 `CLAUDE.md`가 수십 개 있을 수 있습니다. 전부 미리 로드하면 컨텍스트 윈도우가 지침만으로 가득 차서 정작 코드를 볼 공간이 없어집니다. 필요할 때만 가져오는 것이 컨텍스트 예산을 아끼는 방법입니다.

### 하위 디렉터리 CLAUDE.md — 모노레포의 핵심

**문제 상황:** 모노레포가 `packages/api`, `packages/web`, `packages/shared`로 구성돼 있습니다. api 팀은 자기네 DB 규칙과 테스트 규칙이 있는데, 이걸 루트 `CLAUDE.md`에 넣으면 web 작업 중에도 불필요하게 로드되어 컨텍스트를 낭비합니다.

**해결:** `packages/api/CLAUDE.md`를 만듭니다. 로딩은 두 경로로 자동 성립합니다.

1. **시작 시 로드(at launch)** — Claude를 `packages/api` 디렉터리에서 실행하면 그 디렉터리의 `CLAUDE.md`가 자동 로드됩니다.
2. **온디맨드 로드(on demand)** — 루트에서 시작했더라도, Claude가 `packages/api/` 안의 파일을 읽는 순간 그 디렉터리의 `CLAUDE.md`를 함께 끌어옵니다.

루트 파일을 오염시키지 않고, 중복도 없습니다.

### 자주 오해하는 지점

- 작업 디렉터리 아래 모든 `CLAUDE.md`를 전부 미리 로드하지 **않습니다**.
- 하위 디렉터리 파일이 상위 파일과 결합되지 않는다는 규칙은 **없습니다**(계층 병합이 기본).
- 상위 파일을 쓰기 위해 명시적 import 선언이 필요하지 **않습니다**.

## 1.4 `@` 임포트 문법

`CLAUDE.md` 안에서 `@경로` 를 쓰면, Claude Code가 **그 파일의 내용을 실제로 읽어 컨텍스트에 붙여 넣습니다.** 단순한 텍스트 링크가 아니라 실제 파일 삽입 명령입니다. 이것을 임포트(import)라고 합니다.

```markdown
See @README for project overview and @package.json for available npm commands.
```

이렇게 쓰면 `README`와 `package.json`의 **내용 전체**가 세션에 로드됩니다.

```markdown
# 프로젝트 규칙
@docs/architecture.md
@packages/shared/CONVENTIONS.md
```

**특징**

- 상대 경로(`@docs/style.md`), 홈 경로(`@~/.claude/personal.md`) 모두 사용 가능합니다.
- 임포트된 파일 안에서 또 임포트할 수 있습니다(중첩). 다만 깊이에 제한이 있습니다.
- 로드된 내용은 토큰을 소비합니다. 큰 파일을 무심코 임포트하면 컨텍스트가 낭비됩니다.
- 파일이 **자기 자신을 임포트**하는 것은 순환 참조라 무의미하며 유효하지 않습니다.

**왜 존재하는가(단일 진실 공급원)**: 같은 내용을 두 파일에 복사해 두면 한쪽만 고쳐지는 동기화 문제가 생깁니다. 임포트를 쓰면 공통 내용은 한 파일에만 두고, 도구별 고유 지침만 각자 파일에 덧붙일 수 있습니다.

**심볼릭 링크와의 차이**: 심링크(`CLAUDE.md -> AGENTS.md`)는 두 파일을 완전히 같은 내용으로 묶어버립니다. 즉 "공통 내용 + 추가 내용"이 불가능합니다. 임포트는 "공통 내용을 불러온 뒤 그 아래에 더 쓰기"가 가능하므로 확장성이 있습니다.

### 임포트의 함정 — 조건부 로딩과는 정반대

모노레포에서 루트 `CLAUDE.md`가 하위 패키지 파일들을 임포트하는 패턴이 흔합니다.

```markdown
@packages/web/CLAUDE.md
@packages/admin-dashboard/CLAUDE.md
@packages/legacy-billing/CLAUDE.md
```

편리하지만, 이러면 `packages/web`만 담당하는 사람에게도 **모든 패키지의 내용이 강제 로드**됩니다.

> 루트 `CLAUDE.md`에서 `@packages/api/CLAUDE.md`를 임포트하면 **작업 디렉터리와 무관하게 항상 로드**됩니다. "api에서 작업할 때만"이라는 요구와는 정반대의 결과입니다.

임포트는 "항상 필요한 공통 문서"에 쓰고, "특정 영역에서만 필요한 규칙"은 그 위치에 파일을 두거나(1.3) `paths` 범위 규칙(1.10)을 쓰는 것이 맞습니다. 이 상황이 뒤에 나오는 `claudeMdExcludes`가 필요해지는 배경이기도 합니다.

## 1.5 임포트하지 않고 경로만 "언급"하기 — 백틱

**문제**: 문서에서 "이 파일도 참고하세요" 정도로 **사람에게만** 알려주고 싶은데, `@`를 그냥 쓰면 Claude가 그 파일을 통째로 읽어 토큰을 잡아먹습니다. 오래된 레거시 노트처럼 큰 파일이면 낭비가 큽니다.

**해결: 인라인 코드 스팬(백틱)으로 감쌉니다.**

```markdown
과거 배경은 `@docs/legacy-notes.md` 를 참고하세요. (사람용 안내이며 로드되지 않음)
```

**원리**: Claude Code의 임포트 파서는 **마크다운 코드 스팬(백틱 하나로 감싼 구간)과 펜스드 코드 블록(백틱 세 개로 감싼 구간) 내부를 건너뜁니다.** 그 안의 `@경로`는 실행 지시가 아니라 리터럴 텍스트로 취급됩니다. 동시에 마크다운에서는 정상 렌더링되어 사람 눈에는 잘 보이므로, "사람에게는 보이되 기계는 실행하지 않는다"는 목적을 정확히 만족합니다. 이것이 공식 문서가 안내하는 방식입니다.

**작동하지 않는 방법들 (잘못된 통념)**

| 시도 | 왜 안 되는가 |
|---|---|
| `<!-- @docs/legacy-notes.md -->` (HTML 주석) | 임포트를 막는 공식 보장 방법이 아닐뿐더러, 주석은 렌더링 시 **화면에 안 보입니다.** "사람에게 보여주기"라는 목적 자체가 깨집니다. |
| `@@docs/legacy-notes.md` (`@` 두 번) | Claude Code에 그런 이스케이프 문법은 없습니다. 일부 템플릿 엔진(Blade 등)의 관습이지 여기 문법이 아닙니다. |
| `@ docs/legacy-notes.md` (공백 삽입) | 공식 이스케이프 규칙이 아닙니다. 임포트는 막힐지 몰라도 경로가 깨져 보입니다. |

**정리: 로드하려면 맨 `@경로`, 로드 없이 언급만 하려면 백틱으로 감싼다.**

**일반 원리**: 마크다운 기반 지시 파일에서 "특수 문법을 문자 그대로 보여주고 싶다"면 코드 스팬/코드 블록이 표준 해법입니다.

## 1.6 AGENTS.md — 벤더 중립 지침 파일

`AGENTS.md`는 여러 AI 코딩 도구가 공통으로 읽도록 만들어진 벤더 중립 지침 파일 이름입니다. 한 저장소에서 여러 도구를 섞어 쓸 때, 팀 컨벤션을 AGENTS.md에 모아두고 각 도구의 전용 파일에서 이를 참조하는 구성이 일반적입니다.

```markdown
@AGENTS.md

## Claude 전용 추가 지침
- src/billing/ 아래를 변경할 때는 반드시 플랜 모드를 사용한다.
```

**핵심 정리**: 공통 컨벤션은 `AGENTS.md`에, Claude 전용 규칙은 `CLAUDE.md`에, 그리고 `CLAUDE.md` 첫 줄에서 `@AGENTS.md`로 끌어옵니다.

## 1.7 관련 명령과 설정

### `claudeMdExcludes`

`settings.local.json` 등 설정 파일에서 특정 지침 파일을 **로딩 대상에서 제외**하는 옵션입니다. 예를 들어 상위 디렉터리의 어떤 `CLAUDE.md`가 방해될 때 이를 배제하는 용도입니다.

- 어디까지나 "읽지 않게 만드는" 스위치이며, 진단이나 로깅 기능이 아닙니다.
- `CLAUDE.md` 로딩 예외 처리용이며, **`.claude/rules/*.md` 규칙 파일을 제외하는 공식 수단이 아닙니다.**

### `/init`

프로젝트를 훑어 `CLAUDE.md` 초안을 자동 생성해 주는 슬래시 명령입니다. 신규 프로젝트 세팅용 편의 기능이며, 기존 규칙 파일이 언제 로드되었는지를 검사하는 도구가 **아닙니다.**

### `/memory` — 무엇이 실제로 로드됐는지 확인하기

`/memory`는 **현재 세션에 어떤 메모리/지침 파일이 실제로 로드되어 있는지 보여주고 편집하는 슬래시 명령어**입니다. `CLAUDE.md`, `CLAUDE.local.md`, 규칙 파일 목록과 내용을 확인할 수 있습니다.

경로 범위 규칙을 "강제 활성화"하는 명령은 아닙니다. 경로 범위 규칙은 조건이 충족되면 자동으로 로드됩니다.

**전형적 활용 상황**: 같은 저장소·같은 브랜치인데도 한 사람의 Claude는 "커밋 전 린터 실행" 규칙을 지키고, 다른 사람의 Claude는 그 규칙을 아예 언급조차 하지 않는 경우.

규칙 문구가 모호한지 따지기 **전에**, 그 규칙이 애초에 로드되긴 했는지부터 확인해야 합니다. 두 사람이 각각 `/memory`를 실행해 목록을 비교하면 몇 초 만에 판가름 납니다. 흔한 원인:

- 한쪽의 `CLAUDE.md`가 `.gitignore`에 걸려 있어 애초에 받아지지 않음
- 파일이 서로 다른 디렉터리에 있어 로딩 범위 밖
- 한쪽의 `CLAUDE.local.md`가 프로젝트 규칙을 덮어쓰고 있음
- 실행 위치(작업 디렉터리)가 달라 프로젝트 메모리가 잡히지 않음

무관하거나 우선순위가 낮은 요인들: OS 재부팅은 아무 상관 없습니다(설정 변경은 새 세션이면 반영). git 이력 삭제 후 재클론은 과도하고 느립니다. Claude Code 버전 차이보다 로컬 메모리 로딩 누락일 확률이 훨씬 높으므로 진단 순서상 뒤입니다.

> **일반 원칙: 지시가 안 먹히면 "지시가 나쁜가"보다 "지시가 도착했는가"를 먼저 확인한다.**

## 1.8 CLAUDE.md의 한계 — `.claude/rules/`가 존재하는 이유

`CLAUDE.md`에는 네 가지 근본적 한계가 있습니다.

**1) 항상 로드된다 = 항상 토큰을 먹는다.**
루트 `CLAUDE.md`는 아무도 안 쓰는 날에도 그 내용의 토큰 비용을 냅니다. 실제로는 CSS만 만지는 세션에서도 GraphQL 규칙과 DB 마이그레이션 규칙이 함께 로드됩니다. 드물게 필요한 대용량 참조 문서를 여기 붙여넣으면 매 세션이 비싸집니다. 상시 필요한 정보(빌드 명령, 프로젝트 성격)만 루트에 두는 게 원칙입니다.

**2) 커지면 준수율(adherence)이 떨어진다.**
300~500줄을 넘어가면 개별 지시가 잡음에 묻힙니다. 지침은 많을수록 잘 지켜지는 것이 아니라 **관련성이 높을수록** 잘 지켜집니다. 사람이 유지보수하기도 어려워집니다(어디를 고칠지 찾기 힘들고, 여러 사람이 동시에 수정하면 충돌).

**3) 하위 디렉터리 `CLAUDE.md`는 디렉터리 구조에 종속된다 = 놓치기 쉽다.**
`src/api/tests/CLAUDE.md`에 테스트 규칙을 넣어두면, 나중에 누군가 `e2e/` 디렉터리를 새로 만들고 거기에 테스트를 추가했을 때 그 규칙은 **적용되지 않습니다.** 여러 테스트 디렉터리마다 같은 내용을 복붙하면 중복(duplication) 문제가 생기고, 하나를 고쳐도 나머지는 낡은 상태로 남습니다(드리프트).

**4) 강제력이 없다.**
`CLAUDE.md`는 "컨텍스트"일 뿐입니다. 모델이 그 순간의 추론으로 "이번엔 건너뛰어도 되겠다"고 판단하면 무시될 수 있습니다. 파일에 커밋되어 있다고 해서 기술적 제어와 같은 보장력이 생기지 않습니다. 여러 하위 디렉터리에 반복해 써 넣어도 마찬가지입니다 — **반복은 강제력이 아닙니다.** 반드시 강제되어야 하는 보안 정책은 훅/권한 같은 기술적 수단으로 다뤄야 합니다.

**결론적으로 CLAUDE.md에 담아야 할 것**

- 매 세션 필요한 짧은 핵심 정보 (기술 스택, 기본 컨벤션, 어디에 무엇이 있는지 가리키는 포인터)
- 담지 말아야 할 것: 드물게 쓰는 대용량 참조 문서, 반드시 강제되어야 하는 보안 정책

원하는 것은 **"디렉터리가 아니라 파일 종류를 기준으로, 필요할 때만"** 로드되는 규칙입니다. `.claude/rules/`가 정확히 이걸 제공합니다.

## 1.9 `.claude/` 디렉터리와 규칙 파일

저장소 루트의 `.claude/` 폴더는 Claude Code의 프로젝트 설정 공간입니다.

```
.claude/
  settings.json        # 권한, 환경 변수, 훅 등 프로젝트 설정 (커밋 대상)
  settings.local.json  # 개인 오버라이드 (보통 gitignore)
  rules/               # 규칙 파일 모음
  skills/              # 스킬(재사용 가능한 절차) 모음
  agents/              # 서브에이전트 정의
```

`.claude/rules/`는 지침을 **주제별로 쪼갠 파일들**을 담는 디렉터리입니다. `CLAUDE.md` 하나에 모든 것을 몰아넣는 대신 이렇게 나눕니다.

```
.claude/rules/
├── code-style.md
├── testing.md
├── security.md
├── graphql.md
├── migrations.md
├── css-modules.md
└── deployment.md
```

주제별 파일로 나누면 사람에게는 유지보수성이, 모델에게는 구조화된 컨텍스트가 생깁니다.

**중요: rules는 CLAUDE.md를 대체하지 않습니다.** 둘은 공존합니다. 권장 패턴은 `CLAUDE.md`를 짧은 "프로젝트 포인터"(개요 + 어디를 보라는 안내)로 남기고, 상세 내용을 rules 파일들로 분산하는 것입니다.

```markdown
# 상세 규칙
주제별 상세 규칙은 `.claude/rules/` 아래를 참조.
```

**단, 단순히 500줄을 통째로 `rules/all-conventions.md` 한 파일로 옮기는 것은 아무 문제도 해결하지 못합니다.** 파일 위치만 바뀌었을 뿐 여전히 거대한 단일 덩어리이고, `paths`를 붙이지 않았다면 로딩 동작도 이전과 완전히 동일합니다.

### 사용자 수준 rules — `~/.claude/rules/`

홈 디렉터리의 `~/.claude/rules/`에 둔 규칙은 **그 머신의 모든 프로젝트에 적용**되고, **어떤 프로젝트 저장소에도 커밋되지 않습니다.**

**전형적 용도:** 개인 편집기 취향, 서식 선호(들여쓰기, 따옴표 스타일), "설명은 한국어로" 같은 개인 습관.

**왜 여기인가:**
- 프로젝트 저장소를 오염시키지 않음 (다른 팀원에게 내 취향을 강요하지 않음)
- 모든 프로젝트에 자동 적용 (프로젝트마다 복붙할 필요 없음)

**대비되는 위치들:**
- 프로젝트 안 `.claude/rules/`에 복붙 → 저장소에 커밋되어야 하고, 저장소마다 중복 관리 필요
- `CLAUDE.local.md` → 그 **프로젝트 하나**에만 적용, 전역 적용 수단이 아님
- 관리형 정책 CLAUDE.md → 조직이 통제하는 파일이지 개인 취향용이 아님

## 1.10 YAML 프론트매터와 `paths` — 조건부 로딩의 핵심

각 규칙 파일은 맨 위에 **YAML 프론트매터(frontmatter)** 를 가질 수 있습니다. 프론트매터란 파일 최상단에 `---` 세 줄 사이에 넣는 메타데이터 블록으로, 파일의 "본문"이 아니라 "설정"입니다. 정적 사이트 생성기(Jekyll, Hugo 등)에서 널리 쓰이는 관습을 그대로 차용했습니다.

```markdown
---
description: 컴포넌트 prop 명명 규칙
paths: ["src/components/**/*.tsx"]
---

- prop 이름은 camelCase로 작성한다.
- boolean prop은 is/has 접두사를 사용한다.
```

`paths`는 **이 규칙이 어떤 파일에 적용될지**를 글로브(glob) 패턴의 **배열**로 지정합니다.

### 두 가지 동작 규칙 — 이것이 전부입니다

| `paths` 필드 | 이름 | 로딩 시점 |
|---|---|---|
| **없음(생략)** | 무조건 규칙 (unconditional rule) | **세션 시작 시 즉시** 로드. 조건 없이 항상 적용되는 기본 컨텍스트가 됨 |
| **있음** | 경로 범위 규칙 (path-scoped rule) | Claude가 **그 패턴에 일치하는 파일을 실제로 읽거나 수정할 때만** 동적으로 주입 |

즉 `paths`를 **빼면 항상 적용**, **넣으면 해당 파일 작업 시에만 적용**입니다. 매칭되지 않으면 **토큰을 전혀 쓰지 않습니다.** 이것이 이 기능의 요점 — **필요한 순간에만 등장하는 규칙(just-in-time context)** 입니다.

**왜 이렇게 설계되었는가**: 컨텍스트는 유한한 자원입니다. 저장소에 규칙이 수십 개 있는데 전부 항상 로드되면 토큰이 낭비되고 중요한 지침이 묻힙니다. 실제로 그 영역의 코드를 만질 때만 규칙을 끌어오는 지연 로딩(lazy loading)이 효율적입니다.

### 트리거는 "경로 문자열의 등장"이 아니라 "실제 읽기"

자주 헷갈리는 지점은 "경로가 화면에 보이는 것"과 "파일을 읽는 것"의 차이입니다.

| 상황 | 규칙 로드? |
|---|---|
| `git status`를 Bash로 실행해 `src/api/foo.ts`라는 문자열이 출력에 나타남 | **로드되지 않음** |
| Glob으로 디렉터리 목록을 조회해 `src/api/foo.ts`가 목록에 포함됨 | **로드되지 않음** |
| Read로 `src/api/foo.ts`의 내용을 실제로 열어봄 | **로드됨** |

### 문법상 주의점

- 올바른 키 이름은 **`paths`** 입니다. `include` 같은 다른 이름은 지원되지 않습니다.
- `paths`는 **YAML 배열(list)** 로 써야 합니다. 단일 문자열 형태는 올바른 형식이 아닙니다.

```yaml
# 올바름
paths:
  - "terraform/**/*"

# 올바름 (인라인 배열)
paths: ["terraform/**/*"]

# 잘못됨 (단일 문자열)
paths: "terraform/**/*"

# 잘못됨 (키 이름 오류)
include:
  - "terraform/**/*"
```

### `paths: "**/*"` 는 안티패턴

"모든 파일에 적용하고 싶으니 `**/*`로 스코프하자"는 발상은 잘못된 방향입니다. 모든 파일 읽기마다 규칙을 로드/평가하는 불필요한 부담을 만듭니다. **항상 적용하고 싶으면 `paths`를 아예 쓰지 않으면 됩니다.**

### 스코핑에 대한 오해 정리

- **`paths`는 필수 항목이 아닙니다.** 없어도 파일은 정상 인식되고 로드됩니다.
- `paths`를 생략한다고 해서 `"**/*"` 같은 기본 와일드카드가 붙어 "파일을 열 때까지 대기"하는 방식으로 바뀌는 것이 **아닙니다.** 그냥 시작 시 무조건 로드입니다.
- **파일 이름으로 범위가 추론되지 않습니다.** `src-api-only.md`라고 이름 지어도 Claude Code가 "아하 `src/api`용이구나"라고 해석하지 않습니다. 스코핑은 **오직 `paths` 프론트매터**로만 선언합니다. 파일 이름은 사람이 알아보기 위한 것입니다.
- **규칙 파일을 하위 디렉터리에 넣는다고 자동 스코핑되지 않습니다.** `.claude/rules/`는 프로젝트 루트에 두고 관리하는 것이 표준이며, 위치가 아니라 `paths`가 범위를 결정합니다.
- 규칙 파일의 적용 범위가 `.claude/rules/` 디렉터리 자신으로 한정되는 일은 없습니다.

## 1.11 Glob 패턴 문법

`paths`에 쓰는 패턴은 **Glob**이라는 표준 파일 경로 매칭 문법입니다. 정규표현식이 아니며, 훨씬 단순합니다.

### 1.11.1 기본 기호

| 기호 | 의미 |
|---|---|
| `*` | 0개 이상의 임의 문자. **단, 경로 구분자 `/` 는 넘지 못한다.** 즉 한 단계 디렉터리 안에서만 매칭. |
| `**` (globstar) | 디렉터리 경계를 넘어 **임의의 깊이**까지 재귀 매칭 (0단계 포함) |
| `?` | 임의의 한 글자 |
| `{a,b}` | 중괄호 확장(brace expansion). a 또는 b. `*.{ts,tsx}` = `.ts` 또는 `.tsx` |

### 1.11.2 `*` 와 `**` 의 결정적 차이 — 가장 자주 헷갈리는 부분

```
패턴: src/components/*.tsx

매칭됨:      src/components/Button.tsx
매칭 안 됨:  src/components/forms/Input.tsx     ← * 가 / 를 못 넘음
매칭 안 됨:  src/components/layout/Grid.tsx
```

```
패턴: src/components/**/*.tsx

매칭됨:      src/components/forms/Input.tsx
매칭됨:      src/components/layout/Grid.tsx
매칭됨:      src/components/a/b/c/Deep.tsx
```

**전형적인 사고 흐름**: 처음에 컴포넌트가 `src/components/` 바로 아래 평평하게 있어서 `src/components/*.tsx`로 잘 작동했다 → 리팩터링으로 `forms/`, `layout/` 같은 하위 폴더로 정리했다 → 규칙이 조용히 적용되지 않는다. 해결은 `**` 를 넣는 것 하나뿐입니다.

요구사항에 **"at any subfolder depth(어떤 하위 폴더 깊이에서든)"**, **"anywhere under(~ 아래 어디든)"** 같은 표현이 나오면 반드시 `**`가 필요합니다.

### 1.11.3 접두 경로가 붙으면 범위가 잘린다

패턴은 보통 **저장소 루트를 기준**으로 해석됩니다.

```
src/**/*.test.tsx
```
→ `src/` 로 시작하는 경로만. 프로젝트 루트의 `tests/Button.test.tsx` 는 매칭되지 않습니다.

```
**/*.test.tsx
```
→ 프로젝트 어디에 있든(루트 포함, 임의 깊이) 모든 `.test.tsx`. `src/` 안팎을 가리지 않습니다.

파일들이 여기저기 흩어져 있고(예: `src/components/__tests__/`, `src/pages/tests/`, 소스 옆에 나란히, 루트 `tests/`) 공통점이 확장자뿐이라면 답은 `**/*.확장자` 형태입니다.

실제 경로가 `src/api/...`인데 패턴을 `api/**/*.ts`라고 쓰면, 루트 바로 아래에 `api/` 디렉터리가 없으므로 의도한 파일이 하나도 잡히지 않습니다.

### 1.11.4 폴더 이름으로 매칭하면 놓치는 것들

```
**/__tests__/*.tsx
```
→ 이름이 정확히 `__tests__` 인 폴더 **바로 안**의 `.tsx` 파일만. 확장자가 같아도 다른 폴더(`src/pages/tests/`)나 소스 옆에 놓인 파일은 못 잡습니다.

### 1.11.5 와일드카드 없는 리터럴 경로는 재귀하지 않는다

| 패턴 | 매칭됨 | 매칭 안 됨 |
|---|---|---|
| `src/api` | 정확히 `src/api`라는 **그 항목 하나** | `src/api/users.ts` |

**아주 중요합니다.** 와일드카드 없는 리터럴 문자열 `"src/api"`는 하위 파일들에 재귀적으로 매칭되지 **않습니다.** 하위 전체를 잡으려면 반드시 `src/api/**/*`처럼 명시적으로 와일드카드를 써야 합니다. 글로브는 "디렉터리 이름을 쓰면 알아서 하위 포함"이라는 편의를 제공하지 않습니다.

### 1.11.6 중괄호 확장으로 항목 수 줄이기

```yaml
# 3줄
paths:
  - "src/**/*.ts"
  - "src/**/*.tsx"
  - "lib/**/*.ts"

# 같은 결과, 2줄
paths:
  - "src/**/*.{ts,tsx}"
  - "lib/**/*.ts"
```

"가능한 한 적은 항목으로(as few entries as possible)"라는 요구가 있으면 중괄호 확장을 쓰는 쪽입니다. 반대로 "정확히 이 디렉터리들만"이라는 제약이 있는데 `**/*.ts` 처럼 프로젝트 전체를 잡으면 범위 초과라 요구를 어깁니다.

### 1.11.7 종합 정리 표

| 패턴 | 매칭됨 | 매칭 안 됨 |
|---|---|---|
| `src/api/*.ts` | `src/api/index.ts` | `src/api/routes/user.ts` (한 단계 더 깊음) |
| `src/api/**/*.ts` | `src/api/index.ts`, `src/api/routes/v2/user.ts` | `src/utils/date.ts` |
| `src/api/**/*` | `src/api/users.ts`, `src/api/v2/orders/handler.ts` | `src/web/app.ts` |
| `src/**/*.ts` | `src/api/x.ts`, `src/utils/x.ts` (범위가 너무 넓음) | `lib/x.ts` |
| `**/migrations/**` | `src/db/migrations/001.sql`, `services/billing/migrations/002.sql` | `src/db/models/user.ts` |
| `**/*.test.ts` | `src/a.test.ts`, `packages/x/tests/b.test.ts`, `e2e/c.test.ts` | `src/a.ts` |
| `**/*.test.*` | `a.test.ts`, `a.test.js`, `a.test.py` | `a.spec.ts` |
| `**/*.test.tsx` | 프로젝트 전체, 모든 깊이의 `.test.tsx` | — |
| `src/**/*.test.tsx` | `src/` 아래 모든 깊이만 | 루트 `tests/Button.test.tsx` |
| `src/components/*.test.tsx` | `src/components/` 바로 아래만 | `src/components/forms/X.test.tsx` |
| `**/__tests__/*.tsx` | 이름이 `__tests__`인 폴더 바로 안만 | `src/pages/tests/X.tsx` |
| `terraform/**/*` | `terraform/` 아래 모든 깊이의 모든 파일 | 루트의 `main.tf` |
| `terraform/*` | `terraform/` 바로 아래만 | `terraform/modules/vpc/main.tf` |
| `src/**/*.{ts,tsx}` | `src/` 아래 모든 깊이의 `.ts`와 `.tsx` | `src/a.js` |
| `src/api` | 정확히 `src/api` 항목 하나 | `src/api/users.ts` |

### 1.11.8 요구사항 → 패턴 변환 연습

> "`src/api/` 안의 TypeScript 파일 전부, 아무리 깊이 중첩되어 있어도. 단 `src/utils/`나 `src/components/`는 제외."

→ **`src/api/**/*.ts`**

세 가지 실패 유형을 각각 이해해 두세요.

| 실패 유형 | 잘못된 패턴 | 문제 |
|---|---|---|
| 범위가 너무 넓음 | `src/**/*.ts` | `src/` 아래 전부를 잡아 `utils`, `components`까지 포함 |
| 범위가 너무 좁음 | `src/api/*.ts` | `src/api/` 바로 아래 파일만 잡고 중첩 서브폴더를 놓침 |
| 접두 경로 오류 | `api/**/*.ts` | 루트 기준 `api/`를 찾으므로 `src/api/`와 어긋남 |

### 1.11.9 Glob에 대한 잘못된 통념

- 프로젝트 파일 개수가 일정 수를 넘으면 경로 규칙이 자동으로 꺼진다 → **그런 동작은 없습니다.**
- 맨 앞에 `/`를 붙이지 않아서 실패한다 → **깊이 문제와 무관합니다.**
- `.tsx`를 인식시키려면 중괄호 확장이 필수다 → **아닙니다.** 중괄호는 여러 확장자를 한 번에 쓰고 싶을 때의 편의 문법일 뿐입니다.

## 1.12 대표 활용 시나리오

### 시나리오 A — 디렉터리 기준 스코핑

"`src/api/` 밑에서 작업할 때만 입력 검증과 표준 에러 응답 규칙을 적용하고, 프론트엔드나 인프라 작업 때는 컨텍스트를 차지하지 않게 하라."

`.claude/rules/api-conventions.md`:
```markdown
---
paths: ["src/api/**/*"]
---

# API 컨벤션
- 모든 핸들러는 요청 본문을 스키마로 검증한 뒤 로직을 실행한다.
- 오류 응답은 `{ "error": { "code": ..., "message": ... } }` 형태로 통일한다.
- 인증 토큰은 로그에 남기지 않는다.
```

### 시나리오 B — 파일 유형 기준 스코핑

"테스트 파일이 `src/`, `lib/`, `packages/*/tests/`, `e2e/` 등 여기저기 흩어져 있는데, 디렉터리마다 `CLAUDE.md`를 복붙하지 않고 한 곳에서 관리하고 싶다."

`.claude/rules/testing.md`:
```markdown
---
paths: ["**/*.test.ts"]
---

# 테스트 컨벤션
- 테스트 이름은 `describe`/`it`으로 행동을 서술한다.
- 외부 네트워크 호출은 반드시 목(mock) 처리한다.
- 하나의 `it` 블록에는 하나의 단언만 둔다.
```

디렉터리 구조와 무관하게 파일 이름 패턴으로 걸리므로, 미래에 새 디렉터리가 생겨도 그 안의 `*.test.ts`에 규칙이 자동 적용됩니다. **중복 제거 + 누락 방지**를 동시에 달성합니다.

### 시나리오 C — 비대한 CLAUDE.md 분해

비대한 `CLAUDE.md` 해결법의 정석은 이것입니다.

> 주제별로 규칙 파일을 나누고, **각각에 그 주제와 관련된 파일 패턴을 `paths`로 지정한다.**

```
.claude/rules/graphql.md      → paths: ["src/graphql/**/*.ts"]
.claude/rules/migrations.md   → paths: ["**/migrations/**"]
.claude/rules/css-modules.md  → paths: ["**/*.module.css"]
.claude/rules/terraform.md    → paths: ["terraform/**/*"]
```

GraphQL 리졸버를 만질 때만 GraphQL 규칙이 들어오고, CSS 모듈을 만질 때만 CSS 규칙이 들어옵니다.

> 다시 강조: `paths`를 붙이지 않고 파일만 옮기면, **디스크상의 파일 이름만 바뀌었을 뿐 로딩 동작은 이전과 완전히 동일합니다.** 문제는 해결되지 않습니다.

### 시나리오 D — 모노레포에서 팀별 규칙 격리

모노레포(monorepo)는 여러 패키지/팀 코드를 한 저장소에 모아 둔 구조입니다.

```
packages/
├── team-a/
│   └── .claude/rules/*.md
└── team-b/
    └── .claude/rules/*.md
```

팀 A 엔지니어가 `packages/team-a/`에서만 작업하는데 팀 B의 규칙까지 컨텍스트에 들어오면 낭비이고 혼선입니다.

**올바른 해법은 규칙 파일 자체에 `paths`를 붙여 범위를 좁히는 것**입니다.

```markdown
---
paths: ["packages/team-b/**"]
---
```

이렇게 해 두면 팀 B 규칙은 `packages/team-b/` 하위 파일을 만질 때만 로드됩니다. **규칙이 자기 영역을 스스로 선언하도록 만드는 것**이 모노레포의 정석입니다.

이 목적에 맞지 **않는** 방법들:

- **팀 A 규칙에서 `paths`를 지우는 것**: 팀 A 규칙이 전역으로 바뀔 뿐, 팀 B 규칙의 발견/로딩을 막는 효과는 전혀 없습니다.
- **`claudeMdExcludes`**: `CLAUDE.md` 로딩 예외 처리용 설정이며, `.claude/rules/*.md`를 제외하는 공식 수단이 아닙니다.
- **`autoMemoryEnabled`**: 자동 기억/메모리(`MEMORY.md`) 기능 스위치이며, 외부 디렉터리의 `.claude/rules/` 탐색과는 무관합니다.

## 1.13 로드 순서와 충돌 — 매우 중요

- **로드 순서**: 사용자 레벨(`~/.claude/rules/`)이 프로젝트 레벨(`./.claude/rules/`)보다 **먼저** 로드됩니다.
- **그러나 로드 순서가 충돌의 결정론적 해결을 보장하지 않습니다.**

같은 이름의 `formatting.md`가 개인 레벨과 프로젝트 레벨에 각각 있고, 둘 다 `paths` 없이 무조건 로드되며, 서로 모순되는 내용을 담고 있다면:

- 하나가 다른 하나를 덮어쓰거나 무시하지 **않습니다.** 둘 다 컨텍스트에 들어갑니다.
- "프로젝트가 더 구체적이니 항상 이긴다" 같은 확정 규칙도 **없습니다.**
- Claude는 둘 중 하나를 임의로(arbitrarily) 선택할 수 있습니다.

> **공식적인 권장 대응은 우선순위에 기대는 것이 아니라, 충돌하는 지침 자체를 찾아 제거하는 것입니다.**

**주의**: 이 "충돌 시 비결정론적" 성질은 rules 파일(메모리/컨텍스트)에 대한 이야기입니다. **skills의 이름 충돌은 별개로 명확한 우선순위 규칙이 있습니다.** 둘을 혼동하지 마세요.

## 1.14 심볼릭 링크로 규칙 공유하기

**심볼릭 링크(symlink)란**: 실제 파일이 아니라 "다른 경로를 가리키는 바로가기" 파일입니다. 복사본이 아니라 참조이므로, 원본이 바뀌면 링크를 통해 읽는 내용도 즉시 바뀝니다. 링크를 읽으면 운영체제가 실제 대상 파일로 따라갑니다(이를 resolve, 해제라고 합니다). 유닉스/리눅스/macOS의 기본 파일시스템 기능이고 Windows에도 있습니다.

```bash
# 파일 단위
ln -s /shared/company-rules/security.md .claude/rules/security.md

# 디렉터리 단위
ln -s /shared/company-rules             .claude/rules/org
```

**왜 쓰는가 — 단일 진실 공급원(Single Source of Truth)**: 조직 안 여러 저장소가 **동일한** 코드 리뷰 규칙을 글자 그대로(verbatim) 재사용해야 한다고 합시다. 각 저장소에 물리적으로 복사하면 규칙이 바뀔 때마다 N개 저장소를 모두 고쳐야 하고 금방 어긋납니다. 중앙 폴더 하나를 두고 각 저장소에서 심볼릭 링크로 가리키면, **중앙 파일 하나만 고치면 모두가 자동으로 최신 상태**가 됩니다.

**Claude Code의 동작**

- `.claude/rules/` 는 심볼릭 링크를 **정상적으로 따라갑니다(resolve)**. 조용히 무시하지 않습니다.
- **개별 파일 링크와 디렉터리 전체 링크 모두** 지원됩니다. "디렉터리만 되고 파일 하나는 안 된다" 같은 제약은 없습니다.
- 링크 대상이 같은 git 저장소 안에 있을 필요가 없습니다. 저장소 **바깥의 절대 경로**나 별개의 저장소 폴더를 가리켜도 정상 해제됩니다. **git 서브모듈이어야 한다는 제약도 없습니다.**
- 링크된 항목이 "일반 파일이 아니라서" 조용히 무시되는 일은 없습니다.
- **순환 감지(circular detection)** 가 내장되어 있습니다. A → B → A 처럼 링크가 자기 자신으로 되돌아오는 구조에서도 이미 방문한 경로를 기억해 두었다가 감지하면 멈추므로, 무한 루프에 빠지지 않고 안전하게 종료됩니다.

**따라서 실무에서 확인할 것은 단 하나**: 심볼릭 링크가 지원되는지를 걱정할 게 아니라, **각 저장소의 링크가 의도한 공유 원본을 정확히 가리키고 있는지**를 검증하는 것입니다. 링크가 깨졌거나(대상 경로 없음) 잘못된 경로를 가리키면 규칙이 조용히 빠집니다.

```bash
# 링크 대상 확인
ls -l .claude/rules/
readlink -f .claude/rules/security.md
```

**운영상 주의점**

- Windows에서는 심볼릭 링크 생성에 별도 권한이나 설정(`core.symlinks`, 개발자 모드)이 필요할 수 있습니다. 이는 Claude Code가 아니라 git/OS 차원의 이슈입니다.
- git은 심볼릭 링크를 링크 자체로 저장하지만, 클론된 환경에서는 링크가 가리키는 대상 경로가 존재하지 않을 수 있습니다. 절대 경로와 상대 경로 중 무엇을 쓸지 신중히 결정해야 합니다.
- git 서브모듈은 한 저장소 안에 다른 저장소를 포함시키는 별개의 기능이며, 규칙 공유의 전제 조건이 아닙니다. 심볼릭 링크와 서브모듈은 각각 독립적인 선택지입니다.

## 1.15 디렉터리별 CLAUDE.md vs. 경로 범위 규칙 — 선택 기준

둘 다 "특정 파일에만 지침을 적용한다"는 목적을 갖지만, 적용 방식이 다릅니다.

- **디렉터리별 `CLAUDE.md`**: **위치(location)** 기준. 그 디렉터리 트리 안에 있는 파일에 적용됩니다. 대상이 한 곳에 모여 있을 때 자연스럽습니다.
- **`.claude/rules/` + `paths` 글로브**: **패턴(pattern)** 기준. 저장소 트리 전역(tree-wide)에서 패턴에 맞는 파일이라면 어디에 있든 적용됩니다.

판단 기준은 단순합니다.

> 대상 파일이 **한 디렉터리에 모여 있는가**, 아니면 **여러 무관한 서브시스템에 흩어져 있는가**?

예: 데이터베이스 마이그레이션 파일이 `src/db/migrations/`, `services/billing/migrations/`, `packages/auth/migrations/` 등 서로 무관한 여러 곳에 흩어져 있다고 합시다. `src/db/CLAUDE.md` 하나로는 나머지 두 곳을 덮을 수 없습니다. 이때는 `paths: ["**/migrations/**"]`인 경로 범위 규칙이 정확한 도구입니다.

흩어져 있다고 해서 같은 `CLAUDE.md`를 모든 디렉터리에 수동 복제할 필요는 없습니다. 복제본은 반드시 시간이 지나며 서로 어긋나고(드리프트), 유지보수 부채가 됩니다. 경로 범위 규칙이 재귀 글로브를 지원하므로 복제는 불필요합니다.

### 세 가지 배치 비교

| 방식 | 로드 조건 | 장점 | 단점 |
|---|---|---|---|
| 루트 `CLAUDE.md` | 항상 | 확실히 적용됨 | 무관한 세션에서도 토큰 소모 |
| 하위 `CLAUDE.md` | 그 디렉터리 파일을 읽을 때 | 지역적 맥락 | 구조 종속, 중복, 새 디렉터리 누락 |
| `.claude/rules/*.md` + `paths` | 패턴 일치 파일 작업 시 | 단일 소스, 구조 무관, 조건부 | 패턴을 정확히 써야 함 |

### 상황별 권장 구조

| 상황 | 적합한 구조 |
|---|---|
| 규칙 대상이 한 디렉터리 트리에 모여 있음 | 디렉터리별 `CLAUDE.md` |
| 규칙 대상이 여러 무관한 위치에 흩어져 있음 | `.claude/rules/` + `paths` 글로브 |
| 프로젝트 전체에 항상 적용 | 루트 `CLAUDE.md` 또는 `paths` 없는 규칙 파일 |
| 개인 취향을 모든 프로젝트에 | `~/.claude/CLAUDE.md` 또는 `~/.claude/rules/` |
| 한 프로젝트에서 나만 쓰는 지침 | `CLAUDE.local.md` |
| 여러 저장소가 같은 규칙을 공유 | 중앙 폴더 + `.claude/rules/`에 심볼릭 링크 |
| 여러 AI 도구가 공통 컨벤션 공유 | `AGENTS.md` + `CLAUDE.md`에서 `@AGENTS.md` 임포트 |

> **설계 원칙**: 상시 필요한 소수의 정보는 루트 `CLAUDE.md`(짧은 포인터), 특정 작업 유형에만 필요한 세부 규칙은 `.claude/rules/`로 분리.

## 1.16 함정과 잘못된 통념 총정리

| 통념 / 실수 | 실제 |
|---|---|
| 개인 `~/.claude/CLAUDE.md`에 팀 규칙을 적어도 된다 | git으로 공유되지 않습니다. 신규 팀원은 규칙을 전혀 못 받습니다. |
| 팀 규칙을 `CLAUDE.local.md`에 복사해 두면 안전하다 | 같은 내용이 두 번 로드되어 컨텍스트만 낭비합니다. |
| 하위 `CLAUDE.md`도 세션 시작 시 전부 로드된다 | 아닙니다. 그 하위의 파일을 실제로 읽을 때 온디맨드로 로드됩니다. |
| 하위 파일이 있으면 상위 파일이 무시된다 | 아닙니다. 계층 병합이 기본입니다. |
| 루트에서 `@packages/api/CLAUDE.md`를 임포트하면 조건부 로딩이 된다 | 반대입니다. 작업 디렉터리와 무관하게 항상 로드됩니다. |
| HTML 주석 / `@@` / `@ 공백`으로 임포트를 막을 수 있다 | 공식 방법이 아닙니다. 백틱 코드 스팬이 정답입니다. |
| 500줄 CLAUDE.md를 `rules/all.md` 한 파일로 옮기면 해결된다 | 파일 위치만 바뀝니다. 주제별 분리 + `paths`가 있어야 합니다. |
| `paths`를 생략하면 기본 `**/*`가 붙어 대기한다 | 아닙니다. 시작 시 무조건 로드됩니다. |
| 모든 파일에 적용하려면 `paths: "**/*"`를 쓴다 | 안티패턴입니다. `paths`를 아예 쓰지 않으면 됩니다. |
| `paths`를 단일 문자열로 써도 된다 | YAML 배열이어야 합니다. 키 이름도 반드시 `paths`(`include` 아님). |
| 규칙 파일 이름으로 범위가 추론된다 | 아닙니다. 오직 `paths`만이 범위를 결정합니다. |
| 규칙 파일을 하위 디렉터리에 두면 자동 스코핑된다 | 아닙니다. 위치가 아니라 `paths`가 범위입니다. |
| 경로가 출력 화면에 보이면 규칙이 로드된다 | 아닙니다. 매칭 파일을 **실제로 읽을 때**만 로드됩니다. |
| `src/api` 처럼 쓰면 하위 전체가 잡힌다 | 아닙니다. `src/api/**/*` 처럼 와일드카드가 필요합니다. |
| `*` 가 하위 디렉터리도 넘어간다 | 아닙니다. `/`를 못 넘습니다. `**`가 필요합니다. |
| 파일 개수가 많으면 경로 규칙이 자동으로 꺼진다 | 그런 동작은 없습니다. |
| 패턴 앞에 `/`를 안 붙여서 실패했다 | 깊이 문제와 무관합니다. |
| `.tsx` 매칭에 중괄호 확장이 필수다 | 아닙니다. 여러 확장자를 묶는 편의 문법일 뿐입니다. |
| 사용자 규칙이 먼저 로드되므로 프로젝트 규칙이 이긴다 | 로드 순서가 충돌 해결을 보장하지 않습니다. 충돌 자체를 제거해야 합니다. |
| skills의 이름 충돌도 비결정론적이다 | 아닙니다. skills는 별도의 명확한 우선순위 규칙이 있습니다. |
| `.claude/rules/`는 심링크를 무시한다 | 정상 해제하며, 파일/디렉터리 모두 지원하고 순환도 감지합니다. |
| 심링크 대상은 git 서브모듈이어야 한다 | 아닙니다. 저장소 바깥의 평범한 경로여도 됩니다. |
| `claudeMdExcludes`로 `.claude/rules/*.md`를 뺄 수 있다 | 아닙니다. `CLAUDE.md` 로딩 예외용입니다. |
| `/init`으로 규칙 로딩 이력을 검사한다 | 아닙니다. CLAUDE.md 초안 생성용입니다. 진단은 `/memory`. |
| `/memory`로 경로 범위 규칙을 강제 활성화한다 | 아닙니다. 조건이 맞으면 자동 로드됩니다. `/memory`는 확인/편집용입니다. |
| CLAUDE.md에 적으면 반드시 지켜진다 | 강제력이 없습니다. 컨텍스트일 뿐이며 반복도 강제력이 아닙니다. |
| 규칙이 안 지켜지면 문구부터 다듬는다 | 먼저 "지시가 도착했는가"를 `/memory`로 확인합니다. |
