# 시나리오5_고객지원

## 질문 1

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : A developer adds allowed-tools: Read Grep Glob to a triage skill's SKILL.md, intending to guarantee the skill can never call the process_refund tool. Which two approaches align with how these mechanisms actually behave?


**A(정답).** Enforce the guarantee with a permission deny rule on the refund tool, since deny rules take precedence over a skill's allowed-tools grant.

**설명**

이 답이 옳다. 권한 규칙의 우선순위는 deny, ask, allow 순서이며, 매칭되는 deny 규칙은 allow 승인이 함께 매칭되더라도 호출을 차단한다. 따라서 allowed-tools 프런트매터로는 불가능한 강제 차단을, deny 규칙을 통해 제공할 수 있다. allowed-tools 필드는 나열된 도구를 사전 승인하는 역할만 하기 때문이다.

**B.** Rely on omitting the refund tool from the allowed-tools list to keep it blocked for as long as the skill's instructions remain loaded in context.

**설명**

이 답은 두 가지 이유로 틀렸다. allowed-tools에서 도구를 생략해도 해당 도구가 차단되지는 않는다. 이 필드는 나열된 도구에 사전 승인을 부여할 뿐이며, 그 승인 자체도 스킬 지침이 컨텍스트에 남아 있는 기간이 아니라 호출한 턴에만 한정된다.

**C.** Invoke the skill once at the start of the session so its allowed-tools grant persists for every subsequent turn in that session.

**설명**

이 답은 틀렸다. allowed-tools 승인은 턴 단위로 범위가 한정되어, 사용자가 다음 메시지를 보내면 초기화된다. 스킬을 다시 호출하면 새 턴에 대해 승인이 다시 적용되지만, 세션 전체에 걸쳐 자동으로 이어지는 것은 없다.

**D(정답).** Treat allowed-tools as a turn-scoped pre-approval grant for the listed tools, and expect unlisted tools to stay callable under normal permissions.

**설명**

이 답이 옳다. allowed-tools 필드는 제한이 아니라 사전 승인이다. 이 필드는 호출한 턴 동안 나열된 도구를 권한 확인 없이 사용할 수 있게 해줄 뿐이며, 나열되지 않은 도구는 세션의 일반 권한 설정에 따라 여전히 사용 가능한 상태로 남는다.

### 전반적인 설명

핵심 개념 모델은, SKILL.md 프런트매터의 allowed-tools가 도구 제한이 아니라 권한 승인이라는 점이다. Read Grep Glob을 나열하는 것은 스킬을 호출하는 턴 동안 해당 도구들이 권한 확인 없이 실행된다는 의미일 뿐, Claude가 그 외에 무엇을 호출할 수 있는지에 대해서는 아무것도 규정하지 않는다. 환불 도구와 같은 MCP 도구를 포함해 나열되지 않은 도구는 여전히 사용 가능한 풀에 남아 있으며 세션의 일반 권한 규칙에 따라 관리된다. 이 승인은 턴 단위로 범위가 한정되므로, 스킬 지침이 여전히 컨텍스트에 남아 있더라도 사용자가 다음 메시지를 보내면 초기화된다.

도구를 절대 호출할 수 없도록 보장하려면, 그 메커니즘은 스킬의 승인 목록이 아니라 권한 시스템에 있어야 한다. 권한 규칙은 deny가 ask보다, ask가 allow보다 우선하는 방식으로 평가된다. 즉, 매칭되는 deny 규칙은 스킬의 allowed-tools를 포함한 allow 승인이 함께 매칭되더라도 호출을 차단한다. 이러한 역할 분담은 의도적인 설계다. 스킬은 사전 승인을 통해 몇몇 안전한 도구에 마찰 없이 접근할 수 있지만, 엄격한 제한은 스킬이 무엇을 나열하든 우회할 수 없는 곳에서 명시적으로 선언된다.

환불 처리처럼 금전적으로 중대한 작업의 경우, deny 규칙(또는 코드 상에서 도구 호출을 가로채는 훅)이 어떤 스킬이 활성화되어 있는지, 어떤 턴이 진행 중인지와 무관하게 세션 전체에 걸친 강제력을 제공한다. 프런트매터 동작에 대해서는 Claude Code 스킬 문서를, deny/ask/allow 우선순위에 대해서는 권한 레퍼런스를 참고하라.


## 질문 2

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : The repository ships a team skill at .claude/skills/summarize-ticket/ that the whole team uses on escalation cases. You want a personal variant with different formatting, keeping the shared /summarize-ticket unchanged and still invocable for you. Where does your variant belong?

**A.** In .claude/skills/summarize-ticket/SKILL.md, edited directly but left uncommitted in your working tree.

**설명**

이 방법은 커밋된 팀 스킬 자체를 수정하는 것이므로, 로컬에서 공유 동작에 대한 접근을 잃게 되고 실수로 개인적인 변경사항을 커밋할 위험이 있다. 공유 파일에 대한 커밋되지 않은 수정은 팀이 그 스킬에 앞으로 적용할 모든 업데이트와도 충돌한다.

**B(정답).** In ~/.claude/skills/ under a new directory name, such as summarize-ticket-alt/SKILL.md.

**설명**

개인 스킬은 ~/.claude/skills/에 위치하며 버전 관리를 통해 전달되지 않으므로 팀원들에게 영향을 주지 않는다. 별도의 디렉터리 이름을 사용하면 이름 충돌을 피할 수 있는데, 이는 중요하다. 같은 이름의 개인 스킬은 프로젝트 스킬을 덮어써서 당신에게 보이지 않게 만들기 때문이다.

**C.** In .claude/skills/ under a new directory, with the frontmatter name field changed to rename it.

**설명**

프로젝트 스킬 디렉터리는 버전 관리에 커밋되므로, 이 변형은 다음 풀(pull) 시 모든 팀원에게 전달된다. 게다가 프로젝트 스킬과 개인 스킬 모두 슬래시 명령어 이름은 디렉터리 이름에서 나오며, 프런트매터의 name 필드는 표시 레이블만 바꿀 뿐이다.

**D.** In ~/.claude/skills/summarize-ticket/SKILL.md, reusing the shared skill's directory name.

**설명**

위치는 개인 디렉터리로 맞게 잡았지만, 이름을 재사용하면 충돌이 발생한다. 스킬 우선순위는 개인이 프로젝트보다 우선하므로, /summarize-ticket은 이제 당신의 변형을 실행하게 되고 팀의 공유 스킬은 더 이상 당신에게 호출되지 않는다.

### 전반적인 설명

Claude Code는 여러 위치에서 동시에 스킬을 해석한다. ~/.claude/skills/에 있는 개인 스킬은 사용자의 모든 프로젝트에 걸쳐 적용되며 버전 관리를 통해 공유되지 않는 반면, .claude/skills/에 있는 프로젝트 스킬은 커밋되어 저장소를 풀(pull)하는 모든 팀원에게 전달된다. 이 구분이 개인화를 안전하게 만드는 이유다. 홈 디렉터리 아래에 있는 것은 구조적으로 팀에게 보이지 않으므로, 공유 워크플로우의 개인 변형은 그곳에 두는 것이 맞다.

별도의 디렉터리 이름이 반드시 필요한 이유는 두 가지 세부사항 때문이다. 첫째, 개인 스킬과 프로젝트 스킬 모두 슬래시 명령어 이름은 프런트매터의 name 필드가 아니라 디렉터리 이름에서 파생되므로, 이름을 바꾸려면 새 디렉터리가 필요하며 프런트매터만 바꾸는 것은 호출 시점에 아무 효과가 없다. 둘째, 서로 다른 레벨의 스킬이 같은 이름을 가질 때 우선순위는 엔터프라이즈, 개인, 프로젝트 순으로 적용된다. 즉 개인 summarize-ticket은 당신의 컴퓨터에서 팀 스킬을 조용히 가려버리게 되어, /summarize-ticket이 더 이상 공유 버전을 실행하지 않게 된다. summarize-ticket-alt와 같은 변형 이름을 쓰면 두 명령을 나란히 사용할 수 있다.

커밋된 SKILL.md를 수정하고 커밋되지 않은 채로 남기를 바라는 것은 여기서 전형적인 안티패턴이다. 이는 공유 아티팩트를 갈라져 나온 로컬 포크로 만들고, 실수로 커밋될 위험을 부르며, 앞으로의 팀 업데이트와 충돌한다. .claude/skills/에 이름을 바꾼 복사본을 두는 방법도 다른 방식으로 실패한다. 그 디렉터리는 정확히 팀원들에게 전파되는 디렉터리이기 때문이다. 스킬 위치, 네이밍, 우선순위 규칙에 대해서는 Claude Code 스킬 문서를 참고하라.


## 질문 3

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : You are about to implement the agent's billing-dispute workflow. On past features, specs written up front kept missing failure modes nobody anticipated, such as chargebacks and partial refunds. Which technique best surfaces these considerations before implementation starts?

**A.** Provide two or three concrete input and output examples demonstrating how representative disputes should be resolved.

**설명**

구체적인 예시는 이미 알고 있는 변환 작업이 프롬프트 상에서 일관되지 않게 서술될 때 적합한 기법이다. 예시는 이미 이해하고 있는 패턴을 전달할 뿐이며, 아직 예상하지 못한 엣지 케이스와 실패 모드를 드러낼 수는 없다. 그런데 이 문제에서 지적된 것은 바로 그런 미예상 실패 모드다.

**B.** Use plan mode so Claude explores the existing codebase read-only and hands you an implementation plan to approve before any code is written.

**설명**

플랜 모드는 안전한 탐색과 실행 전 접근법 검토에 유용하지만, 산출되는 계획은 Claude가 코드와 프롬프트에서 발견할 수 있는 내용을 반영할 뿐이다. 개발자의 머릿속이나 비즈니스 도메인에만 존재하는 요구사항과 실패 모드를 끌어내기 위해 개발자에게 체계적으로 질문하지는 않는다.

**C(정답).** Ask Claude to interview you about edge cases, concerns, and tradeoffs, capturing the decisions in a spec before coding.

**설명**

이것이 바로 인터뷰 패턴이다. Claude가 기술적 구현, 엣지 케이스, 트레이드오프를 파고드는 질문을 던져 개발자가 미처 생각하지 못했던 고려사항을 드러낸다. 답변들은 서면 스펙으로 정리되며, 이는 사전 작성된 스펙이 계속 예상치 못한 실패 모드를 놓칠 때 정확히 필요한 해결책이다.

**D.** Write a more exhaustive upfront specification yourself, enumerating every billing edge case your team can identify.

**설명**

더 긴 단독 스펙이라도 팀이 이미 알고 있어서 적을 수 있는 내용에 한정되며, 문제의 전제 자체가 그런 접근법이 계속 실패 모드를 놓쳐왔다고 말하고 있다. 팀이 현재 인식하지 못하는 고려사항을 드러내는 메커니즘을 추가하지는 못한다.

### 전반적인 설명

인터뷰 패턴은 일반적인 프롬프트 작성 방향을 뒤집는다. 개발자가 모든 요구사항을 나열하려 애쓰는 대신, Claude가 질문을 던진다. Anthropic은 이를 "Claude가 당신을 인터뷰하게 하라"는 방식으로 문서화하고 있다. 큰 기능을 최소한의 프롬프트로 시작하고, Claude에게 내장된 AskUserQuestion 도구를 사용해 기술적 구현, UX, 엣지 케이스, 우려사항, 트레이드오프에 대해 당신을 인터뷰하도록 지시하며, 단순히 명백한 질문만 하지 않고 어려운 부분까지 파고들도록 유도한다. 최종 결과물은 SPEC.md와 같은 서면 스펙이며, 이후 Anthropic은 실행에 집중된 깨끗한 컨텍스트에서 구현이 진행되도록 새 세션을 시작할 것을 권장한다.

여기서 핵심 개념 모델은, 청구 분쟁 같은 도메인에는 코드베이스가 아니라 비즈니스 도메인 안에 존재하는 실패 모드(차지백, 부분 환불, 결제 주기 중도 취소 등)가 있다는 것이다. 스펙을 혼자 작성하는 개발자는 이미 고려할 줄 아는 내용만 담을 수 있는데, 바로 이 때문에 과거 스펙들이 계속 무언가를 놓쳐왔다. 체계적인 인터뷰는 모델이 가진 폭넓은 패턴 지식을 활용해 개발자가 전혀 언급하지 않았던 시나리오를 탐색하게 하며, 각 답변은 하나의 기록된 설계 결정이 된다.

다른 기법들은 인접하지만 다른 문제를 해결한다. 플랜 모드는 안전한 읽기 전용 탐색과 검토 가능한 계획을 제공하지만, 그 계획은 주어진 코드와 프롬프트에서 도출되는 것이며 개발자로부터 명시되지 않은 요구사항을 체계적으로 끌어내지는 않는다. 퓨샷 입출력 예시는 이미 알고 있는 변환이 프롬프트 상 일관되지 않게 서술될 때 최선의 도구이지, 문제가 알려지지 않은 엣지 케이스일 때는 아니다. 그리고 더 철저한 단독 스펙은 이 시나리오에서 이미 실패했다고 명시된 접근법을 그대로 반복할 뿐이다.

문서화된 인터뷰 워크플로우와 AskUserQuestion 도구에 대해서는 Claude Code 모범 사례와 도구 레퍼런스를 참고하라.


## 질문 4

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : A developer refactoring the agent's escalation logic enters plan mode and notices Claude running git log and grep shell commands before any plan has been presented. What should the developer do?

**A.** Move the work into a temporary git worktree so any edits Claude stages during planning stay isolated until approval.

**설명**

플랜 모드는 어디에도 수정 내용을 스테이징하지 않는다. 승인 전까지 수정 자체를 완전히 미뤄두므로 격리할 대상이 없다. 워크트리는 하나의 코드베이스에서 병렬 세션을 실행하기 위한 별개의 메커니즘이며, 플랜 모드의 동작 방식과는 무관하다.

**B(정답).** Continue planning; exploratory reads and shell commands are expected, and source edits wait until the plan is approved.

**설명**

이는 플랜 모드가 실제로 제한하는 것과 일치한다. 플랜 모드는 분석을 우선하는 모드다. Claude는 코드베이스를 조사하고 파일을 읽고 탐색을 위해 셸 명령을 실행할 수 있지만, 소스 수정은 사용자가 제안된 계획을 승인할 때까지 보류된다. 따라서 개입이 필요 없다.

**C.** Block all tool calls for the rest of the planning phase so the plan is produced only from context already in the session.

**설명**

플랜 모드의 가치는 바로 능동적인 탐색에서 나온다. 즉, 변경을 제안하기 전에 파일을 읽고 명령을 실행해 코드베이스를 이해하는 것이다. 모든 도구 사용을 금지하면 근거가 아니라 짐작에 기반한 계획이 나오게 된다.

**D.** Interrupt the session and re-enter plan mode, since running shell commands means the session has dropped out of plan mode.

**설명**

플랜 모드는 셸 명령을 제외하는 고정된 허용 목록으로 정의되지 않는다. 탐색 과정의 일부로 계획 단계에서 명령이 실행될 수 있으므로, 명령이 실행되는 것을 본다고 해서 세션이 플랜 모드에서 벗어났다는 뜻은 아니며, 세션을 재시작하면 유용한 조사 내용을 잃게 된다.

### 전반적인 설명

플랜 모드는 도구 사용을 봉쇄하는 것이 아니라 수정 작업에 대한 게이트로 이해하는 것이 가장 적절하다. 플랜 모드가 활성화되어 있는 동안에도 Claude Code는 코드베이스를 자유롭게 조사한다. 파일을 읽고, grep으로 검색하고, git 히스토리를 살펴보며, 그 조사의 일환으로 셸 명령을 실행할 수 있다. 보류되는 것은 소스 파일 수정이며, 이는 사용자가 제안된 계획을 검토하고 승인한 후에만 이루어진다. 따라서 계획 단계에서 탐색 명령이 실행되는 것을 보는 것은 예상된 동작이며 모드가 우회되었다는 신호가 아니다. 따라서 올바른 대응은 조사가 계속되도록 그냥 두는 것이다.

이 설계는 플랜 모드가 존재하는 이유인 트레이드오프를 반영한다. 에스컬레이션 로직을 재작업하는 것과 같은 작업에 유용한 계획을 세우려면 코드가 실제로 어떻게 동작하는지에 대한 실질적인 근거가 필요하므로, 탐색은 저비용이면서 제약이 없어야 한다. 반면 비용이 크고 되돌리기 어려운 단계는 변경 사항을 실제로 작성하는 것이므로, 바로 그 단계가 승인 뒤에 배치된다. 승인은 또한 전환점이기도 하다. 계획을 승인하면 플랜 모드에서 벗어나 자동으로든 편집별 검토를 거치든 편집이 진행될 수 있는 권한 모드로 세션이 이동한다.

대안으로 제시된 응답들은 각기 특징적인 방식으로 실패한다. 셸 명령이 플랜 모드에서 벗어났다는 신호라고 가정하고 세션을 재시작하는 것은 정상적인 탐색을 모드 위반으로 잘못 해석한 것이며, 모든 도구 사용을 차단하면 Claude가 오래되었거나 존재하지 않는 컨텍스트로부터 계획을 세워야 하게 되어, 실행 전에 설계를 먼저 하는 전체 취지를 훼손한다. 워크트리를 사용하려는 시도는 플랜 모드를 별개의 병렬 세션 워크플로우와 혼동한 것이다. 플랜 모드는 어디에도 수정 내용을 스테이징하지 않으며, 단지 미루기만 한다. 문서화된 동작에 대해서는 권한 모드 문서를 참고하라.

Claude Code의 테스트 주도 워크플로우에 대한 Anthropic의 가이드는 에이전틱 코딩 모범 사례와 일반 워크플로우 문서의 워크플로우 패턴을 참고하라.

별도의 리뷰 세션이 작성 세션이 놓친 문제를 잡아내는 이유는 두 번째 인스턴스가 더 똑똑하기 때문이 아니라, 깨끗한 컨텍스트를 갖고 있기 때문이다. 코드를 생성한 세션은 각 결정으로 이어진 전체 추론 사슬을 그대로 지니고 있어서, 리뷰를 요청받으면 같은 결론을 다시 도출하고 자신의 선택을 지지하는 경향을 보인다. 멀티 인스턴스 워크플로우에 대한 Anthropic의 가이드는 명확하다. 신선한 컨텍스트를 가진 리뷰어는 자신이 방금 작성한 코드에 편향되지 않는다는 것이며, 이 때문에 문서화된 패턴은 작성자 세션과 리뷰어 세션을 분리한다.

작성자의 추론이 다시 복사되어 들어오는 순간 이 이점은 사라진다. 전체 대화 기록을 붙여넣거나, 작성자 스스로 작성한 근거 요약을 주입하거나, 작성자 세션의 복사본을 재개하는 것 모두 원래의 프레이밍을 리뷰어의 컨텍스트에 전달한다. 그러면 리뷰어는 코드가 아니라 정당화 논리를 평가하게 된다. 올바른 입력은 결과물 자체다. 즉 diff와, 리뷰어가 원래도 로드했을 프로젝트 컨텍스트(CLAUDE.md의 규칙, 관련 표준)다. 리뷰어가 정말로 의도를 알아야 한다면, 작성자 자신의 구현에 대한 변론이 아니라 중립적인 요구사항 서술로 표현해야 한다.

경계선을 기억해두어야 한다. 독립성은 자기 리뷰 편향을 완화할 뿐, 모든 결함이 발견됨을 보장하지는 않으며, 리뷰어는 여전히 팀의 표준을 적용할 만큼 충분한 프로젝트 컨텍스트가 필요하다. 다중 세션 작성 후 리뷰 패턴에 대해서는 Claude Code 모범 사례와 일반 워크플로우 문서를 참고하라.

### 전반적인 설명

Claude에게 이슈를 전달할 때의 판단 기준은 편의성이 아니라 상호의존성이다. 결함들이 상호작용한다는 것, 즉 한쪽의 수정이 다른 쪽의 올바른 수정 방식을 바꾼다는 것을 의미할 때는, 반드시 한 메시지에 함께 담아야 한다. 한 번에 이슈를 하나씩만 주면 Claude는 지역적으로 최적화한다. 즉 환불 승인 검사가 같은 정책 조항을 참조한다는 것을 모른 채 에스컬레이션 임계값을 고치거나, process_refund의 파싱을 조정하지 않은 채 lookup_order의 출력 형식을 바꾸게 되며, 각 수정은 조용히 다음 수정을 무효화하거나 충돌시킨다. 결합된 이슈들을 함께 제시하면 모델이 공유된 제약(하나의 정책 해석, 하나의 주문 ID 계약)을 고려해 하나의 일관된 변경을 낼 수 있다.

독립적인 이슈는 이 트레이드오프를 반대로 만든다. 인사말 오타와 화폐 기호, 또는 로깅 구문과 오래된 독스트링은 공유된 로직이 없으므로 이들을 합쳐서 얻는 것은 없고, 오히려 잃는 것이 있다. 묶인 프롬프트는 주의를 관련 없는 수정들에 분산시키고, 검토하기 더 어려운 diff를 만들며, 어떤 변경이 회귀를 일으켰는지 파악하기 더 어렵게 만든다. 순차적인 턴은 각 수정을 작고, 독립적으로 검증 가능하며, 개별적으로 수락하거나 되돌리기 쉽게 유지한다.

유용한 개념 모델은 개수나 파일의 근접성이 아니라 근본 원인과 계약을 기준으로 묶으라는 것이다. 두 수정이 시스템을 일관되게 유지하기 위해 함께 적용되어야 한다면 그것은 하나의 작업이고, 둘 중 하나가 아무것도 깨뜨리지 않고 단독으로 배포될 수 있다면 그것들은 별개의 작업이다. 이는 Claude Code에 대한 더 넓은 반복적 개선 가이드와도 일맥상통한다. 각 요청의 범위를 모델이 상호작용하는 제약 전체를 한눈에 담을 수 있을 만큼, 그리고 그 이상은 아니게 좁혀라. Claude Code 모범 사례와 Claude Code 문서를 참고하라.


## 질문 11

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : The repository's CLAUDE.md mixes conventions for MCP tool-handler code in src/tools/, conventions for test files scattered throughout the tree, and deployment notes. You want each convention set loaded only when matching files are being worked on. What should you do?

**A.** Keep one CLAUDE.md and use @import statements to pull each convention set in from separate topic files.

**설명**

임포트는 내용을 별도의 파일로 정리해주지만, 임포트된 모든 내용은 실행 시점에 펼쳐져 로드된다. 이는 유지보수성을 개선할 뿐 조건부 로딩을 달성하지는 못하므로, 모든 컨벤션 세트가 여전히 모든 세션에서 컨텍스트를 차지하게 된다.

**B(정답).** Move each convention set into its own .claude/rules/ file with paths glob frontmatter matching relevant files.

**설명**

이 답이 옳다. .claude/rules/의 규칙 파일은 YAML 프런트매터에 paths 필드를 선언할 수 있으며, 이러한 규칙은 Claude가 글롭 패턴에 매칭되는 파일로 작업할 때만 로드된다. 이는 주제별 조건부 로딩을 제공하여, 관련 없는 컨벤션이 컨텍스트에 들어오지 않게 해준다.

**C.** Add a CLAUDE.md inside src/tools/ and inside each directory that contains test files or deployment scripts.

**설명**

디렉터리 단위 CLAUDE.md 파일은 해당 디렉터리에 묶여 있으므로, 여러 위치에 흩어진 테스트 파일에는 통하지 않는다. 테스트가 있는 모든 디렉터리에 복사본이 필요해진다. 글롭 범위의 규칙은 위치와 무관하게 파일 유형별로 적용되므로 이 상황에 더 적합하다.

**D.** Convert each convention set into a slash command that developers run when they start work in that area.

**설명**

슬래시 명령어는 선택적으로 사용하는 프롬프트 템플릿이므로, 누군가 명령어를 호출하는 것을 기억할 때만 컨벤션이 적용된다. 매칭되는 파일 작업을 자동으로 규율해야 하는 컨벤션에는 수동 호출 없이 로드되는 메커니즘이 필요하다.

### 전반적인 설명

.claude/rules/ 디렉터리는 단일 거대 CLAUDE.md에 대한 모듈식 대안이며, 그 핵심 레버는 YAML 프런트매터의 paths 필드다. paths: ["src/tools/**/*"] 또는 paths: ["**/*.test.ts"]가 있는 규칙은 Claude가 해당 글롭에 매칭되는 파일로 작업할 때만 로드되는 반면, paths가 없는 규칙은 .claude/CLAUDE.md와 동일한 우선순위로 실행 시점에 무조건 로드된다. 개념 모델은 다음과 같다. 무조건 로드되는 모든 것은 매 세션에서 주의를 두고 경쟁하므로, 조건부 로딩은 단순한 토큰 최적화가 아니라, 실제로 적용될 때 각 규칙이 더 잘 준수되도록 만들어준다.

글롭 범위의 규칙은 디렉터리 단위 CLAUDE.md 파일이 풀 수 없는 위치 문제도 해결한다. 디렉터리 CLAUDE.md는 하나의 폴더를 규율하는데, 이는 하나의 영역에 묶인 컨벤션에는 통하지만, 테스트 대상 코드와 함께 배치된 테스트 파일처럼 트리 전체에 흩어진 파일 유형에는 통하지 않는다. **/*.test.ts와 같은 패턴은 하나의 규칙 파일로 이들을 모두 다룬다. Claude Code는 .claude/rules/ 아래를 재귀적으로 탐색해 규칙 파일을 찾아내므로, 규칙 자체도 주제별로 하위 디렉터리로 정리할 수 있다는 점도 참고할 만하다.

오답들은 각각 조건부 로딩 요구사항을 놓치고 있다. @import 구문은 소스 파일을 모듈화하지만, 임포트된 내용은 실행 시점에 인라인으로 펼쳐지므로 컨텍스트 사용량은 변하지 않는다. 슬래시 명령어는 컨벤션을 선택적으로 만드는데, 이는 가끔 있는 워크플로우에는 적합하지만 매칭되는 모든 편집을 규율해야 하는 표준에는 적합하지 않다. 규칙과 경로 범위 지정의 전체 동작에 대해서는 "Claude의 메모리 관리" 문서를 참고하라.


## 질문 12

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : The repository for this agent keeps orchestration code at the root and the MCP tool implementations under tools/. Strict TypeScript standards must apply everywhere, while error-handling conventions apply only to the tool code. Where should each set of instructions live?

**A.** Put the error-handling conventions in the project root CLAUDE.md and the TypeScript standards in a CLAUDE.md inside the tools/ directory.

**설명**

이 방법은 계층 구조를 뒤집는다. 보편적인 TypeScript 표준은 tools/ 아래에서 작업할 때만 나타나게 되고, tools에만 해당하는 에러 처리 컨벤션은 저장소 전체의 모든 세션에 로드되어 관련 없는 컨텍스트를 추가하게 된다.

**B(정답).** Put the TypeScript standards in the project root CLAUDE.md and the error-handling conventions in a CLAUDE.md inside the tools/ directory.

**설명**

이 답은 각 컨벤션을 계층 구조상 올바른 레벨에 맞춘다. 프로젝트 레벨 CLAUDE.md는 저장소의 모든 세션에서 로드되므로 보편적인 표준이 항상 적용되며, 디렉터리 레벨 CLAUDE.md는 에러 처리 컨벤션의 범위를 tools/ 내 작업으로 한정해 관련 없는 세션을 어지럽히지 않는다.

**C.** Put the TypeScript standards in each developer's ~/.claude/CLAUDE.md and the error-handling conventions in the project root CLAUDE.md.

**설명**

사용자 레벨 CLAUDE.md 파일은 개인적인 것이며 버전 관리를 통해 전달되지 않으므로, 그곳에 둔 팀 전체 표준은 시간이 지나며 어긋나거나 새 팀원에게는 아예 존재하지 않게 된다. 또한 디렉터리 특정 컨벤션을 프로젝트 범위로 끌어올려, 적용되지 않아야 할 곳에서도 로드되게 만든다.

**D.** Put both sets in the project root CLAUDE.md, using section headings that state which directory each set of conventions applies to.

**설명**

루트 CLAUDE.md는 모든 세션에서 전체가 로드되므로, 관련 없는 코드를 편집하는 중에도 도구 특정 컨벤션이 컨텍스트를 차지하게 된다. 헤딩은 범위 지정 메커니즘이 아니라 모델이 해석해야 하는 프롬프트일 뿐이며, 컨벤션을 올바른 레벨에 두는 것보다 신뢰성이 떨어진다.

### 전반적인 설명

Claude Code의 메모리는 계층화되어 있다. 사용자 레벨(~/.claude/CLAUDE.md)은 모든 프로젝트에 걸친 한 사람의 선호를 담고 있으며 버전 관리를 통해 공유되지 않는다. 프로젝트 레벨(루트 CLAUDE.md 또는 .claude/CLAUDE.md)은 커밋되어 저장소의 모든 세션에서 로드된다. 하위 디렉터리의 디렉터리 레벨 CLAUDE.md 파일은 그 트리 부분에서 작업할 때 적용되는 컨벤션을 추가한다. 개념 모델은 광범위한 것에서 구체적인 것으로 향한다는 것이다. 각 레벨은 상위 레벨이 이미 말한 것을 반복하지 않고 범위를 좁혀나간다.

이 계층 구조 뒤에 있는 설계상의 트레이드오프는 컨텍스트 경제성과 커버리지 사이의 균형이다. 루트 파일에 있는 모든 것은 매 대화에 로드되며, 모든 줄이 모델의 주의를 두고 다른 모든 줄과 경쟁한다. 따라서 한 영역에만 중요한 지침이 모든 곳에 중요한 지침을 희석시킨다. TypeScript 표준을 프로젝트 레벨에 두면 모든 작업에 그 표준이 반영되는 것이 보장되며, tools/CLAUDE.md는 에러 처리 컨벤션을 그것이 규율하는 코드에 계속 붙여둔다. CLAUDE.md는 모델이 따르는 가이드라인이며 강제되는 설정이 아니라는 점을 기억해야 한다. 규칙을 절대 건너뛸 수 없게 해야 한다면, 훅이 적합한 수단이다.

다른 배치 방식들은 각각 이러한 특성 중 하나를 깨뜨린다. 레벨을 뒤집으면 보편적인 표준이 조건부가 되고 지역적인 컨벤션이 전역화된다. 단일 거대 루트 파일은 도구 특정 규칙을 관련 없는 세션에 로드하며 모델이 해석해야 하는 헤딩에 의존한다. 그리고 사용자 레벨 배치는 팀 표준의 공유를 완전히 없애버리는데, 이는 새 팀원의 세션이 컨벤션을 무시하게 되는 전형적인 원인이다. 전체 계층 구조에 대해서는 "Claude의 메모리 관리" 문서를 참고하라.
