# 사전 학습 노트: 도구 설계(Tool Design)와 MCP 통합

이 문서는 이 주제를 처음 접하는 사람을 위한 개념 정리입니다. LLM 에이전트가 "도구(tool)"를 어떻게 인식하고 고르는지, 도구가 실패했을 때 무엇을 돌려줘야 하는지, MCP(Model Context Protocol) 서버를 어떻게 설정하고 연결하는지, 그리고 여러 에이전트를 조합할 때의 설계 원칙을 다룹니다.

---

## 1. 기초: LLM 에이전트와 도구(Tool)란 무엇인가

### 1.1 왜 도구가 필요한가
LLM(대형 언어 모델)은 학습 시점까지의 지식만 가지고 텍스트를 생성합니다. 그래서 다음을 스스로 할 수 없습니다.

- 오늘 날짜의 실시간 데이터 조회 (환율, 재고, 티켓 상태)
- 외부 시스템에 대한 실제 작업 수행 (환불 처리, 회의실 예약, 파일 쓰기)

**도구(Tool)** 는 이 한계를 메우기 위해 모델에게 "네가 호출할 수 있는 함수 목록"을 미리 알려주는 장치입니다. 모델은 직접 코드를 실행하지 않습니다. 대신 "이 함수를 이런 인자로 불러 줘"라는 요청(tool call / function call)을 JSON 형태로 출력하고, 실제 실행은 애플리케이션(호스트, 클라이언트)이 담당합니다.

### 1.2 한 번의 도구 호출이 흘러가는 순서
1. 애플리케이션이 모델에게 **시스템 프롬프트 + 대화 + 도구 정의 목록**을 보냅니다.
2. 모델이 "지금은 `search_web`을 `{"query": "..."}`로 부르겠다"는 tool call을 출력합니다.
3. 애플리케이션이 실제 함수/API를 실행합니다.
4. 실행 결과(성공이든 실패든)를 **tool result**로 다시 모델에게 돌려줍니다.
5. 모델이 그 결과를 읽고 다음 행동(또 다른 도구 호출, 또는 사용자에게 최종 답변)을 결정합니다.

이 4번 단계, 즉 **결과를 어떤 모양으로 돌려주느냐**가 이 주제의 절반을 차지합니다. 모델은 그 결과 텍스트/데이터만 보고 판단하기 때문입니다.

### 1.3 도구 정의(Tool Definition)의 구성 요소
도구 하나는 보통 세 가지로 정의됩니다.

| 요소 | 역할 |
|---|---|
| `name` | 도구 식별자 (예: `search_web`) |
| `description` | 자연어 설명. **모델이 도구를 고를 때 쓰는 주된 근거** |
| `input_schema` | 입력 파라미터의 JSON Schema (타입, 필수 여부, 설명) |

예시:

```json
{
  "name": "search_web",
  "description": "웹 검색 엔진에 질의를 보내 최신 정보를 담은 결과 스니펫 목록을 돌려준다. 아직 어떤 페이지를 봐야 할지 모를 때 사용한다. 이미 특정 URL을 알고 있다면 fetch_webpage_results를 사용할 것.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": { "type": "string", "description": "검색어" }
    },
    "required": ["query"]
  }
}
```

핵심 감각: **도구 정의는 코드가 아니라 모델을 향한 문서다.** 모델은 함수 본문을 볼 수 없고 이름과 설명, 스키마만 봅니다.

## 2. 도구 선택(Tool Selection): 모델이 올바른 도구를 고르게 만드는 법

### 2.1 모델은 의미(semantic)로 고른다
모델은 사용자 요청 문장과 각 도구의 이름·설명을 의미적으로 비교해서 가장 잘 맞는 것을 고릅니다. 따라서 선택 정확도는 **설명 문장의 품질**에 거의 전적으로 달려 있습니다.

### 2.2 좋은 설명에 들어가야 할 것
비슷한 도구가 여러 개일 때 혼동을 줄이는 요소는 다음 세 가지입니다.

1. **기대하는 입력 형식** — 어떤 모양의 인자를 받는지. 모델이 "내가 지금 가진 정보로 이 도구를 부를 수 있나?"를 판단하게 해 줍니다.
2. **한두 개의 예시 질의(example query)** — "이런 요청이 오면 이 도구다"라는 구체적 유스케이스. 이는 소수 예시 학습(few-shot) 효과를 냅니다. 예시를 많이 넣을 필요는 없고, 대표적인 것 한둘이면 충분합니다.
3. **경계 안내 / 비교 노트 (negative guidance)** — "언제 이 도구 대신 다른 도구를 써야 하는지"를 명시. 예: "특정 URL의 본문이 필요하면 `fetch_webpage_results`를 쓸 것." 유사 도구 간 경계를 직접 그어 주는 것이 가장 효과가 큽니다.

### 2.3 도움이 되지 않는 것들
다음은 설명에 넣어도 도구 선택 품질을 개선하지 못합니다.

- **파라미터 조합의 나열만** — 스키마는 "어떻게 부르는가"를 알려 줄 뿐 "언제 부르는가"를 알려 주지 않습니다. 서술적 용도 설명이 없으면 모델은 호출 시점을 판단할 근거가 없습니다.
- **구현 세부 정보** — 구현한 엔지니어 이름, 내부 구현 언어(Python/Rust 등)는 사용자의 요청과 아무 의미적 연관이 없습니다.
- **이모지나 눈에 띄는 이름** — 시각적 구분은 사람에게만 의미가 있습니다. 모델은 텍스트 토큰의 의미를 볼 뿐 "화면에서 튀는 정도"를 보지 않습니다.

### 2.4 중복 설명 문제 (가장 흔한 실패)
두 도구가 이름만 다르고 설명이 사실상 같으면(예: `process_data`와 `process_information` 둘 다 "Processes data provided by the user."), 모델에게는 **구별 신호가 0**입니다. 결과적으로 라우팅이 거의 동전 던지기 수준이 됩니다.

이때 오해하기 쉬운 잘못된 진단들:

- "컨텍스트 창이 부족해서" — 도구 정의 두 개는 수백 토큰 수준이라 컨텍스트 한계와 무관합니다.
- "사용자 프롬프트가 모호해서" — 원인은 개발자가 작성한 도구 정의 쪽에 있습니다. 사용자가 아무리 명확히 말해도 두 도구가 구분되지 않으면 정확히 고를 수 없습니다.
- "도구 배열의 선언 순서 때문에" — 순서를 바꾸면 앞쪽 도구로 편향이 생길 뿐, 모호성 자체가 사라지지 않습니다.

올바른 해법은 **각 도구의 설명을 서로 다르게, 배타적으로 다시 쓰는 것**입니다. 예:

```
process_data:        CSV/JSON 등 구조화된 데이터 파일을 정규화·집계한다. 비정형 텍스트에는 쓰지 말 것.
process_information: 자유 서술형 텍스트 문서를 요약·분류한다. 표 형식 데이터에는 process_data를 쓸 것.
```

### 2.5 시스템 프롬프트가 만드는 키워드 편향
도구 설명이 정확해도, 상위 계층인 **시스템 프롬프트의 문구가 특정 도구 쪽으로 모델을 끌어당길 수 있습니다.**

예: 시스템 프롬프트에 "Always prefer **searching** for the most up to date information."이 있고 도구 이름이 `search_web`이라면, 모델은 'searching'이라는 단어와 `search_web`이라는 이름 사이의 어휘적 연관을 강하게 형성합니다. 그 결과, 실제로는 `fetch_webpage_results`가 적절한 상황에서도 거의 항상 `search_web`을 고릅니다. 이를 **앵커링(anchoring) / 키워드 연관 편향**이라 부릅니다.

이 현상의 교훈:
- 시스템 프롬프트는 도구 설명보다 상위 지시로 작동하므로, 특정 도구명과 겹치는 동사·명사를 무심코 쓰면 안 됩니다.
- 편향을 없애려면 프롬프트 문구를 도구 중립적으로 고쳐야 합니다. 예: "필요하면 최신 정보를 확보하되, 어떤 도구가 적절한지는 각 도구 설명을 근거로 판단할 것."

혼동하기 쉬운 오해들:
- 병렬 도구 사용 시 특정 도구가 자동으로 걸러진다는 메커니즘은 **없습니다.**
- 도구 스키마 안에 개별 `temperature` 값을 넣는 필드는 **없습니다.** temperature는 모델 호출 단위의 샘플링 파라미터이지 도구별 속성이 아닙니다.
- 설명이 일정 토큰 길이를 넘으면 모델이 그 도구를 체계적으로 회피한다는 임계값은 **없습니다.**

## 3. `tool_choice`: 도구 사용을 강제하거나 막는 스위치

Anthropic Messages API 같은 도구 호출 API에는 요청마다 `tool_choice` 파라미터를 줄 수 있습니다. 이는 "이번 턴에 모델이 도구를 써야 하는가"를 제어합니다.

| 값 | 동작 | 언제 쓰나 |
|---|---|---|
| `{"type": "auto"}` | 모델이 턴마다 스스로 판단: 도구를 부르거나(act), 그냥 텍스트로 답하거나(respond) | 기본값. 대부분의 대화형 에이전트 |
| `{"type": "any"}` | **반드시 제공된 도구 중 최소 하나를 호출**해야 함. 텍스트만으로 답하는 것 불가 | 모든 요청이 실시간 데이터 조회나 실제 작업을 요구해서, 모델의 내부 지식만으로 답하면 안 되는 경우 |
| `{"type": "tool", "name": "X"}` | 지정한 단 하나의 도구 `X`를 강제 호출 | 출력 형식을 고정하고 싶을 때(구조화 추출 등). 여러 도구 중 상황에 맞게 고르는 유스케이스에는 부적합 |
| `{"type": "none"}` | 도구를 전혀 호출하지 못하게 함. 텍스트 응답만 | 도구 실행을 잠시 막고 계획만 말하게 할 때 |

```json
{
  "model": "claude-...",
  "tools": [ /* ... */ ],
  "tool_choice": { "type": "any" },
  "messages": [ /* ... */ ]
}
```

설계 감각:
- "모델이 내부 지식으로 대충 답해 버리는 것"을 막고 싶다 → `any`.
- "권한 밖의 도구를 쓰는 것"을 막고 싶다 → `tool_choice`가 아니라 **도구 목록 자체를 줄이는 것**이 정답입니다. `any`나 특정 도구 강제는 오히려 자율성을 없애면서 오용 문제는 그대로 남깁니다.
- 에이전트가 "행동할지 말할지"를 스스로 정하는 능력을 유지하려면 반드시 `auto`여야 합니다.

## 4. 도구 오류 응답 설계 (Error Response Design)

### 4.1 왜 오류 모양이 중요한가
도구가 실패하면 그 결과 문자열이 모델에게 그대로 전달됩니다. 모델은 그것만 보고 두 가지를 결정합니다.

1. **사용자에게 뭐라고 설명할 것인가**
2. **다시 시도해야 하는가, 아니면 포기해야 하는가**

따라서 오류 응답은 사람 눈이 아니라 **모델의 판단을 위한 인터페이스**로 설계해야 합니다.

### 4.2 두 층으로 나눠 담기
좋은 오류 응답은 두 부분을 함께 가집니다.

**(1) 사람이 읽을 수 있는 자연어 설명 (text block / `description` 필드)**
모델이 그대로 사용자에게 옮겨 말할 수 있는 문장. 무엇이 왜 실패했는지 구체적으로 담습니다.

**(2) 기계 지향 구조화 메타데이터 (structured content)**
모델이 재시도 여부 등 제어 판단을 내리기 위한 필드. 대표적으로 `errorCategory`, `isRetryable`.

이 둘은 **분리**되어 있어야 합니다. 자연어에 제어 정보가 섞이면 모델이 파싱해야 하고, 구조화 필드만 있으면 사용자에게 설명할 문장이 없습니다.

```json
{
  "isError": true,
  "content": [
    { "type": "text",
      "text": "환불이 거절되었습니다. 이 주문은 구매일로부터 30일이 지나 반품 가능 기간을 벗어났습니다." }
  ],
  "structuredContent": {
    "errorCategory": "business",
    "isRetryable": false,
    "description": "주문 #12345는 30일 반품 기간을 초과하여 환불 대상이 아닙니다."
  }
}
```

### 4.3 `errorCategory`: 오류의 성격 분류
모델이 "다시 부를까?"를 판단하는 가장 강한 신호입니다. 대표적 범주:

| 카테고리 | 의미 | 모델이 취해야 할 행동 |
|---|---|---|
| `transient` | 일시적 오류 (네트워크 끊김, 레이트 리밋, 타임아웃) | 잠시 후 **동일 호출 재시도** 가능 |
| `business` | 비즈니스 규칙 위반 (기한 초과, 잔액 부족, 정책 위반) | 입력이 같으면 결과도 같음 → **재시도 무의미**, 사용자에게 설명 |
| `permission` | 권한/인증 부족 (자격 증명에 접근 권한 없음) | 같은 자격 증명으로 재시도해도 무의미. 상위 권한 필요, 또는 관리자 문의 |
| `validation` | 입력 값이 잘못됨 | **입력을 고쳐서** 재시도 |
| `not_found` | 대상 리소스 없음 | 다른 식별자로 시도하거나 포기 |

카테고리를 잘못 붙이면 모델이 정확히 잘못된 행동을 합니다. 예를 들어 30일 반품 기한 초과(비즈니스 규칙)를 `transient`로 표시하면, 모델은 "30초 뒤 재시도"를 무한 반복합니다. 반대로 권한 문제를 `business`로 표시하면 해결 가능한 문제를 포기해 버립니다.

### 4.4 `isRetryable` 플래그
`errorCategory`를 보완하는 불리언 신호입니다. `true`는 "같은 요청을 다시 보내면 성공할 수도 있다"는 뜻입니다. 회의실이 이미 예약된 경우처럼 **사용자가 조건(시간대)을 바꾸지 않는 한 절대 성공하지 않는 상황**에 `isRetryable: true`를 주면 무한 재시도 루프를 유발합니다.

### 4.5 하지 말아야 할 오류 응답
- **빈약한 텍스트만** — `"Refund denied"` 한 줄. 이유도 없고 재시도 판단 근거도 없습니다. 모델은 사용자에게 설명도 못 하고, 다시 시도해야 할지도 모릅니다.
- **날것의 예외 스택 트레이스 반환** — 모델에게 텍스트 파싱을 시키는 셈입니다. 토큰 낭비이고, 파싱이 틀리면 잘못된 설명이 나가며, 내부 구현 정보가 유출됩니다.
- **`description` 없이 카테고리만** — `errorCategory: "business"`만으로는 "무엇이 왜"인지 모르므로, 모델이 맥락에 맞는 구체적 안내를 만들어 낼 수 없습니다. 카테고리는 대분류일 뿐 구체 사유를 대체하지 못합니다.
- **제어 정보를 자연어에 섞기** — "wait 30 seconds and resubmit" 같은 지시를 텍스트에 넣으면서 카테고리는 다른 이야기를 하면 모델이 혼란스러워집니다.

### 4.6 설계 체크리스트
1. 이 실패는 재시도로 해결되는가? → 그에 맞는 카테고리/`isRetryable` 선택
2. 사용자에게 그대로 읽어 줄 문장이 있는가? → 구체적 `description`
3. 대안 행동을 제시할 수 있는가? → "다른 시간대를 선택해 보세요" 같은 힌트
4. 내부 스택 트레이스나 비밀 정보가 새고 있지 않은가?

## 5. 멀티 에이전트 아키텍처

### 5.1 기본 구조
복잡한 작업은 하나의 거대한 에이전트보다 역할별로 나눈 여러 에이전트로 처리하는 편이 안정적입니다.

- **코디네이터(Coordinator) / 오케스트레이터**: 작업을 쪼개어 서브에이전트에게 위임하고, 결과를 모아 다음 단계를 결정.
- **서브에이전트(Subagent)**: 좁은 역할 하나를 맡음. 예: 리서치 에이전트, 코딩 에이전트, QA 에이전트 / 접수(intake)·처리(processing)·전달(delivery) 파이프라인.

서브에이전트들은 서로 다른 폴더·데이터 구간을 맡아 **병렬로** 실행될 수 있습니다.

### 5.2 도구 스코핑과 최소 권한 원칙 (Least Privilege)
가장 중요한 설계 원칙입니다. **각 에이전트에게는 자기 역할에 필요한 도구만 준다.**

왜 중요한가: 모델은 손에 쥔 도구를 쓰고 싶어하는 경향이 있습니다. 접근 권한이 열려 있는 도구는 언젠가 호출됩니다.

전형적 사례: 종합(synthesis) 에이전트는 리서치 에이전트가 이미 모아 준 자료를 정리해 최종 답변을 만드는 역할입니다. 그런데 두 에이전트가 **공용 도구 레지스트리**를 공유하는 바람에 종합 에이전트에게도 `web_search`가 노출되면, 종합 도중에 임의로 검색을 돌려 원래 자료에 없던 출처를 섞습니다. 결과적으로 인용이 일관되지 않게 됩니다.

이 문제의 근본 해법은 **종합 에이전트의 도구 목록에서 `web_search`를 아예 제거**하는 것입니다.

효과가 약한 대안들과 그 이유:
- **temperature 낮추기(예: 0.2)** — 확률적으로 호출 빈도를 줄일 뿐, 노출된 도구를 근본적으로 막지 못합니다.
- **도구 설명에 "종합 중에는 쓰지 마시오" 문구 추가** — 프롬프트 지시는 모델이 무시하거나 우회할 수 있습니다. 텍스트 지시보다 물리적 차단이 훨씬 견고합니다.
- **상류 데이터가 부실해서라고 진단하기** — 원인 오진입니다. 자료가 충분해도 검색 도구가 있으면 부르게 됩니다.

### 5.3 좁은 범위의 역할 간 도구 (Limited Cross-Role Tools)
현실에서는 한 에이전트가 다른 역할의 기능을 가끔 필요로 합니다. 예: 접수 에이전트가 처리 상태를 확인해야 하는 경우.

세 가지 나쁜 선택과 하나의 좋은 선택:

- 나쁨: **처리 에이전트의 전체 도구 세트를 통째로 준다** → 과도한 권한 부여(over-privileging). 상태 조회만 필요한데 데이터 변경 작업까지 실행할 수 있게 됩니다.
- 나쁨: **그 기능을 파이프라인에서 없앤다** → 필요한 기능을 삭제하는 것은 요구사항 회피이지 설계가 아닙니다.
- 나쁨: **필요하지 않은 쪽 에이전트에 도구를 복사해 준다** → 문제와 무관하고 권한만 넓힙니다.
- **좋음: 그 특정 목적만 수행하는 좁은 도구 하나(`check_status`)만 부여**하고, 나머지 깊은 처리 작업은 계속 처리 에이전트를 경유하도록 라우팅합니다.

이 방식이 최소 권한과 관심사 분리(separation of concerns)를 동시에 만족합니다. 판단 기준은 "빈번하게 필요한가"와 "부작용 없는 읽기 전용에 가까운가"입니다.

### 5.4 도구 스코핑과 `tool_choice`를 함께 고려하기
"에이전트가 자기 소관 밖 도구를 건드린다"는 문제에 대한 옳은 조합은:

- **도구 세트**: 역할별로 축소 (리서치 에이전트엔 검색 도구만, QA 에이전트엔 테스트 도구만)
- **`tool_choice`**: `{"type": "auto"}` 유지 — 각 에이전트가 턴마다 도구를 쓸지 텍스트로 답할지 자율 판단하는 능력을 보존

`any`로 강제하면 도구가 필요 없는 턴에도 억지로 도구를 부르고, 15개 전체 세트를 그대로 두면 오용 문제도 남습니다. `none`으로 막으면 서브에이전트가 아무 일도 못 합니다. 단일 도구 강제는 상황별 유연성을 없앱니다.

## 6. 서브에이전트의 실패 보고와 코디네이터의 후속 처리

### 6.1 부분 결과(Partial Results)의 가치
배치 작업 중 일부만 실패하는 상황은 흔합니다. 예: 50건 고객 레코드 보강 중 47건 성공, 3건은 자격 증명 부족(`permission`)으로 실패, 그리고 서브에이전트는 스스로 더 넓은 권한을 얻을 수 없음.

이때 서브에이전트가 코디네이터에게 돌려보내야 하는 것:

1. **성공한 47건의 결과 (부분 결과)** — 유효한 작업을 버리지 않습니다.
2. **미해결 3건의 식별 정보** — 누가 남았는지 명시.
3. **마주친 오류의 성격** — `errorCategory: "permission"` 등.
4. **시도한 내용** — 어떤 복구를 시도했고 왜 실패했는지.

이것을 **우아한 실패 보고(graceful failure reporting)** 라고 합니다. 코디네이터는 이 정보를 받아 더 높은 권한으로 재처리하거나 사람에게 에스컬레이션할 수 있습니다.

피해야 할 패턴:
- **전체를 `isError: true`로 처리하고 47건을 폐기** — 이미 쓴 비용을 버리는 낭비.
- **실패 3건을 조용히 누락(silently dropping)** — 상위에서 데이터 누락 사실을 알 수 없어 정합성이 깨집니다. 이것이 가장 위험합니다.
- **같은 자격 증명으로 무한 재시도 루프** — `permission` 오류는 자격 증명이 바뀌지 않는 한 절대 해결되지 않습니다. 무한 루프와 자원 낭비만 발생합니다.

### 6.2 "보고된 실패" vs "프로세스 크래시"의 결정적 차이
병렬로 세 서브에이전트를 돌렸다고 합시다.

- **서브에이전트 1**: 정상 완료 → 추가 조치 없음.
- **서브에이전트 2**: 일부 성공 + 특정 파일의 권한 오류를 **보고하며** 종료 → 부분 결과와 진단 정보가 모두 존재.
- **서브에이전트 3**: 프로세스가 **아무 출력 없이 크래시** → 결과물도, 오류 로그도, 어디까지 진행했는지도 알 수 없음.

코디네이터의 후속 처리는 달라야 합니다.

| | 서브에이전트 2 | 서브에이전트 3 |
|---|---|---|
| 가진 정보 | 부분 결과 + 구체적 실패 원인 | 아무것도 없음 |
| 조치 | 부분 결과를 그대로 활용하고, 보고된 그 한 파일의 권한 문제만 핀포인트로 해결(권한 부여 후 재시도) | 진행 상황을 판단할 근거가 없으므로 **폴더 전체를 미처리(unprocessed)로 간주**하고 처음부터 재작업 |

여기서 나오는 원칙:

1. **진단 정보의 유무가 처리 전략을 가른다.** 보고된 실패는 정밀 조치가 가능하고, 침묵한 크래시는 보수적 전량 재처리가 안전합니다.
2. **원인을 추측하지 말 것.** "크래시도 아마 권한 문제였겠지"라고 가정하고 처리하는 것은 위험한 자율성 설계입니다. 데이터 없이 내리는 추정은 잘못된 복구로 이어집니다.
3. **미완료를 완료로 표시하지 말 것.** "대부분 성공했으니 완료"나 "오류 보고가 없었으니 완료"는 조용한 데이터 누락을 만듭니다. 특히 크래시한 에이전트는 오류를 보고할 기회조차 없었다는 점이 중요합니다.
4. **유효한 부분 결과를 버리지 말 것.** 둘을 똑같이 취급해 서브에이전트 2의 결과까지 폐기하는 것은 비효율입니다.

## 7. MCP (Model Context Protocol)

### 7.1 MCP란 무엇인가
MCP는 AI 애플리케이션(호스트/클라이언트)과 외부 도구·데이터 제공자(서버) 사이의 **표준 연결 규약**입니다. USB 규격에 비유할 수 있습니다. 서버를 MCP 규격에 맞춰 한 번 만들면, MCP를 지원하는 어떤 클라이언트(Claude Code 등)에서도 그대로 붙일 수 있습니다.

- **MCP 서버**: 도구(tools), 리소스(resources), 프롬프트(prompts)를 노출하는 프로세스. 로컬에서 실행될 수도, 원격 HTTP로 붙을 수도 있습니다. 예: Notion 워크스페이스 조회 서버, 사내 티켓 시스템 서버.
- **MCP 클라이언트 / 호스트**: 서버에 연결해서 도구 목록을 받아오고, 모델에게 그 도구들을 제시하며, 모델이 호출을 요청하면 서버에 실제로 전달합니다.

### 7.2 MCP 서버 등록 스코프 (Scope)
서버 설정을 **어디에 저장하느냐**에 따라 누구에게 보이고 어디서 로드되는지가 결정됩니다.

| 스코프 | 저장 위치 | 적용 범위 | 팀 공유 여부 |
|---|---|---|---|
| **user (사용자)** | `~/.claude.json` (홈 디렉터리) | 그 머신에서 여는 **모든 프로젝트** | 공유 안 됨 (프로젝트 코드베이스 밖) |
| **project (프로젝트)** | 프로젝트 루트의 `.mcp.json` | 그 프로젝트에서만 | Git에 커밋되어 **팀 전체에 공유** |
| **local (로컬)** | 프로젝트별 로컬 설정 | 그 프로젝트에서, 나에게만 | 공유 안 됨 |

선택 기준을 요구사항에서 뽑아내는 방법:

- "다른 팀원에게 보이면 안 된다" → 프로젝트에 커밋되는 `.mcp.json`(project scope)은 탈락.
- "내 머신에서 **어떤 프로젝트를 열든** 항상 쓰고 싶다" → 특정 프로젝트 디렉터리에 묶이는 local scope도 탈락.
- 두 조건을 동시에 만족하는 것은 **user scope (`~/.claude.json`)** 뿐입니다.

예: 개인 Notion 워크스페이스를 조회하는 실험용 로컬 MCP 서버 → user scope.

주의할 오해들:
- project scope 항목을 `.gitignore`로 빼도 여전히 **그 프로젝트 디렉터리에 묶여 있어서** 다른 프로젝트에서는 로드되지 않습니다. "공유 안 됨"은 해결해도 "모든 프로젝트에서 사용"은 해결되지 않습니다.
- `.claude/settings.json`은 Claude Code 동작 설정(권한, 훅, 환경변수 등)을 담는 파일이며, 모든 프로젝트에 전역으로 MCP 서버를 연동하는 표준 경로가 아닙니다.
- project scope에는 "개인 전용으로 표시(mark as personal-only)" 같은 토글이 따로 없습니다. 개인 전용이 필요하면 애초에 스코프를 다르게 골라야 합니다.

일반적인 등록 방식은 CLI로 스코프를 명시하는 형태입니다.

```
claude mcp add --scope user notion-personal -- npx -y @my/notion-mcp-server
```

### 7.3 예약된 내장 이름 (Reserved Built-in Names)
호스트는 자체 기능을 위해 특정 MCP 서버 이름을 예약해 둘 수 있습니다. 예를 들어 `computer-use`는 화면 조작·GUI 제어를 위한 내장 식별자입니다.

커스텀 서버에 이런 예약 이름을 붙이면, 호스트는 이름 충돌과 섀도잉(shadowing)을 막기 위해 **그 서버 등록을 거부하거나 건너뜁니다.** 해결책은 단순합니다. 겹치지 않는 다른 이름(`custom-computer-use`, `my-screenshot-tool` 등)을 고르면 됩니다.

일어나지 않는 일들:
- 서버는 로드되고 특정 도구만 몰래 제거되는 부분 로드는 없습니다.
- 커스텀 서버가 내장 서버를 덮어써서 숨기는 것은 허용되지 않습니다.
- 예약 이름 아래에 커스텀 도구와 내장 도구를 병합해 주지도 않습니다.

### 7.4 동적 도구 목록 변경: `list_changed` 알림
MCP 서버의 도구 목록은 세션 시작 시점에 고정되지 않습니다. 서버는 자기 백엔드 상태가 바뀌어 도구가 추가·제거·변경되면 **`notifications/tools/list_changed`** 라는 알림을 클라이언트에 보낼 수 있습니다.

클라이언트(예: Claude Code)의 올바른 동작은:
1. 알림을 수신하고,
2. 해당 서버에 `tools/list`를 다시 호출해 **도구 목록을 자동으로 새로고침**하고,
3. 새 도구를 즉시 사용 가능하게 만듭니다.

이때 **연결을 끊었다 다시 붙일 필요도, 사용자가 수동으로 새로고침할 필요도 없습니다.** 장시간 실행되는 세션 도중에도 도구 구성이 진화할 수 있게 하는 것이 이 알림의 존재 이유입니다.

잘못된 기대들:
- "도구는 세션 시작 때만 로드되고 동적 갱신은 없다" → 사실이 아닙니다.
- "사용자가 `/mcp`에서 수동으로 Refresh tools를 눌러야 한다" → 서버가 알림을 보낸 경우에는 불필요합니다.
- "연결을 끊고 조용히 재연결한다" → 진행 중인 도구 호출을 잃게 되고, 프로토콜이 의도한 동작도 아닙니다.

(비슷한 방식으로 리소스와 프롬프트에도 각각 list_changed 알림이 있습니다.)

## 8. 파일 편집 도구 사용 패턴 (Claude Code / 에이전트 SDK)

에이전트가 코드 파일을 다룰 때 쓰는 대표 도구들과 각자의 용도입니다.

| 도구 | 하는 일 | 하지 않는 일 |
|---|---|---|
| `Read` | 파일 내용을 읽어 옴 | 수정하지 않음 |
| `Write` | 파일 전체를 주어진 내용으로 덮어씀 | 부분 수정에는 과함 |
| `Edit` | `old_string`을 찾아 `new_string`으로 정확히 치환. 국소 수정용 | 대규모 전면 변경에는 비효율 |
| `Glob` | 경로 패턴(`**/*.ts` 등)으로 **파일 경로**를 찾음. 수정 시간순 정렬 결과 반환 | 파일 **내용**을 읽거나 고치지 않음 |
| `Grep` | 파일 내용에서 정규식 패턴 **검색**. `output_mode: content`면 매칭 줄을 보여 줌 | 파일을 다시 쓰지 않음. 읽기 전용 |

### 8.1 `Write` vs `Edit` 선택 기준
- **몇 줄만 고친다** → `Edit`. 주변 맥락을 유지하고 diff가 작습니다.
- **파일 거의 전체가 바뀐다** (전체 재들여쓰기, 전면 포매팅, 생성 파일 재생성) → `Write` 한 번으로 전체를 덮어쓰는 것이 정석입니다.

예: 900줄짜리 파일의 거의 모든 줄에서 선행 공백이 제각각이라 들여쓰기를 표준화해야 하는 경우, 줄마다 `Edit`을 900번 호출하는 것은 토큰과 API 요청 면에서 극단적으로 비효율적입니다. 재정렬된 전체 내용을 담아 `Write`를 **한 번** 부르는 것이 맞습니다.

### 8.2 덮어쓰기 전 최신 상태 확인
`Write`로 전체를 덮어쓰기 전에는 파일을 다시 `Read`해서 현재 내용을 확정하는 것이 모범 사례입니다. 이전에 한 번 읽었더라도, 그 사이 외부 도구나 다른 프로세스가 파일을 바꿨을 수 있기 때문입니다. 많은 에이전트 하네스는 "읽지 않은 파일의 덮어쓰기"를 아예 막기도 합니다.

패턴 요약: **Read(최신 확인) → Write(전체 1회 호출).**

### 8.3 도구 목적을 혼동하지 말 것
- `Glob`은 검색 도구이며 파일 내부 공백을 정규화하는 기능이 없습니다. 수정 시간순 정렬은 "어떤 파일이 최근에 바뀌었나"를 알려 줄 뿐입니다.
- `Grep`은 조회 도구이며 "줄을 가져오면서 동시에 제자리에서 다시 쓴다"는 동작은 존재하지 않습니다.

이런 혼동은 도구 이름만 보고 기능을 추정할 때 생깁니다. 각 도구의 **부작용(side effect) 유무**를 정확히 알아 두는 것이 중요합니다.

## 9. 전체를 관통하는 설계 원칙 요약

1. **도구 정의는 모델을 위한 문서다.** 설명이 곧 라우팅 정확도. 서로 다른 도구는 서로 다르고 배타적인 설명을 가져야 한다.
2. **제약은 프롬프트가 아니라 구조로 건다.** "쓰지 마세요"라고 부탁하는 대신 도구를 제거한다.
3. **최소 권한 원칙.** 각 에이전트에게 역할에 필요한 최소한의 도구만. 예외가 필요하면 전체 세트가 아니라 좁은 단일 도구로.
4. **자율성은 남긴다.** 도구 오용은 도구 목록으로 막고, `tool_choice`는 `auto`로 두어 행동/응답 판단은 모델에게 맡긴다.
5. **오류는 두 층으로.** 사람이 읽을 설명 + 기계가 판단할 카테고리/재시도 플래그.
6. **실패해도 성과는 보존하고, 실패는 숨기지 않는다.** 부분 결과 + 명시적 미해결 보고.
7. **정보가 없으면 추측하지 말고 보수적으로.** 진단 데이터 없는 크래시는 전량 재처리.
8. **설정은 요구사항에서 역산한다.** "누구에게 보이나 / 어디서 로드되나" 두 축으로 스코프를 고른다.
9. **작업 규모에 맞는 도구를 쓴다.** 국소 수정은 Edit, 전면 변경은 Write 한 번.

## 10. 용어 사전 (Glossary)

| 영어 용어 | 한국어 설명 |
|---|---|
| **Tool / Function Calling** | 모델이 직접 실행하지 않고 "이 함수를 이렇게 불러 달라"는 요청을 출력하면 애플리케이션이 실행해 결과를 되돌려 주는 방식 |
| **Tool Definition** | 도구의 `name`, `description`, `input_schema`로 이루어진 선언. 모델이 도구를 이해하는 유일한 근거 |
| **Tool Description** | 도구의 자연어 설명. 모델이 유사 도구 중 하나를 고를 때 쓰는 주된 신호 |
| **Input Schema** | 도구 입력 파라미터의 JSON Schema. 타입·필수 여부·필드 설명 포함 |
| **Tool Selection / Routing** | 모델이 여러 도구 중 어떤 것을 호출할지 결정하는 과정 |
| **Tool Registry** | 시스템이 보유한 도구들의 목록/저장소. 여러 에이전트가 공유하면 불필요한 노출이 생길 수 있음 |
| **Tool Scoping** | 에이전트별로 노출할 도구를 역할에 맞게 제한하는 설계 |
| **Principle of Least Privilege** | 최소 권한 원칙. 각 주체에게 작업 수행에 꼭 필요한 권한(도구)만 부여 |
| **Cross-Role Tool** | 원래 다른 역할의 소관인 도구. 필요하면 전체가 아닌 좁은 단일 도구로만 허용 |
| **Negative Guidance** | "이럴 때는 이 도구 대신 저 도구를 써라"처럼 경계를 명시하는 안내 |
| **Few-Shot (예시 쿼리)** | 도구 설명에 대표 요청 예시를 한둘 넣어 사용 시점을 구체적으로 알려 주는 기법 |
| **Anchoring / Keyword Association Bias** | 시스템 프롬프트의 특정 단어가 이름이 비슷한 도구 쪽으로 모델 선택을 끌어당기는 편향 |
| **System Prompt** | 대화 전체에 걸쳐 모델의 역할과 규칙을 정하는 상위 지시문. 도구 설명보다 강하게 작용할 수 있음 |
| **Temperature** | 생성 시 무작위성을 조절하는 샘플링 파라미터. 모델 호출 단위 설정이며 도구별 속성이 아님 |
| **Context Window** | 한 번의 요청에 담을 수 있는 토큰 총량의 한계 |
| **tool_choice** | 이번 턴에 도구를 쓸지 말지 제어하는 API 파라미터 |
| **tool_choice: auto** | 모델이 턴마다 도구 호출 여부를 스스로 결정 (기본값) |
| **tool_choice: any** | 반드시 제공된 도구 중 최소 하나를 호출해야 함. 텍스트만 응답 불가 |
| **tool_choice: tool (name 지정)** | 지정된 단 하나의 도구를 강제 호출 |
| **tool_choice: none** | 도구 호출 금지, 텍스트 응답만 허용 |
| **Tool Result** | 도구 실행 후 모델에게 되돌려 주는 결과 메시지 |
| **isError** | 도구 결과가 실패임을 표시하는 플래그 |
| **Text Block** | 결과 중 자연어 문장 부분. 모델이 사용자에게 그대로 설명할 수 있는 내용 |
| **Structured Content / Metadata** | 결과 중 기계가 읽는 구조화 필드. 카테고리·재시도 여부 등 제어 정보 |
| **errorCategory** | 오류의 성격 분류. `transient`, `business`, `permission`, `validation` 등 |
| **transient (오류)** | 일시적 오류. 잠시 후 동일 요청 재시도가 유효 |
| **business (오류)** | 비즈니스 규칙 위반. 같은 입력으로는 결과가 바뀌지 않아 재시도 무의미 |
| **permission (오류)** | 권한/자격 증명 부족. 같은 자격 증명으로 재시도해도 실패 |
| **isRetryable** | 동일 요청 재시도가 성공 가능한지 알려 주는 불리언 플래그 |
| **description (오류 필드)** | 실패의 구체적 사유를 담은 사람이 읽을 수 있는 문장 |
| **Stack Trace** | 예외 발생 위치를 담은 날것의 디버깅 출력. 모델에게 그대로 넘기면 안 되는 형태 |
| **Coordinator / Orchestrator** | 작업을 나눠 서브에이전트에게 위임하고 결과를 취합하는 상위 에이전트 |
| **Subagent** | 좁은 역할 하나를 맡아 수행하는 하위 에이전트 |
| **Synthesis Agent** | 이미 수집된 자료를 종합해 최종 답변을 만드는 에이전트 |
| **Partial Results** | 배치 작업 중 성공한 일부 결과. 실패가 있어도 버리지 않고 상위로 전달해야 함 |
| **Graceful Failure Reporting** | 실패 시 부분 결과 + 미해결 항목 + 오류 원인 + 시도 내역을 명시해 보고하는 방식 |
| **Silent Dropping** | 실패 항목을 알리지 않고 누락시키는 안티패턴. 데이터 정합성을 깨뜨림 |
| **Process Crash** | 출력도 로그도 없이 프로세스가 죽는 것. 진단 정보가 없어 전량 재처리가 안전 |
| **Unprocessed** | 미처리 상태 표시. 재작업 대상임을 나타냄 |
| **Escalation** | 하위에서 해결 못 한 문제를 더 높은 권한의 주체에게 넘기는 것 |
| **MCP (Model Context Protocol)** | AI 애플리케이션과 외부 도구/데이터 제공자를 잇는 표준 연결 규약 |
| **MCP Server** | 도구·리소스·프롬프트를 MCP 규격으로 노출하는 프로세스 (로컬 또는 원격) |
| **MCP Client / Host** | MCP 서버에 연결해 도구 목록을 받고 모델에 제시하며 호출을 중계하는 쪽 |
| **User Scope** | `~/.claude.json`에 저장. 그 머신의 모든 프로젝트에 적용되며 팀과 공유되지 않음 |
| **Project Scope** | 프로젝트 루트 `.mcp.json`에 저장. Git으로 팀 전체에 공유되며 그 프로젝트에만 적용 |
| **Local Scope** | 특정 프로젝트에서 나에게만 적용되는 개인 설정 |
| **`.mcp.json`** | 프로젝트 스코프 MCP 서버 설정 파일 |
| **`~/.claude.json`** | 사용자(전역) 스코프 설정 파일 |
| **`.claude/settings.json`** | Claude Code의 동작 설정 파일(권한·훅·환경변수 등). 전역 MCP 등록 경로가 아님 |
| **Reserved Built-in Name** | 호스트가 내장 기능용으로 예약한 서버 이름. 커스텀 서버가 쓰면 등록이 거부/스킵됨 |
| **`computer-use`** | 화면 조작·GUI 제어용 예약된 내장 식별자 |
| **Shadowing** | 같은 이름의 커스텀 항목이 내장 항목을 가려 버리는 현상. 예약어 정책으로 방지 |
| **`list_changed` Notification** | 서버의 도구/리소스/프롬프트 목록이 바뀌었음을 클라이언트에 알리는 MCP 알림 |
| **`tools/list`** | 서버의 도구 목록을 조회하는 MCP 요청. `list_changed` 수신 후 자동 재호출됨 |
| **Dynamic Tool Refresh** | 세션 중간에 재연결 없이 도구 목록을 자동 갱신하는 동작 |
| **`/mcp`** | Claude Code에서 MCP 서버 상태를 확인·관리하는 명령 |
| **Read (도구)** | 파일 내용을 읽는 도구. 수정하지 않음 |
| **Write (도구)** | 파일 전체를 덮어쓰는 도구. 전면 변경에 적합 |
| **Edit (도구)** | `old_string`을 `new_string`으로 치환하는 국소 수정 도구 |
| **Glob (도구)** | 경로 패턴으로 파일 경로를 찾는 검색 도구. 수정 시간순 정렬. 내용 변경 없음 |
| **Grep (도구)** | 파일 내용을 정규식으로 검색하는 읽기 전용 도구. `output_mode: content`로 매칭 줄 출력 |
| **Separation of Concerns** | 관심사 분리. 각 구성 요소가 자기 책임 범위만 담당하도록 나누는 설계 원칙 |
| **Over-privileging** | 필요 이상의 권한/도구를 부여해 오용 위험을 만드는 안티패턴 |
