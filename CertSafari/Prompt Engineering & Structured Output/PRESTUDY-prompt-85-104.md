# 사전 학습 노트 — 프롬프트 엔지니어링과 구조화된 출력 (Prompt Engineering & Structured Output)

이 문서는 Claude API를 이용해 "코드 리뷰 자동화", "문서 필드 추출", "티켓 분류" 같은 시스템을 만들 때 알아야 할 개념들을 **아무것도 모르는 상태에서** 읽을 수 있도록 처음부터 설명한다.

---

## 0. 큰 그림: 우리가 만들려는 것

LLM(대규모 언어 모델, 여기서는 Claude)을 **소프트웨어 부품처럼** 파이프라인에 끼워 넣는 상황을 가정한다. 대표적인 두 가지 형태가 반복해서 등장한다.

1. **자동 코드 검토기(Automated Code Reviewer)**
   - 입력: Pull Request의 diff(변경된 코드 조각)
   - 출력: "발견 사항(finding)" 목록 — 어디에 어떤 문제가 있는지
   - 이 출력을 CI/CD 파이프라인이 받아서 자동 수정하거나, 사람에게 넘기거나, 병합을 막는다.

2. **문서 추출기(Document Extraction)**
   - 입력: 송장(invoice), 진료 기록, 고객 티켓 같은 자유 형식 텍스트
   - 출력: 정해진 스키마(schema)를 따르는 JSON — 예: `{"vendor": "...", "total": 1200, "currency": "USD"}`
   - 이 JSON을 DB에 넣거나 재고/회계 시스템이 그대로 사용한다.

두 경우 모두 **LLM의 출력이 사람이 읽는 글이 아니라, 다른 프로그램이 먹는 데이터**라는 점이 핵심이다. 그래서 "형식이 항상 맞는가", "틀린 걸 맞다고 하지는 않는가", "얼마나 확신하는가"가 전부 중요해진다.

## 1. 기초 용어: 오탐, 정밀도, 발견 사항

### 1.1 Finding (발견 사항)
검토 도구가 찾아낸 문제 하나를 가리키는 단위. 보통 다음 정보를 담는다.
- 위치(파일, 줄 번호)
- 문제 설명
- 심각도(severity)
- (설계에 따라) 신뢰도(confidence), 이 문제를 촉발한 코드 패턴 이름 등

### 1.2 False Positive (오탐)
**실제로는 문제가 아닌데 문제라고 잘못 표시한 것.** 반대는 False Negative(미탐, 진짜 문제인데 놓친 것).

예시. 파이썬에서 `except Exception:` 처럼 모든 예외를 잡는 광범위한 except 절은 보통 나쁜 습관이다. 하지만:

```python
# (1) 진짜 문제 — 에러를 삼켜버림
try:
    charge_card(user)
except Exception:
    pass          # 결제 실패가 조용히 사라진다

# (2) 문제 아님 — 최상위 에러 경계에서 로깅 후 재발생
try:
    run_request(req)
except Exception:
    logger.exception("unhandled")
    raise         # 로그만 남기고 그대로 다시 던진다
```

(2)까지 문제라고 표시하면 그게 오탐이다.

### 1.3 Precision (정밀도) / Recall (재현율)
- **정밀도** = 도구가 "문제다"라고 말한 것 중 실제로 문제인 비율. 오탐이 많으면 정밀도가 낮다.
- **재현율** = 실제 문제 중 도구가 찾아낸 비율. 미탐이 많으면 재현율이 낮다.

둘은 대개 맞바꾸는(trade-off) 관계다. 검사 규칙을 아예 없애면 오탐은 0이 되지만 재현율도 0이 된다 — 즉 **"규칙을 삭제한다"는 오탐 문제의 해결책이 아니다.** 목표는 항상 "진짜 문제는 계속 잡으면서 오탐만 줄인다"이다.

### 1.4 Alert Fatigue (알림 피로)
오탐이 많으면 사람이 도구의 출력을 아예 안 읽게 된다. 이 순간 정확했던 다른 카테고리의 결과까지 함께 무시당한다. 즉 **한 카테고리의 노이즈가 시스템 전체의 신뢰를 무너뜨린다.**

대응 원칙:
- 노이즈가 심한 카테고리는 **즉시 비활성화(격리)** 하고, 별도로 프롬프트를 개선한 뒤 재활성화한다.
- 하지 말아야 할 것: 노이즈 카테고리를 정확한 카테고리에 **합치기**(정확한 쪽까지 오염됨), 심각도만 낮춰서 계속 노출하기(여전히 읽는 비용 발생), "일부 카테고리는 정확도가 낮습니다"라는 **면책 배너**만 붙이기(판단 부담을 사람에게 떠넘길 뿐 노이즈는 그대로).

## 2. 신뢰도 기반 라우팅과 Human-in-the-Loop

### 2.1 Confidence Level (신뢰도 수준)
모델이 각 발견 사항에 대해 "내가 이걸 얼마나 확신하는가"를 함께 출력하게 하는 것. 보통 `high / medium / low` 같은 열거값이나 0~1 점수로 만든다. **severity(심각도)와는 완전히 다른 축**이다.

- **severity**: 이게 진짜 버그라면 얼마나 위험한가
- **confidence**: 이게 진짜 버그일 가능성이 얼마나 되는가

심각도가 아주 높아도 신뢰도가 낮으면 자동으로 고쳐서는 안 된다.

### 2.2 Human-in-the-Loop (HITL, 사람 개입 루프)
자동화를 100%로 밀어붙이지 않고, **불확실한 건만 사람에게 넘기는** 설계. 전형적인 형태:

```
findings → confidence 태그 부여
        ├─ high   → 자동 수정(auto-fix) 후 커밋
        └─ low/medium → 사람 검토 큐로 라우팅
```

이것을 **Confidence-based Routing(신뢰도 기반 분기)** 이라고 부른다. 장점:
- 확실한 것은 사람 시간을 안 쓴다.
- 불확실한 것이 자동으로 코드에 반영되어 사고를 내는 일이 없다.
- 사람에게 넘긴 것도 **버려지지 않는다** — 모델이 스스로 의심스러운 항목을 조용히 폐기(quietly discard)하면 사람이 검토할 기회조차 사라지므로 이는 잘못된 설계다.

### 2.3 구조화가 라우팅의 전제 조건
자동 분기를 하려면 신뢰도가 **필드로 분리되어** 있어야 한다. 모든 발견 사항을 하나의 요약 문단으로 뭉쳐 놓으면 프로그램이 파싱할 수 없고, 결국 사람이 다시 읽어서 판단해야 한다. **자동화하려면 구조화하라**가 원칙이다.

## 3. 프롬프트 설계 기법

### 3.1 Zero-shot vs Few-shot
- **Zero-shot(제로샷)**: 예시 없이 지시문(instruction)만 준다. "버그를 찾아라."
- **Few-shot(퓨샷)**: 입력–정답 쌍 예시를 몇 개 프롬프트에 넣어 준다. 모델은 그 예시에서 판정 기준을 읽어낸다. 이를 **In-context Learning(문맥 내 학습)** 이라 한다 — 모델 가중치를 바꾸는 학습(fine-tuning)이 아니라, 프롬프트 안에서만 일어나는 임시 학습이다.

경험칙: **지시문을 길게 늘려 쓰는 것보다 예시 몇 개가 훨씬 강력하다.** 규칙을 문장으로 아무리 촘촘히 나열해도 모델이 그중 일부를 놓치는 현상(instruction drift)이 생기고, 프롬프트만 비대해진다.

### 3.2 Paired / Contrasting Examples (대조 예시)
"같은 패턴인데 어떤 때는 문제이고 어떤 때는 괜찮다"는 미묘한 경계는 **문제가 되는 사례와 허용되는 사례를 짝지어** 각각의 정답(verdict)과 함께 주는 것이 가장 효과적이다. 앞의 `except Exception:` 예시 (1)/(2)를 그대로 프롬프트에 넣고 각각 `verdict: issue`, `verdict: acceptable` 라벨을 붙이면 모델이 경계 조건을 학습한다.

```
예시 1:
  코드: try: charge_card(user) / except Exception: pass
  판정: issue — 예외를 삼켜 실패가 은폐됨

예시 2:
  코드: try: run_request(req) / except Exception: logger.exception(...); raise
  판정: acceptable — 최상위 에러 경계, 로깅 후 재발생
```

### 3.3 좋은 예시 세트의 조건
분류 일관성을 높이기 위한 예시 세트는 다음을 만족해야 한다.

- **개수는 3~5개 정도.** 너무 적으면 기준이 안 잡히고, 너무 많으면 프롬프트만 길어진다.
- **다양성(diverse).** 명백한 버그, 명백한 스타일 이슈, 그리고 **판정이 애매한 경계선 사례(borderline case)** 를 모두 포함한다. 경계선 사례가 실제로 판정이 흔들리는 지점이므로 가장 값어치가 크다.
- **라벨 + 짧은 이유.** 정답 라벨만 주는 것보다 "왜 그 라벨인지" 한 줄 이유를 붙이면 모델이 기준을 일반화하기 쉽다.
- **한 가지 유형을 10개 복제하지 않는다.** 같은 off-by-one 버그만 변주해서 10개 넣으면 그 패턴만 과적합되고 다른 유형을 놓친다.
- **하나의 극단적 사례를 장황하게 쓰지 않는다.** "역사상 가장 심각했던 버그" 하나를 아주 자세히 넣으면 척도가 그쪽으로 쏠려(anchoring) 평범한 버그를 과소평가한다.

### 3.4 다양한 입력 형태에 대한 예시
문서 추출에서 입력 레이아웃이 제각각일 때(표, 일반 단락, 여러 통화로 나뉜 합계 등), **실제로 들어오는 레이아웃 유형별로 원본–정답 추출 결과 쌍**을 소량씩 넣어 주는 것이 가장 효과적이다. 각 유형에서 무엇을 뽑고 무엇을 무시할지 모델이 문맥으로 파악하게 된다.

같은 상황에서 피해야 할 접근:
- 모든 레이아웃 규칙을 서술식 문단으로 나열 → 길어지고 지시 누락 발생
- 모든 문서를 하나의 평문(plain text)으로 강제 전처리 → 표의 행·열 같은 **구조적/공간적 정보가 소실**되어 오히려 정확도가 떨어짐
- 출력 필드 수를 줄이기 → 요구사항을 포기하는 임시방편일 뿐 환각의 원인은 그대로

### 3.5 분류 기준을 고정하는 법 (일관성)
여러 PR, 여러 검토자에 걸쳐 심각도 분류가 흔들리지 않게 하려면 **각 등급마다 짧은 정의문 + 그 등급에 해당하는 구체적 코드 예시**를 프롬프트에 고정해 둔다. 이게 항상 같은 **참조 기준점(reference point)** 이 된다.

```
Critical: 원격 코드 실행이나 데이터 유실을 직접 초래.
  예) 사용자 입력을 그대로 os.system()에 전달

High: 정상 경로에서 잘못된 결과나 장애를 유발.
  예) 결제 금액 계산에서 반올림 누락
...
```

피해야 할 방식:
- "얼마나 긴급하게 **느껴지는지**" 같은 주관적 기준 → 호출마다 흔들린다.
- 무조건 medium을 기본값으로 잡고 필요할 때만 조정 → 중앙으로 쏠리는 편향만 생기고, 등급별 기준 자체가 없어 근본 해결이 아니다.
- "최근 10개 PR의 평균 심각도와 비교" → **기준선(baseline)이 계속 움직여서** 절대적 일관성이 불가능하다.

### 3.6 환각(Hallucination)과 null 허용 예시
**환각**은 근거가 없는데 그럴듯한 값을 지어내는 현상이다. 예: 진료 기록에 "알약 두어 개(a couple tablets)"라고만 적혀 있는데 모델이 `dosage: 2`라는 정확한 숫자를 만들어내는 것.

해결책: 정규화(normalization) 예시와 **"값을 채울 수 없을 때는 null을 낸다"는 예시를 함께** 준다.

```
입력: "매일 아침 500mg 한 알"     → {"amount": 500, "unit": "mg", "note": null}
입력: "알약 두어 개"              → {"amount": null, "unit": null, "note": "a couple tablets"}
입력: "물 반 컵 정도"             → {"amount": null, "unit": null, "note": "about half a cup"}
```

핵심은 **모델에게 "모른다"고 말할 출구를 제공**하는 것이다. 반대로 스키마에서 모든 dosage 필드를 `required`로 만들면 모델은 값을 채워야만 하므로 오히려 환각이 늘어난다. 사후 정규식 필터로 숫자 아닌 값을 걷어내는 방식은 "알약 두어 개" 같은 **비정형이지만 쓸모 있는 정보까지 버린다.** 임의로 미터법 단위 변환을 시키는 것도 없는 정보를 만들어내는 행위다.

## 4. 프롬프트 체이닝과 다중 인스턴스 설계

### 4.1 Prompt Chaining (프롬프트 체이닝)
하나의 큰 작업을 여러 번의 API 호출로 쪼개고, 앞 호출의 출력을 뒤 호출의 입력으로 넘기는 구조.

```
1차 호출: diff → 초안 발견 사항 12개 생성 (recall 위주)
2차 호출: 각 초안 → 명시적 기준에 비추어 개별 검증 (precision 위주)
결과: 검증 통과한 항목만 최종 확정
```

**왜 단일 호출(single-pass)보다 정밀도가 높아지는가?**
한 번의 응답에서 수십 개 후보를 동시에 찾고, 서술하고, 형식을 맞추고, 기준까지 적용하려면 모델의 주의가 분산된다(cognitive load). 그 결과 기준을 느슨하게 적용해 오탐이 섞인다. 2차 패스는 **이미 뽑힌 항목 하나하나만 놓고 기준 충족 여부만 독립적으로(in isolation)** 판단하므로 훨씬 엄격해진다.

주의: 체이닝의 이점은 **작업 분리라는 구조** 에서 나온다. "두 번째 호출이 자동으로 더 좋은 모델을 쓴다"거나 "시스템 프롬프트가 리셋되어 편향이 지워진다"거나 "컨텍스트 양이 두 배가 된다" 같은 설명은 사실이 아니다.

### 4.2 Generator / Reviewer 분리 (독립 검토자 패턴)
코드를 만든(또는 발견 사항을 만든) 인스턴스와 그것을 검토하는 인스턴스를 **분리된 호출**로 둔다. 목적은 **편향되지 않은 제3자 시각**이다.

이 패턴을 무력화하는 대표적 실수: 토큰을 아끼려고 **생성자가 스스로 쓴 요약본**을 검토자에게 넘기는 것. 그러면 검토자는 실제 코드가 아니라 **생성자의 주관적 프레이밍(self-framing)** 을 평가하게 된다. 생성자가 놓치거나 잘못 이해한 부분은 요약에도 없으므로 영원히 발견되지 않는다. 검토자에게는 **원본 diff(raw context)** 를 그대로 줘야 한다.

같은 이유로, 생성자가 자기 검토 결과 중 동의하지 않는 항목을 사람에게 보이기 전에 폐기하는 설계도 잘못이다.

### 4.3 Per-file Pass vs Integration Pass
큰 변경 묶음(changeset)을 검토할 때 흔히 2단계로 나눈다.

- **파일별 패스(per-file pass)**: 파일 하나씩만 보고 검토. 문법 오류, 스타일/들여쓰기, 명명 규칙, 그 파일 안의 중복 로직, 국소적 함수 로직 등 **한 파일 안에서 완결되는 문제**에 최적이다.
- **통합 패스(integration pass)**: 변경 묶음 전체를 함께 보고 검토. 파일별 패스가 원리적으로 볼 수 없는 것, 즉 **파일 간(cross-file) 문제**에 집중해야 한다.
  - 공유 인터페이스/계약(contract)을 파일마다 다르게 사용하는 경우
  - 데이터 흐름 불일치 — A 파일이 넘기는 값의 형태와 B 파일이 기대하는 형태가 다름
  - 한쪽에서 시그니처를 바꿨는데 다른 쪽 호출부를 안 고친 경우

핵심: 통합 패스가 파일 내부 문법이나 서식을 다시 보는 것은 **중복 낭비**다. 역할을 계층적으로 나눠야 한다.

## 5. 구조화된 출력(Structured Output)과 스키마 설계

### 5.1 JSON Schema 기초
LLM에게 "이 형태의 JSON으로 답하라"고 지시할 때 쓰는 명세. 필드 이름, 타입(`string`, `integer`, `boolean`, `array`, `object`), 필수 여부(`required`), 허용값 목록(`enum`) 등을 기술한다.

```json
{
  "type": "object",
  "properties": {
    "category":         {"type": "string", "enum": ["billing","technical","shipping","account","refund"]},
    "confidence":       {"type": "string", "enum": ["high","medium","low"]},
    "detected_pattern": {"type": "string"},
    "severity":         {"type": "string", "enum": ["critical","high","medium","low"]}
  },
  "required": ["category", "confidence"]
}
```

### 5.2 Enum과 "other" 폴백 패턴
`enum`은 값을 정해진 목록으로 제한한다(**closed enum, 폐쇄형 열거형**). 문제는 현실 데이터에 그 목록에 안 맞는 것이 섞일 때다. 모델은 답을 내야 하므로 **가장 비슷해 보이는 값에 억지로 끼워 맞춘다(forced fitting).** 그러면 잘못된 라벨이 조용히 데이터에 섞여 기존 카테고리 통계까지 오염된다.

해결: **`other` 값을 enum에 추가하고, 그와 함께 자유 텍스트 상세 필드를 둔다.**

```json
"category": {"enum": ["billing","technical","shipping","account","refund","other"]},
"category_detail": {"type": "string", "description": "category가 other일 때 실제 내용"}
```

이렇게 하면 애매한 건이 `other`로 격리되어 5개 정상 카테고리가 깨끗하게 유지되고, `category_detail`을 나중에 분석해 새 카테고리를 만들 근거로 쓸 수 있다.

피해야 할 대안:
- enum을 없애고 완전 자유 텍스트로 → 표기가 제각각이 되어 집계 불가
- `strict`를 끄고 필드를 생략하게 → 데이터에 구멍이 생기고 감사가 불가능
- `miscellaneous_unclear_ticket_type_pending_manual_review` 같은 장황한 6번째 값 하나만 추가 → **상세 내용을 담을 자유 텍스트 필드가 없어** 왜 애매했는지 알 수 없다

### 5.3 분석 가능성을 위한 필드 설계 (Observability)
"어떤 종류의 경고가 자주 기각(dismiss)되는가"를 시간에 따라 분석하려면, 스키마에 **그 경고를 촉발한 구문/규칙을 식별하는 범주형 필드**가 있어야 한다.

```json
"detected_pattern": {"type": "string", "example": "sanitize_input_helper_call"}
```

이 필드가 있으면 `SELECT detected_pattern, COUNT(*) FROM findings WHERE dismissed = true GROUP BY detected_pattern` 같은 집계가 가능해진다. 반면:
- 발견 사항당 **단일 종합 신뢰도 점수만** 있고 어떤 규칙이 만들었는지 기록이 없으면 → 원인 추적 불가
- **자유 텍스트 코멘트**만 있으면 → 검토자마다 표현이 달라 그룹화·집계 불가
- 모든 경고의 severity를 일괄 상향 → 분석과 무관하고 알림 피로만 가중

원칙: **집계하고 싶은 축은 반드시 범주형(categorical) 필드로 저장하라.** 자유 텍스트는 분석 단위가 될 수 없다.

### 5.4 Strict Tool Use (`strict: true`)의 범위와 한계
`strict: true`를 켜면 모델의 출력이 정의된 JSON Schema를 **문법적으로 100% 준수**하도록 강제된다. 필드 이름이 틀리거나, `integer` 자리에 문자열이 오거나, 필수 필드가 빠지는 일이 없어진다.

**하지만 보장하는 것은 딱 두 가지뿐이다.**
- **구조 적합성(structural conformance)** — 필드 구성이 스키마와 일치
- **타입 적합성(type conformance)** — 각 값의 데이터 타입이 일치

**보장하지 않는 것:**
- 값이 원본 문서에 실제로 있던 사실인지 (환각 방지 아님)
- 값이 비즈니스적으로 말이 되는지

예: `quantity`가 `integer`여야 한다고 했을 때 `-99999`나 `1000000`도 스키마는 통과한다. 창고에 100만 개가 있을 리 없다는 판단은 스키마가 못 한다. 따라서 **비즈니스 타당성 검사(business-plausibility check)** 를 애플리케이션 코드에서 별도로 해야 한다.

```python
def validate(rec):
    q = rec["quantity"]            # strict:true 덕분에 int인 건 확실
    assert 0 < q <= MAX_PER_SHIPMENT, f"implausible quantity: {q}"
```

또한 `strict: true`는 내부적으로 원본을 다시 읽어 의미를 재확인하는 기능이 **아니다.** 필드 타입이 숫자라는 이유로 검증이 면제되는 것도 아니다.

## 6. `tool_choice` — 도구 호출 제어

Claude API에서 "도구(tool)"는 모델이 호출할 수 있는 함수 명세다. 구조화된 출력을 얻는 표준 방법이기도 하다: 원하는 JSON 스키마를 `input_schema`로 가진 도구를 하나 정의하고, 모델이 그 도구를 호출하게 만들면 인자가 곧 구조화된 출력이 된다.

`tool_choice`는 **모델이 도구를 호출할지 말지, 어떤 도구를 호출할지** 를 제어하는 요청 파라미터다.

| 설정 | 동작 |
|---|---|
| `{"type": "auto"}` | **기본값.** 모델이 알아서 판단. 도구를 부를 수도, 그냥 텍스트로만 답할 수도 있다. |
| `{"type": "any"}` | 등록된 도구 중 **반드시 하나 이상**을 호출해야 함. 어느 것을 고를지는 모델이 문맥 보고 결정. |
| `{"type": "tool", "name": "X"}` | **지정한 도구 X를 반드시** 호출. 다른 도구는 선택 불가. |
| `{"type": "none"}` | 도구를 전혀 호출하지 않음. |

### 6.1 텍스트 응답을 원천 차단해야 할 때
감사 추적(audit trail)처럼 "모든 문서가 반드시 구조화된 도구 호출을 만들어냈다"를 증명해야 하는 경우, `auto`로는 안 된다. 일부 요청이 `tool_use` 블록 없이 텍스트만 반환할 수 있기 때문이다. 시스템 프롬프트로 아무리 강하게 경고해도 이는 **확률적 설득일 뿐 보장이 아니다.**

해결: `tool_choice`를 `{"type": "any"}` 또는 `{"type": "tool", "name": "extract_record"}` 로 바꾼다.

참고로 다음은 이 문제와 무관하다.
- `max_tokens`를 키우기 → 잘림(truncation) 문제이지 도구 호출 여부 문제가 아니다
- `input_schema`의 필드를 optional → required로 바꾸기 → 도구를 **호출했을 때** 안의 필드 규칙일 뿐, 호출 자체를 강제하지 않는다

### 6.2 여러 도구 중 특정 하나를 이번 턴에 강제해야 할 때
`translate_text`, `summarize_document`, `extract_metadata`가 모두 등록되어 있는데 이번 턴에는 반드시 `extract_metadata`가 먼저 실행되어야 한다면:

```json
"tool_choice": {"type": "tool", "name": "extract_metadata"}
```

`any`는 "아무 도구나 하나"이므로 다른 도구가 선택될 수 있어 보장이 안 된다.

### 6.3 `any` + 여러 개의 작은 도구 (스키마 모듈화)
문서 종류(송장/영수증/발주서)가 업로드마다 다르고 한 번에 한 건씩 들어온다면, 두 가지 설계가 가능하다.

- (a) 모든 종류를 한 스키마에 담은 거대한 `extract_document` 도구 하나
- (b) `extract_invoice`, `extract_receipt`, `extract_purchase_order` 세 개의 작은 도구 + `tool_choice: {"type":"any"}`

**(b)가 `any`의 의도된 사용법이다.** `any`는 "반드시 도구를 호출하라(강제)" + "어떤 도구인지는 문서 내용 보고 네가 골라라(자율)"의 조합이다. 각 도구는 해당 문서 유형에만 맞는 좁고 명확한 스키마를 가지므로:
- 관련 없는 필드가 프롬프트 노이즈로 섞이지 않는다
- 어떤 유형으로 판정했는지가 **호출된 도구 이름 자체로** 드러난다
- 유형별 필수 필드를 각각 엄격하게 강제할 수 있다

반면 (a)의 거대 통합 스키마는 대부분 비어 있는 필드가 많아 모델이 혼동하고, 유형별 required 제약을 걸기 어렵다. 또한 **`any`가 도구 1개만 등록할 것을 요구한다는 말은 사실이 아니며**, `any`로 특정 도구를 기본값으로 고정할 수도 없다(그건 `{"type":"tool","name":...}`의 역할이다).

### 6.4 Extended Thinking과 `tool_choice`의 호환 제약
**Extended Thinking(확장 사고)** 은 모델이 최종 답을 내기 전에 내부적으로 길게 추론하도록 하는 기능이다(요청에 `thinking` 파라미터로 켠다). 어려운 판단이 필요할 때 정확도를 높인다.

**제약: Extended Thinking은 `tool_choice`가 `auto` 또는 `none`일 때만 사용할 수 있다.** 강제 도구 선택(`{"type":"any"}` 또는 `{"type":"tool","name":...}`)과 동시에 쓰면 API가 유효성 검사 오류를 반환한다.

즉 둘 중 하나를 골라야 한다.
- 확장 사고를 쓰고 싶다 → `tool_choice`를 `auto`로 내린다 (도구를 부를지는 모델에 맡김)
- 도구 호출을 반드시 강제해야 한다 → 확장 사고를 끈다

`input_schema` 안에 `thinking_mode` 같은 필드를 넣어 우회할 수 있다는 것은 사실이 아니다. `input_schema`는 도구 인자의 형태를 기술할 뿐 API 동작을 바꾸지 않는다.

## 7. Messages API vs Message Batches API

Claude API에는 요청을 보내는 두 가지 방식이 있다.

### 7.1 Messages API (동기식)
- HTTP 요청을 보내고 **그 자리에서 응답을 기다린다**(blocking).
- 보통 수 초 내 응답.
- 스트리밍 지원.
- 실시간 상호작용, 사용자가 기다리고 있는 화면, **CI 파이프라인이 결과를 기다리며 막혀 있는 상황**에 적합하다.

### 7.2 Message Batches API (비동기 배치)
- 많은 요청을 한 묶음으로 제출하고, 나중에 결과를 가져간다.
- **비용 50% 할인.**
- 처리 목표는 **최대 24시간 이내**이며, **지연 시간 SLA가 보장되지 않는다.** 대기열 상황에 따라 몇 분일 수도, 몇 시간일 수도 있다.
- 야간 대량 처리, 오프라인 분류/분석처럼 **즉시성이 필요 없는** 작업에 적합하다.

### 7.3 어느 쪽을 고를지 판단하는 기준
판단 축은 **비용이 아니라 지연 시간 요구사항**이다.

예: PR 병합을 막고 Claude의 판정을 기다리는 **merge gate**는 수 초 내 응답이 필요한 대표적 블로킹 워크플로우다. 50% 할인이 아무리 매력적이어도 개발자가 몇 시간씩 병합을 못 하면 생산성이 붕괴된다. → **동기식 Messages API**를 써야 한다.

반대로 야간에 송장 15만 장을 분류하는 작업은 아침까지만 끝나면 되므로 → **Batches API**.

### 7.4 배치당 제한 (Per-batch Limits)
단일 Message Batch 하나는 다음 한계 중 **먼저 도달하는 것**에 걸린다.

- **최대 100,000개 요청**
- **최대 256 MB 총 페이로드**

따라서 150,000건을 처리하려면 최소 2개의 배치로 나눠 제출해야 한다(예: 100,000 + 50,000). 스캔 이미지처럼 요청 하나가 큰 경우 총 용량이 256MB를 넘어 **개수와 무관하게 더 잘게 쪼개야 할 수도 있다.**

(참고로 "배치 최대 크기 1,000개", "시간당 500 요청 제한", "요청 수 제한 없음" 같은 수치는 모두 사실이 아니다.)

### 7.5 배치와 도구 사용
도구에는 두 종류가 있다.

- **클라이언트 측 도구(client-side tool)**: 모델이 `tool_use`를 출력하면 **애플리케이션이 직접 실행**하고 그 결과를 `tool_result`로 다시 보내야 한다. 즉 여러 번의 왕복(multi-turn)이 필요하다. 비동기 배치 구조에서는 이 왕복을 하기 어렵다.
- **서버 측 도구(server-side tool / built-in tool)**: 웹 검색(web search) 같은 것. **Anthropic 서버 내부에서 검색 실행과 결과 반영이 하나의 요청 안에서 자동으로 끝난다(self-contained).** 애플리케이션이 페이지를 가져오거나 결과를 되먹일 필요가 없다.

따라서 **서버 측 웹 검색 도구는 Message Batches API 안에서 정상 동작한다.** 배치가 도구 정의를 포함한 요청을 무조건 거부하는 것도 아니고, 서버 도구가 스트리밍 동기 응답에서만 작동하는 것도 아니며, 별도의 동기 요청을 병렬로 띄워 줄 필요도 없다.

## 8. 종합 체크리스트

LLM 기반 추출/검토 시스템을 설계할 때 스스로에게 던질 질문들.

1. 출력이 프로그램에 먹히는가? → **구조화된 스키마 + 도구 호출**로 받아라.
2. 도구 호출을 반드시 받아야 하는가? → `tool_choice`를 `any` 또는 특정 도구로 강제하라.
3. 확장 사고도 함께 쓰고 싶은가? → 강제 도구 선택과는 양립 불가. `auto`로 내려라.
4. 스키마가 통과했다고 값이 옳은가? → 아니다. **비즈니스 타당성 검사를 코드로 따로** 하라.
5. 예상 밖의 값이 들어오면? → `other` enum + 자유 텍스트 상세 필드.
6. 나중에 통계로 분석할 축이 있는가? → 그 축을 **범주형 필드**로 저장하라(`detected_pattern` 등).
7. 오탐이 많은가? → 규칙 삭제 대신 **대조 예시(paired examples)** 를 넣어라.
8. 분류가 흔들리는가? → 등급별 **정의문 + 구체 예시**를 고정 참조점으로 넣어라.
9. 정밀도를 더 올려야 하는가? → **생성 호출과 검증 호출을 분리(chaining)** 하라.
10. 검토자를 따로 두었는가? → 요약본이 아니라 **원본**을 넘겨라.
11. 자동 수정을 할 것인가? → **confidence 태그 → 고신뢰만 자동, 나머지는 사람에게 라우팅.**
12. 응답을 실시간으로 기다리는가? → 동기 Messages API. 아니면 Batches(50% 할인, 24시간 목표, 배치당 10만 건/256MB).
13. 특정 카테고리 노이즈로 신뢰를 잃었는가? → 그 카테고리만 **즉시 비활성화**하고 별도로 개선하라.

## 9. 용어 사전 (Glossary)

| 영어 용어 | 한국어 설명 |
|---|---|
| **Finding** | 검토 도구가 찾아낸 문제 하나. 위치·설명·심각도·신뢰도 등을 담는 구조화 단위 |
| **False Positive (오탐)** | 실제로는 문제가 아닌데 문제라고 표시한 것 |
| **False Negative (미탐)** | 실제 문제인데 놓친 것 |
| **Precision (정밀도)** | 문제라고 표시한 것 중 실제 문제인 비율. 오탐이 많으면 낮아짐 |
| **Recall (재현율)** | 실제 문제 중 찾아낸 비율. 미탐이 많으면 낮아짐 |
| **Alert Fatigue (알림 피로)** | 오탐이 많아 사용자가 도구 출력을 통째로 무시하게 되는 현상 |
| **Confidence Level (신뢰도)** | 모델이 그 판단을 얼마나 확신하는지. 심각도와 별개의 축 |
| **Severity (심각도)** | 그 문제가 진짜라면 얼마나 위험한지 |
| **Confidence-based Routing** | 신뢰도에 따라 자동 처리와 사람 검토로 분기하는 설계 |
| **Human-in-the-Loop (HITL)** | 불확실한 건만 사람에게 넘겨 처리하는 자동화/사람 협업 구조 |
| **Auto-fix** | 고신뢰 발견 사항을 사람 개입 없이 자동으로 수정하는 것 |
| **Zero-shot** | 예시 없이 지시문만으로 시키는 프롬프트 방식 |
| **Few-shot Prompting** | 입력–정답 예시 몇 개를 프롬프트에 넣어 기준을 학습시키는 방식 |
| **In-context Learning** | 가중치 변경 없이 프롬프트 문맥만으로 일어나는 임시 학습 |
| **Paired / Contrasting Examples** | 문제 사례와 허용 사례를 짝지어 각각의 정답과 함께 제시하는 예시 기법 |
| **Borderline Case** | 판정이 애매한 경계선 사례. 예시 세트에 반드시 포함해야 값어치가 큼 |
| **Instruction Drift** | 지시문이 길어질수록 모델이 일부 규칙을 놓치거나 무시하는 현상 |
| **Anchoring** | 하나의 극단적 예시가 기준 척도를 그쪽으로 끌어당기는 편향 |
| **Hallucination (환각)** | 근거가 없는데 그럴듯한 값을 지어내는 현상 |
| **Fabrication** | 환각 중에서도 특히 없는 수치·사실을 만들어내는 것 |
| **Normalization (정규화)** | 비정형 표현을 정해진 형식·단위로 변환하는 것 |
| **Null Fallback** | 값을 확정할 수 없을 때 `null`을 내도록 명시적 예시로 학습시키는 패턴 |
| **Prompt Chaining** | 작업을 여러 API 호출로 나누고 출력을 다음 입력으로 넘기는 구조 |
| **Single-pass** | 한 번의 호출로 생성과 검증을 모두 처리하는 방식 |
| **Multi-pass / Two-step Review** | 생성 호출과 검증 호출을 분리한 방식 |
| **Generator Instance** | 결과(코드 변경·초안 발견 사항)를 만드는 쪽 인스턴스 |
| **Reviewer Instance** | 생성 결과를 독립적으로 검증하는 별도 인스턴스 |
| **Raw Context Integrity** | 검토자에게 요약본이 아닌 원본(raw diff)을 그대로 전달해야 한다는 원칙 |
| **Self-framing** | 생성자가 자기 결과를 자기 관점으로 서술해 검토자의 시야를 가두는 편향 |
| **Per-file Pass** | 파일 하나 단위로 수행하는 검토. 문법·스타일·국소 로직에 강함 |
| **Integration Pass** | 변경 묶음 전체를 보는 검토. 파일 간 데이터 흐름과 계약 불일치를 잡음 |
| **Contract** | 파일/모듈 간에 지켜야 할 인터페이스 규격(시그니처, 타입, 의미) |
| **Changeset** | 한 번에 변경된 파일들의 묶음 |
| **Structured Output** | 자유 텍스트가 아니라 정해진 스키마를 따르는 형태로 받는 출력 |
| **JSON Schema** | 필드 이름·타입·필수 여부·허용값을 기술하는 명세 형식 |
| **Enum** | 필드가 가질 수 있는 값을 정해진 목록으로 제한하는 스키마 제약 |
| **Closed Enum** | 예외를 허용하지 않는 폐쇄형 열거형. 예상 밖 입력에서 강제 맞춤을 유발 |
| **Forced Fitting** | 맞는 enum 값이 없을 때 모델이 억지로 가장 비슷한 값에 끼워 넣는 현상 |
| **"Other" Fallback Pattern** | `other` enum 값 + 자유 텍스트 상세 필드로 예외를 안전하게 격리하는 설계 |
| **Categorical Field** | 집계·그룹화가 가능한 범주형 필드. 통계 분석의 전제 |
| **Free-text Field** | 자유 서술 필드. 세부 정보 보존에는 좋으나 집계 축으로는 부적합 |
| **detected_pattern** | 발견 사항을 촉발한 코드 구문/규칙 이름을 담는 필드. 기각 경향 분석의 핵심 |
| **Observability / Telemetry** | 시스템 동작을 사후에 측정·분석할 수 있게 데이터를 남기는 것 |
| **Dismissal** | 개발자가 발견 사항을 "문제 아님"으로 기각하는 행위 |
| **Strict Tool Use (`strict: true`)** | 출력이 JSON Schema를 문법적으로 100% 준수하도록 강제하는 옵션 |
| **Structural Conformance** | 필드 구성이 스키마와 일치하는가 |
| **Type Conformance** | 각 값의 데이터 타입이 스키마와 일치하는가 |
| **Business-plausibility Check** | 값이 비즈니스적으로 말이 되는지 애플리케이션 코드에서 하는 별도 검증 |
| **Tool / Tool Definition** | 모델이 호출할 수 있는 함수 명세. 구조화 출력의 표준 수단 |
| **input_schema** | 도구가 받는 인자의 JSON Schema. API 동작이 아니라 인자 형태만 규정 |
| **tool_use block** | 모델이 도구를 호출했음을 나타내는 응답 블록 |
| **tool_result** | 클라이언트 측 도구 실행 결과를 모델에게 되돌려 주는 메시지 |
| **`tool_choice: auto`** | 기본값. 도구 호출 여부를 모델이 결정. 텍스트만 답할 수도 있음 |
| **`tool_choice: any`** | 등록된 도구 중 반드시 하나 호출. 어느 것인지는 모델이 선택 |
| **`tool_choice: {"type":"tool","name":X}`** | 지정 도구 X를 반드시 호출하도록 강제 |
| **`tool_choice: none`** | 도구를 전혀 호출하지 않음 |
| **Forced Tool Calling** | `any` 또는 특정 도구 지정으로 도구 호출을 강제하는 것 |
| **Tool Schema Modularization** | 거대 통합 스키마 대신 유형별 소형 도구 여러 개로 쪼개는 설계 |
| **Monolithic Schema** | 모든 경우를 한 스키마에 담은 거대 스키마. 노이즈와 혼동을 유발 |
| **Extended Thinking** | 답하기 전 내부적으로 길게 추론하게 하는 기능. 강제 도구 선택과 병용 불가 |
| **Messages API** | 동기식 API. 요청을 보내고 그 자리에서 수 초 내 응답을 받음 |
| **Message Batches API** | 비동기 배치 API. 50% 할인, 24시간 내 처리 목표, 지연 SLA 없음 |
| **Latency SLA** | 응답까지 걸리는 시간에 대한 보장. 배치 API에는 없음 |
| **Blocking Workflow** | 결과가 나올 때까지 후속 작업이 멈춰 있는 흐름(예: merge gate) |
| **Merge Gate** | 검토 결과가 나올 때까지 PR 병합을 막는 CI 관문 |
| **Per-batch Limits** | 단일 배치 한계: 요청 100,000개 또는 총 페이로드 256MB 중 먼저 도달하는 것 |
| **Payload** | 요청에 실려 보내지는 데이터 전체의 크기 |
| **Client-side Tool** | 애플리케이션이 직접 실행하고 결과를 되먹여야 하는 도구. 다단계 왕복 필요 |
| **Server-side Tool (Built-in Tool)** | 웹 검색처럼 서버 내부에서 한 요청 안에 자동 완결되는 도구 |
| **Self-contained Resolution** | 서버 도구가 애플리케이션 개입 없이 단일 요청 패스 안에서 해결되는 성질 |
