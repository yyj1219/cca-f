# 사전 학습 노트 — Claude Code 설정과 워크플로우 (conf-50~59 대비)

이 문서는 해당 범위에서 다루는 개념을 아무 배경지식이 없는 상태에서도 이해할 수 있도록 처음부터 설명합니다.

---

## 1. Claude Code란 무엇인가

Claude Code는 터미널에서 동작하는 AI 코딩 도구입니다. 사람이 자연어로 요청하면, Claude가 파일을 읽고(Read), 검색하고(Glob/Grep), 셸 명령을 실행하고(Bash), 파일을 수정(Edit/Write)하면서 작업을 수행합니다.

핵심적으로 이해해야 할 두 가지 축이 있습니다.

1. **컨텍스트(Context)**: Claude가 지금 이 순간 "알고 있는" 텍스트 뭉치. 대화 내용, 읽은 파일, 로드된 지침 파일이 모두 여기에 들어갑니다. 컨텍스트에 들어오지 않은 지침은 Claude에게 존재하지 않는 것과 같습니다.
2. **설정 계층(Scope)**: 같은 이름의 설정/스킬이 여러 위치에 있을 때 무엇이 이기는지를 정하는 우선순위 규칙.

이 범위의 내용은 대부분 "이 지침이 언제 컨텍스트에 들어오는가", "충돌하면 누가 이기는가", "어떤 모드/도구를 언제 쓰는가"로 요약됩니다.

## 2. 지침 파일(Instruction Files) 체계

### 2.1 CLAUDE.md

프로젝트 루트에 두는 마크다운 파일로, Claude Code가 세션 시작 시 자동으로 읽어 컨텍스트에 넣는 "항상 적용되는 프로젝트 규칙" 문서입니다. 코딩 컨벤션, 빌드/테스트 명령, 디렉터리 구조 설명, 금지 사항 등을 적습니다.

```markdown
# 프로젝트 규칙

- 패키지 매니저는 pnpm만 사용한다.
- 테스트는 `pnpm test`로 실행한다.
- src/legacy/ 는 수정 금지.
```

CLAUDE.md는 사용자 홈(`~/.claude/CLAUDE.md`, 개인 전역 규칙), 프로젝트 루트(`./CLAUDE.md`, 팀 공유), 하위 디렉터리 등 여러 위치에 존재할 수 있고 함께 합쳐져 사용됩니다.

### 2.2 `@` 임포트 구문

CLAUDE.md 안에서 `@경로/파일.md` 한 줄을 쓰면, 그 파일의 내용을 그 자리에 끌어와 포함시킵니다. 흔히 말하는 include/import입니다.

```markdown
@AGENTS.md

## Claude 전용 추가 지침
- src/billing/ 아래를 변경할 때는 반드시 플랜 모드를 사용한다.
```

**왜 존재하는가**: 같은 내용을 두 파일에 복사해 두면 한쪽만 고쳐지는 동기화 문제가 생깁니다. 임포트를 쓰면 공통 내용은 한 파일(단일 진실 공급원, single source of truth)에만 두고, 도구별 고유 지침만 각자 파일에 덧붙일 수 있습니다.

**심볼릭 링크와의 차이**: 심링크(`CLAUDE.md -> AGENTS.md`)는 두 파일을 완전히 같은 내용으로 묶어버립니다. 즉 "공통 내용 + 추가 내용"이 불가능합니다. 임포트는 "공통 내용을 불러온 뒤 그 아래에 더 쓰기"가 가능하므로 확장성이 있습니다.

### 2.3 AGENTS.md

여러 AI 코딩 도구가 공통으로 읽도록 만들어진 벤더 중립 지침 파일 이름입니다. 한 저장소에서 여러 도구를 섞어 쓸 때, 팀 컨벤션을 AGENTS.md에 모아두고 각 도구의 전용 파일에서 이를 참조하는 구성이 일반적입니다.

핵심 정리: 공통 컨벤션은 AGENTS.md에, Claude 전용 규칙은 CLAUDE.md에, 그리고 CLAUDE.md 첫 줄에서 `@AGENTS.md`로 끌어옵니다.

### 2.4 `claudeMdExcludes` 설정

`settings.local.json` 등 설정 파일에서 특정 지침 파일을 **로딩 대상에서 제외**하는 옵션입니다. 예를 들어 상위 디렉터리의 어떤 CLAUDE.md가 방해될 때 이를 배제하는 용도입니다. 어디까지나 "읽지 않게 만드는" 스위치이며, 진단이나 로깅 기능은 아닙니다.

### 2.5 `/init` 명령

프로젝트를 훑어 CLAUDE.md 초안을 자동 생성해 주는 슬래시 명령입니다. 신규 프로젝트 세팅용 편의 기능이며, 기존 규칙 파일이 언제 로드되었는지를 검사하는 도구가 아닙니다.

## 3. 규칙 파일(`.claude/rules/`)과 경로 범위 지정

### 3.1 규칙 파일이란

`.claude/rules/` 디렉터리 아래에 놓는 마크다운 지침 조각들입니다. CLAUDE.md 하나에 모든 규칙을 몰아넣으면 파일이 비대해지고, 관계없는 지침까지 항상 컨텍스트를 차지합니다. 규칙 파일은 주제별로 지침을 쪼개 두고 **필요할 때만** 불러오기 위한 장치입니다.

### 3.2 프론트매터(frontmatter)와 `paths`

마크다운 파일 맨 위에 `---`로 감싼 YAML 블록을 프론트매터라고 하며, 파일에 대한 메타데이터를 적습니다. 규칙 파일에서는 `paths` 필드로 적용 범위를 지정합니다.

```markdown
---
paths: ["src/api/**/*.ts"]
---

# API 보안 규칙
- 모든 핸들러는 입력 검증을 먼저 수행한다.
- 인증 토큰은 로그에 남기지 않는다.
```

`**`는 하위 디렉터리 전체를 뜻하는 glob 패턴입니다. 즉 `src/api/` 아래 어느 깊이의 `.ts` 파일이든 매칭됩니다.

### 3.3 로딩 시점: 이것이 핵심

- **`paths`가 없는 규칙**: 세션 시작 시 무조건 로드됩니다(항상 적용).
- **`paths`가 있는 규칙(경로 범위 지정 규칙, path-scoped rule)**: **Claude가 그 패턴에 매칭되는 파일을 실제로 읽을 때(Read)** 비로소 컨텍스트에 동적으로 로드됩니다.

여기서 자주 헷갈리는 지점은 "경로가 화면에 보이는 것"과 "파일을 읽는 것"의 차이입니다.

- `git status`를 Bash로 실행해 `src/api/foo.ts`라는 문자열이 출력에 나타남 → **로드되지 않음**
- Glob으로 디렉터리 목록을 조회해 `src/api/foo.ts`가 목록에 포함됨 → **로드되지 않음**
- Read로 `src/api/foo.ts`의 내용을 실제로 열어봄 → **로드됨**

즉 트리거는 "경로 문자열의 등장"이 아니라 "매칭 파일의 실제 읽기"입니다.

**왜 이렇게 설계되었는가**: 컨텍스트는 유한한 자원입니다. 저장소에 규칙이 수십 개 있는데 전부 항상 로드되면 토큰이 낭비되고 중요한 지침이 묻힙니다. 실제로 그 영역의 코드를 만질 때만 해당 규칙을 끌어오는 지연 로딩(lazy loading) 방식이 효율적입니다.

### 3.4 `/memory` 명령

현재 로드된 메모리/지침 파일을 확인하고 편집하기 위한 슬래시 명령입니다. 경로 범위 규칙을 "강제 활성화"하는 명령이 아닙니다. 경로 범위 규칙은 조건이 충족되면 자동으로 로드됩니다.

## 4. 훅(Hooks) 시스템

### 4.1 훅이란

훅은 Claude Code가 동작하는 특정 생명주기 시점(lifecycle event)에 사용자가 정의한 셸 명령이나 스크립트를 자동 실행시키는 장치입니다. "이 사건이 일어나면 저것을 실행하라"는 이벤트-핸들러 구조입니다.

훅은 보통 설정 파일(`settings.json`)에 이벤트 이름과 실행할 명령을 짝지어 등록합니다.

```json
{
  "hooks": {
    "InstructionsLoaded": [
      {
        "hooks": [
          { "type": "command", "command": "cat >> ~/instructions.log" }
        ]
      }
    ]
  }
}
```

훅에는 이벤트 정보가 JSON 형태로 전달되므로, 위처럼 로그 파일에 그대로 쌓아두면 나중에 무슨 일이 있었는지 추적할 수 있습니다.

### 4.2 `InstructionsLoaded` 훅

지침 파일(CLAUDE.md, `.claude/rules/*.md` 등)이 컨텍스트에 로드되는 시점에 발동하는 훅입니다. **어떤 파일이**, **언제**, **왜(어떤 트리거로)** 로드되었는지를 기록할 수 있습니다.

**언제 쓰는가**: "규칙을 분명히 써 뒀는데 Claude가 안 지킨다"는 상황에서, 원인이 두 가지로 갈립니다.

1. 규칙이 애초에 컨텍스트에 들어오지 않았다 (경로 패턴 오타, 트리거 미발생 등)
2. 규칙은 들어왔는데 Claude가 따르지 않았다 (지침 문구가 모호함)

이 둘을 구분하는 정확한 진단 방법이 `InstructionsLoaded` 훅으로 로딩 사실 자체를 로그로 남겨 확인하는 것입니다. 로드 기록이 없으면 (1), 있으면 (2)입니다. 규칙에서 `paths`를 지워 항상 로드되게 만드는 것은 증상을 우회할 뿐 원인을 알려주지 않습니다.

## 5. 스킬(Skills)과 우선순위

### 5.1 스킬이란

스킬은 특정 작업을 위한 절차와 지침을 담은 재사용 가능한 패키지입니다. 디렉터리 이름이 스킬 이름이 되고, 그 안의 `SKILL.md`가 본문입니다.

```
.claude/skills/
  review/
    SKILL.md
  commit/
    SKILL.md
```

`SKILL.md`는 프론트매터(이름, 설명 등)와 본문 지침으로 구성되며, 사용자가 `/review`, `/commit` 같은 슬래시 명령으로 호출하거나 Claude가 상황에 맞게 스스로 불러 쓸 수 있습니다.

**왜 존재하는가**: 매번 같은 긴 지시를 타이핑하는 대신, "코드 리뷰 체크리스트", "커밋 메시지 작성 규칙" 같은 반복 절차를 파일로 고정해 팀 전체가 공유하기 위해서입니다.

### 5.2 스킬이 놓이는 범위(Scope)

| 범위 | 위치 | 성격 |
|---|---|---|
| Enterprise | 조직 관리 경로 | 조직 전체 강제 정책 |
| Personal (개인) | `~/.claude/skills/` | 개인 노트북, git에 올라가지 않음 |
| Project (프로젝트) | `.claude/skills/` | 저장소에 커밋, 팀 공유 |
| Plugin | 설치한 플러그인 내부 | 외부 패키지가 제공 |

`~`는 사용자 홈 디렉터리를 뜻합니다. 따라서 `~/.claude/`는 개인 전역 설정, `.claude/`(프로젝트 루트 기준)는 그 저장소 전용 설정입니다.

### 5.3 우선순위 규칙

같은 이름의 스킬이 여러 범위에 존재할 때 적용 순서는 다음과 같습니다.

```
Enterprise > Personal (~/.claude/skills/) > Project (.claude/skills/) > Plugin
```

동작 방식의 핵심:

- 병합되지 않습니다. 여러 개가 순차 실행되는 일도 없습니다.
- 이름 충돌 에러가 나지도 않습니다.
- **가장 높은 우선순위 하나만 선택되어 실행**되고 나머지는 가려집니다(override).

즉 프로젝트에 `.claude/skills/review/SKILL.md`가 있고 개인 환경에 `~/.claude/skills/review/SKILL.md`가 있다면, 그 사람이 그 저장소에서 `/review`를 실행해도 **개인 스킬**이 실행됩니다.

**왜 Personal이 Project보다 높은가**: 개인의 로컬 맞춤 설정이 공유 설정에 의해 덮이지 않게 하기 위해서입니다. 개인 환경은 사용자 본인만 영향을 받으므로, 개인 취향을 우선 적용해도 팀에는 피해가 없습니다.

### 5.4 이 규칙을 활용한 개인 오버라이드 패턴

팀 공유 스킬은 그대로 두고, 나만 다른 동작을 원할 때:

```
~/.claude/skills/commit/SKILL.md   ← 같은 이름으로 개인 사본 생성
```

이렇게 하면

- 나는 `/commit`을 그대로 입력해도 내 버전이 실행되고
- 저장소 파일은 손대지 않았으므로 팀원들은 원래 프로젝트 스킬을 계속 사용합니다.

비교되는 대안들과 그 단점:

- **저장소 파일을 고치고 커밋하지 않기**: 워킹 트리가 지저분해지고, 실수로 커밋되거나 `git clean`이나 브랜치 전환에서 날아갑니다. 개인 설정을 공유 저장소에 두는 것 자체가 잘못된 위치 선택입니다.
- **다른 이름의 스킬 만들기(`commit-verbose`)**: 동작은 하지만 호출 명령이 `/commit-verbose`로 바뀝니다. "같은 명령어를 유지하고 싶다"는 요구를 만족시키지 못합니다.
- **공유 파일에 비활성화 플래그 넣기**: 공유 파일 변경이므로 커밋되면 팀 전체에 영향이 갑니다.

### 5.5 `disable-model-invocation`

스킬 프론트매터에 넣을 수 있는 옵션으로, **Claude가 스스로 판단해 이 스킬을 자동 호출하는 것**을 막습니다. 사용자가 슬래시 명령으로 명시적으로 부르는 것만 허용하고 싶을 때 씁니다. "스킬을 완전히 죽이는" 스위치가 아니며, 개인 오버라이드 수단도 아닙니다.

## 6. 플랜 모드(Plan Mode)와 직접 실행(Direct Execution)

### 6.1 두 모드의 정의

- **플랜 모드**: Claude가 파일을 읽고 조사·분석할 수는 있지만, 파일을 수정하거나 상태를 바꾸는 명령을 실행하지 않는 모드입니다. 결과물은 "무엇을 어떻게 바꿀 것인가"라는 계획입니다. 사용자가 계획을 승인해야 실제 작업으로 넘어갑니다.
- **직접 실행**: Claude가 곧바로 파일을 편집하고 명령을 실행하는 일반 모드입니다.

### 6.2 각각을 언제 쓰는가

플랜 모드가 유리한 상황:

- 여러 설계 대안(예: 캐싱 전략 3가지)을 비교하고 하나를 골라야 할 때
- 변경 범위가 넓거나 영향도가 불확실할 때
- 낯선 코드베이스 구조를 먼저 파악해야 할 때
- 되돌리기 어려운 작업(마이그레이션, 대규모 리팩터링) 전에 검토가 필요할 때

직접 실행이 유리한 상황:

- 이미 결정이 끝났고 변경이 작고 국소적일 때(예: 파일 2개 수정)
- 계획을 세우는 비용이 작업 자체보다 큰 경우

### 6.3 전형적인 올바른 순서

```
[플랜 모드] 대안 비교 · 트레이드오프 분석 · 전략 확정
        ↓  플랜 모드 종료
[직접 실행] 확정된 소규모 변경을 적용
```

반대로 하는 것(비교 분석을 직접 실행으로, 확정된 소규모 수정을 플랜 모드로)은 두 모드의 목적을 뒤집은 것입니다. 또한 "세 전략을 전부 구현해 보고 두 개를 지운다"는 방식은 비교라는 목적에 비해 낭비가 크고, 비교 자체를 건너뛰는 것은 사전 분석 요구를 무시하는 것입니다.

## 7. 요구사항 도출: `AskUserQuestion` 도구

### 7.1 무엇인가

Claude가 사용자에게 **선택지가 있는 질문을 던지고 답을 받아오는** 도구입니다. 자유 서술로 되묻는 대신 구조화된 질문과 선택지 형태로 물어, 사용자가 빠르게 답하고 그 답이 그대로 설계 입력이 됩니다.

### 7.2 왜 존재하는가

복잡한 시스템 설계에서 가장 큰 실패 원인은 "말해주지 않은 전제"입니다. 특히:

- **실패 모드(failure mode)**: 정상 동작이 아니라 무언가 고장 났을 때의 동작. 예) 특정 리전이 통째로 다운되면?
- **네트워크 파티션(network partition)**: 시스템 일부가 서로 통신하지 못하도록 네트워크가 갈라진 상태.
- **스플릿 브레인(split-brain)**: 파티션 상황에서 양쪽이 각자 자기가 주인이라 믿고 따로 쓰기를 받아들여 데이터가 갈라지는 문제. 그래서 "어느 쪽이 권한(authoritative)을 갖는가"를 미리 정해야 합니다.
- **상태 조정(reconciliation)**: 파티션이 복구된 뒤 갈라졌던 데이터를 어떻게 합칠 것인가.
- **페일오버(failover)**: 장애 시 예비 자원으로 자동 전환하는 것.
- **일관성 트레이드오프**: 강한 일관성을 택하면 가용성과 지연이 나빠지고, 최종적 일관성을 택하면 일시적 불일치를 감수합니다.

이런 항목들은 사용자가 먼저 떠올리기 어렵고, Claude 입장에서는 코드만 봐서는 알 수 없는 비즈니스 판단입니다.

### 7.3 권장 흐름

1. 사용자가 목표를 **간단히** 설명한다.
2. Claude가 `AskUserQuestion`으로 **뻔하지 않은 부분**(실패 모드, 트레이드오프, 제약)을 인터뷰한다.
3. 확정된 답을 근거로 설계·구현한다.

피해야 할 방식:

- 검토 없이 바로 구현하고 실제 운영 장애가 터지면 고치는 방식(위험 전가)
- 일반 튜토리얼의 기본값을 서비스 제약 고려 없이 그대로 채택
- 사람이 혼자 모든 시나리오를 사전에 완벽히 문서화(공수 과다, 상호작용의 이점 상실)

## 8. 프롬프트 명확화: 예시 기반 지시(Few-Shot)

### 8.1 문제의 본질

"주소를 표준 형식으로 정리해줘", "전화번호를 표준 형식으로 정규화해줘" 같은 지시는 사람에게는 자연스럽지만 **모호합니다**. 표준 형식이 정확히 무엇인지 정의되어 있지 않기 때문입니다. 특히 예외 케이스에서 해석이 갈립니다.

- 주소: 동/호수 누락, 사서함(PO Box), 시골 도로 주소(rural route)
- 전화번호: 내선번호(extension), 국가 코드(international code)

같은 지시를 여러 번 반복해도 매번 다른 결과가 나오는 이유는 지시가 부족해서가 아니라 **정답이 정의되지 않았기 때문**입니다.

### 8.2 해법: 입력/출력 쌍(Few-Shot Prompting)

각 애매한 케이스마다 "이 입력이면 이 출력"을 하나씩 보여주면 모호성이 사라집니다. 2~3개면 충분한 경우가 많습니다.

```
입력: "02-123-4567 내선 89"      → 출력: "+82-2-123-4567 x89"
입력: "+1 (415) 555-0100"        → 출력: "+1-415-555-0100"
입력: "010 1234 5678"            → 출력: "+82-10-1234-5678"
```

이렇게 하면 모델은 구분자, 국가 코드 표기, 내선 표기 규칙을 예시에서 정확히 추론합니다. 이 방식을 퓨샷 프롬프팅(few-shot prompting) 또는 예시 기반 지시라고 부릅니다.

**왜 산문 설명보다 강력한가**: 산문은 아무리 길게 써도 해석 여지가 남고, 케이스가 늘수록 문장이 서로 충돌합니다. 예시는 결과물 그 자체이므로 해석의 여지가 없습니다. 또한 예시는 나중에 그대로 테스트 케이스로 재활용할 수 있습니다.

### 8.3 효과가 없거나 역효과인 접근

- **temperature나 창의성 설정 올리기**: temperature는 출력의 무작위성을 조절하는 값입니다. 높이면 표현이 다양해지므로 **일관성이 더 나빠집니다**. 일관된 형식이 목표라면 정반대 방향입니다.
- **IMPORTANT, MUST 같은 대문자 강조 반복**: 강조는 우선순위를 높일 뿐 "무엇이 정답인지"를 알려주지 않습니다. 모호함은 그대로 남습니다.
- **케이스별로 함수를 쪼개기**: 같은 목적의 함수를 3개로 나누면 호출하는 쪽이 어떤 함수를 쓸지 분기해야 합니다. 복잡도를 호출자에게 전가하는 나쁜 설계입니다.
- **전체 팀 설계 회의 소집**: 몇 줄짜리 예시로 해결될 문제에 조직 프로세스를 붙이면 오버헤드가 과도합니다.
- **라이브러리 여러 개 조사 후 다수결**: 시간이 많이 들면서도 사용자가 실제로 원하는 고유 포맷을 보장하지 못합니다.

## 9. CLI 플래그와 구조화된 출력

### 9.1 Claude Code CLI와 자동화

Claude Code는 대화형 터미널 세션뿐 아니라 스크립트에서 호출되는 CLI로도 쓰입니다. 예를 들어 릴리스 노트 생성기가 커밋 로그를 넘기고 정리된 결과를 받아오는 식입니다. 이때는 자유 텍스트가 아니라 **기계가 파싱할 수 있는 구조화된 출력**이 필요합니다.

### 9.2 JSON Schema란

JSON 데이터의 형태를 기술하는 표준 규격입니다. 어떤 필드가 있고, 타입이 무엇이고, 무엇이 필수인지를 JSON으로 적습니다.

```json
{
  "type": "object",
  "properties": {
    "version": { "type": "string" },
    "changes": { "type": "array", "items": { "type": "string" } }
  },
  "required": ["version", "changes"]
}
```

### 9.3 `--json-schema` 플래그

CLI 호출 시 이 스키마를 넘기면, 모델의 출력이 해당 구조를 따르도록 강제됩니다. 결과를 받는 쪽에서 파싱 실패를 걱정하지 않아도 됩니다.

### 9.4 잘못된 스키마를 넘기면 어떻게 되는가

스키마 문자열은 API를 호출하기 **전에 로컬에서 먼저 파싱하고 검증**됩니다. 셸에서 따옴표나 중괄호를 잘못 이스케이프해 JSON으로 파싱되지 않는 문자열이 들어오면:

- 즉시 검증 실패로 판정되고,
- "유효한 JSON Schema가 아니다"는 오류 메시지와 검증기의 진단 내용을 출력하며,
- 어떤 출력도 생성하지 않고 오류 종료 코드로 프로세스가 끝납니다.

일어나지 않는 일들과 그 이유:

- **조용히 평문 텍스트로 폴백**: 자동화 파이프라인에서 조용한 폴백은 최악입니다. 잘못된 결과가 그대로 하류로 흘러 나중에 원인 불명의 버그가 됩니다. 그래서 명시적으로 실패시킵니다(fail fast).
- **빈 객체 반환**: 마찬가지로 오류를 숨기는 동작이므로 하지 않습니다.
- **재시도**: `--max-retries` 류의 재시도는 네트워크 오류나 일시적 API 장애처럼 **다시 하면 성공할 수 있는** 문제에 적용됩니다. 입력 문자열의 문법 오류는 몇 번을 다시 해도 똑같이 실패하는 결정론적 오류이므로 재시도 대상이 아닙니다.

이 "재시도할 가치가 있는 오류(transient)와 없는 오류(deterministic/validation)를 구분한다"는 원칙은 CLI 설계 전반에 적용되는 일반 규칙입니다.

### 9.5 실무 팁: 이스케이프 문제 피하기

셸에서 긴 JSON을 인라인으로 넘기면 따옴표와 중괄호 이스케이프 실수가 잦습니다. 파일로 빼서 넘기는 편이 안전합니다.

```bash
claude -p "릴리스 노트를 추출해줘" --json-schema "$(cat schema.json)"
```

## 10. 전체 구조 한눈에 보기

```
설정/지침이 컨텍스트에 들어오는 경로
├─ CLAUDE.md ................... 세션 시작 시 항상 로드
│   └─ @AGENTS.md ............. 임포트로 공통 내용 끌어옴
├─ .claude/rules/*.md
│   ├─ paths 없음 ............. 세션 시작 시 항상 로드
│   └─ paths 있음 ............. 매칭 파일을 Read할 때 로드
└─ 진단: InstructionsLoaded 훅으로 로딩 여부/시점/이유 로깅

같은 이름 충돌 시 우선순위
Enterprise > Personal(~/.claude) > Project(.claude) > Plugin
(병합이 아니라 하나만 선택)

작업 방식 선택
분석과 대안 비교      → 플랜 모드
확정된 소규모 변경    → 직접 실행
요구사항이 불명확     → AskUserQuestion으로 인터뷰
출력 형식이 불명확    → 입력/출력 예시 제공
기계가 소비할 출력    → --json-schema
```

## 11. 용어 사전

| 영어 용어 | 한국어 설명 |
|---|---|
| Context | Claude가 현재 참조 가능한 텍스트 전체(대화, 읽은 파일, 로드된 지침). 여기 없으면 모르는 것과 같음 |
| CLAUDE.md | 프로젝트/개인 지침 파일. 세션 시작 시 자동 로드됨 |
| AGENTS.md | 여러 AI 코딩 도구가 공유하는 벤더 중립 지침 파일 |
| `@import` (`@AGENTS.md`) | 지침 파일 안에서 다른 마크다운 파일 내용을 끌어오는 구문. 내용 중복 관리를 방지 |
| Single source of truth | 동일 정보를 한 곳에서만 관리하는 원칙 |
| Symlink (symbolic link) | 다른 파일을 가리키는 파일. 내용이 100% 동일해지므로 "공통 + 추가" 구성이 불가능 |
| Frontmatter | 마크다운 상단 `---`로 감싼 YAML 메타데이터 블록 |
| `paths` | 규칙 파일 프론트매터 필드. 이 규칙이 적용될 파일 경로 패턴 목록 |
| Path-scoped rule | 경로 범위 지정 규칙. 매칭 파일을 Read할 때 비로소 로드되는 조건부 규칙 |
| Glob pattern | `src/api/**/*.ts` 처럼 와일드카드로 파일 경로를 표현하는 문법. `**`는 하위 전체 |
| Glob (도구) | 패턴으로 파일 목록을 조회하는 도구. 목록에 경로가 나와도 규칙 로딩 트리거는 아님 |
| Read (도구) | 파일 내용을 실제로 여는 도구. 경로 범위 규칙의 로딩 트리거 |
| Lazy loading | 필요한 순간에만 자원을 불러오는 방식. 경로 범위 규칙이 이 방식 |
| Hook | 특정 생명주기 시점에 자동 실행되는 사용자 정의 명령 |
| `InstructionsLoaded` | 지침 파일이 로드될 때 발동하는 훅. 무엇이/언제/왜 로드됐는지 로깅해 진단 |
| `claudeMdExcludes` | 특정 지침 파일을 로딩에서 제외하는 설정. 진단용이 아님 |
| `/init` | 프로젝트를 분석해 CLAUDE.md 초안을 생성하는 명령 |
| `/memory` | 로드된 메모리/지침을 확인하고 편집하는 명령. 규칙 강제 활성화 기능은 아님 |
| Skill / SKILL.md | 반복 절차를 담아 재사용하는 지침 패키지와 그 본문 파일 |
| Slash command | `/review`처럼 슬래시로 시작하는 명시적 호출 명령 |
| Scope (범위) | 설정이 놓인 계층. Enterprise / Personal / Project / Plugin |
| Personal scope | `~/.claude/` 아래. 개인 전역이며 git에 올라가지 않음 |
| Project scope | 저장소의 `.claude/` 아래. 커밋되어 팀이 공유 |
| Precedence / Override | 같은 이름 충돌 시 상위 범위가 하위를 덮고 하나만 실행되는 규칙 |
| `disable-model-invocation` | Claude의 자동 스킬 호출을 막고 명시적 호출만 허용하는 옵션 |
| Plan mode | 수정 없이 조사·분석·계획만 수행하는 모드 |
| Direct execution | 실제로 파일을 편집하고 명령을 실행하는 일반 모드 |
| `AskUserQuestion` | Claude가 사용자에게 구조화된 질문을 던져 요구사항을 도출하는 도구 |
| Requirements elicitation | 요구사항 도출. 명시되지 않은 전제와 판단을 끌어내는 과정 |
| Failure mode | 실패 모드. 정상이 아닌 고장 상황에서의 동작 |
| Regional outage | 특정 리전(지역 데이터센터) 전체 장애 |
| Network partition | 네트워크가 갈라져 시스템 일부끼리 통신이 끊긴 상태 |
| Split-brain | 파티션 중 양쪽이 각자 주인이라 믿고 따로 쓰기를 받아 데이터가 갈라지는 문제 |
| Authoritative region | 분할 상황에서 최종 권한을 갖는 리전 |
| Reconciliation | 파티션 복구 후 갈라진 상태를 합쳐 정합성을 맞추는 작업 |
| Failover | 장애 시 예비 자원으로 자동 전환 |
| Few-shot prompting | 소수의 입력/출력 예시로 규칙을 전달하는 프롬프트 기법 |
| Input/output pair | 입력과 기대 출력의 짝. 모호성을 제거하는 가장 확실한 명세 |
| Prose description | 산문 설명. 길수록 해석 여지와 상호 충돌이 늘어남 |
| Temperature | 출력의 무작위성 조절값. 높이면 다양해지고 일관성은 떨어짐 |
| Edge case | 예외적 경계 사례. 예) 내선번호, 사서함 주소 |
| CLI flag | 명령줄 옵션. 예) `--json-schema` |
| JSON Schema | JSON 데이터의 구조, 타입, 필수 여부를 기술하는 표준 규격 |
| `--json-schema` | 출력이 지정한 스키마 구조를 따르도록 강제하는 CLI 플래그 |
| Structured output | 기계가 파싱 가능한 형태로 강제된 출력 |
| Validator / Diagnostic | 검증기와 그 진단 메시지. 어디가 왜 잘못됐는지 알려줌 |
| Fail fast | 오류를 숨기지 않고 즉시 명시적으로 실패시키는 설계 원칙 |
| Silent fallback | 오류를 알리지 않고 다른 동작으로 넘어가는 것. 자동화에서 위험 |
| Transient vs deterministic error | 재시도로 해결 가능한 일시적 오류와, 몇 번을 해도 같은 결과인 결정론적 오류 |
| `--max-retries` | 일시적 오류에 대한 재시도 횟수 옵션. 문법 오류에는 적용되지 않음 |
