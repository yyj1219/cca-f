# 사전 학습 노트 — 에이전트 아키텍처와 오케스트레이션 (101~114 범위)

이 문서는 해당 범위에서 다루는 개념들을 아무 배경지식이 없는 상태에서도 이해할 수 있도록 처음부터 설명합니다.

## 0. 출발점: "에이전트(Agent)"란 무엇인가

일반적인 챗봇은 사용자의 말을 받아 텍스트로 답하고 끝납니다. **에이전트**는 여기에 두 가지가 더해진 것입니다.

1. **도구(Tool) 사용**: 모델이 스스로 "지금은 파일을 읽어야겠다", "웹을 검색해야겠다", "환불 API를 호출해야겠다"고 판단하고 외부 기능을 호출합니다.
2. **루프(Loop)**: 도구를 호출하고 → 결과를 받아 → 그 결과를 보고 다시 생각하고 → 필요하면 또 도구를 호출하는 과정을 목표가 달성될 때까지 반복합니다.

이 두 가지 때문에 에이전트는 "한 번 답하고 끝"이 아니라 **여러 턴에 걸쳐 스스로 일을 진행하는 프로그램**이 됩니다. 그래서 등장하는 것이 이 문서에서 다룰 주제들입니다. 즉,

- 여러 에이전트를 어떻게 조직할 것인가 (오케스트레이션)
- 루프를 언제 멈출 것인가 (정지 조건)
- 위험한 도구 호출을 어떻게 막을 것인가 (훅, 권한)
- 대화 기록(컨텍스트)을 어떻게 관리할 것인가 (세션, 격리)

## 1. 멀티 에이전트 오케스트레이션

### 1.1 오케스트레이터-서브에이전트 패턴 (Orchestrator-Subagent Pattern)

하나의 큰 작업을 하나의 에이전트가 다 하려고 하면 대화 기록이 너무 길어지고, 서로 무관한 정보가 뒤섞여 판단이 흐려집니다. 그래서 흔히 쓰는 구조가 이것입니다.

- **오케스트레이터(Orchestrator)** 또는 **코디네이터(Coordinator)**: 전체 작업을 계획하고, 잘게 쪼개서 하위 에이전트에게 나눠주고, 돌아온 결과를 모아 최종 답을 만드는 "지휘자".
- **서브에이전트(Subagent)**: 지시받은 좁은 범위의 작업만 수행하고 결과를 위로 보고하는 "작업자".

이 구조를 그림으로 보면 중앙에 오케스트레이터가 있고 바퀴살처럼 서브에이전트가 붙습니다. 이 모양을 **허브 앤 스포크(Hub-and-Spoke)** 아키텍처라고 부릅니다. 중요한 점은 **서브에이전트끼리 직접 통신하지 않는다**는 것입니다. 모든 통신은 허브(오케스트레이터)를 거칩니다. 이렇게 하면 흐름을 한 곳에서 통제할 수 있고, 누가 무엇을 했는지 추적하기 쉽습니다.

```
            [사용자]
               │
        ┌──────▼───────┐
        │ 오케스트레이터 │
        └──┬───┬───┬───┘
           │   │   │
        [A] [B] [C]   ← 서브에이전트 (서로 직접 대화하지 않음)
```

**서브에이전트를 왜 쓰는가:**
- **컨텍스트 격리**: 각 서브에이전트는 자기 작업에 필요한 정보만 가진 별도의 대화 창을 쓰므로, 오케스트레이터의 대화 기록이 잡음으로 가득 차지 않습니다.
- **병렬성**: 서로 독립적인 작업은 동시에 돌릴 수 있습니다.
- **전문화**: 각 서브에이전트에 서로 다른 지시문(프롬프트)과 서로 다른 도구 목록을 줄 수 있습니다.

### 1.2 결과 종합(Synthesis)과 정보 상충 처리

오케스트레이터의 마지막 임무는 서브에이전트들의 결과를 모아 하나의 답으로 **종합(Synthesize)** 하는 것입니다. 그런데 서브에이전트들이 서로 다른 출처를 참고해 **서로 모순되는 답**을 가져오는 일이 흔합니다(예: 같은 사건의 연도를 하나는 1969년, 하나는 1970년으로 보고).

이때의 올바른 원칙은 **투명성(Transparency)** 입니다.

- 오케스트레이터에게는 어느 쪽이 진실인지 판정할 근거가 없습니다. 근거 없이 하나를 고르면 그것은 사실상 **환각(Hallucination)** 을 만들어내는 행위입니다.
- 정보를 통째로 버리고 답하지 않는 것도 틀렸습니다. 시스템의 유용성이 사라집니다.
- 응답 속도(먼저 도착한 결과)는 정확성과 아무 관계가 없습니다. "먼저 답한 쪽이 옳다"는 규칙은 존재하지 않습니다.
- 서브에이전트가 모호하거나 상충되는 결과를 보고하는 것은 **허용되며 오히려 바람직합니다**. 서브에이전트는 발견한 것을 있는 그대로 보고해야 하고, 억지로 하나로 정리해 올리면 정보가 손실됩니다.

따라서 올바른 처리는 **양쪽 결과를 모두 집계하고, 각각의 출처를 함께 붙여 사용자에게 상충 사실을 그대로 알려 주고 판단을 돕는 것**입니다.

### 1.3 정적 파이프라인 vs 동적 라우팅

**정적(Static) 파이프라인**은 입력이 무엇이든 항상 같은 순서로 같은 에이전트를 전부 실행하는 구조입니다. 예를 들어 고객 지원 티켓 처리에서 늘 다음 5개를 다 돌리는 식입니다.

1. classifier (분류기)
2. sentiment analyzer (감정 분석기)
3. knowledge-base search (지식베이스 검색)
4. summarizer (요약기)
5. escalation checker (이관 판정기)

문제는 "비밀번호 재설정 링크 주세요" 같은 한 줄짜리 문의에도 5개가 전부 돌아간다는 점입니다. 결과적으로 **지연 시간(Latency)** 과 **토큰 비용**이 폭증합니다.

**동적 라우팅(Dynamic Routing)** 은 이 문제의 표준 해법입니다. 코디네이터가 먼저 **경량 분류 단계**를 한 번 돌려서 "이 입력에는 무엇이 필요한가"를 판단하고, 필요한 에이전트만 골라 부릅니다.

경량 분류 단계는 보통 작고 빠른 프롬프트 한 번으로 구조화된 JSON을 받아오는 식으로 구현합니다.

```json
{
  "complexity": "low",
  "required_subagents": ["classifier"]
}
```

```json
{
  "complexity": "high",
  "required_subagents": ["classifier", "sentiment_analyzer",
                         "kb_search", "summarizer", "escalation_checker"]
}
```

코디네이터는 `required_subagents`에 나온 것만 호출합니다. 이렇게 하면 단순 티켓은 1개 에이전트로 즉시 끝나고, 복잡한 티켓만 전체 파이프라인을 탑니다.

**JSON으로 받는 이유**: 자연어 문장("이건 간단해 보입니다")은 프로그램이 파싱하기 어렵고 매번 표현이 달라집니다. 필드 이름과 값 집합을 정해둔 구조화된 출력은 코드에서 `if "kb_search" in result["required_subagents"]` 처럼 확정적으로 분기할 수 있습니다.

**흔히 헷갈리는 대안들과 그 한계:**

- **전부 병렬 실행**: 총 지연 시간이 "합계"에서 "가장 느린 하나"로 줄어드는 이점은 있지만, **불필요한 작업 자체는 그대로 다 수행**되므로 토큰 비용은 전혀 줄지 않습니다. 근본 해결이 아닙니다. (병렬화는 라우팅과 함께 쓰는 보조 최적화입니다.)
- **5개를 1개로 합쳐 순차 실행**: 지연 시간은 오히려 늘고, 단계별 제어·병렬화·전문화를 모두 잃습니다.
- **코디네이터를 없애고 서브에이전트끼리 직접 호출**: 에이전트 간 결합도(coupling)가 높아지고 흐름을 한 곳에서 통제할 수 없게 되어 관측·디버깅이 어려워집니다. 허브 앤 스포크의 장점을 버리는 선택입니다.

### 1.4 중첩 서브에이전트(Nested Subagents)와 깊이 제한

서브에이전트가 다시 자기 서브에이전트를 만드는 것을 **중첩(Nesting)** 이라고 합니다. Claude Code는 이를 지원하되, 무한 재귀와 과도한 API 비용을 막기 위해 **최대 5단계(메인 에이전트를 1단계로 포함)** 라는 **하드 리밋(Hard Limit)** 을 둡니다.

```
Level 1: 메인 에이전트
Level 2:   └ 서브에이전트
Level 3:       └ 서브에이전트
Level 4:           └ 서브에이전트
Level 5:               └ 서브에이전트   ← 여기까지
```

기억할 점:
- 이 제한은 모델 등급(tier)이나 설정으로 풀리는 유연한 값이 아니라 고정된 상한입니다.
- 도구 목록에 `Agent` 도구가 들어 있다고 해서 무제한으로 중첩되지 않습니다.
- "서브에이전트는 절대 자식을 만들 수 없다"는 것은 초기 버전의 제약이었고, 지금은 5단계까지 가능합니다.
- 각 단계는 자기만의 독립 컨텍스트 창을 가집니다.

### 1.5 서브에이전트의 컨텍스트 격리와 상태 없음(Stateless)

핵심 원칙: **서브에이전트를 호출할 때마다 완전히 새로운(fresh) 빈 컨텍스트에서 시작합니다.**

같은 이름의 서브에이전트 타입(예: `endpoint-finder`)을 연속으로 두 번 불러도, 두 번째 호출은 첫 번째 호출에서 무엇을 했는지 **전혀 모릅니다**. 이미 설명했던 규칙을 다시 설명하고, 이미 훑었던 배경을 다시 훑습니다.

이것은 버그가 아니라 **의도된 정상 동작**입니다. 이유는 다음과 같습니다.
- 컨텍스트 오염(무관한 이전 작업 내용이 판단을 흐리는 것)을 막기 위해
- 매 호출마다 이전 기록을 다 실어 보내면 토큰이 낭비되기 때문에

기억을 이어가고 싶다면 **특정 에이전트 ID를 명시적으로 재개(resume)** 해야 합니다. 즉 "같은 타입을 또 부른다"와 "그때 그 에이전트를 이어서 부른다"는 완전히 다른 동작입니다.

틀린 통념 정리:
- 같은 코디네이터 세션 안의 서브에이전트들이 하나의 컨텍스트 창을 공유한다 → 아닙니다. 격리가 목적입니다.
- 대상(서비스 등)이 같으면 자동으로 기억이 공유된다 → 아닙니다. 대상과 무관합니다.
- 서브에이전트 정의가 호출 간 추론을 자동 캐싱한다 → 그런 기능은 없습니다.

### 1.6 서브에이전트 실행이 중간에 끊겼을 때 (부분 출력 반환)

긴 작업 도중 서버 과부하(Server Overload), 타임아웃, 중단 등으로 서브에이전트 응답이 도중에 잘릴 수 있습니다. 이때 코디네이터가 받는 `Agent` 도구 결과는 다음과 같습니다.

> **이미 생성된 부분 텍스트 출력 + "완료되지 않았음"을 알리는 안내 노트**

즉 지금까지 나온 분석 단락들은 살아서 전달되고, 미완료 상태라는 표시가 함께 붙습니다. 이렇게 설계된 이유는 **코디네이터가 제어권을 쥔 채 다음 행동을 결정하게 하기 위해서**입니다. 이미 얻은 정보를 버리지 않고 활용하면서, 재시도할지·다른 방법을 쓸지·사용자에게 보고할지를 코디네이터가 판단합니다.

이와 대비되는 잘못된 기대들:
- 시스템이 몰래 자동 재시도해서 성공할 때까지 반복한다 → 무한 루프와 비용 폭증 위험이 있어 그렇게 하지 않습니다.
- 오류 표시 없이 완전히 빈 결과가 온다 → 아닙니다. 부분 출력과 미완료 표시가 포함됩니다.
- 캐시된 중간 도구 호출로 "완성된 전체 출력"을 복원해 준다 → 실제로 생성되지 않은 내용을 만들어낼 수는 없습니다.

### 1.7 사람에게 넘기는 인수인계(Handoff) 요약 작성법

에이전트가 처리하던 건을 사람 상담원/관리자에게 넘겨야 할 때가 있습니다(예: 사람만 승인할 수 있는 정책 예외). 이때 **인계받는 사람이 대화 전문(transcript)에 접근할 수 없다**는 조건이 자주 붙습니다.

좋은 인수인계 요약은 대화를 읽지 않고도 **즉시 결정하고 조치할 수 있게** 해야 합니다. 필수 3요소는 다음과 같습니다.

1. **식별자(Identifier)**: 어떤 고객/주문/거래 건인가 (예: `Customer ID 88213`)
2. **근본 원인(Root Cause)**: 조사로 밝혀낸 기술적/업무적 원인 (예: 재시도된 결제 게이트웨이 호출 때문에 생긴 중복 승인 보류(authorization hold)가 해제되지 않음)
3. **권장 조치(Recommended Action)**: 구체적으로 무엇을 하면 되는가 (예: 해당 보류를 무효화(void)하라)

좋은 예:
```
Customer ID 88213
Root cause: 재시도된 게이트웨이 호출로 중복 authorization hold 발생, 미해제 상태
Recommended action: 해당 hold를 void 처리
```

나쁜 요약의 전형:
- **모호함**: "청구 문제 이관됨, 고객이 환불 원함, 알아서 판단 바람" → 근거 데이터도 원인도 없어 인계받은 사람이 조사를 처음부터 다시 해야 합니다.
- **감정/과정 서술만 있음**: "고객이 화가 난 듯하고 여러 질문을 했음" → 원인도 조치도 없습니다.
- **전문(transcript)을 보라고 안내**: 전제상 접근 권한이 없으므로 실행 불가능한 지시입니다.

원칙: 인수인계 요약은 **자기완결적(self-contained)** 이어야 합니다.

## 2. 에이전트 루프와 `stop_reason`

### 2.1 에이전트 루프의 실제 동작

Messages API 기반 에이전트 루프는 대략 이렇게 돕니다.

```
1. 사용자 메시지 + tools 정의를 모델에 보낸다
2. 응답을 받는다
3. 응답의 stop_reason 을 본다
   - "tool_use"  → 모델이 도구를 부르고 싶다는 뜻
                   → 도구를 실제로 실행하고
                   → 그 결과를 tool_result 블록으로 대화에 추가하고
                   → 1번으로 돌아간다
   - "end_turn"  → 모델이 할 말을 다 했다는 뜻 → 루프 종료
4. 최종 답변을 사용자에게 전달
```

여기서 **`stop_reason`** 은 모델이 왜 응답 생성을 멈췄는지를 알려주는 필드입니다. 주요 값:

| 값 | 의미 |
|---|---|
| `tool_use` | 도구를 호출하려고 멈춤. 루프를 계속해야 함 |
| `end_turn` | 자연스럽게 발언을 끝냄. 루프 종료 신호 |
| `stop_sequence` | 지정한 정지 문자열을 만나 멈춤. 역시 종료 신호 |
| `max_tokens` | 출력 토큰 한도에 걸려 잘림 |

**`tool_result`** 는 도구 실행 결과를 모델에게 되돌려주는 메시지 블록입니다. 각 `tool_use`에는 대응하는 `tool_result`가 대화 기록에 붙어야 모델이 다음 판단을 할 수 있습니다.

### 2.2 정지 메커니즘: 무엇이 "주 조건"이어야 하는가

**올바른 주 정지 조건은 `stop_reason`입니다.** `end_turn`(또는 `stop_sequence`)이 오면 멈추고, `tool_use`면 계속합니다. 이것이 "모델이 목표를 달성했다"는 유일한 신뢰 가능한 신호입니다.

반대로 **"정확히 5회 반복하면 무조건 종료" 같은 고정 반복 상한(Fixed Iteration Cap)을 주 정지 메커니즘으로 삼으면 안 됩니다.** 문제는 명확합니다.

> `stop_reason`이 아직 `tool_use`인데 상한에 걸려 루프가 끊기면, 모델이 아직 추론을 끝내지 못한 작업을 강제로 포기하게 됩니다. 결과물은 미완성 상태로 남습니다.

복잡한 조사 작업은 필요한 도구 호출 횟수를 미리 알 수 없습니다. 어떤 질문은 2회로 끝나고 어떤 질문은 30회가 필요합니다.

**그렇다고 상한을 아예 두지 말라는 뜻은 아닙니다.** 고정 상한은 **안전 가드레일 / 서킷 브레이커(circuit breaker)** 로서는 반드시 필요합니다. 모델이 같은 도구를 무의미하게 반복 호출하는 무한 루프에 빠질 때 비용 폭주를 막아주기 때문입니다. 역할 구분이 핵심입니다.

- 정상 종료 판단 → `stop_reason`
- 비정상 상황의 비상 정지 → 반복 상한 (그리고 상한에 걸렸다는 사실을 로그로 남기고 경고 처리)

### 2.3 흔한 오해 바로잡기

- Messages API에 "총 도구 호출 5회"라는 하드 리밋은 **없습니다**. 상한은 개발자가 코드에서 정하는 값입니다.
- 특정 반복 횟수 이후에 `tool_result` 블록 추가가 차단되는 규칙 같은 것도 **없습니다**.
- 반복 상한을 설정한다고 해서 이후 요청에서 `tools` 파라미터가 자동으로 빠지지도 **않습니다**. 그런 자동 동작은 존재하지 않습니다.

## 3. 훅(Hooks)을 통한 결정론적 제어

### 3.1 훅이란 무엇이고 왜 필요한가

**훅(Hook)** 은 에이전트의 실행 흐름 중 정해진 지점에서 자동으로 실행되는 사용자 정의 코드입니다. 대표적인 지점:

- **`PreToolUse`**: 도구가 **실행되기 직전**. 여기서 허용/거부/변형을 결정할 수 있습니다.
- **`PostToolUse`**: 도구가 **실행된 직후**. 결과를 후처리하거나 로그를 남길 수 있지만, **실행 자체를 막을 수는 없습니다** (이미 실행됐기 때문).

훅이 필요한 이유는 **결정론적 제어(Deterministic Control)** 때문입니다.

LLM에게 시스템 프롬프트로 "500달러 넘는 환불은 하지 마"라고 적어두는 것은 **확률적(probabilistic)** 통제입니다. 대부분은 지켜지지만 100%는 아닙니다. 프롬프트 주입 공격, 이상한 입력, 모델의 오판으로 뚫릴 수 있습니다.

훅은 **코드**입니다. `if amount > 500:` 는 매번 똑같이 동작합니다. 이것이 결정론적 제어이며, 금전·삭제·외부 전송처럼 되돌릴 수 없는 작업에는 반드시 이런 코드 레벨 가드레일이 필요합니다.

### 3.2 훅이 프롬프트보다 강한 근본적 이유: 관심사의 분리

시나리오: 환불 정책을 모르는 다른 팀원이 나중에 시스템 프롬프트를 수정하다가 "환불은 500달러까지"라는 문장을 지웠다고 합시다.

- 규칙이 **프롬프트 문장으로만** 존재했다면 → 그 순간 규제가 **조용히 사라집니다**. 아무도 모르게, 아무 오류도 없이.
- 규칙이 **훅으로** 존재한다면 → 훅은 프롬프트와 **분리된 애플리케이션 코드**에 등록되어 있으므로 프롬프트를 어떻게 고치든 그대로 작동합니다. 이 규제를 없애려면 코드를 고쳐야 하고, 코드 변경은 리뷰·버전 관리·테스트를 거칩니다.

이것이 **관심사의 분리(Separation of Concerns)** 이며, 훅을 선택하는 설계상의 핵심 근거입니다.

주의할 오해들:
- 훅은 샘플링 파라미터(temperature 등)를 조절해 모델의 "신뢰도 점수"를 높이는 장치가 **아닙니다**. 훅은 도구 호출을 가로채는 코드 레벨 인터셉터입니다.
- 훅이 시스템 프롬프트와 같은 설정 파일에 저장되어 프롬프트 저장 시 자동 검증해 주는 구조도 **아닙니다**.
- 훅이 매 세션 시작마다 템플릿에서 프롬프트를 재생성해 주는 것도 **아닙니다**.

### 3.3 `PreToolUse` 훅의 출력 구조와 `permissionDecision`

`PreToolUse` 훅은 `hookSpecificOutput` 안에 판정을 담아 반환합니다. 핵심 필드가 **`permissionDecision`** 이며 값은 세 가지입니다.

| 값 | 동작 | 언제 쓰나 |
|---|---|---|
| `allow` | 도구를 그대로 실행 (사용자에게 묻지 않음) | 안전하다고 판정된 호출을 자동 승인 |
| `deny` | 도구 실행을 차단하고 모델에게 거부 사실을 전달 | 절대 허용하면 안 되는 호출 |
| `ask` | 실행을 일시 정지하고 **사람에게 승인/거절을 물음** | 사람의 판단이 필요한 회색지대 |

관련 필드들:
- **`permissionDecisionReason`**: 거부/질의 사유 문자열. 모델이나 사람에게 왜 막혔는지 설명합니다.
- **`updatedInput`**: 도구에 전달될 **입력 인자를 훅이 바꿔치기**할 수 있는 필드. 즉 훅은 통과/차단만이 아니라 **입력 변환(Input Rewriting)** 도 할 수 있습니다.
- **`additionalContext`**: 모델에게 추가 정보를 덧붙여 주는 필드(강제력은 없는 참고 정보).
- **`async` / `asyncTimeout`**: 훅 실행을 비동기로 돌리거나 타임아웃(밀리초)을 조절하는 설정. **주의: 이것들은 실행 타이밍/시간 제어일 뿐, 사람에게 승인을 요청하는 기능이 전혀 아닙니다.** 사람 승인은 오직 `permissionDecision: 'ask'`가 담당합니다.

### 3.4 `ask`: 사람 개입(Human-in-the-Loop) 유도

정책이 "일정 금액 구간(예: $500~$1000)의 환불은 **완전 차단도 아니고 자동 실행도 아니고**, 사람 검토자가 승인/거절하게 하라"고 요구한다면 정답은 `permissionDecision: 'ask'` 하나뿐입니다.

- `deny` + 사유 문구로 "사람에게 연락해 보라"고 모델에게 시키는 것은 **승인 인터페이스를 띄우는 것이 아닙니다**. 그냥 차단입니다.
- `allow` + `additionalContext`로 "나중에 금액을 언급해 달라"고 하는 것은 **이미 환불이 실행된 뒤**입니다. 사전 승인 정책 위반입니다.
- `async: true`, `asyncTimeout: 60000` 은 시간만 벌 뿐 승인 UI를 만들지 않습니다.

`ask`를 쓰면 도구 호출이 대기 상태가 되고 검토자에게 노출(surface)되며, 사람이 승인하면 실행되고 거절하면 실행되지 않습니다. 되돌릴 수 없는(irreversible) 작업에 대한 표준 감독 장치입니다.

### 3.5 `deny`의 부작용: 에이전트 재시도 루프

실무에서 자주 만나는 함정입니다.

LLM은 도구 호출이 `deny`로 실패하면 그것을 **"해결 가능한 오류"** 로 받아들이는 경향이 있습니다. 그래서 인자를 살짝 바꾸거나 그냥 똑같이, 계속해서 재시도합니다. 사용자 입장에서는 "왜 같은 걸 다섯 번씩 시도하지" 하는 나쁜 경험이 됩니다.

**해결 조건이 "사람을 부르지 않고, 훅 코드 자체가 자동으로 결정론적 제어를 유지한 채 재시도를 끊는 것"일 때**의 패턴은 다음과 같습니다.

> `permissionDecision: 'allow'` 를 반환하되, `updatedInput` 으로 실제 실행될 명령을 **무해한 no-op**(예: `echo` 같은 아무 일도 하지 않는 명령)으로 바꿔치기한다.

작동 원리:
- 에이전트 입장에서는 도구 호출이 **성공**했으므로 재시도할 이유가 없어져 루프가 즉시 끝납니다.
- 실제로는 환불이 수행되지 않았으므로 훅이 완전한 통제권을 유지합니다.

각 대안이 왜 요구사항에 안 맞는지:
- `PostToolUse`로 옮겨 실행 후 되돌리기 → 환불이 **이미 나갔습니다**. 사전 차단이 아니며 되돌리기가 실패할 수도 있습니다.
- `permissionDecisionReason` 문자열을 지워 짧게 만들기 → 문구 몇 개를 손보는 프롬프트 튜닝으로는 LLM의 재시도 성향을 결정론적으로 통제할 수 없습니다.
- `ask`로 바꾸기 → 재시도 루프는 멈추지만 **결정을 사람에게 넘기는 것**이므로 "훅이 자동으로 처리하라"는 요구와 어긋나고, 매번 물으면 사용자 피로도가 올라갑니다. (요구사항이 "사람 승인"이면 `ask`가 정답이고, "자동 결정론적 처리"면 `allow` + `updatedInput`이 정답입니다. **문제의 요구 조건에 따라 답이 갈립니다.**)

### 3.6 훅 매처(Matcher)와 정규표현식 앵커

훅은 모든 도구에 무차별로 걸지 않고 **매처(Matcher)** 로 대상 도구 이름을 지정합니다. 매처는 정규표현식(Regex)으로 해석됩니다.

여기서 아주 흔한 실수가 나옵니다.

```
매처: /refund/
의도: refund 라는 도구 하나만 게이트
실제: 이름에 "refund" 가 들어간 모든 도구에 매칭
```

이유는 **정규표현식은 기본적으로 부분 문자열(substring) 검색**이기 때문입니다. `/refund/`는 다음 모두와 일치합니다.

- `refund` ✔ (의도한 것)
- `issue_refund_note` ✔ (의도하지 않음 — 내부 메모만 쓰는 도구)
- `refund_user` ✔
- `process_refund` ✔

이것을 **오버매칭(Over-matching)** 이라고 합니다. 훅이 걸리면 안 되는 무해한 도구까지 차단되어 기능이 망가집니다.

**해결책은 앵커(Anchor)** 입니다.

- `^` : 문자열의 **시작**을 의미
- `$` : 문자열의 **끝**을 의미

```
/^refund$/
```

이렇게 쓰면 "시작하자마자 refund가 나오고 그걸로 끝나는" 이름, 즉 정확히 `refund`인 도구에만 매칭됩니다. `issue_refund_note`는 앞에 `issue_`가 있으므로 `^` 조건에서 탈락합니다.

부수적으로 알아둘 사실:
- 훅의 정규표현식 매처는 **자동으로 앵커링되지 않습니다**. 명시하지 않으면 부분 일치입니다.
- 매처는 `mcp__` 접두사가 붙은 MCP 서버 도구뿐 아니라 **일반 인-프로세스 커스텀 도구 이름도 자유롭게 대상으로 삼을 수 있습니다**. 접두사를 붙이려고 도구 이름을 바꿀 필요가 없습니다.
- 타임아웃 설정은 매칭 패턴과 아무 관련이 없습니다. 매칭 문제는 정규표현식으로 고쳐야 합니다.

## 4. 권한(Permission)과 설정 계층

### 4.1 서브에이전트의 `tools` 필드

서브에이전트를 정의할 때 그 에이전트가 쓸 수 있는 도구 목록을 지정합니다.

```
name: test-runner
tools: ["Bash", "Read", "Grep"]
```

여기서 중요한 오해가 있습니다. **이 `tools` 목록은 "권한 부여"가 아니라 "권한 축소"에 가깝습니다.** 즉 "이 에이전트에게는 이 도구들만 보이게 하라"는 화이트리스트일 뿐, 상위에서 금지한 것을 되살리는 힘은 없습니다.

### 4.2 권한 상속(Permission Inheritance)

`settings.local.json` 같은 설정 파일에는 **deny 규칙**(특정 도구/명령 사용 차단)을 쓸 수 있습니다.

핵심 규칙:

> **서브에이전트는 코디네이터(상위) 레벨의 보안 설정과 deny 규칙을 상속받습니다. 하위 설정으로 상위 금지를 우회할 수 없습니다.**

구체적 상황:
- `test-runner` 서브에이전트는 자기 정의에 `Bash`를 포함하고 있다.
- 그런데 이 서브에이전트를 부르는 코디네이터의 `settings.local.json`에는 `Bash`를 막는 deny 규칙이 있다.
- 결과: **`Bash`는 실행되지 않습니다. 첫 번째 호출부터 즉시 차단됩니다.**

왜 이렇게 설계되었는가: 만약 하위 정의가 상위 정책을 뚫을 수 있다면, 보안 설정이 무의미해집니다. 누구든 서브에이전트를 하나 정의해서 금지된 도구를 쓸 수 있게 되기 때문입니다. 그래서 **deny는 항상 위에서부터 강하게 적용되는 상위 가드레일**입니다.

틀린 통념:
- 서브에이전트의 `tools` 필드가 독립적으로 접근 권한을 준다 → 아닙니다.
- `Task`(에이전트 호출 도구)를 `tools`에 넣어야 다른 도구들이 활성화된다 → 그런 규칙은 없습니다. 차단 원인은 상속된 deny 규칙입니다.
- 첫 호출만 허용되고 이후가 막힌다 → 아닙니다. 횟수와 무관하게 처음부터 차단됩니다.

## 5. 세션(Session)과 컨텍스트 관리

### 5.1 세션이란

**세션(Session)** 은 하나의 작업 대화 전체(주고받은 메시지, 도구 호출 기록, 그 결과)를 담은 단위입니다. Claude Code CLI는 세션을 저장해 두었다가 나중에 이어서 작업할 수 있게 해 줍니다.

### 5.2 세션 이름 짓기와 재개(Resume)

기본적으로 세션에는 자동 생성된 식별자가 붙습니다. 원시 **세션 ID**(긴 무작위 문자열)나 "디렉토리 이름 + 무작위 접미사" 형태의 표시 이름 같은 것들입니다. 문제는 같은 날 여러 조사 작업을 병렬로 돌리면 이런 이름으로는 어느 게 어느 작업인지 구분이 안 된다는 점입니다.

해결책은 **사람이 읽을 수 있는 이름(human-readable handle)을 직접 붙이는 것**입니다.

- 세션 **시작 시점**에 설명적인 이름을 지정하거나,
- 세션 도중 **`/rename`** 슬래시 명령으로 이름을 바꿉니다.

그 후에는 이름으로 바로 재개할 수 있습니다.

```
claude --resume <name>
```

(원시 세션 ID로도 재개는 됩니다: `claude --resume <session-id>`. 하지만 ID를 스프레드시트에 일일이 적어 관리하는 것은 번거롭고, "기억하기 쉬운 핸들"이라는 요구를 충족하지 못합니다.)

다른 대안들의 문제:
- 자동 생성 이름에 의존 → 병렬 작업 구분이 안 됩니다.
- 세션을 끄지 않고 계속 켜두기 → 리소스 낭비이고, 애초에 "종료 후 나중에 이름으로 재개"라는 목적과 맞지 않습니다.

### 5.3 스테일(Stale) 컨텍스트와 컨텍스트 오염

**스테일(Stale)** 하다는 것은 저장된 정보가 **더 이상 현실과 맞지 않는다**는 뜻입니다.

전형적 상황: 이전 세션에서 대규모 코드베이스를 수십 턴에 걸쳐 읽고 상호 참조했는데, 그 이후에 코드가 대대적으로 리팩토링되었습니다. 세션 기록 속의 파일 내용, 함수 위치, 구조 파악은 전부 **옛날 코드**의 것입니다.

이 기록을 그대로 안고 작업을 재개하면 **컨텍스트 오염(Context Pollution)** 이 일어납니다. 모델은 대화 기록에 있는 내용을 사실로 간주하므로, 이미 사라진 함수를 호출하려 하거나 존재하지 않는 파일 경로를 참조하는 잘못된 전제 위에서 추론합니다.

### 5.4 이어가기 전략: 언제 무엇을 쓰는가

| 전략 | 의미 | 이 상황에서의 문제 |
|---|---|---|
| **Resume** (재개) | 이전 세션을 그대로 열어 모든 기록을 물려받음 | 스테일한 도구 결과를 전부 상속 → 잘못된 답 생성 |
| **Fork** (분기) | 이전 세션을 복제해 별도 갈래로 진행 | 복제해도 스테일한 히스토리는 그대로 따라옴 |
| **Resume + `/clear`** | 재개한 뒤 컨텍스트 창을 비움 | 결과적으로 빈 상태가 되지만, 굳이 재개했다가 지우는 불필요한 우회. 세션 관리 오버헤드만 생김 |
| **Fresh Session + 요약 주입** | 새 세션을 열고 미리 정리해 둔 구조화 요약본을 첫 프롬프트로 넣음 | **가장 신뢰할 수 있는 방법** |

**Fresh Session Injection**이 표준인 이유:
- 스테일한 중간 도구 호출 기록이 애초에 들어오지 않으므로 오염 가능성이 0입니다.
- 필요한 것(검증된 결론)만 들어가므로 토큰도 절약됩니다.
- 모델이 최신·정제된 전제 위에서만 추론합니다.

전제 조건은 **최종 결론이 이미 구조화된 형태로 정리되어 있어야 한다**는 것입니다. 진행 상황 노트(progress notes)나 요약 문서(summary document)가 그 역할을 합니다. 그래서 긴 작업을 할 때는 중간중간 결론을 별도 문서에 남겨두는 습관이 중요합니다. 그 문서가 다음 세션의 "씨앗"이 됩니다.

**`/clear`** 는 현재 세션의 컨텍스트 창을 비우는 슬래시 명령입니다. 세션 도중 주제가 완전히 바뀔 때 유용하지만, 위 시나리오처럼 애초에 새로 시작하면 되는 경우에는 굳이 재개 후 지울 이유가 없습니다.

## 6. 관통하는 설계 원칙 정리

전체 범위를 관통하는 사고방식을 몇 줄로 정리하면 다음과 같습니다.

1. **확률적 통제보다 결정론적 통제**: 중요한 규칙은 프롬프트 문장이 아니라 코드(훅, 권한 설정)에 둡니다.
2. **투명성 우선**: 모르는 것을 아는 척 정리하지 말고, 상충·불확실·미완료 상태를 그대로 위로 올립니다.
3. **컨텍스트는 자산이자 부채**: 필요한 정보만 넣고, 오래된 정보는 적극적으로 버립니다. 격리가 기본값입니다.
4. **정지 조건은 모델의 신호를 따르되, 안전망은 따로 둡니다**: `stop_reason`이 주 조건, 반복 상한은 서킷 브레이커.
5. **필요한 만큼만 실행**: 정적 전체 파이프라인보다 입력에 따라 경로를 고르는 동적 라우팅.
6. **되돌릴 수 없는 작업에는 사람을 넣습니다**: `ask`를 통한 human-in-the-loop.
7. **명시적으로 좁히기**: 정규표현식은 앵커로, 권한은 최소한으로, 이름은 사람이 읽을 수 있게.

## 7. 용어 사전 (Glossary)

| 영어 용어 | 한국어 설명 |
|---|---|
| **Agent** | 도구를 스스로 호출하며 목표 달성까지 루프를 도는 LLM 기반 프로그램 |
| **Orchestrator / Coordinator** | 작업을 분해해 서브에이전트에게 배분하고 결과를 종합하는 상위 에이전트 |
| **Subagent** | 오케스트레이터의 지시로 좁은 범위 작업만 수행하는 하위 에이전트 |
| **Hub-and-Spoke** | 모든 통신이 중앙 허브(오케스트레이터)를 거치는 아키텍처 형태 |
| **Synthesis** | 여러 서브에이전트의 결과를 하나의 일관된 답으로 종합하는 과정 |
| **Hallucination** | 모델이 근거 없이 그럴듯한 정보를 지어내는 현상 |
| **Nesting Depth** | 에이전트가 자식 에이전트를 만드는 중첩 단계 수. Claude Code는 메인 포함 최대 5단계 |
| **Hard Limit** | 설정으로 풀 수 없는 고정 상한 |
| **Context Window** | 모델이 한 번에 참조할 수 있는 대화·문서 내용의 총량 |
| **Context Isolation** | 각 서브에이전트가 별도의 독립 컨텍스트를 갖게 하는 설계 |
| **Stateless** | 호출 간 상태를 기억하지 않는 성질. 서브에이전트의 기본 동작 |
| **Session Resumption** | 특정 에이전트/세션 ID를 지정해 이전 상태를 이어받는 것 |
| **Fresh Context** | 이전 기록이 전혀 없는 깨끗한 새 컨텍스트 |
| **Partial Output** | 실행이 중단되기 전까지 생성된 부분 결과물. 미완료 표시와 함께 코디네이터에게 전달됨 |
| **Server Overload** | 서버 과부하로 응답이 중간에 끊기는 오류 상황 |
| **Handoff Summary** | AI가 사람에게 업무를 넘길 때 전달하는 자기완결적 요약(식별자·근본원인·권장조치) |
| **Root Cause** | 증상이 아닌 문제의 근본 원인 |
| **Transcript** | 대화 전문 기록 |
| **Latency** | 요청부터 응답까지 걸리는 지연 시간 |
| **Static Pipeline** | 입력과 무관하게 항상 동일한 전체 단계를 실행하는 고정 구조 |
| **Dynamic Routing** | 입력의 성격을 먼저 판단해 필요한 단계만 골라 실행하는 방식 |
| **Structured Output (JSON)** | 코드가 확정적으로 파싱할 수 있도록 필드를 정해 반환하는 출력 형식 |
| **Agentic Loop** | 도구 호출과 결과 반영을 반복하는 에이전트의 실행 순환 구조 |
| **`stop_reason`** | 모델이 응답을 멈춘 이유를 나타내는 API 응답 필드 |
| **`tool_use`** | 모델이 도구를 호출하려고 멈췄다는 `stop_reason` 값. 루프를 계속해야 함 |
| **`end_turn`** | 모델이 발언을 자연스럽게 마쳤다는 `stop_reason` 값. 루프 종료 신호 |
| **`tool_result`** | 도구 실행 결과를 모델에게 되돌려주는 메시지 블록 |
| **Iteration Cap** | 루프 반복 횟수 상한. 주 정지 조건이 아니라 안전망으로만 써야 함 |
| **Circuit Breaker** | 비정상 폭주를 감지해 강제로 끊는 안전 장치 |
| **Hook** | 에이전트 실행 흐름의 특정 지점에서 자동 실행되는 사용자 정의 코드 |
| **`PreToolUse`** | 도구 실행 직전에 동작하는 훅. 허용/거부/입력변형이 가능 |
| **`PostToolUse`** | 도구 실행 직후에 동작하는 훅. 실행 자체는 막을 수 없음 |
| **`hookSpecificOutput`** | 훅이 판정 결과를 담아 반환하는 출력 구조 |
| **`permissionDecision`** | 훅의 판정 값: `allow`(실행) / `deny`(차단) / `ask`(사람 승인 요청) |
| **`permissionDecisionReason`** | 거부·질의 사유를 설명하는 문자열 |
| **`updatedInput`** | 훅이 도구에 전달될 입력 인자를 바꿔치기하는 필드 |
| **`additionalContext`** | 모델에게 참고 정보를 덧붙이는 필드(강제력 없음) |
| **`async` / `asyncTimeout`** | 훅의 비동기 실행 여부와 타임아웃(ms) 설정. 사람 승인 기능과 무관 |
| **Input Rewriting** | 훅이 도구 입력을 안전한 형태로 변환하는 기법 |
| **No-op** | 아무 동작도 하지 않는 명령(예: `echo`) |
| **Deterministic Control** | 매번 동일하게 작동하는 코드 기반의 확정적 통제 |
| **Guardrail** | 위험 행동을 사전에 막는 안전 장치 |
| **Human-in-the-Loop (HITL)** | 중요한 결정 지점에 사람의 승인/판단을 끼워 넣는 설계 |
| **Separation of Concerns** | 서로 다른 책임을 분리해 한쪽 변경이 다른 쪽을 망가뜨리지 않게 하는 원칙 |
| **Matcher** | 훅을 적용할 도구 이름을 지정하는 패턴 |
| **Regex Anchor (`^`, `$`)** | 문자열의 시작과 끝을 고정해 정확 일치를 강제하는 정규표현식 기호 |
| **Unanchored Regex** | 앵커가 없어 부분 문자열만 있어도 일치하는 정규표현식 |
| **Over-matching** | 의도보다 넓은 대상에 패턴이 걸리는 문제 |
| **`mcp__` prefix** | MCP 서버가 제공하는 도구 이름에 붙는 접두사. 매처 사용의 필수 조건은 아님 |
| **`settings.local.json`** | 로컬 권한·설정을 담는 파일. deny 규칙 등을 정의 |
| **Deny Rule** | 특정 도구·명령의 사용을 차단하는 규칙 |
| **Permission Inheritance** | 서브에이전트가 상위 코디네이터의 보안 정책을 그대로 물려받는 성질 |
| **`tools` field** | 서브에이전트가 사용할 도구 화이트리스트. 상위 deny를 우회하지 못함 |
| **Session** | 대화·도구 호출·결과를 담은 하나의 작업 단위 |
| **`/rename`** | 진행 중인 세션에 사람이 읽기 쉬운 이름을 부여하는 슬래시 명령 |
| **`claude --resume <name>`** | 이름 또는 세션 ID로 이전 세션을 재개하는 CLI 명령 |
| **`/clear`** | 현재 세션의 컨텍스트 창을 비우는 슬래시 명령 |
| **Fork** | 기존 세션을 복제해 별도 갈래로 진행하는 것(히스토리도 함께 복제됨) |
| **Stale** | 저장된 정보가 현실 변화로 더 이상 유효하지 않은 상태 |
| **Context Pollution** | 낡거나 무관한 정보가 컨텍스트에 남아 판단을 그르치는 현상 |
| **Fresh Session Injection** | 새 세션을 열고 정제된 요약본만 첫 프롬프트로 주입하는 이어가기 전략 |
| **Messages API** | Claude에 메시지와 도구 정의를 보내 응답을 받는 API |
