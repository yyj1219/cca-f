# 1. 컨텍스트 윈도우와 관리 기법

**이 장에서 다루는 것**

- 토큰, 컨텍스트 윈도우, 컨텍스트 예산 — 그리고 "창을 키우면 다 해결되나?"
- LLM API의 무상태성(Stateless)과 흔한 오해
- 요약/압축(Summarization, Compaction)의 손실성과 정보 유실
- 스크래치패드와 영속 메모리 — 컨텍스트 → 디스크 오프로딩
- 프롬프트 구조화와 Lost in the Middle
- 컨텍스트 오염 방지 — 도구 출력 트리밍과 구조화 레코드

## 1.1 컨텍스트 윈도우와 토큰 예산

### 1.1.1 LLM과 토큰

**LLM(Large Language Model, 대규모 언어 모델)** 은 텍스트를 입력받아 그 다음에 올 텍스트를 생성하는 모델입니다. Claude, GPT 같은 것들이 여기에 해당합니다. 우리가 "AI가 대화한다"고 느끼는 것은, 실제로는 **매번 대화 전체를 다시 입력해서 다음 문장을 생성**하는 과정의 반복입니다.

LLM은 글자가 아니라 **토큰(token)** 단위로 텍스트를 처리합니다. 토큰은 대략 단어 조각 하나 정도의 크기입니다.

- 영어 기준 대략 1토큰 ≈ 4글자, 1토큰 ≈ 0.75단어
- 한국어는 더 잘게 쪼개져 글자당 1~2토큰 정도를 소비합니다

비용과 속도가 모두 토큰 수에 비례하므로, "토큰을 아낀다"는 말은 곧 **"돈과 시간과 정확도를 아낀다"** 는 뜻입니다.

### 1.1.2 컨텍스트 윈도우(Context Window)

**컨텍스트 윈도우**란 한 번의 모델 호출(추론)에 넣을 수 있는 토큰의 최대치입니다. LLM은 별도의 기억 장치가 없고, 매번 응답을 만들 때 **입력으로 들어온 텍스트 전체**만 보고 판단합니다. 이 "한 번에 볼 수 있는 텍스트의 최대 분량"이 컨텍스트 윈도우입니다.

여기에는 다음이 **모두** 들어가야 합니다.

- 시스템 프롬프트 / 규칙
- 대화 기록(messages)
- 도구 호출 결과
- 첨부 문서, 파일 내용
- 모델이 생성할 답변(출력)

예: 컨텍스트 윈도우가 20만 토큰인 모델은, 위의 것을 전부 합쳐 20만 토큰을 넘을 수 없습니다. 윈도우가 100만 토큰이라 해도 무한이 아닙니다. 로그 덤프, 파일 전문(全文), 검색 결과 같은 것은 놀라울 정도로 빠르게 윈도우를 채웁니다.

컨텍스트 윈도우는 **고정된 크기**입니다. 대화 도중에 저절로 줄어들거나 늘어나지 않습니다.

**왜 이게 중요한가?** 상한을 넘으면 요청이 실패하거나 앞부분이 잘려 나갑니다(**truncation, 절단**). 그러면 모델은 그 내용을 "잊어버립니다". 잊었다는 사실조차 인지하지 못하고, 그럴듯한 답을 지어내기도 합니다.

토큰이 늘어나면 세 가지 비용이 함께 늘어납니다.

| 비용 | 내용 |
|---|---|
| 금전적 비용 | API는 입력 토큰 수에 비례해 과금됩니다. 매 턴 20만 토큰을 보내면 비용이 선형으로 증가합니다 |
| 지연 시간(Latency) | 입력이 길수록 응답이 느려집니다 |
| 정확도 저하 | 관련 없는 정보가 많을수록 모델이 핵심을 놓칩니다 |

따라서 "컨텍스트에 무엇을 넣을 것인가"는 성능·비용·품질을 **동시에** 결정하는 설계 문제입니다.

### 1.1.3 컨텍스트 예산(Context Budget)

실무에서는 윈도우 크기를 그냥 쓰는 게 아니라, 용도별로 **예산을 배분**합니다. 시스템 설계 시 각 구성 요소가 쓸 수 있는 토큰 양을 미리 배분해 둔 것을 컨텍스트 예산이라고 부릅니다.

```
전체 200,000 토큰 예산 예시
├─ 시스템 프롬프트 / 규칙        2,000
├─ 영속 팩트 블록                 500
├─ 대화 요약                    3,000
├─ 검색·도구 결과              40,000
├─ 참조 문서                  100,000
└─ 출력 여유분                 20,000
```

예: 요약 작성 에이전트에게 총 20만 토큰이 주어졌다면, 여기에 6개 서브에이전트의 결과가 모두 들어가야 합니다.

**예산을 넘기면 일어나는 일:**

- **오류**: 호출 자체가 거부됩니다.
- **잘림(Truncation)**: 앞부분(또는 뒷부분)이 통째로 버려집니다. 6개 중 뒤 2개 결과가 완전히 사라지는 식입니다.
- **버림(Drop)**: 파이프라인이 임의로 일부 입력을 통째로 버립니다.

마지막 경우가 **가장 위험합니다.** 에러가 안 나고, 결과물에서 특정 내용이 그냥 없어지기 때문입니다.

### 1.1.4 다운스트림(Downstream) 에이전트와 생산자 책임

여러 에이전트를 파이프라인으로 연결하면, 앞 단계 출력이 뒤 단계 입력이 됩니다. 앞 단계 5개가 각각 "약간 장황"하면, 뒤 단계에서는 그것이 5배로 곱해져 폭발합니다.

> **핵심 규칙: 컨텍스트 예산은 생산자(producer) 쪽에서 지켜야 한다.**
> 소비자(consumer) 쪽에서 "알아서 잘 읽어라"라고 요구하는 것으로는 해결되지 않습니다.

### 1.1.5 흔한 오해 정리

**(1) max_tokens(최대 출력 토큰)를 늘리면 되지 않나?**

`max_tokens`는 **모델이 한 번에 생성할 답변의 길이 상한**입니다. 이것을 늘려도:

- 입력으로 들어갈 수 있는 과거 대화의 양은 늘어나지 않습니다.
- 이미 컨텍스트에서 밀려난 정보를 되살려 주지도 않습니다.

**(2) 더 큰 모델 / 더 큰 컨텍스트 윈도우로 바꾸면 기억이 돌아오나?**

아닙니다. 모델 파라미터 수가 늘어난다고 해서 **입력에 없는 정보**를 알 수는 없습니다. 컨텍스트에서 이미 잘려 나간 사실은 어떤 모델로도 복원되지 않습니다. 더 큰 윈도우는 도움이 되지만 근본 해결책이 아닙니다.

- **비용**: 입력 토큰만큼 요금이 선형 증가합니다.
- **지연 시간**: 입력이 길수록 느려집니다.
- **Needle-in-a-Haystack 문제(건초더미 속 바늘)**: 컨텍스트가 매우 길면 모델이 그 안의 특정 사실을 정확히 찾아내는 능력이 떨어집니다. **창 안에 있어도 "못 보는" 일이 생깁니다.**

따라서 큰 창에 다 넣는 것보다, **넣을 것을 고르는 설계**가 중요합니다. **큰 컨텍스트 윈도우는 컨텍스트 설계를 대체하지 못합니다.**

### 1.1.6 컨텍스트 열화 / 저하 (Context Degradation)

긴 세션에서 초반에 확인했던 구체적 사실이 후반부에 사라지거나 흐려지는 현상입니다. 몇 시간짜리 긴 세션에서 자주 관찰됩니다.

전형적인 사례:

1. 세션 초반, 서브에이전트가 "이 서비스는 예외(exception) 대신 커스텀 `Result` 타입을 쓴다"는 구체적 사실을 발견하고 보고합니다.
2. 세션이 계속되며 대화가 누적됩니다.
3. 3시간 후 같은 질문을 하면 에이전트가 "일반적으로 try/catch와 로깅을 씁니다"라고 **일반론**으로 답합니다. 이전 발견과 모순됩니다.

**여기서 두 번째 답은 환각(hallucination)입니다.** 실제 코드를 확인한 게 아니라, 학습 과정에서 익힌 "보통 이렇게들 한다"는 일반적 패턴을 그럴듯하게 재생산한 것입니다. 초기 발견 내용이 활성 컨텍스트 밖으로 밀려났거나(잘림), 압축 과정에서 생략되었고, 모델은 근거를 잃자 학습된 일반적 패턴으로 빈칸을 채웁니다.

원인은 모델 고장도, 권한 문제도, 네트워크 문제도, 애플리케이션 고장도 아닙니다. 컨텍스트 윈도우의 유한성에서 나오는 **구조적이고 정상적인** 현상입니다. 따라서 해결책도 재시작이 아니라 **설계**입니다.

## 1.2 LLM API의 무상태성 (Stateless API)

### 1.2.1 무상태란

**무상태(Stateless)** 란 서버가 이전 요청에 대한 정보를 전혀 기억하지 않는다는 뜻입니다. Claude API를 포함한 표준 LLM API 서버는 무상태입니다.

- 모델은 **서버 쪽에 대화 내역을 저장하지 않습니다.**
- 매 API 호출마다 클라이언트(개발자의 애플리케이션)가 **필요한 모든 맥락을 직접 다시 보내야** 합니다.
- 요청에 포함되지 않은 정보는 모델 입장에서 **존재하지 않는 정보**입니다.

각 요청은 그 요청에 담긴 내용만으로 완결적으로 처리됩니다.

```python
# 잘못된 이해: "모델이 알아서 기억하겠지"
client.messages.create(model="...", messages=[{"role": "user", "content": "아까 말한 그 좌석으로 예약해줘"}])
# → 모델은 "아까"가 무엇인지 전혀 모름. 그 대화가 요청에 없기 때문.

# 올바른 방식: 대화 전체를 매번 다시 보냄
messages = [
    {"role": "user", "content": "비즈니스석으로 알아봐줘"},
    {"role": "assistant", "content": "비즈니스석 조회 결과입니다..."},
    # ... 중간 대화들 ...
    {"role": "user", "content": "아까 말한 그 좌석으로 예약해줘"},
]
client.messages.create(model="...", messages=messages)
```

### 1.2.2 messages 배열

API 요청의 `messages` 파라미터는 대화 기록을 담는 배열입니다. 각 원소는 `role`(`user` 또는 `assistant`)과 `content`를 가집니다. **이 배열이 곧 모델이 볼 수 있는 세계의 전부입니다.**

### 1.2.3 흔한 오해: session_id

개발자가 자기 앱에서 만든 `session_id`를 요청에 함께 보내면서 "API가 알아서 이전 대화를 찾아 붙여주겠지"라고 가정하는 실수가 흔합니다.

그 결과: 사용자가 세션을 재개하면 어시스턴트가 이전에 논의한 위험 감수 성향, 투자 목표 같은 것을 "잊어버린" 것처럼 보입니다. 실제로는 잊은 게 아니라 **애초에 전달받은 적이 없습니다.**

세션 ID는 **당신의 애플리케이션이 만든 값**입니다. API는 그 값의 의미를 모릅니다.

### 1.2.4 올바른 구현

대화 이력은 **애플리케이션이 저장하고, 매 요청마다 `messages` 배열에 실어 보냅니다.**

```python
# 1) 앱의 DB에서 이 세션의 이전 대화를 불러온다 (resolve)
history = db.load_messages(session_id)
# history = [
#   {"role": "user",      "content": "은퇴 자금을 모으고 싶어요"},
#   {"role": "assistant", "content": "위험 감수 성향은 어떠신가요?"},
#   {"role": "user",      "content": "보수적인 편입니다"},
# ]

# 2) 이전 이력 + 새 메시지를 함께 보낸다
response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    messages=history + [{"role": "user", "content": new_user_message}],
)

# 3) 이번 턴도 DB에 저장해서 다음 재개에 대비한다
db.append_messages(session_id, new_user_message, response.content)
```

**핵심 결론:** "모델에 내장된 대화 메모리"라는 것은 존재하지 않습니다. 대화의 연속성은 **애플리케이션(개발자)이 책임지고 관리**하는 것입니다.

**왜 다른 방법들은 해결책이 아닌가:**

| 잘못된 대안 | 왜 안 되는가 |
|---|---|
| 컨텍스트 윈도우가 더 큰 모델로 교체 | 창 크기 문제가 아닙니다. 데이터가 애초에 요청에 담기지 않았습니다. 창을 아무리 키워도 없는 것은 보이지 않습니다 |
| 새 메시지를 짧게 쓰기 | 보내지도 않은 과거를 모델이 "회상"할 방법은 없습니다 |
| 사용자에게 매번 다시 말해달라고 요청 | 앱이 저장하고 다시 보내면 완전히 해결되는 문제를 사용자에게 떠넘기는 것입니다. 시스템의 책임을 사용자에게 전가하는 잘못된 설계입니다 |

### 1.2.5 부수적 함의

무상태이기 때문에 대화가 길어질수록 매 요청의 토큰 수가 계속 증가합니다. 이것이 다음 절의 압축과 스크래치패드가 필요한 **근본 이유**이기도 합니다. (반복되는 앞부분을 캐싱하는 프롬프트 캐싱 같은 기법도 이 성질에서 나옵니다.)

## 1.3 요약/압축과 정보 유실

### 1.3.1 용어 정리

같은 아이디어가 문맥에 따라 여러 이름으로 불립니다. 모두 "대화 이력을 요약으로 대체해 토큰 공간을 회수하는 것"입니다.

| 용어 | 뉘앙스 |
|---|---|
| 압축 / 컴팩션(Compaction) | 길어진 세션의 대화 기록을 요약으로 대체해 컨텍스트 공간을 **되찾는(reclaim)** 동작. 코딩 에이전트의 `/compact` 명령이 대표적 |
| 롤링 요약 / 순환 요약(Rolling Summary) | 앞부분 대화를 요약문으로 대체하고, 매 호출에는 "요약 + 최신 메시지"만 보냄 |
| 반복 요약(Iterative Summarization) | 요약본 위에 또 요약을 얹는 방식 |
| 러닝 서머리(Running Summary) | 몇 턴마다 지금까지 내용을 요약해 원문 대신 유지 |

**장점**: 컨텍스트 초과를 막고, 토큰이 줄어드니 비용과 지연 시간이 감소합니다.

**한계**: 요약은 본질적으로 **손실 압축(lossy compression)** 입니다. **압축이 모든 사실을 보존한다는 보장은 없습니다.**

### 1.3.2 무엇이 가장 먼저 사라지는가

요약 알고리즘은 문장의 "요지"를 남기고 세부를 버립니다. 요약 모델에게 중요한 것은 "이야기의 흐름"이지 "숫자 하나하나"가 아닙니다. 그래서 다음이 잘 사라집니다.

- **정확한 숫자**: 금액 $6,400 → "수천 달러"로 뭉개짐
- **식별자(ID)**: 주문번호, 청구 번호 #C-1092 같은 것
- **정확한 리터럴 값**: 설정값, 변수명, 버전 번호, 파일 경로, 에러 코드
- **날짜와 마감일**
- **여러 개체 간의 구분**: 두 건의 청구가 "그 청구"로 합쳐짐
- **인용 정보(citations)**: 출처 URL, 문서명

### 1.3.3 요약 드리프트(Summarization Drift) — 실제 예시

요약을 반복할수록 디테일이 점점 **일반화(generalized)** 되거나 아예 **누락(dropped)** 되고, 이 유실은 **가속**됩니다.

**예 1 — 결제 이중 청구**

```
1차 원문 : "2026년 3월 14일에 주문번호 #12345로 $150.00을 결제했는데 이중 청구되었습니다."
2차 요약 : "3월 중순 주문 #12345에 대해 약 $150 이중 청구 발생"
3차 요약 : "이전 주문의 이중 청구 문제"
4차 요약 : "결제 관련 이슈"
```

**예 2 — 환불 요청**

```
원본:
  "주문번호 A-4471-20 건인데요, 214.88달러 환불 요청드립니다.
   15일까지는 처리돼야 합니다."

3차 요약 후:
  "고객이 곧 환불을 원하며 지난달 주문에 대해 언급했다"
```

주문번호, 정확한 금액, 마감일이 전부 사라졌습니다.

**예 3 — 의료 예약 (안전 사고 시나리오)**

```
원본:  "페니실린 알레르기가 있고, 22일에 예약을 원합니다"
1차:   "페니실린 알레르기, 22일 예약 희망"
3차:   "약물 알레르기 있음, 이번 달 예약 희망"
5차:   "환자가 몇몇 알레르기가 있고 곧 예약을 원함"
```

"페니실린"이 "몇몇 알레르기"가 되는 순간, 의료 시스템에서는 이것이 **안전 사고**가 됩니다.

### 1.3.4 요약에 대한 함정과 오해

- **요약을 반복하면 원본 수치의 오류가 교정된다?** 아닙니다. 모델에는 대조할 원본이 이미 없습니다.
- **요약 프로세스가 숫자만 알아서 별도 메모리로 옮겨준다?** 그런 기능은 기본 제공되지 않습니다. **직접 설계해야 존재합니다.**
- **요약을 1문장에서 3문장으로 늘리면 된다?** 손실 압축이라는 성질 자체는 그대로이므로, 언제든 다른 디테일이 누락될 수 있습니다.
- **요약 주기를 더 자주 돌리면 된다?** 해결이 아니라 **악화**입니다. 압축 특성 자체가 바뀌지 않고, 압축을 여러 번 반복하면 정보 손실이 누적됩니다.
- **요약 빈도를 낮추면 된다?** 압축 시점을 미룰 뿐, 압축이 일어나는 순간 같은 손실이 발생합니다.
- 요약이 반복될수록 원문에 없던 표현이 끼어드는 **환각 위험**도 커집니다.

### 1.3.5 서버 측 컨텍스트 압축 (Server-side Context Compaction)

Claude API가 제공하는 기능으로, 대화가 길어졌을 때 서버가 자동으로 이전 메시지들을 요약·압축해 컨텍스트 안에 유지시켜 줍니다.

- 관련 설정: `context_management` 파라미터
- 베타 헤더 예시: `compact-2026-01-12`

**동작 범위**: 압축은 도구 실행 결과(tool results)뿐 아니라 **대화 내역 전체(모델이 생성한 텍스트 포함)** 를 대상으로 합니다.

**전형적인 실패 양상**: 여러 차례 압축을 거치면 "발견한 사실(findings)"은 살아남지만 그 사실을 뒷받침하던 **인용 정보(citations, 출처 URL·문서명)** 가 사라집니다. 요약을 수행하는 모델이 출처 정보를 "부연 설명"으로 판단해 버리기 때문입니다.

**대응 원칙**: 압축 규칙이나 요약 프롬프트에 **"각 주장과 그 출처의 매핑(claim-source mapping)을 반드시 보존하라"** 는 지시를 명시적으로 넣어야 합니다. 명시하지 않으면 보존되지 않습니다.

참고로 **존재하지 않는 것들**: 대화 차례 수에 따라 인용만 따로 지워지는 별도 임시 캐시, 대화 도중 컨텍스트 윈도우가 저절로 줄어드는 동작 — 이런 메커니즘은 없습니다.

### 1.3.6 해결책 (1): 영속 팩트 블록 (Persistent Case-Facts Block)

핵심 원칙은 요약 빈도를 조절하는 것이 아니라, **절대 잃으면 안 되는 정밀 정보를 요약 대상 텍스트에서 빼내는 것**입니다. "절대 요약하지 않는 구역"을 만들고, 매 프롬프트마다 **요약본 바깥에** 그대로 주입합니다.

**형식 예 1 — 고객 지원(환불)**

```
[시스템 프롬프트]
...

[CASE FACTS - 요약 금지, 매 턴 그대로 유지]
order_id: A-4471-20
refund_amount_usd: 214.88
customer_stated_deadline: 2026-03-15
account_status: verified

[대화 요약]
고객이 환불을 요청 중이며 배송 지연에 불만을 표시함...

[최근 대화 원문]
...
```

**형식 예 2 — 보험 청구**

```
## CASE FACTS (요약 대상 아님)
- 고객 ID: CU-88213
- 청구 #C-1092 | 수해 | $6,400 | 심사 중
- 청구 #C-1108 | 자동차 유리 | $310 | 승인됨
- SLA 만료: 2026-09-12
```

**형식 예 3 — 의료 예약**

```
=== 확정 사실 (변경 금지, 원문 그대로 유지) ===
- 알레르기: 페니실린
- 요청 예약일: 22일
- 환자 ID: 88213
=============================================

=== 대화 요약 ===
환자가 정기 검진 일정 변경을 문의 중이며 …
```

**특징:**

- 요약 파이프라인을 **통과하지 않는다** → 절대 흐려지지 않음
- 구조화된 키-값 형태라 토큰도 적게 씀
- 프로그램이 검증·재사용 가능
- 매 호출마다 그대로 재주입됨

### 1.3.7 해결책 (2): 구조화된 상태(Structured Memory State) 분리

대화의 **서술적 맥락**과 **정확해야 하는 사실**을 물리적으로 분리합니다. 이것은 대화 메모리를 **"흐릿해도 되는 것"과 "정확해야 하는 것"으로 분리**하는 상태 관리(state management) 패턴입니다.

- 서술적 맥락 → 요약으로 압축해도 무방
- 트랜잭션 사실(금액, 날짜, ID, 계약 조건 등) → 별도의 구조화된 저장소에 원본 그대로 보관하고, 필요할 때 통째로 프롬프트에 다시 주입

```json
{
  "order_id": "#12345",
  "charge_date": "2026-03-14",
  "amount_usd": 150.00,
  "issue": "duplicate_charge",
  "status": "refund_pending"
}
```

이 JSON은 요약 대상이 아니라 **상태(state)** 입니다. 요약을 100번 반복해도 이 값들은 변하지 않습니다. 이것이 **"요약만으로 컨텍스트를 관리하면 안 되는"** 이유입니다.

### 1.3.8 잘못된 대안 정리

| 대안 | 왜 부족한가 |
|---|---|
| 요약을 더 자주 하기 | 압축 특성이 그대로라 유실을 오히려 가속 |
| 요약 빈도 낮추기 | 압축 시점만 미룰 뿐, 같은 손실 발생 |
| 요약 길이를 1→3문장으로 늘리기 | 손실 압축이라는 성질은 그대로 |
| 사용자에게 매 턴 다시 말해달라고 하기 | 시스템 설계 실패를 사용자에게 떠넘기는 최악의 UX |
| 컨텍스트 윈도우가 가장 큰 모델로 바꾸기 | 비용·지연·건초더미 문제가 그대로 남음 |
| 요약을 아예 안 쓰고 전체 원문을 사람이 검토 | 자동화의 목적 자체를 포기 |

## 1.4 스크래치패드와 영속 메모리

### 1.4.1 스크래치패드(Scratchpad)란

**스크래치패드**는 에이전트가 작업/탐색 도중 알아낸 사실을 **컨텍스트 밖의 파일에 기록해 두는 것**입니다. 일종의 외부 메모장 겸 장기 기억이며, 보통 대화 밖의 평범한 파일입니다 (`notes.md`, `findings.json`, `notes/phase1-findings.md` 등).

**왜 존재하는가**: 컨텍스트 윈도우는 **휘발성**이지만 파일은 **영속적**입니다. 컨텍스트에서 밀려나거나 압축으로 사라져도, 파일은 남아 있고 필요할 때 다시 읽을 수 있습니다. 컨텍스트 윈도우 바깥에 존재하므로 압축이나 잘림의 영향을 받지 않습니다. 이것이 컨텍스트 저하(1.1.6절)에 대한 **정면 대응책**입니다.

**durable(지속 가능한, 영속적인)** 저장소라는 표현은 "세션이 끝나거나 컨텍스트가 날아가도 남아 있는 곳"을 뜻합니다.

> **직관적 비유 — 컨텍스트 → 디스크 오프로딩**
> 컨텍스트 윈도우는 **RAM**, 파일은 **디스크**라고 생각하면 됩니다. RAM을 비우기 전에 저장하는 게 당연합니다.

### 1.4.2 핵심 순서 — 이 주제의 가장 중요한 실무 패턴

> **1. 잃으면 안 되는 정확한 사실을 스크래치패드 파일에 먼저 기록한다(persist).**
> **2. 그런 다음에 대화를 압축(컴팩션)하여 공간을 회수한다.**

순서가 뒤바뀌면 안 됩니다. 아무것도 기록하지 않고 먼저 압축하면 그 시점에 정보가 이미 사라져 **복구할 수 없습니다.**

그리고 짝이 되는 규칙 하나 더: **답변하기 전에 그 파일을 먼저 읽는다.**

### 1.4.3 무엇을 적어야 하나

**구체적인 사실(concrete facts)을, 발견하는 즉시** 적습니다.

기록 대상: 정확한 설정값, 파일 경로와 줄 번호, 클래스/타입 이름, 함수 시그니처, 상속 구조, 발견한 아키텍처 사실과 메커니즘, 결정 사항과 그 이유, 미해결 질문.

**좋은 기록 예 1 — 탐색 결과 요약**

```markdown
## 발견 사실 (2025-03-04 탐색)
- billing service는 예외 대신 커스텀 `Result<T, E>` 타입 사용
  - 정의: src/billing/result.py:14
- 재시도 상한: config/billing.yaml 의 `max_retries: 3`
- 결제 게이트웨이 타임아웃: 8000ms (config/gateway.yaml:22)
```

**좋은 기록 예 2 — 메커니즘 기록**

```markdown
## billing-service 에러 처리
- 발견 위치: src/billing/result.ts
- 예외(exception)를 던지지 않음. 커스텀 `Result<T, E>` 타입을 반환.
- 호출부는 `if (res.isErr())` 패턴으로 분기 (src/billing/invoice.ts:142)
- 로깅은 별도 미들웨어 src/middleware/logger.ts 에서 처리
```

**좋은 기록 예 3 — 클래스 구조**

```markdown
# notes.md
## OrderService
- 위치: services/order/OrderService.java
- 상속: TransactionalBase (커스텀, 표준 컨트롤러 아님)
- 특이사항: 지수 백오프 기반 커스텀 재시도 메커니즘 보유
```

여기에 담긴 것은 정확한 **클래스/타입 이름**, **파일 경로**, **발견된 메커니즘**입니다. 나중에 "이 서비스 에러 처리 어떻게 해?"라고 물었을 때, 이 기록만 다시 읽으면 정확한 근거에 기반한 답을 할 수 있습니다.

**나쁜 기록의 유형:**

| 유형 | 예 | 왜 나쁜가 |
|---|---|---|
| 타임스탬프만 남기기 | "10:32 - 탐색 단계 1 수행" | 언제 했는지는 알겠지만 **무엇을 알아냈는지**가 없어 아무 도움이 안 됨 |
| 모호한 한 줄 | "코드베이스를 살펴봤고 대체로 괜찮아 보임" | 검증 가능한 정보가 0 |
| 파일 전체 원시 내용 통째 복사 | (raw dump) | 이건 스크래치패드가 아니라 **두 번째 컨텍스트 오염**. 원본 파일을 읽는 것과 다를 게 없음. 목적은 **압축된 핵심**을 남기는 것 |

### 1.4.4 근거 유지 (Groundedness)

**그라운디드(grounded)** 하다는 것은 답변이 실제로 확인된 근거에 기반하고 있다는 뜻입니다. 그 반대가 **환각**입니다.

스크래치패드는 그라운디드니스를 시간이 지나도 유지시켜 주는 장치입니다. 이 기록이 있으면 압축 후에도, 세션 후반에도, 심지어 다음 세션에서도 파일을 다시 읽어 **사실에 근거한(grounded)** 답변을 유지할 수 있습니다.

### 1.4.5 매니페스트(Manifest)와 중복 탐색 방지

**문제:** 긴 탐색 작업에서 몇 시간 전에 이미 조사한 영역을 서브에이전트가 또 조사하는 **중복 탐색(redundant exploration)** 이 발생합니다. 시간과 API 비용이 이중으로 나갑니다.

**해결:** 수행한 작업과 발견 사실을 **외부의 지속적 기록**에 남깁니다.

- **스크래치패드(Scratchpad)**: 에이전트들이 중간 결과를 적어 두는 공유 작업 공간(파일, DB, 공유 메모리). "무엇을 알아냈는가".
- **매니페스트(Manifest)**: 어떤 작업/영역이 이미 처리되었는지 목록화한 인덱스. "무엇을 했는가"의 목록.

새 서브에이전트를 스폰하기 **전에** 매니페스트/스크래치패드를 먼저 조회하는 것이 표준 절차입니다.

**신뢰하면 안 되는 것:**

- **메인 에이전트의 기억(unaided memory)**: 몇 시간 전 대화는 이미 요약되었거나 컨텍스트에서 밀려났을 가능성이 높습니다. 모델의 "기억"은 컨텍스트에 남아 있는 텍스트일 뿐이며, 신뢰할 수 있는 저장소가 아닙니다.
- **세션 밖의 사용자 개인 메모**: 시스템이 접근할 수 없고 자동화할 수 없으므로 아키텍처의 일부가 될 수 없습니다.

### 1.4.6 동시 실행 시 스크래치패드 컨벤션 — 경쟁 조건(Race Condition)

여러 서브에이전트가 **동시에(concurrently)** 실행되며 각자 결과를 기록할 때, 파일 사용 규칙을 잘못 정하면 데이터가 손상됩니다.

- **경쟁 조건(Race Condition)**: 여러 실행 주체가 동시에 같은 자원(파일)에 접근할 때 순서에 따라 결과가 달라지고 데이터가 깨지는 현상.
- **덮어쓰기(Overwrite) 버그**: 고정된 같은 파일명에 각자 쓰면, 나중에 쓴 에이전트가 앞선 에이전트의 기록을 지워 버립니다.

**안전한 컨벤션 — 격리(Isolation):**

```
scratch/
  module-auth.md      ← 서브에이전트 1
  module-billing.md   ← 서브에이전트 2
  module-search.md    ← 서브에이전트 3
```

각 서브에이전트에 **고유한 파일명**(예: 담당 모듈당 하나)을 부여하고, 코디네이터는 **모든 서브에이전트가 종료된 뒤에** 파일들을 한꺼번에 집계(Aggregate)합니다. 이렇게 하면 쓰기 충돌 자체가 발생하지 않습니다.

### 1.4.7 잘못된 대안들

| 대안 | 왜 나쁜가 |
|---|---|
| 기록 없이 바로 컴팩션 | 복구 불가능한 손실. "나중에도 접근할 수 있겠지"라는 믿음은 틀렸습니다 |
| 세션을 삭제하고 빈 세션에서 시작 | 탐색으로 알아낸 것을 전부 잃습니다. **최악** |
| 압축을 아예 회피하고 무한 누적 | 컨텍스트 한계 도달, 비용 증가, 성능 저하, 강제 truncation, 환각 증가, 결국 Context Window Exceeded 오류 |
| 질문마다 전체 저장소를 처음부터 다시 읽기 | 토큰·시간 낭비 |
| 스크래치패드 없이 최종 응답 텍스트로만 보고 | 긴 조사 과정에서 중간 결과를 보존할 곳이 없어 컨텍스트 한계로 정보를 잃습니다 |
| `max_tokens` 늘리기 / 더 큰 모델로 전환 | 무관한 조치 |

## 1.5 프롬프트 구조화와 Lost in the Middle

### 1.5.1 현상

LLM은 긴 입력의 **맨 앞**과 **맨 뒤**에 있는 정보는 잘 인지하지만, **중간**에 놓인 정보는 놓치는 경향이 있습니다. 이를 **"Lost in the Middle"** 이라 부릅니다. 성능을 위치별로 그리면 U자 곡선(양 끝이 높고 가운데가 낮음)이 나옵니다.

```
회상률
 높음 │■                                      ■
      │ ■                                   ■
      │   ■                              ■
 낮음 │      ■■■■■■■■■■■■■■■■■■■■■■■■
      └──────────────────────────────────────
       앞부분          중간부분          뒷부분
```

이것은 버그가 아니라 **트랜스포머 어텐션의 알려진 특성**입니다.

> **컨텍스트에 넣었다고 해서 모델이 그것을 사용한다는 보장은 없습니다.**

**전형적인 사고 사례:**

- 5개 서브에이전트의 결과를 하나의 긴 문서로 이어 붙여 종합 에이전트에 넘겼는데, 3번째 섹션에 있던 "규제 리스크" 내용이 최종 메모에서 통째로 누락됩니다.
- 4개 서비스의 조사 메모를 순서대로 이어 붙인 긴 문서에서, **두 번째(가운데) 서비스의 근본 원인만 결과물에서 반복적으로 빠집니다.**

### 1.5.2 완화 방법 (1): 프론트로딩(Front-loading)

문서 최상단에 짧은 **핵심 요약(key-findings summary)** 을 배치합니다. 모든 섹션의 요점이 주의력이 가장 강한 위치에 한 번 등장하게 됩니다.

**예 1 — 시장 조사 종합**

```markdown
## Key Findings
1. 시장 규모: TAM $4.2B, CAGR 11%
2. 경쟁사 가격: 평균 $29/월
3. 규제 리스크: EU AI Act 고위험 분류 가능성   ← 중간이지만 최상단에 한 번 등장
4. 고객 심리: NPS 42
5. 유통 채널: 파트너 재판매 비중 60%

## 1. Market Sizing
...
## 3. Regulatory Risk
...
```

**예 2 — 장애 원인 분석**

```markdown
## 요약: 서비스별 근본 원인
- auth-service: JWT 만료 시각 검증 누락
- billing-service: 커넥션 풀 고갈
- notify-service: 재시도 폭주로 인한 self-DDoS
- search-service: 인덱스 재구축 중 읽기 타임아웃

---

## 상세: auth-service
(로그와 상세 메모…)

## 상세: billing-service
...
```

핵심 결론이 모두 맨 앞(가장 잘 읽히는 위치)에 들어가고, 상세 내용은 명확한 **헤딩** 아래 구조화됩니다.

### 1.5.3 완화 방법 (2): 명시적 구조화 마크업

각 상세 섹션을 명확한 제목 아래 둡니다. 헤딩은 모델에게 **정보의 경계**를 알려주는 구조적 신호입니다.

- 마크다운 헤딩 (`## 3. Regulatory Risk`)
- XML 태그 (`<service name="billing">…</service>`)
- 명확한 구분선

이런 마크업은 모델에게 "여기가 하나의 독립된 단위"라는 신호를 줍니다.

### 1.5.4 완화 방법 (3): 중요 정보를 끝에도 반복 배치

앞과 뒤 모두 회상률이 높으므로, 결정적 지시사항을 마지막에 한 번 더 놓는 것도 유효합니다.

### 1.5.5 효과 없는 대응

| 잘못된 대응 | 왜 효과가 없는가 |
|---|---|
| "문서를 두 번 읽어라"라고 지시 | 어텐션 메커니즘 자체를 바꾸지 못하는 **주술적 프롬프팅**. 토큰만 낭비 |
| 문서 끝에 "중간 부분을 주의 깊게 보세요"라고 써 두기 | 구조적 어텐션 문제를 문장 한 줄로 고칠 수 없음 |
| 누락된 섹션만 맨 뒤로 옮기기 | 다른 섹션이 대신 중간으로 밀려나 같은 문제 재발. **위치 땜질은 근본 해결이 아님** |
| 입력 순서를 매번 무작위로 바꾸기 | 어느 항목이 희생되는지 무작위로 바뀔 뿐, 여전히 가운데 것은 누락 |
| 요약이나 헤더 없이 문서를 두 개로 쪼개기 | 각 문서 내부 구조가 그대로라 여전히 중간 유실 발생, 관리 복잡도만 증가 |
| 모든 걸 줄바꿈 없는 한 단락으로 합치기 | 구조가 사라져 더 나빠짐. **길이를 줄이는 것과 구조를 없애는 것은 다름** |
| 더 큰 컨텍스트 윈도우 모델로 바꾸고 요약 중단 | 넣는 양이 늘면 중간 구간도 길어져 오히려 악화 |

> **원칙: 프롬프트 엔지니어링은 "부탁"이 아니라 "배치"다.**

## 1.6 컨텍스트 오염 방지

### 1.6.1 컨텍스트 오염(Context Pollution)이란

컨텍스트 윈도우에 **다시 쓸 일이 없는 대량의 원시 데이터(raw output)** 가 들어차는 것을 컨텍스트 오염이라고 합니다.

예: 5만 개 파일이 있는 저장소에서 테스트 파일을 검색하면 수천 줄의 경로 목록이 나옵니다. 이걸 메인 대화에 그대로 넣으면:

- 토큰을 대량 소비해 남은 여유 공간이 줄어듭니다.
- 정작 중요한 고수준 계획 내용이 그 잡음에 묻힙니다.
- 이후 모든 턴에서 그 잡음이 계속 재전송되어 **비용과 지연 시간이 증가**합니다.

### 1.6.2 도구 호출 결과가 컨텍스트를 잠식하는 문제

에이전트(Agent)는 외부 시스템을 호출하는 **도구(Tool)** 를 사용합니다. 실제 업무 API는 필요 이상으로 많은 필드를 반환합니다.

**예 1 — 주문 조회 도구**

```json
{
  "order_id": "A-10023",
  "status": "delivered",
  "purchase_date": "2026-02-11",
  "item": "무선 이어폰",
  "amount": 129000,
  "return_window_deadline": "2026-03-13",
  "shipping_carrier_code": "CJ-LOG-77",
  "carrier_tracking_events": ["...30개..."],
  "warehouse_bin": "SEO-B4-1129",
  "marketing_tags": ["spring_promo", "email_cohort_7"]
}
```

실제 필드가 40개 이상이라고 해봅시다. 반품 자격을 판단하는 데 필요한 필드는 5개(주문 상태, 구매일, 품목, 금액, 반품 기한)뿐인데, 나머지 35개 이상의 필드가 매 호출마다 컨텍스트에 쌓입니다. 조회를 열 번만 해도 컨텍스트의 대부분이 쓸모없는 메타데이터로 채워집니다.

**예 2 — CRM 연락처 조회**

레코드 하나당 60개 필드(내부 리드 스코어, 마케팅 캠페인 태그, 감사 타임스탬프 등)를 돌려주는데, 정작 팔로업 이메일을 쓰는 데 필요한 건 이름, 회사, 거래 단계, 마지막 연락일 4개뿐일 수 있습니다. 연락처 10건을 조회하면 **600개 필드가 컨텍스트를 점령**합니다.

### 1.6.3 해결책: 도구 출력 트리밍 / 컨텍스트 프루닝(Pruning)

**도구 결과가 컨텍스트에 들어가기 전에, 애플리케이션 코드 단계에서 필요한 필드만 남기는 전처리(Pre-processing)** 가 정답입니다.

```python
NEEDED = ("status", "purchase_date", "item", "amount", "return_window_deadline")

def slim(payload: dict) -> dict:
    return {k: payload[k] for k in NEEDED if k in payload}

# 에이전트 컨텍스트에는 slim(raw) 결과만 추가한다
```

```python
FIELDS = ("name", "company", "deal_stage", "last_contact_date")

def trim(record):
    return {k: record[k] for k in FIELDS if k in record}

context.append(trim(crm.lookup(contact_id)))   # 60개 → 4개
```

**왜 이게 옳은 해법인가:**

- **결정적(deterministic)** 이고, 추가 LLM 호출이 없으니 비용·지연이 0에 가깝습니다.
- 필요한 필드가 잘려 나갈 위험이 없습니다.
- 토큰 비용이 15분의 1로 줄어듭니다.
- 모델이 봐야 할 노이즈가 사라져 정확도와 속도가 올라갑니다.

> **원칙: 결정적으로 풀 수 있는 문제에 확률적 도구(LLM)를 쓰지 않는다.**

**대안들이 왜 열등한지:**

| 대안 | 문제점 |
|---|---|
| 고정 글자 수로 자르기(Truncation) | JSON 구문이 깨지고, 뒤쪽 필수 필드가 잘려 나감. 어떤 정보가 남을지 통제 불가 |
| 원본 전체를 캐싱(Cache) | 재호출은 줄지만 컨텍스트 점유량 자체는 그대로. 원인을 건드리지 않음 |
| 별도 LLM 요약 호출 | 단순 필드 선택에 LLM을 쓰는 것은 과잉. 비용·지연 증가 + 요약 과정의 수치 왜곡 위험 |
| 포맷만 압축하고 60개 필드는 다 넣기 | 불필요한 정보가 여전히 모델의 주의력을 갉아먹음. 문제는 **글자 수**가 아니라 **관련 없는 정보의 존재** |
| 나중에 필요할지 모르니 60개 다 쌓아두기 | 컨텍스트 오염과 비용 폭증. 필요해지면 그때 다시 조회하면 됨 |
| 출력을 아예 컨텍스트에 남기지 않고 모델 기억에 맡기기 | 컨텍스트에 없는 정보는 모델에게 존재하지 않는 것과 같고, 없는 값을 지어내는 **환각**을 유발 |

### 1.6.4 개체별 구조화 레코드 (Structured Record per Entity)

**문제:** 하나의 대화 안에 독립된 개체가 여러 개 있을 때, 이들을 하나의 서술형 문장(blended narrative)으로 뭉쳐 요약하면 **엔티티 모호성(Entity Ambiguity)** 이 생깁니다. 예: 보험 청구 두 건을 한 단락으로 요약해 두면, 이후 "그 청구", "그 금액"이 어느 건을 가리키는지 알 수 없게 됩니다.

**해결:** 개체 하나당 레코드 하나. 반드시 **고유 식별자(ID)** 를 키로 갖게 하고, 서술형 텍스트와 분리해 보관합니다.

```json
{
  "claims": [
    {"id": "C-1092", "type": "water_damage", "amount": 6400, "status": "under_review"},
    {"id": "C-1108", "type": "auto_glass",   "amount": 310,  "status": "approved"}
  ]
}
```

이렇게 하면 후속 질문에 답할 때 모델이 특정 ID의 상태값을 정확히 참조할 수 있습니다.

**하면 안 되는 대안들:**

- 가장 최근 언급된 것만 남기고 나머지는 종료된 것으로 가정 → **데이터 손실**
- 두 건을 하나의 번호로 병합 → 서로 다른 사건을 합치는 것이므로 **데이터 정합성 파괴**
- 사용자에게 매번 청구 번호를 말하라고 요구 → 시스템의 상태 관리 실패를 사용자에게 떠넘기는 나쁜 UX. **시스템이 감당해야 할 책임을 사용자 부담으로 전가하지 않는 것이 원칙입니다.**

### 1.6.5 증상 → 기법 매핑

실무의 실패는 대개 한 가지 원인이 아니라 여러 원인이 겹칩니다. 증상 → 대응 기법을 1:1로 매핑하는 습관을 들이면 좋습니다.

| 증상 | 원인 | 대응 기법 |
|---|---|---|
| 정확한 수치가 유실됨 | 롤링 요약의 손실 압축 | 팩트 블록으로 수치/ID 고정 |
| 동시에 진행되는 이슈들이 뒤섞임 | 서술형 혼합 요약 | 이슈별 구조화 레코드 분리 |
| 컨텍스트가 도구 출력으로 가득 참 | 원본 도구 출력 그대로 삽입 | 관련 필드만 트리밍 |
| 긴 종합 문서의 중간 내용 누락 | Lost in the Middle | 상단 핵심 요약 + 명시적 헤딩 |
| 세션 후반 일반론적 답변(환각) | 컨텍스트 열화 / 압축 손실 | 스크래치패드 기록 후 컴팩션, 답변 전 재독 |
| 세션 재개 시 이전 대화를 모름 | API 무상태성 미인지 | 앱이 이력을 저장하고 매 요청 messages에 재전송 |
| 서브에이전트가 같은 영역을 중복 조사 | 메인 에이전트 기억에 의존 | 매니페스트 조회 후 스폰 |
