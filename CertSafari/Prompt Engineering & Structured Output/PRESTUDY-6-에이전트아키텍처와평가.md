# 6. 에이전트 아키텍처와 프롬프트 평가

이 장에서 다루는 것:

- 정밀도·재현율·오탐(FP)·미탐(FN)의 정의와 알림 피로
- 생성자(generator)와 검증자(verifier)를 왜 분리해야 하는가
- 서브에이전트의 컨텍스트 격리, 최소 권한 도구 설계, 워크플로 오케스트레이션
- LLM 기반 코드 리뷰 아키텍처 — 파일별 패스와 교차 파일 통합 패스(map-reduce)
- 신뢰도 기반 라우팅과 Human-in-the-Loop
- 프롬프트 평가와 회귀 테스트 — held-out/골든 데이터셋, 정량 지표
- 모니터링, 피드백 루프, 사용자 신뢰

## 1. 정밀도·재현율·오탐 기초

### 1.1 Finding (발견 사항)

검토 도구가 찾아낸 문제 하나를 가리키는 단위입니다. 보통 다음 정보를 담습니다.

- 위치(파일, 줄 번호)
- 문제 설명
- 심각도(severity)
- (설계에 따라) 신뢰도(confidence), 이 문제를 촉발한 코드 패턴 이름(`detected_pattern`) 등

이 필드 설계가 뒤에 나오는 라우팅(3장)과 모니터링(7장)의 전제 조건이 됩니다.

### 1.2 혼동 행렬과 오탐/미탐

어떤 항목을 "문제 있음"으로 지적하는 시스템(코드 리뷰 봇, 스팸 필터 등)을 생각합시다.

| | 실제로 문제 있음 | 실제로 문제 없음 |
|---|---|---|
| **문제 있다고 지적** | True Positive (TP) | **False Positive (FP)** |
| **지적 안 함** | False Negative (FN) | True Negative (TN) |

- **False Positive(거짓 양성 / 오탐)**: 문제가 없는데 문제라고 잘못 표시한 것. 사용자가 가장 짜증내는 오류이며, 많아지면 사람들이 시스템 전체를 무시하기 시작합니다.
- **False Negative(거짓 음성 / 미탐)**: 진짜 문제를 놓친 것.
- **False Positive Rate(오탐율)**: 문제없는 항목 중 잘못 지적된 비율.
- **Precision(정밀도)** = TP / (TP + FP). 지적한 것 중 실제로 맞았던 비율. 오탐이 많으면 낮아집니다.
- **Recall(재현율)** = TP / (TP + FN). 실제 문제 중 찾아낸 비율. 미탐이 많으면 낮아집니다.

**오탐 예시 — 광범위한 except 절.** 파이썬에서 `except Exception:`은 보통 나쁜 습관이지만 항상 그런 것은 아닙니다.

```python
# (1) 진짜 문제 — 에러를 삼켜버림
try:
    charge_card(user)
except Exception:
    pass          # 결제 실패가 조용히 사라진다

# (2) 문제 아님 — 최상위 에러 경계에서 로깅 후 재발생
try:
    run_request(req)
except Exception:
    logger.exception("unhandled")
    raise         # 로그만 남기고 그대로 다시 던진다
```

(2)까지 문제라고 표시하면 그것이 오탐입니다.

**정밀도와 재현율은 대개 맞바꾸는(trade-off) 관계입니다.** 검사 규칙을 아예 삭제하면 오탐은 0이 되지만 재현율도 0이 됩니다. 즉 **"규칙을 삭제한다"는 오탐 문제의 해결책이 아닙니다.** 목표는 언제나 "진짜 문제는 계속 잡으면서 오탐만 줄인다"입니다.

### 1.3 Alert Fatigue (알림 피로)

오탐이 많으면 사람이 도구의 출력을 아예 안 읽게 됩니다. 이 순간 정확했던 다른 카테고리의 결과까지 함께 무시당합니다. 즉 **한 카테고리의 노이즈가 시스템 전체의 신뢰를 무너뜨립니다.** (자세한 메커니즘은 7.3.)

대응 원칙:

- 노이즈가 심한 카테고리는 **즉시 비활성화(격리)** 하고, 별도로 프롬프트를 개선한 뒤 재활성화한다.
- 하지 말아야 할 것:
  - 노이즈 카테고리를 정확한 카테고리에 **합치기** → 정확한 쪽까지 오염됩니다.
  - 심각도만 낮춰서 계속 노출하기 → 여전히 읽는 비용이 발생합니다.
  - "일부 카테고리는 정확도가 낮습니다"라는 **면책 배너**만 붙이기 → 판단 부담을 사람에게 떠넘길 뿐 노이즈는 그대로입니다.

## 2. 생성자와 검증자의 분리

### 2.1 에이전트와 서브에이전트

**에이전트(Agent)** 는 LLM이 도구(파일 읽기, 명령 실행, 검색 등)를 사용하며 여러 턴/단계에 걸쳐 스스로 작업을 수행하는 구성입니다.

- **상위(부모, parent) 에이전트**: 전체 작업을 조율하는 쪽.
- **서브에이전트(subagent)**: 부모가 특정 하위 작업을 위임해 띄우는 별도의 에이전트 인스턴스. 보통 자기만의 컨텍스트 창, 시스템 프롬프트, 도구 집합을 가집니다.

**생성기(generator)** 는 코드를 만든 모델/세션, **검증자(verifier/evaluator/reviewer)** 는 그 결과를 검사하는 별도 인스턴스입니다.

### 2.2 자가 검토(Self-Review)는 왜 잘 안 되는가

흔한 설계: 코드를 생성한 다음, **같은 대화(세션) 안에서** "끝내기 전에 네 작업을 다시 읽고 실수를 지적하라"고 지시하는 것. 관찰되는 현상은 자가 검토가 문제를 거의 찾아내지 못하고, 나중에 새 리뷰어가 보면 문제가 발견된다는 것입니다.

**원인은 확증 편향(Confirmation Bias) / 자기 일관성 편향(Self-Consistency Bias)** 입니다.

모델은 코드를 생성하면서 그 설계 결정들을 이미 채택했고, 그 근거가 대화 이력에 그대로 남아 있습니다. 다음 토큰을 예측할 때 모델은 앞선 컨텍스트와 **일관되게** 이어가려는 강한 경향이 있습니다. 방금 스스로 정당화한 선택을 이제 와서 부정하는 것은 그 일관성을 깨는 방향이므로 확률적으로 불리합니다. 결과적으로 모델은 자기 결정을 재확인하는 쪽으로 기울고 비판을 회피합니다.

같은 이야기를 다르게 표현하면: **생성 당시의 잘못된 가정·오개념·놓친 조건 같은 맹점(blind spots)이 검증 단계에도 그대로 상속됩니다.**

**흔한 오해들:**

- *"명령문 대신 질문형으로 바꾸면 된다"* → 문장 형식은 편향의 원인이 아닙니다. 원인은 컨텍스트 공유입니다.
- *"파일을 다시 읽을 권한이 없어서 그렇다"* → 생성자는 자기가 방금 쓴 내용을 컨텍스트에 갖고 있고, 보통 파일 읽기 도구도 있습니다. 접근성 문제가 아닙니다.
- *"Extended Thinking이 꺼져 있어서 그렇다"* → 켜도 같은 세션에서는 같은 편향이 유지됩니다.
- *"self-review 지시를 더 엄격하게 쓰면 된다"* → 프롬프트 문구를 강화해도 오염된 컨텍스트가 남아 있는 한 편향은 사라지지 않습니다.
- *"같은 세션에서 두 번 검토하게 하면 된다"* → 같은 편향된 컨텍스트에서의 반복일 뿐이고, 오히려 첫 검토 결론까지 컨텍스트에 쌓여 편향이 강화됩니다. 비용만 두 배가 됩니다.

같은 이유로 **신뢰도 라벨을 생성기가 스스로 붙이면 의미가 약합니다.** 자기가 못 본 것을 "낮은 신뢰도"로 표시할 수는 없기 때문입니다.

### 2.3 해법: 생성자-검증자 분리 (Generator-Evaluator Separation)

**독립된 두 번째 인스턴스**를 띄워 검토하게 합니다. 핵심 조건은 그 인스턴스가 **생성 세션의 대화 이력에 접근하지 못하는 것(fresh context)** 입니다.

새 인스턴스는 코드가 어떤 논리로 쓰였는지, 어떤 근거로 정당화되었는지 모릅니다. 오직 결과물만 보고 판단하므로 편향 없이 평가할 수 있습니다. 소프트웨어 공학에서 작성자와 리뷰어를 분리하는 이유와 정확히 같은 원리입니다.

```
[생성자 세션]  코드 작성  ──▶  산출물(diff/파일)
                                    │
                        (대화 이력은 전달하지 않음)
                                    ▼
[리뷰어 세션]  백지 상태에서 산출물만 보고 검토
```

이것은 프롬프트 문구 조정이 아니라 **아키텍처 수준의 변경**입니다. 그래서 근본적으로 효과가 있습니다.

### 2.4 세션 재개(Resume)와 독립 검토의 차이

**세션 재개(resume)** 는 이전에 실행했던 세션을 그 대화 이력째로 이어서 실행하는 것입니다. resume하면 **이전 대화, 추론 과정, 도구 호출 기록이 그대로 보존됩니다.** 지워지지 않습니다.

따라서 "설정을 재사용하려고 같은 세션을 재개해서 자기 diff를 리뷰시키는 것"은 독립 검토가 아닙니다. 겉으로는 다른 요청처럼 보여도, 편향의 원천인 이전 컨텍스트가 그대로 살아 있기 때문입니다.

| 필요한 것 | 올바른 수단 |
|---|---|
| 독립 검토 | **새 서브에이전트를 새 컨텍스트로** 띄우고, 필요한 맥락만 프롬프트로 전달 |
| 하던 작업 이어가기 | resume |

### 2.5 리뷰 서브에이전트의 권한 설계 — 최소 권한 원칙

리뷰 전용 서브에이전트는 코드를 **분석만 하고 절대 수정하면 안 된다**는 제약을 갖는 경우가 많습니다. 에이전트 설정의 **`tools` 필드**로 사용 가능한 도구 목록을 지정해 이를 보장합니다.

| 도구 | 성격 | 하는 일 |
|---|---|---|
| `Read` | 읽기 전용 | 파일 내용 읽기 |
| `Grep` | 읽기 전용 | 파일 내용 패턴 검색 |
| `Glob` | 읽기 전용 | 파일 경로 패턴 검색 |
| `Edit` | 쓰기 | 파일 수정 |
| `Write` | 쓰기 | 파일 생성/덮어쓰기 |
| `Bash` | **사실상 쓰기** | 임의의 셸 명령 실행 |

**올바른 설정: `tools`를 읽기 전용 도구만으로 명시적으로 제한한다.**

```yaml
name: code-reviewer
tools: Read, Grep, Glob
```

`Edit`, `Write`는 물론이고 **`Bash`도 반드시 제외해야 합니다.** Bash가 있으면 `sed -i`, `echo > file`, `rm` 같은 명령으로 얼마든지 파일을 바꿀 수 있습니다. "Bash는 파일을 읽는 데만 쓸 것"이라는 가정은 성립하지 않습니다. Bash는 읽기 도구가 아니라 **임의 실행 권한**입니다.

**잘못된 대안들:**

- *`tools` 필드를 비워두고(=부모의 모든 도구 상속) 프롬프트로 "Edit/Write 쓰지 마"라고 지시하기*: **소프트 제약(soft constraint)** 입니다. 모델이 지시를 어기거나, 프롬프트 인젝션으로 우회되거나, 단순히 헷갈리면 파일이 수정됩니다. 지시는 보장이 아닙니다.
- *수정 권한을 주되 매 수정마다 수동 승인을 받게 하기*: 사람이 실수로 승인할 수 있고, 승인 피로(approval fatigue)로 무비판적 클릭이 발생합니다. 무엇보다 "수정 불가"라는 요구를 **구조적으로 보장하지 못합니다.**

**원칙: 하드 제약(도구 자체를 주지 않음) > 소프트 제약(프롬프트로 부탁함).** 이것이 보안의 **최소 권한 원칙(Principle of Least Privilege)** 입니다. 필요한 최소한의 권한만 부여하면, 위반이 "일어나지 않기를 바라는" 것이 아니라 **애초에 불가능해집니다.**

## 3. 서브에이전트와 컨텍스트 격리

### 3.1 컨텍스트 창(Context Window)

**컨텍스트 창**은 모델이 한 번에 볼 수 있는 토큰의 총량입니다. 대화 기록, 시스템 프롬프트, 도구 호출과 그 결과, 읽어들인 파일 내용이 모두 여기에 쌓입니다. 유한한 자원이며, 길어질수록 비용이 오르고 **노이즈 때문에 모델 성능이 떨어질 수 있습니다.**

### 3.2 컨텍스트 격리(Context Isolation) 원칙

**핵심 규칙: 서브에이전트는 자신만의 깨끗하고 비어 있는 컨텍스트 창(clean context)에서 시작합니다.**

서브에이전트가 시작할 때 가지고 있는 것은 정확히 두 가지뿐입니다.

1. **서브에이전트 자신의 시스템 프롬프트**
2. **부모가 Agent 도구를 호출하며 전달한 프롬프트 문자열(prompt string)**

**자동으로 상속되지 않는 것들:**

- 부모의 대화 기록(conversation history)
- 부모의 추론 흔적(reasoning trace)
- 부모가 실행한 도구 호출과 그 결과 (읽어들인 파일 내용 포함)
- 부모의 컨텍스트 창 자체 (공유하지 않고 별도로 할당받음)

그래서 "코드 생성 직후 리뷰 서브에이전트를 불렀는데 어떤 파일이 왜 바뀌었는지 모르더라"는 현상은 **버그가 아니라 설계상 당연한 동작**입니다.

혼동하기 쉬운 다른 설정들:

- **`model` 오버라이드**: 어떤 LLM 모델로 실행할지 바꾸는 설정일 뿐, 프롬프트 전달을 막지 않습니다.
- **`tools` 필드 미설정**: 도구 사용 권한에 영향을 줄 수는 있어도, 프롬프트 텍스트를 받는 것 자체를 막지는 않습니다.

### 3.3 왜 이렇게 설계되었나

- **토큰 낭비 방지**: 부모의 긴 생성 과정 전부를 검토자에게 넘기면 비용이 폭증합니다.
- **노이즈 차단**: 검토자는 "코드가 어떻게 만들어졌는지"에 오염되지 않은 채 결과물만 보고 판단해야 더 객관적입니다. (2.3의 편향 제거와 같은 이야기)
- **부모 컨텍스트 보호**: 서브에이전트의 긴 탐색 과정이 부모 창을 채우지 않습니다.

### 3.4 실무적 함의 — 맥락은 명시적으로 전달한다

서브에이전트가 부모의 작업 결과를 볼 수 없다면 **부모가 명시적으로 전달해야 합니다.** 방법은 두 가지입니다.

- **프롬프트 문자열에 필요한 내용을 담아 전달** (파일 경로, 요약, 판단 기준 등)
- **서브에이전트가 스스로 도구를 써서 다시 읽게 하기** (파일 경로만 알려주고 검토자가 직접 Read)

실무에서는 후자가 흔합니다. 부모가 "`src/auth.js`와 `tests/auth.test.js`를 읽고 검토하라"고 지시하면, 서브에이전트가 자기 컨텍스트에 필요한 것만 담습니다.

```
# 나쁜 호출
prompt: "방금 작성한 코드를 리뷰해줘"

# 좋은 호출
prompt: """
다음 파일들이 변경되었습니다:
- src/auth/session.py (세션 만료 검사 추가)
- src/auth/token.py (토큰 서명 알고리즘을 HS256에서 RS256으로 변경)

변경 이유: 만료된 토큰이 통과되는 보안 이슈(#412) 수정.
`git diff HEAD~1` 로 변경 내용을 확인하고, <security_criteria>에 정의된 기준으로 리뷰하세요.
"""
```

### 3.5 전용 서브에이전트로 오탐 줄이기

특정 종류의 검토(예: 네이밍 규칙)를 전담하는 서브에이전트를 두는 설계가 있습니다. 구성 요소는 셋입니다.

1. **격리된 컨텍스트 창** — 다른 리뷰 주제의 내용이 섞여 판단을 흐리지 않게 합니다.
2. **맞춤형 시스템 프롬프트** — 판정 기준을 명시적으로 못 박습니다.
3. **최소 권한 도구 접근 (least privilege)** — 그 작업에 필요한 도구만 줍니다. 보안 원칙이자, 엉뚱한 행동을 줄이는 장치이기도 합니다.

**전형적인 문제 상황:** 한 파일 안에 여러 세대의 레거시 네이밍 스타일이 섞여 있습니다. 새 헬퍼 함수가 그중 한 레거시 스타일을 따랐다면 "파일 내 우세한 스타일과 다르다"는 이유로 지적됩니다. 이는 유용하지 않은 오탐입니다. 판단 기준이 **파일의 지역적 관행**이었기 때문입니다.

해결의 핵심은 시스템 프롬프트로 **기준점을 옮기는 것**입니다.

```
파일 내에 이미 존재하는 레거시 스타일 편차는 무시한다.
프로젝트의 표준 네이밍 규칙(canonical naming standard) 위반만 지적한다.
```

이러면 지역적 혼재로 인한 오탐은 줄면서, 진짜 표준 위반은 계속 잡힙니다. 다만 **모든 오탐을 없앨 수는 없다**는 점을 인정하는 것도 좋은 설계 태도입니다.

비교되는 열등한 접근들:

- 네이밍 지적을 전부 끄기 → 오탐과 함께 **진짜 결함(genuine defect)도 사라집니다.** (1.2의 "규칙 삭제는 해결책이 아니다")
- 오탐을 그냥 낮은 심각도로 계속 보고하기 → 노이즈는 여전하고 알림 피로도 해결되지 않습니다.
- "신뢰도 90% 이상일 때만" → 모델의 자기 확신도는 신뢰할 수 있는 척도가 아닙니다.

### 3.6 규모 확장: 워크플로 오케스트레이션

200개 파일이 바뀐 대규모 마이그레이션처럼, 단일 대화에서 **턴 바이 턴(turn-by-turn)으로 위임**하기엔 너무 큰 작업이 있습니다.

턴 바이 턴 위임의 한계:

- 각 위임과 결과 요약이 부모 대화의 컨텍스트에 계속 쌓여 **컨텍스트 창을 잠식**합니다.
- 순차적이라 처리량(throughput)이 낮고 지연이 누적됩니다.

정석적인 해결책은 **오케스트레이션을 코드로 옮기는 것**입니다. 스크립트나 워크플로 도구가 다수의 서브에이전트를 **병렬로 생성·조율**하고, 각 결과를 수집해 집계합니다.

```python
# 개념 예시
results = run_parallel([
    spawn_review_agent(prompt=make_prompt(f)) for f in changed_files
], max_concurrency=10)
report = aggregate(results)
```

장점:

- 각 서브에이전트가 **깨끗한 작은 컨텍스트**를 갖는다.
- 병렬 실행으로 총 소요 시간이 크게 준다.
- 재시도, 실패 처리, 집계 로직을 **결정적인 코드로** 제어할 수 있다.

열등한 대안들:

- **확장 사고(extended thinking)를 늘려 한 모델이 200개를 다 보게 하기**: 사고 시간을 늘려도 컨텍스트 창 한계와 정보 과부하는 해결되지 않습니다.
- **20개만 샘플링해서 나머지를 추정**: 검토하지 않은 180개의 독립적 결함을 놓칩니다. 코드 리뷰의 목적 자체와 어긋납니다.
- **단일 서브에이전트가 한 대화에서 200개를 순차 처리**: 컨텍스트 초과, 후반부 품질 저하, 환각 증가가 발생합니다.

## 4. LLM 코드 리뷰 아키텍처 (사례)

### 4.1 문제: 큰 입력을 한 번에 주면 생기는 일

60개 파일에 걸친 변경(diff)을 단일 모델 호출에 통째로 넣으면:

- **주의력 분산**: 입력이 길어질수록 모델은 특정 부분에 대한 집중도를 잃습니다.
- **Lost in the middle**: 긴 컨텍스트의 중간 부분 정보가 앞뒤보다 덜 활용되는 현상.
- 앞부분에서 세운 기준을 뒷부분에서 잊거나 다르게 적용합니다.
- 결과적으로 **파일 간 모순되는 검토 결과**(A 파일에서는 이렇게 하라 하고, B 파일에서는 반대로 지적)가 나옵니다.

**컨텍스트 윈도우를 키우는 것만으로는 해결되지 않습니다.** 넣을 수 있는 양(용량)과 실제로 잘 활용하는 능력(주의력)은 다른 문제입니다. "담을 수 있다"가 "잘 볼 수 있다"를 뜻하지 않습니다.

### 4.2 해법: 분할 정복 / 계층적 리뷰 (Map-Reduce 패턴)

역할을 두 계층으로 나눕니다.

**1단계 — 파일별 검토(per-file pass) = Map**

- 변경된 파일을 하나씩, 별도의 호출로 격리해서(in isolation) 검토합니다. 컨텍스트가 작고 병렬화가 쉽습니다.
- 잘 잡는 것: 문법 오류, 컴파일 가능 여부, 들여쓰기·명명 규칙 등 스타일/포맷, **같은 파일 안**의 중복 로직, 로컬 로직 버그, 미사용 변수, 파일 내 예외 처리 누락.
- 한계: **각 파일을 격리해서 판단하므로 파일 밖의 사실은 모릅니다.**

**2단계 — 교차 파일 통합 검토(cross-file integration pass) = Reduce**

- 개별 결과와 인터페이스 변경 요약을 모아, 전체 변경 집합(changeset)을 한꺼번에 봅니다.
- 이 단계가 존재하는 유일한 이유는 **파일 경계를 넘는 문제**를 잡기 위함입니다:
  - 파일 간 **데이터 흐름(data flow)** 불일치
  - 모듈 간 **계약(contract)/타입 계약** 불일치 — 공유 인터페이스를 파일마다 다른 규격·다른 의도로 사용
  - 모듈 A의 함수 시그니처가 바뀌었는데 호출부 B, C가 일관되게 갱신되지 않은 문제
  - 순환 의존, 설정 값의 앞뒤 불일치

각 파일은 격리해서 보면 문법적으로 완벽하고 타입 오류도 없어 보일 수 있지만, 합쳐 놓으면 서로 어긋납니다. 반대로, 파일 하나 안에서 끝나는 문제(문법, 스타일, 동일 파일 내 중복)를 통합 패스의 주된 목표로 삼는 것은 **단계 배치를 잘못한 것**입니다. 지역적 문제와 전역적 문제는 성격이 다르므로 서로 다른 패스에서 다루는 것이 맞습니다.

### 4.3 파일별 결과가 서로 충돌할 때

상호 의존적인 두 파일 A, B를 각각 격리 검사했더니 **같은 근본 원인(데이터 흐름 문제)** 에 대해 서로 모순되는 수정안을 냈다고 합시다. 각 패스는 자기 파일만 보므로 전체 흐름을 오해한 상태입니다.

올바른 해결책은 **두 파일을 함께 보는 교차 파일 통합 패스를 추가**해, 실제 데이터 흐름에 근거한 **단일한 권고안**을 도출하는 것입니다.

**잘못된 대안들:**

- **파일별 검토를 두 번 하기 / 같은 파일을 두 번 읽기**: 격리 판단이라는 구조적 한계는 그대로입니다. 모듈 A를 아무리 여러 번 읽어도 모듈 B의 잘못된 호출은 시야에 없습니다.
- **A와 B만 한꺼번에 읽기**: 임시방편입니다. 모듈 C와의 불일치는 여전히 놓칩니다. 교차 파일 분석의 정식 메커니즘을 대체하지 못합니다.
- **동일한 검토를 두 번 돌려 교집합만 남기기**: 근본 원인(컨텍스트 과부하)이 그대로이므로 두 번 다 틀릴 수 있습니다. 비용만 두 배가 되고, 한 번만 발견된 진짜 버그는 버려집니다.
- **재실행 후 "더 자신 있어 보이는 문구"를 채택**: 표현의 확신도는 정확성의 근거가 아닙니다.
- **리뷰 편의를 위해 두 소스 파일을 물리적으로 병합**: 리뷰 도구의 한계 때문에 실제 코드 구조를 훼손하는 본말전도이며 모듈화 원칙 위반입니다.
- **원래 코드를 쓴 생성기에게 중재를 맡기기**: 2.2의 자기 검토 편향을 그대로 안고 있습니다. 그 세션은 애초에 문제를 만든 맹점을 그대로 갖고 있습니다.
- **최근 커밋만 검토하기 / 커밋을 잘게 나눠 최신 커밋만 매번 리뷰하기**: 개별 커밋은 잘 보게 되지만, 누적된 변경 사이의 상호작용과 **전체 리팩토링의 맥락**, 파일 간 일관성은 영원히 검토되지 않습니다.

### 4.4 일반 원칙

> 격리된 검사는 격리된 문제만 잡는다. 관계에서 발생하는 문제는 관계를 보는 단계가 따로 있어야 잡힌다.

"구조 검증과 의미 검증은 별개 계층"이라는 사고방식과 같은 계열입니다.

### 4.5 리뷰 명령의 노력 수준(effort level)과 비용·시간 트레이드오프

Claude Code에는 코드 리뷰 명령이 있고, **노력 수준**을 지정할 수 있습니다.

| 방식 | 실행 위치 | 특징 |
|---|---|---|
| `/code-review` (기본) | 로컬 | 빠름. 일상 리뷰에 적합. 각 지적을 독립적으로 재현·검증하지는 않음 |
| `/code-review ultra` | 클라우드 | **다수의 리뷰어 에이전트 군단(fleet)** 을 병렬 실행. 각 이슈를 **독립 재현(reproduce)·검증(verify)**. 수 분 소요, 크레딧 소모 큼, 오탐이 걸러진 고신뢰 결과 |
| `/review <pr>` 같은 빠른 패스 | - | 수초 내 종료. 깊은 독립 검증을 대체하지 못함 |

판단 기준: **"몇 분과 크레딧을 써서라도 각 지적이 독립 검증되기를 원하는가?"** 대규모 다중 파일 변경의 머지 직전처럼 위험이 큰 순간이라면 그렇습니다. 참고로, 같은 명령을 수동으로 세 번 돌려 공통 항목만 남기는 방식은 비효율적일 뿐 아니라, 독립된 에이전트가 실제로 이슈를 재현해 보는 동작을 흉내 내지 못합니다.

### 4.6 리뷰 기준(criteria) 작성법 — 객관성과 명시적 분류

여러 리뷰어(사람이든 에이전트든)가 **같은 이슈에 대해 같은 분류로 수렴(converge)** 하게 하려면, 심각도 정의가 **객관적이고 검증 가능**해야 합니다. 좋은 정의의 조건은 **코드만 보면 참/거짓을 판정할 수 있다**는 것입니다.

```
Critical: 권한 검증이 필요한 데이터에 인증 없이 접근할 수 있게 되는 변경.
예) 다른 사용자의 레코드를 반환하는 DB 쿼리 앞의 권한 검사가 제거된 경우.
```

→ 누가 보든 "권한 검사가 제거되었는가?"는 사실 판정이므로 판단이 일치합니다.

나쁜 정의의 특징:

- **주관적 감정 의존**: "경험 많은 엔지니어가 불안함을 느낄 만한 위험한 패턴" → 사람마다 다름
- **주관적 인지 난이도 의존**: "주변 코드보다 현저히 복잡하거나 추론하기 어려운" → 역량·시각에 따라 다름
- **변경 내용이 아닌 이력 의존**: "과거에 장애가 잦았던 모듈을 건드리는 변경" → 현재 변경 자체의 위험도를 반영하지 못함

### 4.7 무엇을 보고하고 무엇을 건너뛸지 명시하기

치명적 이슈를 놓치지 않으면서 잡음(noise)을 줄이려면, **모델의 확률적 신뢰도 점수에 판정을 맡기지 말고** 보고 대상과 제외 대상을 **범주로 직접 명시**하는 것이 확실합니다.

```
반드시 보고(Report):
  - 보안 취약점을 유입시키는 변경
  - 기존 동작을 깨뜨리는 정확성(correctness) 버그

반드시 제외(Skip):
  - 포맷팅 취향 문제
  - 해당 파일에 이미 자리 잡은 로컬 컨벤션에서 벗어난 정도의 사항
```

판단 기준이 결정적이어서 리뷰어들 사이의 결과가 수렴합니다.

반면 잘못된 구성:

- **신뢰도 임계값(예: 0.9 초과만 보고)에 의존** → 애초에 "신뢰도에 맡기지 않겠다"는 목표와 정반대. 모델의 자기 신뢰도는 잘 보정(calibration)되어 있지 않습니다.
- **두 번째 패스의 신뢰도 점수 일치 여부로 결정** → 여전히 신뢰도 점수 기반이며, 범주 정의가 없습니다.
- **문서화된 스타일 가이드 위반을 전부 보고** → 줄이려던 포맷팅 잡음을 오히려 폭증시킵니다.

### 4.8 참고: 도구(Tool) 설계에서의 같은 문제 — 모호한 선택

에이전트는 여러 도구 중 무엇을 어떤 인자로 부를지 스스로 정합니다. 도구 정의의 구성 요소는 다음과 같습니다.

```json
{
  "name": "search_code",
  "description": "소스 코드 저장소에서 심볼, 함수, 설정 값의 실제 정의 위치를 찾는다.",
  "input_schema": { "type": "object", "properties": { "query": {"type": "string"} } },
  "input_examples": [ ... ]
}
```

- **name**: 도구 식별자. 명확해야 하지만, 이름만으로 모든 모호성이 해소되지는 않습니다.
- **description**: 자연어 설명. 모델이 도구 선택의 1차 근거로 삼습니다.
- **input_schema**: 인자의 구조.
- **input_examples**: 이 도구를 **언제, 어떤 요청에 대해** 어떤 인자로 부르는지 보여주는 예시. 도구 정의 안에 넣는 few-shot입니다.

"레이트 리밋(rate limit)이 어디에 정의되어 있나?"는 문서에도, 코드에도 답이 있을 수 있는 **모호한 요청**이라 세션마다 다른 도구를 고르게 됩니다.

**효과적인 해법 — `input_examples`에 근거를 담은 예시 넣기:**

```
요청: "레이트 리밋이 어디에 정의되어 있나?"
선택: search_code
이유: "어디에 정의(defined)되어 있는가"는 실제 값의 소스 위치를 묻는 것이므로,
      설명 문서보다 코드 저장소가 정답을 담고 있다.
      (정책이나 사용자 대상 한도 자체를 묻는다면 search_docs를 택한다.)
```

**선택 + 근거**라는 원칙이 그대로 적용됩니다. 예시가 "왜 다른 그럴듯한 선택지를 이겼는지"를 담아야 새로운 모호한 요청에도 일반화됩니다.

**덜 효과적인 대안들:**

- **설명에 형용사를 더 붙이기**: 장황해질 뿐 판단 기준을 주지 못합니다.
- **이름을 더 구별되게 바꾸기**: `search_docs`/`search_code`는 이미 충분히 구별됩니다. 문제는 이름 혼동이 아니라 **경계 기준의 부재**입니다.
- **하드코딩된 라우팅(항상 A를 먼저 호출하고 실패 시 B로 폴백)**: 에이전트의 추론을 없애버리고, 코드 검색이 명백히 맞는 상황에서도 불필요한 호출과 지연을 발생시킵니다.

## 5. 신뢰도 기반 라우팅과 Human-in-the-Loop

### 5.1 Confidence Level (신뢰도 수준)

모델이 각 발견 사항에 대해 "내가 이걸 얼마나 확신하는가"를 함께 출력하게 하는 것입니다. 보통 `high / medium / low` 같은 열거값이나 0~1 점수로 만듭니다. **severity(심각도)와는 완전히 다른 축**입니다.

| 축 | 의미 |
|---|---|
| **severity** | 이게 진짜 버그라면 얼마나 위험한가 |
| **confidence** | 이게 진짜 버그일 가능성이 얼마나 되는가 |

심각도가 아주 높아도 신뢰도가 낮으면 자동으로 고쳐서는 안 됩니다.

신뢰도 라벨에 관한 흔한 오해들:

- 신뢰도 라벨을 출력하는 데 코드베이스 **쓰기 권한이 필요하지는 않습니다** (리뷰는 읽기·분석 작업).
- 신뢰도 점수/라벨은 프롬프트 지시나 구조화된 출력으로 **얼마든지 생성할 수 있습니다** (지원되지 않는 형식이 아닙니다).
- 신뢰도 산출이 **단일 파일 검토에서만 가능하다는 기술적 제약은 없습니다** (다중 파일에도 적용 가능).

단, 2.2에서 본 대로 **생성기가 자기 결과에 스스로 붙인 신뢰도는 신뢰하기 어렵고**, 모델의 자기 신뢰도는 일반적으로 잘 보정(calibration)되어 있지 않습니다. 그래서 4.7처럼 "신뢰도 임계값으로 보고 여부를 정하는" 용도로는 부적합하고, 아래처럼 **사람에게 넘길지 말지를 정하는 라우팅 신호**로 쓰는 것이 적절한 용법입니다.

### 5.2 Human-in-the-Loop (HITL, 사람 개입 루프)

자동화를 100%로 밀어붙이지 않고, **불확실한 건만 사람에게 넘기는** 설계입니다.

```
findings → confidence 태그 부여
        ├─ high   → 자동 수정(auto-fix) 후 커밋
        └─ low/medium → 사람 검토 큐로 라우팅
```

이것을 **Confidence-based Routing(신뢰도 기반 분기)** 이라고 부릅니다. 장점:

- 확실한 것은 사람 시간을 안 씁니다.
- 불확실한 것이 자동으로 코드에 반영되어 사고를 내는 일이 없습니다.
- 사람에게 넘긴 것도 **버려지지 않습니다** — 모델이 스스로 의심스러운 항목을 조용히 폐기(quietly discard)하면 사람이 검토할 기회조차 사라지므로 이는 잘못된 설계입니다.

### 5.3 구조화가 라우팅의 전제 조건

자동 분기를 하려면 신뢰도가 **필드로 분리되어** 있어야 합니다. 모든 발견 사항을 하나의 요약 문단으로 뭉쳐 놓으면 프로그램이 파싱할 수 없고, 결국 사람이 다시 읽어서 판단해야 합니다. **자동화하려면 구조화하라**가 원칙입니다.

## 6. 프롬프트 평가와 회귀 테스트

### 6.1 왜 필요한가

프롬프트는 코드와 비슷합니다. 고치면 좋아질 수도 있지만, 다른 곳이 망가질 수도 있습니다. 그런데 프롬프트는 동작이 확률적이라 "읽어보고 괜찮은지" 판단하는 것이 특히 불가능합니다. 프롬프트를 바꿨다면 **측정해야 합니다.**

지표 정의(정밀도, 재현율, 오탐율)는 1.2를 그대로 사용합니다.

### 6.2 Held-out 데이터셋과 골든 데이터셋

- **Held-out set(격리 평가 세트)**: 프롬프트를 개선할 때 **보지 않고 따로 떼어둔** 평가 전용 데이터. 개발 중에 보면서 튜닝한 데이터로 성능을 재면, 그 데이터에 맞춰 조정한 결과를 자기가 채점하는 셈이라 점수가 부풀려집니다.
- **Golden dataset / Ground truth(정답 데이터)**: 각 입력에 대해 **정답이 이미 확정되어 있는** 데이터. 예: 과거 PR들과, 그 PR에서 실제로 유효했던 지적 / 오탐이었던 지적 기록.

### 6.3 회귀 테스트(Regression Testing) 절차

프롬프트를 고친 뒤 전체 배포 전에 밟아야 할 표준 절차:

1. 정답이 알려진 held-out 데이터셋을 준비한다.
2. 수정된 프롬프트를 그 데이터셋 전체에 대해 실행한다.
3. 오탐율, 정밀도 등 **정량 지표**를 계산한다.
4. 목표 기준(예: 오탐율 5% 이하)을 만족하는지 확인한다.
5. 기존에 잘 되던 케이스가 망가지지 않았는지(회귀 여부)도 함께 본다.
6. 통과하면 배포한다.

**전형적인 시나리오:** 코드 리뷰 에이전트의 "성능 제안" 카테고리가 오탐이 너무 많아 일시 비활성화했고, 판단 기준을 구체적이고 검증 가능한 규칙으로 다시 썼습니다. 이제 팀 전체에 다시 켜도 될까요? → **다시 켜기 전에 held-out PR 세트로 돌려보고 오탐율이 실제로 목표치까지 떨어졌음을 데이터로 확인해야 합니다.**

**부적절한 검증 방식들:**

- *규칙을 명확하게 썼으니 검증 없이 바로 켠다*: 프롬프트 문구가 명확하다는 것과 모델이 그 문구대로 행동한다는 것은 별개입니다. 검증 없는 배포는 추측입니다. 게다가 새 규칙이 다른 유형의 오탐이나 미탐을 만들었을 수도 있습니다.
- *시니어 엔지니어 한 명이 소수의 과거 PR을 눈으로 훑어보고 판단한다*: 표본이 작고(통계적으로 무의미), 편향되어 있으며(오탐을 냈던 케이스만 봄 → 미탐은 전혀 확인 안 됨), 주관적이고, 정량 지표가 없어 "얼마나 좋아졌는지" 말할 수 없습니다.
- *오탐을 신고한 엔지니어의 PR에만 켜서 파일럿한다*: 실제 운영 환경에서 검증되지 않은 것을 돌리는 것이고, 한 사람의 코드는 다양성이 없으며, 그 사람에게 테스트 부담을 떠넘깁니다. 과거 데이터로 오프라인 측정하면 될 일을 굳이 프로덕션에서 할 이유가 없습니다.

**원칙: 사람의 인상(impression)이 아니라 재현 가능한 정량 지표로 판단한다.**

## 7. 모니터링, 피드백 루프와 사용자 신뢰

### 7.1 구조화된 필드가 모니터링을 가능하게 한다

출력을 구조화하는 이유는 저장 편의만이 아닙니다. **구조화된 필드는 곧 집계 가능한 지표(metric)** 가 됩니다.

예: 코드 리뷰 어시스턴트의 각 발견 사항에 `detected_pattern` 필드를 넣어두면, 나중에 **패턴 값별로** 통계를 낼 수 있습니다.

```sql
SELECT detected_pattern,
       COUNT(*) AS total,
       AVG(CASE WHEN status='dismissed' THEN 1.0 ELSE 0 END) AS dismissal_rate
FROM findings
GROUP BY detected_pattern;
```

`detected_pattern`이라는 필드가 없었다면 이런 분석 자체가 불가능합니다. **모니터링을 염두에 둔 스키마 설계**가 중요한 이유입니다. (5.3의 "자동화하려면 구조화하라"와 같은 원리가 사후 분석에도 적용됩니다.)

### 7.2 피드백 루프(Feedback Loop)와 기각률(Dismissal Rate)

**기각률**은 사용자가 알림을 "이건 문제 아님"으로 닫아버린 비율입니다. **오탐의 실전 대리 지표(proxy)** 입니다.

몇 달 치 데이터를 모아보니 `detected_pattern`이 `"decorator-wrapped test fixture"` 인 발견 사항의 **90% 이상이 기각**된다는 사실이 드러났다고 합시다.

이 피드백 루프가 주는 **주된 가치는, 과도하게 트리거되는(over-triggering) 특정 패턴 하나를 정확히 집어내어(pinpoint), 그 구문에 한정해 탐지 규칙을 조정(tune)하거나 억제(suppress)할 수 있게 해주는 것**입니다.

즉 "이 도구는 별로다"라는 막연한 불만을 **"이 규칙의 이 케이스가 문제다"라는 실행 가능한 작업 항목**으로 바꿔줍니다.

**과잉 해석에 주의:**

- 특정 패턴 하나에 기각이 집중된 것은 "개발자들이 무작위로 기각한다"는 증거가 **아닙니다.** 리뷰 프로세스 전체를 중단할 근거가 되지 않습니다.
- 높은 기각률은 **판단 규칙의 도메인 적합성 문제**이지, JSON 스키마의 구문 결함(syntax defect)과는 무관합니다.
- 한 카테고리의 오탐을 발견했다고 해서 **모든** 카테고리의 향후 발견을 사람 검토 없이 자동 종결하는 것은 위험한 일반화입니다.

### 7.3 신뢰 훼손(Trust Erosion)과 알림 피로

기술적으로는 옳은데도 시스템이 실패하는 대표적 경로입니다.

시나리오: 코드 리뷰 어시스턴트가 보안(security), 정확성(correctness), 스타일(style) 세 카테고리로 결과를 냅니다.

| 카테고리 | 품질 |
|---|---|
| 보안 | 정밀도 90% 이상 |
| 정확성 | 정밀도 90% 이상 |
| 스타일 | **오탐률 60%** |

그런데 개발자들이 **보안 알림까지 포함해 도구의 모든 결과를 불신**하기 시작했습니다.

**설명**: 사용자는 출력을 카테고리별로 나눠서 인식하지 않습니다. **모든 결과가 "같은 하나의 AI 리뷰어"라는 미분화된 단일 출처(single undifferentiated source)에서 나온 것으로 체감합니다.** 그래서 **오탐률이 높은 단 하나의 카테고리가 정확한 나머지 카테고리에 대한 신뢰까지 잠식합니다.**

**설계적 교훈:**

- 카테고리별 정밀도 지표가 좋아도, **가장 나쁜 카테고리가 전체 신뢰도를 결정**합니다.
- 정밀도가 낮은 카테고리는 **차라리 끄거나, 분리된 채널로 내보내거나, 임계값을 올리는** 편이 낫습니다. 끈 뒤에는 6.3의 회귀 테스트로 개선을 확인하고 다시 켭니다.
- 이는 통계 계산 오류나 "보안 이슈가 검증하기 어려워서" 생기는 문제가 아니라, **사용자 경험 차원의 심리 현상**입니다.
