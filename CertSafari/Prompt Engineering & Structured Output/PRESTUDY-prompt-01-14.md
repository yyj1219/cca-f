## 1. LLM API 호출 방식: 동기식과 비동기 배치

### 1.1 동기식(Synchronous) Messages API

LLM(대규모 언어 모델)을 프로그램에서 쓰려면 API를 호출합니다. Anthropic의 기본 API는 **Messages API**이고, 이것은 **동기식(synchronous)** 입니다. 동기식이란 "요청을 보내고 응답이 돌아올 때까지 기다린다"는 뜻입니다.

```python
import anthropic
client = anthropic.Anthropic()

resp = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "이 계약서를 요약해줘: ..."}],
)
print(resp.content[0].text)   # 보통 수 초 내에 결과가 손에 들어옴
```

특징:
- 응답이 즉시(수 초) 온다 → 챗봇, 실시간 UI, 프롬프트 실험에 적합
- 요청 1건당 1회 호출 → 15,000건이면 15,000번 호출해야 함
- 정가 요금
- **Rate Limit(호출 제한)** 이 있음: 분당 요청 수(RPM), 분당 토큰 수(TPM) 등에 상한이 있어, 스레드를 많이 띄워 병렬 호출해도 무한정 빨라지지 않고 429 에러(Too Many Requests)를 맞는다

### 1.2 Message Batches API (비동기 대량 처리)

**Message Batches API**는 "지금 당장 답이 필요 없는 대량 작업"을 위한 별도 API입니다. 수많은 요청을 한 파일처럼 묶어서 제출하면, 서버가 여유 있을 때 처리해 두었다가 결과를 한꺼번에 돌려줍니다.

핵심 성질:

| 항목 | 값 / 의미 |
|---|---|
| 처리 시간 | 최대 **24시간** (대부분 훨씬 빨리 끝나지만 최악의 경우 24시간으로 설계해야 함) |
| 비용 | 동기식 대비 **약 50% 할인** |
| 규모 | 한 배치에 수천~수만 건 요청을 담을 수 있음 (요청 수/총 용량 한도는 문서 기준을 따름) |
| 결과 식별 | 요청마다 **`custom_id`** 를 붙여 제출하고, 결과도 같은 `custom_id` 로 짝지어 돌아옴 |
| 순서 | 처리 순서는 보장되지 않음. 순서가 필요하면 `custom_id` 로 직접 정렬 |

제출 예시(개념):

```python
batch = client.messages.batches.create(requests=[
    {"custom_id": "contract-0001",
     "params": {"model": "claude-sonnet-4-5", "max_tokens": 1024,
                "messages": [{"role": "user", "content": "계약서 1 내용..."}]}},
    {"custom_id": "contract-0002",
     "params": {...}},
    # ... 15,000건
])
```

**왜 존재하는가**: 대량 문서 분류/추출/요약처럼 "문서당 비용"이 총비용을 좌우하는 워크로드에서, 즉시성을 포기하는 대신 절반 가격을 얻기 위해서입니다. 마감이 24시간 이상 여유가 있으면 거의 항상 배치가 유리합니다.

**언제 동기식을 쓰나**: 사용자가 화면 앞에서 기다리는 경우, 그리고 **프롬프트를 다듬는 실험 단계**.

### 1.3 배치를 쪼갤 필요가 있는가?

배치는 대용량을 처리하도록 설계되어 있으므로, "안정성을 위해 몇 백 건씩 잘라 몇 분 간격으로 제출"할 이유는 없습니다. 오히려 배치를 잘게 나누면 관리 복잡도와 추적 부담만 늘어납니다. 쪼개는 근거는 오직 문서에 명시된 한도(요청 수 한도, 용량 한도)를 넘길 때뿐입니다.

### 1.4 배치 만료(expired)와 부분 실패 처리

배치가 24시간 안에 전부 처리되지 못하면, **처리되지 못한 요청만** 결과 타입 `expired` 로 돌아옵니다.

중요한 규칙 세 가지:
1. **이미 성공한 요청의 결과는 그대로 유효하다.** 배치가 만료됐다고 전체 결과가 폐기되지 않는다.
2. **`expired` 요청에는 과금되지 않는다.**
3. **만료는 종료 상태(terminal state)다.** 플랫폼 수요가 줄어도 자동으로 재대기열(requeue)되지 않는다.

따라서 올바른 대응은:

```python
expired_ids = [r.custom_id for r in results if r.result.type == "expired"]
# 성공분은 그대로 저장해 두고, expired 건만 새 배치로 재제출
client.messages.batches.create(requests=[build_request(i) for i in expired_ids])
```

전체 배치를 통째로 재제출하면 이미 성공한 요청까지 다시 과금되므로 낭비입니다. 또한 일시적인 수요 급증 때문에 생긴 만료를 이유로 워크로드 전체를 더 비싼 동기식 API로 바꿀 필요도 없습니다.

### 1.5 대량 배치 제출 전의 필수 절차 — 소규모 표본 검증

배치는 싸지만, **프롬프트가 잘못돼 있으면 8만 건 전부를 버리고 다시 돌려야** 합니다. 그래서 표준 절차는 다음과 같습니다.

1. 전체 데이터에서 **대표성 있는(representative)** 소규모 표본(예: 50~200건)을 뽑는다. 정상 케이스뿐 아니라 지저분한 케이스, 값이 없는 케이스도 포함시킨다.
2. 그 표본을 **동기식 API** 로 돌려 빠르게 결과를 본다.
3. 출력 품질(필드 누락, 형식 위반, 잘못된 값)을 확인하고 프롬프트/스키마를 고친다.
4. 품질이 충분해지면 그때 전체를 배치로 제출한다.

`max_tokens` 를 무작정 키우거나, 배치를 반으로 쪼개는 것은 "프롬프트 품질" 문제를 전혀 해결하지 못합니다. `max_tokens` 는 출력이 길이 제한으로 **잘리는(truncation)** 문제에만 효과가 있고, 지시 불이행·형식 오류와는 무관합니다.

## 2. 마감 기한(SLA) 관점의 배치 주기 설계

배치 파이프라인의 총 지연 시간은 **세 조각의 합**입니다.

```
총 소요 시간 = (다음 배치가 출발할 때까지의 대기 시간) + (배치 처리 시간) + (후처리 시간)
```

핵심은 첫 항입니다. 데이터가 **배치가 막 출발한 직후에 도착**하면, 그 데이터는 다음 배치까지 꼬박 한 주기(= 제출 간격 I)를 기다립니다. 이것이 **최악의 대기 시간**이며, 마감 보장 계산에는 항상 이 최악값을 써야 합니다.

일반식:

```
I + (배치 최악 처리 시간) + (후처리 시간) ≤ 마감 기한
```

예: 마감 36시간, 배치 최악 처리 24시간, 후처리 2시간이라면

```
I + 24 + 2 ≤ 36  →  I ≤ 10시간
```

즉 배치를 **최소 10시간마다** 제출해야(간격이 10시간을 넘지 않아야) 최악의 경우에도 36시간을 지킵니다.

자주 하는 실수:
- 후처리 2시간을 빼먹고 36의 절반인 12시간으로 잡기 → 12+24+2 = 38시간으로 초과
- 후처리 시간만 보고 2시간 주기로 잡기 → 24시간 처리 시간을 무시한 계산
- "배치 처리 시간을 줄여서 후처리를 흡수한다" → **외부 API의 최악 처리 시간(24시간)은 사용자가 줄일 수 없는 상수**입니다. 내가 조절할 수 있는 변수는 제출 간격 I 뿐입니다.

## 3. 프롬프트 엔지니어링: 모델 출력을 개선하는 순서

### 3.1 Zero-shot: 지시문만 주기

예시 없이 "무엇을 하라"만 적는 방식입니다. 가장 간단하고 토큰이 적게 듭니다.

```
계약서에서 renewal_notice_period(갱신 통보 기간)를 추출해 JSON으로 출력하라.
```

지시문을 더 자세하고 명시적으로 쓰는 것이 1차 개선 수단입니다. 하지만 지시문 개선만으로는 **"어떤 문장이 그 정보에 해당하는가"** 같은 판단 경계를 모델에 전달하기 어렵습니다.

### 3.2 Few-shot Prompting (퓨샷 프롬프팅) / In-context Learning

지시문 개선으로 효과가 없을 때의 **다음 단계**는 **예시(examples)를 프롬프트에 넣는 것**입니다. 모델은 학습을 다시 하지 않고, 프롬프트 안의 예시를 보고 그 자리에서 패턴을 잡습니다. 이것을 문맥 내 학습(in-context learning)이라고 합니다.

좋은 예시 세트의 구성 요소:
- **긍정 예시(positive example)**: 정보가 특이하게 표현된 실제 문장에서 올바르게 값을 뽑아낸 사례
- **부정 예시(negative example)**: 정보가 정말 없을 때 `null` 을 반환하는 것이 정답인 사례

두 종류를 함께 주는 것이 중요합니다. 긍정 예시만 주면 모델이 아무 데서나 값을 지어내고, 부정 예시만 주면 조금만 애매해도 `null` 을 뱉습니다. 둘을 같이 보여줘야 **"값이 있다/없다"의 경계선**을 배웁니다.

```
예시 1 (특이한 표현에서 추출):
입력: "Either party may terminate by giving sixty (60) days written notice
       prior to the end of the then-current term."
출력: {"renewal_notice_period": "60 days"}
  ← '갱신(Renewal)'이라는 제목의 조항이 아니라 '해지(termination)' 문장에 묻혀 있어도 추출한다.

예시 2 (정말 없을 때):
입력: "This agreement is effective from January 1, 2024 for one year."
출력: {"renewal_notice_period": null}
```

### 3.3 예시에 근거(reasoning)를 함께 넣기 — Chain-of-Thought 성격의 예시

입력·출력 쌍만 나열한 예시는, 모델이 **표면적인 키워드 매칭 패턴**만 흉내 내게 만들 위험이 있습니다. 특히 판단이 모호한 경계 사례(edge case)에서 그렇습니다.

예시에 **"왜 그 답이 다른 그럴듯한 답보다 나은가"** 하는 짧은 설명을 덧붙이면, 모델은 결과가 아니라 **판단 원리**를 배웁니다. 그 결과 예시에 없던 새로운 사례에도 판단을 **일반화(generalization)** 할 수 있게 됩니다. 이것이 생각의 사슬(Chain-of-Thought, CoT) 프롬프팅의 원리를 예시에 적용한 형태입니다.

고객 지원 티켓 라우팅 예시:

```
티켓: "결제가 두 번 청구됐는데, 앱에서 결제 내역 페이지가 아예 안 열려요."
선택한 큐: technical
이유: 고객의 즉각적인 차단 요인은 앱이 열리지 않는 것이며, 중복 청구 확인 자체가
      그 화면에 의존한다. 결제 키워드가 있어도, 진행을 막는 원인이 기술적이면 technical 이 우선한다.
```

예시 설계 시 유의점:
- **실제 데이터에서 뽑은 사례**를 쓴다. 지나치게 정제된 이상적 예시는 현업의 지저분한 입력에 대한 일반화 능력을 길러 주지 않는다.
- **정책 문서 전문을 예시마다 반복 삽입하지 않는다.** 공통 규칙·정책은 시스템 프롬프트 상단에 **한 번만** 쓰고, 예시에는 개별 사례만 담는다. 반복 삽입은 문맥 창(context window)과 토큰을 심각하게 낭비한다.

### 3.4 하면 안 되는 "해결책"들

정보 추출이 실패할 때 흔히 시도하지만 잘못된 접근들:

- **데이터 타입을 열거형(enum)으로 바꾸기**: 스키마 타입 변경은 출력 *형식*을 제약할 뿐, 본문에서 숨은 표현을 찾아내는 **이해 능력**을 향상시키지 않는다.
- **기본값(fallback default) 하드코딩**: "못 찾으면 30일로 채운다"는 식은, 실제로는 다른 값이었을 수도 있는 자리에 거짓 데이터를 밀어 넣어 데이터셋을 오염시킨다. 추출 실패는 실패로 남겨 두고(`null`) 별도 처리해야 한다.
- **검색 범위를 제목 키워드로 좁히기**: "'renewal' 또는 'termination' 이 제목에 들어간 조항만 보라"는 지시는, 애초에 문제였던 "제목 없는 곳에 묻힌 정보"를 아예 못 보게 만들어 상황을 악화시킨다.
- **Temperature 올리기**: 온도는 출력의 **무작위성(randomness)** 을 키우는 값이다. 없는 정보를 찾아내는 능력과는 무관하고, 오히려 없는 값을 지어낼(환각) 확률만 높인다.
- **더 큰 모델로 교체**: 원본에 정보 자체가 없으면 어떤 모델도 복구할 수 없다.

## 4. 구조화된 출력(Structured Output)과 검증

### 4.1 JSON 스키마가 하는 일과 못 하는 일

구조화된 출력은 모델이 자유 문장 대신 정해진 JSON 형태로 답하게 하는 기법입니다. JSON 스키마로 필드 이름, 타입, 필수 여부, 형식(`"format": "date"` 등)을 지정할 수 있습니다.

```json
{
  "type": "object",
  "properties": {
    "start_date": {"type": "string", "format": "date"},
    "end_date":   {"type": "string", "format": "date"}
  },
  "required": ["start_date", "end_date"]
}
```

**스키마가 보장하는 것**: 각 필드가 존재하는가, 타입이 맞는가, 날짜 문자열 형식이 맞는가.

**스키마가 보장하지 못하는 것**: **필드들 사이의 논리적 관계**. 예를 들어 `start_date` 와 `end_date` 가 각각 올바른 날짜 문자열이더라도, `end_date < start_date` 인 논리적 모순은 스키마 타입 검증으로 절대 잡히지 않습니다. 이런 규칙을 **비즈니스 규칙(business rule) / 논리 제약(logic constraint)** 이라고 부릅니다.

### 4.2 Self-Correction 루프 (검증 → 피드백 → 재시도)

논리 제약은 **코드로 직접 검사**하고, 위반 시 그 내용을 **피드백 메시지로 만들어 모델에 다시 요청**하는 것이 표준 패턴입니다. 이를 자기 수정(self-correction) 루프 또는 피드백 루프라고 합니다.

```python
MAX_RETRIES = 3

def extract_with_check(text):
    feedback = None
    for attempt in range(MAX_RETRIES):
        data = call_model(text, feedback)          # feedback 이 있으면 프롬프트에 덧붙임
        if data["end_date"] >= data["start_date"]:
            return data                            # 검증 통과
        feedback = (f"직전 출력의 end_date({data['end_date']})가 "
                    f"start_date({data['start_date']})보다 앞섭니다. "
                    f"원문을 다시 확인해 계약 기간의 순서를 바로잡아 주세요.")
    return None                                    # 한도 소진 → 사람에게 이관
```

핵심 포인트:
- 검증은 **추출 이후에 코드가** 수행한다 (결정적이고 신뢰할 수 있음)
- 재시도 시 **무엇이 왜 틀렸는지를 구체적으로** 알려 준다. 단순 재요청보다 훨씬 성공률이 높다
- 프롬프트에 "날짜에 주의하라"고 한 번 적어 두는 것만으로는 부족하다. 확률적 생성 모델은 지시를 항상 지키지 않으므로 **사후 검증이 반드시 필요**하다
- 문제가 되는 필드를 스키마에서 삭제해 버리는 것은 오류를 없애는 게 아니라 **요구사항 자체를 포기**하는 것이다

### 4.3 재시도 한계와 Human-in-the-Loop

재시도 루프에는 반드시 **최대 재시도 횟수(maximum retries)** 가 있어야 합니다. 그리고 더 중요한 것은 **실패 원인의 구분**입니다.

| 실패 유형 | 원인 | 올바른 대응 |
|---|---|---|
| 구조적 실패 | 형식 위반, 필드 누락, 논리 제약 위반 — 정보는 원본에 있음 | 피드백 재시도로 해결 가능 |
| 원본 데이터 부재 (genuinely absent) | 애초에 원본에 그 정보가 없음 | 재시도 중단, **사람에게 이관** |

예: 스캔된 경비 보고서에서 직원이 프로젝트 코드 칸을 아예 비워 뒀다면, 이미지 어디에도 그 값이 없습니다. 이때 재시도를 계속하면:
- 프롬프트/스키마를 아무리 정교하게 다듬어도 없는 데이터가 생기지 않고
- 온도를 올리면 모델이 그럴듯한 코드를 **지어낼(환각, hallucination)** 확률만 커지며
- 더 큰 모델로 바꿔도 마찬가지입니다

따라서 재시도를 멈추고 해당 건을 예외로 표시해 담당자에게 넘기는 **Human-in-the-Loop(사람 개입)** 설계가 정답입니다. 잘 만든 파이프라인은 "실패를 조용히 채워 넣지" 않고 "실패를 사람에게 드러냅니다".

## 5. AI 코드 리뷰 아키텍처

### 5.1 Per-file pass vs Integration(Cross-file) pass

대규모 변경을 리뷰할 때 흔히 두 단계로 구성합니다.

**1단계 — 파일별 검사(per-file pass)**: 변경된 파일을 하나씩 격리해서(in isolation) 본다.
- 잘 잡는 것: 문법 오류, 컴파일 가능 여부, 들여쓰기·명명 규칙 등 스타일/포맷, **같은 파일 안**의 중복 로직, 파일 내부의 로컬 로직 버그
- 못 잡는 것: 그 파일 밖의 사정

**2단계 — 통합 검사(integration pass / cross-file pass)**: 전체 변경 집합(changeset)을 한꺼번에 본다.
- 이 단계가 존재하는 유일한 이유는 **파일 경계를 넘는 문제**를 잡기 위함이다:
  - 파일 간 **데이터 흐름(data flow)** 불일치
  - 모듈 간 **계약(contract)** 불일치 — 공유 인터페이스를 파일마다 다른 규격·다른 의도로 사용
  - 한쪽이 바꾼 함수 시그니처를 다른 쪽이 옛 방식으로 호출하는 경우

각 파일은 격리해서 보면 문법적으로 완벽하고 타입 오류도 없어 보일 수 있지만, 합쳐 놓으면 서로 어긋납니다. 이것이 통합 패스가 필요한 이유입니다. 반대로, 파일 하나 안에서 끝나는 문제(문법, 스타일, 동일 파일 내 중복)를 통합 패스의 주된 목표로 삼는 것은 단계 배치를 잘못한 것입니다.

### 5.2 파일별 결과가 서로 충돌할 때

상호 의존적인 두 파일 A, B를 각각 격리 검사했더니 **같은 근본 원인(데이터 흐름 문제)** 에 대해 서로 모순되는 수정안을 냈다고 합시다. 각 패스는 자기 파일만 보므로 전체 흐름을 오해한 상태입니다.

올바른 해결책은 **두 파일을 함께 보는 교차 파일 통합 패스를 추가**해, 실제 데이터 흐름에 근거한 **단일한 권고안**을 도출하는 것입니다.

잘못된 대안들:
- **파일을 물리적으로 합치기**: 리뷰 편의를 위해 소스 구조를 훼손하는 것은 모듈화 원칙 위반이다
- **재실행 후 "더 자신 있어 보이는 문구"를 채택**: 표현의 확신도는 정확성의 근거가 아니다
- **원래 코드를 쓴 생성기에게 중재를 맡기기**: 그 세션은 애초에 문제를 만든 맹점을 그대로 갖고 있다 (다음 절 참조)

### 5.3 Generator-Verifier 분리와 셀프 리뷰의 맹점

**생성기(generator)** 는 코드를 만든 모델/세션이고, **검증자(verifier/reviewer)** 는 그 결과를 검사하는 별도 인스턴스입니다.

핵심 원리: **코드를 생성한 그 세션에게 자기 코드를 검토시키면(self-review), 생성 당시의 잘못된 가정·오개념·놓친 조건 같은 맹점(blind spots)을 검증 단계에서도 똑같이 놓칩니다.** 같은 문맥에서 나온 판단이므로 오류가 상속됩니다.

그래서 신뢰도 라벨('high confidence' / 'low confidence')도 생성기가 스스로 붙이면 의미가 약합니다. 자기가 못 본 것을 "낮은 신뢰도"로 표시할 수는 없기 때문입니다. 검증은 **독립적인 문맥을 가진 별도 인스턴스**가 수행해야 합니다.

참고로 흔한 오해들:
- 신뢰도 라벨을 출력하는 데 코드베이스 쓰기 권한이 필요하지는 않다 (리뷰는 읽기·분석 작업)
- 신뢰도 점수/라벨은 프롬프트 지시나 구조화된 출력으로 얼마든지 생성할 수 있다 (지원되지 않는 형식이 아니다)
- 신뢰도 산출이 단일 파일 검토에서만 가능하다는 기술적 제약은 없다 (다중 파일에도 적용 가능)

### 5.4 Claude Code의 리뷰 명령과 비용·시간 트레이드오프

Claude Code에는 코드 리뷰 명령이 있고, **노력 수준(effort level)** 을 지정할 수 있습니다.

- **기본(default) 수준의 `/code-review`**: 로컬에서 빠르게 수행. 일상적인 리뷰에 적합하지만, 각 지적 사항을 독립적으로 재현·검증하는 깊은 절차는 수행하지 않는다.
- **`/code-review ultra`**: 클라우드에서 **다수의 리뷰어 에이전트 군단(fleet)** 을 병렬로 돌려, 발견된 각 이슈를 **독립적으로 재현(reproduce)하고 검증(verify)** 한다. 수 분이 걸리고 사용 크레딧(토큰)을 더 소모하지만, 오탐(false positive)이 걸러진 높은 신뢰도의 결과를 준다.
- **`/review <pr>`** 같은 수초 내에 끝나는 빠른 패스는 그 깊은 독립 검증을 대체하지 못한다.

판단 기준: **"몇 분과 크레딧을 써서라도 각 지적이 독립 검증되기를 원하는가?"** 대규모 다중 파일 변경의 머지 직전처럼 위험이 큰 순간이라면 그렇습니다. 참고로, 같은 명령을 수동으로 세 번 돌려 공통 항목만 남기는 방식은 비효율적일 뿐 아니라, 독립된 에이전트가 실제로 이슈를 재현해 보는 동작을 흉내 내지 못합니다.

### 5.5 리뷰 기준(criteria) 작성법 — 객관성과 명시적 분류

여러 리뷰어(사람이든 에이전트든)가 **같은 이슈에 대해 같은 분류로 수렴(converge)** 하게 하려면, 심각도 정의가 **객관적이고 검증 가능**해야 합니다.

좋은 정의의 조건: 코드만 보면 참/거짓을 판정할 수 있다.

```
Critical: 권한 검증이 필요한 데이터에 인증 없이 접근할 수 있게 되는 변경.
예) 다른 사용자의 레코드를 반환하는 DB 쿼리 앞의 권한 검사가 제거된 경우.
```
→ 누가 보든 "권한 검사가 제거되었는가?"는 사실 판정이므로 판단이 일치합니다.

나쁜 정의의 특징:
- **주관적 감정 의존**: "경험 많은 엔지니어가 불안함을 느낄 만한 위험한 패턴" → 사람마다 다름
- **주관적 인지 난이도 의존**: "주변 코드보다 현저히 복잡하거나 추론하기 어려운" → 역량·시각에 따라 다름
- **변경 내용이 아닌 이력 의존**: "과거에 장애가 잦았던 모듈을 건드리는 변경" → 현재 변경 자체의 위험도를 반영하지 못함

### 5.6 무엇을 보고하고 무엇을 건너뛸지 명시하기

치명적 이슈를 놓치지 않으면서 잡음(noise)을 줄이려면, **모델의 확률적 신뢰도 점수에 판정을 맡기지 말고** 보고 대상과 제외 대상을 **범주로 직접 명시**하는 것이 확실합니다.

```
반드시 보고(Report):
  - 보안 취약점을 유입시키는 변경
  - 기존 동작을 깨뜨리는 정확성(correctness) 버그

반드시 제외(Skip):
  - 포맷팅 취향 문제
  - 해당 파일에 이미 자리 잡은 로컬 컨벤션에서 벗어난 정도의 사항
```

이렇게 하면 판단 기준이 결정적이어서 리뷰어들 사이의 결과가 수렴합니다.

반면 잘못된 구성:
- **신뢰도 임계값(예: 0.9 초과만 보고)에 의존** → 애초에 "신뢰도에 맡기지 않겠다"는 목표와 정반대. 모델의 자기 신뢰도는 잘 보정(calibration)되어 있지 않다
- **두 번째 패스의 신뢰도 점수 일치 여부로 결정** → 여전히 신뢰도 점수 기반이며, 범주 정의가 없다
- **문서화된 스타일 가이드 위반을 전부 보고** → 줄이려던 포맷팅 잡음을 오히려 폭증시킨다

## 6. 용어 사전 (Glossary)

| 용어 | 설명 |
|---|---|
| **Messages API** | Anthropic의 기본 동기식 LLM 호출 API. 요청을 보내고 수 초 내 응답을 받는다. |
| **Message Batches API** | 대량 요청을 묶어 비동기로 처리하는 API. 최대 24시간 소요, 동기식 대비 약 50% 저렴. |
| **Synchronous / Asynchronous** | 동기식은 응답을 기다린다. 비동기식은 제출해 두고 나중에 결과를 회수한다. |
| **custom_id** | 배치의 각 요청에 붙이는 고유 식별자. 결과를 원래 요청과 짝짓고, 실패 건만 골라 재제출할 때 쓴다. |
| **expired (result type)** | 배치가 24시간 안에 처리하지 못한 요청의 결과 타입. 과금되지 않으며 자동 재대기열되지 않는 종료 상태. |
| **Terminal state** | 더 이상 상태가 바뀌지 않는 최종 상태. 만료된 배치는 여기에 해당하므로 직접 재제출해야 한다. |
| **Rate Limit** | 단위 시간당 허용되는 요청 수/토큰 수 상한. 동기식 병렬 호출을 무한정 늘릴 수 없는 이유. |
| **max_tokens** | 모델이 생성할 수 있는 최대 출력 토큰 수. 출력이 도중에 잘리는 문제에만 관계하며 품질 문제와는 무관. |
| **Temperature** | 샘플링 무작위성 파라미터. 높이면 다양해지지만 환각 위험이 커진다. 정보 추출에는 보통 낮게 둔다. |
| **SLA (Service Level Agreement)** | 서비스가 보장하는 처리/응답 기한. 배치 주기 설계의 상한 조건이 된다. |
| **Zero-shot Prompting** | 예시 없이 지시문만으로 작업을 시키는 방식. |
| **Few-shot Prompting** | 프롬프트에 입출력 예시 몇 개를 넣어 패턴을 알려 주는 방식. |
| **In-context Learning** | 모델 파라미터를 바꾸지 않고, 프롬프트 안의 예시만으로 그 자리에서 패턴을 익히는 현상. |
| **Positive / Negative Example** | 값을 뽑아내야 하는 사례 / 값이 없어 null이 정답인 사례. 둘을 함께 줘야 경계가 잡힌다. |
| **Chain-of-Thought (CoT)** | 답만이 아니라 판단 과정·근거를 함께 다루게 하는 프롬프팅. 예시에 이유를 붙이면 일반화가 좋아진다. |
| **Generalization** | 예시에 없던 새로운 입력에도 올바른 판단을 확장 적용하는 능력. |
| **Edge case** | 판단이 애매한 경계 사례. 설명 없는 예시만으로는 여기서 오판하기 쉽다. |
| **Context Window** | 모델이 한 번에 다룰 수 있는 토큰 총량. 예시마다 정책 문서를 반복 삽입하면 낭비된다. |
| **System Prompt** | 대화 전체에 적용되는 상위 지시문. 공통 정책·규칙은 여기에 한 번만 적는다. |
| **Structured Output** | 모델이 정해진 JSON 스키마 형태로 답하게 하는 기법. |
| **JSON Schema** | 필드 이름·타입·필수 여부·형식을 규정하는 명세. 타입은 검사하지만 필드 간 논리 관계는 못 잡는다. |
| **Enum (열거형)** | 값을 고정된 후보 집합으로 제한하는 타입. 형식 제약일 뿐 이해 능력을 높이지는 않는다. |
| **Business Rule / Logic Constraint** | "end_date는 start_date 이후" 같은 필드 간 논리 규칙. 코드로 별도 검증해야 한다. |
| **Validation Check** | 모델 출력이 규칙을 지켰는지 코드로 확인하는 단계. |
| **Self-Correction / Feedback Loop** | 검증 실패 내용을 피드백으로 넣어 모델에 재요청하는 루프. |
| **Retry Limit (Maximum Retries)** | 재시도 상한. 없으면 무한 루프와 비용 폭증, 환각 유도로 이어진다. |
| **Hallucination (환각)** | 모델이 근거 없는 값을 사실인 양 만들어 내는 현상. |
| **Genuinely Absent Data** | 원본에 정보가 실제로 존재하지 않는 상태. 재시도·모델 교체로 해결되지 않는다. |
| **Human-in-the-Loop** | 자동 처리로 해결 불가한 건을 사람에게 이관하는 설계. |
| **Fallback Default** | 실패 시 자동으로 채우는 기본값. 추출 파이프라인에서는 데이터 오염 원인이 되므로 지양. |
| **Changeset** | 리뷰 대상이 되는 변경 사항 전체 묶음. |
| **Per-file Pass** | 파일을 하나씩 격리해 보는 검사 단계. 문법·스타일·파일 내부 로직에 적합. |
| **Integration / Cross-file Pass** | 변경 집합 전체를 함께 보는 검사 단계. 파일 간 데이터 흐름·계약 불일치를 잡는다. |
| **Contract (계약)** | 모듈·인터페이스가 서로에게 약속한 입출력 규격과 동작. |
| **Data Flow** | 값이 파일과 모듈을 거쳐 흐르는 경로. 파일 단위 검사로는 전체를 볼 수 없다. |
| **Generator / Verifier** | 결과를 만든 주체 / 그것을 검사하는 주체. 분리해야 검증이 유효하다. |
| **Self-review** | 생성한 세션이 스스로 검토하는 것. 생성 시 맹점을 그대로 물려받는다. |
| **Blind Spot (맹점)** | 생성 시의 잘못된 가정·누락된 조건. 같은 세션에서는 반복해서 놓친다. |
| **Confidence Score / Label** | 결과의 확신 정도를 나타내는 점수·라벨. 보정이 부정확할 수 있어 판정 기준으로 삼기엔 위험하다. |
| **False Positive (오탐)** | 실제 문제가 아닌데 문제라고 보고된 결과. 독립 재현·검증으로 걸러낸다. |
| **Fleet (에이전트 군단)** | 여러 리뷰어 에이전트를 병렬로 돌리는 구성. `ultra` 수준 리뷰가 이 방식을 쓴다. |
| **Effort Level** | 리뷰의 깊이/비용 수준 설정. 높일수록 시간·크레딧을 더 쓰고 검증 정확도가 오른다. |
| **Severity Definition** | Critical 등 심각도 등급의 정의. 객관적·검증 가능해야 리뷰 결과가 수렴한다. |
| **Convergence (수렴)** | 여러 리뷰어가 같은 이슈에 같은 분류를 내리는 상태. |
| **Noise** | 중요하지 않은 지적이 쌓여 진짜 이슈를 가리는 현상. |
| **Representative Sample** | 전체 데이터의 다양한 양상을 반영한 소규모 표본. 대량 배치 전 프롬프트 검증에 사용. |
| **Iterative Refinement** | 소규모 실험 → 결과 확인 → 프롬프트 수정을 반복하며 품질을 올리는 절차. |
