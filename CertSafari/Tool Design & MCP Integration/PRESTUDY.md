## 공통 기초: LLM 에이전트와 도구(Tool)

### 왜 도구가 필요한가

대규모 언어 모델(LLM)은 본질적으로 **텍스트를 생성하는 함수**입니다. 학습 시점까지의 지식으로 다음 텍스트를 만들 뿐이므로, 스스로는 다음을 할 수 없습니다.

- 실시간 데이터 조회 (오늘의 환율, 재고, 티켓 상태)
- 파일 읽기·쓰기, 데이터베이스 조회
- 외부 API 호출, 명령어 실행
- 외부 시스템에 대한 실제 작업 수행 (환불 처리, 회의실 예약, 배포)

**도구(Tool)** 는 이 한계를 메우기 위해 모델에게 "네가 호출할 수 있는 함수 목록"을 미리 알려주는 장치입니다. 이 방식을 **Tool Use**(도구 사용), 다른 이름으로 **Function Calling**(함수 호출)이라고 부릅니다.

### 한 번의 도구 호출이 흘러가는 순서

모델은 직접 코드를 실행하지 않습니다. "이 함수를 이런 인자로 불러 줘"라는 **구조화된 출력(JSON)** 을 낼 뿐이고, 실제 실행은 모델을 감싸고 있는 애플리케이션(호스트, 클라이언트, 에이전트 런타임)이 합니다.

1. 애플리케이션이 모델에게 **시스템 프롬프트 + 대화 + 도구 정의 목록(tools)** 을 보냅니다.
2. 모델이 요청을 읽고 "지금은 `search_web`을 `{"query": "..."}`로 부르겠다"고 판단하면, 일반 텍스트 대신 **tool_use 블록**(도구 이름 + 인자 JSON)을 출력합니다.
3. **모델은 도구를 직접 실행하지 않습니다.** 애플리케이션 쪽 코드가 실제 함수/API를 실행합니다.
4. 실행 결과(성공이든 실패든)를 **tool_result 블록**으로 다시 모델에게 돌려줍니다.
5. 모델이 그 결과를 읽고 다음 행동을 결정합니다 — 또 다른 도구 호출이거나, 사용자에게 보내는 최종 답변이거나.

이 1~5의 반복을 **에이전트 루프(agent loop)** 라고 부릅니다.

```
사용자 요청
  → 모델이 도구 목록 + description 을 읽음
  → 모델이 "어떤 도구를, 어떤 인자로" 호출할지 결정
  → 런타임이 실제로 실행
  → 결과를 다시 모델에게 전달
  → 모델이 다음 행동을 결정하거나 최종 답변 생성
```

이 루프에는 **결정 지점이 두 곳** 있습니다. 어떤 도구를 고를 것인가(**도구 선택 / 라우팅**), 그리고 어떤 인자를 넣을 것인가(**인자 추출**). 이 주제의 대부분은 "이 두 결정을 어떻게 하면 모델이 덜 틀리게 만들 수 있는가"에 관한 것입니다.

그리고 4번 단계, 즉 **결과를 어떤 모양으로 돌려주느냐**가 나머지 절반을 차지합니다. 모델은 그 결과 텍스트/데이터만 보고 다음을 판단하기 때문입니다.

### 도구 정의(Tool Definition)의 구성 요소

도구 하나는 보통 세 가지로 정의됩니다.

| 요소 | 역할 |
|---|---|
| `name` | 도구 식별자. `get_user_profile`처럼 짧지만 의미를 담은 스네이크 케이스 문자열 |
| `description` | 자연어 설명. **모델이 이 도구를 언제 쓸지 판단하는 주된(사실상 유일한) 근거** |
| `input_schema` | 인자의 이름·타입·필수 여부·설명을 정의한 JSON Schema. 모델이 만들어 낼 수 있는 입력의 모양을 제한한다 |

```json
{
  "name": "search_web",
  "description": "웹 검색 엔진에 질의를 보내 최신 정보를 담은 결과 스니펫 목록을 돌려준다. 아직 어떤 페이지를 봐야 할지 모를 때 사용한다. 이미 특정 URL을 알고 있다면 fetch_webpage_results를 사용할 것.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": { "type": "string", "description": "검색어" }
    },
    "required": ["query"]
  }
}
```

설명 안에 **무엇을 하는지 + 언제 쓰는지 + 언제 쓰지 말지(다른 도구로 넘길 조건)** 를 함께 적는 것이 이 예시의 요점입니다. 좀 더 구체적인 예:

```json
{
  "name": "generate_summary_report",
  "description": "계정의 한 페이지 분량 요약 보고서를 생성한다. 총 잔액, 최근 5건 거래, 이상징후 여부만 포함한다(약 300단어). 예: '이 계정 간단히 훑어줘'. 거래 내역 전체나 월별 상세 분석이 필요하면 generate_detailed_report를 사용할 것.",
  "input_schema": {
    "type": "object",
    "properties": {
      "account_id": { "type": "string", "description": "계정 식별자, 예: 'ACCT-10293'" }
    },
    "required": ["account_id"]
  }
}
```

MCP 서버의 도구 정의도 같은 형태이며, 필드 이름만 `inputSchema`로 표기되기도 합니다.

### 핵심 감각: 모델은 "글"만 보고 도구를 고른다

모델은 도구의 **소스 코드를 보지 못합니다.** 모델이 보는 것은 오직 이름, 설명, JSON 스키마(파라미터 이름·타입·required 여부·각 파라미터 설명)뿐이고, 여기에 시스템 프롬프트가 얹혀서 전체 판단이 이뤄집니다. 모델은 이것들을 읽고 "지금 상황에 어떤 도구가 맞는가"를 **확률적으로** 판단합니다.

> **도구 정의는 코드가 아니라 모델을 향한 문서다.** 이름과 설명은 UI 문구가 아니라 모델을 향한 프롬프트다.

따라서 모델이 도구를 잘못 고르거나 이상한 인자를 만들어내는 문제는 거의 항상 **이름·설명·스키마·도구 집합의 품질 문제**입니다. 모델을 탓하기 전에 도구 정의를 봐야 합니다. 도구 설계에서 가장 큰 영향력을 가진 것은 코드가 아니라 텍스트라는 이 사실이 이후 모든 장의 근본 원리가 됩니다.

### 에이전트가 도구를 쓴다는 것의 의미

Claude Code 같은 **에이전트**는 사람이 말로 요청하면 스스로 "어떤 도구를 어떤 인자로 호출할지" 판단해 실행하고, 결과를 보고 다음 행동을 정하는 프로그램입니다. 사람이 코드로 흐름을 고정하는 게 아니라 **모델이 매 턴마다 결정**합니다. 여기서 두 가지 결론이 따라옵니다.

- 모델이 판단하려면 **정보가 텍스트로 주어져야** 합니다. 도구 이름, 설명, 그리고 **오류 메시지**가 곧 모델의 유일한 판단 근거입니다.
- 모델의 작업 기억(**컨텍스트 윈도우**)은 **유한**합니다. 쓸데없는 정보를 넣으면 정말 필요한 정보가 밀려납니다.

**컨텍스트 윈도우(Context Window)** 는 모델이 한 번에 볼 수 있는 텍스트의 총량이며, 토큰(대략 단어 조각) 단위로 셉니다. 지금까지의 대화, 읽은 파일 내용, 도구 결과가 전부 여기에 쌓입니다. 한도를 넘으면 오래된 내용이 잘려나가거나 요약되고, 그러면 모델이 앞서 본 것을 "잊습니다". 또한 토큰은 곧 비용이자 지연시간입니다. 그래서 **"필요한 것만, 필요할 때 읽는다"** 가 에이전트 작업의 기본 원칙입니다.

## 전체를 관통하는 설계 원칙

아래는 6개 원본의 원칙 요약을 합쳐 중복을 제거한 것입니다. 각 항목의 근거와 사례는 해당 장에서 다룹니다.

### 도구 정의와 라우팅

1. **모델은 텍스트로 판단한다.** 도구 정의는 모델을 위한 문서이고, 이름·설명·스키마가 라우팅 정확도의 1차 결정 요인이다. 모델이 틀리면 명세를 고쳐라.
2. **모호성을 남기지 마라.** 두 도구의 설명이 겹치면 반드시 오호출이 난다. 서로 다른 도구는 서로 다르고 배타적인 설명을 가져야 하며, 반환 필드와 사용 시점까지 구체적으로 쓴다. 겹치는 도구는 이름을 구체화하고 범위를 한정해 겹침을 제거한다.
3. **할 수 있는 것과 할 수 없는 것을 둘 다 써라.** 트리거 조건과 배제 조건, 즉 부정 제약이 오호출을 가장 확실히 줄인다.
4. **카탈로그를 유지보수하라.** 새 도구를 추가했으면 기존 도구의 이름·설명도 함께 갱신한다.

### 도구 집합과 제어

5. **구조적 차단 > 지시적 통제.** 제약은 프롬프트가 아니라 구조로 건다. "쓰지 마세요"라고 부탁하는 대신 도구를 아예 제거한다. 자유도는 스키마의 타입으로 제거하는 편이 안전하다.
6. **최소 권한 원칙.** 각 에이전트/도구에게 자기 역할에 딱 맞는 최소 범위만. 예외가 필요하면 전체 세트가 아니라 좁은 단일 도구로 준다.
7. **범용 도구는 허용 목록 검증이 붙은 제약된 도구로 교체한다.** 이름만 바꾸거나 복제 도구를 더하는 것은 무의미하다.
8. **후보군을 작게.** 도구 개수가 늘면 선택 정확도가 떨어진다. 10~20개를 넘으면 역할별 서브에이전트로 쪼개고 각각 4~5개만 노출한다.
9. **"보장"이 필요하면 프롬프트가 아니라 API를 써라.** `tool_choice`는 결정론적이고 프롬프트는 확률적이다. 다만 그런 강제가 필요한 경우가 아니라면 **자율성은 남긴다** — 오용은 도구 목록으로 막고 `tool_choice`는 `auto`로 두어 행동/응답 판단은 모델에게 맡긴다.
10. **바퀴를 다시 만들지 않는다.** 표준 서비스는 기존 MCP 서버를 채택하고, 커스텀 서버는 사내 고유 시스템에만 만든다.

### 오류와 실패

11. **오류는 두 층으로.** 사람이 읽을 자연어 설명 + 기계가 판단할 카테고리/재시도 플래그. 재시도 가능 여부를 기계가 판단할 수 있어야 올바른 후속 조치가 나온다.
12. **에러는 원인의 성질로 분류하라.** 실행 위치나 검사 순서가 아니라 "요청이 well-formed인가"가 기준이다. 스키마 위반은 핸들러 실행 전 JSON-RPC 프로토콜 에러, 도메인 실패는 결과 안의 `isError: true`.
13. **재시도 가능 여부는 "입력을 안 바꾸고 다시 보내면 성공할 수 있는가"로 판단한다.** 유효성 에러를 transient로 분류하면 무한 재시도 루프가 생긴다.
14. **빈 결과와 없는 리소스를 구별하라.** 빈 결과는 에러가 아니다 — `isError: false` + 빈 배열로 반환한다.
15. **일시적 오류는 가장 낮은 계층에서 흡수하라.** 안에서 해결됐으면 밖에는 성공만 보고한다.
16. **실패해도 성과는 보존하고, 실패는 숨기지 않는다.** 부분 결과 + 명시적 미해결 보고.
17. **정보가 없으면 추측하지 말고 보수적으로.** 진단 데이터 없는 크래시는 전량 재처리.

### 설정과 운영

18. **설정의 저장 위치가 곧 공유 범위다.** 스코프는 "어디서 로드되나 × 누가 보나" 두 축으로 요구사항에서 역산해 고른다. 충돌 시 로컬이 프로젝트를 이기고, 병합 없이 통째로 대체된다.
19. **안전한 기본값.** 클론한 설정은 승인 전까지 연결하지 않고, 덮어쓰기 전에는 읽게 한다.
20. **최적화는 표적 지향으로.** 한 서버가 문제면 그 서버만 고쳐라. 전역 스위치를 끄지 마라.
21. **재발 방지는 표준화로.** 개별 수정이 아니라 팀 템플릿/규범을 만든다.
22. **`list_changed` 알림을 받으면 연결을 유지한 채 `tools/list`를 재요청**해 도구 목록을 자동 갱신한다.

### 도구 사용 실무

23. **작업 규모에 맞는 도구를 쓴다.** 도구마다 하는 일이 정해져 있다 — Glob은 파일명/경로, Grep은 파일 내용, Edit은 국소 치환, Write는 전체 교체(새 파일 생성은 선행 Read 없이 Write 한 번).
24. **고치기 전에 전체 범위를 먼저 파악하라.** 특히 별칭과 re-export를 놓치지 마라.
25. **치환은 유일성이 생명이다.** 문맥을 넓혀 유일하게 만들되, 전역 치환으로 도망가지 마라.
26. **정적 조회로 런타임을 추론하지 마라.** 실행 결과가 필요하면 실제로 실행하라.
27. **반복 탐색은 컨텍스트 부족의 신호다.** 도구를 더 붙이지 말고 리소스로 미리 알려 줘라.
