# 시나리오4_데이터추출

## 질문 1

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : A nightly extraction job runs claude -p with --output-format json and --json-schema over incoming documents. The pipeline's parser reads the top-level result field and intermittently fails to obtain schema-conformant JSON. What change fixes this?

**A.** Extract the payload with jq -r '.result', since the wrapper nests the model's answer there.

**설명**

jq로 result를 추출하는 것은 스키마 없이 --output-format json만 사용해서 텍스트 답변을 얻고자 할 때의 정석적인 패턴이다. --json-schema를 사용하는 경우에는 검증된 페이로드가 structured_output에 담기므로, 이 방식은 파서가 계속 잘못된 필드를 가리키게 만든다.

**B.** 각 추출 결과가 개별적으로 파싱 가능한 JSON 줄로 도착하도록 --output-format stream-json으로 전환한다.

**설명**

stream-json은 실시간 이벤트 스트리밍을 위해 줄바꿈으로 구분된 JSON을 내보내는 방식으로, 전달 형식은 바뀌지만 스키마 검증된 페이로드의 위치는 옮기지 않는다. 파이프라인은 여전히 최종 result에서 structured_output을 읽어야 검증된 데이터를 얻을 수 있다.

**C.** Claude가 result 필드 안에 스키마에 맞는 JSON을 출력하도록 지시하는 프롬프트 지침을 추가한다.

**설명**

프롬프트 지침으로는 CLI가 검증된 출력을 어디에 배치하는지를 바꿀 수 없다. JSON 봉투 내 필드 배치는 Claude Code가 결정하는 것이며, 모델의 서술 내용이 결정하는 것이 아니다. 프롬프트에 의존하면 --json-schema가 원래 없애려던 확률적 포맷팅 문제가 다시 생긴다.

**D(정답).** JSON 봉투의 structured_output 필드에서 검증된 추출 페이로드를 읽는다.

**설명**

이것이 정답인 이유는, --json-schema가 지정되면 스키마 검증을 통과한 페이로드가 result가 아니라 JSON 래퍼의 structured_output 필드에 담기기 때문이다. result 필드는 텍스트 답변을 담고 있으며, 이 필드를 파싱해서 스키마에 맞는 JSON을 얻으려 하면 간헐적으로 실패하는 이유가 바로 여기에 있다.

### 전반적인 설명

Claude Code의 print 모드는 --output-format json으로 호출되면 출력을 JSON 봉투로 감싼다. 여기서 가져야 할 사고 모델은, 이 봉투가 서로 다른 역할을 가진 별도의 필드들로 구성되어 있다는 것이다. result에는 모델의 텍스트 답변이 담기고, 세션 메타데이터가 그 옆에 놓이며, --json-schema가 지정되면 스키마 검증된 페이로드가 별도의 structured_output 필드에 나타난다. result를 파싱하면서 스키마에 맞는 데이터를 기대하는 파이프라인은 사실 서술(prose) 채널을 읽고 있는 셈이며, 이것이 간헐적 실패를 설명한다. 어떤 때는 텍스트가 우연히 깨끗한 JSON이고, 어떤 때는 그렇지 않기 때문이다.

이러한 분리는 의도적인 설계다. 사람이 읽는 답변과 기계가 검증한 페이로드를 서로 다른 필드에 유지함으로써, Claude Code는 structured_output에 담기는 내용이 실제로 스키마 검증을 통과했다는 것을 보장하면서도, 모델이 result에서는 자유롭게 서술할 수 있게 한다. 자동화 과정에서 여전히 처리해야 할 두 가지 실패 모드가 있다. 첫째, 출력이 스키마 검증에 반복적으로 실패하면 실행은 구조화된 데이터 대신 error_max_structured_output_retries와 같은 오류 서브타입으로 종료된다. 둘째, 이와는 별개로, 결과가 success 서브타입을 가지면서도 structured_output 필드가 없는 경우도 있을 수 있다. 견고한 파이프라인이라면 진행하기 전에 성공 서브타입과 structured_output 존재 여부를 모두 확인해야 한다.

오답들은 구조적인 이유로 성립하지 않는다. jq -r '.result'는 스키마가 없는 순수 JSON 출력에서만 올바른 추출 방식이고, stream-json은 검증된 페이로드의 위치를 옮기지 않으면서 전달 방식만 줄바꿈 구분 이벤트로 바꾸며, 프롬프트 지침은 봉투 구조를 지시할 수 없다. 검증된 출력을 어디에 배치할지는 모델이 아니라 CLI가 결정하기 때문이다. 문서화된 호출 패턴과 출력 구조는 Headless mode와 CLI 레퍼런스를 참고하고, 검증 및 재시도 동작은 Structured outputs를 참고하라.


## 질문 2

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : A nightly Claude Code job reviews changes to a structured extraction pipeline and posts findings to a team dashboard. Every run re-posts the same schema-validation findings, so engineers now ignore the dashboard. How should the job be redesigned?

**A.** Run the review at temperature zero so successive runs emit identical findings the dashboard can deduplicate by exact text match.

**설명**

결정론적 샘플링은 검토 대상 코드가 바뀌면 동일한 출력을 보장하지 못하므로, 정확한 텍스트 일치 방식은 여전히 취약하다. 또한 팀이 이미 수정한 발견 사항과 모델이 다시 검출한 발견 사항을 구분하지 못해, 해결된 이슈와 미해결 이슈를 동일하게 취급한다.

**B.** 검토자가 치명적(critical) 심각도의 스키마 위반만 보고하도록 지시하여 대시보드에 반복되는 발견 사항의 수를 크게 줄인다.

**설명**

심각도로 필터링하면 출력량은 줄지만, 남은 치명적 발견 사항이 매일 밤 다시 게시되는 것을 막지는 못한다. 또한 근본적인 반복 문제는 해결하지 못한 채, 정당한 낮은 심각도 이슈에 대한 커버리지를 희생시킨다.

**C(정답).** 직전 실행의 발견 사항을 컨텍스트로 제공하고, 검토자가 새로운 이슈나 아직 해결되지 않은 이슈만 드러내도록 지시한다.

**설명**

이것이 반복 검토에 대한 문서화된 패턴이다. 검토자에게 자신의 이전 발견 사항과 명시적인 차이(delta) 지시를 함께 주면 중복은 억제되면서도 새로운 이슈와 미해결로 이어진 이슈는 계속 드러난다. 이는 반복 문제를 실제 그 본질인 컨텍스트 설계 문제로 다루는 방식이다.

**D.** 검토자가 각 발견 사항에 대해 스스로 신뢰도를 평가하게 하고, 게시 단계에서 신뢰도가 특정 기준 이하인 발견 사항을 제외한다.

**설명**

자체 평가한 신뢰도는 불확실성 문제를 다루는 것이며, 반복 문제를 다루는 것이 아니다. 신뢰도가 높은 발견 사항은 실행마다 똑같이 다시 검출되어 다시 게시될 것이다. 또한 모델이 스스로 산출한 신뢰도 점수는 필터링 신호로서 신뢰할 수 없다. 모델이 확신을 가지고도 틀릴 수 있기 때문이다.

### 전반적인 설명

자동화된 검토 작업은 같은 내용을 반복하면 청중을 빠르게 잃는다. 여기서 중요한 근본 메커니즘은, Claude Code의 각 CI 호출이 이전에 무엇을 보고했는지에 대한 기억이 없는, 매번 새로운 무상태(stateless) 실행이라는 점이다. 따라서 동일한 파이프라인 코드가 주어지면 매일 밤 동일한 스키마 검증 발견 사항을 자연스럽게 다시 생성하게 된다. 해결책은 이 누락된 상태를 명시적으로 만드는 것이다. 이전 실행의 발견 사항을 검토 컨텍스트에 포함시키고, Claude에게 새로운 이슈이거나 아직 해결되지 않은 이슈만 보고하도록 지시한다. 그러면 모델은 현재 코드를 이전 발견 사항과 비교하여 무엇이 수정되었는지 인식하고, 아직 수정되지 않은 것은 이어서 보고하며, 최신 변경으로 새로 생긴 문제를 표시할 수 있다.

이 방식이 효과적인 이유는 모델이 의미 기반의 중복 제거를 수행할 수 있게 하기 때문이다. 후처리 방식으로는 이를 할 수 없다. 온도 0에서의 정확한 텍스트 일치는 검토 대상 코드가 바뀌고 표현이 달라지는 순간 깨지며, 이 방식도 신뢰도 필터도 해결된 이슈와 재검출된 이슈를 구분하지 못한다. 신뢰도 기준은 전혀 다른 실패 모드(반복이 아니라 불확실성)를 겨냥하는 것이고, 심각도 필터링은 게시되는 중복 수를 줄일 뿐 유효한 낮은 심각도 커버리지를 버리게 된다.

CI 통합에 대한 일반적인 교훈은, 중복 억제가 후처리 문제가 아니라 컨텍스트 관리 문제라는 것이다. 모델이 호출 간에 필요로 하는 상태, 예를 들어 자신의 이전 출력 같은 것은 명시적으로 다시 넣어주어야 한다. 비대화형 검토 실행이 어떻게 구성되는지는 Claude Code GitHub Actions와 Run Claude Code programmatically를 참고하라.


## 질문 3

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : The team's /extract-fields skill requires a source document path and a target schema name, but engineers keep invoking the skill bare and get empty or malformed extractions. Which SKILL.md frontmatter change best addresses this?

**A.** Document the required parameters and their defaults in the skill's instruction body.

**설명**

지침 본문에 문서화하는 방식은 스킬 파일을 직접 열어서 읽는 사람에게는 도움이 되지만, 호출하는 시점에 엔지니어에게 노출되지는 않는다. 스킬을 그냥(bare) 실행하는 사람은 매개변수가 부족한 실행이 진행되기 전에 그 문서를 접할 일이 전혀 없다.

**B.** allowed-tools를 설정하여 스킬이 의존하는 읽기 및 추출 도구가 프롬프트 없이 실행되도록 한다.

**설명**

allowed-tools는 나열된 도구를 사전 승인하여 Claude가 해당 실행 턴에서 권한 요청 없이 도구를 사용할 수 있게 한다. 도구 승인을 매끄럽게 하는 것은, 스킬을 그냥 호출했을 때 빠져 있는 문서 경로와 스키마 이름을 전달하는 것과는 아무런 관련이 없다.

**C.** description 필드를 확장하여 Claude가 이 스킬을 언제 호출해야 하는지 더 정확히 판단하게 한다.

**설명**

description 필드는 Claude에게 어떤 스킬이 언제 관련성이 있는지를 알려주어 적절하게 선택되도록 하는 역할을 한다. 엔지니어가 스킬을 명시적으로 호출할 때 제공해야 하는 인자를 노출하지는 않으므로, 그냥 호출하는 습관은 계속된다.

**D(정답).** argument-hint를 추가하여 엔지니어가 스킬을 호출할 때 예상되는 인자가 표시되도록 한다.

**설명**

이것이 정답인 이유는, argument-hint가 호출 시점에 스킬이 기대하는 인자를 사용자에게 알려주기 위한 프런트매터 필드이며, 스킬이 호출되는 바로 그 위치에 나타나기 때문이다. 엔지니어가 명령을 입력하는 순간 필요한 문서 경로와 스키마 이름을 바로 노출시키는 것은, 잘못된 추출을 유발하는 그냥 호출하는 습관을 정확히 겨냥한다.

### 전반적인 설명

.claude/skills/에 정의된 스킬은 SKILL.md 파일에 YAML 프런트매터를 가지며, 각 프런트매터 필드는 서로 다른 문제를 해결한다. 유지해야 할 사고 모델은 다음과 같다. argument-hint는 사용자에게 스킬이 기대하는 입력을 알려주어 호출에 어떤 인자를 포함해야 하는지 보여준다. description은 Claude에게 이 스킬이 무엇을 위한 것인지 알려주어 적절한 시점에 호출되도록 한다. allowed-tools는 나열된 도구를 사전 승인하여 호출 턴 동안 권한 프롬프트 없이 사용할 수 있게 함으로써, 인자에 대해 무언가를 전달하는 것이 아니라 실행을 매끄럽게 만든다.

엔지니어가 매개변수가 필요한 스킬을 반복해서 그냥 호출하는 경우, 문제는 필요한 입력이 사용 시점에 보이지 않는다는 것이므로, argument-hint가 정확히 맞는 수단이다. 이는 사람들이 기억해서 읽어야 하는 문서에서, 호출 경험 자체로 해결책을 옮겨준다. 필요한 문서 경로와 스키마 이름이 스킬이 호출되는 위치에 표시되므로, 엔지니어는 실행하기 전에 무엇을 제공해야 하는지 보게 된다. 이 메커니즘의 한계도 짚어둘 필요가 있다. argument-hint는 기대치를 노출할 뿐, 인자를 검증하거나 매개변수가 부족한 실행을 막지는 않으므로, 스킬 내부에서 누락된 입력을 우아하게 처리하는 로직과 함께 사용하는 것이 여전히 좋은 관행이다. 지침 본문에 매개변수를 문서화하는 것은 수동적이며 호출 시점에는 전혀 나타나지 않고, description을 더 풍부하게 만드는 것은 사람이 매개변수를 어떻게 지정하는가가 아니라 Claude가 스킬을 선택하는 시점을 개선하며, 도구를 사전 승인하는 것은 근본 원인을 전혀 건드리지 않는다. 입력을 전혀 받지 못한 스킬은 도구가 얼마나 마찰 없이 실행되든 결과가 비어 있을 것이기 때문이다.

프런트매터 필드 전체 목록과 스킬의 범위 지정 및 공유 방식은 Claude Code의 Agent Skills 공식 문서를 참고하라.


## 질문 4

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : The team uses Claude Code to generate tests for the extraction pipeline. Generated tests keep re-covering scenarios the existing suite already handles, such as missing fields and malformed dates. What change fixes this?

**A.** Run test generation in plan mode so the proposed tests are reviewed before any files are written.

**설명**

플랜 모드는 변경 사항이 언제 반영되는지를 바꿀 뿐, Claude가 무엇을 알고 있는지는 바꾸지 않는다. 모델이 기존 커버리지를 전혀 볼 수 없으므로 제안된 계획에도 여전히 중복된 시나리오가 포함될 것이고, 사람은 결국 같은 중복 내용을 검토하게 될 뿐이다.

**B.** 팀의 테스트 표준과 픽스처 관례를 CLAUDE.md에 추가하여 생성이 정립된 패턴을 따르게 한다.

**설명**

표준과 픽스처 문서화는 생성되는 테스트의 스타일과 품질을 높이지만, 스위트가 이미 다루고 있는 시나리오에 대해서는 아무 정보도 주지 않는다. 커버리지 정보가 컨텍스트에 없으므로 Claude는 여전히 중복 테스트를 제안할 것이다.

**C(정답).** 기존 테스트 파일을 컨텍스트에 포함시키고, Claude에게 아직 커버되지 않은 시나리오에 대해서만 테스트를 생성하도록 지시한다.

**설명**

Claude는 실제로 볼 수 있는 커버리지만 중복하지 않을 수 있다. 현재 테스트 파일을 컨텍스트로 제공하고 빈틈을 겨냥하라는 지시를 함께 주면, 생성은 스위트의 스타일과 일관성을 유지하면서 실제로 테스트되지 않은 동작에 집중할 수 있다.

**D.** 파이프라인에서 생성된 테스트를 후처리하여, 기존 스위트의 테스트 이름과 일치하는 테스트를 제외한다.

**설명**

이름 일치 방식은 취약하다. 두 테스트가 이름은 다르지만 같은 시나리오를 다룰 수 있고, 서로 다른 시나리오가 비슷한 이름을 가질 수도 있다. 사후 필터링은 또한 근본에서 중복을 막는 대신 생성 노력을 낭비한다.

### 전반적인 설명

중복 테스트 생성은 워크플로우나 필터링의 문제가 아니라 컨텍스트의 문제다. 언어 모델은 저장소에 대한 주변적 인식을 갖고 있지 않으며, 오직 컨텍스트 윈도우에 있는 내용만으로 추론한다. 기존 테스트 파일이 제공되지 않으면 Claude는 필드 누락 처리나 날짜 형식 엣지 케이스가 이미 다뤄지고 있다는 것을 알 수 없으므로, 가장 뻔한 시나리오를 자연스럽게 다시 제안하게 된다. 현재 스위트를 제공하고 테스트되지 않은 동작만 다루라는 명시적 지시를 함께 주면 모델에게 커버리지 지도와 목표를 모두 제공하는 셈이며, 이는 Claude Code의 문서화된 테스트 워크플로우가 작동하도록 의도된 방식과 정확히 일치한다. 테스트되지 않은 코드를 식별하고, 빈틈에 대한 뼈대를 생성하고, 의미 있는 엣지 케이스를 추가한 다음, 실행하고 검증하는 방식이다.

오답들은 각각 인접한 문제를 해결할 뿐이다. CLAUDE.md 관례는 생성된 테스트의 품질과 일관성을 높이지만 커버리지에 대한 정보를 전혀 담고 있지 않으므로 중복은 계속된다. 파이프라인에서의 이름 기반 중복 제거는 의미적 중복에 대한 손실이 큰 대체 지표다. 이름이 다른 동일 시나리오 테스트를 놓치고, 이름이 비슷한 서로 다른 테스트를 잘못 폐기할 수 있다. 플랜 모드는 크고 모호한 변경의 범위를 정하는 데는 유용하지만, 실행을 검토를 위해 연기할 뿐이다. 계획 자체가 여전히 같은 커버리지에 대해 눈이 먼 컨텍스트에서 생성되므로 여전히 중복 테스트로 가득할 것이다.

일반적인 사고 모델은 다음과 같다. 생성된 출력이 저장소 상태에 의존하는 방식으로 잘못되었다면, 먼저 물어야 할 질문은 그 상태가 모델에게 보여진 적이 있는가이다. 테스트 생성 및 컨텍스트 관리에 대한 권장 접근 방식은 Claude Code Common Workflows를 참고하라.

**SCENARIO** : You are building a structured data extraction system using Claude. **QUESTION** : The extraction pipeline's date normalizer regresses with each revision: fixing one reported format breaks previously handled edge cases, and a latency requirement on large documents goes unchecked. Which refinement approach improves the implementation most reliably?

**A.** Lower the sampling temperature to zero so repeated implementation attempts interpret the written normalization rule identically on each run.

**설명**

온도는 토큰 선택의 변동성에 영향을 줄 뿐, 구현의 정확성에는 영향을 주지 않는다. 결정론적 실행은 동일한 엣지 케이스에 계속 실패하고 지연 시간 요구사항을 놓치는 코드를 일관되게 만들어낼 수 있으며, 루프 안의 어떤 요소도 그 실패들을 드러내지 못한다.

**B.** 실패가 발생할 때마다 서술문으로 설명하고, Claude에게 이전에 고친 시나리오를 재검증하지 않고 코드를 패치하도록 요청한다.

**설명**

이전 시나리오를 재검증하지 않고 보고된 실패를 하나씩 패치하는 것은, 팀이 이미 겪고 있는 회귀 순환 그 자체다. 모든 이전 케이스를 다시 확인하는 스위트가 없으면, 각 수정이 이전 수정을 무너뜨릴 수 있고, 지연 시간 요구사항은 전혀 검증되지 않는다.

**C(정답).** 구현 전에 예상되는 정규화 결과, 엣지 케이스, 지연 시간 목표에 대한 테스트를 작성하고, 실패한 테스트 출력을 공유하여 각 수정을 이끈다.

**설명**

테스트 주도 반복은 점진적 개선을 위한 신뢰할 수 있는 기법이다. 구현 전에 구축된 스위트는 예상 동작, 엣지 케이스, 성능 요구사항을 담아내고, 각 수정은 구체적인 실패 출력에 의해 이끌어진다. 전체 스위트가 매번 다시 실행되므로, 하나의 형식에 대한 수정이 이전에 처리된 케이스를 몰래 깨뜨릴 수 없다.

**D.** IMPORTANT 표시와 더 강한 강조를 사용해 정규화 규칙을 서술문으로 다시 작성하여, 모델이 모든 구현 시도에서 이를 일관되게 우선시하도록 한다.

**설명**

강조는 주변의 조용한 지시들에 비해 규칙의 우선순위를 높이지만, 결과로 나온 구현을 검증하거나 회귀를 잡아내지는 못한다. 강조된 서술 규칙이라도 각 수정 후에 엣지 케이스와 지연 시간 목표는 여전히 확인되지 않은 채로 남는다.

### 전반적인 설명

각 수정이 하나의 실패를 고치면서 다른 것을 깨뜨릴 때, 빠져 있는 것은 더 나은 문구의 규칙이 아니라 검증 하니스다. 이 상황에 맞는 기법은 테스트 주도 반복이다. 구현 전에, 예상 동작(대표적인 날짜 문자열과 그에 대한 ISO 8601 결과), 엣지 케이스(두 자리 연도, 모호한 일/월 순서, 누락된 구성 요소), 그리고 대용량 문서에 대한 지연 시간 목표와 같은 비기능적 요구사항을 담아내는 테스트 스위트를 구축한다. 그런 다음 실패한 테스트 출력을 Claude와 공유하며 반복하고, 각 수정을 전체 스위트를 기준으로 판단한다.

여기서의 사고 모델은, 서술문은 의도를 설명하지만 테스트는 완료를 정의한다는 것이다. 전체 스위트가 매 반복마다 실행되므로, 회귀는 나중에 새로운 버그 보고로 나타나는 대신 즉시 드러나며, 테스트로 표현된 성능 요구사항은 단순히 언급되는 것이 아니라 실제로 검증된다. 실패한 출력 그 자체가 고품질 피드백이다. 어떤 입력이 어떤 잘못된 결과를 낳았는지 모델에게 정확히 알려주며, 이는 서술문으로 된 불만보다 훨씬 실행 가능하다.

대안들은 각각 회귀 순환을 그대로 남겨둔다. 한 번에 하나의 실패를 보고하고 재검증 없이 패치하는 것은 이미 이러한 혼란을 일으키고 있는 안티패턴이며, 이전에 고친 케이스를 지켜주는 것이 아무것도 없다. IMPORTANT와 같은 강조 표시는 규칙의 우선순위를 높이는 데 주의 예산을 쓰지만, 그 결과로 나온 코드에 대해서는 아무것도 검증하지 않는다. 온도를 0으로 하면 반복 시도가 더 결정론적으로 되지만 그것이 정확해지는 것은 아니다. 결정론적인 구현도 매번 동일한 엣지 케이스에 실패할 수 있다.

Claude Code common workflows와 Prompt engineering overview를 참고하라.


## 질문 6

**SCENARIO** : You are building a structured data extraction system using Claude. **QUESTION** : A team's CI pipeline uses a Claude Code job to draft updates to their document extraction schemas, and they are now designing the review stage that runs before merge. How should the review stage obtain its findings?

**A.** Continue in the drafting session but prompt it with a strict reviewer persona to critique the diff line by line.

**설명**

페르소나 지침은 이미 오염된 컨텍스트 위에 얹힌 프롬프트 수준의 지시일 뿐이다. 세션은 여전히 그 변경을 만들어낸 논거를 그대로 지니고 있으므로, 페르소나와 무관하게 자신의 결정을 받아들이려는 경향이 그대로 남는다.

**B.** 초안 작성 세션에서 확장 사고(extended thinking)를 활성화한 채로 계속 진행하여, 발견 사항을 보고하기 전에 더 깊이 추론하게 한다.

**C(정답).** 변경을 초안 작성한 세션과는 별도로, 새로운 컨텍스트를 가진 깨끗한 Claude Code 인스턴스를 실행하여 diff를 검토하게 한다.

**설명**

이것이 정답인 이유는, 초안 작성 세션이 그 변경을 만들어낸 논거를 그대로 유지하고 있어서 자신의 결정 쪽으로 편향되기 때문이다. 새롭고 독립적인 인스턴스는 diff를 그 자체의 타당성만으로 평가하며, 원래 세션이 합리화해서 넘겨버릴 문제들을 잡아낸다.

**D.** /compact를 실행하여 요약된 이력이 더 이상 초안 작성 논거를 담고 있지 않게 한 뒤, 그 초안 작성 세션을 검토용으로 재개한다.

**설명**

압축(compaction)은 컨텍스트 공간을 확보하기 위해 이전 이력을 요약하지만, 그 요약본은 여전히 세션의 추론과 결정을 보존한다. 검토자는 여전히 자신의 선택에 고정되어 있으므로 편향은 그대로 남는다.

### 전반적인 설명

여기서의 사고 모델은 세션 컨텍스트 격리다. Claude Code 세션이 변경을 만들어내기 위해 한 모든 것, 즉 탐색, 고려했던 트레이드오프, 최종적으로 정착한 논거는 모두 그 컨텍스트에 남아 있다. 같은 세션에게 결과를 검토하라고 요청하면, 낯선 코드를 평가하는 것이 아니라 자신이 그 변경이 옳다고 확신하게 된 추론과 함께 변경 내용을 다시 읽는 셈이 된다. 이는 자신의 결정에 이의를 제기할 가능성을 체계적으로 낮추며, 눈에 띄게 관대한 검토를 만들어낸다. Anthropic이 문서화한 패턴은 별도의 작성 세션과 별도의 검토 세션을 두는 것이다. 새로운 컨텍스트는 자신이 방금 작성한 코드에 편향되어 있지 않으므로, diff에 대해 자기 자신의 기준을 그대로 적용할 수 있다.

오답들은 모두 컨텍스트를 제거하지 않은 채 컨텍스트 문제를 해결하려는 시도들이다. /compact는 대화 기록을 요약본으로 대체하지만, 그 요약본은 여전히 세션의 결정을 인코딩하고 있으므로 고정 효과는 압축을 거쳐도 살아남는다. 더 엄격한 검토자 페르소나는 창 안에 이미 누적된 논거와 경쟁하는 지시일 뿐이며, 톤을 바꿀 뿐 독립성을 바꾸지는 못한다. 확장 사고는 더 많은 추론 깊이를 제공하지만, 동일하게 고정된 컨텍스트 위에서의 더 많은 추론은 대개 원래 논거를 다시 도출해낼 뿐, 그 결함을 드러내지는 않는다. 독립성은 검토자가 얼마나 열심히 또는 얼마나 엄격하게 사고하는지가 아니라, 검토자의 컨텍스트에 무엇이 들어 있는지에 관한 속성이다.

실제로 이 원칙은 CI 설계를 이끈다. 검토 작업은 변경을 만들어낸 세션을 재사용하는 대신, diff에 대해 깨끗한 Claude Code 인스턴스를 호출해야 한다. 작성자/검토자 분리 패턴은 Claude Code Best Practices와 Common Workflows를 참고하라.

**설명**

사용자 수준 메모리도 모든 세션에 로드되므로, 그곳의 @path 참조 역시 픽스처 내용을 컨텍스트로 확장시킬 것이다. 게다가 이는 픽스처 문서를 공유되지 않게 만들어, 이를 필요로 하는 동료들에게 숨겨버린다.

**D.** 각 세션 시작 시 /compact를 실행하여 임포트된 픽스처 내용을 컨텍스트 윈도우에서 다시 요약해 낸다.

**설명**

압축은 대화 이력을 사후에 요약하며 세부 정보를 잃을 위험이 있다. @path 임포트가 실행 시점에 확장되는 것을 막지는 못한다. 픽스처는 매 세션마다 일단 로드된 다음, 손실이 있는 형태로 요약될 것이다.

### 전반적인 설명

CLAUDE.md에서 @path/to/file 문법은 파일 경로를 편하게 적는 방식이 아니라 임포트 지시문이다. 실행 시점에 Claude Code는 임포트된 각 파일을 컨텍스트에 인라인으로 확장하며, 임포트는 여러 단계까지 재귀적으로 이어질 수 있다. 이는 의도된 설계다. 팀이 표준을 별도 파일로 분리하면서도 자동으로 로드되도록 CLAUDE.md를 모듈화할 수 있게 해준다. 그 대가는, 맨 @ 접두사로 작성된 것은 의도했는지 여부와 무관하게 항상 로드되는 콘텐츠가 된다는 점이다.

목표가 단지 Claude에게 픽스처가 어디 있는지 알려주는 것뿐이라면, 문서화된 기법은 경로를 백틱으로 감싸는 것이다. 예를 들어 `@tests/fixtures/invoice.json`처럼 쓴다. 그러면 경로는 비활성 텍스트로 나타난다. Claude는 실제로 작업이 필요할 때 파일 도구로 그 파일을 필요 시점에 읽을 수 있으며, 모든 세션의 컨텍스트 예산에 픽스처 바이트가 소비되지 않는다.

다른 접근법들은 증상만 다룬다. 시작 이후에 압축하는 것은 원래 로드되지 않았어야 할 콘텐츠에서 세부 정보를 버리는 것이다. 목록을 사용자 수준 메모리로 옮기는 것은 파일을 여전히 임포트하면서(사용자 메모리도 모든 세션에 로드된다) 문서를 버전 관리에서 제외시켜 버린다. 픽스처를 줄이는 것은 잘못된 지시를 수용하기 위해 테스트 자산을 희생시키는 것이다. 가져가야 할 사고 모델은 다음과 같다. CLAUDE.md에서 @path는 "지금 이것을 로드하라"는 뜻이고, 백틱은 "이것은 그냥 이름이다"라는 뜻이다. Manage Claude's memory와 Claude Code best practices를 참고하라.

**QUESTION** : The team's /extract-record skill declares an argument-hint listing the expected document path and schema name. Engineers still occasionally pass a schema name that does not exist, and the extraction fails downstream. What is the correct fix?

**설명**

context: fork 옵션은 스킬의 상세한 출력을 메인 대화에서 격리시킨다. 실패가 발생하는지 여부가 아니라 실패가 어디서 발생하는지를 바꿀 뿐이며, 잘못된 스키마 이름은 여전히 추출 실패를 낳는다.

**설명**

allowed-tools 필드는 스킬이 실행 중에 호출할 수 있는 도구를 제한하는 것이며, 스킬에 전달되는 인자를 제약하거나 검증하지는 않는다. 잘못된 스키마 이름은 여전히 그대로 스킬에 흘러들어갈 것이다.

### 전반적인 설명

SKILL.md 프런트매터에 대해 유용한 사고 모델은, 필드를 두 계열로 나누는 것이다. 일부 필드는 스킬이 어떻게 발견되고 호출되는지를 형성하는 표시용 메타데이터다. description은 Claude에게 이 스킬이 언제 적용되는지 알려주고, argument-hint는 개발자에게 호출 시점에 스킬이 기대하는 인자를 보여준다. 다른 필드들은 스킬이 실행될 때 실제로 무엇이 일어나는지를 제약하는 실행 통제 장치다. allowed-tools는 스킬이 호출할 수 있는 도구를 제한하고, context: fork는 그 작업을 서브에이전트에서 격리한다. 표시 계열의 어떤 필드도 무언가를 강제하지 않으며, 실행 계열의 어떤 필드도 인자 값을 검증하지 않는다.

바로 이 때문에 여기서의 실패가 계속된다. argument-hint는 엔지니어가 올바른 인자를 제공할 가능성을 높여주지만, 실제로 입력된 내용을 결코 검사하지 않으므로, 그럴듯해 보이지만 존재하지 않는 스키마 이름이 그대로 통과된다. 인자 값의 검증은 동작이 정의되는 곳에 있어야 한다. 스킬에게 추출 전에 프로젝트에 등록된 스키마와 대조하여 스키마 이름을 검증하도록 지시하고, 일치하지 않으면 명확한 메시지와 함께 실패하도록 한다. 지침보다 더 강한 보장이 필요하다면, 같은 검사를 예를 들어 훅(hook)과 같은 코드로 실행할 수도 있지만, 핵심은 힌트가 게이트가 아니라는 점을 인식하는 것이다.

오답들은 각각 실제 프런트매터 필드를 문서화된 경계 너머로 무리하게 확장한 것이다. 힌트에 스키마를 나열하는 것은 여전히 아무것도 거부하지 않고, allowed-tools는 인자 내용이 아니라 도구 접근을 통제하며, context: fork는 실패를 막지 않고 단지 위치만 옮긴다. 프런트매터 참고 자료는 Agent Skills와 Slash commands를 참고하라.

**D.** 병합 전에 개발자가 Claude가 느슨하게 만든 어설션을 다시 조여주는 상시 수동 검토 단계를 추가한다.

**설명**

이는 증상을 사후에 잡아낼 뿐, 그 행동을 막는 대신 재작업을 제도화하는 것이다. 또한 루프 안의 모든 반복이 이미 약화된 스위트를 기준으로 실행되게 두므로, 검토가 이루어지기 전에 이미 중간 실패 피드백이 오염되어 있는 상태다.

### 전반적인 설명

테스트 주도 반복은 테스트가 움직이지 않는 목표일 때만 작동한다. 이 루프의 가치는 비대칭성에서 나온다. 스위트는 요구되는 동작을 인코딩하고, 구현만이 바뀔 수 있는 유일한 것이다. 장기간에 걸친 반복 작업에 대한 Anthropic의 가이드는, 구현 전에 테스트를 작성하고, 이를 구조적으로 추적하며, 테스트를 제거하거나 편집하는 것은 용납되지 않는다는 것을 Claude에게 명시적으로 상기시키라는 것이다. 이는 정확히, 통과하는 스위트를 최적화하려는 모델이 때로는 코드를 고치는 대신 어설션을 약화시키는 것과 같은 가장 짧은 경로를 택할 수 있기 때문이다. 이 제약을 명시적으로 만들면 그 우회 경로가 막히고, 실패가 실제로 해결되어야 할 곳인 추출 로직에서 해결되도록 강제된다.

기저의 사고 모델은, Claude Code가 실행할 수 있는 검증 검사에 대해 가장 잘 반복한다는 것이다. 스위트를 실행하고, 실패를 읽고, 코드를 조정하고, 반복한다. 오답들은 각각 이 루프를 다른 방식으로 손상시킨다. 구현으로부터 테스트를 다시 생성하는 것은 검사를 코드의 거울로 만들어버려, 결코 결함을 탐지할 수 없게 한다. 테스트를 CLAUDE.md의 서술문으로 대체하는 것은 실행 가능한 이진 신호를, 모델이 확률적으로 따르는 지침으로 바꿔버리며, 각 반복을 이끄는 실패 출력도 제거해버린다. 수동 재조임 단계는 순전히 사후 대응적이다. 약화되는 것을 막지 못하며, 자동화된 루프가 그동안 계속 오염된 목표를 기준으로 반복하고 있었다는 뜻이 된다.

테스트를 먼저 작성하고 장기 반복 중 테스트 편집을 금지하는 안내는 Prompt templates and variables를 참고하고, Claude에게 실행하고 반복할 수 있는 검증 검사를 주는 더 넓은 원칙은 Claude Code best practices를 참고하라.


## 질문 11

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : A stack trace shows the pipeline's date normalizer rejects two-digit years, and the fix is one added conditional in a single function. A teammate asks whether to enter plan mode in Claude Code before making this change. What do you advise?

**A.** Delegate to an Explore subagent to survey the codebase before touching the normalizer function.

**설명**

이는 틀렸다. Explore 서브에이전트는 크거나 낯선 코드베이스에서 여러 단계로 이루어진 작업 중 상세한 탐색 출력을 격리하기 위해 존재한다. 여기서는 스택 트레이스가 이미 결함을 하나의 함수로 특정해 놓았으므로, 격리할 탐색 단계 자체가 없다.

**B.** 검증 로직에 대한 어떤 수정이든 변경이 반영되기 전에 검토된 계획을 거쳐야 하므로, 먼저 플랜 모드로 들어간다.

**설명**

이는 틀렸다. 플랜 모드는 접근 방식이 불확실하거나, 여러 파일에 걸친 변경이거나, 낯선 코드일 때를 위한 것이며, 파일의 한 부류 전체에 무조건적으로 적용하는 것이 아니다. 원인이 알려진 한 줄짜리 조건문 추가는 계획 단계로부터 얻을 것이 없으며, 단지 수정을 느리게 만들 뿐이다.

**C.** 플랜 모드로 시작해서 계획을 즉시 승인하여, 수정이 여전히 검토 단계의 안전성을 물려받게 한다.

**설명**

이는 틀렸다. 실제로 검토하지 않고 계획을 승인하는 것은 실질적인 안전상의 이점을 전혀 제공하지 않으며, 사소한 변경에 형식적인 절차만 추가할 뿐이다. 검토 단계는 경쟁하는 접근 방식이나 평가해야 할 광범위한 영향이 있을 때 가치가 있는데, 한 줄짜리 조건문 수정에는 둘 다 해당하지 않는다.

**D(정답).** 변경 범위가 하나의 함수로 한정되어 있고 접근 방식이 이미 명확하므로, 직접 실행한다.

**설명**

이것이 정답인 이유는, 스택 트레이스로 식별된 하나의 함수에 단일 조건문을 추가하는 것처럼 범위가 명확하고 잘 이해된 작은 변경에는 직접 실행이 적절한 선택이기 때문이다. 이렇게 범위가 좁은 수정에서는 플랜 모드가 결과를 개선하지 못한 채 오버헤드만 더할 것이다.

### 전반적인 설명

플랜 모드와 직접 실행 중 무엇을 택할지의 결정은, 프로세스의 무게를 불확실성의 정도에 맞추는 문제다. 플랜 모드는 Claude Code를 읽기 전용 조사 태세로 만든다. 파일을 탐색하고 구현 계획을 제안하며, 계획이 승인되기 전까지 편집은 차단된다. 이는 접근 방식이 불확실하거나, 변경이 여러 파일에 걸쳐 있거나, 코드가 낯설 때 가치가 있다. 계획을 반복해서 다듬는 것이 잘못된 구현을 정리하는 것보다 훨씬 저렴하기 때문이다. Anthropic의 가이드는 계획을 세우는 데 오버헤드가 든다는 것과, 명확하고 범위가 작은 수정은 그냥 직접 하면 된다는 것을 명시적으로 밝히고 있다. 유용한 경험 법칙은, diff를 한 문장으로 설명할 수 있다면 계획을 생략해도 된다는 것이다.

이 상황에서는 진단이 이미 끝나 있다. 스택 트레이스가 함수를 지목하고, 실패 모드가 이해되어 있으며, 해결책은 조건문 하나다. 계획이 해소해줄 모호함이 전혀 없으므로, 직접 실행이 아무것도 희생하지 않으면서 더 빠르게 수정을 반영한다. 검증 코드는 항상 계획하라는 식의 일괄적인 규칙은 이 프레임워크를 잘못 적용하는 것이다. 계획을 세울지의 트리거는 불확실성과 범위의 넓이이지, 수정 대상이 되는 서브시스템이 아니기 때문이다. 계획을 읽지 않고 승인하는 것은 계획을 건너뛰는 것보다도 나쁘다. 비용은 그대로 유지하면서 이점은 버리는 셈이기 때문이다. 마찬가지로, Explore 서브에이전트는 긴 다단계 작업 중 상세한 탐색 출력을 메인 대화 밖에 두는 컨텍스트 문제를 해결하는 것인데, 결함이 이미 특정된 상황에서는 그런 문제 자체가 존재하지 않는다.

계획을 세울지 직접 실행할지에 대한 가이드는 Claude Code best practices를 참고하고, 계획이 승인되기 전 플랜 모드가 어떻게 동작하는지는 Permission modes를 참고하라.


## 질문 12

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : The extraction prompt includes two examples of cleanly formatted invoices, yet output still varies on invoices that omit a purchase order number or list multiple dates. Which two additions to the examples best improve consistency? (Select two.)

**A(정답).** Add an input/output pair where the source invoice omits the purchase order number and the expected output records that field as null.

**설명**

이것이 정답인 이유는, 예시가 실제로 동작이 갈리는 엣지 케이스를 다뤄야 하기 때문이다. 해당 필드가 없는 문서를, 그 필드가 null인 출력과 짝지어 보여주는 것은, 존재하지 않는 데이터를 스키마를 만족시키기 위해 조작해내는 대신 없는 상태 그대로 보고해야 한다는 것을 보여준다.

**B.** 올바르게 포맷된 출력 레코드 여러 개만 추가하고, 그 출처가 되는 원본 발췌는 생략하여 프롬프트를 더 짧게 유지한다.

**설명**

이는 틀렸다. 출력만 있는 샘플은 목표 형식은 보여주지만 변환 과정은 보여주지 못한다. 각 출력과 함께 원본 문서가 없으면, 모델은 누락되거나 상충하는 입력이 어떻게 기대되는 결과로 매핑되는지 배울 수 없다.

**C.** 깨끗하게 포맷된 송장에서 뽑아낸 예시 열 개를 더 추가하여 지배적인 추출 패턴을 강하게 강화한다.

**설명**

이는 틀렸다. 모델은 이미 깨끗한 송장은 잘 처리한다. 불일치는 필드 누락과 모호한 날짜에서 나타난다. 쉬운 케이스를 반복하는 것은 어려운 케이스를 어떻게 해결해야 하는지 보여주지 못한 채 토큰만 추가한다.

**D(정답).** 여러 날짜가 나열된 송장에 대한 입력/출력 예시 쌍을 추가하고, 출력에서 어떤 날짜를 추출해야 하는지 보여준다.

**설명**

이것이 정답인 이유는, 모호한 케이스가 바로 서술 규칙이 일관성 없이 해석되는 지점이기 때문이다. 실제로 모호한 입력이 어떻게 해소되는지를 보여주는 예시는 출력 형식뿐 아니라 판단의 경계선을 가르친다.

### 전반적인 설명

퓨샷 예시는 형식뿐 아니라 판단을 보여줌으로써 작동한다. 상세한 서술 규칙이 일관성 없는 추출을 낳을 때, 그 실패는 거의 항상 규칙이 충분히 규정하지 못하는 케이스에 집중되어 있다. 즉 원본에 단순히 없는 필드, 그리고 여러 후보 값이 한 필드를 그럴듯하게 채울 수 있는 입력이다. 해결책은 바로 그러한 판단 경계선 위에 있는 예시를 골라내는 것이다.

발주서 번호가 없는 문서를, 그 필드가 null인 출력과 짝지어 보여주는 예시는 누락된 데이터에 대한 올바른 대응이 그 부재를 그대로 보고하는 것임을 확립한다. 이는 스키마 검증 추출에서 특히 중요하다. 모든 필드를 채우도록 압박받는 모델은 값을 조작해낼 것이고, 만들어낸 발주서 번호가 담긴 문법적으로 유효한 JSON 객체는 스키마 검증은 통과하면서 하위 시스템을 조용히 오염시킨다. 여러 날짜가 있는 송장을 하나의 올바른 날짜로 해소하는 예시는, 입력이 모호할 때 어떤 값이 우선하는지를 가르치는데, 이는 출력 샘플만으로는 결코 전달할 수 없는 것이다.

오답들은 상호보완적인 이유로 실패한다. 모델이 이미 잘 처리하는 케이스의 예시를 더 쌓는 것은 애초에 문제가 아니었던 패턴을 강화하며, 커버리지 대신 중복에 컨텍스트를 소비한다. 출력만 있는 샘플은 결과의 형태는 전달하지만 입력에서 출력으로의 매핑을 끊어버린다. 모델은 올바른 레코드가 어떻게 생겼는지는 보지만, 그 옆에 어려운 원본 문서가 어떻게 생겼는지는 결코 보지 못하므로, 특히 누락과 충돌에 대한 변환 자체는 여전히 명시되지 않은 채로 남는다. 실제 실패 모드를 겨냥한 잘 선택된 입력/출력 예시 두세 개가, 이미 잘 작동하는 케이스를 겨냥한 수많은 예시보다 낫다.

효과적인 예시를 선택하는 방법에 대한 가이드는 Use examples (multishot prompting) to guide Claude's behavior를 참고하라.
