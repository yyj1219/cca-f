## 공통 기초

### LLM은 "텍스트를 이어 쓰는 기계"다

LLM(Large Language Model, 대규모 언어 모델)은 앞의 텍스트를 보고 그다음에 올 토큰(단어 조각)을 확률적으로 예측하는 모델입니다. Claude, GPT 같은 것들이 여기에 속합니다. 이 한 문장에서 이 노트 전체의 문제들이 파생됩니다.

1. **출력은 결정론적이지 않다.** 같은 입력을 두 번 줘도 다른 출력이 나올 수 있습니다. "세션마다 판단이 달라진다"는 현상, "형식을 지켜라"라고 시켰는데 가끔 어기는 현상이 여기서 나옵니다.
2. **모델은 "그럴듯한" 것을 생성하지 "참인" 것을 생성하지 않는다.** 입력에 없는 것을 억지로 만들면 그것이 환각(hallucination)입니다. 산술 오류, 자기 검토의 한계도 같은 뿌리입니다.
3. **"~하지 마라"는 지시는 물리적 보장이 아니다.** "JSON만 출력해"라고 말해도 모델은 그 확률을 높일 뿐, 어길 수 있습니다.
4. **모델은 프롬프트 안의 텍스트를 역할별로 구분해서 보지 않는다.** 지시문, 예시, 실제 입력이 전부 하나의 긴 텍스트일 뿐입니다. 우리가 구조로 구분해 주지 않으면 모델이 혼동합니다.
5. **모델은 자기 확신도를 객관적으로 계산하지 못한다.** 뒤에 나오는 "신뢰도 지시어가 잘 안 먹히는 이유"의 근본 원인입니다.

모델의 가중치는 학습되어 고정되어 있고, 우리가 바꿀 수 있는 것은 **입력뿐**입니다. 재학습 없이 입력 텍스트만 고쳐서 원하는 동작을 얻어내는 일 — 그것이 **프롬프트 엔지니어링(Prompt Engineering)** 입니다.

### 프롬프트의 구성

프롬프트(prompt)는 모델에게 주는 입력 텍스트 전체이고, 보통 두 부분으로 나뉩니다.

- **시스템 프롬프트(system prompt)**: 역할, 규칙, 정책 등 대화 전체에 걸쳐 유지되는 지시.
- **사용자 메시지(user message)**: 이번 요청의 구체적 내용(처리할 문서, 질문 등).

### 토큰과 컨텍스트 윈도우

모델은 글자를 그대로 보지 않고 **토큰(token)** 이라는 조각 단위로 봅니다. 영어 기준 대략 4글자 = 1토큰이고, 한국어는 글자당 토큰이 더 많이 듭니다. API 요금은 보통 "입력 토큰 수 + 출력 토큰 수"로 과금되고 속도도 토큰 개수에 비례하므로, "프롬프트를 길게 쓴다"는 것은 곧 "돈과 시간을 더 쓴다"는 뜻입니다.

**컨텍스트 윈도우(context window)** 는 모델이 한 번의 요청에서 볼 수 있는 **입력 + 출력 토큰 총량의 상한**입니다. 시스템 프롬프트 + 대화 이력 + 이번 입력 + 생성할 출력이 모두 이 창 안에 들어가야 합니다. 예를 들어 20만 토큰짜리 창이라면 프롬프트와 답변을 합쳐 20만 토큰을 넘길 수 없고, 300페이지 계약서를 통째로 넣으면 요청 자체가 거절됩니다. 해결책은 **청킹(chunking)** — 문서를 의미 단위로 잘라 여러 요청으로 나눠 처리하고 결과를 나중에 합치는 것입니다.

여기서 흔한 오해가 하나 있습니다.

> "컨텍스트 윈도우가 크니까 다 넣으면 되지 않나?"

**아닙니다.** 창에 들어간다는 것과 모델이 그 내용을 고르게 잘 활용한다는 것은 다른 문제입니다. 긴 컨텍스트에서 모델은 맨 앞과 맨 뒤의 정보는 잘 쓰지만 **중간에 위치한 정보는 놓치는 경향**이 있습니다. 어텐션(attention)이 긴 입력 전체에 고르게 분산되지 않기 때문이고, 이 현상을 **Lost in the Middle(중간 정보 소실)** 이라고 부릅니다. 그래서 컨텍스트를 무작정 채우면 비용 증가, 지연 시간(latency) 증가, 정확도 하락이 한꺼번에 일어납니다. 이것을 통틀어 **컨텍스트 과부하(context overload)** 라고 합니다.

### max_tokens와 컨텍스트 윈도우는 다르다 (아주 자주 헷갈림)

| 항목 | 뜻 | 무엇을 제한하나 |
|---|---|---|
| **컨텍스트 윈도우** | 모델이 한 번에 다룰 수 있는 전체 용량 | 입력 + 출력 **합계** |
| **max_tokens** | 요청 파라미터. "답변을 최대 몇 토큰까지 쓸지" | **출력(생성)만** |

즉 **입력 문서가 너무 길어서 생긴 문제를 `max_tokens`를 줄여서 고칠 수는 없습니다.** `max_tokens`를 줄이면 답변이 중간에 잘릴(truncation) 뿐, 입력이 짧아지지 않습니다.

- 입력이 길어서 생긴 문제 → 입력을 자른다(청킹).
- 답변이 중간에 끊겨서 생긴 문제 → `max_tokens`를 늘린다.

또 `max_tokens`를 키운다고 모델이 "더 깊이 생각"하지는 않습니다. 입력(프롬프트)의 품질이나 모델의 추론 능력·일반화 성능과는 아무 관계가 없고, 단지 더 길게 쓸 수 있게 될 뿐입니다.

```json
{
  "model": "claude-...",
  "max_tokens": 1024,
  "messages": [{"role": "user", "content": "..."}]
}
```

### API는 상태를 기억하지 않는다 (Stateless)

Messages API 같은 LLM API는 기본적으로 **무상태(stateless)** 입니다. 서버가 "아까 그 문서"를 기억하고 있지 않습니다.

- 대화가 이어지는 것처럼 보이는 이유는, 클라이언트가 **이전 메시지 전체를 매 요청마다 다시 보내기 때문**입니다.
- 그러므로 "아까 준 문서를 참고해서 고쳐줘"라고만 보내면, 그 문서를 다시 첨부하지 않는 한 모델은 문서를 볼 수 없습니다.
- 이 사실은 **자기 수정 재시도(self-correction retry)** 설계의 핵심 전제입니다(4장).

### 동기와 비동기

- **동기(synchronous) 호출**: 요청을 보내고 응답이 올 때까지 기다립니다. 보통 수 초 내 응답. 채팅처럼 사람이 기다리는 상황에 적합합니다.
- **비동기(asynchronous) 호출**: 요청을 큐에 넣어두고 나중에 결과를 찾아갑니다. 즉시성이 없는 대신 저렴하거나 대량 처리에 유리합니다.

**지연 시간(latency)** 은 요청부터 응답까지 걸리는 시간입니다. 실시간 사용자 경험에서 가장 중요한 지표입니다(5장).

### 이 분야가 다루는 문제: 정보 추출 파이프라인

기업에는 **비구조화 데이터(unstructured data)** 가 넘쳐납니다. 이메일, PDF 계약서, 이력서, 웹페이지, 고객 지원 티켓 같은 것들이죠. 사람이 읽으면 "아, 배송일은 3월 14일이구나" 하고 바로 알지만, 데이터베이스나 리포트 도구 같은 프로그램은 이런 자유 텍스트를 다룰 수 없습니다.

그래서 필요한 것이 **정보 추출(Information Extraction)** — 자유 텍스트를 넣으면 정해진 필드를 가진 JSON 같은 **구조화된 데이터(structured data)** 가 나오게 하는 것입니다.

```
[비구조화 입력]                  [LLM 추출]              [구조화 출력]
"안녕하세요, 귀하의 화물은   →   Claude + 스키마   →   {"ship_date": "03/14/2026",
 03/14/2026에 발송되었습니다"                            "carrier": "FedEx"}
```

실무에서 LLM은 혼자 쓰이지 않고 **파이프라인**의 한 부품으로 들어갑니다.

```
원본 문서(PDF/스캔본) → 전처리 → 프롬프트 조립 → LLM 호출
    → 출력 파싱 → 스키마 검증 → 비즈니스 규칙 검증 → 저장/전달
                              ↘ 실패 시 재시도(retry) 또는 사람에게 이관(escalation)
```

단계로 풀어 쓰면 보통 여섯 칸입니다.

1. **수집(Ingestion)** — 이메일/파일/티켓이 들어옴
2. **추출(Extraction)** — LLM이 스키마에 맞춰 필드를 뽑아냄
3. **검증(Validation)** — 결과가 스키마를 만족하는지 프로그램이 확인
4. **정규화(Normalization)** — 날짜, 통화, 단위 등 형식을 통일
5. **저장(Storage)** — 데이터베이스에 기록
6. **모니터링/피드백(Monitoring & Feedback)** — 잘 되고 있는지 지표로 추적

이 노트에서 다루는 개념들은 대부분 이 그림의 어느 칸에 속하느냐로 정리됩니다.

### 반복해서 등장하는 두 가지 시스템

- **문서 추출기(Document Extraction)** — 송장(invoice), 진료 기록, 고객 티켓 같은 자유 형식 텍스트를 받아 정해진 스키마의 JSON(`{"vendor": "...", "total": 1200, "currency": "USD"}`)을 내놓고, 그 JSON을 DB에 넣거나 재고·회계 시스템이 그대로 사용합니다.
- **자동 코드 검토기(Automated Code Reviewer)** — Pull Request의 diff(변경된 코드 조각)를 받아 "발견 사항(finding)" 목록을 내놓고, CI/CD 파이프라인이 그것을 받아 자동 수정하거나 사람에게 넘기거나 병합을 막습니다.

두 경우 모두 **LLM의 출력이 사람이 읽는 글이 아니라 다른 프로그램이 먹는 데이터**라는 점이 핵심입니다. 그래서 "형식이 항상 맞는가", "틀린 걸 맞다고 하지는 않는가", "얼마나 확신하는가"가 전부 중요해집니다.

### 네 갈래의 대응

- 예시로 모델을 가르치는 법 (Few-shot prompting) → 2장
- 출력 형태를 기계적으로 강제하는 법 (Tool use / JSON Schema / Structured Output) → 3·4장
- 프롬프트를 고쳤을 때 정말 좋아졌는지 재는 법 (Evaluation) → 6장
- 여러 에이전트를 조합해 시스템을 만드는 법 (Agent architecture) → 6장

## 전체를 관통하는 설계 원칙

### 먼저 던져야 할 네 가지 질문

**Q1. 이 실패의 원인은 어느 계층에 있는가?**
프롬프트 설계 / 모델의 우발적 실수 / 출력 구조 / 출력 의미 / 원본 데이터 / 시스템 아키텍처. 원인 계층과 다른 계층을 수정하면 절대 고쳐지지 않습니다.

**Q2. 지시로 충분한가, 예시가 필요한가?**
단순 사실 전달이면 지시. 다단계 절차나 경계선 판단이면 근거를 곁들인 예시.

**Q3. 이 검증은 구조를 보는가, 의미를 보는가?**
스키마는 구조만 봅니다. 의미는 별도의 교차 검증 규칙이 필요합니다.

**Q4. 재시도가 이걸 고칠 수 있는가?**
모델의 실수면 예. 원본의 부재나 모순이면 아니오 → 중단하고 사람에게.

### 설계 원칙

**프롬프트와 지시**

1. **모델에게 판단 기준을 떠넘기지 말고 명시하라.** 모호한 형용사는 오탐의 원천입니다. "확신하면 보고"는 아무 규칙도 주지 않습니다. 판단 기준은 신뢰도가 아니라 범주로 쓰십시오.
2. **경계는 구조로 표현하라.** XML 태그로 지시·예시·실제 입력을 구획하고, 반복 복사로 때우지 마십시오.
3. **형식은 설명보다 예시로 고정하라.** 모호한 판단 기준도 예시로, 흔들리는 출력 형식도 예시로 잡습니다. 엣지 케이스 예시와 대조 예시(paired examples)를 반드시 포함하고, 등급별로는 정의문 + 구체 예시를 고정 참조점으로 두십시오. 지시문을 늘리는 것은 대부분 답이 아닙니다.
4. **예시는 다양하게.** 예시 집합에 우연히 공통된 특징은 그대로 편향으로 학습됩니다.
5. **더 많이 넣는 것이 더 좋은 것이 아니다.** 예시도, 컨텍스트도, diff도 — 양이 늘면 비용·지연·부정확이 함께 늘어납니다. 선별과 분할이 답입니다.

**스키마와 검증**

6. **스키마는 원본 현실을 표현할 수 있어야 한다.** 없을 수 있는 값에는 "없음"의 자리를 만드십시오. 출구가 없으면 모델은 제약을 만족시키려고 거짓을 만들어냅니다(필수 필드 → 환각). 예상 밖의 값에는 `other` enum + 자유 텍스트 상세 필드를 둡니다.
7. **스키마는 느슨하게, 검증은 나중에 확실하게.** 엄격한 패턴을 스키마에 박으면 실패율만 올라갑니다. `description`은 지침이고 검증기가 판정자입니다 — 설명을 잘 쓴다고 검증 실패가 사라지지 않습니다.
8. **형태의 보장과 내용의 보장은 다르다.** 스키마가 통과했다고 값이 옳은 것은 아닙니다. 의미·산술·사실성은 애플리케이션 코드가 따로 검증해야 하고, 교차 검증으로 그럴듯한 오류를 잡되 값을 덮어쓰지 말고 플래그를 세우십시오.
9. **확률적 작업과 결정론적 작업을 분리하라.** 찾아오기(이해)는 모델, 형식 변환·계산·검증(정규화)은 코드. 반대로 분류처럼 규칙으로 짜기 어려운 것은 정규표현식이 아니라 모델의 이해에 맡길 수 있습니다.
10. **모니터링을 염두에 두고 스키마를 설계하라.** 나중에 통계로 분석할 축이 있다면 그 축을 범주형 필드(`detected_pattern` 등)로 저장하고, 지표로 규칙을 튜닝하십시오.

**보장과 재시도**

11. **부탁(soft)이 아니라 구조(hard)로 보장하라.** 자연어 지시 대신 `input_schema` + `tool_use`, 필요하면 strict. "하지 마"라고 부탁하는 대신 도구를 주지 않습니다. 감으로 판단하는 대신 held-out 세트로 측정합니다.
12. **도구 호출을 반드시 받아야 하면 `tool_choice`를 `any` 또는 특정 도구로 강제하라.** `auto`는 텍스트로 샐 수 있습니다. 다만 강제 호출은 사전 자연어 텍스트를 억제하고, 확장 사고(Extended Thinking)와는 양립하지 않으니 둘을 함께 쓰려면 `auto`로 내려야 합니다.
13. **모델은 없는 정보를 만들 수 없다.** 재시도로 고칠 수 있는 실패와 없는 실패를 구분하십시오. 형식 오류는 피드백을 붙여 재시도하고, 의미 오류에만 사람을 부릅니다.
14. **재시도에는 원본 + 이전 실패 출력 + 구체적 지적을 모두 담아라.** API는 기억하지 않습니다.
15. **모호할 때는 추측하지 말고 드러내라.** 충돌 플래그를 세우고 사람에게 넘기는 것이 조용히 하나를 고르는 것보다 항상 낫습니다. 자동 수정은 confidence 태그를 기준으로 고신뢰만 하고, 나머지는 사람에게 라우팅합니다.

**아키텍처와 운영**

16. **생성 호출과 검증 호출을 분리하라(chaining).** 정밀도를 더 올려야 할 때의 표준 수단입니다. 같은 세션에서 반성시키는 대신 독립된 인스턴스를 띄우고, 검토자에게는 요약본이 아니라 **원본**을 넘기십시오.
17. **서브에이전트는 깨끗한 컨텍스트에서 시작한다.** 컨텍스트는 자동으로 전달되지 않으므로 필요한 것은 프롬프트로 명시하거나 스스로 읽게 하십시오. 독립 검토는 깨끗한 컨텍스트에서만 가능하고, 재개된 세션은 편향을 그대로 물려받습니다.
18. **규모가 커지면 대화가 아니라 코드로 오케스트레이션하라.**
19. **지연 시간 요구에 맞는 API를 골라라.** 응답을 실시간으로 기다리면 동기 Messages API, 아니면 Batches(50% 할인, 24시간 목표, 배치당 10만 건/256MB). 싸다고 실시간에 배치를 쓰지 마십시오. 배치는 왕복이 없는 단방향 처리라 에이전트 도구 루프를 담을 수 없습니다.
20. **약속은 관측된 평균이 아니라 보장된 상한선 위에 세워라.** 배치 SLA = 제출 주기 + 최대 처리 시간.
21. **가장 시끄러운 카테고리가 전체 신뢰도를 결정한다.** 신뢰는 카테고리 단위가 아니라 도구 단위로 무너지므로, 노이즈가 심한 카테고리는 규칙을 삭제하지 말고 **즉시 비활성화**한 뒤 따로 개선하십시오.

### 공통 안티패턴

- 증상을 숨기기 (검증 필드 삭제, 어려운 입력 거부)
- 근본 원인과 무관한 파라미터 만지기 (`max_tokens`, 컨텍스트 크기, 메시지 위치)
- 같은 접근을 더 세게 / 더 여러 번 반복하기
- 데이터 해상도를 편의를 위해 버리기
