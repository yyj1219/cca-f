# 사전 학습 노트: 컨텍스트 관리와 신뢰성 (Context Management & Reliability)

이 문서는 이 주제를 전혀 모르는 상태에서 시작하는 학습자를 위한 개념 정리입니다.
LLM(대규모 언어 모델) 기반 에이전트 시스템을 "안정적으로" 만들기 위해 알아야 하는
개념들을 밑바닥부터 설명합니다.

---

## 0. 먼저: 이 분야가 다루는 세계

### 0.1 LLM과 컨텍스트 윈도우

LLM(Large Language Model, 대규모 언어 모델)은 텍스트를 입력받아 다음에 올 텍스트를
예측하는 모델입니다. 모델이 한 번에 "볼 수 있는" 텍스트의 총량에는 물리적 한계가 있고,
이 한계를 **컨텍스트 윈도우(context window)** 라고 부릅니다. 단위는 **토큰(token)** 입니다.
토큰은 대략 단어 조각 하나 정도의 크기이며, 영어 기준 1토큰 ≈ 4글자 정도입니다.

핵심 성질 세 가지:

1. **컨텍스트 안에 없는 것은 모델에게 존재하지 않는다.** 모델은 "기억"하지 않습니다.
   매 요청마다 전달된 텍스트만 봅니다.
2. **컨텍스트는 유한하다.** 대화가 길어지면 한계에 도달하고, 초과하면
   요청 자체가 실패하거나(Context Window Exceeded) 오래된 내용이 잘려나갑니다.
3. **길수록 비싸고 느리다.** 토큰 수에 비례해 비용과 지연시간이 증가합니다.

### 0.2 에이전트와 멀티 에이전트

**에이전트(agent)** 는 LLM이 도구(파일 읽기, API 호출, 검색 등)를 사용하면서
목표를 향해 여러 단계를 스스로 수행하는 시스템입니다.

**멀티 에이전트(multi-agent)** 구조에서는 역할이 나뉩니다.

- **코디네이터(coordinator) / 오케스트레이터(orchestrator) / 메인 에이전트**:
  전체 작업을 계획하고, 하위 작업을 나눠주고, 결과를 종합(synthesis)합니다.
- **서브에이전트(subagent)**: 코디네이터가 시킨 좁은 범위의 작업을 수행하고
  결과를 되돌려 보고합니다. 자기만의 독립된 컨텍스트를 가집니다.

이 구조가 존재하는 이유는 단 하나입니다. **컨텍스트 예산을 아끼기 위해서**입니다.
서브에이전트가 파일 50개를 읽어도, 코디네이터에게는 요약 10줄만 돌아옵니다.
50개 파일 원문이 코디네이터 컨텍스트를 오염시키지 않습니다.

## 1. 오류 처리: "실패"와 "빈 결과"는 다르다

에이전트 시스템 신뢰성의 가장 기본적인 구분입니다.

### 1.1 두 가지 결과 유형

| 유형 | 의미 | 예시 | 재시도? |
|---|---|---|---|
| **접근 실패 (Access Failure)** | 시스템이 질문에 **답을 못 했다** | 타임아웃, 연결 거부, DB 오프라인, 500 에러, 429 | 예 (재시도 가능) |
| **유효한 빈 결과 (Valid Empty Result)** | 시스템이 정상 동작해서 **"없다"고 답했다** | HTTP 200 + 결과 0건, 빈 배열 `[]` | 아니오 |

이 둘을 헷갈리면 두 방향 모두에서 사고가 납니다.

- **빈 결과를 실패로 취급하면**: 정상적으로 "없음"을 확인했는데도 계속 재시도합니다.
  API 호출 낭비, 응답 지연, 불필요한 오류 알람이 발생합니다.
- **실패를 빈 결과로 취급하면**: 훨씬 위험합니다. 실제로는 데이터가 **존재하는데**
  타임아웃 때문에 못 받은 것을, 시스템이 "데이터 없음"으로 확정해 버립니다.
  잘못된 결론이 아래 단계로 조용히 전파되는 **데이터 손실(silent data loss)** 입니다.

### 1.2 판별 기준

"응답이 왔는가?"가 아니라 **"조회 작업 자체가 성공적으로 완료되었는가?"** 를 봅니다.

```
질의 실행 → 서버가 정상 응답(2xx) → 결과 0건  → 유효한 빈 결과
질의 실행 → 타임아웃 / 연결 실패 / 5xx / 429   → 접근 실패 (재시도 대상)
```

구체적 사례:
- 단종된 SKU를 카탈로그에서 조회 → 200 OK, 0행. **정상적인 "그런 상품 없음"** 입니다.
- 신규 지원 언어의 용어집을 조회 → 조회 성공, 매칭 용어 0건.
  신규 언어이므로 **예상된 정상 결과**입니다.
- 같은 용어 DB가 **오프라인**이라서 응답 없음 → 인프라 장애, **재시도 가능한 접근 실패**입니다.

### 1.3 HTTP 상태 코드 기초

- **200 OK**: 요청 성공. 본문(body)이 비어 있어도 요청 자체는 성공입니다.
- **429 Too Many Requests**: 속도 제한(rate limit). 너무 많이 요청해서 서버가 잠시 거부.
  일시적이므로 **재시도 가능**합니다.
- **5xx**: 서버 측 오류. 일반적으로 재시도 가능.
- **4xx (429 제외)**: 요청 자체가 잘못됨. 대체로 재시도해도 의미 없습니다.
- **타임아웃**: 상태 코드조차 못 받은 상태. 서버가 처리 중일 수도, 죽었을 수도 있습니다.
  일시적 장애로 보고 재시도 대상입니다.

## 2. 재시도, 백오프, 에스컬레이션

### 2.1 지수 백오프 (Exponential Backoff)

일시적 장애에 대응하는 표준 재시도 전략입니다. 재시도 간격을 지수적으로 늘립니다.

```
1차 실패 → 1초 대기 → 재시도
2차 실패 → 2초 대기 → 재시도
3차 실패 → 4초 대기 → 재시도
...
```

왜 간격을 늘리는가? 서버가 이미 과부하 상태(429)인데 즉시 재시도를 퍼부으면
장애를 더 악화시킵니다. 간격을 벌려 서버가 회복할 시간을 줍니다.
실무에서는 **지터(jitter)**, 즉 간격에 약간의 무작위성을 더해
여러 클라이언트가 동시에 재시도하는 현상(thundering herd)을 방지합니다.

의사코드:

```python
delay = 1.0
for attempt in range(MAX_RETRIES):      # 반드시 상한이 있어야 한다
    result = call_api()
    if result.ok:
        return result
    if not is_retryable(result):        # 400, 404 등은 즉시 포기
        return result
    sleep(delay + random.uniform(0, 0.5))
    delay *= 2
# 상한 소진 → 재시도로 해결 못 함 → 에스컬레이션
return escalate(failure_type=result.error, attempted=..., partial=...)
```

### 2.2 재시도 상한이 반드시 필요한 이유

"429는 언젠가는 풀리니 무한히 재시도하면 된다"는 생각은 위험합니다.

- 워크플로우 전체가 무한 대기(hang) 상태에 빠집니다.
- 스레드, 커넥션, 토큰 예산 등 시스템 자원이 고갈됩니다.
- 진짜 문제(예: API 키 쿼터 소진, 계약 만료)는 재시도로 절대 해결되지 않습니다.

### 2.3 에스컬레이션 (Escalation)

**정의**: 자기 수준에서 해결할 수 없는 문제를 상위 결정권자에게 **정보와 함께** 넘기는 것.

서브에이전트가 로컬 재시도 예산(예: 지수 백오프 2회)을 다 쓰고도 실패했다면,
더 재시도하는 것은 의미가 없습니다. 이때 코디네이터로 에스컬레이션합니다.

**에스컬레이션 시 반드시 포함해야 하는 정보:**

1. **실패 유형(failure type)**: "429 rate limit", "timeout", "tool crash" 등 구체적으로.
2. **시도한 작업(attempted queries)**: 어떤 질의를 어떤 파라미터로 했는지.
3. **부분 결과(partial results)**: 실패 전까지 이미 얻은 것.
4. **미처리 범위(unprocessed scope)**: 아직 못 한 부분이 무엇인지.
5. (가능하면) **제안 대안(suggested alternatives)**: 다른 인덱스, 캐시된 데이터 등.

이 정보가 있어야 코디네이터가 판단할 수 있습니다. 다른 경로로 우회할지,
나중에 재시도할지, 부분 결과로 진행할지, 사람을 부를지.

**하지 말아야 할 대응들:**

- **전체 워크플로우 즉시 실패**: 서브에이전트 하나의 실패로 정상 처리 가능한
  나머지 작업(예: 배치의 다른 티켓들)까지 죽이는 것은 과잉 대응입니다.
  실패는 **격리(isolation)** 되어야 합니다.
- **실패를 성공으로 위장**: 조회 실패인데 빈 결과를 반환하고 티켓을 "해결됨"으로
  표시하는 것은 데이터 오염이자 거짓 보고입니다.

### 2.4 부분 진행 결과 보고 (Partial Progress Reporting)

도구가 작업 도중 크래시했다면, 이미 얻은 결과는 **버리지 않고** 실패 정보와 함께 보고합니다.

예: 보안 스캐너가 파일 40개 중 15개를 처리하고 취약점 2건을 찾은 뒤 크래시한 경우.

올바른 보고:

```json
{
  "status": "partial_failure",
  "failure_type": "static_analyzer_crash",
  "findings": [
    {"file": "auth/session.py", "severity": "high", "issue": "..."},
    {"file": "api/upload.py",   "severity": "medium", "issue": "..."}
  ],
  "files_scanned":   ["auth/session.py", "api/upload.py", "..."],
  "files_unscanned": ["billing/charge.py", "..."]
}
```

- 아무것도 안 보내면(재시작될 때까지 침묵) 이미 찾은 취약점 2건이 낭비되고
  코디네이터는 무엇이 일어났는지 알 수 없습니다.
- 취약점 2건만 "완전한 최종 결과"로 보내면, 스캔되지 않은 파일이 **안전한 것처럼**
  잘못 인식됩니다. 이것이 가장 위험합니다.
- 일반 실패 통보만 보내면 이미 확보한 진단 정보가 버려집니다.

원칙: **가진 것을 주고, 못 가진 것을 명시한다.**

## 3. 구조화된 출력 계약 (Output Contract / Schema)

### 3.1 출력 계약이란

서브에이전트가 코디네이터에게 결과를 돌려줄 때 지켜야 하는 **형식 약속**입니다.
JSON Schema 등으로 필드 이름, 타입, 필수 여부(`required`)를 명시합니다.

### 3.2 왜 단순 문자열 상태로는 부족한가

두 스키마를 비교해 봅시다.

**빈약한 스키마:**
```json
{ "status": "error" }
```

**풍부한 스키마 (Rich Error Reporting):**
```json
{
  "status": "error",
  "failure_type": "rate_limited_429",
  "attempted_query": "vector_search(index='kb-prod', q='refund policy')",
  "partial_results": [ { "doc_id": "POL-118", "score": 0.81 } ],
  "suggested_alternatives": ["keyword_search fallback", "retry after 60s"]
}
```

8개 서브에이전트 중 3개가 **서로 다른 이유로** 실패한 상황을 상상해 보세요.
빈약한 스키마에서는 세 개 모두 `"error"` 입니다. 코디네이터는 아무 판단도 할 수 없습니다.
재시도해야 할지, 다른 도구를 써야 할지, 그냥 진행해도 되는지 구분이 불가능합니다.

풍부한 스키마에서는 각 실패의 원인과 부분 진행 상황을 보고 **실패마다 다르게**
대응할 수 있습니다. 하나는 재시도, 하나는 대체 경로, 하나는 부분 결과로 진행.

**중요한 뉘앙스**: 구조화된 객체가 좋은 이유는 "구조화되었기 때문"이 아닙니다.
**그 안에 진단과 의사결정에 필요한 정보가 담겨 있기 때문**입니다.
필드만 많고 내용이 없는 객체는 문자열과 다를 바 없습니다.

또한 "에러 메시지를 단순화하면 서브에이전트가 알아서 해결하게 된다"는 것은
성립하지 않습니다. 보고 형식을 줄인다고 해결 능력이 생기지 않으며,
상위 전달 시 정보만 사라집니다.

### 3.3 필수 메타데이터 필드: 수치에는 시점을 붙인다

여러 서브에이전트의 결과를 코디네이터가 병합(merge)할 때, 값 자체만으로는
모순을 해석할 수 없는 경우가 많습니다.

예: 서브에이전트 A가 "해수면 상승 3.2mm/년", 서브에이전트 B가 "4.1mm/년"을 보고했습니다.
이것은 학계의 **실제 이견**일까요, 아니면 두 연구의 **측정 시기 차이**일까요?
출판 연도가 없으면 판단할 수 없습니다.

해결책은 스키마 수준의 수정입니다. 모든 추출된 수치 옆에
**출판일 또는 데이터 수집 시점**을 필수 필드로 요구합니다.

```json
{
  "type": "object",
  "required": ["figure", "unit", "source", "publication_date"],
  "properties": {
    "figure":           { "type": "number" },
    "unit":             { "type": "string" },
    "source":           { "type": "string" },
    "publication_date": { "type": "string", "format": "date" }
  }
}
```

일반 원칙: **어떤 사실을 다른 사실과 비교하거나 병합할 계획이라면,
비교에 필요한 메타데이터를 처음부터 필수 필드로 강제한다.**
(단어 수, 자금 출처 같은 필드는 이 특정 모호성을 해소하지 못합니다.
스키마에 필드를 추가할 때는 "이 필드가 실제로 어떤 판단을 가능하게 하는가"를 물어야 합니다.
또한 모델에게 "값이 그 뒤로 어떻게 변했을지 추측하라"고 요구하는 것은
사실 대신 환각을 필수 필드로 만드는 일입니다.)

### 3.4 여러 이슈를 하나의 서술로 관리하지 않기

한 대화 세션에서 서로 다른 성격의 이슈가 동시에 진행되는 경우가 흔합니다.
예: 청구 분쟁(송장 #4821, $89.00 초과 청구)과 서비스 장애(오후 2:15 시작).

이것을 한 문장의 줄글 요약으로 관리하면 "the amount(그 금액)", "the time(그 시각)"
같은 표현이 **어느 이슈를 가리키는지 모호해집니다**. 이것을 참조 모호성이라고 합니다.

라벨을 붙이는 것("billing: $89.00", "outage: 2:15pm")은 완화책일 뿐이며,
여전히 하나의 텍스트 덩어리 안에서 관리됩니다.

올바른 방식은 **이슈별로 독립된 구조화 레코드를 유지**하는 것입니다.

```json
{
  "issues": [
    { "type": "billing_dispute",
      "invoice_number": "4821",
      "disputed_amount": 89.00,
      "status": "open" },
    { "type": "service_outage",
      "start_time": "2025-03-04T14:15:00Z",
      "status": "investigating" }
  ]
}
```

각 이슈 타입은 자기만의 필드 집합(스키마)을 갖습니다. 청구 분쟁에는 송장 번호와 금액,
장애에는 시작 시각과 상태. 이러면 어떤 값이 어느 이슈에 속하는지 구조적으로 확정됩니다.

또한 새 이슈가 등장했다고 이전 이슈를 자동으로 "해결됨" 처리하거나,
고객에게 "한 번에 하나씩만 말해달라"고 요구하는 것은 문제 해결이 아닙니다.
시스템이 여러 이슈를 동시에 추적할 수 있어야 합니다.

## 4. 데이터 형식과 표현 형식의 정합성

### 4.1 데이터 성격에 맞는 서식 선택

에이전트가 최종 보고서를 만들 때, **정보의 성격에 따라 서식을 다르게** 해야
가독성과 전달력이 올라갑니다.

| 정보 성격 | 예시 | 적합한 형식 |
|---|---|---|
| 정량적, 열거 가능, 반복 구조 | API 메서드/파라미터/반환값, 설정 항목, 벤치마크 수치 | 구조화된 목록 또는 표 |
| 정성적, 서사적, 맥락 의존 | 커뮤니티 여론, 정성 평가, 배경 설명 | 줄글(narrative prose) |

API 명세를 줄글로 풀어쓰면 독자가 메서드 이름과 파라미터를 문장 속에서 찾아내야 합니다.
반대로 여론 요약을 "메서드/파라미터" 표에 억지로 밀어 넣으면 뉘앙스가 파괴됩니다.

**두 성격의 정보를 하나의 공통 표에 강제로 합치거나, 하나의 문단으로 병합해서
"통일된 서사"를 만드는 것은 개선이 아닙니다.** 각각을 자기에게 맞는 형식으로 유지한 채
같은 보고서 안에 배치하는 것이 올바른 구조입니다.

## 5. 컨텍스트 관리

### 5.1 컨텍스트 열화 (Context Degradation)

몇 시간짜리 긴 세션에서 자주 관찰되는 현상입니다.

1. 세션 초반, 서브에이전트가 "이 서비스는 예외(exception) 대신 커스텀 `Result` 타입을 쓴다"는
   구체적 사실을 발견하고 보고합니다.
2. 세션이 계속되며 대화가 누적됩니다.
3. 세션 후반, 같은 질문을 하면 에이전트가 "일반적으로 try/catch와 로깅을 씁니다"라고
   **일반론**으로 답합니다. 이전 발견과 모순됩니다.

**원인**: 초기 발견 내용이 활성 컨텍스트 밖으로 밀려났거나(잘림), 압축 과정에서 생략되었습니다.
모델은 근거를 잃자 학습된 일반적 패턴으로 빈칸을 채웁니다. 이것이 **환각(hallucination)** 입니다.

이것은 권한 문제도, 애플리케이션 고장도, 네트워크 문제도 아닙니다.
컨텍스트 윈도우의 유한성에서 나오는 **구조적이고 정상적인** 현상입니다.
따라서 해결책도 재시작이 아니라 **설계**입니다.

### 5.2 압축 (Compaction / Summarization)

**정의**: 길어진 대화 이력을 모델이 요약하여 짧은 텍스트로 대체하고,
토큰 공간을 회수하는 기법입니다.

**장점**: 컨텍스트 초과를 막고 비용을 줄입니다.
**한계**: 요약은 본질적으로 **손실 압축(lossy)** 입니다.
세부 사항, 정확한 리터럴 값(설정값, 변수명, 버전 번호, 파일 경로, 에러 코드)은
"덜 중요해 보이면" 생략될 수 있습니다. **압축이 모든 사실을 보존한다는 보장은 없습니다.**

### 5.3 스크래치패드 (Scratchpad)

**정의**: 에이전트가 중요한 사실을 기록해 두는 **외부의 영속적 저장소**.
보통 대화 밖의 파일입니다 (`notes.md`, `findings.json` 등).

**왜 존재하는가**: 컨텍스트는 휘발성이지만 파일은 영속적입니다.
컨텍스트에서 밀려나거나 압축으로 사라져도, 파일은 남아 있고 필요할 때 다시 읽을 수 있습니다.

**핵심 순서 — 이것이 이 주제의 가장 중요한 실무 패턴입니다:**

```
1. 잃으면 안 되는 정확한 사실을 스크래치패드 파일에 먼저 기록한다
2. 그 다음에 대화를 압축하여 공간을 회수한다
```

순서가 뒤바뀌면 안 됩니다. 아무것도 기록하지 않고 먼저 압축하면
그 시점에 정보가 이미 사라져 복구할 수 없습니다.

**대안들이 왜 나쁜가:**
- 세션을 삭제하고 빈 세션에서 시작 → 탐색으로 알아낸 것을 전부 잃습니다. 최악입니다.
- 압축을 아예 회피하고 무한 누적 → 컨텍스트 한계 도달, 비용 증가, 성능 저하,
  결국 Context Window Exceeded 오류.

**스크래치패드에 기록해야 할 것**: 정확한 설정값, 파일 경로와 줄 번호, 함수 시그니처,
발견한 아키텍처 사실, 결정 사항과 그 이유, 미해결 질문.

예:

```markdown
## 발견 사실 (2025-03-04 탐색)
- billing service는 예외 대신 커스텀 `Result<T, E>` 타입 사용
  - 정의: src/billing/result.py:14
- 재시도 상한: config/billing.yaml 의 `max_retries: 3`
- 결제 게이트웨이 타임아웃: 8000ms (config/gateway.yaml:22)
```

이 기록이 있으면 압축 후에도, 세션 후반에도, 심지어 다음 세션에서도
파일을 다시 읽어 **사실에 근거한(grounded)** 답변을 유지할 수 있습니다.

## 6. 서브에이전트 위임 (Delegation)

### 6.1 위임하는 이유

메인 에이전트가 세 개 서비스의 파일을 전부 직접 열어 읽으면,
그 모든 원문이 메인 컨텍스트에 쌓입니다. 결과적으로 메인 에이전트는
정작 중요한 일(재설계 제안 종합)을 할 컨텍스트 공간과 집중력을 잃습니다.

서브에이전트에 위임하면 탐색의 **원문은 서브에이전트 컨텍스트에서 소비되고**,
메인 에이전트에는 **정제된 요약(distilled summary)** 만 돌아옵니다.

### 6.2 좋은 위임 프롬프트의 조건

1. **범위가 명확할 것 (bounded)**: 무엇을 조사할지, 어디를 볼지 구체적으로.
2. **목적이 명시될 것**: 왜 필요한지 알면 관련성 판단이 정확해집니다.
3. **요약 반환을 지시할 것**: 원문 전량 반환을 금지합니다.

좋은 예:

> "payments, ledger, notifications 세 서비스에 걸친 환불 흐름의 의존 관계를 추적하고,
> 발견한 내용을 요약해서 보고하라."

나쁜 예와 그 이유:

- "코드베이스를 좀 둘러보고 흥미로운 걸 아무거나 보고해라"
  → 범위가 없어 서브에이전트가 무관한 곳을 헤매고 토큰만 소모합니다.
- "아무 지시도 주지 않고 git status만 보고 목표를 추론하게 한다"
  → 목표 추측은 실패 확률이 높습니다.
- "조사 중에 연 모든 파일의 전체 내용을 요약 없이 그대로 보고해라"
  → 위임의 목적 자체를 파괴합니다. 원문이 그대로 메인 컨텍스트로 쏟아지면
     직접 읽은 것과 똑같아지고, 전달 비용만 추가됩니다.

### 6.3 위임하지 말아야 할 때 — 조정 오버헤드

위임은 공짜가 아닙니다. **조정 오버헤드(coordination overhead)** 가 있습니다.

- 서브에이전트 생성(spawn) 비용
- 프롬프트와 필요한 컨텍스트를 전달하는 토큰 비용
- 결과를 되받아 해석하는 비용
- 왕복으로 인한 지연 시간

**판단 기준:**

| 상황 | 선택 |
|---|---|
| 범위가 넓고, 여러 파일/서비스를 훑어야 하고, 원문이 많이 발생 | 위임 |
| 작고 목표가 명확한 단일 조회/수정 (예: 작은 모듈 안의 함수 하나 찾아 고치기) | 메인 에이전트가 직접 수행 |

작은 작업까지 무조건 위임하면 오버헤드가 작업 자체보다 커집니다.
반대로 "모든 직접 도구 사용을 금지하고 무조건 위임"하는 정책도 비효율적입니다.
또 같은 작업을 여러 서브에이전트에게 중복 실행시켜 교차 검증하는 것은
확실성이 필요한 특수한 경우가 아니면 낭비입니다.

원칙: **위임은 도구이지 규칙이 아니다. 컨텍스트 절약 이득이 조정 비용보다 클 때만 쓴다.**

## 7. 상태 영속성과 재개 가능성

### 7.1 왜 필요한가

수 시간짜리 멀티 에이전트 작업은 도중에 죽을 수 있습니다.
프로세스 크래시, OOM, 인프라 장애, 네트워크 단절, 배포로 인한 재시작 등.

상태를 아무 데도 저장하지 않았다면 지금까지의 모든 작업이 사라집니다.
LLM 호출은 비싸므로 재실행 비용이 실제 금액으로 나타납니다.

### 7.2 체크포인팅과 매니페스트

**체크포인팅(checkpointing)**: 각 에이전트가 진행 상황과 결과를
디스크나 외부 저장소에 **진행하면서 지속적으로** 기록하는 것.

**매니페스트(manifest)**: 어떤 에이전트가 어떤 상태이고 결과물이 어디에 있는지를
정리한 색인 파일.

```json
{
  "run_id": "explore-2025-03-04",
  "agents": [
    { "id": "a1", "task": "payments 서비스 탐색",  "status": "completed",
      "output": "out/a1-payments.json" },
    { "id": "a2", "task": "ledger 서비스 탐색",    "status": "completed",
      "output": "out/a2-ledger.json" },
    { "id": "a3", "task": "notifications 탐색",    "status": "completed",
      "output": "out/a3-notify.json" },
    { "id": "a4", "task": "auth 서비스 탐색",      "status": "pending" },
    { "id": "a5", "task": "webhook 처리 탐색",     "status": "pending" }
  ]
}
```

### 7.3 재개(resume) 절차

코디네이터가 크래시 후 재시작되면:

1. 매니페스트를 읽어 각 에이전트의 상태를 파악합니다.
2. `completed` 인 에이전트는 **다시 실행하지 않습니다.**
3. 완료된 에이전트의 결과 파일을 로드하여, 남은 에이전트의 프롬프트에
   기존 발견 사항으로 **주입(inject)** 합니다.
4. `pending` 인 작업만 실행합니다.

**잘못된 대응들:**
- 완료된 결과물을 버리고 5개 전부 처음부터 재실행 → 비용과 시간 낭비.
- 완료된 결과를 버리고 사용자에게 "기억나는 대로 말해달라"고 요청 → 파일에
  이미 정확히 저장되어 있는데 인간의 기억에 의존하는 퇴행입니다.
- 크래시된 에이전트가 스스로 살아나기를 무한정 기다림 → 아무 일도 일어나지 않습니다.
- 각 에이전트가 상태를 자기 메모리에만 보관하고 아무것도 파일로 쓰지 않음
  → 애초에 복구가 불가능해집니다. 이것이 근본 원인입니다.
- 대화 이력이 컨텍스트에 영원히 남아 있으리라 가정 → 5.1의 컨텍스트 열화로 실패합니다.

원칙: **재개 가능성은 사후 대응이 아니라 사전 설계다.**
크래시가 나기 전에 상태를 파일에 써 두었어야만 복구가 가능합니다.

## 8. LLM API의 무상태성 (Stateless API)

### 8.1 무상태란

Claude API를 포함한 표준 LLM API 서버는 **무상태(stateless)** 입니다.
서버는 요청 사이에 대화를 저장하지 않습니다.
각 요청은 그 요청에 담긴 내용만으로 완결적으로 처리됩니다.

### 8.2 흔한 오해와 그 결과

개발자가 자기 앱에서 만든 `session_id`를 요청에 함께 보내면서
"API가 알아서 이전 대화를 찾아 붙여주겠지"라고 가정하는 실수가 흔합니다.

그 결과: 사용자가 세션을 재개하면 어시스턴트가 이전에 논의한 위험 감수 성향,
투자 목표 같은 것을 "잊어버린" 것처럼 보입니다.
실제로는 잊은 게 아니라 **애초에 전달받은 적이 없습니다.**

세션 ID는 **당신의 애플리케이션이 만든 값**입니다. API는 그 값의 의미를 모릅니다.

### 8.3 올바른 구현

대화 이력은 **애플리케이션이 저장하고, 매 요청마다 `messages` 배열에 실어 보냅니다.**

```python
# 1) 앱의 DB에서 이 세션의 이전 대화를 불러온다 (resolve)
history = db.load_messages(session_id)
# history = [
#   {"role": "user",      "content": "은퇴 자금을 모으고 싶어요"},
#   {"role": "assistant", "content": "위험 감수 성향은 어떠신가요?"},
#   {"role": "user",      "content": "보수적인 편입니다"},
# ]

# 2) 이전 이력 + 새 메시지를 함께 보낸다
response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    messages=history + [{"role": "user", "content": new_user_message}],
)

# 3) 이번 턴도 DB에 저장해서 다음 재개에 대비한다
db.append_messages(session_id, new_user_message, response.content)
```

**왜 다른 방법들은 해결책이 아닌가:**
- 컨텍스트 윈도우가 더 큰 모델로 교체 → 창 크기 문제가 아닙니다. 데이터가
  애초에 요청에 담기지 않았습니다. 창을 아무리 키워도 없는 것은 보이지 않습니다.
- 새 메시지를 짧게 쓰기 → 보내지도 않은 과거를 모델이 "회상"할 방법은 없습니다.
- 사용자에게 매번 다시 말해달라고 요청 → 앱이 저장하고 다시 보내면 완전히
  해결되는 문제를 사용자에게 떠넘기는 것입니다.

### 8.4 부수적 함의

무상태이기 때문에 대화가 길어질수록 매 요청의 토큰 수가 계속 증가합니다.
이것이 5장의 압축과 스크래치패드가 필요한 근본 이유이기도 합니다.
(반복되는 앞부분을 캐싱하는 프롬프트 캐싱 같은 기법도 이 성질에서 나옵니다.)

## 9. Claude의 검색 결과(Search Results) 기능과 인용

### 9.1 RAG란

**RAG (Retrieval-Augmented Generation, 검색 증강 생성)** 는
질문에 답하기 전에 외부 지식 베이스에서 관련 문서를 **검색(retrieve)** 해서
모델의 컨텍스트에 넣어주고, 그 근거 위에서 답을 **생성(generate)** 하게 하는 구조입니다.

목적: 모델이 학습하지 않은 사내 문서, 최신 정보에 대해 환각 없이 답하게 하는 것.

### 9.2 근거 제시와 출처 귀속

**그라운딩(grounding)**: 답변을 실제 제공된 자료에 근거하게 하는 것.
**출처 귀속(source attribution)**: 답변의 각 주장이 어느 문서, 어느 구절에서 왔는지 밝히는 것.

Claude의 웹 검색 기능은 답변에 자연스러운 인용(citation)을 붙여줍니다.
"이 문장은 이 출처에서 왔다"를 모델이 직접 표시합니다.

### 9.3 search_results 기능이 하는 일

**Search Results (검색 결과 블록)** 기능은, **자체 구축한 커스텀 지식 베이스**에서
검색한 결과를 `search_results` 형태의 컨텍스트 블록으로 Claude에 전달할 수 있게 합니다.

그 효과는 하나로 요약됩니다.

> **커스텀 지식 베이스의 내용에 대해서도, 웹 검색 인용과 동등한 품질의
> 자연스러운 인용과 정확한 출처 귀속을 얻는다.**

즉 "이 답변의 이 부분은 사내 정책 문서 POL-118의 이 구절에 근거한다"가
모델의 최종 종합(synthesis) 결과물에 자연스럽게 남습니다.
감사(audit) 가능성과 신뢰성이 필요한 내부 정책 Q&A 같은 곳에서 핵심적입니다.

### 9.4 이 기능이 하지 **않는** 일 (경계 이해)

이 기능은 인용/귀속 기능이지 데이터 파이프라인 기능이 아닙니다. 다음은 하지 않습니다.

- 검색된 문서들을 하나의 **정규화된 포맷으로 자동 변환**해 주지 않습니다. (포맷팅 도구가 아님)
- 문서 간 **상충하는 내용을 자동으로 조정/해결(reconciliation)** 해 주지 않습니다.
  상충 판단과 처리는 여전히 설계자의 몫입니다.
- 검색된 구절이 해당 문서의 **최신 버전임을 보장**하지 않습니다.
  버전 관리와 최신성 보장은 데이터베이스와 검색 인덱스의 책임입니다.
  낡은 문서를 색인에 넣어두면 낡은 내용이 인용될 뿐입니다.

## 10. 모호성 처리와 안전한 에스컬레이션

### 10.1 조회 결과가 여럿일 때 (Disambiguation)

에이전트가 이름과 노선으로 승객을 조회했더니 **동명이인 3명**이 서로 다른
예약 번호로 나왔다고 합시다.

올바른 대응은 하나입니다. **고객에게 추가 식별자를 요청해 대상을 특정(pinpoint)하는 것.**
예약 확인 번호(booking confirmation number), 회원 번호, 이메일 등.

**추측이 왜 위험한가:**
- "가장 최근 예약" 선택 → 근거 없는 가정입니다. 틀리면 **다른 사람의 개인정보**를
  엉뚱한 사람에게 노출하거나, 남의 수하물 청구를 잘못 처리합니다.
- "프로필이 가장 완전한 계정" 선택 → 마찬가지로 근거 없습니다.
  프로필 완성도는 신원과 무관합니다.
- **세 레코드를 병합(merge)** → 최악입니다. 서로 다른 세 사람의 정보를 섞어
  존재하지 않는 가상의 레코드를 만듭니다. 데이터 오염이자 개인정보 침해입니다.

일반 원칙: **식별이 모호할 때 추측하지 말고 되묻는다(ask, don't guess).**
특히 개인정보, 금전, 안전이 걸린 경우에는 예외가 없습니다.

### 10.2 문서에 없는 상황을 만났을 때

RAG 에이전트나 정책 상담 에이전트가, 제공된 약관/지식베이스에
**명시되어 있지 않은 시나리오**를 질문받는 경우가 있습니다.
(예: 제조사 리콜 수리 기간 동안의 렌터카 비용 보장 여부가 약관에 없음)

올바른 대응은 **에스컬레이션**입니다. "정책 문서가 이 시나리오를 다루지 않으므로
사람에게 확인이 필요하다"고 넘깁니다.

**하면 안 되는 것:**
- 없는 근거로 **거부** → 문서에 "안 된다"고 쓰여 있지 않은데 거부하면 부당 거절입니다.
- 다른 조항과 "비슷하니까" **승인** → 유추에 의한 승인은 재정적 책임을 발생시킵니다.
- 근거 없이 다른 곳으로 **책임 전가** → 실제 보장 여부를 확인하지 않은 채 떠넘기는 것입니다.

핵심: **약관에 없다는 것은 "안 된다"도 "된다"도 아니라 "모른다"입니다.**
모를 때 판단을 만들어내는 것이 환각(hallucination)이며,
누락된 정보를 임의로 채우지 않고 넘기는 것이 안전한 설계입니다.

### 10.3 신원 확인 절차 (Identity Verification)

고객 지원 에이전트가 금전적 이의 제기(예: 무단 결제 분쟁)를 처리하려면
계정 소유권을 확인해야 합니다.

Anthropic의 공식 절차 기준:

- 소비자 티어(Claude Pro 등) 사용자가 **계정 번호나 전화번호를 제공하지 못하고**,
  **유사한 계정이 여러 개 검색되는** 경우,
- 제3자 신원 인증 플랫폼 **Persona**를 통해 **정부 발급 사진 신분증과 실시간 셀카**를
  제출받아 신원과 계정 소유권을 확인합니다.

**대안이 부적절한 이유:**
- 사용자가 계정 번호를 제공할 수 없다고 이미 말했는데 다시 계정 번호나 PIN을 요구하는 것은
  막다른 길입니다. (PIN 확인 방식은 이 상황에 해당하지 않습니다.)
- 요금제에 대한 일반적 질문으로 계정을 **추론**하는 것은 신원 확인이 아닙니다.
  누구나 답할 수 있는 정보로 남의 계정에 접근하게 됩니다.
- "최근 결제 활동이 있는 계정"을 선택하는 것은 10.1의 추측과 같은 오류이며,
  금전 분쟁에서 특히 위험합니다.

이것은 10.1의 원칙(모호하면 추측 금지)이 보안·금전 영역에 적용된 형태입니다.
다만 여기서는 "되묻기"만으로 부족하고, **정식 신원 인증 절차**가 필요합니다.

## 11. 모델 평가와 신뢰도 임계값

### 11.1 사람 검토를 줄이는 구조

문서에서 정보를 추출하는 파이프라인은 보통 이렇게 동작합니다.

```
문서 → 추출 모델 → (필드값, 신뢰도 점수)
                     ├ 신뢰도 ≥ 임계값 → 자동 통과 (사람 검토 생략)
                     └ 신뢰도 <  임계값 → 사람 검토(Human Review)로 라우팅
```

**신뢰도 점수(confidence score)**: 모델이 자기 예측에 얼마나 확신하는지를 나타내는 숫자.
**임계값(threshold)**: 자동 통과와 사람 검토를 가르는 기준선.

### 11.2 보정 (Calibration)

**보정(calibration)** 이란 신뢰도 점수가 **실제 정확도와 일치하는 상태**를 말합니다.
"신뢰도 0.95라고 말한 예측들이 실제로 약 95% 맞는다"면 잘 보정된 것입니다.

**중요한 사실: 보정은 특정 입력 데이터 분포 위에서 성립합니다.**
어떤 조건의 데이터로 측정해서 정한 임계값은, 그 조건이 유지될 때만 유효합니다.

### 11.3 데이터 드리프트 / 입력 분포 변화

**데이터 드리프트(data drift) 또는 입력 모집단 변화(input population shift)**:
운영 중에 모델에 들어오는 데이터의 분포가 이전과 달라지는 현상.

예: **해상도가 조금 낮은 새 문서 스캐너**를 배포했습니다.
이미지 품질이 달라졌으므로 입력 분포가 변한 것입니다.
같은 0.95라는 신뢰도가 나와도 실제 정확도는 90%로 떨어져 있을 수 있습니다.
결과적으로 **잘못 추출된 데이터가 사람 검토를 통과**하게 됩니다.

### 11.4 올바른 대응

**새 스캐너로 촬영한 문서 샘플로 정확도와 신뢰도 보정 상태를 재검증한 뒤,
기존 임계값을 계속 쓸 수 있는지 판단합니다.**

```
새 스캐너 도입
  → 새 조건의 문서 샘플 수집
  → 정답(ground truth) 라벨링
  → 정확도 측정 + 신뢰도별 실제 정확도 확인 (보정 재검증)
  → 임계값 유지 / 조정 결정
```

**부적절한 대응들:**
- 하드웨어 변경 시마다 임계값을 **고정된 수치만큼 자동으로 낮춤**
  → 품질 저하가 신뢰도에 미치는 영향은 상황마다 다릅니다. 근거 없는 자의적 조정입니다.
- 임계값을 끄고 새 스캐너 결과를 **영구히 100% 사람 검토**로 보냄
  → 과잉 대응입니다. 자동화의 이점을 통째로 버립니다. 재검증으로 충분할 수 있습니다.
- **아무것도 안 하고 기존 임계값 유지** ("임계값은 모델 동작에 대해 보정된 것이므로
  이미지 품질과 무관하다")
  → 잘못된 전제입니다. 신뢰도와 실제 정확도의 관계는 입력 품질에 직접 영향을 받습니다.

### 11.5 세그먼트별 평가 (Sliced Metrics)

**합산 정확도(aggregate accuracy)** 하나로 시스템 전체를 판단하면 안 됩니다.

예: 자동차/주택/건강 보험 청구를 처리하는 추출 파이프라인의 전체 정확도가 94%라고 합시다.
이제 **건강 보험 청구에 대해서만** 사람 검토를 줄이려고 합니다.

합산 94%는 건강 보험 세그먼트의 성능을 **은폐할 수 있습니다.**
자동차 98%, 주택 97%, 건강 82%여도 비율에 따라 합산은 94%가 나올 수 있습니다.

**올바른 방법**: 이미 라벨링된 평가 데이터셋이 있으므로,
**건강 보험 예시들만 슬라이싱(slicing)해서 그 세그먼트의 정확도를 따로 계산**하고,
그 값이 독립적으로 기준을 넘을 때만 검토를 줄입니다.

**부적절한 방법들:**
- 모델에게 **자기 신뢰도 점수로 문서 유형별 정확도를 스스로 추정**하게 함
  → 자가 보고는 정답(ground truth) 대비 측정이 아닙니다. 검증이 아니라 추측입니다.
- 세 유형 모두 데이터를 **똑같이 늘려 합산 신뢰구간을 좁힘**
  → 합산값의 정밀도가 올라가도 그것이 특정 세그먼트의 성능을 말해주지는 않습니다.
- **"같은 프롬프트와 같은 모델을 쓰니 세그먼트도 합산과 비슷할 것"이라고 가정**
  → 같은 모델이어도 입력 문서의 성격(레이아웃, 용어, 필드 구성)이 다르면
     성능이 크게 달라집니다. 프롬프트가 같다는 것은 성능이 같다는 근거가 아닙니다.

일반 원칙: **어떤 세그먼트에 대해 결정을 내릴 것이라면,
그 세그먼트에 대해 직접 측정하라.** 이미 라벨 데이터가 있다면 슬라이싱이 가장 직접적인 길입니다.

## 12. 전체를 관통하는 원칙 요약

1. **모델은 컨텍스트 안의 것만 안다.** 전달하지 않은 것은 존재하지 않습니다.
2. **컨텍스트는 유한하고 휘발성이다.** 중요한 것은 파일에 남깁니다.
3. **압축 전에 기록한다.** 순서를 지키지 않으면 복구 불가입니다.
4. **실패와 빈 결과를 구분한다.** 판별 기준은 "조회가 성공했는가"입니다.
5. **재시도에는 반드시 상한이 있다.** 상한 후에는 정보를 실어 에스컬레이션합니다.
6. **오류 보고는 풍부하게.** 실패 유형, 시도 내용, 부분 결과, 미처리 범위.
7. **가진 것을 주고, 못 가진 것을 명시한다.** 부분 결과는 버리지 않되 완전한 척하지 않습니다.
8. **스키마로 모호성을 제거한다.** 비교에 필요한 메타데이터는 필수 필드로 강제합니다.
9. **모호하면 추측하지 말고 묻거나 넘긴다.** 특히 개인정보, 금전, 안전 영역에서.
10. **위임은 컨텍스트 절약 이득이 조정 비용보다 클 때만.**
11. **크래시를 전제로 설계한다.** 체크포인트와 매니페스트로 재개 가능하게.
12. **입력 조건이 바뀌면 재검증한다.** 그리고 결정을 내릴 세그먼트는 직접 측정합니다.

## 13. 용어 사전 (Glossary)

**Access Failure (접근 실패)**
시스템이 질문에 답하지 못한 상태. 타임아웃, 연결 실패, 5xx, 429 등. 재시도 대상.

**Aggregate Accuracy (합산 정확도)**
전체 평가 데이터셋에 대한 하나의 평균 정확도 수치. 하위 그룹의 성능을 가릴 수 있음.

**Ambiguity (모호성)**
어떤 값이나 표현이 무엇을 가리키는지 확정할 수 없는 상태. 스키마 분리나 되묻기로 해소.

**Calibration (보정)**
신뢰도 점수가 실제 정확도와 일치하는 상태. 특정 입력 분포 위에서만 성립함.

**Checkpointing (체크포인팅)**
장시간 작업 도중 진행 상태를 외부 저장소에 주기적으로 저장하는 것. 크래시 복구의 전제.

**Citation (인용)**
답변의 특정 부분이 어느 출처에서 왔는지 표시하는 것.

**Compaction / Summarization (압축 / 요약)**
길어진 대화를 요약으로 대체해 토큰 공간을 회수하는 기법. 손실 압축이므로 세부가 사라질 수 있음.

**Confidence Score (신뢰도 점수)**
모델이 자기 출력에 대해 얼마나 확신하는지를 나타내는 수치.

**Confidence Threshold (신뢰도 임계값)**
자동 처리와 사람 검토를 가르는 기준선.

**Context Degradation (컨텍스트 열화)**
긴 세션 동안 초기 발견 사실이 활성 컨텍스트에서 밀려나 사라지는 현상. 환각의 흔한 원인.

**Context Window (컨텍스트 윈도우)**
모델이 한 번에 처리할 수 있는 토큰의 최대 총량.

**Context Window Exceeded (컨텍스트 초과)**
전달 토큰이 창 한계를 넘어 요청이 실패하는 오류.

**Coordination Overhead (조정 오버헤드)**
서브에이전트를 띄우고 지시하고 결과를 취합하는 데 드는 추가 토큰·시간 비용.

**Coordinator / Orchestrator (코디네이터 / 오케스트레이터)**
작업을 계획·분배하고 결과를 종합하는 상위 에이전트.

**Data Drift / Input Population Shift (데이터 드리프트 / 입력 모집단 변화)**
운영 중 입력 데이터의 분포가 달라지는 현상. 기존 보정과 임계값을 무효화할 수 있음.

**Delegation (위임)**
하위 작업을 서브에이전트에 맡기고 요약만 돌려받는 설계 패턴.

**Disambiguation (모호성 해소)**
여러 후보 중 정확한 대상을 특정하는 과정. 추가 식별자 요청이 표준 방법.

**Escalation (에스컬레이션)**
자기 수준에서 해결 불가한 문제를 필요한 정보와 함께 상위 결정권자나 사람에게 넘기는 것.

**Exponential Backoff (지수 백오프)**
재시도 간격을 지수적으로 늘리는 재시도 전략. 서버 회복 시간을 확보.

**Fault Tolerance (결함 허용)**
일부 구성 요소가 실패해도 시스템 전체가 계속 동작하는 성질.

**Grounding (그라운딩)**
답변을 실제 제공된 자료에 근거하게 하는 것. 환각의 반대 개념.

**Hallucination (환각)**
근거 없는 내용을 사실처럼 생성하는 현상. 컨텍스트 유실이나 정보 부재 시 자주 발생.

**Human Review (사람 검토)**
자동화 결과를 사람이 확인하는 단계. 신뢰도가 낮은 건을 여기로 라우팅.

**Isolation (격리)**
한 구성 요소의 실패가 다른 정상 작업까지 죽이지 않도록 분리하는 것.

**JSON Schema**
JSON 데이터의 구조·타입·필수 필드(`required`)를 기술하는 표준 규격.

**Manifest (매니페스트)**
각 에이전트의 상태와 결과물 위치를 정리한 색인 파일. 재개의 출발점.

**Multi-Agent Architecture (멀티 에이전트 아키텍처)**
코디네이터와 여러 서브에이전트로 역할을 나눈 시스템 구조.

**Narrative Prose (서사적 줄글)**
문장으로 흐르는 서술 형식. 정성적·맥락 의존적 정보에 적합.

**Output Contract (출력 계약)**
서브에이전트가 결과를 돌려줄 때 지켜야 하는 형식 약속. 스키마로 명시.

**Partial Results / Partial Progress (부분 결과 / 부분 진행)**
실패 전까지 확보한 중간 결과. 버리지 않고 실패 정보와 함께 보고.

**Persona**
Anthropic이 사용하는 제3자 신원 인증 플랫폼. 정부 발급 사진 신분증과 실시간 셀카로 확인.

**Rate Limit / 429**
단위 시간당 요청 수 제한. 초과 시 HTTP 429 반환. 일시적이므로 재시도 가능.

**RAG (Retrieval-Augmented Generation, 검색 증강 생성)**
외부 지식 베이스에서 관련 문서를 검색해 컨텍스트에 넣고 그 근거로 답을 생성하는 구조.

**Resumable Architecture (재개 가능 아키텍처)**
중단 후 처음부터가 아니라 중단 지점부터 이어서 실행할 수 있게 설계된 구조.

**Retryable Error (재시도 가능 오류)**
다시 시도하면 성공할 가능성이 있는 일시적 오류.

**Rich Error Reporting (풍부한 오류 보고)**
실패 유형, 시도 내용, 부분 결과, 대안을 포함한 구조화된 오류 전달 방식.

**Scratchpad (스크래치패드)**
중요한 사실을 기록해 두는 대화 밖의 영속적 파일. 압축·컨텍스트 유실에 대한 방어.

**search_results (검색 결과 블록)**
커스텀 지식 베이스의 검색 결과를 Claude에 전달하는 컨텍스트 블록 형식.
웹 검색과 동등한 자연스러운 인용과 출처 귀속을 가능하게 함.

**Segment / Sliced Metrics (세그먼트 / 슬라이스 지표)**
데이터를 하위 그룹으로 나눠 각각 따로 측정한 성능 지표.

**Session ID (세션 ID)**
애플리케이션이 대화를 식별하기 위해 만든 값. LLM API는 이 값으로 이력을 복원해 주지 않음.

**Source Attribution (출처 귀속)**
답변의 각 주장이 어느 문서·구절에서 유래했는지 명시하는 것.

**State Persistence (상태 영속성)**
에이전트의 상태와 결과를 프로세스 밖(파일·DB)에 저장해 유지하는 것.

**Stateless (무상태)**
서버가 요청 사이에 상태를 보관하지 않는 성질. LLM API의 기본 동작.
대화 이력은 매 요청마다 클라이언트가 다시 보내야 함.

**Structured Output / Structured Record (구조화된 출력 / 레코드)**
필드가 명시된 객체 형태의 데이터. 자유 텍스트보다 기계 처리와 판단에 유리.

**Subagent (서브에이전트)**
코디네이터가 위임한 좁은 범위의 작업을 자기 컨텍스트에서 수행하고 요약을 보고하는 에이전트.

**Synthesis (종합)**
여러 출처·에이전트의 결과를 하나의 최종 산출물로 통합하는 단계.

**Timeout (타임아웃)**
정해진 시간 안에 응답이 오지 않아 요청을 포기하는 것. 접근 실패로 분류.

**Token (토큰)**
모델이 텍스트를 처리하는 최소 단위. 비용과 컨텍스트 사용량의 계산 기준.

**Valid Empty Result (유효한 빈 결과)**
조회가 정상적으로 성공했지만 일치하는 데이터가 없는 결과. 재시도 대상이 아님.
