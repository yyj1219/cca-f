# 6. CLI 실행과 자동화

이 장에서 다루는 것:

- 대화형 모드와 비대화형(`-p`/print) 모드의 차이, CI에서 `-p`가 필수인 이유
- 자주 쓰는 CLI 플래그와 각 플래그가 **하지 않는** 일
- 구조화된 출력: `--output-format`(text/json/stream-json)과 `--json-schema`
- JSON 응답 본문에 들어 있는 비용·토큰 메타데이터
- stdin 파이프 조합과 10MB 상한, 도구 권한 차단
- `--bare`로 자동 탐색을 끄고 재현성 확보하기
- 헤드리스의 상태 없음(statelessness) 함정과 해법
- GitHub Actions `claude-code-action` v1 통합

---

## 6.1 대화형 모드 vs 비대화형(프린트) 모드

`claude`를 그냥 실행하면 **대화형(interactive) 모드**입니다. 터미널에 UI가 뜨고 사용자의 표준 입력(stdin)을 기다립니다.

```bash
claude              # 대화형 — 사람이 앉아서 입력한다고 가정
```

`-p`(= `--print`)를 주면 **비대화형/프린트(headless) 모드**입니다. 프롬프트를 한 번 처리하고 결과를 표준 출력으로 뱉은 뒤 종료합니다. 스크립트, CI 파이프라인, cron 야간 배치, npm 스크립트, 봇에서 쓰는 형태입니다.

```bash
claude -p "이 PR의 diff를 요약해줘"
claude -p "이 저장소의 보안 이슈를 점검해줘" > report.txt
claude -p "run the migration script" --allowedTools "Bash(npm run migrate)"
```

주의할 점 둘:

- `--print`는 단지 "대화형 UI 없이 출력하고 종료"를 의미할 뿐, **도구를 비활성화하지 않습니다.**
- 비대화형이므로 **승인 프롬프트에 답할 사람이 없습니다.** 권한을 미리 열어 두지 않으면 중간에 멈춥니다.

### CI/CD에서 왜 `-p`가 필수인가

GitHub Actions 같은 CI 러너에는 사람이 없습니다. `-p` 없이 `claude`를 실행하면:

- 대화형 세션이 열린다
- stdin에서 사용자 입력이 오기를 기다린다
- 러너는 영원히 입력을 주지 않는다
- **로그에 아무 출력도 없이 잡(job) 타임아웃까지 무한 대기(hang)한다**

"CI에서 아무 출력 없이 멈춤 + API 키와 프롬프트는 정상"이라는 증상의 전형적 원인이 바로 이것입니다.

### 증상 감별 — 다른 원인들은 "소리를 낸다"

같은 CI 환경의 다른 문제들은 멈추지 않고 에러를 내며 종료합니다.

| 원인 | 증상 |
|---|---|
| 대화형 모드(`-p` 누락) | **조용히 무한 대기.** 출력 없음 |
| 얕은 복제(`git clone --depth=1`) | Git이 에러 메시지를 출력하고 실패. 무한 대기 아님 |
| 인증 실패 / API 키 문제 | 에러 로그가 나옴. "조용한 무한 재시도 루프"에 빠지지 않음. 시크릿 마스킹 여부는 보안 표시 기능일 뿐 인증 동작과 무관 |
| Node.js 버전 미달 | SyntaxError/호환성 에러를 내고 **즉시 종료** |

정리: **"조용히 무한 대기" = 입력 대기 = 대화형 모드 문제.**

## 6.2 주요 CLI 플래그

| 플래그 | 의미 |
|---|---|
| `-p`, `--print` | 비대화형 1회 실행, 결과 출력 후 종료 |
| `--output-format` | 출력 형식 (`text` / `json` / `stream-json`) |
| `--json-schema` | 응답 구조를 JSON Schema로 강제 |
| `--input-format` | 구조화된 JSON 이벤트 스트림을 **입력**으로 줄 때 사용 |
| `--allowedTools` | 지정한 도구만 허용 (화이트리스트, 자동 승인 패턴) |
| `--disallowedTools` | 지정한 도구 사용 금지 (블랙리스트) |
| `--max-turns N` | 에이전트가 도는 최대 턴(왕복) 수 제한 |
| `--max-budget-usd` | 한 작업의 비용 상한 |
| `--continue` | 이전 대화를 이어서 진행 |
| `--append-system-prompt` | 시스템 프롬프트 뒤에 지시문을 덧붙임 |
| `--settings <path>` | 사용할 설정 파일을 명시적으로 지정 |
| `--bare` | 자동 탐색(auto-discovery)을 전면 비활성화 |
| `--no-session-persistence` | 실행 간 세션 기록을 남기지 않음 |
| `--verbose`, `--include-partial-messages` | 실행 중 도구 호출 등 상세 로그 / 스트리밍 중간 이벤트 노출 |

### 각 플래그가 "하지 않는" 일 — 흔한 오해

| 플래그 | 흔한 오해 | 실제 |
|---|---|---|
| `--allowedTools` | 패턴을 좁게 준 줄 안다 | 패턴 끝 `*`는 **접두사 매칭**이라 범위가 넓어짐 |
| `--max-turns` | 보안 통제 수단이다 | **아님.** 폭주 방지와 비용 상한용. 어떤 명령을 실행할지는 제어 못 함. 늘린다고 PR 댓글을 스스로 읽어오지도 않음 |
| `--output-format` | 출력이 좋아진다 | 형식만 바꿀 뿐, **없던 로직을 만들어주지 않음** |
| `--max-budget-usd` | 품질을 올린다 | 안전장치일 뿐. 올린다고 중복 출력이 줄지 않음(오히려 늚) |
| `--no-session-persistence` | 로컬 파일 인식과 관련 있다 | 무관 |
| `--append-system-prompt` | 프로젝트 규칙을 여기 둔다 | 일회성 조정용. 지속적 규칙은 `CLAUDE.md`가 맞음 |
| `--verbose` | 비용 정보를 얻으려면 필수다 | 아님(6.3 참조). 디버깅용 |

## 6.3 구조화된 출력 — `--output-format`

스크립트에서 CLI를 호출할 때는 자유 텍스트가 아니라 **기계가 파싱할 수 있는 구조화된 출력**이 필요합니다. 예를 들어 릴리스 노트 생성기가 커밋 로그를 넘기고 정리된 결과를 받아오는 식입니다.

| 값 | 설명 |
|---|---|
| `text` | 사람이 읽는 평문 (기본값) |
| `json` | 하나의 JSON 객체로 반환. 스크립트가 파싱하기 좋음 |
| `stream-json` | 생성 과정을 줄 단위 JSON 이벤트로 실시간 스트리밍 |

`stream-json` 계열은 **진행 상황을 실시간으로 관찰**하기 위한 것입니다. 최종 결과의 **형태를 특정 스키마로 고정하는 기능이 아니며**, 어디까지나 후처리 도구이지 모델이 애초에 더 좋은 출력을 내게 만드는 수단도 아닙니다.

### JSON 응답 구조 — 여기에 비용 정보가 있다

```bash
claude -p --output-format json "summarize the changes in this release"
```

반환되는 JSON에는 **응답 텍스트만 들어있는 게 아닙니다.** 실행 메타데이터가 함께 들어옵니다.

```json
{
  "type": "result",
  "subtype": "success",
  "is_error": false,
  "duration_ms": 12345,
  "num_turns": 3,
  "result": "이번 릴리스에서는 ...",
  "session_id": "abc-123",
  "total_cost_usd": 0.0432,
  "usage": {
    "input_tokens": 15234,
    "output_tokens": 892,
    "cache_read_input_tokens": 10000
  },
  "modelUsage": {
    "claude-opus-...": { "inputTokens": 1200, "outputTokens": 300, "costUSD": 0.031 },
    "claude-haiku-...": { "inputTokens": 14034, "outputTokens": 592, "costUSD": 0.012 }
  }
}
```

핵심 필드:

- **`result`** — 실제 응답 텍스트. 스크립트가 보통 이것만 꺼내 씀 (`jq -r '.result'`)
- **`total_cost_usd`** — 이번 호출의 **총 API 비용(달러)**
- **`modelUsage`(모델별 비용 내역)** — 여러 모델이 섞여 쓰인 경우(메인 모델 + 서브에이전트용 저렴한 모델 등) 모델마다 얼마 썼는지
- `usage` — 입력/출력/캐시 토큰 수
- `duration_ms`, `num_turns`, `session_id` — 실행 메타데이터

**핵심 이해:** 비용 정보를 얻으려고 **플래그를 추가할 필요가 없습니다.** `--output-format json`을 이미 쓰고 있다면 비용은 **이미 같은 응답 본문 안에** 들어 있습니다. `.result`를 읽던 스크립트에 한 줄만 더하면 됩니다.

```bash
OUT=$(claude -p --output-format json "summarize the changes")
echo "$OUT" | jq -r '.result'          > summary.txt
echo "$OUT" | jq -r '.total_cost_usd' >> costs.log
echo "$OUT" | jq -c '.modelUsage'     >> costs.log
```

**오해하기 쉬운 점들:**

- `stream-json` + `--verbose` 조합이 있어야만 비용이 보이는 것이 **아닙니다.** 일반 `json`에도 들어 있습니다.
- 실행이 끝난 뒤 **웹 대시보드를 따로 조회해야만** 알 수 있는 것이 아닙니다. (대시보드도 있지만 자동화 파이프라인에는 부적합합니다.)
- `.claude/usage.log` 같은 **로컬 로그 파일을 파싱**해야 하는 구조가 아닙니다.

### `--json-schema` — 응답 구조 강제

CI에서 Claude의 답을 코드로 파싱해 빌드 성공/실패를 판단하려면, 모델이 어떤 문장으로 추론을 서술하든 상관없이 답변이 **항상 같은 JSON 모양**이어야 합니다.

**JSON Schema란** JSON 데이터의 형태를 기술하는 표준 규격입니다. 어떤 필드가 있고, 타입이 무엇이고, 무엇이 필수인지를 JSON으로 적습니다.

```json
{
  "type": "object",
  "properties": {
    "version": { "type": "string" },
    "changes": { "type": "array", "items": { "type": "string" } }
  },
  "required": ["version", "changes"]
}
```

문법 최소 지식:

- `"type": "object"` — 결과가 객체임
- `"properties"` — 각 필드의 이름과 타입
- `"type": "boolean"` / `"array"` / `"string"` — 타입 지정
- `"items"` — 배열 원소의 타입
- `"required"` — 반드시 존재해야 하는 필드 목록

`--output-format json`과 `--json-schema`를 함께 쓰면 응답 구조가 강제됩니다(structured output). 결과를 받는 쪽에서 파싱 실패를 걱정하지 않아도 됩니다.

```bash
claude -p "review this diff" \
  --output-format json \
  --json-schema '{
    "type": "object",
    "properties": {
      "passed": { "type": "boolean" },
      "issues": { "type": "array", "items": { "type": "string" } }
    },
    "required": ["passed", "issues"]
  }'
```

CI 스크립트는 이렇게 안심하고 파싱할 수 있습니다.

```bash
result=$(claude -p "..." --output-format json --json-schema '...')
passed=$(echo "$result" | jq -r '.passed')
[ "$passed" = "true" ] || exit 1
```

### 왜 프롬프트로 부탁하는 것으로는 부족한가

다음 두 방식은 **보장이 아니라 요청**일 뿐입니다.

- 프롬프트 본문에 "passed: true/false 형식으로만 답해"라고 쓰고 `--output-format text` 사용
- `--append-system-prompt "Always respond with valid JSON matching {passed, issues}"` 사용

모델은 대체로 잘 따르지만, 앞뒤에 설명 문장을 붙이거나 마크다운 코드 펜스(```)를 두르거나 필드 이름을 살짝 다르게 쓸 수 있습니다. 그러면 파싱이 깨지고 빌드가 오작동합니다. **스키마 검증·강제는 프롬프트 지시로 대체할 수 없습니다.**

### 잘못된 스키마를 넘기면 어떻게 되는가

스키마 문자열은 API를 호출하기 **전에 로컬에서 먼저 파싱하고 검증**됩니다. 셸에서 따옴표나 중괄호를 잘못 이스케이프해 JSON으로 파싱되지 않는 문자열이 들어오면:

- 즉시 검증 실패로 판정되고,
- "유효한 JSON Schema가 아니다"는 오류 메시지와 검증기의 진단 내용을 출력하며,
- **어떤 출력도 생성하지 않고 오류 종료 코드로 프로세스가 끝납니다.**

일어나지 않는 일들과 그 이유:

- **조용히 평문 텍스트로 폴백** — 자동화 파이프라인에서 조용한 폴백은 최악입니다. 잘못된 결과가 그대로 하류로 흘러 나중에 원인 불명의 버그가 됩니다. 그래서 명시적으로 실패시킵니다(fail fast).
- **빈 객체 반환** — 마찬가지로 오류를 숨기는 동작이므로 하지 않습니다.
- **재시도** — `--max-retries` 류의 재시도는 네트워크 오류나 일시적 API 장애처럼 **다시 하면 성공할 수 있는(transient)** 문제에 적용됩니다. 입력 문자열의 문법 오류는 몇 번을 다시 해도 똑같이 실패하는 결정론적(deterministic) 오류이므로 재시도 대상이 아닙니다. 이 구분은 CLI 설계 전반에 적용되는 일반 규칙입니다.

**실무 팁:** 셸에서 긴 JSON을 인라인으로 넘기면 이스케이프 실수가 잦습니다. 파일로 빼서 넘기는 편이 안전합니다.

```bash
claude -p "릴리스 노트를 추출해줘" --json-schema "$(cat schema.json)"
```

## 6.4 파이프와 조합 — stdin, 리다이렉션, 도구 권한

### stdin 파이프로 데이터 넣기

셸의 파이프(`|`)로 앞 명령의 출력을 Claude의 **표준 입력(stdin)**에 넣을 수 있습니다.

```bash
git diff main | claude -p "너는 오타 린터다. 오타만 지적해라."
cat build-error.txt | claude -p "근본 원인을 설명해라" > output.txt
```

장점은 Claude가 파일을 읽으러 **도구를 호출할 필요가 없다**는 점입니다. 내용이 이미 프롬프트에 들어와 있으니까요. 파이프와 리다이렉션은 OS 셸의 표준 기능이라 `-p`와 문제없이 함께 동작합니다.

### stdin 10MB 상한(cap)

Claude Code CLI는 파이프로 들어오는 stdin 크기에 **10MB 상한**을 둡니다. 메모리 폭주와 프롬프트 토큰 오버플로를 막기 위한 안전장치입니다. 입력이 10MB를 넘으면 처리하지 않고 **에러와 함께 즉시 종료**합니다.

그래서 평소엔 잘 되던 빌드 로그 파이프가, 유난히 장황한 실패가 난 날에만 갑자기 아무 설명도 없이 즉시 죽는 현상이 생깁니다. 원인은 인코딩도, 리다이렉션 연산자도 아니고 **크기**입니다.

대처:

```bash
# 뒤쪽 2000줄만 보내기
tail -n 2000 build-error.txt | claude -p "근본 원인을 설명해라"

# 에러 라인만 추려서 보내기
grep -E "ERROR|FAILED|Exception" build-error.txt | head -500 | claude -p "..."
```

부수적으로 알아둘 것:

- 일반 텍스트 파이프 입력은 별도 옵션 없이 기본으로 받아들여집니다. `--input-format stream-json`을 반드시 설정해야 하는 게 아닙니다. (`--input-format`은 구조화된 JSON 이벤트 스트림을 입력으로 줄 때 쓰는 옵션입니다.)
- 인코딩 문제만으로 `-p` 모드가 무조건 즉시 강제 종료되지는 않습니다.

### 도구 권한 제어 — `--disallowedTools` / `--allowedTools`

기본적으로 Claude Code는 여러 도구에 접근할 수 있고, 여기엔 셸 명령을 실행하는 **Bash 도구**가 포함됩니다. 신뢰할 수 없는 입력(예: 외부 기여자의 diff)을 다루는 자동화 단계에서는 이걸 아예 막고 싶을 수 있습니다. **확실한 방법은 CLI 플래그로 명시적으로 차단하는 것입니다.**

```bash
git diff main | claude -p "너는 오타 린터다..." --disallowedTools Bash
```

- `--disallowedTools <도구...>` — 지정한 도구 사용을 금지 (블랙리스트)
- `--allowedTools <도구...>` — 지정한 도구만 허용 (화이트리스트, 더 엄격)

이 플래그는 CLI 인자이므로 Windows 러너든 Linux 러너든 동일하게 동작합니다. 즉 **이식성(portability)**도 만족합니다.

**반드시 구분해야 할 오해들:**

| 잘못된 생각 | 왜 틀렸나 |
|---|---|
| npm 스크립트를 경유해 실행하면 도구 접근이 차단된다 | npm은 그저 자식 프로세스를 띄울 뿐입니다. 자식으로 실행된 `claude` 프로세스의 내부 도구 권한은 그대로입니다. |
| stdin으로 파이프했으니 Bash 권한이 필요 없다 → 안전하다 | "필요 없다"와 "쓸 수 없다"는 다릅니다. diff를 읽는 데는 Bash가 안 필요하지만, Bash 도구 자체는 여전히 **활성 상태**입니다. 모델이 다른 이유로 호출할 수 있습니다. |
| 프롬프트에 "Bash 쓰지 마"라고 적으면 된다 | 자연어 지시는 **가이드**일 뿐 강제가 아닙니다. 프롬프트 인젝션이나 모델의 판단으로 무시될 수 있습니다. 보안 경계는 시스템 수준(플래그·권한)에서 세워야 합니다. |

**핵심 원칙:** *"필요 없어서 안 쓴다"는 보안이 아니다. "쓸 수 없게 막았다"가 보안이다.*

## 6.5 재현성 확보 — 자동 탐색과 `--bare`

### 자동 탐색(auto-discovery)과 그 위험

기본적으로 Claude Code는 실행될 때 주변 환경을 스스로 뒤져서 설정을 끌어옵니다.

- 작업 디렉터리의 `CLAUDE.md`, `.claude/settings.json`, `.claude/rules/`
- 작업 디렉터리의 `.mcp.json` (MCP 서버 정의)
- 홈 디렉터리의 `~/.claude/` (전역 설정, 훅, 에이전트 정의)

대화형 개발에서는 편리합니다. 그런데 **CI/CD나 자동화 배치 작업에서는 이게 재앙**이 됩니다.

- **MCP(Model Context Protocol)란**: Claude가 외부 시스템(DB, API, 파일 시스템, 사내 도구 등)에 접근할 수 있게 해주는 표준 프로토콜입니다. `.mcp.json`에 서버를 정의하면 그 도구들이 Claude에게 추가로 주어집니다.
- **훅(Hook)이란**: 특정 이벤트(도구 실행 전후, 세션 시작/종료 등)에 자동으로 실행되는 사용자 정의 명령입니다. "파일을 수정한 뒤에는 항상 포매터를 돌린다" 같은 자동화를 설정할 수 있습니다. 훅은 **도구 실행을 차단하거나 입력을 변형할 수도 있습니다.**

### 재현성 문제 시나리오

야간에 도는 보안 점검 작업이 여러 대의 자체 호스팅 러너(self-hosted runner) 중 아무 데서나 실행됩니다. 그런데 러너마다 환경이 미묘하게 다릅니다.

- 어떤 러너의 공유 작업 디렉터리에는 누가 남긴 `.mcp.json`이 있어 낯선 MCP 서버가 붙습니다.
- 어떤 러너의 `~/.claude`에는 동료가 예전에 설정한 훅이 남아 있어 도구 호출이 간섭받습니다.

결과: **같은 명령인데 러너마다 다른 결과.** 이것을 재현성(reproducibility)이 깨졌다고 합니다. 보안 점검처럼 결과를 신뢰해야 하는 작업에서는 치명적입니다.

### 해결: `--bare` + 명시적 플래그

`--bare`는 작업 디렉터리와 홈 디렉터리로부터의 **모든 자동 탐색을 끕니다.** 설정도, 훅도, MCP 서버도, 프로젝트 규칙도 자동으로 로드되지 않습니다. 그 위에 **필요한 것만 명시적으로** 플래그로 주입합니다.

```bash
claude -p --bare \
  --settings ./ci/claude-settings.json \
  --append-system-prompt "보안 감사 모드로 동작하고 파일을 수정하지 마라." \
  "의존성의 알려진 취약점을 점검하고 요약해줘"
```

이제 이 명령은 러너 A에서 돌든 러너 B에서 돌든 **동일한 입력, 동일한 동작**을 갖습니다. 환경이 아니라 **명령 자체가 실행 조건을 완전히 서술**하기 때문입니다. 컨테이너 이미지를 고정 태그로 핀하거나 패키지 lockfile을 쓰는 것과 같은 사고방식입니다: **암묵적 환경 의존을 제거하고 모든 것을 명시한다.**

### 재현성을 확보하지 **못하는** 접근들

- **`--output-format stream-json` + 출력 필터링** — 출력에서 훅/MCP 관련 이벤트를 걸러내도, 그 훅과 MCP 서버는 **이미 실행 중에 동작했습니다.** 파일을 건드렸거나 도구 호출을 변형했을 수 있습니다. 사후 필터링은 부작용(side effect)을 되돌리지 못합니다. 로그를 지운다고 일어난 일이 사라지지 않습니다.
- **`--max-turns 2`로 턴 제한** — 턴 수를 줄여도 그 2턴 안에서 훅과 MCP는 정상 동작합니다. 간섭의 **양**을 줄일 뿐 **원인**을 제거하지 못하며, 애초에 작업이 2턴에 안 끝날 수도 있습니다.
- **`--continue`로 깨끗한 환경의 세션 이어받기** — `--continue`는 **대화 기록**을 복원할 뿐입니다. 현재 러너의 훅과 MCP 자동 탐색은 그대로 일어납니다. 과거 상태를 불러온다고 현재 환경이 격리되지 않습니다.

**원칙:** 오염은 **발생 전에 차단**해야지, 발생 후에 걸러낼 수 없습니다.

## 6.6 상태 없음(Statelessness) 함정

헤드리스 실행은 기본적으로 **매번 아무것도 기억하지 못한 채 시작**합니다. 이것이 자동화 봇의 대표적 함정입니다.

**시나리오**: PR에 새 커밋이 올라올 때마다 리뷰 봇이 재실행됩니다. 작성자가 null 체크 누락을 아직 고치지 않았으므로, 봇은 매번 같은 결함을 새로 발견하고 **같은 인라인 댓글을 중복 게시**합니다.

원인은 명확합니다. 봇은 자신이 이전 실행에서 이미 그 지적을 했다는 사실을 **모릅니다.** 코드는 그대로이니 결함도 그대로 검출되는 것이 당연합니다.

### 해결 — 이전 결과를 컨텍스트에 주입하기

**핵심: 이전 실행의 발견 사항(prior findings)을 새 실행의 프롬프트/컨텍스트에 넣어주고, 중복을 제외하라고 명시적으로 지시한다.**

```bash
PRIOR=$(gh pr view "$PR" --json comments -q '.comments[].body')

claude -p "이 PR의 변경 사항을 리뷰하라.

아래는 이전 실행에서 이미 보고한 지적 사항이다:
---
$PRIOR
---
위 목록에 이미 존재하는 지적은 다시 보고하지 말고,
새로 발견된 사항만 보고하라."
```

일반화하면: **상태 없는 에이전트에게 상태가 필요하면, 그 상태를 명시적으로 넘겨줘야 한다.** 모델이 알아서 이전 실행을 기억하거나 PR 댓글을 조회해 주지 않습니다.

작동하지 않는 접근들:

- **턴 수를 늘린다** — 봇이 알아서 PR 댓글을 읽으러 가지 않습니다. 필요한 것은 턴이 아니라 정보와 지시입니다.
- **세션 지속성을 끈다** — 기억을 더 지우는 방향이므로 중복이 줄기는커녕 정반대입니다.
- **출력 형식을 바꾼다** — 대조·필터링 로직이 저절로 생기지 않습니다.

## 6.7 CI 통합

### 기본 형태 — 워크플로우에서 CLI 직접 호출

```yaml
- name: Summarize PR diff
  env:
    ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
  run: |
    git diff origin/main...HEAD > diff.txt
    claude -p "다음 diff를 요약해줘: $(cat diff.txt)"
```

### `claude-code-action`

`claude-code-action`은 GitHub Actions 워크플로우에서 Claude Code를 실행하는 액션입니다. PR이 열리거나 이슈에 코멘트가 달렸을 때 Claude가 자동으로 리뷰·수정·응답하도록 만들 수 있습니다.

**베타에서 v1.0으로의 인터페이스 변화**

베타 시절에는 목적별로 개별 입력 파라미터가 여러 개 있었습니다.

- `direct_prompt` — 직접 전달하는 프롬프트
- `custom_instructions` — 추가 지침
- `mode` — 실행 모드 지정
- `max_turns` — 대화 턴 수 제한

이 방식은 파라미터가 늘어날수록 액션 고유의 이름들을 계속 배워야 하고, CLI에서 쓰던 표기와 달라 혼란스러웠습니다. 같은 개념이 CLI와 액션에서 다른 이름을 갖는 상황이었습니다.

**v1.0의 설계 방향**은 세 가지로 요약됩니다.

1. **프롬프트 입력의 단일화(unify)**: 여러 프롬프트 관련 입력을 **단일 `prompt` 파라미터**로 통합했습니다.
2. **CLI와의 정렬(align)**: 나머지 세부 설정은 **`claude_args`** 에 담아 전달합니다. Claude Code CLI에 넘기는 인자와 같은 형태이므로 CLI에서 알던 지식이 그대로 재사용되고, 액션 전용 이름을 따로 외울 필요가 줄어듭니다.
3. **실행 모드 자동 감지(auto-detect)**: 이벤트 맥락(이슈 코멘트인지, PR 리뷰인지, 워크플로우 직접 실행인지 등)을 보고 실행 모드를 스스로 판단하므로 `mode`를 명시할 필요가 없어졌습니다.

```yaml
- uses: anthropics/claude-code-action@v1
  with:
    prompt: "이 PR을 리뷰하고 보안 문제를 지적해줘"
    claude_args: "--max-turns 10 --allowed-tools Read,Grep"
```

**오해하기 쉬운 지점들:**

- 커스텀 지침이나 턴 제한 기능이 **없어진 것이 아닙니다.** Anthropic API가 자동으로 관리하게 된 것도 아닙니다. 표현 위치가 `claude_args` 쪽으로 옮겨졌을 뿐, 기능 자체는 살아 있습니다.
- 단순한 **이름 변경(rename)이 아닙니다.** `prompt_text`, `instructions`, `execution_mode`, `max_steps` 같은 새 이름으로 1:1 대응된 것이 아니라, 구조 자체가 통합·재편되었습니다.
- 저장소 루트의 **단일 `config.yml`로 모든 설정을 강제하고 환경 변수를 대체하는 방식도 아닙니다.** 설정은 여전히 워크플로우 YAML 안의 액션 입력으로 전달됩니다.

**마이그레이션 시 사고방식**: "이 파라미터의 새 이름은 무엇인가?"가 아니라, **"이 설정은 통합된 `prompt`에 속하는가, 아니면 CLI 인자로서 `claude_args`에 속하는가?"** 를 묻는 것이 맞습니다.
