# 시나리오5_고객지원

## 질문 1

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : Many customers share a phone number on family plans, so when the agent looks up an account by phone, get_customer often returns several accounts; the agent picks one and sometimes applies billing credits to the wrong household member. What should you change?

**A.** Have the agent apply the credit to the account flagged as the primary plan holder and ask the customer to confirm once the credit posts.

**설명**

기본 요금제 소유자 플래그는 신원 확인이 아니라 하나의 휴리스틱일 뿐이며, 조치가 끝난 뒤에 확인하는 방식은 금융 관련 작업에는 너무 늦다. 추측이 틀렸다면 다른 사람이 이의를 제기하기도 전에 이미 다른 가구 구성원의 계정에 크레딧이 적용된 상태가 된다.

**B(정답).** Instruct the agent to request a distinguishing identifier (email, account number, or a recent order) before applying any account-specific change.

**설명**

이 방법이 정답인 이유는, 어떤 계정이 자신의 것인지 확실히 아는 것은 고객뿐이므로 한 번의 확인 질문으로 모호성을 안정적으로 해소할 수 있기 때문이다. 어떤 선택 휴리스틱을 사용하더라도 잘못된 계정에 조치를 취할 가능성이 0이 아니며, 이는 청구 크레딧 같은 금융 조치에서는 허용될 수 없다.

**C.** Modify get_customer to rank the candidate accounts and return only the single highest-scoring one so the agent never sees ambiguous results.

**설명**

모호성을 도구 내부에 숨긴다고 해서 사라지는 것은 아니다. 순위 산정 알고리즘이 여전히 잘못된 가구 구성원을 선택할 수 있고, 이제 에이전트는 명확화 단계가 필요하다는 신호 자체를 받지 못한다. 다중 일치 상태를 숨기면 잘못된 계정 오류가 줄어드는 것이 아니라 오히려 발견하기 어려워질 뿐이다.

**D.** Route every phone lookup that returns multiple accounts to escalate_to_human so a person settles the identity question.

**설명**

다중 일치는 흔히 발생하며 쉽게 해결되는 상황일 뿐, 상담원에게 직접 요청하거나 정책상의 공백이 있는 경우와 같은 진짜 에스컬레이션 트리거가 아니다. 이를 일괄적으로 에스컬레이션하면 에이전트가 확인 질문 한 번으로 해결할 수 있는 사례에 상담 인력을 소모하게 되며, 최초 접촉 해결률 목표를 직접적으로 훼손한다.

### 전반적인 설명

전화번호처럼 공유되는 속성으로 조회했을 때 여러 후보 계정이 반환된다면, 이는 신원 모호성 문제이며 가장 안정적인 해결책은 실제로 답을 아는 유일한 주체인 고객으로부터 추가 정보를 얻는 것이다. 이메일 주소, 계정 번호, 최근 주문 내역과 같은 구분 식별자를 요청하면 불확실한 추측을 확정적인 일치로 바꿀 수 있다. 비용은 대화 한 턴을 추가하는 것뿐이며, 이를 통해 잘못된 가구 구성원에게 청구 크레딧과 계정 변경이 적용되는, 금전적으로도 손해이고 고객 신뢰도 훼손하는 오류 유형을 제거할 수 있다.

여기서 가져야 할 사고 모델은 "휴리스틱은 추정하고, 식별자는 검증한다"는 것이다. 기본 요금제 소유자, 가장 최근 활동한 계정, 또는 가장 높은 일치 점수를 선택하는 방식은 대부분의 경우 맞을 수 있지만, 확률적 추측에 근거해 계정별 조치를 취하는 에이전트는 결국 잘못된 사람의 데이터에 조치를 취하게 된다. 최상위 순위 항목만 반환하도록 휴리스틱을 도구 내부로 옮기는 것은 프롬프트에 남겨두는 것보다 오히려 더 나쁠 수 있는데, 이는 명확화를 촉발해야 할 신호(다중 일치가 존재한다는 사실) 자체를 에이전트에게서 빼앗기 때문이다. 조치 후 확인 방식은 올바른 순서를 뒤집는 것으로, 검증은 금융 작업에 앞서야 하며 뒤따라서는 안 된다. 모든 다중 일치 사례를 상담원에게 에스컬레이션하는 것은 정반대의 실패로, 일상적인 모호성 해소를 정책 공백이나 상담원에 대한 명시적 요청처럼 취급하여 에스컬레이션 역량을 소모시키고 최초 접촉 해결률을 떨어뜨린다.

Claude는 대화와 도구 정의를 바탕으로 도구를 선택하고 매개변수를 지정하므로, 모호성 해소 규칙은 에이전트의 지침에 포함되어야 한다. 즉 다중 일치가 발생하면 조치를 취하기 전에 먼저 물어보도록 해야 한다. 도구 결과가 모델의 다음 결정에 어떻게 반영되는지에 대해서는 tool use 개요를 참고하라. 바로 이 지점이 에이전트가 추측 대신 명확화를 요청하도록 지시할 수 있는 시점이다.

## 질문 2

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : The coordinator completes a multi-turn investigation of a billing dispute, then spawns a resolution subagent that re-fetches customer data and misstates the disputed amounts. How should the coordinator hand its findings to the subagent?

**A.** Have the resolution subagent re-run get_customer and lookup_order at the start of its task to rebuild the case state from source systems.

**설명**

재조회는 백엔드의 원시 레코드는 복구하지만, 근본 원인 분석, 고객이 밝힌 기대사항, 대화 중에 이미 내려진 결정과 같은 조사 결론은 복구하지 못한다. 또한 도구 호출이 중복되고 지연이 늘어나는데, 이는 코디네이터가 제거해야 할 낭비적 행동 그 자체다.

**B.** Rely on the subagent automatically inheriting the coordinator's conversation history, since the Task tool spawns it within the same session.

**설명**

이 방법은 실패한다. 서브에이전트는 부모의 대화 이력이나 이전 도구 결과를 상속받지 않기 때문이다. 서브에이전트가 이전 작업으로부터 필요로 하는 모든 것은 프롬프트에 명시적으로 포함되어야 하므로, 상속을 신뢰하면 서브에이전트는 조사 결과 없이 작업을 시작하게 된다.

**C.** Write the investigation findings into the project CLAUDE.md so the subagent picks them up as part of its startup context.

**설명**

CLAUDE.md는 정적이고 공유되는 프로젝트 설정 파일이며, 사례별 트랜잭션 데이터를 전달하는 채널이 아니다. 고객 분쟁마다 버전 관리되는 메모리 파일을 수정하는 것은 안티패턴으로, 팀 전체가 공유하는 가이드에 일시적인 사례 상태를 오염시킨다.

**D(정답).** Compile a structured summary of the findings (customer ID, disputed amounts, decisions made) and include it in the delegation prompt.

**설명**

이 방법이 정답인 이유는, 서브에이전트가 격리된 컨텍스트에서 동작하며 코디네이터의 대화 이력이나 이전 도구 결과를 자동으로 상속받지 않기 때문이다. 조사 결과는 위임 프롬프트에 명시적으로 전달되어야 하므로, 그곳에 구조화된 요약을 배치하는 것이 안정적인 인계 메커니즘이다.

### 전반적인 설명

Claude Agent SDK에서 서브에이전트는 자체적으로 격리된 컨텍스트를 가진 별도의 에이전트 인스턴스다. 코디네이터의 대화 이력, 이전 도구 결과, 코디네이터가 이미 읽은 파일을 자동으로 상속받지 않는다. 중간 작업 내용은 각 에이전트 내부에 머물고, 최종 결과만 부모에게 전달된다. 이러한 격리는 의도된 설계다. 코디네이터의 컨텍스트를 방대한 중간 작업으로부터 보호하고 특화된 지침을 깨끗하게 적용할 수 있게 하지만, 그 대가로 명시적인 인계가 필요해진다. 여기서 가져야 할 사고 모델은 "프롬프트에 넣지 않으면 아무것도 공유되지 않는다"는 것이다.

그래서 단계 전환의 올바른 패턴은, 완료된 단계를 식별자, 금액, 결정 사항, 제약 조건 등을 포함한 구조화된 블록으로 요약하여 다음 서브에이전트의 위임 프롬프트에 직접 주입하는 것이다. 문제에서 나타난 증상들, 즉 중복된 데이터 조회와 잘못 기재된 금액은 이러한 인계 없이 서브에이전트가 생성되었을 때 나타나는 전형적인 징후다.

각 대안은 각기 다른 메커니즘에서 실패한다. 서브에이전트가 코디네이터의 세션 이력을 상속받을 것이라 기대하는 것은 존재하지 않는 공유 모델을 가정하는 것이다. 서브에이전트는 해당 이력 없이 시작되며, 필요한 것은 명시적으로 주어져야 한다. CLAUDE.md는 세션 전체에서 공유되는 정적 프로젝트 메모리로 로드되므로, 고객별 사례 사실을 그 안에 채워 넣으면 버전 관리에 남을 이유가 없는 일시적 상태로 공유 설정을 오염시키게 된다. get_customer와 lookup_order를 재실행하면 원시 레코드는 재구성되지만, 조사 과정에서 만들어진 대화상의 사실과 판단은 복구할 수 없으며 도구 트래픽만 두 배로 늘어난다.

서브에이전트의 컨텍스트가 어떻게 구성되는지에 대해서는 Claude Agent SDK의 Subagents와 Claude Code subagents를 참고하라.

## 질문 3

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : QA currently reviews only cases the agent escalates; resolutions the agent completes autonomously go unreviewed. You need ongoing assurance that these unreviewed resolutions remain accurate and that novel error patterns surface early. What should you implement?

**A.** Audit every autonomous resolution for one quarter, then discontinue review once aggregate accuracy exceeds the target threshold.

**설명**

일회성 감사는 미래의 동작에 대해서는 아무것도 증명하지 못한다. 고객 행동, 정책, 요청의 구성비는 계속 변하며, 집계된 정확도 수치는 실패하고 있는 특정 이슈 유형을 가려버릴 수 있다. 감사 후 모든 측정을 중단하면 드리프트와 새로운 오류 패턴을 감지하는 데 필요한 계측을 정확히 제거하는 셈이 된다.

**B.** Have the agent self-rate its confidence on each resolution and route only the low-confidence ones to QA for human review.

**설명**

모델이 스스로 평가하는 확신도는 보정이 잘 되어 있지 않으며, 가장 위험한 오류는 에이전트가 확신을 갖고 틀리는 경우다. 에이전트가 스스로 낮은 확신도로 표시한 사례만 검토하면, 확신을 갖고 잘못 처리한 사례는 영구히 검토 대상에서 빠지게 된다.

**C.** Monitor customer complaint and case-reopen rates, treating any sustained rise in either signal as evidence that resolution quality has slipped.

**설명**

불만 제기와 케이스 재오픈은 지연되고 불완전한 신호다. 특히 고객에게 유리한 오류나 고객이 인지하지 못하는 오류는 불만으로 이어지지 않는 경우가 많다. 이 신호에만 의존하면 조용히 확산되는 오류 패턴이 오랫동안 발견되지 않을 수 있다.

**D(정답).** Draw a stratified random sample of autonomous resolutions across issue types and review it on an ongoing basis to measure error rates.

**설명**

이 방법이 정답인 이유는, 계층화 무작위 샘플링이 더 이상 체계적인 검토를 받지 않는 바로 그 모집단을 계속해서 측정하며, 이슈 유형별로 계층화함으로써 반품, 청구 분쟁, 계정 문제가 각각 대표성 있게 포함되기 때문이다. 지속적인 샘플링은 기존의 어떤 플래그나 불만으로도 드러나지 않는 드리프트와 새로운 오류 패턴을 잡아내는 견고한 방법이다.

### 전반적인 설명

여기서 핵심 문제는 측정 공백이다. 한 부류의 작업이 완전히 자동화되어 검토를 받지 않게 되면, 그것이 여전히 올바르게 수행되고 있는지 알 방법을 잃게 된다. 계층화 무작위 샘플링은 이른바 "안전하다"고 여겨지는 모집단 중 무작위로 선택된 일부를 지속적으로 감사함으로써 이 문제를 해결한다. 이때 샘플을 세그먼트(반품, 청구 분쟁, 계정 문제 등 이슈 유형)별로 계층화하면, 작지만 심하게 실패하고 있는 세그먼트가 건강한 평균 속에 숨을 수 없게 된다. 무작위 선택이 중요한 이유는 누군가 실패 모드를 사전에 예측할 필요가 없다는 점이다. 다른 신호도 간혹 발견에 도움이 될 수 있지만, 무작위 샘플링은 기존의 어떤 규칙, 플래그, 분류기도 감시하지 않는 새로운 오류 패턴을 드러내는 특히 견고한 방법이다.

각 대안은 모두 같은 결함을 공유한다. 이미 신호가 존재하는 곳만 살핀다는 점이다. 불만 및 재오픈 비율은 고객이 알아차리고 제기하는 오류만 감지하며, 고객에게 유리한 잘못된 환불과 같은 조용한 실패는 놓친다. 이는 유용한 보조 지표이지만 그것만으로는 충분하지 않다. 에이전트의 자기 평가 확신도로 검토 대상을 선정하는 방식은 자기 평가의 알려진 신뢰성 부족을 그대로 이어받는다. 모델은 체계적으로 틀리는 사례에 대해 오히려 가장 확신을 가지는 경우가 많으므로, 그러한 사례는 검토자에게 절대 도달하지 못한다. 일회성 전면 감사 후 검토를 중단하는 방식은 한 시점의 스냅숏을 지속적인 모니터링과 혼동하는 것이며, 집계된 통과 기준은 (예를 들어 청구 분쟁처럼) 훨씬 높은 오류율을 가진 세그먼트를 감출 수 있다.

프로덕션에 적용할 사고 모델은 다음과 같다. 인적 검토를 줄이는 것은 측정의 필요성을 줄이는 것이 아니라 오히려 늘리는 것이다. 왜냐하면 이제 오류가 검증 없이 고객에게 그대로 흘러가기 때문이다. Claude 기반 시스템 평가에 대한 Anthropic의 가이드는 일회성 검증보다는 대표성 있는 사례에 대한 지속적인 경험적 측정을 강조한다. Create strong empirical evaluations를 참고하고, 관련 설계 가이드로 Anthropic의 엔지니어링 글 Building effective agents도 참고하라.

**설명**

**설명**

**D.** Verify that the agent's self-rated confidence exceeded a calibrated threshold on every case included in the audit sample.

**설명**

### 전반적인 설명

올바른 사고 모델은 정확도는 정의된 세그먼트에 대해서만 의미가 있다는 것이다. Anthropic의 평가 가이드는 단일 전역 점수를 신뢰하기보다 측정 가능하고 과제에 특화된 성공 기준을 정의하고 그에 대해 평가를 구축할 것을 강조한다. Define your success criteria와 Create strong empirical evaluations를 참고하라. 실무적으로는 이슈 카테고리별로(추출형 출력의 경우 필드별로도) 결과를 분해하고, 감독을 줄이기 전에 모든 세그먼트에서 성능 하한선을 확인해야 한다는 의미다.

## 질문 5

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : You are writing the escalation section of the agent's system prompt and must define behavior for two openings: an explicit demand for a human, and an angry complaint with no such demand. Which rule pair is correct?

**A.** Escalate immediately in both situations, since anger and a human request both signal lost confidence in automated handling.

**설명**

불만 그 자체는 에스컬레이션 트리거가 아니다. 많은 화난 고객들은 에이전트가 감정을 인정하고 문제를 빠르게 해결해주면 만족한다. 부정적으로 시작하는 모든 대화를 에스컬레이션하면, 에이전트가 충분히 처리할 수 있는 사례에서도 최초 접촉 해결률이 80% 목표를 크게 밑돌게 된다.

**B.** Apply a sentiment threshold to both situations, escalating whenever measured negativity exceeds a calibrated level regardless of wording.

**설명**

감정 분석은 에스컬레이션이 필요한지를 판단하는 데 신뢰할 수 없는 대체 지표다. 고객의 기분은 사례의 복잡도나 고객의 실제 선호와 상관관계가 없기 때문이다. 또한 차분한 말투이지만 명시적으로 상담원을 요청하는 경우를 무시할 위험도 있는데, 이는 항상 존중되어야 한다.

**C(정답).** Escalate at once on an explicit request for a human; for frustration without such a request, acknowledge it and offer a resolution first.

**설명**

이것이 두 패턴을 올바르게 짝지은 방법이다. 상담원에 대한 명시적 요청은 즉시 존중되어야 할 최우선 트리거이며, 단순한 불만은 감정을 인정하고 구체적인 해결책을 제시한 뒤, 고객이 그 후에도 사람을 원한다고 고집할 때만 에스컬레이션하는 방식으로 처리한다.

**D.** Acknowledge the emotion and offer one resolution attempt in both situations, escalating only if the customer restates the demand afterward.

**설명**

명시적인 상담원 요청에 "인정 후 해결" 패턴을 적용하면 고객이 이미 명확히 밝힌 요구를 다시 반복하게 만든다. 해결을 시도하기 위해 고객이 밝힌 선호를 무시하는 것은, 그 문제가 얼마나 쉽게 해결될 수 있어 보이든 상관없이 신뢰를 훼손한다.

### 전반적인 설명

에스컬레이션 설계는 "누가 결정하는가"와 "사례가 얼마나 어려운가"를 분리한다. 고객이 명시적으로 상담원을 요청하면 그 결정은 이미 고객이 내린 것이며, 에이전트의 역할은 먼저 자신의 능력을 증명하려 하지 않고 escalate_to_human을 호출해 즉시 그 요청을 존중하는 것이다. "더 나은 인계를 위해서"라는 명목으로 해결을 시도하거나 심지어 조사를 계속하는 것은, 고객이 명시적으로 에이전트에게 닫아버린 사례에 대해 작업을 계속하는 것이며, 근본적인 문제가 아무리 쉽게 해결 가능해 보이더라도 신뢰를 훼손한다.

명시적 요청이 없는 불만은 완전히 다른 신호다. 이에 대해 문서화된 패턴은 미묘하다. 감정을 인정한 뒤 구체적인 해결책을 제시하고, 고객이 사람을 원한다고 다시 밝힐 때만 에스컬레이션한다. 이는 화가 났지만 해결 가능한 대다수 사례에서 최초 접촉 해결률을 유지하면서도, 고객의 판단이 명시되는 순간에는 그것을 존중한다. 신뢰할 수 있는 트리거는 행동적이고 명시적인 것들이다. 상담원에 대한 명시적 요청, 정책 공백이나 예외, 또는 진정으로 진행이 불가능한 상태가 그것이다.

감정 점수나 모델의 자기 평가 확신도 같은 대체 지표는 좋은 대안이 되지 못한다. 이들은 사례의 복잡도나 고객의 의도가 아니라 기분이나 자기 인식을 측정하기 때문이다. 감정 임계값은 과도한 에스컬레이션(일상적인 문제인데 화가 난 고객)과 부족한 에스컬레이션(차분하고 예의 바르게 "상담원에게 연결해 주세요"라고 말하면 중립으로 채점될 수 있음)을 동시에 유발한다. 시스템 프롬프트에 명시적인 기준을 두고, 이상적으로는 에스컬레이션할 때와 해결을 시도할 때를 보여주는 few-shot 예시로 보강하면, 에이전트가 실제로 적용할 수 있는 결정 경계를 갖게 된다. 권장되는 사람에게 넘기는 인계 패턴에 대해서는 Anthropic의 고객 지원 에이전트 가이드를 참고하라.

**설명**

이는 긴 세션 전반에서 정밀한 트랜잭션 데이터를 보존하기 위한 문서화된 패턴이다. 모든 프롬프트에 포함되는 구조화된 블록은 요약의 대상이 되지 않으므로, 몇 개의 턴이 압축되더라도 금액과 주문 ID는 올바른 이슈에 계속 결부되어 있다.

**설명**

임계값을 높이는 것은 요약이 정밀한 세부 사항을 훼손하는 시점을 늦출 뿐이다. 여러 이슈를 다루는 세션은 결국 그 임계값을 넘어서게 된다. 실패 양상은 그대로 남아있고, 단지 더 긴 세션으로 미뤄질 뿐이다.

### 전반적인 설명

여기서 근본 원인은 점진적 요약의 함정이다. 이전 턴들이 압축될 때, 정밀한 트랜잭션 값(주문 ID, 금액, 상태)이 가장 먼저 모호한 표현으로 흐려지며, 특정 금액과 특정 이슈 사이의 연관 관계가 사라진다. 여러 이슈를 다루는 세션에서는 바로 이 연관 관계가 전부라고 할 수 있는데, 같은 고객이 동시에 여러 주문과 수치를 가지고 있기 때문이다.

신뢰할 수 있는 설계는 지속적인 사례 사실(case facts) 블록이다. 이슈별로(주문 ID, 금액, 상태, 합의된 해결책) 구조화된 레코드를 별도의 컨텍스트 레이어에 두고, 새로운 사실이 나타날 때마다 갱신하며, 대화 이력이 어떻게 압축되든 상관없이 모든 프롬프트에 포함시킨다. 이 블록은 절대 요약되지 않으므로, 세션이 얼마나 길어지든 정밀성이 유지된다. Anthropic의 memory tool은 바로 이런 종류의 상태를 활성 컨텍스트 윈도우 바깥에 지속시키기 위한 문서화된 메커니즘이며, 애플리케이션이 저장소를 직접 제어한다. 또한 structured outputs를 사용하면 이런 블록을 채울 스키마 검증된 이슈별 레코드를 생성할 수 있다.

각 대안은 모두 증상만 공격한다. 요약 프롬프트를 강화하는 방법은 중요한 데이터를 여전히 손실 가능한 경로에 남겨둔다. 지침이 잘 작성된 요약기라도 간혹 수치를 빠뜨리거나 잘못 귀속시키며, 요약 단계가 반복될수록 위험이 누적된다. 매 턴마다 주문을 재조회하는 방법은 백엔드의 진실을 복구하지만 방대한 다중 필드 결과로 컨텍스트를 채우며, 고객이 어떤 이슈에 대해 어떤 환불 금액을 받아들였는지와 같은 대화상의 사실은 여전히 재구성할 수 없다. 요약 임계값을 높이는 것은 절벽을 단순히 뒤로 미루는 것일 뿐이다. 가져야 할 사고 모델은, 정확해야 하는 것은 요약이 그것을 살려낼 수 있는지에 절대 의존해서는 안 된다는 것이다.

**QUESTION** : The agent escalates "data inconsistency" cases whenever the store credit figure in its case facts block differs from a fresh get_customer result after a mid-session refund posts. Which change prevents this misinterpretation?

**A.** Store only one value per field in the case facts block, overwriting on each update so conflicting entries never coexist.

**설명**

암묵적인 덮어쓰기는 시간적 측면을 표현하지 않고 숨겨버린다. 에이전트는 환불 전 잔액이 얼마였는지에 대한 기록을 잃게 되는데, 이는 변경 사항을 고객에게 설명하고 세션 중 취해진 조치를 감사하는 데 필요하다.

**설명**

모든 불일치를 에스컬레이션하는 것은 정상적인 상태 전환을 결함으로 취급하는 것이며, 이는 상담원에게 일상적인 사례가 쏟아지게 만들어 최초 접촉 해결률 목표를 훼손한다. 여기서의 불일치는 환불 이후 예상되는 정상적인 동작이며, 백엔드 무결성 문제가 아니다.

**설명**

일괄적인 최신성 규칙은 해석 메커니즘이 아니라 하나의 휴리스틱일 뿐이다. 이력이 요약되고 나면 대화상의 위치는 신뢰할 수 없게 되며, 나중에 언급된 값을 무조건 선호하는 방식은 실제로 조사나 에스컬레이션이 필요한 진짜 데이터 충돌마저 조용히 무시해버릴 수 있다.

**D(정답).** Record a capture timestamp alongside each fact in the case facts block so a later value is read as superseding the earlier one.

**설명**

이 방법이 정답인 이유는, 두 수치가 서로 충돌하는 것이 아니라 상태 변경 전과 후에 찍힌 동일 계정의 스냅숏이기 때문이다. 구조화된 사실에 수집 시각을 함께 기록하면 에이전트가 그 차이를 시간순으로 해석할 수 있게 되어, 환불이 잔액을 갱신한 것일 뿐 모순된 데이터가 드러난 것이 아니라는 것을 인식할 수 있다.

### 전반적인 설명

같은 필드에 대한 두 개의 다른 값이 모순이 되는 것은, 그 값들이 같은 시점을 나타낼 때뿐이다. 세션 중간에 환불이 처리되면 스토어 크레딧 잔액은 정당하게 변경되므로, 이전에 기록된 사실과 새로 조회한 도구 결과는 설계상 서로 다르게 나타난다. 여기서의 실패는 백엔드 데이터에 있는 것이 아니라, 에이전트의 컨텍스트가 그것을 표현하는 방식에 있다. 사례 사실 블록에 있는 단순한 숫자는 그것이 언제 참이었는지에 대한 표시를 전혀 담고 있지 않으므로, 에이전트는 상태 변화와 충돌을 구분할 방법이 없다.

해결책은 시간을 구조화된 출력의 1급 요소로 만드는 것이다. 각 사실에 수집 시각을 함께 기록하면 에이전트가 시간순으로 추론할 수 있게 된다. 즉 더 새로운 스냅숏이 이전 것을 대체하며, 이전 값은 감사 기록으로 계속 사용할 수 있다(고객이 환불 이전 금액을 언급할 때 유용하다). 이는 여러 출처를 종합하는 리서치에서 발행일과 수집일이 시간적 차이를 모순된 주장으로 잘못 해석하지 않도록 방지하는 것과 같은 원리이며, 여기서는 세션 내 도구 데이터에 적용된 것이다.

각 대안은 각기 특징적인 방식으로 실패한다. 나중에 언급된 값을 선호하는 프롬프트 규칙은 대화상의 순서에 의존하는데, 이는 요약이 이루어지면 신뢰도가 떨어지며, 주의가 필요한 진짜 충돌마저 감출 수 있다. 필드를 덮어써서 하나의 값만 남기는 방법은 불일치를 해석하는 대신 억누르는 것이며, 변경 사항을 설명하는 데 필요한 이력을 파괴한다. 모든 불일치를 에스컬레이션하는 것은 일상적이고 예상되는 상태 전환을 인적 업무로 전환시켜, 높은 최초 접촉 해결률 목표에 정면으로 반한다. 견실한 컨텍스트 엔지니어링이란 모델이 올바르게 추론할 수 있도록 윈도우에 들어가는 내용을 구조화하는 것이며, 필요한 정보를 제거하거나 순서만 바꾸는 것이 아니다. **SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : During multi-turn testing, the agent loses track of details customers provided two turns earlier. Logs show each API request contains only the system prompt and the newest user message. What change restores conversational coherence?

**A(정답).** Include all prior user and assistant turns, along with tool results, in the messages array of every request.

**설명**

Messages API는 상태를 저장하지 않으므로, Claude는 이전 API 호출에 대한 기억이 없다. 대화의 연속성은 애플리케이션이 누적된 이력을 다시 전송할 때만 존재한다. 어시스턴트의 답변과 도구 결과를 포함해 이전의 모든 턴을 전달하는 것이, 다중 턴에서 일관성을 유지하기 위해 설계된 메커니즘이다.

**B.** Reference the previous response's message ID in each new request so the API links the turns into one session.

**설명**

Messages API에는 세션이나 메시지 ID를 연결하는 메커니즘이 없다. /v1/messages에 대한 각 POST 요청은 완전히 독립적이다. 이전 턴이 응답에 영향을 미칠 수 있는 유일한 방법은 현재 요청의 messages 배열에 그것들을 포함시키는 것이다.

**C.** Add cache_control breakpoints to earlier turns so the API retains the conversation server-side between calls.

**설명**

프롬프트 캐싱은 반복되는 프롬프트 접두사에 대한 비용과 지연 시간을 줄여주지만, 서버 측 대화 상태를 만들어내지는 않는다. 캐시된 접두사도 여전히 요청에 포함되어 전송되어야 한다. 캐싱은 성능 최적화 기법이지, 메모리 메커니즘이 아니다.

**D.** Move key customer details into the system prompt at session start so they persist across subsequent calls.

**설명**

세션 시작 시점에 설정된 것은 서버에 지속되지 않는다. 시스템 프롬프트는 실제로 그것을 포함한 요청에만 적용된다. 매번 다시 전송하더라도, 고정된 시스템 프롬프트는 대화가 진행되는 동안 턴마다 새로 드러나는 세부 사항을 담아낼 수 없다.

### 전반적인 설명

여기서 핵심 사고 모델은, Claude의 Messages API가 상태를 저장하지 않는다는 것이다. POST /v1/messages에 대한 각 호출은 독립적인 요청이며, 모델은 오직 그 요청에 포함된 내용만을 근거로 다음 메시지를 생성한다. 세션 ID도 없고, 서버 측 대화록도 없으며, 이전 호출에 대한 자동적인 기억도 없다. 지속되는 대화라는 착각은 완전히 애플리케이션 계층이 만들어내는 것으로, 사용자와 어시스턴트가 번갈아 주고받는 턴(tool_result 콘텐츠 포함)을 누적하고 매 요청마다 messages 배열에 전체 이력을 다시 전송함으로써 생긴다. 로그에 가장 최신의 사용자 메시지만 전송되고 있는 것으로 나타난다면, 에이전트가 "잊어버린" 것이 아니라 애초에 이전 턴들을 전혀 받지 못한 것이다.

이 설계는 의도적인 것이다. 무상태성은 API를 단순하고 수평적으로 확장 가능하게 유지하며, 애플리케이션에 모델이 보게 될 내용에 대한 완전한 제어권을 준다. 이를 통해 방대한 도구 출력을 정리하거나, 지속적인 사례 사실 블록을 유지하거나, 합성된 어시스턴트 메시지를 주입하는 등의 기법을 활용할 수 있다. 그 제어권의 대가는 이력 관리가 여러분의 책임이 된다는 것이다.

여기서 흔히 있는 오해들은 내면화할 가치가 있다. 프롬프트 캐싱(cache_control)은 반복되는 접두사의 처리 속도를 높이고 비용을 할인해주지만, 접두사는 여전히 매 요청마다 함께 전송되어야 하며 대화 상태를 저장하지는 않는다. API에는 메시지 ID나 세션 연결 파라미터가 없으므로, 이전 응답을 참조한다고 해서 컨텍스트를 재구성할 수는 없다. 또한 "세션 시작 시점에" 설정된 시스템 프롬프트도 지속성을 갖지 않는다. 그것을 포함한 요청에만 영향을 미치며, 대화 중간에 드러나는 세부 사항을 담아둘 수 없다. 다중 턴 요청이 어떻게 구성되는지는 Working with Messages와 Messages API reference를 참고하라.

이 방법이 정답인 이유는, 콘텐츠 유형마다 자연스러운 표현 방식이 있기 때문이다. 숫자로 된 금융 데이터는 표로 볼 때 가장 정확하게 훑어볼 수 있고, 서사적 맥락은 일반 문장으로 읽는 것이 가장 좋으며, 개별적으로 완료된 조치는 목록에 속한다. 형식을 콘텐츠 유형에 맞추면 금액이 문장 속에 묻히거나 단계가 누락되는 것을 방지할 수 있다.

### 전반적인 설명

여기서 설명된 실패는 일률적 형식 종합 문제다. 서로 다른 유형의 콘텐츠(수치, 서사, 개별 조치)가 하나의 표현 방식으로 눌려버렸고, 각 콘텐츠 유형은 각기 다른 방식으로 피해를 입었다. 문장 중간에 삽입된 금액은 잘못 읽기 쉽고, 문장 형태로 작성된 일련의 시도된 조치는 놓치기 쉬워 상담원이 이미 한 작업을 반복하게 된다. 신뢰할 수 있는 설계 원칙은 콘텐츠 유형에 따라 표현 방식을 달리하는 것이다. 금융 데이터는 표로, 설명적인 배경은 일반 문장으로, 기술적이거나 절차적인 사항은 구조화된 목록으로 표현한다.

이것이 효과적인 이유는 형식이 단순한 장식이 아니라, 독자가 정보를 찾고 검증하는 방식 자체이기 때문이다. 표는 모든 수치에 라벨이 붙은 위치를 부여하므로, 89.99달러의 환불액이 문단 속에 숨을 수 없다. 목록은 각 시도된 조치를 개별적으로 확인 가능한 항목으로 만든다. 일반 문장은 사건들 사이의 관계가 훑어보기보다 더 중요한 분쟁의 인과적 서사를 전달하는 데 여전히 적합한 수단이다. Anthropic의 프롬프팅 가이드도 이를 뒷받침한다. 모델이 알맞은 표현 방식을 스스로 추론할 것이라고 가정하기보다, 원하는 출력 형식을 명시적으로 지정하고, 항목이 개별적이거나 순서가 중요할 때는 목록을 사용하며, 형식을 목적에 맞춰야 한다. 특히 Anthropic 자체의 형식 지정 가이드도 모든 곳에서 구조를 없애라고 권장하지 않는다는 점이 눈에 띈다. 마크다운을 최소화하라는 예시에서도 진정으로 개별적인 항목에는 목록을 여전히 허용한다.

일률적인 대안들은 모두 예측 가능한 방식으로 실패한다. 하나의 거대한 표는 서사를 셀 안에 억지로 밀어 넣어 인과적 맥락을 잃게 만든다. 원시 JSON 객체는 명시된 소비자가 대화 기록에 접근할 수 없는 사람 상담원, 즉 읽기 쉽고 자기 완결적인 요약이 필요한 상담원인 상황에서 기계 파싱에 최적화된 방식이다. 형식이 전혀 없는 일반 문장은 단순히 보고된 실패를 그대로 재현할 뿐이다. 출력 형식을 명시적으로 제어하는 방법에 대해서는 Prompt templates and variables를, 출력 형식을 정밀하게 정의하는 방법에 대해서는 Increase output consistency를 참고하라.
