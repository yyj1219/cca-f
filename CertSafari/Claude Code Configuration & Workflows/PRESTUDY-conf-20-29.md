# 사전 학습 노트 — Claude Code 설정과 워크플로 (conf 20-29 대비)

이 문서는 해당 주제를 전혀 모르는 상태에서 시작하는 사람을 위한 개념 정리입니다.
Claude Code라는 도구가 무엇인지, 어떤 파일로 설정하는지, 작업을 어떤 순서로 진행해야 하는지를
바닥부터 설명합니다.

---

## 0. 배경: Claude Code란 무엇인가

Claude Code는 Anthropic이 만든 **터미널(CLI) 기반 코딩 에이전트**입니다.
개발자가 자연어로 요청하면 Claude가 직접 저장소의 파일을 읽고, 검색하고, 수정하고,
셸 명령을 실행합니다.

핵심 특징 세 가지를 먼저 이해하면 나머지가 쉬워집니다.

1. **컨텍스트(context)로 동작한다.**
   Claude는 "지금 대화에 들어와 있는 텍스트"만 알고 있습니다. 저장소에 파일이 있어도
   컨텍스트에 로드되지 않으면 Claude는 그 내용을 모릅니다. 그래서 "무엇을 컨텍스트에
   넣을 것인가"를 설정 파일로 관리합니다.
2. **컨텍스트에는 비용이 있다.**
   로드되는 모든 텍스트는 토큰(token)을 소비합니다. 토큰은 모델이 텍스트를 세는 단위이며
   비용과 처리 한도에 직결됩니다. 그래서 "필요 없는 것은 로드하지 않기"가 중요한 설계 원칙입니다.
3. **파일을 실제로 바꾸고 명령을 실제로 실행한다.**
   따라서 보안(무엇을 자동 실행해도 되는가)과 절차(먼저 계획할 것인가 바로 실행할 것인가)가
   중요한 주제가 됩니다.

## 1. CLAUDE.md — 프로젝트/개인 지침 파일

### 1.1 CLAUDE.md가 무엇인가

`CLAUDE.md`는 Claude Code가 **세션 시작 시 자동으로 읽어 컨텍스트에 넣는 마크다운 파일**입니다.
사람이 신입에게 건네는 "우리 팀 규칙 문서"에 해당합니다. 여기에 적는 대표적인 내용:

- 커밋 메시지 형식 (예: Conventional Commits, 접두어 규칙)
- 테스트 실행 방법 (`npm test`인지 `pytest -q`인지)
- 코드 스타일, 금지 사항, 디렉터리 구조 설명
- 자주 쓰는 명령어 모음

예시:

```markdown
# 프로젝트 규칙

## 커밋
- Conventional Commits 형식 사용: feat: ..., fix: ...

## 테스트
- 전체 테스트: pnpm test
- 단일 파일: pnpm test -- path/to/file.test.ts

## 스타일
- 새 의존성 추가 전 반드시 상의할 것
```

### 1.2 CLAUDE.md의 계층 구조 (매우 중요)

CLAUDE.md는 **한 개가 아니라 여러 위치에 존재할 수 있고, 각각 적용 범위가 다릅니다.**

| 위치 | 이름 | 적용 범위 | 버전 관리 |
|---|---|---|---|
| `~/.claude/CLAUDE.md` | 개인(글로벌) 지침 | 그 사용자의 **모든** 프로젝트 | 안 됨 (개인 머신에만 존재) |
| `<프로젝트 루트>/CLAUDE.md` | 프로젝트 지침 | 그 저장소에서 작업하는 **모든 사람** | 됨 (git에 커밋) |
| 하위 디렉터리의 `CLAUDE.md` | 서브디렉터리 지침 | 해당 디렉터리 작업 시 | 됨 |
| `CLAUDE.local.md` | 개인 로컬 오버라이드 | 본인만 | 보통 gitignore |

여기서 반드시 알아야 할 **핵심 포인트**가 있습니다.

> `~/.claude/CLAUDE.md`(개인 글로벌 파일)에 적은 규칙은 **그 사람의 머신에만** 있습니다.
> git으로 공유되지 않습니다.

이 때문에 생기는 전형적인 사고 시나리오:

- 팀원 A, B, C가 각자 자기 `~/.claude/CLAUDE.md`에 "커밋은 이렇게, 테스트는 이렇게"를 적어 두었다.
- 세 사람 모두 Claude가 규칙을 잘 지키는 것처럼 보인다.
- 저장소 루트의 `CLAUDE.md`는 사실 **빈 파일**이다. 아무도 눈치채지 못한다.
- 신입 D가 저장소를 clone 한다. 저장소 파일은 다 받았지만 A/B/C의 홈 디렉터리 파일은 받을 수 없다.
- D의 Claude는 규칙을 하나도 모른다.

**교훈: 팀 공통 규칙은 반드시 저장소에 커밋되는 프로젝트 `CLAUDE.md`에 적어야 한다.**
개인 글로벌 파일은 "나만의 취향"(예: 답변 언어, 개인 단축 습관)에만 씁니다.

함께 알아둘 사실:

- `CLAUDE.md`는 세션이 시작될 때 **디스크에서 직접 읽습니다.** 머신별로 캐시해 두었다가
  수동으로 캐시를 재빌드해야 하는 구조가 아닙니다. 파일을 고치면 다음 세션에 반영됩니다.
- git은 확장자에 따라 파일을 골라서 체크아웃하지 않습니다. `.md`만 조용히 빠지는 일은 없습니다.
- 빈 파일은 토큰을 거의 쓰지 않으므로 "토큰 한도 초과로 드롭됐다" 같은 설명도 성립하지 않습니다.

### 1.3 `@` 임포트 문법

`CLAUDE.md` 안에서 `@경로` 를 쓰면, Claude Code가 **그 파일의 내용을 읽어 컨텍스트에 붙여 넣습니다.**
이것을 임포트(import)라고 합니다.

```markdown
See @README for project overview and @package.json for available npm commands.
```

이렇게 쓰면 README와 package.json의 **내용 전체가 실제로 로드**됩니다.
CLAUDE.md를 짧게 유지하면서 필요한 문서를 끌어오는 용도입니다.

특징:

- 상대 경로(`@docs/style.md`), 홈 경로(`@~/.claude/personal.md`) 모두 사용 가능합니다.
- 임포트된 파일 안에서 또 임포트할 수 있습니다(중첩). 다만 깊이에 제한이 있습니다.
- 로드된 내용은 토큰을 소비합니다. 큰 파일을 무심코 임포트하면 컨텍스트가 낭비됩니다.

### 1.4 임포트를 **하지 않고** 경로만 언급하는 방법

문서에서 "이 파일도 참고하세요" 정도로 **사람에게만** 알려주고 싶은데,
`@`를 그냥 쓰면 실제로 로드되어 토큰을 잡아먹습니다. 이때의 해법은 **백틱(code span)** 입니다.

```markdown
과거 배경은 `@docs/legacy-notes.md` 를 참고하세요. (사람용 안내이며 로드되지 않음)
```

원리: Claude Code의 임포트 파서는 **마크다운 코드 스팬(백틱 하나로 감싼 구간)과
코드 블록(백틱 세 개로 감싼 구간) 내부를 건너뜁니다.** 그 안의 `@경로`는 실행 지시가 아니라
그냥 리터럴 텍스트로 취급됩니다.

작동하지 **않는** 방법들 (잘못된 통념):

- HTML 주석(`<!-- ... -->`)으로 감싸기 — 임포트를 막는 공식적으로 보장된 방법이 아닙니다.
  게다가 HTML 주석은 렌더링 시 화면에 보이지도 않으므로 "사람에게 보여주기"라는 목적 자체가 깨집니다.
- `@` 와 경로 사이에 공백 넣기 — 공식 이스케이프 규칙이 아닙니다.
- `@` 를 두 번 쓰기 — 그런 이스케이프 문법은 없습니다.

**정리: 로드하려면 맨 `@경로`, 로드 없이 언급만 하려면 백틱으로 감싼다.**

## 2. `.claude/` 디렉터리와 규칙(rules)

### 2.1 `.claude/` 디렉터리

저장소 루트의 `.claude/` 폴더는 Claude Code의 프로젝트 설정 공간입니다. 대표 구성:

```
.claude/
  settings.json        # 권한, 환경 변수, 훅 등 프로젝트 설정 (커밋 대상)
  settings.local.json  # 개인 오버라이드 (보통 gitignore)
  rules/               # 규칙 파일 모음
  skills/              # 스킬(재사용 가능한 절차) 모음
  agents/              # 서브에이전트 정의
```

### 2.2 규칙 파일과 `paths` 범위 지정

`.claude/rules/` 안의 마크다운 파일은 "특정 상황에서 지켜야 할 규칙"을 담습니다.
파일 상단의 **프론트매터(frontmatter)** — 문서 맨 앞에 `---` 로 감싼 YAML 메타데이터 —
에 적용 범위를 지정할 수 있습니다.

```markdown
---
description: 컴포넌트 prop 명명 규칙
paths: ["src/components/**/*.tsx"]
---

- prop 이름은 camelCase로 작성한다.
- boolean prop은 is/has 접두사를 사용한다.
```

`paths`에 적힌 **glob 패턴**과 일치하는 파일을 다룰 때만 이 규칙이 적용됩니다.
관련 없는 규칙이 항상 컨텍스트를 차지하지 않도록 하는 절약 장치입니다.

### 2.3 Glob 패턴 — `*` 와 `**` 의 결정적 차이

glob은 파일 경로를 패턴으로 매칭하는 오래된 표준 문법입니다. 반드시 외워야 할 규칙:

| 패턴 | 의미 |
|---|---|
| `*` | 0개 이상의 문자와 매칭. **단, 디렉터리 구분자 `/` 는 넘지 못한다.** |
| `**` (globstar) | 디렉터리 경계를 넘어 **임의의 깊이**까지 재귀적으로 매칭 |
| `?` | 임의의 한 문자 |
| `{a,b}` | 중괄호 확장(brace expansion). `*.{ts,tsx}` = `.ts` 또는 `.tsx` |

구체적 예시 — 이 차이가 실무 사고의 원인이 됩니다.

```
패턴: src/components/*.tsx

매칭됨:      src/components/Button.tsx
매칭 안 됨:  src/components/forms/Input.tsx     ← * 가 / 를 못 넘음
매칭 안 됨:  src/components/layout/Grid.tsx
```

```
패턴: src/components/**/*.tsx

매칭됨:      src/components/forms/Input.tsx
매칭됨:      src/components/layout/Grid.tsx
매칭됨:      src/components/a/b/c/Deep.tsx
```

전형적인 사고 흐름: 처음에 컴포넌트가 `src/components/` 바로 아래 평평하게 있어서
`src/components/*.tsx`로 잘 작동했다 → 리팩터링으로 `forms/`, `layout/` 같은 하위 폴더로
정리했다 → 규칙이 조용히 적용되지 않는다. 해결은 `**` 를 넣는 것 하나뿐입니다.

**주의할 잘못된 통념:**

- 프로젝트 파일 개수가 일정 수를 넘으면 경로 규칙이 자동으로 꺼진다 → 그런 동작은 없습니다.
- 맨 앞에 `/`를 붙이지 않아서 실패한다 → 깊이 문제와 무관합니다.
- `.tsx`를 인식시키려면 중괄호 확장이 필수다 → 아닙니다. 중괄호는 여러 확장자를 한 번에
  쓰고 싶을 때의 편의 문법일 뿐입니다.

### 2.4 심볼릭 링크(symlink)로 규칙 공유하기

**심볼릭 링크란?** 파일 시스템에서 "다른 경로를 가리키는 바로가기 파일"입니다.
링크를 읽으면 운영체제가 실제 대상 파일로 따라갑니다(이를 resolve, 해제라고 합니다).

```bash
# 중앙 규칙 폴더를 각 저장소에서 참조
ln -s /shared/claude-rules/security.md .claude/rules/security.md   # 파일 단위
ln -s /shared/claude-rules             .claude/rules/org           # 디렉터리 단위
```

**왜 쓰는가:** 조직 전체가 같은 코드 리뷰 규칙을 써야 하는데, 저장소마다 복사해 두면
원본이 바뀔 때 전부 다시 복사해야 합니다(단일 진실 공급원, single source of truth 위배).
심볼릭 링크를 걸면 중앙 원본 하나만 고치면 모든 저장소에 즉시 반영됩니다.

**Claude Code의 동작:**

- `.claude/rules/` 는 심볼릭 링크를 **정상적으로 지원**합니다. 링크를 따라가서 실제 내용을 로드합니다.
- **개별 파일**도, **디렉터리 전체**도 링크할 수 있습니다. 둘 중 하나만 되는 제한은 없습니다.
- 대상이 같은 git 저장소 안에 있을 필요가 없습니다. 저장소 **바깥의 절대 경로**나
  별개의 저장소 폴더를 가리켜도 정상 해제됩니다. git submodule이어야 한다는 제약도 없습니다.
- **순환 참조 감지(circular detection)** 가 내장되어 있습니다. A가 B를, B가 A를 가리키는
  루프가 생겨도 무한 루프에 빠지지 않고 안전하게 처리됩니다.

**따라서 실무에서 확인해야 할 것은 단 하나:** 각 저장소의 링크가 의도한 공유 원본을
정확히 가리키고 있는지(끊어진 링크나 오래된 경로가 아닌지)입니다.

실무 주의사항: git은 심볼릭 링크를 커밋할 수 있지만 Windows에서는 별도 설정
(`core.symlinks`, 개발자 모드 등)이 필요할 수 있습니다. 이는 Claude Code가 아니라
git/OS 차원의 이슈입니다.

## 3. 스킬(Skills)과 권한 모델

### 3.1 스킬이란

스킬(Skill)은 "이런 종류의 작업은 이렇게 해라"를 담은 **재사용 가능한 절차 묶음**입니다.
`SKILL.md` 파일 하나(필요하면 보조 스크립트/문서 포함)로 구성되며,
관련 있는 작업이 들어올 때 로드되어 Claude의 행동 지침이 됩니다.

두 가지 저장 위치:

| 위치 | 범위 | 특징 |
|---|---|---|
| `~/.claude/skills/<name>/SKILL.md` | 개인 스킬 | 내 모든 프로젝트에서 사용, 내가 직접 작성 |
| `.claude/skills/<name>/SKILL.md` | 프로젝트 스킬 | 저장소에 커밋되어 팀 공유, clone 시 함께 들어옴 |

### 3.2 SKILL.md 프론트매터

```markdown
---
name: publish
description: npm 패키지를 배포한다. 릴리스/퍼블리시 요청 시 사용.
allowed-tools: Bash(npm publish *)
---

1. 테스트를 실행한다.
2. 버전을 올린다.
3. npm publish 를 실행한다.
```

- `name` — 스킬 이름.
- `description` — 언제 이 스킬을 써야 하는지. 모델이 이걸 보고 선택합니다.
- `allowed-tools` — **이 스킬이 실행되는 동안 사용자 승인 없이 자동 실행해도 되는 도구/명령의
  사전 승인 목록.** `Bash(npm publish *)` 는 "`npm publish`로 시작하는 bash 명령"을 뜻합니다.
- `context: fork` 같은 선언은 스킬을 별도의 서브에이전트에서 돌릴지를 정하는 별개의 옵션이며,
  `allowed-tools`가 동작하기 위한 전제 조건이 **아닙니다.** `allowed-tools`는 포크 여부와
  무관하게 유효합니다.

기억할 점: 명령의 자동 승인은 `allowed-tools`에 적습니다. `arguments` 같은 다른 필드에
명령을 적는 것은 올바른 문법이 아닙니다.

### 3.3 워크스페이스 신뢰(Workspace Trust) — 보안의 관문

여기가 스킬 권한에서 가장 중요한 개념입니다.

**문제 상황을 먼저 생각해 봅시다.** 인터넷에서 아무 저장소나 clone 했는데,
그 저장소 안에 `.claude/skills/` 가 들어 있고 위험한 명령이 `allowed-tools` 로
사전 승인되어 있다면? 저장소를 여는 것만으로 악성 명령이 승인 없이 실행될 수 있습니다.
이것은 심각한 공급망 공격 경로입니다.

**Claude Code의 방어책:** 처음 보는 프로젝트를 열면 **워크스페이스 신뢰 대화상자**가 뜹니다.
"이 폴더의 파일을 신뢰하고 실행을 허용하시겠습니까?" 라고 묻는 것입니다.

- 사용자가 **수락하기 전까지**, 저장소에 커밋되어 들어온 프로젝트 스킬의 `allowed-tools`
  사전 승인 권한은 **효력이 없습니다.**
- 결과적으로 스킬을 호출해도 `npm publish` 같은 명령마다 **매번 수동 승인 창**이 뜹니다.
- 대화상자를 닫아 버렸거나 무시했다면, 사전 승인이 적용되지 않는 것이 정상 동작이며 버그가 아닙니다.

**따라서 "clone 한 프로젝트 스킬의 allowed-tools가 먹히지 않는다"의 1순위 원인은 신뢰 미수락입니다.**

부수적으로 정리해 둘 사실:

- `allowed-tools`는 개인 스킬(`~/.claude/skills/`)만의 기능이 아닙니다.
  프로젝트 스킬에서도 쓸 수 있습니다. 다만 프로젝트 스킬은 워크스페이스 신뢰가 전제됩니다.
  이 비대칭은 합리적입니다 — 개인 스킬은 내가 직접 쓴 것이고, 프로젝트 스킬은
  남이 써서 저장소에 넣어 준 것이기 때문입니다.

### 3.4 관련 권한 개념

- **권한 모드(permission mode)**: Claude가 도구를 얼마나 자유롭게 쓸 수 있는지의 단계.
  - 기본(default): 파일 수정, 명령 실행마다 승인을 묻습니다.
  - `acceptEdits`: 파일 편집을 자동 수락합니다. 승인 클릭을 줄여 주지만
    **"먼저 조사할 것인가"라는 문제를 해결해 주지는 않습니다.** 그저 더 빨리 고치기 시작할 뿐입니다.
  - plan mode: 아래 4장 참조.
- `.claude/settings.json` 의 `permissions.allow` / `deny` 로 프로젝트 차원의 허용/차단 규칙을
  정할 수도 있습니다.

## 4. 플랜 모드(Plan Mode)와 작업 진행 방식

### 4.1 플랜 모드란

플랜 모드는 Claude가 **코드를 수정하지 않고, 읽기와 검색만 하면서 실행 계획을 세우는 모드**입니다.
탐색이 끝나면 계획을 제시하고, 사용자가 검토·승인한 뒤 플랜 모드를 빠져나와 실제 실행(Act)으로
넘어갑니다. Claude Code에서는 보통 Shift+Tab으로 모드를 전환합니다.

핵심 가치는 두 가지입니다.

1. **안전성** — 계획 단계에서는 파일이 바뀌지 않으므로 마음껏 조사해도 위험이 없습니다.
2. **일관성** — 작업을 시작하기 **전에** 하나의 표준 패턴을 확정할 수 있습니다.

### 4.2 왜 일관성 문제가 생기는가 (핵심 메커니즘)

Claude는 컨텍스트에 있는 것을 근거로 판단합니다. 사전 조사 없이 곧바로 파일 1번부터
고치기 시작하면 이런 일이 벌어집니다.

- 파일 1~10을 볼 때는 A 패턴이 자연스러워 보여서 A 방식으로 변환합니다.
- 작업이 진행되며 컨텍스트가 바뀌고, 파일 40~60에서 다른 형태의 코드를 만나
  B 방식이 더 자연스럽다고 판단합니다.
- 결과: **한 마이그레이션 안에서 앞부분과 뒷부분이 서로 호환되지 않는 두 패턴으로 갈립니다.**
- 이를 맞추기 위해 전체를 다시 훑는 **2차 작업(second pass)** 이 강제됩니다.

이 불일치의 근본 원인은 "모델이 나쁘다"가 아니라 **작업 시작 전에 하나의 패턴을
확정하지 않았다**는 절차상의 결정입니다. 플랜 모드에서 먼저 전수 조사를 하면
"이런 호출 패턴이 3종류 있고, 각각의 대체 관용구는 이것이다"를 미리 못 박을 수 있습니다.

### 4.3 플랜 모드를 **써야 할** 때

- **다중 파일 마이그레이션/리팩터링.** 예: 60개 파일에서 ORM 라이브러리를 교체하는데,
  호출 지점마다 쿼리 패턴이 제각각이고 패턴별로 올바른 대체 관용구가 다르다.
  → 먼저 패턴을 전부 조사·분류하고 마이그레이션 방식을 초안으로 작성한 뒤,
  승인받고 플랜 모드를 나가 실행한다.
- **아키텍처 선택이 아직 안 끝났을 때.** 예: 새 결제 연동을
  (a) 메시지 큐 + 비동기 워커 방식으로 갈지, (b) 기존 서비스에서 동기 호출 + 재시도 로직으로
  갈지 미정이다. 각각 인프라와 운영상의 트레이드오프가 다르다.
  → 구현을 시작하기 전에 플랜 모드로 양쪽을 탐색하고 트레이드오프를 드러내게 한 뒤 결정한다.
- 요구사항이 모호하거나, 변경 범위가 어디까지 번질지 모를 때.

### 4.4 플랜 모드를 **건너뛰어도 될** 때

플랜 모드가 정당하게 생략되는 조건은 하나로 요약됩니다:
**변경의 전체 범위가 이미 알려져 있고, 탐색하거나 설계 결정할 것이 남아 있지 않을 때.**

예: 한 모듈 안의 내부 헬퍼 함수 하나의 이름을 바꾸고, 그 호출 지점 몇 개를 고친다.
호출 지점이 전부 지금 열려 있는 파일 안에서 눈으로 확인된다.
→ 조사할 것도, 설계할 것도 없으므로 바로 실행하는 것이 맞습니다.

여기서 헷갈리지 말아야 할 것들:

- "최근에 작성된 코드니까 검토 없이 맞다고 가정한다" — 생략의 근거가 아닙니다.
  코드의 나이는 정확성의 보증이 아닙니다.
- "이름 변경에는 플랜 모드를 쓸 수 없다" — 사실이 아닙니다. 저장소 전체에 걸친 대규모
  이름 변경이라면 플랜 모드가 오히려 유용합니다.
- "이름 변경은 호출 지점 검증이 전혀 필요 없고 위험도가 0이다" — 사실이 아닙니다.
  호출 지점 검증은 항상 필요합니다. 위 예시가 안전한 이유는 그 검증이 **이미 눈앞에서
  끝나 있기 때문**이지, 이름 변경이 본질적으로 안전해서가 아닙니다.

### 4.5 좋은 워크플로와 나쁜 워크플로

**좋은 패턴:**

- 플랜 모드로 탐색 → 계획 승인 → 플랜 모드 종료 → 승인된 계획을 직접 실행.
  (계획 후 실행으로 전환하는 것 자체는 지극히 정상적이며 권장되는 흐름입니다.)
- 탐색 전용 서브에이전트(Explore)로 코드베이스 전반의 사용 패턴 목록을 먼저 만들기.
- 마이그레이션 범위를 **하나의 라이브러리로 좁히기.** 무관한 프레임워크 업그레이드를
  같은 작업에 섞으면 실패 원인 파악이 어려워집니다. 범위를 좁히는 것은 위험 감소 기법입니다.

**나쁜 패턴:**

- 첫 번째 파일에서 본 대체 관용구를 나머지 전부에 확인 없이 일괄 적용.
- 조사를 생략한 채 한 번에 전부 고쳐 놓고 테스트 스위트가 잡아 주기를 기대.
  (60개 파일 규모에서는 회귀 버그와 수동 수정이 폭증합니다. 테스트는 안전망이지 설계 대체재가 아닙니다.)
- 사전 평가 없이 두 아키텍처를 **둘 다 끝까지 구현**해서 PR로 비교.
  (계획 단계 비교로 충분히 결정할 수 있는 것을 두 배의 시간·토큰으로 사는 낭비입니다.)
- 아직 결정되지 않은 아키텍처를 "인프라 작업이 더 중요하니까" 같은 근거 없는 규칙으로 임의 확정.
- 파일 생성 개수 같은 피상적 지표만으로 기술 아키텍처를 선택.

## 5. Claude에게 문제를 전달하는 방법 (프롬프팅)

### 5.1 서로 얽힌 문제는 한 메시지에 함께 준다

Claude는 준 정보만으로 판단합니다. 따라서 **한 지점을 공유하는 여러 문제는 함께 설명해야 합니다.**

먼저 용어부터:

- **임계 영역(critical section)** — 여러 스레드가 동시에 들어가면 안 되는 코드 구간.
  보통 락(lock)으로 보호합니다.
- **락킹 동작(locking behavior)** — 어떤 락을 언제 잡고 언제 푸는가. 이것이 바뀌면
  그 구간에 의존하는 모든 코드의 전제가 바뀝니다.
- **stale read(오래된 값 읽기)** — 캐시가 제때 무효화되지 않아 낡은 데이터를 읽는 버그.
- **캐시 무효화(cache invalidation)** — 원본이 바뀌었을 때 캐시된 값을 버리는 처리.
- **동시성 버그(concurrency bug)** — 실행 순서/타이밍에 따라 결과가 달라지는 버그.
- **회귀(regression)** — 고치는 과정에서 이전에 잘 되던 것이 깨지는 현상.

**시나리오:** 캐시 무효화 로직의 stale-read 버그를 고치면 락킹 동작이 바뀌는데,
아직 열려 있는 별개의 동시성 버그가 **같은 임계 영역**을 건드린다.

**올바른 대응:** 두 버그를 **하나의 메시지에 함께 기술한다.**
공유 임계 영역을 고치면 다른 버그가 의존하고 있는 락킹 제약이 바뀌기 때문입니다.
전체 맥락을 함께 줘야 두 제약을 동시에 만족하는 통합 설계가 나옵니다.

**잘못된 대응들과 그 이유:**

- stale-read만 먼저 고쳐 머지하고, 나중에 동시성 버그를 **공유 임계 영역 언급 없이** 별도 제출
  → 1차 수정으로 락킹이 이미 바뀌었는데 그 사실을 모르는 상태에서 2차 수정을 하게 되어
  회귀가 발생하거나 문제가 더 꼬입니다.
- 둘 중 하나를 무작위로 골라 고치고, 나머지는 CI가 실패할 때만 처리
  → 엔지니어링은 결정론적이어야 합니다. 무작위 선택과 "테스트가 잡아 주겠지"는 설계가 아닙니다.
- 발견 순서 같은 무관한 이유로 하나만 우선하고 다른 하나를 다음 스프린트로 미루기
  → 공유 임계 영역의 무결성이 깨진 채로 방치됩니다.

### 5.2 일반 원칙

- **제약 조건을 함께 준다.** "이 락은 X 순서를 보장해야 한다" 같은 불변식(invariant)을 명시합니다.
- **범위를 명확히 한다.** 어디까지 고쳐야 하고 어디는 건드리면 안 되는지.
- **관련 없는 작업은 섞지 않는다.** 기준은 하나입니다 —
  **의존 관계가 있으면 합치고, 없으면 나눈다.**

## 6. 서브에이전트(Subagent) 개념

서브에이전트는 **별도의 컨텍스트를 가진 보조 Claude 인스턴스**입니다.
메인 대화의 컨텍스트를 오염시키지 않고 큰 조사를 시킬 때 씁니다.

- **Explore 서브에이전트** — 읽기 전용 탐색 담당. "이 코드베이스에서 옛 ORM이 어떻게
  쓰이는지 패턴을 전부 목록화해 줘" 같은 광범위한 조사에 적합합니다.
  결과 요약만 메인 컨텍스트로 돌아오므로 토큰이 절약됩니다.
- 마이그레이션 전에 Explore로 사용 패턴을 미리 카탈로그화하는 것은
  **패턴 불일치를 예방하는 모범 사례**입니다. 문제의 원인이 아니라 해결책 쪽입니다.

## 7. 전체 정리 — 실무 체크리스트

1. 팀 규칙은 **저장소에 커밋되는** `CLAUDE.md`에. 개인 홈의 `~/.claude/CLAUDE.md`는 개인 취향만.
2. 파일을 실제로 로드하려면 `@경로`. 사람에게 안내만 하려면 백틱으로 감싼다.
3. 규칙의 `paths`에서 하위 폴더까지 잡으려면 `**` 를 반드시 쓴다.
4. 규칙 공유는 `.claude/rules/` 안의 심볼릭 링크로. 파일/디렉터리 모두 가능하고 순환도 안전.
   확인할 것은 링크 대상이 맞는지뿐.
5. clone 한 저장소의 프로젝트 스킬 권한이 안 먹으면 **워크스페이스 신뢰**부터 확인.
6. 범위가 이미 눈앞에 다 보이면 바로 실행. 조사·설계가 남아 있으면 플랜 모드.
7. 서로 얽힌 버그는 한 메시지에 함께, 무관한 작업은 분리.

## 8. 용어 사전 (Glossary)

| 영어 용어 | 한국어 설명 |
|---|---|
| **CLAUDE.md** | Claude Code가 세션 시작 시 자동 로드하는 지침 마크다운 파일. 프로젝트용(커밋)과 개인용(`~/.claude/`)이 있다. |
| **context** | 모델이 현재 알고 있는 텍스트 전체. 여기 없는 정보는 모델이 모른다. |
| **token** | 모델이 텍스트를 세는 단위. 비용과 한도의 기준. |
| **import (`@path`)** | CLAUDE.md에서 다른 파일 내용을 컨텍스트로 끌어오는 문법. |
| **code span** | 백틱 하나로 감싼 인라인 코드 구간. 임포트 파서가 내부를 건너뛴다. |
| **fenced code block** | 백틱 세 개로 감싼 여러 줄 코드 블록. 역시 임포트 파싱에서 제외된다. |
| **frontmatter** | 마크다운 문서 맨 앞에 `---` 로 감싸 넣는 YAML 메타데이터 영역. |
| **glob** | 파일 경로를 패턴으로 매칭하는 문법(`*`, `**`, `?`, 중괄호). |
| **globstar** | `**`. 디렉터리 경계를 넘어 임의의 깊이까지 재귀 매칭하는 glob 패턴. |
| **brace expansion** | `{ts,tsx}` 처럼 여러 대안을 한 패턴에 쓰는 중괄호 확장 문법. |
| **symlink (symbolic link)** | 다른 경로를 가리키는 바로가기 파일. 읽으면 OS가 대상으로 따라간다. |
| **resolve** | 심볼릭 링크를 따라가 실제 대상 파일을 찾아내는 동작. |
| **circular detection** | 링크가 서로를 가리키는 순환을 감지해 무한 루프를 막는 기능. |
| **single source of truth** | 동일 정보의 원본을 한 곳에만 두는 원칙. 복사본 난립을 막는다. |
| **submodule** | 다른 git 저장소를 내 저장소 안에 참조로 포함시키는 git 기능. |
| **Skill / SKILL.md** | 재사용 가능한 작업 절차를 담은 지침 묶음. `.claude/skills/` 또는 `~/.claude/skills/`에 위치. |
| **allowed-tools** | 스킬 프론트매터에서 사용자 승인 없이 자동 실행 가능한 도구/명령을 지정하는 필드. |
| **Workspace Trust** | 처음 여는 프로젝트를 신뢰할지 묻는 보안 관문. 수락 전에는 프로젝트 스킬의 사전 승인이 무효. |
| **context: fork** | 스킬을 별도 서브에이전트에서 실행할지 정하는 옵션. `allowed-tools` 동작의 전제 조건은 아니다. |
| **permission mode** | 도구 사용 승인 방식의 단계(기본 / acceptEdits / plan 등). |
| **acceptEdits** | 파일 편집을 자동 수락하는 권한 모드. 승인 클릭을 줄일 뿐, 사전 조사를 대체하지 않는다. |
| **plan mode** | 코드를 수정하지 않고 탐색·계획만 수행하는 모드. 승인 후 실행으로 전환한다. |
| **direct execution (Act)** | 계획 없이 곧바로 코드를 수정·실행하는 방식. |
| **subagent** | 별도 컨텍스트를 갖는 보조 에이전트. 결과 요약만 메인으로 돌아온다. |
| **Explore subagent** | 읽기 전용 탐색 담당 서브에이전트. 광범위한 코드 조사에 사용. |
| **migration** | 라이브러리·프레임워크·구조를 다른 것으로 옮기는 대규모 변경 작업. |
| **call site** | 어떤 함수/API가 실제로 호출되는 코드 지점. |
| **idiom** | 특정 라이브러리에서 통용되는 관용적 코드 작성 방식. |
| **second pass** | 1차 작업의 불일치를 맞추기 위해 다시 전체를 훑는 재작업. |
| **regression** | 수정 과정에서 기존에 정상이던 기능이 깨지는 현상. |
| **critical section** | 동시 진입이 금지된 코드 구간. 락으로 보호한다. |
| **locking behavior** | 락을 언제 잡고 푸는가에 대한 동작 규칙. |
| **stale read** | 캐시가 무효화되지 않아 낡은 값을 읽는 버그. |
| **cache invalidation** | 원본 변경 시 캐시된 값을 폐기하는 처리. |
| **concurrency bug** | 실행 순서/타이밍에 따라 결과가 달라지는 버그. |
| **trade-off** | 한쪽을 얻으면 다른 쪽을 잃는 선택 관계. 아키텍처 결정의 핵심 판단 재료. |
| **message queue** | 작업을 큐에 넣어 비동기로 처리하게 하는 인프라 구성 요소. |
| **asynchronous worker** | 큐에서 작업을 꺼내 백그라운드로 처리하는 프로세스. |
| **retry logic** | 실패한 호출을 조건에 따라 다시 시도하는 로직. |
| **ORM** | Object-Relational Mapping. 객체와 관계형 DB를 이어 주는 라이브러리 계층. |
| **CI (continuous integration)** | 변경마다 자동으로 빌드·테스트를 돌리는 체계. 안전망이지 설계 대체재는 아니다. |
