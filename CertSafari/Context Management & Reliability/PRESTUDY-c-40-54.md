# 사전 학습 노트: 컨텍스트 관리와 신뢰성 (Context Management & Reliability)

이 문서는 이 주제를 처음 접하는 학습자를 위한 개념 정리입니다. LLM(대규모 언어 모델) 기반 에이전트 시스템을 실제 서비스에 올렸을 때 발생하는 "정보가 새어 나가고, 성능이 조용히 무너지고, 잘못된 판단이 자동화되는" 문제들과 그 대응 기법을 다룹니다.

---

## 0. 큰 그림: 왜 이런 주제가 존재하는가

LLM은 두 가지 구조적 한계를 가집니다.

1. **컨텍스트 윈도우(Context Window)가 유한하다.** 모델이 한 번에 볼 수 있는 텍스트 양에는 상한이 있습니다. 대화가 길어지거나 도구 호출 결과가 쌓이면 반드시 무언가를 버려야 합니다. → **컨텍스트 관리(Context Management)**
2. **모델의 출력은 확률적이고, 스스로의 정확도를 모른다.** 그럴듯하지만 틀린 답(환각, Hallucination)을 자신 있게 내놓습니다. → **신뢰성(Reliability)**

이 두 축에서 파생되는 실무 주제가 아래 섹션들입니다.

- 컨텍스트 윈도우 절약 기법과 그 부작용
- 멀티 에이전트에서의 정보 합성(Synthesis)과 출처 추적성
- 에러 처리와 복구를 위한 구조화된 페이로드 설계
- 정확도 평가: 집계 지표의 함정과 세분화 평가
- 신뢰도 점수(Confidence Score)의 교정 문제
- 이관(Escalation) 판단 기준의 설계

---

## 1. 컨텍스트 윈도우와 그 관리

### 1.1 컨텍스트 윈도우(Context Window)란

모델이 한 번의 추론에서 입력으로 받을 수 있는 토큰(Token) 수의 상한입니다. 시스템 프롬프트, 대화 이력, 도구 호출 결과, 사용자의 새 질문이 전부 여기에 들어갑니다. 상한을 넘으면 요청이 실패하거나 앞부분이 잘려 나갑니다.

토큰이 늘어나면 세 가지 비용이 함께 늘어납니다.

- **금전적 비용**: API는 입력 토큰 수에 비례해 과금됩니다.
- **지연 시간(Latency)**: 입력이 길수록 응답이 느려집니다.
- **정확도 저하**: 관련 없는 정보가 많을수록 모델이 핵심을 놓치는 경향이 있습니다.

따라서 "컨텍스트에 무엇을 넣을 것인가"는 성능·비용·품질을 동시에 결정하는 설계 문제입니다.

### 1.2 도구 호출 결과가 컨텍스트를 잠식하는 문제

에이전트(Agent)는 외부 시스템을 호출하는 **도구(Tool)** 를 사용합니다. 예를 들어 주문 조회 도구는 다음과 같은 JSON 페이로드(Payload, 응답 본문)를 돌려줍니다.

```json
{
  "order_id": "A-10023",
  "status": "delivered",
  "purchase_date": "2026-02-11",
  "item": "무선 이어폰",
  "amount": 129000,
  "return_window_deadline": "2026-03-13",
  "shipping_carrier_code": "CJ-LOG-77",
  "carrier_tracking_events": ["...30개..."],
  "warehouse_bin": "SEO-B4-1129",
  "marketing_tags": ["spring_promo", "email_cohort_7"]
}
```

실제 필드가 40개 이상이라고 해봅시다. 반품 자격을 판단하는 데 필요한 필드는 5개(주문 상태, 구매일, 품목, 금액, 반품 기한)뿐인데, 나머지 35개 이상의 필드가 매 호출마다 컨텍스트에 쌓입니다. 조회를 열 번만 해도 컨텍스트의 대부분이 쓸모없는 메타데이터로 채워집니다.

### 1.3 해결책: 필드 필터링 / 컨텍스트 프루닝(Pruning)

**도구 결과가 컨텍스트에 들어가기 전에, 애플리케이션 코드 단계에서 필요한 필드만 남기는 전처리(Pre-processing)** 가 정답입니다.

```python
NEEDED = ("status", "purchase_date", "item", "amount", "return_window_deadline")

def slim(payload: dict) -> dict:
    return {k: payload[k] for k in NEEDED if k in payload}

# 에이전트 컨텍스트에는 slim(raw) 결과만 추가한다
```

이 방식의 장점은 명확합니다. 결정적(deterministic)이고, 추가 LLM 호출이 없으니 비용·지연이 0에 가깝고, 필요한 필드가 잘려 나갈 위험이 없습니다.

**대안들이 왜 열등한지:**

| 대안 | 문제점 |
|---|---|
| 고정 글자 수로 자르기(Truncation) | JSON 구문이 깨지고, 뒤쪽에 있는 필수 필드가 잘려 나감. 어떤 정보가 남을지 통제 불가 |
| 원본 전체를 캐싱(Cache) | 재호출은 줄지만 컨텍스트 점유량 자체는 그대로. 문제의 원인을 건드리지 않음 |
| 별도 LLM 요약 호출 | 단순 필드 선택에 LLM을 쓰는 것은 과잉. 비용·지연 증가 + 요약 과정에서 수치 왜곡 위험 |

원칙: **결정적으로 풀 수 있는 문제에 확률적 도구(LLM)를 쓰지 않는다.**

### 1.4 반복 요약(Iterative Summarization)과 정보 손실

대화가 길어질 때 흔히 쓰는 기법이 **요약으로 이력을 압축**하는 것입니다. 이전 대화를 요약본으로 대체하고, 다시 길어지면 그 요약본을 또 요약합니다.

문제는 **요약이 "간결함"을 목표로 최적화된다**는 점입니다. 요약 모델에게 중요한 것은 "이야기의 흐름"이지 "숫자 하나하나"가 아닙니다. 그래서 압축이 반복될수록 다음과 같은 열화가 일어납니다.

```
1차 원문 : "2026년 3월 14일에 주문번호 #12345로 $150.00을 결제했는데 이중 청구되었습니다."
2차 요약 : "3월 중순 주문 #12345에 대해 약 $150 이중 청구 발생"
3차 요약 : "이전 주문의 이중 청구 문제"
4차 요약 : "결제 관련 이슈"
```

금액, 날짜, 주문번호 같은 **정확한 수치(exact figures)** 는 점진적으로 **일반화(generalized)** 되거나 아예 **누락(dropped)** 됩니다. 요약은 숫자를 특별 취급하지 않습니다. 또한 요약이 반복될수록 원문에 없던 표현이 끼어드는 환각 위험도 커집니다.

중요한 오해 두 가지를 정리합니다.

- 요약을 반복한다고 원본 수치의 오류가 저절로 교정되지 않습니다. 모델에는 대조할 원본이 이미 없습니다.
- 요약 프로세스가 "숫자만 알아서 별도 메모리에 옮겨주는" 기능은 기본 제공되지 않습니다. 그런 동작은 직접 설계해야 존재합니다.

### 1.5 해결책: 구조화된 상태(Structured Memory State) 분리

대화의 **서술적 맥락**과 **정확해야 하는 사실**을 물리적으로 분리합니다.

- 서술적 맥락 → 요약으로 압축해도 무방
- 트랜잭션 사실(금액, 날짜, ID, 계약 조건 등) → 별도의 구조화된 저장소에 원본 그대로 보관하고, 필요할 때 통째로 프롬프트에 다시 주입

```json
{
  "order_id": "#12345",
  "charge_date": "2026-03-14",
  "amount_usd": 150.00,
  "issue": "duplicate_charge",
  "status": "refund_pending"
}
```

이 JSON은 요약 대상이 아니라 상태(state)입니다. 요약을 100번 반복해도 이 값들은 변하지 않습니다. 이것이 "요약만으로 컨텍스트를 관리하면 안 되는" 이유입니다.

## 2. 멀티 에이전트 합성(Synthesis)과 출처 추적성

### 2.1 기본 구조: 코디네이터와 서브에이전트

복잡한 조사 작업은 하나의 에이전트가 처리하기 어렵습니다. 그래서 다음 구조를 씁니다.

- **코디네이터(Coordinator) / 오케스트레이터(Orchestrator)**: 작업을 쪼개서 배분하고, 결과를 모으고, 실패를 복구합니다.
- **서브에이전트(Subagent)**: 각자 좁은 범위의 조사를 수행합니다. (예: 판례 검색 담당 3개, 경쟁사 매출 조사 담당 2개)
- **합성 에이전트(Synthesis Agent)**: 서브에이전트들의 산출물을 하나의 보고서로 통합합니다.

각 서브에이전트는 자체 컨텍스트 윈도우를 가지므로, 작업을 나누면 전체가 다룰 수 있는 정보량이 늘어납니다. 대신 **정보가 단계를 건널 때마다 손실될 위험**이 생깁니다.

### 2.2 출처 추적성(Provenance / Traceability)

**Provenance(출처 내력)** 는 "이 주장이 어디서, 언제, 누구를 통해 왔는가"를 추적할 수 있는 성질입니다.

합성 에이전트에게 "모든 서브에이전트 결과를 간결하게 통합 요약하라"고만 지시하면, 문장은 매끄러워지지만 다음이 사라집니다.

- 어떤 서브에이전트가 찾은 정보인지
- 어떤 문서/URL에 근거하는지
- 언제 기준 데이터인지

검토자는 보고서를 검증할 수 없게 되고, 보고서는 사실상 신뢰할 수 없는 산문이 됩니다.

**해결책은 프롬프트에 메타데이터 유지(carry forward)를 명시적으로 지시하는 것입니다.**

```
각 주장을 보고서에 옮길 때, 해당 주장에 붙어 있던
source(출처 문서/URL), date(자료 기준일), agent(수집 서브에이전트)
메타데이터를 반드시 함께 유지하라. 메타데이터가 없는 주장은 포함하지 마라.
```

결과 예시:

> 경쟁사 A의 2025년 매출은 4억 2천만 달러다. [출처: 2026-01-14 자사 보도자료, 수집: revenue-agent-1]

주의할 점: **문체를 격식 있게 바꾸거나, 보고서를 더 짧게 만들거나, 말미에 "출처는 요청 시 제공" 같은 일반 면책 조항을 붙이는 것은 추적성 문제를 전혀 해결하지 못합니다.** 추적성은 각 주장 옆에 메타데이터가 실제로 붙어 있어야 성립합니다. 오히려 더 짧게 만들면 손실이 심해집니다.

### 2.3 상충하는 정보(Discrepancy)의 처리

서로 다른 서브에이전트가 같은 항목에 대해 다른 값을 가져오는 일은 흔합니다.

- 서브에이전트 1: 보도자료 인용 → 연매출 $420M
- 서브에이전트 2: 애널리스트 리포트 인용 → 연매출 $460M
- 두 출처 모두 신뢰할 만함

이때 합성 에이전트가 해서는 **안 되는** 일:

- 한쪽을 임의로 골라 채택하고 다른 쪽을 숨기기 → 편향과 정보 은폐. "애널리스트가 항상 더 엄밀하다", "회사 발표가 항상 더 정확하다"는 일반 규칙은 성립하지 않습니다.
- 두 값을 평균 내어 $440M으로 제시하기 → **어떤 출처에도 존재하지 않는 숫자를 창작하는 것**입니다. 이것은 데이터 왜곡이자 환각의 일종이며, 단일 숫자로 보이기 때문에 더 위험합니다.

**올바른 처리: 병렬 제시 + 출처 명기 + 충돌 사실 명시**

> 연매출 추정치는 출처에 따라 상이함:
> - $420M — 회사 보도자료(2026-01-14)
> - $460M — XYZ증권 애널리스트 리포트(2026-02-02)
>
> 두 수치는 서로 상충하며, 회계 기준 또는 집계 범위 차이일 가능성이 있음.

원칙: **불확실성은 해소된 척 감추는 것이 아니라, 사용자에게 그대로 전달되어야 합니다.** 판단에 필요한 정보를 가진 것은 최종 의사결정자입니다.

### 2.4 증거 가치(Evidentiary Weight)의 차등 표현

여러 출처를 합성할 때 각 주장의 **근거 강도가 다르다는 사실 자체가 정보**입니다. 그런데 요약을 거치면 모든 문장이 같은 어조로 평평해집니다.

법률 리서치 예시:

- 주장 X: 검토한 **모든 항소법원이 긍정적으로 인용**한 확립된 판례 → 근거 매우 강함
- 주장 Y: **단 하나의 하급심 판결에만** 등장하고 다른 곳에서 검증되지 않은 주장 → 근거 매우 약함

이 둘이 같은 단락에 똑같은 문구로 나열되면, 독자는 두 주장이 같은 무게라고 오해합니다. 법률·의료·금융처럼 판단의 결과가 무거운 도메인에서 이는 심각한 결함입니다.

**올바른 수정: 증거 가치별로 섹션을 분리하고, 서술 방식을 다르게 하기**

```
## 확립된 판례 (Well-Settled Authority)
- 판례 X: 이 원칙을 검토한 모든 항소법원이 일관되게 지지함.

## 검증되지 않은 단일 판결 주장 (Untested / Single-Opinion)
- 주장 Y: 하급심 1건에서만 제시되었으며, 상급심 검증 이력 없음. 인용 시 주의 필요.
```

잘못된 대안들:

- 약한 주장을 아무 설명 없이 부록으로 치우기 → 왜 부록인지 알 수 없어 오히려 오해를 유발
- 각주 번호만 붙이고 서술의 확신 수준은 그대로 두기 → 독자는 여전히 같은 무게로 읽음
- 둘 다 "법원들이 시사한 바 있다" 같은 동일한 완곡 표현(hedging language)으로 통일 → 강한 근거의 신뢰도를 인위적으로 깎아내리는 반대 방향의 왜곡

원칙: **평평하게 만드는 것(flattening)은 중립이 아니라 왜곡입니다.** 차이가 있으면 차이가 보이게 써야 합니다.

## 3. 에러 페이로드(Error Payload) 설계

### 3.1 왜 에러 설계가 중요한가

서브에이전트가 도구 호출에 실패했을 때, 코디네이터는 다음 중 하나를 결정해야 합니다.

- 그대로 재시도한다 (일시적 네트워크 오류라면 유효)
- 다른 도구나 다른 경로로 우회한다 (해당 API가 영구 폐기되었다면)
- 부분 결과만 가지고 진행한다
- 사람에게 이관한다

이 판단은 **에러가 전달하는 정보의 질에 전적으로 달려 있습니다.** 코디네이터가 LLM이라는 점이 중요합니다. LLM은 의미(semantic)를 읽고 판단하지, 숫자 코드를 룩업 테이블에서 찾아보지 못합니다.

### 3.2 좋은 에러 페이로드의 4가지 필드

```json
{
  "failure_type": "rate_limit_exceeded",
  "action_attempted": "search_case_law(query='fair use 2024', court='9th Cir')",
  "partial_results": [
    {"case": "Smith v. Jones", "year": 2023}
  ],
  "alternative_approaches": [
    "60초 후 재시도",
    "보조 검색 인덱스(secondary_index) 도구로 우회",
    "쿼리 범위를 단일 연도로 축소하여 결과 수 감소"
  ]
}
```

각 필드의 역할:

1. **failure_type (실패 유형)** — 무슨 종류의 오류인가. 일시적(transient)인지 영구적(permanent)인지가 재시도 여부를 결정합니다.
2. **action_attempted (시도한 작업)** — 어떤 도구를 어떤 인자로 호출했는가. 같은 실수를 반복하지 않기 위해 필요합니다.
3. **partial_results (부분 결과)** — 완전히 실패하기 전에 이미 확보한 유효 정보. 이것을 버리면 작업을 처음부터 다시 해야 합니다.
4. **alternative_approaches (대안)** — 실패 현장에 있던 서브에이전트가 제안하는 다음 수단. 코디네이터보다 상황 정보가 많은 쪽이 제안하는 것이 효율적입니다.

이 네 가지가 갖춰져야 코디네이터가 재시도 / 도구 전환 / 사용자 개입 요청 중 최적의 복구 동작을 고를 수 있습니다.

### 3.3 나쁜 에러 설계

| 형태 | 문제 |
|---|---|
| 내부 추론 트레이스 전체를 자유 텍스트로 전달 | 토큰 낭비가 극심하고, 핵심 실패 원인이 잡음에 묻힘. 구조가 없어 코디네이터가 파싱 불가 |
| 재시도 횟수 + 타임스탬프만 전달 | "몇 번 실패했다"는 알 수 있어도 "왜"와 "그래서 무엇을"은 알 수 없음 |
| 단일 숫자 에러 코드 (예: `ERR_4021`) | 사람 엔지니어가 문서를 찾아보는 용도. LLM 코디네이터는 그 코드의 의미를 모르며, 룩업 테이블 접근 권한도 없음 |

원칙: **에러는 실패를 알리는 신호가 아니라, 복구 결정을 내리기 위한 입력 데이터입니다.** 구조화하되(structured), 의미가 읽히도록(semantic) 설계합니다.

## 4. 정확도 평가: 집계 지표의 함정

### 4.1 문서 추출 파이프라인과 Human-in-the-Loop

전형적인 구조:

```
문서 입력 → LLM 추출(필드 값 + 신뢰도 점수)
          → 신뢰도 ≥ 임계값 : 자동 처리
          → 신뢰도 <  임계값 : 사람 검토(Human Review)
```

**Human-in-the-Loop(HITL, 사람 개입)** 는 안전장치입니다. 이것을 걷어내는 순간 오류가 그대로 다운스트림으로 흘러갑니다. 그래서 "사람 검토를 줄여도 되는가"는 반드시 증거로 답해야 하는 질문입니다.

### 4.2 집계 정확도(Aggregate Accuracy)의 위험

"전체 필드 정확도 97%"라는 수치는 **평균**입니다. 평균은 소수 집단의 재앙을 감춥니다.

```
표준 전자 송장 (전체의 90%)  : 99.5% 정확
손글씨 영수증  (전체의 10%)  : 74%   정확
──────────────────────────────────────
가중 평균                     : 약 97%  ← 겉보기에는 훌륭
```

이 현상은 데이터 불균형에서 비롯되며, 넓게는 **심슨의 역설(Simpson's Paradox)**, 실무에서는 "평균의 함정"이라 불립니다. 전체가 좋아 보이는 상태에서 특정 세그먼트만 심각하게 망가져 있을 수 있습니다.

### 4.3 해결책: 세분화 평가(Granular / Stratified Evaluation)

**사람 검토를 제거하기 전에 가장 먼저 해야 할 일은, 정확도를 문서 유형(document type)별 × 필드(field)별로 쪼개어 보는 것입니다.**

| 문서 유형 | 공급업체명 | 총액 | 날짜 | 품목 |
|---|---|---|---|---|
| 표준 PDF 송장 | 99% | 99% | 98% | 98% |
| 스캔 송장 | 97% | 96% | 97% | 95% |
| 손글씨 영수증 | 82% | **68%** | 79% | 71% |

이 표가 있어야 비로소 "어디를 자동화해도 되는가"를 답할 수 있습니다.

**효과 없는 대안들:**

- 같은 평가셋을 같은 설정으로 재실행해 97%가 재현되는지 확인 → 재현성은 확인되지만, 집계 지표의 사각지대는 그대로입니다. 같은 함정을 두 번 확인할 뿐입니다.
- 평가셋 크기만 늘려 통계적 유의성을 높이기 → 집계로 보는 한 세그먼트별 붕괴는 여전히 평균에 묻힙니다. 표본 수가 아니라 **분해(breakdown)의 부재**가 문제입니다.
- 모델에게 자기 정확도를 자체 평가시키기 → 모델은 자신의 오류를 인지하지 못합니다(5장 참조). 환각과 과신 편향을 유발하므로 객관적 측정 수단이 될 수 없습니다.

### 4.4 세그먼트 결함 발견 시의 대응

의료 기록 추출 예시:

- 전체 정확도 96%
- 그러나 **손글씨 처방전의 '약물 용량(medication dosage)' 필드만 81%**
- 다른 모든 필드/문서 유형은 97% 초과

이때 올바른 조치는 **해당 필드의 원인이 규명되고 개선될 때까지, 파이프라인 전반의 사람 검토 수준을 현행 유지**하는 것입니다.

이유는 **리스크 가중(risk-weighted)** 판단입니다. 약물 용량 오류는 환자 안전과 직결되는 고위험(high-risk) 결함이며, 오류 1건의 비용이 다른 필드와 비교 불가능하게 큽니다. 81%는 "5건 중 1건이 틀린다"는 뜻입니다.

잘못된 대응들:

- 손글씨 처방전 **문서 유형 전체**를 불신하고 나머지는 전면 자동화 → 문제는 특정 필드에 국한되는데 진단을 뭉갠 것이고, 동시에 원인 규명 전에 다른 영역의 안전장치를 성급히 제거합니다.
- 하필 그 약물 용량 필드에서만 사람 검토를 제거 → 가장 위험한 지점의 안전장치를 걷어내는 정반대 조치. "우연보다는 낫다(above chance)"는 안전 기준이 아니며, 오류가 고르게 분포한다는 근거도 없습니다.
- 96%라는 평균이 이미 약점을 반영하니 전체를 균일하게 축소 → 평균이 문제를 "반영"한다는 말은 곧 "감춘다"는 뜻입니다.

원칙: **자동화 범위는 최악의 세그먼트와 그 세그먼트의 위험도에 맞춰 정합니다. 평균에 맞추지 않습니다.**

### 4.5 지속적 모니터링(Ongoing Monitoring)과 드리프트

**초기 검증(Initial Validation)은 특정 시점의 정적 스냅샷일 뿐입니다.** 그 시점에 존재하던 문서 모집단(population)과 조건에서의 성능만을 측정합니다.

프로덕션에서는 입력이 계속 변합니다.

- 공급업체가 송장 양식을 개편함
- 신규 고객사가 들어와 새로운 레이아웃이 유입됨
- 스캐너 교체로 이미지 품질이 달라짐
- 새로운 언어/통화/날짜 형식이 등장함

이런 입력 분포의 변화를 **데이터 드리프트(Data Drift)** 또는 분포 이동(Distribution Shift)이라 하고, 정답의 정의 자체가 바뀌는 경우를 **개념 드리프트(Concept Drift)** 라 합니다.

중요한 개념 정정: **모델은 기계 부품처럼 "마모(wear out)"되지 않습니다.** 모델 가중치는 그대로입니다. 성능이 떨어지는 이유는 모델이 늙어서가 아니라 **세상이 바뀌어 입력이 달라졌기 때문**입니다. 이 인과관계를 정확히 이해하는 것이 중요합니다.

따라서 "초기 검증에서 95% 나왔으니 샘플링을 영구 중단하자"는 주장에 대한 가장 강한 반론은:

> 초기 검증은 그 당시의 문서 모집단과 조건에서의 성능만을 측정한다. 입력이 변화함에 따라 나타나는 오류율 변동과 새로운 실패 유형(failure mode)을 감지하려면 지속적인 층화 샘플링이 필요하다.

이 엔지니어링 논거가 규제 준수 논거보다 강한 이유는, **모든 산업에 그런 규제가 있는 것도 아니고, 규제가 없어도 이 문제는 똑같이 발생하기 때문**입니다. 감사·규제 대응은 부수적 효과이지 근본 원인이 아닙니다.

### 4.6 층화 무작위 샘플링(Stratified Random Sampling)

지속 모니터링의 표준 기법입니다.

- **무작위(Random)**: 표본이 편향되지 않도록 검토 대상을 임의로 뽑습니다.
- **층화(Stratified)**: 모집단을 의미 있는 계층(strata)으로 나누고, 각 계층에서 표본을 뽑습니다. 여기서 계층은 **문서 유형 × 필드**입니다.
- **정기적(Recurring)**: 일회성이 아니라 주기적으로 반복합니다.
- **베이스라인 대비 비교**: 관측된 오류율을 초기 검증 때 확립한 베이스라인(baseline)과 비교해 변화를 감지합니다.

왜 단순 무작위가 아니라 층화인가? 손글씨 영수증이 전체의 3%뿐이라면, 단순 무작위 표본 100건에는 3건만 들어옵니다. 3건으로는 그 세그먼트의 오류율 변화를 감지할 수 없습니다. 층화하면 소수 세그먼트에서도 충분한 표본을 확보할 수 있습니다.

특히 **사람 검토에서 빠져나간 고신뢰도(high-confidence) 추출물**을 샘플링 대상에 반드시 포함해야 합니다. 아무도 보지 않는 영역에서 발생하는 오류를 **사일런트 실패(Silent Failure)** 라 하며, 이것이 가장 위험합니다.

**잘못된 샘플링 방식들:**

| 방식 | 왜 안 되는가 |
|---|---|
| 처리 속도에 비례해 샘플링 | 처리 속도는 추출 품질과 통계적 연관이 없음. 빨리 처리되는 쉬운 문서가 과대표집되어 오히려 편향 유발 |
| 매일 첫 1시간 전수 검토 | 시간대 편향. 특정 시간에 특정 공급업체/채널 문서만 집중 유입되면 나머지는 영원히 관찰되지 않음 |
| 한가할 때 검토자가 수상해 보이는 것만 확인 | 비체계적·비정기적이고 검토자 주관에 의존. 통계적 대표성이 없어 오류율 추정 불가. "수상해 보이지 않는 오류"는 영원히 못 잡음 |

## 5. 신뢰도 점수(Confidence Score)와 교정(Calibration)

### 5.1 신뢰도 점수란

추출이나 답변에 대해 시스템이 부여하는 "이 결과가 맞을 것 같은 정도"의 수치(예: 0.0~1.0)입니다. 임계값(threshold)을 정해 그 이상은 자동 처리, 미만은 사람 검토로 라우팅하는 데 씁니다.

### 5.2 교정(Calibration)이란

신뢰도가 **교정되어 있다(well-calibrated)** 는 것은 다음이 성립함을 뜻합니다.

> 신뢰도 0.9로 출력한 건들을 모아보면, 실제로 약 90%가 정답이다.

교정되지 않은(uncalibrated) 모델은 이 대응이 깨져 있습니다. 특히 LLM은 **과신(Overconfidence)** 경향이 강해, 0.95라고 말해놓고 실제 정확도는 70%인 경우가 흔합니다.

### 5.3 임계값은 반드시 정답 데이터로 검증해야 한다

전형적인 실패 사례:

> 신뢰도 0.85 미만을 사람 검토로 보내는 파이프라인. 몇 달 후 검토자들이 "0.9 이상 점수를 받은 필드도 자주 틀린다"고 보고하고, 결국 점수와 무관하게 대부분을 다시 확인하기 시작함. 임계값의 존재 의미가 사라짐.

**근본 원인은 0.85라는 임계값이 라벨링된 정답 데이터(Ground Truth)로 검증된 적이 없다는 것입니다.** 즉 "0.85 이상 구간의 실제 정확도가 허용 가능한 수준인가"를 아무도 측정하지 않고 숫자를 정했습니다.

올바른 절차:

1. 대표성 있는 표본에 대해 **사람이 정답을 라벨링**합니다 (Ground Truth 구축).
2. 신뢰도 구간별로 실제 정확도를 측정합니다.

   | 신뢰도 구간 | 건수 | 실제 정확도 |
   |---|---|---|
   | 0.95~1.00 | 4,100 | 99.1% |
   | 0.90~0.95 | 1,800 | **86.0%** |
   | 0.85~0.90 | 900 | 71.2% |
   | 0.85 미만 | 1,200 | 52.4% |

3. 허용 오류율(예: 99% 이상)을 만족하는 지점에서 임계값을 정합니다. 위 표라면 0.85가 아니라 **0.95**여야 합니다.
4. 드리프트가 있으므로 주기적으로 재검증합니다.

**오진하기 쉬운 원인들:**

- "검토자가 필드당 시간을 너무 많이 쓴다 → 임계값을 올려 검토 물량을 줄이자" → 검토 부담은 증상이지 원인이 아닙니다. 임계값을 올리면 오히려 더 많은 건이 미만 구간에 들어가 검토량이 늘어납니다. 방향도 논리도 틀립니다.
- "문서가 많아져 고정 임계값이 무의미해졌다 → 고정 비율 검토로 바꾸자" → 문제는 물량이 아니라 점수의 신뢰성입니다. 점수를 버리고 무작위 비율 검토로 가는 것은 신호를 통째로 포기하는 것입니다.
- "검토자가 0.9와 0.95를 해석할 훈련이 부족하다" → 점수가 교정되어 있지 않다면 해석 훈련은 무의미합니다. 애초에 해석할 만한 의미가 없습니다.

### 5.4 자체 보고 신뢰도(Self-reported / Verbalized Confidence)

모델에게 "이 답변에 대한 확신도를 %로 말해봐"라고 물어 얻는 수치입니다. **이것은 특히 신뢰할 수 없습니다.**

이유:

- 모델은 자신의 내부 상태를 관찰(introspection)하지 못합니다. 그럴듯한 숫자를 생성할 뿐입니다.
- 그 숫자는 질문의 어조, 주제의 난이도 인상, 프롬프트의 표현에 따라 흔들립니다.
- 실제 정답 여부와의 상관관계가 약합니다.

구체 사례:

> SaaS 지원 에이전트가 청구 일할계산(billing proration) 질문에 답하면서 자체 신뢰도를 45%로 보고함. 그러나 검색된 문서와 계정 데이터는 그 답을 **명확하고 모호함 없이** 뒷받침함. 이관해야 하는가?

**답은 "아니오"입니다.** 자체 보고 점수는 사건의 복잡성을 나타내는 신뢰할 만한 대리 지표(proxy)가 아니며, **근거(grounding evidence)가 명확하게 답을 뒷받침한다면 그 근거가 우선합니다.**

주의할 논리들:

- "낮은 자체 신뢰도는 항상 사건이 사실적으로 모호하다는 뜻이다" → 틀립니다. 미교정 점수는 근거 상태와 무관하게 나올 수 있습니다.
- "50% 미만이면 무조건 자동 이관" → 미교정 지표에 하드 규칙을 거는 것이므로, 불필요한 이관을 대량 생산합니다.
- "청구 일할계산 질문은 이관 규칙에서 제외 대상이라서 이관 안 함" → 결론은 맞지만 이유가 틀립니다. 주제 카테고리 때문이 아니라 **근거가 명확하기 때문**입니다. 잘못된 이유는 다른 상황에서 잘못된 판단으로 이어집니다.

원칙: **모델이 자기 자신에 대해 말한 수치보다, 외부의 검증 가능한 근거와 라벨 데이터로 측정된 값이 항상 우선합니다.**

## 6. 이관(Escalation) 판단 설계

### 6.1 이관이란

AI 에이전트가 스스로 처리하지 않고 사람 상담원이나 상급 프로세스로 넘기는 것입니다. 두 방향의 오류가 있습니다.

- **과소 이관(Under-escalation)**: 넘겨야 할 것을 에이전트가 처리 → 잘못된 정책 판단, 손해, 규정 위반
- **과잉 이관(Over-escalation)**: 처리 가능한 것을 넘김 → 사람 상담 비용 증가, 자동화 가치 상실, 고객 대기 시간 증가

좋은 설계는 **이관 트리거를 "실제로 판단 능력이나 권한을 벗어나는 조건"에 맞추는 것**입니다.

### 6.2 이관해야 하는 경우: 정책 공백(Policy Gap)

핵심 사례:

> 고객이 두 개의 프로모션 코드를 중복 적용(stacking)해 달라고 요청함. 정책 문서는 이 조합을 **허용한다고도, 금지한다고도 명시하지 않음**. 고객은 침착하고 사람 상담원을 요청하지도 않음.

**정답은 이관입니다.** 이유는 감정이나 난이도가 아니라 **정책 자체에 공백이 있기 때문**입니다. 에이전트에게는 이 사안을 결정할 권한(authority)이 없습니다. 문서에 없는 것을 판단하는 순간, 에이전트는 사실상 **새로운 정책을 만들고 있는 것**이며, 그 결정은 선례가 되어 전체 고객에게 일관되지 않게 적용됩니다.

잘못된 대응들:

- "문서에 없으면 기본적으로 불허" → 임의의 기본값 설정. 조직이 승인한 규칙이 아니며, 정당한 요청을 거절해 고객 손해와 분쟁을 유발합니다.
- "명시적으로 금지하지 않았으니 허용" → 반대 방향의 임의 기본값. 재정적 손실과 악용 가능성이 있습니다.
- "하나만 고르게 하고 그것을 적용" → 겉보기엔 타협 같지만, 실제로는 "중복 적용은 불가"라는 정책 결정을 몰래 내린 것입니다. 고객에게는 그것이 확정된 규칙인 것처럼 전달됩니다.

**"고객이 화나지 않았고 사람을 요청하지도 않았다"는 조건은 이관 필요성과 무관합니다.** 이 조건들은 감정 기반 이관 규칙이 발동하지 않는다는 뜻일 뿐이며, 정책 공백이라는 진짜 이유를 지우지 못합니다.

### 6.3 이관하지 말아야 하는 경우: 감정 플래그(Sentiment Flag)

대비되는 사례:

> 모니터링 시스템이 대화를 "매우 부정적 감정"으로 플래그함. 고객이 날 선 표현을 썼기 때문. 그런데 요청 자체는 **온라인 뱅킹 비밀번호 재설정**으로, 완전히 셀프서비스 가능한 일상적 요청임.

**정답은 이관하지 않고 처리하는 것입니다.** 근거는 두 가지입니다.

1. **감정만으로는 문제의 복잡도를 판단할 수 없습니다.** 감정(sentiment)과 복잡도(complexity)는 독립적인 축입니다. 고객은 단지 바쁘거나 표현이 직설적일 수 있고, 반대로 매우 정중하게 극도로 복잡한 요청을 할 수도 있습니다.
2. **해당 작업은 에이전트의 능력 범위 안에 있습니다.** 비밀번호 재설정은 정해진 절차가 있는 일상 작업입니다.

여기서 감정에 반응해 이관하면, 오히려 고객은 즉시 해결될 일을 기다리게 되어 경험이 더 나빠집니다.

잘못된 논리들:

- "부정적 감정 점수는 사건이 너무 복잡함을 신뢰성 있게 나타낸다" → 상관관계가 약합니다.
- "감정 플래그는 실제 난이도와 무관하게 항상 이관을 유발해야 한다" → 과잉 이관을 제도화하는 규칙입니다.
- "비밀번호 재설정은 감정 기반 이관 규칙에서 항상 면제되기 때문에 이관 안 함" → 결론은 맞지만 이유가 틀립니다. 특정 주제의 예외 목록이 아니라 **일반 원칙(감정 ≠ 복잡도, 그리고 능력 범위 내)** 이 근거입니다.

### 6.4 두 사례를 관통하는 원칙

| 신호 | 이관 근거가 되는가 | 이유 |
|---|---|---|
| 정책이 사안을 다루지 않음 | **된다** | 에이전트에게 결정 권한이 없음. 판단하면 새 정책을 만드는 것 |
| 고객 감정이 부정적임 | 되지 않는다 | 감정은 복잡도의 대리 지표가 아님 |
| 모델의 자체 신뢰도가 낮음 | 되지 않는다 | 미교정 지표. 근거가 명확하면 근거가 우선 |
| 고객이 사람을 명시적으로 요청함 | 된다 | 고객의 명시적 의사 |
| 요청이 에이전트의 도구/권한 범위 밖 | 된다 | 물리적으로 수행 불가 |

정리: **이관 여부는 "에이전트가 정당한 근거와 권한을 가지고 이 사안을 결정할 수 있는가"로 판단합니다. 감정이나 자기 확신 같은 대리 지표로 판단하지 않습니다.**

## 7. 전체를 관통하는 5가지 원칙

1. **압축은 항상 손실이다.** 요약·자르기·평균 내기는 모두 정보를 버립니다. 무엇을 버리는지 통제하지 않으면, 가장 중요한 것부터 사라집니다.
2. **결정적으로 풀 수 있는 문제에 LLM을 쓰지 않는다.** 필드 선택, 필터링, 라우팅은 코드로 하는 것이 싸고 빠르고 정확합니다.
3. **불확실성은 감추지 말고 전달한다.** 상충하는 값, 약한 근거, 알 수 없는 정책은 그 상태 그대로 사용자에게 보이게 합니다. 매끄러운 단일 답변이 항상 더 나은 답변은 아닙니다.
4. **평균을 믿지 말고 쪼개서 본다.** 집계 지표는 소수 세그먼트의 재앙을 감춥니다. 자동화 범위는 최악의 세그먼트와 그 위험도에 맞춥니다.
5. **모델이 자기 자신에 대해 말한 것을 증거로 삼지 않는다.** 자체 신뢰도, 자체 평가는 외부의 라벨 데이터와 근거로 검증되어야 의미를 가집니다.

## 8. 용어 사전 (Glossary)

### 컨텍스트 관리

| 영어 용어 | 한국어 설명 |
|---|---|
| Context Window | 컨텍스트 윈도우. 모델이 한 번의 추론에서 입력으로 받을 수 있는 토큰 수의 상한 |
| Token | 토큰. 모델이 텍스트를 처리하는 최소 단위. 과금과 길이 제한의 기준 |
| Payload | 페이로드. 도구 호출이나 API가 돌려주는 응답 본문 데이터 |
| Field Filtering / Pruning | 필드 필터링·프루닝. 컨텍스트에 넣기 전 필요한 필드만 남기고 나머지를 버리는 전처리 |
| Pre-processing | 전처리. LLM에 데이터를 넘기기 전에 애플리케이션 코드에서 가공하는 단계 |
| Truncation | 잘라내기. 고정 길이로 텍스트를 자르는 것. 구조가 깨지고 중요 정보가 유실될 수 있음 |
| Caching | 캐싱. 결과를 저장해 재호출을 줄이는 기법. 컨텍스트 점유량 자체는 줄이지 못함 |
| Iterative Summarization | 반복 요약. 대화 이력을 요약본으로 대체하기를 반복하는 컨텍스트 절약 기법 |
| Information Loss / Generalization | 정보 손실·일반화. 압축 과정에서 구체적 수치가 추상적 표현으로 바뀌거나 사라지는 현상 |
| Structured Memory State | 구조화된 상태 저장소. 금액·날짜·ID 등 정확해야 하는 값을 요약과 분리해 원본으로 보관하는 저장소 |
| Transactional Details | 트랜잭션 세부 정보. 금액, 날짜, 주문번호 등 정확성이 요구되는 거래 데이터 |
| Latency | 지연 시간. 요청부터 응답까지 걸리는 시간 |

### 멀티 에이전트와 합성

| 영어 용어 | 한국어 설명 |
|---|---|
| Agent | 에이전트. 도구를 호출하며 목표를 향해 자율적으로 여러 단계를 수행하는 LLM 시스템 |
| Tool | 도구. 에이전트가 호출할 수 있는 외부 함수·API |
| Subagent | 서브에이전트·하위 에이전트. 좁은 하위 작업을 전담하며 자체 컨텍스트를 가지는 에이전트 |
| Coordinator / Orchestrator | 코디네이터·오케스트레이터. 작업을 분배하고 결과를 모으며 실패를 복구하는 상위 에이전트 |
| Synthesis Agent | 합성 에이전트. 여러 서브에이전트의 산출물을 하나의 보고서로 통합하는 에이전트 |
| Provenance / Traceability | 출처 내력·추적성. 각 주장이 어떤 출처·날짜·에이전트에서 왔는지 되짚을 수 있는 성질 |
| Metadata | 메타데이터. 데이터에 붙는 부가 정보. 여기서는 출처, 날짜, 수집 주체 등 |
| Carry Forward | 유지 전달. 하위 단계의 메타데이터를 상위 산출물까지 그대로 끌고 가는 것 |
| Attribution | 출처 명기. 각 주장 옆에 근거 출처를 명시하는 것 |
| Discrepancy | 불일치·상충. 신뢰할 만한 여러 출처가 서로 다른 값을 제시하는 상황 |
| Blended Estimate | 혼합 추정치. 상충하는 값들을 평균 등으로 합쳐 만든 단일 수치. 어떤 출처에도 없는 값이므로 위험 |
| Evidentiary Weight | 증거 가치·증거 중량. 어떤 주장이 얼마나 강한 근거에 뒷받침되는지의 정도 |
| Hedging Language | 완곡 표현. "~로 보인다", "시사한 바 있다" 같이 확신을 낮추는 서술 방식 |
| Hallucination | 환각. 모델이 근거 없는 내용을 사실처럼 생성하는 현상 |
| Competitive Intelligence | 경쟁 정보 조사. 경쟁사에 대한 공개 정보를 수집·분석하는 업무 |

### 에러 처리

| 영어 용어 | 한국어 설명 |
|---|---|
| Error Payload | 에러 페이로드. 실패 시 상위 에이전트에게 전달되는 구조화된 오류 정보 |
| Failure Type | 실패 유형. 오류의 종류. 일시적/영구적 구분이 재시도 여부를 결정 |
| Action Attempted | 시도한 작업. 어떤 도구를 어떤 인자로 호출했는가 |
| Partial Results | 부분 결과. 완전 실패 전까지 확보된 유효 정보 |
| Alternative Approaches | 대안 접근법. 실패 지점에서 제안하는 다음 시도 후보 |
| Reasoning Trace | 추론 트레이스. 모델의 내부 사고 과정 기록. 비구조적이고 길어 에러 전달용으로 부적합 |
| Recovery / Self-correction | 복구·자가 교정. 실패 후 재시도, 우회, 이관 등으로 작업을 이어가는 것 |
| Retry | 재시도. 실패한 호출을 다시 수행하는 것 |

### 평가와 모니터링

| 영어 용어 | 한국어 설명 |
|---|---|
| Human-in-the-Loop (HITL) | 사람 개입. 자동 처리 결과를 사람이 검토하는 안전장치 |
| Human Review | 사람 검토. HITL의 실제 검토 작업 |
| Initial Validation | 초기 검증. 배포 전 특정 시점에 수행하는 일회성 성능 측정 |
| Aggregate Accuracy | 집계 정확도. 전체를 뭉뚱그린 평균 정확도. 세그먼트별 결함을 감춤 |
| Granular Breakdown | 세분화 분해. 문서 유형별·필드별로 성능을 쪼개어 보는 것 |
| Segment | 세그먼트. 문서 유형, 공급업체, 필드 등 의미 있게 구분되는 하위 집단 |
| Simpson's Paradox | 심슨의 역설. 전체 집계에서의 경향이 하위 집단별로 보면 뒤집히거나 사라지는 현상 |
| Ground Truth | 정답 데이터. 사람이 라벨링한 참값. 모든 정확도 측정의 기준 |
| Baseline | 베이스라인. 이후 변화를 비교할 기준이 되는 검증된 성능 수치 |
| Ongoing Sampling | 지속 샘플링. 배포 후에도 정기적으로 표본을 추출해 품질을 감시하는 것 |
| Stratified Random Sampling | 층화 무작위 샘플링. 모집단을 계층으로 나눈 뒤 각 계층에서 무작위 표본을 뽑는 기법 |
| Stratum / Strata | 층. 층화 샘플링에서 나눈 하위 집단 (예: 문서 유형 × 필드) |
| Population | 모집단. 측정 대상 전체 집합 |
| Data Drift | 데이터 드리프트. 입력 데이터의 분포가 시간에 따라 변하는 현상 |
| Concept Drift | 개념 드리프트. 입력과 정답 사이의 관계 자체가 변하는 현상 |
| Distribution Shift | 분포 이동. 학습·검증 시점과 운영 시점의 데이터 분포가 달라지는 것 |
| Failure Mode | 실패 모드. 시스템이 고장 나는 유형·패턴 |
| Silent Failure | 사일런트 실패. 아무도 검토하지 않는 경로에서 발생해 발견되지 않는 오류 |
| Spot Check | 스팟 체크. 임의로 몇 건만 확인하는 비체계적 점검. 통계적 대표성 없음 |
| Statistical Significance | 통계적 유의성. 관측된 차이가 우연이 아닐 가능성. 표본 크기를 키워도 분해 없이는 세그먼트 결함을 못 봄 |

### 신뢰도와 이관

| 영어 용어 | 한국어 설명 |
|---|---|
| Confidence Score | 신뢰도 점수. 결과가 정확할 가능성에 대해 시스템이 부여한 수치 |
| Confidence Threshold | 신뢰도 임계값. 자동 처리와 사람 검토를 가르는 기준값 |
| Calibration | 교정. 신뢰도 0.9인 건들의 실제 정확도가 90%가 되도록 점수와 실제가 일치하는 성질 |
| Uncalibrated | 미교정. 신뢰도 점수와 실제 정확도가 어긋난 상태 |
| Overconfidence | 과신. 모델이 실제 정확도보다 높은 신뢰도를 부여하는 편향 |
| Self-reported / Verbalized Confidence | 자체 보고 신뢰도. 모델이 언어로 스스로 말한 확신도. 신뢰할 수 없음 |
| Proxy | 대리 지표. 직접 측정이 어려운 값을 대신하는 관측 가능한 지표 |
| Grounding Evidence | 근거 자료. 답변을 뒷받침하는 검색된 문서나 조회된 데이터 |
| Escalation | 이관. 에이전트가 사람 상담원이나 상급 프로세스로 사안을 넘기는 것 |
| Policy Gap / Ambiguity | 정책 공백·모호성. 정책 문서가 해당 사안을 허용도 금지도 하지 않은 상태 |
| Edge Case | 엣지 케이스. 정상 시나리오 밖에 있는 예외적 상황 |
| Sentiment Flag | 감정 플래그. 대화의 감정 극성을 자동 분석해 붙이는 표시 |
| Task Complexity | 작업 복잡도. 사안을 해결하는 데 필요한 판단의 난이도. 감정과는 독립적인 축 |
| Guardrail | 가드레일. 시스템이 위험한 행동을 하지 못하도록 막는 안전 장치 |
| Risk-weighted Decision | 리스크 가중 판단. 오류 1건의 피해 크기를 반영해 자동화 범위를 정하는 방식 |
| High-risk Domain | 고위험 도메인. 의료·금융·법률처럼 오류의 결과가 심각한 분야 |
