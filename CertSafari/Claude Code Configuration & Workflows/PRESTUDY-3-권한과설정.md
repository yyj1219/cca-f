# 3. 권한 모델과 설정 계층

이 장에서 다루는 것:

- 설정 파일이 놓이는 세 스코프(개인 / 프로젝트 / 관리형)와 충돌 시 우선순위
- `managed-settings.json`이 유일하게 "강제"가 되는 이유
- 권한 모드 4종(default / plan / acceptEdits / bypassPermissions)과 `dontAsk`
- `--allowedTools` / `permissions.allow`의 패턴 문법과 접두사 매칭 함정
- 어디에 무엇을 둘 것인가 — 종합 결정표

---

## 1. 설정 파일 스코프 계층과 우선순위

### 1.1 파일이 어디 있느냐가 곧 적용 범위다

Claude Code의 동작(권한, 허용 도구, 환경 변수, 훅 등)은 JSON 설정 파일로 조정합니다.
이 주제의 핵심 감각은 하나입니다 — **파일의 위치가 곧 그 설정의 적용 범위**입니다.

| 스코프 | 위치 | 적용 범위 | Git 추적 | 용도 |
|---|---|---|---|---|
| 사용자(개인 / User) | `~/.claude/settings.json` | 그 사람의 노트북 전체, 모든 프로젝트 | ❌ 저장소 밖이라 아예 대상이 아님 | 개인 기본 취향 |
| 프로젝트(Project) | `<프로젝트>/.claude/settings.json` | 그 저장소를 받은 팀 전원 | ✅ 커밋됨 | 팀 공통 규칙 |
| 로컬 프로젝트(Local) | `<프로젝트>/.claude/settings.local.json` | 그 프로젝트, 나만 | ❌ 보통 `.gitignore` | 개인 로컬 오버라이드 |
| 관리형(Managed / Enterprise) | OS 시스템 디렉터리의 `managed-settings.json` | 조직의 모든 머신·모든 리포지토리 | ❌ 구성 관리 시스템으로 배포 | 보안·컴플라이언스 강제 |
| 플러그인(Plugin) | 설치된 플러그인이 제공 | 그 플러그인을 켠 환경 | — | 외부에서 가져온 기능 묶음 |

`~`는 홈 디렉터리를 뜻하는 기호입니다 (Linux는 `/home/이름`, macOS는 `/Users/이름`, Windows는 `C:\Users\이름`). `./`는 현재 프로젝트 디렉터리를 뜻합니다.

### 1.2 우선순위 (충돌하면 누가 이기나)

낮은 우선순위 → 높은 우선순위 순서:

1. **사용자 설정** — `~/.claude/settings.json`. 개인 전역, 본인이 자유롭게 수정 가능.
2. **프로젝트 설정** — `.claude/settings.json`. 팀 공유용, git에 커밋됨. 하지만 개발자가 로컬에서 바꾸거나 커밋을 되돌릴 수 있음.
3. **로컬 프로젝트 설정** — `.claude/settings.local.json`. 개인용, 보통 `.gitignore` 처리.
4. **관리형 설정** — `managed-settings.json`. **최고 우선순위. 위 항목들을 전부 덮어씁니다(override).**

즉 일반적으로 **좁은 범위가 넓은 범위를 덮어씁니다(local > project > user)**. 단, 관리형 설정만은 예외적으로 그 위에 올라앉습니다.

**핵심 판단 기준**: "이 설정이 팀 전체에 적용되어야 하는가, 나에게만인가?"
팀 전체면 `settings.json`(커밋), 나만이면 `settings.local.json`.
개인 취향을 커밋된 파일에 넣으면 다른 팀원의 환경까지 바꿔버립니다.

### 1.3 전형적인 프로젝트 구조

```
my-project/
├── CLAUDE.md                      # 항상 로드되는 프로젝트 지침
└── .claude/
    ├── settings.json              # 훅, 권한, 환경변수 등 설정
    ├── rules/                     # 주제별 규칙 파일들
    │   ├── code-style.md
    │   ├── testing.md
    │   └── terraform.md
    ├── skills/                    # 온디맨드로 로드되는 지식/절차
    │   └── deploy-checklist/
    │       └── SKILL.md
    ├── commands/                  # /슬래시커맨드 정의
    │   └── review.md
    └── agents/                    # 서브에이전트 정의
        └── researcher.md
```

### 1.4 `managed-settings.json` — 유일하게 "강제"가 되는 것

조직 전체에 강제해야 하는 보안·컴플라이언스 정책을 위한 파일입니다.
사용자 홈이 아니라 **OS의 시스템 디렉터리**에 배치합니다.

- Linux: `/etc/claude-code/managed-settings.json`
- macOS: `/Library/Application Support/ClaudeCode/managed-settings.json`
- Windows: `C:\ProgramData\ClaudeCode\managed-settings.json`

배포는 보통 조직의 **구성 관리 시스템(configuration management)** — Ansible, Puppet, Chef, MDM(Jamf, Intune) 등 — 으로 모든 머신에 뿌립니다.

**왜 이것만이 "강제"가 되는가**

시스템 디렉터리는 일반적으로 관리자 권한이 있어야 쓸 수 있고,
설정 우선순위상 개발자 개인 설정이나 프로젝트 설정으로 **덮어쓸 수 없기 때문**입니다.
"모든 개발자가, 모든 머신에서, 모든 리포지토리에서 받고, 개인이 끌 수 없어야 한다"는 요구를 만족하는 유일한 수단입니다.

**왜 다른 방법은 부족한가 (개념 이해용 대조)**

- 리포지토리 루트 `CLAUDE.md`: 프로젝트 수준일 뿐입니다. 개발자가 로컬에서 수정·삭제할 수 있고, 리포지토리마다 따로 챙겨야 하며, 더 높은 우선순위 설정으로 우회될 수 있습니다.
- `~/.claude/CLAUDE.md`를 온보딩 스크립트로 채우기: 개인 디렉터리라 이후 개발자가 자유롭게 편집·삭제할 수 있고 우선순위도 낮습니다. 강제력이 없습니다.
- `CLAUDE.local.md`: 애초에 개인 로컬 전용이고 `.gitignore` 대상이라 추적도 강제도 되지 않습니다.

**요령: "강제(enforce)" 요구가 나오면 시스템 수준 관리형 설정, "공유(share)" 요구면 프로젝트 파일.**

### 1.5 개인 범위 vs 프로젝트 범위 — 두 개의 `.claude` 디렉터리가 만드는 상황

**상황 A — 팀과 공유하려던 게 공유되지 않는다.**
개발자가 `/lint-report` 슬래시 명령어를 만들었는데, 본인은 잘 되고 팀원은 "그런 명령어 없다"고 합니다. 확인해 보니 그 파일은 어떤 커밋에도 스테이징된 적이 없습니다.

원인: 파일을 `~/.claude/commands/lint-report.md`에 만든 것입니다. 이 경로는 **저장소 바깥**이므로 `git status`에도 잡히지 않고, `git add`도 되지 않고, 당연히 팀원이 pull해도 오지 않습니다.

해결: `<프로젝트>/.claude/commands/lint-report.md`(또는 스킬 구조)에 두고 커밋합니다.

(참고: CI 파이프라인이 돌아야 슬래시 명령어가 활성화된다거나, 새 명령어를 인식하려면 컴퓨터를 재부팅해야 한다거나, 스킬 공유에 엔터프라이즈 라이선스가 필요하다는 것은 전부 사실이 아닙니다.)

**상황 B — 나만 쓰고 싶은데 팀에 노출된다.**
개발자가 자기 스탠드업 노트를 정리하는 `/my-standup` 명령어를 만들고 싶은데, 팀원의 `/` 메뉴에 뜨거나 PR에 파일이 올라가는 건 원치 않습니다.

해결: `~/.claude/skills/my-standup/SKILL.md`에 만듭니다. 홈 디렉터리이므로 Git이 추적하지 않고, 본인 환경에서만 `/my-standup`으로 호출됩니다.

여기서 두 가지 흔한 오해:

- `.claude/commands/_my-standup.md`처럼 **파일명 앞에 밑줄을 붙이면 무시된다** → 그런 규칙은 없습니다. 프로젝트 폴더에 있는 이상 Git에 잡히고 PR에 올라갑니다.
- 프로젝트에 넣고 "PR 리뷰어에게 이 파일은 무시해 달라고 부탁" → 규율에 의존하는 방식이라 언제든 깨집니다. 경로로 해결하는 게 옳습니다.

### 1.6 커스텀 명령어 vs 스킬 (`commands/` vs `skills/`)

**`commands/` 형태 — 파일 하나**
```
~/.claude/commands/my-standup.md      → /my-standup 으로 호출
.claude/commands/lint-report.md       → /lint-report 으로 호출
```
파일 이름이 곧 명령어 이름입니다. 초기부터 있던 방식입니다.

**`skills/` 형태 — 디렉터리 + SKILL.md** (현재 권장 구조)
```
~/.claude/skills/my-standup/SKILL.md
.claude/skills/migration-plan/SKILL.md
```
`SKILL.md`는 프론트매터로 이름과 설명을 선언하고, 본문에 지시사항을 씁니다. 디렉터리 형태이므로 참조 문서·스크립트 같은 부속 파일을 함께 담을 수 있고, 설명을 근거로 상황에 맞게 자동 호출되기도 합니다.

`commands/`도 여전히 동작하지만, Anthropic의 현재 모범 사례는 **`skills/` 아래 `SKILL.md` 구조**입니다.

### 1.7 CLAUDE.md — 프로젝트 상시 컨텍스트

`CLAUDE.md`는 **프로젝트 루트에 두면 Claude Code가 세션 시작 시 자동으로 읽어 컨텍스트에 넣는** 파일입니다. 매 프롬프트에 반복해서 붙일 필요 없이 항상 적용됩니다. 로컬 실행이든 CI 실행이든 동일하게 적용됩니다.

여기에 넣기 좋은 것: 코딩 컨벤션, 빌드/테스트 명령어, 아키텍처 개요, 테스트 기준, 사용 가능한 픽스처 목록, 하지 말아야 할 것.

### 1.8 `claudeMdExcludes` — 개인 환경 문제는 개인 설정으로

**무엇인가**: 특정 경로 패턴의 `CLAUDE.md` 파일이 자동 로드되지 **않도록 차단**하는 설정입니다.
"제외 목록"이며, **로드를 유발하는 설정이 아닙니다.** (방향을 헷갈리기 쉬운 지점입니다.)

**언제 쓰는가**: 모노레포에서 루트 `CLAUDE.md`가 임포트로 모든 하위 패키지를 끌어오는데, 나는 `packages/web`만 담당해서 나머지가 전부 잡음일 때.

**개인만 적용하려면 `settings.local.json`에 넣습니다:**

`.claude/settings.local.json`
```json
{
  "claudeMdExcludes": [
    "packages/admin-dashboard/**",
    "packages/legacy-*/**"
  ]
}
```

이러면 내 기기의 세션에서만 그 패키지들의 `CLAUDE.md`가 로드되지 않습니다. `admin-dashboard`를 담당하는 동료의 환경은 그대로입니다.

**하지 말아야 할 대안들과 그 이유:**

- **커밋된 `settings.json`에 넣기** → 팀 전원의 세션에서 차단됩니다. 그 패키지 담당자가 필요한 컨텍스트를 잃습니다.
- **다른 패키지의 `CLAUDE.md` 파일 자체를 삭제** → 남의 작업 환경을 파괴하는 행위입니다. 파일은 실제로 사용 중입니다.
- **팀에게 파일 구조를 바꿔달라고 요청** → 개인 환경 하나 정리하려고 조직 전체를 움직이는 과잉 대응이며, "내 세션에서만"이라는 요구와 맞지 않습니다.

**원칙**: 개인 환경 문제는 개인 설정 파일로 푼다.

## 2. 권한 모드 (Permission Modes)

### 2.1 왜 권한 모드가 필요한가

Claude Code는 실제로 파일을 고치고 셸 명령을 실행합니다. 에이전트가 셸을 쓸 수 있다는 것은 `rm -rf`도 실행할 수 있다는 뜻이고, 의도치 않은 외부 네트워크 전송도 실질적 피해를 줍니다.
그래서 도구 호출마다 **승인(approval)** 절차를 두고, "어디까지 사람 확인 없이 진행해도 되는가"를 **모드**로 구분합니다. 모드는 위험도를 조절하는 다이얼이라고 생각하면 됩니다.

기본 동작은 "위험한 동작을 하기 전에 사용자에게 프롬프트를 띄워 물어본다"입니다. 하지만 CI 같은 자동화 환경에는 답할 사람이 없으므로, 미리 규칙으로 정해두어야 합니다.

### 2.2 모드 일람

| 모드 | 동작 | 쓰는 상황 |
|---|---|---|
| **default (normal, 대화형)** | 파일 수정·셸 실행 등 미승인 동작마다 그때그때 승인 요청 | 사람이 앞에 앉아 있는 로컬 개발. 가장 안전한 기본값 |
| **plan** (계획 모드) | **읽기 전용.** 모든 수정/파괴적 명령이 시스템 차원에서 차단. 읽기·검색은 승인 없이 진행 | 큰 변경 전 설계 검토 |
| **acceptEdits** (accept-edits) | 파일 편집류를 자동 승인, 그 외(예: 위험한 Bash)는 여전히 확인 | 방향이 확실한 반복 편집, 신뢰하는 작업을 빠르게 반복할 때 |
| **bypassPermissions** | 승인 절차를 광범위하게 우회 | 격리된 샌드박스/CI에서 매우 제한적으로만 (고위험) |
| **dontAsk** | 프롬프트를 띄우지 않음. `permissions.allow` 규칙이나 내장 읽기 전용 명령 세트에 없는 것은 **즉시 거부** | 사람이 없는 CI/CD, 잠금 환경 |

### 2.3 Plan mode 상세

**무엇인가:** Claude가 코드베이스를 탐색해서 이해한 뒤, **수정하기 전에 사람에게 계획서를 제출**하는 모드입니다. 사람이 승인해야 비로소 실행 단계로 넘어갑니다.

**왜 있는가:** 큰 아키텍처 변경에서는 "어떻게 고칠지"보다 "어느 방향으로 나눌지"가 훨씬 중요합니다. 잘못된 방향으로 200개 파일을 고친 뒤에 되돌리는 비용은 막대합니다. 계획 모드는 그 되돌리기 비용을 **0으로** 만듭니다 — 아직 아무것도 안 고쳤으니까요.

**어떻게 동작하는가:**
1. Claude가 관련 파일을 읽고 구조를 파악
2. 여러 대안(예: 서비스 경계를 A/B/C로 나누는 세 가지 안)을 비교
3. 트레이드오프와 함께 설계안 제시
4. 사람이 승인 / 수정 요청 / 거부
5. 승인 시에만 편집 시작

**권한 모델 관점에서:**
- **모든 파일 수정과 파괴적 명령이 시스템 차원에서 차단**됩니다.
- **읽기와 읽기 전용 검색은 매번 승인을 묻지 않고 그냥 진행**됩니다.

두 번째가 처음엔 이상해 보이지만, 이유는 단순합니다. 수정이 원천적으로 불가능하다는 **읽기 전용 보장(read-only guarantee)** 이 이미 있으므로, 읽기 하나하나에 승인을 받는 것은 안전성에 아무것도 더해 주지 않고 탐색만 느리게 만듭니다. 그래서 프롬프트를 생략하는 것이 정상 설계입니다.

**언제 쓰는가 (판단 기준):**
- 변경이 **여러 파일 / 여러 모듈**에 걸친다
- **정답이 여러 개**다 (설계 선택지가 경쟁 관계)
- 되돌리기 비용이 크다 (데이터 모델, 서비스 경계, 배포 구조 등)
- 예: 모놀리스를 마이크로서비스 3개로 쪼개는 작업 → 공유 데이터 모델, 서비스 경계, 배포 토폴로지가 모두 얽힘 → **계획 모드가 정석**

**언제 안 쓰는가:** 원인이 이미 명확하고 한 줄 고치면 되는 일. 계획 모드는 안전장치이지 의무적인 의식(ritual)이 아닙니다.

**정리해 둘 사실 (오해 방지):**
- Plan mode가 사용자 모르게 `acceptEdits`로 자동 전환되는 동작은 **없습니다**.
- 읽기 전용 명령이 **모든** 권한 모드에서 영구 면제되는 것은 **아닙니다**. 일반 모드에서는 설정이나 위험도 판단에 따라 읽기/실행에도 승인이 걸릴 수 있습니다. Plan mode에서 승인 없이 진행되는 것은 그 모드의 고유 성질입니다.

### 2.4 acceptEdits의 정확한 범위

`--permission-mode acceptEdits`는 이름 그대로 **"편집(edits)"을 자동 승인**합니다.

**자동 승인되는 것**
- 파일 생성·수정·삭제 (Write / Edit)
- 흔한 파일시스템 명령: `mkdir`, `mv`, `cp` 등

**자동 승인되지 않는 것**
- 그 밖의 임의 셸 명령
- **네트워크 요청** (외부에서 데이터를 가져오거나 보내는 동작)

이유는 위험 성격이 다르기 때문입니다. 로컬 파일 편집은 git으로 되돌릴 수 있지만, 네트워크 요청은 외부로 데이터를 유출하거나 신뢰할 수 없는 코드를 끌어올 수 있어 되돌릴 수 없는 부류입니다. 그래서 별도 허용이 필요합니다.

이런 동작을 자동화하려면 **명시적으로 허용**해야 합니다.
- CLI 플래그: `--allowedTools`
- 설정 파일: `permissions.allow` 규칙

**전형적인 CI 실패 시나리오**

```bash
claude -p "apply the lint fixes" --permission-mode acceptEdits
```

CI는 **비대화형(non-interactive)** 환경이라 승인 프롬프트에 사람이 답할 수 없습니다.
앞부분의 파일 편집은 `acceptEdits` 범위라 조용히 통과하지만, 중간에 "최신 의존성 목록을 가져오자"며 네트워크 요청을 시도하는 순간 승인이 필요해지고, 물어볼 사람이 없으므로 **실행이 중단(abort)** 됩니다.
해결은 그 도구/명령을 `--allowedTools` 또는 `permissions.allow`에 넣어 주는 것입니다.

**정리해 둘 사실 (오해 방지):**
- `acceptEdits`가 "첫 번째 도구 호출에만" 적용된다는 규칙은 **없습니다**. 편집은 몇 번이든 자동 승인됩니다.
- 프린트 모드(`-p`)라고 해서 네트워크 요청이 무조건 차단되는 것은 **아닙니다**. 권한 정책으로 허용 가능합니다.
- `acceptEdits`가 동작하려면 `--bare` 같은 별도 플래그가 필요하다는 조건은 **없습니다**.

### 2.5 dontAsk — 자동화 환경의 정답

`dontAsk`가 자동화에 맞는 이유: 비대면(non-interactive) 환경에서 프롬프트가 뜨면 프로세스가 **무한 대기**에 빠집니다. `dontAsk`는 애초에 묻지 않고 거부하므로 실행이 즉시 중단되고, CI 잡은 명확히 실패합니다. "허용 목록 + 그 외 전부 거부"라는 화이트리스트 보안 모델이기도 합니다.

각 대안이 "읽기 전용 최소 집합만 허용, 그 외에는 중단" 요구를 못 맞추는 이유:

- `acceptEdits`는 **쓰기 작업을 자동 승인**하므로 요구와 정반대입니다.
- **턴 수 제한**(`--max-turns 1`)은 에이전트가 몇 번 왕복할지를 제한할 뿐, *어떤* 명령을 실행할 수 있는지는 전혀 통제하지 못합니다. 1턴 안에서도 위험한 명령이 실행될 수 있습니다.
- **프롬프트 + 짧은 타임아웃**은 무의미한 대기 시간을 만들고, 타임아웃이 어긋나면 파이프라인이 블로킹됩니다. 애초에 물어보지 않게 만드는 것이 옳습니다.

### 2.6 bypassPermissions 주의점

모든 승인 절차를 없애므로 사람의 검토 지점이 사라집니다.
아키텍처 수준의 의사결정을 이 모드로 CI에 맡기면, 잘못된 설계가 사람 눈을 거치지 않고 머지됩니다.
"자동화 = 좋음"이 아니라 **"검토가 필요 없는 일만 자동화"** 가 원칙입니다.

## 3. allow / deny / ask 규칙

### 3.1 `--allowedTools`와 `permissions.allow`

`--allowedTools`는 **프롬프트 없이 자동 승인할 도구/명령을 지정**하는 CLI 옵션입니다.

```bash
claude -p "run the migration script" --allowedTools "Bash(npm run migrate)"
```

형식은 `도구이름(인자패턴)`입니다. `Bash(...)` 안의 문자열이 실행될 명령과 대조됩니다.

같은 규칙을 설정 파일에 영구적으로 적어둘 수도 있습니다.

- `permissions.allow`: 설정 파일(`settings.json`)에 적어두는 허용 규칙 목록. `--allowedTools`와 **같은 패턴 문법**을 씁니다.
- **내장 읽기 전용 명령 세트**: `ls`, `cat`, `grep` 처럼 상태를 바꾸지 않는다고 판단되는 명령들. 별도 승인 없이 허용되는 기본 안전 집합입니다.

`dontAsk`는 정확히 이 두 집합(=`permissions.allow` + 내장 읽기 전용 세트)만 통과시키고 나머지를 막습니다.

### 3.2 핵심 규칙 — 끝에 붙은 별표는 접두사 매칭(prefix matching)

| 패턴 | 매칭되는 것 |
|---|---|
| `Bash(npm run migrate)` | 정확히 `npm run migrate` 만 |
| `Bash(npm run migrate*)` | `npm run migrate`, `npm run migrate-cleanup`, `npm run migrate:dev`, `npm run migrateEverything` … |

`*`는 "그 뒤에 무엇이 오든 상관없음"을 뜻합니다. 따라서 `Bash(npm run migrate*)`로 써 두면 의도하지 않은 `npm run migrate-cleanup`까지 **프롬프트 없이 자동 실행**됩니다. 정확히 한 명령만 허용하려면 **별표를 빼야** 합니다.

### 3.3 혼동하기 쉬운 오해들

- 이 패턴은 정규표현식이 아니라 **글로브(glob) 스타일 와일드카드**입니다. 정규식의 `*`(앞 문자 0회 이상 반복)나 교차(alternation)와는 의미가 다릅니다.
- `acceptEdits` 같은 다른 권한 모드가 `--allowedTools`의 매칭 폭을 몰래 넓히지 않습니다. "migrate라는 단어를 포함하면 매칭" 같은 규칙도 존재하지 않습니다.
- 매칭 방식을 바꾸는 마법의 플래그(`--bare` 등) 같은 것은 없습니다. 넓어진 원인은 **패턴 그 자체**입니다.

### 3.4 스킬 수준의 도구 제어

규칙은 전역 설정뿐 아니라 스킬 단위로도 걸 수 있습니다.

- 스킬 프론트매터의 `allowed-tools`: 그 스킬이 도는 동안 특정 도구를 **승인 없이** 쓰게 사전 승인.
- 스킬 프론트매터의 `disallowed-tools`: 특정 도구를 아예 **풀에서 제거**해 절대 못 쓰게 함.
- 100% 강제되어야 하는 정책은 `settings.json` + `PreToolUse` 훅으로 결정론적으로 막습니다 (모델의 판단에 맡기지 않음).

| 특정 도구를 절대 못 쓰게 하기 | 스킬 + `disallowed-tools` | 풀에서 제거 |

| CI 등 비대화형 환경의 안전한 실행 | `dontAsk` + `permissions.allow` | 무한 대기 대신 즉시 실패, 화이트리스트 |
