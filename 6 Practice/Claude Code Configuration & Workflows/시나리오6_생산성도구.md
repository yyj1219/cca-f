# 시나리오6_생산성도구

## 질문 1

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : An engineer must swap a deprecated messaging library across roughly 50 files of an unfamiliar legacy service; two integration approaches with different infrastructure needs are both viable. How should the work begin in Claude Code?

**A.** Use direct execution with /compact after each batch of files to keep the growing context from derailing the migration.

**설명**

압축(compaction)은 긴 세션 동안 컨텍스트 크기를 관리하는 기능일 뿐, 두 가지 접근 방식 중 무엇을 선택할지 해결해주지도 않고 편집을 시작하기 전에 낯선 코드에 대한 이해를 쌓는 데도 도움이 되지 않는다. 요약 과정에서 정밀한 세부 정보가 누락될 수도 있어, 광범위한 마이그레이션에서는 위험을 줄이기보다 오히려 늘리는 결과를 낳는다.

**B.** Begin direct execution on a small subset of files and let the emerging changes reveal which integration approach fits.

**설명**

이 방식은 코드가 이미 작성된 이후로 아키텍처 결정을 미루는 것이므로, 마이그레이션 중간에 선택한 접근 방식이 인프라 요구사항과 충돌한다는 사실을 발견할 위험이 있다. 일부만 마이그레이션된 파일을 다시 작업하는 것은 실행 전에 계획을 반복해서 다듬는 것보다 훨씬 더 큰 비용이 든다.

**C.** Write a detailed upfront prompt specifying every file to change, then run in direct execution against that specification.

**설명**

이 방식은 엔지니어가 이미 레거시 코드베이스를 충분히 이해하고 있어서 모든 변경 사항을 나열할 수 있다고 가정하는데, 이는 상황과 맞지 않는다. 탐색 과정 없이는 사양에서 호출 지점과 의존 관계가 빠질 가능성이 높고, 두 접근 방식 중 어느 것을 선택할지에 대한 검토도 여전히 이루어지지 않는다.

**D(정답).** Enter plan mode so Claude explores the codebase read-only and proposes an approach for approval before any edits.

**설명**

이 방식이 정답인 이유는 이 작업이 계획 모드를 사용해야 하는 모든 조건에 해당하기 때문이다. 많은 수의 파일, 낯선 코드베이스, 그리고 인프라에 서로 다른 영향을 미치는 여러 유효한 접근 방식이 모두 존재한다. 계획 모드는 Claude가 변경을 가하지 않고 안전하게 조사할 수 있게 하며, 엔지니어에게 검토할 계획을 제공하므로, 어떤 코드도 커밋되기 전에 접근 방식에 대한 결정을 신중하게 내릴 수 있다.

### 전반적인 설명

Claude Code의 계획 모드는 정확히 이런 유형의 작업을 위해 설계된 권한 모드다. Claude는 파일을 읽고 코드베이스를 탐색할 수 있지만, 사용자가 제안된 계획을 승인하기 전까지는 소스 편집이 차단된다. 이때의 사고 모델은 "먼저 조사하고 제안한 뒤, 그다음에 실행한다"는 것이다. Anthropic이 권장하는 작업 흐름은 탐색-계획-구현-커밋이다. 계획 모드에 진입해 Claude가 부작용 없이 질문에 답하고 의존 관계를 파악하게 한 뒤, Claude가 만든 구현 계획을 검토하고, 계획을 승인해 실행 모드로 전환한다.

이 의사결정 프레임워크는 세 가지 신호에 좌우되며, 이 사례에는 모두 해당된다. 변경이 여러 파일에 걸쳐 있다는 점, 코드베이스가 낯설다는 점, 그리고 코드를 작성하기 전에 인프라적 영향을 저울질해야 하는 경쟁적인 접근 방식이 존재한다는 점이다. 계획을 반복해서 다듬는 것은 빠르고 비용이 적게 들지만, 절반쯔음 완료된 50개 파일 마이그레이션을 반복해서 고치는 것은 둘 다 아니다. 반대로, 단일 파일 수정처럼 작고 이미 잘 이해된 변경에는 계획 모드가 불필요한 오버헤드를 더할 뿐이다. 그래서 이 프레임워크는 "항상 계획하라"는 규칙이 아니라 실질적인 트레이드오프에 관한 것이다.

오답들은 각기 다른 방식으로 실패한다. 접근 방식을 "발견"하기 위해 점진적으로 실행하는 방식은 아키텍처 결정을 매몰 비용에 기반한 재작업으로 바꿔버린다. 상세한 사전 사양 작성은 엔지니어가 갖고 있지 않은 레거시 코드에 대한 지식을 전제하며, 접근 방식 비교 자체를 건너뛴다. /compact는 긴 세션을 위한 컨텍스트 관리 도구일 뿐, 코드베이스를 탐색하거나 대안을 평가하지 않으므로 다른 문제를 다루는 도구다. 계획이 언제 도움이 되는지에 대한 공식 문서화된 지침은 권한 모드(Permission modes)와 Claude Code 모범 사례(Claude Code best practices) 문서를 참고하라.

## 질문 2

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : An engineer on this team wants Claude Code to follow their personal working preferences (for example, explaining shell commands before running them) in every repository they open, while guaranteeing teammates never receive those preferences through version control. Where should these instructions live?

**A.** In the project-level CLAUDE.md under a clearly labeled personal section.

**설명**

프로젝트 수준의 CLAUDE.md는 버전 관리에 커밋되며 모든 팀원의 세션에 로드된다. 레이블을 붙인다고 해서 가시성이 제한되는 것은 아니므로, 개인 선호 설정이 여전히 팀 전체에 전달된다.

**B.** In a gitignored CLAUDE.local.md file created in each repository.

**설명**

CLAUDE.local.md은 버전 관리에서 제외되는 개인적인 프로젝트별 지침을 위한 공식 문서화된 위치이며, 그 범위는 모든 프로젝트가 아니라 하나의 프로젝트에 한정된다. 이 방식으로는 엔지니어가 여는 모든 저장소마다 선호 설정을 다시 만들고 유지 관리해야 한다. 모든 프로젝트에 적용되어야 하는 선호 설정에는 사용자 수준 파일이 적절한 범위다.

**C.** In ~/.claude/settings.json, which applies personal configuration across all projects.

**설명**

사용자 수준의 settings.json은 범위는 맞지만 콘텐츠 유형이 맞지 않는다. 이 파일은 권한이나 도구 설정 같은 JSON 구성을 담는 곳이며, Claude가 따라야 할 자연어 지침을 담는 곳이 아니다. 행동 관련 선호 설정은 메모리 파일에 두어야 한다.

**D(정답).** In ~/.claude/CLAUDE.md in the engineer's home directory.

**설명**

사용자 수준의 CLAUDE.md는 해당 사용자에게만 적용되며 그 사람의 컴퓨터에 있는 모든 프로젝트에 걸쳐 적용되고, 버전 관리를 통해 전달되는 일이 결코 없다. 이는 팀원에게 영향을 주지 않으면서 한 엔지니어를 어디서나 따라다녀야 하는 개인 선호 설정을 위한 공식 문서화된 정확한 위치다.

### 전반적인 설명

Claude Code의 메모리 파일은 위치에 따라 범위가 정해지며, 이를 이해하는 사고 모델은 두 축으로 이루어진 격자다. 누가 그 지침을 보는가(나 혼자, 또는 팀 전체)와 어디에 적용되는가(하나의 프로젝트, 또는 모든 프로젝트)이다. ~/.claude/CLAUDE.md에 있는 사용자 수준 파일은 "나 혼자, 모든 프로젝트"에 해당하는 칸을 차지한다. 이 파일은 홈 디렉터리에 있으므로 그 컴퓨터에서 엔지니어가 시작하는 모든 세션에 로드되며, 저장소에 커밋될 수 없으므로 구조적으로 팀원이 받을 수 없다. 이 때문에 프로젝트 전체에 걸친 개인 선호 설정을 위한 올바른 위치가 된다.

격자의 나머지 칸들을 보면 다른 선택지들이 왜 맞지 않는지 알 수 있다. CLAUDE.local.md는 "나 혼자, 하나의 프로젝트" 칸에 해당한다. 개인적인 프로젝트별 지침을 담고 .gitignore를 통해 버전 관리에서 제외된다. 이 범위는 저장소에 종속된 개인 메모에는 적합하지만, 저장소별로 선호 설정을 두면 모든 프로젝트에서 중복 작성하고 동기화를 유지해야 하므로 항상 적용되어야 하는 개인 선호 설정의 취지에 맞지 않는다. 저장소 루트에 있는 프로젝트 수준 CLAUDE.md는 "팀 전체" 칸이다. 여기에 작성된 내용은 섹션에 어떤 레이블을 붙였는지와 무관하게 소스 관리를 통해 공유되므로, 팀원이 절대 봐서는 안 되는 내용을 두기에는 잘못된 위치다. 마지막으로 ~/.claude/settings.json은 사용자 범위는 공유하지만 전혀 다른 목적을 갖는다. 이 파일은 권한 규칙 같은 구조화된 설정을 담는 곳이며, Claude의 동작을 형성하는 서술형 지침을 담는 곳이 아니다.

지침 파일의 전체 계층 구조와 공유 범위에 대해서는 Claude Code 메모리(Claude Code memory) 공식 문서를, JSON 설정 파일에 무엇이 들어가야 하는지에 대해서는 Claude Code 설정(Claude Code settings) 문서를 참고하라.

## 질문 3

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : A nightly pipeline job invokes Claude Code to scaffold boilerplate modules, but the job hangs indefinitely waiting for input no human will provide. Which two invocation changes prevent the hang? (Select two.)

**A(정답).** Run the invocation with the -p flag so the prompt is processed non-interactively and the process exits.

**설명**

-p(또는 --print) 플래그는 Claude Code를 비대화형으로 실행하는 공식 문서화된 방법이다. 프롬프트를 처리하고 결과를 표준 출력에 기록한 뒤 사용자 입력을 기다리지 않고 종료한다. 이는 작업이 멈추게 만드는 대화형 세션 자체를 없애버린다.

**B.** Add --output-format json, which switches Claude Code into non-interactive mode for automated environments.

**설명**

--output-format 플래그는 결과가 출력되는 형식을 제어하며, 파이프라인에서 출력을 파싱할 때 유용하지만 실행 모드를 바꾸지는 않는다. -p 없이는 세션이 여전히 대화형으로 유지되어 작업이 계속 멈춘다.

**C.** Pass the prompt as a positional argument to claude, which runs the command without entering an interactive session.

**설명**

-p 플래그 없이 인용된 프롬프트만으로 claude를 실행하면 그 프롬프트로 시작된 대화형 세션이 열리므로, 프로세스는 여전히 추가 입력을 기다린다. 실행을 비대화형으로 만드는 것은 오직 -p 또는 --print 플래그뿐이다.

**D(정답).** Pre-approve the tools the job needs with --allowedTools so tool calls never pause for a permission prompt.

**설명**

print 모드에서도, 평소 권한 확인을 요구하는 도구 호출은 답할 사람이 없는 실행을 멈춰 세울 수 있다. --allowedTools로 필요한 도구들을 나열하면 자동으로 승인되어 파이프라인이 사람 개입 없이 진행된다.

### 전반적인 설명

Claude Code에는 근본적으로 다른 두 가지 실행 모드가 있으며, 이런 종류의 CI 실패는 거의 항상 이 둘을 혼동한 데서 발생한다. claude "some prompt"를 실행하면 그 프롬프트를 시작 메시지로 삼은 대화형 세션이 열린다. 이후 프로세스는 다음 턴을 기다리는데, 파이프라인에서는 이것이 영원히 기다리는 것을 의미한다. claude -p "some prompt"(--print와 동일)를 실행하면 헤드리스 모드로 동작한다. 프롬프트가 처리되고 결과가 표준 출력으로 나가고 프로세스가 종료된다. 실행을 스크립트에서 안전하게 만드는 것은 프롬프트 인자의 존재 여부가 아니라 바로 이 플래그다.

플래그만으로는 사람 개입 없는 실행을 위한 필요조건이지만 충분조건은 아니다. 평소 권한 확인 프롬프트를 유발하는 도구 호출들도 여전히 해결 경로가 필요하므로, 헤드리스 호출은 보통 --allowedTools와 함께 사용되어 작업에 필요한 특정 도구들을 자동으로 승인한다(이는 "이 도구들을 묻지 않고 실행하라"는 의미이며, "실행을 이 도구들로 제한하라"는 의미가 아님에 주의하라). 여기서의 사고 모델은 두 개의 별도 관문이다. -p는 대화 대기를 제거하고, 권한 설정은 승인 대기를 제거한다. 이 두 관문 중 어느 하나라도 닫혀 있으면 작업이 멈출 수 있다.

출력 형식은 이 두 관문과는 무관하다. --output-format json은 결과를 기계가 파싱할 수 있게 만들어주며, 파이프라인이 결과를 소비해야 할 때 유용하지만, 프로세스가 입력을 기다리는지 여부에는 아무런 영향을 주지 않는다. 공식 문서화된 호출 방식은 헤드리스 모드(Headless mode)와 CLI 레퍼런스(CLI reference)를 참고하라.

## 질문 4

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : This team's automated PR review re-runs whenever new commits are pushed, and each re-run already receives the prior findings so it posts only deltas. An engineer proposes shrinking what each re-run examines to cut latency. Which review scope is correct?

**A.** Review only the diff of the commits pushed since the previous review ran.

**설명**

이 방식은 잘못되었다. 증분 diff만 보는 방식은 새 커밋이 PR에서 이전에 변경된 코드와 어떻게 상호작용하는지에서 발생하는 문제를 놓치기 때문이다. 새 커밋이 세 커밋 전에 도입된 불변 조건을 깨뜰 수 있는데, 그 자체만 보면 최신 diff에는 아무런 의심스러운 점이 나타나지 않을 수 있다.

**B.** Review only the files that carried findings in the previous review.

**설명**

이 방식은 잘못되었다. 이전 검토에서 문제없다고 판단한 파일에서 발생하는 새로운 문제를 전혀 보지 못하게 만들기 때문이다. 새 커밋은 이전에 발견 사항이 없던 파일에도 흔히 문제를 만들어내므로, 이 범위는 재검토가 제공해야 할 바로 그 커버리지를 희생시킨다.

**C(정답).** Review the full cumulative PR diff on every re-run.

**설명**

이 방식이 정답인 이유는 중복 억제가 이미 컨텍스트로 제공된 이전 발견 사항으로 처리되고 있으므로, diff 범위는 완전한 상태로 유지되어야 한다는 것이다. 새 커밋은 이전 변경 사항과 상호작용할 수 있으며, 전체 diff를 검토해야만 그런 상호작용을 발견하고 어떤 이전 발견 사항이 실제로 해결되었는지 확인할 수 있다.

**D.** Review the newest commit's diff plus any files it touches that earlier commits also modified.

**설명**

이 방식은 잘못되었다. 커밋 간 상호작용이 두 번 이상 편집된 파일에만 한정되지 않기 때문이다. 새 커밋은 공유 인터페이스나 호출자를 변경하는 방식으로, 자신이 전혀 건드리지 않은 파일에서 이전에 추가된 코드의 동작을 바꿀 수 있다. 따라서 이 방식으로는 여전히 커버리지 공백이 남는다.

### 전반적인 설명

핵심 사고 모델은 재검토의 노이즈와 재검토의 커버리지가 서로 독립된 두 개의 레버로 제어된다는 것이다. 노이즈는 컨텍스트 설계 문제다. 검토자에게 자신의 이전 발견 사항을 다시 제공하고 새롭거나 아직 해결되지 않은 문제만 보고하도록 지시함으로써 중복 댓글을 억제한다. 커버리지는 범위 문제다. 검토자는 자신이 읽은 것만 표시할 수 있다. 설명된 설정에서는 노이즈 레버가 이미 갖춰져 있으므로, diff를 좁히는 것은 이미 해결된 문제를 위해 커버리지를 희생하는 셈이 된다.

매번 재실행할 때마다 전체 누적 diff를 검토하는 것이야말로 델타 보고를 신뢰할 수 있게 만든다. 풀 리퀘스트의 변경 사항들은 서로 독립적이지 않다. 이후 커밋이 이전 커밋에서 도입된 가정을 위반하거나, 수정 사항을 되돌리거나, 이전 코드가 의존하는 공유 인터페이스를 변경할 수 있다. 전체 변경 집합을 보는 검토자만이 이러한 상호작용을 탐지할 수 있고, 모든 것을 다시 검토하는 검토자만이 이전 발견 사항이 최신 커밋의 diff에 단순히 나타나지 않은 것이 아니라 실제로 해결되었는지를 확인할 수 있다.

범위를 좁히는 각 전략은 같은 축에서 실패한다. 증분 diff만 보는 방식은 커밋 간 영향을 완전히 숨긴다. 이전에 발견 사항이 있던 파일로만 검토를 제한하면 문제없던 파일의 새로운 결함이 검토되지 않는다. 여러 커밋에서 건드린 파일을 추가하는 절충적 방식은 우연히 같은 파일에서 겹치는 상호작용만 잡아낼 뿐, 호출자나 인터페이스, 설정을 통한 동작적 결합은 놓친다. 올바른 트레이드오프는 검토 범위를 완전하게 유지하고, 축소된 diff가 아니라 이전 발견 사항 컨텍스트가 출력을 조용하게 유지하도록 하는 것이다.

CI에서 자동화된 검토를 실행하는 방법은 Claude Code GitHub Actions를 참고하라.

The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : The team wants the agent to interview an engineer about requirements and edge cases before automating a legacy-system task. Using the Agent SDK, how does the agent's clarifying question actually reach your application?

**A.** Configure a PreToolUse hook that intercepts the AskUserQuestion call and returns the engineer's answer as the hook's output.

**설명**

훅(hook)은 도구 호출을 검증하거나 차단하거나 반응하기 위해 존재하는 것이지, 사용자의 명확화 질문에 대한 답을 전달하는 채널이 아니다. Agent SDK는 AskUserQuestion을 can_use_tool 콜백을 통해 애플리케이션으로 전달하며, 이 콜백은 앱이 응답할 때까지 실행을 일시 정지시킨다.

**설명**

이것이 바로 Agent SDK가 명확화 질문을 드러내는 방식이다. Claude는 AskUserQuestion 도구를 통해 사용자 입력을 요청하며, 이는 can_use_tool 콜백을 트리거하고 애플리케이션이 응답을 제공할 때까지 실행을 일시 정지시켜, 앱이 원하는 방식으로 질문을 렌더링할 수 있게 한다.

**C.** Read the question from a plain text block in the assistant's final message, then send the answer as the next user turn in a new query.

**설명**

명확화 질문은 애플리케이션이 파싱해야 하는 최종 메시지 속 서술문 형태로 도착하지 않는다. 이는 can_use_tool 콜백을 통해 실행을 일시 정지시키는 구조화된 AskUserQuestion 도구 호출 형태로 도착하므로, 메시지 파싱이나 새 쿼리는 필요하지 않다.

**D.** Expose a custom MCP tool for questions, since the SDK's built-in tools cannot request input from the user mid-run.

**설명**

별도의 질문 도구를 만드는 것은 플랫폼이 이미 제공하는 기능을 다시 만드는 것이다. AskUserQuestion은 요구 사항을 수집하고 모호함을 명확히 하기 위해 정확히 설계된 내장 도구이며, SDK는 이를 can_use_tool 콜백을 통해 애플리케이션으로 전달한다.

### 전반적인 설명

인터뷰 패턴은 구현에 앞서 Claude가 개발자에게 질문하도록 하여, 원샷 프롬프트로는 놓칠 수 있는 예외 상황, 트레이드오프, 제약 조건을 드러내게 한다. Claude Code와 Agent SDK에서 이 패턴을 뒷받침하는 메커니즘은 내장 AskUserQuestion 도구이며, Claude는 요구 사항이 모호할 때 이를 사용해 다중 선택형 명확화 질문을 제기한다.

Agent SDK 애플리케이션에는 Claude가 출력할 터미널이 없으므로, SDK는 콜백 계약을 중심으로 설계되어 있다. Claude는 정확히 두 가지 공식 문서화된 상황, 즉 도구 권한 요청과 AskUserQuestion을 통한 명확화 질문에서 사용자 입력을 요청하며, 둘 다 canUseTool/can_use_tool 콜백을 트리거한다. 실행은 애플리케이션이 응답을 반환할 때까지 일시 정지된다. 이 설계는 SDK를 헤드리스하고 임베드 가능하게 유지해준다. 애플리케이션은 그 질문을 웹 폼, 채팅 위젯, 혹은 CLI 프롬프트 중 어디에 표시할지 스스로 결정한 뒤, 답을 되돌려주어 에이전트가 엔지니어의 입력을 반영해 계속 진행할 수 있게 한다.

다른 접근 방식들은 이 계약을 잘못 이해하고 있다. 최종 메시지에서 텍스트 블록을 파싱하는 방식은 에이전트가 턴을 끝내고 질문을 서술문으로 돌려준다고 가정하지만, 실제로는 실행이 턴 중간에 중단되어 콜백의 응답을 기다리고 있는 상태다. PreToolUse 훅은 도구 호출이 실행되기 전에 이를 검증하거나 수정하거나 차단하는 메커니즘일 뿐, 명확화 질문에 답하기 위한 공식 문서화된 채널이 아니다. 그리고 별도의 MCP 질문 도구는 플랫폼이 네이티브로 제공하는 기능을 중복시켜, 얻는 것 없이 유지 관리 부담만 늘린다.

## 질문 6

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : During an interactive Claude Code session, an engineer used plan mode to investigate a legacy scheduler, and Claude produced a sound implementation plan. The engineer typed "exit plan mode and implement this" in chat, but Claude's edit attempts remain blocked. What should the engineer do?

**A(정답).** Switch out of plan mode with Shift+Tab, then have Claude execute the approved plan.

**설명**

계획 모드는 Claude Code 자체가 강제하는 권한 모드이므로, 대화형 세션에서 Shift+Tab 같은 컨트롤을 사용해 오직 사용자만 이를 변경할 수 있다. 엔지니어가 계획 모드를 벗어나면 Claude는 이미 만들어 둔 계획을 실행할 수 있으며, 조사 과정에서 쌓인 모든 컨텍스트도 그대로 유지된다.

**B.** Repeat the instruction with stronger, more explicit wording so Claude changes the mode itself.

**설명**

채팅에서 Claude에게 권한 모드를 바꿔달라고 요청하는 것은 요청을 어떻게 표현하든 모드를 바꾸지 못한다. 모드 강제는 하니스(harness)에 있으며 모델의 통제 밖에 있는데, 이는 정확히 지침이 이를 무시하고 넘어가지 못하도록 하기 위한 것이다.

**C.** Add a CLAUDE.md rule stating that file edits are permitted once Claude has presented a plan.

**설명**

CLAUDE.md은 모델이 읽는 안내일 뿐 강제되는 설정이 아니므로, 현재 활성화된 권한 모드가 막고 있는 쓰기 권한을 부여할 수 없다. 계획 모드의 읽기 전용 제한은 프로젝트 지침이 무엇을 말하든 관계없이 Claude Code에 의해 적용된다.

**D.** Start a fresh session and paste the plan in, since a session's permission mode is fixed at launch.

**설명**

권한 모드는 실행 시점에 고정되지 않는다. 대화형 세션에서는 사용자가 Shift+Tab으로 모드를 순환시킬 수 있다. 또한 새 세션을 시작하면 계획 단계에서 쌓인 조사 컨텍스트가 사라지는데, 이는 바로 계획-후-실행 작업 흐름이 보존하고자 하는 것이다.

### 전반적인 설명

계획-후-실행 작업 흐름은 계획 모드가 실제로 무엇인지 이해하는 데 달려 있다. 이는 모델이 따르는 행동 지침이 아니라 Claude Code 하니스가 강제하는 권한 모드다. 계획 모드에서 Claude는 읽기 전용 조사(Read, Grep, Glob)로 제한되며 파일을 편집할 수 없고, 이 제한은 대화 내용이 무엇을 말하든 관계없이 도구 계층에서 적용된다. 이러한 분리는 의도적이다. 채팅이나 CLAUDE.md에 담긴 지침은 확률적 안내인 반면, 권한 모드는 결정론적으로 강제되므로, Claude 자신을 포함한 누구도 말로 모드를 바꿀 수 없다.

그 결과, 조사에서 구현으로의 전환은 사용자의 행동이다. 대화형 Claude Code 세션에서 엔지니어는 Shift+Tab으로 계획 모드를 벗어난다(세션을 처음부터 claude --permission-mode plan으로 계획 모드에서 시작할 수도 있고, /plan으로 하나의 프롬프트에만 계획을 적용할 수도 있다). 그런 다음 Claude에게 만들어진 계획을 실행하도록 지시한다. 같은 세션이 계속되므로, 탐색 중에 수집된 모든 컨텍스트가 구현 단계로 그대로 이어지며, 이것이 두 모드를 결합하는 핵심 가치다.

실패한 대안들은 각각 강제 경계를 잘못 이해하고 있다. 채팅 요청을 다르게 표현하는 것은 모델이 자신의 권한 모드에 대한 권한을 갖고 있지 않기 때문에 통하지 않는다. CLAUDE.md 규칙은 메모리 파일이 설정이 아니라 안내이므로 하니스가 막고 있는 접근 권한을 부여할 수 없다. 새 세션을 시작하는 것은 결국에는 통하겠지만, 모드가 세션 중간에 바뀔 수 있다는 잘못된 전제에 근거하며 축적된 조사 컨텍스트를 불필요하게 버리는 결과를 낳는다. 공식 문서화된 모드 컨트롤은 권한 모드(Permission modes)를 참고하라.

## 질문 7

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : An engineer reviewing agent-generated boilerplate finds five issues: three are interdependent (a shared interface change plus two call sites that must change with it) and two are unrelated formatting problems. How should the feedback be delivered?

**A.** Start a fresh session for each issue so no fix is influenced by context accumulated while handling the others.

**설명**

이슈마다 새 세션을 시작하는 방식은 서로 의존하는 수정 사항들이 필요로 하는 공유 컨텍스트를 버리고, 코드베이스를 반복해서 다시 탐색하도록 강제한다. 여기서 관련된 수정 작업 중 쌓인 컨텍스트는 오염이 아니라 자산이다.

**B.** Send one issue per message in strict priority order so each fix stays small, isolated, and easy to verify before moving on.

**설명**

엄격하게 순차적인 피드백은 독립적인 이슈에는 잘 작동하지만 상호작용하는 이슈에는 무너진다. 의존하는 호출 지점 수정 사항을 보지 않고 인터페이스 변경을 고치면, 관련 이슈가 나중에 도착했을 때 다시 작업해야 하는 해법을 만들게 된다.

**C.** Combine all five issues into a single message so the agent resolves everything in one pass and conserves turns.

**설명**

독립적인 이슈들을 상호 의존적인 변경 집합과 함께 묶으면 주의력이 분산되고, 어떤 수정이 어떤 변경을 일으켰는지 확인하기가 더 어려워진다. 일괄 처리는 턴 수를 아끼고 싶다는 이유가 아니라 수정 사항들 사이의 상호작용이 있을 때 정당화된다.

**D(정답).** Describe the three interdependent fixes together in one detailed message, then address the unrelated issues in later turns.

**설명**

이 방식은 반복적 개선을 위한 결정 규칙에 부합한다. 상호작용하는 수정 사항들은 에이전트가 하나의 일관된 변경을 설계할 수 있도록 함께 제시해야 하고, 독립적인 이슈들은 각 반복을 집중적이고 확인하기 쉽게 유지하도록 순차적으로 처리해야 한다.

### 전반적인 설명

에이전트와의 반복적 개선에는 단순한 구분선이 있다. 상호 의존적인 이슈는 하나의 상세한 메시지에 담고, 독립적인 이슈는 순차적으로 전달한다. 인터페이스 변경이 호출 지점에서 조율된 편집을 강제하는 경우처럼 수정 사항들이 서로 상호작용할 때, 에이전트는 하나의 일관된 설계를 만들어내기 위해 전체 제약 집합을 한 번에 봐야 한다. 하나씩 전달하면, 각각의 부분적 수정은 다음 메시지가 추가할 제약을 모른 채 이루어지므로, 앞서 만든 수정이 나중에 다시 작업되거나 조각들이 서로 일치하지 않게 된다.

독립적인 이슈들은 이 트레이드오프를 뒤집는다. 서식 수정은 다른 어떤 것에도 의존하지 않으므로, 이를 다중 부분 변경과 같은 메시지에 담으면 관련 없는 관심사에 주의가 분산되고 검증이 흐려질 뿐이다. 이런 이슈들을 별도의 턴에서 처리하면 각 반복이 작고, 검토 가능하며, 다음으로 넘어가기 전에 확인하기 쉬운 상태로 유지된다.

오답들은 각각 규칙의 절반만 과도하게 적용한 것이다. 모든 것을 일괄 처리하는 방식은 실제 비용이 일관성 없는 변경에서 오는 재작업과 검증 가능성 상실임에도 턴 수를 최소화해야 할 비용으로 취급한다. 엄격하게 순차적으로 전달하는 방식은 두 가지 서식 수정에는 맞지만 상호작용하는 세 가지 수정에는 맞지 않다. 이슈마다 새 세션을 여는 방식은 유용한 공유 컨텍스트를 오염으로 잘못 진단한다. 세션 분리는 세션이 자신의 출력을 스스로 검토할 때 가치가 있는 것이지, 관련된 수정 사항들이 코드베이스에 대한 공통된 이해를 필요로 할 때는 그렇지 않다. 에이전트 방식 작업 흐름에서 피드백을 구성하고 반복하는 방법에 대해서는 Claude Code 모범 사례(Claude Code best practices)를 참고하라.

## 질문 8

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : The agent renames legacy database columns to your new API field scheme. Its prompt contains a prose casing rule plus several correctly formatted sample field names, yet acronyms and mixed-case legacy names still convert inconsistently. Which prompt change is most effective?

**A.** Instruct the agent to pause and ask a clarifying question whenever it encounters a name it considers ambiguous.

**설명**

오답. 인터뷰 패턴은 아직 알려지지 않은 설계상의 고려 사항을 드러내는 데 유용하지만, 여기서 원하는 매핑은 팀이 이미 완전히 알고 있는 것이다. 결정론적인 변환 작업을 일련의 명확화 왕복 질문으로 바꾸는 것은 그 규칙을 가르치지 못한 채 지연 시간만 늘린다.

**B(정답).** Replace the output-only samples with two or three input/output pairs covering the acronym and mixed-case names.

**설명**

정답. 출력만 보여주는 샘플은 좋은 결과가 어떤 모습인지는 보여주지만, 까다로운 입력이 어떻게 그 결과로 매핑되는지는 보여주지 않는다. 정확히 모호한 형태를 포함하는 입력/출력 쌍 예시는 변환 작업 자체를 보여주며, 이는 모델이 규칙을 일관되게 적용하기 위해 필요한 것이다.

**C.** Extend the prose rule with an exhaustive written enumeration of every casing edge case in the legacy schema.

**설명**

오답. 이 시나리오는 규칙에 대한 서술형 설명이 이미 일관되지 않게 해석되고 있음을 보여준다. 서술문을 더 길게 만드는 것은 모델이 해석해야 할 텍스트만 늘릴 뿐 모호함을 제거하지는 못한다. 구체적인 시연은 확장된 자연어 규칙보다 변환 작업을 더 확실하게 전달한다.

**D.** Add IMPORTANT emphasis to the casing rule and instruct the agent to apply the naming convention strictly to every column.

**설명**

오답. 강조는 다른 지침에 비해 그 지침의 우선순위를 높이지만, 서술문이 애초에 명확히 하지 못한 입력에 대해 그 지침이 무엇을 의미하는지는 해결해주지 못한다. 이 실패는 규칙이 무시되고 있어서가 아니라, 규칙이 불충분하게 명시되어 있어서 발생한다.

### 전반적인 설명

변환 작업이 서술문으로 기술되어 있고 결과가 일관되지 않게 나온다면, 근본적인 문제는 보통 자연어가 매핑을 충분히 명시하지 못한다는 것이다. 모델은 설명이 명시적으로 다루지 않은 입력에 규칙을 어떻게 적용할지 추측해야 하고, 그때마다 다르게 추측한다. 구체적인 입력/출력 예시는 변환 작업을 직접 보여주기 때문에 이 격차를 좁혀준다. 예시가 의도적으로 선택된다면 보통 두세 개면 충분하다. 가장 가치 있는 예시는 이름 변경 작업에서 약어나 대소문자가 섞인 식별자처럼 현재 실패하고 있는 사례를 정확히 다루는 예시다.

이 문제를 가르는 구분은 원하는 출력의 샘플과 매핑을 쌍으로 시연하는 예시 사이의 차이다. 올바르게 형식이 맞춰진 필드 이름 목록은 모델에게 목적지가 어떤 모습인지는 알려주지만, 특정 레거시 이름이 어떻게 그곳에 도달하는지는 전혀 알려주지 않는다. Input: HTTP_url → Output: httpUrl과 같은 쌍은 그 결정 자체를 인코딩한다. 이것이 퓨샷 예시 쌍이 더 긴 서술문(해석해야 할 텍스트는 늘지만 모호함은 그대로임)과 IMPORTANT 같은 강조 표시(지침의 우선순위는 높이지만 모호함을 해소하지는 못함) 둘 다보다 더 나은 이유다. Claude가 명확화 질문을 하는 인터뷰 패턴은 다른 문제에 속한다. 이는 개발자가 아직 결정하지 않은 설계상의 고려 사항을 드러내는 것이며, 팀이 이미 알고 있는 매핑을 실행하는 것이 아니다.

전형적인 입력뿐 아니라 예외 상황까지 다루는 예시를 선택하는 방법에 대해서는 예시 사용하기(멀티샷 프롬프팅)(Use examples (multishot prompting))와 더 넓은 범위의 프롬프트 엔지니어링 개요(Prompt engineering overview)를 참고하라.

## 질문 9

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : A teammate sets context: fork on a skill whose entire body is a list of API-convention guidelines, hoping to save main-session tokens. Invocations now complete but return nothing useful. What is the correct fix?

**A.** Expand allowed-tools so the forked subagent can read the codebase and gather the context it lacks.

**설명**

여기서 제약 요인은 도구 접근 권한이 아니다. 서브에이전트에게는 어떤 도구로든 무엇을 달성해야 하는지 알려주는 지침이 아예 없다. allowed-tools를 넓힌다고 해서 수동적인 규칙 텍스트가 실행 가능한 프롬프트로 바뀌지는 않는다.

**B(정답).** Remove context: fork so the guideline content loads inline; forking suits skills that define an explicit task.

**설명**

포크된 스킬에서는 SKILL.md의 내용이 서브에이전트를 이끄는 프롬프트가 된다. 수동적인 가이드라인만 담긴 본문은 서브에이전트에게 실행 가능한 작업을 전혀 주지 못하므로, 의미 있는 출력을 만들어내지 못한다. 가이드라인 콘텐츠는 인라인으로 실행되어야 Claude가 이를 대화와 함께 적용할 수 있다.

**C.** Set the agent frontmatter field to Explore so the fork runs with a leaner built-in subagent configuration.

**설명**

agent 필드는 포크를 실행할 서브에이전트 구성을 선택할 뿐, 스킬 본문이 서브에이전트에게 요청하는 작업 내용을 바꾸지는 않는다. 가이드라인만 있는 본문은 어떤 에이전트 유형에 대해서도 여전히 작업을 담고 있지 않으므로, 출력은 그대로 비어 있게 된다.

**D.** Add an argument-hint entry so invocations prompt for the missing parameters before the fork starts.

**설명**

argument-hint는 스킬이 인자 없이 호출될 때 개발자에게 인자를 입력하도록 요청하는 기능으로, 매개변수화된 작업 흐름에 도움이 된다. 여기서의 실패 원인은 인자가 빠진 것이 아니라, 스킬 본문 자체에 포크된 서브에이전트가 수행할 작업이 전혀 담겨 있지 않다는 것이다.

### 전반적인 설명

context: fork를 이해하는 사고 모델은 이것이 스킬 본문의 성격 자체를 바꾼다는 것이다. 일반적인 스킬은 콘텐츠를 인라인으로 로드하며, Claude는 이를 실제 대화와 함께 읽고 안내로 적용한다. 반면 포크된 스킬은 전체 프롬프트가 SKILL.md 콘텐츠인 서브에이전트를 새로 띄우며, 이 서브에이전트는 메인 대화 이력에 접근할 수 없다. 이 격리가 바로 이 기능의 핵심이다. 방대한 중간 작업은 서브에이전트 안에 머물고, 그 결과만 메인 세션으로 돌아온다.

그 대신 트레이드오프는 본문이 명시적인 작업이어야 한다는 것이다. Anthropic의 공식 문서는 "이 API 컨벤션을 사용하라"처럼 수동적인 안내만 담긴 스킬을 포크하면 서브에이전트에게 실행 가능한 것이 아무것도 주어지지 않아, 포크가 의미 있는 출력을 내지 못한다고 경고한다. 수동적인 컨벤션은 인라인으로 로드되는 포크되지 않은 스킬이나 CLAUDE.md 같은 프로젝트 메모리에 두어야 하며, 그곳에서는 컨텍스트 안에서 이미 진행 중인 작업을 형성하는 역할을 한다. 포크는 분석이나 생성 작업처럼 자체 완결적인 작업 흐름을 위한 것이다.

오답들은 각각 실제로 존재하는 프런트매터 메커니즘을 조정하지만, 이 실패를 해결하지는 못한다. 다른 에이전트 유형을 선택하는 것은 실행되는 서브에이전트의 구성을 바꿀 뿐, 그 작업이 비어 있다는 사실은 바꾸지 못한다. argument-hint는 매개변수가 빠진 맨 호출을 해결하고, allowed-tools는 스킬이 호출할 수 있는 것을 제한한다. 둘 다 안내성 서술문을 실행 가능한 프롬프트로 바꿔주지는 못한다. 포크된 스킬의 실행 모델에 대해서는 Claude Code의 에이전트 스킬(Agent Skills in Claude Code)을 참고하라.
