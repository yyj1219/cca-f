SCENARIO: You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

QUESTION: Production sessions that run 30+ turns across several customer issues show a distinct failure pattern: early in the session the agent quotes exact refund amounts and return-eligibility fields from lookup_order results, but by the later turns it answers with statements like "standard policy typically allows returns within 30 days" even when the retrieved order data said otherwise. Which TWO changes counteract this degradation? (Select TWO.)

**선택지**:
1. Record retrieved order and refund details in a structured case-facts block that is injected into every prompt outside the conversation history => 정답
2. Add a system prompt directive telling the agent to base every answer on previously retrieved data rather than general support knowledge
3. Have the agent re-invoke get_customer and lookup_order at the start of each turn so the specific details stay recent in context
4. Filter each backend tool result down to the fields needed for the active issue before appending it to the conversation => 정답

**설명**:
- 정보를 대화 기록(Message History)에만 남겨두면 턴이 지남에 따라 뒤로 밀려나거나 압축(Compaction) 과정에서 유실됩니다. 이를 독립된 구조화된 블록(State/Case-Facts Block)으로 만들어 매 턴 프롬프트 외부(시스템 영역 등)에 지속적으로 주입(Inject)해 주면, 턴 수가 아무리 늘어나도 핵심 주문 정보를 100% 정확하게 유지할 수 있습니다.
- 백엔드 도구(lookup_order 등)에서 반환되는 원본 JSON 데이터 전체를 대화 기록에 그대로 넣으면 컨텍스트 창이 쓸데없는 정보로 채워집니다. 대화에 추가하기 전에 현재 이슈에 꼭 필요한 핵심 필드로만 필터링(Filter down)하여 저장하면 컨텍스트 오염을 막고 모델이 중요한 정보에 집중할 수 있도록 돕습니다.

**문제 구분 포인트, 어려운 표현**:
- return-eligibility: 반품 가능 여부
- structured case-facts block: 구조화된 대화 사실(case-facts) 블록
