# 사전 학습 노트: 컨텍스트 관리와 신뢰성 (Context Management & Reliability)

이 문서는 이 주제를 처음 접하는 학습자를 위한 개념 정리입니다. LLM(대형 언어 모델) 기반 에이전트 시스템을 설계할 때 반복해서 등장하는 핵심 개념들을 밑바닥부터 설명합니다.

---

## 1. LLM API의 기본 동작 원리

### 1.1 LLM이란 무엇인가

LLM(Large Language Model, 대형 언어 모델)은 텍스트를 입력받아 그 다음에 올 텍스트를 생성하는 모델입니다. Claude, GPT 같은 모델이 여기에 해당합니다. 우리가 "AI가 대화한다"고 느끼는 것은, 실제로는 **매번 대화 전체를 다시 입력해서 다음 문장을 생성**하는 과정의 반복입니다.

### 1.2 무상태성 (Statelessness) — 가장 중요한 기본 개념

**무상태(Stateless)** 란 서버가 이전 요청에 대한 정보를 전혀 기억하지 않는다는 뜻입니다.

LLM API는 무상태입니다. 즉:

- 모델은 **서버 쪽에 대화 내역을 저장하지 않습니다.**
- 매 API 호출마다 클라이언트(개발자의 애플리케이션)가 **필요한 모든 맥락을 직접 다시 보내야** 합니다.
- 요청에 포함되지 않은 정보는 모델 입장에서 **존재하지 않는 정보**입니다.

```python
# 잘못된 이해: "모델이 알아서 기억하겠지"
client.messages.create(model="...", messages=[{"role": "user", "content": "아까 말한 그 좌석으로 예약해줘"}])
# → 모델은 "아까"가 무엇인지 전혀 모름. 그 대화가 요청에 없기 때문.

# 올바른 방식: 대화 전체를 매번 다시 보냄
messages = [
    {"role": "user", "content": "비즈니스석으로 알아봐줘"},
    {"role": "assistant", "content": "비즈니스석 조회 결과입니다..."},
    # ... 중간 대화들 ...
    {"role": "user", "content": "아까 말한 그 좌석으로 예약해줘"},
]
client.messages.create(model="...", messages=messages)
```

**핵심 결론:** "모델에 내장된 대화 메모리"라는 것은 존재하지 않습니다. 대화의 연속성은 **애플리케이션(개발자)이 책임지고 관리**하는 것입니다. 사용자에게 "매번 선호도를 다시 말해 달라"고 요구하는 것도 해결책이 아닙니다 — 그것은 시스템의 책임을 사용자에게 떠넘기는 잘못된 설계입니다.

### 1.3 messages 배열

API 요청의 `messages` 파라미터는 대화 기록을 담는 배열입니다. 각 원소는 `role`(`user` 또는 `assistant`)과 `content`를 가집니다. 이 배열이 곧 모델이 볼 수 있는 세계의 전부입니다.

## 2. 컨텍스트 윈도우와 그 관리

### 2.1 토큰(Token)과 컨텍스트 윈도우(Context Window)

- **토큰**: 모델이 텍스트를 처리하는 최소 단위. 대략 영어 단어 하나가 1~2토큰, 한글은 글자당 1토큰 이상입니다.
- **컨텍스트 윈도우**: 한 번의 요청에서 모델이 처리할 수 있는 **최대 토큰 수**. 입력(대화 기록 + 시스템 프롬프트 + 도구 결과)과 출력이 모두 이 한도를 공유합니다.

컨텍스트 윈도우는 **고정된 크기**입니다. 대화 도중에 저절로 줄어들거나 늘어나지 않습니다.

### 2.2 컨텍스트 예산 (Context Budget)

시스템 설계 시 각 구성 요소가 쓸 수 있는 토큰 양을 미리 배분해 둔 것을 컨텍스트 예산이라고 부릅니다. 예: 요약 작성 에이전트에게 총 20만 토큰이 주어졌다면, 여기에 6개 서브에이전트의 결과가 모두 들어가야 합니다.

예산을 초과하면 다음 중 하나가 일어납니다:
- **잘림(Truncation)**: 초과분이 통째로 버려짐. 6개 중 뒤 2개 결과가 완전히 사라지는 식.
- **오류**: 요청 자체가 거부됨.

### 2.3 최대 출력 토큰(Max Output Tokens)과의 혼동 주의

`max_tokens`(최대 출력 토큰)은 **모델이 한 번에 생성할 답변의 길이 상한**입니다. 이것을 늘려도:
- 입력으로 들어갈 수 있는 과거 대화의 양은 늘어나지 않습니다.
- 이미 컨텍스트에서 밀려난 정보를 되살려 주지도 않습니다.

### 2.4 더 큰 모델로 바꾸면 기억이 돌아오는가

아닙니다. 모델 파라미터 수가 늘어난다고 해서 **입력에 없는 정보**를 알 수는 없습니다. 컨텍스트에서 이미 잘려 나간 사실은 어떤 모델로도 복원되지 않습니다.

## 3. 대화 맥락을 줄이는 기법들과 그 위험

컨텍스트가 한도에 가까워질 때 흔히 쓰는 기법들입니다. 모두 **정보 손실**이라는 공통 위험을 가집니다.

### 3.1 순환 요약 (Rolling Summary)

이전 대화 전체를 짧은 요약문 한두 문장으로 압축해 두고, 매 호출에는 "요약 + 최신 메시지"만 보내는 방식입니다.

- **장점**: 토큰이 줄어드니 지연 시간(Latency)과 비용이 감소.
- **위험**: 요약은 본질적으로 **손실 압축**입니다. "좌석 등급은 비즈니스" 같은 구체적 디테일이 요약 과정에서 사라지면, 나중에 사용자가 그것을 참조해도 모델은 답할 수 없습니다.
- **요약을 1문장에서 3문장으로 늘리는 것은 근본 해결책이 아닙니다.** 손실 압축이라는 성질 자체는 그대로이므로, 언제든 다른 디테일이 누락될 수 있습니다. 근본 원인은 "무상태 API에 필요한 맥락을 충분히 제공하지 않았다"는 점입니다.

### 3.2 서버 측 컨텍스트 압축 (Server-side Context Compaction)

Claude API가 제공하는 기능으로, 대화가 길어졌을 때 서버가 자동으로 이전 메시지들을 요약·압축해 컨텍스트 안에 유지시켜 줍니다.

- 관련 설정: `context_management` 파라미터
- 베타 헤더 예시: `compact-2026-01-12`

**동작 범위**: 압축은 도구 실행 결과(tool results)뿐 아니라 **대화 내역 전체(모델이 생성한 텍스트 포함)** 를 대상으로 합니다.

**전형적인 실패 양상**: 여러 차례 압축을 거치면 "발견한 사실(findings)"은 살아남지만 그 사실을 뒷받침하던 **인용 정보(citations, 출처 URL·문서명)** 가 사라집니다. 요약을 수행하는 모델이 출처 정보를 "부연 설명"으로 판단해 버리기 때문입니다.

**대응 원칙**: 압축 규칙이나 요약 프롬프트에 **"각 주장과 그 출처의 매핑(claim-source mapping)을 반드시 보존하라"** 는 지시를 명시적으로 넣어야 합니다. 명시하지 않으면 보존되지 않습니다.

참고로 존재하지 않는 것들: 대화 차례 수에 따라 인용만 따로 지워지는 별도 임시 캐시, 대화 도중 컨텍스트 윈도우가 저절로 줄어드는 동작 — 이런 메커니즘은 없습니다.

### 3.3 스크래치패드 (Scratchpad) — 외부 지속 메모리

**스크래치패드**란 에이전트가 작업 도중 발견한 사실을 기록해 두는 **외부 파일**입니다(`notes.md` 같은 평범한 파일). 컨텍스트 윈도우 바깥에 존재하므로 압축이나 잘림의 영향을 받지 않습니다.

**왜 필요한가 — 장기 세션의 망각 문제**

수 시간짜리 코딩 세션의 전형적 사고:

1. 초반에 에이전트가 `OrderService`가 커스텀 `TransactionalBase`를 상속하며 독특한 재시도 로직을 갖는다는 것을 정확히 파악.
2. 몇 시간 뒤 컨텍스트가 압축/잘림.
3. 같은 질문을 하면 에이전트가 "일반적으로 표준 base controller를 상속하고 기본 오류 처리를 사용합니다"라는 **일반론적 환각(Hallucination)** 을 답변.

**해결 패턴**: 구체적 발견(정확한 클래스명, 상속 구조, 특이 로직)을 발견 즉시 스크래치패드에 기록하고, **답변하기 전에 그 파일을 먼저 읽는** 규칙을 세웁니다.

```markdown
# notes.md
## OrderService
- 위치: services/order/OrderService.java
- 상속: TransactionalBase (커스텀, 표준 컨트롤러 아님)
- 특이사항: 지수 백오프 기반 커스텀 재시도 메커니즘 보유
```

비효율적인 대안들: 질문마다 전체 저장소를 처음부터 다시 읽기(토큰·시간 낭비), max_tokens 늘리기(무관), 더 큰 모델로 전환(무관).

### 3.4 동시 실행 시 스크래치패드 컨벤션 — 경쟁 조건(Race Condition)

여러 서브에이전트가 **동시에(concurrently)** 실행되며 각자 결과를 기록할 때, 파일 사용 규칙을 잘못 정하면 데이터가 손상됩니다.

- **경쟁 조건(Race Condition)**: 여러 실행 주체가 동시에 같은 자원(파일)에 접근할 때 순서에 따라 결과가 달라지고 데이터가 깨지는 현상.
- **덮어쓰기(Overwrite) 버그**: 고정된 같은 파일명에 각자 쓰면, 나중에 쓴 에이전트가 앞선 에이전트의 기록을 지워 버립니다.

**안전한 컨벤션 — 격리(Isolation)**:

```
scratch/
  module-auth.md      ← 서브에이전트 1
  module-billing.md   ← 서브에이전트 2
  module-search.md    ← 서브에이전트 3
```

각 서브에이전트에 **고유한 파일명**(예: 담당 모듈당 하나)을 부여하고, 코디네이터는 **모든 서브에이전트가 종료된 뒤에** 파일들을 한꺼번에 집계(Aggregate)합니다. 이렇게 하면 쓰기 충돌 자체가 발생하지 않습니다.

스크래치패드를 아예 쓰지 않고 최종 응답 텍스트로만 보고하는 방식은, 긴 조사 과정에서 중간 결과를 보존할 곳이 없어 컨텍스트 한계로 정보를 잃을 위험이 있습니다.

## 4. 멀티 에이전트 아키텍처

### 4.1 구성 요소

- **오케스트레이터(Orchestrator) / 코디네이터(Coordinator)**: 작업을 쪼개 하위 작업자에게 배분하고, 결과를 취합·종합(Synthesis)하는 상위 에이전트.
- **서브에이전트(Subagent)**: 배정받은 좁은 범위의 작업(문서 읽기, 검색, 분석)을 수행하고 결과를 반환하는 하위 에이전트.
- **합성/종합 에이전트(Synthesis Agent)**: 여러 서브에이전트 결과를 하나의 최종 산출물(보고서 등)로 합치는 역할.

각 서브에이전트는 **자기 자신의 컨텍스트 윈도우**를 가집니다. 그래서 병렬 조사에 유리하지만, 서로의 컨텍스트를 볼 수 없으므로 **주고받는 데이터의 형식이 매우 중요**해집니다.

### 4.2 출력 계약 (Output Contract)

**출력 계약**이란 서브에이전트가 반환해야 할 데이터의 **형식과 필수 항목을 사전에 규정한 약속**입니다. 인터페이스, 출력 스키마(Output Schema), 데이터 계약(Data Contract)이라고도 부릅니다.

**왜 필요한가**: 자유 형식 문단(free-form paragraph)으로 결과를 주고받으면 상위 에이전트가 프로그램적으로 파싱·비교·검증할 수 없습니다. 계약을 정하고 구조화된 형식(예: JSON)으로 반환하게 하면 코디네이터가 날짜를 비교하고, 출처를 추적하고, 충돌을 판별할 수 있습니다.

멀티 에이전트 시스템의 대부분의 문제는 "모델을 바꿔서" 가 아니라 **"출력 계약을 고쳐서"** 해결됩니다.

## 5. 출처 추적성 (Provenance)

### 5.1 Provenance란

**Provenance(출처 추적성)** 는 "이 정보가 어디서 왔는가"를 끝까지 따라갈 수 있는 성질입니다. 원래 미술품의 소장 이력을 뜻하는 단어로, 데이터 세계에서는 각 사실의 근거 문서를 추적하는 능력을 의미합니다.

Provenance가 없으면:
- 최종 보고서의 주장을 검증할 수 없습니다.
- 환각(Hallucination, 모델이 사실이 아닌 것을 지어내는 현상)을 걸러낼 수 없습니다.
- 상충하는 정보 중 무엇이 옳은지 판단할 수 없습니다.

### 5.2 주장-출처 매핑 (Claim-Source Mapping)

Provenance를 지키는 구체적 방법은 **모든 주장(Claim) 하나하나에 출처를 1:1로 짝지어(pair)** 두는 것입니다. 여기에 **뒷받침 발췌문(Supporting Excerpt)** 까지 함께 두면 검증이 쉬워집니다.

```json
{
  "claims": [
    {
      "claim": "경쟁사 A의 프로 요금제는 월 49달러다",
      "source": "https://competitor-a.com/pricing",
      "document_name": "Competitor A Pricing Page",
      "excerpt": "Pro plan — $49/month, billed annually",
      "retrieval_date": "2026-09-01",
      "publication_date": "2026-08-15"
    }
  ]
}
```

**문단 끝 참고문헌 목록(Bibliography)만으로는 부족합니다.** "이 문단을 쓰면서 이 문서 5개를 봤다"는 정보만으로는 문단 속 특정 주장 하나가 그 5개 중 어느 것에서 나왔는지 알 수 없습니다. 1:1 매핑이어야 추적이 성립합니다.

### 5.3 메타데이터 (Metadata)

메타데이터는 "데이터에 대한 데이터"입니다. 각 사실과 함께 반드시 실어야 할 대표 항목:

| 항목 | 의미 | 왜 필요한가 |
|---|---|---|
| source location / URL | 어디서 얻었는가 | 검증과 추적 |
| document name | 문서 이름 | 사람이 식별 |
| retrieval date | 언제 가져왔는가 | 데이터 신선도(Recency) 판단 |
| publication date | 원 자료 발행 시점 | 시점 차이 판별 |
| excerpt | 근거 원문 | 환각 검증 |

이 메타데이터가 있어야 코디네이터가 **프로그램적으로** 날짜를 비교해 최신 값을 고를 수 있습니다. 긴 서술문으로 추론 과정을 아무리 자세히 써도, 비구조화 텍스트에서는 날짜를 안정적으로 파싱·정렬할 수 없습니다.

### 5.4 허위 모순 (False Contradiction)

**허위 모순**이란 실제로는 모순이 아닌데 모순으로 오인되는 상황입니다.

예: 서브에이전트 A는 실업률 5.1%, 서브에이전트 B는 6.3%를 보고. 코디네이터는 충돌로 판단하지만, 사실은 **14개월 간격으로 발행된 서로 다른 시점의 보고서**에서 나온 값이었습니다. 시간에 따라 값이 변한 것이지 모순이 아닙니다.

**예방책**: 모든 수치에 **발행일 또는 데이터 수집 날짜**를 메타데이터로 붙이도록 출력 스키마를 강제합니다.

하지 말아야 할 대응들:
- 수치를 대략적 범위로 바꾸기 → 정밀도만 잃고 시점 문제는 그대로.
- 6개월 지난 데이터를 무조건 폐기 → 시계열·추세 분석 자체가 불가능해지는 과잉 조치.
- 서브에이전트가 임의로 12개월 이동 평균으로 변환 → 원본 시점별 값이 사라지고 데이터가 왜곡됨.

### 5.5 중복 주장 병합 (Merging Near-Duplicates)

여러 서브에이전트가 같은 주제를 다른 각도에서 조사하면, **표현만 조금 다른 거의 동일한 주장**이 여러 개 생기고 각각의 출처는 서로 다릅니다.

**올바른 병합**: 중복 주장을 **하나의 엔트리로 통합(Consolidate)** 하되, 이를 뒷받침하는 **출처 인용 전체를 합집합으로 보존**합니다.

```json
{
  "claim": "해당 지역 실업률은 2026년 상반기에 하락 추세였다",
  "sources": [
    {"document": "BLS Report 2026-03", "excerpt": "...", "date": "2026-03-01"},
    {"document": "Regional Economic Review", "excerpt": "...", "date": "2026-05-20"},
    {"document": "State Labor Bulletin", "excerpt": "...", "date": "2026-06-10"}
  ]
}
```

여러 독립 출처가 같은 주장을 뒷받침한다는 사실 자체가 **신뢰도를 높이는 정보**입니다. 그러므로:
- 인용 없는 새 문장으로 다시 쓰기 → provenance 전멸.
- 가장 먼저 도착한 것만 남기고 나머지 폐기 → 다른 에이전트가 찾은 출처를 잃음.
- "이제 충분히 입증됐으니" 출처를 지우기 → 검증 불가능해짐. 치명적 오류.

### 5.6 컨텍스트 예산 안에서 정보 밀도 높이기

서브에이전트가 결론에 이르기까지의 **탐색적 추론(Exploratory Reasoning)** 을 여러 문단씩 그대로 반환하면, 상위 요약 에이전트의 컨텍스트 예산이 금방 소진되어 뒤쪽 서브에이전트 결과가 통째로 잘립니다.

**해결책**: 출력 계약을 바꿔 **탐색적 서술을 버리고(drop) 밀도 높은 핵심만** 반환하게 합니다.
- 핵심 사실(Key Facts)
- 뒷받침 인용(Supporting Citations)
- 연관성 점수(Relevance Score)

상위 취합 에이전트에게 필요한 것은 "어떻게 생각했는가"가 아니라 "무엇을 알아냈고 근거가 무엇인가"입니다.

효과 없는 대안들: 뒤 2개를 버리고 "분석 완료"라고 통보(정보 누락), 읽는 순서를 뒤집기(잘리는 대상만 바뀜), 에이전트 수를 늘리되 여전히 긴 서술 유지(총 토큰량이 오히려 증가).

## 6. 오류 처리와 부분 실패

### 6.1 구조화된 실패 보고

서브에이전트가 실패했을 때 `'search unavailable'` 같은 **모호한 문자열 하나만** 반환하면, 코디네이터는 아무 판단도 할 수 없습니다. 인증 실패인지, 네트워크 타임아웃인지, 검색어가 잘못됐는지 알 수 없기 때문입니다. 이를 "복구 세부 정보를 숨긴다(hides recovery detail)"고 표현합니다.

**올바른 실패 반환 계약**:

```json
{
  "status": "error",
  "failure_type": "AUTH_ERROR",
  "queried": "renewal notice period site:kb.internal",
  "partial_results": [ { "...": "타임아웃 전까지 얻은 결과" } ],
  "message": "Knowledge base returned 401 Unauthorized"
}
```

이 정도 정보가 있어야 코디네이터가 **자격 증명 갱신, 쿼리 수정, 대체 서브에이전트 호출, 사용자 알림** 같은 복구 전략(Fallback)을 선택할 수 있습니다.

피해야 할 설계:
- 단순 boolean 성공/실패 플래그 → 정보가 더 줄어 복구 불가.
- 오류를 서브에이전트 로그에만 남기고 코디네이터에게 숨기기 → 시스템 전체가 복구 불능.
- 조용한 무한 재시도(Silent Retry) → 인증 오류는 자격 증명이 바뀌지 않는 한 재시도로 해결되지 않으며, 무한 루프와 자원 낭비를 초래.

### 6.2 부분 실패(Partial Failure)의 투명한 전달

6개 서브에이전트 중 2개가 도중에 출처 접근 권한을 잃었다면, 최종 보고서는 **정보 커버리지가 불균등**합니다. 이때 하위 독자(Downstream Reader)에게 신뢰성을 정직하게 전달하는 방법은 **커버리지 주석(Coverage Annotation)** 입니다.

즉, 섹션별로 "이 부분은 완료된 출처로 충분히 뒷받침됨 / 이 부분은 출처 접근 실패로 공백(gap) 있음"을 명시합니다.

```markdown
## 유럽 시장 동향  [커버리지: 완전 — 출처 4/4 확보]
...

## 아시아 시장 동향  [커버리지: 부분 — 지정 출처 3개 중 1개만 접근 성공]
> 주의: 이 섹션은 출처 접근 실패로 불완전합니다.
...
```

피해야 할 방식:
- 두루뭉술한 일반 면책 조항(Generic Disclaimer) 하나 붙이기 → 독자가 어느 부분이 부실한지 알 수 없음.
- 완전한 섹션과 불완전한 섹션을 구분 없이 하나의 균질한 서술로 제시 → 독자가 불완전한 정보를 무비판적으로 신뢰.
- 영향받은 섹션을 통째로 삭제 → 보고서의 주제 범위가 왜곡되고, 조사 시도조차 있었는지 알 수 없어짐.

**원칙**: 신뢰성은 "완벽함"이 아니라 **한계의 투명한 공개**에서 나옵니다.

## 7. 사람의 개입 (Human-in-the-Loop)과 위험 기반 라우팅

### 7.1 HITL (Human-in-the-Loop)

**HITL**은 자동화 파이프라인 중간에 사람의 검토·승인 단계를 두는 설계입니다. 완전 자동화가 위험한 고위험 영역(법률, 의료, 금융, 세무)에서 필수적입니다.

### 7.2 검토 라우팅 (Review Routing)과 임계값

파이프라인은 보통 조건에 따라 처리 경로를 나눕니다.
- 안전한 건 → 자동 처리
- 위험 신호가 있는 건 → 사람 검토로 이관(Route to human review / Escalation)

이때 쓰이는 기준 중 하나가 **신뢰도 점수(Confidence Score)** 와 **라우팅 임계값(Routing Threshold)** 입니다.

### 7.3 신뢰도 점수의 한계

**신뢰도 점수는 만능이 아닙니다.** 모델이 어떤 값을 높은 확신으로 추출했다고 해서, 그 값이 옳다는 보장은 없습니다. 특히 **입력 문서 자체에 모순이 있는 경우**, 모델은 두 값 중 하나를 골라 놓고도 높은 확신을 보고할 수 있습니다.

### 7.4 문서 내부 모순 (In-document Contradiction)

계약서의 서로 다른 페이지에서 같은 항목에 대해 상충하는 조건을 명시하는 경우가 있습니다(예: 갱신 통지 기간이 한쪽은 30일, 다른 쪽은 60일).

**올바른 처리**: 모델이 **문서 전체에 걸쳐 값들이 충돌하는지 감지(Conflict Detection)** 하고, 충돌이 있으면 **자신이 고른 값에 대한 신뢰도가 아무리 높아도 해당 추출 건을 사람 검토로 라우팅**합니다.

절대 해서는 안 되는 처리:
- 30일과 60일을 평균 내 45일로 만들기 → 계약의 실제 의도를 완전히 왜곡하는 심각한 오류. 법적 기간은 평균 낼 수 있는 값이 아닙니다.
- 앞 페이지 조항을 무조건 우선 적용 → 계약서에서 앞선 조항이 항상 우선한다는 법칙은 없습니다(특약 사항이 뒤에 오는 경우도 많음).
- 신뢰도 점수만 믿고 통과 → 점수는 원문의 모순 여부를 반영하지 않습니다.

### 7.5 종합 정확도의 함정과 슬라이스 분석

**종합 정확도(Aggregate Accuracy)** 는 전체 데이터에 대한 평균 정확도입니다. 예: "신고 상태 필드의 정확도 99.2%".

**함정**: 이 높은 수치는 대부분을 차지하는 **흔하고 단순한 케이스** 덕분에 만들어졌을 수 있습니다. 드물지만 중요한 하위 그룹에서는 정확도가 처참할 수 있는데, 전체 평균에 묻혀 보이지 않습니다. 이런 현상을 **평균의 착시(Aggregate Fallacy)** 라 하고, 관련된 통계 현상으로 **심프슨의 역설(Simpson's Paradox)** — 전체 경향과 하위 그룹별 경향이 반대로 나타나는 현상 — 이 있습니다.

**슬라이스 분석 (Sliced Analysis)**: 사람 검토를 줄이기 전에, 정확도를 **하위 세그먼트(Sub-segment) 단위로 쪼개서** 확인합니다.
- 문서 유형별(document type)
- 알려진 **엣지 케이스(Edge Case)** 조건별 — 예: 수정 신고서(amended returns), 성이 서로 다른 부부의 공동 신고(joint filings with differing last names)

목표는 **어떤 하위 구간도 종합 평균보다 크게 떨어지지 않음을 확인**하는 것입니다.

부적절한 검증 방법들:
- 검토자 대상 신뢰도 설문조사 → 주관적 인상은 정량적 성능 지표가 될 수 없음.
- 필드의 평균 글자 수가 짧은지 확인 → 짧다고 추출이 쉬운 것은 아니며, 단답형에도 맥락 판단이 필요한 엣지 케이스가 많음.
- 다른 필드들의 평균/중앙값과 비교 → 해당 필드 내부의 하위 세그먼트 취약점을 전혀 걸러내지 못함.

## 8. 사용자 대면 에이전트 설계 원칙

### 8.1 공감과 자동 해결의 병행

고객 지원 AI 에이전트가 감정이 섞인 요청을 받았을 때의 원칙:

1. **감정 인정(Acknowledgement)**: 고객의 불만·좌절을 먼저 짧게 인정합니다. 감정적 표현을 "해결과 무관하다"며 무시하고 기계적으로 처리하면 불만이 악화됩니다.
2. **정책 범위 내라면 즉시 처리(Automated Resolution)**: 표준 규정(예: 30일 교환 정책) 안에서 해결 가능한 단순 건이라면 지체 없이 처리합니다.

### 8.2 불필요한 에스컬레이션과 마찰 피하기

- **감정적 어조 = 사람 상담원 이관 신호가 아닙니다.** 고객이 사람과 대화하겠다고 **명시적으로 요청하지 않았고** 요청이 규정 내에서 해결 가능하다면, 곧바로 사람에게 넘길 이유가 없습니다.
- **불필요한 확인 절차를 추가하지 않습니다.** "사람 상담원을 원하시는 게 아닌 거 맞죠?" 같은 되묻기는 처리를 지연시키고 마찰(Friction)을 늘려 불만을 키웁니다.

에스컬레이션은 **정책 밖의 건, 판단이 필요한 건, 고객이 명시적으로 요청한 경우**에 하는 것입니다.

## 9. 출력 렌더링: 콘텐츠 유형에 맞는 형식

최종 보고서를 만들 때, 서로 성격이 다른 데이터를 하나의 형식(예: 전부 글머리 기호 목록)으로 통일하면 가독성이 떨어집니다.

**원칙: 각 콘텐츠 유형을 그 유형의 자연스러운 형식에 맞춥니다.**

| 데이터 성격 | 적합한 형식 | 이유 |
|---|---|---|
| 정량적·시계열·비교 데이터 (주가, 매출 추세) | **표(Table)** | 값의 정렬·비교·스캔(Scannability)이 쉬움 |
| 정성적 서술 (뉴스 요약, 맥락 설명) | **서술문(Prose)** | 흐름과 맥락이 자연스럽게 전달됨 |
| 병렬적 항목 나열 | 목록(List) | 항목 간 독립성이 드러남 |

피해야 할 방식:
- 모든 것을 하나의 형식으로 강제 통일(일관성이라는 이름의 가독성 저하).
- 숫자와 서술 문장을 하나의 목록 안에서 교대로 섞기 → 혼란 가중.
- 재무 수치를 서술형 문단으로 풀어쓰기 → 수치 비교가 매우 어려워짐.

## 10. 설계 원칙 요약

1. **API는 무상태다.** 맥락 관리는 전적으로 애플리케이션의 책임이다.
2. **모든 압축·요약은 손실이다.** 보존해야 할 것(특히 출처)은 명시적으로 지시해야 남는다.
3. **중요한 사실은 컨텍스트 밖(스크래치패드)에 적어 둔다.** 컨텍스트는 신뢰할 수 있는 저장소가 아니다.
4. **에이전트 간 통신은 구조화된 계약으로 한다.** 자유 형식 텍스트는 파싱·검증·비교가 불가능하다.
5. **모든 사실에 출처와 날짜를 붙인다.** 병합할 때도 출처는 합집합으로 보존한다.
6. **실패는 구조화해서 보고한다.** 실패 유형, 시도한 쿼리, 부분 결과를 함께 준다.
7. **불확실성과 공백은 숨기지 말고 표시한다.**
8. **평균을 믿지 말고 하위 그룹을 쪼개 본다.**
9. **모순이 감지되면 신뢰도와 무관하게 사람에게 넘긴다.**
10. **동시 실행 시에는 쓰기 영역을 격리한다.**

## 용어 사전 (Glossary)

| 영어 용어 | 한국어 설명 |
|---|---|
| Stateless | 무상태. 서버가 이전 요청 정보를 저장하지 않는 성질. LLM API의 기본 동작 방식 |
| Context Window | 컨텍스트 윈도우. 한 요청에서 모델이 처리 가능한 최대 토큰 수 |
| Context Budget | 컨텍스트 예산. 시스템 각 구성 요소에 미리 배분해 둔 토큰 사용 한도 |
| Token | 토큰. 모델이 텍스트를 처리하는 최소 단위 |
| Max Output Tokens | 최대 출력 토큰. 모델이 한 번에 생성할 답변의 길이 상한 (입력 용량과 무관) |
| Truncation | 잘림. 한도 초과분이 버려지는 현상 |
| Latency | 지연 시간. 요청부터 응답까지 걸리는 시간 |
| Rolling Summary | 순환 요약. 이전 대화를 짧은 요약으로 대체해 유지하는 손실 압축 기법 |
| Context Compaction | 컨텍스트 압축. 대화 내역을 요약해 윈도우 안에 유지하는 기법 (서버 측 기능으로도 제공) |
| `context_management` | 서버 측 컨텍스트 압축을 설정하는 Claude API 파라미터 |
| `compact-2026-01-12` | 서버 측 압축 기능을 사용하기 위한 베타 헤더 값 |
| `messages` | 대화 기록을 담는 API 요청 배열. 모델이 볼 수 있는 맥락의 전부 |
| Scratchpad | 스크래치패드. 발견한 사실을 기록해 두는 외부 파일 형태의 지속 메모리 |
| Race Condition | 경쟁 조건. 동시 접근 순서에 따라 결과가 달라지고 데이터가 깨지는 현상 |
| Overwrite Bug | 덮어쓰기 버그. 나중 쓰기가 앞선 기록을 지워 버리는 문제 |
| Isolation | 격리. 각 실행 주체에 고유한 자원(파일)을 배정해 충돌을 원천 차단하는 전략 |
| Concurrency | 동시성. 여러 작업이 동시에 진행되는 상태 |
| Orchestrator | 오케스트레이터. 작업을 배분하고 결과를 취합하는 상위 에이전트 |
| Coordinator | 코디네이터. 서브에이전트 결과를 모아 최종 산출물을 만드는 에이전트 |
| Subagent | 서브에이전트. 배정된 좁은 범위 작업을 수행하는 하위 에이전트 |
| Synthesis | 합성/종합. 여러 결과를 하나의 산출물로 통합하는 단계 |
| Output Contract | 출력 계약. 반환 데이터의 형식과 필수 항목을 규정한 사전 약속 |
| Output Schema | 출력 스키마. 출력 계약을 구조로 명세한 것 |
| Data Contract | 데이터 계약. 주고받는 데이터 형식에 대한 합의 |
| Provenance | 출처 추적성. 정보가 어디서 왔는지 끝까지 추적할 수 있는 성질 |
| Traceability | 추적 가능성. Provenance와 거의 같은 의미로 사용 |
| Claim | 주장. 보고서에 담기는 개별 사실 진술 |
| Claim-Source Mapping | 주장-출처 매핑. 각 주장에 근거 출처를 1:1로 연결한 구조 |
| Citation | 인용 정보. 주장을 뒷받침하는 출처 표기 |
| Supporting Excerpt | 뒷받침 발췌문. 주장의 근거가 되는 원문 일부 |
| Bibliography | 참고문헌 목록. 참조한 문서 전체 목록 (개별 주장 추적에는 불충분) |
| Metadata | 메타데이터. 데이터에 대한 데이터 (출처, 날짜 등) |
| Retrieval Date | 검색/수집 날짜. 데이터를 가져온 시점 |
| Publication Date | 발행일. 원 자료가 공개된 시점 |
| Recency | 최신성. 데이터가 얼마나 최근 것인가 |
| False Contradiction | 허위 모순. 시점 차이 등으로 실제 모순이 아닌데 모순으로 오인되는 상황 |
| Consolidate | 통합. 중복 항목을 하나로 합치되 정보(출처)는 보존하는 병합 |
| Near-duplicate | 거의 중복. 표현만 다르고 내용이 사실상 같은 항목 |
| Exploratory Reasoning | 탐색적 추론. 결론에 이르기까지의 장문 사고 과정 |
| Relevance Score | 연관성 점수. 해당 사실이 질문에 얼마나 관련 있는지의 수치 |
| Hallucination | 환각. 모델이 사실이 아닌 내용을 그럴듯하게 지어내는 현상 |
| Temperature | 온도. 출력의 무작위성을 조절하는 파라미터. 높이면 창의성과 함께 환각 위험도 증가 |
| Failure Type | 실패 유형. 오류의 종류를 구분하는 코드 (예: AUTH_ERROR) |
| Partial Results | 부분 결과. 실패 이전까지 확보한 유효한 결과 |
| Fallback | 대체 경로. 실패 시 선택하는 우회 처리 전략 |
| Silent Retry | 조용한 재시도. 보고 없이 반복 재시도하는 위험한 패턴 |
| Partial Failure | 부분 실패. 일부 구성 요소만 실패한 상태 |
| Coverage Annotation | 커버리지 주석. 섹션별 조사 완성도와 공백을 명시하는 표기 |
| Gap | 공백. 정보가 확보되지 못한 영역 |
| Generic Disclaimer | 일반 면책 조항. 구체성이 없어 독자 판단에 도움이 안 되는 두루뭉술한 고지 |
| Downstream Reader | 하위 독자. 산출물을 최종적으로 소비하는 사람 또는 시스템 |
| Transparency | 투명성. 한계와 불확실성을 숨기지 않고 드러내는 것 |
| HITL (Human-in-the-Loop) | 자동화 흐름 중간에 사람의 검토·승인 단계를 두는 설계 |
| Review Routing | 검토 라우팅. 조건에 따라 자동 처리와 사람 검토로 경로를 나누는 것 |
| Escalation | 에스컬레이션. 상위 처리 주체(사람 등)로 이관하는 것 |
| Confidence Score | 신뢰도 점수. 모델이 자기 출력에 대해 보고하는 확신 정도 (원문 모순은 반영하지 못함) |
| Routing Threshold | 라우팅 임계값. 자동 처리와 사람 검토를 가르는 기준값 |
| Conflict Detection | 충돌 감지. 문서 내 값들이 서로 모순되는지 탐지하는 기능 |
| In-document Contradiction | 문서 내부 모순. 같은 문서 안에서 같은 항목에 상충하는 값이 존재하는 상태 |
| Aggregate Accuracy | 종합 정확도. 전체 데이터에 대한 평균 정확도 |
| Aggregate Fallacy | 평균의 착시. 전체 평균이 높아 하위 그룹의 취약점을 가리는 오류 |
| Simpson's Paradox | 심프슨의 역설. 전체 경향과 하위 그룹별 경향이 반대로 나타나는 통계 현상 |
| Sliced Analysis | 슬라이스 분석. 성능을 하위 세그먼트별로 쪼개 검증하는 방법 |
| Sub-segment | 하위 세그먼트. 전체 데이터를 조건별로 나눈 부분 집합 |
| Edge Case | 엣지 케이스. 드물지만 처리 난도가 높은 예외적 사례 |
| Empathy / Acknowledgement | 공감/인정. 사용자의 감정 상태를 먼저 짧게 인정하는 응답 태도 |
| Automated Resolution | 자동 해결. 정책 범위 내 요청을 사람 개입 없이 즉시 처리하는 것 |
| Friction | 마찰. 불필요한 확인 절차 등으로 사용자 경험을 저해하는 요소 |
| Prose | 서술문. 문단 형태의 자연스러운 산문 |
| Scannability | 스캔 용이성. 눈으로 훑어 원하는 값을 빨리 찾을 수 있는 정도 |
