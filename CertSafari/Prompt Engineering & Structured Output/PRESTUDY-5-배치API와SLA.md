# 5. Messages API vs Message Batches API와 SLA 설계

이 장에서 다루는 것:

- 동기식 Messages API와 비동기 Message Batches API의 차이와 선택 기준
- Batches API의 제약과 사용법: 배치당 한도, `custom_id`, 결과 순서, 상태 폴링, 결과 유형과 오류 복구
- 배치가 맞는 작업 / 맞지 않는 작업 (도구 호출 루프, 실시간 UI, 서버 측 도구)
- 마감 기한(SLA) 관점의 배치 제출 주기 설계 — 최악의 경우 계산 예제
- 흔한 오해와 잘못된 근거들

## 5.1 동기 Messages API와 비동기 Batches API 비교

### 5.1.1 Messages API (동기식, synchronous)

Anthropic의 기본 API는 **Messages API**이고, 이것은 **동기식(synchronous)** 입니다. 동기식이란 "요청을 보내고 응답이 돌아올 때까지 기다린다(blocking)"는 뜻입니다.

```python
import anthropic
client = anthropic.Anthropic()

resp = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "이 계약서를 요약해줘: ..."}],
)
print(resp.content[0].text)   # 보통 수 초 내에 결과가 손에 들어옴
```

특징:

- 응답이 즉시(보통 수 초) 온다 → 챗봇, 실시간 UI, 코드 어시스턴트, 프롬프트 실험에 적합
- **스트리밍 지원** — 토큰이 생성되는 즉시 받을 수 있음
- 요청 1건당 1회 호출 → 15,000건이면 15,000번 호출해야 함
- 정가 요금
- **Rate Limit(호출 제한)** 이 있음: 분당 요청 수(RPM), 분당 토큰 수(TPM) 등에 상한이 있어, 스레드를 많이 띄워 병렬 호출해도 무한정 빨라지지 않고 429 에러(Too Many Requests)를 맞는다
- 대량 작업에는 비효율적이고 비싸다

**CI 파이프라인이 결과를 기다리며 막혀 있는 상황**처럼, 누군가(또는 무언가)가 결과를 붙잡고 대기하는 블로킹 워크플로우도 동기식의 영역입니다.

### 5.1.2 Message Batches API (비동기, asynchronous)

**Message Batches API**는 "지금 당장 답이 필요 없는 대량 작업"을 위한 별도 API입니다. 수천~수만 건의 요청을 한 묶음(batch)으로 제출하면, 서버가 여유 있을 때 처리해 두었다가 결과를 나중에 한꺼번에 돌려줍니다.

핵심 성질:

| 항목 | 값 / 의미 |
|---|---|
| 처리 시간 | 최대 **24시간** (대부분 훨씬 빨리, 종종 1시간 이내에 끝나지만 공식 보장은 "24시간 이내"뿐) |
| 지연 시간 SLA | **없음.** 짧은 완료 시간에 대한 보장이 존재하지 않음 |
| 비용 | 동기식 대비 **약 50% 할인** (프리미엄이 붙는 것이 아니라 더 쌈) |
| 규모 | 배치당 최대 **100,000개 요청** 또는 **256 MB 총 페이로드** 중 먼저 도달하는 쪽 |
| 결과 식별 | 요청마다 **`custom_id`** 를 붙여 제출하고, 결과도 같은 `custom_id` 로 짝지어 돌아옴 |
| 순서 | 처리/반환 순서는 보장되지 않음. 순서가 필요하면 `custom_id` 로 직접 정렬 |
| 결과 수거 | API를 통한 **자동화된 폴링(polling)** 으로 완전히 가능. 콘솔에서 수동으로 꺼내는 방식이 아님 |

제출 예시(개념):

```python
batch = client.messages.batches.create(requests=[
    {"custom_id": "contract-0001",
     "params": {"model": "claude-sonnet-4-5", "max_tokens": 1024,
                "messages": [{"role": "user", "content": "계약서 1 내용..."}]}},
    {"custom_id": "contract-0002",
     "params": {...}},
    # ... 15,000건
])
```

**왜 존재하는가**: 대량 문서 분류/추출/요약처럼 "문서당 비용"이 총비용을 좌우하는 워크로드에서, 즉시성을 포기하는 대신 절반 가격을 얻기 위해서입니다. 마감이 24시간 이상 여유가 있으면 거의 항상 배치가 유리합니다.

**전형적 용도**: 야간 배치 요약, 대량 문서 분류/번역, 데이터셋 백필(backfill), 평가(eval) 데이터셋 실행.

### 5.1.3 어느 쪽을 고를 것인가

판단 축은 **비용이 아니라 지연 시간 요구사항**입니다. 질문은 딱 두 가지입니다.

1. **누군가(또는 어떤 파이프라인이) 결과를 기다리며 막혀 있는가?** → 기다린다면 동기, 아니면 배치 후보.
2. **비용이 중요한가?** → 중요하고 지연이 허용되면 배치.

| 상황 | 선택 | 이유 |
|---|---|---|
| PR 병합을 막고 판정을 기다리는 merge gate | Messages API | 수 초 내 응답 필요. 50% 할인보다 개발자 생산성이 큼 |
| 라이브 채팅, 자동완성, 대화형 어시스턴트 | Messages API | 사용자가 참아줄 수 있는 지연은 길어야 수 초 |
| 프롬프트를 다듬는 실험 단계 | Messages API | 빠른 반복이 목적 |
| 야간에 송장 15만 장 분류 | Batches API | 아침까지만 끝나면 됨 |
| 매일 밤 40,000개 모듈의 테스트 케이스 생성, 개발자는 다음 날 아침 확인 | Batches API | 지연 허용 + 대량 + 50% 절감이 모두 맞아떨어짐 |

**배치가 라이브 채팅에 부적합한 이유는 가격이 아니라 지연 시간(latency)입니다.** 비용이 싸다는 이유로 실시간 대화를 배치로 돌리면 답변이 몇 시간 뒤 도착해 제품 자체가 성립하지 않습니다.

## 5.2 Batches API의 제약과 사용법

### 5.2.1 배치당 제한 (Per-batch Limits)

단일 Message Batch 하나는 다음 한계 중 **먼저 도달하는 것**에 걸립니다.

- **최대 100,000개 요청**
- **최대 256 MB 총 페이로드**

따라서 150,000건을 처리하려면 최소 2개의 배치로 나눠 제출해야 합니다(예: 100,000 + 50,000). 스캔 이미지처럼 요청 하나가 큰 경우에는 총 용량이 256MB를 넘어 **요청 개수와 무관하게 더 잘게 쪼개야 할 수도 있습니다.**

참고로 "배치 최대 크기 1,000개", "시간당 500 요청 제한", "요청 수 제한 없음" 같은 수치는 모두 사실이 아닙니다.

### 5.2.2 배치를 굳이 쪼갤 필요가 있는가?

배치는 애초에 대용량을 처리하도록 설계되어 있으므로, "안정성을 위해 몇 백 건씩 잘라 몇 분 간격으로 제출"할 이유는 없습니다. 오히려 잘게 나누면 관리 복잡도와 추적 부담만 늘어납니다. **쪼개는 근거는 오직 문서에 명시된 한도(요청 수 100,000개, 용량 256MB)를 넘길 때뿐입니다.**

### 5.2.3 custom_id — 가장 중요한 개념

배치의 각 요청에는 개발자가 직접 붙이는 고유 식별자 `custom_id`가 있습니다. 결과를 받으면 `custom_id`를 보고 원래 어떤 요청의 답인지 매칭(correlate)합니다.

```json
{
  "requests": [
    {
      "custom_id": "doc-2026-report_final",
      "params": {
        "model": "claude-sonnet-4-5",
        "max_tokens": 1024,
        "messages": [{"role": "user", "content": "다음 문서를 한국어로 번역: ..."}]
      }
    },
    {"custom_id": "doc-00043", "params": {"model": "...", "messages": [...]}}
  ]
}
```

**결과 순서는 보장되지 않습니다.** 내부적으로 요청들을 병렬 처리하기 때문에 완료된 순서나 임의의 순서로 결과 파일에 기록될 수 있습니다. 따라서 결과를 원본과 짝지을 때 **배열 위치(index)로 zip하면 안 됩니다.**

```python
# 잘못된 방법 - 결과가 뒤섞여 엉뚱한 문서에 요약이 붙는다
for doc, res in zip(documents, results):
    doc.summary = res.text

# 올바른 방법 - custom_id로 매칭
by_id = {r.custom_id: r for r in results}
for doc in documents:
    doc.summary = by_id[doc.id].text
```

이 순서 미보장은 **요청 건수와 무관합니다.** "1,000건을 넘으면 순서가 바뀐다" 같은 임계값은 존재하지 않습니다.

### 5.2.4 custom_id의 형식 제약

`custom_id`에는 엄격한 문자 제한이 있습니다.

**허용되는 문자:**
- 영문 대소문자 `a-z`, `A-Z`
- 숫자 `0-9`
- 하이픈 `-`
- 언더스코어 `_`

**길이 제한:** 최대 64자.

**고유성:** 하나의 배치 안에서 `custom_id`는 **중복될 수 없습니다.**

허용되지 않는 문자를 쓰면 배치 제출 시 **유효성 검사 에러(validation error)** 로 거부됩니다.

| 예시 | 문제 |
|---|---|
| `doc/2026/report:final` | 슬래시 `/`, 콜론 `:` 불가 |
| `doc#2026#report#final#v2` | 샵 `#` 불가 |
| `doc 2026 report final v2` | 공백 불가 |
| `doc-2026-report_final` | **유효함** (영숫자, 하이픈, 언더스코어만 사용) |

"추적하기 편하다", "눈으로 읽기 좋다" 같은 이유는 API 규격을 바꿔주지 않습니다. **의미 있는 정보를 넣고 싶다면 허용된 문자만으로 인코딩해야 합니다.** 예: 날짜와 구획을 하이픈/언더스코어로만 구분한 `doc-20260315-report_final-v2`.

### 5.2.5 결과 유형(result type)과 오류

배치 결과의 각 항목에는 결과 유형이 붙습니다.

| 결과 유형 | 의미 |
|---|---|
| `succeeded` | 정상 처리 |
| `errored` | 오류 발생. 안에 오류 객체가 들어 있음 |
| `canceled` | 취소됨 |
| `expired` | 처리 기한(24시간) 내에 완료되지 못함 |

`errored` 항목의 대표적인 오류가 **`invalid_request_error`** 입니다. 이는 **클라이언트 측 입력 문제(4xx 계열)** 를 뜻합니다. 예를 들어 문서가 컨텍스트 창을 초과한 경우입니다.

중요한 성질: **입력을 고치지 않고 똑같이 다시 보내면 똑같이 실패합니다.** 배치 API가 오류 요청을 알아서 재시도해 주지도 않습니다.

### 5.2.6 배치 만료(expired)와 부분 실패 처리

배치가 24시간 안에 전부 처리되지 못하면, **처리되지 못한 요청만** 결과 타입 `expired` 로 돌아옵니다.

중요한 규칙 세 가지:

1. **이미 성공한 요청의 결과는 그대로 유효하다.** 배치가 만료됐다고 전체 결과가 폐기되지 않는다.
2. **`expired` 요청에는 과금되지 않는다.**
3. **만료는 종료 상태(terminal state)다.** 플랫폼 수요가 줄어도 자동으로 재대기열(requeue)되지 않는다.

따라서 올바른 대응은 실패분만 골라 재제출하는 것입니다.

```python
expired_ids = [r.custom_id for r in results if r.result.type == "expired"]
# 성공분은 그대로 저장해 두고, expired 건만 새 배치로 재제출
client.messages.batches.create(requests=[build_request(i) for i in expired_ids])
```

전체 배치를 통째로 재제출하면 이미 성공한 요청까지 다시 과금되므로 낭비입니다. 또한 일시적인 수요 급증 때문에 생긴 만료를 이유로 워크로드 전체를 더 비싼 동기식 API로 바꿀 필요도 없습니다.

### 5.2.7 배치 오류 복구의 정석

20,000건 중 일부가 컨텍스트 초과(`invalid_request_error`)로 실패했다면:

1. 결과 파일에서 `errored` 항목을 찾아 **`custom_id`로 어떤 문서가 실패했는지 식별**한다.
2. **그 문서들만** 작은 청크로 분할한다(원인 해결).
3. **실패한 것들만** 새 배치로 다시 제출한다.

이미 성공한 수만 건을 다시 돌리는 것은 시간과 비용의 낭비입니다. 실패했다고 영구 폐기할 이유도 없습니다 — 청킹이라는 전처리로 충분히 처리 가능하기 때문입니다. 그리고 `max_tokens`를 줄이거나 늘리는 것은 **입력 길이 문제와 무관합니다.**

### 5.2.8 대량 배치 제출 전의 필수 절차 — 소규모 표본 검증

배치는 싸지만, **프롬프트가 잘못돼 있으면 8만 건 전부를 버리고 다시 돌려야** 합니다. 그래서 표준 절차는 다음과 같습니다.

1. 전체 데이터에서 **대표성 있는(representative)** 소규모 표본(예: 50~200건)을 뽑는다. 정상 케이스뿐 아니라 지저분한 케이스, 값이 없는 케이스도 포함시킨다.
2. 그 표본을 **동기식 API** 로 돌려 빠르게 결과를 본다.
3. 출력 품질(필드 누락, 형식 위반, 잘못된 값)을 확인하고 프롬프트/스키마를 고친다.
4. 품질이 충분해지면 그때 전체를 배치로 제출한다.

`max_tokens` 를 무작정 키우거나, 배치를 반으로 쪼개는 것은 "프롬프트 품질" 문제를 전혀 해결하지 못합니다. `max_tokens` 는 출력이 길이 제한으로 **잘리는(truncation)** 문제에만 효과가 있고, 지시 불이행·형식 오류와는 무관합니다.

## 5.3 배치가 맞는 작업 / 맞지 않는 작업

### 5.3.1 맞는 작업

- 야간 대량 요약, 대량 문서 분류/번역/추출
- 데이터셋 백필(backfill)
- 평가(eval) 데이터셋 실행
- 오프라인 분석 — **즉시 응답이 필요 없고**, 비용이 총량으로 좌우되는 모든 작업

### 5.3.2 맞지 않는 작업 (1) — 사람이 기다리는 모든 것

라이브 채팅, 자동완성, 대화형 어시스턴트, 블로킹 merge gate. 이유는 반복하지만 **가격이 아니라 지연 시간**입니다.

### 5.3.3 맞지 않는 작업 (2) — 클라이언트 측 도구 호출 루프

에이전트가 도구를 쓰는 과정은 **여러 단계의 왕복(round trip)** 입니다.

1. 모델이 `tool_use` 블록으로 "DB 조회 도구를 이 인자로 불러줘"라고 요청 → **여기서 응답이 한 번 끝난다**
2. **애플리케이션이** 실제로 DB를 조회한다 (이건 모델이 아니라 우리 코드가 한다)
3. 우리가 `tool_result`를 담아 **새 요청을 보낸다**
4. 모델이 그 결과를 근거로 추론해 최종 답을 낸다

즉 도구 실행은 모델 바깥에서 일어나며, 그 사이에 **모델 호출이 두 번 이상** 필요합니다.

**단일 배치 요청은 처리 도중에 일시 정지하여 애플리케이션이 제공하는 도구 결과를 받아들일 수 없습니다.** 각 배치 요청은 독립적으로 해결되며, **요청 중간의 왕복(mid-request round trip)이 존재하지 않습니다.** 따라서 "도구 요청 → 결과 수신 → 후속 추론 → 최종 답변"을 **하나의 배치 요청 안에서** 끝낼 수 없습니다.

**사실이 아닌 통념들:**

- "배치 요청은 대화당 메시지 하나로 제한된다" → **거짓.** 배치 요청에도 이전 대화 이력이 담긴 `messages` 배열을 여러 개 넣을 수 있습니다.
- "배치 API에는 `tools`를 첨부할 수 없다" → **거짓.** 도구 정의는 정상적으로 첨부되고 모델은 도구를 요청할 수 있습니다.
- "배치 API가 응답에서 `tool_use` 블록을 조용히 제거한다" → **거짓.** `tool_use` 블록은 정상적으로 반환됩니다.

**정확한 제약은 오직 하나**: 한 요청 안에서 멈췄다가 외부 결과를 받아 이어가는 것이 불가능하다는 점입니다. 배치의 각 요청이 이미 완성된 대화 이력을 담아 한 번에 끝나는 형태라면 도구가 관련된 요청도 배치로 보낼 수 있습니다. 불가능한 것은 *루프 자체*를 배치 안에 넣는 일입니다.

### 5.3.4 예외 — 서버 측 도구는 배치에서 잘 동작한다

도구에는 두 종류가 있습니다.

| 종류 | 실행 주체 | 왕복 | 배치 적합성 |
|---|---|---|---|
| **클라이언트 측 도구(client-side tool)** | 애플리케이션이 `tool_use`를 받아 직접 실행하고 `tool_result`를 되돌려 보냄 | 여러 번(multi-turn) 필요 | 루프를 배치 안에 넣을 수 없음 |
| **서버 측 도구(server-side / built-in tool)** | 예: 웹 검색. Anthropic 서버 내부에서 검색 실행과 결과 반영이 **하나의 요청 안에서 자동으로(self-contained)** 끝남 | 애플리케이션 왕복 불필요 | **배치 안에서 정상 동작** |

따라서 **서버 측 웹 검색 도구는 Message Batches API 안에서 정상 동작합니다.** 배치가 도구 정의를 포함한 요청을 무조건 거부하는 것도 아니고, 서버 도구가 스트리밍 동기 응답에서만 작동하는 것도 아니며, 별도의 동기 요청을 병렬로 띄워 줄 필요도 없습니다.

## 5.4 SLA·마감 기한 관점의 배치 주기 설계

### 5.4.1 지연 시간 SLA가 없다는 사실의 무게

**SLA(Service Level Agreement, 서비스 수준 협약)** 는 "우리 서비스는 이 정도 수준을 지킵니다"라는 약속입니다.

**Batches API는 짧은 완료 시간에 대한 지연 시간 SLA를 제공하지 않습니다.**

전형적인 실수: 운영 리드가 "대부분의 배치가 1시간 안에 끝난다"는 **관측 데이터**를 근거로 고객에게 "야간 요약은 90분 이내 완료"라는 **고정 약속**을 하자고 제안합니다.

가장 강력한 기술적 반박은 이것입니다. **관측된 평균은 보장이 아닙니다.** Batches API에는 지연 시간 SLA가 없으므로, 수요가 몰리는 상황에서 배치가 최대 24시간까지 걸리는 것은 **장애가 아니라 사양대로의 정상 동작(legitimate behavior)** 입니다. 그런 상황에서 90분 약속은 필연적으로 깨집니다.

즉, **고객에게 하는 약속은 관측된 중앙값이 아니라 공식적으로 보장된 상한선 위에 세워야 합니다.**

### 5.4.2 총 소요 시간 공식

배치 파이프라인의 최악의 경우(worst case) 총 지연 시간은 세 조각의 합입니다.

```
최악 총 소요 시간 = 배치 제출 주기(I)  +  배치 최대 처리 시간(24시간)  +  후처리 시간
                    └ 누적/수집 지연        └ 처리 창                      └ 있을 때만
                      (Accumulation Delay)   (Processing Window)
```

**왜 제출 주기가 통째로 더해지는가**: 어떤 항목이 **직전 배치가 제출된 직후에 도착**하면, 다음 배치 제출까지 최대 주기 I만큼 꼬박 기다려야 합니다. 그 후에야 처리가 시작되고, 처리는 최대 24시간까지 걸릴 수 있습니다. 이것이 **최악의 대기 시간**이며, 마감 보장 계산에는 항상 이 최악값을 써야 합니다.

일반식:

```
I + (배치 최악 처리 시간) + (후처리 시간) ≤ 마감 기한(SLA)
```

후처리가 없다면 간단히:

```
I + T_배치최대실행시간 ≤ T_SLA
∴ I(최대) = T_SLA − T_배치최대실행시간
```

### 5.4.3 계산 예제 A — 후처리가 없는 경우 (SLA 30시간)

법률 검토 파이프라인이 "모든 계약서는 도착 후 30시간 이내에 결과를 받는다"를 보장해야 합니다.

```
I + 24 ≤ 30
I ≤ 6
```

따라서 **최소 6시간마다 한 번은 새 배치 제출 주기를 시작해야 합니다.** 최악의 경우라도 6(대기) + 24(처리) = 30시간으로 SLA를 정확히 만족합니다.

다른 주기를 넣어보면 왜 안 되는지 바로 보입니다.

| 제출 주기 | 최악 총 시간 | 30시간 SLA |
|---|---|---|
| 6시간 | 6 + 24 = 30 | 만족 |
| 18시간 | 18 + 24 = 42 | 위반 |
| 24시간 | 24 + 24 = 48 | 위반 |
| 30시간 | 30 + 24 = 54 | 크게 위반 |

### 5.4.4 계산 예제 B — 후처리가 있는 경우 (SLA 36시간)

마감 36시간, 배치 최악 처리 24시간, 후처리 2시간이라면:

```
I + 24 + 2 ≤ 36  →  I ≤ 10시간
```

즉 배치를 **최소 10시간마다** 제출해야(간격이 10시간을 넘지 않아야) 최악의 경우에도 36시간을 지킵니다.

### 5.4.5 계산 예제 C — "가장 긴 허용 주기"를 묻는 경우 (SLA 48시간)

SLA가 수집 후 48시간, 배치 최대 처리 시간이 24시간이라면:

```
최장 제출 주기 = 48 − 24 = 24시간
```

- 6시간이나 12시간 주기도 SLA는 만족하지만, "**가장 긴** 허용 간격"을 묻는 문제라면 답이 아닙니다.
- 48시간 주기는 최악의 경우 48 + 24 = 72시간이 되어 SLA를 위반합니다.

**마감 시간을 그대로 제출 주기로 쓰면 안 됩니다** — 처리 시간(과 후처리)을 뺀 나머지가 대기 예산입니다.

## 5.5 흔한 오해와 잘못된 근거

**API 선택에 대해**

- "요청이 수백 건 넘으면 배치가 **필수**다" → 그런 강제 규칙은 없습니다. 선택 기준은 지연 허용 여부와 비용입니다.
- "야간 작업이니 총 소요 시간을 최소화해야 하므로 동기 + 스트리밍" → 아무도 안 기다리는데 벽시계 시간을 줄일 이유가 없습니다.
- "순차 실행이 완료를 보장한다" → 40,000건 순차 호출은 엄청난 시간과 비용, 타임아웃 위험만 낳습니다.
- "배치는 비싸다/프리미엄이다" → 반대로 **약 50% 쌉니다.**

**배치 한도·동작에 대해**

- "배치 최대 크기는 1,000개", "시간당 500 요청 제한", "요청 수 제한 없음" → 모두 사실이 아닙니다. 실제는 **100,000 요청 / 256 MB** 중 먼저 걸리는 쪽입니다.
- "1,000건을 넘으면 결과 순서가 바뀐다" → 순서 미보장은 **건수와 무관**하게 항상 성립합니다.
- "안정성을 위해 배치를 잘게 쪼개야 한다" → 한도를 넘지 않는 한 쪼갤 이유가 없습니다.
- "결과는 콘솔에서 수동으로 꺼내야 한다" → API 폴링으로 완전 자동화 가능합니다.
- "만료되면 배치 전체가 폐기된다 / 나중에 자동 재대기열된다" → 성공분은 유효하고, `expired`는 과금되지 않으며, 만료는 **종료 상태**입니다.
- "실패한 요청은 배치가 알아서 재시도한다" → 하지 않습니다. 입력을 고쳐 실패분만 재제출해야 합니다.

**custom_id에 대해**

- "읽기 편하니까 `/`, `:`, `#`, 공백을 써도 된다" → 유효성 검사 에러로 거부됩니다. 영숫자·`-`·`_`, 최대 64자, 배치 내 고유.

**도구 사용에 대해**

- "배치 요청은 대화당 메시지 하나로 제한된다", "배치에는 `tools`를 첨부할 수 없다", "배치가 `tool_use` 블록을 제거한다" → 모두 거짓. 유일한 제약은 **한 요청 안에서 멈췄다가 외부 도구 결과를 받아 이어갈 수 없다**는 것뿐입니다.
- "서버 측 웹 검색은 배치에서 못 쓴다" → 씁니다. 서버 도구는 한 요청 안에서 self-contained하게 완결됩니다.

**SLA 계산에 대해**

- "배치 처리 창이 24시간이니 24시간마다 제출하면 된다" → 대기 시간을 빼먹은 계산. 실제로는 48시간이 걸릴 수 있습니다.
- "제출 주기를 SLA 길이에 맞추면 된다" → 처리 시간을 아예 무시한 계산입니다.
- "여유를 두려고 주기를 늘린다" → 여기서 "여유"는 **주기를 짧게** 해야 생깁니다. 18시간은 6시간보다 여유가 적은 것이 아니라 아예 요구 조건 위반입니다.
- 후처리 시간을 빼먹기 → 36시간 SLA에 12시간 주기를 쓰면 12+24+2 = 38시간으로 초과합니다.
- 후처리 시간만 보고 2시간 주기로 잡기 → 24시간 처리 시간을 무시한 계산입니다.
- "배치 처리 시간을 줄여서 후처리를 흡수한다" → **외부 API의 최악 처리 시간(24시간)은 사용자가 줄일 수 없는 상수**입니다. 내가 조절할 수 있는 변수는 제출 간격 I 뿐입니다.
- "대부분 1시간이면 끝나니 90분을 약속하자" → 관측된 중앙값은 보장이 아닙니다. 약속은 공식 상한선(24시간) 위에 세웁니다.
