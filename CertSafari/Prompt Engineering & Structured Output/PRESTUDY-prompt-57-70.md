# 사전 학습 노트 — 프롬프트 엔지니어링과 구조화된 출력 (Prompt Engineering & Structured Output)

이 문서는 이 주제를 처음 접하는 학습자를 위한 개념 정리 노트입니다. LLM(대규모 언어 모델), 특히 Anthropic Claude를 실제 시스템에 붙여서 "정해진 형식의 데이터"를 뽑아내고, 그 시스템을 안정적으로 운영하는 데 필요한 개념들을 바닥부터 설명합니다.

---

## 0. 큰 그림: LLM으로 만드는 정보 추출 파이프라인

### 왜 이런 시스템이 필요한가

기업에는 **비구조화 데이터(unstructured data)** 가 넘쳐납니다. 이메일, PDF 계약서, 이력서, 웹페이지, 고객 지원 티켓 같은 것들이죠. 사람이 읽으면 "아, 배송일은 3월 14일이구나" 하고 바로 알지만, 컴퓨터 프로그램(데이터베이스, 리포트 도구)은 이런 자유 텍스트를 다룰 수 없습니다.

그래서 필요한 것이 **정보 추출(Information Extraction)** 입니다. 자유 텍스트를 넣으면 정해진 필드를 가진 JSON 같은 **구조화된 데이터(structured data)** 가 나오게 하는 것입니다.

```
[비구조화 입력]                  [LLM 추출]              [구조화 출력]
"안녕하세요, 귀하의 화물은   →   Claude + 스키마   →   {"ship_date": "03/14/2026",
 03/14/2026에 발송되었습니다"                            "carrier": "FedEx"}
```

### 전형적인 파이프라인 단계

실무에서 쓰는 추출 파이프라인은 보통 이렇게 생겼습니다.

1. **수집(Ingestion)** — 이메일/파일/티켓이 들어옴
2. **추출(Extraction)** — LLM이 스키마에 맞춰 필드를 뽑아냄
3. **검증(Validation)** — 결과가 스키마를 만족하는지 프로그램이 확인
4. **정규화(Normalization)** — 형식을 통일 (날짜, 통화, 단위 등)
5. **저장(Storage)** — 데이터베이스에 기록
6. **모니터링/피드백(Monitoring & Feedback)** — 잘 되고 있는지 지표로 추적

이 노트에서 다루는 개념들은 대부분 이 6단계 어딘가에 속합니다.

## 1. 스키마(Schema)와 구조화된 출력

### 1.1 JSON Schema란 무엇인가

**JSON Schema**는 "이 JSON은 이렇게 생겨야 한다"를 기계가 읽을 수 있게 적어둔 명세서입니다. 어떤 필드가 있어야 하는지, 각 필드의 타입은 무엇인지, 값의 제약은 무엇인지를 정의합니다.

```json
{
  "type": "object",
  "properties": {
    "ship_date": {
      "type": "string",
      "description": "운송업체가 명시한 발송일 문자열"
    },
    "carrier": { "type": "string" }
  },
  "required": ["carrier"]
}
```

주요 키워드:

| 키워드 | 뜻 |
|---|---|
| `type` | 값의 타입 (`string`, `number`, `integer`, `boolean`, `object`, `array`, `null`) |
| `properties` | 객체가 가질 수 있는 필드들의 정의 |
| `required` | 반드시 있어야 하는 필드 이름 목록 |
| `description` | 사람과 모델이 읽는 설명문. LLM에게는 사실상 "필드별 미니 프롬프트" 역할 |
| `enum` | 허용되는 값의 목록을 한정 (예: `["stated", "estimated", "unknown"]`) |
| `pattern` | 문자열이 만족해야 할 정규표현식 |
| `format` | 의미적 형식 힌트 (예: `date`, `email`) |

### 1.2 스키마 검증(Schema Validation)과 검증 실패

**검증기(Validator)** 는 LLM이 뱉은 JSON을 스키마와 대조해서 통과/실패를 판정하는 프로그램입니다. Python이면 `jsonschema`, `pydantic` 같은 라이브러리를 씁니다.

검증에 실패하면 그 응답은 파이프라인에서 거부됩니다. 즉 **아무리 모델이 올바른 정보를 읽어냈어도, 형식이 스키마와 안 맞으면 그 추출은 실패로 처리됩니다.** 이것이 이후 여러 개념의 출발점입니다.

```python
from jsonschema import validate, ValidationError

try:
    validate(instance=model_output, schema=SHIPMENT_SCHEMA)
except ValidationError as e:
    print("검증 실패:", e.message)   # 예: "'14-Mar-2026' does not match '^\\d{4}-\\d{2}-\\d{2}$'"
```

### 1.3 엄격한 패턴 제약이 만드는 문제

스키마에 `pattern`으로 강한 정규표현식을 걸면 직관적으로는 "안전해 보입니다". 그러나 **원본 데이터의 형식이 제각각일 때는 오히려 실패율을 폭증시킵니다.**

예: 물류 회사가 여러 운송업체로부터 배송 확인 이메일을 받는데, 날짜가 이렇게 옵니다.

- `03/14/2026` (미국식 MM/DD/YYYY)
- `14-Mar-2026` (유럽식 + 월 이름)
- `2026.03.14` (점 구분 ISO 유사형)

스키마가 `ship_date`에 대해 ISO 8601(`YYYY-MM-DD`) 정규표현식을 강제하면, 모델이 원본을 정확히 읽어냈더라도 형식이 안 맞아 계속 검증 실패가 납니다.

### 1.4 핵심 설계 원칙: 추출과 정규화의 역할 분리

**모범 사례는 "LLM에게는 느슨하게 뽑게 하고, 형식 통일은 결정론적 코드가 한다"입니다.**

- **추출 단계**: 스키마 제약을 `type: "string"` 수준으로 **완화(loosen)** 합니다. 모델은 원본에 있는 그대로 안정적으로 뽑아냅니다.
- **후속 처리(Downstream Processing) 단계**: 애플리케이션 코드에 있는 **날짜 파서(date parser)** 로 ISO 8601로 **정규화(normalization)** 한 뒤 DB에 저장합니다.

```python
from dateutil import parser  # 결정론적 date parser

raw = extracted["ship_date"]          # "14-Mar-2026" 같은 원본 문자열
iso  = parser.parse(raw).date().isoformat()   # "2026-03-14"
db.insert(ship_date=iso)
```

왜 이게 더 나은가:

- **결정론적(deterministic)**: 날짜 파서는 같은 입력에 항상 같은 출력을 냅니다. LLM은 확률적(probabilistic)이라 매번 같으리란 보장이 없습니다.
- **실패 지점 축소**: LLM은 "읽기"만 담당하고, "형식 맞추기"라는 별개의 부담을 지지 않습니다.
- **유지보수**: 새 날짜 형식이 등장해도 파서 라이브러리가 대부분 흡수하며, 스키마는 손댈 필요가 없습니다.

### 1.5 하지 말아야 할 스키마 설계

같은 문제에 대해 흔히 떠올리지만 나쁜 해법들:

- **필드를 아예 제거하고 나중에 추론하기** — 핵심 정보를 버리고, 운송장 번호 조회 같은 외부 API 호출로 복원하려는 것은 불필요한 복잡도와 비용을 만듭니다.
- **엄격한 제약은 그대로 두고 `description`으로만 지시하기** — 모델에게 "ISO로 바꿔서 넣어줘"라고 설명을 달아도, 모델은 확률적이라 가끔 어긋납니다. 그때마다 검증기가 거부하므로 오류가 계속됩니다. `description`은 유용하지만 **검증기의 판정을 대신해 주지는 않습니다.**
- **형식마다 필드를 쪼개기** (`ship_date_us`, `ship_date_eu`, `ship_date_iso`) — 스키마가 불필요하게 복잡해지고, 새 형식이 나올 때마다 스키마를 고쳐야 해서 유지보수성이 급락합니다.

## 2. 스키마 설계와 환각(Hallucination) 방지

### 2.1 환각이란

**환각(Hallucination)** 은 모델이 근거 없는 정보를 그럴듯하게 만들어내는 현상입니다. 정보 추출에서는 "원본에 없는 값을 지어내는 것"으로 나타납니다.

### 2.2 required + number 조합이 환각을 유발하는 메커니즘

부동산 매물 추출 시나리오를 봅시다. 스키마가 이렇게 되어 있습니다.

```json
{
  "properties": { "square_footage": { "type": "number" } },
  "required": ["square_footage"]
}
```

그런데 오래된 매물 글에는 면적 숫자가 없고 "spacious with room to grow(널찍하고 여유 있음)" 같은 서술만 있습니다.

이때 모델은 딜레마에 빠집니다. 필드는 **필수(required)** 이고 타입은 **숫자(number)** 인데, 원본에는 숫자가 없습니다. 스키마를 만족시키려면 무언가 숫자를 넣어야 하고, 결국 **그럴듯한 값을 지어냅니다.** 즉, **과도하게 엄격한 스키마가 모델에게 환각을 강요하는 구조**입니다.

### 2.3 해법 1 — 필드를 선택적(optional)으로

`required` 목록에서 빼거나 `null`을 허용하면, 모델은 "값이 없음"을 정직하게 표현할 수 있습니다. 지어낼 이유가 사라집니다.

```json
{
  "properties": {
    "square_footage": { "type": ["number", "null"] }
  },
  "required": []
}
```

### 2.4 해법 2 — 출처/신뢰도 메타데이터 필드 추가

값이 비었을 때 "왜 비었는지"를 구별하지 못하면 다운스트림 리포트가 곤란해집니다. 그래서 **`enum` 타입의 출처(source) 필드**를 함께 둡니다.

```json
{
  "properties": {
    "square_footage": { "type": ["number", "null"] },
    "square_footage_source": {
      "type": "string",
      "enum": ["stated", "estimated", "unknown"],
      "description": "stated=원문에 명시됨, estimated=문맥에서 추정, unknown=정보 없음"
    }
  }
}
```

이렇게 하면 리포트에서 **확인된 값(stated)** 과 **부재/추정 값** 을 명확히 분리해 집계할 수 있습니다. 두 변경(optional 전환 + source enum 추가)이 **함께** 작동해야 환각도 막고 데이터 품질도 지킵니다.

### 2.5 흔한 오답 패턴과 이유

- **숫자 필드를 문자열로 바꾸고 "N/A" 넣기** — 필드는 항상 채워지지만, 다운스트림에서 평균/합계 같은 수치 연산을 할 때 타입 오류가 납니다. 데이터 품질이 오히려 나빠집니다.
- **`number` 필수 필드에 "N/A"를 출력하라고 시스템 프롬프트로 지시** — 스키마 타입 검증에서 즉시 실패합니다. 프롬프트 지시는 스키마 타입을 이길 수 없습니다.
- **필드를 빼고 정규표현식 스크립트로 대체** — 모호한 서술문("널찍한")의 문맥을 정규표현식이 이해할 리 없으며, LLM 추출의 장점을 통째로 버리는 선택입니다.

**일반 원칙**: 스키마는 "원본 현실"을 표현할 수 있어야 합니다. 원본에 없을 수 있는 값이라면, 스키마에 "없음"을 표현할 자리를 만들어 주어야 합니다.

## 3. 오류 복구 패턴: 재시도 vs 에스컬레이션

### 3.1 오류의 두 종류

검증 실패를 만났을 때, 먼저 **어떤 종류의 오류인지 분류**하는 것이 대응 전략을 결정합니다.

| 종류 | 정의 | 예시 | 대응 |
|---|---|---|---|
| **형식 오류 (Formatting Error)** | 값 자체는 맞는데 표기 방식만 스키마와 다름 | 스키마는 `YYYY-MM-DD`인데 `14/03/2026`이 나옴 | 교정 재시도 |
| **의미 오류 (Semantic Error)** | 값 자체가 틀림. 잘못 읽었거나 계산이 틀림 | 총액이 항목 합계와 안 맞음 | 교차 검증, 필요시 사람 개입 |

### 3.2 피드백 기반 교정 재시도 (Corrective Retry / Self-Correction via Feedback)

형식 오류는 **가장 값싸게 고칠 수 있는 오류**입니다. 검증기가 낸 에러 메시지를 그대로 모델에게 되돌려주고 다시 요청하면 됩니다.

```python
try:
    validate(result, schema)
except ValidationError as e:
    messages.append({"role": "assistant", "content": raw_response})
    messages.append({"role": "user",
        "content": f"출력이 스키마 검증에 실패했습니다: {e.message}. "
                   f"start_date는 반드시 YYYY-MM-DD 형식이어야 합니다. 수정해서 다시 출력하세요."})
    result = call_claude(messages)   # 교정 재시도
```

핵심은 **에러 메시지에 "무엇이 왜 틀렸고 무엇을 원하는지"를 명시**하는 것입니다. 단순히 "다시 해봐"가 아니라 "형식은 `YYYY-MM-DD`여야 합니다"라고 요구 형식을 이름 붙여 알려줘야 모델이 정확히 고칩니다.

### 3.3 대응 사다리

비용이 낮은 순서로 시도합니다.

1. **피드백을 붙인 자동 재시도** — 형식 오류의 표준 해법
2. **스키마/프롬프트 조정** — 같은 오류가 반복되면 설계 문제
3. **사람 검토로 에스컬레이션(Human-in-the-loop)** — 자동 복구가 실패했거나 의미 오류일 때만

단순 형식 오류를 곧바로 사람에게 넘기는 것은 인적 자원 낭비이고, 반대로 구조화 추출 자체를 포기하고 자유 텍스트로 저장하는 것은 파이프라인 설계를 무너뜨립니다.

## 4. Claude API의 도구 사용(Tool Use)과 `tool_choice`

### 4.1 Tool Use란

**도구 사용(Tool Use / Function Calling)** 은 개발자가 "이런 이름과 입력 스키마를 가진 함수가 있다"고 모델에게 알려주고, 모델이 그 함수를 호출하는 형태로 응답하게 하는 기능입니다.

구조화된 출력을 얻는 표준 방법이기도 합니다. "이 스키마대로 JSON을 뽑아라"를 도구 하나로 표현하면, API가 스키마 준수를 훨씬 강하게 뒷받침합니다.

```python
tools = [
    {
        "name": "extract_invoice",
        "description": "송장에서 구조화된 필드를 추출합니다.",
        "input_schema": {
            "type": "object",
            "properties": {
                "invoice_number": {"type": "string"},
                "total_amount":   {"type": "number"},
            },
            "required": ["invoice_number"]
        }
    },
    # extract_resume, extract_contract ...
]
```

모델이 도구를 호출하면 응답에 `tool_use` 블록이 담기고, 그 안의 `input`이 곧 스키마를 만족하는 구조화 데이터입니다.

### 4.2 `tool_choice` 파라미터 — 네 가지 값

`tool_choice`는 "모델이 도구를 쓸지 말지, 쓴다면 어느 것을 쓸지"를 개발자가 통제하는 파라미터입니다. **시험에서든 실무에서든 이 네 가지 구분이 핵심입니다.**

| 값 | 동작 | 언제 쓰나 |
|---|---|---|
| `{"type": "auto"}` | **기본값.** 모델이 도구를 호출할지, 일반 텍스트로 답할지 스스로 결정 | 대화형 에이전트처럼 도구가 항상 필요하진 않은 경우 |
| `{"type": "any"}` | **등록된 도구 중 하나를 반드시 호출.** 어느 것을 고를지는 모델이 판단 | 여러 후보 중 모델이 분류해서 골라야 하고, 텍스트 응답으로 새는 것은 막아야 할 때 |
| `{"type": "tool", "name": "X"}` | **지정한 도구 X를 반드시 호출** | 쓸 도구가 하나로 확정되어 있을 때 |
| `{"type": "none"}` | 도구를 전혀 호출하지 않음 | 도구를 잠시 끄고 싶을 때 |

### 4.3 `any`의 쓸모: 모델을 라우터로 쓰기

문서 처리 서비스가 들어오는 파일이 송장/이력서/계약서 중 무엇인지 **사전에 모릅니다.** 요구사항은 두 가지입니다.

1. 반드시 셋 중 하나의 추출 도구가 실행되어야 한다 (일반 텍스트로 새면 안 됨)
2. 어느 도구인지는 문서 내용에 따라 달라야 한다

이 두 요구를 동시에 만족시키는 것이 정확히 `{"type": "any"}`입니다. 세 도구를 모두 `tools`에 등록하고 `any`로 강제하면, 모델이 문서를 읽고 적합한 도구를 스스로 고르되 반드시 하나는 호출합니다.

```python
response = client.messages.create(
    model="claude-sonnet-4-5",
    tools=[extract_invoice, extract_resume, extract_contract],
    tool_choice={"type": "any"},     # 셋 중 반드시 하나
    messages=[{"role": "user", "content": document_text}],
)
```

### 4.4 안티패턴: 외부 정규표현식 라우팅

지원 자동화 플랫폼이 티켓을 `bug_report` / `feature_request` / `billing_issue`로 분류해야 합니다. 흔한 초기 설계는 이렇습니다.

```
티켓 텍스트 → 정규표현식 키워드 매칭 → 분류 결정 → tool_choice: {"type":"tool", "name": 그 도구}
```

문제는 **정규표현식이 자연어 의미를 이해하지 못한다**는 것입니다. "결제가 안 되는 버그"처럼 키워드가 섞이면 오분류하고, 오분류된 채로 특정 도구가 강제되므로 잘못된 도구가 실행됩니다.

**더 나은 아키텍처**: 세 도구를 모두 한 요청에 등록하고 `tool_choice: {"type": "any"}`로 두어, 분류 판단 자체를 모델의 자연어 이해에 맡깁니다. 정규표현식 계층이 통째로 사라지고, 도구 실행 보장은 그대로 유지됩니다.

주의할 대안들:

- **`{"type": "auto"}`** — 모호한 티켓에서 모델이 도구를 건너뛰고 텍스트로 답할 수 있습니다. "항상 추출이 일어나야 하는" 파이프라인에는 부적합합니다.
- **도구별로 3번 병렬 호출 후 성공한 것만 취하기** — 토큰 비용과 컴퓨팅이 3배가 됩니다.
- **`tools` 파라미터를 아예 빼고 프롬프트로만 JSON을 요구** — 도구 호출 기능의 형식 보장을 포기하는 것이며, 프롬프트 지시만으로는 형식 준수를 보장할 수 없습니다.

### 4.5 강제 도구 사용의 트레이드오프: 사전 자연어 텍스트 억제

이력서 파싱 팀이 두 가지를 원한다고 합시다.

1. 이번 턴에 반드시 `parse_resume`가 호출될 것
2. 모호한 이력서 구간에 대한 자연어 설명도 도구 호출 **이전에** 함께 받을 것

특정 도구를 확실히 강제하는 문서화된 방법은 `tool_choice: {"type": "tool", "name": "parse_resume"}`입니다. 다만 **트레이드오프가 있습니다: 도구 사용이 강제되면 도구 호출 앞에 붙는 자연어 텍스트 생성이 억제(suppress)됩니다.** 즉 1번은 보장되지만 2번은 그 설정만으로는 얻을 수 없습니다.

이 사실이 실무에서 갖는 함의:

- 모델의 사고 과정을 텍스트로 보고 싶다면, 그 정보를 **도구 입력 스키마 안의 필드**로 만드는 편이 낫습니다. 예: `ambiguity_notes`, `reasoning` 같은 문자열 필드를 스키마에 추가.
- `{"type": "none"}`은 도구를 아예 호출하지 않으므로, "호출을 보장한다"는 요구와 정반대입니다.
- `{"type": "auto"}` + 프롬프트 지시는 호출을 **보장**하지 못합니다.
- `{"type": "any"}`가 강제 호출과 자연어 해설을 자유롭게 섞게 해준다는 것도 사실이 아닙니다. `any` 역시 강제 도구 사용에 해당합니다.

## 5. 프롬프트 엔지니어링 기법

### 5.1 명확성과 구체성 (Clarity and Specificity)

프롬프트 엔지니어링의 1원칙은 **모호함을 제거하는 것**입니다. 모델은 지시가 모호할수록 자기 판단 폭을 넓게 가져가고, 그 결과 출력이 흔들립니다.

두 프롬프트를 비교해 봅시다.

- **프롬프트 X**: "보안 위험처럼 보이는(looks like) 것은 무엇이든 표시하라."
- **프롬프트 Y**: "사용자 입력을 매개변수화 없이 SQL 쿼리 문자열에 직접 쓰는 코드, 또는 평문 비밀번호를 저장하는 코드를 표시하라."

**오탐(False Positive)을 줄인다는 관점에서는 Y가 명백히 우월합니다.** Y는 **구체적이고 검증 가능한 조건(specific, checkable conditions)** 을 이름 붙여 정의했기 때문에, 모델이 "이 코드가 그 조건에 해당하는가?"라는 판정 가능한 질문으로 환원할 수 있습니다. X는 "위험해 보인다"는 열린 주관적 판단이라, 조금이라도 미심쩍은 평범한 코드까지 전부 걸려 오탐이 쏟아집니다.

트레이드오프도 알아둡시다. 구체적인 목록은 목록 밖의 위험을 놓칠 가능성(**미탐, False Negative**)을 갖습니다. 그래서 **어떤 지표를 개선하려는지에 따라 평가가 달라집니다.** 오탐 감소가 목표라면 구체성이 답입니다.

### 5.2 정밀도(Precision), 오탐, 미탐

탐지 시스템을 평가하는 기본 용어입니다.

- **True Positive (TP)**: 진짜 문제를 문제라고 맞게 표시
- **False Positive (FP, 오탐/거짓 양성)**: 문제가 아닌데 문제라고 표시
- **False Negative (FN, 미탐/거짓 음성)**: 진짜 문제인데 놓침
- **정밀도(Precision)** = TP / (TP + FP) — "표시한 것 중 진짜 문제의 비율"
- **재현율(Recall)** = TP / (TP + FN) — "진짜 문제 중 잡아낸 비율"

오탐이 많으면 정밀도가 떨어지고, 사용자가 알림을 무시하기 시작합니다.

### 5.3 퓨샷 프롬프팅 (Few-Shot Prompting / In-Context Learning)

**퓨샷 프롬프팅**은 프롬프트 안에 **입력-출력 예시 몇 개**를 직접 넣어, 모델이 그 패턴을 보고 따라 하게 만드는 기법입니다. 예시 0개면 제로샷(zero-shot), 몇 개면 퓨샷입니다. 모델 가중치를 바꾸는 학습이 아니라 문맥만으로 일어나므로 **인컨텍스트 러닝(In-Context Learning)** 이라 부릅니다.

**퓨샷이 서술형 지시보다 강한 두 가지 상황:**

#### (1) 미묘한 경계 사례의 판단 기준을 정할 때

PR 리뷰 에이전트가 "테스트 커버리지가 없는 분기"를 표시해야 하는데, **기존 통합 테스트가 간접적으로 커버하는 새 분기**까지 일관성 없이 표시해서 오탐이 쏟아집니다. "커버리지"에 대한 서술형 설명을 아무리 상세히 써도 해결되지 않습니다.

이유는, "간접적으로 커버됨"과 "커버 안 됨"의 경계가 **말로 정의하기 어려운 개념**이기 때문입니다. 이럴 때는 **diff와 그에 대한 올바른 커버리지 판정을 짝지은 예시 두어 개** — 테스트가 전혀 없는 분기 하나, 간접적으로 커버되는 분기 하나 — 를 넣어주는 것이 가장 효과적입니다. 모델은 설명보다 실제 사례에서 경계를 훨씬 정확히 잡아냅니다.

#### (2) 출력 형식의 일관성을 강제할 때

코드 리뷰 어시스턴트가 이미 **철저하고 항목화된 루브릭(exhaustive, itemized rubric)** 을 갖고 있는데도, 실행할 때마다 출력이 흔들립니다. 어떤 실행은 심각도를 위치보다 먼저 쓰고, 어떤 실행은 제안 수정을 아예 빠뜨립니다.

여기서 중요한 통찰: **지시문을 더 길게, 더 자세히 쓰는 것은 이 문제를 풀지 못합니다.** 이미 상세한 루브릭이 있는데 더 늘리면 컨텍스트만 커지고 지시 준수율은 오히려 떨어질 수 있습니다.

가장 효과적인 해법은 **원하는 필드 순서와 서식이 정확히 반영된 완성 예시(worked examples) 3~5개를 예시 태그 안에 넣는 것**입니다. 모델은 서술적 규칙보다 예시의 구조적 패턴을 훨씬 안정적으로 재현합니다.

```xml
<examples>
  <example>
    <input>if (user.isAdmin) { deleteAll(); }  // 새 분기, 테스트 없음</input>
    <output>
      location: src/admin.js:42
      severity: high
      finding: 관리자 삭제 분기에 테스트가 없습니다
      suggested_fix: isAdmin=true 경로에 대한 단위 테스트를 추가하세요
    </output>
  </example>
  <example>
    ... (형식이 완전히 동일한 두 번째, 세 번째 예시)
  </example>
</examples>
```

### 5.4 XML 태그로 프롬프트 구조화

Claude는 `<example>`, `<examples>`, `<document>`, `<instructions>` 같은 **XML 태그로 프롬프트의 구획을 나눠주면 지시를 더 정확히 따릅니다.** 예시와 지시문과 입력 데이터가 뒤섞인 평문보다, 태그로 명확히 구분된 프롬프트가 훨씬 안정적입니다.

### 5.5 형식 일관성 문제에 대한 다른 접근들과 그 한계

- **2단계 호출로 분리** (1차: 발견 생성, 2차: 형식 재정렬) — 동작은 하지만 단순 형식 고정을 위해 API 호출과 지연 시간을 2배로 만드는 과잉 설계입니다.
- **`temperature`를 0으로 낮추기** — `temperature`는 토큰 샘플링의 무작위성을 조절하는 파라미터입니다. 0에 가까울수록 결정론적으로 동작하지만, **입력(리뷰할 코드)이 매번 달라지면 출력 형식도 여전히 흔들릴 수 있습니다.** 재현성에는 도움이 되지만 형식 준수의 근본 해법은 아닙니다.

## 6. Message Batches API — 비동기 대량 처리

### 6.1 Batches API란

**Message Batches API**는 다수의 요청을 하나의 배치(batch)로 묶어 **비동기(asynchronous)** 로 처리하는 API입니다. 요청을 제출하면 즉시 결과가 오는 것이 아니라, 처리 후 나중에 결과를 가져옵니다.

**핵심 특성:**

- **비용이 약 50% 저렴합니다.** 즉시성을 포기하는 대가로 할인을 받는 구조입니다.
- **처리 창(processing window)은 최대 24시간입니다.** 대부분의 배치는 훨씬 빨리(종종 1시간 이내) 끝나지만, **공식적으로 보장되는 것은 "24시간 이내"뿐입니다.**
- 결과 조회는 API를 통한 **자동화된 폴링(polling)** 으로 완전히 가능합니다. 콘솔에서 수동으로 꺼내야 하는 것이 아닙니다.

**언제 쓰나**: 야간 요약 작업, 대량 문서 분류, 백필(backfill), 평가 데이터셋 실행처럼 **즉시 응답이 필요 없는 대량 작업**.

### 6.2 SLA와 지연 시간 보장의 부재

**SLA(Service Level Agreement, 서비스 수준 협약)** 는 "우리 서비스는 이 정도 수준을 지킵니다"라는 약속입니다.

**Batches API는 짧은 완료 시간에 대한 지연 시간(latency) SLA를 제공하지 않습니다.** 이것이 실무 설계에 미치는 영향은 큽니다.

전형적인 실수: 운영 리드가 "대부분의 배치가 1시간 안에 끝난다"는 **관측 데이터**를 근거로 고객에게 "야간 요약은 90분 이내 완료"라는 **고정 약속**을 하자고 제안합니다.

이에 대한 가장 강력한 기술적 반박은 이것입니다. **관측된 평균은 보장이 아닙니다.** Batches API에는 지연 시간 SLA가 없으므로, 수요가 몰리는 상황에서 배치가 최대 24시간까지 걸리는 것은 **장애가 아니라 사양대로의 정상 동작(legitimate behavior)** 입니다. 그런 상황에서 90분 약속은 필연적으로 깨집니다.

즉, **고객에게 하는 약속은 관측된 중앙값이 아니라 공식적으로 보장된 상한선 위에 세워야 합니다.**

### 6.3 배치 파이프라인 SLA 계산 공식

배치 기반 파이프라인에서 **최악의 경우(worst case)** 총 소요 시간은 두 부분의 합입니다.

```
최악 총 소요 시간 = 배치 제출 주기(T)  +  배치 최대 처리 시간(24시간)
                    └ 누적/수집 지연        └ 처리 창
                      (Accumulation Delay)   (Processing Window)
```

**왜 제출 주기가 통째로 더해지는가**: 어떤 항목이 **직전 배치가 제출된 직후에 도착**하면, 다음 배치 제출까지 최대 주기 T만큼 기다려야 합니다. 그 후에야 처리가 시작되고, 처리는 최대 24시간까지 걸릴 수 있습니다.

**계산 예시**: 법률 검토 파이프라인이 "모든 계약서는 도착 후 30시간 이내에 결과를 받는다"를 보장해야 합니다.

```
T + 24 ≤ 30
T ≤ 6
```

따라서 **최소 6시간마다 한 번은 새 배치 제출 주기를 시작해야 합니다.** 최악의 경우라도 6(대기) + 24(처리) = 30시간으로 SLA를 정확히 만족합니다.

다른 주기를 넣어보면 왜 안 되는지 바로 보입니다.

| 제출 주기 | 최악 총 시간 | 30시간 SLA |
|---|---|---|
| 6시간 | 6 + 24 = 30 | 만족 |
| 18시간 | 18 + 24 = 42 | 위반 |
| 24시간 | 24 + 24 = 48 | 위반 |
| 30시간 | 30 + 24 = 54 | 크게 위반 |

**흔한 오해들:**

- "배치 처리 창이 24시간이니 24시간마다 제출하면 된다" — 대기 시간을 빼먹은 계산입니다. 실제로는 48시간이 걸릴 수 있습니다.
- "제출 주기를 SLA 길이(30시간)에 맞추면 된다" — 처리 시간을 아예 무시한 계산입니다.
- "여유를 두려고 18시간으로" — 18시간은 6시간보다 **여유가 적은** 것이 아니라 아예 요구 조건을 위반합니다. 여기서 "여유"는 **주기를 짧게** 해야 생깁니다.

## 7. 에이전트 아키텍처와 서브에이전트 컨텍스트 격리

### 7.1 컨텍스트 창(Context Window)

**컨텍스트 창**은 모델이 한 번에 볼 수 있는 토큰의 총량입니다. 대화 기록, 시스템 프롬프트, 도구 호출과 그 결과, 읽어들인 파일 내용이 모두 여기에 쌓입니다. 유한한 자원이며, 길어질수록 비용이 오르고 **노이즈 때문에 모델 성능이 떨어질 수 있습니다.**

### 7.2 서브에이전트(Subagent)란

**서브에이전트**는 메인(부모) 에이전트가 특정 하위 작업을 위해 호출하는 별도의 에이전트입니다. 예: 코드를 생성한 뒤 `code-reviewer` 서브에이전트를 불러 검토를 시킴.

서브에이전트는 자체 정의를 가집니다 — 고유한 **시스템 프롬프트**, 사용 가능한 도구 목록 등.

### 7.3 컨텍스트 격리(Context Isolation) 원칙

**핵심 규칙: 서브에이전트는 자신만의 깨끗한 컨텍스트 창(clean context)에서 시작합니다.**

서브에이전트가 시작할 때 가지고 있는 것은 정확히 두 가지뿐입니다.

1. **서브에이전트 자신의 시스템 프롬프트**
2. **부모가 Agent 도구를 호출하며 전달한 프롬프트 문자열(prompt string)**

**자동으로 상속되지 않는 것들:**

- 부모의 대화 기록(conversation history)
- 부모의 추론 흔적(reasoning trace)
- 부모가 실행한 도구 호출과 그 결과 (읽어들인 파일 내용 포함)
- 부모의 컨텍스트 창 자체 (공유하지 않고 별도로 할당받음)

### 7.4 왜 이렇게 설계되었나

- **토큰 낭비 방지**: 부모의 긴 생성 과정 전부를 검토자에게 넘기면 비용이 폭증합니다.
- **노이즈 차단**: 검토자는 "코드가 어떻게 만들어졌는지"에 오염되지 않은 채 결과물만 보고 판단해야 더 객관적입니다.
- **부모 컨텍스트 보호**: 서브에이전트의 긴 탐색 과정이 부모 창을 채우지 않습니다.

### 7.5 실무적 함의

서브에이전트가 부모의 작업 결과를 볼 수 없다면, **부모가 명시적으로 전달해야 합니다.** 방법은 두 가지입니다.

- **프롬프트 문자열에 필요한 내용을 담아 전달** (파일 경로, 요약, 판단 기준 등)
- **서브에이전트가 스스로 도구를 써서 다시 읽게 하기** (예: 파일 경로만 알려주고 검토자가 직접 Read)

실무에서는 후자가 흔합니다. 부모가 "`src/auth.js`와 `tests/auth.test.js`를 읽고 검토하라"고 지시하면, 서브에이전트가 자기 컨텍스트에 필요한 것만 담습니다.

## 8. 모니터링, 피드백 루프, 사용자 신뢰

### 8.1 구조화된 필드가 모니터링을 가능하게 한다

출력을 구조화하는 이유는 저장 편의만이 아닙니다. **구조화된 필드는 곧 집계 가능한 지표(metric)** 가 됩니다.

예: 코드 리뷰 어시스턴트의 각 발견 사항에 `detected_pattern` 필드를 넣어두면, 나중에 **패턴 값별로** 통계를 낼 수 있습니다.

```sql
SELECT detected_pattern,
       COUNT(*) AS total,
       AVG(CASE WHEN status='dismissed' THEN 1.0 ELSE 0 END) AS dismissal_rate
FROM findings
GROUP BY detected_pattern;
```

`detected_pattern`이라는 필드가 없었다면 이런 분석 자체가 불가능합니다. **모니터링을 염두에 둔 스키마 설계**가 중요한 이유입니다.

### 8.2 피드백 루프(Feedback Loop)와 기각률(Dismissal Rate)

**기각률**은 사용자가 알림을 "이건 문제 아님"으로 닫아버린 비율입니다. **오탐의 실전 대리 지표(proxy)** 입니다.

몇 달 치 데이터를 모아보니 `detected_pattern`이 `"decorator-wrapped test fixture"` 인 발견 사항의 **90% 이상이 기각**된다는 사실이 드러났다고 합시다.

이 피드백 루프가 주는 **주된 가치는, 과도하게 트리거되는(over-triggering) 특정 패턴 하나를 정확히 집어내어(pinpoint), 그 구문에 한정해 탐지 규칙을 조정(tune)하거나 억제(suppress)할 수 있게 해주는 것**입니다.

즉 "이 도구는 별로다"라는 막연한 불만을 **"이 규칙의 이 케이스가 문제다"라는 실행 가능한 작업 항목**으로 바꿔줍니다.

**과잉 해석에 주의:**

- 특정 패턴 하나에 기각이 집중된 것은 "개발자들이 무작위로 기각한다"는 증거가 **아닙니다.** 리뷰 프로세스 전체를 중단할 근거가 되지 않습니다.
- 높은 기각률은 **판단 규칙의 도메인 적합성 문제**이지, JSON 스키마의 구문 결함(syntax defect)과는 무관합니다.
- 한 카테고리의 오탐을 발견했다고 해서 **모든** 카테고리의 향후 발견을 사람 검토 없이 자동 종결하는 것은 위험한 일반화입니다.

### 8.3 신뢰 훼손(Trust Erosion)과 알림 피로(Alert Fatigue)

기술적으로는 옳은데도 시스템이 실패하는 대표적 경로입니다.

시나리오: 코드 리뷰 어시스턴트가 보안(security), 정확성(correctness), 스타일(style) 세 카테고리로 결과를 냅니다.

- 보안: 정밀도 90% 이상
- 정확성: 정밀도 90% 이상
- 스타일: **오탐률 60%**

그런데 개발자들이 **보안 알림까지 포함해 도구의 모든 결과를 불신**하기 시작했습니다.

**설명**: 사용자는 출력을 카테고리별로 나눠서 인식하지 않습니다. **모든 결과가 "같은 하나의 AI 리뷰어"라는 미분화된 단일 출처(single undifferentiated source)에서 나온 것으로 체감합니다.** 그래서 **오탐률이 높은 단 하나의 카테고리가 정확한 나머지 카테고리에 대한 신뢰까지 잠식합니다.**

**설계적 교훈:**

- 카테고리별 정밀도 지표가 좋아도, **가장 나쁜 카테고리가 전체 신뢰도를 결정**합니다.
- 정밀도가 낮은 카테고리는 **차라리 끄거나, 분리된 채널로 내보내거나, 임계값을 올리는** 편이 낫습니다.
- 이는 통계 계산 오류나 "보안 이슈가 검증하기 어려워서" 생기는 문제가 아니라, **사용자 경험 차원의 심리 현상**입니다.

## 9. 전체를 관통하는 설계 원칙 정리

1. **스키마는 원본 현실을 표현할 수 있어야 한다.** 없을 수 있는 값에는 "없음"의 자리를 만든다. 과도한 엄격함은 검증 실패나 환각을 부른다.
2. **LLM에게는 이해를, 결정론적 코드에게는 형식을.** 추출은 느슨하게, 정규화는 파서로.
3. **`description`은 지침이고, 검증기는 판정자다.** 설명을 잘 쓴다고 검증 실패가 사라지지 않는다.
4. **형식 오류는 피드백을 붙여 재시도하고, 의미 오류에만 사람을 부른다.**
5. **도구 호출을 보장해야 하면 `any` 또는 특정 도구 강제를 쓰고, `auto`는 텍스트로 샐 수 있음을 기억한다.** 강제 호출은 사전 자연어 텍스트를 억제한다.
6. **분류는 정규표현식이 아니라 모델의 이해에 맡길 수 있다.**
7. **모호한 판단 기준은 예시로, 흔들리는 출력 형식도 예시로.** 지시문을 늘리는 것은 대부분 답이 아니다.
8. **약속은 관측된 평균이 아니라 보장된 상한선 위에 세운다.** 배치 SLA = 제출 주기 + 최대 처리 시간.
9. **서브에이전트는 깨끗한 컨텍스트에서 시작한다.** 필요한 것은 명시적으로 전달하거나 스스로 읽게 한다.
10. **모니터링을 염두에 두고 스키마를 설계하고, 지표로 규칙을 튜닝한다.**
11. **가장 시끄러운 카테고리가 전체 신뢰도를 결정한다.**

## 10. 용어 사전 (Glossary)

### 스키마 및 데이터

| 용어 | 설명 |
|---|---|
| **Unstructured Data** | 비구조화 데이터. 이메일, PDF, 자유 텍스트처럼 정해진 필드 구조가 없는 데이터 |
| **Structured Data** | 구조화 데이터. 정해진 필드와 타입을 가진 JSON/테이블 형태의 데이터 |
| **Information Extraction** | 정보 추출. 비구조화 텍스트에서 정해진 필드 값을 뽑아내는 작업 |
| **JSON Schema** | JSON의 구조·타입·제약을 기계가 읽을 수 있게 기술한 명세 |
| **Schema Validation** | 스키마 검증. 출력이 스키마를 만족하는지 프로그램이 판정하는 단계 |
| **Validator** | 검증기. `jsonschema`, `pydantic` 같은 검증 수행 라이브러리/코드 |
| **Validation Failure** | 검증 실패. 스키마를 만족하지 못해 출력이 거부되는 것 |
| **required** | 반드시 존재해야 하는 필드를 지정하는 JSON Schema 키워드 |
| **optional** | 선택적 필드. `required`에 없거나 `null`을 허용하는 필드 |
| **enum** | 허용 값을 정해진 목록으로 한정하는 키워드 (예: `stated`/`estimated`/`unknown`) |
| **pattern** | 문자열이 만족해야 할 정규표현식을 지정하는 키워드 |
| **description** | 필드 설명문. 모델에게는 필드별 지시문 역할을 하지만 검증기의 판정을 대체하지 못함 |
| **Type Validation Error** | 타입 검증 오류. `number` 필드에 `"N/A"` 문자열을 넣는 등 타입이 어긋날 때 발생 |
| **ISO 8601** | 국제 표준 날짜/시간 표기법. 날짜는 `YYYY-MM-DD` (예: `2026-03-14`) |
| **Normalization** | 정규화. 제각각인 표기를 하나의 표준 형식으로 통일하는 것 |
| **Date Parser** | 날짜 파서. `14-Mar-2026` 같은 다양한 표기를 날짜 객체로 변환하는 라이브러리 (예: `dateutil`) |
| **Downstream Processing** | 후속 처리. 추출 이후 단계(정규화, 저장, 리포팅)의 애플리케이션 코드 |
| **Deterministic** | 결정론적. 같은 입력에 항상 같은 출력. 파서/정규표현식이 여기 해당 |
| **Probabilistic** | 확률적. LLM처럼 같은 입력에도 출력이 달라질 수 있는 성질 |
| **Placeholder** | 자리표시자. 값이 없을 때 채우는 `"N/A"`, `"unspecified"` 같은 임시 값 |
| **Metadata Field** | 메타데이터 필드. 값 자체가 아니라 값의 출처·신뢰도를 기술하는 부가 필드 |

### 오류와 복구

| 용어 | 설명 |
|---|---|
| **Hallucination** | 환각. 모델이 근거 없는 값을 그럴듯하게 지어내는 현상 |
| **Formatting Error** | 형식 오류. 값은 맞는데 표기 형식만 스키마와 다른 오류 |
| **Semantic Error** | 의미 오류. 값 자체가 틀린 오류. 교차 검증이 필요 |
| **Corrective Retry** | 교정 재시도. 오류 내용을 알려주고 다시 요청하는 복구 방식 |
| **Self-Correction via Feedback** | 피드백 기반 자가 교정. 검증기 에러 메시지를 모델에게 되돌려 고치게 하는 패턴 |
| **Escalation** | 에스컬레이션. 자동 복구가 불가능할 때 상위 처리(사람)로 넘기는 것 |
| **Human-in-the-loop** | 사람이 개입해 검토·승인하는 단계를 파이프라인에 두는 설계 |

### Claude API / 도구 사용

| 용어 | 설명 |
|---|---|
| **Tool Use / Function Calling** | 도구 사용. 모델이 개발자가 정의한 함수를 호출하는 형태로 응답하게 하는 기능 |
| **tools** | API 요청에서 사용 가능한 도구 목록을 넘기는 파라미터 |
| **input_schema** | 도구가 받는 입력의 JSON Schema |
| **tool_choice** | 도구 사용 방식을 통제하는 파라미터 |
| **tool_choice: auto** | 기본값. 도구 호출과 텍스트 응답 중 모델이 스스로 선택 |
| **tool_choice: any** | 등록된 도구 중 반드시 하나를 호출. 어느 것인지는 모델이 판단 |
| **tool_choice: tool + name** | 지정한 특정 도구를 반드시 호출 |
| **tool_choice: none** | 도구를 전혀 호출하지 않음 |
| **Forced Tool Use** | 강제 도구 사용. `any` 또는 특정 도구 지정. 도구 호출 전 자연어 텍스트가 억제됨 |
| **Fallback to Plain Text** | 도구를 호출하지 않고 일반 텍스트로 응답해 버리는 것. `auto`에서 발생 가능 |
| **Routing** | 라우팅. 입력을 유형에 따라 알맞은 처리 경로/도구로 보내는 것 |
| **temperature** | 토큰 샘플링의 무작위성 조절 파라미터. 0에 가까울수록 결정론적 |

### 프롬프트 엔지니어링

| 용어 | 설명 |
|---|---|
| **Prompt Engineering** | 프롬프트 엔지니어링. 모델 입력을 설계해 원하는 동작을 끌어내는 기술 |
| **System Prompt** | 시스템 프롬프트. 모델의 역할·규칙을 정하는 최상위 지시문 |
| **Zero-Shot** | 예시 없이 지시문만으로 작업을 시키는 방식 |
| **Few-Shot Prompting** | 퓨샷 프롬프팅. 입력-출력 예시 몇 개를 프롬프트에 넣어 패턴을 따르게 하는 기법 |
| **In-Context Learning** | 인컨텍스트 러닝. 가중치 학습 없이 문맥 속 예시만으로 패턴을 습득하는 현상 |
| **Worked Example** | 완성 예시. 원하는 출력 형식이 완전히 구현된 본보기 |
| **XML Tags** | `<example>`, `<instructions>` 등으로 프롬프트 구획을 나누는 기법. Claude에 특히 효과적 |
| **Clarity and Specificity** | 명확성과 구체성. 모호한 표현 대신 검증 가능한 조건을 명시하는 원칙 |
| **Checkable Condition** | 검증 가능한 조건. "위험해 보이는" 대신 "매개변수화 없는 SQL 문자열 결합" 같은 판정 가능한 기준 |
| **Rubric** | 루브릭. 판단 기준을 항목화해 정리한 지침 |
| **Output Consistency** | 출력 일관성. 실행마다 필드 순서·구성이 동일하게 유지되는 성질 |
| **Over-engineering** | 과잉 설계. 단순 문제에 불필요하게 복잡한 해법(예: 형식 고정을 위한 2단계 API 호출)을 적용하는 것 |

### 평가 지표와 운영

| 용어 | 설명 |
|---|---|
| **True Positive (TP)** | 진짜 문제를 문제라고 맞게 표시한 경우 |
| **False Positive (FP)** | 오탐/거짓 양성. 문제가 아닌데 문제라고 표시한 경우 |
| **False Negative (FN)** | 미탐/거짓 음성. 진짜 문제인데 놓친 경우 |
| **Precision** | 정밀도 = TP/(TP+FP). 표시한 것 중 진짜 문제의 비율 |
| **Recall** | 재현율 = TP/(TP+FN). 진짜 문제 중 잡아낸 비율 |
| **False Positive Rate** | 오탐률. 알림 중 잘못된 알림의 비율 |
| **Over-triggering** | 과도한 트리거. 규칙이 필요 이상으로 자주 발동해 오탐을 양산하는 상태 |
| **Dismissal Rate** | 기각률. 사용자가 "문제 아님"으로 닫아버린 알림의 비율. 오탐의 실전 대리 지표 |
| **Feedback Loop** | 피드백 루프. 운영 결과를 지표로 모아 시스템을 개선하는 순환 구조 |
| **Suppression** | 억제. 특정 패턴/케이스에 대한 알림을 꺼서 노이즈를 줄이는 것 |
| **Tuning** | 튜닝. 탐지 규칙이나 프롬프트를 실제 데이터에 맞춰 조정하는 것 |
| **Alert Fatigue** | 알림 피로. 알림이 너무 많아 사용자가 전부 무시하게 되는 현상 |
| **Trust Erosion** | 신뢰 훼손. 한 부분의 낮은 품질이 시스템 전체에 대한 신뢰를 무너뜨리는 현상 |
| **Single Undifferentiated Source** | 미분화된 단일 출처. 사용자가 여러 카테고리 출력을 하나의 출처로 뭉뚱그려 인식하는 것 |

### 배치 처리와 SLA

| 용어 | 설명 |
|---|---|
| **Message Batches API** | 요청을 묶어 비동기로 처리하는 Anthropic API. 비용 약 50% 절감 |
| **Asynchronous** | 비동기. 요청 즉시 결과가 오지 않고 나중에 조회하는 방식 |
| **Processing Window** | 처리 창. 배치가 완료되기까지 허용되는 최대 시간. Batches API는 최대 24시간 |
| **Latency** | 지연 시간. 요청부터 결과까지 걸리는 시간 |
| **SLA (Service Level Agreement)** | 서비스 수준 협약. 제공자가 보장하는 성능/가용성 약속 |
| **Turnaround Time** | 처리 완료 시간. 작업 접수부터 결과 제공까지의 총 시간 |
| **Worst Case** | 최악의 경우. SLA 설계는 평균이 아니라 이 값을 기준으로 해야 함 |
| **Accumulation / Ingestion Delay** | 누적 지연. 항목이 도착해서 다음 배치에 실릴 때까지 기다리는 시간 |
| **Submission Cadence** | 제출 주기. 새 배치를 얼마나 자주 제출하는지의 간격 |
| **Polling** | 폴링. 주기적으로 API에 상태를 물어 완료 여부를 확인하는 방식 |
| **Rate Limit** | 요청량 제한. 일정 시간당 허용되는 요청 수의 상한 |
| **Throughput** | 처리량. 단위 시간당 처리할 수 있는 작업의 양 |

### 에이전트 아키텍처

| 용어 | 설명 |
|---|---|
| **Agent** | 에이전트. 목표를 받아 도구를 써가며 스스로 단계를 진행하는 LLM 시스템 |
| **Agentic Workflow** | 에이전트 워크플로. 여러 단계와 도구 사용이 이어지는 자동화 흐름 |
| **Subagent** | 서브에이전트. 부모 에이전트가 하위 작업을 위임하는 별도 에이전트 |
| **Parent Agent** | 부모/메인 에이전트. 서브에이전트를 호출하는 상위 에이전트 |
| **Context Window** | 컨텍스트 창. 모델이 한 번에 볼 수 있는 토큰 총량 |
| **Context Isolation** | 컨텍스트 격리. 서브에이전트가 부모와 분리된 자체 컨텍스트에서 시작하는 원칙 |
| **Clean Context** | 깨끗한 컨텍스트. 부모 이력이 섞이지 않은 새 컨텍스트 창 |
| **Conversation Transcript** | 대화 기록. 지금까지 오간 메시지 전체. 서브에이전트에 자동 상속되지 않음 |
| **Reasoning Trace** | 추론 흔적. 모델이 결론에 이르기까지의 사고 과정 기록 |
| **Tool Result** | 도구 실행 결과. 부모의 도구 결과는 서브에이전트에 자동 전달되지 않음 |
| **Prompt String** | 부모가 Agent 도구를 호출하며 서브에이전트에 넘기는 지시 문자열. 시스템 프롬프트와 함께 서브에이전트가 갖는 유일한 초기 컨텍스트 |
