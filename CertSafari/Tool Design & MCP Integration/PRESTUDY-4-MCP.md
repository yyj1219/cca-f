# 4. MCP (Model Context Protocol)

이 장에서 다루는 것:

- MCP란 무엇이고 왜 필요한가 (N×M → N+M)
- 서버·클라이언트 구조, 세 가지 원시 타입(Tools/Resources/Prompts), JSON-RPC, 전송 방식(stdio / HTTP·SSE)
- 도구 이름 네임스페이스와 예약된 내장 이름
- 설정 파일(`.mcp.json`)과 설정 범위(local / project / user / enterprise), 우선순위, 프로젝트 범위의 승인 대기
- 환경 변수 확장 `${VAR}` / `${VAR:-기본값}`과 주입 변수 `CLAUDE_PROJECT_DIR`
- 인증: `headers` / `oauth` / `headersHelper`, 시크릿을 커밋하지 않고 공유하기
- 여러 서버 동시 사용과 이름 충돌
- 도구 목록 동적 갱신 `notifications/tools/list_changed`
- Tool Search와 `alwaysLoad`
- 리소스 참조 `@서버:URI` 멘션
- 흔한 오해 정리

---

## 4.1 MCP란 무엇인가 — 왜 필요한가

**Model Context Protocol(MCP)** 은 AI 애플리케이션(호스트/클라이언트)과 외부 시스템(데이터베이스, SaaS API, 파일 시스템, 사내 서비스)을 연결하는 **개방형 표준 프로토콜**입니다. Anthropic이 공개했고 누구나 구현할 수 있습니다.

문제 배경은 조합 폭발입니다. 도구 통합을 애플리케이션마다 따로 구현하면 **N개 앱 × M개 서비스 = N×M 개의 커넥터**가 필요합니다. "Claude에 Postgres를 붙이는 코드", "Slack을 붙이는 코드"를 각 도구·각 클라이언트마다 새로 짜야 했습니다. MCP는 그 사이에 표준 규격을 하나 두어 이를 **N+M**으로 줄입니다.

흔히 **AI 애플리케이션의 USB-C 포트**에 비유합니다. 서버를 MCP 규격에 맞춰 한 번 만들면, MCP를 지원하는 어떤 클라이언트(Claude Code, Claude 데스크톱 앱 등)에서도 그대로 붙습니다.

### 구성 요소

- **MCP 서버(server)**: 특정 외부 시스템의 기능을 표준 형태의 도구/리소스/프롬프트로 노출하는 프로그램. 예: GitHub 서버(`create_issue`, `list_prs`), Postgres 서버, Sentry 서버, Notion 서버, 사내 코드 인덱스 서버. 로컬 프로세스일 수도, 원격 HTTP 엔드포인트일 수도 있습니다.
- **MCP 클라이언트(client)/호스트**: 서버에 연결해 도구 목록을 받아오고, 그 도구들을 모델에게 제시하며, 모델이 호출을 요청하면 서버로 중계하는 쪽. Claude Code가 여기에 해당합니다.

### 기존 서버를 쓸 것인가, 직접 만들 것인가 (build vs. adopt)

| 대상 시스템 | 판단 |
|---|---|
| Jira, GitHub, Slack, Google Drive, Postgres 등 **널리 쓰이는 표준 서비스** | 이미 커뮤니티/벤더가 만든 MCP 서버가 존재 → **채택(adopt)** |
| 사내 배포 파이프라인처럼 **외부에 동등물이 없는 고유 시스템** | 아무도 만들 수 없음 → **커스텀 서버 직접 구축** |

이유는 단순합니다. 외부 개발자는 여러분의 사내 파이프라인의 존재조차 모릅니다. 반대로 Jira 같은 공개 API는 이미 여러 곳에서 잘 만들어 두었고 유지보수도 계속됩니다. 개발 공수와 유지보수 부담을 **커스텀이 꼭 필요한 곳에만** 집중시키는 것이 합리적입니다.

흔한 오해 반박:

- "사내에서 만든 서버만 프로덕션 자격증명을 맡길 수 있다" — 틀립니다. 신뢰성은 자체 제작 여부가 아니라 **코드 검토·감사·평판·권한 범위 제한**으로 확보합니다. 서드파티 서버를 도입할 때는 **버전 고정**과 **최소 권한 토큰 발급**을 병행하면 됩니다.
- "서드파티 서버는 이미 내부 도구를 이해한다" — 명백히 틀립니다. 외부 서버가 사내 전용 파이프라인을 알 방법은 없습니다.

### MCP를 건너뛰고 Bash + curl로 하면 안 되나

가능은 하지만 권장되지 않습니다. 에이전트에게 임의의 셸 명령 권한을 주면:

- 어떤 작업이 허용되는지 **경계가 사라집니다** (임의 명령 실행 = 사실상 무제한 권한).
- 자격증명이 **명령줄·로그에 노출**되기 쉽습니다.
- 도구별 **스키마가 없어** 모델이 URL과 파라미터를 창작하게 되어 신뢰성이 떨어집니다.
- 재사용·감사·에러 처리가 매번 즉흥적입니다.

MCP 서버는 "허용된 동작 목록"을 **명시적 계약**으로 만들어 줍니다.

## 4.2 서버가 노출하는 세 가지 원시 타입 (Primitives)

| Primitive | 성격 | 누가 주도하는가 | 예 |
|---|---|---|---|
| **Tools** | 실행/행동. 동적 연산, 검색, 상태 변경 | **모델**이 호출 | `create_issue`, `search_issues`, `deploy_service`, `create_invoice` |
| **Resources** | 읽기 전용 컨텍스트 데이터/문서 | **애플리케이션**이 컨텍스트에 주입 | 이슈 요약 카탈로그, 인증 가이드 문서, 스키마 파일, 로그 |
| **Prompts** | 재사용 가능한 프롬프트 템플릿 | **사용자**가 선택 | "이 PR 리뷰해줘" 슬래시 명령 |

Tools는 "동사", Resources는 "명사"라고 기억하면 편합니다.

### Tool vs Resource — 이 구분이 왜 중요한가

전형적인 문제 상황:

> 에이전트가 큰 이슈 트래커를 다룰 때, "어떤 이슈들이 존재하는지" 파악하려고 탐색적 검색 도구를 계속 반복 호출한다. 토큰과 지연 시간이 낭비된다.

이건 **검색 성능 문제가 아니라 "무엇이 있는지 모른다"는 컨텍스트 부족 문제**입니다. 매번 도구로 물어보게 하는 대신 **이슈 요약 카탈로그를 MCP 리소스로 노출**하면, 에이전트는 처음부터(up front) 목록을 보고 시작할 수 있습니다. 탐색 호출이 통째로 사라집니다.

핵심 판단 기준:

- 에이전트가 반복적으로 "무엇이 있지?"를 묻고 있다 → **Resource**로 미리 제공하라.
- 에이전트가 "이걸 해줘 / 이 조건으로 계산해줘"를 하고 있다 → **Tool**이 맞다.

효과 없는 대안들:

| 시도 | 왜 안 되는가 |
|---|---|
| 검색 도구를 더 추가한다 | 여전히 "도구 호출로 탐색"하는 구조. 도구 개수만 늘어 라우팅 정확도까지 나빠짐 |
| 도구 호출 타임아웃을 늘린다 | 타임아웃은 한 호출이 얼마나 오래 기다릴 수 있는지일 뿐, 반환량이나 호출 횟수와 무관 |
| 전송 계층을 stdio → HTTP로 바꾼다 | 통신 방식 차이일 뿐. 반복 탐색 구조 자체는 그대로 |

### 도구 에러 반환

MCP 도구 결과는 **`isError`** 필드로 실패를 표시합니다. 구조화된 에러 설계는 이 `isError: true` 응답의 본문에 `errorCategory`, `isRetryable` 같은 필드를 실어 보내는 형태로 적용됩니다.

## 4.3 통신 방식: JSON-RPC와 전송 계층

### JSON-RPC 2.0

MCP는 **JSON-RPC 2.0** 메시지를 주고받습니다. 요청/응답 쌍과, 응답이 필요 없는 단방향 **알림(Notification)** 이 있습니다. 대표적인 메서드:

- `tools/list` — 서버가 제공하는 도구 목록을 달라는 요청
- `tools/call` — 특정 도구를 인자와 함께 실행해 달라는 요청
- `notifications/tools/list_changed` — 서버가 클라이언트에게 "내 도구 목록이 바뀌었다"고 알리는 알림

### 전송 방식 (transport)

- **stdio**: 클라이언트가 서버를 **자식 프로세스로 직접 실행(spawn)** 하고 표준 입출력으로 JSON-RPC를 주고받습니다. 로컬 개인 도구에 적합. 설정에는 실행 명령과 인자(`command`, `args`), 환경 변수(`env`)를 씁니다.
- **HTTP (Streamable HTTP / SSE)**: 네트워크 엔드포인트 **URL**로 원격 서버에 접속합니다. 팀 공용 서비스에 적합하고 여러 클라이언트가 공유할 수 있습니다. 인증 정보는 보통 HTTP **헤더**(`Authorization` 등)로 보냅니다.

전송 계층은 **어디서 어떻게 연결하느냐**의 문제이지, **에이전트의 행동 패턴**을 바꾸는 수단이 아닙니다.

## 4.4 도구 이름 네임스페이스와 예약된 내장 이름

여러 서버의 도구가 하나의 목록으로 합쳐지므로, 도구 이름은 **서버 이름으로 네임스페이싱**됩니다. 서버 이름이 곧 네임스페이스이기 때문에 **서버 이름이 겹치면 안 됩니다.**

호스트는 자체 기능을 위해 특정 MCP 서버 이름을 **예약**해 둘 수 있습니다. 예를 들어 `computer-use`는 화면 조작·GUI 제어를 위한 내장 식별자입니다.

커스텀 서버에 이런 예약 이름을 붙이면, 호스트는 이름 충돌과 **섀도잉(shadowing)** 을 막기 위해 **그 서버 등록을 거부하거나 건너뜁니다.** 해결책은 단순합니다. 겹치지 않는 다른 이름(`custom-computer-use`, `my-screenshot-tool` 등)을 고르면 됩니다.

일어나지 **않는** 일들:

- 서버는 로드되고 특정 도구만 몰래 제거되는 **부분 로드는 없습니다.**
- 커스텀 서버가 내장 서버를 **덮어써서 숨기는 것은 허용되지 않습니다.**
- 예약 이름 아래에 커스텀 도구와 내장 도구를 **병합해 주지도 않습니다.**
- 이름 충돌을 가정해 **숫자 접미사를 붙여 자동으로 개명**하는 동작 같은 것도 없습니다.

## 4.5 설정 파일과 설정 범위(Scope)

같은 MCP 서버라도 **어디에 등록하느냐**가 곧 **누가, 어디서 그 서버를 쓰게 되느냐**를 결정합니다.

### 네 가지 범위

| 범위 | 저장 위치 | 공유 대상 | 적용 프로젝트 |
|---|---|---|---|
| **local (로컬, 기본값)** | `~/.claude.json` 안의 **해당 프로젝트 경로 항목 아래** | 나만 (커밋 안 됨) | 그 프로젝트 하나만 |
| **project (프로젝트)** | 저장소 루트의 `.mcp.json` (버전 관리 대상) | **팀 전체** (git 커밋) | 그 저장소 |
| **user (사용자 전역)** | `~/.claude.json`의 사용자 전역 영역 | 나만 | 내 **모든** 프로젝트 |
| **enterprise (관리형)** | 조직이 배포하는 관리 설정 | 조직 전체 | 정책으로 강제 |

혼동 포인트:

- **Local과 User는 둘 다 `~/.claude.json`에 들어가서 헷갈립니다.** 차이는 "**프로젝트 경로에 묶여 있는가**"입니다. Local은 특정 프로젝트 디렉터리 항목 아래 저장되어 그 프로젝트에서만 보이고, User는 전역이라 모든 프로젝트에서 보입니다.
- **Project 범위만** 파일이 저장소에 커밋되어 팀과 공유됩니다.
- Enterprise는 조직 차원의 **정책 배포 수단**이지, "서버를 한 프로젝트로 한정하는 유일한 방법" 같은 것이 아닙니다.

### 어떻게 고르는가 — 두 축으로 판단

1. **범위**: 한 프로젝트만인가, 이 머신의 모든 프로젝트인가?
2. **가시성**: 나만 볼 것인가, 팀과 공유할 것인가?

| 원하는 것 | 정답 범위 |
|---|---|
| 팀 전원이 이 프로젝트에서 쓸 공용 서버 | **project** |
| 아직 불안정한 실험용 서버를 나만, 지금 프로토타이핑 중인 그 프로젝트에서만 | **local** (팀에 노출 안 되고, 내 다른 프로젝트도 오염 안 됨) |
| 내 머신 어디서든, 나만 쓸 개인 도구 | **user** |

### 구체 사례

> "개인 Notion 워크스페이스를 조회하는 실험적 로컬 MCP 서버를, 동료에게는 보이지 않게 하고, 내 머신에서 **어떤 프로젝트를 열든** 쓰고 싶다."

→ **user 스코프**. `~/.claude.json`에 기록되고, 모든 프로젝트에서 로드되며, git 저장소에는 들어가지 않습니다.

요구사항에서 답을 뽑아내는 방법:

- "다른 팀원에게 보이면 안 된다" → 프로젝트에 커밋되는 `.mcp.json`(project)은 탈락.
- "내 머신에서 **어떤 프로젝트를 열든** 항상 쓰고 싶다" → 특정 프로젝트 디렉터리에 묶이는 local도 탈락.
- 두 조건을 동시에 만족하는 것은 **user (`~/.claude.json`)** 뿐입니다.

왜 다른 답은 안 되는가:

- `.mcp.json` + `.gitignore` → `.mcp.json`은 **프로젝트 단위**입니다. 공유는 막을 수 있어도 "모든 프로젝트에서 사용 가능"이라는 조건을 만족하지 못합니다. 프로젝트마다 다시 설정해야 합니다.
- project 범위는 **애초에 공유용**입니다. "개인 전용으로 표시(mark as personal-only)"하는 플래그·토글 같은 건 없습니다.
- `.claude/settings.json`은 Claude Code **동작 설정**(권한, 훅, 환경 변수 등)을 담는 파일이며, 모든 프로젝트에 전역으로 MCP 서버를 연동하는 표준 경로가 아닙니다. 게다가 프로젝트 단위 범위에 묶입니다.

### 등록 명령 (CLI)

```bash
claude mcp add --scope user notion-personal -- npx -y @my/notion-mcp-server
claude mcp add notion --scope user -- npx -y @modelcontextprotocol/server-notion
claude mcp add deploy-tools --scope project -- node ./scripts/deploy-mcp-server.js
claude mcp list        # 등록된 서버와 연결 상태 확인
```

### `.mcp.json` 예시 (프로젝트 범위)

```json
{
  "mcpServers": {
    "deploy-tools": {
      "command": "node",
      "args": ["./scripts/deploy-mcp-server.js"],
      "env": { "DEPLOY_ENV": "staging" }
    },
    "analytics": {
      "command": "node",
      "args": ["./tools/analytics-server.js", "--root", "${CLAUDE_PROJECT_DIR}"],
      "env": { "ANALYTICS_ENDPOINT": "https://internal.example.com" }
    }
  }
}
```

stdio 서버 설정 예 (기본값 문법 포함):

```json
{
  "mcpServers": {
    "my-api": {
      "command": "node",
      "args": ["./server.js", "--region", "${API_REGION:-us-east-1}"],
      "env": { "LOG_LEVEL": "info" }
    }
  }
}
```

HTTP 서버 설정 예:

```json
{
  "mcpServers": {
    "github": {
      "type": "http",
      "url": "https://api.example.com/mcp",
      "headers": { "Authorization": "Bearer ${GITHUB_TOKEN}" }
    }
  }
}
```

### 이름 충돌 시 우선순위: 로컬 > 프로젝트 > 사용자 전역

같은 서버 이름이 여러 범위에 정의되면 **더 좁고 개인적인 범위가 이깁니다.**

1. **로컬이 프로젝트를 이깁니다.** 개발자가 팀 기본 설정을 자기 환경에 맞게 덮어쓸 수 있도록 **의도된 설계**입니다. `.mcp.json`이 Git에 들어 있다는 사실은 우선순위를 높여주지 않습니다.
2. **병합되지 않습니다.** 필드 단위로 섞이지 않고, 이긴 범위의 **엔트리 전체가 통째로** 채택됩니다. 프로젝트 정의의 `env`가 로컬 정의에 스며드는 일은 없습니다.
3. 중복 이름은 **오류가 아닙니다.** 둘 다 차단되는 게 아니라, 우선순위에 따라 하나가 선택되어 정상 동작합니다.

실무적 함의: 팀원 한 명만 "나는 다른 엔드포인트에 붙는다"고 하면, **그 사람의 로컬 범위에 같은 이름의 서버가 남아 있는지** 의심해야 합니다.

### 프로젝트 범위의 핵심 보안 동작: 승인 대기(pending approval)

`.mcp.json`은 저장소 안의 파일이므로, **저장소를 클론하기만 해도 임의의 명령이 실행되는 상황**이 생길 수 있습니다. 악의적인 PR이 `.mcp.json`에 위험한 서버를 심어 넣는 공격이 가능합니다.

그래서 Claude Code는 이렇게 동작합니다:

> 프로젝트 범위(`.mcp.json`)로 정의된 MCP 서버는, 그 저장소를 처음 여는 **각 사용자마다 명시적으로 승인하기 전까지 연결되지 않으며, 승인 대기(pending approval) 상태로 표시**됩니다.

따라서 팀 저장소를 클론한 기여자가 처음 `claude mcp list`를 실행하면 `deploy-tools`는 **pending approval**로 보입니다.

정리해 둘 오해:

- 저장소에 체크인되어 있다는 사실은 **암묵적 승인이 아닙니다.** 조용히 자동 연결되지 않습니다.
- 최초 등록자만 쓸 수 있는 것도 아닙니다. 모든 팀원이 쓸 수 있고, **각자 한 번 승인만** 하면 됩니다.

설계 철학: 안전하지 않은 기본값 대신 **명시적 사용자 동의**를 요구합니다.

## 4.6 환경 변수 확장과 `CLAUDE_PROJECT_DIR`

설정 파일에 실제 값을 박아 넣지 않고 **환경 변수 참조**를 쓸 수 있습니다. 문법은 셸(POSIX)과 같습니다.

| 문법 | 의미 |
|---|---|
| `${VAR}` | 환경 변수 `VAR`의 값으로 치환. 설정되어 있지 않으면 오류가 나거나 빈 값이 됨 |
| `${VAR:-기본값}` | `VAR`이 설정되어 있으면 그 값, **설정되어 있지 않거나 비어 있으면** 문자열 `기본값`으로 치환 |

핵심 동작 예:

```json
"args": ["--region", "${API_REGION:-us-east-1}"]
```

`API_REGION`이 설정되지 않은 머신에서 서버가 실제로 받는 값은 **문자열 `us-east-1`** 입니다. 빈 문자열도, 파싱 실패도, `${API_REGION:-us-east-1}`이라는 리터럴 텍스트도 아닙니다. 그게 기본값 문법이 존재하는 이유입니다.

또 하나 자주 틀리는 점: 이 확장은 **`env` 블록 전용이 아닙니다.** `command`, `args`, `url`, `headers` 등 설정 값 전반에 적용됩니다.

### 주입되는 내장 변수 `CLAUDE_PROJECT_DIR`

`CLAUDE_PROJECT_DIR`는 프로젝트 루트의 절대 경로를 담는 변수로, **Claude Code가 자식 프로세스(MCP 서버 등)를 실행할 때 그 프로세스의 환경에 스스로 주입**합니다. 이것이 일반 환경 변수와 다른 점입니다.

- 팀원의 셸 환경(`~/.bashrc` 등)에 이 변수가 정의되어 있지 **않아도** `${CLAUDE_PROJECT_DIR}`는 정상적으로 확장됩니다. 빈 문자열이 되거나 확장이 실패하지 않습니다.
- 값이 없을 때 자동으로 홈 디렉터리(`~`)로 대체되는 **암묵적 기본값 같은 것은 없습니다.** 기본값을 원하면 직접 써야 합니다.
- 그럼에도 `${CLAUDE_PROJECT_DIR:-.}`처럼 기본값을 적어두는 편이 **더 안전한 관행**입니다. 다른 실행 경로나 도구에서 설정을 재사용할 때 방어가 됩니다.

정리: **동작한다. 다만 기본값을 쓰는 편이 낫다.**

```json
{
  "mcpServers": {
    "analytics": {
      "command": "node",
      "args": ["./tools/analytics-server.js", "--root", "${CLAUDE_PROJECT_DIR}"],
      "env": { "ANALYTICS_ENDPOINT": "https://internal.example.com" }
    }
  }
}
```

### 시크릿을 커밋하지 않고 팀과 설정 공유하기

전형적 요구사항: "GitHub MCP 서버 설정을 저장소에 체크인해야 하는데, 팀원마다 개인 액세스 토큰(PAT)이 다르고, 실제 시크릿은 절대 커밋되면 안 된다."

정답 패턴:

1. **프로젝트 범위**로 `.mcp.json`에 서버를 등록해 저장소에 커밋한다.
2. 인증 헤더 값에 **환경 변수 참조**를 쓴다: `"Authorization": "Bearer ${GITHUB_TOKEN}"`
3. 각 팀원은 자기 셸 환경(`.zshrc`, `.env`, 시크릿 매니저 등)에 `GITHUB_TOKEN`을 설정한다.
4. 연결 시점에 각자의 로컬 환경 값이 주입된다.

저장소에는 **변수 이름만** 들어가고 시크릿은 절대 들어가지 않으며, 팀원은 아무 파일도 손으로 고칠 필요가 없습니다.

피해야 할 안티패턴:

| 안티패턴 | 왜 나쁜가 |
|---|---|
| 리터럴 토큰을 설정 파일에 붙여넣고 커밋 | **시크릿 유출**. 게다가 한 사람의 토큰을 팀이 공유하면 감사 추적(누가 무엇을 했는가)도 깨짐 |
| `.mcp.json`을 `.gitignore`에 넣기 | "설정을 저장소에 체크인한다"는 요구사항 자체를 포기. 팀원이 각자 재현해야 하고 설정이 표류(drift)함 |
| 각 팀원이 플레이스홀더를 자기 토큰으로 손수 치환 | 수동 작업이 반복되고, 실수로 커밋될 위험이 항상 남음 |

## 4.7 인증(Authentication)

원격 MCP 서버에 붙으려면 보통 인증이 필요합니다. Claude Code의 MCP 설정은 세 가지 방식을 제공합니다.

### 4.7.1 정적 헤더 (`headers`)

값이 거의 변하지 않는 API 키에 적합합니다. 값 자체는 4.6의 환경 변수 참조로 써서 커밋을 피합니다.

```json
{
  "mcpServers": {
    "internal-api": {
      "type": "http",
      "url": "https://mcp.internal.example.com",
      "headers": { "Authorization": "Bearer ${INTERNAL_API_TOKEN}" }
    }
  }
}
```

한계: 토큰이 짧은 주기로 만료되거나 **매 연결마다 새로 발급되어야 한다면** 쓸 수 없습니다. 사람이 설정 파일을 계속 갈아 끼우는 운영은 현실적으로 불가능합니다.

### 4.7.2 OAuth 블록 (`oauth`, `authServerMetadataUrl`)

표준 OAuth 2.0 인가 서버가 있을 때 사용합니다. `authServerMetadataUrl`은 인가 서버의 메타데이터 문서(엔드포인트 목록 등)를 가리키며, 클라이언트가 인증 흐름을 자동으로 발견하게 해 줍니다.

전제 조건: **OAuth 인가 서버가 실제로 존재해야 합니다.** Kerberos처럼 OAuth가 아닌 인증 체계를 이 블록으로 처리할 수는 없습니다. Kerberos 렐름(realm) 주소를 `authServerMetadataUrl`에 넣는 것은 의미가 없습니다. Kerberos 영역은 OAuth 메타데이터를 제공하지 않기 때문입니다.

### 4.7.3 동적 헤더 헬퍼 (`headersHelper`)

**연결할 때마다 새 토큰을 발급받아야 하는** 인증 체계를 위한 기능입니다.

- **무엇인가**: 서버에 연결할 때마다 Claude Code가 실행하는 **외부 스크립트**를 지정하는 설정 항목.
- **동작**: 스크립트가 토큰을 새로 발급받아 **결과 헤더를 JSON으로 stdout에 출력**하고, Claude Code가 그 JSON을 요청 헤더로 사용합니다.
- **왜 좋은가**: 토큰 발급 로직(kinit, 사내 SDK, 시크릿 매니저 조회 등)을 스크립트에 캡슐화할 수 있고, **매 연결마다 신선한 값**이 보장되며, 설정 파일에는 시크릿이 남지 않습니다.

```json
{
  "mcpServers": {
    "kerberos-service": {
      "type": "http",
      "url": "https://mcp.corp.internal",
      "headersHelper": "/usr/local/bin/mint-kerberos-header.sh"
    }
  }
}
```

스크립트는 헤더 객체를 JSON으로 stdout에 출력하기만 하면 됩니다:

```bash
#!/bin/bash
TOKEN=$(kinit-and-mint --service mcp.corp.internal)   # 매번 새 토큰 발급
printf '{"Authorization": "Negotiate %s"}\n' "$TOKEN"
```

이것이 Kerberos 파생 토큰, 단기 STS 자격증명, 서명 기반 인증 등 **OAuth가 아니면서 수명이 매우 짧은** 인증 방식을 다루는 표준적인 방법입니다.

관련 오해: "Claude Code가 Kerberos를 지원하지 않으니 Kerberos로 인증하고 API 키를 발급해 주는 중개(intermediary) 서비스를 따로 세워야 한다"는 접근은, `headersHelper`가 있는 상황에서는 불필요한 추가 인프라입니다.

### 4.7.4 선택 요약

| 상황 | 사용할 설정 |
|---|---|
| 장기 고정 API 키 | `headers` (환경 변수 참조 권장) |
| 표준 OAuth 인가 서버 존재 | `oauth` + `authServerMetadataUrl` |
| 매 연결마다 새 토큰 필요(Kerberos, STS 등) | `headersHelper` 스크립트 → stdout JSON |

한 줄 요약: **정적이면 `headers`, OAuth면 `oauth` 블록, 매번 새로 계산해야 하면 `headersHelper`.**

## 4.8 여러 MCP 서버 동시 사용과 이름 충돌

### 4.8.1 동시 연결은 기본 동작

MCP 클라이언트는 **여러 서버와 동시에 세션을 유지**할 수 있습니다. 개수 제한이나 "한 번에 하나만 연결" 같은 제약은 없습니다.

- 연결된 모든 서버의 도구가 **하나의 통합된 도구 목록**으로 모델에게 동시에 노출됩니다.
- 모델은 **같은 턴(하나의 사용자 요청) 안에서** 서버를 넘나들며 도구를 호출할 수 있습니다.
- 프롬프트의 단어와 서버 이름이 얼마나 닮았는지에 따라 도구가 선택적으로 로드되는 일은 **없습니다.** 모두 처음부터 로드되어 있습니다.
- 어떤 서버의 호출이 끝나야 다른 서버의 도구가 "선택 가능해지는" 블로킹 구조도 **없습니다.** 턴 시작 시점부터 전부 선택 가능합니다.

예: "DB 스키마를 뽑아 → 최근 Sentry 에러와 대조해 → 요약을 Slack에 올려줘"라는 한 번의 요청은, Postgres·Sentry·Slack 세 서버의 도구를 한 턴 안에서 순차적으로 호출해 처리됩니다.

> 다만 서버를 많이 붙일수록 도구 수가 늘어 선택 정확도와 토큰 사용량이 나빠진다는 별개의 문제가 있습니다. 그 대응이 4.10의 Tool Search입니다.

### 4.8.2 같은 서버 이름이 여러 범위에 있을 때

도구 이름은 4.4에서 본 대로 서버 이름으로 네임스페이스가 갈리므로 서버가 다르면 충돌하지 않습니다. 문제는 **같은 서버 이름이 서로 다른 설정 범위에 정의된 경우**입니다.

우선순위는 **더 좁고 개인적인 범위가 이깁니다: 로컬 > 프로젝트 > 사용자 전역.**

1. **로컬 범위가 프로젝트 범위를 이깁니다.** 개발자가 팀 기본 설정을 자기 환경에 맞게 덮어쓸 수 있도록 의도된 설계입니다. `.mcp.json`이 Git에 들어 있다는 사실은 우선순위를 높여 주지 않습니다.
2. **병합되지 않습니다.** 필드 단위로 섞이지 않고, 이긴 범위의 **엔트리 전체가 통째로** 채택됩니다. 프로젝트 정의의 `env`가 로컬 정의에 스며드는 일은 없습니다.
3. 중복 이름은 **오류가 아닙니다.** 둘 다 차단되는 게 아니라, 우선순위에 따라 하나가 선택되어 정상 동작합니다.
4. 이름 충돌을 가정해 **숫자 접미사를 붙여 자동 개명하는 동작도 없습니다.**

실무적 함의: 팀원 한 명만 "나는 다른 엔드포인트에 붙는 것 같다"고 하면, 그 사람의 로컬 범위에 같은 이름의 서버가 남아 있는지부터 의심해야 합니다.

## 4.9 도구 목록의 동적 갱신 (`notifications/tools/list_changed`)

### 4.9.1 문제 상황

세션은 몇 시간씩 지속될 수 있습니다. 그 사이 서버 백엔드 상태가 바뀌어(새 DB가 붙거나, 사용자 권한이 올라가서) **새 도구가 생길 수 있습니다.** 세션 시작 때 한 번 받은 도구 목록만 고집한다면 새 도구는 영영 쓸 수 없습니다.

### 4.9.2 MCP의 해법 — 이벤트 기반 알림

1. 서버가 도구 목록을 변경한다.
2. 서버가 클라이언트에 `notifications/tools/list_changed` 알림을 보낸다.
3. 클라이언트는 **연결을 유지한 채** 다시 `tools/list`를 호출해 최신 목록을 받아온다.
4. 새 도구가 즉시 사용 가능해진다.

### 4.9.3 중요한 성질

- **재연결이 필요 없습니다.** 연결을 끊었다 다시 붙는 방식이 아니므로, 진행 중인 도구 호출(in-flight call)을 폐기할 이유도 없습니다.
- **사용자의 수동 개입이 필요 없습니다.** 서버가 알림을 정상적으로 보냈다면 클라이언트가 알아서 갱신합니다. `/mcp` 화면에서 수동으로 다시 연결하는 것은, 서버가 알림을 보내지 않는 등 **비정상 상황의 대응책**입니다.
- 이 동작은 **서버가 알림을 보냈을 때** 성립합니다. 알림을 구현하지 않은 서버라면 클라이언트는 변경 사실을 알 수 없습니다.

## 4.10 Tool Search와 `alwaysLoad`

### 4.10.1 문제: 도구가 너무 많다

MCP 서버를 10개쯤 붙이면 도구가 수백 개가 될 수 있습니다. 모든 도구의 이름·설명·스키마를 **매 요청마다 컨텍스트에 넣으면**:

- 토큰이 대량으로 낭비되고,
- 선택지가 많아져 모델의 도구 선택 정확도가 떨어집니다.

### 4.10.2 해결: Tool Search (지연 로딩)

**Tool Search**는 모든 도구 정의를 미리 넣지 않고, **필요할 때 검색해서 그 도구의 정의만 불러오는** 방식입니다. 이를 **deferred loading**(지연 로딩)이라 부릅니다.

- 장점: 컨텍스트 절약, 선택 정확도 향상
- 단점: 도구를 찾아 해석하는 **추가 단계**가 생겨 약간의 **지연(latency)** 발생

### 4.10.3 예외 처리: `alwaysLoad: true`

어떤 서버의 도구를 **거의 매 턴마다** 쓴다면, 매번 탐색하는 것은 순수한 낭비입니다. 그 서버의 설정 항목에 `alwaysLoad: true`를 주면 **세션 시작 시점에 그 서버의 도구 정의가 컨텍스트에 즉시 로드**되어 탐색 단계를 건너뜁니다.

```json
{
  "mcpServers": {
    "internal-tools": {
      "command": "node",
      "args": ["./internal-mcp/server.js"],
      "alwaysLoad": true
    }
  }
}
```

핵심: **서버 단위로 개별 적용**할 수 있습니다. 그래서 "붙여 둔 10개 중 그 1개 서버만 즉시 로드" 같은 요구를 정확히 충족합니다.

### 4.10.4 혼동하기 쉬운 다른 설정들

| 설정 | 실제 의미 | 이 문제와의 관계 |
|---|---|---|
| `MAX_MCP_OUTPUT_TOKENS` | 도구 **응답 결과**의 최대 토큰 수 제한 | 호출 **이후** 출력 크기 문제. 로딩 지연과 무관 |
| `ENABLE_TOOL_SEARCH=false` | 도구 탐색을 **전역으로** 비활성화 | 10개 서버 전부의 도구가 컨텍스트에 올라와 토큰 폭증. "한 서버만"이라는 요구와 어긋남 |
| 설정 범위 변경 (project→user) | 설정 파일 위치와 공유 범위만 바뀜 | 로딩 시점을 제어하는 옵션이 전혀 아님 |

## 4.11 리소스 참조 — `@서버:URI` 멘션

### 4.11.1 다시 확인: 리소스란

4.2에서 본 세 원시 타입 중 하나로, MCP 서버가 노출하는 **읽기 대상 데이터**입니다. 각 리소스는 **URI**로 식별됩니다. 예: `file://api/authentication`, `db://schema/users`.

### 4.11.2 프롬프트 안에서 직접 참조하기

Claude Code에서는 로컬 파일을 `@src/index.ts`처럼 `@`로 참조합니다. MCP 리소스도 같은 감각으로 다음 형태를 씁니다.

```
@<server_name>:<resource_uri>
```

실제 예:

```
@docs:file://api/authentication 이 문서 기준으로 우리 로그인 플로우가 맞는지 검토해줘
```

이렇게 쓰면 해당 리소스의 내용이 **프롬프트 실행 시점에 컨텍스트로 직접 삽입**되어, Claude가 그 문서를 바로 분석할 수 있습니다.

### 4.11.3 왜 다른 방법은 부적절한가

| 대안 | 문제 |
|---|---|
| `.mcp.json`에 `resources` 필드를 넣어 매 세션 자동 로드 | 그런 필드는 **표준이 아니며**, 설령 있어도 필요 없을 때까지 컨텍스트를 낭비함. "이번 프롬프트에서 이 문서를"이라는 요구와 다름 |
| `list_resources`를 수동 호출해 원시 JSON을 복붙 | 번거롭고 형식이 깨지기 쉬운 임시방편. 리소스 참조 기능을 우회하는 셈 |
| "docs 서버 좀 열어봐"라고 자연어로 막연히 요청 | 어느 리소스인지 특정되지 않아 모델이 추측함. 명시적 참조 구문이 존재하는 이유가 바로 이 모호성 제거 |

## 4.12 흔한 오해 정리

| 오해 | 실제 |
|---|---|
| MCP는 Anthropic 전용 규격이다 | **개방형 표준**입니다. 서버를 한 번 만들면 MCP를 지원하는 어떤 클라이언트에서도 씁니다 |
| 한 번에 하나의 MCP 서버만 연결할 수 있다 | 여러 서버를 **동시에** 유지하고, 한 턴 안에서 서버를 넘나들며 호출합니다 |
| 프롬프트 내용에 따라 관련 서버의 도구만 로드된다 | Tool Search를 쓰지 않는 한 연결된 **모든** 도구가 처음부터 노출됩니다. 서버 이름과 프롬프트 단어의 유사도로 고르는 동작은 없습니다 |
| 새 도구를 쓰려면 재연결하거나 세션을 다시 시작해야 한다 | 서버가 `notifications/tools/list_changed`를 보내면 **연결을 유지한 채** 자동 갱신됩니다 |
| `.mcp.json`이 저장소에 있으니 클론하면 바로 연결된다 | **각 사용자가 명시적으로 승인**하기 전까지 pending approval 상태로 남습니다. 체크인은 암묵적 승인이 아닙니다 |
| `.mcp.json`은 Git에 있으니 로컬 설정보다 우선한다 | 반대입니다. **로컬 > 프로젝트 > 사용자 전역** 순으로 좁은 범위가 이깁니다 |
| 같은 서버 이름이 겹치면 오류이거나 자동 개명된다 | 오류가 아니고 접미사도 붙지 않습니다. 우선순위에 따라 **엔트리 전체가 통째로** 하나 선택됩니다 |
| 여러 범위의 정의가 필드 단위로 병합된다 | 병합되지 않습니다. 이긴 쪽 엔트리만 쓰입니다 |
| `${VAR}` 확장은 `env` 블록에서만 된다 | `command`, `args`, `url`, `headers` 등 설정 값 전반에 적용됩니다 |
| `${VAR:-기본값}`은 변수가 없으면 빈 문자열이 된다 | 기본값 **문자열 그대로** 치환됩니다. 리터럴 텍스트가 남지도 않습니다 |
| `CLAUDE_PROJECT_DIR`는 셸에 정의해 두어야 한다 | Claude Code가 자식 프로세스 환경에 **주입**합니다. 다만 `${CLAUDE_PROJECT_DIR:-.}`처럼 기본값을 쓰는 편이 안전합니다 |
| 값이 없으면 `CLAUDE_PROJECT_DIR`가 홈 디렉터리로 대체된다 | 그런 암묵적 기본값은 **없습니다** |
| 토큰을 공유하려면 `.mcp.json`에 넣고 `.gitignore` 하면 된다 | 체크인 요구를 포기하는 것입니다. 정답은 **환경 변수 참조 + 각자 로컬 환경 설정** |
| Kerberos 같은 비-OAuth 인증은 별도 중개 서비스가 필요하다 | `headersHelper` 스크립트로 매 연결마다 헤더를 생성하면 됩니다 |
| `oauth` 블록으로 아무 인증 체계나 처리할 수 있다 | **OAuth 인가 서버가 실재해야** 합니다. Kerberos 렐름을 `authServerMetadataUrl`에 넣는 것은 무의미합니다 |
| 도구가 너무 많으면 `MAX_MCP_OUTPUT_TOKENS`로 줄인다 | 그것은 **응답 출력** 크기 제한입니다. 도구 정의 로딩과 무관합니다 |
| `alwaysLoad`는 전역 스위치다 | **서버 단위** 설정입니다. 전역 스위치는 `ENABLE_TOOL_SEARCH`이며 성격이 다릅니다 |
| MCP 리소스를 쓰려면 내용을 복붙해야 한다 | `@서버:URI` 멘션으로 프롬프트 실행 시점에 직접 삽입됩니다 |
