# PRE-STUDY: Claude Code 설정과 워크플로 (conf 90-103 대비 개념 정리)

이 문서는 해당 주제를 전혀 모르는 학습자를 위한 사전 학습 노트입니다.
Claude Code가 "무엇인지"부터 시작해서, 설정 파일 계층, 컨텍스트 로딩 규칙,
권한 모델, CLI 자동화, 그리고 AI와 협업하는 작업 패턴까지 순서대로 설명합니다.

---

## 0. 출발점: Claude Code란 무엇인가

**Claude Code**는 터미널(CLI)에서 실행되는 AI 코딩 에이전트입니다.
일반 챗봇과 다른 점은, 단순히 텍스트로 답하는 것이 아니라 **도구(tool)를 직접 사용**한다는 것입니다.

- 파일을 읽는다 (Read)
- 파일을 수정하거나 새로 만든다 (Edit / Write)
- 코드베이스를 검색한다 (Grep / Glob)
- 셸 명령을 실행한다 (Bash)
- 네트워크 요청을 보낸다 (WebFetch 등)

이 때문에 두 가지 문제가 생깁니다.

1. **컨텍스트 문제** — 모델은 프로젝트 규칙("우리 팀은 이렇게 코딩한다")을 모릅니다.
   → 해결책: `CLAUDE.md`, `.claude/rules/` 같은 **지침 파일**
2. **안전 문제** — 파일을 마음대로 지우거나 위험한 명령을 실행하면 곤란합니다.
   → 해결책: **권한 모드(permission mode)** 와 **설정 계층(settings precedence)**

아래 모든 개념은 이 두 축 위에 있습니다.

## 1. 컨텍스트(Context)와 컨텍스트 윈도우

### 1.1 컨텍스트란

**컨텍스트(context)** 는 모델이 답을 생성할 때 "지금 눈앞에 보고 있는 모든 텍스트"입니다.
여기에는 시스템 프롬프트, 사용자 대화, 읽은 파일 내용, 도구 실행 결과,
그리고 자동으로 주입된 프로젝트 지침 파일이 모두 포함됩니다.

컨텍스트에 **없는 정보는 모델에게 존재하지 않는 것**입니다.
파일이 디스크에 멀쩡히 있어도, 컨텍스트에 로드되지 않았다면 모델은 그 지침을 따를 수 없습니다.
이 문장이 이번 주제의 절반을 차지하는 핵심입니다.

### 1.2 컨텍스트 윈도우와 그 한계

모델이 한 번에 볼 수 있는 텍스트 양에는 상한(**context window**)이 있습니다.
긴 세션에서 파일을 계속 읽고 명령을 계속 실행하면 이 상한에 다다릅니다.

### 1.3 압축(Compaction)

**Compaction(컨텍스트 압축)** 은 대화가 길어져 컨텍스트 윈도우가 가득 찰 때,
지금까지의 대화를 **요약본으로 대체**해 공간을 확보하는 동작입니다.
자동으로 일어나기도 하고 사용자가 직접 유발할 수도 있습니다.

압축의 본질:

- 압축은 **메모리(컨텍스트) 상의 정리**입니다. **디스크의 실제 파일은 전혀 건드리지 않습니다.**
  압축이 파일을 손상시키거나 삭제하는 일은 없습니다.
- 압축 후에도 **프로젝트 루트의 `CLAUDE.md`는 자동으로 다시 읽혀 재주입(re-inject)** 됩니다.
  루트 지침은 세션 전체의 기본 규범이므로 항상 살아있도록 설계되어 있습니다.
- 반면 **하위 디렉터리의 중첩 `CLAUDE.md`는 압축 시 컨텍스트에서 빠집니다.**
  이 파일들은 "그 디렉터리 파일을 만질 때 로드되는" 성격이므로,
  압축 이후 Claude가 **다시 그 디렉터리의 파일을 읽는 시점에야 재로드**됩니다.

> 실무적 증상: 긴 세션에서 압축이 일어난 뒤,
> 루트 지침은 잘 지켜지는데 특정 하위 폴더의 지침만 갑자기 무시되는 것처럼 보입니다.
> 이는 버그가 아니라 위 로딩 규칙의 정상 동작입니다.
> 그 폴더의 파일을 한 번 읽게 하면 지침이 되살아납니다.
>
> "압축은 세션의 처음 200줄만 보존한다" 같은 규칙은 존재하지 않습니다.

## 2. CLAUDE.md — 프로젝트 지침 파일

### 2.1 무엇인가

`CLAUDE.md`는 **Claude에게 주는 프로젝트 설명서**입니다.
마크다운 평문으로, 자연어로 씁니다. 예:

```markdown
# 프로젝트 규칙

- 패키지 매니저는 pnpm을 사용한다. npm/yarn 금지.
- 테스트는 `pnpm test`로 실행한다.
- 모든 API 응답은 snake_case로 직렬화한다.
- 커밋 전에 반드시 `pnpm lint`를 통과시킨다.
```

Claude Code는 세션이 시작될 때 이 파일들을 찾아 컨텍스트에 넣습니다.
따라서 매번 "우리는 pnpm 써"라고 타이핑할 필요가 없어집니다.

### 2.2 계층 구조: 어디에 둘 수 있나

`CLAUDE.md`는 한 개가 아니라 여러 위치에 동시에 존재할 수 있습니다.

| 위치 | 성격 | 버전 관리 |
|---|---|---|
| `~/.claude/CLAUDE.md` | 개인 전역 지침 (모든 프로젝트) | 개인 소유, 자유 편집 |
| 리포지토리 루트 `CLAUDE.md` | 프로젝트 전체 지침 | 보통 git에 커밋 |
| 하위 디렉터리 `CLAUDE.md` | 그 서브트리 전용 지침 | 보통 git에 커밋 |
| `CLAUDE.local.md` | 개인용 로컬 지침 | 보통 `.gitignore` 처리 |

이들은 서로를 **대체하지 않고 병합(merge)** 됩니다.
하위 파일이 있다고 해서 상위 파일이 무시되는 일은 없습니다.

### 2.3 로딩 규칙 (가장 중요)

Claude Code를 실행한 디렉터리를 **작업 디렉터리(working directory, cwd)** 라고 합니다.

**세션 시작 시 즉시 로드되는 것:**
- 작업 디렉터리의 `CLAUDE.md`
- 그 **상위(ancestor) 경로들**을 루트까지 거슬러 올라가며 발견되는 모든 `CLAUDE.md`

**세션 시작 시 로드되지 않는 것:**
- 작업 디렉터리 **하위(subdirectory)** 의 `CLAUDE.md`
  → 이것들은 Claude가 그 하위 디렉터리 안의 파일을 실제로 읽거나 수정할 때
  비로소 컨텍스트에 추가됩니다. 이를 **온디맨드 로딩(on-demand loading)**
  또는 **지연 로딩(lazy loading)** 이라고 부릅니다.

**구체적 예시**

리포지토리 구조:

```
repo/
├── CLAUDE.md                              (A)
└── services/
    └── billing/
        ├── CLAUDE.md                      (B)
        └── reports/
            └── CLAUDE.md                  (C)
```

`services/billing/`에서 Claude Code를 실행했다면:

- **시작 즉시 로드**: A(상위 조상), B(작업 디렉터리) → 둘이 병합되어 적용
- **로드 안 됨**: C. `reports/` 안의 파일을 읽는 순간에야 로드됨

왜 이렇게 설계했을까요?
거대한 모노레포에는 `CLAUDE.md`가 수십 개 있을 수 있습니다.
전부 미리 로드하면 컨텍스트 윈도우가 지침만으로 가득 차서
정작 코드를 볼 공간이 없어집니다.
**필요할 때만 가져오는 것**이 컨텍스트 예산을 아끼는 방법입니다.

### 2.4 자주 오해하는 지점 정리

- 작업 디렉터리 아래 모든 `CLAUDE.md`를 전부 미리 로드하지 **않습니다**.
- 하위 디렉터리 파일이 상위 파일과 결합되지 않는다는 규칙은 **없습니다** (계층 병합이 기본).
- 상위 파일을 쓰기 위해 명시적 import 선언이 필요하지 **않습니다**.

## 3. `.claude/rules/` — 모듈식 규칙 파일

### 3.1 왜 필요한가

`CLAUDE.md` 하나가 수백 줄로 불어나면 관리가 어렵습니다.
"API 코딩 규칙", "테스트 규칙", "스타일 규칙"이 한 파일에 섞이고,
API 코드를 만지지 않는 세션에서도 API 규칙이 컨텍스트를 잡아먹습니다.

`.claude/rules/` 디렉터리는 지침을 **여러 파일로 쪼개고**,
각 파일이 **언제 로드될지를 스스로 선언**할 수 있게 해 줍니다.

```
.claude/
└── rules/
    ├── general-style.md
    ├── api.md
    └── testing.md
```

### 3.2 YAML 프론트매터(frontmatter)

**프론트매터**는 마크다운 파일 맨 위에 `---` 로 감싸 넣는 메타데이터 블록입니다.
파일의 "본문"이 아니라 "설정"입니다.

```markdown
---
paths: ["src/api/**/*.ts"]
---

# API 코딩 규칙

- 모든 핸들러는 zod 스키마로 입력을 검증한다.
- 에러는 ProblemDetails 형식으로 반환한다.
```

### 3.3 `paths` 필드 — 조건부 로딩의 핵심

`paths`는 **글로브(glob) 패턴 배열**입니다.
글로브는 파일 경로 매칭 문법으로, `*`는 한 경로 구간 내 임의 문자,
`**`는 임의 깊이의 디렉터리를 뜻합니다.
`src/api/**/*.ts`는 "src/api 아래 어느 깊이든 있는 모든 .ts 파일"입니다.

동작 규칙은 딱 두 가지입니다.

| `paths` 필드 | 이름 | 로딩 시점 |
|---|---|---|
| **없음(생략)** | 무조건 규칙 (unconditional rule) | **세션 시작 시 즉시** 로드. `.claude/CLAUDE.md`와 같은 우선순위의 기본 컨텍스트가 됨 |
| **있음** | 경로 범위 규칙 (path-scoped rule) | Claude가 **그 패턴에 일치하는 파일을 읽거나 수정할 때만** 동적으로 주입 |

즉 `paths`를 **빼면 항상 적용**, **넣으면 해당 파일 작업 시에만 적용**입니다.

정리해 두면 좋은 사실:
- `paths`는 **필수 항목이 아닙니다.** 없어도 파일은 정상 인식되고 로드됩니다.
- `paths`를 생략한다고 해서 `"**/*"` 같은 기본 와일드카드가 붙어
  "파일을 열 때까지 대기"하는 방식으로 바뀌는 것이 아닙니다. 그냥 시작 시 무조건 로드입니다.
- 규칙 파일의 적용 범위가 `.claude/rules/` 디렉터리 자신으로 한정되는 일은 없습니다.

### 3.4 모노레포에서의 활용

모노레포(monorepo)는 여러 패키지/팀 코드를 한 저장소에 모아 둔 구조입니다.

```
packages/
├── team-a/
│   └── .claude/rules/*.md
└── team-b/
    └── .claude/rules/*.md
```

팀 A 엔지니어가 `packages/team-a/`에서만 작업하는데
팀 B의 규칙까지 컨텍스트에 들어오면 낭비이고 혼선입니다.

**올바른 해법은 규칙 파일 자체에 `paths`를 붙여 범위를 좁히는 것**입니다.

```markdown
---
paths: ["packages/team-b/**"]
---
```

이렇게 해 두면 팀 B 규칙은 `packages/team-b/` 하위 파일을 만질 때만 로드됩니다.
팀 A에서만 작업하는 동안에는 경로가 매칭되지 않으므로 컨텍스트에 들어오지 않고,
동시에 팀 A 자신의 경로 범위 규칙들은 평소대로 조건부 로딩됩니다.
**규칙이 자기 영역을 스스로 선언하도록 만드는 것**이 모노레포의 정석입니다.

참고로 다음은 이 목적에 맞지 않습니다.
- 팀 A 규칙에서 `paths`를 지우는 것: 팀 A 규칙이 전역으로 바뀔 뿐,
  팀 B 규칙의 발견/로딩을 막는 효과는 전혀 없습니다.
- `claudeMdExcludes`: `CLAUDE.md` 로딩 예외 처리용 설정이며,
  `.claude/rules/*.md` 규칙 파일을 제외하는 공식 수단이 아닙니다.
- `autoMemoryEnabled`: 자동 기억/메모리(`MEMORY.md`) 기능 스위치이며,
  외부 디렉터리의 `.claude/rules/` 탐색과는 무관합니다.

## 4. 설정 계층과 우선순위 (settings precedence)

### 4.1 설정 파일의 종류

Claude Code의 동작(권한, 허용 도구, 환경 변수 등)은 JSON 설정 파일로 제어합니다.
이들은 여러 수준에 존재하고, **충돌하면 정해진 우선순위로 결정**됩니다.

낮은 우선순위 → 높은 우선순위 순서:

1. **사용자 설정** — `~/.claude/settings.json`
   개인 전역 설정. 본인이 자유롭게 수정 가능.
2. **프로젝트 설정** — 리포지토리의 `.claude/settings.json`
   팀 공유용, git에 커밋됨. 하지만 개발자가 로컬에서 바꾸거나 커밋을 되돌릴 수 있음.
3. **로컬 프로젝트 설정** — `.claude/settings.local.json`
   개인용, 보통 `.gitignore` 처리.
4. **관리형 설정 (Managed / Enterprise settings)** — `managed-settings.json`
   **최고 우선순위. 아래 항목들을 전부 덮어씁니다(override).**

### 4.2 `managed-settings.json`

조직 전체에 강제해야 하는 보안·컴플라이언스 정책을 위한 파일입니다.
사용자 홈이 아니라 **OS의 시스템 디렉터리**에 배치합니다.

- Linux: `/etc/claude-code/managed-settings.json`
- macOS: `/Library/Application Support/ClaudeCode/managed-settings.json`
- Windows: `C:\ProgramData\ClaudeCode\managed-settings.json`

배포는 보통 조직의 **구성 관리 시스템(configuration management)**
— Ansible, Puppet, Chef, MDM(Jamf, Intune) 등 — 으로 모든 머신에 뿌립니다.

**왜 이것만이 "강제"가 되는가**

시스템 디렉터리는 일반적으로 관리자 권한이 있어야 쓸 수 있고,
설정 우선순위상 개발자 개인 설정이나 프로젝트 설정으로 **덮어쓸 수 없기 때문**입니다.
"모든 개발자가, 모든 머신에서, 모든 리포지토리에서 받고,
개인이 끌 수 없어야 한다"는 요구를 만족하는 유일한 수단입니다.

**왜 다른 방법은 부족한가 (개념 이해용 대조)**

- 리포지토리 루트 `CLAUDE.md`: 프로젝트 수준일 뿐입니다.
  개발자가 로컬에서 수정·삭제할 수 있고, 리포지토리마다 따로 챙겨야 하며,
  더 높은 우선순위 설정으로 우회될 수 있습니다.
- `~/.claude/CLAUDE.md`를 온보딩 스크립트로 채우기: 개인 디렉터리라
  이후 개발자가 자유롭게 편집·삭제할 수 있고 우선순위도 낮습니다. 강제력이 없습니다.
- `CLAUDE.local.md`: 애초에 개인 로컬 전용이고 `.gitignore` 대상이라
  추적도 강제도 되지 않습니다.

**요령: "강제(enforce)" 요구가 나오면 시스템 수준 관리형 설정, "공유(share)" 요구면 프로젝트 파일.**

## 5. 권한 모델 (Permission Model)

### 5.1 왜 권한이 필요한가

Claude Code는 실제로 파일을 고치고 셸 명령을 실행합니다.
잘못된 `rm -rf`, 의도치 않은 외부 네트워크 전송 등은 실질적 피해를 줍니다.
그래서 도구 호출마다 **승인(approval)** 절차를 둡니다.

기본 동작은 "위험한 동작을 하기 전에 사용자에게 프롬프트를 띄워 물어본다"입니다.

### 5.2 권한 모드(permission mode) 종류

| 모드 | 동작 |
|---|---|
| **default (normal)** | 파일 수정, 셸 실행 등에 대해 그때그때 승인을 요청 |
| **plan** | **읽기 전용**. 모든 수정/파괴적 명령이 차단됨. 읽기·검색은 승인 없이 진행 |
| **acceptEdits** | 파일 편집류를 자동 승인. 그 외는 여전히 승인 필요 |
| **bypassPermissions** | 승인 절차를 광범위하게 우회 (고위험, 격리 환경 전용) |

### 5.3 Plan mode의 권한 모델

**Plan mode(플랜 모드)** 는 "코드를 바꾸기 전에 먼저 코드베이스를 조사하고 계획을 세우는 모드"입니다.

이 모드에서는:
- **모든 파일 수정과 파괴적 명령이 시스템 차원에서 차단**됩니다.
- **읽기와 읽기 전용 검색은 매번 승인을 묻지 않고 그냥 진행**됩니다.

두 번째가 처음엔 이상해 보이지만, 이유는 단순합니다.
수정이 원천적으로 불가능하다는 **읽기 전용 보장(read-only guarantee)** 이 이미 있으므로,
읽기 하나하나에 승인을 받는 것은 안전성에 아무것도 더해 주지 않고
탐색만 느리게 만듭니다. 그래서 프롬프트를 생략하는 것이 정상 설계입니다.

정리해 둘 사실:
- Plan mode가 사용자 모르게 `acceptEdits`로 자동 전환되는 동작은 **없습니다**.
- 읽기 전용 명령이 **모든** 권한 모드에서 영구 면제되는 것은 **아닙니다**.
  일반 모드에서는 설정이나 위험도 판단에 따라 읽기/실행에도 승인이 걸릴 수 있습니다.
  Plan mode에서 승인 없이 진행되는 것은 그 모드의 고유 성질입니다.

### 5.4 acceptEdits의 정확한 범위

`--permission-mode acceptEdits`는 이름 그대로 **"편집(edits)"을 자동 승인**합니다.

**자동 승인되는 것**
- 파일 생성·수정·삭제 (Write / Edit)
- 흔한 파일시스템 명령: `mkdir`, `mv`, `cp` 등

**자동 승인되지 않는 것**
- 그 밖의 임의 셸 명령
- **네트워크 요청** (외부에서 데이터를 가져오거나 보내는 동작)

이유는 위험 성격이 다르기 때문입니다.
로컬 파일 편집은 git으로 되돌릴 수 있지만,
네트워크 요청은 외부로 데이터를 유출하거나 신뢰할 수 없는 코드를 끌어올 수 있어
되돌릴 수 없는 부류입니다. 그래서 별도 허용이 필요합니다.

이런 동작을 자동화하려면 **명시적으로 허용**해야 합니다.
- CLI 플래그: `--allowedTools`
- 설정 파일: `permissions.allow` 규칙

**전형적인 CI 실패 시나리오**

```bash
claude -p "apply the lint fixes" --permission-mode acceptEdits
```

CI는 **비대화형(non-interactive)** 환경이라 승인 프롬프트에 사람이 답할 수 없습니다.
앞부분의 파일 편집은 `acceptEdits` 범위라 조용히 통과하지만,
중간에 "최신 의존성 목록을 가져오자"며 네트워크 요청을 시도하는 순간
승인이 필요해지고, 물어볼 사람이 없으므로 **실행이 중단(abort)** 됩니다.
해결은 그 도구/명령을 `--allowedTools` 또는 `permissions.allow`에 넣어 주는 것입니다.

정리해 둘 사실:
- `acceptEdits`가 "첫 번째 도구 호출에만" 적용된다는 규칙은 **없습니다**. 편집은 몇 번이든 자동 승인됩니다.
- 프린트 모드(`-p`)라고 해서 네트워크 요청이 무조건 차단되는 것은 **아닙니다**. 권한 정책으로 허용 가능합니다.
- `acceptEdits`가 동작하려면 `--bare` 같은 별도 플래그가 필요하다는 조건은 **없습니다**.

## 6. Plan mode vs Direct Execution — 언제 계획을 세우는가

### 6.1 두 가지 작업 방식

- **Direct execution (직접 실행)**: 바로 코드를 수정하기 시작.
- **Plan mode (플랜 모드)**: 먼저 읽기 전용으로 코드베이스를 조사하고,
  구현 계획을 세워 사용자 승인을 받은 뒤 실행.

Plan mode는 공짜가 아닙니다. 탐색·계획·검토 단계만큼 **시간과 토큰을 소비**합니다.
따라서 "언제나 안전하니까 항상 쓰자"는 잘못된 판단이며 오버헤드를 만듭니다.

### 6.2 판단 기준 (이것이 핵심)

**Plan mode가 적합한 신호**
- 여러 파일 / 여러 모듈에 걸친 변경
- 아키텍처적 결정이 필요함
- 구현 경로가 여러 개이거나 모호함
- **아직 결정되지 않은(open) 설계 사안**이 남아 있음
- 파급 효과(side effect)를 사전에 파악해야 함

**Direct execution이 적합한 신호**
- 변경이 **단일 파일**에 국한됨
- **명확한 단일 구현 경로**가 있음 (특히 같은 파일 내 기존 패턴을 그대로 따르는 경우)
- **다른 모듈에 영향이 없음**
- 미결 설계 사안이 없음

즉 판단 축은 **범위(scope) × 모호성(ambiguity) × 파급효과(blast radius)** 입니다.

### 6.3 판단 기준이 **아닌** 것들

개념적으로 반드시 구분해야 할 오해들입니다.

- **누가 코드를 썼는가**: 기존 패턴을 다른 엔지니어가 작성했다는 사실은
  인적 요소일 뿐 기술적 판단 기준이 아닙니다.
- **요청 문장의 길이**: 한 문장으로 설명된다고 범위가 작은 것이 아닙니다.
  "인증을 OAuth로 바꿔줘"는 짧지만 수십 파일을 건드립니다.
  실제로 몇 개 모듈을 만지게 되는지가 기준입니다.
- **비즈니스 중요도만으로**: 결제·체크아웃 모듈이 중요하다는 이유로
  사소한 변경까지 항상 동일한 고정 프로세스를 강제하면 불필요한 오버헤드입니다.
  중요도는 리뷰 강도의 근거는 되어도, 계획 단계 필요 여부의 자동 기준은 아닙니다.
- **"DB 스키마를 건드리면 무조건 플랜 모드"**: 사실이 아닙니다.
  예를 들어 *한 테이블에 nullable 컬럼 하나 추가 + 이를 읽는 모델 파일 하나 수정,
  다른 파일 영향 없음, 남은 설계 결정 없음*이라면 이는 명백히 직접 실행 대상입니다.
  스키마 변경이라도 범위가 작고 결정이 끝났다면 계획 단계는 순수 오버헤드입니다.
  반대로 "테이블을 쪼갤지 말지 아직 안 정했다"면 그건 미결 사안이 있으므로 플랜 모드입니다.
- **"스키마 변경은 플랜 모드도 직접 실행도 건너뛰고 마이그레이션 툴로 직행"**:
  그런 규칙은 없습니다. 마이그레이션 파일 작성도 결국 코드 작업입니다.

## 7. 피드백을 구조화하는 법 (코드 리뷰 결과 전달)

### 7.1 문제 상황

Claude가 만든 diff(변경 사항)를 리뷰하다가 여러 문제를 발견했다고 합시다.
이 피드백을 **어떤 단위로 묶어서 전달하느냐**가 결과 품질을 좌우합니다.

### 7.2 결합도(coupling)라는 개념

두 코드 조각이 같은 자원을 공유하거나 서로의 동작에 영향을 주면
**결합되어 있다(coupled)** 고 말합니다.

예: 재시도 백오프(retry backoff) 로직과 작업 잠금(job-locking) 로직이
**같은 타이머 인스턴스를 공유**한다면, 한쪽을 고치면 다른 쪽 동작이 바뀝니다.

- **retry backoff**: 실패한 작업을 재시도할 때 대기 시간을 점점 늘리는 기법.
- **job locking**: 같은 작업이 동시에 두 번 실행되지 않도록 잠그는 기법.
- 둘이 같은 타이머를 쓰면, 백오프 간격을 늘리는 순간 잠금 유효 시간도 함께 흔들립니다.

### 7.3 원칙: 결합된 것은 묶고, 무관한 것은 분리한다

**결합된 문제들은 한 메시지에 함께, 결합 관계를 명시해서 설명합니다.**
모델이 두 로직의 상호작용을 한 번에 보고 근본 원인(공유 타이머)을 다룰 수 있게 하기 위함입니다.

**무관한 문제는 별도 항목으로 분리해 전달합니다.**
예를 들어 로그 레벨 한 단어를 고치는 일은 타이머와 아무 관계가 없습니다.
이것을 결합된 문제와 한 덩어리로 묶어 "분리 불가능한 하나의 변경"이라고 지시하면,
모델은 존재하지 않는 관계를 있다고 가정하고 엉뚱한 리팩터링을 할 수 있습니다.

### 7.4 피해야 할 두 가지 극단

1. **과잉 결합(over-coupling)**: 무관한 사소한 수정까지 하나로 묶기.
   → 잘못된 인과관계를 모델에 심어 줍니다.
2. **원인 은폐(context stripping)**: 증상만 목록으로 나열하고
   ("재시도 백오프", "작업 잠금", "로그 레벨")
   **둘이 공유 타이머로 결합되어 있다는 사실을 빼먹기**.
   → 모델은 각각을 독립 증상으로 보고 표면만 고칩니다. 근본 원인은 그대로 남습니다.

또 하나: 사소한 수정을 먼저 처리하고 완료를 확인할 때까지 나머지 피드백을 미루는
**불필요한 직렬화(sequential blocking)** 도 비효율입니다.
의존 관계가 없는 일을 순서로 묶을 이유가 없습니다.

**요약 규칙: 피드백의 그룹 경계는 "기술적 의존 관계"를 따라 그린다.**

## 8. 테스트 주도 반복 (Test-Driven Iteration)

### 8.1 TDD 기본 개념

**TDD(Test-Driven Development)** 는 구현 코드보다 **테스트를 먼저** 작성하는 방식입니다.

1. 원하는 동작을 검증하는 테스트를 작성한다 (당연히 실패한다).
2. 그 테스트를 통과시키는 최소 구현을 작성한다.
3. 테스트가 통과할 때까지 다듬는다.

### 8.2 AI 에이전트와 결합하면 왜 강력한가

AI에게 자연어로 요구사항을 설명하면 해석이 흔들릴 수 있습니다.
반면 **테스트 코드는 모호하지 않은 기계 검증 가능한 명세**입니다.

게다가 테스트 실패 메시지는 **자동으로 생성되는 정확한 피드백**입니다.
"이게 좀 이상한데?"라고 사람이 매번 설명하는 대신,
실패 로그를 그대로 Claude에게 넘기면 됩니다.
이것이 **수정 주기(correction cycle)** 를 줄이는 핵심 메커니즘입니다.

### 8.3 구체적 순서

예: 내부 API용 **rate limiter(속도 제한기)** 를 만든다고 합시다.

- **throttle(스로틀)**: 정해진 시간당 요청 수를 넘으면 거절/지연시키는 것.
- **burst limit(버스트 제한)**: 순간적으로 몰리는 요청을 어디까지 허용할지.
- **reset window(리셋 창)**: 카운터가 초기화되는 시간 구간.

권장 흐름:

1. Claude에게 **먼저 테스트 스위트를 작성**하게 한다
   — 예상 스로틀 동작, 버스트 제한, 리셋 타이밍을 모두 커버.
2. 그 다음 rate limiter 구현을 요청한다.
3. 테스트를 실행하고, **실패 결과를 Claude에게 공유하며 반복(iterate)** 한다.

### 8.4 열등한 대안들과 그 이유

- **설계 문서만 쓰고 테스트 없이 구현**: 문서는 실행되지 않습니다.
  구현이 문서를 따랐는지 검증할 자동 수단이 없어 수정 주기가 늘어납니다.
- **구현 먼저, 테스트 나중(test-last)**: 테스트가 "이미 만들어진 동작"을 문서화할 뿐,
  요구사항을 사전에 고정하지 못합니다. 초기 구현 오류가 그대로 굳습니다. TDD가 아닙니다.
- **터미널에서 수동 검증만**: 반복 실행이 번거롭고, 재현성이 없으며,
  회귀(regression)를 잡지 못합니다. 수정 주기 단축에 기여하지 않습니다.

## 9. 요구사항 도출: AskUserQuestion 인터뷰 패턴

### 9.1 문제 상황

경험이 없는 도메인(예: 실시간 협업 문서 편집기)을 만들 때,
아키텍트 스스로는 **무엇을 모르는지조차 모릅니다**.
이런 도메인에는 초보자가 놓치기 쉬운 함정이 있습니다.

- **cache invalidation (캐시 무효화)**: 캐시에 저장된 데이터가 언제 낡은 것이 되는지,
  어떻게 갱신·폐기할지. 분산 환경에서 가장 어려운 문제 중 하나입니다.
- **conflict resolution (충돌 해결)**: 두 사용자가 같은 문서의 같은 부분을 동시에 편집했을 때
  결과를 어떻게 하나로 합칠지. (OT, CRDT 같은 접근법이 존재)
- **failure handling (실패 처리)**: 네트워크가 끊기거나 서버가 죽었을 때
  편집 내용을 어떻게 보존·복구할지.

### 9.2 AskUserQuestion 도구

`AskUserQuestion`은 **Claude가 사용자에게 구조화된 질문을 던지는 도구**입니다.
방향이 평소와 반대입니다 — 사람이 AI에게 묻는 게 아니라, **AI가 사람을 인터뷰**합니다.

### 9.3 인터뷰 패턴

1. Claude에게 만들려는 기능을 **간략히** 설명한다.
2. **구현 전에**, `AskUserQuestion`을 사용해 나를 인터뷰해 달라고 요청한다
   — 기술적 구현 방식, 엣지 케이스, 트레이드오프를 훑도록.
3. 그 문답을 통해 몰랐던 고려사항이 드러난다.
4. 그 결과를 바탕으로 명세(spec)를 작성하고, 그 다음 구현에 들어간다.

핵심 가치: 모델은 이 도메인의 일반적 함정을 알고 있으므로,
**사용자가 질문할 줄 몰랐던 것을 질문해 줍니다.**
설계 결함을 코드 작성 전에 잡는 것이 가장 저렴합니다.

### 9.4 열등한 대안들과 그 이유

- **혼자 완벽한 기술 명세를 다 쓰고 고정된 지시로 넘기기**:
  경험 없는 도메인에서는 애초에 불가능하고, 누락이 대량 발생합니다.
- **오픈소스 편집기 아키텍처를 그대로 복제**:
  그 프로젝트의 제약과 우리 시스템의 제약이 다릅니다.
  트레이드오프 검토 과정 자체가 생략되어, 왜 그렇게 만들어졌는지 모른 채 따라가게 됩니다.
- **일단 최소 구현 후 수동 테스트로 버그를 찾아 설계를 역산**:
  아키텍처 결함을 구현 이후에 발견하면 **재작업(rework) 비용이 폭증**합니다.
  선제적 설계 도출 전략이 아닙니다.

## 10. 스킬(Skill)과 SKILL.md 프론트매터

### 10.1 스킬이란

**스킬(skill)** 은 자주 쓰는 작업 절차를 패키징해 둔 재사용 단위입니다.
`/fix-issue`처럼 슬래시 명령으로 호출하거나, 모델이 상황에 맞게 자동 호출할 수 있습니다.

정의는 `SKILL.md` 파일에 두며, 맨 위에 YAML 프론트매터로 메타데이터를 씁니다.

```markdown
---
name: fix-issue
description: GitHub 이슈 번호를 받아 해당 이슈를 분석하고 수정한다
argument-hint: [issue-number]
---

이슈 $1 을(를) 읽고, 원인을 파악한 뒤 수정 패치를 작성한다.
```

### 10.2 주요 프론트매터 필드

| 필드 | 역할 |
|---|---|
| `name` | 스킬 이름 (슬래시 명령 이름) |
| `description` | 이 스킬이 무슨 일을 하는지 설명. **모델이 자동 호출 여부를 판단하는 근거**이자 목록에 표시되는 설명문 |
| `argument-hint` | 자동완성 메뉴에 표시되는 **인자 플레이스홀더**. 순수 UI 힌트 |
| `disable-model-invocation` | `true`면 모델이 스스로 호출하지 못하게 막고, 사용자의 수동 호출만 허용 |

### 10.3 `argument-hint` 자세히

**해결하는 문제**: `/fix-issue`가 이슈 번호를 필요로 하는데,
팀원이 `/fix-issue`만 치고 무엇을 넣어야 할지 몰라 헤매는 상황.

**동작**: `argument-hint: [issue-number]`를 넣으면
CLI 자동완성 메뉴에서 명령 옆에 `[issue-number]`라는 안내 문구가 보입니다.
`/fix-issue 482`처럼 입력해야 한다는 사실이 눈으로 전달됩니다.

**중요한 성질**: 이것은 **순수하게 표시(display)용**입니다.
- 스킬의 실행 방식을 바꾸지 않습니다.
- 인자를 **강제하거나 검증하지 않습니다**. 값을 안 넣어도 실행은 됩니다.

즉 문서화 장치이지 유효성 검사 장치가 아닙니다.

### 10.4 혼동하기 쉬운 필드 구분

- `disable-model-invocation: true`는 **모델의 자동 호출을 막는** 스위치입니다.
  자동완성에 인자 힌트를 띄우는 기능이 아니고, 인자 입력을 강제하지도 않습니다.
- `arguments:` 라는 이름으로 인자 타입/유효성 검사를 하는 표준 프론트매터 필드는
  Claude Code `SKILL.md`에 **존재하지 않습니다**.
- `description`은 스킬 설명문입니다.
  Claude가 실행 전에 사용자에게 소리 내어 읽어 주지 않고,
  자동완성의 인자 플레이스홀더로도 쓰이지 않습니다.

## 11. CLI 자동화와 구조화된 출력 (Structured Output)

### 11.1 프린트 모드 `-p`

```bash
claude -p "이 diff를 리뷰해줘"
```

`-p`(print mode, headless/non-interactive)는 대화형 UI 없이
프롬프트를 한 번 처리하고 결과를 stdout으로 출력한 뒤 종료합니다.
CI 파이프라인, 스크립트, 자동화에서 쓰는 형태입니다.

주의: 비대화형이므로 **승인 프롬프트에 답할 사람이 없습니다.**
그래서 5.4에서 본 것처럼 권한을 미리 열어 두지 않으면 중간에 멈춥니다.

### 11.2 출력 형식 플래그

| 플래그 | 용도 |
|---|---|
| `--output-format text` | 사람이 읽는 평문 (기본) |
| `--output-format json` | 결과를 JSON 객체로 반환 |
| `--output-format stream-json` | 생성 과정을 실시간 JSON 이벤트 스트림으로 반환 |
| `--verbose`, `--include-partial-messages` | 스트리밍 시 중간 이벤트/메타데이터를 더 자세히 노출 |

`stream-json` 계열은 **진행 상황을 실시간으로 관찰**하기 위한 것입니다.
최종 결과의 **형태를 특정 스키마로 고정하는 기능이 아닙니다.**

### 11.3 `--json-schema` — 스키마 강제

CI에서 Claude의 답을 코드로 파싱해 빌드 성공/실패를 판단하려면,
답변이 **항상 같은 JSON 모양**이어야 합니다.
모델이 어떤 문장으로 추론을 서술하든 상관없이 말입니다.

`--output-format json`과 `--json-schema`를 함께 쓰면
**JSON Schema로 응답 구조를 강제(structured output)** 할 수 있습니다.

```bash
claude -p "review this diff" \
  --output-format json \
  --json-schema '{
    "type": "object",
    "properties": {
      "passed": { "type": "boolean" },
      "issues": { "type": "array", "items": { "type": "string" } }
    },
    "required": ["passed", "issues"]
  }'
```

**JSON Schema 문법 최소 지식**
- `"type": "object"` — 결과가 객체임
- `"properties"` — 각 필드의 이름과 타입
- `"type": "boolean"` / `"array"` / `"string"` — 타입 지정
- `"items"` — 배열 원소의 타입
- `"required"` — 반드시 존재해야 하는 필드 목록

그러면 CI 스크립트는 이렇게 안심하고 파싱할 수 있습니다.

```bash
result=$(claude -p "..." --output-format json --json-schema '...')
passed=$(echo "$result" | jq -r '.passed')
[ "$passed" = "true" ] || exit 1
```

### 11.4 왜 프롬프트로 부탁하는 것으로는 부족한가

다음 두 방식은 **보장이 아니라 요청**일 뿐입니다.

- 프롬프트 본문에 "passed: true/false 형식으로만 답해"라고 쓰고 `--output-format text` 사용
- `--append-system-prompt "Always respond with valid JSON matching {passed, issues}"` 사용

모델은 대체로 잘 따르지만, 앞뒤에 설명 문장을 붙이거나 마크다운 코드 펜스(```)를 두르거나
필드 이름을 살짝 다르게 쓸 수 있습니다. 그러면 파싱이 깨지고 빌드가 오작동합니다.
**스키마 검증·강제는 프롬프트 지시로 대체할 수 없습니다.**
자동화의 신뢰성이 필요하면 `--json-schema`를 씁니다.

## 12. 전체 그림 한 장 요약

```
[ 무엇을 알려줄 것인가 — 컨텍스트 ]
  CLAUDE.md 계층      : cwd + 상위 → 시작 시 로드 / 하위 → 온디맨드
  .claude/rules/*.md  : paths 없음 → 시작 시 무조건 / paths 있음 → 매칭 시 조건부
  Compaction          : 루트 CLAUDE.md는 재주입, 중첩 파일은 다시 읽을 때 복귀

[ 무엇을 허용할 것인가 — 권한 ]
  plan          : 읽기 전용, 읽기는 무승인
  acceptEdits   : 파일 편집 + mkdir/mv/cp 자동승인, 셸/네트워크는 별도 허용 필요
  allowedTools / permissions.allow : 명시적 허용
  managed-settings.json (시스템 디렉터리) : 최고 우선순위, 개인이 못 끔

[ 어떻게 일할 것인가 — 워크플로 ]
  범위 작고 명확  → 직접 실행
  범위 넓고 모호  → 플랜 모드
  구현 전 요구사항 발굴 → AskUserQuestion 인터뷰
  구현 정확도    → 테스트 먼저 → 구현 → 실패 공유 반복
  피드백 그룹핑  → 결합된 것은 묶고 무관한 것은 분리

[ 어떻게 자동화할 것인가 — CLI ]
  -p                      : 비대화형 실행
  --output-format json
  + --json-schema         : 응답 구조 강제 (파싱 가능)
  --output-format stream-json : 실시간 관찰용 (구조 강제 아님)
```

## 13. 용어 사전 (Glossary)

**컨텍스트 / 설정**

| 용어 | 설명 |
|---|---|
| context | 모델이 응답 생성 시 참조하는 전체 텍스트. 여기에 없으면 모델은 모른다 |
| context window | 한 번에 담을 수 있는 컨텍스트의 최대 크기 |
| compaction | 컨텍스트가 가득 찰 때 이전 대화를 요약으로 대체해 공간을 확보하는 동작. 디스크 파일은 건드리지 않음 |
| re-inject | 압축 후 루트 `CLAUDE.md`를 다시 읽어 컨텍스트에 재삽입하는 것 |
| working directory (cwd) | Claude Code를 실행한 디렉터리. 로딩 계산의 기준점 |
| ancestor directory | 작업 디렉터리의 상위 경로들. 여기의 `CLAUDE.md`는 시작 시 로드됨 |
| subdirectory | 작업 디렉터리의 하위 경로. 여기의 `CLAUDE.md`는 온디맨드 로드 |
| on-demand loading / lazy loading | 필요해지는 시점(해당 경로 파일 접근 시)에 비로소 로드하는 방식 |
| preload | 미리 전부 로드하는 것. Claude Code는 하위 `CLAUDE.md`를 이렇게 하지 않음 |
| CLAUDE.md | 프로젝트/디렉터리 지침을 자연어로 적는 마크다운 파일 |
| CLAUDE.local.md | 개인 로컬 전용 지침 파일. 보통 `.gitignore` 대상, 강제력 없음 |
| `.claude/rules/` | 지침을 여러 파일로 분할해 두는 디렉터리 |
| YAML frontmatter | 마크다운 파일 최상단 `---` 사이에 쓰는 메타데이터 블록 |
| `paths` | 규칙 파일의 적용 경로 글로브 배열. 생략하면 무조건 로드, 지정하면 조건부 로드 |
| glob pattern | 경로 매칭 문법. `*`=구간 내 임의 문자, `**`=임의 깊이 디렉터리 |
| unconditional rule | `paths` 없는 규칙. 세션 시작 시 항상 로드 |
| path-scoped rule | `paths` 있는 규칙. 매칭 파일 작업 시에만 로드 |
| monorepo | 여러 패키지/팀 코드를 한 저장소에 모아 둔 구조 |
| settings.json | Claude Code 동작 설정 파일 (사용자/프로젝트/로컬 수준) |
| managed-settings.json | 시스템 디렉터리에 배치되는 조직 관리형 설정. 최고 우선순위, 개인이 우회 불가 |
| precedence | 설정 충돌 시 어느 쪽이 이기는지 정하는 우선순위 규칙 |
| configuration management system | Ansible/Puppet/MDM 등 조직 전체 머신에 설정을 배포하는 도구 |
| `claudeMdExcludes` | 특정 `CLAUDE.md` 로딩을 건너뛰기 위한 설정 필드. rules 파일 제외용은 아님 |
| `autoMemoryEnabled` | 자동 기억(MEMORY.md) 기능 스위치. 규칙 디렉터리 탐색과 무관 |

**권한 / 모드**

| 용어 | 설명 |
|---|---|
| permission mode | 도구 호출 승인 정책을 정하는 모드 |
| plan mode | 읽기 전용 조사·계획 모드. 수정 차단, 읽기는 승인 없이 진행 |
| direct execution | 계획 단계 없이 바로 구현에 들어가는 방식 |
| acceptEdits | 파일 편집과 `mkdir`/`mv`/`cp` 등을 자동 승인하는 모드 |
| bypassPermissions | 승인을 광범위하게 우회하는 고위험 모드 |
| `--allowedTools` | 특정 도구/명령을 명시적으로 허용하는 CLI 플래그 |
| `permissions.allow` | 설정 파일에서 허용 규칙을 정의하는 항목 |
| read-only guarantee | 수정이 원천 차단된다는 보장. plan mode에서 읽기 승인을 생략하는 근거 |
| non-interactive | 승인 프롬프트에 답할 사람이 없는 실행 환경 (CI 등) |

**CLI / 출력**

| 용어 | 설명 |
|---|---|
| `-p` / print mode | 대화형 UI 없이 한 번 실행 후 결과 출력하고 종료 |
| `--output-format text` | 사람이 읽는 평문 출력 |
| `--output-format json` | 결과를 JSON 객체로 반환 |
| `--output-format stream-json` | 생성 과정을 실시간 JSON 이벤트로 스트리밍. 구조 강제 기능 아님 |

| `--json-schema` | JSON Schema로 응답 구조를 강제하는 플래그 |
| structured output | 응답이 사전 정의된 스키마를 반드시 따르도록 보장하는 기능 |
| JSON Schema | JSON 데이터 구조를 기술하는 표준. `type`, `properties`, `items`, `required` 등 |
| `--append-system-prompt` | 시스템 프롬프트에 문구를 덧붙이는 플래그. 스키마 강제는 못 함 |

**스킬**

**워크플로 / 설계**

| 용어 | 설명 |
|---|---|
| coupling | 두 코드 조각이 자원을 공유하거나 서로 영향을 주는 상태 |
| shared timer instance | 여러 로직이 함께 쓰는 하나의 타이머 객체. 전형적 결합 원인 |
| retry backoff | 재시도 시 대기 간격을 점진적으로 늘리는 기법 |
| job locking | 동일 작업의 중복 실행을 막기 위한 잠금 |
| double execution | 같은 작업이 두 번 실행되는 사고 |
| blast radius | 변경이 미치는 영향 범위 |
| side effect | 의도한 대상 밖에서 발생하는 부수적 영향 |
| nullable column | NULL 값을 허용하는 DB 컬럼. 기존 행에 영향이 적어 추가가 안전한 편 |
| migration | DB 스키마 변경을 버전 관리하며 적용하는 절차/파일 |
| TDD | 테스트를 먼저 작성하고 구현하는 개발 방식 |
| test-driven iteration | 테스트 작성 → 구현 → 실패 결과를 AI에 공유 → 반복하는 협업 패턴 |
| test-last | 구현 후에 테스트를 붙이는 방식. TDD가 아님 |
| correction cycle | 잘못된 결과를 고치기 위해 다시 요청하는 반복 주기 |
| rate limiter | 단위 시간당 요청 수를 제한하는 구성 요소 |
| throttle | 한도를 넘는 요청을 거절/지연시키는 동작 |
| burst limit | 순간적으로 몰리는 요청의 허용 한도 |
| reset window | 요청 카운터가 초기화되는 시간 구간 |
| AskUserQuestion | Claude가 사용자에게 구조화된 질문을 던지는 도구 |
| interview pattern | 구현 전 AI가 사용자를 인터뷰해 숨은 요구사항을 끌어내는 기법 |
| cache invalidation | 캐시된 데이터를 언제 무효화·갱신할지의 전략 |
| conflict resolution | 동시 편집 충돌을 병합·해결하는 방식 (OT, CRDT 등) |
| failure handling | 장애·중단 시 데이터 보존과 복구 처리 |
| rework | 잘못 만든 것을 다시 만드는 비용 |
| spec | 구현 전에 확정하는 기술 명세 |
