# 사전 학습 노트: 컨텍스트 관리와 신뢰성 (Context Management & Reliability)

이 문서는 이 분야를 전혀 모르는 상태에서 읽기 시작해도 되도록 작성되었습니다. LLM(대형 언어 모델) 기반 에이전트 시스템을 설계할 때 등장하는 개념들을 하나씩 밑바닥부터 설명합니다.

---

## 0. 먼저 알아야 할 기본 배경

### 0.1 LLM과 컨텍스트 윈도우 (Context Window)

LLM은 "지금 눈앞에 보이는 글자들"만 보고 다음 글자를 생성하는 기계입니다. 이 "눈앞에 보이는 범위"를 **컨텍스트 윈도우(context window)** 라고 부릅니다. 단위는 **토큰(token)** 이며, 토큰은 대략 단어 조각 하나 정도입니다(영어 기준 약 4글자, 한국어는 더 짧게 쪼개집니다).

핵심 성질 세 가지:

1. **유한하다.** 20만 토큰이든 100만 토큰이든 끝이 있습니다. 넘어가면 잘리거나 오류가 납니다.
2. **비용이 든다.** API 요금은 대개 입력 토큰 수 × 단가로 계산됩니다. 쓸데없는 내용을 넣으면 그대로 돈입니다.
3. **주의력(attention)이 희석된다.** 컨텍스트에 넣은 내용이 많을수록, 그중 특정 한 줄에 모델이 집중할 확률은 떨어집니다.

그래서 "컨텍스트에 무엇을 넣고 무엇을 뺄 것인가"를 설계하는 일이 하나의 공학 분야가 되었고, 이를 **컨텍스트 엔지니어링(Context Engineering)** 이라 부릅니다.

### 0.2 에이전트(Agent)란 무엇인가

**에이전트**는 LLM에게 "도구(tool)"를 쥐여 주고, 목표를 준 뒤, 스스로 판단해서 도구를 호출하고 결과를 보고 다음 행동을 결정하게 만든 시스템입니다.

- **도구(Tool / Function Calling):** 모델이 호출할 수 있는 외부 함수. 예: `web_fetch(url)`, `crm_lookup(contact_id)`, `get_logs(service, minutes)`. 모델은 함수를 직접 실행하지 않고 "이 함수를 이 인자로 불러 줘"라는 JSON을 출력하며, 실제 실행은 여러분의 코드가 합니다. 실행 결과(도구 출력)는 다시 컨텍스트에 넣어 모델에게 돌려줍니다.
- **루프(Agent Loop):** 모델 출력 → 도구 실행 → 결과를 컨텍스트에 추가 → 다시 모델 호출. 이 반복이 에이전트의 심장입니다. 반복할수록 컨텍스트가 계속 불어난다는 점이 중요합니다.

### 0.3 멀티 에이전트와 오케스트레이션

한 에이전트가 모든 일을 하면 컨텍스트가 금방 터지고 역할도 뒤섞입니다. 그래서 흔히 이렇게 나눕니다.

- **코디네이터(Coordinator) / 오케스트레이터(Orchestrator) / 메인 에이전트:** 전체 작업을 쪼개고, 하위 작업을 배분하고, 결과를 모아 최종 산출물을 만드는 상위 에이전트.
- **서브에이전트(Subagent):** 하나의 좁은 하위 작업만 담당하는 하위 에이전트. 자기만의 컨텍스트 윈도우를 갖습니다. 예: "규제 리스크만 조사해라".
- **스폰(Spawn):** 코디네이터가 서브에이전트를 새로 생성/실행하는 행위.
- **종합 단계(Synthesis step):** 여러 서브에이전트의 결과물을 하나의 보고서로 합치는 마지막 단계.

서브에이전트를 쓰는 가장 큰 이유는 **컨텍스트 격리**입니다. 서브에이전트가 100개 파일을 읽어도 코디네이터에게는 요약 3줄만 돌려주면, 코디네이터의 컨텍스트는 깨끗하게 유지됩니다.

## 1. 컨텍스트 관리 기법

### 1.1 도구 출력 트리밍 (Tool Output Trimming / Field Extraction)

**문제:** 실제 업무 API는 필요 이상으로 많은 필드를 반환합니다. 예를 들어 CRM 연락처 조회 API가 레코드 하나당 60개 필드(내부 리드 스코어, 마케팅 캠페인 태그, 감사 타임스탬프 등)를 돌려주는데, 정작 팔로업 이메일을 쓰는 데 필요한 건 이름, 회사, 거래 단계, 마지막 연락일 4개뿐일 수 있습니다. 연락처 10건을 조회하면 600개 필드가 컨텍스트를 점령합니다.

**해결:** 도구 출력을 **컨텍스트에 넣기 전에** 코드 레벨에서 필요한 필드만 뽑아냅니다.

```python
FIELDS = ("name", "company", "deal_stage", "last_contact_date")

def trim(record):
    return {k: record[k] for k in FIELDS if k in record}

context.append(trim(crm.lookup(contact_id)))   # 60개 → 4개
```

**왜 이게 옳은 해법인가:**
- 토큰 비용이 15분의 1로 줄어듭니다.
- 모델이 봐야 할 노이즈가 사라져 정확도와 속도가 올라갑니다.
- "포맷만 압축하고 60개 필드는 다 넣기"는 해법이 아닙니다. 불필요한 정보가 여전히 모델의 주의력을 갉아먹기 때문입니다. 문제는 **글자 수**가 아니라 **관련 없는 정보의 존재**입니다.
- 반대로 "혹시 나중에 필요할지 모르니 60개 다 쌓아두기"는 **컨텍스트 오염(Context Pollution)** 과 비용 폭증을 부릅니다. 필요해지면 그때 다시 조회하면 됩니다.
- "출력을 아예 컨텍스트에 남기지 않고 모델의 기억에 맡기기"도 위험합니다. 컨텍스트에 없는 정보는 모델에게 존재하지 않는 것과 같고, 모델은 없는 값을 그럴듯하게 지어내는 **환각(Hallucination)** 을 일으킵니다.

### 1.2 롤링 요약 (Rolling Summarization)과 그 한계

**롤링 요약**은 대화가 길어지면 앞부분 대화를 요약문으로 대체해 컨텍스트를 줄이는 기법입니다. 며칠씩 이어지는 고객 지원 대화에서 흔히 씁니다.

**한계:** 요약은 본질적으로 **손실 압축(lossy compression)** 입니다. 특히 다음이 잘 사라집니다.

- 정확한 숫자 (금액 $6,400 → "수천 달러"로 뭉개짐)
- 식별자 (청구 번호 #C-1092 같은 ID)
- 여러 개체 간의 구분 (두 건의 청구가 "그 청구"로 합쳐짐)

요약 주기를 더 자주 돌리는 것은 해결이 아니라 악화입니다. 압축을 여러 번 반복하면 정보 손실이 누적됩니다.

### 1.3 팩트 블록 (Case-Facts Block)

**롤링 요약의 손실을 막는 방법**은 "절대 요약하지 않는 구역"을 만드는 것입니다. 대화 요약과 별개로, 변하면 안 되는 사실을 구조화된 블록으로 컨텍스트에 항상 고정 유지합니다.

```
## CASE FACTS (요약 대상 아님)
- 고객 ID: CU-88213
- 청구 #C-1092 | 수해 | $6,400 | 심사 중
- 청구 #C-1108 | 자동차 유리 | $310 | 승인됨
- SLA 만료: 2026-09-12
```

요약본이 아무리 뭉개져도 이 블록의 숫자와 ID는 원문 그대로 남습니다.

### 1.4 개체별 구조화 레코드 (Structured Record per Entity)

**문제:** 하나의 대화 안에 독립된 개체가 여러 개 있을 때, 이들을 하나의 서술형 문장(blended narrative)으로 뭉쳐 요약하면 **엔티티 모호성(Entity Ambiguity)** 이 생깁니다. 예: 보험 청구 두 건을 한 단락으로 요약해 두면, 이후 "그 청구", "그 금액"이 어느 건을 가리키는지 알 수 없게 됩니다.

**해결:** 개체 하나당 레코드 하나. 반드시 **고유 식별자(ID)** 를 키로 갖게 하고, 서술형 텍스트와 분리해 보관합니다.

```json
{
  "claims": [
    {"id": "C-1092", "type": "water_damage", "amount": 6400, "status": "under_review"},
    {"id": "C-1108", "type": "auto_glass",   "amount": 310,  "status": "approved"}
  ]
}
```

이렇게 하면 후속 질문에 답할 때 모델이 특정 ID의 상태값을 정확히 참조할 수 있습니다.

**하면 안 되는 대안들:**
- 가장 최근 언급된 것만 남기고 나머지는 종료된 것으로 가정 → 데이터 손실.
- 두 건을 하나의 번호로 병합 → 서로 다른 사건을 합치는 것이므로 데이터 정합성 파괴.
- 사용자에게 매번 청구 번호를 말하라고 요구 → 시스템의 상태 관리 실패를 사용자에게 떠넘기는 나쁜 UX. 시스템이 감당해야 할 책임을 사용자 부담으로 전가하지 않는 것이 원칙입니다.

### 1.5 Lost in the Middle (중간 정보 유실)

**현상:** LLM은 긴 입력의 **맨 앞**과 **맨 뒤**에 있는 정보는 잘 인지하지만, **중간**에 있는 정보는 놓치는 경향이 있습니다. 이를 "Lost in the Middle"이라 부릅니다. 성능 곡선이 U자 모양(양 끝이 높고 가운데가 낮음)을 그립니다.

**전형적인 사고:** 5개 서브에이전트의 결과를 하나의 긴 문서로 이어 붙여 종합 에이전트에 넘겼는데, 3번째 섹션에 있던 "규제 리스크" 내용이 최종 메모에서 통째로 누락됩니다.

**해결책 — 구조화된 입력 설계:**

1. **프런트로딩(Front-loading):** 문서 최상단에 짧은 **핵심 요약(key-findings summary)** 을 배치합니다. 모든 섹션의 요점이 주의력이 가장 강한 위치에 한 번 등장하게 됩니다.
2. **명시적 헤딩(Explicit headings):** 각 상세 섹션을 명확한 제목 아래 둡니다. 헤딩은 모델에게 정보의 경계를 알려주는 구조적 신호입니다.

```markdown
## Key Findings
1. 시장 규모: TAM $4.2B, CAGR 11%
2. 경쟁사 가격: 평균 $29/월
3. 규제 리스크: EU AI Act 고위험 분류 가능성   ← 중간이지만 최상단에 한 번 등장
4. 고객 심리: NPS 42
5. 유통 채널: 파트너 재판매 비중 60%

## 1. Market Sizing
...
## 3. Regulatory Risk
...
```

**효과가 없는 대안들:**
- "문서를 두 번 읽어라"라는 지시 → 어텐션 메커니즘 자체를 바꾸지 못하는 주술적 프롬프팅이며 토큰만 낭비합니다.
- 누락된 섹션만 맨 뒤로 옮기기 → 다른 섹션이 대신 중간으로 밀려나 같은 문제가 재발합니다. 위치 땜질은 근본 해결이 아닙니다.
- 요약이나 헤더 없이 문서를 두 개로 쪼개기 → 각 문서 내부의 구조가 개선되지 않아 여전히 중간 유실이 발생하고, 관리 복잡도만 늘어납니다.
- 컨텍스트 윈도우가 더 큰 모델로 바꾸고 요약을 아예 중단 → 넣는 양이 늘어나면 중간 구간도 길어져 오히려 악화됩니다. **큰 컨텍스트 윈도우는 컨텍스트 설계를 대체하지 못합니다.**

### 1.6 매니페스트와 스크래치패드 (Manifest / Scratchpad)

**문제:** 긴 탐색 작업에서 몇 시간 전에 이미 조사한 영역을 서브에이전트가 또 조사하는 **중복 탐색(redundant exploration)** 이 발생합니다. 시간과 API 비용이 이중으로 나갑니다.

**해결:** 수행한 작업과 발견 사실을 **외부의 지속적 기록**에 남깁니다.

- **스크래치패드(Scratchpad):** 에이전트들이 중간 결과를 적어 두는 공유 작업 공간(파일, DB, 공유 메모리). 컨텍스트 윈도우 밖에 있으므로 요약에 의해 손실되지 않습니다.
- **매니페스트(Manifest):** 어떤 작업/영역이 이미 처리되었는지 목록화한 인덱스. "무엇을 했는가"의 목록.

새 서브에이전트를 스폰하기 **전에** 매니페스트/스크래치패드를 먼저 조회하는 것이 표준 절차입니다.

**신뢰하면 안 되는 것:**
- **메인 에이전트의 기억(unaided memory):** 몇 시간 전 대화는 이미 요약되었거나 컨텍스트에서 밀려났을 가능성이 높습니다. 모델의 "기억"은 컨텍스트에 남아 있는 텍스트일 뿐이며, 신뢰할 수 있는 저장소가 아닙니다.
- **세션 밖의 사용자 개인 메모:** 시스템이 접근할 수 없고 자동화할 수 없으므로 아키텍처의 일부가 될 수 없습니다.

### 1.7 컨텍스트 엔지니어링 기법의 조합

실무의 실패는 대개 한 가지 원인이 아니라 여러 원인이 겹칩니다. 증상 → 대응 기법을 1:1로 매핑하는 습관을 들이면 좋습니다.

| 증상 | 원인 | 대응 기법 |
|---|---|---|
| 정확한 수치가 유실됨 | 롤링 요약의 손실 압축 | 팩트 블록으로 수치/ID 고정 |
| 동시에 진행되는 이슈들이 뒤섞임 | 서술형 혼합 요약 | 이슈별 구조화 레코드 분리 |
| 컨텍스트가 도구 출력으로 가득 참 | 원본 도구 출력 그대로 삽입 | 관련 필드만 트리밍 |
| 긴 종합 문서의 중간 내용 누락 | Lost in the Middle | 상단 핵심 요약 + 명시적 헤딩 |

## 2. 오류 처리와 결함 허용성

### 2.1 부분 성공 처리 (Partial Success Handling)

**시나리오:** 코디네이터가 서브에이전트 5개를 보내 시장 분석 자료를 수집했습니다. 그중 1개의 웹 페치 도구에서 복구 불가능한 연결 오류가 발생했습니다.

**나쁜 설계:** 파이프라인 전체를 중단하고 이미 완료된 4개의 결과까지 폐기 → 이미 지불한 API 비용과 시간을 통째로 버리는 안티 패턴.

**좋은 설계:**
1. 성공한 4개의 결과로 종합을 진행한다.
2. 실패한 부분은 **보고서에 명시적으로 결손 영역(coverage gap)으로 표기**한다. "유통 채널 항목은 데이터 소스 접근 실패로 수집되지 않았음"처럼.

이것이 **결함 허용성(Fault Tolerance)** 과 **회복탄력성(Resiliency)** 의 기본형입니다. 독립적인 하위 작업들은 서로의 실패에 연동되어 무너지면 안 됩니다.

**절대 하면 안 되는 것:** 빈 구간을 그럴듯한 내용으로 지어내 채우는 것. 이는 의도적 환각이며 안전성·신뢰성 원칙의 심각한 위반입니다. **공백을 감추는 것보다 공백을 드러내는 것이 항상 낫습니다.**

**전부 재실행도 나쁩니다.** 성공한 4개를 "배치 일관성"을 위해 처음부터 다시 돌리는 것은 불필요한 비용과 지연입니다. 실패한 것만 재시도하면 됩니다(**멱등성/재시도 최소화** 원칙).

### 2.2 구조화된 실패 보고 (Structured Failure Report)

**나쁜 에러 메시지:**

```
Query failed.
```

이 메시지로 코디네이터는 아무 결정도 할 수 없습니다. 재시도해야 할지(일시적 오류), 다른 서브에이전트를 써야 할지(도구 문제), 그 부분을 포기해야 할지(불가능한 요청) 구별할 근거가 전혀 없습니다.

여기서 문제는 메시지가 **짧다는 것 자체가 아니라 필요한 정보가 빠졌다는 것**입니다. 타임스탬프만 붙인다고 해결되지 않고, HTTP 상태 코드만이 유일한 필수 정보인 것도 아닙니다(도구 실행 오류, 논리적 실패 등 HTTP와 무관한 실패가 많습니다).

**좋은 에러 메시지 — 최소 4요소:**

```
failure_type: access_failure
attempted:    last-15-minutes log pull (payments service)
partial:      3 of 4 pods returned data
alternative:  retry against read replica
```

| 요소 | 의미 | 코디네이터가 얻는 것 |
|---|---|---|
| **실패 유형(failure type)** | access_failure / validation_error / timeout / not_found … | 재시도 가능 여부 판단 |
| **시도한 작업(attempted)** | 무엇을 하려 했는가 | 결손 범위 파악 |
| **부분 결과(partial results)** | 얼마나 얻었는가 | 즉시 활용 가능한 데이터 확보 |
| **대안(alternative)** | 다음에 시도해 볼 경로 | 복구 경로 선택지 |

JSON 형태로 규격화하면 코드로 분기하기도 쉽습니다.

```json
{
  "status": "partial_failure",
  "failure_type": "access_failure",
  "attempted": "log_pull(payments, 15m)",
  "partial_results": {"pods_returned": 3, "pods_total": 4},
  "alternative": "retry_read_replica"
}
```

### 2.3 구조화된 실패 보고를 받은 코디네이터의 행동

두 가지를 **분리해서** 처리하는 것이 정답입니다.

1. **확보된 부분 결과는 즉시 활용한다.** 파드 3개의 로그는 지금 바로 장애 타임라인에 넣습니다. 장애 대응에서는 신속성이 최우선입니다.
2. **누락분에 대한 복구는 별도로 판단한다.** 읽기 복제본(read replica) 재시도를 할지 말지는 독립적인 의사결정입니다.

**하면 안 되는 것:**
- 서브에이전트가 제안한 대안을 원칙적으로 무시하기 → 대안 제안은 유용한 정보이며, 코디네이터가 그것을 참고하는 것은 정상적인 협업입니다(맹목적 실행이 아니라 판단 재료로 씁니다).
- 4개 파드를 원자적(atomic)으로 한 번에 가져올 때까지 3개 결과를 버리기 → 로그 수집은 원자성이 필요한 트랜잭션이 아닙니다. 불필요한 지연입니다.
- 상세한 구조화 보고서를 단순 'error'로 취급하고 해당 서비스 조사를 포기하기 → 애써 만든 정보를 버리는 것이며 결함 허용성 원칙 위반입니다.

### 2.4 접근 실패 vs 정당한 빈 결과 (Access Failure vs Legitimate Empty Result)

이것은 실무에서 가장 자주 틀리는 구분입니다. 겉보기에는 둘 다 "데이터가 없음"이지만 성격이 정반대입니다.

| | 접근 실패 (Access Failure) | 정당한 빈 결과 (Final Empty Result) |
|---|---|---|
| 예시 | 캐시가 허용 임계값을 넘어 만료(stale)되어 신선도 검사(freshness check) 실패, 네트워크 타임아웃, 인증 만료 | 해당 세션에 시간외 거래가 실제로 한 건도 없었음 |
| 의미 | **데이터가 존재할지도 모르는데 못 읽었다** | **데이터가 존재하지 않는다는 사실을 확인했다** |
| 처리 | 재시도 대상(retryable), 실패로 분류 | 성공적 완료, 빈 결과로 확정 보고 |

**왜 중요한가:** 접근 실패를 "빈 결과"로 잘못 취급하면, 실제로 존재하는 데이터를 "없다"고 결론 내리는 **조용한 데이터 유실(silent data loss)** 이 발생합니다. 반대로 정당한 빈 결과를 "실패"로 취급하면 영원히 성공하지 않을 재시도를 반복하며 자원을 낭비합니다.

**또한 둘 다 사람에게 에스컬레이션할 필요는 없습니다.** 캐시 만료는 재시도로 해결될 가능성이 높은 일상적·일시적 오류이지, 사람이 개입해야 하는 치명적 오류가 아닙니다.

설계 시 도구 반환값은 최소한 세 가지 상태를 구분해야 합니다.

```python
{"status": "ok",    "data": [...]}          # 데이터 있음
{"status": "empty", "data": []}             # 확인 결과 없음 (성공)
{"status": "error", "failure_type": "...", "retryable": True}   # 못 읽음
```

### 2.5 에스컬레이션과 휴먼 인 더 루프 (Escalation / Human-in-the-Loop)

**에스컬레이션**은 에이전트가 스스로 해결할 수 없는 상황에서 사람 담당자에게 사건을 넘기는 것입니다. 자율 에이전트 설계에서 **언제 넘길 것인가(escalation condition)** 를 명확히 정의하는 것은 필수 요소입니다.

**전형적인 조건:**
- 사용 가능한 복구 도구/옵션을 모두 소진했는데 문제가 미해결일 때
- 동일한 실패가 반복되어 진전이 없을 때(무한 루프 위험)
- 정책상 사람의 승인이 필요한 행동일 때(환불, 계정 삭제 등)
- 사용자가 명확히 사람을 요청했고, 시도할 수 있는 것을 이미 시도했을 때

**시나리오:** 클라우드 지원 에이전트가 멈춘 배포를 고치려고 도구 기반 복구를 3가지 시도했지만 모두 실패했고, 더 이상 남은 옵션이 없습니다. → **지금까지의 시도 이력과 실패 맥락을 함께 담아 사람 상담원에게 이관**합니다. 맥락을 함께 넘기는 것이 중요합니다. 사람이 처음부터 다시 조사하지 않아도 되게 하는 것이 에스컬레이션의 가치입니다.

**하면 안 되는 것:**
- 이관 없이 "해결 불가"로 종결 → 고객 방치.
- 같은 조치를 무한 반복 재시도 → 무한 루프, 토큰·컴퓨팅 낭비. "시도한 조치가 옳았으니 언젠간 되겠지"는 근거 없는 낙관입니다.
- 해결되지 않았는데 해결되었다고 통보 → 신뢰를 파괴하는 허위 보고. **올바른 절차를 시도한 것과 문제가 해결된 것은 전혀 다른 사실입니다.**

### 2.6 AI-First 지원 워크플로우

사용자가 처음부터 "봇 말고 사람 연결해 줘"라고 요구하는 경우가 있습니다. Anthropic이 권장하는 지원 접근 방식은 **AI-First** 모델입니다.

권장 흐름:
1. 요청을 무시하지 않고 응대한다.
2. 먼저 문제를 설명하고 해결을 시도해 본다(예: 초과 요금이 왜 발생했는지 사용 이력을 확인해 설명).
3. 그래도 고객이 다시 사람을 요청하거나 문제가 해결되지 않으면 사람 상담원에게 이관한다.

**하면 안 되는 것:**
- 계정 확인이나 해결 시도를 전혀 하지 않고 즉시 사람에게 넘기기 → AI-First 모델의 취지에 어긋납니다.
- 에스컬레이션 요청 자체를 무시한 채 조사만 진행하기 → 고객 커뮤니케이션 무시.
- "왜 봇과 대화하기 싫으신가요?"라고 이유를 캐묻기 → 고객 여정에 마찰(friction)만 더하는 부적절한 응대.

핵심은 **"해결 시도 + 요청 존중 + 조건부 이관"이 하나의 완결된 워크플로우**라는 점입니다.

### 2.7 엔티티 모호성 해소 (Disambiguation)

**시나리오:** 청구 문의를 처리하려고 고객을 조회했더니, 같은 성(last name)과 같은 이메일 도메인을 쓰는 프로필이 두 개 나왔습니다(패밀리 요금제로 보임). 한쪽이 훨씬 활발하게 이용 중입니다.

**정답:** 등록된 결제 카드 뒤 4자리 같은 **추가 식별자(additional identifier)** 를 고객에게 요청해 대상을 확정합니다.

**왜 휴리스틱으로 추측하면 안 되는가:**
- "사용량이 많으니 이 사람일 것" → 사용량이 적은 부계정 소유자가 결제 문의를 했을 수 있습니다.
- "먼저 만든 계정이 주 계정일 것" → 문의 주체가 누구인지와는 무관합니다.
- 두 프로필의 청구 정보를 확인 없이 병합해 답변 → **타인의 개인정보를 노출**하는 심각한 프라이버시 위반입니다.

일반 원칙: **개인 데이터나 금전이 걸린 판단에서, 정황 기반 추측은 절대 신원 확인을 대신할 수 없습니다.** 앞서 1.4에서 "사용자에게 계속 묻는 것은 나쁜 UX"라고 했던 것과 모순되어 보일 수 있는데, 구분 기준은 이렇습니다. **시스템이 이미 알고 있는 것을 다시 묻는 것은 나쁘고, 시스템이 원리적으로 알 수 없는 것(어느 계정의 문의인지, 본인 확인)을 묻는 것은 옳습니다.**

## 3. 근거 제시와 신뢰성

### 3.1 인용 기능 (Citations)

**Citations**는 모델이 답변을 생성할 때, 프롬프트로 제공된 문서 안의 **정확한 원문 구절(exact source passage)** 을 각 문장에 연결해 주는 기능입니다.

**일반 참고문헌과의 차이:**

| | 서브에이전트가 붙인 평문 참고문헌 | Citations 기능 |
|---|---|---|
| 단위 | 문서/출처 단위 목록 | 생성된 **문장(statement)** 단위 |
| 검증 | 사용자가 문서 전체를 뒤져야 함 | 해당 구절로 바로 이동(click-through) |
| 신뢰성 | 모델이 지어낸 출처일 수 있음 | 실제 제공된 문서의 위치를 가리킴 |

**언제 쓰는가:** 최종 사용자가 "이 문장의 근거가 어디냐"를 클릭해서 확인해야 하는 시스템(다중 출처 종합, 법률·의료·금융 리서치 등)에서 결정적입니다. 이를 **그라운딩(Grounding)**, 즉 생성 내용을 실제 근거에 묶어 두는 것이라고 합니다.

**Citations가 해 주지 않는 것 — 흔한 오해:**
- 각 문장에 발행일 타임스탬프를 자동으로 붙여 주지 않습니다.
- 문서를 대신 검색해 오지 않습니다. Citations는 **이미 프롬프트에 제공된 문서** 안에서 위치를 매핑할 뿐이며, RAG 검색이나 서브에이전트의 문서 읽기를 대체하지 않습니다.
- 출처 간 상충하는 통계를 자동으로 하나의 합의값으로 조정(reconcile)해 주지 않습니다. 모순을 드러내 줄 뿐, 판단은 여전히 설계자와 사용자의 몫입니다.

### 3.2 신뢰도 점수 (Confidence Score)와 캘리브레이션 (Calibration)

**신뢰도 점수**란 모델이 추출한 각 값에 대해 "얼마나 확신하는가"를 함께 출력하게 하는 것입니다. 예: 이력서 파싱에서 "이름: 홍길동 (0.98), 졸업연도: 2019 (0.61)". 검토자는 점수가 낮은 필드부터 확인하면 되므로 한정된 시간을 효율적으로 씁니다.

**캘리브레이션(Calibration, 보정)** 이란: 모델이 0.9라고 말한 것들이 실제로 약 90% 정확한지를 **라벨링된 검증 세트(labeled validation set)**, 즉 정답이 붙어 있는 데이터와 비교해 검증하고, 어긋나면 점수를 보정하는 작업입니다. 검증 결과를 바탕으로 "0.85 미만은 사람이 검토"와 같은 **임계값(threshold)** 을 정할 수 있게 됩니다.

**캘리브레이션이 가능하려면 프롬프트 설계 단계에서 갖춰야 할 조건:**

1. **필드별(per-field) 점수** — 추출된 각 값 옆에 1:1로.
2. **일관된 수치 스케일(consistent numeric scale)** — 모든 필드, 모든 문서에서 동일하게(예: 0.0~1.0).
3. **빠짐없이 전 필드** — 일부만 출력하면 데이터셋이 불완전해집니다.

```json
{
  "name":            {"value": "홍길동", "confidence": 0.98},
  "email":           {"value": "hong@example.com", "confidence": 0.95},
  "graduation_year": {"value": 2019, "confidence": 0.61}
}
```

**부적합한 설계:**
- 숫자 대신 텍스트 설명만 출력 → 서술형은 정량적 통계 비교와 자동 임계값 판정이 불가능합니다.
- 문서 전체에 대한 단일 점수 → 어느 필드를 먼저 검토할지 알 수 없어 목적 자체를 달성하지 못합니다.
- 모델이 "어렵다"고 판단한 필드에만 점수 부여 → 데이터셋이 결측되어 통계적 평가 체계를 세울 수 없습니다. 게다가 무엇이 어려운지에 대한 모델의 판단 자체가 검증 대상입니다.

### 3.3 교차 검증과 종합 보고서 구조 (Corroboration)

**교차 검증(Corroboration)** 은 서로 다른 독립적인 출처가 같은 사실을 뒷받침하는 것을 말합니다.

**시나리오:** 여러 서브에이전트가 어떤 치료법의 작용 기전(mechanism of action)에는 일치하지만, 장기 부작용에 대해서는 단 하나의 소규모 연구만이 시사하고 다른 어떤 출처도 뒷받침하지 않습니다.

**올바른 보고서 구조:** 잘 교차 검증된 발견과, 단일 출처이거나 이견이 있는(contested / uncorroborated) 발견을 **별도의 섹션으로 분리**하고, 각 출처가 스스로 어떻게 특성화했는지(연구 규모, 한계 등)를 그대로 보존합니다.

```markdown
## 잘 교차 검증된 발견 (다수 출처 일치)
- 작용 기전: ... (출처 A, B, C, D)

## 단일 출처 / 미검증 발견 (해석 주의)
- 장기 부작용 가능성: 소규모 연구 1건(n=42)에서만 시사됨. 타 출처의 확인 없음. (출처 E)
```

**하면 안 되는 것:**
- 신뢰도가 다른 정보를 하나의 매끄러운 서술로 뭉치기 → 확실성의 차이를 은폐해 독자를 오도합니다.
- 미검증 발견을 검증된 발견과 같은 확신 어조(confidence language)로 서술하기 → 어조의 일관성보다 정보 가치의 정확성이 우선입니다.
- 단일 출처라는 이유로 아예 삭제하기 → 특히 안전 관련 리스크 신호를 임의로 누락하는 것은 위험합니다. **불확실한 정보는 삭제 대상이 아니라 라벨링 대상입니다.**

이는 2.1에서 본 "결손을 감추지 말고 표기하라"와 같은 원칙의 다른 얼굴입니다: **불확실성은 숨기지 말고 구조로 드러낸다.**

## 4. 품질 모니터링과 샘플링

### 4.1 왜 샘플링하는가

LLM 추출 파이프라인이 하루 수만 건을 처리한다면 모든 결과를 사람이 검토할 수는 없습니다. 그래서 일부를 뽑아(샘플링) 사람이 검증하고, 그 결과로 전체 품질을 추정합니다. 특히 모델이 "높은 신뢰도"라고 표시한 결과도 주기적으로 뽑아 봐야 3.2의 캘리브레이션이 유지되는지 알 수 있습니다.

### 4.2 층화 추출 (Stratified Sampling)

**층화(stratification)** 란 모집단을 의미 있는 하위 집단(**세그먼트/스트라텀**)으로 나눈 뒤 각 집단에서 따로 샘플을 뽑는 것입니다. 예: 문서 유형별로 나누기.

**볼륨 비례 샘플링(volume-proportional sampling)** 은 각 세그먼트의 물량 비율대로 샘플 수를 배분하는 방식입니다.

**문제:** 물량이 극도로 치우쳐 있을 때 소량 세그먼트가 **과소 샘플링(under-sampling)** 됩니다.

예를 들어 문서 유형 5종 중 한 유형이 일일 물량의 70%, 나머지 4종이 각 7.5%인 상황에서 하루 100건을 순수 비례로 뽑으면:

| 유형 | 물량 비율 | 비례 배분 샘플 수 |
|---|---|---|
| A | 70% | 70건 |
| B~E | 각 7.5% | 각 7~8건 |

7~8건으로는 그 유형의 오류율을 통계적으로 의미 있게 추정할 수 없습니다. 오류율이 10%여도 샘플에 0건이 잡힐 확률이 상당합니다. 즉 **소량 유형의 품질 저하를 아예 감지하지 못하는 사각지대**가 생깁니다.

**해결 — 최소 샘플 수 하한선(Minimum Sample Size Floor):** 물량 비율과 무관하게 각 세그먼트마다 최소 N건을 반드시 뽑도록 보장합니다.

```python
MIN_PER_TYPE = 30

def allocate(total, shares):
    n = {t: max(MIN_PER_TYPE, round(total * s)) for t, s in shares.items()}
    return n   # 총량은 늘어나지만 모든 세그먼트가 감지 가능해짐
```

**잘못된 대안:**
- "비례 샘플링은 항상 통계적으로 최적"이라는 생각 → 비례 배분은 **전체 평균 오류율**을 추정하는 데는 효율적이지만, **각 세그먼트별 오류를 탐지**하는 목적에는 최적이 아닙니다. 목적이 무엇이냐에 따라 최적 배분이 달라집니다.
- 대량 유형을 샘플링에서 완전히 제외 → 70%를 차지하는 유형의 오류는 전체 품질에 가장 큰 영향을 미칩니다. 제외가 아니라 하한선 추가가 답입니다.
- "프롬프트 템플릿이 같으면 문제없다"는 생각 → 같은 프롬프트를 써도 문서 포맷, 데이터 분포, 레이아웃 차이 때문에 유형별 오류율은 얼마든지 달라집니다. 과소 샘플링 문제는 프롬프트 구성과 무관하게 항상 고려해야 합니다.

## 5. 관통하는 설계 원칙 정리

1. **컨텍스트에 들어가는 모든 토큰은 비용이자 노이즈다.** 필요한 것만, 필요할 때 넣는다.
2. **큰 컨텍스트 윈도우는 컨텍스트 설계를 대체하지 못한다.** 구조가 없으면 크기를 늘려도 유실은 계속된다.
3. **중요한 것은 요약하지 말고 구조로 고정하라.** 숫자·ID·상태는 팩트 블록과 구조화 레코드로.
4. **개체는 ID로 구분하라.** 서술형에 뭉뚱그리면 모호성이 생긴다.
5. **주의력이 강한 위치(맨 앞)에 핵심을 배치하고, 헤딩으로 경계를 그어라.**
6. **부분 성공은 성공이다.** 살릴 수 있는 것은 살리고, 못 채운 부분은 표기한다.
7. **실패는 행동 가능한 형태로 보고하라.** 유형 + 시도 내역 + 부분 결과 + 대안.
8. **"데이터 없음"의 두 가지 의미를 절대 섞지 마라.** 못 읽은 것과 없는 것.
9. **모르면 지어내지 말고 드러내라.** 결손, 미검증, 모호성 모두 명시한다.
10. **한계에 도달하면 맥락과 함께 사람에게 넘겨라.** 무한 재시도도, 거짓 완료 보고도 아니다.
11. **추측으로 신원을 대신하지 마라.** 개인정보·금전 관련 판단은 확인 후에.
12. **품질은 측정 가능하게 만들어라.** 일관된 수치 척도, 캘리브레이션, 세그먼트별 최소 샘플.

## 6. 용어 사전 (Glossary)

| English Term | 한국어 설명 |
|---|---|
| **Context Window** | 컨텍스트 윈도우. 모델이 한 번에 볼 수 있는 입력 범위. 토큰 단위로 유한하며 비용과 직결된다. |
| **Token** | 토큰. 모델이 텍스트를 처리하는 최소 단위. 과금과 길이 제한의 기준. |
| **Context Engineering** | 컨텍스트 엔지니어링. 무엇을 컨텍스트에 넣고 뺄지, 어떻게 배치할지를 설계하는 기술 분야. |
| **Context Pollution** | 컨텍스트 오염. 불필요한 정보가 컨텍스트에 쌓여 모델의 정확도와 효율을 떨어뜨리는 현상. |
| **Context Trimming / Field Extraction** | 컨텍스트 트리밍 / 필드 추출. 도구 출력에서 작업에 필요한 필드만 골라 컨텍스트에 넣는 기법. |
| **Rolling Summarization** | 롤링 요약. 긴 대화의 앞부분을 주기적으로 요약해 대체하는 기법. 손실 압축이라 수치·ID가 유실되기 쉽다. |
| **Case-Facts Block** | 팩트 블록. 요약 대상에서 제외하고 원문 그대로 유지하는 핵심 사실(수치, ID, 상태) 구역. |
| **Structured Record** | 구조화 레코드. 개체 하나를 ID를 키로 하는 독립된 데이터 구조로 보관하는 방식. |
| **Blended Narrative** | 혼합 서술. 여러 개체 정보를 하나의 문장/단락으로 뭉뚱그린 형태. 모호성의 원인. |
| **Entity Ambiguity** | 엔티티 모호성. "그 청구", "그 금액"처럼 지시 대상이 특정되지 않는 상태. |
| **Disambiguation** | 모호성 해소. 추가 식별자를 요청하는 등으로 대상을 확정하는 절차. |
| **Lost in the Middle** | 긴 입력의 중간 부분 정보를 모델이 놓치는 현상. 성능이 U자 곡선을 그린다. |
| **Front-loading** | 프런트로딩. 핵심 요약을 문서 최상단에 배치해 주의력이 강한 위치를 활용하는 기법. |
| **Explicit Headings** | 명시적 헤딩. 섹션 제목으로 정보의 경계를 구조적으로 표시하는 것. |
| **Attention** | 어텐션(주의력). 모델이 입력의 각 부분에 얼마나 비중을 두는지를 결정하는 메커니즘. |
| **Agent** | 에이전트. 도구를 사용해 목표를 자율적으로 수행하는 LLM 기반 시스템. |
| **Tool Calling / Function Calling** | 도구 호출. 모델이 외부 함수를 호출하도록 요청하고 그 결과를 받아 이어가는 방식. |
| **Coordinator / Orchestrator** | 코디네이터 / 오케스트레이터. 작업을 분배하고 결과를 종합하는 상위 에이전트. |
| **Subagent** | 서브에이전트. 좁은 하위 작업을 담당하며 자체 컨텍스트를 갖는 하위 에이전트. |
| **Spawn** | 스폰. 새로운 서브에이전트를 생성·실행하는 행위. |
| **Synthesis Step** | 종합 단계. 여러 서브에이전트 결과를 하나의 최종 산출물로 합치는 단계. |
| **Manifest** | 매니페스트. 어떤 작업/영역이 이미 처리되었는지 기록한 인덱스. 중복 탐색 방지용. |
| **Scratchpad** | 스크래치패드. 에이전트들이 중간 결과를 기록·공유하는 컨텍스트 외부의 작업 공간. |
| **Redundant Exploration** | 중복 탐색. 이미 조사한 영역을 다시 조사해 비용과 시간을 낭비하는 것. |
| **Fault Tolerance** | 결함 허용성. 일부 구성요소가 실패해도 전체 시스템이 계속 동작하는 성질. |
| **Resiliency** | 회복탄력성. 장애 이후에도 유용한 결과를 내고 복구할 수 있는 능력. |
| **Partial Success / Partial Results** | 부분 성공 / 부분 결과. 일부만 완료된 작업의 유효한 산출물. 버리지 말고 활용한다. |
| **Coverage Gap** | 결손 영역. 수집·분석되지 못한 부분. 감추지 말고 보고서에 명시한다. |
| **Structured Failure Report** | 구조화된 실패 보고. 실패 유형·시도 내역·부분 결과·대안을 규격화해 전달하는 오류 보고. |
| **Failure Type** | 실패 유형. access_failure, timeout, validation_error 등 오류의 성격 분류. |
| **Recovery Path / Recovery Strategy** | 복구 경로 / 복구 전략. 재시도, 대체 에이전트 투입, 포기 중 무엇을 택할지의 계획. |
| **Retryable Failure** | 재시도 가능 실패. 일시적 원인이라 다시 시도하면 성공할 수 있는 오류. |
| **Access Failure** | 접근 실패. 데이터가 있을 수 있는데 읽지 못한 상태(캐시 만료, 네트워크 오류 등). |
| **Legitimate / Final Empty Result** | 정당한 빈 결과. 확인 결과 데이터가 실제로 존재하지 않는, 성공적으로 종료된 상태. |
| **Stale Cache** | 오래된 캐시. 허용 기한을 넘겨 신선하지 않은 캐시 데이터. |
| **Freshness Check** | 신선도 검사. 캐시 데이터가 허용 임계값 내에 있는지 확인하는 절차. |
| **Read Replica** | 읽기 복제본. 읽기 전용으로 운영되는 데이터베이스 사본. 기본 경로 실패 시 대안이 된다. |
| **Atomic Retry** | 원자적 재시도. 전부 성공하거나 전부 실패하게 묶어 재시도하는 방식. 로그 수집 등에는 불필요하게 과한 경우가 많다. |
| **Escalation** | 에스컬레이션. 에이전트가 해결 불가 상황을 사람 담당자에게 맥락과 함께 이관하는 것. |
| **Human-in-the-Loop** | 휴먼 인 더 루프. 사람이 판단·승인 지점으로 개입하도록 설계된 구조. |
| **Handoff** | 핸드오프. 작업을 다른 주체(사람 또는 다른 에이전트)에게 넘기는 행위. |
| **AI-First Support** | AI 우선 지원. AI가 먼저 설명·해결을 시도하고, 미해결이거나 재요청 시 사람에게 이관하는 지원 모델. |
| **Infinite Loop** | 무한 루프. 같은 실패 조치를 반복하며 자원만 소모하는 상태. |
| **Hallucination** | 환각. 모델이 근거 없는 내용을 사실처럼 생성하는 현상. 결손을 지어내 메우는 것은 의도적 환각이다. |
| **Grounding** | 그라운딩. 생성된 내용을 실제 근거 자료에 묶어 두는 것. |
| **Citations** | 인용 기능. 생성된 각 문장을 제공된 문서의 정확한 원문 구절에 연결해 클릭 검증을 가능하게 하는 기능. |
| **Per-statement Reference** | 문장별 참조. 문서 단위 목록이 아니라 문장 단위로 붙는 출처 표시. |
| **Corroboration** | 교차 검증. 서로 독립된 여러 출처가 같은 사실을 뒷받침하는 것. |
| **Contested / Uncorroborated Finding** | 이견 있는 / 미검증 발견. 단일 출처이거나 반박이 있는 정보. 별도 섹션으로 분리해 표기한다. |
| **Confidence Score** | 신뢰도 점수. 모델이 각 추출값에 대해 스스로 매기는 확신도 수치. |
| **Calibration** | 캘리브레이션(보정). 신뢰도 점수가 실제 정확도와 일치하는지 검증 세트로 확인하고 조정하는 작업. |
| **Labeled Validation Set** | 라벨링된 검증 세트. 정답이 부여된 평가용 데이터셋. |
| **Threshold** | 임계값. 이 점수 미만은 사람이 검토한다는 식의 자동 판정 기준선. |
| **Consistent Numeric Scale** | 일관된 수치 척도. 모든 필드·문서에서 동일한 범위(예: 0.0~1.0)를 쓰는 것. 정량 비교의 전제. |
| **Stratified Sampling** | 층화 추출. 모집단을 의미 있는 하위 집단으로 나눠 각각에서 샘플을 뽑는 방법. |
| **Segment / Stratum** | 세그먼트 / 층. 층화의 단위가 되는 하위 집단(예: 문서 유형). |
| **Volume-proportional Sampling** | 볼륨 비례 샘플링. 물량 비율대로 샘플 수를 배분하는 방식. 소량 세그먼트를 과소 샘플링한다. |
| **Under-sampling** | 과소 샘플링. 특정 세그먼트에서 통계적으로 부족한 수의 샘플만 뽑히는 문제. |
| **Minimum Sample Size Floor** | 최소 샘플 수 하한선. 물량과 무관하게 세그먼트별로 보장하는 최소 표본 수. |
| **Failure Mode** | 실패 모드. 시스템이 잘못되는 구체적인 양상(수치 유실, 이슈 혼동, 중간 유실 등). |
| **Anti-pattern** | 안티 패턴. 흔히 쓰이지만 해로운 설계 방식. |
