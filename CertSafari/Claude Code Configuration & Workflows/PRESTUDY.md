## 공통 기초

### Claude Code란 무엇인가

Claude Code는 Anthropic이 만든 **터미널(CLI) 기반 AI 코딩 에이전트**입니다. 터미널에서 `claude` 명령으로 실행하면
대화형 세션이 열리고, 사용자가 "이 함수 버그 고쳐줘" 같은 요청을 자연어로 하면 Claude가 직접 작업을 수행합니다.

일반 챗봇처럼 코드를 붙여넣고 답변을 받아 다시 붙여넣는 방식이 아니라, Claude가 **도구(Tool)** 를 써서 실제로 움직입니다.

| 도구 | 하는 일 |
|---|---|
| `Read` | 파일 내용 읽기 |
| `Write` | 파일 새로 쓰기 |
| `Edit` | 기존 파일 일부 수정 |
| `Grep` | 파일 내용 검색 |
| `Glob` | 파일 경로 패턴 검색 |
| `Bash` | 셸 명령 실행 (git, npm, 테스트 실행 등) |
| `WebFetch` 등 | 네트워크 요청 |

여기서 세 가지 성질이 따라 나오고, 이 노트 전체의 주제가 됩니다.

1. **파일시스템에 실제로 접근하고 명령을 실제로 실행한다.** 그래서 "무엇을 자동 실행해도 되는가"라는 **권한(permission)** 이 필요합니다.
2. **여러 턴에 걸쳐 반복 작업한다.** 그래서 **워크플로 선택**(바로 실행할 것인가, 먼저 계획할 것인가)과 **컨텍스트 관리**가 중요해집니다.
3. **설정 파일로 행동을 조종할 수 있다.** 그래서 `CLAUDE.md`, `.claude/rules/`, `.claude/skills/` 같은 **계층 구조**가 존재합니다.

### 컨텍스트 — 모든 설계의 이유

**컨텍스트(context)** 는 Claude가 지금 이 순간 "알고 있는" 텍스트 뭉치입니다. 대화 내용, 읽은 파일, 로드된 지침 파일이
모두 여기에 들어갑니다. 중요한 것은 그 반대편입니다 — **컨텍스트에 들어오지 않은 것은 Claude에게 존재하지 않습니다.**
저장소에 규칙 파일이 있어도 로드되지 않았다면 Claude는 그 내용을 모르고, 모델은 여러분의 파일시스템 전체를 자동으로 알지 못합니다.

LLM이 한 번에 볼 수 있는 텍스트 양에는 한계가 있고, 이 창을 **컨텍스트 윈도우(context window)** 라고 합니다.
여기에는 두 가지 비용이 붙습니다.

1. **토큰 비용** — 컨텍스트에 들어간 분량만큼 돈과 시간이 듭니다. 토큰은 모델이 텍스트를 세는 단위이며 비용과 처리 한도에 직결됩니다.
   세션마다 무조건 로드되는 내용이 크면 매 세션이 비싸집니다. 이를 **컨텍스트 발자국(context footprint)**, 세션당 비용이라고 부릅니다.
2. **주의력 희석(attention attenuation)** — 지시사항이 너무 많고 길어지면 모델이 개별 지시를 덜 확실하게 따릅니다.
   500줄짜리 지침 파일을 주면 오히려 준수율이 떨어지는 현상이 이것입니다.

그래서 Claude Code의 설정 체계 전체가 **"무엇을 항상 로드할 것인가 vs. 필요할 때만 로드할 것인가"** 라는 질문을 중심으로 설계되어 있습니다.
`CLAUDE.md` / rules / skills / commands / agents / hooks의 차이는 사실상 전부 이 질문에 대한 서로 다른 답입니다.

### 설정이 왜 계층으로 존재하는가

같은 종류의 지침이라도 적용되어야 할 범위가 다릅니다 — 나만, 이 프로젝트 팀 전체, 이 하위 디렉터리에서만, 조직 전체 강제.
Claude Code는 이 범위를 대부분 **파일이 놓인 경로**로 결정합니다. 그래서 같은 이름의 설정이나 스킬이 여러 위치에 존재할 수 있고,
충돌할 때 무엇이 이기는지를 정하는 **우선순위(scope precedence)** 규칙이 필요합니다. 이때 규칙은 병합이 아니라 **하나만 선택**하는 방식입니다.

계층에는 또 하나의 축이 겹칩니다. **"이 규칙이 반드시 지켜져야 하는가, 아니면 지켜지면 좋은가"** 입니다.

- **비결정론적(non-deterministic) 층 = 프롬프트/컨텍스트**: `CLAUDE.md`, rules, 스킬 본문 등. 모델에게 "이렇게 해라"고 **말해주는** 것입니다.
  모델은 확률적으로 동작하므로 대부분 따르지만 100%는 아닙니다.
- **결정론적(deterministic) 층 = 기술적 제어(technical control)**: 훅(hooks), 권한(permissions). 프로그램 코드가 도구 실행 자체를 **검사하고 막습니다.**
  모델의 판단과 무관하게 항상 작동합니다.

"Claude가 기억하거나 따르기로 선택하는 것에 의존하면 안 된다"는 요구가 있으면, 답은 언제나 프롬프트가 아니라 훅/권한 쪽입니다.

## 전체를 관통하는 원칙

### 1. 컨텍스트는 유한한 자원이다

항상 로드되는 지침은 최소화하고, 관련 있을 때만 들어오게 만듭니다(`paths`). 중복 로딩은 준수율을 높이지 않고 비용만 늘립니다.
크고 버려질 산출물(대규모 조사)은 서브에이전트로 격리하고 결론만 받습니다. 문서에서 경로를 언급만 하고 싶을 때는 백틱으로 감싸 임포트를 막습니다.

- 항상 필요한 것 → 루트 `CLAUDE.md`
- 특정 파일 종류에만 필요한 것 → `.claude/rules/` + `paths` 글로브
- 개인적으로 빼고 싶은 것 → `settings.local.json`의 `claudeMdExcludes`
- 대량의 탐색 출력 → 서브에이전트에 위임하여 격리

### 2. 모호성은 정보로만 해소된다

어조를 강하게 하거나 "알아서 해"라고 맡기는 것으로는 해결되지 않습니다. 구체적 예시(퓨샷)나 실행 가능한 테스트(TDD)처럼
**새로운 정보**를 넣어야 합니다. 요구사항은 인터뷰(`AskUserQuestion`)로, 버그 정의는 입출력 예시로 확정합니다.

### 3. 절차의 무게를 작업의 복잡도에 맞춰라

절차 자체에도 비용이 있습니다 — 계획 수립, 탐색, 승인 대기, 세션 분리는 모두 시간과 토큰을 씁니다.

- 되돌리기 쉬운 변경 → 직접 실행 / 되돌리기 어려운 변경(아키텍처, 데이터 모델, 서비스 경계) → 플랜 모드
- 정보가 어디 있는지 안다 → 직접 읽고 고치기 / 모르고 탐색 범위가 넓다 → 서브에이전트 위임
- 범위가 이미 눈앞에 다 보인다 → 바로 실행 / 조사·설계가 남아 있다 → 플랜 모드
- 요구사항이 모호하다 → 테스트를 먼저 써서 명세를 고정, 또는 인터뷰
- 출력 형식이 불명확하다 → 입력/출력 예시 제공. 기계가 소비할 출력이면 `--json-schema`
- 피드백은 결합도 기준으로 — 서로 얽힌 문제는 한 메시지에 함께, 무관한 것은 하나씩 순차적으로 각각 구체적 증상과 함께

### 4. 필드 이름을 그 동작이라고 믿지 말라

이름의 직관과 실제 의미가 어긋나는 지점이 실무 사고의 원인입니다. `allowed-tools`는 제한이 아니라 사전 승인이고,
`context: fork`는 파일 제거가 아니라 컨텍스트 분기이며, `--max-turns`·`--output-format`·`paths`도 이름만 보고 기대하는 일을 해주지 않습니다.

### 5. 단일 진실 공급원을 유지하라

복사본 대신 심볼릭 링크로 중앙 규칙을 참조하고, 흩어진 파일은 위치가 아니라 패턴으로 겨냥합니다.
심볼릭 링크는 파일·디렉터리 모두 가능하고 순환도 안전하므로, 확인할 것은 링크 대상이 맞는지뿐입니다.

### 6. 단계 사이에는 문서를 둔다

대화 기록이 아니라 자립형 스펙이 단계 간 전달 매체입니다. 헤드리스처럼 상태 없는 실행에는 필요한 상태를 명시적으로 주입합니다.

### 7. 권한은 화이트리스트로, 자동 편의성은 신뢰성과 상충한다

자동화 환경에서는 묻지 말고 거부(`dontAsk`)하고, 패턴은 필요한 만큼만 좁게 씁니다.
자동 탐색, 자동 임포트, 같은 세션 연속 작업은 편리하지만 각각 오염과 편향을 부릅니다.
신뢰성이 중요한 곳(자동화 파이프라인, 코드 리뷰)에서는 **명시성과 격리**를 택합니다 — `--bare` + 명시적 플래그, 별도 세션에서의 리뷰가 그 구현체입니다.

### 8. 진단은 "전달됐는가"부터

지시가 안 먹히면 지시문 자체를 의심하기 전에 로딩 여부를 확인합니다. `InstructionsLoaded` 훅으로 로딩 여부·시점·이유를 로깅할 수 있습니다.
clone 한 저장소에서 프로젝트 스킬 권한이 안 먹으면 **워크스페이스 신뢰**부터 확인합니다.

### 전체 지도 한 장

```
[ 무엇을 알려줄 것인가 — 컨텍스트 ]
  CLAUDE.md 계층      : cwd + 상위 → 시작 시 로드 / 하위 → 온디맨드
  @AGENTS.md          : 임포트로 공통 내용 끌어옴
  .claude/rules/*.md  : paths 없음 → 시작 시 무조건 / paths 있음 → 매칭 파일 Read 시 조건부
  Compaction          : 루트 CLAUDE.md는 재주입, 중첩 파일은 다시 읽을 때 복귀
  진단                : InstructionsLoaded 훅으로 로딩 여부·시점·이유 로깅

[ 무엇을 허용할 것인가 — 권한 ]
  plan          : 읽기 전용, 읽기는 무승인
  acceptEdits   : 파일 편집 + mkdir/mv/cp 자동승인, 셸/네트워크는 별도 허용 필요
  allowedTools / permissions.allow : 명시적 허용
  managed-settings.json (시스템 디렉터리) : 최고 우선순위, 개인이 못 끔
  같은 이름 충돌 : Enterprise > Personal(~/.claude) > Project(.claude) > Plugin
                   (병합이 아니라 하나만 선택)

[ 어떻게 일할 것인가 — 워크플로 ]
  범위 작고 명확        → 직접 실행
  범위 넓고 모호        → 플랜 모드
  구현 전 요구사항 발굴 → AskUserQuestion 인터뷰
  구현 정확도           → 테스트 먼저 → 구현 → 실패 공유 반복
  피드백 그룹핑         → 결합된 것은 묶고 무관한 것은 분리

[ 어떻게 자동화할 것인가 — CLI ]
  -p                          : 비대화형 실행
  --output-format json
  + --json-schema             : 응답 구조 강제 (파싱 가능)
  --output-format stream-json : 실시간 관찰용 (구조 강제 아님)
  --bare                      : 자동 탐색 끄고 재현성 확보
```

### 어디에 무엇을 둘 것인가

```
~/                                       # 홈 (Git 밖, 나만)
└── .claude/
    ├── CLAUDE.md                        # 내 모든 프로젝트 공통 지침
    ├── commands/my-standup.md           # 개인 명령어 (레거시 구조)
    ├── skills/my-standup/SKILL.md       # 개인 스킬 ★현재 권장
    └── settings.json                    # 개인 CLI 설정

<프로젝트 루트>/                          # Git 안
├── CLAUDE.md                            # 팀 공유 프로젝트 지침 (커밋)
├── CLAUDE.local.md                      # 개인용 프로젝트 지침 (.gitignore)
├── .gitignore
└── .claude/
    ├── rules/                           # 재귀 탐색됨
    │   ├── security-review.md           # → 중앙 원본으로 symlink 가능
    │   ├── frontend/react.md
    │   └── backend/api.md
    ├── commands/lint-report.md          # 팀 공유 명령어 (커밋)
    ├── skills/migration-plan/SKILL.md   # 팀 공유 스킬 (커밋)
    └── settings.local.json              # 개인 권한/CLI 설정 (JSON)
```

- **팀 전체가 써야 하나?** → 프로젝트 `.claude/` 안에 두고 커밋. 커밋하면 그것이 곧 배포입니다.
- **나만 써야 하나?** → `~/.claude/` (또는 프로젝트 안 + gitignore). 홈의 `~/.claude/CLAUDE.md`는 개인 취향만 담습니다.
- **여러 저장소에 걸쳐 동일해야 하나?** → 중앙 원본 + 각 저장소에 symlink.
- **특정 파일 종류에만 적용해야 하나?** → `.claude/rules/`에 `paths:` 프론트매터. 하위 폴더까지 잡으려면 `**`를 반드시 씁니다.
- **문서형 지침인가, 권한/CLI 설정인가?** → 전자는 `.md`, 후자는 `settings*.json`.
- **파일을 실제로 로드하려면** `@경로`. 사람에게 안내만 하려면 백틱으로 감쌉니다.

## 오개념 정리 — 실제로 존재하지 않는 기능들

학습 과정에서 그럴듯하게 들리지만 실제로는 없는 동작들입니다. 미리 알아두면 혼동을 막을 수 있습니다.

- `CLAUDE.md`의 `effort: low` 프론트매터가 지침을 축약 로드해준다 → **없음**
- `CLAUDE_core.md`, `CLAUDE_compliance.md`처럼 나누면 알파벳순 첫 파일만 로드된다 → **없음**
- `CLAUDE.md` 안에 Claude가 오버라이드할 수 없는 "managed policy" 계층이 있다 → **없음** (강제력은 시스템 디렉터리의 `managed-settings.json` 쪽)
- rules 프론트매터의 경로 지정 키가 `include`다 → **없음** (`paths`)
- 커맨드 파일은 투명한 압축(transparent compression)을 거쳐 컨텍스트가 줄어든다 → **없음**
- 커맨드는 모든 사용자 메시지 전에 자동 실행된다 → **없음** (직접 입력해야 함)
- `allowed-tools`에 `Write*`처럼 와일드카드를 붙여야 제한이 걸린다 → **없음** (애초에 제한이 아니라 사전 승인)
- `allowed-tools`는 스킬 종료 후에 평가된다 → **없음**
- `model: inherit`로 Claude의 자율 도구 선택을 재정의한다 → **그런 동작 아님**
- `context: fork`가 도구를 샌드박싱하고 미등록 도구를 차단한다 → **그런 동작 아님** (컨텍스트 격리 용도)
- 같은 이름 스킬이 있으면 이름 충돌 에러가 나거나 병합/순차 실행된다 → **없음** (우선순위로 하나만 선택)
- 직접 실행 모드는 한 번에 한 파일만 수정할 수 있다 → **사실 아님**
- `--output-format stream-json`이 출력 구조를 강제해준다 → **아님** (구조 강제는 `--json-schema`)
- 이름이 그럴듯한 옵션이 원하는 일을 해준다 → `--max-turns`, `--output-format`, `paths`는 각각 실제 의미를 확인하고 써야 합니다
