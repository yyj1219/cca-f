## 질문 1

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : A single extraction pass over 60-page contract bundles produces detailed results for early sections but sparse or missing fields for later ones, and identical clause types are classified inconsistently across sections. How should the extraction be restructured?

**A.** Switch to a model with a larger context window so all sections receive adequate attention within a single pass.

**설명**

이는 흔한 오해다. 컨텍스트 윈도우에 더 많은 콘텐츠를 담는 것만으로는 분석 품질이 개선되지 않는다. 묶음 문서는 이미 윈도우에 들어갈 수도 있으며, 실제 문제는 길고 복잡한 문서를 한 번의 패스로 처리할 때 일부 섹션의 가중치가 낮아지는 경향이 있다는 것이다. 이로 인해 윈도우 크기와 무관하게 결과가 얕아진다.

**B.** Run the single-pass extraction three times and keep only field values that agree across at least two of the runs.

**설명**

동일한 단일 패스의 약점을 공유하는 실행 결과들에 대해 다수결을 적용해도 소외된 섹션의 깊이는 회복되지 않는다. 모든 실행에서 희소하게 추출된 필드는 여전히 누락되며, 합의(consensus) 방식은 단 한 번의 실행에서만 나타난 올바른 값을 오히려 걸러낼 수 있다.

**C(정답).** Extract each section in its own focused pass, then run a separate pass to reconcile cross-section references and totals.

**설명**

정답이다. 깊이가 불균일하고 분류가 상충되는 이 실패 패턴은 매우 길고 복잡한 문서에 대한 단일 패스 분석에서 흔히 나타나는 특징이며, 중간이나 후반부의 내용일수록 가중치가 낮아지기 쉽다. 섹션별 패스는 국지적 필드에 대해 더 일관된 깊이를 유지하도록 도와 세부 사항 누락 가능성을 줄이며, 별도의 조정(reconciliation) 패스는 여러 섹션에 걸친 값을 처리한다.

**D.** Mark every field required in the JSON schema so shallow extractions fail validation and trigger automatic retries.

**설명**

스키마는 구조를 강제할 뿐 추출 품질을 보장하지는 않는다. 섹션이 얕게 처리된 상태에서 필드를 필수로 지정하면 모델은 정확하게 추출하는 대신 값을 지어내도록 압박받는다. 동일하게 과부하된 단일 패스에 대한 재시도 역시 같은 근본적 약점을 그대로 물려받는다.

### 전반적인 설명

이 상황의 증상은 매우 길고 복잡한 문서에 대한 단일 패스 분석의 특징적인 양상이다. 일부 부분에서는 결과가 철저하지만 다른 부분에서는 얕아지고, 판단이 일관되지 않아지며(같은 조항 유형이 위치에 따라 다르게 처리됨), 중간이나 후반부의 내용일수록 가중치가 낮아지기 쉬운데, 이는 흔히 "lost in the middle" 위험이라고 불린다. 여기서 유지해야 할 사고 모델은 컨텍스트 용량과 분석 품질이 서로 별개라는 것이다. 문서가 윈도우에 들어가더라도, 균일하게 깊은 단일 패스 추출을 하기에는 여전히 너무 클 수 있다.

해결책은 대규모 다중 파일 코드 리뷰에 사용되는 것과 동일한 분해 패턴이다. 작업을 단위별(여기서는 섹션별)로 집중된 로컬 패스들로 나누고, 각 패스는 하나의 한정된 임무만 수행하도록 하며, 이후 별도의 통합 패스에서 섹션 간 참조, 반드시 일치해야 하는 합계, 분류 일관성 등 단위 간(cross-unit) 문제만을 검토한다. 이는 프롬프트 체이닝(prompt chaining)의 한 형태로, 각 프롬프트가 하나의 한정된 임무만 가지므로 정확도와 추적 가능성이 향상된다. 이는 섹션 간 더 일관된 깊이를 유지하도록 도와주며, 단위를 넘나드는 분석을 부수 효과가 아닌 명시적 단계로 만들어준다. 더 강력한 성능을 위해 복잡한 프롬프트를 체이닝하는 방법과 긴 컨텍스트 프롬프팅 팁을 참고하라.

대안들은 모두 근본 원인을 놓치고 있다. 더 큰 컨텍스트 윈도우는 용량 문제를 다룰 뿐, 긴 문서에 대한 단일 패스 분석의 불균일한 품질 문제는 해결하지 못한다. 반복된 단일 패스에 대한 다수결은 동일한 체계적 약점을 공유하는 실행들의 평균을 내는 것이므로, 지속적으로 소외된 섹션은 결코 회복되지 않는다. 모든 필드를 필수로 지정해 스키마를 강화하는 것은 오히려 해롭다. JSON 스키마는 출력 형태를 보장할 뿐 추출 품질을 보장하지 않으며, 얕게 처리된 섹션에서 필수 값을 강제하는 것은 정확히 모델이 그럴듯해 보이는 데이터를 지어내는 조건을 만드는 것이다.


## 질문 2

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : The pipeline downloads batch results as a .jsonl file and matches each result line to its source document by line position; some extractions end up attached to the wrong records. What is the correct correlation design?


**A(정답).** Assign each request a unique custom_id derived from the document identifier at submission and match results on that field.

**설명**

정답이다. custom_id 필드는 개발자가 직접 지정하는 값으로, 각 배치 결과를 원래 요청과 연결하기 위해 존재한다. 결과의 순서가 제출 순서와 일치한다는 보장이 없으므로, custom_id는 신뢰할 수 있는 매칭을 위해 문서화된 메커니즘이다.

**B.** Poll processing_status until the batch reports ended before downloading results, since positional matching is only reliable once every request has finished.

**설명**

processing_status가 ended가 될 때까지 기다리는 것은 결과를 사용할 수 있게 되기 전에 필요한 절차이지만, 이것만으로 위치 기반 매칭이 안전해지지는 않는다. 완전히 완료된 배치에서도 결과 순서가 요청 순서와 일치한다는 보장은 없으므로, 이 방법은 매칭 오류 버그를 그대로 남긴다.

**C.** Split each nightly run into smaller batches so that results within any single batch preserve the order of the submitted requests.

**설명**

결과 순서는 배치 크기와 무관하게 어떤 배치에서도 보장되지 않는다. 배치를 작게 나누면 제출 및 폴링 오버헤드만 늘어날 뿐, 위치 기반 매칭이 지원되지 않는다는 근본적인 사실은 변하지 않는다.

**D.** Sort the downloaded results file by the message id contained in each result so the lines align with the original submission order.

**설명**

성공한 결과에 포함된 message id는 API가 생성한 것으로 제출 순서와 아무런 관계가 없으므로, 이를 기준으로 정렬해도 원래 순서를 재구성할 수 없다. 오류(errored), 취소(canceled), 만료(expired)된 결과에는 message 자체가 존재하지 않으므로, 이 방식은 실패가 발생하면 무너진다.

### 전반적인 설명

Message Batches API는 "제출 후 잊어버리는(fire-and-forget)" 방식의 비동기 시스템이다. requests 배열을 제출하면 배치는 최대 24시간에 걸쳐 처리되며, 결과는 결국 .jsonl 파일로 스트리밍되어 돌아온다. 문서에는 결과가 반드시 요청이 제출된 순서로 반환되는 것은 아니며 임의의 순서로 반환될 수 있다고 명시되어 있다. 따라서 위치 기반 매칭(줄 번호, 배열 인덱스)은 의미가 없으며, 애플리케이션은 각 결과를 명시적으로 원래 요청과 연결해야 한다.

이 문제를 해결하기 위해 설계된 메커니즘이 custom_id다. 제출된 requests 배열의 각 항목은 params와 함께 개발자가 지정한 custom_id(배치 내에서 고유해야 하며, 문자·숫자·하이픈·밑줄로 구성된 1~64자)를 가진다. 결과 파일의 모든 줄은 해당 결과 객체와 함께 이 custom_id를 그대로 반영하므로, 자신의 문서 키(예: doc-invoice-2024-001)로부터 식별자를 도출하면 원본 레코드와 추출 결과 사이에 지속적인 조인 키가 생긴다. 이는 실패 처리도 깔끔하게 해준다. 결과는 succeeded, errored, canceled, expired 중 하나가 될 수 있으며, custom_id는 어떤 문서를 수정해서 재제출해야 하는지 정확히 알려주므로 이미 성공한 요청을 다시 처리할 필요가 없다.

대안들은 모두 순서 보장이 어디에 있는지를 잘못 이해하고 있다. message.id로 정렬하는 방법은 그 식별자가 처리 시점에 생성되고 성공하지 않은 결과에는 존재하지 않기 때문에 실패한다. processing_status가 ended가 될 때까지 폴링하는 것은 다운로드 전에 반드시 필요하지만, 완료되었다는 사실이 순서를 만들어내지는 않는다. 그리고 배치 크기를 줄이는 것은 아무것도 바꾸지 못한다. 어떤 크기의 배치도 결과 순서를 보장하지 않기 때문이다. Batch processing과 Create a Message Batch 참조 문서를 참고하라.


## 질문 3

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : A nightly extraction batch completes with errored results: most are invalid_request_error failures caused by documents that exceeded the context limit, and a few are server errors. How should the team construct the retry submission?

**A.** Resubmit the entire original batch, since errored requests were not billed and reprocessing the successful requests adds no extra cost.

**설명**

과금이 되지 않는 것은 오류(errored), 취소(canceled), 만료(expired)된 요청뿐이며, 이미 성공적으로 처리된 요청은 과금되었고 재제출하면 다시 과금된다. 실패한 소수를 재시도하기 위해 전체 자료를 다시 처리하는 것은 비용과 시간을 낭비하는 것이며, 이는 정확히 custom_id를 통한 매칭이 피하고자 하는 문제다.

**B.** Resubmit every errored request unchanged in a new batch, since invalid_request_error failures are usually transient and resolve on retry.

**설명**

서버 오류는 수정 없이 그대로 재시도할 수 있지만, invalid_request_error는 요청 본문 자체가 유효하지 않다는 것을 나타내므로 재전송 전에 반드시 수정해야 한다. 컨텍스트 한도를 초과한 문서는 청크로 나누기 전까지는 동일한 실패를 반복할 것이다.

**C(정답).** Chunk the oversized documents, give each chunk a unique custom_id, and resubmit the chunks plus the server-error requests as a new batch.

**설명**

이는 문서화된 재시도 패턴과 일치한다. invalid_request_error 결과는 재전송 전에 수정해야 하므로 크기가 초과된 문서는 청크로 나누고, 서버 오류는 그대로 재시도할 수 있다. 각 청크는 자신만의 custom_id가 필요한데, 이는 이 필드가 배치 내에서 고유해야 하며 결과가 custom_id로 다시 매칭되기 때문이다.

**D.** Split each oversized document into chunks that all reuse the original custom_id so results still correlate to one source document.

**설명**

custom_id 값은 하나의 Message Batch 내에서 고유해야 하므로, 여러 청크가 하나의 식별자를 공유할 수 없다. 원본 문서와의 연결은 출처와 청크 인덱스를 서로 다른 custom_id 값에 인코딩함으로써 처리된다.

### 전반적인 설명

Message Batches API는 각 요청을 독립적으로 처리하므로, 하나의 요청이 실패해도 다른 요청에는 영향을 주지 않는다. 요청별 결과 유형은 succeeded, errored, canceled, expired이며, 각 결과 줄에는 개발자가 지정한 custom_id가 포함된다. 결과는 순서 보장이 없는 스트리밍 .jsonl 파일로 도착하므로, custom_id는 실패를 원본 문서에 다시 매핑할 수 있는 유일하게 신뢰할 수 있는 방법이며, 이것이 선택적 재제출을 가능하게 한다. 즉 실패한 부분만 수정하여 재전송하고, 이미 과금된 성공 건은 절대 다시 보내지 않는다.

재시도 자체는 오류 유형에 따라 구분해야 한다. Anthropic의 가이드는 재전송 전에 요청 본문을 수정해야 하는 invalid_request_error와, 수정 없이 바로 재시도할 수 있는 서버 오류를 구분한다. 컨텍스트 한도를 초과한 문서는 전자에 속한다. 수정 없이 재제출하면 같은 실패가 반복되므로 먼저 청크로 나누어야 한다. 문서를 여러 청크로 나누면 각 청크는 별도의 요청이 되며 자신만의 custom_id가 필요하다. 이 필드는 배치 내에서 고유해야 하고 제한된 패턴(문자·숫자·밑줄·하이픈으로 구성된 1~64자)을 따라야 한다. 흔히 사용하는 방식은 원본 문서 ID와 청크 인덱스를 함께 인코딩하는 것으로, 이렇게 하면 이후 재조립 과정이 결정적(deterministic)으로 유지된다.

오답들은 각각 이 모델의 한 부분을 깨뜨린다. 유효하지 않은 요청을 수정 없이 재시도하는 것은 실패가 구조적이라는 사실을 무시하는 것이고, 여러 청크에 하나의 custom_id를 재사용하는 것은 고유성 제약을 위반하는 것이며, 배치 전체를 재제출하는 것은 이미 성공한 모든 요청에 대해 두 번 비용을 지불하는 것이다. 문서화된 동작에 대해서는 Batch processing과 Create a Message Batch를 참고하라.


## 질문 4

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : The team adds a per-field confidence score to each extraction and plans to auto-accept high-confidence results while routing low-confidence ones to human review. What should they do before relying on these scores for routing in production?

**A.** Replace the numeric scores with a model-set route_to_human boolean so each extraction arrives with an unambiguous routing decision already made.

**설명**

신뢰도를 이진 플래그로 축약하는 것은 라우팅 판단을 동일하게 보정되지 않은 자기평가에 위임하는 것이며, 팀이 조정할 수 있는 임계값을 제거해 버린다. 레이블된 데이터로 검증된 숫자 점수는 정확도 목표나 검토 역량이 변할 때 라우팅을 조정할 수 있게 해주지만, 고정된 불리언 값은 그렇지 못하다.

**B.** Set the sampling temperature to zero so the reported confidence values become deterministic and consistent enough to use without further checks.

**설명**

temperature를 낮추면 실행 간 출력 변동이 줄어들지만, 신뢰도 값이 실제 정확도를 반영하도록 만들어주지는 않는다. 일관되게 잘못 보정된 점수는 여전히 잘못 보정된 점수일 뿐이다. 결정론적(deterministic)이라는 것과 보정(calibration)되었다는 것은 같지 않다.

**C.** Trust the scores as reported, since the model generates them together with the extraction and can directly assess its own field-level certainty.

**설명**

추출과 함께 신뢰도 값을 생성한다고 해서 그 값이 신뢰할 만한 것이 되지는 않는다. 스스로 밝힌 신뢰도는 체계적으로 과신되거나 과소평가될 수 있다. 레이블된 결과와 대조해보지 않고 원시 점수를 라우팅에 그대로 사용하면, 잘못된 추출을 자동 승인하고 정작 올바른 추출로 검토자를 불필요하게 넘치게 할 위험이 있다.

**D(정답).** Validate the self-reported scores against a labeled document sample to confirm they track actual accuracy, then derive routing thresholds from that data.

**설명**

정답이다. 모델이 스스로 보고하는 신뢰도는 유용한 신호이지만, 기본적으로 잘 보정되어 있다는 보장은 없다. 실제 정답 레이블과 점수를 비교해 측정하면 높은 신뢰도가 실제로 높은 정확도와 상응하는지 알 수 있으며, 팀이 원하는 자동 승인/인간 검토 비율을 만들어내는 임계값을 설정할 수 있게 된다.

### 전반적인 설명

스스로 보고하는 신뢰도는 보정된(calibrated) 검토 라우팅을 가능하게 한다. 모델이 확신하는 추출 결과는 곧바로 다운스트림 시스템으로 흘러가고, 불확실한 것은 사람에게 전달된다. 이 패턴에서 실제로 중요한 것은 "보정되었다(calibrated)"는 단어다. 신뢰도 점수는 실제로 정확성을 예측할 때만 라우팅에 유용하며, 언어 모델의 자기평가가 반드시 그렇다는 보장은 없다. 점수가 척도의 상단에 몰릴 수도 있고, 필드 유형에 따라 달라질 수도 있다. 이 패턴을 안전하게 만드는 엔지니어링 단계는 경험적인 검증이다. 레이블된 샘플에 대해 추출기를 실행하고, 보고된 각 신뢰도를 해당 필드가 실제로 맞았는지와 비교한 뒤, 관측된 오류율이 목표 정확도를 만족하는 지점에서 임계값을 정한다. 샘플을 문서 유형별로 층화(stratify)하면 쉬운 사례뿐 아니라 어려운 사례에서도 임계값이 정직하게 유지된다.

이는 "찾아내는 것(finding)"과 "걸러내는 것(filtering)"을 분리하라는 Anthropic의 전반적인 가이드와도 일치한다. 모델이 출력과 함께 신뢰도 신호를 보고하도록 하고, 무엇을 받아들이고 순위를 매기고 상위로 올릴지에 대한 판단은 모델의 내부가 아니라 여러분이 통제하는 다운스트림 단계에 두어야 한다는 것이다. 검증 또는 필터링 단계가 결과의 순위를 매길 수 있도록 발견 항목에 신뢰도 수준을 부여하는 권장 패턴은 Prompting Claude Sonnet 5를 참고하라.

각 대안은 이 패턴을 깨뜨린다. 원시 점수를 그대로 신뢰하는 것은 한 번도 측정된 적 없는 보정을 가정하는 것이다. 모델이 정하는 route_to_human 불리언은 라우팅 판단을 보정되지 않은 자기평가로 옮기고 조정 가능한 임계값을 없애버려, 팀이 검토 부담과 정확도 사이에서 트레이드오프를 할 수 없게 만든다. temperature를 0으로 설정하면 출력이 더 반복 가능해지지만, 자신의 신뢰성에 대해 일관되게 틀린 점수를 교정하지는 못한다.

**설명**

이는 주된 아키텍처로는 적절하지 않다. 일관되지 않은 결합 실행들에 대해 다수결을 적용하면 실제 신호를 억제할 수 있다. 단 한 번의 실행에서만 올바르게 추출된 필드는 버려지게 된다. 여러 실행을 비교하는 것은 보조적인 검증 수단으로는 쓸 수 있지만, 문서별 집중 추출과 별도의 통합 패스를 대체하지는 못한다.

**설명**

**설명**

이는 정답이다. 통합 패스는 단일 문서 패스에서는 볼 수 없는 관계, 예를 들어 송장이 참조하는 구매 주문서 합계와 같은 것을 포착하기 위해 존재한다. 필드 단위 추출을 문서별 패스에 유지하면 분리를 하게 된 이유인 일관된 깊이가 보존된다.

### 전반적인 설명

다중 패스 설계의 근간이 되는 사고 모델은, 언어 모델이 단지 유한한 컨텍스트 윈도우만 가지는 것이 아니라 패스당 유한한 주의력(attention)을 가진다는 것이다. 여러 문서를 함께 분석하면 그 주의력은 불균일하게 분산되는 경향이 있다. 일부 문서는 깊이 처리되지만 다른 문서는 필드가 희소해지고, 동일한 패턴이 위치에 따라 다르게 판단된다. 이것이 주의력 분산(attention dilution)이며, 이는 근본적으로 용량 문제가 아니라 품질 문제다. 컨텍스트 용량을 늘리는 것만으로는 긴 컨텍스트에서의 품질 문제가 안정적으로 해결되지 않으므로, 같은 묶음을 더 큰 윈도우에 넣는 것은 집중된 패스를 대체할 신뢰할 만한 방법이 아니다.

해결책은 작업의 분담이다. 문서별 패스는 국지적 추출을 담당하며, 모든 문서에 모델의 온전한 주의력과 일관된 깊이를 부여한다. 별도의 통합 패스는 문서 간 관점에서만 포착할 수 있는 것들, 즉 구매 주문서와 일치해야 하는 송장 합계, 항목이 참조하는 배송 수량, 문서 간 상충되는 날짜 등을 다룬다. 모든 것을 다시 추출하는 대신 통합 패스의 범위를 이러한 문서 간 관계로 한정하면, 각 패스가 자신이 가장 잘 수행할 수 있는 분석에 집중할 수 있다. 이는 복잡한 작업을 집중된 순차 단계들로 분해하라는 Anthropic의 프롬프트 체이닝 원칙과 동일하다.

오답들은 각각 시사점이 있는 이유로 틀렸다. 결합 패스를 반복해서 다수결을 취하는 방식은 Best-of-N 비교라는 정당한 사촌 기법을 가지고 있으며, 이는 보조적인 검증 기법으로는 유용할 수 있다. 그러나 핵심 아키텍처로 사용하면 일관된 문서별 주의력을 회복시키지 못한 채 잡음을 평균 내는 것에 불과하며, 단 한 번의 실행에서만 나타난 올바른 추출은 버려지게 된다. 그리고 스키마 검증에 의존하는 것은 구조적 보장과 의미적 보장을 혼동하는 것이다. 스키마는 각 추출이 올바른 필드를 가진 형식이 맞는 JSON임을 보장하지만, 묶음 내 문서들 간에 값이 실제로 일치하는지에 대해서는 아무런 가시성이 없다. 문서 간 일관성을 확인하려면 문서들을 서로 연관지어 보는 패스가 필요하다.

### 전반적인 설명

비형식적인 계량 표현은 few-shot 프롬프팅이 산문식 지시를 능가하는 대표적인 사례다. 예시 기반 프롬프팅에 대한 Anthropic의 가이드는 관련성 있고, 다양하며, 구조화된 예시를 권장한다. 실제 사용 사례를 반영하고 엣지 케이스를 의도적으로 포함해야 하는데, 비형식적인 수량과 혼재된 문서 레이아웃이 바로 그런 경우다. 다만 이 주장의 한계도 짚어둘 필요가 있다. 예시는 정확도와 일관성을 개선하지만 환각을 완전히 없애지는 못하므로, 추출된 값에 대한 검증은 여전히 가치가 있으며, 이는 Anthropic의 환각 감소 가이드에서 다루는 내용이다.

오답들은 각각 실패 양상을 놓치고 있다. 모든 경우를 나열하는 변환 테이블은 무한한 입력 공간을 뒤쫓는 것이며, 새로운 표현에 대해서는 여전히 모델을 안내하지 못한다. temperature에 의존하는 것은 문제를 잘못 진단한 것이다. 이 매개변수는 토큰 선택의 무작위성만 조절할 뿐, 출력이 원문에 근거하도록 만들지는 못하므로, 지어낸 값은 단지 반복 가능한 지어낸 값이 될 뿐이다. 그리고 스키마를 엄격한 필수 숫자 필드로 강화하는 것은 상황을 더 악화시킨다. 문서에 구체적인 숫자가 없을 때 필수 필드는 모델의 정직한 선택지를 제거하고 지어내기를 유도한다. 이것이 바로 원본 데이터가 비형식적이거나 없을 수 있는 경우 스키마 설계 가이드에서 nullable하거나 근사값에 친화적인 필드를 권장하는 이유다.

**설명**

가장 가까운 기존 값을 선택하는 것은 정확히 이미 발생하고 있는 실패 그 자체이며, 이를 명시적으로 지시하는 것은 오분류를 제도화하는 것에 불과하다. 스키마는 어휘 밖의 유형에 대해 정당한 출구를 제공해야 하며, 이는 프롬프트 지시만으로는 제공할 수 없다.

**D.** Expand the enum with every new category observed so far and redeploy the schema after each addition.

**설명**

관찰된 모든 카테고리를 나열하는 것은 끝없는 유지보수 부담을 만들며, 다음에 처음 보는 문서 유형이 도착하는 순간 다시 실패한다. 폐쇄형 목록은 아무리 길어도 개방형 입력 분포를 예상할 수 없다.

### 전반적인 설명

JSON 스키마의 enum은 하나의 계약이다. 모델은 나열된 값 중 하나를 내놓아야 하며, 다운스트림 시스템은 별도의 정규화 로직 없이 그 어휘를 신뢰할 수 있다. 여기서 트레이드오프는 enum이 폐쇄형이지만 실제 문서 스트림은 개방형이라는 점이다. 스키마가 어휘 밖의 입력에 대해 정직한 답을 제공하지 못하면, 모델은 거부하지 않고 그중 가장 덜 잘못된 값을 골라 제약을 만족시키는데, 이는 구조적으로는 유효하지만 의미적으로는 오염된 결과다. 이는 필수 필드가 지어낸 값을 강제하는 것과 같은 계열의 실패다. 스키마가 "위 어느 것도 아님"이라고 말할 정당한 방법을 남겨두지 않는 것이다.

"other"와 세부 문자열을 결합한 패턴은 이 긴장을 해소한다. enum은 알려진 카테고리에 대한 보장을 유지하고, "other"는 모델에게 진실한 도피구를 제공하며, 자유 텍스트 세부 필드는 문서가 실제로 무엇인지를 기록한다. 이 세부 필드는 또한 운영상의 피드백 채널이 되기도 한다. "other"에 무엇이 몰리는지 검토하면 어떤 카테고리가 enum으로 승격될 자격을 얻었는지 알 수 있으므로, 어휘 확장은 스키마 재배포가 아니라 근거에 의해 이루어진다. 관련 기법으로는 진짜로 애매한 경우를 위해 "unclear" 값을 추가하는 것이 있는데, 이는 "어휘 밖"과 "확신 있게 분류할 수 없음"을 구분해준다.

enum을 자유 형식 문자열로 바꾸는 것은 한 가지 실패를 다른 실패로 바꾸는 것일 뿐이다. 이제 라우팅은 모델이 일관되지 않게 지어내는 레이블에 의존하게 된다. 관찰된 카테고리를 계속 추가하는 방식도 격차를 결코 좁히지 못한다. 다음에 등장하는 새로운 유형이 항상 먼저 오분류되기 때문이다. 그리고 모델에게 가장 가까운 값을 고르도록 지시하는 것은 스키마 변경으로 없애려던 그 억지 끼워맞추기를 그대로 규정해버리는 것이다. 입력 스키마가 모델 출력을 어떻게 제약하는지에 대해서는 Tool use with Claude를 참고하라.


## 질문 8

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : The extraction prompt instructs Claude to "only extract values you are highly confident about," yet fields are still populated with guessed values from ambiguous passages. What change most improves extraction precision?

**A.** Rewrite the instruction as "extract a value only when you are absolutely certain it appears in the document".

**설명**

이는 주관적인 지시를 더 강한 어조로 바꿀 뿐 어떤 운영상의 내용도 추가하지 않는다. "absolutely certain"은 "highly confident"만큼이나 해석이 불가능하므로, 모델의 추출 행동은 여전히 일관되지 않게 남는다.

**B(정답).** Replace the confidence wording with explicit rules defining when a field may be populated and when it must be null.

**설명**

이는 정답이다. 구체적이고 검증 가능한 기준은 모델에게 실행 가능한 판단 규칙을 제공한다. 예를 들어 문서가 날짜를 명시적으로 표기한 경우에만 날짜 필드를 채우고 그렇지 않으면 null을 반환하도록 하는 것이다. 모호한 신뢰도 표현은 운영상의 내용이 전혀 없으므로, 모델은 문서마다 다르게 해석하게 된다.

**C.** Have the model attach a self-rated confidence score to each extracted field and discard values below a fixed threshold.

**설명**

스스로 보고하는 신뢰도 점수는 보정이 잘 되어 있지 않으므로, 이를 기준으로 임계값을 적용하는 것은 그 판단을 만들어낸 근본 원인을 고치기보다는 값을 신뢰할 수 없게 걸러낼 뿐이다. 모델은 여전히 필드를 언제 채워야 하는지에 대한 구체적인 규칙이 없다.

**D.** Lower the sampling temperature so the model stops committing to values it cannot verify in the source.

**설명**

temperature는 토큰이 얼마나 결정론적으로 샘플링되는지에 영향을 줄 뿐, 값이 실제로 문서에 의해 뒷받침되는지에 대한 모델의 판단에는 영향을 주지 않는다. 판단 규칙이 모호한 모델은 같은 추측성 추출을 더 자주 하지 않는 것이 아니라 더 일관되게 반복할 것이다.

### 전반적인 설명

"신중하게 하라"거나 "높은 확신을 가진 발견만 보고하라" 같은 지시는 주관적이기 때문에 실패한다. 모델은 이를 반복 가능한 판단으로 옮길 방법이 없다. 문서마다 "highly confident"가 무엇을 의미하는지 새롭게 해석하게 되며, 이것이 바로 지시가 있음에도 추측이 계속되는 이유다. 해결책은 그 의도를 명시적인 범주적 기준으로 바꾸는 것이다. 필드를 채울 수 있는 조건(예: 원문에 값이 명시적으로 진술되거나 표기되어 있음)과 null이 필요한 조건(값을 추론해야 하거나 문구가 모호함)을 정확히 명시하는 것이다. 이렇게 하면 감(vibe)이 모델이 일관되게 적용할 수 있는 규칙(rubric)으로 바뀌며, 값이 없다고 말할 정당한 방법을 주는 nullable 스키마와도 자연스럽게 어울린다.

오답들은 각각 그 메커니즘을 놓치고 있다. 표현을 강화하는 것("absolutely certain")은 여전히 검증 가능한 경계가 없는 지시에 강조만 더할 뿐이다. 스스로 매긴 신뢰도 점수는 보정이 잘 되어 있지 않은 것으로 알려져 있어, 이를 기준으로 필터링하면 잡음을 줄이기보다는 순서만 바꾸게 된다. 이는 라우팅 신호로는 유용할 수 있지만 판단 규칙의 대체물은 될 수 없다. temperature를 낮추는 것은 샘플링의 결정성만 바꿀 뿐 판단을 바꾸지는 못한다. 기준이 없는 추출 정책은 단지 재현 가능하게 틀리게 될 뿐이다.

일반적인 사고 모델은 다음과 같다. 모델 출력의 정밀도 문제는 거의 항상 명세(specification)의 문제이며, 샘플링이나 표현 강조의 문제가 아니다. 주관적인 수식어를 구체적이고 검증 가능한 지시로 대체하도록 권장하는 명확하고 직접적으로 지시하기에 대한 Anthropic의 가이드를 참고하라.

**설명**

이 지시는 모델이 값 중 하나를 조용히 바꾸도록 압박하여, 진짜 원본 데이터의 불일치를 드러내는 대신 감추게 만든다. 구조화된 출력은 스키마의 형태만 강제할 뿐, 숫자 값이 다른 필드와 산술적으로 일치하는지는 검증하지 못한다.

이는 일관되지 않은 원본 데이터를 위해 문서화된 자기 교정(self-correction) 패턴이다. stated_total과 calculated_total을 나란히 담아두면 출력에서 불일치가 명시적으로 드러나고, conflict_detected 플래그는 다운스트림 시스템이 일관되지 않은 문서를 자동으로 라우팅할 수 있게 하며, 코드 수준의 산술 검사는 모델이 합계 계산 자체를 잘못하는 경우를 막아준다.

### 전반적인 설명

여기서 핵심 사고 모델은 구조적 보장과 의미적 정확성 사이의 경계다. 구조화된 출력과 tool-use 스키마는 추출 결과가 올바른 필드와 타입을 가진 유효하고 파싱 가능한 JSON임을 보장하지만, 이 메커니즘의 어떤 부분도 그 안의 숫자들이 서로 일치하는지를 검사하지 않는다. 원본 문서 자체가 일관되지 않은 경우(항목들의 합이 인쇄된 총액과 맞지 않는 경우), 올바른 설계는 그 불일치를 감추는 것이 아니라 눈에 보이고 기계가 읽을 수 있게 만드는 것이다.

자기 교정 추출 패턴이 정확히 이를 수행한다. 스키마는 stated_total(문서에 적힌 값), calculated_total(추출된 항목들의 합), conflict_detected 불리언을 담는다. 두 총액 간의 불일치는 다운스트림 시스템이 라우팅에 활용할 수 있는 일급(first-class) 신호가 된다. 예를 들어 충돌이 있는 송장은 사람의 검토를 위해 보류하고, 문제가 없는 것은 그대로 흘러가게 할 수 있다. 모델 역시 합계를 잘못 계산할 수 있으므로, 애플리케이션 코드는 항목 합계를 독립적으로 재계산해야 한다. 이것이 바로 스키마가 제공할 수 없는 의미적 검증 계층이다.

대안들은 모두 검사를 잘못된 위치에 두고 있다. JSON 스키마는 필드 간 산술 관계를 표현할 어휘가 없고, 구조화된 출력은 숫자 제약조건을 명시적으로 제외하므로, 스키마 수준의 조정(reconciliation) 규칙은 존재할 수 없다. 추출을 두 번 실행하는 것은 재현성을 테스트할 뿐 정확성을 테스트하지 못한다. 두 실행은 동일하게 일관되지 않은 원본 수치에 대해 기꺼이 서로 일치할 것이다. 그리고 모델에게 총액이 결코 불일치하지 않도록 하라고 지시하는 것은 모델이 일치를 지어내도록 유도하는 것이며, 이는 나쁜 원본 데이터를 알려주는 바로 그 신호를 없애버리는 것이다. 스키마 강제가 무엇을 보장하고 무엇을 보장하지 않는지에 대해서는 Structured outputs를 참고하라.


## 질문 11

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : The extraction schema labels each contract clause with an enum of six clause types. On genuinely ambiguous clauses, the model still commits to one of the six types, and downstream teams act on wrong labels. Which change best fixes this?

**A.** Set the sampling temperature to zero so the model selects each clause type deterministically.

**설명**

이는 오답이다. 결정론적이라는 것이 정확성을 만들어내지는 않는다. temperature를 0으로 설정하면 모델은 강제된 선택을 피하는 것이 아니라 동일하게 반복할 뿐이다. 문제는 스키마가 애매한 조항에 대해 유효한 답을 제공하지 않는다는 것이며, 어떤 샘플링 설정으로도 이를 고칠 수 없다.

**B.** Run the classification twice for each clause and accept a label only when both runs return the same value.

**설명**

이는 오답이다. 두 실행 간의 일치가 레이블이 맞다는 것을 의미하지는 않는다. 모델은 애매한 조항에 대해 동일하게 잘못된 유형을 일관되게 선택할 수 있다. 이는 비용을 두 배로 만들면서도 출력에서 진짜 애매함을 표현할 방법은 여전히 제공하지 못한다.

**C.** Instruct the model in the prompt to assign a clause type only when it is highly confident in the label.

**설명**

이는 오답이다. 스키마는 여전히 6가지 유형 중 하나를 요구하므로, 프롬프트가 무엇을 말하든 모델은 불확실성을 표현할 정당한 방법이 없다. 신뢰도 기반의 산문식 지시 역시 모호하여 일관되지 않은 행동을 낳는다. 결국 구조적 제약이 지시를 압도한다.

**D(정답).** Add an "unclear" value to the clause-type enum so the model can flag ambiguous clauses for human review.

**설명**

이는 정답이다. 실제 카테고리만으로 구성된 폐쇄형 enum은 조항이 그중 어느 것에도 명확히 해당하지 않을 때조차 모델이 하나를 선택하도록 강제한다. "unclear" 값은 모델에게 정직한 도피구를 제공하며, 이렇게 추출된 항목은 확신 있는 레이블로 처리되는 대신 인간 검토로 라우팅될 수 있다.

### 전반적인 설명

추출 스키마의 enum 필드는 강제 선택(forced-choice) 메커니즘이다. 요청이 정상적으로 완료되고 필드가 필수인 경우, 스키마 강제는 모델이 나열된 값 중 하나를 내놓도록 제약한다(Anthropic은 거부, max_tokens에 의한 잘림, 문자열 enum 값의 대소문자 차이 같은 예외를 문서화하고 있으므로, 준수가 절대적이라기보다는 대부분의 경우에 보장된다). 바로 이 제약 때문에 enum 설계가 중요하다. 목록의 모든 값이 확정된 카테고리를 나타낸다면, 조항이 어디에도 명확히 속하지 않을 때 스키마 자체는 정직한 답을 남겨두지 않으므로, 모델은 구조가 요구하는 대로 가장 가까운 값을 고르게 되고, 이는 다운스트림에서 확신 있는 분류로 읽히게 된다.

이에 대해 설계된 해결책은 불확실성을 일급 값으로 만드는 것이다. enum에 "unclear"를 추가하면 애매한 경우에 대해 모델에게 정당한 출력을 제공하며, 애매함을 조용한 오분류 대신 파이프라인이 인간 검토로 라우팅할 수 있는 기계가 인식 가능한 신호로 바꾼다. 이는 알려진 카테고리 밖의 입력에 대해 "other" 값과 자유 텍스트 세부 필드를 짝짓는 것과 동일한 설계 원칙이다. 스키마는 편리한 상태만이 아니라 원본 데이터의 모든 진실한 상태를 표현할 수 있어야 한다. 참고로 표준 JSON 스키마는 enum에 어떤 JSON 값이든 허용하지만, Anthropic의 구조화된 출력 기능은 enum 값을 문자열, 숫자, 불리언, null로 특별히 제한하며, Anthropic은 대소문자가 엄격히 보장되지 않으므로 문자열 enum 값을 대소문자 구분 없이 비교하도록 권고한다.

다른 접근법들은 구조적 제약을 그대로 둔 채로 실패한다. "확신이 있을 때만 분류하라"는 프롬프트 지시는 값을 요구하는 스키마와 충돌하며, 신뢰도 관련 모호한 표현은 그런 충돌이 없어도 신뢰할 수 없다. 분류를 두 번 실행하는 것은 정확성이 아니라 일관성을 측정할 뿐이며, 강제된 잘못된 선택은 실행 간에 흔히 안정적으로 유지된다. temperature를 0으로 하는 것도 마찬가지로 토큰이 샘플링되는 방식만 바꿀 뿐, 스키마가 정직한 답을 허용하는지 여부는 바꾸지 못한다. 스키마와 enum 제약에 대해서는 Structured outputs를 참고하라.


## 질문 12

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : The extraction prompt contains four few-shot examples, all drawn from a single supplier's invoice layout. Accuracy is high on that layout, but values land in the wrong fields on documents with other structures. What change best fixes this?

**A.** Add a prose instruction stating that layouts vary and the example layout should not be assumed elsewhere.

**설명**

이는 목표만 언급할 뿐 판단 자체를 전달하지는 못한다. 모델은 레이아웃이 다르다는 말을 듣지만 여전히 하나만을 보여받는다. 추상적인 지시는 출력 행동을 형성하는 데 있어 구체적인 예시보다 효과가 떨어진다는 것이 문서화되어 있으므로, 다양성은 예시 자체가 담아야 한다.

**B.** Add fifteen more examples from the same supplier's invoices so the extraction pattern is reinforced.

**설명**

동일한 레이아웃의 예시를 더 추가하면 의도치 않은 레이아웃 특화 패턴이 깨지는 대신 오히려 강화된다. 여기서 실패의 본질은 하나의 구조에 대한 과적합(overfitting)이며, 같은 구조를 더 많이 추가하는 것은 프롬프트를 비대하게 만들면서 그 과적합을 심화시킬 뿐이다.

**C.** Expand the prompt into an exhaustive catalog with one example per layout the system may ever encounter.

**설명**

이는 few-shot 프롬프팅을 일반화가 아니라 사례 매칭으로 취급하는 것이며, 비정형 문서는 사전에 나열할 수 없는 레이아웃으로 도착하기 때문에 실현 불가능하다. 소수의 잘 선택된 다양한 예시 집합이 있으면 모델은 한 번도 본 적 없는 구조로도 확장하여 적용할 수 있다.

**D(정답).** Replace the set with a few examples spanning varied document structures so the extraction logic generalizes.

**설명**

서로 다른 구조를 포괄하는 다양한 예시는 특정 레이아웃이 값을 어디에 배치하는지가 아니라 무엇을 추출해야 하는지를 모델에게 가르친다. Anthropic의 가이드에 따르면 예시는 모델이 의도치 않은 패턴을 습득하지 않도록 충분히 관련성 있고 다양해야 하는데, 단일 레이아웃으로 구성된 예시 집합이 바로 그런 의도치 않은 패턴을 만들어낸다.

### 전반적인 설명

few-shot 예시는 두 가지 역할을 동시에 한다. 원하는 출력을 시연하는 동시에, 예시들이 공유하는 모든 규칙성을 암묵적으로 가르친다. 네 가지 예시 모두 한 공급업체의 레이아웃에서 나온 것이라면, 그 공유된 레이아웃이 학습된 패턴의 일부가 되어, 모델은 추출해야 할 의미적 내용이 아니라 그 레이아웃 내의 위치에 필드를 결부시키게 된다. multishot 프롬프팅에 대한 Anthropic의 가이드는 이를 명시적으로 다룬다. 예시는 모델이 의도치 않은 패턴을 습득하지 않도록 정확히 관련성 있고, 다양하며, 엣지 케이스를 다루어야 한다는 것이다. 동질적인 예시 집합을 구조적으로 서로 다른 문서에서 뽑은 몇 개의 예시로 바꾸면 불필요한 신호가 제거되고 의도한 신호만 남아, 추출 로직이 프롬프트가 한 번도 보여주지 않은 레이아웃으로도 전이될 수 있다.

오답들은 시사점이 있는 방식으로 실패한다. 동일 공급업체의 예시를 더 쌓는 것은 과적합을 고치기는커녕 강화한다. 지렛대가 되는 것은 예시의 수가 아니라 예시의 다양성이다. 레이아웃이 다양하다는 산문식 면책 조항은 목표를 진술할 뿐 시연하지는 못하며, Anthropic은 원하는 행동에 대한 구체적인 예시가 추상적인 지시보다 출력을 형성하는 데 더 효과적이라고 문서화하고 있다. 레이아웃별로 예시를 모두 나열한 카탈로그는 그 메커니즘을 완전히 잘못 이해한 것이다. few-shot 프롬프팅의 가치는 Claude가 소수의 예시로부터 일반화한다는 데 있으므로, 모든 형식에 대한 사례 매칭 테이블은 필요하지 않으며, 진정으로 비정형적인 입력에 대해서는 그런 테이블을 만들 수조차 없다. 예시 집합은 작게 유지하고(대략 3~5개), 각각을 구조적으로 뚜렷이 다르게 만들고, 지시와 명확히 구분되도록 <example> 태그로 감싸라. 효과적인 예시를 작성하는 방법에 대한 전체 가이드는 Anthropic의 프롬프트 엔지니어링 문서를 참고하라.
