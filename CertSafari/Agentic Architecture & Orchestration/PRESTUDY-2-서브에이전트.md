# 2. 서브에이전트와 위임

이 장에서 다루는 것:

- 서브에이전트란 무엇이고 왜 쓰는가 (컨텍스트 격리·전문화·병렬성·권한 격리)
- `AgentDefinition`의 주요 필드와 `.claude/agents` 파일 정의
- `description`과 `prompt`의 역할 분리, 두 층의 프롬프트 결합
- 설명 기반 동적 라우팅과 "이름을 부르면 보장된다"는 오해
- `tools`로 하는 하드 제약 — 최소 권한의 원칙
- `allowedTools`와 `Task` 도구 (승인 프롬프트가 매번 뜨는 문제)
- 병렬 호출 규칙 — 한 턴에 여러 도구 호출
- 중첩 서브에이전트와 5레벨 하드 리밋
- 상태 없음(stateless)과 컨텍스트 명시적 주입
- 코디네이터-서브에이전트(허브 앤 스포크) vs Agent Teams
- 결과 종합: 구조화된 데이터 전달, 정보 상충 처리, 부분 출력, 사람에게 넘기는 인수인계 요약
- 정적 파이프라인 vs 동적 라우팅

---

## 2.1 서브에이전트란

**서브에이전트(subagent)** 는 **자기만의 독립된 컨텍스트 윈도우, 시스템 프롬프트, 도구 목록을 가진 별도의 에이전트 인스턴스**입니다. 상위 에이전트 — **코디네이터(coordinator)** 또는 **오케스트레이터(orchestrator)**, 메인 에이전트라고도 부릅니다 — 가 특정 하위 작업을 맡기면(위임), 서브에이전트가 그 작업을 수행하고 **요약된 결과만** 상위로 돌려준 뒤 사라집니다. 위임은 보통 `Agent`(또는 `Task`) 도구 호출의 형태로 이루어집니다.

왜 나누는가:

- **컨텍스트 격리(Context Isolation)** — 서브에이전트가 파일 50개, 수백 개를 뒤져도 그 원시 내용이 코디네이터의 컨텍스트를 오염시키지 않습니다. 결론만 올라옵니다.
- **전문화(Specialization)** — 역할별로 다른 시스템 프롬프트, 다른 도구 집합, 다른 모델을 줄 수 있습니다. 단일 책임이 지켜지므로 각 프롬프트가 짧고 정확해집니다.
- **병렬화(Parallelism)** — 서로 독립적인 작업을 동시에 돌릴 수 있습니다.
- **권한 격리** — 위험한 도구를 특정 서브에이전트에게만 주거나, 반대로 뺏을 수 있습니다.

## 2.2 AgentDefinition — 정의의 구조

서브에이전트는 **정의(AgentDefinition)** 객체 혹은 정의 파일로 선언합니다.

| 필드 | 역할 |
|---|---|
| `name` | 서브에이전트의 이름 |
| `description` | **무엇을 위한 에이전트인지 요약한 설명** — 라우팅의 핵심 트리거 |
| `prompt` | 이 에이전트의 시스템 프롬프트 (역할·절차·출력 형식) |
| `tools` | 허용된 도구 배열 — 여기 없는 도구는 아예 쓸 수 없음 (하드 제약) |
| `disallowedTools` | 명시적으로 금지할 도구 목록 |
| `model` | 사용할 모델 (추론 능력·비용 선택, 생략 시 기본 모델) |
| `maxTurns` | 이 에이전트의 최대 턴 수 (실행 예산 가드레일) |
| `background` | 백그라운드(비동기)로 실행할지 여부 |

```jsonc
{
  "name": "doc-reviewer",
  // 언제 이 에이전트를 부를지 — 라우팅 트리거
  "description": "문서와 README의 정확성·명확성을 검토할 때 사용. 문서 리뷰, 오탈자 점검, 설명 누락 확인 요청 시 호출.",
  // 호출된 뒤 어떻게 행동할지 — 시스템 프롬프트
  "prompt": "당신은 기술 문서 리뷰어입니다. 각 문단의 정확성을 확인하고 ...",
  // 사용 가능한 도구 화이트리스트 — 하드 제약
  "tools": ["Read", "Grep"],
  // 이 에이전트가 사용할 모델
  "model": "opus"
}
```

**정의 방식은 두 가지입니다.**

1. **프로그래밍 방식** — SDK 옵션에 `AgentDefinition` 객체로 전달
2. **파일시스템 방식** — 프로젝트의 `.claude/agents/` 디렉터리에 마크다운 파일로 저장 (프론트매터에 메타데이터, 본문에 프롬프트)

`.claude/agents`는 **정의를 저장·공유하는 장소**일 뿐이라는 점을 기억하세요. 이 위치에 둔다고 해서 에이전트끼리 실시간으로 상태를 공유하거나 메시지를 주고받게 되지는 않습니다.

### `description` — 언제 부를지 (라우팅 트리거)

코디네이터가 "이 요청을 내가 직접 처리할까, 어떤 서브에이전트에게 넘길까"를 판단할 때 보는 필드입니다.

이 필드가 모호하거나 비어 있으면, 코디네이터는 이 서브에이전트가 언제 적용되는지 알 수 없어 **그냥 자기가 직접 처리해버립니다**. 자동 위임이 안 되는 가장 흔한 원인이 바로 이것입니다.

예를 들어 `performance-optimizer`라는 서브에이전트의 `prompt`가 아무리 상세하고 기술적으로 정확해도, `description`이 "성능 관련 도우미" 정도로 모호하면 사용자가 "쿼리가 느려요"라고 물었을 때 코디네이터는 위임하지 않습니다. **고쳐야 할 곳은 `prompt`가 아니라 `description`입니다.**

좋은 `description`은 **트리거 조건을 구체적으로 명시**합니다.

```
"느린 데이터베이스 쿼리, 인덱스 누락, N+1 쿼리, 쿼리 실행 계획 분석이 필요할 때 사용."
```

참고로, 코디네이터의 시스템 프롬프트에 서브에이전트 이름을 하드코딩할 필요는 없습니다. 런타임이 등록된 정의들을 읽어 동적으로 라우팅합니다.

### `prompt` — 호출된 뒤 어떻게 행동할지

서브에이전트가 실제로 실행될 때 받는 시스템 프롬프트입니다. 작업 절차, 출력 형식, 주의사항을 담습니다. `description`과 역할이 완전히 다릅니다.

- `description` = **언제 부르는가** (코디네이터가 읽음)
- `prompt` = **불려온 뒤 무엇을 하는가** (서브에이전트가 읽음)

프롬프트를 1인칭으로 쓰든 2인칭으로 쓰든, 그것이 위임 여부를 결정하지는 않습니다.

### `model` — 어떤 모델로 실행할 것인가

서브에이전트별로 독립적인 모델을 지정할 수 있습니다. 이 필드를 설정해도 **코디네이터 자신의 모델 설정은 전혀 바뀌지 않습니다.**

예: 일상적인 보안 리뷰는 저렴한 모델로, "엄격한(strict)" 변형 리뷰만 더 강력한 모델로 실행하고 싶다면 — 그 엄격 변형용 `AgentDefinition`의 `model` 필드만 강력한 모델로 지정하면 끝입니다.

잘못된 우회 방법들:

- 코디네이터 세션을 다른 모델 인자로 재개(resume)하기 → 코디네이터 자신의 모델까지 바뀌므로 조건 위반.
- 모델 이름을 `tools` 배열에 넣기 → `tools`는 도구 목록이지 모델 지정 수단이 아닙니다.
- 세션을 포크해서 기본 모델을 바꾸기 → 필드 하나로 될 일에 불필요한 세션 조작.

## 2.3 두 층의 프롬프트 — 정의 프롬프트와 호출 프롬프트

서브에이전트는 **두 층의 프롬프트**로 작동합니다. 이 구분이 자주 헷갈립니다.

```
AgentDefinition {
  description: "DB 마이그레이션 전문가",
  prompt: "너는 SQL 마이그레이션 전문가다. 항상 롤백 전략을 세우고,
           데이터 무결성 검사를 포함하며, ...",   ← 정적 / 지속적
  tools: [...],
  model: "..."
}
```

- **`AgentDefinition.prompt`** = 그 서브에이전트의 **지속적인 시스템 프롬프트이자 전문성/페르소나**. 정의 시점에 한 번 정해지고, 호출될 때마다 항상 적용됩니다. SQL 모범 사례, 롤백 전략, 데이터 무결성 검사 같은 **변하지 않는 공통 지침**이 여기 들어갑니다.
- **호출 시 프롬프트(per-call prompt)** = 코디네이터가 이번 실행에서 맡기는 **구체적 작업 지시**. "`orders` 테이블에 `region` 컬럼을 추가해라" 같은 것.

**둘은 대체 관계가 아니라 결합 관계입니다.** 정의 프롬프트는 시스템 지침으로, 호출 프롬프트는 그 회차의 작업 지시로 함께 모델에 전달되어 하나의 완전한 맥락을 이룹니다.

흔한 오해들 (모두 사실이 아님):

- 호출 프롬프트가 오면 `AgentDefinition.prompt`가 런타임에 무시된다 ✗
- 호출 프롬프트가 서브에이전트가 아니라 **코디네이터의 시스템 프롬프트**로 병합된다 ✗
- 둘을 이어 붙인 뒤 **짧은 쪽 길이에 맞춰 잘라낸다** ✗ (그런 로직은 존재하지 않습니다)

## 2.4 설명 기반 라우팅 (Description-based Routing)

사용자 쿼리에 서브에이전트 이름이 **명시되지 않았을 때**, 코디네이터는 어떻게 어느 서브에이전트를 부를지 정할까요?

답: **각 서브에이전트의 `description` 필드를 쿼리와 의미적으로 매칭(semantic matching)해서, 적합한 것이 있으면 자동으로 위임합니다.**

동작 원리는 이렇습니다. 정의된 서브에이전트들의 `description`이 코디네이터의 프롬프트/시스템 맥락에 포함됩니다. 새 쿼리가 들어오면 LLM이 쿼리의 의도와 각 `description`을 비교해 가장 적합한 것을 고릅니다. 여기서 얻는 실무적 교훈: **`description`은 잘 써야 합니다.** 이것이 라우팅 품질을 직접 결정합니다.

잘못된 통념들:

- "쿼리에 정확한 이름이 들어 있어야만 위임이 고려된다" → 아닙니다. 설명 기반 의미 매칭으로 동적 호출됩니다.
- "설정 파일에 정의된 순서대로 호출한다" → 그것은 정적 체인이지 동적 라우팅이 아닙니다.
- "일단 모든 서브에이전트를 다 호출하고 관련 없는 출력은 버린다" → 심각한 토큰 낭비와 지연을 유발하는 잘못된 설계입니다.

### 프롬프트로 이름을 부르는 것은 "보장"이 아니다

"code-reviewer 에이전트를 사용해서 인증 모듈을 검토해줘"라고 프롬프트에 명시하면, 그 서브에이전트가 **반드시** 호출될까요?

**아닙니다.** 이것은 자연어 지시이므로 모델에 **영향(influence)** 을 줄 뿐 **강제(force)** 하지 못합니다. 모델은 위임하지 않고 스스로 검토 답변을 내놓을 수도 있습니다. 대원칙은 같습니다: **자연어 프롬프트는 확률적이고, 보장이 필요하면 프로그래밍적 제약이 필요합니다.**

확정적으로 보장하려면:

- `tool_choice` 파라미터로 특정 도구/서브에이전트 호출을 강제하거나,
- 전용 서브에이전트 호출 문법(예: Claude Code의 `@code-reviewer`)을 사용하거나,
- 그 밖의 프로그래밍적 제약(훅, 코드 레벨 라우팅)을 씁니다.

관련 오해 정정:

- "`description` 필드를 지우면 이름 언급이 강제 호출이 된다" → 아닙니다.
- "이름을 부르면 자동 매칭을 우회하는 명시적 호출이 되어 100% 보장된다" → 아닙니다. 여전히 자연어 안내일 뿐입니다.
- "이름에 의한 명시적 지정은 내장 에이전트에만 통한다" → 아닙니다. 커스텀·내장 모두 영향을 받지만, 둘 다 **텍스트 지시만으로는 100% 강제되지 않는다**는 점이 핵심입니다.

## 2.5 능력은 "도구"로 결정된다 — 최소 권한의 원칙

에이전트가 무엇을 **할 수 있는지**는 모델 크기나 실행 방식이 아니라 **어떤 도구를 가졌는가**로 결정됩니다.

**최소 권한의 원칙(Principle of Least Privilege)**: 어떤 주체에게든 자기 임무 수행에 꼭 필요한 최소한의 권한만 부여한다는 보안 원칙. 에이전트 세계에서 이것은 곧 **`tools` 목록을 좁히는 것**입니다.

반드시 구분해야 할 두 종류의 제약:

| 구분 | 수단 | 성격 |
| --- | --- | --- |
| **소프트 제약 (Soft Limit)** | 프롬프트에 "파일을 수정하지 마세요"라고 적기 | 모델이 지시를 어길 수 있음. 환각·오판으로 무너짐. **보장 없음** |
| **하드 제약 (Hard Limit)** | `tools`에서 `Edit`, `Write`를 제외 | 도구 자체가 없으므로 물리적으로 불가능. **보장됨** |

"절대로 ~해서는 안 된다(must never, even accidentally)"는 요구가 나오면 답은 항상 하드 제약, 즉 도구 목록 제한입니다.

**예시 1 — 읽기 전용 리뷰어.** 문서를 읽고 코멘트만 해야 하는 `doc-reviewer`가 실수로 파일을 수정하는 것을 막고 싶다.

```jsonc
{
  "name": "doc-reviewer",
  "description": "문서를 읽고 검토 의견을 제시할 때 사용.",
  "prompt": "...",
  "tools": ["Read", "Grep"]   // Edit, Write 없음 → 수정 불가능
}
```

여기서 중요한 성질: **서브에이전트는 `tools`에 나열된 것만 받으며, 코디네이터가 무엇을 가지고 있든 상관없습니다.** 코디네이터가 `Read, Edit, Write, Grep, Glob`을 전부 가지고 있어도, 서브에이전트의 `tools`가 `["Read", "Grep"]`이면 그 서브에이전트에는 `Edit`/`Write`가 전달되지 않습니다.

**예시 2 — 중첩 생성 권한 통제.** `lead-investigator`는 스스로 하위 조사관을 만들 수 있어야 하고, `final-summarizer`는 절대 하위 에이전트를 만들면 안 된다고 합시다. 서브에이전트를 생성하는 행위 자체가 **`Agent`(서브에이전트 호출) 도구**를 쓰는 일이므로, `lead-investigator`의 `tools`에는 그 도구를 **포함**시키고, `final-summarizer`의 `tools`에서는 **제외**하거나 `disallowedTools`에 넣습니다. 이것이 구조적 강제(enforcement)입니다.

통제 수단이 되지 못하는 것들:

- **`description` 필드에 "읽기 전용"이라고 적기** — `description`은 라우팅용 메타데이터일 뿐 실행 권한을 통제하지 않습니다.
- **`tools`를 비워두고 프롬프트로만 금지** — 소프트 제약이라 보장이 없고, `tools`를 지정하지 않으면 상위의 도구를 상속받게 되어 오히려 위험합니다.
- **코디네이터 자신의 `allowedTools`를 좁히기** — 코디네이터가 본래 해야 할 작업까지 막히고, 서브에이전트 권한을 정의하는 표준 방식도 아닙니다.
- **모델 크기·티어를 낮추기** — 성능이 낮은 모델은 오히려 지시를 더 잘 어깁니다. 큰 모델이라 위임이 가능하고 작은 모델이라 불가능한 게 아닙니다. 능력 차이는 추론 품질이지 권한이 아니며, 능력 저하는 제약 장치가 아닙니다.
- **`background: true`** — 비동기 실행 방식일 뿐, 도구 권한을 부여하지 않습니다.
- **`maxTurns`를 낮추기** — 턴이 적어도 **첫 턴에 곧바로** 서브에이전트를 만들 수 있습니다. 권한 차단이 아니라 실행 예산 제한일 뿐입니다.
- **모든 도구를 다 뺏기** — 문서를 읽어야 하는데 `Read`조차 없으면 본연의 임무를 못 합니다. 최소 권한은 "0 권한"이 아니라 "필요한 만큼만"입니다.

일반화하면: **권한은 도구 목록(allow/deny)으로, 예산은 `maxTurns`로** 통제합니다. 둘을 바꿔 쓰면 안 됩니다.

## 2.6 `allowedTools`와 `Task` 도구 — 위임이 매번 승인 프롬프트에서 멈출 때

**`allowedTools`** 는 사전 승인된(자동 실행 가능한) 도구 이름 목록입니다. 여기에 없는 도구를 쓰려고 하면 실행 전에 사람에게 승인을 묻는 프롬프트가 뜹니다.

중요한 사실: **서브에이전트를 호출하는 행위 자체도 하나의 도구입니다.** 그 도구의 이름이 **`Task`** 입니다.

그래서 이런 상황이 벌어집니다:

```
allowedTools: ["Read", "Grep", "Glob"]
agents: { "research-assistant": {...} }

→ 코디네이터가 research-assistant에게 위임하려 할 때마다 승인 프롬프트에서 멈춤
```

**원인**: 위임에 필요한 `Task` 도구가 `allowedTools`에 없기 때문입니다.
**해결**: `allowedTools`에 `"Task"`를 추가합니다.

```
allowedTools: ["Read", "Grep", "Glob", "Task"]
```

이 증상의 다른 원인 후보들이 왜 아닌지:

- 서브에이전트의 `tools` 배열이 코디네이터보다 권한이 많아서 → 이 사례의 원인이 아닙니다. 원인은 위임 도구 자체의 자동 승인 누락입니다.
- 시스템 프롬프트에 서브에이전트 이름이 없어서 → 권한 레이어는 시스템 프롬프트의 이름 언급 여부를 검사해서 승인 여부를 정하지 않습니다.
- `model` 필드가 빠져서 → `model`이 없으면 기본 모델이 적용되거나 설정 오류가 날 뿐, 호출마다 승인 팝업이 뜨지는 않습니다.

## 2.7 병렬(동시) 호출

서로 의존하지 않는 하위 작업은 **동시에(concurrently)** 호출해야 합니다.

- 순차 실행: 총 시간 = 각 작업 시간의 **합(sum)**
- 동시 실행: 총 시간 ≈ **가장 느린 작업 하나(slowest)** 의 시간

병렬성의 핵심 규칙:

> **하나의 assistant 응답(턴) 안에 여러 개의 도구 호출 블록을 넣으면, 런타임이 그것들을 동시에 실행한다.**

반대로 한 턴에 하나씩 호출하고 결과를 기다린 뒤 다음 턴에 또 하나를 호출하면, 구조적으로 **직렬**이 됩니다. 아무리 옵션을 조정해도 이 흐름은 병렬이 되지 않습니다.

```
[직렬] 턴1: Task(A) → 결과 대기 → 턴2: Task(B) → 결과 대기 → 턴3: Task(C)
[병렬] 턴1: Task(A), Task(B), Task(C) 를 한 응답에 함께 발행 → 셋이 동시 실행 → 결과 일괄 수신
```

예: PR 리뷰에 스타일 검사·보안 검사·테스트 커버리지 검사 3개가 필요하고 서로 독립적이라면, 셋을 한꺼번에 띄우고 전부 끝난 뒤 종합합니다.

병렬화를 방해하는 흔한 오해:

- **여러 에이전트를 하나로 합치기** — 동시성이 아니라 그냥 하나의 긴 직렬 작업이 됩니다. 컨텍스트 오염과 단일 에이전트 오버헤드가 커지고, 관심사 분리라는 설계 이점도 잃습니다.
- **`maxTurns` 증가** — `maxTurns`는 에이전트가 수행할 수 있는 최대 턴(대화/도구 호출 횟수)을 제한하는 **가드레일**입니다. 상한을 올린다고 개별 작업이 빨리 끝나거나 실행이 겹치지 않습니다.
- **세션 저장 비활성화(`persistSession: false`)** — 트랜스크립트를 디스크에 남길지 여부의 설정일 뿐, 호출 흐름의 직렬/병렬과 무관합니다.
- **셋 중 하나만 돌리고 결과에 따라 나머지를 생략** — 세 결과를 모두 종합해야 하는 요구사항 위반입니다.

## 2.8 중첩 서브에이전트(Nested Subagents)와 깊이 제한

서브에이전트가 다시 자기 서브에이전트를 만드는 것을 **중첩(Nesting)** 이라고 합니다. 초기 버전에서는 금지되었으나, Claude Code는 이후 중첩 서브에이전트를 **공식 지원**합니다. 다만 무한 재귀와 자원 고갈·API 비용 폭증을 막기 위해 **메인 에이전트를 1단계로 포함하여 최대 5단계(5 levels deep)** 라는 **하드 리밋**을 둡니다.

```
Level 1: 메인 에이전트
Level 2:   └ 서브에이전트
Level 3:       └ 서브에이전트
Level 4:           └ 서브에이전트
Level 5:               └ 서브에이전트   ← 여기까지
```

기억할 점:

- 이 제한은 모델 등급(tier)이나 설정으로 풀리는 유연한 값이 아니라 **고정된 상한**입니다.
- 도구 목록에 `Agent` 도구를 허용해도 **무제한으로 중첩되지 않습니다** — 시스템 캡(cap)이 걸립니다.
- "서브에이전트는 절대 자식을 만들 수 없다"는 것은 초기 버전의 제약이며 현재는 사실이 아닙니다.
- 각 단계는 자기만의 **독립 컨텍스트 창**을 갖고, 상위에는 요약 결과만 올립니다.

## 2.9 상태 없음(Stateless) — 컨텍스트는 자동으로 상속되지 않는다

핵심 원칙: **서브에이전트를 호출할 때마다 완전히 새로운(fresh) 빈 컨텍스트에서 시작합니다.** 부모나 형제 에이전트의 대화 맥락을 자동으로 물려받지 않고, 각자 깨끗한 상태(clean state)에서 출발합니다.

같은 이름의 서브에이전트 타입(예: `endpoint-finder`)을 연속으로 두 번 불러도, 두 번째 호출은 첫 번째 호출에서 무엇을 했는지 **전혀 모릅니다**. 이미 설명했던 규칙을 다시 설명하고, 이미 훑었던 배경을 다시 훑습니다.

이것은 버그가 아니라 **의도된 정상 동작**입니다. 이유:

- 컨텍스트 오염(무관한 이전 작업 내용이 판단을 흐리는 것)을 막기 위해
- 매 호출마다 이전 기록을 다 실어 보내면 토큰이 낭비되기 때문에

기억을 이어가고 싶다면 **특정 에이전트 ID를 명시적으로 재개(resume)** 해야 합니다. 즉 "같은 타입을 또 부른다"와 "그때 그 에이전트를 이어서 부른다"는 완전히 다른 동작입니다.

**전형적인 실패 사례**: 코디네이터가 `web-researcher`를 돌려 자료 10건을 모은 뒤, `synthesis` 서브에이전트에게 "방금 완료된 조사를 바탕으로 보고서를 써라"라고만 지시하는 경우. `synthesis`는 "방금 완료된 조사"가 무엇인지 **볼 방법이 없어서** 일반론만 새로 지어냅니다.

해결책은 단 하나: **코디네이터가 `web-researcher`의 결과를 `synthesis`의 프롬프트에 직접 넣어 준다**(명시적 주입).

효과가 없는 대안들:

- 더 큰 모델로 교체 — 존재하지 않는 정보를 추론해 낼 수는 없습니다.
- `maxTurns` 증가 — 이미 끝난 조사를 처음부터 다시 하게 만드는 낭비이고, 분업의 목적에 어긋납니다.
- 검색 도구를 똑같이 부여 — 마찬가지로 중복 수행입니다.

틀린 통념 정리:

- 같은 코디네이터 세션 안의 서브에이전트들이 하나의 컨텍스트 창을 공유한다 → 아닙니다. 격리가 목적입니다.
- 대상(서비스 등)이 같으면 자동으로 기억이 공유된다 → 아닙니다. 대상과 무관합니다.
- 서브에이전트 정의가 호출 간 추론을 자동 캐싱한다 → 그런 기능은 없습니다.

## 2.10 코디네이터-서브에이전트 패턴 (허브 앤 스포크)

하나의 큰 작업을 하나의 에이전트가 다 하려고 하면 대화 기록이 너무 길어지고, 서로 무관한 정보가 뒤섞여 판단이 흐려집니다. 그래서 흔히 쓰는 구조가 이것입니다.

- **오케스트레이터/코디네이터**: 전체 작업을 계획하고, 잘게 쪼개서 하위 에이전트에게 나눠주고, 돌아온 결과를 모아 최종 답을 만드는 "지휘자".
- **서브에이전트**: 지시받은 좁은 범위의 작업만 수행하고 결과를 위로 보고하는 "작업자".

중앙에 오케스트레이터가 있고 바퀴살처럼 서브에이전트가 붙는 이 모양을 **허브 앤 스포크(Hub-and-Spoke)** 아키텍처라고 부릅니다.

```
            [사용자]
               │
        ┌──────▼───────┐
        │ 오케스트레이터 │  (Hub)
        └──┬───┬───┬───┘
           │   │   │
      [스타일] [보안] [커버리지]   (Spokes, 서로 직접 대화하지 않음)
```

특징:

- 통신은 **수직적**입니다. 코디네이터 ↔ 각 서브에이전트만 오갑니다. **서브에이전트끼리 직접 통신하지 않습니다.** 모든 통신은 허브를 거치므로 흐름을 한 곳에서 통제할 수 있고, 누가 무엇을 했는지 추적하기 쉽습니다.
- 서브에이전트 호출은 **일회성(one-shot)** 입니다. 작업을 맡기고, 최종 요약만 돌려받습니다.

### 설계 원칙: 공통 관심사는 허브에 모은다

에러 처리, 로깅 포맷, 재시도 정책, 속도 제한 백오프(rate-limit backoff) 같은 **횡단 관심사(cross-cutting concern)** 를 각 서브에이전트가 제멋대로 구현하면 시스템 전체가 일관성을 잃습니다. 로그 포맷이 제각각이라 모니터링이 안 되고, 재시도 정책이 달라 어떤 에이전트는 API 한도를 계속 때립니다. 이를 코디네이터로 **중앙화(centralize)** 하면 하나의 규칙으로 모든 서브에이전트 통신이 관리됩니다.

잘못된 대안들:

- 재시도와 로깅을 아예 없애기 — 관측 가능성과 복원력을 모두 버리는 것입니다.
- 동일한 로직을 각 서브에이전트 프롬프트에 복사·붙여넣기 — 파편화는 그대로이고 유지보수만 나빠집니다.
- 다른 에이전트를 감시하는 감시자 에이전트를 하나 더 두기 — 오케스트레이션은 원래 허브의 책임인데, 불필요한 계층을 덧붙여 책임을 흐립니다.
- 코디네이터를 없애고 서브에이전트끼리 직접 호출하기 — 결합도(coupling)가 높아지고 흐름을 한 곳에서 통제할 수 없게 되어 관측·디버깅이 어려워집니다.

## 2.11 Agent Teams (에이전트 팀)

코디네이터-서브에이전트 패턴의 한계는 명확합니다. 일회성이고, 단방향이며, 요약만 오갑니다. 여러 에이전트가 **장기간에 걸쳐 서로 직접 메시지를 주고받으며** 공유 작업 목록을 함께 조율해야 한다면 이 모델로는 부족합니다.

**Agent Teams**는 이런 요구를 위한 패턴입니다.

- **에이전트 간 메시징(inter-agent messaging)**: 피어 투 피어로 직접 주고받음
- **여러 협력 세션의 중앙 관리**: 팀 전체 상태를 한 곳에서 관리

| | 코디네이터-서브에이전트 | Agent Teams |
|---|---|---|
| 통신 방향 | 수직, 단방향(위임→요약) | 수평, 양방향 |
| 지속성 | 일회성 태스크 | 장기 세션에 걸친 지속 협업 |
| 적합 상황 | 독립적 하위 작업 분담 | 상호 조율이 계속 필요한 공동 작업 |

참고로, 서브에이전트에게서 `Agent` 도구를 뺏는 것(중첩 생성 금지)은 단순한 **제약 설정**이지 협업 기능이 아닙니다. 또 한 에이전트의 `maxTurns`를 늘려 여러 참여자를 흉내 내게 하는 것도 실제 독립 에이전트 간 통신이 아닙니다.

## 2.12 정적 파이프라인 vs 동적 라우팅

**정적(Static) 파이프라인**은 입력이 무엇이든 항상 같은 순서로 같은 에이전트를 전부 실행하는 구조입니다. 예를 들어 고객 지원 티켓 처리에서 늘 다음 5개를 다 돌리는 식입니다.

1. classifier (분류기)
2. sentiment analyzer (감정 분석기)
3. knowledge-base search (지식베이스 검색)
4. summarizer (요약기)
5. escalation checker (이관 판정기)

문제는 "비밀번호 재설정 링크 주세요" 같은 한 줄짜리 문의에도 5개가 전부 돌아간다는 점입니다. 결과적으로 **지연 시간(Latency)** 과 **토큰 비용**이 폭증합니다.

**동적 라우팅(Dynamic Routing)** 은 이 문제의 표준 해법입니다. 코디네이터가 먼저 **경량 분류 단계**를 한 번 돌려서 "이 입력에는 무엇이 필요한가"를 판단하고, 필요한 에이전트만 골라 부릅니다. 경량 분류 단계는 보통 작고 빠른 프롬프트 한 번으로 구조화된 JSON을 받아오는 식으로 구현합니다.

```json
{
  "complexity": "low",
  "required_subagents": ["classifier"]
}
```

```json
{
  "complexity": "high",
  "required_subagents": ["classifier", "sentiment_analyzer",
                         "kb_search", "summarizer", "escalation_checker"]
}
```

코디네이터는 `required_subagents`에 나온 것만 호출합니다. 단순 티켓은 1개 에이전트로 즉시 끝나고, 복잡한 티켓만 전체 파이프라인을 탑니다.

**JSON으로 받는 이유**: 자연어 문장("이건 간단해 보입니다")은 프로그램이 파싱하기 어렵고 매번 표현이 달라집니다. 필드 이름과 값 집합을 정해둔 구조화된 출력은 코드에서 `if "kb_search" in result["required_subagents"]` 처럼 확정적으로 분기할 수 있습니다.

**흔히 헷갈리는 대안들과 그 한계:**

- **전부 병렬 실행**: 총 지연 시간이 "합계"에서 "가장 느린 하나"로 줄어드는 이점은 있지만, **불필요한 작업 자체는 그대로 다 수행**되므로 토큰 비용은 전혀 줄지 않습니다. 근본 해결이 아닙니다. (병렬화는 라우팅과 함께 쓰는 보조 최적화입니다.)
- **5개를 1개로 합쳐 순차 실행**: 지연 시간은 오히려 늘고, 단계별 제어·병렬화·전문화를 모두 잃습니다.

## 2.13 에이전트 사이로 데이터를 넘기는 방법: 구조화가 답이다

멀티 에이전트에서 자주 나오는 문제: 검색 에이전트와 문서 분석 에이전트가 조사한 결과를 종합(synthesis) 에이전트가 보고서로 쓰는데 **출처가 자꾸 뒤바뀝니다.** 어떤 주장에 엉뚱한 URL이나 페이지 번호가 붙습니다.

원인은 전달 형식입니다. 자유 형식 산문으로 넘기면 본문 내용과 메타데이터(URL, 문서명, 페이지)가 한 덩어리로 섞이고, 모델은 어느 문장이 어느 출처에서 왔는지 문맥으로 "추측"해야 합니다. 추측은 틀립니다.

**해결: 콘텐츠와 메타데이터를 분리한 구조화된 항목으로 넘긴다.**

```json
[
  {
    "claim": "2024년 3분기 이탈률이 12% 감소했다",
    "source_url": "https://example.com/report-q3",
    "document_name": "Q3 Retention Report",
    "page": 14
  },
  {
    "claim": "신규 온보딩 흐름 도입 후 활성화율이 개선되었다",
    "source_url": "https://example.com/blog/onboarding",
    "document_name": null,
    "page": null
  }
]
```

이렇게 하면 문장과 출처가 **자료 구조 수준에서 묶여 있으므로** 모델이 짝을 잃을 여지가 구조적으로 사라집니다.

피해야 할 대안:

- 요약만 넘기고 종합 에이전트가 원본을 다시 가져오게 하기 — 이미 한 일을 반복하는 것이라 비용과 지연만 늘어납니다.
- 채팅체 원문 그대로 복사 — 문구가 정확해도 구조가 없으면 귀속은 여전히 추측입니다.
- 모든 출처의 텍스트를 하나의 연속된 산문으로 합치기 — 출처 경계가 아예 사라져 오귀속이 더 심해집니다.

## 2.14 결과 종합(Synthesis)과 정보 상충 처리

오케스트레이터의 마지막 임무는 서브에이전트들의 결과를 모아 하나의 답으로 **종합(Synthesize)** 하는 것입니다. 그런데 서브에이전트들이 서로 다른 출처를 참고해 **서로 모순되는 답**을 가져오는 일이 흔합니다(예: 같은 사건의 연도를 하나는 1969년, 하나는 1970년으로 보고).

이때의 올바른 원칙은 **투명성(Transparency)** 입니다.

- 오케스트레이터에게는 어느 쪽이 진실인지 판정할 근거가 없습니다. 근거 없이 하나를 고르면 그것은 사실상 **환각(Hallucination)** 을 만들어내는 행위입니다.
- 정보를 통째로 버리고 답하지 않는 것도 틀렸습니다. 시스템의 유용성이 사라집니다.
- 응답 속도(먼저 도착한 결과)는 정확성과 아무 관계가 없습니다. "먼저 답한 쪽이 옳다"는 규칙은 존재하지 않습니다.
- 서브에이전트가 모호하거나 상충되는 결과를 보고하는 것은 **허용되며 오히려 바람직합니다**. 서브에이전트는 발견한 것을 있는 그대로 보고해야 하고, 억지로 하나로 정리해 올리면 정보가 손실됩니다.

따라서 올바른 처리는 **양쪽 결과를 모두 집계하고, 각각의 출처를 함께 붙여 사용자에게 상충 사실을 그대로 알려 주고 판단을 돕는 것**입니다.

## 2.15 서브에이전트 실행이 중간에 끊겼을 때 (부분 출력 반환)

긴 작업 도중 서버 과부하(Server Overload), 타임아웃, 중단 등으로 서브에이전트 응답이 도중에 잘릴 수 있습니다. 이때 코디네이터가 받는 `Agent` 도구 결과는 다음과 같습니다.

> **이미 생성된 부분 텍스트 출력 + "완료되지 않았음"을 알리는 안내 노트**

즉 지금까지 나온 분석 단락들은 살아서 전달되고, 미완료 상태라는 표시가 함께 붙습니다. 이렇게 설계된 이유는 **코디네이터가 제어권을 쥔 채 다음 행동을 결정하게 하기 위해서**입니다. 이미 얻은 정보를 버리지 않고 활용하면서, 재시도할지·다른 방법을 쓸지·사용자에게 보고할지를 코디네이터가 판단합니다.

이와 대비되는 잘못된 기대들:

- 시스템이 몰래 자동 재시도해서 성공할 때까지 반복한다 → 무한 루프와 비용 폭증 위험이 있어 그렇게 하지 않습니다.
- 오류 표시 없이 완전히 빈 결과가 온다 → 아닙니다. 부분 출력과 미완료 표시가 포함됩니다.
- 캐시된 중간 도구 호출로 "완성된 전체 출력"을 복원해 준다 → 실제로 생성되지 않은 내용을 만들어낼 수는 없습니다.

## 2.16 사람에게 넘기는 인수인계(Handoff) 요약 작성법

에이전트가 처리하던 건을 사람 상담원/관리자에게 넘겨야 할 때가 있습니다(예: 사람만 승인할 수 있는 정책 예외). 이때 **인계받는 사람이 대화 전문(transcript)에 접근할 수 없다**는 조건이 자주 붙습니다.

좋은 인수인계 요약은 대화를 읽지 않고도 **즉시 결정하고 조치할 수 있게** 해야 합니다. 필수 3요소:

1. **식별자(Identifier)**: 어떤 고객/주문/거래 건인가 (예: `Customer ID 88213`)
2. **근본 원인(Root Cause)**: 조사로 밝혀낸 기술적/업무적 원인 (예: 재시도된 결제 게이트웨이 호출 때문에 생긴 중복 승인 보류(authorization hold)가 해제되지 않음)
3. **권장 조치(Recommended Action)**: 구체적으로 무엇을 하면 되는가 (예: 해당 보류를 무효화(void)하라)

좋은 예:

```
Customer ID 88213
Root cause: 재시도된 게이트웨이 호출로 중복 authorization hold 발생, 미해제 상태
Recommended action: 해당 hold를 void 처리
```

나쁜 요약의 전형:

- **모호함**: "청구 문제 이관됨, 고객이 환불 원함, 알아서 판단 바람" → 근거 데이터도 원인도 없어 인계받은 사람이 조사를 처음부터 다시 해야 합니다.
- **감정/과정 서술만 있음**: "고객이 화가 난 듯하고 여러 질문을 했음" → 원인도 조치도 없습니다.
- **전문(transcript)을 보라고 안내**: 전제상 접근 권한이 없으므로 실행 불가능한 지시입니다.

원칙: 인수인계 요약은 **자기완결적(self-contained)** 이어야 합니다.
