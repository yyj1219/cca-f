# 시나리오2_개발가속화

## 질문 1

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : A developer keeps a custom slash command for database migrations in a file at ~/.claude/commands/db-migrate.md, so teammates cannot invoke it. What change makes the command available to everyone who clones the repository?

**A.** Add an @import in the project CLAUDE.md pointing at the file's home directory path.

**설명**

@path import 문법은 CLAUDE.md의 내용을 모듈화하는 용도이지 커맨드 정의를 위한 것이 아니므로, 이 방법으로는 슬래시 커맨드가 등록되지 않는다. 또한 한 개발자의 홈 디렉터리 경로를 참조하게 되는데, 이 경로는 다른 팀원의 머신에는 존재하지 않는다.

**B.** Have each teammate copy the file into their own ~/.claude/commands/ directory.

**설명**

수동 복사는 한 번은 통하지만 이후 커맨드가 관리되지 않는 상태로 남는다. 앞으로 개선될 때마다 모든 팀원이 다시 복사해야 하고, 새로 합류한 사람은 이를 전혀 받지 못한다. 수작업으로 배포되는 설정은 결국 서로 달라지게 마련이며, 이것이 바로 버전 관리되는 프로젝트 스코프가 막아주는 문제다.

**C.** Paste the command's prompt body into the project CLAUDE.md under a # Commands heading.

**설명**

CLAUDE.md은 항상 로드되는 프로젝트 컨텍스트와 컨벤션을 담는 곳이며, 슬래시 커맨드를 정의하는 메커니즘이 아니다. 그곳에 넣은 텍스트는 모든 세션에 지침으로 로드되긴 하지만, 실행 가능한 커맨드를 만들어내지는 않는다.

**D(정답).** Move the command file into .claude/commands/ in the repository and commit it.

**설명**

이것이 정답인 이유는 커맨드의 스코프가 파일 위치로 결정되기 때문이다. 저장소 내 .claude/commands/ 안의 파일은 프로젝트 스코프이며 버전 관리와 함께 이동하므로, 저장소를 클론하거나 pull하는 모든 팀원이 자동으로 이 커맨드를 받게 된다. 파일을 옮기더라도 동일한 마크다운 파일이 커맨드의 동작을 계속 정의한다.

### 전반적인 설명

Claude Code는 파일 위치를 기준으로 커스텀 슬래시 커맨드를 찾으며, 바로 그 위치가 누가 그 커맨드를 쓸 수 있는지를 결정한다. ~/.claude/commands/ 안의 마크다운 파일은 사용자 스코프로, 한 사람을 따라 모든 프로젝트에서 사용되며 버전 관리에 커밋되지 않는다. 같은 파일을 저장소 내부의 .claude/commands/에 두면 프로젝트 스코프가 되어 코드베이스와 함께 배포되므로, 저장소를 클론하거나 pull한 누구나 즉시 호출할 수 있다. 두 위치 모두에서 마크다운 파일 자체가 커맨드 정의이며, 파일을 옮기는 것은 커맨드가 하는 일이 아니라 누가 그 커맨드를 볼 수 있는지를 바꾸는 것이다.

여기서 얻을 수 있는 사고 모델은, 공유 가능성이 팀이 이미 다른 모든 것을 공유하는 데 쓰는 메커니즘인 git 위에 놓여야 한다는 것이다. 홈 디렉터리 사이에서 파일을 복사하면 커맨드는 한 번 복제되지만 업데이트 경로가 끊겨서, 이후 수정될 때마다 머신들 사이에 조용한 차이가 생긴다. 프롬프트를 CLAUDE.md에 붙여넣는 것은 서로 다른 두 개념을 혼동하는 것이다. CLAUDE.md은 항상 로드되는 컨텍스트와 컨벤션을 담는 곳이고, 커맨드 파일은 필요할 때 호출되는 동작을 정의하는 곳이다. 마찬가지로 @path import는 CLAUDE.md 자체를 모듈화하기 위해 존재하는 것으로, 커맨드를 등록하지 않으며, 한 사용자의 홈 디렉터리를 가리키는 경로는 다른 머신에서는 아무 의미가 없다.

참고로 .claude/commands/는 예전 방식의 커맨드 포맷이며 지금도 계속 지원된다. 현재 Anthropic 가이드는 .claude/skills/<name>/SKILL.md에 두는 Agent Skills도 제공하는데, 이는 동일한 프로젝트 대 사용자 스코프 로직을 따른다. 자세한 내용은 Slash commands 문서를 참고하라.

## 질문 2

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : After splitting a 600-line project CLAUDE.md into topic files under .claude/rules/, sessions still load every rule, including database migration conventions needed only when editing files under db/migrations. What change makes that rule load conditionally?

**A.** List the migrations rule file in claudeMdExcludes so it is skipped at launch and picked up when relevant.

**설명**

claudeMdExcludes 설정은 일치하는 메모리 파일이 로드되는 것을 영구적으로 제외하는 것이며, 일치하는 파일을 편집할 때까지 로드를 지연시키는 것이 아니다. 이 규칙을 제외하면 마이그레이션 컨벤션이 아예 적용되지 않게 된다.

**B(정답).** Add YAML frontmatter with a paths field matching db/migrations glob patterns to the migrations rule file.

**설명**

경로 기반 규칙(path-scoped rules)은 조건부 로딩을 위해 공식 문서에 명시된 메커니즘이다. YAML 프런트매터에 paths 필드가 있는 규칙은 Claude가 해당 글롭 패턴에 일치하는 파일을 다룰 때만 적용된다. 이것이 바로 마이그레이션 파일을 전혀 다루지 않는 세션에서 거의 관련 없는 컨벤션을 배제해주는 방법이다.

**C.** Reference the migrations file from CLAUDE.md with an @import so its content is pulled in only on demand.

**설명**

import는 여러 파일에 걸쳐 내용을 정리하는 용도이지만, import된 파일은 지연 로딩되는 것이 아니라 실행 시점에 확장되어 컨텍스트에 로드된다. @import를 사용하면 팀이 없애려는 바로 그 무조건적 로딩이 그대로 발생한다.

**D.** Move the migrations rule file into a db/ subdirectory under .claude/rules/ so it applies only in that area.

**설명**

.claude/rules/ 아래의 하위 디렉터리는 순전히 정리 목적으로만 지원되는 것으로, 모든 마크다운 파일은 재귀적으로 탐색되며 디렉터리 위치가 규칙이 로드되는 시점을 결정하지는 않는다. paths 필드가 없으면 해당 규칙은 여전히 실행 시점에 무조건 로드된다.

### 전반적인 설명

큰 CLAUDE.md을 .claude/rules/ 아래의 주제별 파일들로 나누면 유지보수성은 좋아지지만, 그것만으로는 무엇이 로드되는지가 바뀌지 않는다. paths 필드가 없는 규칙 파일은 .claude/CLAUDE.md과 동일한 우선순위로 실행 시점에 무조건 로드된다. 컨텍스트 절감은 별도의 두 번째 단계에서 나온다. 즉, 글롭 패턴을 담은 paths 필드를 YAML 프런트매터에 추가하는 것이다(예: paths: ["db/migrations/**/*"]). 경로 기반 규칙은 Claude가 그 패턴에 일치하는 파일을 다룰 때만 컨텍스트에 들어오며, 이것이 프로젝트 지침이 커질 때 문서가 이 방식을 권장하는 이유다.

내면화해야 할 사고 모델은, Claude Code에는 지침에 대한 서로 다른 두 축이 있다는 것이다. 하나는 내용이 어디에 있는가(파일 하나 대 여러 주제별 파일, 재귀적으로 탐색되는 하위 디렉터리를 포함해 원하는 대로 정리 가능)이고, 다른 하나는 내용이 언제 로드되는가(실행 시점에 무조건 로드 대 경로 일치 시 조건부 로드)이다. paths 프런트매터만이 규칙을 조건부 쪽으로 옮긴다. .claude/rules/ 내부의 디렉터리 배치는 오직 정리에만 영향을 주고, @import 문은 실행 시점에 컨텍스트로 확장되므로 정리는 하되 로딩을 지연시키지는 않으며, claudeMdExcludes는 파일을 지연시키는 것이 아니라 로딩에서 완전히 제거하므로 제외된 규칙은 아예 적용되지 않는다.

규칙 디렉터리, 경로 기반 프런트매터, import 동작에 대해서는 Manage Claude's memory 문서를 참고하고, 더 큰 저장소에서 경로 기반 규칙이 디렉터리별 CLAUDE.md 파일과 어떻게 비교되는지는 Working with large codebases 문서를 참고하라.

## 질문 3

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : While reviewing a plan Claude produced for a multi-file refactor, a developer notices the plan omits a shared utility module the change must also update. What should the developer do at the approval prompt?

**A(정답).** Keep planning and point out the missing module so the plan is revised before any edits begin.

**설명**

승인 프롬프트는 바로 이런 상황을 위해 계획을 계속 진행하는 선택지를 명시적으로 제공한다. 아직 아무 편집도 이루어지지 않은 상태에서 계획을 수정하는 것이 이미 실행된 변경을 고치는 것보다 훨씬 저렴하며, 이것이 plan mode가 제공하는 핵심 가치다.

**B.** Approve the plan in auto mode, since Claude's earlier exploration will surface the module during execution.

**설명**

auto 모드는 편집 하나하나에 대한 감독 없이 승인된 계획을 실행하며, Claude가 계획 자체가 놓친 범위를 다시 발견해줄 것이라는 보장은 없다. 계획이 무엇을 구현할지를 정의하므로, 계획에 생긴 공백은 결과의 공백으로 이어지는 경향이 있다.

**C.** Exit plan mode with Shift+Tab and direct Claude to implement the refactor with the module included.

**설명**

승인된 계획 없이 plan mode를 벗어나면 검토 체크포인트를 버리는 셈이 되고, 여러 파일에 걸친 큰 변경이 direct execution으로 넘어가게 된다. 이는 애초에 plan mode를 이 작업에 적합한 선택으로 만들었던, 커밋 전에 설계를 먼저 하는 안전장치를 포기하는 것이다.

**D.** Approve the plan with manual edit review and correct the omission as the affected edits appear.

**설명**

수동 검토를 사용하면 개발자가 편집 하나하나를 살펴볼 수 있지만, 여기서 문제가 되는 것은 개별 diff가 아니라 계획의 범위 자체다. 불완전하다고 알고 있는 계획을 승인하면, 실행 중간에 빠진 모듈의 변경이 드러날 때 재작업이 발생하는 것은 거의 확실하다.

### 전반적인 설명

plan mode는 설계와 커밋을 분리하기 위해 존재한다. 활성화되어 있는 동안 Claude Code는 코드베이스를 조사하고 구현 계획을 작성하지만 소스 파일을 편집하지는 않는다. 개발자가 계획을 승인해야만 세션이 실행 권한 모드로 전환된다. 따라서 승인 프롬프트는 신중한 결정 지점이며, 세 가지 경로를 제공한다. auto 모드로 승인하고 실행하기, 편집마다 수동 검토를 거쳐 승인하기, 또는 계획을 계속 진행하기.

여기서 얻을 수 있는 사고 모델은, 계획은 저렴하고 쉽게 수정 가능한 산출물이지만 실행된 변경은 되돌리는 데 비용이 많이 든다는 것이다. 계획을 검토하는 과정에서 리팩터링이 반드시 건드려야 하는 공유 모듈처럼 범위의 공백이 드러나면, 올바른 대응은 plan mode에 머물면서 Claude에게 계획을 수정하도록 하는 것이다. 계획 단계를 몇 번 더 거치는 데는 몇 초밖에 들지 않지만, 실행 중간에 그 공백을 발견하면 부분적으로만 완료된 리팩터링, 일관성 없는 호출부, 여러 파일에 걸친 정리 작업이라는 비용이 든다.

다른 대안들은 모두 이미 알고 있는 계획의 결함을 나중에 수리하는 비용으로 맞바꾸는 것이다. 수동 편집 검토로 승인하면 diff를 하나씩 살펴볼 수 있어 구현상의 실수는 잡아내지만, 계획의 범위에 내재된 누락은 잡아내지 못한다. auto 모드로 승인하면 편집별 감독을 완전히 없애버려 문제가 더 커진다. Shift+Tab으로 plan mode를 벗어나 direct execution으로 전환하는 것은 체크포인트 자체를 완전히 버리는 것으로, 여러 파일에 걸친 큰 변경에는 정확히 반대되는 방향이다.

plan mode, 승인 선택지, 모드 전환이 어떻게 동작하는지에 대해서는 permission modes에 관한 공식 문서를 참고하라.

## 질문 4

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : A developer sets context: fork on a /deep-review skill to keep its verbose analysis out of the main session. Invoked mid-conversation with "review the changes we discussed", the fork reports finding no relevant changes. What should the developer do?

**A.** Set agent: Explore in the frontmatter so the fork runs with a richer exploration context that includes recent project state.

**설명**

이것은 틀렸다. agent 필드는 fork를 실행할 서브에이전트 구성을 선택하는 것일 뿐이며, 어떤 agent를 선택하더라도 메인 대화 기록에 접근할 수 있게 되지는 않는다. 오히려 Explore는 컨텍스트를 작게 유지하기 위해 CLAUDE.md와 git status를 건너뛰므로, 이 변경으로는 세션에서 논의한 변경 사항에 대한 참조를 해결할 수 없다.

**B(정답).** Keep context: fork and pass the specific files and change details to the skill explicitly as invocation arguments.

**설명**

이것이 정답이다. context: fork가 설정된 skill은 프롬프트 자체가 skill 내용인 포크된 서브에이전트에서 실행되며, 그 서브에이전트는 메인 대화 기록에 접근할 수 없다. "우리가 논의한 변경 사항"과 같은 참조는 fork가 결코 받지 못하는 컨텍스트를 가리키므로, 관련 세부 정보를 명시적으로 전달해야 하며, 그러면서도 fork는 여전히 방대한 출력을 격리된 상태로 유지할 수 있다.

**C.** Add allowed-tools with Read, Grep, and Bash so the fork can inspect the repository and locate the discussed changes.

**설명**

이것은 틀렸다. allowed-tools를 생략한다고 해서 포크된 skill의 도구가 제거되는 것은 아니며, 이 옵션은 설정되었을 때만 도구 접근을 제한한다. fork의 문제는 도구 접근이 아니라 대화 컨텍스트가 없다는 것이므로, 저장소를 살펴본다고 해서 "우리가 논의한 변경 사항"이 무엇을 가리키는지 해결되지는 않는다.

**D.** Remove context: fork so the skill runs inline with the conversation and accept its full output into the main session.

**설명**

이것은 틀렸다. 방대한 분석을 메인 세션 밖에 두려는 원래 목표를 포기하는 것이기 때문이다. 인라인으로 실행하면 skill이 대화에 접근할 수는 있지만, 수천 줄에 달하는 탐색 내용이 메인 컨텍스트에 그대로 쌓이게 되는데, 이것이 바로 fork를 도입해서 막으려 했던 문제다.

### 전반적인 설명

context: fork에 대해 가져야 할 사고 모델은, 이것이 현재 세션을 들여다보는 창이 아니라 클린룸 작업자라는 것이다. skill이 context: fork를 선언하면 Claude Code는 프롬프트 자체가 skill 내용인 서브에이전트를 새로 띄운다. 시스템 프롬프트는 선택된 agent 유형에서 온다(agent 필드가 설정되지 않으면 기본값은 general-purpose다). 결정적으로, 그 서브에이전트는 메인 대화 기록에 접근할 수 없다. 이 격리야말로 이 패턴이 동작하는 이유다. 수천 줄에 달하는 탐색 결과가 fork 자체의 컨텍스트에 쌓이고, 정제된 결과만 메인 세션으로 돌아온다. 그 대가로 fork는 메인 세션이 아는 모든 것을 잃게 되므로, "우리가 논의한 변경 사항"과 같은 지시는 fork 내부에서는 해결할 수 없는 참조가 된다.

이것이 실무 설계에 주는 함의는, 포크된 skill은 반드시 독립적으로 완결된 작업 워크플로여야 한다는 것이다. 절차는 skill 본문에 담고, 세션에 특화된 세부 정보(파일 경로, 브랜치 이름, 검토할 특정 diff 등)는 인자로 명시적으로 전달해야 한다. 이것이 바로 Anthropic이 수동적인 가이드라인 콘텐츠를 포크하는 것을 경고하는 이유이기도 하다. 본문이 컨벤션뿐인 fork는 실행 가능한 작업이 없어 아무 유용한 결과도 돌려주지 못한다. 진행 중인 작업의 방향을 잡아주어야 하는 가이드라인은 인라인(CLAUDE.md나 일반 skill)에 두어야, 실시간 대화와 함께 자리하게 된다.

다른 선택지들은 핵심 메커니즘을 놓치고 있다. fork를 제거하면 대화 접근은 복구되지만, 개발자가 애초에 분리하려 했던 방대한 출력이 메인 세션에 그대로 쏟아진다. Explore agent를 선택하는 것은 fork를 실행할 서브에이전트 구성만 바꿀 뿐이고, Explore는 가볍게 유지하기 위해 의도적으로 CLAUDE.md와 git status를 건너뛴다. 어떤 agent를 선택해도 대화 기록을 가져오지는 못한다. 그리고 allowed-tools는 스스로 설정해야 적용되는 제한이므로 생략한다고 도구가 비활성화되는 것도 아니며, 저장소 조사로는 대화상의 참조를 해결할 수 없다. 포크된 실행 모델과 프런트매터 레퍼런스는 Agent Skills 문서를 참고하라.

**A(정답).** Provide two or three concrete test cases showing sample input rows containing nulls and the exact expected output for each.

**설명**

서술형 설명이 계속 일관되지 않게 해석될 때, 구체적인 입력/출력 예시는 기대하는 변환을 전달하는 가장 효과적인 방법이다. null인 email을 가진 행과 그에 대해 기대하는 정확한 결과를 함께 보여주면, "gracefully" 같은 모호한 표현이 남기는 불확실성이 사라진다.

**설명**

**설명**

plan mode는 아키텍처에 영향을 미치는 큰 변경이나 여러 실행 가능한 접근 방식이 있을 때 유용하며, 명세가 부족한 엣지 케이스 동작을 명확히 하는 데 쓰는 것이 아니다. 똑같이 모호한 지시로 만든 계획은 워크플로 앞쪽에서 같은 모호함을 그대로 담고 있을 뿐이다.

**D.** Restate the null-handling requirement in stronger prose, marking it IMPORTANT at the top of the prompt so it cannot be missed.

**설명**

문제는 지시가 무시되고 있다는 것이 아니라, "handle missing values gracefully"라는 표현 자체가 실제로 올바른 동작이 무엇인지에 대해 모호하다는 점이다. 강조는 우선순위를 높일 뿐 명세를 추가해주지 않으므로, 해석의 문제는 여전히 남는다.

"handle missing values gracefully"라는 문구는 여러 해석을 허용한다. 행을 건너뛴다, 기본값으로 대체한다, 감사 로그를 남긴다, 타입이 있는 오류를 발생시킨다 등이다. 모델은 그중 하나를 선택해야 하고, 생성할 때마다 다른 선택을 한다. 두세 개의 구체적인 테스트 케이스(email이 null인 입력 행과 정확히 기대되는 출력 행 또는 오류)는 이 해석의 공간을 검증 가능한 하나의 동작으로 좁혀준다. Anthropic의 프롬프트 예시와 템플릿에 관한 가이드는 멀티샷 예시를 출력 동작을 조정하는 신뢰할 수 있는 방법으로 설명하며, 평가 가이드에서는 누락되거나 잘못된 형식의 입력 데이터 같은 엣지 케이스를 명시적으로 반영하라고 요구한다.

이 예시들은 회귀 테스트로도 기능한다. 한 번 기록해두면 수정된 스크립트에 대해 다시 실행할 수 있으며, Anthropic의 공통 워크플로 가이드는 정확히 이런 엣지 조건 케이스를 명시하고 실행한 후 실패를 고치는 루프를 권장한다. 오답들은 모두 진단을 잘못하고 있다. 요구 사항을 굵게 강조하는 것은 명세를 추가하지 않은 채 강조 자원을 쓰는 것일 뿐이다. plan mode는 크고 여러 접근 방식이 있는 변경을 위한 범위 설정 도구로, 검토를 앞당길 수는 있지만 지시 자체가 정하지 않은 모호함을 해결하지는 못한다. temperature를 낮추는 것은 "틀리고 제각각인" 것을 "틀리지만 일관된" 것으로 바꾸는 것일 뿐이며, 결정론이 누락된 올바른 동작의 정의를 대신 제공해주지는 않는다.

새로 시작하면 계획 세션이 쌓아온 탐색 컨텍스트를 버리게 되고, Claude는 손실이 있는 요약본만으로 작업해야 한다. 원래 설계된 워크플로는 같은 세션을 유지한 채 계획을 승인함으로써 plan mode를 벗어나는 것이다.

이러한 설계가 의도하는 트레이드오프는 분명하다. 계획 단계에서는 편집이 차단된 상태로 유지되어, 서비스 재구성 같은 큰 아키텍처 변경이 사람이 접근 방식에 동의하기 전에 파일을 변형시키기 시작할 수 없게 한다. 이것이 바로 plan mode에 머문 채 Claude에게 구현을 지시해도 아무 진전이 없는 이유이며, bypassPermissions로 건너뛰는 것이 안티패턴인 이유이기도 하다. 워크플로에 필요한 것은 모드 전환뿐인데, 그 대신 모든 승인 검사를 포기해버리는 셈이기 때문이다. 새 세션을 시작하는 것은 애초에 좋은 계획을 만들어낸 탐색 컨텍스트를 버리고, 세부 사항이 손실된 요약본으로 대체하는 것이다. 전체 워크플로에 대해서는 Permission modes와 Claude Code best practices 문서를 참고하라.

**C.** Enable extended thinking during direct execution so the model reasons through the strategy choice while editing.

**설명**

이것은 틀렸다. extended thinking은 주어진 단계에서의 추론을 심화시킬 뿐 워크플로 자체를 바꾸지는 않는다. 근본적인 접근 방식이 아직 결정되지 않은 상태에서도 Claude는 여전히 편집을 커밋하게 된다. 또한 수십 개의 파일이 바뀌기 전에 팀이 검토할 계획 산출물도 제공하지 못한다.

**설명**

이것이 정답이다. 이 작업은 plan mode가 필요한 두 가지 특징, 즉 여러 파일에 걸친 큰 변경과 여러 실행 가능한 접근 방식을 모두 갖고 있다. plan mode를 사용하면 Claude가 편집 없이 읽고 탐색해, 두 전략을 놓고 평가할 수 있는 계획을 만들어내며, 그런 다음에야 구현으로 넘어갈 수 있다. 이는 잘못된 방향으로 진행된 60개 파일 변경을 나중에 다시 작업하는 것보다 훨씬 저렴하다.

### 전반적인 설명

plan mode는 탐색과 구현을 분리하는 Claude Code의 권한 모드다. Claude는 파일을 읽고 조사 명령을 실행할 수 있지만, 제안한 계획을 승인하기 전까지는 아무런 편집도 하지 않는다. 여기서 얻을 사고 모델은 워크플로에 내장된 설계 리뷰다. 추가 단계의 비용은 적으며, 잘못된 접근 방식에 커밋했을 때 되돌리는 비용이 큰 경우라면 이 단계는 충분히 값어치가 있다. 이것이 정확히 여기에 해당하는 상황이다. 약 60개 파일이 영향을 받고, 코드베이스 탐색이 실제로 드러내는 것과 맞대어 평가해야 할, 진정으로 실행 가능한 두 전략(어댑터 레이어 대 직접 재작성)이 존재한다.

의사결정 프레임워크는 범위와 확실성에 따라 달라진다. direct execution은 명확한 스택 트레이스가 있는 단일 파일 수정처럼, diff를 한 문장으로 설명할 수 있는 변경에 적합하다. plan mode는 대규모 변경, 낯선 코드, 아키텍처 결정, 그리고 경쟁하는 접근 방식이 있는 상황에 적합하다. 일반적인 흐름은 이 둘을 결합한다. 먼저 계획을 세우고, 계획을 검토하며 반복 개선한 다음(계획을 반복 개선하는 것은 방향이 잘못된 실행 후 정리하는 것보다 훨씬 빠르다), 승인한 뒤 Claude가 실행하도록 한다.

완전히 명세된 어댑터 설계를 미리 밀어붙이는 것은 두 전략 사이에서 결정을 내려야 할 조사 과정을 생략하는 것이다. 점진적으로 실행하다가 충돌이 나타날 때만 계획을 세우는 것은, 계획이 미리 막아줄 수 있었던 재작업의 비용을 그대로 치르는 것이다. extended thinking은 한 단계 내에서의 추론 깊이를 개선하지만 편집을 지연시키거나 검토 가능한 계획을 만들어내지는 못하므로, 이 워크플로 문제를 해결하지 못한다. 승인 전에 plan mode가 어떻게 동작을 제한하는지는 Permission modes 문서를 참고하라.

plan mode가 세션을 어떻게 제한하는지, 그리고 모드 사이를 어떻게 이동하는지는 Permission modes 문서를 참고하라.

### 전반적인 설명

Claude Code의 가이드는 계획이 그 비용을 벌어들이는 경우와 순수한 오버헤드에 불과한 경우 사이에 분명한 선을 긋는다. plan mode는 읽기 전용 조사 단계다. Claude는 파일을 읽고 탐색 명령을 실행할 수 있지만, 계획을 승인할 때까지는 아무런 편집도 하지 않는다. 이 게이트는 접근 방식을 잘못 잡았을 때 비용이 큰 경우에 정확히 가치가 있으며, 문서는 이를 세 가지 상황으로 규정한다. 접근 방식이 불확실할 때, 변경이 여러 파일에 걸칠 때, 또는 수정 대상 코드에 익숙하지 않을 때다.

작고 잘 이해된 변경에서는 같은 게이트가 아무런 보상 없는 마찰일 뿐이다. Claude Code best practices는 이를 직접적으로 명시한다. plan mode는 오버헤드를 더하므로, 범위가 명확하고 수정이 작은 작업(오타, 로그 라인, 변수 이름 변경, 하나의 빠진 조건문 등)에는 Claude에게 직접 해달라고 요청해야 한다. 여기서 제시되는 실용적인 기준은, diff를 한 문장으로 설명할 수 있다면 계획 단계를 건너뛰라는 것이다. direct execution은 따로 이름 붙여진 모드가 아니다. 이는 단지 평소의 권한 모드 설정 하에서 Claude에게 변경을 요청하는 것을 의미하며, 여전히 정확한 프롬프트와 이후의 검증 단계가 필요하다.

잘못된 제안들은 이 프레임워크를 뒤집는다. 여러 파일에 걸친 변경, 낯선 영역, 경쟁하는 접근 방식은 plan mode를 트리거하는 전형적인 신호들이다. 대규모의 반복적인 편집이라도 되돌리기 비용이 큰 패턴에 커밋하게 되며, 낯선 영역을 편집하면서 탐색하는 것은 이해가 확립되기 전에 변경을 커밋하는 것을 의미하고, 여러 접근 방식 중 하나를 직접 시도해보는 것은 코드베이스를 실험 대상으로 만들어버린다. 무조건 모든 것을 계획하라는 정책은 반대 방향으로 실패한다. 위험이 전혀 없던 변경에 대해서도 팀의 속도를 늦추는 절차를 사소한 수정에까지 부과하게 된다.

## 질문 11

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : The review job's --json-schema declares a suggested_fix_url field with "format": "uri", yet the comment-posting step occasionally receives values that are not valid URIs even though the run reported validated output. What is the correct fix?

**A(정답).** Validate URI syntax in the pipeline, since the format keyword is accepted as an annotation, not enforced.

**설명**

이것이 정답이다. Claude Code의 스키마 검증은 format 키워드(uri나 email 등)를 어노테이션으로만 취급하며, 그 형식의 문법 규칙을 따르지 않는 값을 거부하지 않는다. 이후 댓글 게시 단계가 의존하는 문법적 보장은 파이프라인 코드에서 확인해야 한다.

**B.** Add an explicit instruction in the prompt stating that the field must contain a syntactically valid URI.

**설명**

프롬프트 지시는 형식이 올바른 값이 나올 가능성을 높이지만 이를 보장하지는 않는다. 모델은 여전히 스키마 검증을 통과하는 잘못된 형식의 URI를 낼 수 있다. 댓글을 자동으로 게시하는 파이프라인에는 확률적인 확인이 아니라 결정론적인 확인이 필요하다.

**C.** Switch the invocation to --output-format stream-json so each finding is validated as it is emitted.

**설명**

stream-json 형식은 출력이 전달되는 방식(실시간 스트리밍을 위한 줄바꿈 구분 JSON)을 바꿀 뿐, 스키마 검증이 동작하는 방식을 바꾸지는 않는다. 어떤 출력 형식을 선택하든 format 키워드는 여전히 강제되지 않는다.

**D.** Add the field to the schema's required array so malformed URIs fail validation and trigger a reprompt.

**설명**

required 배열은 그 필드가 출력에 존재하는지만 확인한다. 필드 값이 문법적으로 유효한 URI인지 검증하는 것은 전혀 하지 않으므로, 잘못된 형식의 값도 여전히 검증을 통과하게 된다.

### 전반적인 설명

Claude Code가 --output-format json과 --json-schema로 실행될 때, 출력은 structured_output으로 반환되기 전에 제공된 JSON Schema에 대해 검증된다. 이 검증은 타입, required 필드, enum, 객체 형태 같은 구조적 속성을 다룬다. format 키워드(예: "format": "uri"나 "format": "email")는 다른 경우다. 이는 받아들여지지만 어노테이션으로만 취급되므로, not-a-real-url 같은 값도 문자열이기만 하면 검증을 통과한다. 이는 JSON Schema 명세 자체를 그대로 반영한 것으로, format 검사는 검증기(validator)에게 선택 사항이며, 이것이 왜 어떤 실행이 스키마 검증을 통과한 출력이라고 정직하게 보고하면서도 다운스트림 시스템이 쓸 수 없는 값을 여전히 내놓을 수 있는지를 설명해준다.

여기서 가져야 할 올바른 사고 모델은 2계층 계약이다. 스키마는 형태(shape)를 보장하고, 여러분의 파이프라인 코드는 의미(semantics)를 보장한다. 파싱 가능한 URI, 해석 가능한 파일 경로, diff 내의 라인 번호처럼 게시 단계가 실제로 정확성을 위해 의존하는 것은, 댓글이 게시되기 전에 코드에서 결정론적으로 확인해야 한다. 필드를 required로 표시하는 것은 존재 여부만을 단언할 뿐 문법을 단언하지는 않는다. stream-json으로 전환하는 것은 전달 메커니즘(하나의 최종 JSON 봉투 대신 줄바꿈으로 구분된 이벤트)을 바꿀 뿐, 검증이 강제하는 것을 바꾸지는 않는다. 프롬프트 지시는 유효한 값이 나올 확률을 높이지만 실패율을 0으로 만들지는 못하는데, 이것이 바로 파이프라인이 지금 겪고 있는 상황이다.

format 키워드가 강제되지 않는다는 공식적인 언급은 Headless mode 문서를, 스키마 검증과 재시도가 어떻게 동작하는지는 Structured outputs 문서를 참고하라.

You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : Claude Code is implementing a caching layer in a domain your team knows poorly. A test suite exists, and the first run reports several failures. Which two refinement practices fit this situation? (Select TWO.)

**A(정답).** Feed the failing test output back to Claude and iterate, letting each cycle apply fixes and re-run the suite to verify progress.

**설명**

이것이 정답이다. 테스트 주도 반복 개선은 문서에 명시된 피드백 루프다. 실행 가능한 테스트는 Claude에게 구체적이고 검증 가능한 목표를 제공하며, 매 사이클마다 실패를 공유하면 스위트가 통과할 때까지 점진적인 개선을 이끌어낼 수 있다. 각 반복은 이미 동작하는 것은 보존하고 동작하지 않는 것만 고친다.

**B(정답).** Use the interview pattern before implementing so Claude asks questions that surface considerations like cache invalidation and failure modes.

**설명**

이것이 정답이다. 인터뷰 패턴은 낯선 도메인을 위해 설계된 것으로, Claude가 질문을 던지게 하면 코드가 작성되기 전에 팀이 예상하지 못했던 설계상의 고려 사항을 드러낼 수 있다. 이는 구현이 잘못된 가정에 맞춰 최적화될 가능성을 줄여준다.

**C.** Discard the current implementation after each failing run and regenerate it from scratch so earlier flawed reasoning does not carry over.

**설명**

이것은 테스트 주도 반복 개선의 핵심인 점진적 개선을 포기하는 것이다. 처음부터 다시 생성하면 테스트가 이미 검증한 구현 부분까지 버리게 되고, 특정 실패를 고쳐나가면서 얻는 누적 효과를 포기하게 된다.

**D.** Relax the failing assertions so the suite passes now, then restore the original expectations once the implementation stabilizes.

**설명**

이것은 테스트 주도 반복 개선을 동작하게 만드는 바로 그 신호를 약화시킨다. 완화된 어서션은 잘못된 동작을 눈치채지 못하고 통과시키며, 나중으로 미룬 재강화는 대개 실제로는 이루어지지 않아, 캐싱 레이어가 실제 요구 사항에 대해 검증되지 않은 채로 남게 된다.

### 전반적인 설명

Claude Code를 이용한 테스트 주도 반복 개선에는 내면화해야 할 두 가지 차원이 있다. 구현 전에 어떻게 준비하는가, 그리고 이후 실패를 어떻게 피드백하는가이다. 낯선 도메인에서는 준비 단계가 가장 중요하다. 인터뷰 패턴은 일반적인 흐름을 뒤집는다. 모든 것을 사전에 명시하는 대신, Claude에게 설계에 대해 여러분을 인터뷰해달라고 요청하는 것이다. 캐싱 레이어의 경우, 이런 대화는 무효화 전략, 오래된 데이터 읽기, 메모리 압박 상황에서의 축출, 백엔드 스토어를 사용할 수 없을 때의 동작 같은 질문들을 자연스럽게 드러내는데, 이는 그 도메인에 익숙하지 않은 팀이 흔히 명시하지 못하고 지나치는 고려 사항들이다. 그 답변들은 구현이 한 줄도 작성되기 전에 구체적인 테스트 케이스가 된다.

피드백 쪽에서 반복을 효과적으로 만드는 메커니즘은 실행 가능한 검증이다. 테스트 스위트는 Claude에게 올바른 동작에 대한 객관적이고 기계로 검증 가능한 정의를 제공하므로, 각 사이클은 근거를 갖게 된다. 실패 출력을 공유하고, Claude가 수정을 제안하게 하고, 스위트를 다시 실행하고, 반복한다. 형식이나 로직 오류로 인한 실패는 이 루프에 잘 반응하는데, 실패한 테스트가 정확히 무엇이 기대되었는지를 명시하고, 통과한 테스트는 이후 사이클이 깨뜨려서는 안 되는 동작을 고정해주기 때문이다.

두 오답 모두 이 루프를 서로 다른 방향에서 무너뜨린다. 스위트를 통과시키기 위해 어서션을 완화하는 것은 피드백 신호 자체를 파괴한다. 테스트는 기대되는 동작을 인코딩하기 위해 존재하는데, 이를 완화하면 구현이 더 이상 실제 요구 사항에 대해 측정되지 않는다는 뜻이다. 실패할 때마다 구현을 처음부터 다시 생성하는 것은 통과한 테스트가 이미 고정해둔 동작을 버리는 것이며, 반복 개선의 요점 자체, 즉 각 사이클이 동작하는 것은 보존하고 동작하지 않는 것은 고친다는 원칙을 포기하는 것이다. 테스트 주도 개발 워크플로에 대해서는 Claude Code Best Practices와 Claude Code common workflows 문서를 참고하라.
