# 시나리오2_개발가속화

## 질문 1

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : A nightly job submits thousands of documentation-generation requests as one Message Batch, one request per source file. When designing the custom_id scheme for these requests, which TWO design decisions are correct? (Select TWO.)

**A.** Use each file's full repository path, slashes included, as its custom_id, since any UTF-8 string up to 256 characters is accepted.

**설명**

이는 잘못된 답이다. custom_id는 1자에서 64자 사이로 제한되며 문자, 숫자, 하이픈, 밑줄만 포함할 수 있다. 슬래시가 포함된 원본 파일 경로는 거부되므로, 경로는 인코딩하거나 규격에 맞는 식별자로 매핑해야 한다.

**B(정답).** Generate the identifier in your own code at submission time and use it to map each returned result back to its source file.

**설명**

이는 올바른 답이다. custom_id는 각 요청의 래퍼에서 개발자가 직접 제공하는 값이며, 결과를 조회할 때 결과 객체와 함께 나타나므로 각 출력을 원본 파일에 매핑할 수 있다. 이는 성공한 결과 내부에 있는 서버 생성 메시지 식별자와는 별개의 값이다.

**C.** Omit custom_id on each request and rely on the API to generate one automatically in the batch creation response for later matching.

**설명**

이는 잘못된 답이다. custom_id는 배치 내 각 요청 항목에서 개발자가 반드시 제공해야 하는 필수 필드이며, API가 대신 식별자를 생성해주지 않는다. 상관 관계 매칭이 동작하는 이유는 여러분의 코드가 값을 선택했고 이를 원본 파일로 다시 매핑할 수 있기 때문이다.

**D(정답).** Assign each request a custom_id that is unique within the batch, so no two requests in one submission share a value.

**설명**

이는 올바른 답이다. Message Batches API는 배치 내에서 custom_id 값이 고유해야 함을 요구한다. 동일한 제출 내에 중복된 값이 있으면 각 결과를 원본 요청과 명확하게 대응시키는 것이 불가능해진다.

### 전반적인 설명

Message Batches API는 개별 Messages 요청을 정확히 두 개의 필드, custom_id와 params로 감싼다. custom_id는 제출 시점에 여러분이 지정하는 상관 관계 키이며, 배치가 종료되면 결과 엔드포인트가 .jsonl 파일을 스트리밍하는데 이때 모든 줄에는 해당 결과 객체와 함께 동일한 custom_id가 실려 있다. 결과가 제출 순서대로 도착한다는 보장이 없기 때문에, 이 필드가 각 출력을 그것을 생성한 파일에 다시 연결할 수 있는 유일하게 신뢰할 수 있는 방법이다.

이 방식이 동작하는 데는 두 가지 속성이 핵심이다. 첫째는 배치 내 고유성이다. 두 요청이 동일한 값을 공유하면 결과 줄이 모호해지므로, API는 하나의 제출 내에서 각 custom_id가 서로 달라야 함을 요구한다. 둘째는 개발자 소유권이다. 이 값은 서비스가 아니라 여러분의 코드가 선택하는 값이며, 바로 그 덕분에 파이프라인에 의미 있는 정보(파일 해시, 데이터베이스 키, 정제된 경로 등)를 담을 수 있다. 이는 성공한 결과 내부에 있는 API 생성 message.id와는 다른 것이다. 그 식별자는 서버 측에서 생성되며 요청이 어느 원본 파일에서 왔는지에 대해서는 아무런 정보도 알려주지 않는다.

형식에도 제약이 있다. ^[a-zA-Z0-9_-]{1,64}$ 패턴에 맞는 1자에서 64자 사이의 문자열이어야 한다. 슬래시, 공백, 기타 구두점은 거부되므로, 저장소의 원본 경로를 그대로 식별자로 사용하려는 단순한 계획은 실패한다. 팀들은 보통 경로를 해시하거나, 규격에 맞는 ID에서 원본 파일로 이어지는 조회 테이블을 유지하는 방식을 사용한다. 필드 제약 사항과 결과 상관 관계 매칭 워크플로에 대해서는 Batch processing 문서와 Create a Message Batch API 레퍼런스를 참고하라.

## 질문 2

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : Your team's documentation pipeline runs Claude Code non-interactively with a validation-retry loop that resends each failed extraction along with its specific validation errors. The source documents never contain owner_team; that field is recorded only in a separate service catalog that is not included in the prompt or tool context. Which change to the retry policy is correct?

**A.** Stop retrying summary strings that exceed the maximum length allowed by the validation rules, and truncate those entries in a post-processing step before downstream delivery.

**설명**

길이가 초과된 요약은 모델이 이미 생성한 텍스트를 압축해서 고칠 수 있는 형식 문제이므로 재시도 루프에 남아 있어야 한다. 무조건적인 잘라내기는 문장 중간에서 의미를 훼손할 위험이 있는 반면, 구체적인 길이 오류를 다시 피드백해주면 모델에게 명확하고 실행 가능한 수정 목표를 제공하게 된다.

**B(정답).** Stop retrying blank owner_team values and instead supply the service catalog data as context so the model can ground the field in provided information.

**설명**

이것이 올바른 정책 변경이다. 필수 정보가 제공된 컨텍스트에 없는 경우 재시도는 성공할 수 없다. 어떤 오류 피드백을 주더라도 모델이 처음부터 받지 못한 데이터를 만들어낼 수는 없으며, 필드를 채우라는 압박은 값을 조작해낼 위험을 높인다. 카탈로그 데이터를 컨텍스트로 제공하거나 통합을 통해 제공하는 것이 근본 원인을 해결하는 방법이다.

**C.** Stop retrying dates emitted as MM/DD/YYYY where the schema requires ISO 8601, and route those extractions to a manual reformatting queue for human correction instead.

**설명**

형식 불일치는 재시도로 해결 가능한 전형적인 실패 유형이므로, 이를 루프에서 제외하는 것은 잘못된 판단이다. 재시도 프롬프트에 실패한 출력과 구체적인 오류가 포함되면 모델은 날짜 형식을 다시 맞추는 데 필요한 모든 정보를 갖게 되며, 보통 한두 번의 재시도로 이런 종류의 문제는 해결된다.

**D.** Stop retrying extractions whose parameters array is nested under the wrong parent object, and regenerate those documents from scratch with a fresh prompt and no error context.

**설명**

배열이 잘못된 위치에 들어가는 것과 같은 구조적 오류는 재시도로 고칠 수 있으므로 루프에 남아 있어야 한다. 처음부터 다시 생성하는 방식은 수정을 정밀하게 만들어주는 오류 피드백을 버리는 것이다. 원본 콘텐츠와 검증 오류를 함께 제공하면 모델은 무엇을 어떻게 재구성해야 하는지 정확히 알 수 있다.

### 전반적인 설명

검증-재시도 루프에 대한 사고 모델은 단순하다. 재시도는 수정에 필요한 모든 정보가 이미 모델 앞에 놓여 있을 때만 성공할 수 있다. 재시도 프롬프트에 원본 자료, 실패한 출력, 구체적인 검증 오류가 포함되어 있으면 잘못된 날짜 형식, 잘못된 구조, 길이 초과 문자열 같은 실패는 스스로 고칠 수 있으며 보통 한두 번의 재시도로 해결된다. 이 루프가 동작하는 이유는 모델이 자신이 이미 가지고 있는 정보를 다시 근거로 삼기 때문이다.

owner_team 값의 누락은 이 전제를 깨뜨린다. 소유권 데이터는 컨텍스트에 절대 들어오지 않는 외부 서비스 카탈로그에만 존재하므로, 재시도할 때마다 동일하게 불가능한 상황이 반복된다. 더 나쁜 것은, 모델이 알 수 없는 값을 반복적으로 요구하면 값을 조작해낼 압박이 생긴다는 점이다. Anthropic의 환각 방지 가이드는 정보가 부족하다고 모델이 스스로 말할 수 있게 허용하고 제공된 문서로만 범위를 제한하라고 권장하는데, 이는 그렇지 않으면 모델이 그럴듯해 보이지만 근거 없는 내용을 생성하기 때문이다. 올바른 해결책은 구조적인 것이다. 카탈로그 내보내기 결과를 프롬프트에 포함시키거나(Anthropic의 문서 근거화 가이드는 모델이 활용할 수 있도록 원본 문서를 감싸는 방법을 다룬다), 도구를 통해 데이터를 가져오거나, 필드를 null 허용으로 만들어 부재를 정직하게 표현하는 것이다.

다른 제안된 변경 사항들은 재시도로 해결 가능한 실패를 루프에서 빼내어 열등한 대체 메커니즘으로 바꾸는 것이다. 수동 재포맷 대기열은 모델이 안정적으로 처리할 수 있는 수정 작업에 사람의 수고를 추가하고, 오류 컨텍스트 없이 처음부터 재생성하는 방식은 재시도를 정밀하게 만들어주는 피드백을 버리며, 후처리 단계의 잘라내기는 모델이 압축을 통해 보존했을 의미를 훼손할 수 있다. 형식·구조 오류와 정보 부재라는 이 두 범주를 구분하는 것이 재시도 예산을 절대 수렴할 수 없는 실패에 낭비하지 않도록 지켜주는 핵심이다.

## 질문 3

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : The team's automated review pass over Claude-generated refactors is prompted to "only report findings you are highly confident about." Precision looks good, but real defects now slip through unreported. What change best restores recall while keeping noise manageable?

**A.** Run the conservative review pass three times per change and report the union of findings across the runs.

**설명**

낮은 확신도의 발견 사항을 억제하도록 지시받은 리뷰 패스를 반복 샘플링해도, 무작위로 동일한 기준을 통과하는 것만 회수될 뿐이다. 비용은 배로 늘어나지만 체계적인 억제 지시는 그대로 남아 있으므로, 프롬프트가 모델에게 보류하라고 지시한 종류의 발견 사항은 여전히 대부분 보고되지 않는다.

**B.** Keep self-filtering in the prompt but lower the bar from "highly confident" to "reasonably confident" findings.

**설명**

이는 모호한 프롬프트 내 자체 필터링이라는 동일한 설계 결함을 그대로 유지하며, 단지 억제 기준선을 옮기는 것에 불과하다. "적당히 확신"과 같은 표현은 실행 가능한 의미가 없으므로, 모델은 여전히 그 기준을 일관성 없게 해석하고 예측 불가능한 실제 결함들을 계속 억제하게 된다.

**C.** Add a prompt instruction telling the model to prioritize recall over precision when deciding what to report.

**설명**

이는 실행 가능한 내용이 없는 모호한 지시로, 원래의 보수적 지시와 동일한 실패 유형이다. "재현율을 우선하라"와 같은 추상적인 목표는 어떤 발견 사항을 포함하거나 제외해야 하는지 모델에게 알려주지 않으므로, 출력은 정교하게 조정되지 못한 채 일관성 없는 상태로 남는다.

**D(정답).** Report every finding with a self-rated confidence level, moving the confidence threshold into a downstream filter step.

**설명**

이는 발견과 필터링을 분리하기 때문에 올바른 답이다. 리뷰 패스는 커버리지를 최적화하고, 자체 보고된 확신도는 각 발견 사항의 순위를 매길 수 있게 하며, 임계값은 후속 단계에서 결정론적으로 적용된다. 낮은 확신도의 발견 사항은 있는 그대로 노출되는 대신 필터링되거나 별도 경로로 처리되므로, 개발자를 넘치는 정보로 압도하지 않으면서 재현율을 회복할 수 있다.

### 전반적인 설명

"확신도가 높은 발견 사항만 보고하라"와 같은 지시는 문자 그대로 따라진다. 모델은 철저히 조사할 수는 있지만, 자신이 해석한 기준선 아래에 있는 모든 것을 억제해버린다. 이는 재현율을 정밀도와 맞바꾸는 것이며, 그것도 관찰이 불가능한 단일 단계 내부에서 이루어진다. 병합된 코드로 결함이 새어나가는 것이 우려하는 실패라면, 이는 그 맞교환을 하기에 정확히 잘못된 위치다.

문서화된 패턴은 발견과 필터링을 분리하는 것이다. 발견 패스에게는 커버리지가 임무라고 알려준다. 즉 불확실하거나 심각도가 낮은 것을 포함해 모든 이슈를 보고하고, 각각에 자체 보고 확신도(및 심각도)를 붙이도록 한다. 이후 후속 검증 또는 필터링 단계에서 명시적인 임계값을 적용하므로, 정교한 라우팅 결정(자동 노출, 중복 제거, 폐기)은 모델의 불투명한 판단 내부가 아니라 여러분이 통제하고 조정할 수 있는 코드에서 이루어진다. 모든 발견 사항이 확신도 점수와 함께 출력되므로, 시간이 지남에 따라 보정 상태를 측정하고 임계값을 경험적으로 조정할 수도 있다.

대안들은 모두 필터링을 프롬프트 안에 그대로 남겨둔다. 기준선을 "적당히 확신"으로 바꾸거나 "재현율을 우선하라"를 추가하는 것은 하나의 모호하고 실행 불가능한 지시를 또 다른 것으로 바꾸는 것일 뿐이다. 모델은 여전히 "적당히"나 "우선하라"와 같은 단어를 일관된 결정 규칙으로 매핑할 수 없다. 보수적인 패스를 재실행하고 합집합을 취하는 방식은 동일한 억제 기준선을 무작위로 통과하는 발견 사항만 회수하면서 비용은 세 배로 든다. 발견 단계를 커버리지에 집중시키고 확신도 필터링을 후속 단계로 옮기는 방법에 대한 Anthropic의 가이드는 Prompting Claude Sonnet 5를 참고하라.

## 질문 4

**SCENARIO** : You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : Your documentation workflow extracts function metadata into a schema. JSDoc-style files extract correctly, but files using inline comments or docstrings return null for fields the comments clearly contain, even after detailed prose instructions. What should you add?

**A(정답).** Few-shot examples pairing each comment style with the correct extracted output for the same fields.

**설명**

이는 올바른 답이다. 모델이 한 문서 형식은 잘 처리하지만 다른 형식에서는 null을 반환한다면, 서로 다른 구조의 소스에서 동일한 필드를 추출하는 대조적인 예시를 보여주면 형식 전반에 걸친 패턴을 인식하도록 가르칠 수 있다. 다양한 문서 구조에서의 추출은 few-shot 예시가 프롬프트 지시보다 우수한 성능을 내는 것으로 문서화된 사례다.

**B.** An emphatic instruction that the model must never return null when the information exists in the file.

**설명**

이는 잘못된 답이다. 이 지시는 목표만 언급할 뿐 능력을 전달하지 못한다. 모델은 이미 존재하는 값을 추출하려는 의도를 갖고 있지만, 익숙하지 않은 주석 스타일에서는 그 값을 인식하지 못할 뿐이다. 실행 가능한 내용이 없는 규칙을 강조하는 것으로는 추출 동작이 바뀌지 않는다.

**C.** A preprocessing step that rewrites inline comments and docstrings into JSDoc blocks before extraction.

**설명**

이는 잘못된 답이다. 이 방법은 모든 주석 스타일을 스스로 올바르게 파싱해야 하는 취약한 변환 계층을 추가하는 것으로, 결국 원래 문제를 재진술하는 것과 같다. 예시가 매핑을 보여주기만 하면 모델은 별도의 장치 없이도 형식 전반에 걸쳐 직접 일반화할 수 있다.

**D.** Schema changes marking every metadata field as required so the model cannot return null for them.

**설명**

이는 잘못된 답이다. null을 금지하는 것은 모델이 익숙하지 않은 형식에서 값을 찾도록 가르치는 것이 아니라, 정직한 대안을 제거하는 것이다. 모델이 값을 찾지 못했을 때 필수 필드는 그럴듯해 보이는 값을 조작하도록 압박하게 되며, 이는 null보다 더 나쁜 결과다.

### 전반적인 설명

한 문서 구조에서는 정확히 추출되지만 다른 구조에서는 빈 값이나 null이 나오는 이 실패 패턴은 few-shot 프롬프팅의 전형적인 사례다. 프롬프트 지시는 무엇을 해야 하는지 설명하지만, 동일한 정보가 JSDoc 블록, 인라인 주석, docstring에서 각각 어떻게 보이는지를 쉽게 전달하지는 못한다. 각 형식과 올바르게 채워진 출력을 함께 보여주는 소규모 예시 집합은 매핑 자체를 시연한다. 그러면 모델은 이미 처리할 수 있는 한 가지 형식을 단순히 매칭하는 것이 아니라, 새로운 파일에도 그 패턴을 일반화하게 된다. 이것이 바로 다양한 문서 구조에서의 추출이 예시가 추가적인 지시 개선보다 확실히 우수한 상황 중 하나인 이유다.

오답들은 각각 근본 원인을 놓치고 있다. 스키마에서 필드를 필수로 지정하는 것은 증상(null)을 공격할 뿐 원인(인식되지 않는 형식)을 공격하지 못하며, 값이 없다는 것을 정당하게 표현할 수 있는 모델의 수단을 없애버린다. 모델이 찾을 수 없는 값에 대한 스키마 압박은 정확히 조작된 데이터가 만들어지는 조건이다. 모든 주석을 JSDoc으로 정규화하는 전처리 단계는 파싱 문제를 단순히 모든 변형을 처리해야 하는 결정론적 코드로 옮기는 것일 뿐이며, 모델이 변형을 직접 학습할 수 있는 상황에서는 취약하고 불필요하다. null을 절대 반환하지 말라는 강조된 지시는 실행 가능한 내용이 없다. 모델이 값을 의도적으로 숨기는 것이 아니라 인식하지 못하는 것이므로, 강조된 문구로는 아무것도 바뀌지 않는다.

유용한 사고 모델은 다음과 같다. 지시는 목표를 설정하고, 예시는 판단력을 전달한다. 명확한 지시에도 입력 변형에 따라 출력이 일관되지 않다면, 해당 변형을 다루는 2~4개의 표적화된 예시를 추가하되, 파이프라인이 처리해야 하는 각 형식마다 최소 하나씩 포함하라. 이 기법에 대한 공식 가이드는 Use examples (multishot prompting) to guide Claude's behavior를 참고하라.

### 전반적인 설명

JSON 스키마와 함께 tool_use를 사용하는 것은 구조화된 출력을 얻는 가장 신뢰할 수 있는 방법이다. 모델은 도구의 input_schema를 따르는 입력을 생성하도록 학습되어 있으므로, 중괄호가 제대로 닫히고, 필수 필드가 존재하며, 타입이 일치한다. 이는 (마크다운 펜스, 부가 설명, 손상된 구문 같은) 실패 클래스 전체를 원천적으로 제거한다. 하지만 그 보장은 형태에서 멈춘다. tool_use 스키마는 구문, 타입, 필수 구조를 강제하지만, 어떤 개수가 그 아래 나열된 항목 수와 실제로 일치하는지, 수정 사항이 올바른 파일에 귀속되는지와 같은 의미적 정확성이나 소스에 근거한 일관성은 보장하지 않는다.

이러한 설계에서 나오는 결론은, 구조화된 추출 파이프라인에는 두 번째 층이 필요하다는 것이다. 파생된 값을 재계산하고, 필드 배치를 소스와 대조하며, 비즈니스 규칙을 적용하는 코드 수준의 검증(커스텀 검증기)이 그것이다. 유용한 패턴은 모델이 자체 점검용 필드를 함께 출력하도록 하는 것이다. 예를 들어 stated_total과 calculated_total을 모두 추출하게 하면, 둘이 불일치할 때 conflict_detected 플래그를 발생시켜 후속 시스템이 대응할 수 있게 하고, 이는 보통 오류 피드백을 동반한 재시도 루프로 이어진다.

스키마를 더 엄격하게 만드는 것은 이 실패를 해결하지 못한다. tool_use가 제공하는 강제력은 구조와 타입을 다루는 것이지, 값들이 서로 맞는지나 소스에 근거하고 있는지를 다루는 것이 아니기 때문이다. 프롬프트 기반 JSON으로 되돌아가는 것은 이미 해결된 문제(구문)를 다시 미해결 상태로 되돌리면서 의미적 문제는 그대로 남겨두는 것이다. 온도를 낮추는 것은 출력을 더 반복 가능하게 만들 뿐이며, 반복 가능한 오답도 여전히 오답이다. 스키마로 제약된 도구 입력이 어떻게 동작하고 그 보장이 어디서 끝나는지에 대해서는 Tool use with Claude를 참고하라.

거부된 두 가지 접근 방식은 동일한 근본적인 이유로 실패한다. 억제 임계값을 가진 자체 확신도 점수는 보정되지 않은 신호를 그저 기계적으로 처리할 뿐이다. 모델이 스스로 말하는 확신도는 발견 사항이 실제인지 여부와 느슨하게만 관련되므로, 임계값을 조정하는 것은 하나의 소음 패턴을 다른 소음 패턴으로 바꾸는 것에 불과하다. "완전한 확신"을 요구하는 것은 아무런 결정 경계도 추가하지 않은 채 표현만 강화하는 것으로, 이는 Anthropic의 프롬프팅 모범 사례가 경고하는 모호한 지시의 실패 유형과 정확히 같다. 명확하고 직접적이며 구체적으로 작성해야 하는데, 구체성이야말로 실제로 전달되는 것이기 때문이다.

**설명**

**설명**

**D.** Remove ticket_id from the required list so the model can omit the field entirely whenever a refactor has no tracking ticket.

**설명**

### 전반적인 설명

여기서 근본 원인은 모델에게 정직하게 행동할 방법을 남겨두지 않는 스키마다. ticket_id가 필수 문자열일 때, 스키마를 준수하는 모든 출력은 그것에 대한 문자열 값을 포함해야 한다. 티켓이 없는 리팩터의 경우 스키마를 만족시키는 유일한 방법은 값을 조작해내는 것이다. 지나치게 엄격한 스키마 아래에서의 조작은 모델의 버그가 아니라 스키마가 작성된 그대로 동작하는 것이므로, 수정은 지시가 아니라 구조적인 방식이어야 한다.

핵심적인 설계 구분은 optional 필드와 nullable 필드의 차이다. optional 필드(required에서 제외됨)는 출력 객체에서 완전히 생략될 수 있다. nullable 필드(["string", "null"]과 같은 유니온 타입)는 반드시 나타나야 하지만 null 값을 가질 수 있다. Anthropic이 지원하는 JSON Schema 하위 집합에는 null 타입과 이러한 타입 유니온이 포함되어 있는데, 이는 정확히 부재를 명시적으로 표현할 수 있도록 하기 위함이다. 이 파이프라인의 파서는 키가 없을 때 오류를 내므로, 올바른 형태는 필수이면서 nullable한 것이다. 즉 모든 요약에 키가 존재하고, null은 명확하게 티켓이 없음을 의미한다. 참고로, 구조화된 출력은 대부분의 경우 응답을 스키마에 맞게 제약하지만, 문서화된 예외(예를 들어 거부 응답이나 최대 토큰 잘림)가 존재하므로 후속 검증은 여전히 가치가 있다.

대안들은 각자의 기준에서 실패한다. 필드를 required에서 제외하는 것은 조작을 없애는 대신 키 누락 문제를 초래하여, 명시된 역직렬화 계약을 깨뜨린다. 프롬프트 지시는 모델이 어차피 만족시켜야 하는 엄격한 구조적 요구 사항과 지침을 서로 충돌시키는 것이다. NONE과 같은 센티널 문자열은 정상 범위 내의 값에 범위 밖의 의미를 몰래 끼워넣는 것으로, null이 정확히 이 목적을 위해 이미 존재하는데도 모든 소비자가 이를 특별 처리하도록 강제한다.

지원되는 스키마 기능과 가이드에 대해서는 Structured Outputs와 Increase output consistency를 참고하라.

이러한 구분 뒤에 있는 설계 의도는 명확하다. 제약된 생성은 문법을 저렴하고 결정론적으로 강제할 수 있지만, 콘텐츠의 정확성은 원본 자료에 의존하며 스키마가 표현할 수 없는 검증 로직을 필요로 한다. 아키텍처적으로 올바른 방향은 스키마 강제를 도입한 후 구문 복구 코드는 삭제하고, 의미적 검증은 유지하거나 오히려 강화하는 것이다.

오답들은 그 경계의 서로 반대쪽에서 실패한다. 모든 null에 대한 자동 재시도는 부재를 수정해야 할 오류로 취급하지만, 피드백을 동반한 재시도는 형식, 구조, 산술 문제에만 효과가 있다. 정보가 소스에 단순히 없는 경우, 더 엄격한 재시도는 모델을 추측으로 몰아넣는다. replacement_api를 필수로 지정하는 것도 스키마 수준에서 동일한 피해를 입힌다. 존재하지 않을 수 있는 정보에 대한 필수 필드는 모델에게 정직한 답을 남겨두지 않으며, 이는 정확히 조작된 그럴듯한 값이 나타나는 조건이다. 스키마 설계 규칙은 그러한 필드를 optional이나 nullable로 유지한 다음, 예시를 사용해 언제 null이 적절하고 언제 그렇지 않은지를 정교화하는 것이다.

더 넓은 사고 모델은 다음과 같다. 스키마는 출력의 형태를 통제하고, 예시는 그 형태 안에서 적용되는 판단을 전달하며, 재시도는 소스 문서가 실제로 해결할 수 있는 오류만을 고친다. 관련 기법에 대해서는 Use examples (multishot prompting)와 Tool use overview를 참고하라.

**설명**

이는 올바른 답이다. 도구를 강제하는 것은 모델의 응답 형태만 결정할 뿐 아무것도 실행하지 않는다. 애플리케이션은 tool_use 블록을 파싱하고, extract_metadata를 직접 실행하고, tool_use id를 참조하는 tool_result를 다시 보낸 다음, 보강 단계로 루프를 이어가야 한다.

### 전반적인 설명

여기서 유지해야 할 사고 모델은, tool_choice가 모델이 하는 말을 제약하는 것일 뿐, 여러분의 시스템이 하는 일을 오케스트레이션하는 메커니즘이 아니라는 것이다. {"type": "tool", "name": "extract_metadata"}로 강제하면 응답에 해당 도구의 tool_use 블록이 포함되도록 보장되며, 응답은 stop_reason: "tool_use"와 함께 도착한다. 그 시점에서 API의 임무는 끝난 것이다. 여러분의 애플리케이션은 블록의 id, name, input을 읽고, 추출 로직을 직접 실행하고, 다음 사용자 메시지에 tool_use_id를 참조하는 tool_result 블록을 추가해야 한다. 그런 다음에야 보강 단계로 루프를 이어갈 수 있으며, 보통 이때는 모델이 여러 보강 도구 중에서 선택할 수 있도록 tool_choice를 auto로 완화한다. 이러한 역할 분담은 의도된 것이다. 모델은 순수한 텍스트와 구조 생성기로 남고, 여러분의 코드는 부작용, 오류 처리, 순서 제어에 대한 완전한 통제권을 유지한다.

오답들은 각각 이 계약을 깨뜨린다. API가 서버 측에서 도구를 직접 실행할 것이라고 기대하는 것은 클라이언트 도구를 모델 자신의 출력과 혼동하는 것이다. 자동으로 실행되는 것은 아무것도 없다. 보강 도구를 지정해 tool_choice를 즉시 재전송하는 것은 대기 중인 도구 호출을 완전히 건너뛰는 것이며, tool-result 형식은 엄격하다. 결과는 어시스턴트의 도구 사용 메시지 뒤에 따라와야 하므로, 이를 답하지 않은 채 넘어가면 대화 구조가 깨진다. 메타데이터를 텍스트 블록에서 찾으려는 시도는, tool_choice가 any나 tool일 때 어시스턴트 턴이 도구 사용을 강제하도록 미리 채워지므로 호출 앞에 설명하는 산문이 존재하지 않기 때문에 실패한다. 구조화된 데이터는 tool_use 블록의 input이다.

클라이언트 측 에이전틱 루프에 대해서는 How tool use works를, tool_use 블록을 파싱하고 tool_result 블록을 올바르게 반환하는 방법에 대해서는 Handle tool calls를 참고하라.

프롬프트에 예시를 넘치게 채우면 컨텍스트가 비대해지고 실제 실패를 다루는 예시들의 신호가 희석된다. 모델은 잘 선택된 소수의 시범 사례로부터 일반화하므로, 철저한 커버리지는 불필요하며 오히려 역효과를 낸다.

Few-shot 프롬프팅은 모델이 틀리는 사례를 목표로 한 작고 표적화된 세트에서 가장 잘 작동한다. 실패하는 테이블 형식에 소수의 예시를 집중시키면, 이미 잘 작동하는 형식들로 신호가 희석되는 것을 막고 교정 신호를 강하게 유지할 수 있다.

Markdown 테이블과 그에 대해 올바르게 채워진 추출 결과를 함께 보여주면, 모델은 패턴을 통해 테이블 행도 문장과 마찬가지로 데이터 소스라는 것을 배운다. 이것이 가장 강력한 예시가 저장소의 실제 문서에서 가져온 현실적인 것이고, 정확한 목표 스키마의 출력과 짝지어져 있는 이유다. 추상적인 플레이스홀더는 모델이 해석하지 못하고 있는 바로 그 구조적 디테일(열 헤더, 셀 정렬, 필드 배치)을 제거해버린다.

You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

**QUESTION** : A custom slash command instructs Claude to report findings as location, issue, severity, and suggested fix, and includes three examples written with placeholder pseudocode (foo, bar). On the team's real TypeScript files, output format still drifts. What should change?

**A(정답).** Replace the placeholder examples with realistic snippets drawn from the team's actual codebase.

**설명**

이는 올바른 답이다. 효과적인 few-shot 예시는 관련성이 있어야 한다. 즉 모델이 실제로 보게 될 입력을 근접하게 반영해야 한다. 추상적인 foo/bar 의사코드는 형식을 약하게만 시연할 뿐이며, 실제 프로젝트 코드로 만든 예시는 그 패턴을 실제 리뷰 입력으로 훨씬 더 신뢰성 있게 전이시킨다.

**C.** Increase the number of examples to ten or more so every possible finding type is demonstrated.

**설명**

수량은 관련성 부족을 보완하지 못한다. Anthropic은 대략 3~5개의 잘 만들어진 예시를 권장하며, 10개 이상의 플레이스홀더 예시는 프롬프트를 비대하게 만들면서도 명령이 처리하는 실제 입력을 여전히 반영하지 못한다.

**설명**

CLAUDE.md는 프로젝트 가이드를 제공하지만 여전히 주의를 끌기 위해 경쟁하는 텍스트 지시일 뿐, 패턴의 시연은 아니다. 동일한 추상적인 형식 규칙을 옮기는 것은 그것이 로드되는 위치를 바꿀 뿐, 모델이 그것을 실제 코드에 얼마나 잘 매칭시킬 수 있는지는 바꾸지 못한다.

### 전반적인 설명

Few-shot 예시는 모델에게 모방할 구체적인 패턴을 제공함으로써 작동하며, 이 메커니즘은 예시가 모델이 실제로 받게 될 입력과 유사할 때만 발동한다. Anthropic의 가이드는 관련성이 있고(실제 사용 사례를 근접하게 반영), 다양하며(엣지 케이스를 다룸), 구조화된(<example> 태그로 감싸서 지시와 구별 가능하게 함) 예시를 요구한다. foo와 bar로 이루어진 플레이스홀더 의사코드는 관련성 기준을 전혀 만족시키지 못한다. 모델은 장난감 같은 패턴을 본 다음, import, 제네릭, 프로젝트 관행이 있는 실제 TypeScript를 맞닥뜨리게 되며, 코드를 위치·이슈·심각도·제안된 수정 레코드로 매핑하는 시연된 방식이 깔끔하게 이어지지 않는다.

유지해야 할 사고 모델은, 예시가 규칙이 아니라 유추를 통해 가르친다는 것이다. 예시 입력이 실제 운영 입력에 가까울수록 유추의 도약 거리가 짧아지고 출력 형식이 더 일관되게 유지된다. 이것이 팀 자체 코드베이스의 현실적인 스니펫이 추상적인 것보다 우수한 이유다. 이런 종류의 코드를 이런 종류의 발견 사항으로 바꾸는 정확한 판단을 보여주기 때문이다.

대안들은 각각 이 메커니즘을 놓치고 있다. 10개 이상의 예시를 쌓아 올리는 것은 컨텍스트를 부풀리면서도 모든 예시가 여전히 대표성이 없는 상태로 남는다. 권장되는 수는 잘 선택된 3~5개다. 형식 지시를 대문자로 강조하는 것은 시연보다 이미 열등한 것으로 판명된 프롬프트 문구를 강화하는 것일 뿐이다. 원하는 출력의 예시를 제공하는 것이 추상적인 형식 지침보다 더 효과적이라는 것이 문서화되어 있기 때문이다. 규칙을 CLAUDE.md로 옮기는 것은 전달 경로를 바꿀 뿐, 그 내용은 여전히 지시 텍스트이며, CLAUDE.md 가이드는 패턴을 시연하는 것이 아니라 컨텍스트 내 다른 모든 것과 경쟁한다. Prompt engineering과 Increase output consistency를 참고하라.
