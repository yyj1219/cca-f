# PRESTUDY: Claude Code 설정과 워크플로우 (conf-75-89 사전학습 노트)

이 문서는 Claude Code의 설정 파일 체계, 컨텍스트 관리, 규칙(rules)·스킬(skills)·훅(hooks)·커맨드·서브에이전트, Glob 패턴, CI 실행 방식, 그리고 효과적인 프롬프팅 방법을 아무 사전 지식이 없는 상태에서 이해할 수 있도록 정리한 것이다.

---

## 0. 먼저 알아야 할 큰 그림

### 0.1 Claude Code란 무엇인가

Claude Code는 터미널(명령줄)에서 실행하는 AI 코딩 도구다. `claude`라는 CLI 명령으로 실행하며, 실행하면 대화형 세션이 열리고 사용자가 "이 버그 고쳐줘" 같은 요청을 하면 Claude가 파일을 읽고, 편집하고, 셸 명령을 실행하면서 작업한다.

Claude가 실제 작업을 하기 위해 쓰는 수단을 **도구(Tool)** 라고 부른다. 대표적인 도구:

| 도구 | 하는 일 |
|---|---|
| `Read` | 파일 내용 읽기 |
| `Write` | 파일 새로 쓰기 |
| `Edit` | 기존 파일 일부 수정 |
| `Grep` | 파일 내용 검색 |
| `Glob` | 파일 경로 패턴 검색 |
| `Bash` | 셸 명령 실행 (git, npm, 테스트 실행 등) |

### 0.2 컨텍스트 윈도우 — 모든 설계의 이유

LLM(대형 언어 모델)은 한 번에 볼 수 있는 텍스트 양에 한계가 있다. 이 "한 번에 볼 수 있는 텍스트 창"을 **컨텍스트 윈도우(context window)** 라고 한다.

여기에는 두 가지 비용이 따른다.

1. **토큰 비용**: 컨텍스트에 들어간 글자 수만큼 돈과 시간이 든다. 세션마다 무조건 로드되는 내용이 크면 매 세션이 비싸진다. 이를 **컨텍스트 발자국(context footprint)** 또는 세션당 비용(per-session cost)이라고 부른다.
2. **주의력 희석(attention attenuation)**: 지시사항이 너무 많고 길어지면, 모델이 그 안의 개별 지시를 덜 확실하게 따른다. 500줄짜리 지침 파일을 주면 오히려 준수율이 떨어지는 현상이 이것이다.

그래서 Claude Code의 설정 체계 전체가 **"무엇을 항상 로드할 것인가 vs. 필요할 때만 로드할 것인가"** 라는 질문을 중심으로 설계되어 있다. 아래 나오는 CLAUDE.md / rules / skills / commands / agents / hooks의 차이는 사실상 전부 이 질문에 대한 답이다.

### 0.3 확정성(결정론) vs. 비확정성 — 두 번째 축

두 번째 중요한 축은 **"이 규칙이 반드시 지켜져야 하는가, 아니면 지켜지면 좋은가"** 이다.

- **비결정론적(non-deterministic) 층 = 프롬프트/컨텍스트**: CLAUDE.md, rules, skills 본문 등. 이것들은 모델에게 "이렇게 해라"고 **말해주는** 것이다. 모델은 확률적으로 동작하므로 대부분 따르지만 100%는 아니다.
- **결정론적(deterministic) 층 = 기술적 제어(technical control)**: hooks, permissions. 이것들은 프로그램 코드가 도구 실행 자체를 **검사하고 막는다**. 모델의 판단과 무관하게 항상 작동한다.

"Claude가 기억하거나 따르기로 선택하는 것에 의존하면 안 된다"는 요구가 있으면 답은 언제나 프롬프트가 아니라 훅/권한 쪽이다.

## 1. 설정 파일이 놓이는 위치 (스코프 계층)

Claude Code 설정은 세 개의 **스코프(scope, 범위)** 에 놓일 수 있다.

| 스코프 | 위치 | 성격 |
|---|---|---|
| 개인(Personal / User level) | `~/.claude/` | 그 사람의 노트북 전체에 적용. git에 안 올라감. |
| 프로젝트(Project level) | `<프로젝트루트>/.claude/` | 저장소에 커밋되어 팀 전체가 공유. |
| 플러그인(Plugin) | 설치된 플러그인이 제공 | 외부에서 가져온 기능 묶음. |

`~`는 홈 디렉터리(윈도우면 `C:\Users\이름`, 맥/리눅스면 `/home/이름`)를 뜻하는 기호다. `./`는 현재 프로젝트 디렉터리를 뜻한다.

전형적인 프로젝트 구조:

```
my-project/
├── CLAUDE.md                      # 항상 로드되는 프로젝트 지침
└── .claude/
    ├── settings.json              # 훅, 권한, 환경변수 등 설정
    ├── rules/                     # 주제별 규칙 파일들
    │   ├── code-style.md
    │   ├── testing.md
    │   └── terraform.md
    ├── skills/                    # 온디맨드로 로드되는 지식/절차
    │   └── deploy-checklist/
    │       └── SKILL.md
    ├── commands/                  # /슬래시커맨드 정의
    │   └── review.md
    └── agents/                    # 서브에이전트 정의
        └── researcher.md
```

## 2. CLAUDE.md — 항상 로드되는 프로젝트 지침

### 2.1 무엇인가

`CLAUDE.md`는 프로젝트 루트에 놓는 마크다운 파일이다. Claude Code가 세션을 시작할 때 **무조건, 자동으로** 그 내용을 컨텍스트에 넣는다. 프로젝트에 대한 상시 배경지식과 지침을 담는 자리다.

예:

```markdown
# 프로젝트 개요
결제 백엔드 서비스. Python 3.12 + FastAPI.

# 기본 규칙
- 패키지 관리는 uv 사용, pip 사용 금지
- 커밋 전 `make test` 통과 필수

# 상세 규칙
주제별 상세 규칙은 `.claude/rules/` 아래를 참조.
```

### 2.2 왜 존재하는가

매번 "우리 프로젝트는 uv 씁니다"라고 타이핑하지 않아도 되게 하려고. 프로젝트의 상시 상수(constant)를 담는 자리다.

### 2.3 핵심 특성과 한계

1. **항상 로드된다.** 이것이 장점이자 단점이다. 아무도 안 쓰는 날에도 그 내용의 토큰 비용을 낸다. 드물게 필요한 대용량 참조 문서를 여기 붙여넣으면 매 세션이 비싸진다.
2. **커지면 준수율이 떨어진다.** 500줄이 넘어가면 개별 지시가 묻힌다. 짧고 핵심적일수록 잘 지켜진다.
3. **강제력이 없다.** CLAUDE.md는 "컨텍스트"일 뿐, 모델이 그 순간의 추론으로 "이번엔 건너뛰어도 되겠다"고 판단하면 무시될 수 있다. 파일에 커밋되어 있다고 해서 기술적 제어와 같은 보장력이 생기지 않는다. 여러 하위 디렉터리에 반복해서 써 넣어도 마찬가지다 — 반복은 강제력이 아니다.
4. **"Claude가 절대 무시할 수 없는 특별 등급"은 CLAUDE.md 안에 존재하지 않는다.** managed policy 같은 이름의 "오버라이드 불가 CLAUDE.md 계층"은 실제 기능이 아니다.

### 2.4 결론적으로 CLAUDE.md에 담아야 할 것

- 매 세션 필요한 짧은 핵심 정보 (기술 스택, 기본 컨벤션, 어디에 무엇이 있는지 가리키는 포인터)
- 담지 말아야 할 것: 드물게 쓰는 대용량 참조 문서, 반드시 강제되어야 하는 보안 정책

## 3. Rules (`.claude/rules/`) — 주제별로 쪼갠 지침

### 3.1 무엇인가

`.claude/rules/` 디렉터리 아래에 놓는 마크다운 파일들이다. 하나의 거대한 CLAUDE.md 대신 주제별로 파일을 나눠 관리한다.

```
.claude/rules/
├── code-style.md
├── testing.md
├── security.md
└── deployment.md
```

### 3.2 왜 존재하는가

500줄짜리 단일 파일은 두 가지 문제가 있다.
- 사람이 유지보수하기 어렵다 (어디를 고쳐야 하는지 찾기 힘듦, 여러 사람이 동시에 수정하면 충돌)
- 모델의 지시 준수율이 떨어진다

주제별 파일로 나누면 사람에게는 유지보수성이, 모델에게는 구조화된 컨텍스트가 생긴다.

중요한 점: **rules는 CLAUDE.md를 대체하지 않는다.** 둘은 공존한다. 권장 패턴은 CLAUDE.md를 짧은 "프로젝트 포인터"(개요 + 어디를 보라는 안내)로 남기고, 상세 내용을 rules 파일들로 분산하는 것이다. 그리고 단순히 500줄을 통째로 `rules/all-conventions.md` 한 파일로 옮기는 것은 아무 문제도 해결하지 못한다 — 파일 위치만 바뀌었을 뿐 여전히 거대한 단일 덩어리다.

### 3.3 프론트매터와 `paths` — 조건부 로딩

rules 파일 맨 위에는 **YAML 프론트매터(frontmatter)** 를 붙일 수 있다. 프론트매터란 파일 최상단에 `---` 로 감싼 메타데이터 블록이다.

```markdown
---
paths:
  - "terraform/**/*"
---

# Terraform 컨벤션
- 모든 리소스에 `Environment` 태그를 붙일 것
- `terraform fmt` 를 통과할 것
```

`paths` 키는 **이 규칙이 어떤 파일에 적용될지**를 Glob 패턴으로 지정한다. 위 예시는 "Claude가 `terraform/` 아래 파일을 다룰 때만 이 규칙을 적용" 이라는 뜻이다.

문법상 주의점:

- 올바른 키 이름은 **`paths`** 다. `include` 같은 다른 이름은 지원되지 않는다.
- `paths`는 **YAML 배열(list)** 로 써야 한다. 즉 `- "패턴"` 형태의 항목들로. 단일 문자열(`paths: "terraform/**/*"`)로 쓰는 형태는 올바른 형식이 아니다.

```yaml
# 올바름
paths:
  - "terraform/**/*"

# 잘못됨 (단일 문자열)
paths: "terraform/**/*"

# 잘못됨 (키 이름 오류)
include:
  - "terraform/**/*"
```

### 3.4 `paths`가 없으면 = 무조건 로드

`paths` 필드를 아예 쓰지 않은 rules 파일은 **무조건적(unconditional)** 규칙이 되어 항상 로드된다. 조건 없이 모든 상황에 적용된다.

### 3.5 `paths: "**/*"` 는 안티패턴

"모든 파일에 적용하고 싶으니 `**/*`로 스코프하자"는 발상은 잘못된 방향이다. 모든 파일 읽기마다 규칙을 로드/평가하는 불필요한 부담을 만든다. 항상 적용하고 싶으면 `paths`를 쓰지 않으면 된다.

### 3.6 로드 순서와 충돌 — 매우 중요

- 로드 순서: **사용자 레벨(`~/.claude/rules/`)이 프로젝트 레벨(`./.claude/rules/`)보다 먼저 로드된다.**
- 그러나 **로드 순서가 충돌의 결정론적 해결을 보장하지 않는다.**

즉, 같은 이름의 `formatting.md`가 개인 레벨과 프로젝트 레벨에 각각 있고 둘 다 `paths` 없이 무조건 로드되며 서로 모순되는 내용을 담고 있다면:

- 하나가 다른 하나를 덮어쓰거나 무시하지 **않는다**. 둘 다 컨텍스트에 들어간다.
- "프로젝트가 더 구체적이니 항상 이긴다" 같은 확정 규칙도 **없다**.
- Claude는 둘 중 하나를 임의로(arbitrarily) 선택할 수 있다.

**공식적인 권장 대응은 우선순위에 기대는 것이 아니라, 충돌하는 지침 자체를 찾아 제거하는 것이다.**

> 주의: 이 "충돌 시 비결정론적" 규칙은 rules 파일(메모리/컨텍스트)에 대한 이야기다. 뒤에 나오는 **skills의 이름 충돌은 별개로 명확한 우선순위 규칙이 있다.** 둘을 혼동하지 말 것.

## 4. Glob 패턴 — 파일 경로 매칭 문법

`paths`에 쓰는 패턴은 Glob이라는 표준 파일 매칭 문법이다. 정규표현식이 아니다.

### 4.1 기본 기호

| 기호 | 의미 |
|---|---|
| `*` | **한 단계 경로 안에서** 임의의 문자열. `/`를 넘지 않는다. |
| `**` | 임의의 깊이의 디렉터리(0단계 포함). 재귀 매칭. |
| `{a,b}` | 중괄호 확장(brace expansion). a 또는 b 중 하나. |
| `?` | 임의의 한 글자 |

### 4.2 `*` 와 `**` 의 결정적 차이

이것이 가장 자주 헷갈리는 부분이다.

```
src/*.ts
```
→ `src/` **바로 아래**의 `.ts` 파일만. `src/index.ts` ✅ / `src/utils/date.ts` ❌

```
src/**/*.ts
```
→ `src/` 아래 **모든 깊이**의 `.ts` 파일. `src/index.ts` ✅ / `src/utils/date.ts` ✅ / `src/a/b/c/x.ts` ✅

"at any subfolder depth(어떤 하위 폴더 깊이에서든)", "anywhere under(~ 아래 어디든)" 같은 표현이 요구사항에 나오면 반드시 `**`가 필요하다.

### 4.3 접두 경로가 붙으면 범위가 잘린다

```
src/**/*.test.tsx
```
→ `src/` 로 시작하는 경로만. 프로젝트 루트의 `tests/Button.test.tsx` 는 매칭되지 않는다.

```
**/*.test.tsx
```
→ 프로젝트 어디에 있든(루트 포함, 임의 깊이) 모든 `.test.tsx`. `src/` 안팎을 가리지 않는다.

파일들이 여기저기 흩어져 있고(예: `src/components/__tests__/`, `src/pages/tests/`, 소스 옆에 나란히, 루트 `tests/`) 공통점이 확장자뿐이라면 답은 `**/*.확장자` 형태다.

### 4.4 폴더 이름으로 매칭하면 놓치는 것들

```
**/__tests__/*.tsx
```
→ 이름이 정확히 `__tests__` 인 폴더 **바로 안**의 `.tsx` 파일만. 확장자가 같아도 다른 폴더(`src/pages/tests/`)나 소스 옆에 놓인 파일은 못 잡는다.

### 4.5 중괄호 확장으로 항목 수 줄이기

여러 확장자를 하나의 패턴으로 묶는다.

```yaml
# 3줄
paths:
  - "src/**/*.ts"
  - "src/**/*.tsx"
  - "lib/**/*.ts"

# 같은 결과, 2줄
paths:
  - "src/**/*.{ts,tsx}"
  - "lib/**/*.ts"
```

"가능한 한 적은 항목으로(as few entries as possible)"라는 요구가 있으면 중괄호 확장을 쓰는 쪽이다. 반대로 "정확히 이 디렉터리들만"이라는 제약이 있는데 `**/*.ts` 처럼 프로젝트 전체를 잡으면 범위 초과라 요구를 어긴다.

### 4.6 정리 표

| 패턴 | 잡는 것 |
|---|---|
| `**/*.test.tsx` | 프로젝트 전체, 모든 깊이의 `.test.tsx` |
| `src/**/*.test.tsx` | `src/` 아래 모든 깊이만 |
| `src/components/*.test.tsx` | `src/components/` 바로 아래만 |
| `**/__tests__/*.tsx` | 이름이 `__tests__`인 폴더 바로 안만 |
| `terraform/**/*` | `terraform/` 아래 모든 깊이의 모든 파일 |
| `terraform/*` | `terraform/` 바로 아래만 |
| `src/**/*.{ts,tsx}` | `src/` 아래 모든 깊이의 `.ts`와 `.tsx` |

---

## 5. Skills (`.claude/skills/`) — 필요할 때만 로드되는 지식

### 5.1 무엇인가

**스킬(Skill)** 은 특정 작업을 어떻게 하는지 담은 지침 묶음이다. 디렉터리 하나에 `SKILL.md` 파일을 두는 형태다.

```
.claude/skills/
└── deploy-checklist/
    └── SKILL.md
```

`SKILL.md` 예시:

```markdown
---
name: deploy-checklist
description: 릴리스 배포 시 따라야 할 8단계 체크리스트
---

# 배포 체크리스트
1. main 브랜치가 최신인지 확인
2. 전체 테스트 통과 확인
3. CHANGELOG 갱신
...
```

### 5.2 왜 존재하는가 — 온디맨드 로딩(progressive disclosure)

스킬의 핵심 가치는 **로딩 방식**이다.

- 평소에는 스킬의 **메타데이터(이름 + description)만** 컨텍스트에 상주한다. 이건 아주 작다.
- Claude나 사용자가 실제로 그 스킬을 **호출(invoke)** 했을 때에만 **본문(body)** 이 컨텍스트로 들어온다.

이것을 **온디맨드(on-demand) 로딩** 또는 점진적 공개(progressive disclosure)라고 부른다.

CLAUDE.md와 정확히 대비된다:

| | CLAUDE.md | Skill |
|---|---|---|
| 로드 시점 | 매 세션, 무조건 | 호출될 때만 |
| 평소 비용 | 전체 내용의 토큰 | description 한 줄 정도 |
| 적합한 내용 | 짧고 항상 필요한 것 | 크고 가끔 필요한 것 |

### 5.3 언제 쓰는가

**크고, 드물게 필요하고, 절차적인 것**은 스킬로 옮기는 게 정석이다.

- 대용량 규정 준수(compliance) 참조 문서
- 8단계 배포 체크리스트
- 특정 마이그레이션 절차
- 매번 채팅에 붙여넣던 긴 지시문

효과: 평상시 세션당 토큰 비용이 크게 줄고, 필요한 날에는 호출 한 번으로 전체 내용을 얻는다.

### 5.4 중요한 부작용 — 한 번 로드되면 계속 남는다

스킬 본문은 **일단 로드되면 그 세션의 남은 시간 동안 컨텍스트에 계속 남는다.** 즉, 스킬이 절약해주는 것은 "그 스킬을 쓰지 않는 세션들"의 비용이다. 그 스킬을 쓰는 세션에서는 여전히 자리를 차지한다.

이 사실이 두 가지 결론을 낳는다.
1. 그래도 **일반적인 세션당 비용(typical per-session cost)** 은 크게 준다 — 대부분의 세션은 그 스킬을 안 쓰니까.
2. 스킬 실행 중에 생기는 **긴 출력물**까지 세션에 남는 문제는 별도의 해법(`context: fork`, 아래 5.5)이 필요하다.

### 5.5 스킬 프론트매터 속성들

`SKILL.md` 최상단 YAML 프론트매터에 넣을 수 있는 주요 속성:

#### `allowed-tools`

```yaml
allowed-tools: Write Edit
```

**나열된 도구를 사전 승인(pre-approve)** 한다는 뜻이다. 즉 그 도구들은 사용자 확인 프롬프트 없이 바로 실행된다.

**흔한 오해**: 이것은 화이트리스트가 **아니다.** 나열되지 않은 도구(예: Bash)를 사용 가능 목록(pool)에서 제거하지 않는다. Bash는 여전히 쓸 수 있고, 다만 사용자 승인을 물어본 뒤 실행된다.

또한 `Write*` 처럼 뒤에 와일드카드를 붙여야 제한이 걸린다는 규칙은 존재하지 않는다.

#### `disallowed-tools`

```yaml
disallowed-tools: Bash
```

이것이 진짜 **금지**다. 스킬이 활성화되어 있는 동안 해당 도구를 아예 사용 가능 풀에서 제거한다. "Bash를 절대 못 쓰게 하고 싶다"면 이쪽을 써야 한다.

기억법: **`allowed-tools` = 승인 생략, `disallowed-tools` = 사용 금지.**

#### `context: fork`

```yaml
context: fork
```

이 스킬을 **격리된 서브에이전트(subagent) 컨텍스트**에서 실행시킨다. 스킬이 수행하는 긴 탐색과 방대한 중간 출력은 그 격리된 컨텍스트 안에만 남고, **메인 대화에는 최종 요약 결과만 반환된다.**

언제 쓰는가: 스킬이 코드베이스 전체를 훑고 긴 분석 결과를 뱉어서, 스킬이 끝난 뒤에도 그 출력물이 메인 대화 컨텍스트를 계속 잡아먹을 때. 이것이 그 문제의 정확한 해법이다.

#### `disable-model-invocation: true`

```yaml
disable-model-invocation: true
```

**Claude가 스스로 판단해서 이 스킬을 호출하는 것을 막는다.** 사용자가 명시적으로 호출할 때만 실행된다.

주의: 이것은 "출력이 컨텍스트를 차지하는 문제"를 해결해주지 않는다. 호출 주체를 제한할 뿐이다. 또한 어떤 규칙을 자동 강제하는 수단도 전혀 아니다 — 오히려 자동 실행을 **막는** 설정이다.

#### `argument-hint`

```yaml
argument-hint: [directory]
```

사용자가 이 스킬을 호출할 때 어떤 인자를 넣어야 하는지 **UI에 힌트 문구를 보여주는** 용도다. 실제로 동작 범위를 제한하거나 컨텍스트를 분리하지 않는다. 순수하게 표시용이다.

#### 속성 요약

| 속성 | 실제 효과 | 흔한 오해 |
|---|---|---|
| `allowed-tools` | 나열 도구를 승인 없이 실행 | 다른 도구를 차단한다(❌) |
| `disallowed-tools` | 해당 도구를 사용 풀에서 제거 | — |
| `context: fork` | 격리 서브에이전트에서 실행, 요약만 반환 | 도구 샌드박싱/차단(❌) |
| `disable-model-invocation` | 모델의 자동 호출 금지, 수동만 허용 | 출력 크기를 줄인다(❌) |
| `argument-hint` | 인자 입력 힌트 표시 | 스캔 범위를 제한한다(❌) |

### 5.6 스킬 이름 충돌 시 우선순위

같은 이름의 스킬이 여러 스코프에 있으면 정해진 우선순위에 따라 **하나만** 실행된다. 병합되지도 않고, 순차 실행되지도 않고, 에러를 내지도 않는다.

우선순위(높은 쪽이 이김):

```
Enterprise (기업 중앙 관리) > Personal (~/.claude/skills/) > Project (.claude/skills/) > Plugins
```

즉 **개인 레벨 스킬이 프로젝트 레벨 스킬을 오버라이드한다.** 노트북에 `~/.claude/skills/review/SKILL.md`를 두고 있는 엔지니어가 공유 저장소에서 `/review`를 실행하면, 저장소에 커밋된 팀 스킬이 아니라 자기 개인 스킬이 실행된다. 이는 팀 협업에서 조용한 사고의 원인이 되므로 이름 충돌을 피하는 것이 좋다.

**주의: rules(3.6)의 무조건 규칙 충돌은 비결정론적이지만, skills 이름 충돌은 확정적 우선순위가 있다.** 두 규칙이 다르다는 점을 분명히 구분해 두어야 한다.

## 6. Commands (`.claude/commands/`) — 슬래시 커맨드

### 6.1 무엇인가

`.claude/commands/deploy.md` 라는 파일을 만들면, 사용자가 세션에서 `/deploy` 라고 입력했을 때 그 파일의 내용이 프롬프트로 들어간다. 자주 쓰는 프롬프트 템플릿을 단축키처럼 만드는 기능이다.

### 6.2 중요한 특성

- **사용자가 직접 입력해야 실행된다.** 모든 사용자 메시지 앞에 자동으로 실행되는 것이 아니다.
- **자동으로 압축되지 않는다.** 커맨드 파일이 "투명한 압축(transparent compression)"을 거쳐 CLAUDE.md보다 작은 컨텍스트를 쓴다는 동작은 존재하지 않는다.
- 도구 실행을 감시하거나 차단하는 능력이 없다. 강제력의 수단이 아니다.

## 7. Hooks — 결정론적 강제 장치

### 7.1 무엇인가

**훅(Hook)** 은 Claude Code의 생애주기 중 정해진 이벤트 시점에 자동으로 실행되는 **프로그램(셸 명령/스크립트)** 이다. `.claude/settings.json` 에 정의한다.

LLM이 실행하는 게 아니라 **Claude Code 하네스(프로그램 자체)가 실행한다.** 그래서 모델의 기억, 판단, 추론과 완전히 무관하게 작동한다. 이것이 훅의 존재 이유 전부다.

### 7.2 대표 이벤트

- **`PreToolUse`**: Claude가 어떤 도구를 실행하기 **직전**. 훅이 도구의 입력 파라미터를 검사하고, 문제가 있으면 **실행 자체를 차단(block)** 하고 메시지를 반환할 수 있다.
- `PostToolUse`: 도구 실행 직후 (예: 파일 편집 후 포매터 자동 실행)
- `Stop`, `SessionStart` 등 다른 이벤트들도 있다.

### 7.3 전형적인 사용 예 — main 브랜치 직접 커밋 차단

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": ".claude/hooks/block-main-commit.sh"
          }
        ]
      }
    ]
  }
}
```

스크립트는 Bash 도구에 전달된 명령 문자열을 받아, 현재 브랜치가 `main`인데 `git commit`을 하려 하는지 검사하고, 그렇다면 차단 신호와 함께 "main에 직접 커밋하지 말고 PR을 여세요"라는 메시지를 반환한다.

### 7.4 훅 vs. 프롬프트 — 선택 기준

요구사항에 다음 표현이 나오면 훅(또는 settings.json 권한 규칙)이 답이다.

- "must be enforced automatically" (자동으로 강제되어야 한다)
- "must not depend on Claude remembering or choosing to follow" (Claude가 기억하거나 따르기로 선택하는 것에 의존하면 안 된다)
- "must hold even if Claude decides skipping would be fine" (Claude가 건너뛰어도 된다고 판단해도 유지되어야 한다)

반대로 "이런 스타일로 작성해주면 좋겠다" 수준의 가이드라인은 CLAUDE.md나 rules로 충분하다.

### 7.5 훅이 아닌 것

훅은 "절차 지침을 로드하는" 수단이 아니다. 배포 체크리스트 같은 **읽을 내용**을 훅에 넣는 것은 용도 오류다. 훅은 **검사하고 차단하는** 코드다. 읽을 내용은 스킬로 간다.

또한 "PreToolUse 훅이 모든 도구 호출 전에 배포 단계를 실행한다" 같은 구성은 의미가 없다 — 매 도구 호출마다 배포를 시도하게 된다.

## 8. Subagents (`.claude/agents/`)

**서브에이전트(subagent)** 는 독립된 컨텍스트에서 작업을 수행하는 별도의 Claude 인스턴스다. `.claude/agents/` 아래에 정의한다. 복잡하고 독립적인 탐색/조사 작업을 메인 대화와 분리해서 시키고, 결과 요약만 받아오는 데 쓴다.

스킬과의 구분:

- **스킬**: "이 절차를 이렇게 수행하라"는 **지식/절차 문서**. 순차적 체크리스트 같은 참조 자료의 온디맨드 로딩에 적합.
- **서브에이전트**: 스스로 판단하며 여러 단계를 수행하는 **작업 수행 주체**. 컨텍스트 격리가 목적.

배포 체크리스트처럼 "필요할 때 읽고 따를 절차"는 서브에이전트가 아니라 스킬이 맞는 단위다. 반대로 긴 코드베이스 분석 같은 실행 작업의 컨텍스트 격리가 필요하면 서브에이전트 또는 스킬의 `context: fork`가 맞다.

## 9. 어디에 무엇을 둘 것인가 — 종합 결정표

| 요구사항 | 정답 위치 | 이유 |
|---|---|---|
| 매 세션 필요한 짧은 프로젝트 개요 | `CLAUDE.md` | 항상 로드 |
| 주제별 상세 컨벤션, 관리 용이하게 | `.claude/rules/주제.md` 여러 개 | 모듈화 + 준수율 |
| 특정 디렉터리/확장자에서만 적용할 규칙 | rules + `paths` 프론트매터 | 조건부 로딩 |
| 크고 드물게 쓰는 참조 문서 | `.claude/skills/이름/SKILL.md` | 온디맨드 로딩, 세션당 비용 절감 |
| 반복적으로 붙여넣던 긴 절차/체크리스트 | 스킬 | 온디맨드 로딩 |
| 스킬의 긴 출력이 메인 컨텍스트를 오염 | 스킬 + `context: fork` | 서브에이전트 격리, 요약만 반환 |
| 특정 도구를 승인 없이 쓰게 하기 | 스킬 + `allowed-tools` | 사전 승인 |
| 특정 도구를 절대 못 쓰게 하기 | 스킬 + `disallowed-tools` | 풀에서 제거 |
| 반드시 100% 강제되어야 하는 정책 | `settings.json` + `PreToolUse` 훅 | 결정론적 제어 |
| 자주 쓰는 프롬프트 단축 | `.claude/commands/이름.md` | `/이름` 으로 호출 |
| 독립적 다단계 작업의 컨텍스트 격리 | `.claude/agents/` 서브에이전트 | 컨텍스트 분리 |

## 10. CLI 실행: 대화형 모드 vs. 비대화형(프린트) 모드

### 10.1 두 가지 실행 모드

`claude` 를 그냥 실행하면 **대화형(interactive) 모드**로 시작한다. 터미널에 UI가 뜨고, 사용자의 표준 입력(stdin)을 기다린다.

```bash
claude              # 대화형 — 사람이 앉아서 입력한다고 가정
```

`-p` (또는 `--print`) 플래그를 주면 **비대화형/프린트 모드**로 실행된다. 프롬프트를 한 번 처리하고 결과를 표준 출력으로 뱉은 뒤 종료한다.

```bash
claude -p "이 PR의 diff를 요약해줘"
```

### 10.2 CI/CD에서 왜 `-p`가 필수인가

GitHub Actions 같은 CI 러너에는 사람이 없다. 터미널 입력을 아무도 주지 않는다.

여기서 `-p` 없이 `claude`를 실행하면:
- 대화형 세션이 열린다
- stdin에서 사용자 입력이 오기를 기다린다
- 러너는 영원히 입력을 주지 않는다
- **로그에 아무 출력도 없이 잡(job) 타임아웃까지 무한 대기(hang)한다**

"CI에서 아무 출력 없이 멈춤 + API 키와 프롬프트는 정상"이라는 증상의 전형적 원인이 바로 이것이다.

### 10.3 다른 오류들과의 구분 (증상 감별)

같은 CI 환경의 다른 문제들은 **멈추지 않고 에러를 내며 종료한다.**

- **얕은 복제(shallow clone)**: `git clone --depth=1` 로 히스토리가 잘려 diff를 못 구하면, Git이 에러 메시지를 출력하고 실패한다. 무한 대기가 아니다.
- **인증 실패 / API 키 문제**: 인증이 실패하면 에러 로그가 나온다. "조용히 무한 재시도 루프"에 빠지지 않는다. 시크릿의 마스킹(로그에서 값을 가리는 것) 여부는 보안 표시 기능일 뿐, 인증 동작 자체와 무관하다.
- **Node.js 버전 미달**: 문법 오류(SyntaxError)나 호환성 에러를 내고 **즉시 종료**한다. 살아서 대기하지 않는다.

정리: **"조용히 무한 대기" = 입력 대기 = 대화형 모드 문제.** 다른 원인들은 소리를 낸다.

### 10.4 올바른 CI 예시

```yaml
- name: Summarize PR diff
  env:
    ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
  run: |
    git diff origin/main...HEAD > diff.txt
    claude -p "다음 diff를 요약해줘: $(cat diff.txt)"
```

## 11. Plan Mode — 계획 먼저, 실행 나중

### 11.1 무엇인가

**플랜 모드(Plan Mode)** 는 Claude Code가 코드를 즉시 수정하지 않고, 먼저 코드베이스를 탐색하고 접근 방법을 조사한 뒤 **실행 계획을 제시하고 사용자 승인을 받는** 모드다. 승인 전까지는 파일을 변경하지 않는다.

반대는 **직접 실행(direct execution)** — 요청받자마자 바로 편집을 시작하는 방식이다.

### 11.2 왜 존재하는가

잘못된 전제로 시작한 대규모 변경은 되돌리는 비용이 크다. 계획 단계에서 사람이 방향을 확인하면 그 위험을 앞단에서 걷어낼 수 있다.

### 11.3 언제 플랜 모드를 쓰는가

다음 신호 중 하나라도 있으면 플랜 모드가 타당하다.

1. **여러 파일에 걸친 변경** (예: 5개의 서비스 엔트리 포인트를 수정해야 함)
2. **실질적인 기술 선택/트레이드오프가 존재** (예: 경쟁하는 두 라이브러리 중 하나를 골라야 함)
3. **핵심 시스템 동작을 직접 건드림** (예: 세션 처리 로직, 토큰 저장 방식)
4. 요구사항이 모호하거나 코드베이스 탐색이 선행되어야 함

반대로 오탈자 수정, 단일 파일의 작은 변경 같은 것은 직접 실행이 낫다.

### 11.4 흔한 오해 정리

- **"요구사항이 다 적혀 있으면 직접 실행해도 된다"** — 요구사항 기술의 명확성과 작업의 구조적 복잡성은 별개다. 다중 파일 + 아키텍처 결정이 걸려 있으면 여전히 계획이 필요하다.
- **"인증/보안 코드는 정책상 항상 플랜 모드"** — 그런 무조건적 정책 규칙은 없다. 인증 작업이 플랜 모드에 적합한 이유는 주제가 "보안"이라서가 아니라 대개 다중 파일 + 핵심 동작 변경이라는 **구조적 특성** 때문이다.
- **"직접 실행은 한 번에 한 파일만 수정 가능"** — 사실이 아니다. 직접 실행도 여러 파일을 수정할 수 있다. 플랜 모드는 기술적 제약이 아니라 안전성과 체계성을 위한 선택이다.

## 12. 프롬프팅: 예시로 명세하기 (Few-shot / Example-driven)

### 12.1 문제 상황

어떤 요구사항은 말로 정확히 기술하기가 어렵다. 예를 들어 CSV → JSON 변환기를 만들 때:

- 빈 셀(empty cell)은 `null`인가, 빈 문자열 `""`인가, 아예 키를 생략하는가?
- 따옴표 안의 쉼표(`"Seoul, Korea"`)는 필드 구분자가 아니라 데이터의 일부다 — 어떻게 파싱할 것인가?
- 중복된 헤더(같은 컬럼명이 두 번)는 어떻게 다룰 것인가? 뒤엣것으로 덮어쓰기? 배열로 묶기? 접미사 붙이기?

이런 것들은 산문으로 설명하면 길고 모호해진다.

### 12.2 해법 — 입출력 쌍(pair)을 준다

구현을 요청하기 **전에**, 엣지 케이스를 포함한 샘플 입력과 정확히 기대하는 출력을 짝지어 보여준다.

입력:
```csv
name,city,note
Alice,"Seoul, Korea",hello
Bob,,
```

기대 출력:
```json
[
  {"name": "Alice", "city": "Seoul, Korea", "note": "hello"},
  {"name": "Bob", "city": null, "note": null}
]
```

이 한 쌍이 "빈 셀은 null로", "따옴표 안 쉼표는 값의 일부로" 라는 두 규칙을 모호함 없이 전달한다. 산문 설명보다 짧고 정확하다.

### 12.3 반복적 개선 루프(iterative refinement loop)

예시를 먼저 주는 방식은 그 자체로 좋은 피드백 루프를 만든다.

1. 입출력 예시 제시 → 요구사항이 명확해짐
2. 구현
3. 예시가 곧 테스트 케이스가 됨 → 검증
4. 어긋나면 예시를 추가하거나 수정 → 다시 구현

예시는 명세이자 동시에 테스트다. 그래서 이 방식을 예시 기반 프롬프팅(few-shot prompting) 또는 테스트 주도 프롬프팅(test-driven prompting)이라고 부른다.

### 12.4 좋지 않은 대안들과 그 이유

- **예시 없이 먼저 다 짜게 하고 나중에 말로 고친다**: 잘못된 전제 위에 코드가 쌓인다. 그리고 "말로 설명하기 어렵다"는 것이 애초의 문제였으므로, 사후에 말로 설명하는 것도 똑같이 어렵다.
- **인기 있는 라이브러리의 기본 동작에 맡긴다**: 라이브러리의 기본값이 우리 도메인 요구와 일치한다는 보장이 없다. 특히 빈 셀/중복 헤더 처리는 라이브러리마다 다르다. 라이브러리를 쓰는 것 자체는 좋지만, 기대 동작을 명시하지 않고 기본값에 위임하는 것이 문제다.
- **엣지 케이스는 TODO 주석으로 남기고 넘어간다**: 핵심 요구사항을 미해결로 남긴 채 완료 처리하는 것이다. 반복 개선 루프를 아예 만들지 않는다.

## 13. 실제로 존재하지 않는 기능들 (오개념 정리)

학습 과정에서 그럴듯하게 들리지만 실제로는 없는 동작들. 미리 알아두면 혼동을 막는다.

- CLAUDE.md의 `effort: low` 프론트매터가 지침을 축약 로드해준다 → **없음**
- `CLAUDE_core.md`, `CLAUDE_compliance.md` 처럼 나누면 알파벳순 첫 파일만 로드된다 → **없음**
- 커맨드 파일은 투명한 압축(transparent compression)을 거쳐 컨텍스트가 줄어든다 → **없음**
- 커맨드는 모든 사용자 메시지 전에 자동 실행된다 → **없음** (직접 입력해야 함)
- `allowed-tools`에 `Write*` 처럼 와일드카드를 붙여야 제한이 걸린다 → **없음**
- `model: inherit` 로 Claude의 자율 도구 선택을 재정의한다 → **그런 동작 아님**
- `context: fork` 가 도구를 샌드박싱하고 미등록 도구를 차단한다 → **그런 동작 아님** (컨텍스트 격리 용도)
- `allowed-tools`는 스킬 종료 후에 평가된다 → **없음**
- CLAUDE.md 안에 Claude가 오버라이드할 수 없는 "managed policy" 계층이 있다 → **없음**
- 같은 이름 스킬이 있으면 이름 충돌 에러가 나거나 병합/순차 실행된다 → **없음** (우선순위로 하나만 선택)
- rules 프론트매터의 경로 지정 키가 `include` 다 → **없음** (`paths`)
- 직접 실행 모드는 한 번에 한 파일만 수정할 수 있다 → **사실 아님**

## 14. 용어 사전 (Glossary)

| English term | 한국어 설명 |
|---|---|
| Context window | 모델이 한 번에 볼 수 있는 텍스트 창. 여기 들어간 만큼 토큰 비용과 주의력 분산이 발생한다. |
| Context footprint | 컨텍스트 사용량/발자국. 세션 시작 시점에 이미 차지하고 있는 분량. |
| Per-session cost | 세션당 비용. 매 세션 무조건 로드되는 내용이 클수록 커진다. |
| Attention attenuation | 주의력 희석. 지침이 길어질수록 개별 지시의 준수율이 떨어지는 현상. |
| Token | 모델이 텍스트를 세는 단위. 비용과 컨텍스트 소모의 척도. |
| CLAUDE.md | 프로젝트 루트의 마크다운 파일. 매 세션 무조건 로드되는 상시 지침. |
| Rules (`.claude/rules/`) | 주제별로 나눈 지침 파일들. 프론트매터의 `paths`로 조건부 로딩 가능. |
| Frontmatter | 마크다운 파일 최상단에 `---`로 감싼 YAML 메타데이터 블록. |
| YAML | 들여쓰기로 구조를 표현하는 설정 파일 형식. `- ` 로 시작하는 줄이 배열 항목. |
| `paths` | rules 프론트매터에서 규칙 적용 대상 파일을 Glob 패턴 배열로 지정하는 키. |
| Unconditional rule | `paths`가 없어 조건 없이 항상 로드되는 규칙. |
| Glob pattern | `*`, `**`, `{a,b}` 등을 쓰는 파일 경로 매칭 문법. 정규식과 다름. |
| `*` (single star) | 한 경로 단계 안의 임의 문자열. `/`를 넘지 않음. |
| `**` (globstar) | 임의 깊이의 디렉터리를 재귀적으로 매칭. |
| Brace expansion | `{ts,tsx}` 형태의 중괄호 확장. 여러 후보를 하나의 패턴으로 묶음. |
| Skill (`SKILL.md`) | 온디맨드로 로드되는 지식/절차 문서. 평소엔 메타데이터만 상주. |
| On-demand loading | 호출 시점에만 본문을 컨텍스트로 불러오는 방식. |
| Progressive disclosure | 필요한 만큼만 단계적으로 정보를 노출하는 설계 원칙. |
| Invoke | 스킬/커맨드를 실제로 호출하여 실행시키는 것. |
| `allowed-tools` | 나열된 도구를 사용자 승인 없이 실행되게 사전 승인하는 스킬 속성. 차단 기능 아님. |
| `disallowed-tools` | 해당 도구를 사용 가능 풀에서 아예 제거하는 스킬 속성. 진짜 금지. |
| Pre-approve | 사전 승인. 실행 전 사용자 확인 프롬프트를 생략하는 것. |
| Tool pool | 그 시점에 Claude가 사용할 수 있는 도구들의 집합. |
| `context: fork` | 스킬을 격리된 서브에이전트 컨텍스트에서 실행하고 요약만 메인에 반환하는 속성. |
| `disable-model-invocation` | 모델의 자동 스킬 호출을 막고 사용자 수동 호출만 허용하는 속성. |
| `argument-hint` | 인자 입력 힌트를 UI에 표시하는 순수 표시용 속성. |
| Command (`.claude/commands/`) | `/이름` 으로 호출하는 프롬프트 템플릿 파일. 자동 실행되지 않음. |
| Hook | settings.json에 정의하여 특정 이벤트 시점에 하네스가 실행하는 프로그램. |
| `PreToolUse` | 도구 실행 직전에 발동하는 훅 이벤트. 입력을 검사하고 차단할 수 있음. |
| `PostToolUse` | 도구 실행 직후 발동하는 훅 이벤트. |
| `settings.json` | `.claude/` 아래의 설정 파일. 훅, 권한, 환경변수 등을 정의. |
| Deterministic control | 결정론적 제어. 모델의 판단과 무관하게 항상 동일하게 작동하는 강제 장치(훅 등). |
| Technical control | 기술적 제어. 프롬프트가 아닌 프로그램 레벨의 강제 수단. |
| Enforcement layer | 강제 레이어. CLAUDE.md는 여기에 해당하지 않음. |
| Subagent (`.claude/agents/`) | 독립 컨텍스트에서 작업하고 요약을 반환하는 별도 에이전트. |
| Personal / User level | `~/.claude/` 스코프. 개인 머신 전역. |
| Project level | `./.claude/` 스코프. 저장소에 커밋되어 팀 공유. |
| Precedence / Override | 우선순위와 덮어쓰기. 스킬은 Enterprise > Personal > Project > Plugins. |
| Interactive mode | 대화형 모드. 터미널에서 사용자 입력(stdin)을 기다림. |
| Non-interactive / Print mode | `-p` / `--print` 플래그로 실행하는 비대화형 1회성 실행 모드. |
| `-p` / `--print` | 프롬프트를 한 번 처리하고 결과 출력 후 종료시키는 CLI 플래그. CI 필수. |
| Hang | 프로세스가 종료도 출력도 없이 멈춰 대기하는 상태. |
| stdin | 표준 입력. 대화형 모드가 기다리는 대상. |
| CI/CD runner | GitHub Actions 등에서 잡을 실행하는 자동화 머신. 사람 입력 없음. |
| Shallow clone | `--depth` 옵션으로 히스토리를 잘라 받은 얕은 git 복제. |
| Masked secret | CI 로그에서 값이 가려지는 시크릿. 인증 동작 자체와는 무관. |
| Plan mode | 코드 변경 전 탐색·계획·승인을 먼저 수행하는 모드. |
| Direct execution | 계획 단계 없이 곧바로 편집을 시작하는 방식. |
| Trade-off | 두 선택지 사이의 득실 비교. 존재하면 플랜 모드의 신호. |
| Entry point | 서비스나 모듈의 진입 지점. 여러 개를 고쳐야 하면 다중 파일 변경. |
| Few-shot prompting | 입출력 예시 몇 개를 주어 요구사항을 전달하는 프롬프팅 기법. |
| Test-driven prompting | 기대 출력을 먼저 명시해 명세이자 테스트로 삼는 방식. |
| Iterative refinement loop | 예시 → 구현 → 검증 → 예시 보강을 반복하는 개선 루프. |
| Edge case | 빈 셀, 따옴표 안 쉼표, 중복 헤더처럼 경계에서 문제가 되는 특수 사례. |
| Quoted comma | CSV에서 따옴표로 감싸인 필드 내부의 쉼표. 구분자가 아닌 데이터. |
| Duplicate header | CSV에서 같은 컬럼명이 두 번 이상 나오는 경우. |
| Default behavior | 라이브러리가 명시적 설정 없이 취하는 기본 동작. 도메인 요구와 다를 수 있음. |
