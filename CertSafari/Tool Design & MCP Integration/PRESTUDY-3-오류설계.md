# 3. 도구 오류 설계

도구가 실패하면 그 결과는 그대로 모델에게 전달됩니다. 모델은 그 응답 하나만 보고 (1) 사용자에게 뭐라고 설명할지, (2) 다시 시도할지 포기할지를 결정합니다. 따라서 오류 응답은 사람 눈에 예쁜 로그가 아니라 **모델의 판단을 위한 인터페이스**로 설계해야 합니다.

## 이 장에서 다루는 것
- 좋은 오류 응답이란 무엇인가 (자연어 층 + 구조화 층)
- 검증 에러 vs 비즈니스 에러
- MCP 도구 결과 형태와 `isError` — 프로토콜 에러와의 구분
- 구조화된 에러 메타데이터 필드 설계
- 재시도 의미론 — 재시도 가능/불가, 백오프·지터·유한 재시도
- 흔한 오류 설계 실패와 함정

---

## 3.1 좋은 오류 응답이란 무엇인가

### 3.1.1 두 층으로 나눠 담기
좋은 오류 응답은 두 부분을 **분리해서** 함께 가집니다.

**(1) 사람이 읽을 수 있는 자연어 설명** (text block 또는 `message`/`description` 필드)
모델이 그대로 사용자에게 옮겨 말할 수 있는 문장. 무엇이 왜 실패했는지 구체적으로 담습니다.

**(2) 기계 지향 구조화 메타데이터** (structured content)
모델이 재시도 여부 등 제어 판단을 내리기 위한 필드. 대표적으로 `errorCategory`, `isRetryable`.

이 둘이 섞이면 안 됩니다. 자연어에 제어 정보("30초 뒤 다시 시도하세요")가 섞이면 모델이 문장을 파싱해야 하고, 반대로 구조화 필드만 있으면 사용자에게 설명할 문장이 없습니다.

```json
{
  "isError": true,
  "content": [
    { "type": "text",
      "text": "환불이 거절되었습니다. 이 주문은 구매일로부터 30일이 지나 반품 가능 기간을 벗어났습니다." }
  ],
  "structuredContent": {
    "errorCategory": "business",
    "isRetryable": false,
    "description": "주문 #12345는 30일 반품 기간을 초과하여 환불 대상이 아닙니다."
  }
}
```

### 3.1.2 좋은 오류 메시지가 담아야 할 것
- **무엇이** 실패했는가 (어떤 작업 / 어떤 리소스)
- **왜** 실패했는가 (분류 + 구체적 원인)
- **무엇을 하면 되는가** (재시도 가능 여부, 고쳐야 할 인자 이름, 대안 행동 힌트)

### 3.1.3 균일한 에러 메시지가 왜 최악인가
"모든 실패에 대해 똑같이 `isError: true` + `"Operation failed"`만 반환하면 도구 작성자 입장에서 인터페이스가 단순하다"는 주장이 있을 수 있습니다. 하지만 이건 **작성자의 편의를 위해 소비자(에이전트)의 능력을 파괴하는** 설계입니다.

에이전트가 실패 후 고를 수 있는 행동은 크게 셋입니다.

1. **재시도(retry)** — 일시적 오류일 때
2. **입력 수정 후 재요청(adjust input)** — 검증 오류일 때
3. **에스컬레이션(escalate)** — 권한 문제 등 스스로 못 푸는 경우, 사람이나 상위 에이전트에게 넘김

동일한 일반 메시지만 오면 이 셋 중 무엇을 골라야 할 **근거가 전혀 없습니다.** 결과적으로 에이전트는 아무거나 추측하거나, 무의미하게 반복하거나, 그냥 멈춥니다. 이것이 균일한 오류 메시지에 대한 가장 강력한 아키텍처적 반론입니다.

> 참고로 "MCP 명세가 고유 진단 문자열을 요구한다", "모든 `isError: true`에 스택 트레이스를 포함해야 한다", "상수 문자열이 프로토콜 최대 콘텐츠 길이를 초과시킨다" 같은 주장은 프로토콜 사실이 아닙니다. 진짜 문제는 규격 위반이 아니라 **에이전트의 복구 판단 불가**입니다.

### 3.1.4 설계 체크리스트
1. 이 실패는 재시도로 해결되는가? → 그에 맞는 카테고리 / `isRetryable` 선택
2. 사용자에게 그대로 읽어 줄 문장이 있는가? → 구체적 `message` / `description`
3. 대안 행동을 제시할 수 있는가? → "다른 시간대를 선택해 보세요" 같은 힌트
4. 내부 스택 트레이스나 비밀 정보가 새고 있지 않은가?

## 3.2 검증 에러 vs 비즈니스 에러

### 3.2.1 두 범주의 정의

**Validation Error (검증 에러)** — 입력 자체가 잘못됨
- 필수 필드 누락
- 타입 불일치 (숫자여야 하는데 문자열)
- 형식 위반 (날짜 포맷, 이메일 형식, enum 밖의 값)
- 스키마 구조 자체가 어긋남

핵심: **요청을 고쳐 쓰면(reformat) 통과할 수 있다.**

**Business Error / Domain Error (비즈니스 에러)** — 입력은 완벽하지만 규칙이 막음
- 계정이 정지(suspended) 상태
- 잔액 부족
- 법적 보류(legal hold) 중이라 삭제·취소 불가
- 이미 처리된 주문을 다시 취소하려 함
- 환불 가능 기간 30일 초과

핵심: **요청 형식을 아무리 고쳐도 상태/정책이 바뀌지 않는 한 계속 실패한다.**

### 3.2.2 구별 기준 (외우기)
> 요청 자체가 **well-formed**(형식적으로 올바름)인가?
> - 아니다 → Validation Error
> - 그렇다. 그런데도 거부됐다 → Business Error

### 3.2.3 구체 예: 법적 보류(legal hold)
`cancel_subscription` 도구가 "이 계정은 법적 보류 중이라 취소 불가"로 거부했습니다.

- 요청 JSON은 완벽함 — `account_id`도 문자열이고 존재하는 값
- 거부 사유는 **계정의 상태에 대한 정책 규칙**
- 재시도·재구성해도 정책이 바뀌기 전엔 절대 성공 못 함

→ 따라서 **Business Error**입니다.

### 3.2.4 자주 나오는 잘못된 논리
- **"스키마 검사 이후에 거부됐으니 전부 validation이다"** → 아닙니다. 검사 **시점**이 아니라 **원인의 성질**이 기준입니다.
- **"별도 서비스에서 검사했으니 business error다"** → 결론은 맞아도 **이유가 틀렸습니다.** 코드가 어디에서 실행되는지(아키텍처 위치)는 에러 분류 기준이 아닙니다.
- **"account_id 필드가 원인이니 그 필드의 validation 실패다"** → 아닙니다. **필드의 형식적 유효성**과 **그 필드가 가리키는 대상의 상태**는 엄격히 다른 층위입니다.

### 3.2.5 왜 이 구분이 중요한가
에이전트의 후속 행동이 달라지기 때문입니다.
- Validation Error → 인자를 고쳐서 **재요청**하면 성공 가능
- Business Error → 재시도해도 무의미. 사용자에게 **상황을 설명**하거나 다른 경로를 찾아야 함

### 3.2.6 인접 범주와의 혼동
- **permission vs business** — 둘 다 "규칙에 막혔다"지만 층위가 다릅니다. `permission`은 IAM/인가(authorization) 층의 문제(누가 무엇을 할 자격이 있는가)이고, `business`는 도메인 규칙 층의 문제(환불 기간, 최소 주문 금액 등)입니다. 배포 권한 제한은 IAM 문제이지 비즈니스 정책이 아닙니다.
- **permission vs validation** — 토큰이 **깨진 형식**이면 `validation`, 형식은 멀쩡한데 **권한이 모자라면** `permission`입니다.
- **permission vs transient** — 권한 부족은 서버가 접근 불가능한 것이 아니라 서버가 **의도적으로 거절**한 것입니다. 백오프 재시도로 해결되지 않습니다.

## 3.3 MCP 도구 결과 형태와 `isError`

에러에는 **계층**이 있고, 계층마다 표현 방법과 에이전트의 반응이 다릅니다. 실무에서 가장 자주 틀리는 부분입니다.

### 3.3.1 두 계층: 프로토콜 에러 vs 도구 실행 결과 에러

**(1) 프로토콜 수준 에러 — JSON-RPC Error**
- **언제**: 도구의 핸들러 로직이 **실행되기 전**, 요청 자체가 잘못되었을 때
- **원인 예**: 입력 스키마 위반(타입 불일치, 필수 필드 누락), JSON 파싱 실패, 존재하지 않는 메서드/도구
- **표현**: JSON-RPC 에러 응답. 대표적으로 `-32602 Invalid params`, `-32700 Parse error`, `-32601 Method not found`
- **핵심**: **핸들러 코드는 한 줄도 실행되지 않습니다.** 프로토콜/스키마 계층에서 걸러집니다.

예: `charge_card`의 스키마가 `amount`를 숫자(number)로 정의했는데 `"$45.00"`이라는 문자열이 들어온 경우 → 결제 로직이 돌기도 전에 스키마 검증 단계에서 JSON-RPC 프로토콜 에러가 납니다.

**(2) 도구 실행 결과 에러 — `isError: true`**
- **언제**: 요청은 유효해서 **핸들러가 정상 실행되었지만**, 그 결과가 실패인 경우
- **원인 예**: 카드 결제 거절(declined), DB 연결 실패, 권한 부족, 외부 API가 500 반환
- **표현**: `tools/call`이 정상 응답하되, 결과 객체 안에 `isError: true`와 사람이 읽을 수 있는 설명을 담습니다.
- **핵심**: 프로토콜은 성공, **도메인 결과가 실패**입니다.

```json
{
  "content": [{ "type": "text", "text": "카드가 거절되었습니다: 잔액 부족 (code: insufficient_funds)" }],
  "isError": true
}
```

**요약 비교**

| | 프로토콜 에러 | 도구 실행 결과 에러 |
|---|---|---|
| 발생 시점 | 핸들러 실행 **전** | 핸들러 실행 **후** |
| 원인 | 스키마/형식 위반 | 도메인·시스템 실패 |
| 표현 | JSON-RPC error (`-32602` 등) | 결과 안의 `isError: true` |
| 에이전트의 올바른 반응 | **인자를 고쳐** 다시 호출 | 결과를 읽고 사용자에게 설명하거나 대안 시도 |

같은 `charge_card` 도구에서 "금액이 문자열로 들어옴"은 프로토콜 에러, "정상 요청이었으나 카드가 거절됨"은 `isError: true`인 실행 결과 에러입니다. 두 실패는 계층이 다릅니다.

### 3.3.2 `isError` 필드의 의미
MCP 도구 호출 결과에는 성공/실패를 나타내는 `isError` 불리언이 있습니다.

- `isError: false` (또는 없음) → 호출이 **성공적으로 완수**됨
- `isError: true` → 호출이 **실패**함. 이때 `content`의 텍스트 블록에 실패 이유를 담습니다.

중요한 원칙: **도구가 요청된 일을 하지 못했다면 반드시 `isError: true`** 여야 합니다. 필수 인자가 빠져서 아무 일도 못 했는데 "기술적으로는 호출이 반환됐으니 성공"이라고 처리하면, 에이전트는 실패를 성공으로 오인하고 **잘못된 데이터 위에서 다음 단계를 진행**합니다.

또한 `isError: true`는 "재시도를 무제한 허용하라"는 신호가 아니라 단지 "실패"라는 표시일 뿐입니다. 재시도 판단은 별도의 구조화 필드가 담당합니다(3.4, 3.5절).

### 3.3.3 가장 흔한 함정: "빈 결과 ≠ 에러"

반드시 구별해야 하는 두 상황이 있습니다.

**상황 A — 존재하는 고객인데 주문이 0건**
- 조회는 정상적으로 수행되었고, 답이 "없음"일 뿐입니다. DB는 잘 붙었고, 쿼리는 잘 돌았습니다.
- **성공입니다.**

```json
{
  "content": [{ "type": "text", "text": "조건에 맞는 티켓이 0건입니다." }],
  "structuredContent": { "tickets": [], "count": 0 },
  "isError": false
}
```

**상황 B — 애초에 존재하지 않는 고객 ID**
- 조회 대상 리소스 자체가 없습니다. 요청 전제가 틀렸습니다.
- **에러입니다.**

```json
{
  "isError": true,
  "errorCategory": "not_found_error",
  "message": "Customer ID 'cus_99999' was not found."
}
```

### 3.3.4 왜 반드시 구별해야 하는가
- 둘 다 `isError: false` + 빈 배열로 처리하면 → **에러가 은폐**됩니다. 에이전트는 "이 고객은 주문이 없구나"라고 잘못 결론 내리고, 오타난 ID를 영영 잡아내지 못합니다.
- 둘 다 `isError: true`로 처리하면 → 정상 상황을 실패로 취급해 불필요한 재시도·에러 핸들링이 발생합니다. 예를 들어 `search_tickets`가 0건에 대해 `isError: true` + `"No tickets found"`를 반환하면, 조정 에이전트는 이를 시스템 장애로 이해하고 사용자에게 "시스템 오류가 발생했습니다"라고 사과합니다.

**효과가 없거나 더 나쁜 대응들:**
- `isError: true`를 유지한 채 `errorCategory`만 `transient`로 바꾸기 → 에이전트가 "언젠가 티켓이 생기겠지" 하며 동일 검색을 무한 재시도합니다. 주문/티켓이 0건인 것은 시간이 지난다고 바뀌는 성질의 것이 아닙니다. 상황이 더 나빠집니다.
- 에러 문구만 부드럽게 다듬기 → 여전히 에러 플래그가 켜져 있으므로 에이전트의 오해는 그대로입니다.

> **규칙**: `isError: true`는 **도구 수행 자체가 실패했을 때만** 씁니다 — 연결 실패, 권한 오류, 구문 오류, 외부 시스템 장애 등.
> **"성공적으로 조회했는데 결과가 없다"는 성공. "조회 대상이 없다"는 에러.**

## 3.4 구조화된 에러 메타데이터 필드 설계

### 3.4.1 불투명한 에러의 문제
도구가 이렇게만 응답한다고 합시다.

```json
{ "isError": true, "content": [{ "type": "text", "text": "Operation failed." }] }
```

에이전트가 이 응답에서 얻을 수 있는 정보는 "실패했다"는 사실뿐입니다. 알 수 없는 것들:

- 이게 잠깐 뒤에 다시 하면 될 일인가? (배포 중 503)
- 아니면 영원히 안 될 일인가? (권한 없음, 존재하지 않는 리소스)
- 얼마나 기다렸다가 재시도해야 하나?

판단 근거가 없으면 에이전트는 **같은 호출을 무의미하게 반복**하다가 포기합니다. 토큰·시간·하위 API 부하가 낭비됩니다.

이때의 **가장 직접적인 원인**은 "에러를 구분할 구조화된 메타데이터가 없다"는 것입니다. 컨텍스트 윈도우 부족이나 `isError` 값 자체가 원인이 아닙니다.

### 3.4.2 좋은 에러 응답의 형태

```json
{
  "isError": true,
  "errorCategory": "transient",
  "retryable": true,
  "retryAfterSeconds": 30,
  "httpStatus": 503,
  "message": "Billing API is temporarily unavailable (deployment in progress). Safe to retry in ~30s."
}
```

권한 문제의 예:

```json
{
  "isError": true,
  "errorCategory": "permission",
  "isRetryable": false,
  "message": "Token scope 'read' is insufficient; 'deploy' scope required.",
  "remediation": "Request a token with the deploy scope, then retry."
}
```

**포함하면 좋은 필드**

| 필드 | 역할 |
|---|---|
| `errorCategory` | 기계가 분기할 수 있는 범주 문자열 |
| `isRetryable` / `retryable` | 재시도가 의미 있는지 불리언 |
| `retryAfter` / `retryAfterSeconds` | 언제 다시 시도할지 힌트 |
| `httpStatus` | 하위 시스템의 원래 상태 코드 |
| `message` / `description` | 사람과 모델이 읽는 구체적 설명 ("무엇이" "왜") |
| `remediation` | 무엇을 고치면 되는지 안내 |

> `errorCategory`와 `isRetryable`은 MCP 코어 명세가 **강제하는 필드가 아니라 도구 설계 관례**입니다. 하지만 에이전트가 올바른 복구 행동을 고르게 하는 사실상의 표준 패턴입니다.

### 3.4.3 에러 카테고리 어휘

자료마다 표기가 조금씩 다릅니다(`validation` / `validation_error`, `permission` / `auth_error` 등). 이름보다 **의미와 재시도 행동**이 중요합니다.

| 카테고리 | 의미 | 예 | 모델/에이전트가 취해야 할 행동 |
|---|---|---|---|
| `validation` (`validation_error`) | 입력값의 형식/타입/필수값이 잘못됨 | 날짜 문자열 형식 오류, 필수 필드 누락, 범위 초과 | **입력을 고쳐서** 새 요청 (같은 요청 재시도 ✗) |
| `not_found` (`not_found_error`) | 대상 리소스 없음 | 존재하지 않는 customer_id | 다른 식별자로 시도하거나 포기 (같은 인자로는 무의미) |
| `permission` (`auth_error`) | 인증은 되었으나 권한/scope 부족 (401, 403) | `read` 토큰으로 `deploy` 시도 | 권한 획득·에스컬레이션·관리자 문의 (재시도 ✗) |
| `business` (`business_error`) | 도메인 정책 규칙 위반 | 환불 30일 기간 초과, 잔액 부족, 재고 부족, legal hold | 사용자에게 설명 / 다른 경로 (상태가 바뀌기 전엔 무의미) |
| `transient` | 일시적 인프라 장애 | 503, 타임아웃, 연결 리셋, 일시적 락 경합 | **백오프 후 동일 호출 재시도 ✓** |
| `rate_limit` | 호출 한도 초과 (429) | 데이터 웨어하우스 속도 제한 | 대기 후 재시도 ✓ (transient의 일종) |

카테고리를 잘못 붙이면 모델이 정확히 잘못된 행동을 합니다. 30일 반품 기한 초과(비즈니스 규칙)를 `transient`로 표시하면 모델은 "30초 뒤 재시도"를 무한 반복합니다. 반대로 권한 문제를 `business`로 표시하면 해결 가능한 문제를 포기해 버립니다.

## 3.5 재시도 의미론 (Retry Semantics)

### 3.5.1 `isRetryable`의 정확한 의미 — 가장 자주 틀리는 지점

`isRetryable: true`가 뜻하는 것은 **"입력을 하나도 바꾸지 않고 그대로 다시 보내도 성공할 가능성이 있다"** 입니다. "언젠가는 어떻게든 해결될 수 있다"가 아닙니다.

> **판별 기준**: 입력을 하나도 바꾸지 않고 그대로 다시 보냈을 때 성공할 가능성이 있는가?
> 있으면 transient → `true`. 없으면 permanent/validation → `false`.

- 네트워크 타임아웃 → 서버가 잠깐 바빴을 뿐, 다시 보내면 성공할 수 있음 → `true`
- 권한 부족 → 토큰의 scope가 바뀌지 않는 한 성공 확률 0% → `false`
- 회의실이 이미 예약된 경우처럼 **사용자가 조건(시간대)을 바꾸지 않는 한 절대 성공하지 않는 상황** → `false`. 여기에 `true`를 주면 무한 재시도 루프를 유발합니다.

`isRetryable: false`를 정확히 표시하는 것은 **불필요한 재시도 폭풍을 막아** 지연과 비용, 서버 부하를 줄입니다.

### 3.5.2 카테고리별 값

| errorCategory | isRetryable | 이유 / 에이전트가 할 일 |
|---|---|---|
| `validation` | **false** | 요청이 잘못됐다(malformed). 같은 요청은 100번 보내도 100번 실패. **입력을 고쳐서** 새 요청 |
| `not_found` | **false** | 대상이 없음. 다른 식별자가 필요 |
| `permission` | 보통 **false** | 권한이 없다. 재시도가 아니라 권한 획득이나 에스컬레이션이 필요 |
| `business` | **false** | 상태·정책이 바뀌기 전엔 동일 결과 |
| `transient` / `rate_limit` | **true** | 서버·네트워크 쪽 일시 장애. 잠시 기다렸다 같은 요청을 보내면 성공 가능 |

**영구(permanent / non-retryable) 오류의 전형**: 400 Bad Request, 401/403, 404, 422, 도메인 정책 위반. 재시도해도 결과가 동일하므로 즉시 상위에 보고하거나 사용자에게 설명해야 합니다.

**일시적(transient) 오류의 전형**: HTTP 503 Service Unavailable(배포·재시작 중), 데이터베이스 커넥션 리셋, 네트워크 타임아웃, 일시적 락 경합, 429 rate limit.

### 3.5.3 필수 인자 누락 사례 — "재시도"가 아니라 "수정 후 재요청"

`update_inventory`가 필수 필드 `sku` 누락에 대해 `errorCategory: "transient"`, `isRetryable: true`를 반환하도록 잘못 분류했다고 합시다. 에이전트는 "일시적이라니 다시 보내면 되겠지" 하고 **똑같이 잘못된 요청을 무한히 재시도**합니다. 영원히 성공하지 않으며 시간·토큰·API 호출 한도를 태웁니다.

"에이전트가 나중에 다른 요청에서 그 필드를 채워줄 것"이라는 기대는 성립하지 않습니다. 각 호출은 독립적이고, 누락된 필드는 **이 요청**에 들어 있어야 합니다. 그건 재시도(retry)가 아니라 **수정 후 재요청(correct and resubmit)** 이며, `isRetryable: true`는 에이전트에게 "그대로 다시 보내라"는 잘못된 신호를 줍니다.

카테고리를 `transient`로 바꾸는 것도 답이 아닙니다. 인자 누락은 시간이 지난다고 저절로 낫는 문제가 아니므로, 오류의 성격을 왜곡해 잘못된 대기·재시도 행동을 부릅니다.

**올바른 수정**: 유효성(영구) 에러이므로 `isRetryable: false`로 분류하고, 메시지에 **무엇이 잘못되었고 어떻게 고쳐야 하는지**를 명시합니다.

```json
{
  "content": [{ "type": "text",
    "text": "필수 필드 'sku'가 누락되었습니다. sku는 문자열이며 예: \"ABC-1234\". 요청에 sku를 추가한 뒤 다시 호출하세요." }],
  "isError": true,
  "errorCategory": "validation",
  "isRetryable": false
}
```

이렇게 하면 에이전트는 맹목적 재시도 대신 **인자를 고쳐 재호출**하는, 실제로 성공 가능한 행동을 택합니다.

### 3.5.4 Rate limit(429)의 올바른 오류 응답

**429 Too Many Requests**는 서버가 "요청이 너무 잦다"며 잠시 거절하는 상태 코드입니다. 요청 자체는 정상이고, 잠시 후면 성공합니다. 전형적인 **일시적(transient)** 오류입니다.

데이터 웨어하우스가 가끔 429를 던지는 `run_report` 도구라면 이렇게 반환합니다.

```json
{
  "isError": true,
  "errorCategory": "transient",
  "isRetryable": true,
  "content": [{
    "type": "text",
    "text": "Data warehouse is rate-limiting requests (HTTP 429). Retry after a short backoff."
  }]
}
```

**잘못된 응답 설계들**
- `permission` + `isRetryable: false` → 원인을 오진해서, 재시도하면 될 일을 포기하게 만듦
- `validation` + `isRetryable: true` → 자기모순. 게다가 "날짜 범위를 줄이라"는 지시는 429의 실제 원인(속도 제한)과 무관
- 구조화된 필드 없이 본문에 "try again later"라고만 적기 → 에이전트가 자연어를 해석해 추측해야 하고, 기계적으로 신뢰할 수 없습니다. **기계 판독 가능한 필드**가 있어야 일관된 행동이 나옵니다

### 3.5.5 백오프·지터·유한 재시도

- **백오프(backoff)**: 재시도 전에 기다리는 것. **지수 백오프(exponential backoff)** 는 대기 시간을 1초 → 2초 → 4초 → 8초처럼 배로 늘려, 이미 과부하인 서버를 더 때리지 않게 합니다.
- **지터(jitter)**: 대기 시간에 무작위 편차를 더해, 여러 클라이언트가 동시에 재시도하는 쏠림(thundering herd)을 막습니다.
- **유한한 재시도(bounded retry)**: 최대 횟수 / 최대 총 시간을 정해두고, 넘으면 포기하고 상위로 알립니다. 무한 재시도는 시스템을 멈추게 하는 장애 패턴입니다.

`validation`, `permission`, `business` 에러에 백오프 재시도를 거는 것은 순수한 낭비입니다.

### 3.5.6 역할 분담: 도구는 사실만, 에이전트가 정책을
**도구는 "이건 일시적이고 재시도 가능하다"는 사실만 정확히 알려주고, 얼마나 기다리고 몇 번 시도할지는 에이전트가 결정**합니다. 도구가 무한 대기를 강요하지 않습니다. `retryAfterSeconds` 같은 필드는 **힌트**이지 명령이 아닙니다.

## 3.6 흔한 오류 설계 실패

| 실패 패턴 | 무슨 일이 벌어지는가 |
|---|---|
| **빈약한 텍스트만** (`"Refund denied"`, `"Operation failed."`) | 이유도 없고 재시도 판단 근거도 없음. 모델은 사용자에게 설명도 못 하고, 다시 시도해야 할지도 모름 |
| **날것의 예외 스택 트레이스 반환** | 모델에게 텍스트 파싱을 시키는 셈. 토큰 낭비, 파싱 오류 시 잘못된 설명, 내부 구현 정보 유출 |
| **`description` 없이 카테고리만** | `errorCategory: "business"`만으로는 "무엇이 왜"인지 모름. 카테고리는 대분류일 뿐 구체 사유를 대체하지 못함 |
| **제어 정보를 자연어에 섞기** | "wait 30 seconds and resubmit"을 텍스트에 넣으면서 카테고리는 다른 이야기를 하면 모델이 혼란 |
| **빈 결과를 에러로 표시** | 정상 상황을 장애로 오인, 사용자에게 "시스템 오류" 사과. `transient`까지 붙이면 무한 재시도 |
| **존재하지 않는 리소스를 빈 결과로 표시** | 에러 은폐. 오타난 ID를 영영 못 잡음 |
| **실패했는데 `isError: false`** | 에이전트가 실패를 성공으로 오인, 잘못된 데이터 위에서 다음 단계 진행 |
| **validation을 `transient`/`isRetryable: true`로 분류** | 똑같이 잘못된 요청을 무한 재시도. 시간·토큰·API 한도 소진 |
| **business/permission을 `transient`로 분류** | 절대 성공하지 않을 호출을 백오프하며 반복 |
| **transient를 `permission`으로 오진** | 재시도하면 될 일을 포기하고 에스컬레이션 |
| **모든 실패에 동일 메시지** | 재시도/입력수정/에스컬레이션 중 무엇을 고를지 판단 근거 상실 |
| **프로토콜 에러와 실행 결과 에러 혼동** | 스키마 위반을 `isError`로 감싸거나, 도메인 실패를 JSON-RPC 에러로 올려 계층이 무너짐 |
