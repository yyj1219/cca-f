# 1부. 기초

## 1. LLM 에이전트와 도구(Tool)의 기본

### 1.1 왜 도구가 필요한가
LLM(대형 언어 모델)은 본질적으로 **텍스트를 생성하는 함수**입니다. 학습 시점까지의 지식만 가지고 텍스트를 만들 뿐, 스스로는 다음을 할 수 없습니다.

- 데이터베이스 조회
- 파일 읽기/쓰기
- 외부 API 호출
- 명령어 실행
- 오늘 날짜의 실시간 데이터 조회 (환율, 재고, 티켓 상태)
- 외부 시스템에 대한 실제 작업 수행 (환불 처리, 회의실 예약, 배포)

**도구(Tool)** 는 이 한계를 메우기 위해 모델에게 "네가 호출할 수 있는 함수 목록"을 미리 알려주는 장치입니다. 이것이 **Tool Use**(도구 사용), 다른 이름으로 **Function Calling**(함수 호출)입니다.

### 1.2 동작 흐름 (Tool Use Loop / Agent Loop)
1. 애플리케이션이 모델에게 **시스템 프롬프트 + 대화 + 도구 정의 목록**을 보냅니다.
2. 모델이 사용자의 요청을 읽고, "이건 `get_weather`를 써야겠다"고 판단하면 일반 텍스트 대신 **tool_use 블록**(도구 이름 + 인자 JSON)을 출력합니다.
3. **모델은 도구를 직접 실행하지 않습니다.** 실행은 애플리케이션(호스트, 클라이언트, 에이전트 런타임)이 합니다.
4. 실행 결과(성공이든 실패든)를 **tool_result 블록**으로 다시 모델에게 돌려줍니다.
5. 모델이 그 결과를 읽고 다음 행동(또 다른 도구 호출, 또는 사용자에게 최종 답변)을 결정합니다.

이 1~5의 반복을 **에이전트 루프(agent loop)** 라고 부릅니다.

```
사용자 요청
  → 모델이 도구 목록 + description 을 읽음
  → 모델이 "어떤 도구를, 어떤 인자로" 호출할지 결정 (= 라우팅)
  → 런타임이 실제로 실행
  → 결과를 다시 모델에게 전달
  → 모델이 다음 행동을 결정하거나 최종 답변 생성
```

이 루프의 **결정 지점**은 두 곳입니다. 어떤 도구를 고를 것인가(**도구 선택**), 그리고 어떤 인자를 넣을 것인가(**인자 추출**). 이 주제 대부분의 내용은 "이 두 결정을 모델이 덜 틀리게 만드는 법"과 "4번 단계, 즉 결과를 어떤 모양으로 돌려주느냐"에 관한 것입니다.

### 1.3 컨텍스트 윈도우(Context Window)
모델이 한 번에 "볼 수 있는" 텍스트의 총량입니다. 토큰(token, 대략 단어 조각) 단위로 셉니다. 지금까지의 대화, 읽은 파일 내용, 도구 결과가 전부 여기에 쌓입니다.

한도를 넘으면 오래된 내용이 잘려나가거나 요약되고, 그러면 모델이 앞서 본 것을 "잊습니다". 또한 토큰은 비용이자 지연시간입니다. 그래서 **"필요한 것만, 필요할 때 읽는다"** 가 에이전트 작업의 기본 원칙입니다.

## 2. 도구 정의의 구성 요소

도구 하나는 보통 세 가지로 정의됩니다.

| 요소 | 역할 |
|---|---|
| `name` | 도구 식별자 (예: `search_web`, `get_user_profile`). 스네이크 케이스, 동사_명사 형태 권장 |
| `description` | 자연어 설명. **모델이 도구를 고를 때 쓰는 주된 근거**이자 모델이 읽는 유일한 사용 설명서 |
| `input_schema` | 입력 파라미터의 JSON Schema (타입, 필수 여부, 필드 설명) |

예시:

```json
{
  "name": "search_web",
  "description": "웹 검색 엔진에 질의를 보내 최신 정보를 담은 결과 스니펫 목록을 돌려준다. 아직 어떤 페이지를 봐야 할지 모를 때 사용한다. 이미 특정 URL을 알고 있다면 fetch_webpage_results를 사용할 것.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": { "type": "string", "description": "검색어" }
    },
    "required": ["query"]
  }
}
```

또 다른 예 (경계와 출력 상세도를 명시한 좋은 설명):

```json
{
  "name": "generate_summary_report",
  "description": "계정의 한 페이지 분량 요약 보고서를 생성한다. 총 잔액, 최근 5건 거래, 이상징후 여부만 포함한다(약 300단어). 예: '이 계정 간단히 훑어줘'. 거래 내역 전체나 월별 상세 분석이 필요하면 generate_detailed_report를 사용할 것.",
  "input_schema": {
    "type": "object",
    "properties": {
      "account_id": { "type": "string", "description": "계정 식별자, 예: 'ACCT-10293'" }
    },
    "required": ["account_id"]
  }
}
```

### 2.1 이 주제 전체를 관통하는 핵심 통찰
모델은 도구의 **소스 코드를 보지 못합니다.** 모델이 보는 것은 오직 이름, 설명, 입력 스키마뿐이고, 여기에 **시스템 프롬프트**가 얹혀 전체 판단이 이뤄집니다.

> **도구 정의는 코드가 아니라 모델을 향한 문서다.**
> 도구 선택이 틀리면, 대개 모델이 아니라 **이름·설명·도구 집합**의 문제다.

그래서 도구 설계에서 가장 큰 영향력을 가진 것은 **코드가 아니라 텍스트**입니다. 도구 설명은 사람이 읽는 주석이 아니라 **모델이 라우팅 결정을 내리는 근거이자 API 계약**입니다. 모델이 도구를 잘못 고르거나 이상한 인자를 만들어내면, 모델을 탓하기 전에 도구 정의를 봐야 합니다.
