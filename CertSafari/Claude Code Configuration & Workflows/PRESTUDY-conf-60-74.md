# 사전학습 노트 — Claude Code 설정과 워크플로

이 문서는 Claude Code를 한 번도 써 본 적 없는 사람을 대상으로, 관련 개념을 바닥부터 설명합니다. 순서대로 읽으면 됩니다.

---

## 0. 큰 그림 — Claude Code란 무엇인가

Claude Code는 터미널에서 실행되는 AI 코딩 도구(CLI)입니다. 사용자가 자연어로 "이 함수 버그 고쳐줘"라고 말하면, Claude가 **도구(tool)**를 써서 실제로 파일을 읽고, 편집하고, 셸 명령을 실행합니다.

핵심 도구 몇 가지:

| 도구 | 하는 일 |
|---|---|
| Read | 파일 내용 읽기 |
| Edit / Write | 파일 수정·생성 |
| Grep / Glob | 코드 검색, 파일 이름 패턴 검색 |
| Bash | 셸 명령 실행 (테스트 실행, git 등) |

Claude Code를 이해하는 데 필요한 두 개의 축이 있습니다.

1. **컨텍스트(Context)** — Claude가 "무엇을 알고 있는가". 모델은 자기 앞에 놓인 텍스트만 압니다. 여러분의 파일 시스템 전체를 자동으로 아는 게 아닙니다.
2. **설정(Configuration)** — 어떤 규칙·명령어·권한이 어느 범위(개인/프로젝트/조직)에 적용되는가. 대부분 파일 경로로 결정됩니다.

이 노트의 나머지는 이 두 축을 자세히 풀어씁니다.

---

## 1. 컨텍스트: LLM이 아는 것과 모르는 것

### 1.1 컨텍스트 윈도우

LLM은 "컨텍스트 윈도우"라는 유한한 작업 공간을 가집니다. 한 번의 요청에 들어간 모든 텍스트(시스템 지시문, 대화 기록, 첨부된 파일 내용, 사용자 메시지)가 이 공간을 차지합니다. 여기 들어오지 않은 정보는 모델에게 **존재하지 않는 것과 같습니다.**

이 사실 하나에서 많은 실무 규칙이 파생됩니다.

### 1.2 관련 있는 것은 넣어야 한다 (Context-Aware 작업)

예: Claude에게 "이 모듈의 단위 테스트를 새로 만들어줘"라고 하면서 **수정된 소스 코드만** 주면, Claude는 이미 존재하는 테스트 파일을 볼 수 없습니다. 그러면 이미 커버된 시나리오를 또 만들어 냅니다. 모델이 게을러서가 아니라, 알 방법이 없어서입니다.

해결책은 단순합니다 — **기존 테스트 파일도 함께 컨텍스트에 넣습니다.**

```bash
# 나쁜 예: 소스만 준다
claude -p "src/inventory.ts 에 대한 단위 테스트를 작성해줘"

# 좋은 예: 이미 커버된 내용을 같이 준다
claude -p "src/inventory.ts 의 변경사항에 대해, tests/inventory.test.ts 에
아직 커버되지 않은 케이스만 추가해줘. 두 파일 모두 읽고 비교할 것."
```

일반 원칙: **"모델이 X를 고려하기를 원한다면, X를 컨텍스트에 넣어라."**

이걸 우회하려는 시도들은 대체로 실패합니다.
- 출력 형식을 바꾸고(예: 스트리밍 JSON) 후처리 스크립트로 중복을 걸러내기 → 생성 자체는 여전히 낭비되고, 파이프라인만 복잡해집니다. 중복 제거는 "생성 후 필터"가 아니라 "생성 전 정보 제공"으로 푸는 게 맞습니다.
- 예산 상한을 올려서 더 많이 생성하게 하기 → 중복이 더 늘어날 뿐입니다.
- 세션 기록을 끄기 → 로컬 파일을 인식시키는 것과 무관합니다.

### 1.3 추상적 지시어의 함정과 퓨샷 프롬프팅(Few-Shot Prompting)

"간결하게 써(concise)", "깔끔하게 해줘", "적당한 길이로" 같은 말은 사람에게는 통하지만 모델에게는 해석 폭이 매우 넓습니다. 어떤 요청에는 한 문장, 어떤 요청에는 세 단락이 나옵니다.

**퓨샷 프롬프팅**은 원하는 입력→출력 쌍의 **실제 예시를 2~3개** 프롬프트에 넣는 기법입니다. 모델은 형용사보다 예시에서 패턴(길이, 톤, 문장 구조, 포맷)을 훨씬 정확하게 뽑아냅니다.

```
다음 형식으로 기사를 요약하라.

[예시 1]
기사: (원문 …)
요약: 국내 배터리 3사가 3분기 합산 영업이익 1.2조 원을 기록하며 전년 대비 18% 성장했다.

[예시 2]
기사: (원문 …)
요약: 미 연준이 기준금리를 0.25%p 인하했고, 시장은 연내 추가 인하 가능성에 무게를 두고 있다.

[실제 입력]
기사: {{article}}
요약:
```

여기서 "concise"라는 단어는 이제 **구체적 사례에 고정(anchored)**됩니다.

대안들이 왜 약한지:
- 형용사를 더 많이 나열하기("short, tight, succinct, to the point") → 여전히 추상어입니다. 모호함의 양은 그대로입니다.
- 지시를 아예 빼고 모델에게 맡기기 → 일관성은 더 나빠집니다.
- **stop sequence**로 강제로 자르기 → 아래 참고.

#### stop sequence (중단 시퀀스)

모델 API에는 "이 문자열이 나오면 생성을 즉시 멈춰라"라고 지정하는 `stop_sequences` 파라미터가 있습니다. 예를 들어 `["\n\n"]`을 주면 빈 줄이 나오는 순간 멈춥니다.

이건 **포맷 경계를 지키는 용도**(예: 다음 예시 블록으로 넘어가는 걸 막기)로 쓰는 것이지, **길이를 제어하는 용도가 아닙니다.** 길이 제어에 쓰면 문장이 중간에서 잘려 부자연스러운 결과가 나옵니다. 길이는 예시와 명시적 수치("2문장, 40단어 이내")로 제어하는 것이 옳습니다.

## 2. 피드백을 구조화하는 법 (테스트 실패 보고)

Claude에게 코드를 고치게 할 때, 테스트 실패를 어떻게 전달하느냐가 결과 품질을 좌우합니다.

### 2.1 기본 루프

```
① 요청 → ② Claude가 코드 작성 → ③ 테스트 실행 →
④ 실패 로그를 Claude에게 전달 → ⑤ 수정 → ⑥ 전체 테스트 재실행으로 검증
```

⑥이 중요합니다. **전체 스위트를 다시 돌려야** 수정이 다른 부분을 깨뜨리지 않았는지(회귀, regression) 확인할 수 있습니다. 고친 테스트 하나만 돌리는 것은 부족합니다.

### 2.2 서로 무관한 버그들이 한꺼번에 나온 경우 → 한 번에 전달

예를 들어 세 개의 실패가 있고, 각각 원인이 완전히 별개라고 합시다.
- 소수점 수량의 **반올림 오차(rounding error)**
- 반복문 경계의 **off-by-one 오류** — `<` 를 써야 하는데 `<=` 를 써서 마지막 요소를 한 번 더 돌거나 빠뜨리는 고전적 버그
- 단종 상품 필드에 대한 **null 체크 누락** — 값이 없을 수 있는 필드를 검사 없이 접근해 런타임 크래시로 이어짐

이 경우 **전체 테스트 출력을 한 메시지에 다 담아 주는 것**이 좋습니다. 이유:
- 모델이 함수 전체 구조를 한 번에 파악해 세 곳을 동시에 고칩니다.
- 대화 턴(turn)이 줄어들어 토큰과 시간이 절약됩니다.
- 뒤에 나올 정보를 감추면(한 번에 하나씩, 나중 세션으로 미루기) 모델은 반쪽 정보로 작업하고, 첫 수정이 나머지와 충돌할 수 있습니다.

또한, **구체적인 로그를 주지 않고 "원인이 뭘 것 같아?"라고 추측을 시키는 것**은 최악입니다. 근거 없는 추측은 할루시네이션(hallucination, 그럴듯하지만 사실이 아닌 출력)을 유발합니다. 항상 실제 에러 메시지, 스택 트레이스, 실패한 어서션 값을 그대로 붙여넣으세요.

### 2.3 서로 연관된 버그가 섞인 경우 → 연관끼리 묶고, 무관한 것은 분리

앞의 원칙은 "무조건 다 몰아서 주라"는 뜻이 아닙니다. 진짜 원칙은 **논리적 그룹핑(logical grouping)**입니다.

예: 웹훅 수집 서비스에서 세 개가 실패.
1. 멱등성 키(idempotency key)로 중복 배달을 걸러내지 못함
2. 중복 제거 윈도우가 만료돼도 오래된 키가 해제되지 않음
3. 잘못된 JSON 페이로드에 400을 반환하지 않음

1번과 2번은 **같은 중복 제거 스토어(dedup store) 로직**에서 나옵니다. 3번은 파싱 계층의 별개 문제입니다.

→ **1·2번은 한 메시지에 묶어서**, 3번은 별도로 전달합니다.
- 묶는 이유: 같은 로직을 건드리는 두 문제를 따로 고치게 하면, 첫 수정이 두 번째 문제의 전제를 바꿔 재작업·충돌이 생깁니다. 함께 보면 스토어 설계를 한 번에 올바르게 잡습니다.
- 분리하는 이유: 무관한 문제를 섞으면 디버깅 범위가 흐려지고 모델이 억지로 공통 원인을 찾으려 합니다.

그리고 이미 명확한 실패 결과가 나왔다면, "플레이키(flaky, 간헐적 실패)인지 확인하려고 여러 번 더 돌려보고 나중에 보고" 하는 식으로 미루지 마세요. 진행만 지연됩니다.

#### 관련 용어
- **멱등성(idempotency)**: 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질. 웹훅은 네트워크 재시도로 중복 배달이 흔해서, 요청마다 고유한 **멱등성 키**를 붙이고 이미 처리한 키인지 저장소에서 확인합니다.
- **중복 제거 윈도우(dedup window)**: 멱등성 키를 영원히 저장할 수 없으므로 일정 시간(예: 24시간)만 보관하고 만료시킵니다.

## 3. 워크플로 모드: Plan 모드 vs 직접 실행 vs 서브에이전트

Claude Code에는 작업을 처리하는 여러 방식이 있고, 작업의 **불확실성 정도**에 따라 골라야 합니다.

### 3.1 직접 실행 (Direct Execution)
Claude가 바로 편집을 수행합니다. 가장 빠릅니다.

**적합한 경우**: 무엇을, 어디를, 어떤 값으로 바꿀지 이미 전부 정해진 작업.
예 — "`config/server.yaml`의 `timeout: 30`을 `timeout: 60`으로 바꿔라." 탐색할 것도, 설계 선택지도 없습니다. 특히 CI 같은 **비대화형(non-interactive)** 환경에서는 사람이 중간에 승인해 줄 수 없으므로, 이런 완전 명세된 작업은 직접 실행이 정답입니다.

### 3.2 Plan 모드
Claude가 먼저 **계획(설계안)을 제시**하고, 사람이 승인한 뒤에 실행합니다.

**적합한 경우**: 접근 방식이 여러 개이고 어느 쪽이 나은지 판단이 필요한 작업. 리팩터링 전략, 스키마 마이그레이션 설계 등.

**부적합한 경우**: 값 하나 바꾸는 작업. 승인 대기가 파이프라인을 막고, 얻는 것이 없습니다. "모든 설정 파일 변경에는 Plan 모드가 필수"라는 규칙은 존재하지 않습니다.

### 3.3 서브에이전트 (Subagent)

**서브에이전트**는 메인 대화가 별도의 Claude 인스턴스에게 작업을 위임하는 기능입니다. 예를 들어 Explore 서브에이전트는 저장소 전역을 뒤져 "타임아웃 설정이 어디어디 있나"를 찾아 요약만 돌려줍니다.

**적합한 경우**: 넓은 범위를 훑어야 하고, 그 과정의 파일 덤프가 메인 컨텍스트를 오염시키는 걸 원치 않을 때.

**부적합한 경우**: 대상 파일과 값이 이미 확정된 작업. 저장소 전체 검색은 순수한 낭비입니다.

#### 서브에이전트의 컨텍스트 격리 (매우 중요)

서브에이전트는 **메인 대화의 히스토리를 물려받지 않습니다.** 독립된 컨텍스트에서 새로 시작합니다. 이건 버그가 아니라 설계 의도입니다 — 메인 컨텍스트를 아끼기 위한 것입니다.

따라서 아래와 같은 스킬 본문은 실패합니다.

```markdown
<!-- .claude/skills/migration-plan/SKILL.md -->
---
name: migration-plan
description: 결제 서비스 마이그레이션 계획을 작성한다
---

우리가 앞서 논의했던 방식대로 결제 서비스를 옮기는 계획을 세워라.
```

"우리가 앞서 논의했던(we discussed)"은 메인 대화에만 존재합니다. 서브에이전트는 그 대화를 본 적이 없으므로, 참조할 게 없어 **일반론적이고 쓸모없는 계획**을 내놓습니다.

**올바른 작성법**: 필요한 구체적 정보를 스킬 본문 안에 직접 다 적거나, 파일 경로로 명시해 서브에이전트가 스스로 읽게 합니다.

```markdown
결제 서비스를 모놀리스에서 분리하는 계획을 세워라.

합의된 제약:
- Strangler Fig 패턴 사용, 빅뱅 전환 금지
- 기존 `/api/v1/billing/*` 엔드포인트는 6개월간 프록시로 유지
- 데이터는 이중 쓰기(dual-write) 후 검증 → 읽기 전환 순서
- 상세 현황은 `docs/billing-architecture.md` 를 읽고 반영할 것
```

참고로, 서브에이전트가 결과 텍스트를 메인 대화로 반환하지 못한다는 건 사실이 아닙니다. 정상적으로 반환합니다. 그리고 `arguments` 같은 필드가 없다고 본문이 무시되지도 않습니다.

## 4. 설정 파일과 경로: 개인 범위 vs 프로젝트 범위

Claude Code에서 **파일이 어디 있느냐가 곧 그 설정의 적용 범위**입니다. 이게 이 주제의 핵심 감각입니다.

### 4.1 두 개의 `.claude` 디렉터리

| 위치 | 의미 | Git에 들어가나? |
|---|---|---|
| `~/.claude/` (홈 디렉터리) | **개인(personal) 범위**. 그 컴퓨터의 그 사용자에게만 적용 | ❌ 저장소 밖이라 아예 대상이 아님 |
| `<프로젝트>/.claude/` | **프로젝트(project) 범위**. 저장소를 받은 모두에게 적용 | ✅ 커밋하면 팀 전체 공유 |

`~`는 홈 디렉터리를 뜻합니다 (Linux/macOS는 `/Users/이름`, Windows는 `C:\Users\이름`).

이 구분에서 자주 나오는 두 가지 상황:

**상황 A — 팀과 공유하려던 게 공유되지 않는다.**
개발자가 `/lint-report` 슬래시 명령어를 만들었는데, 본인은 잘 되고 팀원은 "그런 명령어 없다"고 합니다. 확인해 보니 그 파일은 어떤 커밋에도 스테이징된 적이 없습니다.

원인: 파일을 `~/.claude/commands/lint-report.md`에 만든 것입니다. 이 경로는 **저장소 바깥**이므로 `git status`에도 잡히지 않고, `git add`도 되지 않고, 당연히 팀원이 pull해도 오지 않습니다.

해결: `<프로젝트>/.claude/commands/lint-report.md`(또는 스킬 구조)에 두고 커밋합니다.

(참고: CI 파이프라인이 돌아야 슬래시 명령어가 활성화된다거나, 새 명령어를 인식하려면 컴퓨터를 재부팅해야 한다거나, 스킬 공유에 엔터프라이즈 라이선스가 필요하다는 것은 전부 사실이 아닙니다.)

**상황 B — 나만 쓰고 싶은데 팀에 노출된다.**
개발자가 자기 스탠드업 노트를 정리하는 `/my-standup` 명령어를 만들고 싶은데, 팀원의 `/` 메뉴에 뜨거나 PR에 파일이 올라가는 건 원치 않습니다.

해결: `~/.claude/skills/my-standup/SKILL.md`에 만듭니다. 홈 디렉터리이므로 Git이 추적하지 않고, 본인 환경에서만 `/my-standup`으로 호출됩니다.

여기서 두 가지 흔한 오해:
- `.claude/commands/_my-standup.md`처럼 **파일명 앞에 밑줄을 붙이면 무시된다** → 그런 규칙은 없습니다. 프로젝트 폴더에 있는 이상 Git에 잡히고 PR에 올라갑니다.
- 프로젝트에 넣고 "PR 리뷰어에게 이 파일은 무시해 달라고 부탁" → 규율에 의존하는 방식이라 언제든 깨집니다. 경로로 해결하는 게 옳습니다.

### 4.2 커스텀 명령어 vs 스킬 (`commands/` vs `skills/`)

두 가지 형태가 있습니다.

**`commands/` 형태 — 파일 하나**
```
~/.claude/commands/my-standup.md      → /my-standup 으로 호출
.claude/commands/lint-report.md        → /lint-report 으로 호출
```
파일 이름이 곧 명령어 이름입니다. 초기부터 있던 방식입니다.

**`skills/` 형태 — 디렉터리 + SKILL.md** (현재 권장 구조)
```
~/.claude/skills/my-standup/SKILL.md
.claude/skills/migration-plan/SKILL.md
```
`SKILL.md`는 프론트매터(아래 4.4 참고)로 이름과 설명을 선언하고, 본문에 지시사항을 씁니다. 디렉터리 형태이므로 참조 문서·스크립트 같은 부속 파일을 함께 담을 수 있고, 설명을 근거로 상황에 맞게 자동 호출되기도 합니다.

`commands/`도 여전히 동작하지만, Anthropic의 현재 모범 사례는 **`skills/` 아래 `SKILL.md` 구조**입니다.

### 4.3 CLAUDE.md — 프로젝트 상시 컨텍스트

`CLAUDE.md`는 **프로젝트 루트에 두면 Claude Code가 세션 시작 시 자동으로 읽어 컨텍스트에 넣는** 파일입니다. 매 프롬프트에 반복해서 붙일 필요 없이 항상 적용됩니다. 로컬 실행이든 CI 실행이든 동일하게 적용됩니다.

여기에 넣기 좋은 것: 코딩 컨벤션, 빌드/테스트 명령어, 아키텍처 개요, 테스트 기준, 사용 가능한 픽스처 목록, 하지 말아야 할 것.

```markdown
# CLAUDE.md

## 테스트 기준
"가치 있는 테스트"란 **동작(behavior)을 검증**하는 테스트다.
구현 세부사항(내부 메서드 호출 횟수, 프라이빗 필드 값)을 단언하지 마라.
리팩터링만으로 깨지는 테스트는 가치가 없다.

## 이미 존재하는 픽스처 (tests/helpers/)
- `makeUser(overrides)` — 기본 사용자 객체
- `mockClock(iso)`  — 시간 고정
- `seedOrders(n)`   — 주문 n건 시드
새 픽스처를 만들기 전에 위 목록을 먼저 확인하라.

## 명령어
- 테스트: `npm test`
- 린트:  `npm run lint`
```

**왜 여기여야 하는가** — 대안들의 문제:
- PR 템플릿에 적어 기여자가 매번 손으로 타이핑 → 자동화의 반대이고 사람이 빠뜨립니다.
- `--append-system-prompt` 값을 CI 러너의 셸 프로필에 하드코딩 → 설정이 코드베이스 밖으로 나가 버전 관리가 안 되고, 로컬 개발 환경과 규칙이 달라집니다. (`--append-system-prompt`는 시스템 프롬프트에 텍스트를 덧붙이는 CLI 옵션으로, 기능 자체는 존재하지만 지속적 규칙의 보관 장소로는 부적절합니다.)
- GitHub Actions YAML에 긴 프롬프트 문자열을 각 잡마다 복붙 → 중복이 생기고 유지보수가 지옥이 됩니다.

**`CLAUDE.local.md` — 개인용 프로젝트 컨텍스트**

같은 프로젝트 안이지만 나만 쓰고 싶은 내용(개인 샌드박스 DB URL, 내가 선호하는 테스트 픽스처, 로컬 포트 번호 등)은 `CLAUDE.local.md`에 씁니다. 프로젝트 루트에 두면 `CLAUDE.md`와 함께 자동 로드되지만, **직접 `.gitignore`(또는 `.git/info/exclude`, 전역 git excludes)에 등록해서** 커밋되지 않게 해야 합니다.

```bash
# .gitignore
CLAUDE.local.md
```

주의할 오해들:
- Claude Code가 커밋 전에 개인 정보를 자동으로 걸러 주지 않습니다. 공유 `CLAUDE.md`에 DB URL을 적으면 그대로 저장소에 올라갑니다.
- `.claude/settings.local.json`은 **권한·CLI 설정을 담는 JSON**이지, 프롬프트용 서술 문서가 아닙니다. 그리고 이 파일이 자동으로 전역 git excludes에 등록되는 것도 아닙니다.
- `~/.claude/CLAUDE.md`는 **모든 프로젝트에 공통 적용**되는 전역 파일입니다. "특정 저장소에서 작업할 때만"이라는 요건에는 맞지 않습니다.

세 단계를 정리하면:

| 파일 | 범위 | 공유 |
|---|---|---|
| `~/.claude/CLAUDE.md` | 내 모든 프로젝트 | 나만 |
| `<프로젝트>/CLAUDE.md` | 이 프로젝트 | 팀 전체 (커밋) |
| `<프로젝트>/CLAUDE.local.md` | 이 프로젝트 | 나만 (gitignore) |

### 4.4 `.claude/rules/` — 규칙 파일

`.claude/rules/` 디렉터리에 `.md` 파일을 두면 Claude Code가 자동으로 발견해 규칙으로 로드합니다. `CLAUDE.md` 하나에 모든 걸 몰아넣는 대신 주제별로 쪼갤 수 있습니다.

**재귀적 탐색(recursive discovery)**: `.claude/rules/` **아래의 모든 `.md` 파일이 하위 디렉터리 깊이에 상관없이 재귀적으로** 탐색됩니다. 따라서 모노레포에서 이렇게 정리해도 전부 정상 로드됩니다.

```
.claude/rules/
├── security.md
├── frontend/
│   └── react.md
└── backend/
    └── api.md
```

(오해 정리: 최상위만 스캔한다거나, 하위 디렉터리가 스킬·명령어 전용으로 예약돼 있다는 건 사실이 아닙니다. 스킬과 명령어는 각각 `.claude/skills/`, `.claude/commands/`라는 **별개의 디렉터리**를 씁니다. 또 하위 디렉터리에 있다고 프론트매터가 무시되지도 않습니다.)

#### 프론트매터(frontmatter)와 경로 범위 규칙(path-scoped rules)

**프론트매터**란 마크다운 파일 맨 앞에 `---` 로 감싼 YAML 메타데이터 블록입니다.

```markdown
---
paths:
  - "src/handlers/**/*.go"
---

이 디렉터리의 HTTP 핸들러를 수정할 때는 반드시:
- 모든 에러 경로에서 request ID를 로깅할 것
- 인증 미들웨어를 우회하지 말 것
```

`paths:`가 있는 규칙을 **경로 범위 규칙(path-scoped rule)**이라 부릅니다. 해당 글롭 패턴에 맞는 파일을 다룰 때만 규칙이 발동(trigger)합니다. 관련 없는 규칙이 항상 컨텍스트를 차지하는 걸 막아 줍니다.

**글롭(glob) 패턴 읽는 법**
- `*` — 이름의 임의 문자열 (디렉터리 구분자 `/`는 넘지 않음)
- `**` — 임의 깊이의 디렉터리
- `src/handlers/**/*.go` — `src/handlers/` 아래 **어느 깊이든** 있는 모든 `.go` 파일. 예: `src/handlers/middleware/auth.go` ✅

경로는 **프로젝트 루트 기준 상대 경로**로 씁니다.

### 4.5 심볼릭 링크(symlink)와 경로 해석

**심볼릭 링크**란 "다른 경로를 가리키는 바로가기" 형태의 파일 시스템 항목입니다.

```bash
ln -s /Users/eng/code/service /workspace/service
```
이제 `/workspace/service/...`로 접근하면 실제로는 `/Users/eng/code/service/...`에 닿습니다. 실제 경로를 **정규 경로(canonical path)**라고 부릅니다.

**용법 1 — 규칙의 단일 원본(Single Source of Truth) 만들기**

조직이 저장소 10개를 운영하는데, 인증 코드를 건드릴 때 적용할 보안 검토 체크리스트를 모든 저장소에서 동일하게 지켜야 한다고 합시다. 복붙 없이, 중앙 원본 하나만 고치면 전부 반영되게 하고 싶습니다.

**해법: 중앙 공유 위치에 규칙 파일 원본을 두고, 각 저장소의 `.claude/rules/` 안에 그 원본을 가리키는 심볼릭 링크를 만듭니다.**

```bash
# 중앙 원본
/opt/org-standards/security-review.md

# 각 저장소에서
ln -s /opt/org-standards/security-review.md repo1/.claude/rules/security-review.md
ln -s /opt/org-standards/security-review.md repo2/.claude/rules/security-review.md
# ... 10개 반복
```

Claude Code는 심볼릭 링크를 정상적으로 따라가 로드하므로, 중앙 파일 한 번 수정하면 10개 저장소에 **즉시** 반영됩니다. 이것이 진짜 Single Source of Truth입니다.

비교 — 왜 다른 방법이 못한가:
- **야간 스케줄로 파일을 각 저장소에 복사·커밋** → 매일 밤 의미 없는 커밋이 10개씩 쌓이고, 수정이 최대 하루 늦게 반영됩니다.
- **`managed-settings.json`의 `claudeMd` 키에 넣되 보안팀 머신에만 배포** → `managed-settings.json`은 조직이 중앙에서 정책을 강제 배포하는 관리형 설정 파일이지만, 실제로 코드를 고치는 나머지 엔지니어들에게 배포되지 않으면 목적 자체가 달성되지 않습니다.
- **10개 `CLAUDE.md`에 복붙하고 사람이 갱신** → "복붙 없이", "자동 동기화" 요건에 정면으로 위배됩니다. 시간이 지나면 반드시 내용이 갈라집니다(drift).

**용법 2 — 심볼릭 경로에서 실행해도 규칙이 발동하는가**

실제 저장소는 `/Users/eng/code/service`이고 `/workspace/service`로 심볼릭 링크되어 있으며, 그 링크 경로에서 Claude Code를 실행했다고 합시다. 규칙에는 `paths: ["src/handlers/**/*.go"]`가 있고, `/workspace/service/src/handlers/middleware/auth.go`를 수정합니다.

→ **규칙은 정상 발동합니다.** Claude Code는 프로젝트 루트 기준 상대 경로(`src/handlers/middleware/auth.go`)를 올바르게 계산하며, 직접 경로뿐 아니라 심볼릭 링크를 경유해 도달한 파일도 매칭합니다.

(오해 정리: OS가 반환하는 정규 경로로만 평가해서 심볼릭 링크 시 절대 발동하지 않는다거나, 읽기 작업과 쓰기 작업에 별도의 규칙 세트가 적용된다거나, 심볼릭 루트를 위해 절대 경로 패턴을 따로 추가해야 한다거나 — 전부 사실이 아닙니다. 상대 경로 패턴 하나면 충분합니다.)

## 5. CLI 사용법 — 비대화형 실행, 파이프, 도구 권한

### 5.1 `-p` (print) 모드 — 비대화형 실행

`claude -p "프롬프트"`는 대화형 화면 없이 한 번 실행하고 결과를 표준 출력으로 뱉고 종료합니다. 스크립트, CI 파이프라인, npm 스크립트에서 쓰는 형태입니다.

```bash
claude -p "이 저장소의 CHANGELOG를 최신 커밋 기준으로 갱신해줘"
```

### 5.2 stdin 파이프로 데이터 넣기

셸의 파이프(`|`)로 앞 명령의 출력을 Claude의 **표준 입력(stdin)**에 넣을 수 있습니다.

```bash
git diff main | claude -p "너는 오타 린터다. 오타만 지적해라."
cat build-error.txt | claude -p "근본 원인을 설명해라" > output.txt
```

이 방식의 장점은 Claude가 파일을 읽으러 **도구를 호출할 필요가 없다**는 점입니다. 내용이 이미 프롬프트에 들어와 있으니까요. 그리고 파이프와 리다이렉션은 OS 셸의 표준 기능이라 `-p`와 문제없이 함께 동작합니다.

**stdin 10MB 상한(cap)**

Claude Code CLI는 파이프로 들어오는 stdin 크기에 **10MB 상한**을 둡니다. 메모리 폭주와 프롬프트 토큰 오버플로를 막기 위한 안전장치입니다. 입력이 10MB를 넘으면 처리하지 않고 **에러와 함께 즉시 종료**합니다.

그래서 평소엔 잘 되던 빌드 로그 파이프가, 유난히 장황한 실패가 난 날에만 갑자기 아무 설명도 없이 즉시 죽는 현상이 생깁니다. 원인은 인코딩도, 리다이렉션 연산자도 아니고 **크기**입니다.

대처:
```bash
# 뒤쪽 2000줄만 보내기
tail -n 2000 build-error.txt | claude -p "근본 원인을 설명해라"

# 에러 라인만 추려서 보내기
grep -E "ERROR|FAILED|Exception" build-error.txt | head -500 | claude -p "..."
```

부수적으로 알아둘 것:
- 일반 텍스트 파이프 입력은 별도 옵션 없이 기본으로 받아들여집니다. `--input-format stream-json`을 반드시 설정해야 하는 게 아닙니다. (`--input-format`은 구조화된 JSON 이벤트 스트림을 입력으로 줄 때 쓰는 옵션입니다.)
- 인코딩 문제만으로 `-p` 모드가 무조건 즉시 강제 종료되지는 않습니다.

### 5.3 출력 형식 — `--output-format`

`--output-format stream-json`은 결과를 사람이 읽는 텍스트 대신 구조화된 JSON 이벤트 스트림으로 내보냅니다. 프로그램이 진행 상황을 파싱해야 할 때 유용합니다. 다만 이건 **후처리 도구**이지, 모델이 애초에 더 좋은 출력을 내게 만드는 수단이 아닙니다.

### 5.4 도구 권한 제어 — `--disallowedTools` / `--allowedTools`

기본적으로 Claude Code는 여러 도구에 접근할 수 있고, 여기엔 셸 명령을 실행하는 **Bash 도구**가 포함됩니다. 신뢰할 수 없는 입력(예: 외부 기여자의 diff)을 다루는 자동화 단계에서는 이걸 아예 막고 싶을 수 있습니다.

**확실한 방법은 CLI 플래그로 명시적으로 차단하는 것입니다.**

```bash
git diff main | claude -p "너는 오타 린터다..." --disallowedTools Bash
```

- `--disallowedTools <도구...>` — 지정한 도구 사용을 금지 (블랙리스트)
- `--allowedTools <도구...>` — 지정한 도구만 허용 (화이트리스트, 더 엄격)

이 플래그는 CLI 인자이므로 Windows 러너든 Linux 러너든 동일하게 동작합니다. 즉 **이식성(portability)**도 만족합니다.

**반드시 구분해야 할 오해들:**

| 잘못된 생각 | 왜 틀렸나 |
|---|---|
| npm 스크립트를 경유해 실행하면 도구 접근이 차단된다 | npm은 그저 자식 프로세스를 띄울 뿐입니다. 자식으로 실행된 `claude` 프로세스의 내부 도구 권한은 그대로입니다. |
| stdin으로 파이프했으니 Bash 권한이 필요 없다 → 안전하다 | "필요 없다"와 "쓸 수 없다"는 다릅니다. diff를 읽는 데는 Bash가 안 필요하지만, Bash 도구 자체는 여전히 **활성 상태**입니다. 모델이 다른 이유로 호출할 수 있습니다. |
| 프롬프트에 "Bash 쓰지 마"라고 적으면 된다 | 자연어 지시는 **가이드**일 뿐 강제가 아닙니다. 프롬프트 인젝션이나 모델의 판단으로 무시될 수 있습니다. 보안 경계는 시스템 수준(플래그·권한)에서 세워야 합니다. |

**핵심 원칙**: *"필요 없어서 안 쓴다"는 보안이 아니다. "쓸 수 없게 막았다"가 보안이다.*

### 5.5 기타 CLI 옵션

- `--max-budget-usd` — 한 작업이 쓸 수 있는 비용 상한. 폭주를 막는 안전장치이지, 품질을 올리는 수단이 아닙니다. 올린다고 중복 출력이 줄지 않습니다(오히려 늡니다).
- `--no-session-persistence` — 실행 간에 세션 기록을 남기지 않음. 로컬 파일을 인식시키는 것과는 무관합니다.
- `--append-system-prompt` — 시스템 프롬프트 뒤에 텍스트를 덧붙임. 일회성 조정에는 쓸 만하지만, 지속적 프로젝트 규칙은 `CLAUDE.md`에 두는 게 맞습니다.

## 6. 전체 지도 — 어디에 무엇을 둘 것인가

```
~/                                       # 홈 (Git 밖, 나만)
└── .claude/
    ├── CLAUDE.md                        # 내 모든 프로젝트 공통 지침
    ├── commands/my-standup.md           # 개인 명령어 (레거시 구조)
    ├── skills/my-standup/SKILL.md       # 개인 스킬 ★현재 권장
    └── settings.json                    # 개인 CLI 설정

<프로젝트 루트>/                          # Git 안
├── CLAUDE.md                            # 팀 공유 프로젝트 지침 (커밋)
├── CLAUDE.local.md                      # 개인용 프로젝트 지침 (.gitignore)
├── .gitignore
└── .claude/
    ├── rules/                           # 재귀 탐색됨
    │   ├── security-review.md           # → 중앙 원본으로 symlink 가능
    │   ├── frontend/react.md
    │   └── backend/api.md
    ├── commands/lint-report.md          # 팀 공유 명령어 (커밋)
    ├── skills/migration-plan/SKILL.md   # 팀 공유 스킬 (커밋)
    └── settings.local.json              # 개인 권한/CLI 설정 (JSON)
```

의사결정 요령:
- **팀 전체가 써야 하나?** → 프로젝트 `.claude/` 안에 두고 커밋.
- **나만 써야 하나?** → `~/.claude/` (또는 프로젝트 안 + gitignore).
- **여러 저장소에 걸쳐 동일해야 하나?** → 중앙 원본 + 각 저장소에 symlink.
- **특정 파일 종류에만 적용해야 하나?** → `.claude/rules/`에 `paths:` 프론트매터.
- **문서형 지침인가, 권한/CLI 설정인가?** → 전자는 `.md`, 후자는 `settings*.json`.

## 7. 용어 사전 (Glossary)

| 영어 용어 | 한국어 설명 |
|---|---|
| **Context / Context window** | 모델이 한 번에 볼 수 있는 텍스트 작업 공간. 여기 안 들어간 정보는 모델에게 없는 것과 같다. |
| **Prompt** | 모델에게 주는 지시문 및 입력 전체. |
| **System prompt** | 대화 전체에 걸쳐 적용되는 상위 지시문. `--append-system-prompt`로 덧붙일 수 있다. |
| **Few-shot prompting** | 원하는 입력→출력 예시 2~3개를 프롬프트에 넣어, 추상적 지시("간결하게") 대신 구체적 패턴으로 형식을 고정하는 기법. |
| **Stop sequence** | 이 문자열이 생성되면 즉시 출력을 중단하라고 지정하는 파라미터. 포맷 경계용이며 길이 제어용으로는 부적절하다. |
| **Hallucination** | 근거 없이 그럴듯한 내용을 지어내는 현상. 구체적 로그 없이 추측을 시키면 발생하기 쉽다. |
| **Iteration** | 요청 → 생성 → 검증 → 피드백 → 재수정의 반복 작업 사이클. |
| **Test suite** | 한 프로젝트의 테스트 모음. 수정 후에는 개별 테스트가 아니라 전체를 다시 돌려 회귀를 확인한다. |
| **Regression (회귀)** | 고친 것이 다른 멀쩡하던 기능을 깨뜨리는 현상. |
| **Off-by-one error** | 반복문 경계에서 한 칸 어긋나는 고전적 버그(`<` vs `<=`). |
| **Null check** | 값이 없을 수 있는 필드를 접근 전에 검사하는 것. 빠뜨리면 런타임 크래시. |
| **Flaky test** | 코드 변경 없이도 성공/실패가 오락가락하는 불안정한 테스트. |
| **Idempotency key** | 같은 요청의 중복 처리를 막기 위해 요청마다 붙이는 고유 식별자. |
| **Dedup window** | 멱등성 키를 보관하는 유효 기간. 만료되면 키가 해제된다. |
| **Logical grouping** | 피드백을 전달할 때, 같은 로직에서 나온 실패는 묶고 무관한 실패는 분리하는 원칙. |
| **Direct execution** | 계획 단계 없이 Claude가 곧바로 편집을 수행하는 방식. 완전히 명세된 작업에 적합. |
| **Plan mode** | Claude가 먼저 설계안을 제시하고 승인받은 뒤 실행하는 모드. 접근 방식이 불확실할 때 사용. |
| **Subagent** | 메인 대화가 위임한 작업을 별도 컨텍스트에서 수행하는 하위 Claude 인스턴스. |
| **Explore subagent** | 저장소 전역 탐색·검색 전용 서브에이전트. 결론만 요약해 돌려준다. |
| **Context isolation** | 서브에이전트가 메인 대화 히스토리를 물려받지 않는 성질. 스킬 본문에 "앞서 논의한 대로" 같은 참조를 쓰면 안 되는 이유. |
| **Non-interactive** | 사람의 중간 승인 없이 실행되는 방식(CI 등). `-p` 모드가 여기 해당. |
| **`-p` / print mode** | 대화형 UI 없이 한 번 실행하고 결과를 출력한 뒤 종료하는 CLI 모드. |
| **stdin** | 표준 입력. 파이프(`|`)로 앞 명령의 출력을 Claude에게 전달할 때 쓰인다. |
| **10MB stdin cap** | 파이프 입력 크기 상한. 초과 시 처리 없이 에러와 함께 즉시 종료된다. |
| **`--input-format stream-json`** | 구조화된 JSON 이벤트를 입력으로 받는 옵션. 일반 텍스트 파이프에는 필요 없다. |
| **`--output-format stream-json`** | 결과를 JSON 이벤트 스트림으로 출력하는 옵션. 프로그램 파싱용. |
| **`--allowedTools` / `--disallowedTools`** | 사용 가능/금지 도구를 명시적으로 지정하는 CLI 플래그. Bash 차단의 확실한 방법. |
| **Bash tool** | Claude가 셸 명령을 실행하는 도구. 기본 활성이며, 막으려면 명시적으로 차단해야 한다. |
| **`--max-budget-usd`** | 작업당 비용 상한. 안전장치이지 품질 향상 수단이 아니다. |
| **`--no-session-persistence`** | 실행 간 세션 기록을 남기지 않는 옵션. |
| **CLAUDE.md** | 프로젝트 루트에 두면 자동 로드되는 프로젝트 상시 지침 문서. 커밋해 팀 공유. |
| **CLAUDE.local.md** | 같은 프로젝트의 개인 전용 지침 문서. `.gitignore`에 직접 등록해야 한다. |
| **`~/.claude/`** | 홈 디렉터리의 개인 설정 범위. Git 저장소 밖이라 커밋 대상이 아니다. |
| **`.claude/`** | 프로젝트 안의 설정 범위. 커밋하면 팀 전체에 공유된다. |
| **`.claude/rules/`** | 규칙 `.md` 파일 디렉터리. 하위 폴더까지 **재귀적으로** 탐색된다. |
| **Frontmatter** | 마크다운 맨 앞에 `---`로 감싼 YAML 메타데이터 블록. |
| **Path-scoped rule** | `paths:` 프론트매터로 특정 파일 패턴에만 적용되도록 범위를 제한한 규칙. |
| **Glob pattern** | `*`, `**` 등을 쓰는 파일 경로 매칭 문법. `src/**/*.go` 등. 프로젝트 루트 기준 상대 경로로 쓴다. |
| **`.claude/commands/`** | 슬래시 명령어 파일(`이름.md`) 디렉터리. 초기 방식. |
| **`.claude/skills/<name>/SKILL.md`** | 현재 권장되는 스킬 구조. 디렉터리 형태라 부속 파일을 함께 담을 수 있다. |
| **Slash command** | `/이름` 형태로 호출하는 커스텀 명령. |
| **`settings.local.json`** | 권한·CLI 설정을 담는 개인용 JSON 파일. 서술형 지침 문서가 아니다. |
| **`managed-settings.json`** | 조직이 중앙에서 정책을 강제 배포하는 관리형 설정 파일. 배포 대상 범위가 곧 적용 범위다. |
| **Symlink (심볼릭 링크)** | 다른 경로를 가리키는 파일 시스템 바로가기. `ln -s 원본 링크`. Claude Code는 이를 따라 규칙을 정상 로드한다. |
| **Canonical path** | 심볼릭 링크를 모두 풀어낸 실제 파일 시스템 경로. |
| **Single Source of Truth** | 어떤 정보의 원본이 오직 한 곳에만 존재하는 상태. 복사본이 갈라지는(drift) 문제를 원천 차단한다. |
| **Monorepo** | 여러 프로젝트를 하나의 저장소에서 관리하는 방식. 규칙을 하위 폴더로 분류할 필요가 큰 환경. |
| **CI pipeline** | 커밋마다 자동으로 빌드·테스트·검사를 수행하는 자동화 파이프라인. |
