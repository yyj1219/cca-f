# 시나리오6_생산성도구

## 질문 1

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : Mid-task, the agent hits a legacy database migration decision it cannot resolve autonomously and must escalate to a senior engineer. Engineers receiving escalations have no access to the agent's session transcript. What should the escalation contain?

**A(정답).** Include a structured summary of the affected modules, the analysis completed so far, the blocking question, and a recommended next step.

**설명**

이 답이 정답인 이유는, 인수받는 엔지니어에게 대화 기록이 없으므로 인계 내용 자체로 완결되어야 하기 때문이다. 구조화된 요약은 조사의 현재 상태, 발견 사항, 필요한 구체적 결정, 그리고 권장 조치를 전달하므로 엔지니어가 에이전트의 작업을 다시 하지 않고도 행동할 수 있다.

**B.** Include an urgency rating and an estimate of the task's remaining complexity, so the engineer can slot the escalation into their workload.

**설명**

우선순위 메타데이터는 일정 조율에는 도움이 되지만 조사의 실제 상태에 대해서는 아무것도 전달하지 못한다. 발견 사항, 막힌 지점, 권장 조치가 없으면 엔지니어는 여전히 처음부터 다시 시작해야 한다.

**C.** Send only the original task description, so the engineer investigates from scratch without being anchored by the agent's earlier conclusions.

**설명**

이는 편향 없는 시각을 확보한다는 명목으로 완료된 조사 전체를 버리는 것이며, 엔지니어가 몇 시간의 탐색을 반복하게 만든다. 인계는 발견 사항을 이어가야 하며 버려서는 안 된다.

**D.** Send the complete raw output of every Read, Grep, and Bash call the agent executed, so the engineer has all the evidence gathered.

**설명**

이는 사건의 상태가 아니라 가공되지 않은 잡음을 전달하는 것이다. 엔지니어는 장황한 도구 출력에서 분석을 다시 도출해야 하는데, 이는 애초에 에이전트가 조사를 수행한 목적을 무색하게 만든다.

### 전반적인 설명

에이전트가 대화 기록을 볼 수 없는 사람에게 작업을 에스컬레이션할 때, 인계 자체가 조사 상태를 보존할 수 있는 유일한 통로다. 구조화된 인계 요약은 정확히 이를 위해 존재한다. 즉 식별 맥락(어떤 모듈과 시스템이 관련되는지), 지금까지 축적된 근본 원인 분석 또는 발견 사항, 에스컬레이션을 유발한 구체적 결정이나 차단 요소, 그리고 에이전트의 권장 조치를 담아야 한다. 그러면 인수받는 엔지니어는 에이전트가 수십 번의 도구 호출로 수행했을 조사를 다시 실행하는 대신 한 번의 informed decision을 내릴 수 있다.

여기서 가져야 할 사고 모델은, 에스컬레이션이 단순한 라우팅 문제가 아니라 맥락 전달 문제라는 것이다. 에이전트의 세션 맥락(도구 결과, 추론, 중간 결론)은 세션 밖에서는 보이지 않으므로, 인계 내용에 명시적으로 담기지 않은 것은 사람에게는 실질적으로 존재하지 않는 것과 같다. 이는 Claude Agent SDK에서 서브에이전트 위임을 지배하는 원리와 동일하다. 맥락은 절대 암묵적으로 전달되지 않으므로, 작업을 인계하는 쪽이 수신자에게 필요한 것을 패키징해야 한다. 원본 도구 출력을 그대로 쏟아붓는 방식은 분석 없이 증거만 전달하여 사람이 종합 작업을 다시 해야 하므로 실패한다. 원래 과제만 보내거나 우선순위 메타데이터만 보내는 방식은 반대 방향으로 실패한다. 즉 조사의 가치가 완전히 버려지고 엔지니어는 처음부터 시작하게 된다.

실무에서는 팀들이 인계를 고정된 스키마(과제 맥락, 발견 사항, 막힌 질문, 권장 사항)로 정의하여 에스컬레이션이 일관되고 기계적으로 검증 가능하도록 만드는 경우가 많다. 에이전트 설계에 대한 Anthropic의 가이드는 경계 지점에서의 이러한 명시적 상태 전달을 강조한다. Building Effective Agents와 Claude Agent SDK 개요를 참고하라.

## 질문 2

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : An MCP server the agent relies on returns 40+ fields per response when only five are relevant, bloating context and confusing the model. The server is third-party and cannot be changed. Which mechanism trims each result before the model processes it?

**A.** Register a PreToolUse hook that rewrites the outgoing tool call so the server returns only the fields the agent needs.

**설명**

PreToolUse 훅은 실행 전에 발동하며 나가는 호출을 수정하거나 차단할 수 있지만 결과에는 손댈 수 없다. 항상 40개 이상의 필드를 반환하는 서드파티 서버는 요청을 어떻게 구성하든 여전히 그 필드들을 반환하므로, 장황한 응답이 필터링 없이 그대로 모델에 도달한다.

**B.** Define a separate trim_fields tool that the agent calls after each retrieval to reduce the result to relevant fields.

**설명**

이 방식은 모델이 매번 추가 도구를 호출해야 함을 기억하는 데 의존하며, 매 조회마다 루프 반복과 실패 가능성을 추가한다. 더 나쁜 점은, trimming 도구가 실행되는 시점에는 이미 장황한 결과가 맥락에 추가된 뒤이므로 맥락 과부하가 회피되지 않는다.

**C.** Add a system prompt instruction directing the agent to ignore irrelevant fields in that tool's responses when reasoning.

**설명**

프롬프트 지시는 확률적 준수만을 제공하며, 40개 필드 전체가 여전히 컨텍스트 윈도우에 들어가 토큰을 소비하고 주의를 분산시킨다. 이 지시는 모델이 잡음을 읽는 방식을 바꿀 뿐 잡음 자체를 제거하지는 못한다.

**D(정답).** Register a PostToolUse hook that intercepts the tool's result and passes only the relevant fields through to the agent.

**설명**

PostToolUse 훅은 도구가 성공적으로 완료된 후 실행되며 Claude가 보기 전에 도구 출력을 교체할 수 있다. 이는 모든 결과를 코드 수준에서 결정론적으로 변환하며, 수정할 수 없는 서드파티 MCP 도구에도 적용되고, 불필요한 필드를 맥락에서 완전히 배제한다.

### 전반적인 설명

여기서 가져야 할 사고 모델은, 도구가 반환하는 모든 것이 대화 기록에 추가되며 그 기록이 모델이 세상을 보는 유일한 통로라는 점이다. 도구가 5개만 중요한데 40개 필드를 쏟아내면, 나머지 35개는 단순히 낭비되는 토큰이 아니라 주의를 다투고 추론을 오도할 수 있다. Agent SDK의 훅 시스템은 바로 이 흐름 주변에 결정론적인 코드 수준 개입 지점을 제공하기 위해 존재한다. PreToolUse는 호출이 실행되기 전에 발동하여(나가는 요청을 차단하거나 재작성할 수 있는 지점) PostToolUse는 도구가 성공적으로 완료된 직후 발동한다(모델이 소비하기 전에 결과를 검사하고 재구성할 수 있는 지점).

이 문제에서는 PostToolUse 훅이 설계상 정답이다. 이 훅은 도구 이름, 원래 입력, 도구 응답을 받으며 hookSpecificOutput.updatedToolOutput을 반환하여 Claude가 보게 될 내용을 교체할 수 있다. 다만 교체된 내용은 도구의 출력 형태와 일치해야 한다. 훅이 모델이 아니라 여러분의 하네스에서 실행되므로, 수정할 수 없는 서드파티 MCP 서버에도 동일하게 동작하며 모델의 협조 없이도 매 호출마다 발동한다. 경계를 짚어두자면, PostToolUse는 모델이 보는 것만 바꿀 뿐 실제로 일어난 일은 바꾸지 않는다. 도구는 이미 실행되었으므로 부작용은 영향을 받지 않는다.

각 대안은 모두 개입 지점을 놓치고 있다. PreToolUse 훅은 요청을 조정하지만, 무조건 장황한 응답을 반환하는 서버는 여전히 그렇게 반환한다. 시스템 프롬프트 지시는 이미 오염된 맥락 위에 얹힌 확률적 안내에 불과하다. 전용 trimming 도구는 순서를 뒤바꾼다. 장황한 결과가 먼저 맥락에 들어간 뒤 모델이 그것을 정리해야 함을 기억해야 하므로 지연과 호출별 실패 가능성이 추가된다.

전체 이벤트 스키마와 출력 필드는 Agent SDK 훅 문서와 Claude Code 훅 레퍼런스를 참고하라.

## 질문 3

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : The agent requests a Grep search across a legacy repository, and the harness executes it successfully. What must the harness do so the model can read the search results and choose its next action?

**A.** Send the output back in a dedicated tool role message, keeping tool results separate from ordinary user and assistant content in the history.

**설명**

이 답이 틀린 이유는, Claude의 Messages API에는 별도의 tool이나 function 역할이 없기 때문이다. 도구 상호작용은 기존 구조에 통합되어 있다. tool_use 블록은 assistant 메시지에 나타나고 tool_result 블록은 user 메시지에 나타난다.

**B.** Attach the output to the Grep tool's definition metadata so the model reads it when it re-evaluates the available tools on its next pass.

**설명**

이 답이 틀린 이유는, 도구 정의는 도구의 이름, 설명, 입력 스키마를 정적으로 선언한 것이기 때문이다. 런타임 결과는 절대 정의에 저장되지 않으며, tool_result 콘텐츠 블록으로 대화 기록을 통해 전달된다.

**C.** Do nothing extra, since the API runs the requested Grep call server-side and automatically injects its output into the model's context.

**설명**

이 답이 틀린 이유는, Messages API가 클라이언트 도구를 실행하지 않기 때문이다. Claude는 stop_reason이 tool_use인 구조화된 요청만 내놓으며, 도구를 실행하고 결과를 후속 요청에 담아 반환하는 것은 호출하는 애플리케이션의 책임이다.

**D(정답).** Append a tool_result block referencing the tool_use ID in a user message and send the updated history in the next request.

**설명**

이 답이 정답인 이유는, API는 도구 실행을 결코 보지 못하기 때문이다. 하네스는 출력을 tool_use_id가 원래 요청과 일치하는 tool_result 블록으로 패키징하여 user 메시지에 넣고, 전체 대화를 다시 전송해야 한다. 이렇게 누적되는 메시지 기록을 통해서만 모델이 도구가 반환한 내용을 관찰할 수 있다.

### 전반적인 설명

여기서 가져야 할 사고 모델은, Claude는 상태를 갖지 않으며 클라이언트 도구를 절대 스스로 실행하지 않는다는 것이다. 모델이 도구가 필요하다고 판단하면, 응답은 stop_reason: "tool_use"와 함께 하나 이상의 tool_use 콘텐츠 블록을 담아 도착하며, 여기에는 id, 도구 이름, 입력 인자가 포함된다. 이 시점에서 API의 역할은 끝나며, 그 이후의 모든 것은 여러분의 하네스에 속한다.

하네스는 도구를 실행한 다음, 원래 요청의 id와 일치하는 tool_use_id를 가진 tool_result 블록을 구성하고, 이 블록을 user 메시지 안에 배치한 뒤, 갱신된 전체 대화를 다음 API 호출에서 다시 전송한다. 이렇게 누적되는 메시지 기록만이 모델이 도구가 무엇을 반환했는지 알 수 있는 유일한 통로다. ID 연결 덕분에 한 turn에서 여러 도구가 호출되었을 때도 각 결과를 올바른 요청과 짝지을 수 있다. 이 설계는 프로토콜을 단순하게 유지한다. 별도의 tool 역할도 없고(다른 제공사 API에서 넘어온 흔한 습관), 여러분의 도구를 서버 측에서 실행하는 일도 없으며, 정적 스키마로 남는 도구 정의에 런타임 데이터가 첨부되는 일도 없다.

트레이드오프는 상태에 대한 책임이 여러분의 루프에 있다는 것이다. 결과를 추가하거나 기록을 다시 전송하는 것을 잊으면, 모델은 도구가 실행되었다는 기억 자체가 없다. 전체 요청-응답 사이클은 Tool use overview와 Handle tool calls를 참고하라.

## 질문 4

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : Last week an engineer's session traced how feature flags propagate through a checkout service. A framework migration has since restructured most of the modules that session read. What is the reliable way to continue the investigation?

**A(정답).** Start a new session seeded with a structured summary of the confirmed propagation findings, leaving the outdated tool results behind.

**설명**

세션이 읽었던 파일들이 크게 재구조화되었을 때는, 신뢰할 수 있는 결론은 의도적으로 이어가고 낡은 원시 증거는 버려야 한다. 새 세션은 깨끗한 컨텍스트 윈도우로 시작하므로, 그 안에는 현재 코드베이스 상태와 상충하는 내용이 전혀 없다.

**B.** Resume the prior session and rely on Claude Code's automatic context management to have already dropped the older tool outputs.

**설명**

자동 컨텍스트 관리는 윈도우가 가득 찰 때만 오래된 도구 출력을 정리하는 오버플로 메커니즘이며, 신선도를 판단하는 장치가 아니다. 낡은 관찰 결과가 제거되었다는 보장은 없으며, 요약된 것이라 해도 이미 존재하지 않는 코드에 대한 사실을 여전히 주장하게 된다.

**C.** Resume the prior session after adding a CLAUDE.md note describing the migration so the loaded guidance corrects the stale observations.

**설명**

CLAUDE.md의 내용은 모델이 맥락 속 다른 모든 것과 함께 고려하는 안내일 뿐이며, 재개된 대화 기록이 복원하는 낡은 도구 결과를 제거하거나 다시 작성하지는 못한다. 모델은 파일이 바뀌었다는 메모와 옛 구조를 주장하는 상세한 관찰 내용을 동시에 갖게 되며, 둘 중 어느 쪽에서든 추론할 수 있다.

**D.** Fork the prior session so a new branch inherits the full investigation context while the original stays intact for reference.

**설명**

포크는 낡은 Read와 Grep 출력을 포함한 기존 기록 전체를 새 브랜치로 복사할 뿐, 증거 자체는 전혀 바꾸지 않는다. 포크는 여전히 유효한 기준선에서 서로 다른 접근을 탐색하기 위한 것이며, 더 이상 현실과 맞지 않는 기준선을 고치기 위한 것이 아니다.

### 전반적인 설명

Claude Code의 세션은 코드베이스의 스냅샷이 아니라 누적된 대화, 즉 프롬프트와 모든 도구 호출, 모든 도구 결과, 모든 응답이다. 재개는 이 기록을 그대로 재생하므로, 지난주의 Read와 Grep 출력이 기록된 그대로 맥락에 다시 들어오고, 모델은 그것들이 마이그레이션으로 이미 재구조화된 모듈을 설명하고 있다는 것을 알 방법이 없다. 모델은 윈도우 안의 다른 어떤 것과 마찬가지로 확신을 가지고 그 내용으로부터 추론할 것이다.

여기서 유용한 사고 모델은 결론과 증거를 분리하는 것이다. 전파 관련 발견 사항(결론)은 여전히 가치가 있고 이어가는 비용도 낮다. 원시 도구 결과(증거)는 이제 거짓이 되었고 기록 중 가장 부피가 큰 부분이기도 하다. 새로 시작하면 깨끗한 컨텍스트 윈도우를 확보할 수 있고, 여기에 구조화된 요약을 심으면 보존할 가치가 있는 결론만 정확히 전달된다. 즉 대화 기록을 재생하는 것이 아니라 정제된 인계를 하는 것이다.

각 대안은 저마다 방식으로 나쁜 증거를 그대로 보존한다. 포크는 낡은 출력까지 포함한 전체 기록을 새 브랜치에 복제한다. 포크는 유효한 기준선에서의 발산적 탐색을 위한 것이지 기준선을 정리하기 위한 것이 아니다. CLAUDE.md 메모는 안내를 추가하지만 상충하는 관찰 내용은 그대로 두어 모델의 주의를 다투게 한다. 자동 컨텍스트 관리를 믿는 것은 그 목적을 오해하는 것이다. Claude Code는 파일이 바뀔 때가 아니라 윈도우가 가득 찰 때 오래된 도구 출력을 정리하므로, 낡은 결과가 사라졌다는 보장은 전혀 없다. 세션 기록, 포크, 새 컨텍스트 윈도우가 어떻게 동작하는지는 Agent SDK의 Sessions와 How Claude Code works를 참고하라.

이 시나리오의 동작은 PostToolUse 출력 필드가 작동하는 방식에서 직접 비롯된다. PostToolUse 훅에서 decision: "block"을 반환하는 것은 도구 결과를 숨기거나 대체하지 않는다. 이는 훅의 사유를 원본 출력 옆에 첨부할 뿐이며, Claude는 여전히 원본을 전부 받는다. 이 설계는 문제를 표시하면서도 증거를 그대로 보이게 유지하려는 일반적인 경우에는 합리적이지만, redaction에는 잘못된 도구다. redaction의 핵심은 모델이 원본 콘텐츠를 절대 처리해서는 안 된다는 것이다.

변환을 위해 만들어진 필드는 hookSpecificOutput.updatedToolOutput이다. PostToolUse 훅이 이를 반환하면 그 교체본이 Claude가 보게 될 도구 결과가 되므로, 훅은 자격 증명을 제거하거나 잡음이 많은 필드를 다듬거나 형식을 결정론적으로 정규화할 수 있으며, 모델의 협조에 의존하지 않는다. 두 가지 경계를 새겨둘 만하다. 교체 내용은 도구의 출력 형태와 일치해야 한다(내장 도구는 일반 문자열이 아니라 구조화된 객체를 반환하므로). 그리고 PostToolUse는 부작용을 되돌릴 수 없다. 도구는 이미 실행되었고, 명령어가 실행되어 실제 출력이 생성되었기 때문에 updatedToolOutput은 오직 모델의 맥락에 들어가는 내용만 바꾼다. 행동 자체를 원천적으로 막는 것은 PreToolUse의 영역이지만, PreToolUse는 어떤 출력도 존재하기 전에 발동하므로 출력 redaction 문제를 해결할 수 없다.

아키텍트가 가져야 할 사고 모델은 다음과 같다. PreToolUse는 도구 호출이 일어나는지와 어떻게 일어나는지를 통제하고, PostToolUse는 모델이 그로부터 무엇을 알게 되는지를 통제하며, additionalContext는 보충하는 반면 updatedToolOutput은 대체한다. 민감한 값을 "무시하라"는 프롬프트 수준 지시는 가장 약한 옵션이다. 데이터가 이미 맥락에 들어와 있고 준수는 확률적이기 때문이다. Agent SDK Hooks와 Claude Code Hooks Reference를 참고하라.

**QUESTION** : During long codebase explorations, the agent often emits progress narration such as "I've located the config loaders" in the same response as its tool calls. A developer's hand-rolled loop, built directly on the Messages API, terminates whenever a response contains text, cutting investigations short. What is the correct termination design?

**A.** Terminate when a response contains a text block longer than a set threshold, since substantive narration marks a finished analysis.

**설명**

이는 개발자가 이미 가진 것과 같은 종류의 anti-pattern의 변형일 뿐이다. 즉 텍스트 콘텐츠로부터 완료를 추론하는 것이다. 모델은 작업 중간에 도구 호출과 나란히 긴 추론이나 진행 상황 서술을 흔히 만들어내므로, 길이 임계값을 두어도 조사가 여전히 조기에 종료될 것이다.

**B.** Instruct the agent to append a unique sentinel phrase when the task is complete and terminate whenever that phrase appears in the output.

**설명**

완료 신호를 위해 assistant 텍스트를 파싱하는 것은 특이한 sentinel을 쓰더라도 문서로 명시된 anti-pattern이다. 모델은 그 문구를 일관되지 않게 내놓거나 빠뜻할 수 있으며, 이는 결정론적인 구조화 필드를 확률적인 자연어 관행으로 대체하는 것이다.

**C(정답).** Keep looping while stop_reason is tool_use, treat end_turn as normal completion, and handle any other stop reason as a separate case.

**설명**

stop_reason 필드는 루프 제어를 위해 설계된 구조화 신호다. tool_use는 모델이 도구 결과를 돌려받기를 기대한다는 뜻이고, end_turn은 정상적으로 끝났다는 뜻이며, max_tokens 같은 다른 값들은 성공으로 취급하지 않고 별도로 처리해야 한다. 하나의 응답에 서술 텍스트와 tool_use 블록이 동시에 담길 수 있으므로, 콘텐츠의 존재 여부가 아니라 stop_reason을 기준으로 루프를 제어하면 조기 종료 문제가 해결된다.

**D.** Set a generous fixed iteration cap and treat reaching the cap as the completion signal for the exploration.

**설명**

반복 횟수 상한은 폭주하는 루프를 막기 위한 안전장치이지 완료 신호가 아니다. 상한에 도달했다는 것은 성공이 아니라 오류나 truncation 상태로 표면화되어야 하며, 한 조사에 맞춰 정한 상한은 더 긴 조사를 잘라내거나 더 짧은 조사에서 turn을 낭비하게 만든다.

### 전반적인 설명

Messages API 위에서 직접 만든 에이전틱 루프는 구조적으로 설계된 종료 메커니즘을 갖는다. 각 API 응답은 stop_reason을 담고 있다. tool_use인 동안은 모델이 도구를 요청하고 그 결과를 기다리고 있다는 뜻이므로, 하네스는 도구를 실행하고 결과를 대화에 추가한 뒤 모델을 다시 호출한다. end_turn이면 모델이 정상적으로 끝나 최종 답변을 내놓았다는 뜻이다. max_tokens나 stop_sequence 같은 다른 값도 도구 루프를 종료시키지만, 성공적인 완료로 취급해서는 안 되고 별도의 처리가 필요한 상태를 나타낸다. Claude Agent SDK도 관리형 루프에서 동일한 원리를 구현한다. 즉 Claude가 도구 호출이 없는 응답을 낼 때까지 도구 사용 왕복을 계속하고, 그 결과를 ResultMessage.subtype을 통해 성공과 오류 상태를 구분하여 보고한다. 두 설계 모두 assistant 텍스트의 존재, 부재, 내용은 그 판단에 전혀 관여하지 않는다.

바로 이 점이 개발자의 현재 설계를 무너뜨린다. 응답은 콘텐츠 블록들의 목록이며, 작업 중간의 응답은 텍스트 블록(진행 서술, 추론)과 tool_use 블록을 흔히 함께 담는다. 어떤 텍스트든 완료 지표로 취급하는 것, 즉 존재 여부든 길이든 sentinel 문구든, 결정론적인 프로토콜 필드를 자연어에 대한 확률적 추측으로 바꿔버리는 것이며 이는 정확히 피해야 할 anti-pattern 부류다. sentinel 문구는 모델이 바꿔 말하거나, 빠뜻하거나, 일찍 내놓을 때 실패한다. 길이 임계값은 철저한 에이전트가 작업하면서 서술을 늘어놓기 때문에 실패한다.

반복 횟수 상한은 설계에서 자리를 가질 자격이 있지만, 오직 폭주 루프에 대한 안전망으로서일 뿐 결코 주된 중단 메커니즘이 되어서는 안 된다. Agent SDK는 이 구분을 명시적으로 둔다. max_turns에 도달하면 error_max_turns라는 subtype을 가진 결과가 반환되며, 이는 성공과 구분되는 오류 상태다. 잘 만들어진 루프는 따라서 정상 완료를 위해 구조화된 신호를 확인하고, 성공이 아닌 중단 조건은 오류 처리로 라우팅하며, 상한은 실패 상황에서 비용과 지연을 제한하는 용도로만 유지한다. 표준적인 루프 생명주기와 종료 상태는 Claude Agent SDK의 The Agent Loop를 참고하라.

### 전반적인 설명

PreToolUse 훅은 완전히 다른 채널을 통해 작동한다. 이는 도구 호출이 실행되기 전에 실행되는 코드이므로, 요청된 Bash 명령어를 검사하고 백업 전제조건이 완료되었는지 확인한 뒤 호출을 차단하거나 리다이렉트할 수 있다. 모델이 무엇을 결정했든 상관없이 위반 행동은 물리적으로 일어날 수 없다.

프로덕션 설계에 적용할 사고 모델은 2단계 구조다. 선호, 스타일, 유연한 판단처럼 이따금의 이탈이 용인되고 적응력이 가치 있는 경우에는 프롬프트를 사용한다. 환불 전 신원 확인이나 파괴적인 마이그레이션 전 백업처럼 규칙에 금융적, 법적, 데이터 무결성 결과가 걸려있을 때는 훅이나 프로그래밍적 전제조건을 사용한다. 이 시나리오 자체의 증거(지시가 있음에도 에이전트가 이따금 백업을 건너뛰는 것)는 규칙이 잘못된 계층에 놓였음을 알리는 전형적인 신호다.

temperature를 제안하는 것은 흔히 빠지는 함정이므로 이해해둘 필요가 있다. temperature를 0으로 설정하면 토큰 선택은 결정론적이 되지만, 모델은 여전히 결정론적으로 규칙을 어기는 시퀀스를 만들어낼 수 있다. 준수 실패는 샘플링 잡음이 아니므로 샘플링 파라미터를 조정해서는 해결할 수 없다. PreToolUse 훅이 실행 전에 도구 호출을 가로채고 차단하는 방식은 Claude Code의 hooks 문서를 참고하라.

## 질문 11

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : Midway through an open-ended task to add tests across a legacy module, the agent discovers that many target files are build-generated from templates, invalidating part of its prioritized plan. What should the workflow do next?

**A(정답).** Regenerate the remaining subtasks based on the discovery, redirecting test work to the template sources rather than the generated files.

**설명**

이는 동적 적응형 분해의 정의적 특징이다. 하위 작업은 초기 매핑 단계 이후 고정되는 것이 아니라 중간 발견 사항을 바탕으로 생성되고 수정된다. 파일이 생성물이라는 발견은 어떤 작업이 의미가 있는지를 바꾸므로, 계획은 즉시 적응하여 템플릿을 목표로 삼아야 한다.

**B.** Pause and escalate to an engineer, since encountering conditions the initial plan did not anticipate signals the task exceeds agent scope.

**설명**

초기 계획으로부터의 이탈은 적응형 워크플로에서 예상되는 일이며, 과제가 에이전트의 범위를 넘어선다는 증거가 아니다. 예상하지 못한 발견마다 에스컬레이션하면 개방형 작업에 에이전트를 쓰는 근거인 적응성 자체가 사라진다.

**C.** Finish executing the original plan as written, then schedule a second cleanup pass to repair any work performed against generated files.

**설명**

발견으로 무효화된 계획을 계속 실행하는 것은 적응형 조사를 고정된 파이프라인처럼 다루는 것이다. 생성 파일에 대해 작성된 작업은 다음 빌드에서 덮어써질 것이므로, 이 접근은 다시 해야 할 작업에 알면서도 노력을 쏟는 것이다.

**D.** Abort the run and restart with a longer upfront mapping phase so the initial plan accounts for build-generated files this time.

**설명**

개방형 과제는 사전에 완전히 매핑될 수 없다. 생성 파일 같은 뜻밖의 상황은 정확히 동적 분해가 존재하는 이유다. 재시작은 이미 완료된 유효한 작업을 버리며, 다음 매핑 단계가 모든 조건을 예상할 수 있다는 보장도 여전히 없다.

### 전반적인 설명

고정 파이프라인과 적응형 분해의 차이는 계획이 어디에 존재하는가에 있다. 프롬프트 체이닝에서는 단계의 순서가 실행 전에 코드로 정의되며, 과제가 알려진 하위 작업들로 깔끔하게 분해될 때 잘 동작한다. 동적 적응형 분해에서는 모델 스스로 하위 작업을 생성하며, 중요한 점은 중간 결과가 도착할 때마다 계속해서 다시 생성한다는 것이다. 계획은 살아있는 산출물이다. 지형을 매핑하고, 우선순위를 정하고, 행동하고, 각 발견을 남은 작업에 다시 접어 넣는다. Anthropic의 가이드는 정확히 이 지점에서 사전에 정의된 코드 경로를 따르는 워크플로와, 도구 결과가 드러내는 바를 바탕으로 자신의 진행을 동적으로 지휘하는 에이전트를 구분한다.

목표 파일이 빌드로 생성된다는 사실을 발견하는 것은 실행 중간의 전형적인 발견 사례다. 이는 과제가 실패했거나 매핑이 부실했다는 뜻이 아니라, 에이전트가 코드를 읽기 전에는 알 수 없었던 실제 사실을 환경이 제공했다는 뜻이다. 올바른 대응은 그 사실을 계획에 접어 넣어 노력의 방향을 템플릿 소스로 재설정하는 것이다. 원래 계획을 완료하는 것은 빌드가 덮어쓸 파일에 작업을 낭비하는 것이고, 더 긴 사전 매핑 단계로 재시작하는 것은 적응형 분해가 쓰이는 이유 자체를 오해하는 것이다. 레거시 코드베이스는 어떤 단일 매핑 단계로도 잡을 수 없는 조건을 흔히 숨기고 있다. 그리고 계획에서 벗어날 때마다 에스컬레이션하는 것은 일상적인 적응을 사람의 수고로 바꿔버려, 에이전트가 제공하려는 생산성 이득을 갉아먹는다. 에스컬레이션은 정책 공백이나 되돌릴 수 없는 영향을 가진 결정과 같은 진짜 차단 요소에 쓰여야 하며, 평범한 발견에는 쓰이지 않아야 한다.

사고 모델은 이렇다. 무엇이든 실행하기 전에 단계를 미리 적어둘 수 있다면 고정 체인을 선택하고, 다음 단계가 이전 단계가 드러낸 내용에 의존한다면 적응형 분해를 선택하라. 그리고 그것이 실제로 적응하도록 두라. 워크플로 대 에이전트 구분과 그 뒤에 있는 오케스트레이션 패턴은 Anthropic의 Building Effective Agents를 참고하라.

## 질문 12

**SCENARIO** : You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

**QUESTION** : The coordinator must run three independent read-only codebase investigations plus one boilerplate-generation task that depends on all three sets of findings. How should it schedule these four subagent delegations?

**A(정답).** Emit the three investigation Task calls in one response, then delegate the generation task in a later turn with the findings included.

**설명**

이 답이 정답인 이유는, 세 조사가 독립적이고 읽기 전용이므로 하나의 코디네이터 응답에서 그 Task 호출들을 함께 내놓으면 동시에 실행될 수 있기 때문이다. 생성 작업은 그 출력에 의존하므로 이후에 위임되어야 하며, 서브에이전트는 코디네이터의 맥락을 물려받지 않으므로 발견 사항을 프롬프트에 명시적으로 전달해야 한다.

**B.** Emit all four Task calls in a single response so the investigations and the generation task all execute concurrently from the start.

**설명**

이는 의존관계를 무시한다. 생성 서브에이전트는 소비할 발견 사항 없이 시작하게 될 것이다. 서브에이전트는 격리된 맥락에서 실행되며 프롬프트에 담긴 것만 받기 때문이다. 병렬 생성은 실제로 서로 독립적인 작업에만 적합하다.

**C.** Spawn the generation subagent first and let it launch the three investigation subagents itself, consuming their results directly.

**설명**

조사들을 생성 서브에이전트 안에 중첩시키면 오케스트레이션이 코디네이터가 더 이상 관찰하거나 실패에서 복구할 수 없는 곳에 묻히게 되어 허브-스포크 패턴을 위반한다. 생성 에이전트는 여전히 세 결과를 모두 기다려야 하므로, 이는 동시성을 개선하지 않으면서 간접성만 추가한다.

**D.** Delegate each of the four tasks in its own coordinator turn so results arrive in a guaranteed, predictable order.

**설명**

완전히 순차적인 위임은 세 독립 조사에서 가능한 동시성을 희생하여 그 단계의 지연 시간을 대략 세 배로 늘린다. 순서는 의존적인 생성 단계에만 중요하며, 독립적인 작업은 직렬화한다고 해서 얻는 것이 없다.

### 전반적인 설명

Claude Agent SDK에서 병렬 서브에이전트 실행은 도구 사용 프로토콜을 통해 동작한다. 코디네이터는 stop_reason: "tool_use"인 하나의 응답에 여러 tool_use 블록을 포함시킬 수 있으며, 하네스는 이를 동시에 실행할 수 있다. 런타임은 여러 도구 호출의 실행 순서를 규정하지 않는데, 바로 이 때문에 아키텍트가 무엇을 안전하게 병렬화할 수 있는지 결정해야 한다. 문서화된 원칙은, 독립적이고 읽기 전용인 작업(코드베이스의 다른 부분을 탐색하는 것 같은)은 동시에 실행하는 것이 안전하지만, 순서나 데이터 의존성이 있는 작업은 순차적으로 스케줄링해야 한다는 것이다. 이는 여기서 올바른 형태를 제시한다. 즉 세 조사를 한 turn에서 펼쳐 실행하고, 그 결과를 모은 뒤, 생성을 위임하는 것이다.

두 번째 제약이 이 2단계 구조를 강화한다. 바로 맥락 격리다. 각 서브에이전트는 새로운 맥락에서 시작하며 프롬프트에 담긴 것만 보므로, 조사와 나란히 생성된 생성 서브에이전트는 빌드할 근거가 전혀 없을 것이다. 코디네이터가 발견 사항을 모아 생성 서브에이전트의 프롬프트에 명시적으로 포함시켜야 한다. 완전히 순차적인 위임은 안전하지만 독립적인 조사들이 허용하는 병렬성을 낭비하며, 조사를 생성 서브에이전트 안에 중첩시키는 것은 오케스트레이션을 코디네이터 밖으로 이동시켜 허브-스포크 패턴이 동작하게 만드는 가시성과 오류 처리를 희생시킨다.

현재 SDK 버전에서는 서브에이전트를 생성하는 도구의 이름이 Agent이며, Task는 호환을 위한 별칭으로 유지되고 있다는 점에 주목하라. Parallel tool use와 SDK의 Subagents를 참고하라.
