# 사전 학습 노트 — Agentic Architecture & Orchestration (21~40)

이 문서는 이 주제를 처음 접하는 사람을 위한 개념 정리입니다. 에이전트가 무엇인지부터 시작해서, 훅(Hook), MCP, 에이전트 루프, 세션, 작업 분해 패턴까지 순서대로 설명합니다. 사전 지식은 필요하지 않습니다.

---

## 0. 출발점: "에이전트"란 무엇인가

### 0.1 LLM과 에이전트의 차이

**LLM(Large Language Model, 대형 언어 모델)** 은 텍스트를 입력받아 텍스트를 출력하는 모델입니다. Claude, GPT 같은 것들이 여기에 해당합니다. LLM 자체는 파일을 읽거나, API를 호출하거나, 환불을 처리할 수 없습니다. 오직 "다음에 올 텍스트"를 확률적으로 생성할 뿐입니다.

**에이전트(Agent)** 는 LLM에 "도구(Tool)"를 붙이고, "반복 루프"를 감싼 시스템입니다.

```
사용자 요청
   ↓
LLM이 생각 → "파일을 읽어야겠다" → 도구 호출 요청
   ↓
프로그램이 실제로 파일을 읽음 → 결과를 LLM에게 돌려줌
   ↓
LLM이 결과를 보고 다시 생각 → 또 도구 호출하거나, 최종 답변
   ↓
(반복)
```

이 반복 구조를 **에이전트 루프(Agentic Loop)** 라고 부릅니다. 이 문서의 절반 정도는 이 루프를 어떻게 정확하게 구현하고 제어하느냐에 대한 이야기입니다.

### 0.2 확률적(Probabilistic) vs 결정론적(Deterministic)

이 구분이 이 주제 전체를 관통하는 가장 중요한 개념입니다.

| 구분 | 확률적 (Probabilistic) | 결정론적 (Deterministic) |
|---|---|---|
| 예시 | LLM의 텍스트 생성, 프롬프트 지시 준수 | if 문, 정규식 검사, 코드 로직 |
| 보장 수준 | "대체로" 지킨다 | 100% 지킨다 |
| 실패 원인 | 표현이 낯설거나, 지시가 복잡하거나, 공격을 당하면 어긋남 | 코드에 버그가 없으면 어긋나지 않음 |

LLM에게 "500달러 넘는 환불은 절대 승인하지 마"라고 시스템 프롬프트에 써도, 모델은 이를 **대체로** 지킬 뿐 **항상** 지키지는 않습니다. 이 차이가 보안·규정·금전 관련 규칙에서는 치명적입니다.

그래서 등장하는 것이 **훅(Hook)** 입니다.

## 1. 훅 (Hooks) — 모델 밖에서 강제되는 규칙

### 1.1 훅이란

**훅(Hook)** 은 에이전트 실행 과정의 특정 시점에 자동으로 실행되도록 등록해 두는 **코드**입니다. LLM이 만들어내는 것이 아니라, 개발자가 미리 작성해 놓은 프로그램이 실행됩니다.

핵심은 이것입니다: **훅은 모델의 생성 과정 바깥(outside of model generation)에서 동작합니다.**

이 때문에 훅으로 강제한 규칙은,
- 사용자가 이상하고 낯선 표현(unusual phrasing)으로 요청해도 우회되지 않고,
- 도구 결과 안에 숨겨진 **프롬프트 주입(Prompt Injection)** 공격으로도 우회되지 않으며,
- 모델이 복잡한 지시를 단순히 잘못 적용(misapply)해도 뚫리지 않습니다.

> **프롬프트 주입(Prompt Injection)**: 외부 데이터(웹페이지 내용, 도구 반환값, 사용자 입력 등) 안에 "이전 지시를 무시하고 ~하라" 같은 악의적 문장을 심어두어, LLM이 그것을 개발자의 지시로 착각하게 만드는 공격. LLM은 지시와 데이터를 근본적으로 구분하지 못하기 때문에 프롬프트만으로는 완전히 막을 수 없습니다.

### 1.2 왜 "프롬프트를 더 강하게 쓰는 것"으로는 부족한가

흔한 오해들을 정리하면:

- **"같은 규칙을 3번 반복해서 쓰면 되지 않나?"** → 눈에 더 잘 띄게(salient) 만들어 위반 확률을 낮출 수는 있지만 0으로 만들지는 못합니다. 확률적 시스템은 반복 강조로 결정론이 되지 않습니다.
- **"temperature를 0.1로 낮추면 되지 않나?"** → `temperature`는 생성의 무작위성(randomness)을 줄이는 파라미터입니다. 출력이 더 일관되게는 되지만, 모델이 지시를 애초에 **잘못 해석**하고 있다면 그 잘못된 해석을 더 일관되게 반복할 뿐입니다. 근본 원인을 고치지 못합니다.
- **"프롬프트에는 금액 같은 숫자를 쓸 수 없나?"** → 그렇지 않습니다. 시스템 프롬프트에 달러 임계값이나 어떤 숫자든 자유롭게 쓸 수 있습니다. 훅을 쓰는 이유는 "숫자를 쓸 수 없어서"가 아니라 "프롬프트는 강제력이 없어서"입니다.
- **"훅이 프롬프트보다 쓰기 빠르니까?"** → 아닙니다. 훅은 오히려 조건 로직을 코드로 정확히 구현해야 하므로 더 엄밀한 작업입니다. 훅의 가치는 속도가 아니라 **보장성**입니다.

### 1.3 훅의 종류와 실행 시점

에이전트 루프의 흐름 위에 훅이 어디에 붙는지 보면 이해가 쉽습니다.

```
모델이 도구 호출 요청 생성
        ↓
   [ PreToolUse 훅 ]   ← 도구가 실행되기 "전". 입력(tool_input)을 보고 허용/거부/수정
        ↓
   실제 도구 실행 (MCP 서버 호출, 파일 읽기 등)
        ↓
   [ PostToolUse 훅 ]  ← 도구가 실행된 "후", 결과가 모델에게 가기 "전". 출력을 보고 가공
        ↓
   모델이 결과를 받아 다음 판단
```

이 외에 **Notification 훅** 같은 관찰(observability) 목적의 훅도 있습니다. 이것은 알림·로깅·모니터링용이며, 모델이 실제로 수신하는 도구 결과를 치환하는 표준적인 수단은 아닙니다.

### 1.4 PreToolUse 훅

**언제 쓰는가**: 도구가 실행되기 전에 막아야 할 때, 또는 도구에 전달될 인자를 고쳐야 할 때.

**받는 것**: `tool_input` — 모델이 그 도구에 넘기려는 인자 객체. 예를 들어 `refund_customer` 도구라면 `tool_input.amount`, `tool_input.customer_id` 같은 필드가 들어 있습니다.

**반환하는 것**: `permissionDecision` 값.

| 값 | 의미 | 사용 상황 |
|---|---|---|
| `"allow"` | 도구 실행을 허용 | 검증 통과 |
| `"deny"` | 도구 실행을 차단. 이유(reason)를 함께 전달 | 정책 위반. 실행 자체가 일어나지 않음 |
| `"ask"` | 사람에게 물어봄 (승인 프롬프트) | 사람의 판단이 실제로 필요한 경우 |

`"deny"`를 반환하면 도구는 **아예 실행되지 않습니다**. 환불 예시로 말하면, 돈이 나가는 일이 애초에 발생하지 않습니다. 그리고 `reason`을 함께 주면 모델이 "왜 막혔는지"를 알고 에스컬레이션(사람 검토자에게 전달) 같은 대안 경로로 흐름을 전환할 수 있습니다.

간단한 형태의 의사 코드:

```python
def pre_tool_use(tool_name, tool_input, session_state):
    if tool_name == "refund_customer" and tool_input["amount"] > 500:
        return {
            "permissionDecision": "deny",
            "reason": "500달러를 초과하는 환불은 사람 검토자에게 전달되어야 합니다."
        }
    return {"permissionDecision": "allow"}
```

주의: `permissionDecision`에 `"defer"`(무기한 보류) 같은 값은 표준 동작이 아닙니다. 정상적으로 검증이 끝난 상황에서 시스템을 무기한 멈추는 것은 설계로서도 잘못입니다.

### 1.5 `updatedInput` — 인자 강제 덮어쓰기

PreToolUse 훅은 단순히 허용/거부만 하는 것이 아니라, **모델이 만든 인자를 안전한 값으로 교체**할 수 있습니다. `permissionDecision: "allow"` 와 함께 `updatedInput`을 반환하면 됩니다.

**왜 필요한가**: 모델은 대화 맥락에서 값을 "다시 타이핑(retype)"할 때 오타를 내거나, 다른 값과 혼동하거나, 환각(Hallucination)으로 없는 값을 만들어낼 수 있습니다. 특히 고객 ID, 계좌 번호 같은 식별자는 한 글자만 틀려도 엉뚱한 사람에게 처리가 나갑니다.

**전형적인 패턴** — "검증된 값만 사용하기":

1. 앞선 단계에서 `get_customer` 같은 검증 도구가 성공적으로 실행됨
2. 검증된 `customer_id`를 **세션 상태(session state)** 에 저장해 둠
3. 이후 `process_refund` 호출 시 PreToolUse 훅이 개입:
   - 세션 상태에 검증된 ID가 **없으면** → `deny`
   - **있으면** → `allow` + `updatedInput`으로 `customer_id`를 세션의 검증된 값으로 덮어씀

```python
def pre_tool_use(tool_name, tool_input, session_state):
    if tool_name == "process_refund":
        verified_id = session_state.get("verified_customer_id")
        if not verified_id:
            return {"permissionDecision": "deny", "reason": "고객 검증이 선행되어야 합니다."}
        return {
            "permissionDecision": "allow",
            "updatedInput": {**tool_input, "customer_id": verified_id},
        }
    return {}
```

이 방식의 장점은 **자동화를 유지하면서 안전성을 확보**한다는 것입니다. 대안들이 왜 열등한지 보면:

- 빈 객체를 반환해 그냥 통과시키기 → 세션에 올바른 ID가 있어도 모델이 넘긴 잘못된 값이 그대로 실행됩니다. 검증의 존재가 사용을 보장하지 않습니다.
- 매번 `"ask"`로 사람에게 재입력 요청 → 이미 검증이 성공한 상황인데도 사람이 매번 개입해야 하므로 자동화 가치가 사라집니다.

### 1.6 PostToolUse 훅과 `updatedToolOutput` — 출력 정규화

**언제 쓰는가**: 도구가 반환한 **결과(출력)** 가 지저분하거나 형식이 제각각이어서, 모델이 그것을 보기 **전에** 정리해야 할 때.

전형적 상황: 서로 다른 세 개의 도구가 시간 값을 각각 다른 형식으로 반환합니다.
- Unix epoch 정수: `1717027200`
- ISO 8601 문자열: `"2024-05-30T00:00:00Z"`
- 숫자 상태 코드와 날짜가 뒤섞인 값: `"200|30-05-2024"`

모델은 이런 불일치를 자주 **오독(misread)** 합니다. 특히 시간 순서를 따져야 하는 추론에서 틀립니다.

해결: PostToolUse 훅을 세 도구에 매칭시켜, 각 응답을 파싱한 뒤 `hookSpecificOutput.updatedToolOutput`에 **하나의 일관된 형식으로 재작성한 값**을 담아 반환합니다. 그러면 모델은 원본의 뒤죽박죽한 데이터를 **아예 보지 못하고**, 정규화된 데이터만 받습니다.

```python
def post_tool_use(tool_name, tool_response):
    normalized = normalize_timestamps(tool_response)  # 전부 ISO 8601로
    return {
        "hookSpecificOutput": {
            "updatedToolOutput": normalized
        }
    }
```

**왜 다른 방법은 안 되는가**:
- PreToolUse 훅으로 하려는 시도 → PreToolUse는 도구로 **들어가는 입력**을 다룹니다. 문제는 도구가 **내보내는 출력**의 형식이므로 시점이 맞지 않습니다.
- Notification 훅으로 하려는 시도 → 알림·관찰용 훅이며, 모델이 실제로 수신하는 도구 출력을 치환하는 확정적 경로가 아닙니다.
- 시스템 프롬프트로 "네가 알아서 ISO 8601로 변환해서 읽어라"라고 지시 → 이것은 모델이 **불일치 데이터를 직접 읽고** 변환하는 것입니다. "모델이 보기 전에 정규화"라는 요구를 만족하지 못하고, 오독 위험도 그대로 남습니다.

**요약 규칙**:
- 입력을 검사/차단/수정 → **PreToolUse**
- 출력을 가공/정규화 → **PostToolUse** + `updatedToolOutput`
- 사후 감사 로그만 남기기 → PostToolUse로 가능하지만, 이미 실행된 뒤이므로 **사고를 예방하지는 못합니다**. 무단 고액 환불을 "막고 싶다"면 PostToolUse는 답이 아닙니다.

## 2. MCP와 도구 이름 규칙, 그리고 매처(Matcher)

### 2.1 MCP란

**MCP(Model Context Protocol)** 는 에이전트가 외부 도구·데이터 소스에 연결하기 위한 표준 프로토콜입니다. "MCP 서버"를 하나 붙이면, 그 서버가 노출하는 여러 도구를 에이전트가 쓸 수 있게 됩니다.

예를 들어 `billing`(청구) 서버와 `inventory`(재고) 서버 두 개를 연결하면, 각 서버가 자신의 도구들을 제공합니다.

### 2.2 도구 이름 네임스페이스 규칙

여러 서버가 같은 이름의 도구(`search` 같은)를 노출할 수 있으므로, 이름 충돌을 막기 위해 **네임스페이스**가 붙습니다. 형식은 다음과 같습니다:

```
mcp__<서버이름>__<도구이름>
```

밑줄이 **두 개씩**이라는 점에 주의하세요. 예:

- `mcp__billing__issue_refund`
- `mcp__billing__void_authorization`
- `mcp__billing__apply_credit`
- `mcp__inventory__check_stock`

반면 `Bash`, `Read`, `Grep`, `Glob` 같은 **내장 도구(built-in tool)** 는 이 접두사가 없습니다.

### 2.3 매처(Matcher) — 훅을 어떤 도구에 적용할지 정하기

훅을 등록할 때 **매처**를 지정해서 "이 훅이 어떤 도구 호출에 대해 실행될지"를 정합니다. 매처는 정규식(Regular Expression) 패턴입니다.

목표에 따라 올바른 패턴이 달라집니다.

**목표 A: `billing` 서버의 모든 도구에만 적용 (다른 서버·내장 도구 제외)**

정답: `mcp__billing__.*`

- `mcp__billing__` 라는 정확한 네임스페이스 접두사로 시작
- `.*` 가 그 뒤의 어떤 도구 이름이든 받아냄

왜 다른 것들은 틀린가:
- `^mcp__` → 모든 MCP 서버(inventory 포함)의 도구를 전부 매칭합니다. 너무 넓습니다.
- `billing` → 네임스페이스 규칙(`mcp__billing__...`)과 형태가 맞지 않아 의도한 도구를 제대로 포착하지 못합니다.
- `mcp__billing` → 뒤에 도구 이름 부분을 받는 `__.*`가 빠져 있어 개별 도구명을 온전히 매칭하지 못합니다.

**목표 B: 같은 서버 안에서 특정 몇 개 도구에만 적용 (읽기 전용 도구는 제외)**

예: `billing` 서버에 `issue_refund`, `void_authorization`, `apply_credit`(모두 돈을 움직임)과 여러 읽기 전용 도구가 있을 때, 앞의 셋에만 신원 검증 훅을 걸고 싶다.

세 개의 거의 똑같은 훅을 따로 등록하면 **중복(duplication)** 이 생기고 유지보수가 나빠집니다. 정규식의 **교대(alternation, `|`)** 를 쓰면 한 번의 등록으로 해결됩니다:

```
mcp__billing__(issue_refund|void_authorization|apply_credit)
```

왜 다른 접근은 틀린가:
- 매처를 아예 안 쓰기 → 매처가 없으면 대상이 좁혀지지 않습니다. 훅이 "돈 움직이는 도구를 알아서 알아본다"는 것은 성립하지 않습니다.
- `"*"` 매처 + 짧은 타임아웃 → 타임아웃(예: 5초)은 **훅이 얼마나 오래 실행될 수 있는지**를 정하는 값이지, **어떤 도구에 적용되는지**를 좁히는 값이 전혀 아닙니다. 서로 무관한 개념입니다.
- `mcp__billing` 단독 → 도구명을 정확히 식별하지 못할뿐더러, 목표와 반대로 읽기 전용 도구까지 걸리게 됩니다.

## 3. Messages API와 에이전트 루프 직접 구현하기

프레임워크 없이 클라이언트 쪽에서 직접 에이전트 루프를 짤 때 알아야 할 것들입니다.

### 3.1 `stop_reason` — 모델이 왜 말을 멈췄는가

Messages API에 요청을 보내면 응답에 `stop_reason` 필드가 들어옵니다. 이것은 **모델이 생성을 멈춘 이유**를 알려줍니다. 루프의 계속/종료 판단은 전적으로 이 값에 달려 있습니다.

| `stop_reason` | 의미 | 루프가 할 일 |
|---|---|---|
| `"tool_use"` | 모델이 도구를 호출해 달라고 요청함. 응답 안에 `tool_use` 블록이 들어 있음 | 도구를 실행하고 결과를 돌려준 뒤 **계속** |
| `"end_turn"` | 모델이 할 말을 다 하고 자연스럽게 턴을 마침. 더 요청할 도구가 없음 | **종료** |

**중요한 오해 정정 1**: `"end_turn"`을 "계속" 조건에 넣으면 안 됩니다. `stop_reason in ("tool_use", "end_turn")` 을 continue 조건으로 삼는 코드는 잘못된 코드입니다. `"end_turn"`은 작업이 **이미 끝났다**는 신호이므로, 그 위에서 루프를 계속 돌리면 끝난 작업에 대해 계속 요청을 보내게 됩니다(불필요한 비용, 무한 루프 위험).

**중요한 오해 정정 2**: `"end_turn"`은 첫 번째 요청에서만 나오는 값이 아닙니다. 도구 결과를 받은 뒤의 턴을 포함해 **작업이 완료되는 어느 턴에서든** 반환될 수 있습니다.

**중요한 오해 정정 3**: `"end_turn"`은 과금 경계(billing boundary)와는 아무 상관이 없으며, 이 값을 지나쳐 계속한다고 토큰이 중복 청구되는 개념도 없습니다.

**중요한 오해 정정 4**: `"end_turn"`과 `"tool_use"`는 계정 종류와 무관하게 모두 유효한 표준 값입니다. 둘 중 하나만 나오는 계정 같은 것은 없습니다.

### 3.2 도구 없이 바로 끝나는 것도 정상이다

첫 번째 응답이 `stop_reason: "end_turn"` 이고 `tool_use` 블록이 하나도 없는 경우가 있습니다. 이는 **버그가 아닙니다**. 모델이 도구 없이도 충분히 답할 수 있는 간단한 질문이라면, 도구를 한 번도 호출하지 않고 즉시 완료하는 것이 정상이며 올바른 동작입니다.

관련된 잘못된 믿음들:
- "API가 첫 응답의 `end_turn`을 거부하고 재전송을 요구한다" → 그런 동작 없습니다.
- "도구가 필요 없으면 API가 가짜(placeholder) `tool_use` 블록을 끼워 넣는다" → 그런 동작 없습니다.
- "정식 완료로 인정하려면 최소 1회 도구 왕복을 강제해야 한다" → 그럴 필요 없습니다. 오히려 불필요한 호출을 만드는 나쁜 설계입니다.

### 3.3 `tool_use` → `tool_result` 왕복의 정확한 절차

`stop_reason: "tool_use"` 를 받았을 때 루프가 해야 할 일은 정해져 있습니다.

1. 응답 안의 `tool_use` 블록에서 도구 이름과 인자, 그리고 **`tool_use_id`** 를 꺼낸다.
2. 해당 도구를 실제로 실행한다.
3. 실행 결과를 `tool_result` 블록으로 만든다. 이때 반드시 **같은 `tool_use_id`를 태그로 붙인다**. (어느 도구 호출에 대한 응답인지 짝을 맞추기 위함)
4. 어시스턴트의 원래 응답과 이 `tool_result`를 대화 이력에 이어 붙인다.
5. **업데이트된 전체 대화**를 다시 API에 보낸다.

```python
messages = [{"role": "user", "content": prompt}]

while True:
    resp = client.messages.create(model=..., messages=messages, tools=tools)
    messages.append({"role": "assistant", "content": resp.content})

    if resp.stop_reason != "tool_use":
        break  # end_turn 등 -> 완료

    results = []
    for block in resp.content:
        if block.type == "tool_use":
            out = run_tool(block.name, block.input)
            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,   # 반드시 짝 맞추기
                "content": out,
            })
    messages.append({"role": "user", "content": results})
```

흔한 잘못된 구현들:
- 도구를 실행한 뒤 결과를 **애플리케이션 로그 파일에만** 쓰고, 이전 대화를 그대로 재전송 → 모델은 결과를 전혀 모르므로 진행이 막히거나 같은 도구 호출을 반복합니다.
- `tool_use` 블록을 받고도 "모델이 어떤 출력을 기대하는지 텍스트로 설명해 줄 때까지" 기다림 → `tool_use` 블록에는 이미 도구 이름과 인자가 다 들어 있습니다. 즉시 실행하면 됩니다.
- `tool_use` 블록만 이력에 넣고 `tool_result` 없이 원래 프롬프트만 다시 보냄 → 요청된 도구 호출에 대한 응답이 없어서 API 오류가 나거나 대화가 진행되지 않습니다.

### 3.4 도구 실행이 실패했을 때 — `is_error`

도구 실행 중 예외가 나면 어떻게 할까요? 두 가지 선택지가 있습니다.

1. 루프를 즉시 강제 종료 (Hard Fail)
2. 실패 내용을 `tool_result` 블록에 담고 `"is_error": true` 를 붙여 **모델에게 돌려주고 계속 진행**

일반적으로 **2번이 더 나은 설계**입니다. 이유는 에이전트의 핵심 강점이 **모델 주도 추론(model-driven reasoning)** 에 있기 때문입니다. 오류 내용을 대화 맥락에 넣어주면, Claude는

- 잘못된 파일 경로였구나 → 경로를 고쳐 재시도
- 인자 타입이 틀렸구나 → 다른 인자로 재시도
- 이 도구로는 안 되겠구나 → 다른 도구나 우회 전략 선택

같은 **자율적 복구(recovery)** 를 스스로 수행할 수 있습니다.

```python
results.append({
    "type": "tool_result",
    "tool_use_id": block.id,
    "is_error": True,
    "content": "FileNotFoundError: config/build.yaml 을 찾을 수 없습니다.",
})
```

`is_error`에 대한 오해 정정:
- `is_error`는 **도구 실행 결과의 실패 여부**를 표시할 뿐, 모델 응답의 완료 상태를 나타내는 `stop_reason`을 대체하거나 그 확인을 없애 주지 않습니다. 둘은 완전히 다른 층위의 신호입니다.
- Messages API는 `is_error` 필드가 없다고 해서 대화를 자동 종료하지 않습니다.
- 오류를 돌려준다고 해서 다음 시도의 성공이 보장되지도 않고, 도구의 내부 호출 제한(rate limit)이 초기화되지도 않습니다.

## 4. 세션(Session) — 재개(Resume)와 분기(Fork)

### 4.1 세션이 보존하는 것과 보존하지 않는 것

**세션(Session)** 은 에이전트와의 대화를 나중에 이어서 하기 위해 저장해 두는 단위입니다. 각 세션에는 세션 ID가 있고, 그 ID로 나중에 **재개(resume)** 할 수 있습니다.

여기서 반드시 알아야 할 경계선:

> **세션은 "대화 이력(conversation history)"을 저장합니다. "파일 시스템의 스냅샷"을 저장하지 않습니다.**

즉, 세션 중간에 에이전트가 어떤 파일을 수정했다면, 그 파일의 **예전 내용은 어디에도 보관되지 않습니다**. 세션을 재개해서 "아까 그 상태로 파일을 되돌려줘"라고 요청해도, 에이전트는 디스크에 있는 **현재의 수정된 내용**만 볼 수 있습니다.

(대화 이력에 예전 Read 결과가 텍스트로 남아 있을 수는 있지만, 그것은 우연한 부산물이지 신뢰할 수 있는 복원 메커니즘이 아닙니다.)

**파일을 되돌리고 싶다면 별도의 체크포인팅(checkpointing) 메커니즘이 필요합니다** — Git 커밋, 스냅샷, 백업 복사본 등. 이것은 에이전트 프레임워크가 아니라 개발자가 직접 마련해야 하는 부분입니다.

관련 오해 정정:
- "세션 ID를 올바르게 썼다면 파일 내용이 자동 복원됐을 것이다" → 아닙니다. ID가 맞아도 세션 저장 메커니즘에 파일 스냅샷 복원 기능 자체가 없습니다.
- "`fork_session`을 썼으면 파일 예전 상태가 보존됐을 것이다" → 아닙니다. fork는 **대화 맥락**을 분기하는 기능이지, 파일 시스템을 캡처하는 도구가 아닙니다.

### 4.2 Resume vs Fork

둘 다 "기존 세션에서 이어간다"는 점은 같지만, 결과로 만들어지는 이력의 모양이 다릅니다.

**Resume (재개)**: 같은 세션 ID에 계속 **이어 붙입니다**. 하나의 일직선 이력(single shared history)이 됩니다.

```
[원래 분석] → [탐색 1: 캐싱] → [탐색 2: 큐잉]
                                  ↑ 여기서는 탐색 1의 내용을 다 보고 있음
```

**Fork (분기)**: 지금까지의 이력을 복제해서 **독립된 새 갈래**를 만듭니다.

```
                ┌→ [탐색 A: 캐싱]     (서로를 보지 못함)
[원래 분석] ────┤
                └→ [탐색 B: 큐잉]
```

**전형적인 실수**: "같은 분석 세션을 두 번 resume해서 캐싱 접근법과 큐잉 접근법을 각각 독립적으로 탐색하자."

이것은 **독립적인 탐색이 되지 않습니다**. 두 탐색이 하나의 공유 이력에 순차적으로 쌓이므로, 두 번째 탐색(큐잉)은 첫 번째 탐색(캐싱)의 내용을 이미 보고 있고 그것에 오염(편향)됩니다. 진짜 독립적인 두 갈래를 원한다면 **fork** 를 써야 합니다.

추가 오해 정정:
- "resume은 세션 ID당 한 번만 호출할 수 있다" → 아닙니다. 여러 번 호출 가능하며, 두 번째 호출이 에러로 실패하지 않습니다. 단지 같은 이력 라인 뒤에 계속 덧붙을 뿐입니다.
- "resume은 이전 도구 결과를 조용히 폐기한다" → 아닙니다. 이전 대화 이력과 도구 결과를 모두 보존해서 전달합니다.

## 5. 오케스트레이션 패턴 — 작업을 어떻게 쪼갤 것인가

### 5.1 두 가지 큰 갈래

| | **고정 프롬프트 체인 (Fixed Prompt Chain)** | **동적 오케스트레이터 (Dynamic Orchestrator)** |
|---|---|---|
| 구조 | 정해진 단계를 정해진 순서로 실행 | 실행 중에 다음 하위 작업을 생성 |
| 언제 적합한가 | 할 일과 순서가 미리 정해져 있고, 단계 간 의존이 없을 때 | 다음에 무엇을 할지가 이전 단계 결과에 달려 있을 때 |
| 장점 | 일관성, 결정론성, 예측 가능성, 저비용, 낮은 지연 | 유연성, 탐색 능력 |
| 단점 | 예측 못한 상황에 대응 불가 | 복잡, 비용 증가, 결과 편차 |

### 5.2 판단 기준 하나만 기억하기

> **다음에 무엇을 할지가 이전 단계의 출력에 따라 달라지는가?**
> - 아니오 → 고정 프롬프트 체인
> - 예 → 동적 오케스트레이션

### 5.3 고정 체인이 맞는 경우 (예시)

**분기별 Terraform 컴플라이언스 검토**: 매 분기마다 정확히 같은 11개 규칙 체크리스트를 모든 파일에 적용하고, 어떤 규칙의 결과도 다른 규칙의 검사 여부를 바꾸지 않는다.

→ 하위 작업이 중간 발견 사항에 전혀 의존하지 않으므로, 동적 계획 능력이 **불필요**합니다. 매 분기 같은 순서로 11개를 순회하는 고정 프롬프트 체인이 비용·일관성 면에서 최적입니다.

주의할 나쁜 변형: "고정 체인을 쓰되, 모델이 불필요하다고 판단하는 규칙은 조용히 건너뛰게(silently skip) 한다" → 컴플라이언스 검토에서 규칙을 임의로 누락하는 것은 검토의 완전성 자체를 무너뜨리는 위험한 설계입니다.

**콘텐츠 파이프라인**: 제품 설명 생성 → 항상 같은 브랜드 톤 검사기 → 항상 같은 비속어 필터. 내용과 무관하게 순서가 고정.

→ 여기에 "내용에 따라 톤 검사기와 비속어 필터 중 무엇을 먼저 돌릴지 동적으로 정하는 오케스트레이터"를 도입하자는 제안이 나온다면, 가장 강한 비판은 이것입니다: **두 검사가 어차피 항상 같은 고정 순서로 모두 실행되므로 프롬프트 체인이 이미 예측 가능하게 처리하고 있고, 동적 오케스트레이터는 결과 개선 없이 불필요한 복잡성과 지연(latency)만 추가한다.**

이때 흔히 나오는 잘못된 옹호 논리:
- "제품 설명 길이가 제각각이라 고정 체인으로는 감당 못 한다" → 틀렸습니다. 프롬프트 체인은 입력 텍스트 길이 변동을 자연스럽게 처리합니다.
- "동적 오케스트레이션이 언제나 더 좋은 결과를 낸다" → 근거 없는 주장이며, 이는 비판이 아니라 옹호입니다.
- "비속어 필터는 반드시 톤 검사기보다 먼저여야 한다" → 그런 절대적 제약은 없습니다.

같은 논리로, Terraform 예시에서 "파일 크기가 다양하니 고정 프로세스는 일관되게 적용될 수 없다"는 주장도 성립하지 않습니다. 크기 차이는 동적 오케스트레이터로 전환할 이유가 되지 못합니다.

### 5.4 동적 오케스트레이션이 맞는 경우 (예시)

**열린 결말(open-ended) 조사**: "지난달 결제 이탈률(checkout abandonment)이 15% 증가한 원인은 무엇인가?" 확인해야 할 데이터 소스(로그, 분석 대시보드, 최근 배포 내역)가 사전에 정해져 있지 않고, 초기 조사 결과가 무엇을 시사하느냐에 따라 달라진다.

→ 올바른 분해:
1. **초기 조사 하위 작업**을 하나 생성해서 실행
2. 그 **결과(findings)를 평가**
3. 가장 유망한 단서(promising leads)를 추적하는 **후속 하위 작업을 동적으로 생성**
4. (필요한 만큼 반복)

이것이 **동적 작업 분해(Dynamic Task Decomposition)** 또는 **탐색적 계획(Exploratory Planning)** 입니다.

부적합한 대안들:
- "대시보드 → 서버 로그 → 최근 배포" 순서를 고정한 3단계 체인 → 초기 조사에서 배포가 유력한 단서로 지목돼도 무조건 정해진 순서를 강제하므로 유연성이 없습니다.
- 코드베이스를 파일별로 훑는 방식 → 원인이 로그·대시보드·배포 등 코드 밖에 있을 수 있는 문제의 성격과 맞지 않습니다.
- 어떤 데이터 소스도 보지 않고 문구만으로 즉시 원인을 단정 → **환각(Hallucination)** 을 유발하며 근거 없는 답이 나옵니다.

### 5.5 분해가 너무 좁으면 생기는 문제 (Over-narrow Decomposition)

코디네이터가 광범위한 요청을 하위 작업으로 쪼갤 때, 원래 요청의 **범위(scope)** 를 다 덮지 못하고 지나치게 구체적인 몇 가지 측면(facet)으로만 좁히면, 다뤄지지 않은 영역이 **최종 결과물에서 통째로 사라집니다**.

예시: "전기차 충전 네트워크의 **경쟁 환경 분석**"이라는 넓은 요청을 '충전기 커넥터 유형 찾기', '충전 속도 목록 작성' 같은 기술 사양 수준의 좁은 하위 작업으로만 분해 → 종합 보고서에서 가격 모델, 규제 인센티브, 주요 경쟁사가 **완전히 누락**됩니다.

여기서 근본 원인은 **하위 작업 정의 단계**에 있습니다. 헷갈리기 쉬운 다른 원인들과 구별하세요:
- 서브에이전트들이 서로 작업을 중복해서 시간이 부족했던 것이 아닙니다(각자 다른 작업을 수행했음).
- 종합 단계가 너무 일찍 실행되어 부분 결과만 모은 타이밍 문제가 아닙니다.
- 도구 접근 권한 부족은 **지정된 하위 작업 안에서의** 결과 부실을 설명할 수는 있어도, 주제 자체가 **작업 계획에서 배제된** 이유를 설명하지 못합니다.

**교훈**: 분해할 때는 원래 요청의 전체 범위를 먼저 축(axis)으로 나열하고(예: 기술 사양 / 가격 / 규제 / 경쟁사 / 시장 규모), 그 다음에 각 축을 하위 작업으로 내려야 합니다.

### 5.6 맵-리듀스(Map-Reduce)와 맥락 희석(Context Dilution)

**맥락 희석 / 주의력 분산**: 한 번의 프롬프트에 너무 많은 정보를 넣으면, 모델의 주의(attention)가 전체에 얕게 퍼지면서 개별 항목의 세부 사항을 놓치게 됩니다.

예시 상황: 대규모 코드 리뷰 에이전트가 PR의 **모든 파일을 하나의 결합된 프롬프트**로 분석하고, 그다음 두 번째 프롬프트에서 파일 간(cross-file) 이슈를 요약합니다. 그런데 파일을 직접 비교하면 보이는 실제 통합 버그를 이 요약이 자주 놓칩니다.

**원인**: 첫 번째 패스가 이미 모든 파일에 주의를 분산시켜서 각 파일에 대한 발견이 얕습니다. 두 번째 패스는 그 얕은 결과 위에서 요약하므로, 원본에 없던 디테일을 되살릴 수 없습니다.

**해결 (맵-리듀스 패턴)**:
- **Map 단계**: 파일마다 **개별 분석 패스**를 돌려 각 파일에 대한 깊고 풍부한 발견을 만든다.
- **Reduce 단계**: 그 풍부한 개별 발견들을 입력으로 삼아 파일 간 통합 이슈를 요약한다.

```
[파일1 분석] ┐
[파일2 분석] ├→ [교차 파일 통합 패스] → 최종 리뷰
[파일3 분석] ┘
```

잘못된 대안들:
- 전부를 하나의 프롬프트로 더 크게 합치기 → 주의력 분산과 맥락 오염이 더 심해집니다.
- 두 패스의 순서를 뒤집어 개별 분석 전에 교차 요약 먼저 → 요약할 재료가 없으므로 논리적으로 성립하지 않습니다.
- 시스템 프롬프트를 더 길고 정밀하게 써서 "통합 버그란 무엇인지" 정의하기 → 원인은 정의의 모호함이 아니라 정보 과부하로 인한 주의 분산입니다.

## 6. 서브에이전트(Subagent)와 위임(Delegation)

### 6.1 서브에이전트란

**서브에이전트(Subagent)** 는 특정 목적에 특화된 별도의 에이전트로, **코디네이터(Coordinator)** 또는 **오케스트레이터(Orchestrator)** 에이전트가 필요할 때 호출(위임)합니다.

서브에이전트를 정의할 때(`AgentDefinition`) 들어가는 대표적 필드:

| 필드 | 역할 |
|---|---|
| `name` | 서브에이전트의 이름 |
| `description` | **무엇을 위한 에이전트인지 요약한 설명** — 라우팅의 핵심 |
| `tools` | 이 서브에이전트가 쓸 수 있는 도구 목록 |
| `model` | 사용할 모델 (생략 시 기본 모델이 적용됨) |
| `prompt` | 서브에이전트의 시스템 프롬프트 |

### 6.2 설명 기반 라우팅 (Description-based Routing)

사용자 쿼리에 서브에이전트 이름이 **명시되지 않았을 때**, 코디네이터는 어떻게 어느 서브에이전트를 부를지 정할까요?

답: **각 서브에이전트의 `description` 필드를 쿼리와 의미적으로 매칭(semantic matching)해서, 적합한 것이 있으면 자동으로 위임합니다.**

동작 원리는 이렇습니다. 정의된 서브에이전트들의 `description`이 코디네이터의 프롬프트/시스템 맥락에 포함됩니다. 새 쿼리가 들어오면 LLM이 쿼리의 의도와 각 `description`을 비교해 가장 적합한 것을 고릅니다.

여기서 얻는 실무적 교훈: **`description`은 잘 써야 합니다.** 이것이 라우팅 품질을 직접 결정합니다.

잘못된 통념들:
- "쿼리에 정확한 이름이 들어 있어야만 위임이 고려된다" → 아닙니다. 설명 기반 의미 매칭으로 동적 호출됩니다.
- "설정 파일에 정의된 순서대로 호출한다" → 그것은 정적 체인이지 동적 라우팅이 아닙니다.
- "일단 모든 서브에이전트를 다 호출하고 관련 없는 출력은 버린다" → 심각한 토큰 낭비와 지연을 유발하는 잘못된 설계입니다.

### 6.3 프롬프트로 이름을 부르는 것은 "보장"이 아니다

"code-reviewer 에이전트를 사용해서 인증 모듈을 검토해줘" 라고 프롬프트에 명시하면, 그 서브에이전트가 **반드시** 호출될까요?

**아닙니다.** 이것은 자연어 지시이므로 모델에 **영향(influence)** 을 줄 뿐 **강제(force)** 하지 못합니다. 모델은 위임하지 않고 스스로 검토 답변을 내놓을 수도 있습니다.

이것 역시 1장의 대원칙과 같은 이야기입니다: **자연어 프롬프트는 확률적이고, 보장이 필요하면 프로그래밍적 제약이 필요합니다.**

확정적으로 보장하려면:
- `tool_choice` 파라미터로 특정 도구/서브에이전트 호출을 강제하거나,
- 전용 서브에이전트 호출 문법(예: Claude Code의 `@code-reviewer`)을 사용하거나,
- 그 밖의 프로그래밍적 제약(훅, 코드 레벨 라우팅)을 씁니다.

관련 오해 정정:
- "`description` 필드를 지우면 이름 언급이 강제 호출이 된다" → 아닙니다. `description`을 지운다고 자연어 지시가 확정적 호출로 바뀌지 않습니다.
- "이름을 부르면 자동 매칭을 우회하는 명시적 호출이 되어 100% 보장된다" → 아닙니다. 여전히 자연어 안내일 뿐입니다.
- "이름에 의한 명시적 지정은 내장 에이전트에만 통한다" → 아닙니다. 커스텀·내장 모두 영향을 받지만, 둘 다 **텍스트 지시만으로는 100% 강제되지 않는다**는 점이 핵심입니다.

### 6.4 `allowedTools`와 `Task` 도구 — 위임이 매번 승인 프롬프트에서 멈출 때

**`allowedTools`** 는 사전 승인된(자동 실행 가능한) 도구 이름 목록입니다. 여기에 없는 도구를 쓰려고 하면 실행 전에 사람에게 승인을 묻는 프롬프트가 뜹니다.

중요한 사실: **서브에이전트를 호출하는 행위 자체도 하나의 도구입니다.** 그 도구의 이름이 **`Task`** 입니다.

그래서 이런 상황이 벌어집니다:

```
allowedTools: ["Read", "Grep", "Glob"]
agents: { "research-assistant": {...} }

→ 코디네이터가 research-assistant에게 위임하려 할 때마다 승인 프롬프트에서 멈춤
```

**원인**: 위임에 필요한 `Task` 도구가 `allowedTools`에 없기 때문입니다.
**해결**: `allowedTools`에 `"Task"`를 추가합니다.

```
allowedTools: ["Read", "Grep", "Glob", "Task"]
```

이 증상의 다른 원인 후보들이 왜 아닌지:
- 서브에이전트의 `tools` 배열이 코디네이터보다 권한이 많아서 → 이 사례의 원인이 아닙니다. 원인은 위임 도구 자체의 자동 승인 누락입니다.
- 시스템 프롬프트에 서브에이전트 이름이 없어서 → 권한 레이어는 시스템 프롬프트의 이름 언급 여부를 검사해서 승인 여부를 정하지 않습니다.
- `model` 필드가 빠져서 → `model`이 없으면 기본 모델이 적용되거나 설정 오류가 날 뿐, 호출마다 승인 팝업이 뜨지는 않습니다.

## 7. 전체를 관통하는 원칙 요약

1. **보장이 필요하면 모델 밖에 두어라.** 프롬프트는 영향을 주고, 코드(훅, 권한, `tool_choice`)는 강제한다.
2. **시점이 설계를 결정한다.** 막을 것은 실행 전(PreToolUse), 다듬을 것은 실행 후(PostToolUse), 사후 기록은 예방이 아니다.
3. **복잡성은 필요할 때만 도입하라.** 단계 간 의존이 없으면 고정 체인, 있으면 동적 오케스트레이션.
4. **정보를 한 번에 다 넣지 마라.** 맥락이 희석되면 디테일이 사라진다. Map으로 깊이 파고 Reduce로 합쳐라.
5. **분해는 범위 전체를 먼저 덮어라.** 하위 작업으로 지정되지 않은 영역은 결과에서 통째로 사라진다.
6. **오류는 종료 신호가 아니라 추론 재료다.** `is_error`로 돌려주면 모델이 스스로 복구한다.
7. **세션은 대화를 기억하지, 파일을 기억하지 않는다.** 롤백은 별도의 체크포인팅으로.

## 8. 용어 사전 (Glossary)

### 에이전트 기본

| 용어 | 설명 |
|---|---|
| **Agent** | LLM에 도구와 반복 루프를 결합해, 스스로 도구를 골라 쓰며 작업을 수행하는 시스템. |
| **Agentic Loop** | 모델 응답 → 도구 실행 → 결과 반환 → 다시 모델 응답을 반복하는 에이전트의 실행 구조. |
| **Tool** | 에이전트가 호출할 수 있는 외부 기능(파일 읽기, API 호출, 환불 처리 등). |
| **System Prompt** | 모델에게 역할·규칙·맥락을 미리 지시하는 텍스트. 영향력은 있으나 강제력은 없음. |
| **Deterministic** | 결정론적. 같은 입력에 항상 같은 결과. 코드 로직이 여기에 해당. |
| **Probabilistic** | 확률적. 대체로 맞지만 항상은 아님. LLM 생성이 여기에 해당. |
| **Temperature** | 생성의 무작위성을 조절하는 파라미터. 낮추면 일관성은 오르지만 잘못된 해석 자체는 고쳐지지 않음. |
| **Hallucination** | 환각. 모델이 근거 없는 사실이나 값을 그럴듯하게 지어내는 현상. |
| **Prompt Injection** | 외부 데이터에 악의적 지시를 숨겨 모델이 그것을 개발자 지시로 착각하게 만드는 공격. |
| **Guardrail** | 가드레일. 에이전트가 허용 범위를 벗어나지 못하게 하는 안전장치. |
| **Escalation** | 에스컬레이션. 자동 처리가 불가능하거나 부적절한 건을 사람 검토자에게 넘기는 절차. |

### 훅

| 용어 | 설명 |
|---|---|
| **Hook** | 실행 과정의 특정 시점에 자동 실행되도록 등록해 둔 개발자 코드. 모델 생성 바깥에서 동작. |
| **PreToolUse Hook** | 도구가 실행되기 **전**에 실행되는 훅. 입력을 검사해 허용/거부/수정한다. |
| **PostToolUse Hook** | 도구가 실행된 **후**, 결과가 모델에 전달되기 **전**에 실행되는 훅. 출력을 가공한다. |
| **Notification Hook** | 알림·기록·관찰 목적의 훅. 모델이 받는 도구 출력을 치환하는 표준 수단이 아님. |
| **tool_input** | 모델이 도구에 넘기려는 인자 객체. PreToolUse 훅이 검사·수정하는 대상. |
| **permissionDecision** | PreToolUse 훅의 반환 값. `"allow"`(허용), `"deny"`(차단), `"ask"`(사람에게 확인). |
| **reason** | `deny` 시 함께 전달하는 차단 사유. 모델이 대안 경로를 찾는 데 사용. |
| **updatedInput** | PreToolUse 훅이 `allow`와 함께 반환해 도구 인자를 안전한 값으로 강제 교체하는 필드. |
| **hookSpecificOutput** | 훅이 반환하는 훅 전용 출력 컨테이너. |
| **updatedToolOutput** | `hookSpecificOutput` 안에서 도구의 출력을 재작성해 모델에게 전달하는 필드. |
| **Matcher** | 훅을 어떤 도구 호출에 적용할지 정하는 정규식 패턴. |
| **Timeout (hook)** | 훅이 실행될 수 있는 최대 시간. **적용 대상 도구를 좁히는 기능이 아님.** |

### MCP

| 용어 | 설명 |
|---|---|
| **MCP (Model Context Protocol)** | 에이전트가 외부 도구·데이터 소스에 연결하기 위한 표준 프로토콜. |
| **MCP Server** | MCP를 통해 도구들을 노출하는 서버(예: billing, inventory). |
| **Namespace** | 도구 이름 충돌 방지를 위한 접두사 규칙. `mcp__<서버명>__<도구명>` (밑줄 2개). |
| **Built-in Tool** | `Bash`, `Read`, `Grep`, `Glob`, `Task` 등 MCP 접두사가 붙지 않는 내장 도구. |
| **Regex Alternation** | 정규식의 `|`. `(a|b|c)` 형태로 여러 이름을 한 패턴에 담아 훅 중복 등록을 없앰. |

### Messages API / 루프

| 용어 | 설명 |
|---|---|
| **Messages API** | Claude에 메시지를 보내고 응답을 받는 API. 에이전트 루프의 기반. |
| **stop_reason** | 모델이 생성을 멈춘 이유를 알려주는 응답 필드. 루프 계속/종료 판단의 근거. |
| **"tool_use"** | `stop_reason` 값. 모델이 도구 호출을 요청함 → 도구를 실행하고 **계속**. |
| **"end_turn"** | `stop_reason` 값. 모델이 최종 응답을 냈고 더 요청할 도구가 없음 → **종료**. 첫 턴에도 나올 수 있음. |
| **tool_use block** | 응답 안에서 도구 이름·인자·`tool_use_id`를 담고 있는 블록. |
| **tool_use_id** | 각 도구 호출을 식별하는 ID. 결과를 돌려줄 때 반드시 같은 ID로 짝을 맞춰야 함. |
| **tool_result block** | 도구 실행 결과를 담아 모델에게 돌려주는 블록. `tool_use_id`가 필수. |
| **is_error** | `tool_result`에 붙이는 플래그. 도구 실행이 실패했음을 모델에게 알림. `stop_reason`을 대체하지 않음. |
| **Model-Driven Recovery** | 오류를 모델에게 돌려주어 모델이 스스로 재시도·우회를 판단하게 하는 복구 방식. |
| **Hard Fail** | 오류 발생 시 루프를 즉시 강제 종료하는 방식. 자율 복구 기회를 없앰. |

### 세션

| 용어 | 설명 |
|---|---|
| **Session** | 이어서 대화할 수 있도록 저장되는 대화 단위. 세션 ID로 식별. |
| **Session State** | 세션 동안 유지되는 상태 저장소. 검증된 ID 같은 값을 훅이 읽고 쓸 수 있음. |
| **Resume** | 기존 세션 ID의 이력에 **이어 붙이는** 재개. 여러 번 호출 가능하며 하나의 일직선 이력이 됨. |
| **Fork (fork_session)** | 기존 이력을 복제해 **독립된 새 갈래**를 만드는 분기. 서로를 보지 못하는 병렬 탐색에 필요. |
| **Filesystem State** | 디스크의 실제 파일 상태. **세션에 스냅샷으로 저장되지 않음.** |
| **Checkpointing** | 파일 상태를 되돌리기 위해 별도로 마련해야 하는 스냅샷/버전 관리 메커니즘. |

### 오케스트레이션

| 용어 | 설명 |
|---|---|
| **Coordinator / Orchestrator** | 요청을 하위 작업으로 분해하고 서브에이전트에 배분·종합하는 상위 에이전트. |
| **Subagent** | 특정 목적에 특화된 하위 에이전트. 코디네이터가 위임해서 호출. |
| **AgentDefinition** | 서브에이전트 정의. `name`, `description`, `tools`, `model`, `prompt` 등을 포함. |
| **description (field)** | 서브에이전트의 용도 요약. 코디네이터가 쿼리와 의미 매칭해 라우팅하는 근거. |
| **Description-based Routing** | 쿼리와 각 서브에이전트 `description`을 의미적으로 비교해 자동 위임하는 방식. |
| **Delegation** | 위임. 코디네이터가 작업을 서브에이전트에게 넘기는 행위. |
| **Task (tool)** | 서브에이전트를 호출하는 내장 도구. `allowedTools`에 없으면 위임마다 승인 프롬프트가 뜸. |
| **allowedTools** | 자동 실행이 사전 승인된 도구 이름 목록. |
| **tool_choice** | 특정 도구 호출을 프로그래밍적으로 강제하는 API 파라미터. |
| **Prompt Chain** | 정해진 단계를 정해진 순서로 실행하는 고정 파이프라인. |
| **Dynamic Orchestration** | 실행 중 결과에 따라 다음 하위 작업을 생성하는 방식. |
| **Task Decomposition** | 큰 요청을 하위 작업으로 쪼개는 것. |
| **Dynamic Task Decomposition** | 초기 결과를 평가해 후속 하위 작업을 실행 중에 생성하는 분해 방식. |
| **Exploratory Planning** | 결과가 불확실한 문제에서 단서를 따라가며 계획을 갱신하는 방식. |
| **Over-narrow Decomposition** | 분해가 지나치게 좁아 원래 요청의 넓은 영역이 통째로 누락되는 실패 패턴. |
| **Map-Reduce** | 개별 단위를 각각 깊게 처리(Map)한 뒤 그 결과를 종합(Reduce)하는 패턴. |
| **Context Dilution** | 맥락 희석. 한 프롬프트에 정보가 너무 많아 모델의 주의가 분산되고 디테일이 누락되는 현상. |
| **Over-engineering** | 필요 없는 복잡성 도입. 고정 순서면 충분한 곳에 동적 오케스트레이터를 넣는 것이 대표적. |
| **Latency** | 지연 시간. 불필요한 동적 판단 단계는 비용과 함께 지연도 늘림. |
