# 사전학습 노트: 프롬프트 엔지니어링과 구조화된 출력 (Prompt Engineering & Structured Output)

이 문서는 이 주제를 처음 접하는 학습자를 위한 개념 정리입니다. LLM(대규모 언어 모델)이 무엇인지 정도만 알고 있다고 가정하고, 필요한 배경 지식을 밑바닥부터 설명합니다.

---

## 0. 출발점: LLM은 "텍스트를 이어 쓰는 기계"다

Claude 같은 LLM은 근본적으로 **주어진 텍스트 뒤에 이어질 가장 그럴듯한 토큰(단어 조각)을 확률적으로 예측**하는 장치입니다. 이 한 문장이 이 노트 전체를 관통하는 핵심입니다.

여기서 파생되는 결과가 세 가지입니다.

1. **출력은 확률적이다.** 같은 입력을 두 번 줘도 결과가 다를 수 있습니다.
2. **"~하지 마라"는 지시는 물리적 보장이 아니다.** "JSON만 출력해"라고 말해도 모델은 그저 그 확률을 높일 뿐, 어길 수 있습니다.
3. **모델은 프롬프트 안의 텍스트를 "역할별로" 구분해서 보지 않는다.** 지시문, 예시, 실제 입력이 모두 그냥 하나의 긴 텍스트일 뿐입니다. 우리가 구분해 주지 않으면 모델이 혼동합니다.

이후의 모든 기법은 이 세 가지 한계를 다루는 방법입니다.

---

## 1. 프롬프트의 구조화 (Prompt Structuring)

### 1.1 프롬프트란 무엇인가

프롬프트(prompt)는 모델에게 보내는 입력 텍스트 전체입니다. 실무에서 하나의 프롬프트에는 보통 여러 종류의 내용이 섞입니다.

- **배경 문맥(background context)**: 도메인 설명, 회사 정책, 참고 문서 등
- **지시문(instructions)**: 무엇을 하라는 명령
- **서식 지침(formatting instructions)**: 출력을 어떤 모양으로 만들라는 요구
- **예시(examples)**: 입력-출력 쌍을 보여주는 견본
- **실제 사용자 요청(the live user request)**: 진짜로 처리해야 할 것

### 1.2 구조 없는 프롬프트에서 생기는 전형적 사고

이 모든 게 태그나 구분자 없이 한 덩어리로 들어가면, 모델이 **예시 안의 입력 데이터를 실제 처리해야 할 요청으로 착각**하는 일이 벌어집니다. 그러면 진짜 질문은 무시하고 견본 데이터에 대한 답을 내놓습니다. 이건 모델이 멍청해서가 아니라, 텍스트상 둘을 구분할 근거가 없기 때문입니다.

### 1.3 해결책: XML 태그로 경계를 만든다

Claude는 XML 형태의 태그로 프롬프트 영역을 구분하면 각 영역의 역할을 매우 안정적으로 인식합니다.

```xml
<context>
당사는 B2B SaaS 지원 데스크를 운영합니다. 티켓은 ...
</context>

<instructions>
아래 티켓을 읽고 우선순위와 카테고리를 판정하라.
</instructions>

<examples>
  <example>
    <input>결제가 두 번 청구됐습니다.</input>
    <output>{"priority": "high", "category": "billing"}</output>
  </example>
  <example>
    <input>로고 색상이 마음에 안 듭니다.</input>
    <output>{"priority": "low", "category": "feedback"}</output>
  </example>
</examples>

<ticket>
로그인 후 대시보드가 빈 화면으로 뜹니다.
</ticket>
```

핵심 패턴:

- **개별 예시는 각각 `<example>`로 감싸고**, 예시 묶음 전체를 다시 바깥쪽 `<examples>`로 감쌉니다. 두 겹 구조여야 "여기부터 여기까지가 전부 참고용 견본이다"라는 경계가 분명해집니다.
- 실제 처리 대상은 그 태그 **바깥**에 두거나 별도 태그(`<ticket>`)에 둡니다.
- 태그 이름은 정해진 표준이 아니라 자유롭게 지어도 됩니다. 중요한 건 **일관성과 명확한 경계**입니다.

### 1.4 잘 안 되는 대안들과 그 이유

- **예시를 프롬프트 맨 뒤로 옮기기**: 위치만 바꿔도 경계는 여전히 모호합니다. 오히려 마지막에 있는 텍스트를 최종 명령으로 오인할 위험이 커집니다.
- **예시를 짧은 불릿으로 요약하기**: 입력-출력 쌍이 사라지면서 예시의 학습 효과(뒤의 퓨샷 참조)를 잃습니다.
- **예시를 아예 없애기**: 혼동은 사라지지만 출력 품질이 함께 떨어집니다. 구조 문제를 품질 손실로 맞바꾸는 셈입니다.

## 2. 퓨샷 프롬프팅 (Few-Shot Prompting)

### 2.1 개념

모델을 재학습(fine-tuning)시키지 않고, **프롬프트 안에 몇 개(few)의 입력-출력 견본(shot)을 넣어** 원하는 동작을 유도하는 기법입니다.

- **제로샷(zero-shot)**: 예시 없이 지시문만
- **원샷(one-shot)**: 예시 1개
- **퓨샷(few-shot)**: 예시 여러 개

퓨샷은 특히 **출력 형식 고정**, **레이블 일관성 확보**, **애매한 판정 기준 전달**에 강력합니다. 말로 설명하기 힘든 기준도 예시 세 개면 전달되는 경우가 많습니다.

### 2.2 왜 작동하는가

모델은 프롬프트 안의 패턴을 인식해 그 패턴을 이어갑니다(in-context learning). "입력이 이렇게 생기면 출력은 이렇게 생긴다"는 규칙성을 예시에서 읽어내 새 입력에도 적용합니다.

### 2.3 예시의 다양성이 결정적인 이유

여기가 가장 중요하고, 동시에 가장 자주 실수하는 지점입니다.

모델은 우리가 **의도한 패턴만** 배우지 않습니다. 예시 집합에 우연히 공통된 다른 특징이 있으면, **그것까지 규칙으로 착각해서 배웁니다.** 이걸 **의도치 않은 상관 패턴(spurious pattern)** 또는 **퓨샷 예시 편향(few-shot example bias)** 이라고 합니다.

구체적 사례:

> 문서 분류 프롬프트에 예시 5개를 넣었는데, 5개가 전부 우연히 "100단어 미만의 영어 이메일"이었다. 배포 후 짧은 영어 이메일은 잘 분류되지만, **예시 없던 이전 프롬프트에서는 잘 되던** 긴 문서와 다른 언어 문서가 오분류되기 시작했다.

모델이 배운 것은 "이렇게 분류해라"만이 아니라 "이 작업은 짧은 영어 텍스트에 대한 것이다"였습니다.

**해결책은 예시의 다양화(diversify)입니다.** 길이(짧은 것/긴 것), 언어, 문서 형태, 도메인, 그리고 **정보가 놓인 위치**까지 폭넓게 섞어야 합니다.

주의할 오해들:

- 편향된 예시를 **복제해서 개수만 늘리는 것**은 편향을 강화할 뿐입니다. 토큰만 낭비합니다.
- 예시 추가 직후에 발생한 성능 저하를 "모델 드리프트(model drift, 모델 자체가 시간에 따라 변하는 현상)" 탓으로 돌리는 것은 인과 오판입니다. 변경 시점과 저하 시점이 일치하면 원인은 그 변경입니다.
- "퓨샷은 분류 작업에 안 맞는다"는 것도 사실이 아닙니다. 오히려 분류 일관성을 높이는 대표적 기법입니다.

### 2.4 다양성 부족이 만드는 또 다른 전형적 실패: 위치 편향

> 논문에서 '표본 크기'와 '통계적 방법'을 추출하는 도구가, `Methodology`라는 제목이 붙은 섹션에서는 잘 뽑아내지만 같은 정보가 `Results`나 `Discussion` 문장 속에 제목 없이 묻혀 있으면 `null`을 반환한다.

원인은 컨텍스트 부족도, 검색 순서 문제도 아닙니다. 모델이 **"헤딩(제목) 아래에 있어야 그 정보다"** 라는 편향을 학습한 것입니다.

올바른 해결책: **레이블된 섹션에서 뽑는 예시와, 문장 속에 묻혀 있는 정보를 뽑는 예시를 둘 다** 프롬프트에 제공합니다.

비교를 위한 오답 유형과 이유:

- **컨텍스트 창(context window) 늘리기**: 컨텍스트 창은 모델이 한 번에 볼 수 있는 토큰의 최대 길이입니다. 텍스트가 잘려서 못 읽는 게 원인이라면 유효하지만, 여기서는 읽었는데 **못 알아본** 것이므로 무관합니다.
- **해당 섹션 없는 문서를 파이프라인에서 제외**: 문제를 푸는 게 아니라 시스템의 적용 범위를 임의로 줄이는 회피입니다.
- **Methodology 먼저 검색하고 없으면 다른 섹션으로 폴백(fall back)**: 폴백은 "어디를 볼지"의 순서 문제를 다룰 뿐입니다. 다른 섹션을 보게 해도 그 안의 비구조적 문장에서 여전히 추출하지 못합니다.

## 3. 구조화된 출력 (Structured Output)

### 3.1 문제 정의

실무 파이프라인은 LLM의 답을 프로그램이 파싱해서 DB에 넣거나 다음 단계로 넘깁니다. 그러려면 출력이 **기계가 읽을 수 있는 형식(주로 JSON)** 이어야 합니다.

**JSON**은 `{"key": "value"}` 형태의 데이터 표기법이고, 괄호 하나만 어긋나도 파싱이 실패합니다.

### 3.2 방법 1: 자연어로 부탁하기 (프롬프트 전용) — 취약함

```
JSON으로만 응답하라. 다른 말은 절대 붙이지 마라.
```

이 방식의 실패 양상:

- **사족 텍스트(stray commentary)**: "물론입니다! 요청하신 JSON입니다:" 같은 서문/후문이 붙습니다.
- **깨진 괄호(malformed brackets)**: 중괄호나 따옴표가 빠지거나 쉼표가 남습니다.
- **필드 누락**: 필수 필드를 빠뜨립니다.

근본 원인은 1절에서 본 대로, 이것이 **확률적 텍스트 생성일 뿐 형식에 대한 기술적 보장이 아니기** 때문입니다.

부분적 완화책들과 그 한계:

| 시도 | 하는 일 | 왜 부족한가 |
|---|---|---|
| 시스템 프롬프트를 더 엄격하게 쓰고 실패 시 재시도 | 실패 확률을 낮추고 실패 시 다시 시도 | 근본 원인 미해결. 비용과 지연시간(latency) 증가 |
| `temperature`를 0으로 낮추기 | 출력을 결정론적으로 만들어 변동성 축소 | 결정론적이라고 문법이 옳은 건 아니다. 구문 오류를 차단하지 못함 |
| 백틱(```` ``` ````)으로 감싸게 하고 후처리로 제거 | 코드블록 경계로 사족을 잘라냄 | 백틱 안쪽 JSON 자체의 문법 오류는 그대로 남음 |

> **temperature란**: 다음 토큰을 고를 때의 무작위성 정도를 조절하는 파라미터. 0이면 가장 확률 높은 토큰만 고르고, 높이면 다양성이 늘어납니다. **형식 보장 장치가 아닙니다.**

### 3.3 방법 2: 도구 호출 (Tool Use / Function Calling) — 권장

이것이 신뢰할 수 있는 JSON을 얻는 정석입니다.

**개념**: 모델에게 자유 텍스트를 쓰게 하는 대신, **호출 가능한 "도구"를 정의**하고 그 도구의 **입력 인자를 채우게** 합니다. 그 인자는 API가 구조화된 블록으로 돌려주므로, 우리는 텍스트를 파싱할 필요 없이 그 값을 그대로 씁니다.

**핵심 구성 요소**:

- `tools`: 요청에 첨부하는 도구 정의 목록
- `input_schema`: 각 도구가 받는 인자를 기술한 **JSON Schema**. 필드 이름, 타입, 필수 여부, 설명을 담습니다
- `tool_use`: 응답에 담겨 오는 콘텐츠 블록. 모델이 어떤 도구를 어떤 인자로 부르고 싶은지가 들어 있습니다
- `tool_result`: 우리가 도구를 실제로 실행한 뒤 모델에게 돌려주는 결과 블록

예시(지원 티켓 분류 추출):

```python
tools = [{
    "name": "record_ticket",
    "description": "지원 티켓의 분류 결과를 기록한다",
    "input_schema": {
        "type": "object",
        "properties": {
            "priority": {"type": "string", "enum": ["low", "medium", "high"]},
            "category": {"type": "string"},
            "summary":  {"type": "string", "description": "한 문장 요약"}
        },
        "required": ["priority", "category", "summary"]
    }
}]
```

응답에서 `tool_use` 블록의 `input`을 그대로 꺼내면 이미 파싱된 딕셔너리입니다.

**"추출용 도구(extraction tool)" 패턴**: 실제로 실행할 함수가 없어도 됩니다. 스키마를 강제하기 위한 껍데기 도구를 정의해두고, 모델이 그것을 호출하게 만들어 인자만 받아 쓰는 방식이 널리 쓰입니다.

### 3.4 엄격한 도구 사용 (Strict Tool Use)

도구 호출에 **strict 옵션(엄격한 적용)** 을 켜면, API가 **서버 측에서 디코딩 단계에 스키마를 강제**합니다. 즉 스키마에 맞지 않는 토큰은 애초에 생성될 수 없습니다. 이 경우 구문 오류와 필수 필드 누락이 **구조적으로 차단**됩니다.

따라서 지저분한 스캔 문서 같은 어려운 입력에서도:

- **strict tool_use**: 스키마 준수가 보장됨. 별도의 JSON 복구(JSON-repair) 라이브러리가 필수적이지 않음
- **프롬프트 전용 JSON 요청**: 여전히 유효하지 않은 구문이나 필드 누락으로 벗어날 수 있음

흔한 오해 정리:

- "두 방식은 어차피 같은 모델이 해석하니 신뢰도가 동등하다" → 아닙니다. 한쪽은 확률적 생성, 다른 쪽은 디코딩 제약입니다.
- "도구 정의가 붙으면 프롬프트가 길어져서 오히려 불리하다" → 아닙니다. 형식 보장 이득이 압도적입니다.

### 3.5 스키마 설계: 어디까지 엄격하게 할 것인가

**중요한 구분**: "스키마 준수가 보장된다"는 것과 "값의 **내용**이 옳다"는 것은 다릅니다. strict 도구 사용은 **형태**를 보장할 뿐, 원본에 없는 형식을 만들어내지는 못합니다.

전형적 사례:

> 여러 운송사의 배송 확인 이메일에서 날짜를 뽑는다. 원문 날짜는 `03/14/2026`, `14-Mar-2026`, `2026.03.14` 등 제각각인데, 스키마는 `ship_date`를 **엄격한 ISO 8601 패턴**을 가진 문자열로 정의해 두었다. 그 결과 스키마 유효성 검사(schema validation)가 자주 실패한다.

> **ISO 8601**: 날짜/시간의 국제 표준 표기. 날짜는 `YYYY-MM-DD` (예: `2026-03-14`).

**권장 설계 — 추출과 정규화의 역할 분리(decoupling extraction and normalization)**:

1. 스키마의 `ship_date` 제약을 **평범한 문자열(`type: string`)로 완화(loosen)** 한다 → 모델은 원문 날짜를 실패 없이 그대로 가져온다.
2. **후속 단계(downstream)에서 검증된 날짜 파서 라이브러리**로 ISO 8601로 정규화(normalize)한 뒤 DB에 저장한다.

원칙: **LLM에게는 "원문에서 찾아오기"라는 잘하는 일을 시키고, "형식 변환"이라는 결정론적 작업은 일반 코드에 맡긴다.** 결정론적 코드가 할 수 있는 일을 확률적 모델에 떠넘기지 않습니다.

다른 접근들이 나쁜 이유:

- **엄격한 패턴을 유지한 채 `description`에만 "ISO로 정규화하라"고 적기**: `description`은 스키마 필드에 붙이는 자연어 설명으로 모델의 행동을 유도하는 데 유용하지만, **유도이지 보장이 아닙니다.** 엄격한 패턴 검증을 남겨두면 유효성 검사 실패는 계속됩니다.
- **필드를 아예 빼고 나중에 운송장 조회나 메타데이터로 추론**: 이메일 본문에 있는 데이터를 포기하고 불필요한 복잡성을 들여옵니다.
- **`ship_date_us` / `ship_date_eu` / `ship_date_iso`로 필드 쪼개기**: 데이터 모델이 파편화되고 유지보수가 어려워집니다. 표현 형식은 스키마가 아니라 파싱 계층의 문제입니다.

## 4. 추출 결과의 검증 (Validation)

### 4.1 스키마 검증만으로는 부족하다

**스키마 검증(schema validation)** 은 타입과 형식만 봅니다. `"total": 128.40`은 숫자 형식으로 완벽히 유효하지만, 실제 영수증 금액이 `428.40`이었다면 **형식은 통과하는 잘못된 값(plausible but wrong value)** 입니다.

스캔 문서, OCR, 흐릿한 인쇄물에서는 이런 "그럴듯한 오류"가 반드시 생깁니다. 이건 스키마로 잡을 수 없습니다.

### 4.2 교차 검증 / 산술 일치성 검사 (Cross-Validation, Consistency Check)

**중복된 정보를 함께 추출한 뒤 서로 맞는지 대조**하는 것이 정석입니다.

영수증 예시:

1. **개별 품목 가격(line items)** 을 전부 추출한다
2. **인쇄된 합계(printed total)** 도 추출한다
3. 품목 합을 더해 `calculated_total`을 **코드로 계산**한다
4. `calculated_total`과 `printed_total`이 어긋나는(diverge) 레코드에 **플래그를 세운다**

```python
calculated_total = sum(item["price"] for item in record["line_items"])
if abs(calculated_total - record["printed_total"]) > 0.01:
    record["needs_review"] = True
```

같은 원리를 다른 곳에도 적용할 수 있습니다: 소계+세금 = 합계, 시작일 < 종료일, 개수 × 단가 = 금액 등.

### 4.3 하면 안 되는 것들

- **품목 추출을 생략해 파이프라인을 빠르게 만들기**: 대조할 근거를 스스로 없애는 것입니다. 속도를 위해 검증을 버리는 교환입니다.
- **추출된 값을 그대로 믿기**: 문제를 방치하는 것입니다.
- **모델이 "더 그럴듯한 값"으로 조용히 덮어쓰게 하기(silently overwrite)**: 가장 위험합니다. 원본과 대조할 수 없게 되어 **감사 추적(audit trail)** 이 사라지고, 모델의 추측이 새로운 오류를 만듭니다. **원본 값은 항상 보존하고, 의심 사항은 덮어쓰지 말고 플래그로 표시해 사람이 보게 합니다.**

## 5. 실패 시 재시도 설계 (Retry with Targeted Feedback)

추출이 실패했을 때 어떻게 다시 시도할 것인가도 설계 대상입니다.

### 5.1 대상화된 피드백(targeted feedback)의 3요소

필수 필드 `invoice_number`가 누락된 JSON이 돌아왔다면, 재시도 요청에는 다음 셋이 **모두** 들어가야 합니다.

1. **원본 컨텍스트**: 원래의 PDF/문서. 값을 찾아올 소스가 없으면 채울 수 없습니다.
2. **직전에 실패한 출력**: 모델이 자신이 만든 결과를 보고 무엇을 고쳐야 할지 알 수 있게 합니다. 나머지는 유지하고 빠진 것만 보완할 수 있습니다.
3. **구체적인 오류 지적**: "`invoice_number`가 필수인데 그 시도에서 누락되었다"처럼 **필드명을 명시**합니다.

이는 **멀티턴(multi-turn) 대화**로 구성합니다. 즉 대화 이력(`messages` 배열)에 이전 응답과 피드백을 쌓아 상태를 유지(stateful)하는 방식입니다.

### 5.2 실패하는 재시도 패턴

- **오류 메시지만 단독 전송**: 원본도 이전 출력도 없으니 모델은 무엇을 어디서 고칠지 참조할 대상이 없습니다.
- **똑같은 프롬프트를 그대로 재전송**: 피드백이 0입니다. 샘플링의 무작위성이 우연히 다른 결과를 내주기를 바라는 것뿐이라 같은 오류가 반복될 확률이 높습니다.
- **시스템 프롬프트 문구만 바꿔서 재전송**: 어떤 필드가 빠졌는지 알려주지 않으면 모델은 같은 누락을 반복합니다.

## 6. Message Batches API와 도구 호출 루프

### 6.1 Message Batches API란

Anthropic이 제공하는 **비동기(asynchronous) 대량 요청 처리 API**입니다.

- 여러 요청을 한 배치로 제출하고, 나중에 결과를 받습니다.
- **약 50%의 비용 절감**이 이점입니다.
- 즉시 응답이 필요 없는 대량 작업(문서 일괄 분류, 백필 등)에 적합합니다.

### 6.2 도구 호출 루프는 왜 동기적인가

에이전트가 도구를 쓰는 과정은 다음의 **여러 단계 왕복(round trip)** 입니다.

1. 모델이 `tool_use` 블록으로 "DB 조회 도구를 이 인자로 불러줘"라고 요청 → **여기서 응답이 한 번 끝난다**
2. **애플리케이션이** 실제로 DB를 조회한다 (이건 모델이 아니라 우리 코드가 한다)
3. 우리가 `tool_result`를 담아 **새 요청을 보낸다**
4. 모델이 그 결과를 근거로 추론해 최종 답을 낸다

즉 도구 실행은 모델 바깥에서 일어나며, 그 사이에 **모델 호출이 두 번 이상** 필요합니다.

### 6.3 그래서 무엇이 안 되는가

**단일 배치 요청은 처리 도중에 일시 정지하여 애플리케이션이 제공하는 도구 결과를 받아들일 수 없습니다.** 각 배치 요청은 독립적으로 해결되며, **요청 중간의 왕복(mid-request round trip)이 존재하지 않습니다.** 따라서 "도구 요청 → 결과 수신 → 후속 추론 → 최종 답변"을 **하나의 배치 요청 안에서** 끝낼 수 없습니다.

### 6.4 사실이 아닌 통념들

- "배치 요청은 대화당 메시지 하나로 제한된다" → **거짓.** 배치 요청에도 이전 대화 이력이 담긴 `messages` 배열을 여러 개 넣을 수 있습니다.
- "배치 API에는 `tools`를 첨부할 수 없다" → **거짓.** 도구 정의는 정상적으로 첨부되고 모델은 도구를 요청할 수 있습니다.
- "배치 API가 응답에서 `tool_use` 블록을 조용히 제거한다" → **거짓.** `tool_use` 블록은 정상적으로 반환됩니다.

**정확한 제약은 오직 하나**: 한 요청 안에서 멈췄다가 외부 결과를 받아 이어가는 것이 불가능하다는 점입니다. (배치의 각 요청이 이미 완성된 대화 이력을 담아 한 번에 끝나는 형태라면 도구가 관련된 요청도 배치로 보낼 수 있습니다. 불가능한 것은 *루프 자체*를 배치 안에 넣는 일입니다.)

## 7. LLM 판단 시스템의 지침 설계 (Explicit Criteria)

여기서부터는 "LLM에게 판단을 시키는 시스템"(대표적으로 AI 코드 리뷰 에이전트)을 만들 때의 프롬프트 설계 원칙입니다.

### 7.1 정밀도와 재현율, 오탐

- **오탐 / 거짓 양성(false positive)**: 실제로는 문제가 아닌데 문제라고 지적한 것
- **정밀도(precision)**: 지적한 것들 중 실제 문제인 비율. 오탐이 많으면 정밀도가 낮습니다
- **재현율(recall)**: 실제 문제들 중 잡아낸 비율

리뷰 도구에서 보통 더 치명적인 것은 **낮은 정밀도**입니다. 이유는 다음 절에 있습니다.

### 7.2 신뢰도 기반 필터링이 실패하는 이유

가장 흔한 잘못된 처방은 프롬프트에 이런 줄을 넣는 것입니다.

```
확신하는 이슈만 보고하라. (Only surface issues you are very sure about.)
신뢰도가 높은 지적만 보고하라. (Only report high-confidence findings.)
```

**이렇게 해도 오탐률은 거의 변하지 않습니다.** 왜냐하면:

"높은 신뢰도"라는 말은 **모델에게 무엇을 보고하고 무엇을 건너뛸지에 대한 구체적인 규칙을 전혀 주지 않습니다.** 모델은 '높은 신뢰도'의 정의를 알 수 없으므로, 변경 이전에 오탐을 만들어냈던 **바로 그 내재적 판단 기준을 그대로 다시 적용**합니다. 애초에 모델은 자기 출력을 그렇게 확신했기 때문에 지적한 것입니다.

같은 이유로, 다음 형태의 지침들도 모두 **실질적으로 신뢰도 기반**이라 효과가 없습니다.

- "내부 신뢰도 점수가 0.9를 넘으면 보고하라" (숫자를 붙여도 주관적 자기평가)
- "2차 검토 패스가 1차의 신뢰도 점수를 확인하면 보고하라" (검증을 겹쳐도 기반은 여전히 신뢰도 점수)
- "시니어 엔지니어가 동의할 것이라고 장담할 수 있으면 보고하라" (암묵적 기준에 대한 주관적 추측)
- "주변 코드에 비해 특이해 보이면 보고하라" (주관적 인상이자, 버그가 아닌 스타일 지적)

### 7.3 대안: 명시적/범주적 기준 (Explicit / Categorical Criteria)

**무엇을 항상 보고하고, 무엇을 항상 건너뛸지를 범주로 직접 정의합니다.** 모델의 확신도가 아니라 **코드에서 객관적으로 확인 가능한 조건**으로 씁니다.

보고/스킵 쌍의 예:

```
보고하라: 보안 취약점을 유발하는 변경, 또는 기존 동작을 망가뜨리는 정확성 버그.
건너뛰어라: 서식 선호, 그리고 해당 파일에 자리 잡은 지역적 관례에서 벗어난 정도의 차이.
```

버그 탐지 카테고리를 위한 더 구체적인 재작성 예:

```
변수, 인자, 또는 반환값이 다음 중 하나와 모순되게 사용될 때만 이슈를 보고하라:
  - 선언된 타입
  - 문서화된 계약(contract)
  - 코드 다른 곳에 명시된 전제 조건(precondition)
```

이 지침이 좋은 이유는 **판단 근거가 코드 안에 있고, 검증 가능하다**는 점입니다. 모델이 "확신하는지"를 스스로 물을 필요가 없습니다.

반대로 **"공식 스타일 가이드를 벗어난 모든 변경을 보고하라"** 같은 지침은 명시적이긴 하지만, 주관적 스타일 노이즈를 대량 생산하므로 "주관적 선호로 인한 소음을 피한다"는 목표와 충돌합니다. 명시적인 것만으로는 부족하고, **범주 선택 자체가 중요도에 맞아야** 합니다.

### 7.4 주석-코드 모순 판정

"실제 코드 동작과 모순되는 주석만 지적한다"는 명시적 기준이 있을 때의 적용 예:

> 독스트링(docstring): "캐시된 값이 있으면 그것을 반환하고, 없으면 API에서 가져온다."
> 실제 코드: 캐시 확인 없이 **항상** API를 호출한다.

**이것은 보고 대상입니다.** 독스트링이 캐싱 동작에 대한 **구체적이고 검증 가능한(checkable) 주장**을 하고 있고, 코드의 실제 **제어 흐름(control flow)** 이 그것과 직접 모순되기 때문입니다.

> **독스트링(docstring)**: 함수/클래스 바로 안에 쓰는 설명 문자열. 파이썬 등에서 사용하며, 호출자가 읽는 문서 역할을 합니다.

여기서 정리해 둘 개념들:

- **주석은 "의도"일 뿐이라 불일치는 문제가 아니다?** 아닙니다. 조건부 동작을 구체적으로 서술한 이상, 그것은 호출자가 신뢰하는 **동작 계약(contract)** 이며 실제와 다르면 명백한 결함입니다.
- **호출 횟수(한 곳에서만 쓰이는 함수는 면제)?** 호출 지점 개수는 주석-코드 모순 판정과 아무 관계가 없습니다.
- **캐싱은 구현 세부사항이라 검토 대상 제외?** 문서에 명시적으로 서술된 순간 그것은 내부 구현을 넘어 외부에 약속된 계약이 됩니다.

### 7.5 경고 피로도(Alert Fatigue) 관리

**경고 피로도**란 부정확한 알림이 반복되면 사람들이 **알림 전체를 무시하게 되는** 현상입니다. 핵심은 **오염이 카테고리를 넘어 번진다**는 점입니다.

> 코드 리뷰 도구의 "성능 제안" 카테고리가 오탐률 70%다. 그 결과 개발자들이 **잘 작동하는 다른 카테고리의 지적까지 포함해** 도구의 모든 결과를 읽지 않게 되었다.

몇 주에 걸쳐 그 카테고리의 프롬프트를 개선할 예정일 때 **즉시 취할 조치**:

**문제 카테고리를 일시적으로 비활성화(disable)하고, 정확한 카테고리만 노출한다. 별도로 그 카테고리의 프롬프트를 개선·검증한 뒤 재활성화한다.**

이유: 노이즈 출처를 즉시 차단해야 피로도가 해소되고 나머지 결과에 대한 신뢰가 빠르게 회복됩니다. 이것이 AI 품질 관리의 표준 절차입니다 — **끄고, 고치고, 검증하고, 다시 켠다.**

효과 없는 대안들:

- **심각도 레이블을 "정보성(informational)"으로 낮추기**: 노이즈가 계속 화면에 출력되는 한, 개발자가 다른 카테고리를 무시하는 행동은 멈추지 않습니다.
- **문제 카테고리를 잘 작동하는 정확성 카테고리에 병합하기**: 오탐을 깨끗한 카테고리에 섞어 **그 카테고리의 신뢰까지 함께 파괴**합니다. 반복 노출로 신뢰가 쌓이지 않습니다.
- **"일부 카테고리는 정밀도가 낮습니다" 면책 배너 달기**: 필터링 부담을 사용자에게 떠넘길 뿐 피로도를 전혀 줄이지 못합니다.

---

## 8. 전체를 관통하는 설계 원칙 요약

1. **경계는 태그로 만든다.** 지시/예시/실제 입력을 구조적으로 분리한다.
2. **예시는 다양하게.** 예시 집합에 우연히 공통된 특징은 그대로 편향으로 학습된다.
3. **형식 보장은 부탁이 아니라 메커니즘으로.** 자연어 지시 대신 `input_schema` + `tool_use`, 필요하면 strict.
4. **확률적 작업과 결정론적 작업을 분리한다.** 찾아오기는 모델, 형식 변환·계산·검증은 코드.
5. **스키마는 느슨하게, 검증은 나중에 확실하게.** 엄격한 패턴을 스키마에 박으면 실패율만 올라간다.
6. **형식 검증과 내용 검증은 다르다.** 교차 검증으로 그럴듯한 오류를 잡고, 값을 덮어쓰지 말고 플래그를 세운다.
7. **재시도에는 원본 + 이전 실패 결과 + 구체적 지적을 모두 담는다.**
8. **판단 기준은 신뢰도가 아니라 범주로 쓴다.** "확신하면 보고"는 아무 규칙도 주지 않는다.
9. **노이즈는 즉시 차단한다.** 신뢰는 카테고리 단위가 아니라 도구 단위로 무너진다.
10. **배치 API는 왕복이 없는 단방향 처리다.** 에이전트 도구 루프를 담을 수 없다.

## 용어 사전 (Glossary)

| 영어 용어 | 설명 |
|---|---|
| **Prompt** | 모델에게 보내는 입력 텍스트 전체. 배경, 지시, 예시, 실제 입력이 섞인다 |
| **System prompt** | 대화 전체에 걸쳐 모델의 역할과 규칙을 정하는 상위 지시문 |
| **Prompt structuring** | 프롬프트의 각 영역을 명확히 구분해 배치하는 설계 |
| **XML tags (`<example>`, `<examples>`)** | 프롬프트 영역의 경계를 표시하는 태그. 개별 예시는 `<example>`, 전체 묶음은 `<examples>`로 감싼다 |
| **Few-shot prompting** | 프롬프트 안에 입력-출력 견본 몇 개를 넣어 원하는 동작을 유도하는 기법 |
| **Zero-shot** | 예시 없이 지시문만으로 시키는 방식 |
| **In-context learning** | 재학습 없이 프롬프트 안의 예시 패턴만으로 동작이 바뀌는 현상 |
| **Spurious pattern** | 의도치 않은 상관 패턴. 예시들이 우연히 공유한 특징(길이, 언어 등)을 규칙으로 오학습하는 것 |
| **Few-shot example bias** | 편향된 예시 집합이 특정 유형 밖의 입력에서 성능 저하를 일으키는 현상 |
| **Example diversity** | 예시를 길이·언어·형태·정보 위치 등에서 다양하게 구성하는 것 |
| **Regression** | 이전에 잘 되던 동작이 변경 이후 나빠지는 성능 저하 |
| **Model drift** | 모델 자체가 시간에 따라 변해 성능이 달라지는 현상. 프롬프트 변경 직후의 저하와 혼동하면 안 됨 |
| **Context window** | 모델이 한 번에 볼 수 있는 토큰의 최대 길이 |
| **Temperature** | 다음 토큰 선택의 무작위성 파라미터. 0이면 결정론적. 형식 보장 장치가 아님 |
| **Deterministic** | 결정론적. 같은 입력에 항상 같은 출력 |
| **Structured output** | 기계가 파싱 가능한 형태(주로 JSON)의 모델 출력 |
| **JSON** | `{"key": "value"}` 형태의 데이터 표기법. 문법이 조금만 어긋나도 파싱 실패 |
| **JSON Schema** | JSON 데이터의 필드명·타입·필수 여부·설명을 기술하는 명세 |
| **Malformed brackets** | 괄호/따옴표가 어긋나 파싱이 실패하는 상태 |
| **Stray commentary** | JSON 앞뒤에 붙는 불필요한 설명 텍스트(사족) |
| **Tool use / Function calling** | 모델이 정의된 도구를 호출하겠다고 요청하고, 그 인자를 구조화된 형태로 받는 방식 |
| **`tools`** | 요청에 첨부하는 도구 정의 목록 파라미터 |
| **`input_schema`** | 도구가 받는 인자를 기술한 JSON Schema |
| **`tool_use` block** | 응답에 담겨 오는, 모델의 도구 호출 요청 블록. 인자가 구조화되어 있음 |
| **`tool_result` block** | 애플리케이션이 도구를 실행한 결과를 모델에게 돌려주는 블록 |
| **Strict tool use** | 서버 측 디코딩 단계에서 `input_schema` 준수를 강제하는 옵션. 구문 오류·필드 누락을 구조적으로 차단 |
| **Extraction tool** | 실제 실행 함수 없이, 스키마를 강제해 데이터를 뽑기 위해 정의하는 도구 |
| **`description` (schema)** | 스키마 필드에 붙이는 자연어 설명. 모델을 유도하지만 보장하지는 않음 |
| **Schema validation** | 출력이 스키마의 타입·형식에 맞는지 검사하는 것. 값의 정확성은 보장하지 않음 |
| **ISO 8601** | 날짜/시간 국제 표준 표기. 날짜는 `YYYY-MM-DD` |
| **Normalization** | 제각각인 표현을 하나의 표준 형식으로 변환하는 것 |
| **Downstream** | 파이프라인의 후속 단계 |
| **Decoupling extraction & parsing** | 모델은 원문 추출만, 형식 변환은 결정론적 코드가 담당하도록 역할을 분리하는 설계 |
| **Plausible error** | 형식은 유효해서 스키마 검증을 통과하지만 값이 틀린 오류 |
| **Cross-validation (data)** | 중복 정보를 함께 추출해 서로 대조하는 검증 |
| **Consistency check** | 품목 합 = 인쇄된 합계처럼 산술적 일치를 확인하는 검사 |
| **`calculated_total`** | 개별 품목을 코드로 합산한 값. 인쇄된 합계와 대조하는 데 씀 |
| **Flag** | 의심 레코드에 표시를 남겨 사람 검토로 보내는 것. 값을 덮어쓰지 않는 것이 핵심 |
| **Audit trail** | 감사 추적. 원본과 변경 이력을 남겨 사후 검증을 가능하게 하는 기록 |
| **Targeted feedback** | 무엇이 왜 틀렸는지를 구체적으로 지목하는 피드백 |
| **Stateful retry** | 원본·이전 출력·피드백을 대화 이력에 유지한 채 다시 시도하는 방식 |
| **Multi-turn** | 여러 차례 주고받는 대화 구성 |
| **`messages` array** | 대화 이력을 담는 배열. 배치 요청에도 여러 개 넣을 수 있음 |
| **Sampling variance** | 확률적 생성의 결과 변동성. 이것에만 기대는 재시도는 나쁜 설계 |
| **Message Batches API** | 비동기 대량 요청 처리 API. 약 50% 비용 절감. 요청 중간 왕복은 불가능 |
| **Asynchronous** | 비동기. 제출과 결과 수신이 분리된 처리 |
| **Round trip** | 요청-응답 왕복 |
| **Mid-request round trip** | 한 요청 처리 도중에 외부 결과를 받아 이어가는 왕복. 배치에서는 불가능 |
| **Latency** | 지연시간. 요청부터 응답까지 걸리는 시간 |
| **Agent workflow** | 모델이 도구를 호출하고 결과를 받아 다시 추론하는 다단계 작업 흐름 |
| **False positive** | 오탐. 문제가 아닌데 문제라고 지적한 것 |
| **False positive rate** | 오탐률 |
| **Precision** | 정밀도. 지적한 것 중 실제 문제인 비율 |
| **Recall** | 재현율. 실제 문제 중 잡아낸 비율 |
| **Confidence-based filtering** | 모델의 주관적 확신도로 보고 여부를 거르는 방식. 구체적 규칙이 없어 효과가 없음 |
| **Confidence threshold** | 신뢰도 임계값. 숫자를 붙여도 여전히 주관적 자기평가 |
| **Explicit criteria** | 명시적 기준. 무엇을 보고/스킵할지 구체적으로 명시한 규칙 |
| **Categorical criteria** | 범주적 기준. 확신도가 아니라 문제 유형(보안·정확성 vs 서식·스타일)으로 정하는 기준 |
| **Control flow** | 제어 흐름. 조건문·분기 등 코드가 실제로 실행되는 경로 |
| **Docstring** | 함수/클래스 안에 쓰는 설명 문자열. 호출자가 읽는 문서 |
| **Contract** | 동작 계약. 함수가 외부에 약속한 동작 명세 |
| **Precondition** | 전제 조건. 코드가 실행되기 전에 성립해야 하는 조건 |
| **Local conventions** | 특정 파일/모듈에 자리 잡은 지역적 코딩 관례 |
| **Alert fatigue** | 경고 피로도. 부정확한 알림이 반복되어 전체 알림을 무시하게 되는 현상 |
| **Severity label** | 심각도 레이블(critical/warning/informational 등). 낮춰도 노이즈 출력 자체는 남음 |
| **Prompt iteration** | 프롬프트를 반복 개선하고 검증하는 작업 |
