# 시나리오3_리서치시스템

## 질문 1

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : The system receives a request to assess how a new data privacy regulation affects the healthcare, finance, and education sectors, with one comprehensive cited report expected. How should the coordinator structure this work?

**A.** Delegate the entire request to a single search subagent so all three sectors are covered in one context and cross-sector comparisons stay consistent.

**설명**

세 가지 서로 다른 조사를 하나의 서브에이전트에 몰아넣으면 병렬성을 포기하게 되고 주의력이 분산되어 어떤 섹터는 깊게, 어떤 섹터는 얕게 분석될 위험이 있다. 섹터 간 일관성은 종합(synthesis) 단계에서 코디네이터가 담당할 일이며, 분해를 회피할 이유가 되지 않는다.

**B.** Spawn three parallel subagents whose prompts name only the assigned sector, relying on each to inherit the coordinator's conversation history for the request details.

**설명**

포크(fork)되지 않은 서브에이전트는 부모의 대화 기록을 상속받지 않으며, 각각 위임 프롬프트가 제공하는 내용만 담긴 새로운 컨텍스트로 시작한다. 섹터 이름만 받은 서브에이전트는 규제 세부사항과 보고 요구사항을 알지 못해 사용할 수 없는 결과를 내놓게 된다.

**C(정답).** Split the request into three sector subtasks, run parallel subagents that each receive the full request context in their prompts, then synthesize results into one report.

**설명**

이것이 다중 관심사 요청을 위한 올바른 패턴이다. 독립적인 항목들로 분해하고, 섹터들이 서로 의존하지 않으므로 동시에 조사하며, 서브에이전트가 새로운 컨텍스트로 시작하기 때문에 공유 요청 컨텍스트를 명시적으로 전달한다. 그런 다음 코디네이터가 반환된 요약들을 하나의 통합 보고서로 병합한다.

**D.** Investigate the three sectors sequentially, feeding each subagent the findings from the prior sector so later analyses can build on earlier discoveries.

**설명**

세 섹터 조사는 서로 독립적이므로 순차적으로 진행하면 인위적인 의존성이 생기고 전체 지연 시간이 대략 세 배로 늘어난다. 하위 작업들이 서로의 결과에 의존하지 않을 때는 병렬 위임이 문서화된 접근 방식이다.

### 전반적인 설명

이 문제는 다중 관심사 요청에 대한 표준 오케스트레이션 패턴을 테스트한다. 즉, 별개의 항목들로 분해하고, 각각을 병렬로 조사하며, 통합된 결과로 종합하는 것이다. 세 섹터 분석은 독립적이므로 코디네이터는 한 턴에서 여러 서브에이전트 호출을 발생시켜야 한다. 그러면 독립적인 작업 흐름들이 세 개를 합한 시간이 아니라 가장 느린 것 하나의 시간 정도로 완료된다. SDK의 서브에이전트 문서는 별도의 에이전트 인스턴스에 위임하는 것의 핵심 이점으로 병렬화를 꼽고 있다.

이 패턴이 작동하는 사고 모델은 두 축으로 이루어진다. 첫째는 컨텍스트 격리다. 각 서브에이전트는 자신만의 대화에서 실행되므로 중간 검색과 도구 결과가 코디네이터의 컨텍스트를 부풀리지 않으며, 최종 메시지만 반환된다. 둘째는 그 직접적인 결과인 명시적 컨텍스트 전달이다. 포크가 아닌 서브에이전트는 새로 시작하므로 공유 컨텍스트(해당 규제, 리서치 목표, 인용 요구사항)가 모든 위임 프롬프트에 포함되어야 한다. 상속된 대화 기록에 의존하는 방식이 실패하는 이유가 바로 이것이며, 문서에는 서브에이전트가 필요로 하는 파일 경로, 결정 사항, 기준은 프롬프트 문자열에 직접 넣어야 한다고 명시되어 있다.

하위 작업들이 독립적일 때 순차 조사는 이득 없이 지연 시간만 늘린다. 또한 서로 관련 없는 섹터 간에 결과를 연결하면 통찰보다는 오염을 초래할 위험이 있다. 모든 것을 하나의 서브에이전트에 위임하면 분해 자체를 회피하게 되어, 세 개의 심층 조사가 하나의 컨텍스트에 집중되고 주제 전반에 걸쳐 주의력이 분산된다. 코디네이터-서브에이전트 설계가 만들어내는 트레이드오프는 정확히 이것이다. 명시적 프롬프트 구성에 약간의 비용을 지불하고 동시성, 집중된 컨텍스트, 그리고 주제별 간결한 요약을 바탕으로 한 깨끗한 종합 단계를 얻는 것이다. 각 에이전트 자신의 루프 내에서 도구 호출과 결과가 어떻게 흐르는지는 Agent SDK의 에이전트 루프 문서도 참고하라.


## 질문 2

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : The team adds a weekly market-brief workflow: retrieve the same five sources, summarize each, and assemble a fixed-format report. The steps never vary across runs. Which decomposition approach fits this workflow?

**A.** Run an autonomous agent loop that decides its own steps each week, stopping when it judges the brief complete.

**설명**

자율 에이전트는 단계 수를 예측할 수 없고 경로를 하드코딩할 수 없는 개방형 문제에 적합하다. 완전히 예측 가능한 주간 브리핑은 자율성에서 얻을 이득이 없으면서 더 높은 비용과 오류 누적 위험만 떠안게 된다.

**B.** Handle the whole brief in a single comprehensive request so all summarization decisions share one context.

**설명**

하나의 큰 요청은 분해를 완전히 포기하게 만들어, 한 번의 호출이 검색 요약과 보고서 조립을 동시에 처리해야 한다. 프롬프트 체이닝은 정확히 이를 피하기 위해 존재한다. 작업을 더 단순한 순차 호출로 나누면 약간의 지연 시간을 대가로 각 단계의 정확도를 높일 수 있다.

**C.** Have the coordinator generate the subtask list dynamically at run time based on what the initial retrieval reveals.

**설명**

동적 하위 작업 생성(오케스트레이터-워커 패턴)은 하위 작업을 사전에 예측할 수 없는 작업을 위한 것이다. 여기서는 소스, 단계, 출력 형식이 매주 동일하므로 동적 분해의 추가 비용과 예측 불가능성을 감수해도 얻는 것이 없다.

**D(정답).** Implement a fixed prompt chain where each step consumes the prior step's output, with programmatic gates between steps.

**설명**

이 워크플로우는 고정되어 있고 사전에 알 수 있는 하위 작업들로 깔끔하게 분해되며, 이는 프롬프트 체이닝이 설계된 정확한 사례다. 각 호출은 더 단순하고 정확해지며, 단계 사이의 프로그래밍적 게이트가 파이프라인이 올바른 방향을 유지하는지 검증할 수 있다.

### 전반적인 설명

핵심 선택 규칙은 제어 흐름 구조를 작업의 불확실성 정도에 맞추는 것이다. Anthropic은 LLM 호출이 미리 정의된 코드 경로를 통해 오케스트레이션되는 워크플로우와, 모델이 자신의 프로세스를 동적으로 지휘하는 에이전트를 구분하며, 에이전트적 유연성이 추가될수록 지연 시간, 비용, 예측 가능성 측면의 비용이 커지기 때문에 작동하는 가장 단순한 구조를 권장한다. 동일한 다섯 개의 소스와 동일한 출력 형식을 갖는 주간 브리핑은 단계 불확실성이 전혀 없으므로 프롬프트 체인이 적합하다. 각 단계는 이전 단계의 출력을 소비하고, 모든 호출이 더 작고 정확하게 처리하기 쉬워지며, 단계 사이의 프로그래밍적 게이트가 파이프라인이 계속되기 전에 중간 결과를 결정적으로 검증할 수 있다.

동적 대안들은 다른 문제를 해결한다. 오케스트레이터-워커 패턴은 필요한 하위 작업이 미리 정해지지 않고 입력별로 선택되어야 하는 작업을 위해 존재한다. 이를 고정된 주간 루틴에 적용하면 이미 알고 있는 계획을 재현하거나 오히려 그 계획에서 벗어나기만 하는 런타임 계획 단계가 추가될 뿐이다. 자율 에이전트 루프는 한 걸음 더 나아가 모델이 언제 끝났는지 스스로 판단하게 하는데, 이는 단계 수가 진짜로 예측 불가능하고 모델의 판단을 충분히 신뢰할 수 있는 경우에 적합하며, 매번 단계가 동일한 경우에는 적합하지 않다. 그리고 모든 것을 하나의 종합적인 요청으로 압축하면 분해 자체를 포기하게 되어, 작업을 분리함으로써 해결하려 했던 주의력과 정확도 문제가 다시 나타난다.

사고 모델: 중간 결과가 다음 하위 작업을 결정하는 리서치 시스템의 개방형 주제 조사에는 동적 분해를 남겨두고, 그 주변의 반복적이고 템플릿화된 작업에는 고정 파이프라인을 사용하라. 프롬프트 체이닝, 오케스트레이터-워커, 그리고 각각이 적용되는 시점에 대한 Anthropic의 가이드는 Building Effective Agents를 참고하라.


## 질문 3

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : The synthesis subagent's drafts frequently attribute claims to the wrong sources. Investigation shows the search and analysis subagents return findings as prose paragraphs with all consulted sources listed at the end. How should subagent outputs be restructured?


**A(정답).** Have each subagent emit structured findings that pair every claim with its source URL, document name, and publication date.

**설명**

이것이 정답인 이유는, 각 주장이 구조화된 매핑 안에서 자신만의 소스 메타데이터를 함께 가질 때만 종합 과정에서 출처 표기가 살아남기 때문이다. 끝에 소스 목록만 붙은 프로즈 형태는 종합 에이전트가 어떤 소스가 어떤 주장을 뒷받침하는지 추측하게 만들며, 이는 정확히 관찰된 실패 현상이다.

**B.** Have each subagent append a deduplicated bibliography of every source it consulted to the end of its summary.

**설명**

참고문헌 목록은 어떤 소스가 사용되었는지는 나열하지만 개별 주장을 특정 소스와 연결하지는 않는다. 종합 에이전트는 여전히 주장-소스 매핑을 추측해야 하므로 출처 오귀속이 계속된다.

**C.** Pass the complete raw source documents to the synthesis agent so it can trace each claim back to its origin itself.

**설명**

원문 그대로를 전달하면 종합 에이전트의 컨텍스트가 미가공 자료로 가득 차게 되고, 상위 에이전트들이 이미 수행한 출처 표기 작업을 다시 하게 만든다. 이는 토큰 사용량을 늘리면서도 여전히 오류에 취약한데, 모델이 주장과 소스를 다시 매칭해야 하기 때문이다.

**D.** Have the coordinator keep a master registry of all sources consulted and attach it to the report during final aggregation.

**설명**

코디네이터 수준의 레지스트리는 출처 표기를 주장 자체와 분리시키기 때문에, 최종 보고서는 소스를 나열할 수는 있어도 어떤 소스가 어떤 진술을 뒷받침하는지는 말할 수 없다. 매핑은 분리된 목록에 있는 것이 아니라 각 주장과 함께 이동해야 한다.

### 전반적인 설명

멀티 에이전트 파이프라인에서는 구조화된 주장-소스 매핑으로 전달되지 않으면 매 핸드오프마다 출처 표기가 손실된다. 각 서브에이전트는 자신의 프롬프트에 전달된 것만 볼 수 있으며, 종합 에이전트는 애초에 인코딩되지 않은 출처를 복원할 수 없다. 프로즈 문단 뒤에 소스 목록이 이어지는 형태는 여러 주장과 여러 소스를 주지만 이를 신뢰성 있게 짝지을 방법이 없다. 해결책은 상위 에이전트들이 각 발견 사항이 자신만의 메타데이터(소스 URL, 문서명, 발행일)를 갖고 이동하는 구조화된 레코드를 내놓게 하는 것이다. 그러면 하위 에이전트들은 추론이 아니라 기계적으로 매핑을 보존할 수 있다.

이는 다중 문서 프롬프트에 대한 Anthropic 자체 가이드와도 일치한다. 예를 들어 각 문서를 <document> 태그로 감싸고 별도의 <document_content>와 <source> 서브태그를 두어 콘텐츠와 메타데이터를 명시적 구조로 분리하면, 모델이 어떤 소스가 어떤 텍스트에 속하는지 추측할 필요가 없어진다. Prompt templates and variables를 참고하라. 구조화된 레코드에 발행일을 포함시키면 종합 과정에서 소스 간 시간적 차이가 모순으로 잘못 읽히는 것도 방지할 수 있다. 파이프라인이 Messages API의 문서 블록을 사용할 때, Citations 기능도 동일한 원칙을 적용한다. 즉 문서의 소스 콘텐츠만 인용 가능하며, 제목과 컨텍스트는 그 옆에 메타데이터로 함께 실린다.

대안들은 모두 같은 지점에서 실패한다. 끝에 붙는 참고문헌 목록과 코디네이터가 보유한 레지스트리는 둘 다 어떤 소스가 사용되었는지는 기록하지만 각 소스가 무엇을 뒷받침하는지는 기록하지 않으므로, 주장 단위의 출처 표기는 여전히 추측에 의존한다. 종합 에이전트에게 원문을 그대로 전달하는 것은 상위 에이전트들의 작업을 버리고, 종합 컨텍스트를 미가공 자료로 부풀리며, 해결하려 했던 매칭 문제를 다시 불러온다.


## 질문 4

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : Simple lookup requests currently traverse all four subagents in order, multiplying latency and cost even when only a web search is needed. How should the coordinator be designed so each request invokes only the subagents it requires?

**A.** Mention every subagent by name in the coordinator's delegation prompts so each stage is explicitly forced rather than left to automatic matching.

**설명**

서브에이전트를 명시적으로 지정하면 자동 설명 매칭을 건너뛰고 강제로 호출된다. 모든 요청에서 네 개를 모두 이름으로 강제하면 설계가 없애려는 전체 파이프라인 동작을 오히려 고착시키게 되며, 선택적 위임을 가능하게 하지 못한다.

**B.** Implement a keyword-matching classifier in application code that preselects the required subagents before the coordinator receives the request.

**설명**

키워드 분류기는 모델 기반 선택을 모든 표현 방식을 예측해야 하는 취약한 하드코딩 계층으로 대체한다. 이는 인프라를 추가하면서 모호하거나 다중 파트로 이루어진 요청에 대해 추론하는 코디네이터의 능력을 버리게 되는데, 이것이야말로 에이전트 아키텍처가 제공하는 판단력이다.

**C.** Keep the fixed four-stage flow but move simple requests to subagents on a faster model tier so full traversal completes more quickly.

**설명**

더 빠른 모델 티어는 각 단계를 단축시키지만 요청이 필요로 하지 않았던 단계까지 여전히 실행하므로, 비용과 지연 시간은 불필요한 작업만큼 여전히 곱해진다. 문제는 각 서브에이전트가 얼마나 빠른지가 아니라 어떤 서브에이전트가 실행되는지이다.

**D(정답).** Write distinct, specific descriptions for each subagent and prompt the coordinator to select and invoke only those whose descriptions match the request.

**설명**

이것이 정답인 이유는 Agent SDK의 라우팅이 설명(description) 기반으로 이루어지기 때문이다. Claude는 작업을 각 AgentDefinition의 설명과 매칭시켜 어떤 서브에이전트를 호출할지 결정한다. 명확하고 차별화된 설명과, 관련 전문가를 선택하는 데 초점을 맞춘 코디네이터 프롬프트가 결합되면 모델이 요청에 필요 없는 단계를 건너뛸 수 있다.

### 전반적인 설명

Claude Agent SDK에서는 코디네이터가 누가 무엇을 할지 결정하기 위해 하드코딩된 파이프라인이 필요하지 않다. Claude는 작업을 각 AgentDefinition의 설명과 매칭시켜 서브에이전트에 작업을 라우팅한다. 설명이 선택 신호이며, 코디네이터의 프롬프트가 그 결정의 틀을 제공한다. 설명이 명확하고 구체적이며("현재 소스를 웹에서 검색한다", "제공된 문서를 분석한다") 코디네이터가 요청이 실제로 필요로 하는 전문가만 호출하도록 지시받으면, 단순 조회 요청은 네 단계 순회 대신 단 하나의 Agent 도구 호출만으로 처리될 수 있다. 이것이 동적 선택이다. 모델이 쿼리가 무엇을 요구하는지 추론하는 것이며, 이는 정확히 에이전트형 코디네이터가 존재하는 이유인 판단력이다.

여기서 사고 모델은, 각 서브에이전트 호출이 자신만의 컨텍스트와 자신만의 API 비용을 갖는 새롭고 격리된 인스턴스라는 것이다. 그래서 불필요한 단계를 순회하는 것이 비싼 이유다. 매 단계가 설정을 반복하고, 토큰을 소비하고, 지연 시간을 더하며, 부모는 여전히 각 단계에 컨텍스트를 명시적으로 전달해야 한다. 선택적 위임은 고정 파이프라인과의 트레이드오프로 존재한다. 파이프라인은 예측 가능하고 테스트하기 쉽지만 매 요청마다 전체 비용을 치른다. 반면 설명 기반 라우팅은 요청이 요구하는 작업에 대해서만 비용을 지불한다.

대안들은 모두 이를 놓치고 있다. 애플리케이션 코드의 키워드 분류기는 새로운 표현 방식으로 일반화될 수 없는 하드코딩된 의사결정 트리를 다시 만들며, 코디네이터가 이미 수행하는 추론을 중복시킨다. 모든 서브에이전트를 이름으로 언급하면 강제 호출이 발생하여 자동 매칭을 건너뛰게 되고, 전체 파이프라인을 제거하는 대신 고착시킨다. 더 빠른 모델 티어는 단계별 시간을 줄이지만 단계 수는 줄이지 않으므로, 낭비되는 작업은 단위당 비용만 저렴해질 뿐 여전히 낭비된다.

설명 기반 호출, 이름에 의한 강제 호출, 서브에이전트별 설정이 어떻게 작동하는지는 SDK의 Subagents 문서를 참고하라.

### 전반적인 설명

오케스트레이터-워커 아키텍처에서 코디네이터는 단순한 디스패처가 아니다. 넓은 리서치 주제를 명확하고 경계가 잘 잡힌 하위 작업으로 나누는 책임을 지는 구성 요소다. 각 서브에이전트는 자신이 받은 위임 프롬프트에서 출발하므로, 그 프롬프트가 한 워커의 작업을 다른 워커와 구분 짓는 주된 레버다. 모든 서브에이전트가 동일하게 모호한 지시를 받으면 리서치 영역을 나누는 것이 아무것도 없게 된다. 각 에이전트는 독립적으로 가장 눈에 띄는 줄기(여기서는 생산성 연구)를 선택하게 되어, 거의 중복된 결과를 내면서도 전체 하위 주제는 조사되지 않은 채 남는다.

## 질문 6

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : Your legal team requires that the web search subagent never fetch content from a list of embargoed domains. In testing, system prompt instructions still allow an occasional fetch to slip through. What enforcement design guarantees compliance?

**A.** Add few-shot examples of refusing embargoed-domain requests and instruct the subagent to verify each URL against the list before fetching.

**설명**

퓨샷 예시와 자체 검증 지시는 여전히 프롬프트 지침에 불과하다. 모델은 이를 확률적으로 적용하며, 그럼에도 위반하는 호출을 만들어냈을 때 파이프라인 내에서 이를 막는 것이 아무것도 없다. 이러한 기법들은 위반율을 낮출 수는 있지만 컴플라이언스 요구사항이 요구하는 보장을 제공할 수 없다.

**B.** Add the embargoed domain list to the fetch tool's description and restate the restriction in bold at the top of the subagent's system prompt.

**설명**

도구 설명과 시스템 프롬프트 지시는 모델이 확률적으로 따르는 지침이며, 실행되는 코드가 아니다. 시나리오는 이미 프롬프트 기반 지시가 간혹 위반을 허용하는 상황을 보여주고 있으며, 강조를 추가하는 것은 실패율을 낮추기는 하지만 없애지는 못한다.

**C(정답).** Register a PreToolUse hook that inspects each fetch call's tool input and returns a deny decision with a reason when the URL matches an embargoed domain.

**설명**

이것이 정답인 이유는 PreToolUse가 도구가 실행되기 전에 발생하므로, 훅이 tool_name과 tool_input을 검사하고 거부(deny) 권한 결정을 반환할 수 있어 금지된 fetch가 절대 실행되지 않도록 보장하기 때문이다. 거부와 함께 이유를 포함시키면 모델이 왜 호출이 차단되었는지 알고 접근 방식을 조정할 수 있다. 코드 수준의 인터셉션은 프롬프트 지시가 제공할 수 없는 결정적 보장을 제공한다.

**D.** Register a PostToolUse hook that scans each fetch call's returned content and strips any material from embargoed domains before the model consumes it.

**설명**

PostToolUse는 도구가 이미 성공적으로 실행된 후에만 동작하므로, 훅이 발생하는 시점에는 금지된 도메인으로의 fetch가 이미 일어난 뒤다. 이후에 콘텐츠를 제거하면 모델로부터 데이터를 숨길 수는 있지만, 컴플라이언스 규칙이 요구하는 금지된 요청 자체를 막을 수는 없다.

### 전반적인 설명

이 문제는 프로그래밍적 강제와 프롬프트 지침 사이의 핵심적인 구분을 테스트한다. Claude Agent SDK에서 훅은 에이전트 생명주기의 고정된 지점에서 실행되는 코드다. PreToolUse 훅은 모델이 도구 호출을 요청했을 때, 하지만 하니스가 이를 실행하기 전에 발생한다. 콜백은 tool_name과 tool_input을 포함한 요청 세부사항을 받고, "allow", "deny", "ask", "defer" 같은 permissionDecision을 반환할 수 있으며, 호출이 거부될 때 모델에게 다시 전달되는 permissionDecisionReason도 함께 반환할 수 있다. 이 검사가 일치하는 모든 호출에 대해 코드로 실행되기 때문에, 위반하는 fetch는 절대 네트워크에 도달할 수 없다. 이 보장은 결정적이며, 이것이 바로 컴플라이언스와 법적 요구사항이 요구하는 것이다.

사고 모델은 파이프라인이다. 모델이 행동을 제안하고, 훅이 이를 판정하며, 그 이후에야 하니스가 실행한다. PostToolUse는 실행의 반대편에 위치하므로, 모델이 소비할 결과를 로그로 남기거나, 잘라내거나, 정규화하기에 적합한 지점이지만, 이미 실행된 행동을 막는 데는 구조적으로 무력하다. 프롬프트 기반 접근(도구 설명, 강조된 지시, 퓨샷 예시, 자체 검증 단계)은 모델의 행동을 형성하고 위반 빈도를 줄이는 데 유용하지만 여전히 확률적이다. 시나리오의 테스트 증거가 정확히 그 잔여 실패 양상을 보여준다. 모델에게 자신의 URL을 확인하라고 요청하는 것은 대개 따르는 또 하나의 지시를 추가하는 것일 뿐, 우회할 수 없는 게이트가 아니다.

일반 규칙: 위반이 법적, 금전적, 안전상의 결과를 초래한다면 훅으로 강제하고, 규칙이 선호나 미묘한 차이의 문제라면 프롬프트가 적합하다. PreToolUse 이벤트, 그 입력 필드, 권한 결정 출력 형태에 대해서는 Agent SDK hooks 문서를 참고하라.

**B.** Copy the stored session transcript files to the new infrastructure and resume the original session by its captured session ID.

**설명**

세션 파일을 옮기고 재개하는 방식은 작동할 수는 있지만, 여기서는 더 약한 선택이다. 재개는 빠르게 변하는 소스를 참조하는 원문 웹 검색 결과를 포함한 이전 컨텍스트 전체를 복원하며, 문서에서는 결과를 애플리케이션 상태로 캡처해서 새로운 세션에 넣는 것이 호스트 간에 전사 파일을 옮기는 것보다 흔히 더 견고하다고 명시하고 있다.

**C(정답).** Capture the synthesized findings, decisions, and citations as application state and pass them into a fresh session's prompt.

**설명**

이는 문서화된 신규 세션 패턴이다. 이전 작업의 지속적인 결과물(발견 사항, 결정, 인용)을 추출하여 새로운 세션에 주입하는 것이다. 이는 오래된 원문 도구 결과를 복원하는 것을 피하고, 호스트 간에 세션 파일을 옮기는 것에도 의존하지 않는데, 문서는 이것이 전사 파일을 호스트 간에 옮기는 것보다 흔히 더 견고하다고 언급한다.

**D.** Resume the session and rely on automatic context compaction to condense the stale history into a summary before report generation.

**설명**

컴팩션(compaction)은 컨텍스트 윈도우가 한계에 가까워질 때 자동으로 실행되며, 재개된 세션을 정리하기 위해 호출하는 메커니즘이 아니다. 컴팩션이 일어나더라도 오래된 도구 결과를 새로 고치는 것이 아니라 요약할 뿐이므로, 오래된 웹 데이터를 압축한 버전 역시 여전히 오래된 것이다.

### 전반적인 설명

Agent SDK 세션은 살아있는 상태가 아니라 지속된 대화 기록이다. 즉 프롬프트, 모든 도구 호출, 모든 도구 결과, 모든 응답을 담고 있다. 세션을 재개하면 그 컨텍스트 전체가 기록된 그대로 복원되며, 도구를 다시 실행하거나 무엇도 새로 고치지 않는다. 이 사고 모델이 재개할지 새로 시작할지 결정하는 기준이 된다. 이전 도구 결과가 여전히 유효하다면 재개가 효율적이다. 에이전트가 전체 컨텍스트를 그대로 이어받기 때문이다. 하지만 자주 바뀌는 웹 소스처럼 그 결과가 이미 지나간 세상을 묘사한다면, 재개는 오래된 증거를 다시 주입하고 모델이 이를 최신인 것처럼 추론하게 만든다.

이런 상황에 대해 Anthropic의 문서는 더 견고한 패턴을 명시적으로 설명한다. 이전 실행에서 실제로 필요한 것(분석 결과, 결정, 인용)을 애플리케이션 상태로 캡처한 다음, 이를 새로운 세션의 프롬프트에 전달하는 것이다. 이는 결론은 유지하면서 오래된 원문 도구 출력은 버리며, 환경 간에 세션 파일을 옮겨야 하는 의존성도 제거한다. 문서는 그러한 이동성을 작동시킬 수 있더라도, 이 방식이 호스트 간 전사 파일을 옮기는 것보다 흔히 더 견고하다고 언급한다.

다른 접근들은 실행 가능성이 아니라 이 결정 자체에서 실패한다. 전사 파일을 복사하고 세션 ID로 재개하면 오래된 증거의 전체 흐름이 복원된다. 자동 컴팩션에 의존하는 것은 메커니즘을 잘못 이해한 것이다. 컴팩션은 컨텍스트 윈도우가 한계에 가까워질 때 트리거되어 기록을 요약하므로, 압축된 오래된 발견 사항은 여전히 오래된 발견 사항이다. 그리고 continue_conversation은 새로운 인프라에 작업을 넘기는 방법이 아니라 가장 최근의 로컬 대화를 대상으로 하는 지정 단축 수단이다. Agent SDK Sessions와 The Agent Loop를 참고하라.


## 질문 8

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : In pilot runs, subagents keep surfacing significant angles the coordinator's upfront topic decomposition never anticipated, such as a pending regulation, and those angles are never researched. Which change fixes this?

**A.** Expand the initial decomposition prompt with a much longer checklist of candidate subtopics so unexpected angles are covered before research begins.

**설명**

더 긴 사전 체크리스트는 정의상 예측할 수 없는 주제들과의 군비 경쟁이다. 리서치 시작 전에 작성된 고정 목록은 리서치 자체만이 밝혀낼 수 있는 것을 나열할 수 없다. 또한 대부분의 주제와 무관한 하위 작업으로 매 실행을 부풀리게 된다.

**B(정답).** Have the coordinator evaluate intermediate findings between delegation rounds and generate new subtasks targeting what those findings reveal.

**설명**

이것이 적응적 분해다. 증거가 들어올 때마다 계획이 업데이트되어, 리서치 중간에 발견된 사항이 새로운 조사 하위 작업이 된다. 코디네이터는 계획에 대한 소유권을 유지하면서도 계획 자체는 진화하는데, 이것이 바로 개방형 리서치가 요구하는 것이다.

**C.** Instruct the synthesis subagent to fill in unanticipated angles from its own general knowledge when composing the final report.

**설명**

조사되지 않은 일반 지식으로 보고서를 채우는 것은 인용되고 조사된 결과를 만든다는 시스템의 취지 자체를 훼손한다. 부족한 것은 조사 커버리지이며, 오직 새로운 리서치 하위 작업만이 출처가 있는 자료로 이를 채울 수 있다.

**D.** Give each subagent a broader mandate to independently pursue any related angle it encounters during its own assigned task.

**설명**

조율되지 않은 범위 확장은 중복된 노력과 일관되지 않은 커버리지를 야기하며, 한 서브에이전트가 발견한 사항이 다른 전문 분야의 에이전트에 의한 조사를 촉발시키지도 못한다. 서브에이전트는 격리된 컨텍스트를 가지므로, 여러 영역에 걸친 후속 조치는 코디네이터를 통해 흘러가야 한다.

### 전반적인 설명

개방형 리서치는 동적 적응 분해의 전형적인 사례다. 낯선 주제의 전체 범위는 조사가 시작되기 전에는 알 수 없으므로, 증거가 들어오는 대로 계획이 바뀔 수 있어야 한다. 사고 모델은 파이프라인이 아니라 루프다. 코디네이터는 알고 있는 것을 분해하고, 위임한 다음, 반환된 결과를 새로운 계획 단계의 입력으로 취급한다. 발견된 것 중 무언가가 새로운 하위 작업을 정당화하는가? Anthropic은 이 패턴을 서브에이전트 체이닝으로 문서화하는데, 각 서브에이전트가 작업을 완료하고 결과를 반환하면 Claude가 관련 컨텍스트를 다음 위임에 전달하여, 나중의 하위 작업이 이전 발견 사항에 의해 형성되도록 한다. Create custom subagents를 참고하라.

이 루프가 개별 워커가 아니라 코디네이터에 있어야 하는 이유는 컨텍스트 격리 때문이다. 각 서브에이전트는 자신의 프롬프트에 담긴 내용만 보고 최종 요약만 반환하므로, 웹 검색 에이전트가 발견한 규제는 코디네이터가 이를 새로운 위임으로 라우팅하지 않는 한 다른 모든 에이전트에게 보이지 않는다. 각 워커의 임무를 넓히는 것은 이를 대체할 수 없으며, 애초에 분해를 유용하게 만들었던 전문화와 중복 없는 커버리지를 희생시킨다. 하나의 대화가 조율할 수 있는 범위를 넘어서는 오케스트레이션을 위해, Anthropic은 동적 워크플로우도 문서화하고 있는데, 여기서는 스크립트가 루프와 분기를 담당하여 최종 답변만 Claude의 컨텍스트에 도달하게 한다.

나머지 옵션들은 실행이 아니라 원칙에서 실패한다. 더 큰 사전 체크리스트는 여전히 고정 파이프라인이며, 예측 가능하고 템플릿 같은 작업에는 적합하지만 조사 중간에만 드러나는 발견 사항을 다룰 수 있는 구조가 아니다. 그리고 종합 단계가 일반 지식에서 커버리지를 지어내게 하는 것은 리서치 공백을 인용되지 않은 주장으로 바꾸는 것이며, 이는 공백을 그대로 보고하는 것보다 더 나쁘다. 인용된 리서치 산출물이라면 발견 사항은 조사된 소스로 거슬러 올라갈 수 있어야 한다.


## 질문 9

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : The web search tools return Unix timestamps while the document analysis tools return ISO 8601 strings, and subagents misread the mix when correlating source dates. A hook will normalize them. Which lifecycle event should host the transformation?

**A.** Host the transformation in a PreToolUse hook, which fires before each tool executes, earlier in the agent lifecycle.

**설명**

PreToolUse는 나가는 도구 호출과 그 입력 인자만 볼 수 있으며, 그 시점에는 이형(heterogeneous) 결과 데이터가 아직 존재하지 않는다. 이는 호출을 차단하거나 수정하기에 적합한 이벤트이지, 도구가 반환하는 것을 변형하기 위한 것이 아니다.

**B(정답).** Host the transformation in a PostToolUse hook, which fires after each tool executes and before the model consumes the result.

**설명**

PostToolUse는 도구 결과를 가로채는 지점이다. 도구가 실행된 후에 발생하며 반환된 데이터가 컨텍스트에 추가되기 전에 변형할 수 있다. 그 지점에서 정규화하면 모델은 항상 단 하나의 표준 날짜 형식만 보게 되므로, 추론 과정에서 오해석이 발생할 수 없다.

**C.** Host the transformation in a SubagentStop hook, which fires when a subagent finishes its delegated work.

**설명**

SubagentStop은 서브에이전트가 완료될 때만 발생하며, 그 시점에는 서브에이전트가 이미 자신의 루프 매 반복에서 원본의 혼재된 형식을 놓고 추론을 마친 상태다. 변형 작업을 그곳에 두는 것은 조사 과정 자체에서의 오해석을 막기에는 너무 늦다.

**D.** Host the transformation in a Stop hook, which fires when the agent is about to end its turn.

**설명**

Stop은 턴이 끝나는 바로 그 시점에 발생하며, 모델이 추론 과정에서 모든 원본 도구 출력을 이미 소비한 이후다. 그곳에 붙는 변형 작업은 에이전트가 잘못 읽은 타임스탬프로부터 이미 도출한 결론을 막기에는 너무 늦게 도착한다.

### 전반적인 설명

훅에 대한 사고 모델은 각 도구 호출을 둘러싼 타임라인이다. PreToolUse는 실행 전에 발생하여 나가는 호출(도구 이름과 입력 인자)을 보고, PostToolUse는 실행 후에 발생하여 도구가 만들어낸 결과를 본다. 데이터 정규화는 본질적으로 결과 쪽의 문제다. Unix 타임스탬프와 ISO 8601 문자열은 도구가 실행된 이후에야 존재하게 된다. 따라서 PostToolUse 훅은 모든 결과를 대화에 추가되기 전에 하나의 표준 형식으로 변환하기에 정확히 맞는 지점에 위치하며, 이는 모델이 그 불일치를 전혀 마주치지 않게 된다는 뜻이다. 이는 모델이 건너뛸 수도 있는 지시가 아니라 결정적인 코드이며, 출력 형식을 바꿀 수 없는 서드파티 MCP 서버에 대해서도 작동한다.

타이밍이 바로 이후 이벤트들이 여기서 실패하는 이유다. 에이전트는 원본 도구 결과가 컨텍스트에 들어오는 매 루프 반복마다 추론하면서 혼재된 형식을 오해석한다. SubagentStop과 Stop은 그 추론이 끝난 후에 발생한다. 그때쯤이면 서브에이전트는 한 날짜가 정수처럼 보이고 다른 날짜가 문자열처럼 보였다는 이유로 이미 두 소스를 잘못 연관지었을 수 있다. 그런 이벤트에 붙는 정규화 단계는 피해가 발생한 이후에만 실행된다. 모델 출력의 하류가 아니라 모델 소비의 상류에 수정을 배치하는 것이, 날짜 정규화, 상태 코드 변환, 장황한 필드 잘라내기 같은 PostToolUse 변형 작업의 일반 원칙이다.

훅 이벤트의 전체 목록과 발생 시점은 Claude Code hooks 레퍼런스와 Claude Agent SDK 문서를 참고하라.


## 질문 10

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : The coordinator session has just finished an extensive baseline analysis of gathered sources. You want to evaluate two competing synthesis strategies independently, each building on that same analysis without influencing the other. Which approach fits?

**A.** Spawn two synthesis subagents in one turn, relying on each to inherit the coordinator's conversation history.

**설명**

서브에이전트는 격리된 컨텍스트에서 실행되며 부모 대화를 상속받지 않는다. 필요한 것은 반드시 프롬프트에 명시적으로 전달되어야 한다. 상속에 의존하면 두 서브에이전트 모두 분석에 대해 빈 시야를 갖게 된다.

**B.** Run the first strategy, then instruct the model to disregard it entirely before running the second in the same session.

**설명**

모델은 컨텍스트 윈도우에 남아 있는 내용을 선택적으로 잊을 수 없다. 첫 번째 전략의 추론과 출력은 대화 기록에 그대로 남는다. 두 번째 전략은 필연적으로 앞선 내용에 영향을 받게 되어 독립적 평가라는 목표를 무너뜨린다.

**C(정답).** Fork the session at the analysis point, producing two independent branches that each inherit the baseline context.

**설명**

포크(fork)는 발산형 탐색을 위해 설계된 메커니즘이다. 두 브랜치 모두 분기 지점까지의 전체 대화 기록을 가지고 있다가 이후 독립적으로 진화한다. 각 종합 전략은 다시 실행하거나 수동으로 요약할 필요 없이 완전한 분석에서 시작하며, 어느 브랜치도 다른 브랜치를 오염시킬 수 없다.

**D.** Launch two new sessions and paste a hand-written recap of the analysis into each as the opening prompt.

**설명**

수동 요약은 분석에 대한 손실이 있는 근사치이며, 두 번 준비하고 주입해야 한다. 포크는 요약 손실이나 중복된 설정 작업 없이 완전한 베이스라인 컨텍스트를 두 브랜치 모두에 전달한다.

### 전반적인 설명

Claude Agent SDK에서 세션은 누적된 대화 기록이다. 즉 원래 프롬프트, 도구 호출, 도구 결과, 응답을 포함한다. SDK는 세션을 자동으로 디스크에 저장하며, 이것이 세션을 재개 가능하게 만들고, 여기서 결정적으로 포크 가능하게도 만든다. 세션을 포크하면 분기 지점까지 모든 것을 공유하다가 그 이후 독립적으로 갈라지는 독립 브랜치가 생성된다. 이것이 정확히 A/B 탐색의 형태다. 하나의 분석 단계, 그리고 각각 복사된 기록을 상속받는 두 개의 발산형 후속 작업이다. 분석을 다시 계산하거나 수동으로 요약할 필요가 없으며, 어느 브랜치도 다른 브랜치의 작업을 보지 못한다. 다만 포킹이 토큰 측면에서 공짜는 아니다. 각 브랜치는 이후 요청에서도 자신이 상속받은 전체 컨텍스트를 계속 다시 전송하므로 토큰 비용은 두 브랜치 모두에 적용되며, 프롬프트 캐싱으로 이를 줄일 수는 있다.

가져갈 만한 사고 모델은, 실행 중인 대화 내에서 컨텍스트를 선택적으로 편집할 수 없다는 것이다. 모델에게 첫 번째 전략을 무시하라고 요청해도 그것이 컨텍스트 윈도우에서 제거되지는 않는다. 그 첫 번째 탐색의 모든 토큰은 여전히 사용 가능하며 계속해서 생성에 영향을 미친다. 마찬가지로 Task 도구를 통해 생성된 서브에이전트는 격리된 컨텍스트로 실행된다. 코디네이터의 기록에서 아무것도 상속받지 않으므로, 상속에 의존하면 각 종합 워커에게 빈 상태를 넘기는 셈이 된다. 분석을 두 개의 새 세션에 수동으로 요약해 넣는 방식은 원리상 작동하지만, 두 번 준비해야 하는 손실이 있는 요약이며, 포크였다면 그대로 보존되었을 세부사항을 버리게 된다.

염두에 둘 한 가지 경계는, 세션이 지속시키는 것은 대화 기록이지 파일시스템 상태가 아니라는 점이다. 포킹은 두 브랜치에 동일한 지식을 주지만, 파일을 스냅샷하거나 격리하지는 않는다. 코드를 편집하는 병렬 브랜치는 파일 격리를 위해 워크트리가 필요하다. 발산이 파일 편집이 아니라 추론에 있는 종합 전략 비교의 경우, 포킹만으로 충분하다. continue, resume, fork 옵션에 대해서는 Agent SDK Sessions를 참고하라.


## 질문 11

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : Documents analyzed in earlier agent sessions are sometimes revised before those sessions are resumed. Which two practices are sound for handling resumed sessions after such file changes?

**A.** Resume without any annotation, relying on the session to detect changed documents on disk and re-read them automatically on restore.

**설명**

재개 시 이전 도구 결과에 대한 자동 재검증은 일어나지 않는다. 복원된 기록은 원본 읽기 결과를 그대로 유지하며, 이것이 바로 변경된 파일을 명시적으로 표시하거나 다시 읽어야 하는 이유다.

**B(정답).** Explicitly tell the agent which documents were revised and instruct it to re-read them before relying on its earlier analysis.

**설명**

세션은 대화를 지속시키는 것이지 파일시스템을 지속시키는 것이 아니므로, 수정 전에 캡처된 도구 결과는 기록에 그대로 남아 있다. 변경된 파일을 표시하고 강제로 다시 읽게 하면 에이전트가 오래된 내용을 놓고 추론하지 않도록 보장할 수 있다.

**C(정답).** Start a new session seeded with a structured summary of prior conclusions if most prior tool results now describe outdated content.

**설명**

복원된 증거의 대부분이 오래된 것이라면, 재개는 오해를 부르는 도구 결과로 가득 찬 기록을 그대로 가져온다. 검증된 결론을 새로운 세션에 보존하면 에이전트가 오래된 문서 상태와 새로운 문서 상태를 섞는 것을 피할 수 있다.

**D.** Rely on prompt caching to invalidate the affected cache segments so the earlier read results refresh once the documents change.

**설명**

프롬프트 캐싱은 재처리를 피하기 위해 변경되지 않은 컨텍스트 접두사를 재사용하는 것으로, 파일별 신선도 메커니즘이 없다. 리포지토리의 파일을 편집해도 대화 속 이전 파일 읽기 결과는 새로 고쳐지지 않는다.

### 전반적인 설명

이러한 결정을 쉽게 만드는 사고 모델은, Claude Agent SDK 세션이 파일시스템 스냅샷이 아니라 대화 기록이라는 것이다. 지속된 세션은 프롬프트, 모든 도구 호출, 모든 도구 결과, 모든 응답을 담고 있다. 파일 내용은 에이전트가 그것을 읽는 순간에만 그 기록에 들어가므로, 이후에 문서를 수정한다고 해서 이전 읽기 결과가 소급하여 다시 쓰이지는 않는다. 오래된 내용은 여전히 사실인 것처럼 기록에 남아 있다. 이것이 바로 Sessions 문서가 재개를 이전 컨텍스트를 이어받는 것으로 규정하는 이유이며, 아키텍트가 그 컨텍스트를 현재 존재하는 것이 아니라 관찰된 시점의 기록으로 다뤄야 하는 이유다.

이 설계는 의도적인 트레이드오프다. 저장된 기록을 재생하면 재개가 저렴해지고 에이전트가 다시 탐색하는 대신 완료된 분석 위에 쌓아갈 수 있지만, 신선도를 유지할 부담은 사용자에게 넘어간다. 실무 규칙은 여기서 바로 도출된다. 분석된 파일 몇 개가 변경되었다면, 재개하면서 어떤 파일이 수정되었는지 에이전트에게 명시적으로 알려 이전 발견 사항에 의존하기 전에 다시 읽게 하라. 도구 결과의 대부분이 오래된 것이라면, 아무리 신중하게 주석을 달아도 재개는 신뢰할 수 없다. 더 나은 방법은 검증된 결론을 구조화된 요약으로 담아 새로운 세션을 시작하여, 오래된 증거는 버리면서 통찰은 유지하는 것이다.

두 가지 잘못된 관행은 각각 어떤 메커니즘도 제공하지 않는 신선도 보장에 의존하고 있다. 재개 시 수정된 파일을 다시 읽어 복원된 기록을 패치하는 자동 변경 감지 기능은 없다. 그리고 프롬프트 캐싱은 신선도와 완전히 무관하다. 프롬프트 캐싱 문서에서 설명하듯, 이는 요청 간에 변경되지 않은 컨텍스트 접두사의 재처리를 피하기 위해 존재하는 것으로, 리포지토리 파일을 편집해도 대화 속 이전 파일 읽기 결과가 무효화되거나 새로 고쳐지지 않는다. 캐시 동작과 콘텐츠의 최신성을 혼동하는 것은 재개된 멀티 에이전트 워크플로우에 오래된 컨텍스트 버그가 스며드는 흔한 경로다.


## 질문 12

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : A nightly job runs the coordinator non-interactively with claude -p and logs each run's JSON output. One run produced an incomplete report, and an engineer wants to reopen that exact session interactively, but it does not appear in the session picker. How can they resume it?

**A(정답).** Pass the session ID captured from the run's JSON output to claude --resume.

**설명**

이것이 정답인 이유는 claude -p로 생성된 세션이 세션 피커와 claude --continue에서는 제외되지만, 세션 ID를 claude --resume에 전달하면 여전히 재개할 수 있기 때문이다. 그 ID는 헤드리스 실행의 JSON 출력에서 확인할 수 있다.

**B.** Assign the session a name with /rename in a fresh session, then resume by that name.

**설명**

이는 실패하는데, /rename은 그것이 실행된 세션 자체의 이름을 바꾸는 것이며 이전의 다른 세션이 아니기 때문이다. 새 세션을 열어 이름을 바꾸는 것은 헤드리스 실행의 대화에 접근할 수 있게 만들어주지 못한다.

**C.** Run claude --continue in the project directory to reopen the most recent session.

**설명**

이는 작동하지 않는데, claude --continue는 현재 디렉터리에서 가장 최근의 대화형 세션을 재개하며, claude -p로 생성된 세션은 명시적으로 여기서 제외되기 때문이다. 다른 관련 없는 대화형 세션을 다시 열거나 아무것도 열지 못할 것이다.

**D.** Rerun claude -p with the same prompt so the CLI restores the prior session's saved state.

**설명**

이는 이전 세션을 복원하는 것이 아니라 완전히 새로운 세션을 시작한다. 동일한 프롬프트를 반복해도 새로운 실행이 이전 세션의 대화 기록이나 도구 결과와 연결되지 않는다.

### 전반적인 설명

Claude Code는 모든 세션을 지속시키지만, 모든 세션이 동등하게 발견 가능한 것은 아니다. claude -p(또는 Agent SDK)로 비대화형으로 실행된 세션은 대화형 세션 피커와 claude --continue에서 의도적으로 제외된다. 그렇지 않으면 자동화된 실행이 피커를 어지럽히고 파이프라인이 자주 실행되는 디렉터리에서 --continue를 예측 불가능하게 만들기 때문이다. 이를 벗어나는 방법은 직접 지정이다. claude --resume은 세션 이름이나 세션 ID를 받을 수 있으며, 헤드리스 실행의 ID는 JSON 출력에서 확인할 수 있다. 이 ID를 파이프라인의 일부로 캡처하는 것은 자동화된 실행을 감사 가능하게 만드는 표준 패턴인데, 이를 통해 엔지니어가 코디네이터가 실제로 무엇을 했는지 진단하기 위해 모든 도구 호출과 결과를 포함한 정확한 대화를 다시 열 수 있기 때문이다.

가져가야 할 사고 모델은, 발견 메커니즘(--continue, /resume 피커)과 재개 메커니즘(명시적 식별자를 사용하는 --resume)이 서로 다른 계층이라는 것이다. --continue는 현재 디렉터리에서 가장 최근의 대화형 세션으로 귀결되는 편의 기능이므로, -p 세션에는 전혀 도달할 수 없다. /rename은 현재 열려 있는 세션에만 작동하므로, 과거의 헤드리스 실행에 나중에 이름을 붙일 방법을 제공하지 않는다. 동일한 프롬프트를 재실행하면 이전 세션과 아무 연결도 없는 완전히 새로운 세션이 생성된다. 저장된 상태는 프롬프트 텍스트가 아니라 세션 아이덴티티에 결부되어 있다.

--resume, --continue, 헤드리스 세션 처리의 문서화된 동작에 대해서는 Sessions와 CLI 레퍼런스를 참고하라.


## 질문 13

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : The search subagent's tool calls retrieve full articles with quotes and URLs, yet the coordinator receives only a two-sentence overview from it, so the synthesis subagent produces reports without citations. What should you change?

**A.** Have the coordinator repeat the key searches itself so the detailed results land directly in its own context.

**설명**

코디네이터에서 검색을 다시 실행하면 서브에이전트가 이미 수행한 작업이 중복되고, 위임이 애초에 걸러내려 했던 정확히 그 장황한 출력으로 코디네이터의 컨텍스트가 가득 차게 된다. 이는 증상만 다루는 것이며 컨텍스트 격리의 목적을 무너뜨린다.

**B(정답).** Instruct the search subagent to include its complete findings, key quotes, and source URLs in its final message.

**설명**

서브에이전트의 최종 메시지만 부모에게 반환된다. 중간의 모든 도구 호출과 결과는 서브에이전트의 격리된 컨텍스트 안에 남아 있다가 이후 버려진다. 검색 서브에이전트의 최종 메시지가 얇은 개요에 불과하다면, 세부사항은 사라진 것이다. 그 최종 메시지에 인용문과 URL을 포함한 완전한 결과를 담도록 요구하는 것이야말로 코디네이터가 그것을 보유하고 전달할 수 있는 유일한 방법이다.

**C.** Move the synthesis subagent to a model with a larger context window so more of the search detail fits.

**설명**

여기서 컨텍스트 윈도우 크기는 무관한데, 상세한 결과가 애초에 코디네이터에 도달하지 않으므로 종합 서브에이전트가 얼마나 여유 공간을 갖든 전달될 수 없기 때문이다. 더 큰 윈도우는 상류에서 손실된 정보를 복구할 수 없다.

**D.** Give the synthesis subagent a tool that reads the search subagent's conversation transcript to recover the detail.

**설명**

서브에이전트는 다른 에이전트에게 노출되지 않는 격리된 대화 안에서 실행된다. 서브에이전트가 완료되면 그 중간 컨텍스트는 조회 가능한 리소스가 아니다. 전사(transcript) 읽기 메커니즘을 중심으로 설계하는 것은 아키텍처가 의도적으로 버리는 상태에 접근하려는 시도다.

### 전반적인 설명

여기서 가져가야 할 사고 모델은 서브에이전트가 별개의 격리된 대화라는 것이다. 작업이 진행되는 동안 그 도구 호출과 장황한 결과들은 오직 자신의 컨텍스트 안에만 누적된다. 완료되면 살아남는 유일한 산출물은 부모에게 반환되는 최종 메시지뿐이며, 나머지는 모두 버려진다. 이는 의도적인 트레이드오프다. 격리는 리서치 서브에이전트의 수십 번의 페이지 fetch가 코디네이터의 컨텍스트를 가득 채우는 것을 막아주지만, 동시에 서브에이전트의 최종 메시지가 전체 인계 채널이라는 뜻도 된다. 그 메시지가 두 문장짜리 개요라면, 서브에이전트가 수집한 인용문과 URL은 코디네이터가 도달할 수 있는 어디에도 더 이상 존재하지 않는다.

따라서 해결책은 검색 서브에이전트의 지시사항에 있다. 최종 메시지에 완전한 결과, 핵심 인용문, 소스 URL을(이상적으로는 구조화된 형식으로) 출력하도록 요구하는 것이다. 그러면 코디네이터는 그 결과를 종합 서브에이전트의 프롬프트에 직접 담을 수 있으며, 이는 하위 서브에이전트가 무언가를 받을 수 있는 유일한 채널이다.

다른 접근들은 아키텍처를 잘못 이해하고 있다. 한 서브에이전트가 다른 서브에이전트의 전사를 읽을 수 있는 메커니즘은 없다. 버려진 중간 컨텍스트는 조회 가능한 리소스가 아니다. 코디네이터에서 검색을 다시 실행하는 것은 비용을 중복시키고 위임이 보호하려던 바로 그 컨텍스트로 장황한 출력을 끌어들인다. 그리고 종합 모델의 컨텍스트 윈도우를 늘리는 것은, 실제 문제가 데이터가 애초에 전달되지 않았다는 점인데 용량 문제를 다루는 것이다. 컨텍스트 격리와 최종 메시지 반환이 어떻게 작동하는지는 SDK의 Subagents 문서를 참고하라.


## 질문 14

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : Final reports occasionally include claims whose citations were silently dropped, and the team cannot determine at which stage the loss happens. How should the workflow be restructured to preserve citations and identify where loss occurs?

**A.** Restate the citation requirement in every prompt in the workflow so the instruction is reinforced at every processing stage.

**설명**

여러 단계에 걸쳐 지시를 반복하는 것도 여전히 프롬프트 지침이며, 이는 확률적이라 여전히 조용히 위반될 수 있다. 검사 가능한 중간 출력이 없으면 팀은 여전히 인용이 어디서 사라지는지 감지하거나 위치를 파악할 수 없다.

**B(정답).** Split the workflow into chained sequential calls, validating claim-to-citation mappings at each stage before the next runs.

**설명**

이것이 정답이다. 프롬프트 체이닝은 각 단계의 중간 출력을 호출 사이에서 검사 가능한 산출물로 만들어주므로, 프로그래밍적 검사가 각 핸드오프에서 인용이 살아남는지 확인하고 매핑이 손실된 지점을 정확히 짚어낼 수 있다. 이는 조용한 종단간(end-to-end) 실패를 감지 가능하고 위치를 특정할 수 있는 실패로 바꾼다.

**C.** Give each processing step an isolated context window so later steps cannot overwrite citation data held by earlier steps.

**설명**

컨텍스트 격리 자체는 인용을 보존하지 못한다. 각 단계는 여전히 소스 매핑을 생략한 출력을 내놓을 수 있다. 격리된 컨텍스트라는 사실만으로는 손실을 막지 못하며, 손실이 어디서 발생했는지 파악할 메커니즘도 제공하지 않는다.

**D.** Shorten each request's input so citation mappings stay out of the middle of long contexts where model attention weakens.

**설명**

더 작은 입력은 lost-in-the-middle 효과를 줄일 수는 있지만, 이것이 팀에게 인용 손실을 감지하거나 위치를 파악할 방법을 주지는 않는다. 주의력 개선만으로는 최종 보고서가 나올 때까지 실패가 여전히 눈에 보이지 않는다.

### 전반적인 설명

프롬프트 체이닝은 작업을 순차적인 API 호출로 나누어 각 단계의 출력이 다음 단계의 입력이 되게 하는 것을 의미한다. 그 아키텍처적 가치는 개별 호출 하나하나가 어떻게든 더 똑똑해진다는 것이 아니라, 호출 사이의 이음새가 관찰 가능하고 강제 가능해진다는 데 있다. 종합 단계가 결과를 반환한 후, 결정적 코드가 보고서 생성기가 호출되기 전에 모든 주장이 여전히 주장-소스 매핑을 지니고 있는지 검증할 수 있다. Anthropic의 가이드는 모델이 내부적으로 더 많은 다단계 작업을 처리하게 되더라도 체이닝이 여전히 유의미한 이유를 정확히 이렇게 짚는다. 중간 출력을 검사하고 특정 파이프라인 구조를 강제할 수 있게 해준다는 것이다. 단일한 종단간 요청에서는 인용 손실이 하나의 불투명한 생성 과정 안에서 발생하며 개입할 지점이 없다.

사고 모델은 체크포인트가 있는 파이프라인이다. 각 체크포인트는 검증, 복구, 혹은 중단할 기회이며, 이는 조용한 품질 실패를 위치를 특정할 수 있고 진단 가능한 실패로 바꾼다. 인용이 사라진다면, 그 입력과 출력이 모두 기록되어 있으므로 실패한 단계를 식별할 수 있다. 트레이드오프는 더 많은 호출과 더 많은 오케스트레이션 코드이며, 이것이 중간 검증이 중요할 때는 체이닝을 선택하고 그렇지 않을 때는 건너뛰는 이유다.

다른 접근들은 그럴듯하게 들리지만 잘못된 메커니즘을 설명한다. 매 프롬프트마다 인용 규칙을 다시 언급하는 것은 여전히 확률적인 지시 준수에 불과하므로 위반이 여전히 가능하고 여전히 눈에 보이지 않는다. 단계별 입력을 더 짧게 만드는 것은 긴 컨텍스트에서의 주의력 저하를 완화할 수는 있지만, 그것이 보존을 보장하거나 손실 위치를 드러내지는 못한다. 그리고 단계 간의 컨텍스트 격리는 인용을 전혀 보호하지 못한다. 한 단계가 단순히 인용을 생략한 출력을 만들어낼 수 있으며, 격리는 감지 지점을 제공하지 않는다. 순차적 체이닝이 올바른 구조인 시점에 대한 현재 가이드는 Anthropic의 prompt engineering 문서를 참고하라.


## 질문 15

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : The document analysis subagent devises a categorization scheme in its first delegation. A second delegation tells it to reuse that scheme, but it reports knowing no such scheme. How should the coordinator fix this?

**A(정답).** Include the categorization scheme in the second delegation prompt, or resume the earlier subagent instance.

**설명**

이것이 정답이다. 재개되지 않은 새로운 일반 서브에이전트 호출은 매번 새로운 인스턴스를 생성하므로, 그 체계는 문서화된 부모-서브에이전트 채널인 위임 프롬프트에 명시적으로 전달되어야 한다. 또는 이전 서브에이전트를 재개하는 방법도 있는데, 재개된 서브에이전트는 자신의 이전 대화, 도구 호출, 추론을 그대로 유지하기 때문이다.

**B.** Add SendMessage to the subagent's allowed tools so its memory persists and is shared across invocations.

**설명**

이는 오답인데, SendMessage는 세션 내에서 활성화된 이름이 지정된 에이전트들 간의 메시지 전달을 가능하게 하는 것이며, 서브에이전트 호출 간에 공유되거나 지속되는 메모리를 만들지 않기 때문이다. 이를 부여해도 새 인스턴스가 이전 인스턴스의 컨텍스트에 접근할 수 있게 되지는 않는다.

**C.** Disable automatic context compaction between delegations so the scheme is not summarized away before the second run.

**설명**

이는 오답인데, 서브에이전트 호출 사이에는 컴팩션이 일어나지 않으므로 비활성화할 것이 아무것도 없기 때문이다. 그 체계는 지속되던 컨텍스트에서 요약되어 사라진 것이 아니라, 애초에 별도의 인스턴스 안에 있었고 그 기록은 새로운 호출로 자동으로 넘어가지 않는다.

**D.** Instruct the second invocation to retrieve the scheme from the first run's intermediate tool results.

**설명**

이는 오답인데, 중간 도구 호출과 결과는 그것을 만들어낸 서브에이전트 인스턴스 안에 남아 있으며 새로운 인스턴스에서는 사용할 수 없기 때문이다. 새로운 호출은 다른 실행의 도구 결과를 조회할 채널을 전혀 갖고 있지 않다.

### 전반적인 설명

Claude Agent SDK에서 서브에이전트는 지속적인 메모리를 가진 장기 실행 워커가 아니라, 호출마다 생성되는 인스턴스다. 재개되지 않은 새로운 일반 Agent 도구 호출은 매번 새로운 인스턴스를 생성하며, 그 컨텍스트에는 자신의 시스템 프롬프트, 위임 프롬프트, 도구 정의, 그리고 프로젝트 CLAUDE.md 같은 시작 자료가 담기지만, 동일한 에이전트 유형의 이전 실행에서 온 것은 아무것도 없다(재개된 서브에이전트와 포크는 문서화된 예외다). 따라서 두 번째 위임에서 "당신이 확립한 체계"를 언급하는 것은, 새로운 인스턴스의 관점에서는 애초에 존재하지 않았던 자료를 지칭하는 것이다.

사고 모델은, 서브에이전트의 정체성은 그것의 AgentDefinition(설명, 시스템 프롬프트, 도구 제한)에 있지만, 작업 상태는 호출별 컨텍스트에 있다는 것이다. 일반적인 새 호출은 이전 서브에이전트 기록을 자동으로 넘겨받지 않는다. 오직 명시적으로 재개된 서브에이전트만이 자신의 이전 대화, 도구 호출, 추론을 유지하며, 포크된 서브에이전트는 새로 시작하는 대신 부모의 대화를 상속받는다는 점에서 별도의 예외다. 이러한 격리는 의도적인 것이다. 장황한 탐색 과정을 부모 대화 밖으로 유지시키고 많은 인스턴스가 병렬로 실행될 수 있게 해주지만, 그 대가로 코디네이터가 실행 간 상태를 직접 전달해야 한다. 이 실패에는 두 가지 해결책이 맞는다. 두 번째 위임 프롬프트에 분류 체계를 명시적으로 포함시키는 것(프롬프트 문자열은 문서화된 부모-서브에이전트 채널이다), 또는 Claude에게 이전 서브에이전트를 재개하도록 요청하는 것이다.

다른 조치들은 메커니즘을 잘못 이해하고 있다. 서브에이전트 호출 사이에는 자동 컴팩션이 일어나지 않으므로 비활성화할 것이 없다. 이전 컨텍스트는 단순히 넘어오지 않는 것이다. SendMessage는 세션 내 에이전트 간 메시징을 지원하는 것이지, 호출 간 메모리를 지원하지 않는다. 그리고 중간 도구 결과는 그것을 만들어낸 인스턴스 안에 남아 있으므로, 새로운 호출은 이를 가져올 방법이 없다. SDK의 Subagents와 Create custom subagents를 참고하라.

**QUESTION** : The coordinator receives a broad research topic in a domain the team has never covered; the relevant subtopics and useful source types are unknown in advance. How should the coordinator decompose the research work?

**설명**

이것이 개방형 조사를 위한 올바른 패턴이다. 먼저 지형을 파악하고, 예상 가치에 따라 위임의 우선순위를 정하며, 중간 발견 사항이 계획을 다시 형성하게 하는 것이다. 동적 적응 분해는 전체 범위를 사전에 알 수 없는 바로 이러한 상황을 위해 설계되었다.

**B.** Assign the entire topic to a single general research subagent and let its raw output determine the report's structure and coverage.

**설명**

이는 분해를 위한 전략을 선택하는 것이 아니라 분해 자체를 완전히 포기하는 것이다. 넓은 주제 전체를 다루는 단일 서브에이전트는 장황한 컨텍스트를 축적하고, 하위 영역 전반에 주의력을 분산시키며, 코디네이터에게 우선순위를 정하거나 병렬화하거나 공백을 채울 능력을 전혀 주지 않는다.

**C.** Spawn one subagent per guessed subtopic in a single parallel batch, then synthesize whatever coverage those initial guesses happen to produce.

**설명**

병렬 생성은 효율적이지만, 검증되지 않은 추측에 모든 위임을 고정시키는 것은 어떤 증거도 존재하기 전에 커버리지 결정을 확정짓는 것이다. 범위 파악 단계나 계획을 수정할 메커니즘이 없으면, 잘못된 추측은 최종 보고서에서 영구적인 공백이 된다.

**D.** Delegate against a fixed set of standard research categories, running the same predefined subagent sequence the system applies to every topic.

**설명**

고정된 프롬프트 체인 파이프라인은 항상 동일한 측면을 확인하는 리뷰처럼 예측 가능하고 반복적인 작업에 적합하다. 하위 주제를 알 수 없는 낯선 주제는 미리 정의된 범주에 신뢰성 있게 맞지 않으므로, 이 접근은 주제가 템플릿에서 벗어날 때마다 커버리지 공백을 만들어낸다.

### 전반적인 설명

분해 전략을 선택하는 것은 하나의 질문에서 시작한다. 작업의 구조가 사전에 알려져 있는가? 동일한 측면을 확인하는 반복적인 리뷰는 프롬프트 체이닝, 즉 미리 정해진 초점 있는 단계들의 순서에 적합하다. 낯선 리서치 주제는 그 반대 경우다. 하위 주제 자체가 알려지지 않았으므로, 올바른 패턴은 동적 적응 분해다. 사고 모델은 확정 전에 탐색하는 것이다. 초기 범위 파악 단계가 주제의 구조를 지도로 만들고, 코디네이터는 그 지도로부터 우선순위가 정해진 계획을 세우며, 매 라운드의 서브에이전트 결과에 따라 하위 작업을 추가, 삭제, 재정렬할 수 있다. 이것이 계획이 계속 수정 가능해야 하는 이유다. 주제의 가장 중요한 줄기는 흔히 첫 위임이 결과를 반환한 이후에야 비로소 드러난다.

오답들은 각각 이 모델의 서로 다른 부분을 깨뜨린다. 고정된 범주 템플릿은 구조를 예측할 수 없는 작업에 프롬프트 체이닝을 들여오는 것이므로, 템플릿 밖의 무언가는 조용히 놓치게 된다. 추측된 하위 주제들의 전체 병렬 배치를 생성하는 것은 병렬성은 유지하지만 정보가 가장 적은 시점에 커버리지 결정을 동결시키며 수정 루프가 없다. 전체 주제를 하나의 서브에이전트에 넘기는 것은 분해 결정을 완전히 회피하는 것이며, 멀티 에이전트 아키텍처가 존재하는 이유인 컨텍스트 격리와 병렬 실행을 희생시킨다. 동적 분해도 여전히 병렬성을 사용한다는 점에 주의하라. 차이는 병렬 위임이 한 번의 추측이 아니라 정보에 기반해 진화하는 계획에서 나온다는 것이다.

Anthropic이 이 패턴을 프로덕션 리서치 시스템에 적용하는 방식은 How we built our multi-agent research system을 참고하고, 위임 메커니즘은 SDK의 Subagents를 참고하라.
