# 2. 오류 처리 · 재시도 · 부분 실패

## 이 장에서 다루는 것

- **접근 실패 vs 유효한 빈 결과** — 겉보기에 똑같은 "데이터 없음"을 정반대로 처리해야 하는 이유
- **재시도 가능/불가 판별과 백오프** — 일시적 오류와 구조적 오류, 지수 백오프·지터·재시도 상한, 에스컬레이션
- **에러 페이로드 설계** — LLM 코디네이터가 복구 결정을 내릴 수 있는 구조화된 실패 보고
- **부분 실패와 부분 결과 보고** — 결함 허용성, 커버리지 주석, 공백을 드러내는 방법
- **상태 영속성과 재개 가능성** — 체크포인팅, 매니페스트, 재개 절차
- **실패를 숨기면 생기는 일** — 조용한 실패와 허위 커버리지

## 1. 접근 실패 vs 유효한 빈 결과

에이전트 시스템 신뢰성의 가장 기본적인 구분이자, 실무에서 가장 자주 틀리는 구분입니다.
겉보기에는 둘 다 "데이터가 없음"이지만 성격이 정반대입니다.

### 1.1 두 가지 결과 유형

| | **접근 실패 (Access Failure)** | **유효한 빈 결과 (Valid / Legitimate Empty Result)** |
|---|---|---|
| 의미 | 시스템이 질문에 **답을 못 했다**. 데이터가 존재할지도 모르는데 못 읽었다 (**미지, unknown**) | 시스템이 정상 동작해서 **"없다"고 답했다**. 존재하지 않는다는 **검증된 사실** |
| 예시 | 타임아웃, 연결 거부, DB 오프라인, 500 에러, 429, 커넥션 풀 고갈, 인증 만료, 캐시가 임계값을 넘어 만료(stale)되어 신선도 검사 실패 | HTTP 200 + 결과 0건, 빈 배열 `[]`, 해당 세션에 시간외 거래가 실제로 한 건도 없었음 |
| 재시도 | 예 (retryable) | 아니오 (성공적 완료) |
| 올바른 상태값 | `error`, `error_type: "access_failure"`, `results: null` | `success`, `results: []` |

### 1.2 둘을 헷갈리면 생기는 일

두 방향 모두에서 사고가 납니다.

- **빈 결과를 실패로 취급하면**: 정상적으로 "없음"을 확인했는데도 계속 재시도합니다.
  영원히 성공하지 않을 재시도를 반복하며 API 호출 낭비, 응답 지연, 불필요한 오류 알람이 발생합니다.
- **실패를 빈 결과로 취급하면**: 훨씬 위험합니다. 실제로는 데이터가 **존재하는데**
  타임아웃 때문에 못 받은 것을, 시스템이 "데이터 없음"으로 확정해 버립니다.
  잘못된 결론이 아래 단계로 조용히 전파되는 **조용한 데이터 유실(silent data loss)** 입니다.

법률 리서치를 예로 들면, 판례 DB의 커넥션 풀이 고갈되어 연결이 거부된 상황을 "no results found"로
보고하면 상위 에이전트는 **"그런 판례는 존재하지 않는다"** 는 사실로 받아들입니다. 심각한 오판입니다.

### 1.3 판별 기준

"응답이 왔는가?"가 아니라 **"조회 작업 자체가 성공적으로 완료되었는가?"** 를 봅니다.

```
질의 실행 → 서버가 정상 응답(2xx) → 결과 0건  → 유효한 빈 결과
질의 실행 → 타임아웃 / 연결 실패 / 5xx / 429   → 접근 실패 (재시도 대상)
```

구체적 사례:

- 단종된 SKU를 카탈로그에서 조회 → 200 OK, 0행. **정상적인 "그런 상품 없음"** 입니다.
- 신규 지원 언어의 용어집을 조회 → 조회 성공, 매칭 용어 0건. 신규 언어이므로 **예상된 정상 결과**입니다.
- 같은 용어 DB가 **오프라인**이라서 응답 없음 → 인프라 장애, **재시도 가능한 접근 실패**입니다.

### 1.4 HTTP 상태 코드 기초

- **200 OK**: 요청 성공. 본문(body)이 비어 있어도 요청 자체는 성공입니다.
- **429 Too Many Requests**: 속도 제한(rate limit). 너무 많이 요청해서 서버가 잠시 거부.
  일시적이므로 **재시도 가능**합니다.
- **5xx**: 서버 측 오류. 일반적으로 재시도 가능.
- **4xx (429 제외)**: 요청 자체가 잘못됨. 대체로 재시도해도 의미 없습니다.
- **타임아웃**: 상태 코드조차 못 받은 상태. 서버가 처리 중일 수도, 죽었을 수도 있습니다.
  일시적 장애로 보고 재시도 대상입니다.

주의: HTTP 상태 코드가 **유일한 필수 정보인 것은 아닙니다.** 도구 실행 오류, 논리적 실패 등
HTTP와 무관한 실패가 많습니다.

### 1.5 도구 반환값은 최소 3상태를 구분한다

```python
{"status": "ok",    "data": [...]}                              # 데이터 있음
{"status": "empty", "data": []}                                 # 확인 결과 없음 (성공)
{"status": "error", "failure_type": "...", "retryable": True}   # 못 읽음
```

`results: []`(빈 배열, 사실)과 `results: null`(모름)을 구분하는 것도 좋은 습관입니다.

또한 **둘 다 곧바로 사람에게 에스컬레이션할 필요는 없습니다.** 캐시 만료 같은 접근 실패는
재시도로 해결될 가능성이 높은 일상적·일시적 오류이지, 사람이 개입해야 하는 치명적 오류가 아닙니다.

## 2. 재시도 가능/불가 판별과 백오프

### 2.1 오류의 두 종류

| 구분 | **일시적 오류 (transient)** | **지속적/구조적 오류 (systematic)** |
|---|---|---|
| 예시 | HTTP 503 Service Unavailable, 네트워크 타임아웃, 순간 rate limit(429) | 인증 실패(401/403), 잘못된 자격증명, 권한 부족, 잘못된 설정 |
| 성질 | 원인이 스스로 사라짐 | 환경이 바뀌지 않으면 영원히 실패 |
| 올바른 처리 | **로컬 재시도(local retry)** — 서브에이전트가 조용히 해결, 코디네이터를 귀찮게 하지 않는다 | **상위로 에스컬레이션** — 시도 내역을 첨부해서 |

**503(Service Unavailable)** 은 서버가 일시적으로 처리 불가 상태라는 신호입니다.
1초 뒤 재시도하면 성공하는 경우가 흔합니다.

**자격 증명 로테이션(credential rotation)** 은 보안상 주기적으로 비밀키·토큰을 새 값으로 교체하는 관행입니다.
새 값이 어떤 환경에 **전파(propagate)** 되지 않으면 그 환경은 계속 실패합니다.
이건 재시도로 절대 해결되지 않습니다. 사람이나 시스템이 자격증명을 배포해야 합니다.

### 2.2 지수 백오프 (Exponential Backoff)

일시적 장애에 대응하는 표준 재시도 전략입니다. 재시도 간격을 지수적으로 늘립니다.

```
1차 실패 → 1초 대기 → 재시도
2차 실패 → 2초 대기 → 재시도
3차 실패 → 4초 대기 → 재시도
...
```

**왜 간격을 늘리는가?** 서버가 이미 과부하 상태(429)인데 즉시 재시도를 퍼부으면
장애를 더 악화시킵니다. 간격을 벌려 서버가 회복할 시간을 줍니다.

**지터(jitter)**: 간격에 약간의 무작위성을 더해 여러 클라이언트가 동시에 재시도하는
현상(thundering herd)을 방지합니다.

의사코드:

```python
delay = 1.0
for attempt in range(MAX_RETRIES):      # 반드시 상한이 있어야 한다
    result = call_api()
    if result.ok:
        return result
    if not is_retryable(result):        # 400, 404 등은 즉시 포기
        return result
    sleep(delay + random.uniform(0, 0.5))
    delay *= 2
# 상한 소진 → 재시도로 해결 못 함 → 에스컬레이션
return escalate(failure_type=result.error, attempted=..., partial=...)
```

고정 지연 배열로 쓰는 형태도 같은 기법입니다.

```python
delays = [1, 2, 4, 8]   # 초
for attempt, d in enumerate(delays):
    try:
        return call()
    except TransientError:
        sleep(d + random.uniform(0, 0.5))   # jitter: 동시 재시도 몰림 방지
raise EscalateToCoordinator("구조화된 실패 보고 형식으로")
```

### 2.3 재시도 상한(retry budget)이 반드시 필요한 이유

"429는 언젠가는 풀리니 무한히 재시도하면 된다"는 생각은 위험합니다.

- 워크플로우 전체가 무한 대기(hang) 상태에 빠집니다.
- 스레드, 커넥션, 토큰 예산 등 시스템 자원이 고갈되고 다른 작업까지 지연됩니다.
- 진짜 문제(예: API 키 쿼터 소진, 계약 만료, 자격증명 미전파)는 재시도로 절대 해결되지 않습니다.

### 2.4 재시도 안티패턴

- **무한 재시도(indefinitely)** — 자원 낭비, 무한 루프, 다른 작업까지 지연. 반드시 상한이 필요합니다.
- **조용한 무한 재시도(Silent Retry)** — 인증 오류는 자격 증명이 바뀌지 않는 한 재시도로 해결되지 않습니다.
- **모든 오류를 즉시 에스컬레이션** — 코디네이터가 병목이 됩니다. 서브에이전트가 스스로 처리할 수 있는 건
  스스로 처리해야 자율성의 의미가 있습니다.
- **거꾸로 매핑** (일시적 오류는 올리고, 구조적 오류는 계속 재시도) — 최악의 조합.

### 2.5 에스컬레이션 (Escalation)

**정의**: 자기 수준에서 해결할 수 없는 문제를 상위 결정권자(코디네이터 또는 사람)에게
**정보와 함께** 넘기는 것.

서브에이전트가 로컬 재시도 예산(예: 지수 백오프 2회)을 다 쓰고도 실패했다면,
더 재시도하는 것은 의미가 없습니다. 이때 코디네이터로 에스컬레이션합니다.

**에스컬레이션 시 반드시 포함해야 하는 정보:**

1. **실패 유형(failure type)**: "429 rate limit", "timeout", "tool crash" 등 구체적으로.
2. **시도한 작업(attempted queries)**: 어떤 질의를 어떤 파라미터로 했는지.
3. **부분 결과(partial results)**: 실패 전까지 이미 얻은 것.
4. **미처리 범위(unprocessed scope)**: 아직 못 한 부분이 무엇인지.
5. (가능하면) **제안 대안(suggested alternatives)**: 다른 인덱스, 캐시된 데이터 등.

이 정보가 있어야 코디네이터가 판단할 수 있습니다. 다른 경로로 우회할지,
나중에 재시도할지, 부분 결과로 진행할지, 사람을 부를지.

"시도 내역 첨부"가 중요한 이유는 코디네이터가 같은 실패를 반복하지 않고 바로
원인 계층(자격증명 배포)을 조치할 수 있게 해 주기 때문입니다.

에스컬레이션 보고 예시:

```
실패: metrics-store 쿼리
증상: 2분간 반복 401 Unauthorized
시도: 지수 백오프로 6회 재시도, 모두 동일 오류
추정 원인: 자격증명 로테이션이 이 환경에 미전파
필요 조치: 환경 변수 METRICS_TOKEN 갱신 (에이전트 권한 밖)
```

### 2.6 사람에게 에스컬레이션하는 조건 (Human-in-the-Loop)

자율 에이전트 설계에서 **언제 사람에게 넘길 것인가(escalation condition)** 를
명확히 정의하는 것은 필수 요소입니다.

**전형적인 조건:**

- 사용 가능한 복구 도구/옵션을 모두 소진했는데 문제가 미해결일 때
- 동일한 실패가 반복되어 진전이 없을 때(무한 루프 위험)
- 정책상 사람의 승인이 필요한 행동일 때(환불, 계정 삭제 등)
- 사용자가 명확히 사람을 요청했고, 시도할 수 있는 것을 이미 시도했을 때

**시나리오:** 클라우드 지원 에이전트가 멈춘 배포를 고치려고 도구 기반 복구를 3가지 시도했지만
모두 실패했고, 더 이상 남은 옵션이 없습니다. → **지금까지의 시도 이력과 실패 맥락을 함께 담아
사람 상담원에게 이관**합니다. 사람이 처음부터 다시 조사하지 않아도 되게 하는 것이 에스컬레이션의 가치입니다.

**하면 안 되는 것:**

- 이관 없이 "해결 불가"로 종결 → 고객 방치.
- 같은 조치를 무한 반복 재시도 → 무한 루프, 토큰·컴퓨팅 낭비.
  "시도한 조치가 옳았으니 언젠간 되겠지"는 근거 없는 낙관입니다.
- 해결되지 않았는데 해결되었다고 통보 → 신뢰를 파괴하는 허위 보고.
  **올바른 절차를 시도한 것과 문제가 해결된 것은 전혀 다른 사실입니다.**
- **전체 워크플로우 즉시 실패** → 서브에이전트 하나의 실패로 정상 처리 가능한 나머지 작업(예: 배치의
  다른 티켓들)까지 죽이는 것은 과잉 대응입니다. 실패는 **격리(isolation)** 되어야 합니다.
- **실패를 성공으로 위장** → 조회 실패인데 빈 결과를 반환하고 티켓을 "해결됨"으로 표시하는 것은
  데이터 오염이자 거짓 보고입니다.

### 2.7 AI-First 지원 워크플로우

사용자가 처음부터 "봇 말고 사람 연결해 줘"라고 요구하는 경우가 있습니다.
Anthropic이 권장하는 지원 접근 방식은 **AI-First** 모델입니다.

권장 흐름:

1. 요청을 무시하지 않고 응대한다.
2. 먼저 문제를 설명하고 해결을 시도해 본다(예: 초과 요금이 왜 발생했는지 사용 이력을 확인해 설명).
3. 그래도 고객이 다시 사람을 요청하거나 문제가 해결되지 않으면 사람 상담원에게 이관한다.

**하면 안 되는 것:**

- 계정 확인이나 해결 시도를 전혀 하지 않고 즉시 사람에게 넘기기 → AI-First 모델의 취지에 어긋납니다.
- 에스컬레이션 요청 자체를 무시한 채 조사만 진행하기 → 고객 커뮤니케이션 무시.
- "왜 봇과 대화하기 싫으신가요?"라고 이유를 캐묻기 → 고객 여정에 마찰(friction)만 더하는 부적절한 응대.

핵심은 **"해결 시도 + 요청 존중 + 조건부 이관"이 하나의 완결된 워크플로우**라는 점입니다.

### 2.8 엔티티 모호성 해소 (Disambiguation)

재시도로도 에스컬레이션으로도 풀리지 않는, **정보가 모자라서 진행할 수 없는** 유형의 실패입니다.

**시나리오:** 청구 문의를 처리하려고 고객을 조회했더니, 같은 성(last name)과 같은 이메일 도메인을 쓰는
프로필이 두 개 나왔습니다(패밀리 요금제로 보임). 한쪽이 훨씬 활발하게 이용 중입니다.

**정답:** 등록된 결제 카드 뒤 4자리 같은 **추가 식별자(additional identifier)** 를 고객에게 요청해
대상을 확정합니다.

**왜 휴리스틱으로 추측하면 안 되는가:**

- "사용량이 많으니 이 사람일 것" → 사용량이 적은 부계정 소유자가 결제 문의를 했을 수 있습니다.
- "먼저 만든 계정이 주 계정일 것" → 문의 주체가 누구인지와는 무관합니다.
- 두 프로필의 청구 정보를 확인 없이 병합해 답변 → **타인의 개인정보를 노출**하는 심각한 프라이버시 위반입니다.

일반 원칙: **개인 데이터나 금전이 걸린 판단에서, 정황 기반 추측은 절대 신원 확인을 대신할 수 없습니다.**
"사용자에게 계속 묻는 것은 나쁜 UX"라는 원칙과 모순되어 보이지만, 구분 기준은 이렇습니다.
**시스템이 이미 알고 있는 것을 다시 묻는 것은 나쁘고, 시스템이 원리적으로 알 수 없는 것
(어느 계정의 문의인지, 본인 확인)을 묻는 것은 옳습니다.**

## 3. 에러 페이로드(Error Payload) 설계

### 3.1 왜 에러 설계가 중요한가

서브에이전트가 도구 호출에 실패했을 때, 코디네이터는 다음 중 하나를 결정해야 합니다.

- 그대로 재시도한다 (일시적 네트워크 오류라면 유효)
- 다른 도구나 다른 경로로 우회한다 (해당 API가 영구 폐기되었다면)
- 부분 결과만 가지고 진행한다
- 사람에게 이관한다

이 판단은 **에러가 전달하는 정보의 질에 전적으로 달려 있습니다.** 코디네이터가 LLM이라는 점이 중요합니다.
LLM은 의미(semantic)를 읽고 판단하지, 숫자 코드를 룩업 테이블에서 찾아보지 못합니다.

`Query failed.` 나 `'search unavailable'` 같은 **모호한 문자열 하나만** 반환하면 코디네이터는
아무 결정도 할 수 없습니다. 인증 실패인지, 네트워크 타임아웃인지, 검색어가 잘못됐는지 알 수 없기 때문입니다.
이를 "복구 세부 정보를 숨긴다(hides recovery detail)"고 표현합니다.

여기서 문제는 메시지가 **짧다는 것 자체가 아니라 필요한 정보가 빠졌다는 것**입니다.
타임스탬프만 붙인다고 해결되지 않습니다.

### 3.2 좋은 에러 페이로드의 4가지 필드

| 요소 | 의미 | 코디네이터가 얻는 것 |
|---|---|---|
| **failure_type (실패 유형)** | access_failure / auth_error / rate_limit_exceeded / validation_error / timeout / not_found … | 일시적(transient)인지 영구적(permanent)인지 → **재시도 가능 여부 판단** |
| **action_attempted (시도한 작업)** | 어떤 도구를 어떤 인자로 호출했는가 | 같은 실수 반복 방지, **결손 범위 파악** |
| **partial_results (부분 결과)** | 완전히 실패하기 전에 이미 확보한 유효 정보 | **즉시 활용 가능한 데이터 확보** (버리면 처음부터 다시 해야 함) |
| **alternative_approaches (대안)** | 실패 현장에 있던 서브에이전트가 제안하는 다음 수단 | **복구 경로 선택지** |

대안 제안이 유용한 이유: 코디네이터보다 **상황 정보가 많은 쪽**이 제안하는 것이 효율적입니다.

최소 형태(텍스트):

```
failure_type: access_failure
attempted:    last-15-minutes log pull (payments service)
partial:      3 of 4 pods returned data
alternative:  retry against read replica
```

JSON 형태로 규격화하면 코드로 분기하기도 쉽습니다.

```json
{
  "status": "partial_failure",
  "failure_type": "access_failure",
  "attempted": "log_pull(payments, 15m)",
  "partial_results": {"pods_returned": 3, "pods_total": 4},
  "alternative": "retry_read_replica"
}
```

풍부한 형태(법률 리서치 예):

```json
{
  "failure_type": "rate_limit_exceeded",
  "action_attempted": "search_case_law(query='fair use 2024', court='9th Cir')",
  "partial_results": [
    {"case": "Smith v. Jones", "year": 2023}
  ],
  "alternative_approaches": [
    "60초 후 재시도",
    "보조 검색 인덱스(secondary_index) 도구로 우회",
    "쿼리 범위를 단일 연도로 축소하여 결과 수 감소"
  ]
}
```

원본 오류 메시지를 함께 실어 주는 형태도 좋습니다.

```json
{
  "status": "error",
  "failure_type": "AUTH_ERROR",
  "queried": "renewal notice period site:kb.internal",
  "partial_results": [ { "...": "타임아웃 전까지 얻은 결과" } ],
  "message": "Knowledge base returned 401 Unauthorized"
}
```

이 정도 정보가 있어야 코디네이터가 **자격 증명 갱신, 쿼리 수정, 대체 서브에이전트 호출,
사용자 알림** 같은 복구 전략(Fallback)을 선택할 수 있습니다.

접근 실패를 알릴 때의 최소 스키마:

```json
{
  "status": "error",
  "error_type": "access_failure",
  "detail": "connection pool exhausted, 2 retries failed",
  "results": null
}
```

### 3.3 나쁜 에러 설계

| 형태 | 문제 |
|---|---|
| `Query failed.` / `'search unavailable'` 같은 모호한 단일 문자열 | 재시도할지, 다른 서브에이전트를 쓸지, 포기할지 구별할 근거가 전혀 없음 |
| 단순 boolean 성공/실패 플래그 | 정보가 더 줄어 복구 불가 |
| 내부 추론 트레이스 전체를 자유 텍스트로 전달 | 토큰 낭비가 극심하고, 핵심 실패 원인이 잡음에 묻힘. 구조가 없어 코디네이터가 파싱 불가 |
| 재시도 횟수 + 타임스탬프만 전달 | "몇 번 실패했다"는 알 수 있어도 "왜"와 "그래서 무엇을"은 알 수 없음 |
| 단일 숫자 에러 코드 (예: `ERR_4021`) | 사람 엔지니어가 문서를 찾아보는 용도. LLM 코디네이터는 그 코드의 의미를 모르며, 룩업 테이블 접근 권한도 없음 |
| 오류를 서브에이전트 로그에만 남기고 코디네이터에게 숨기기 | 시스템 전체가 복구 불능 |

원칙: **에러는 실패를 알리는 신호가 아니라, 복구 결정을 내리기 위한 입력 데이터입니다.**
구조화하되(structured), 의미가 읽히도록(semantic) 설계합니다.

## 4. 부분 실패와 부분 결과 보고

### 4.1 결함 허용성(Fault Tolerance)의 기본형

**시나리오:** 코디네이터가 서브에이전트 5개를 보내 시장 분석 자료를 수집했습니다.
그중 1개의 웹 페치 도구에서 복구 불가능한 연결 오류가 발생했습니다.

**나쁜 설계:** 파이프라인 전체를 중단하고 이미 완료된 4개의 결과까지 폐기
→ 이미 지불한 API 비용과 시간을 통째로 버리는 안티 패턴.

**좋은 설계:**

1. 성공한 4개의 결과로 종합을 진행한다.
2. 실패한 부분은 **보고서에 명시적으로 결손 영역(coverage gap)으로 표기**한다.
   "유통 채널 항목은 데이터 소스 접근 실패로 수집되지 않았음"처럼.

이것이 **결함 허용성(Fault Tolerance)** 과 **회복탄력성(Resiliency)** 의 기본형입니다.
독립적인 하위 작업들은 서로의 실패에 연동되어 무너지면 안 됩니다.

**전부 재실행도 나쁩니다.** 성공한 4개를 "배치 일관성"을 위해 처음부터 다시 돌리는 것은
불필요한 비용과 지연입니다. 실패한 것만 재시도하면 됩니다(**멱등성/재시도 최소화** 원칙).

### 4.2 부분 진행 결과 보고 (Partial Progress Reporting)

도구가 작업 도중 크래시했다면, 이미 얻은 결과는 **버리지 않고** 실패 정보와 함께 보고합니다.

예: 보안 스캐너가 파일 40개 중 15개를 처리하고 취약점 2건을 찾은 뒤 크래시한 경우.

올바른 보고:

```json
{
  "status": "partial_failure",
  "failure_type": "static_analyzer_crash",
  "findings": [
    {"file": "auth/session.py", "severity": "high", "issue": "..."},
    {"file": "api/upload.py",   "severity": "medium", "issue": "..."}
  ],
  "files_scanned":   ["auth/session.py", "api/upload.py", "..."],
  "files_unscanned": ["billing/charge.py", "..."]
}
```

- 아무것도 안 보내면(재시작될 때까지 침묵) 이미 찾은 취약점 2건이 낭비되고
  코디네이터는 무엇이 일어났는지 알 수 없습니다.
- 취약점 2건만 "완전한 최종 결과"로 보내면, 스캔되지 않은 파일이 **안전한 것처럼**
  잘못 인식됩니다. 이것이 가장 위험합니다.
- 일반 실패 통보만 보내면 이미 확보한 진단 정보가 버려집니다.

원칙: **가진 것을 주고, 못 가진 것을 명시한다.**

### 4.3 구조화된 실패 보고를 받은 코디네이터의 행동

두 가지를 **분리해서** 처리하는 것이 정답입니다.

1. **확보된 부분 결과는 즉시 활용한다.** 파드 3개의 로그는 지금 바로 장애 타임라인에 넣습니다.
   장애 대응에서는 신속성이 최우선입니다.
2. **누락분에 대한 복구는 별도로 판단한다.** 읽기 복제본(read replica) 재시도를 할지 말지는
   독립적인 의사결정입니다.

**하면 안 되는 것:**

- 서브에이전트가 제안한 대안을 원칙적으로 무시하기 → 대안 제안은 유용한 정보이며,
  코디네이터가 그것을 참고하는 것은 정상적인 협업입니다(맹목적 실행이 아니라 판단 재료로 씁니다).
- 4개 파드를 원자적(atomic)으로 한 번에 가져올 때까지 3개 결과를 버리기
  → 로그 수집은 원자성이 필요한 트랜잭션이 아닙니다. 불필요한 지연입니다.
- 상세한 구조화 보고서를 단순 'error'로 취급하고 해당 서비스 조사를 포기하기
  → 애써 만든 정보를 버리는 것이며 결함 허용성 원칙 위반입니다.

### 4.4 실패한 부분을 명시적으로 표시하기 (Annotation)

**성공한 결과는 보고하되, 실패한 부분을 명시적으로 표시(annotate)한다.**

```markdown
## 경쟁사 가격 비교
| 경쟁사 | 스타터 | 프로 |
|---|---|---|
| Acme  | $19 | $49 |
| Bolt  | $25 | $60 |
| Cirrus | 수집 불가 | 수집 불가 |

주: Cirrus 사이트는 봇 방지 보호로 403 응답 (재시도 2회 후 실패). 가격 정보 미확보.
```

**해서는 안 되는 것들:**

- **추정치로 빈칸 채우기**: "시장 동향상 대략 $22 정도로 추정" → 환각을 데이터인 척 제공하는 행위입니다.
  읽는 사람은 실측치와 구분할 수 없습니다. 빈 구간을 그럴듯한 내용으로 지어내 채우는 것은
  **의도적 환각**이며 안전성·신뢰성 원칙의 심각한 위반입니다.
  **공백을 감추는 것보다 공백을 드러내는 것이 항상 낫습니다.**
- **누락 사실을 표기 없이 숨기기**: 3자 비교인 척하면서 한 곳의 데이터가 없다는 걸 말하지 않는 것은
  신뢰성 훼손입니다.
- **전체 보고서를 무기한 보류하기**: 한 곳이 막혔다고 성공한 2곳 정보까지 붙잡아 두면
  워크플로 전체가 마비됩니다.
- **전체 워크플로를 강제 종료하기**: 서브에이전트 하나의 인프라 장애로 시스템 전체를 죽이는 것은
  과잉 대응입니다. 오류를 상위에 알리고 부분 재시도나 대체 경로를 시도하는 것이 정석입니다.

### 4.5 커버리지 주석 (Coverage Annotation)

6개 서브에이전트 중 2개가 도중에 출처 접근 권한을 잃었다면, 최종 보고서는
**정보 커버리지가 불균등**합니다. 이때 하위 독자(Downstream Reader)에게 신뢰성을 정직하게
전달하는 방법이 **커버리지 주석**입니다.

즉, 섹션별로 "이 부분은 완료된 출처로 충분히 뒷받침됨 / 이 부분은 출처 접근 실패로 공백(gap) 있음"을
명시합니다.

```markdown
## 유럽 시장 동향  [커버리지: 완전 — 출처 4/4 확보]
...

## 아시아 시장 동향  [커버리지: 부분 — 지정 출처 3개 중 1개만 접근 성공]
> 주의: 이 섹션은 출처 접근 실패로 불완전합니다.
...
```

**피해야 할 방식:**

- 두루뭉술한 일반 면책 조항(Generic Disclaimer) 하나 붙이기 → 독자가 어느 부분이 부실한지 알 수 없음.
- 완전한 섹션과 불완전한 섹션을 구분 없이 하나의 균질한 서술로 제시
  → 독자가 불완전한 정보를 무비판적으로 신뢰.
- 영향받은 섹션을 통째로 삭제 → 보고서의 주제 범위가 왜곡되고, 조사 시도조차 있었는지 알 수 없어짐.

**원칙**: 신뢰성은 "완벽함"이 아니라 **한계의 투명한 공개**에서 나옵니다.

## 5. 상태 영속성과 재개 가능성

### 5.1 왜 필요한가

수 시간짜리 멀티 에이전트 작업은 도중에 죽을 수 있습니다.
프로세스 크래시, OOM, 인프라 장애, 네트워크 단절, 배포로 인한 재시작 등.

상태를 아무 데도 저장하지 않았다면 지금까지의 모든 작업이 사라집니다.
LLM 호출은 비싸므로 재실행 비용이 실제 금액으로 나타납니다.

### 5.2 체크포인팅과 매니페스트

**체크포인팅(checkpointing)**: 각 에이전트가 진행 상황과 결과를
디스크나 외부 저장소에 **진행하면서 지속적으로** 기록하는 것.

**매니페스트(manifest)**: 어떤 에이전트가 어떤 상태이고 결과물이 어디에 있는지를 정리한 색인 파일.

```json
{
  "run_id": "explore-2025-03-04",
  "agents": [
    { "id": "a1", "task": "payments 서비스 탐색",  "status": "completed",
      "output": "out/a1-payments.json" },
    { "id": "a2", "task": "ledger 서비스 탐색",    "status": "completed",
      "output": "out/a2-ledger.json" },
    { "id": "a3", "task": "notifications 탐색",    "status": "completed",
      "output": "out/a3-notify.json" },
    { "id": "a4", "task": "auth 서비스 탐색",      "status": "pending" },
    { "id": "a5", "task": "webhook 처리 탐색",     "status": "pending" }
  ]
}
```

### 5.3 재개(resume) 절차

코디네이터가 크래시 후 재시작되면:

1. 매니페스트를 읽어 각 에이전트의 상태를 파악합니다.
2. `completed` 인 에이전트는 **다시 실행하지 않습니다.**
3. 완료된 에이전트의 결과 파일을 로드하여, 남은 에이전트의 프롬프트에
   기존 발견 사항으로 **주입(inject)** 합니다.
4. `pending` 인 작업만 실행합니다.

**잘못된 대응들:**

- 완료된 결과물을 버리고 5개 전부 처음부터 재실행 → 비용과 시간 낭비.
- 완료된 결과를 버리고 사용자에게 "기억나는 대로 말해달라"고 요청 → 파일에 이미 정확히 저장되어 있는데
  인간의 기억에 의존하는 퇴행입니다.
- 크래시된 에이전트가 스스로 살아나기를 무한정 기다림 → 아무 일도 일어나지 않습니다.
- 각 에이전트가 상태를 자기 메모리에만 보관하고 아무것도 파일로 쓰지 않음
  → 애초에 복구가 불가능해집니다. 이것이 근본 원인입니다.
- 대화 이력이 컨텍스트에 영원히 남아 있으리라 가정 → 컨텍스트 열화로 실패합니다.

원칙: **재개 가능성은 사후 대응이 아니라 사전 설계다.**
크래시가 나기 전에 상태를 파일에 써 두었어야만 복구가 가능합니다.

## 6. 실패를 숨기면 생기는 일 — 조용한 실패와 허위 커버리지

### 6.1 조용한 실패 (Silent Failure)

**조용한 실패**란, 실제로는 실패했는데 성공한 것처럼 보고하는 것입니다.
에이전트 시스템에서 가장 위험한 실패 유형입니다.

사례:

```json
// 실제 상황: API 키가 만료되어 데이터 제공자에 접근조차 못 함
// 서브에이전트가 반환한 것:
{ "status": "success", "findings": [] }
```

파이프라인은 "깔끔하게" 계속 진행됩니다. 코디네이터는 `findings: []` 를 보고
**"조사했는데 문제가 없더라"** 로 해석합니다. 그리고 "규제 항목 전체 커버리지 확인, 이상 없음"이라는
보고서를 씁니다.

**결과: 허위 보고.** 실제로는 아무것도 확인하지 못한 공백(gap)인데,
"확인 결과 이상 없음"으로 둔갑했습니다. 규제 대상 업무에서는 치명적입니다.

같은 구조가 보안 스캔에서도 반복됩니다. 40개 파일 중 15개만 스캔하고 크래시했는데 취약점 2건을
"완전한 최종 결과"로 보고하면, 스캔조차 되지 않은 25개 파일이 **"안전 확인됨"** 으로 둔갑합니다.

핵심 원칙: **장애와 데이터 누락은 반드시 명시적인 오류 상태로 상위에 노출되어야 한다.**
상위 에이전트가 올바른 판단을 하려면 정확한 신호를 받아야 합니다.

### 6.2 허위 커버리지가 만들어지는 세 가지 경로

| 경로 | 무슨 일이 벌어지나 | 막는 방법 |
|---|---|---|
| 접근 실패를 빈 결과로 반환 | "못 읽었다"가 "없다"로 확정됨 (silent data loss) | `status: error` + `results: null` (1장) |
| 부분 결과를 완전한 결과로 보고 | 처리되지 않은 범위가 "검사 완료"로 둔갑 | `files_unscanned` 등 미처리 범위 명시 (4.2) |
| 공백을 추정치·생성 텍스트로 메움 | 환각이 실측치와 구분 불가능해짐 | 커버리지 주석으로 공백을 드러냄 (4.4, 4.5) |

### 6.3 검증과 신뢰의 균형

"서브에이전트 출력을 전부 사람이 수동 검증해야 한다"는 대응은 답이 아닙니다.
그러면 자동화를 만든 이유가 사라집니다.
근본 원인은 **잘못된 상태값을 반환한 서브에이전트 쪽**에 있고, 고쳐야 할 곳도 거기입니다.

### 6.4 이 장의 요약 원칙

1. **못 읽은 것과 없는 것을 구분한다.** (`error`/`null` vs `success`/`[]`)
2. **일시적 오류는 상한 있는 백오프로 스스로 처리하고, 구조적 오류는 시도 내역과 함께 올린다.**
3. **에러는 신호가 아니라 복구 결정을 위한 입력 데이터다.** (유형·시도·부분결과·대안)
4. **가진 것을 주고, 못 가진 것을 명시한다.**
5. **재개 가능성은 사전 설계다.** 크래시 전에 파일로 써 둔 것만 살아남는다.
6. **공백을 감추는 것보다 공백을 드러내는 것이 항상 낫다.**
