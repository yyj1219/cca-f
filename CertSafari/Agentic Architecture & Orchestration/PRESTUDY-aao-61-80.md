# 사전 학습 노트 — Agentic Architecture & Orchestration (61~80 범위)

이 문서는 이 범위에서 다루는 개념을 **아무 배경지식이 없는 상태**에서 읽어도 이해할 수 있도록 처음부터 설명합니다.

1. 에이전트 루프의 기본 원리 (Messages API, tool_use / tool_result, stop_reason)
2. 워크플로 아키텍처 패턴 (프롬프트 체이닝, 오케스트레이터-워커, 적응형 분해)
3. 서브에이전트 (정의, 프롬프트 계층, 병렬 호출, 중첩 깊이)
4. 훅(Hooks)과 권한 제어 (PreToolUse / PostToolUse / Notification, permissionDecision)
5. 세션 관리 (resume, fork_session, /clear, /compact, 캐시 무효화, 체크포인팅)
6. 사람 개입(Human-in-the-Loop)과 핸드오프 설계

마지막에 용어 사전이 있습니다.

## 0. 먼저: "에이전트"란 무엇인가

LLM(대규모 언어 모델)은 원래 "텍스트를 받아 텍스트를 뱉는" 함수입니다. 스스로 파일을 읽거나, DB를 조회하거나, 결제를 하지 못합니다.

**에이전트(Agent)** 는 여기에 두 가지를 붙인 것입니다.

- **도구(Tool)**: 모델이 "이 함수를 이런 인자로 실행해 줘"라고 *요청*할 수 있는 외부 기능 목록. 실제 실행은 모델이 아니라 여러분의 애플리케이션 코드가 합니다.
- **루프(Loop)**: 모델이 도구를 요청하면 → 실행하고 → 결과를 다시 모델에게 돌려주고 → 모델이 다음 판단을 하는, 반복되는 사이클.

이 "루프"가 이 범위의 심장입니다. 아래에서 한 바퀴를 완전히 해부합니다.

## 1. 에이전트 루프의 해부

### 1.1 대화는 "메시지 배열"이다

Claude Messages API에 요청을 보낼 때 여러분이 보내는 것은 대화 전체의 기록입니다.

```json
{
  "model": "claude-...",
  "system": "너는 인시던트 대응 도우미다.",
  "tools": [ ],
  "max_tokens": 4096,
  "messages": [
    { "role": "user",      "content": "결제 서비스가 느려요." },
    { "role": "assistant", "content": [ ] },
    { "role": "user",      "content": [ ] }
  ]
}
```

핵심 사실: **API는 상태를 기억하지 않습니다(stateless).** 매 요청마다 지금까지의 messages 배열 전체를 다시 보냅니다. "대화 맥락"이란 곧 이 배열입니다.

### 1.2 content 는 "블록의 배열"이다

`content`는 단순 문자열일 수도 있지만, 도구를 쓰는 순간부터는 **블록(block) 배열**이 됩니다.

| 블록 타입 | 누가 만드나 | 의미 |
|---|---|---|
| `text` | 모델 / 사용자 | 평범한 텍스트 |
| `tool_use` | 모델(assistant) | "이 도구를 이 인자로 실행해 달라"는 요청 |
| `tool_result` | 애플리케이션(user 역할로) | 실행 결과를 모델에게 되돌려 주는 것 |

`tool_use` 블록의 실제 모양:

```json
{
  "type": "tool_use",
  "id": "toolu_01A9",
  "name": "currency_convert",
  "input": { "amount": 100, "from": "USD", "to": "KRW" }
}
```

이에 대응하는 `tool_result` 블록:

```json
{
  "type": "tool_result",
  "tool_use_id": "toolu_01A9",
  "content": "133,200 KRW"
}
```

**`tool_use_id` 짝맞춤이 절대 규칙입니다.** 모델이 요청한 각각의 `tool_use`에는 그와 같은 id를 가진 `tool_result`가 정확히 하나씩 있어야 합니다. 임의로 하나의 id로 합치거나, 일부만 응답하면 API 검증 오류가 나거나 모델이 맥락을 잃습니다.

### 1.3 병렬 도구 호출 (Parallel Tool Use)

모델은 **한 번의 응답(한 턴) 안에서 여러 개의 `tool_use` 블록**을 낼 수 있습니다. 서로 독립적인 조회라면 굳이 순차로 할 이유가 없기 때문입니다.

예: 가격 계산에 환율 조회와 세율 조회가 둘 다 필요하다 → 모델이 한 턴에 두 개의 `tool_use`를 낸다.

이때 애플리케이션 루프가 해야 할 일:

1. 응답 안의 **모든** `tool_use` 블록을 찾는다.
2. **전부** 실행한다 (가능하면 동시에).
3. 각각에 대해 **개별 `tool_result` 블록**을 만든다. 각 블록은 자기 `tool_use_id`를 가진다.
4. 이 `tool_result` 블록들을 **하나의 user 메시지 content 배열에 모두 담아** 다음 요청으로 보낸다.

```python
tool_results = []
for block in response.content:
    if block.type == "tool_use":
        output = run_tool(block.name, block.input)
        tool_results.append({
            "type": "tool_result",
            "tool_use_id": block.id,      # 개별 매칭
            "content": output,
        })

messages.append({"role": "assistant", "content": response.content})
messages.append({"role": "user", "content": tool_results})  # 한 턴에 전부
```

**하지 말아야 할 것들**

- 두 결과를 하나의 `tool_result`로 합치기 → id 매핑 파손, API 검증 오류.
- 대화를 두 갈래로 쪼개서 각각 따로 보내기 → 모델이 두 결과를 종합할 수 없음. 하나의 연관된 스레드 안에서 함께 전달해야 함.
- 첫 번째만 실행하고 나머지 무시 → 데이터 누락으로 작업 실패. **"턴당 도구 하나"라는 제약은 존재하지 않습니다.**

### 1.4 `stop_reason` — 루프의 신호등

응답에는 모델이 왜 생성을 멈췄는지 알려 주는 `stop_reason` 필드가 있습니다. 루프의 분기는 이 값으로 합니다.

| 값 | 의미 | 루프가 해야 할 일 |
|---|---|---|
| `end_turn` | 모델이 할 말을 다 하고 자연스럽게 끝냄 | 루프 종료, 결과 반환 |
| `tool_use` | 도구 실행을 요청하며 멈춤 | 도구 실행 → `tool_result` 붙여서 재요청 |
| `max_tokens` | **출력 토큰 상한에 걸려 문장 중간에 잘림** | 미완성! 이어쓰기 요청하거나 max_tokens를 늘려 재시도 |
| `stop_sequence` | 지정한 중지 문자열이 나와서 멈춤 | 상황에 따라 처리 |

**가장 흔한 버그**: 코드가 `tool_use`와 `end_turn` 두 가지만 분기하고, 나머지는 `else`(= 종료)로 흘려보내는 것.

```python
if resp.stop_reason == "tool_use":
    ...도구 실행...
else:                      # max_tokens 도 여기로 떨어진다
    return resp            # 잘린 미완성 응답을 "완성품"으로 취급
```

이러면 **잘린 보고서를 최종 결과로 오인하고 에이전트를 조기 종료**합니다. 예외도 안 나고 조용히 데이터가 손실되므로 발견하기 어렵습니다.

정확히 알아 둘 사실:

- `max_tokens`는 Messages API가 반환하는 **정식 표준 값**입니다. 그 자체로 미처리 예외나 크래시를 일으키지 않습니다.
- 잘못된 폴백이 있다고 해서 응답을 버리고 첫 요청부터 다시 보내는 일은 일어나지 않습니다.
- 코드를 고치지 않는 한 다음 요청의 `max_tokens` 값이 **자동으로 늘어나지 않습니다.**

그러므로 반드시 명시적으로 분기하십시오.

```python
if resp.stop_reason == "max_tokens":
    raise TruncatedResponse("응답이 잘림 — 이어쓰기 또는 상한 조정 필요")
```

### 1.5 모델 중심 제어 흐름 vs 애플리케이션 하드코딩

에이전트 루프에서 "다음에 무엇을 할지"를 **누가** 결정하느냐가 아키텍처의 핵심 갈림길입니다.

**(A) 모델 중심(Model-driven / Dynamic)**

애플리케이션은 `tool_result`를 대화에 덧붙여 그대로 모델에게 되돌려 줄 뿐입니다. 모델이 갱신된 맥락을 읽고 스스로 "도구를 더 쓸까(`tool_use`), 답을 마무리할까(`end_turn`)"를 판단합니다.

- 장점: 중간 발견에 **적응(adapt)** 한다. 로그를 봤더니 디스크 문제 같으면 메트릭 대신 디스크 도구를 부르는 식.
- 단점: 비결정론적. 같은 입력에도 경로가 달라질 수 있다.
- 예: DB 조회 결과가 0행이면 더 넓은 필터로 재시도할지, 그냥 요약으로 마무리할지를 **모델이** 판단하게 하려면 `tool_result`를 그대로 되돌려 주기만 하면 됩니다.

**(B) 애플리케이션 하드코딩(Deterministic / Static)**

코드에 `if rows == 0: 다시 조회` 같은 규칙을, 혹은 "로그 확인 → 메트릭 확인 → 재시작"처럼 고정된 순서를 박아 둡니다. 이전 단계 결과가 무엇이든 다음 단계는 정해져 있습니다.

- 장점: 예측 가능, 감사(audit)하기 쉬움, 저렴함.
- 단점: 중간 결과를 반영하지 못하는 **고정된 트리(fixed tree)**. 예상 밖 상황을 못 다룸.

같은 성격의 안티패턴들 — 겉으로는 LLM을 쓰지만 제어권은 코드에 있습니다:

- 애플리케이션이 행 개수를 검사해 **하드코딩된 프롬프트 템플릿 두 개 중 하나**를 고르기.
- 가능한 쿼리 개선안을 미리 다 계산해 두고 **행 개수를 키로 하는 룩업 테이블**에서 꺼내기.
- 외부 **룰 엔진**이 다음 도구를 정하고 Claude에게는 승인만 받기.

부수적 사실: (A)에서도 `stop_reason` 검사는 **필수**입니다. 도구 호출 여부를 알아야 루프를 돌 수 있기 때문입니다. 또 (A)라고 해서 사용 가능한 도구를 전부 한 턴에 몰아 부르지 않습니다 — 필요한 것만 골라 부릅니다. 그리고 (A)와 (B)는 도구 호출과 반환값이 다르므로 **대화 기록 자체가 완전히 달라집니다.**

## 2. 워크플로 아키텍처 패턴

작업을 어떻게 쪼갤 것인가(**작업 분해, task decomposition**)에 대한 대표 패턴들입니다. 선택 기준은 단 하나: **작업의 구조가 미리 정해져 있는가, 실행 중에 달라지는가.**

### 2.1 프롬프트 체이닝 (Prompt Chaining)

고정된 선형 단계들을 순서대로 잇는 것. 각 단계의 출력이 다음 단계의 입력이 됩니다.

```
[개요 작성] → [본문 확장] → [문법 교정]
[대화록 수집] → [구조화된 요약] → [3개 언어 번역]
```

**적용 조건**

- 단계의 개수가 절대 변하지 않는다(never varies).
- 각 단계의 출력이 항상 정확히 다음 단계가 필요로 하는 것이다.
- 순서가 런타임에 바뀔 일이 없다.

**체크포인트 / 게이트 (Checkpoint, Gate)**

단계 사이에 **프로그래밍 방식의 검증(programmatic check)** 을 끼워 넣습니다. LLM 판단이 아니라 코드로 확인하는 것이 포인트입니다.

```python
outline = run_stage("개요 작성", transcript)
assert_valid_outline(outline)      # 게이트: 형식이 깨졌으면 여기서 중단
prose = run_stage("본문 확장", outline)
```

이렇게 하면 잘못된 개요가 본문 단계로 흘러 들어가 오류를 증폭시키는 것을 막습니다. "고정 파이프라인 + 단계 사이 프로그래밍 검증"은 결정론적 워크플로의 표준형입니다.

### 2.2 오케스트레이터-워커 (Orchestrator-Workers)

중앙 조정자(오케스트레이터/코디네이터)가 런타임에 **몇 개의, 어떤 하위 작업을 돌릴지 결정**하고, 워커(주로 서브에이전트)에게 나눠 준 뒤 결과를 종합합니다.

- 적용 조건: 필요한 작업 수나 순서가 입력에 따라 달라진다.
- 고정 단계 시나리오에 이걸 쓰면 **불필요한 오버헤드와 비결정성**만 늘어납니다. 순서가 절대 안 바뀌는 파이프라인에 "요약 먼저인지 번역 먼저인지 런타임에 판단"하는 오케스트레이터를 두는 것은 낭비입니다.

### 2.3 적응형 분해 (Adaptive Decomposition)

실행 도중 발견한 사실에 따라 **계획 자체에 새 하위 작업을 추가**하는 방식.

전형적인 실패 사례: 5단계 고정 체인으로 DB 마이그레이션을 설계했는데(스키마 추출 → 마이그레이션 스크립트 생성 → 문법 검증 → 마이그레이션 적용 → 행 수 확인), 테스트 중 "기본값 없는 새 컬럼"이 발견되어 **계획에 없던 백필(backfill) 단계**가 필요해졌습니다.

- 근본 결함: 작업의 구조가 **발견되는 스키마 세부사항에 따라 가변적(variable structure)** 인데 고정 체인을 썼다는 것.
- 올바른 해법: 런타임 분석 결과에 따라 백필 같은 하위 작업을 **동적으로 추가**할 수 있는 적응형 분해 / 동적 오케스트레이션.
- 잘못된 해법들:
  - 체크포인트 하나 추가 → 문제를 *감지*할 뿐, 없던 단계를 *생성*하지는 못함.
  - 여섯 번째 백필 단계를 모든 마이그레이션에 하드코딩 → 백필이 불필요한 경우에도 매번 실행되어 불필요한 연산과 오류 유발.
  - "사전에 스키마를 완전히 알았어야 한다" → 런타임 스키마 추출 자체는 문제가 아님. 추출 결과에 유연히 대응하지 못한 설계가 문제.

### 2.4 패턴 선택 요약

| 상황 | 적합한 패턴 |
|---|---|
| 단계 수·순서 불변, 출력이 곧 다음 입력 | 프롬프트 체이닝 (+ 단계 간 체크포인트) |
| 하위 작업 개수/순서가 입력에 따라 달라짐 | 오케스트레이터-워커 |
| 실행 중 발견에 따라 새 작업이 생김 | 적응형 분해 |
| 중간 결과에 따라 다음 도구를 골라야 함 | 모델 중심 에이전트 루프 |

**단일 서브에이전트에 "알아서 다 해줘"라고 뭉뚱그려 맡기는 것**은 겉보기엔 간단하지만, 단계 경계가 암묵적(implicit)이 되어 중간 산출물을 검증할 수도, 실패 지점을 특정할 수도 없습니다. 명시적 단계와 중간 산출물이 필요한 작업에는 부적합합니다.

## 3. 서브에이전트 (Subagents)

### 3.1 무엇이고 왜 쓰나

**서브에이전트**는 자기만의 컨텍스트 창, 시스템 프롬프트, 도구 목록을 가진 별도의 에이전트 인스턴스입니다. 메인 에이전트(코디네이터)가 하위 작업을 위임합니다.

쓰는 이유:

- **컨텍스트 격리**: 대량의 탐색 결과가 메인 대화를 오염시키지 않고, 결론만 돌아옵니다.
- **전문화**: 역할별로 다른 지침과 도구를 줄 수 있습니다.
- **병렬화**: 독립적인 작업을 동시에 돌립니다.

### 3.2 AgentDefinition — 두 종류의 프롬프트

서브에이전트는 **두 층의 프롬프트**로 작동합니다. 이 구분이 자주 헷갈립니다.

```
AgentDefinition {
  description: "DB 마이그레이션 전문가",
  prompt: "너는 SQL 마이그레이션 전문가다. 항상 롤백 전략을 세우고,
           데이터 무결성 검사를 포함하며, ...",   ← 정적 / 지속적
  tools: [...],
  model: "..."
}
```

- **`AgentDefinition.prompt`** = 그 서브에이전트의 **지속적인 시스템 프롬프트이자 전문성/페르소나**. 정의 시점에 한 번 정해지고, 호출될 때마다 항상 적용됩니다. SQL 모범 사례, 롤백 전략, 데이터 무결성 검사 같은 **변하지 않는 공통 지침**이 여기 들어갑니다.
- **호출 시 프롬프트(per-call prompt)** = 코디네이터가 이번 실행에서 맡기는 **구체적 작업 지시**. "`orders` 테이블에 `region` 컬럼을 추가해라" 같은 것.

**둘은 대체 관계가 아니라 결합 관계입니다.** 정의 프롬프트는 시스템 지침으로, 호출 프롬프트는 그 회차의 작업 지시로 함께 모델에 전달되어 하나의 완전한 맥락을 이룹니다.

흔한 오해들 (모두 사실이 아님):

- 호출 프롬프트가 오면 `AgentDefinition.prompt`가 런타임에 무시된다 ✗
- 호출 프롬프트가 서브에이전트가 아니라 **코디네이터의 시스템 프롬프트**로 병합된다 ✗
- 둘을 이어 붙인 뒤 **짧은 쪽 길이에 맞춰 잘라낸다** ✗ (그런 로직은 존재하지 않습니다)

### 3.3 병렬(동시) 호출

서로 의존하지 않는 하위 작업은 **동시에(concurrently)** 호출해야 합니다.

- 순차 실행: 총 시간 = 각 작업 시간의 **합(sum)**
- 동시 실행: 총 시간 ≈ **가장 느린 작업 하나(slowest)** 의 시간

예: PR 리뷰에 스타일 검사·보안 검사·테스트 커버리지 검사 3개가 필요하고 서로 독립적이라면, 셋을 한꺼번에 띄우고 전부 끝난 뒤 종합합니다.

주의할 오해:

- **`maxTurns`를 올리면 빨라진다** ✗ — `maxTurns`는 에이전트가 수행할 수 있는 최대 턴(대화/도구 호출 횟수)을 제한하는 **가드레일**입니다. 상한을 올린다고 개별 작업이 빨리 끝나지 않습니다.
- 셋 중 하나만 돌리고 결과에 따라 나머지를 생략 → 세 결과를 모두 종합해야 하는 요구사항 위반.
- 서브에이전트를 없애고 코디네이터 한 곳의 로직으로 합치기 → 컨텍스트 오염과 단일 에이전트 오버헤드가 커지고 병렬화 이점도 사라짐.

### 3.4 중첩 깊이 (Nesting Depth)

서브에이전트가 또 다른 서브에이전트를 낳는 재귀 구조가 가능합니다. 초기 버전에서는 금지되었으나, Claude Code는 이후 **중첩 서브에이전트(Nested Subagents)를 공식 지원**합니다.

무한 재귀와 자원 고갈을 막기 위한 시스템 가드레일로, **메인 에이전트를 1단계로 포함하여 최대 5단계(5 levels deep)** 까지 허용됩니다.

- `Agent` 도구를 허용 목록에 넣어도 **무제한이 되지 않습니다** — 시스템 캡(cap)이 걸립니다.
- 서브에이전트의 모델 티어(tier)를 바꾼다고 깊이 제한이 달라지지 않습니다.
- "서브에이전트는 절대 다른 서브에이전트를 못 만든다"는 것은 초기 버전의 제약이며 현재는 해당하지 않습니다.

## 4. 훅(Hooks)과 권한 제어

### 4.1 훅이란

**훅(Hook)** 은 에이전트 실행 중 특정 이벤트가 발생할 때 자동으로 실행되는 사용자 정의 코드입니다. LLM의 판단에 맡기지 않고 **결정론적으로(deterministically)** 정책을 강제하기 위한 장치입니다.

프롬프트로 "환불 전에 반드시 확인해"라고 부탁하는 것은 모델이 지킬 수도, 안 지킬 수도 있는 **확률적** 방법입니다. 훅은 코드이므로 **항상** 실행됩니다. 규정 준수(compliance)가 걸린 곳에는 훅을 씁니다.

### 4.2 주요 훅 이벤트

| 훅 | 시점 | 차단 가능? | 용도 |
|---|---|---|---|
| **PreToolUse** | 도구 실행 **직전** | ✅ 가능 | 권한 검사, 입력 검증, 차단, 인자 수정 |
| **PostToolUse** | 도구 실행 **직후** | ❌ (이미 실행됨) | 결과 로깅, 후처리, 포맷 검사 |
| **Notification** | 알림 발생 시 | ❌ | 상태 메시지 전달, 로깅 |

**PostToolUse는 사후약방문입니다.** 환불이 이미 나간 뒤에 플래그를 다시 검사해 봐야, 되돌릴 수 없는(irreversible) 작업은 이미 부작용(side-effect)을 남겼습니다.

**Notification 훅은 상태 메시지·로깅 전용입니다.** 특정 도구 이름에 매처를 걸 수는 있지만(그건 가능합니다), **`permissionDecision`을 반환할 수 없어 호출을 막지 못합니다.** "검증 없이 환불이 호출되면 경고 로그를 남긴다"는 설계는, 경고가 남을 때쯤이면 환불이 이미 실행된 뒤입니다. 결정론적 강제가 필요하면 **PreToolUse**를 써야 합니다.

Notification 훅에 대한 흔한 오해들 (모두 사실 아님):

- 도구 이름 매칭이 아예 불가능해서 모든 도구 호출마다 발동한다 ✗
- 도구 호출 **전**에 실행되며 사람이 매번 클릭해야 진행된다 ✗
- Python SDK에서만 쓸 수 있고 TypeScript SDK에는 훅 등록 기능이 없다 ✗ (주요 SDK가 공통 지원)

### 4.3 매처(Matcher)와 이벤트 기반 실행

훅은 **매처(matcher)** 로 어떤 도구에 반응할지 지정합니다.

```json
{
  "PreToolUse": [
    {
      "matcher": "process_refund",
      "hooks": [{ "type": "command", "command": "./check_refund.sh" }]
    }
  ]
}
```

**결정적으로 중요한 성질**: PreToolUse 훅은 **매칭된 그 도구가 실제로 호출되는 순간에만** 실행됩니다. 등록만 해 두면 알아서 도는 것이 아닙니다.

여기서 나오는 함정: "선행 도구 강제"를 훅 사이 파일 통신으로 구현하려는 설계입니다.

```
get_customer 훅   →  세션 파일에 "verified" 마커를 쓴다
process_refund 훅 →  그 파일을 읽어 검증한다
```

이 설계는 **안전하지 않습니다.** 이유:

- 각 훅은 자기 매처에 해당하는 도구가 호출될 때만 돕니다.
- 모델이 `get_customer`를 **아예 건너뛰고** `process_refund`를 바로 부를 수 있습니다. LLM의 도구 호출 순서는 런타임이 보장하지 않습니다(**비결정성, nondeterminism**).
- 그러면 마커 파일은 쓰인 적이 없고, `process_refund` 훅은 존재하지 않는 파일이나 유효하지 않은 데이터를 읽게 됩니다.

부수적으로 정확히 알아 둘 사실:

- 훅들끼리 **로컬 파일 시스템이나 동일 세션 환경을 통해 상태를 공유하는 것 자체는 가능**합니다. 문제는 "순서 보장"이지 "공유 불가"가 아닙니다.
- 런타임이 도구 이름을 **알파벳 순으로 정렬해 훅 실행 순서를 보장하는 메커니즘은 존재하지 않습니다.**
- 등록된 모든 PreToolUse 훅이 매처와 무관하게 매번 병렬 실행되는 것도 **아닙니다.** 해당 도구가 트리거될 때 선행 실행됩니다.

올바른 해법 방향: 순서를 "다른 훅이 남긴 흔적"이 아니라, **`process_refund` 훅 자신이 호출 시점에 직접 검증할 수 있는 근거**로 확인하게 만드는 것(4.5절 참조).

### 4.4 `permissionDecision` — 위험 기반 권한 제어

PreToolUse 훅은 JSON을 반환해 실행 여부를 결정합니다.

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Use the sandboxed low-privilege wrapper script instead"
  }
}
```

세 가지 결정 값:

| 값 | 동작 |
|---|---|
| `allow` | 사람 확인 없이 자동 허용. 도구가 즉시 실행됨. |
| `ask` | 사용자에게 **대화형 승인 프롬프트**를 띄움. 사람이 확인해야 진행. |
| `deny` | 도구 호출을 **취소(cancel)**. 실행되지 않음. |

**`permissionDecisionReason`의 역할이 중요합니다.** `deny`일 때 이 사유 문자열이 **Claude에게 피드백으로 전달**됩니다. 모델은 왜 거부됐는지 이해하고, 위 예시처럼 "그럼 샌드박스된 저권한 래퍼 스크립트를 쓰자"는 **대안 행동(subsequent action)** 을 스스로 취할 수 있습니다. 즉 `deny`는 단순 차단이 아니라 **모델을 올바른 방향으로 유도하는 통로**입니다.

`permissionDecisionReason`은 `deny`와 `ask` 모두에서 유효하며, 세션을 에러로 종료시키지 않습니다. 대화형 승인 프롬프트를 띄우려면 `deny`가 아니라 `ask`를 반환해야 합니다.

**위험 기반 차등 적용(Risk-based permission)** — 도구마다 위험도와 **가역성(reversibility)** 이 다르므로 결정을 달리 줍니다.

| 작업 | 성격 | 적절한 결정 |
|---|---|---|
| 마스킹된 주문 내역 조회 | 읽기 전용, 민감정보 마스킹, 저위험 | `allow` (자동 허용) |
| 환불 처리 | 금전적, **되돌릴 수 없음** | `ask` (사람 확인 후 진행) |

잘못된 조합들:

- 둘 다 `allow` → 신원 미검증 상태에서 되돌릴 수 없는 금전 작업까지 자동 허용. 심각한 보안·재무 위험.
- 둘 다 `deny` → 위험도 무관 일괄 차단. 위험 기반 제어의 취지에 어긋나고 UX를 파괴함.
- 읽기에 `ask`, 환불에 `deny` → 저위험 작업을 불필요하게 지연시키고, "확인 후 실행"이라는 `ask`의 용도를 엉뚱한 곳에 배치.

### 4.5 신뢰할 수 있는 검증 데이터 — 상태 결합도 낮추기

에이전트 보안에서 반복되는 실패 유형이 있습니다: **간접적인 공유 상태(플래그)에 의존한 검증.**

문제 사례:

- `process_refund`를 게이트하는 PreToolUse 훅이 `is_verified`라는 불리언 플래그만 봅니다.
- 이 플래그는 별도의 `mark_verified` 도구가 세팅합니다.
- 사람 검토자가 신분증을 **거부**했는데, 소프트웨어 버그로 `is_verified`가 `true`가 되었습니다.
- 훅은 `true`를 믿고 환불을 통과시킵니다 → 무단 환불.

**교훈**: 잘못 쓰일 수 있는 제3의 상태 변수에 의존하지 말고, **도구 호출 파라미터에 포함된 명시적 검증 결과(원천 데이터)를 훅이 직접 검사(inspect)** 하게 만드십시오. "사람 검토가 명시적으로 통과되었음(expressly passed)"을 나타내는 값이 호출 인자에 실려 오고, 훅이 그것을 확인하는 구조입니다. 검증 근거와 검증 대상이 같은 호출에 묶이므로, 중간에 오염될 창구 자체가 사라집니다. 이것을 **상태 결합도 저하(Decoupling State Failure)** 라고 부릅니다.

효과 없는 대안들:

- **PostToolUse로 사후 검증 후 거래 되돌리기** → 이미 부작용 발생. 게다가 똑같이 오염된 플래그를 다시 보는 것이라 근본 해결이 아님.
- **더 크고 유능한 모델로 교체** → 결정론적 소프트웨어 상태 버그와 입력 검증 문제는 모델 크기로 풀리지 않습니다. 비싸고 비효율적입니다.
- **훅 타임아웃을 늘려 플래그를 주기적으로 재확인** → 플래그를 쓴 코드가 애초에 틀린 값을 썼다면, 몇 번을 다시 읽어도 같은 틀린 값입니다.

### 4.6 비동기 훅 (`async`) — 넌블로킹 감사

모든 도구 호출의 인자를 외부 감사(audit) 서비스로 보내야 하는데, 이 감사는 **허용/거부 판단과 무관**하고 **응답 시간을 늦추면 안 되는** 경우가 있습니다.

이때 PreToolUse 훅에서 감사 요청을 쏘고 다음을 반환합니다.

```json
{ "async": true, "asyncTimeout": 30000 }
```

런타임은 이 훅의 완료를 **기다리지 않고** 즉시 도구 실행과 다음 단계를 진행합니다(넌블로킹, non-blocking). `asyncTimeout`은 백그라운드 작업에 허용하는 최대 시간(ms)입니다.

부적절한 대안들:

- `permissionDecision: "ask"` → 매번 사람 확인 프롬프트가 뜨므로 응답 시간이 크게 늘고 불필요한 사용자 개입이 발생.
- `updatedInput`에 감사 페이로드를 끼워 넣기 → `updatedInput`은 원래 **도구 인자를 수정**할 때 쓰는 필드입니다. 감사 데이터를 넣으면 도구 본래의 스키마와 인자를 오염시키고, 백그라운드 외부 전송이라는 목적에도 맞지 않습니다.
- `permissionDecision: "defer"` → 감사 서비스 응답이 올 때까지 세션을 일시 정지(pause)시키므로 "지연시키지 말 것"이라는 핵심 조건 위반.

## 5. 세션 관리

### 5.1 세션이란, 그리고 무엇을 저장하는가

**세션(Session)** 은 하나의 대화 단위입니다. 세션 ID로 식별되며 나중에 **재개(resume)** 할 수 있습니다.

**결정적으로 중요한 사실: 세션은 "대화 이력(conversation history)"을 저장합니다. 파일 시스템의 스냅샷을 저장하지 않습니다.**

그래서 "이 대화 앞부분 시점의 파일 내용으로 되돌려 줘"라고 하면 에이전트는 못 합니다. 에이전트가 볼 수 있는 것은 **디스크의 현재(수정된) 내용**뿐입니다. 파일을 되돌리려면 **별도의 체크포인팅 메커니즘(checkpointing mechanism)** — Git 연동이나 전용 파일 체크포인터 — 가 필요합니다.

정확히 알아 둘 것:

- 세션 ID가 틀려서가 아닙니다. **올바른 resume도 파일 상태를 자동 복원하지 않습니다.**
- `fork_session`도 파일 스냅샷을 보존하는 기능이 **아닙니다** (대화 맥락 분기 기능입니다).
- 읽기 도구의 캐싱 범위 문제도 아닙니다. **세션 영속성의 범위가 애초에 '대화 이력'으로 한정**되어 있는 것입니다.

### 5.2 재개(resume)와 캐시 오염

세션을 재개하면 이전의 메시지, 도구 호출 이력, 그리고 그 위에 쌓인 **축적된 추론(accumulated reasoning)** 이 온전히 살아납니다. 이것이 resume의 최대 가치입니다.

그런데 함정이 있습니다. 과거 세션에서 어떤 파일(예: `CLAUDE.md`, 에이전트 정의 파일)을 읽었다면, 그 **읽은 시점의 내용이 대화 이력 안에 텍스트로 박혀** 있습니다. 그 뒤 다른 엔지니어가 별도 브랜치에서 그 파일을 대폭 고쳐 머지했다면 —

- 디스크의 실제 파일: **새 내용**
- 세션 맥락 안의 내용: **며칠 전의 낡은 내용**

재개했다고 해서 이 낡은 텍스트가 자동으로 갱신되지 않습니다. 그대로 믿으면 환각과 잘못된 분석이 나옵니다.

**올바른 대응**: 세션을 재개하되, **에이전트에게 그 파일이 변경되었음을 명시적으로 알려 다시 읽게(re-read) 합니다.** 그러면 축적된 추론은 보존한 채 해당 파일의 캐시만 최신화됩니다. 두 요구사항(추론 보존 + 변경 반영)을 동시에 만족하는 방법입니다.

효과 없는 대안:

- 그냥 재개하고 캐시된 이해를 믿는다 → 낡은 내용 기반 오작동·환각.
- 재개 후 `/compact` 실행 → `/compact`는 대화 이력을 **요약·압축**하는 기능일 뿐, 외부 파일의 최신 내용을 읽어오지 않습니다.
- 새 세션을 열고 이전 세션의 요약본을 넘긴다 → 요약 과정에서 상세한 추론 맥락이 **손실(context loss)** 됩니다. "축적된 추론 보존" 요구를 못 지킵니다.

### 5.3 `fork_session` — 세션 브랜칭

`fork_session`은 기존 세션을 재개할 때, 그 맥락(베이스라인)을 **복사해 새로운 브랜치 세션**을 만드는 옵션입니다. 원본 세션은 건드리지 않습니다. Git의 브랜치와 같은 개념입니다.

```
[분석 세션: 테스트 스위트 분석 완료]   ← 원본 보존
        ├── fork → 브랜치 1: extract-service 전략 탐색
        └── fork → 브랜치 2: strangler-fig 전략 탐색
```

**언제 쓰나**: 동일한 베이스라인 맥락에서 **서로 오염되면 안 되는 여러 갈래 실험**을 할 때.

같은 분석 세션을 `fork_session`을 켠 채로 두 번 재개하면, 공유 베이스라인을 가진 독립적인 두 브랜치가 생깁니다. 두 전략을 각각 끝까지 탐색해도 서로도, 원본도 오염되지 않습니다.

부적절한 대안:

- 새 세션 두 개를 열고 분석 결과를 **기억(수동 요약)에 의존해** 다시 설명 → 정교한 맥락과 데이터가 누락되고 비효율적.
- 재개 → 전략 1 완료 → `/clear` → 다시 재개 → `/clear`는 대화 맥락을 **초기화**하므로 같은 베이스라인에서 시작할 수 없습니다.
- 한 대화 안에서 두 전략 프롬프트를 번갈아 입력 → 맥락이 뒤섞이는 **교차 오염(cross-contamination)**.

### 5.4 `resume` / `fork_session` / `/compact` / `/clear` 정리

| 기능 | 하는 일 | 맥락 보존 |
|---|---|---|
| `resume` | 기존 세션의 대화 이력을 이어 감 | 100% 보존 |
| `fork_session` | 맥락을 복사해 독립 브랜치 생성 | 베이스라인까지 보존, 이후 분리 |
| `/compact` | 대화 이력을 요약·압축 (토큰 절약) | 요약으로 축약, 세부 손실 |
| `/clear` | 대화 맥락을 초기화 | 전부 폐기 |

**넷 중 어느 것도 디스크 파일 내용을 다시 읽어 오거나 파일 상태를 복원하지 않습니다.**

## 6. 사람 개입과 핸드오프 설계

### 6.1 Human-in-the-Loop (HITL)

에이전트가 되돌릴 수 없거나 고위험인 작업을 하기 전에 사람이 개입하도록 설계하는 것입니다. 앞서 본 `permissionDecision: "ask"` 가 대표적 구현 수단입니다.

### 6.2 핸드오프(Handoff) 프로토콜

에이전트가 처리 도중 사람 관리자에게 **에스컬레이션(escalate)** 해야 할 때, 그 관리자는 대개 **대화 내용을 볼 수 없습니다.** 인계 문서의 품질이 곧 대응 품질입니다.

**나쁜 설계: 자유 형식(free-text) "노트" 상자 하나.**

에이전트가 매번 다른 양식으로 쓰고, 무엇을 빠뜨렸는지 알 수도 없습니다. 전달되는 정보의 일관성과 품질이 보장되지 않습니다.

**좋은 설계: 필수 구조화 필드(required structured fields).**

```
고객 상세 정보(customer details)  : 이름, 계정 ID, 연락처
원인 분석(root cause analysis)   : 지금까지 파악한 문제의 원인
권장 조치(recommended action)    : 에이전트가 제안하는 다음 행동
```

이렇게 하면 **모든 핸드오프가 동일한 필수 요소(same essentials)를 빠짐없이 담습니다.** 관리자는 매번 같은 자리에서 같은 정보를 찾을 수 있고, 필드가 비어 있으면 누락을 즉시 알 수 있습니다. 4.5절의 "구조화된 명시적 데이터가 자유로운 텍스트나 간접 플래그보다 신뢰할 수 있다"는 원칙과 같은 맥락입니다.

효과 없는 개선들:

- **글자 수 제한만 늘리기** → 장황해질 뿐, 핵심 정보가 일관되게 포함된다는 보장이 없음.
- **시스템 프롬프트로 "고객 이름은 꼭 쓰라"고 지시** → 이름 외에도 원인 분석·조치 사항 등 필수 정보가 많고, 프롬프트 지시는 확률적이라 구조적 누락 문제를 해결하지 못함.
- **노트를 없애고 관리자가 고객에게 다시 전화해 처음부터 설명받기** → 고객 경험(CX)을 극단적으로 해치는 비효율.

## 7. 관통하는 설계 원칙 정리

1. **강제는 코드로, 유연성은 모델로.** 규정 준수·보안·순서 강제는 훅(결정론적)에게, 상황 적응은 모델(확률적)에게 맡깁니다.
2. **차단은 사전에.** 되돌릴 수 없는 작업은 PreToolUse에서 막습니다. 사후 로깅·사후 검증은 부작용을 되돌리지 못합니다.
3. **위험도와 가역성으로 권한을 차등한다.** 저위험 읽기는 `allow`, 되돌릴 수 없는 고위험 작업은 `ask`나 `deny`.
4. **검증은 원천 데이터로.** 오염될 수 있는 간접 플래그 대신, 호출 인자에 실린 명시적 검증 결과를 직접 검사합니다.
5. **구조화 > 자유 형식.** 핸드오프든 검증이든, 필수 필드를 못 박으면 누락을 구조적으로 막습니다.
6. **작업 구조가 고정이면 체인, 가변이면 적응형.** 고정 작업에 동적 오케스트레이터를 쓰면 낭비이고, 가변 작업에 고정 체인을 쓰면 막힙니다.
7. **독립 작업은 병렬로.** 총 시간이 "합"에서 "최장 하나"로 줄어듭니다.
8. **세션은 대화이지 파일이 아니다.** 파일 되돌리기에는 별도 체크포인팅이, 파일 변경 반영에는 명시적 재조회가 필요합니다.
9. **모든 `stop_reason`을 다루라.** 특히 `max_tokens`를 `end_turn`으로 흘려보내면 미완성 결과가 조용히 완성품으로 둔갑합니다.
10. **모델 교체는 소프트웨어 버그의 해법이 아니다.**

## 8. 용어 사전 (Glossary)

### 에이전트 루프 / API

| 용어 | 설명 |
|---|---|
| **Agent Loop** | 모델 호출 → 도구 실행 → 결과 반환 → 재호출을 반복하는 제어 사이클. 에이전트의 핵심 구조. |
| **Messages API** | Claude에 대화(messages 배열)를 보내 응답을 받는 API. 상태를 저장하지 않아 매번 전체 이력을 전송. |
| **tool_use** | 모델(assistant)이 내는 블록. "이 도구를 이 인자로 실행해 달라"는 요청. 고유 `id`를 가짐. |
| **tool_result** | 애플리케이션이 user 역할로 되돌려 주는 블록. `tool_use_id`로 원 요청과 짝을 이룸. |
| **tool_use_id** | `tool_use`와 `tool_result`를 1:1로 연결하는 식별자. 임의 병합·누락 시 API 검증 오류 또는 맥락 파손. |
| **Parallel Tool Use** | 모델이 한 턴에 여러 `tool_use` 블록을 내는 것. 전부 실행 후 각각의 `tool_result`를 한 user 턴에 담아 보냄. |
| **Turn (턴)** | 대화의 한 주고받기 단위. 하나의 assistant 응답 또는 하나의 user 메시지. |
| **stop_reason** | 모델이 멈춘 이유. `end_turn`, `tool_use`, `max_tokens`, `stop_sequence`. 루프 분기의 기준. |
| **end_turn** | 모델이 정상적으로 할 말을 마침. 루프 종료 신호. |
| **max_tokens (stop_reason)** | 출력 토큰 상한에 걸려 응답이 **잘림**. 완료가 아니라 미완성. 별도 처리 필수. |
| **max_tokens (parameter)** | 요청 시 지정하는 최대 출력 토큰 수 파라미터. |
| **Truncation (절단)** | 토큰 한도로 출력이 중간에 끊기는 현상. |
| **Model-Driven Control Flow** | 다음 행동을 모델이 갱신된 맥락을 보고 스스로 정하는 방식. 유연하지만 비결정론적. |
| **Deterministic Workflow** | 다음 행동이 코드에 고정되어 있는 방식. 예측 가능하지만 중간 결과에 적응 못 함. |
| **Fixed Tree** | 이전 결과와 무관하게 정해진 경로만 따르는 고정 구조. |
| **Nondeterminism (비결정성)** | LLM이 같은 입력에도 다른 도구 순서·선택을 할 수 있는 성질. 순서 보장을 프롬프트나 관습에 의존하면 안 되는 이유. |
| **Rules Engine (룰 엔진)** | 규칙 기반으로 다음 행동을 정하는 외부 시스템. 이것이 제어하면 모델 중심 루프가 아님. |

### 워크플로 패턴

| 용어 | 설명 |
|---|---|
| **Task Decomposition** | 큰 작업을 하위 작업으로 쪼개는 설계 행위. |
| **Prompt Chaining** | 고정된 선형 단계들을 순서대로 잇는 패턴. 각 출력이 다음 입력. 단계 수가 불변일 때 최적. |
| **Checkpoint / Gate** | 단계 사이에 두는 프로그래밍 방식 검증. 잘못된 중간 산출물이 다음 단계로 넘어가는 것을 차단. |
| **Programmatic Check** | LLM 판단이 아닌 코드로 수행하는 검증. 결정론적이라 신뢰성이 높음. |
| **Orchestrator-Workers** | 코디네이터가 런타임에 하위 작업 수와 종류를 정해 워커에 배분하고 결과를 종합하는 패턴. |
| **Adaptive Decomposition** | 실행 중 발견에 따라 계획에 새 하위 작업을 추가하는 패턴. 가변 구조 작업에 필요. |
| **Adaptive Investigation Plan** | 조사 중 발견된 이슈마다 새 하위 작업을 생성하는 적응형 계획. |
| **Variable Structure** | 실행 전에는 필요한 단계를 알 수 없고 발견에 따라 달라지는 작업 구조. |
| **Backfill (백필)** | 새로 추가된 컬럼 등에 기존 행의 값을 채워 넣는 작업. 스키마에 따라 필요 여부가 달라지는 대표적 가변 단계. |
| **Intermediate Artifact** | 단계 사이에 생기는 중간 산출물(예: 구조화된 요약). 검증 지점이자 다음 단계 입력. |
| **Intermediate Findings** | 실행 도중 얻은 중간 결과. 모델 중심 루프는 여기에 적응하고, 고정 워크플로는 무시함. |
| **Strangler-Fig / Extract-Service** | 모놀리스 리팩토링 전략들. (기존 시스템을 점진적으로 감싸 대체 / 기능을 별도 서비스로 분리) |

### 서브에이전트

| 용어 | 설명 |
|---|---|
| **Subagent** | 자기만의 컨텍스트·시스템 프롬프트·도구를 가진 별도 에이전트 인스턴스. 하위 작업 위임 대상. |
| **Coordinator / Orchestrator** | 서브에이전트를 호출하고 결과를 종합하는 상위 에이전트. |
| **AgentDefinition** | 서브에이전트의 정의(설명, 프롬프트, 도구, 모델 등). |
| **AgentDefinition.prompt** | 서브에이전트의 **지속적 시스템 프롬프트/전문성**. 매 호출마다 항상 적용되는 고정 지침. |
| **Per-call prompt** | 호출 시점에 전달하는 **구체적 작업 지시**. 정의 프롬프트를 대체하지 않고 함께 결합됨. |
| **Context Isolation** | 서브에이전트가 별도 컨텍스트를 써서 상위 대화가 오염되지 않게 하는 것. |
| **Concurrent Invocation** | 독립적인 서브에이전트를 동시에 호출. 총 시간이 합에서 최장 하나로 감소. |
| **Nested Subagents** | 서브에이전트가 또 서브에이전트를 낳는 재귀 구조. **메인 포함 최대 5단계**로 제한. |
| **maxTurns** | 에이전트가 수행할 수 있는 최대 턴 수를 제한하는 **가드레일**. 속도를 높이는 설정이 아님. |
| **Guardrail** | 폭주·무한 재귀·자원 고갈을 막는 시스템적 안전 한계. |
| **Model Tier** | 서브에이전트에 지정하는 모델 성능 등급. 중첩 깊이 제한과 무관. |

### 훅 / 권한

| 용어 | 설명 |
|---|---|
| **Hook** | 특정 이벤트에 자동 실행되는 사용자 코드. 프롬프트와 달리 **항상** 실행되어 결정론적 강제가 가능. |
| **PreToolUse** | 도구 실행 **직전**에 도는 훅. 유일하게 실행을 **차단**할 수 있음. |
| **PostToolUse** | 도구 실행 **직후**에 도는 훅. 이미 부작용이 발생한 뒤라 예방 수단이 아님. |
| **Notification Hook** | 상태 메시지·로깅 전용 훅. `permissionDecision`을 낼 수 없어 호출을 막지 못함. 매처 지정은 가능. |
| **Matcher** | 훅이 어떤 도구에 반응할지 지정하는 조건. 매칭된 도구가 실제 호출될 때만 훅이 돎. |
| **permissionDecision** | PreToolUse 훅이 반환하는 실행 결정 값. `allow` / `ask` / `deny`. |
| **allow** | 사람 확인 없이 자동 허용. 저위험·읽기 전용 작업에 적합. |
| **ask** | 사용자에게 대화형 승인 프롬프트. 되돌릴 수 없는 고위험 작업에 적합. |
| **deny** | 도구 호출을 취소. 실행되지 않으며, 사유가 모델에 전달됨. |
| **permissionDecisionReason** | 결정의 사유 문자열. `deny`/`ask` 모두에서 유효하며, **Claude에게 피드백으로 전달**되어 대안 행동을 유도. |
| **hookSpecificOutput** | 훅 반환 JSON에서 이벤트별 결과를 담는 필드. `hookEventName`, `permissionDecision` 등을 포함. |
| **updatedInput** | PreToolUse 훅이 도구의 **인자를 수정**할 때 쓰는 필드. 무관한 데이터를 넣으면 스키마 오염. |
| **async: true / asyncTimeout** | 훅을 넌블로킹으로 처리하게 하는 반환 옵션. 런타임이 완료를 기다리지 않고 진행. 외부 감사 전송 등에 사용. |
| **Non-blocking** | 결과를 기다리지 않고 다음 단계를 진행하는 방식. 응답 지연을 막음. |
| **Risk-based Permission** | 도구의 위험도와 가역성에 따라 권한 결정을 차등 적용하는 정책. |
| **Reversibility (가역성)** | 작업을 되돌릴 수 있는지 여부. 되돌릴 수 없을수록 사전 차단·사람 확인이 중요. |
| **Side-effect (부작용)** | 도구 실행이 외부 세계에 남기는 되돌리기 어려운 변화(환불 집행, 파일 삭제 등). |
| **Decoupling State Failure** | 검증을 오염 가능한 간접 공유 상태(플래그)에서 떼어내, 호출 인자의 명시적 원천 데이터로 옮기는 것. |
| **Input Validation / Inspection** | 도구 호출 인자를 직접 검사해 정당성을 확인하는 것. 간접 플래그 신뢰보다 안전. |
| **Deterministic Compliance** | 정책이 확률이 아니라 코드로 항상 강제되는 상태. 훅이 담당. |
| **Audit (감사)** | 도구 호출 인자 등을 외부 시스템에 기록해 추적 가능성을 확보하는 것. 허용 판단과 무관하면 비동기로 처리. |

### 세션

| 용어 | 설명 |
|---|---|
| **Session** | 대화 단위. 세션 ID로 식별되며 재개 가능. **대화 이력만** 영속화. |
| **Session Persistence** | 세션이 메시지 턴과 맥락을 저장·복원하는 것. **파일 시스템 스냅샷은 포함하지 않음.** |
| **Resume** | 기존 세션을 이어서 재개. 축적된 추론이 온전히 보존됨. |
| **fork_session** | 재개 시 맥락을 복사해 **독립 브랜치 세션**을 만드는 옵션. 원본과 브랜치 간 오염 방지. |
| **Branching** | 같은 베이스라인에서 여러 갈래 실험을 분리해 진행하는 것. |
| **Baseline** | 분기의 출발점이 되는 공유 맥락 상태. |
| **Cross-contamination** | 한 대화 안에서 여러 주제를 섞어 맥락이 서로 오염되는 현상. |
| **/clear** | 대화 맥락을 초기화. 베이스라인이 사라짐. |
| **/compact** | 대화 이력을 요약·압축해 토큰을 절약. 세부 맥락은 손실되며 외부 파일을 다시 읽지 않음. |
| **Cache Invalidation** | 세션 맥락에 박힌 낡은 파일 내용을 최신화하는 것. 파일 변경 사실을 알려 **재조회(re-read)** 시켜야 함. |
| **Context Loss** | 요약이나 초기화로 상세한 추론 맥락이 사라지는 것. |
| **Accumulated Reasoning** | 세션 동안 쌓인 시스템 이해·판단 근거. resume으로만 온전히 보존됨. |
| **Checkpointing** | 파일/코드 상태의 스냅샷을 따로 저장해 되돌릴 수 있게 하는 별도 메커니즘(Git 등). 세션 기능이 아님. |
| **CLAUDE.md** | 프로젝트 지침을 담아 에이전트가 읽는 설정 파일. 외부에서 수정되면 세션 캐시가 낡을 수 있음. |

### 사람 개입

| 용어 | 설명 |
|---|---|
| **Human-in-the-Loop (HITL)** | 고위험·비가역 작업 전에 사람이 개입하도록 설계하는 것. |
| **Escalation** | 에이전트가 처리 도중 사람 관리자에게 넘기는 것. |
| **Handoff Protocol** | 이관 시 전달할 정보의 형식과 절차를 정한 규약. |
| **Structured Fields** | 고객 정보·원인 분석·권장 조치처럼 **필수로 못 박은 항목들**. 자유 형식의 누락 문제를 구조적으로 해결. |
| **Free-text** | 자유 형식 텍스트. 일관성과 완결성이 보장되지 않음. |
| **Root Cause Analysis** | 문제의 근본 원인 분석. 핸드오프 필수 항목의 하나. |
| **Masking (마스킹)** | 민감 정보를 가려 표시하는 것. 마스킹된 읽기 전용 조회는 위험도가 낮음. |
