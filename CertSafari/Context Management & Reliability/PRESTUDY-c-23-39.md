# 사전 학습 노트: 컨텍스트 관리와 신뢰성 (Context Management & Reliability)

이 문서는 이 주제를 처음 접하는 학습자를 위한 것입니다. LLM 에이전트 시스템이 무엇인지부터 시작해서, 컨텍스트를 어떻게 관리하고, 오류를 어떻게 다루고, 사람의 검토를 언제 끼워 넣고, AI의 출력을 어떻게 검증하는지까지 필요한 개념을 처음부터 설명합니다.

---

## 1. 기초: LLM 에이전트와 컨텍스트 윈도우

### 1.1 LLM과 컨텍스트 윈도우(Context Window)

**LLM(Large Language Model, 대규모 언어 모델)** 은 텍스트를 입력받아 텍스트를 생성하는 모델입니다. Claude, GPT 같은 것들이 여기에 해당합니다.

LLM은 기억 장치가 따로 없습니다. 매번 응답을 만들 때 **입력으로 들어온 텍스트 전체**만 보고 판단합니다. 이 "한 번에 볼 수 있는 텍스트의 최대 분량"을 **컨텍스트 윈도우(context window)** 라고 부릅니다.

- 단위는 **토큰(token)** 입니다. 토큰은 대략 단어 조각 하나 정도의 크기입니다. 영어 기준으로 1토큰 ≈ 0.75단어, 한국어는 글자당 1~2토큰 정도로 더 많이 소비됩니다.
- 예: 컨텍스트 윈도우가 20만 토큰인 모델은, 시스템 프롬프트 + 대화 기록 + 파일 내용 + 도구 출력 전부 합쳐서 20만 토큰을 넘을 수 없습니다.

**왜 이게 중요한가?** 대화가 길어지면 오래된 내용이 창 밖으로 밀려나거나 잘려나갑니다(**truncation, 절단**). 그러면 모델은 그 내용을 "잊어버립니다". 잊었다는 사실조차 인지하지 못하고, 그럴듯한 답을 지어내기도 합니다.

### 1.2 컨텍스트 저하 (Context Degradation)

긴 세션에서 초반에 확인했던 구체적 사실이 후반부에 사라지거나 흐려지는 현상을 **컨텍스트 저하(context degradation)** 라고 합니다.

전형적인 사례:
- 세션 초반에 "이 서비스는 예외(exception) 대신 커스텀 `Result` 타입으로 에러를 처리한다"는 것을 확인함.
- 3시간 후 같은 질문을 하자, 에이전트가 "일반적으로 try/catch와 로깅을 씁니다"라고 답함.

여기서 두 번째 답은 **환각(hallucination)** 입니다. 실제 코드를 확인한 게 아니라, 학습 과정에서 익힌 "보통 이렇게들 한다"는 일반적 패턴을 그럴듯하게 재생산한 것입니다. 원인은 모델 고장도, 네트워크 문제도, 권한 부족도 아닙니다. **단순히 그 사실이 활성 컨텍스트에서 밀려난 것**입니다.

### 1.3 컨텍스트 오염 (Context Pollution)

컨텍스트 윈도우에 **다시 쓸 일이 없는 대량의 원시 데이터(raw output)** 가 들어차는 것을 컨텍스트 오염이라고 합니다.

예: 5만 개 파일이 있는 저장소에서 테스트 파일을 검색하면 수천 줄의 경로 목록이 나옵니다. 이걸 메인 대화에 그대로 넣으면:
- 토큰을 대량 소비해 남은 여유 공간이 줄어듭니다.
- 정작 중요한 고수준 계획 내용이 그 잡음에 묻힙니다.
- 이후 모든 턴에서 그 잡음이 계속 재전송되어 비용과 지연 시간이 증가합니다.

### 1.4 컨텍스트 윈도우를 키우면 다 해결되나?

아닙니다. 더 큰 컨텍스트 윈도우는 도움이 되지만 근본 해결책이 아닙니다.

- **비용**: 입력 토큰만큼 요금이 붙습니다. 매 턴 20만 토큰을 보내면 비용이 선형으로 증가합니다.
- **지연 시간(latency)**: 입력이 길수록 응답이 느려집니다.
- **Needle-in-a-Haystack 문제 (건초더미 속 바늘)**: 컨텍스트가 매우 길면 모델이 그 안의 특정 사실을 정확히 찾아내는 능력이 떨어집니다. 창 안에 있어도 "못 보는" 일이 생깁니다.

따라서 큰 창에 다 넣는 것보다, **넣을 것을 고르는 설계**가 중요합니다.

## 2. 멀티 에이전트 아키텍처

### 2.1 메인 에이전트, 코디네이터, 서브에이전트

**에이전트(agent)** 는 LLM + 도구(파일 읽기, 검색, 웹 요청 등) + 목표로 구성된 실행 단위입니다.

- **메인 에이전트 / 코디네이터(coordinator, orchestrator)**: 사용자와 대화하며 전체 작업을 계획하고 하위 작업을 나눠 맡기고, 결과를 종합하는 역할.
- **서브에이전트(subagent)**: 코디네이터가 특정 작업을 위해 생성(spawn)하는 하위 에이전트. **자기만의 독립된 컨텍스트 윈도우**를 가집니다.

핵심은 이 **컨텍스트 격리(context isolation)** 입니다.

```
[메인 에이전트 컨텍스트]           [서브에이전트 컨텍스트]
 - 사용자 요청                       - grep 원시 출력 4,000줄
 - 계획                       →      - 필터링 과정
 - "테스트 파일 1,203개, 주로  ←      - 정리
    tests/ 와 src/**/__tests__/"
```

서브에이전트 안에서 수천 줄의 원시 출력을 처리하고, **정리된 요약만** 메인으로 돌려보냅니다. 원시 출력은 서브에이전트가 끝나면 함께 사라집니다. 메인 컨텍스트는 깨끗하게 유지됩니다.

**언제 쓰는가**: 출력이 크고, 그 출력의 원시 형태를 나중에 다시 볼 일이 없으며, 결론만 필요할 때. (대량 검색, 저장소 전수 탐색, 여러 문서 스캔 등)

**하지 말아야 할 대안들**:
- 메인에서 파일 5만 개를 하나씩 읽어보기 → 비용·시간 폭발, 컨텍스트 초과.
- 사용자에게 목록을 직접 붙여넣어 달라고 요청 → 자동화의 목적 자체를 훼손.
- 원시 출력을 "혹시 나중에 필요할까 봐" 대화에 그냥 남기기 → 오염 문제를 그대로 방치.

### 2.2 병렬 실행과 부분 실패

코디네이터가 서브에이전트 여러 개를 **병렬(parallel)** 로 돌리는 경우가 많습니다. 예: 경쟁사 3곳의 가격 페이지를 각각 다른 서브에이전트가 수집.

이때 **일부만 실패하는 상황(partial failure, 부분 실패)** 이 반드시 생깁니다. 2개는 성공, 1개는 실패.

### 2.3 실행 재개(Resume)와 결과 캐싱

대규모 멀티 에이전트 실행을 중간에 일시 정지(pause)했다가 **같은 세션 안에서** 재개(resume)하면, 오케스트레이션 엔진은 **이미 완료되어 결과를 반환한 에이전트의 결과를 캐시에서 재사용**하고, 아직 끝나지 않은 에이전트만 실제로 다시 실행합니다.

- 이유: 이미 성공한 작업을 다시 돌리는 것은 API 토큰과 시간의 순수 낭비이기 때문입니다.
- 이를 **상태 지속성(state persistence)** 과 **결과 캐싱(result caching)** 이라고 합니다.
- 즉, 일시 정지가 곧 결과 폐기를 의미하지 않으며, 재개를 위해 애플리케이션을 재설치하거나 새로 시작할 필요도 없습니다.

## 3. 스크래치패드와 지속성 메모리

### 3.1 스크래치패드(Scratchpad)란

**스크래치패드**는 에이전트가 탐색 도중 알아낸 사실을 **컨텍스트 밖의 파일에 기록해 두는 것**입니다. 일종의 외부 메모장 겸 장기 기억입니다.

왜 필요한가: 컨텍스트 윈도우는 휘발성입니다. 밀려나면 끝입니다. 하지만 파일은 남습니다. 나중에 필요할 때 그 파일만 다시 읽으면 됩니다. 이것이 컨텍스트 저하(1.2절)에 대한 정면 대응책입니다.

### 3.2 스크래치패드에 무엇을 적어야 하나

**구체적인 사실(concrete facts)을, 발견하는 즉시** 적습니다.

좋은 기록:
```markdown
## billing-service 에러 처리
- 발견 위치: src/billing/result.ts
- 예외(exception)를 던지지 않음. 커스텀 `Result<T, E>` 타입을 반환.
- 호출부는 `if (res.isErr())` 패턴으로 분기 (src/billing/invoice.ts:142)
- 로깅은 별도 미들웨어 src/middleware/logger.ts 에서 처리
```

여기에 담긴 것: 정확한 **클래스/타입 이름**, **파일 경로**, **발견된 메커니즘**. 나중에 "이 서비스 에러 처리 어떻게 해?"라고 물었을 때, 이 기록만 다시 읽으면 정확한 근거(grounded)에 기반한 답을 할 수 있습니다.

나쁜 기록의 유형:
- **타임스탬프만 남기기**: "10:32 - 탐색 단계 1 수행". 언제 했는지는 알겠지만 **무엇을 알아냈는지**가 없으므로 나중에 아무 도움이 되지 않습니다.
- **모호한 한 줄**: "코드베이스를 살펴봤고 대체로 괜찮아 보임". 검증 가능한 정보가 0입니다.
- **연 파일의 전체 원시 내용을 통째로 복사**: 이건 스크래치패드가 아니라 두 번째 컨텍스트 오염입니다. 다시 읽을 때 원본 파일을 읽는 것과 다를 게 없습니다. 스크래치패드의 목적은 **압축된 핵심**을 남기는 것입니다.

### 3.3 근거 유지 (Groundedness)

**그라운디드(grounded)** 하다는 것은 답변이 실제로 확인된 근거에 기반하고 있다는 뜻입니다. 그 반대가 환각입니다. 스크래치패드는 그라운디드니스를 시간이 지나도 유지시켜 주는 장치입니다.

## 4. 대화 요약(Summarization)과 정보 유실

### 4.1 반복 요약의 문제

프롬프트를 짧게 유지하려고 대화를 몇 턴마다 요약하는 기법을 씁니다(**iterative summarization, 반복 요약**). 요약본 위에 또 요약을 얹는 방식입니다.

문제는 요약이 본질적으로 **압축(lossy compression)** 이라는 점입니다. 요약 알고리즘은 문장의 "요지"를 남기고 세부를 버립니다. 그리고 **정확한 숫자와 식별자가 가장 먼저 버려집니다**.

실제 예:
```
원본:
  "주문번호 A-4471-20 건인데요, 214.88달러 환불 요청드립니다.
   15일까지는 처리돼야 합니다."

3차 요약 후:
  "고객이 곧 환불을 원하며 지난달 주문에 대해 언급했다"
```

주문번호, 정확한 금액, 마감일이 전부 사라졌습니다. 그리고 이 유실은 **요약을 반복할수록 가속**됩니다.

### 4.2 해결책: 지속성 사실 블록 (Persistent Case-Facts Block)

핵심 원칙: **절대 잃어버리면 안 되는 정밀 정보는 요약 대상 텍스트에 두지 말고, 별도의 고정 블록에 보관하고 매 프롬프트마다 그대로 주입한다.**

```
[시스템 프롬프트]
...

[CASE FACTS - 요약 금지, 매 턴 그대로 유지]
order_id: A-4471-20
refund_amount_usd: 214.88
customer_stated_deadline: 2026-03-15
account_status: verified

[대화 요약]
고객이 환불을 요청 중이며 배송 지연에 불만을 표시함...

[최근 대화 원문]
...
```

이 블록은 요약 파이프라인을 거치지 않으므로 손실되지 않습니다. 구조화된 키-값 형태라 토큰도 적게 씁니다.

**대안들이 왜 부족한가**:
- **요약을 더 자주 하기**: 압축 특성 자체가 바뀌지 않으므로 오히려 유실을 가속시킵니다.
- **고객에게 매 턴 다시 말해달라고 하기**: 시스템의 설계 실패를 사용자에게 떠넘기는 최악의 UX입니다.
- **컨텍스트 윈도우가 가장 큰 모델로 바꾸기**: 1.4절에서 본 비용·지연·건초더미 문제가 남습니다.

## 5. 오류 처리와 상태 보고

### 5.1 조용한 실패 (Silent Failure)

**조용한 실패**란, 실제로는 실패했는데 성공한 것처럼 보고하는 것입니다. 에이전트 시스템에서 가장 위험한 실패 유형입니다.

사례:
```json
// 실제 상황: API 키가 만료되어 데이터 제공자에 접근조차 못 함
// 서브에이전트가 반환한 것:
{ "status": "success", "findings": [] }
```

파이프라인은 "깔끔하게" 계속 진행됩니다. 코디네이터는 `findings: []` 를 보고 **"조사했는데 문제가 없더라"** 로 해석합니다. 그리고 "규제 항목 전체 커버리지 확인, 이상 없음"이라는 보고서를 씁니다.

**결과: 허위 보고.** 실제로는 아무것도 확인하지 못한 공백(gap)인데, "확인 결과 이상 없음"으로 둔갑했습니다. 규제 대상 업무에서는 치명적입니다.

핵심 원칙: **장애와 데이터 누락은 반드시 명시적인 오류 상태로 상위에 노출되어야 한다.** 상위 에이전트가 올바른 판단을 하려면 정확한 신호를 받아야 합니다.

### 5.2 "결과 없음"과 "접근 실패"는 다르다

이것은 위 문제의 일반화된 형태입니다. 두 상황을 반드시 구분해야 합니다.

| 상황 | 의미 | 올바른 상태값 |
|---|---|---|
| 판례 DB가 정상 응답했고, 조건에 맞는 판례가 진짜로 0건 | **검증된 사실**: 그런 판례는 없다 | `success`, `results: []` |
| 판례 DB의 커넥션 풀이 고갈되어 연결 거부 | **미지(unknown)**: 있는지 없는지 모른다 | `error`, `error_type: "access_failure"` |

둘 다 "no results found"로 보고하면, 상위 에이전트는 두 번째 경우도 "그런 판례는 존재하지 않는다"는 사실로 받아들입니다. 법률 리서치에서 이는 심각한 오판으로 이어집니다.

권장 스키마 예:
```json
{
  "status": "error",
  "error_type": "access_failure",
  "detail": "connection pool exhausted, 2 retries failed",
  "results": null
}
```
`results: []`(빈 배열, 사실)과 `results: null`(모름)을 구분하는 것도 좋은 습관입니다.

### 5.3 부분 실패의 올바른 처리와 투명성

일부 서브에이전트가 실패했을 때 코디네이터가 해야 할 일:

**성공한 결과는 보고하되, 실패한 부분을 명시적으로 표시(annotate)한다.**

```markdown
## 경쟁사 가격 비교
| 경쟁사 | 스타터 | 프로 |
|---|---|---|
| Acme  | $19 | $49 |
| Bolt  | $25 | $60 |
| Cirrus | 수집 불가 | 수집 불가 |

주: Cirrus 사이트는 봇 방지 보호로 403 응답 (재시도 2회 후 실패). 가격 정보 미확보.
```

**해서는 안 되는 것들**:
- **추정치로 빈칸 채우기**: "시장 동향상 대략 $22 정도로 추정" → 이것은 환각을 데이터인 척 제공하는 행위입니다. 읽는 사람은 실측치와 구분할 수 없습니다.
- **누락 사실을 표기 없이 숨기기**: 3자 비교인 척하면서 한 곳의 데이터가 없다는 걸 말하지 않는 것은 신뢰성 훼손입니다.
- **전체 보고서를 무기한 보류하기**: 한 곳이 막혔다고 성공한 2곳 정보까지 붙잡아 두면 워크플로 전체가 마비됩니다.
- **전체 워크플로를 강제 종료하기**: 서브에이전트 하나의 인프라 장애로 시스템 전체를 죽이는 것은 과잉 대응입니다. 오류를 상위에 알리고 부분 재시도나 대체 경로를 시도하는 것이 정석입니다.

**재시도(retry)**: 일시적 장애에 대비해 서브에이전트가 로컬에서 몇 회 재시도하는 것은 정상적인 설계입니다. 재시도를 다 소진하고도 실패하면 그때 상위로 오류를 올립니다.

### 5.4 검증과 신뢰의 균형

"서브에이전트 출력을 전부 사람이 수동 검증해야 한다"는 대응은 답이 아닙니다. 그러면 자동화를 만든 이유가 사라집니다. 근본 원인은 **잘못된 상태값을 반환한 서브에이전트 쪽**에 있고, 고쳐야 할 곳도 거기입니다.

## 6. 멀티 에이전트 결과 종합 (Synthesis)

### 6.1 데이터 출처 보존 (Data Provenance)

여러 서브에이전트가 서로 다른 값을 보고할 때, 종합 에이전트(synthesis agent)는 어떻게 해야 할까요?

사례: 서브에이전트 5개가 같은 회사의 서로 다른 규제 제출 서류를 검토. 4개는 "부채비율 안정적"이라고 보고, 1개는 **다른 회계 분기의 서류를 사용해서** 훨씬 높은 비율을 보고.

여기서 그 1개는 **이상치(outlier)가 아닙니다.** 시점(fiscal quarter)이 다른, 별개의 정당한 데이터 포인트입니다.

올바른 처리: **안정적 비율은 여러 출처로 잘 뒷받침되는 값으로 제시하고, 높은 비율은 시점이 명시된 별개의 데이터 포인트로 함께 제시한다.**

```markdown
- 부채비율: 1.2 (FY2025 Q1~Q3 제출서류 4건에서 일관되게 확인)
- 참고: FY2024 Q2 제출서류에서는 2.8로 보고됨 (분기가 다름, 폐기하지 않고 별도 표기)
```

**잘못된 처리들**:
- **5개 값의 평균 내기**: 서로 다른 시점의 데이터를 평균 내면 존재한 적 없는 숫자가 만들어집니다.
- **높은 값을 최신이라고 추정해서 채택**: 근거 없는 추정입니다.
- **다수결로 소수 의견을 잡음으로 폐기**: 실제로는 유효한 다른 시점 정보를 버리는 것입니다.

핵심 개념: **데이터 프로버넌스(data provenance, 출처 이력)** — 각 값이 어디서, 언제 나왔는지를 끝까지 유지하는 것.

### 6.2 서브에이전트 출력 스키마와 인용 근거

후속 에이전트가 **원본 문서를 다시 읽지 않고도** 각 주장을 검증하고 재인용할 수 있으려면, 서브에이전트의 구조화된 출력에 다음 세 가지가 들어가야 합니다.

1. **주장 텍스트(claim text)** — 무엇을 알아냈는가
2. **출처 식별자(source URL 또는 문서명)** — 어디서 나왔는가
3. **주장을 뒷받침하는 관련 발췌문(relevant excerpt)** — 원문에 실제로 뭐라고 쓰여 있는가

```json
{
  "claim": "회사는 2025년 1월에 데이터 유출 사고를 공시했다.",
  "source": "https://sec.gov/.../10-K-2025.htm",
  "excerpt": "In January 2025, the Company identified unauthorized access to ..."
}
```

**부족한 대안들**:
- 출처 문서를 명시하지 않고 주변 문단을 요약만 하면 → 검증도 인용도 불가능.
- 어느 서브에이전트가 만들었는지만 적으면 → 그 서브에이전트는 이미 종료됐고 컨텍스트도 사라졌으므로 재질의할 대상이 없습니다. 출처는 문서이지 에이전트가 아닙니다.
- 서브에이전트가 스스로 매긴 신뢰도 점수만 붙이면 → 그 점수 자체가 검증되지 않은 자기 평가입니다(7장 참조). 검증에 쓸 원문 근거가 없습니다.

이것을 **citation grounding(인용 근거 부착)** 이라고 합니다.

## 7. 정확도 평가와 신뢰도 캘리브레이션

### 7.1 집계 정확도의 착시 (Aggregate Accuracy)

**집계 정확도(aggregate accuracy)** 는 모든 필드·모든 문서의 정답률을 하나의 숫자로 합친 값입니다. "99% 정확", "94% 필드 정확도" 같은 것들입니다.

이 단일 숫자는 심각한 착시를 만듭니다.

예 1: 문서에서 100개 필드를 뽑는데 99개는 쉬운 텍스트 라벨이고 1개가 결정적인 금액 필드라고 합시다. 금액을 매번 틀려도 집계 정확도는 **99%** 로 표시됩니다.

예 2: 선하증권(bill of lading) 추출 파이프라인의 집계 정확도는 94%. 그런데 뜯어보면:
- `weight`(무게) 필드는 **단위 표기가 모호할 때(숫자만 있고 단위 라벨 없음) 정확도 70%**
- 같은 필드라도 단위가 명확한 경우는 95% 이상

집계 94%라는 숫자만 보면 "기준 충족"으로 보이지만, 실제로는 특정 조건에서 30%의 오류가 발생하고 있습니다.

**대응 원칙: 세부 분해(granular breakdown).** 정확도는 **문서 유형별, 필드별, 그리고 조건별**로 쪼개서 봐야 의미가 있습니다.

### 7.2 벤더의 정확도 주장을 검증하는 법

벤더가 "99% 정확도, 사람 검토 불필요"라고 주장할 때, 기술적으로 검증하기 위해 물어야 할 것:

**"문서 유형별·필드별 정확도 분해 내역과, 그 99%를 산출하는 데 사용한 라벨링된 검증 방법론을 제공해 주시겠습니까?"**

여기서 두 가지를 묻고 있습니다.
1. **세부 분해(breakdown)** — 7.1절의 착시를 걷어내기 위해.
2. **검증 방법론(validation methodology)** — 정답(ground truth)을 어떻게 정했는지, 누가 라벨링했는지, 검증 세트가 실제 운영 데이터 분포를 대표하는지.

**약한 질문들과 그 이유**:
- **"수치가 떨어지지 않는다는 서면 보증을 주시겠습니까?"** → 계약적·법적 안전장치일 뿐 기술적 검증이 아닙니다. 보증서가 있어도 규제 위반은 이미 발생합니다.
- **"최신 모델 버전을 쓰나요?"** → 모델의 최신성(recency)은 운영 정확도의 강력한 예측 변수가 아닙니다. 최신 모델도 도메인 검증 없이는 실패합니다.
- **"최소 1만 건 샘플로 측정했나요?"** → 샘플 크기는 필요조건이지 충분조건이 아닙니다. 표본 분포가 편향돼 있거나(어려운 케이스 누락), 라벨 품질이 낮으면 1만 건이든 10만 건이든 무의미합니다.

### 7.3 Ground Truth와 라벨링된 검증 세트

- **Ground Truth(정답 데이터)**: 사람이 확인한 "맞는 값". 모델 출력이 옳은지 판정하는 기준.
- **Labeled Validation Set(라벨링된 검증 세트)**: ground truth가 붙어 있는 데이터 묶음. 모델 성능 측정과 임계값 설정에 사용합니다.

검증 세트가 실제 운영에서 들어오는 문서의 분포를 반영해야 측정값이 의미를 갖습니다.

### 7.4 신뢰도 점수와 캘리브레이션 (Confidence Calibration)

모델에게 "각 추출 필드마다 0~1 사이 신뢰도 점수를 함께 출력하라"고 요구할 수 있습니다.

```json
{ "field": "total_amount", "value": "214.88", "confidence": 0.93 }
```

이 점수를 근거로 "0.9 이상이면 사람 검토를 건너뛴다"는 라우팅 규칙을 만들고 싶어집니다. **하지만 그 전에 반드시 해야 할 일이 있습니다.**

LLM이 스스로 매기는 신뢰도는 **자기 보고(self-reported)** 값이고, 흔히 **과잉 확신(overconfidence)** 을 보입니다. 모델이 0.95라고 한 것들이 실제로는 70%만 맞을 수도 있습니다.

**캘리브레이션(calibration, 보정)** 이란: 라벨링된 검증 세트를 놓고, **모델이 점수 X를 준 항목들이 실제로 X의 비율로 맞는지 확인하는 것**입니다.

```
모델이 0.9~1.0 준 항목 500개 → 실제 정답률 측정 → 88%  (거의 맞음, 신뢰 가능)
모델이 0.9~1.0 준 항목 500개 → 실제 정답률 측정 → 62%  (심각한 과잉 확신, 그대로 쓰면 안 됨)
```

이 확인을 거친 뒤에야 "검토 건너뛰기" 임계값을 정할 수 있습니다. 잘 보정된(well-calibrated) 모델이란 0.9라고 말한 것이 실제로 약 90% 맞는 모델입니다.

**하지 말아야 할 것들**:
- **"성공적으로 추출한 필드엔 무조건 0.9 이상을 출력하라"고 지시하기** → 점수가 상수가 되어 정보량이 0이 됩니다. 신뢰도가 아니라 장식입니다.
- **인접 필드 점수와 평균 내서 평활화(smoothing)하기** → 필드마다 난이도가 다른데 섞어버리면, 어려운 필드의 낮은 점수가 쉬운 필드에 가려져 위험 신호가 사라집니다.
- **숫자 대신 high/medium/low 범주 라벨로 바꾸기** → 라벨을 붙인다고 추정 자체가 정확해지지 않습니다. 보정 안 된 범주는 보정 안 된 숫자와 똑같이 못 믿을 값이고, 오히려 해상도만 잃습니다.

### 7.5 Temperature (온도)

**Temperature**는 모델 출력의 무작위성을 조절하는 파라미터입니다.

- 낮음(0에 가까움): 결정적(deterministic)이고 일관된 출력. 사실 추출, 구조화된 데이터 추출에 적합.
- 높음(1 이상): 다양하고 창의적인 출력. 브레인스토밍, 문장 생성에 적합.

**중요**: 정보 추출 정확도가 낮다고 해서 temperature를 올리는 것은 정반대 처방입니다. 무작위성이 커져 정확도가 더 떨어지고, 검토자에게 잘못된 후보값만 잔뜩 던져주게 됩니다. 추출 작업에서는 temperature를 **낮게** 유지합니다.

## 8. Human-in-the-Loop (사람 개입 설계)

### 8.1 개념

**Human-in-the-Loop(HITL)** 는 자동화 파이프라인 중간에 사람의 판단을 끼워 넣는 설계입니다. 목표는 "전부 자동" 또는 "전부 수동"의 양극단이 아니라, **위험한 곳에만 사람을 배치해 효율과 정확성을 동시에 얻는 것**입니다.

### 8.2 선택적 라우팅 (Targeted / Selective Routing)

7.1절의 선하증권 사례로 돌아가 봅시다. `weight` 필드가 단위 모호 시 70%, 명확할 때 95% 이상이라면 올바른 검토 정책은:

**"원본 문서가 단위를 명확히 명시하지 않은 경우에만 무게 필드를 사람 검토로 보내고, 단위가 명확한 고신뢰 케이스는 검토 없이 자동 통과시킨다."**

이것이 선택적 라우팅입니다. 위험 조건만 정확히 겨냥합니다.

**나쁜 대안들**:
- **정책 그대로 두기**: 집계 94%라는 착시를 믿고 모호 케이스의 30% 오류율을 방치.
- **temperature 올리기**: 7.5절 참조. 상황을 악화시킵니다.
- **무게 필드 전체를 수동 입력으로 전환**: 95% 이상 나오는 대다수 정상 문서까지 사람에게 넘기는 것은 과도한 인력 낭비이며 자동화 도입 목적을 훼손합니다.

### 8.3 검토 용량이 제한적일 때: 리스크 기반 라우팅

현실적 제약: 검토 팀이 하루 생산량의 **8%** 만 확인할 수 있습니다. 어디에 그 8%를 써야 할까요?

**정답 원칙: 리스크가 높은 것부터 채우고, 남는 용량으로 소규모 무작위 표본을 검사한다.**

우선순위 1 — **저신뢰도 추출**과 **모호하거나 모순된 원본 값을 가진 문서** (예: 같은 필드가 페이지마다 다른 값으로 나오는 문서). 오류가 실제로 몰려 있는 곳입니다.

우선순위 2 — 남은 용량으로 **고신뢰도 항목의 소규모 무작위 표본**. 이것을 **QA 샘플링(quality assurance sampling)** 이라고 합니다. 이유: 고신뢰도 구간이 계속 잘 작동하는지 감시하기 위해서입니다. 이 감시가 없으면 모델이 조용히 열화되거나 데이터 분포가 바뀌었을 때(**drift, 드리프트**) 알아챌 방법이 없습니다.

**나쁜 대안들**:
- **매일 균일 무작위 8%**: 통계적으로 대표성은 있지만, 검토 용량의 대부분이 이미 잘 처리된 항목에 낭비됩니다. 오류가 몰린 곳을 겨냥하지 못합니다.
- **먼저 처리된 순서대로 8%**: 처리 순서와 오류 확률 사이에는 아무 상관관계가 없습니다.
- **가장 신뢰도 높은 항목만 검토**: 완전히 거꾸로입니다. 오류 발견 확률이 가장 낮은 곳에 자원 전부를 쓰고, 위험한 저신뢰도 항목은 검토 없이 통과시키게 됩니다.

### 8.4 에스컬레이션 (Escalation)

**에스컬레이션**은 AI 에이전트가 대화나 작업의 제어권을 사람 상담원(또는 상급자)에게 넘기는 것입니다.

#### 감정(sentiment)은 복잡도의 지표가 아니다

**감정 분석(sentiment analysis)** 은 텍스트의 정서적 톤을 점수화하는 기법입니다. 모니터링 시스템이 "매우 부정적"으로 대화를 플래그할 수 있습니다.

하지만 **고객의 감정 상태와 요청의 기술적 복잡도는 별개의 축**입니다.

예: 고객이 날카로운 어조로 "온라인 뱅킹 비밀번호 좀 당장 재설정해 주세요"라고 말함. 감정 점수는 매우 부정적. 그러나 비밀번호 재설정은 셀프서비스도 가능한 일상 업무이고 에이전트의 권한과 능력 범위 안에 있습니다.

→ **감정 플래그만으로 에스컬레이션하지 않습니다.** 부정적 감정 점수가 "이 건은 에이전트가 해결하기엔 너무 복잡하다"는 뜻이 아니기 때문입니다. 감정만으로 무조건 이관하면 불필요한 이관 비용이 발생하고 프로세스가 비효율적으로 변합니다.

주의: 이건 "비밀번호 재설정은 감정 기반 규칙에서 항상 면제된다"는 특별 예외 규칙이 있어서가 아닙니다. **작업 자체가 에이전트 역량 범위 내의 일상 업무이기 때문**입니다. 판단 기준은 항목별 면제 목록이 아니라 **실제 작업의 해결 가능성과 난이도**입니다.

#### 고객이 사람을 명시적으로 요구할 때

반대 상황: 항공사 고객이 중간 좌석에 불만을 표함 → 에이전트가 통로 좌석으로 바꿔주겠다고 제안 → 고객이 **"아니요, 실제 사람과 이야기하고 싶다고 말씀드렸잖아요."**

→ **즉시 사람 상담원에게 이관합니다.**

핵심 원칙: **고객이 사람 연결을 명시적으로, 특히 거듭 요구하면 AI는 설득이나 작업 강행을 멈추고 즉시 제어권을 넘긴다.** 작업 자체를 AI가 처리할 수 있는지 여부는 이 시점에서 판단 기준이 아닙니다.

하지 말아야 할 것:
- **"왜 자동 해결이 안 되는지 설명해 달라"고 되묻기** — 이미 짜증 난 고객에게 마찰을 더합니다.
- **거부 의사를 무시하고 좌석 변경을 강행한 뒤 통보하기** — 고객 지시 위반입니다.
- **"간단한 일이니 제가 해드릴게요"라며 같은 제안 반복하기** — 좌절을 증폭시킵니다.

정리하면 에스컬레이션 판단은 두 축입니다.
1. **작업이 에이전트의 능력·권한 범위를 벗어나는가?** (감정이 아니라 실제 난이도)
2. **고객이 사람을 명시적으로 요구했는가?** (그렇다면 능력과 무관하게 이관)

---

## 9. 에스컬레이션 동작을 프롬프트로 설계하기

### 9.1 시스템 프롬프트 (System Prompt)

**시스템 프롬프트**는 대화 시작 전 모델에게 주어지는 지침입니다. 역할, 제약, 판단 기준을 정의합니다.

에이전트가 "이관할 건"과 "직접 해결할 건"을 **일관되고 신뢰성 있게** 구분하도록 하려면 어떻게 해야 할까요?

### 9.2 명시적 기준 + 퓨샷 예시

**정답: 명시적인 에스컬레이션 기준(explicit criteria)을 적고, 이관 사례와 자체 해결 사례를 **둘 다** 보여주는 퓨샷 예시(few-shot examples)를 함께 제공한다.**

**퓨샷 프롬프팅(few-shot prompting)** 이란 지시문에 입출력 예시 몇 개를 함께 넣어 원하는 동작 패턴을 보여주는 기법입니다. 예시 없이 지시만 주는 것을 제로샷(zero-shot)이라고 합니다.

```
## 에스컬레이션 기준
다음 중 하나라도 해당하면 사람 상담원에게 이관하십시오:
1. 고객이 사람과의 대화를 명시적으로 요청한 경우
2. 요청이 계정 폐쇄, 분쟁 조정, 법적 사안을 포함하는 경우
3. 500달러를 초과하는 환불 또는 조정이 필요한 경우
4. 두 번 시도했으나 문제를 해결하지 못한 경우

위에 해당하지 않으면 직접 해결하십시오. 부정적인 어조 자체는
이관 사유가 아닙니다.

## 예시

[이관 사례]
고객: "이건 됐고 그냥 사람 바꿔주세요."
행동: 즉시 이관. → "네, 바로 상담원에게 연결해 드리겠습니다."

[자체 해결 사례]
고객: "이 앱 정말 최악이네요. 비밀번호 좀 초기화해 주세요."
행동: 직접 해결. → "불편을 드려 죄송합니다. 지금 초기화 링크를
등록된 이메일로 보내드렸습니다."

[자체 해결 사례]
고객: "지금 당장! 주문 배송지 바꿔야 해요!!"
행동: 직접 해결. 긴급한 어조는 이관 사유가 아니며 배송지 변경은
에이전트 권한 내입니다.
```

**양쪽 사례를 다 보여주는 것이 핵심입니다.** 이관 예시만 주면 모델은 과잉 이관하고, 해결 예시만 주면 이관해야 할 건도 붙들고 있습니다. 경계선을 학습시키려면 경계의 양쪽을 다 보여줘야 합니다.

**부족한 대안들**:
- **일반 학습 능력에 맡기고 별도 지침 없이 두기**: 조직마다 이관 정책이 다른데 모델은 그 정책을 알 수 없습니다. 일관성이 나오지 않습니다.
- **"부정적 표현이나 긴급함이 있으면 무조건 이관"**: 8.4절에서 본 대로 감정은 복잡도의 지표가 아닙니다. 과잉 이관을 낳습니다.
- **"자기 보고 신뢰도가 임계값 미만이면 이관"**: 7.4절 참조. 보정되지 않은 자기 평가 점수를 그대로 라우팅에 쓰는 것이며, 그 점수 자체를 먼저 캘리브레이션해야 합니다.

## 10. 전체를 관통하는 원칙 정리

1. **컨텍스트는 유한한 자원이다.** 무엇을 넣지 않을지 설계하는 것이 무엇을 넣을지 정하는 것만큼 중요합니다.
2. **잃으면 안 되는 정보는 컨텍스트 밖에 둔다.** 스크래치패드, 지속성 사실 블록.
3. **실패는 반드시 실패로 보고한다.** 조용한 실패는 허위 보고를 낳습니다.
4. **"없다"와 "모른다"를 구분한다.** 빈 결과와 접근 실패는 완전히 다른 정보입니다.
5. **부분 결과는 제공하되 공백은 표시한다.** 추정으로 빈칸을 채우지 않습니다.
6. **모든 주장에 출처를 붙인다.** 검증 가능성이 신뢰성의 기반입니다.
7. **집계 숫자를 믿지 않는다.** 조건별·필드별로 쪼개서 봅니다.
8. **자기 보고 신뢰도는 보정 후에만 쓴다.**
9. **사람의 검토는 위험이 집중된 곳에 배치한다.**
10. **고객이 사람을 요구하면 즉시 넘긴다.** 감정 점수는 이관 근거가 아니지만, 명시적 요청은 근거입니다.

## 용어 사전 (Glossary)

| 영어 용어 | 한국어 설명 |
|---|---|
| **Context Window** | 컨텍스트 윈도우. 모델이 한 번에 처리할 수 있는 최대 토큰 분량. 시스템 프롬프트·대화 기록·도구 출력이 모두 여기에 들어감 |
| **Token** | 토큰. 모델이 텍스트를 처리하는 최소 단위이자 과금 단위. 대략 단어 조각 하나 |
| **Truncation** | 절단. 컨텍스트 한계를 넘어 오래된 내용이 잘려 나가는 것 |
| **Context Degradation** | 컨텍스트 저하. 긴 세션에서 초반에 확인한 사실이 활성 컨텍스트에서 밀려나 사라지는 현상 |
| **Context Pollution** | 컨텍스트 오염. 다시 쓸 일 없는 대량 원시 출력이 컨텍스트를 차지하는 것 |
| **Needle-in-a-Haystack** | 건초더미 속 바늘 문제. 컨텍스트가 매우 길 때 그 안의 특정 사실을 정확히 찾아내는 능력이 저하되는 현상 |
| **Hallucination** | 환각. 모델이 근거 없는 내용을 사실처럼 그럴듯하게 생성하는 것 |
| **Grounded / Groundedness** | 근거 기반. 답변이 실제로 확인된 출처나 데이터에 뿌리를 두고 있는 상태 |
| **Agent** | 에이전트. LLM에 도구 사용 능력과 목표를 부여한 실행 단위 |
| **Main Agent / Coordinator / Orchestrator** | 메인 에이전트 / 코디네이터. 전체 작업을 계획하고 하위 작업을 분배하며 결과를 종합하는 상위 에이전트 |
| **Subagent** | 서브에이전트. 코디네이터가 특정 작업을 위해 생성하는, 자기만의 독립 컨텍스트를 가진 하위 에이전트 |
| **Spawn** | 스폰. 서브에이전트를 생성해 작업을 위임하는 것 |
| **Context Isolation** | 컨텍스트 격리. 서브에이전트의 대량 원시 출력이 메인 컨텍스트에 섞이지 않도록 분리하는 것 |
| **Synthesis Agent** | 종합 에이전트. 여러 서브에이전트의 결과를 모아 최종 산출물을 작성하는 에이전트 |
| **Resume** | 재개. 일시 정지된 워크플로를 다시 이어서 실행하는 것 |
| **Result Caching** | 결과 캐싱. 이미 완료된 에이전트의 결과를 저장해 재개 시 재계산 없이 재사용하는 것 |
| **State Persistence** | 상태 지속성. 실행 상태를 보존해 중단 후에도 이어갈 수 있게 하는 메커니즘 |
| **Scratchpad** | 스크래치패드. 에이전트가 발견한 사실을 컨텍스트 밖 파일에 기록해 두는 외부 메모리 |
| **Persistent Memory** | 지속성 메모리. 세션 컨텍스트와 무관하게 유지되는 저장 공간 |
| **Summarization / Summarization Pass** | 요약 / 요약 단계. 긴 대화를 압축해 프롬프트를 짧게 유지하는 기법 |
| **Iterative Summarization** | 반복 요약. 요약본 위에 다시 요약을 얹는 방식. 반복할수록 세부 정보 유실이 가속됨 |
| **Information Loss / Degradation** | 정보 유실. 압축 과정에서 정확한 숫자·식별자 등 세부 사항이 사라지는 것 |
| **Persistent Case-Facts Block** | 지속성 사건 데이터 블록. 주문번호·금액·기한 등 절대 잃으면 안 되는 정밀 정보를 요약 대상에서 분리해 매 프롬프트에 그대로 주입하는 고정 블록 |
| **Silent Failure / Silent Suppression** | 조용한 실패 / 무언의 은폐. 실제로는 실패했는데 성공으로 보고해 상위 시스템이 오판하게 만드는 것 |
| **Error Propagation** | 오류 전파. 하위에서 발생한 오류를 상위 시스템에 명시적으로 전달하는 것 |
| **Status Reporting** | 상태 보고. 작업 결과를 success/error 등으로 정확히 표기해 반환하는 것 |
| **Error Classification** | 오류 분류. "결과 0건(정상 완료)"과 "접근 실패(연결 불가)"처럼 성격이 다른 결과를 구분해 표시하는 것 |
| **Access Failure** | 접근 실패. 인증 만료, 커넥션 풀 고갈, 차단 등으로 데이터에 도달하지 못한 상태. "결과 없음"과 구분해야 함 |
| **Zero-match** | 제로 매치. 검색이 정상 수행되었으나 조건에 맞는 결과가 실제로 0건인 상태 |
| **Partial Failure** | 부분 실패. 병렬 실행된 작업 중 일부만 실패한 상황 |
| **Retry** | 재시도. 일시적 장애에 대비해 같은 요청을 다시 시도하는 것. 소진 후에도 실패하면 상위에 오류를 보고 |
| **403 Forbidden** | 서버가 요청을 거부한 HTTP 응답 코드. 봇 방지 보호에 의한 차단 등이 원인 |
| **Anti-bot Protection** | 봇 방지 보호. 자동화된 접근을 차단하는 웹사이트 보호 기능 |
| **Annotate** | 주석 표기. 수집하지 못한 항목을 보고서에 명시적으로 표시하는 것 |
| **Transparency** | 투명성. 시스템이 무엇을 확인했고 무엇을 확인하지 못했는지 사용자에게 정확히 알리는 것 |
| **Data Provenance** | 데이터 프로버넌스 / 출처 이력. 각 값이 어떤 문서의, 어느 시점 데이터에서 나왔는지를 끝까지 유지하는 것 |
| **Citation Grounding** | 인용 근거 부착. 각 주장에 출처 식별자와 원문 발췌를 함께 붙여 검증 가능하게 만드는 것 |
| **Outlier** | 이상치. 다수와 어긋나는 값. 다만 시점·출처가 다른 정당한 데이터를 이상치로 오인해 버리면 안 됨 |
| **Structured Output Schema** | 구조화된 출력 스키마. 에이전트가 반환하는 JSON 등의 필드 구조를 미리 정의한 것 |
| **Aggregate Accuracy** | 집계 정확도. 모든 필드·문서를 합쳐 계산한 단일 정확도 수치. 착시를 일으키기 쉬움 |
| **Granular Breakdown** | 세부 분해. 정확도를 문서 유형별·필드별·조건별로 쪼개어 보는 것 |
| **Field Accuracy** | 필드 정확도. 추출 대상 항목(필드) 단위로 측정한 정답률 |
| **Ground Truth** | 정답 데이터. 사람이 확인한 참값. 모델 출력의 정오를 판정하는 기준 |
| **Labeled Validation Set** | 라벨링된 검증 세트. ground truth가 붙은 데이터 묶음. 성능 측정과 임계값 설정에 사용 |
| **Validation Methodology** | 검증 방법론. 정확도 수치를 어떻게 측정했는지에 대한 절차와 기준 |
| **Sample Size** | 표본 크기. 측정에 사용된 데이터 건수. 필요조건이지만 분포 편향과 라벨 품질을 대체하지 못함 |
| **Model Recency** | 모델 최신성. 사용 중인 모델 버전이 얼마나 최신인지. 운영 정확도의 강력한 예측 변수가 아님 |
| **Confidence Score** | 신뢰도 점수. 모델이 자기 출력의 확실성에 대해 스스로 매기는 0~1 사이 값 |
| **Self-reported Confidence** | 자기 보고 신뢰도. 모델 스스로 매긴 점수. 검증 전에는 신뢰할 수 없음 |
| **Overconfidence** | 과잉 확신. 실제 정답률보다 높은 신뢰도를 스스로 부여하는 경향 |
| **Confidence Calibration** | 신뢰도 캘리브레이션 / 보정. 검증 세트로 "점수 X를 준 항목이 실제로 X 비율로 맞는지" 확인해 점수를 신뢰 가능하게 만드는 작업 |
| **Well-calibrated** | 잘 보정된. 0.9라고 말한 항목이 실제로 약 90% 맞는 상태 |
| **Confidence-based Routing** | 신뢰도 기반 라우팅. 신뢰도 점수를 기준으로 검토 여부를 자동 결정하는 것. 보정이 선행되어야 함 |
| **Threshold** | 임계값. 검토를 건너뛸지 여부를 가르는 기준선 |
| **Temperature** | 온도. 출력의 무작위성을 조절하는 파라미터. 낮으면 일관·결정적, 높으면 다양·창의적. 정보 추출에는 낮게 설정 |
| **Human-in-the-Loop (HITL)** | 사람 개입 설계. 자동화 파이프라인에 사람의 판단을 선택적으로 삽입하는 구조 |
| **Targeted / Selective Routing** | 선택적 라우팅. 오류 위험이 높은 조건에 해당하는 건만 골라 사람 검토로 보내고 나머지는 자동 통과시키는 정책 |
| **Bypass Review** | 검토 우회. 고신뢰·비모호 케이스를 사람 검토 없이 자동 통과시키는 것 |
| **Risk-Based Routing** | 리스크 기반 라우팅. 제한된 검토 용량을 오류 가능성이 높은 항목에 우선 배분하는 전략 |
| **QA Sampling** | 품질 보증 샘플링. 남은 검토 용량으로 고신뢰 항목을 소규모 무작위 검사해 시스템 열화를 감시하는 것 |
| **Drift** | 드리프트. 시간이 지나며 데이터 분포나 모델 성능이 서서히 변하는 현상 |
| **Escalation** | 에스컬레이션 / 이관. AI 에이전트가 제어권을 사람 상담원에게 넘기는 것 |
| **Sentiment Analysis** | 감정 분석. 텍스트의 정서적 톤을 점수화하는 기법. 문제의 복잡도 지표로 쓰면 안 됨 |
| **Self-service-eligible** | 셀프서비스 처리 가능. 고객이 스스로 처리할 수 있을 만큼 단순한 요청 |
| **System Prompt** | 시스템 프롬프트. 대화 시작 전 모델에게 주어지는 역할·제약·판단 기준 지침 |
| **Explicit Criteria / Guidance** | 명시적 기준. 모델의 판단 기준을 추측에 맡기지 않고 프롬프트에 구체적으로 적어 주는 것 |
| **Few-shot Examples** | 퓨샷 예시. 지시문에 입출력 예시 몇 개를 함께 넣어 원하는 동작 패턴을 보여주는 기법 |
| **Zero-shot** | 제로샷. 예시 없이 지시문만으로 작업을 수행시키는 방식 |
| **Regulated Workflow** | 규제 워크플로. 법적·규제적 요구사항이 적용되어 정확성과 감사 추적이 필수인 업무 |
| **Coverage** | 커버리지. 조사·검토가 대상 범위를 얼마나 포괄했는지. 접근 실패를 성공으로 처리하면 허위 커버리지가 보고됨 |
