# 1. 프롬프트 설계 기법

이 장에서 다루는 것:

- **개선 시도 순서** — 출력이 나쁠 때 무엇부터 손대야 하는가, 그리고 손대면 안 되는 것들
- **프롬프트 구조화** — 프롬프트를 이루는 요소, XML 태그로 경계 만들기, 섹션 배치와 잘못된 대안들
- **명시적 기준 vs 모호한 지시** — 신뢰도 지시어가 실패하는 이유, 검증 가능한 기준으로 다시 쓰는 법, 정밀도/재현율
- **프롬프트 체이닝과 다중 인스턴스 설계** — 단계 분리, Generator/Reviewer, 파일별 패스 vs 통합 패스
- **흔한 실패** — 경고 피로도, 표면 수정, 과잉 설계

> 예시(few-shot) 설계 자체는 2장에서 따로 다룹니다. 이 장에서는 "언제 예시로 넘어가야 하는가"라는 순서 판단까지만 봅니다.

## 1.1 개선 시도 순서 — 무엇부터 손볼 것인가

출력이 마음에 들지 않을 때 손대는 순서가 있습니다. 순서를 건너뛰면 비용만 늘고 문제는 그대로 남습니다.

| 단계 | 무엇을 하는가 | 언제 충분한가 / 부족한가 |
|---|---|---|
| 1. Zero-shot 지시문 | 예시 없이 "무엇을 하라"만 서술 | 작업이 단순하고 모델이 이미 그 패턴을 아는 경우 충분 |
| 2. 지시문 명확화 | 모호어를 검증 가능한 조건으로 치환 | 원인이 "모호함"일 때의 정석 해법 |
| 3. 구조화 | XML 태그로 지시·규칙·예시·데이터 구획 분리 | 교차 오염·범주 혼동이 원인일 때 |
| 4. Few-shot 예시 | 입력-출력(+근거) 쌍을 넣어 시연 | 말로 정의하기 어려운 경계, 형식 일관성 |
| 5. 체이닝/다중 인스턴스 | 작업을 여러 호출로 분리 | 한 번에 하기엔 주의가 분산되는 복합 작업 |

### 1.1.1 Zero-shot: 지시문만 주기

예시 없이 "무엇을 하라"만 적는 방식입니다. 가장 간단하고 토큰이 적게 듭니다.

```
계약서에서 renewal_notice_period(갱신 통보 기간)를 추출해 JSON으로 출력하라.
```

```
문서에서 모든 인용(citation)을 추출하라. 인용은 본문 안에 있을 수도 있고,
번호가 매겨진 참고문헌 목록에 있을 수도 있다.
```

지시문을 더 자세하고 명시적으로 쓰는 것이 **1차 개선 수단**입니다.

**언제 충분한가**: 작업이 단순하고, 모델이 이미 그 패턴을 잘 알고 있을 때.

**언제 부족한가**:

- **판단 경계**를 전달해야 할 때. "어떤 문장이 그 정보에 해당하는가" 같은 경계는 서술만으로 잘 전달되지 않습니다.
- **여러 단계의 연결(추적)** 을 요구할 때. 본문의 위첨자 `¹`을 보고 → 문서 끝 참고문헌 목록으로 가서 → 1번 항목을 찾아 → 인용으로 기록하는 작업은, "그럴 수 있다"는 한 줄 설명만으로는 실제 절차가 수행되지 않는 경우가 많습니다. 지시는 **"존재를 알려줄" 뿐, "절차를 보여주지" 않기** 때문입니다.

### 1.1.2 다음 단계: 예시(Few-shot / In-context Learning)

지시문 개선으로 효과가 없을 때의 다음 단계는 **예시를 프롬프트에 넣는 것**입니다. 모델은 학습을 다시 하지 않고 프롬프트 안의 예시를 보고 그 자리에서 패턴을 잡습니다. 이를 **문맥 내 학습(in-context learning)** 이라 합니다 — 가중치를 바꾸는 파인튜닝이 아니라 프롬프트 안에서만 일어나는 임시 학습입니다.

경험칙: **지시문을 길게 늘려 쓰는 것보다 예시 몇 개가 훨씬 강력합니다.** 규칙을 문장으로 촘촘히 나열해도 모델이 그중 일부를 놓치는 현상(instruction drift)이 생기고, 프롬프트만 비대해집니다.

특히 **이미 철저하고 항목화된 루브릭(exhaustive, itemized rubric)이 있는데도 출력 형식이 흔들리는 경우**, 지시문을 더 길게 쓰는 것은 해법이 아닙니다. 이미 상세한 규칙을 더 늘리면 컨텍스트만 커지고 지시 준수율은 오히려 떨어질 수 있습니다.

(구체적 예시 설계법 — 대조 예시, 경계선 사례 선택, 근거 첨부, 개수, 다양성 — 은 2장.)

### 1.1.3 하면 안 되는 "해결책"들

정보 추출이나 판정이 실패할 때 흔히 시도하지만 **잘못된** 접근들입니다.

| 잘못된 시도 | 왜 틀렸는가 |
|---|---|
| 데이터 타입을 열거형(enum)으로 바꾸기 | 스키마 타입 변경은 출력 *형식*만 제약할 뿐, 본문에서 숨은 표현을 찾아내는 **이해 능력**을 올리지 않는다 |
| 기본값(fallback default) 하드코딩 | "못 찾으면 30일"은 실제로 다른 값이었을 자리에 거짓 데이터를 밀어 넣어 데이터셋을 오염시킨다. 추출 실패는 `null`로 남기고 별도 처리한다 |
| 검색 범위를 제목 키워드로 좁히기 | "'renewal'/'termination'이 제목에 든 조항만 보라"는 지시는, 애초에 문제였던 "제목 없는 곳에 묻힌 정보"를 아예 못 보게 만든다 |
| Temperature 올리기 | 온도는 출력의 **무작위성**을 키우는 값이다. 없는 정보를 찾는 능력과 무관하고, 환각 확률만 높인다 |
| Temperature를 0으로 낮추기 | 재현성에는 도움이 되지만, **입력이 매번 달라지면 출력 형식은 여전히 흔들린다.** 형식 준수의 근본 해법이 아니다 |
| 더 큰 모델로 교체 | 원본에 정보 자체가 없으면 어떤 모델도 복구할 수 없다 |
| 2단계 호출로 형식만 재정렬 | 동작은 하지만, 단순 형식 고정을 위해 API 호출과 지연 시간을 2배로 만드는 **과잉 설계** |
| 출력 필드 수 줄이기 | 요구사항을 포기하는 임시방편일 뿐, 환각의 원인은 그대로 |

**표면 수정의 함정**: 어떤 지시가 안 먹혔을 때 다음은 모두 **근본 원인을 건드리지 않은 표면 수정**입니다.

- 같은 지시를 대문자로 강조하거나 어조를 세게 바꾸기
- 같은 지시에 숫자만 붙이기
- 같은 지시를 시스템 프롬프트에서 사용자 메시지로 옮기기

원인이 "모호함"이면 해법은 **"구체화"** 여야 합니다.

## 1.2 프롬프트 구조화 (Prompt Structuring)

### 1.2.1 프롬프트를 이루는 요소

프롬프트(prompt)는 모델에게 보내는 입력 텍스트 전체입니다. 실무의 한 프롬프트에는 보통 여러 종류의 내용이 섞입니다.

- **배경 문맥(background context)**: 도메인 설명, 회사 정책, 참고 문서
- **지시문(instructions)**: 무엇을 하라는 명령
- **서식 지침(formatting instructions)**: 출력을 어떤 모양으로 만들라는 요구
- **예시(examples)**: 입력-출력 쌍 견본
- **실제 사용자 요청(the live user request)**: 진짜로 처리해야 할 것

### 1.2.2 구조가 없으면 생기는 두 가지 사고

**(1) 예시를 실제 요청으로 착각** — 모든 게 태그나 구분자 없이 한 덩어리로 들어가면, 모델이 **예시 안의 입력 데이터를 처리 대상으로 오인**합니다. 그러면 진짜 질문은 무시하고 견본 데이터에 대한 답을 내놓습니다. 모델이 멍청해서가 아니라, 텍스트상 둘을 구분할 근거가 없기 때문입니다.

**(2) 교차 오염(cross-contamination)** — 프롬프트가 길어지고 성격이 다른 내용(지시문, 규칙, 예시, 검사 대상 데이터)이 섞이면 모델이 "어디까지가 규칙이고 어디부터가 데이터인지" 헷갈립니다. A 범주에 쓰라고 준 규칙을 B 범주에 적용해버립니다.

### 1.2.3 해결책: XML 태그로 경계를 만들기

Claude는 학습 과정상 **XML 스타일 태그로 구분된 프롬프트를 특히 잘 따릅니다.** `<example>`, `<examples>`, `<document>`, `<instructions>` 같은 태그로 구획을 나눠주면, 평문보다 훨씬 안정적으로 지시를 따릅니다.

전체 프롬프트 배치의 표준형:

```xml
<context>
당사는 B2B SaaS 지원 데스크를 운영합니다. 티켓은 ...
</context>

<instructions>
아래 티켓을 읽고 우선순위와 카테고리를 판정하라.
</instructions>

<examples>
  <example>
    <input>결제가 두 번 청구됐습니다.</input>
    <output>{"priority": "high", "category": "billing"}</output>
  </example>
  <example>
    <input>로고 색상이 마음에 안 듭니다.</input>
    <output>{"priority": "low", "category": "feedback"}</output>
  </example>
</examples>

<ticket>
로그인 후 대시보드가 빈 화면으로 뜹니다.
</ticket>
```

핵심 패턴:

- **개별 예시는 각각 `<example>`로 감싸고, 예시 묶음 전체를 다시 `<examples>`로 감쌉니다.** 두 겹 구조여야 "여기부터 여기까지가 전부 참고용 견본이다"라는 경계가 분명해집니다.
- **실제 처리 대상은 예시 태그 바깥**에 두거나 별도 태그(`<ticket>`)에 둡니다.
- **태그 이름은 내용과 일치하게** 짓습니다. `<section1>`보다 `<security_criteria>`가 훨씬 낫습니다.
- 태그 이름은 정해진 표준이 아니라 자유롭게 지어도 됩니다. 중요한 건 **일관성과 명확한 경계**입니다.
- **중첩(nesting)** 으로 계층을 표현합니다. 규칙 안에 그 규칙의 예시를 넣습니다.
- 태그 이름을 프롬프트 뒷부분에서 **참조**할 수 있습니다. "`<security_criteria>`에 정의된 기준만 사용하라."

범주별 구획화 예 — 규칙이 서로 섞이지 않게 만드는 방식:

```xml
<security_criteria>
  - 사용자 입력이 검증 없이 SQL 문자열에 들어가면 지적한다.
  - 하드코딩된 비밀키를 지적한다.
  <severity_examples>
    critical: 인증 우회가 가능한 경우
    low: 로그에 사용자 ID가 남는 경우
  </severity_examples>
</security_criteria>

<correctness_criteria>
  - 반환 타입이 문서와 다르면 지적한다.
  <severity_examples>
    high: null을 반환할 수 있는데 호출부가 처리하지 않음
  </severity_examples>
</correctness_criteria>

<style_criteria>
  ...
</style_criteria>
```

### 1.2.4 구조화의 잘못된 대안들

| 잘못된 대안 | 왜 안 되는가 |
|---|---|
| 긴 줄글 한 단락으로 쓰기 | 문장 구조만으로 경계를 표현하려는 시도. 긴 컨텍스트에서 범주 경계가 흐려지고 규칙이 섞인다 |
| 헤더 없는 하나의 불릿 목록 | 항목 순서만으로 소속 범주를 암시. 모델이 추측해야 하므로 오염 위험이 크다 |
| 모든 범주의 전체 규칙을 각 섹션마다 반복 | 섹션을 자립적으로 만들려는 의도지만 토큰을 낭비하고 혼란을 키운다. 경계 문제는 **반복이 아니라 구획화**로 푼다 |
| 예시를 프롬프트 맨 뒤로 옮기기 | 위치만 바꿔도 경계는 여전히 모호하다. 오히려 마지막 텍스트를 **최종 명령으로 오인**할 위험이 커진다 |
| 예시를 짧은 불릿으로 요약 | 입력-출력 쌍이 사라지면서 예시의 학습 효과를 잃는다 |
| 예시를 아예 없애기 | 혼동은 사라지지만 출력 품질이 함께 떨어진다. 구조 문제를 품질 손실로 맞바꾸는 셈 |
| 정책 문서 전문을 예시마다 반복 삽입 | 공통 규칙·정책은 **상단에 한 번만** 쓰고 예시엔 개별 사례만 담는다. 반복은 문맥 창과 토큰을 심각하게 낭비한다 |

## 1.3 명시적 기준 vs 모호한 지시

여기서부터는 "LLM에게 판단을 시키는 시스템"(대표적으로 AI 코드 리뷰 에이전트)의 지침 설계 원칙입니다.

### 1.3.1 배경 용어: 정밀도, 재현율, 오탐

- **True Positive (TP)**: 진짜 문제를 문제라고 맞게 표시
- **False Positive (FP, 오탐/거짓 양성)**: 문제가 아닌데 문제라고 표시
- **False Negative (FN, 미탐/거짓 음성)**: 진짜 문제인데 놓침
- **정밀도(Precision)** = TP / (TP + FP) — "표시한 것 중 진짜 문제의 비율". 낮으면 오탐이 많다
- **재현율(Recall)** = TP / (TP + FN) — "진짜 문제 중 잡아낸 비율". 낮으면 누락이 많다

"노이즈가 많은 카테고리"란 보통 **정밀도가 낮은** 카테고리를 뜻합니다.

오탐이 많으면 **알림 피로도(notification fatigue)** 가 생깁니다. 개발자가 "또 사소한 트집이겠지"라며 도구의 출력을 아예 무시하기 시작하면 그 도구는 사실상 죽은 것입니다. 그래서 리뷰 도구에서 보통 더 치명적인 것은 **낮은 정밀도**이고, **정밀도를 올리는 것**이 종종 최우선 과제가 됩니다.

### 1.3.2 모호한 지시가 만드는 문제

"주석이 정확한지 확인하라(check that comments are accurate)" 같은 지시는 왜 나쁠까요? **"정확하다"의 기준이 없기 때문**입니다. 모델은 문구가 조금 어색한 것도 "정확하지 않음"으로 판단해 지적합니다.

다음 표현들은 모두 **기준을 모델의 주관에 떠넘기는 모호한 지시**입니다.

- "높은 확신이 있을 때만(highly confident)" → 얼마가 높은 것인지 정의가 없음
- "충분히 중요하다고 판단되면(significant enough)" → 중요함의 기준이 없음
- "사소한 표현 차이는 무시하라(trivial wording)" → 사소함의 기준이 없음
- "신뢰도가 90%를 넘으면" → LLM의 자기 확신도는 교정(calibration)되어 있지 않아 신뢰할 수 없는 숫자
- "개선될 수 있는 모든 것(could plausibly be improved)" → 사실상 무한대로 지적하게 만들어 오탐을 극대화

### 1.3.3 신뢰도 기반 필터링이 실패하는 이유

가장 흔한 잘못된 처방은 프롬프트에 이런 줄을 넣는 것입니다.

```
확신하는 이슈만 보고하라. (Only surface issues you are very sure about.)
신뢰도가 높은 지적만 보고하라. (Only report high-confidence findings.)
확신도 80% 이상만 출력하라.
```

**이렇게 해도 오탐률은 거의 변하지 않습니다.**

모델에게는 자기 출력의 정확도를 측정하는 내부 계기판이 없습니다(**calibration**, 교정 능력의 한계). "높은 신뢰도"라는 말은 **무엇을 보고하고 무엇을 건너뛸지에 대한 구체적 규칙을 전혀 주지 않습니다.** 정의를 알 수 없으니 모델은 오탐을 만들어냈던 **바로 그 내재적 판단 기준을 그대로 다시 적용**합니다. 애초에 모델은 자기 출력을 확신했기 때문에 지적한 것입니다. "80%"라는 숫자를 줘도 비교할 대상이 없으므로 문장을 흉내 낼 뿐입니다.

같은 이유로 다음 지침들도 모두 **실질적으로 신뢰도 기반**이라 효과가 없습니다.

- "내부 신뢰도 점수가 0.9를 넘으면 보고하라" — 숫자를 붙여도 주관적 자기평가
- "2차 검토 패스가 1차의 신뢰도 점수를 확인하면 보고하라" — 검증을 겹쳐도 기반은 여전히 신뢰도 점수
- "시니어 엔지니어가 동의할 것이라고 장담할 수 있으면 보고하라" — 암묵적 기준에 대한 주관적 추측
- "주변 코드에 비해 특이해 보이면 보고하라" — 주관적 인상이자, 버그가 아닌 스타일 지적

### 1.3.4 대안: 명시적/범주적 기준 (Explicit / Categorical Criteria)

**무엇을 항상 보고하고 무엇을 항상 건너뛸지를 범주로 직접 정의합니다.** 모델의 확신도가 아니라 **코드에서 객관적으로 확인 가능한 조건**으로 씁니다. 좋은 기준은 **객관적으로 참/거짓을 판정할 수 있는 조건**이어야 하고, 그 조건을 보여주는 **구체 예시**가 붙어야 합니다.

**명확성과 구체성의 대비 — 나쁜 프롬프트 / 좋은 프롬프트**

```
[프롬프트 X — 나쁨]
보안 위험처럼 보이는(looks like) 것은 무엇이든 표시하라.

[프롬프트 Y — 좋음]
사용자 입력을 매개변수화 없이 SQL 쿼리 문자열에 직접 쓰는 코드,
또는 평문 비밀번호를 저장하는 코드를 표시하라.
```

Y가 우월한 이유는 **구체적이고 검증 가능한 조건(specific, checkable conditions)** 을 이름 붙여 정의했기 때문입니다. 모델이 "이 코드가 그 조건에 해당하는가?"라는 **판정 가능한 질문**으로 환원할 수 있습니다. X는 "위험해 보인다"는 열린 주관적 판단이라, 미심쩍은 평범한 코드까지 전부 걸려 오탐이 쏟아집니다.

> **트레이드오프**: 구체적인 목록은 목록 밖의 위험을 놓칠 가능성(**미탐, FN**)을 갖습니다. 즉 **어떤 지표를 개선하려는지에 따라 평가가 달라집니다.** 오탐 감소가 목표라면 구체성이 답입니다.

**포함/제외 목록 (Explicit Scoping)**

주관적 판단을 위임하지 말고 객관적으로 판정 가능한 규칙으로 바꿔 씁니다.

```
[이 카테고리에 포함되는 것 — Inclusion]
- 사용자 입력이 SQL 쿼리 문자열에 직접 연결(concatenate)되는 경우
- 검증되지 않은 경로 문자열이 파일 열기 함수에 전달되는 경우

[이 카테고리에서 제외되는 것 — Exclusion]
- 파라미터 바인딩을 사용하는 쿼리
- 테스트 코드 내부의 하드코딩된 문자열
```

이러면 모델은 "내가 얼마나 확신하나?"가 아니라 **"이 항목이 목록에 있나?"** 를 판단하게 되고, 이는 훨씬 안정적입니다.

**보고/스킵 쌍**

```
보고하라: 보안 취약점을 유발하는 변경, 또는 기존 동작을 망가뜨리는 정확성 버그.
건너뛰어라: 서식 선호, 그리고 해당 파일에 자리 잡은 지역적 관례에서 벗어난 정도의 차이.
```

**버그 탐지 카테고리의 구체적 재작성**

```
변수, 인자, 또는 반환값이 다음 중 하나와 모순되게 사용될 때만 이슈를 보고하라:
  - 선언된 타입
  - 문서화된 계약(contract)
  - 코드 다른 곳에 명시된 전제 조건(precondition)
```

이 지침이 좋은 이유는 **판단 근거가 코드 안에 있고 검증 가능하다**는 점입니다. 모델이 "확신하는지"를 스스로 물을 필요가 없습니다.

> **주의**: 명시적인 것만으로는 부족합니다. **"공식 스타일 가이드를 벗어난 모든 변경을 보고하라"** 는 명시적이긴 하지만 주관적 스타일 노이즈를 대량 생산해 "소음을 피한다"는 목표와 충돌합니다. **범주 선택 자체가 중요도에 맞아야** 합니다.

**주석 정확성 기준의 재작성**

```
[나쁜 지시]
주석이 정확한지 확인하라.
```

```
[좋은 지시]
주석이 동작에 대해 구체적인 주장을 하고 있고, 그 주장이 코드가 실제로 하는 일과
모순될 때만 지적하라.
예: docstring에 "returns None"이라고 적혀 있는데 함수가 항상 값을 반환하는 경우.
표현 방식이나 문체에 대한 지적은 하지 않는다.
```

차이의 핵심은 판정 절차가 **검증 가능(verifiable)** 하다는 점입니다. "주석의 주장"과 "코드의 실제 동작"을 비교하면 참/거짓이 결정되고, 취향이 개입할 여지가 없습니다.

### 1.3.5 적용 사례: 주석-코드 모순 판정

> 독스트링(docstring): "캐시된 값이 있으면 그것을 반환하고, 없으면 API에서 가져온다."
> 실제 코드: 캐시 확인 없이 **항상** API를 호출한다.

**이것은 보고 대상입니다.** 독스트링이 캐싱 동작에 대한 **구체적이고 검증 가능한(checkable) 주장**을 하고 있고, 코드의 실제 **제어 흐름(control flow)** 이 그것과 직접 모순되기 때문입니다.

> **독스트링(docstring)**: 함수/클래스 바로 안에 쓰는 설명 문자열. 파이썬 등에서 사용하며, 호출자가 읽는 문서 역할을 합니다.

흔한 오해 정리:

- **"주석은 '의도'일 뿐이라 불일치는 문제가 아니다"?** 아닙니다. 조건부 동작을 구체적으로 서술한 이상, 그것은 호출자가 신뢰하는 **동작 계약(contract)** 이며 실제와 다르면 명백한 결함입니다.
- **"호출 횟수가 한 곳뿐인 함수는 면제"?** 호출 지점 개수는 주석-코드 모순 판정과 아무 관계가 없습니다.
- **"캐싱은 구현 세부사항이라 검토 대상 제외"?** 문서에 명시적으로 서술된 순간 그것은 내부 구현을 넘어 **외부에 약속된 계약**이 됩니다.

### 1.3.6 원칙 요약

- 주관적 판단어("중요한", "확신하는", "적절한")를 **관찰 가능한 조건**으로 치환한다.
- 무엇을 지적할지뿐 아니라 **무엇을 지적하지 말지**도 명시한다.
- 조건마다 **구체 예시를 하나씩** 붙인다.
- 범주 선택이 실제 중요도와 맞는지 확인한다.

## 1.4 프롬프트 체이닝과 다중 인스턴스 설계

### 1.4.1 Prompt Chaining (프롬프트 체이닝)

하나의 큰 작업을 여러 번의 API 호출로 쪼개고, 앞 호출의 출력을 뒤 호출의 입력으로 넘기는 구조입니다.

```
1차 호출: diff → 초안 발견 사항 12개 생성        (recall 위주)
2차 호출: 각 초안 → 명시적 기준에 비추어 개별 검증  (precision 위주)
결과: 검증 통과한 항목만 최종 확정
```

**왜 단일 호출(single-pass)보다 정밀도가 높아지는가?**

한 번의 응답에서 수십 개 후보를 동시에 찾고, 서술하고, 형식을 맞추고, 기준까지 적용하려면 모델의 주의가 분산됩니다(cognitive load). 그 결과 기준을 느슨하게 적용해 오탐이 섞입니다. 2차 패스는 **이미 뽑힌 항목 하나하나만 놓고 기준 충족 여부만 독립적으로(in isolation)** 판단하므로 훨씬 엄격해집니다.

> **주의**: 체이닝의 이점은 **작업 분리라는 구조**에서 나옵니다. "두 번째 호출이 자동으로 더 좋은 모델을 쓴다", "시스템 프롬프트가 리셋되어 편향이 지워진다", "컨텍스트 양이 두 배가 된다" 같은 설명은 사실이 아닙니다.

> 다만 **단순 형식 고정만을 위해** 호출을 2단계로 나누는 것은 과잉 설계입니다(1.1.3 참조). 체이닝은 판정 부담이 실제로 분리될 때 값어치가 있습니다.

### 1.4.2 Generator / Reviewer 분리 (독립 검토자 패턴)

코드를(또는 발견 사항을) 만든 인스턴스와 그것을 검토하는 인스턴스를 **분리된 호출**로 둡니다. 목적은 **편향되지 않은 제3자 시각**입니다.

이 패턴을 무력화하는 대표적 실수: 토큰을 아끼려고 **생성자가 스스로 쓴 요약본**을 검토자에게 넘기는 것. 그러면 검토자는 실제 코드가 아니라 **생성자의 주관적 프레이밍(self-framing)** 을 평가하게 됩니다. 생성자가 놓치거나 잘못 이해한 부분은 요약에도 없으므로 영원히 발견되지 않습니다. 검토자에게는 **원본 diff(raw context)** 를 그대로 줘야 합니다.

같은 이유로, 생성자가 자기 검토 결과 중 동의하지 않는 항목을 **사람에게 보이기 전에 폐기**하는 설계도 잘못입니다.

### 1.4.3 Per-file Pass vs Integration Pass

큰 변경 묶음(changeset)을 검토할 때 흔히 2단계로 나눕니다.

| 패스 | 보는 범위 | 담당해야 할 문제 |
|---|---|---|
| **파일별 패스(per-file)** | 파일 하나씩 | 문법 오류, 스타일/들여쓰기, 명명 규칙, 그 파일 안의 중복 로직, 국소적 함수 로직 — **한 파일 안에서 완결되는 문제** |
| **통합 패스(integration)** | 변경 묶음 전체 | 파일별 패스가 원리적으로 볼 수 없는 **파일 간(cross-file) 문제** |

통합 패스가 잡아야 할 것:

- 공유 인터페이스/계약(contract)을 파일마다 다르게 사용하는 경우
- 데이터 흐름 불일치 — A 파일이 넘기는 값의 형태와 B 파일이 기대하는 형태가 다름
- 한쪽에서 시그니처를 바꿨는데 다른 쪽 호출부를 안 고친 경우

핵심: 통합 패스가 파일 내부 문법이나 서식을 다시 보는 것은 **중복 낭비**입니다. 역할을 계층적으로 나눠야 합니다.

## 1.5 흔한 실패

### 1.5.1 경고 피로도(Alert Fatigue) 관리

**경고 피로도**란 부정확한 알림이 반복되면 사람들이 **알림 전체를 무시하게 되는** 현상입니다. 핵심은 **오염이 카테고리를 넘어 번진다**는 점입니다.

> 코드 리뷰 도구의 "성능 제안" 카테고리가 오탐률 70%다. 그 결과 개발자들이 **잘 작동하는 다른 카테고리의 지적까지 포함해** 도구의 모든 결과를 읽지 않게 되었다.

몇 주에 걸쳐 그 카테고리의 프롬프트를 개선할 예정일 때 **즉시 취할 조치**:

> **문제 카테고리를 일시적으로 비활성화(disable)하고, 정확한 카테고리만 노출한다. 별도로 그 카테고리의 프롬프트를 개선·검증한 뒤 재활성화한다.**

이유: 노이즈 출처를 즉시 차단해야 피로도가 해소되고 나머지 결과에 대한 신뢰가 빠르게 회복됩니다. 이것이 AI 품질 관리의 표준 절차입니다 — **끄고, 고치고, 검증하고, 다시 켠다.**

효과 없는 대안들:

- **심각도 레이블을 "정보성(informational)"으로 낮추기** — 노이즈가 계속 화면에 출력되는 한, 개발자가 다른 카테고리를 무시하는 행동은 멈추지 않습니다.
- **문제 카테고리를 잘 작동하는 정확성 카테고리에 병합하기** — 오탐을 깨끗한 카테고리에 섞어 **그 카테고리의 신뢰까지 함께 파괴**합니다.
- **"일부 카테고리는 정밀도가 낮습니다" 면책 배너 달기** — 필터링 부담을 사용자에게 떠넘길 뿐 피로도를 전혀 줄이지 못합니다.

### 1.5.2 실패 유형 요약표

| 증상 | 잘못된 처방 | 올바른 처방 |
|---|---|---|
| 오탐이 많다 | "확신하는 것만 보고하라" | 포함/제외 목록, 검증 가능한 조건으로 재작성 |
| 지시를 안 따른다 | 대문자 강조, 어조 강화, 시스템↔유저 이동 | 모호어 제거 = 구체화 |
| 규칙이 섞인다 | 각 섹션에 전체 규칙 반복 | XML 태그로 구획화, 태그 이름으로 참조 |
| 예시를 요청으로 착각한다 | 예시를 맨 뒤로 이동 | `<examples>`/`<example>` 이중 태그, 처리 대상은 별도 태그 |
| 출력 형식이 흔들린다 | 루브릭을 더 길게, temperature 0, 2단계 호출 | 원하는 필드 순서가 반영된 완성 예시 3~5개 |
| 값을 지어낸다(환각) | 모든 필드 `required`, 기본값 하드코딩 | `null`로 "모른다"고 말할 출구 제공 |
