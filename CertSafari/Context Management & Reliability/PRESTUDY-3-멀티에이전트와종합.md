# 3. 멀티 에이전트 위임과 결과 종합

이 장에서 다루는 것

- 코디네이터·서브에이전트의 역할 구분과 컨텍스트 격리
- 무엇을 위임하고 무엇을 직접 할 것인가 (위임의 방향 규칙, 조정 오버헤드)
- 서브에이전트가 무엇을 어떤 형태로 돌려줘야 하는가 (출력 계약·스키마·출처 메타데이터)
- 여러 결과를 하나의 산출물로 합치는 종합(Synthesis)과 출처 추적성
- 상충하는 결과를 다루는 법 (충돌 보고, 병렬 제시, 증거 가치의 차등)
- 종합 단계에서 흔히 저지르는 실패

---

## 3.1 코디네이터·서브에이전트 역할과 컨텍스트 격리

### 3.1.1 역할 구분

**에이전트(agent)** 는 LLM + 도구(파일 읽기, 검색, 웹 요청 등) + 목표로 구성된 실행 단위입니다.
멀티 에이전트 구조에서는 다음 역할들이 등장합니다.

| 역할 | 설명 |
|---|---|
| **메인 에이전트(main agent)** | 사용자와 직접 대화하고, 전체 목표를 유지하며, 최종 판단을 내리는 주체 |
| **오케스트레이터(orchestrator)** | 여러 서브에이전트를 실행하고 그 결과를 모아 다음 단계로 넘기는 조율자 |
| **코디네이터(coordinator)** | 오케스트레이터와 거의 같은 뜻. 작업을 쪼개 배분하고, 결과를 모으고, 실패를 복구하며, 조정·결정을 내리는 상위 주체 |
| **서브에이전트(subagent)** | 좁고 구체적인 하위 작업(문서 읽기, 검색, 분석)을 **자기 자신의 별도 컨텍스트**에서 수행하고 결과를 반환하는 하위 실행 단위 |
| **합성/종합 에이전트(synthesis agent) / 종합 단계(synthesis step)** | 여러 서브에이전트의 산출물을 하나의 답/보고서로 통합하는 역할 또는 단계 |

실제 배치 예: 판례 검색 담당 서브에이전트 3개, 경쟁사 매출 조사 담당 2개 + 이를 합치는 합성 에이전트 1개.

### 3.1.2 서브에이전트가 존재하는 진짜 이유: 컨텍스트 격리

서브에이전트의 가장 큰 가치는 "병렬 처리"가 아니라 **컨텍스트 격리(context isolation)** 입니다.

메인 에이전트가 세 개 서비스의 파일을 전부 직접 열어 읽으면 그 모든 원문이 메인 컨텍스트에 쌓이고,
정작 중요한 일(재설계 제안 종합)을 할 공간과 집중력을 잃습니다.
서브에이전트에 위임하면 탐색의 **원문은 서브에이전트 컨텍스트에서 소비되고**,
메인 에이전트에는 **정제된 요약(distilled summary)** 만 돌아옵니다.

```
[메인 에이전트 컨텍스트]           [서브에이전트 컨텍스트]
 - 사용자 요청                       - grep 원시 출력 4,000줄
 - 계획                       →      - 필터링 과정
 - "테스트 파일 1,203개, 주로  ←      - 정리
    tests/ 와 src/**/__tests__/"
```

서브에이전트 안에서 파일 500개를 열고 grep 결과 3만 줄을 봐도 메인 컨텍스트는 전혀 오염되지 않습니다.
원시 출력은 서브에이전트가 끝나면 함께 사라집니다.

```
[메인 에이전트]  ← 요약 300토큰 ←  [서브에이전트 A]  ← 원시 출력 40,000토큰
                 ← 요약 300토큰 ←  [서브에이전트 B]  ← 원시 출력 35,000토큰
                 ← 요약 300토큰 ←  [서브에이전트 C]  ← 원시 출력 50,000토큰
```

각 서브에이전트가 자체 컨텍스트 윈도우를 가지므로 전체가 다룰 수 있는 정보량이 늘어납니다.
대신 대가가 있습니다. 서브에이전트들은 **서로의 컨텍스트를 볼 수 없고**,
**정보가 단계를 건널 때마다 손실될 위험**이 생깁니다. 그래서 주고받는 데이터의 형식이 결정적으로 중요해집니다(3.3절).

**언제 쓰는가**: 출력이 크고, 그 출력의 원시 형태를 나중에 다시 볼 일이 없으며, 결론만 필요할 때.
(대량 검색, 저장소 전수 탐색, 여러 문서 스캔 등)

**하지 말아야 할 대안들**:

- 메인에서 파일 5만 개를 하나씩 읽어보기 → 비용·시간 폭발, 컨텍스트 초과.
- 사용자에게 목록을 직접 붙여넣어 달라고 요청 → 자동화의 목적 자체를 훼손.
- 원시 출력을 "혹시 나중에 필요할까 봐" 대화에 그냥 남기기 → 오염 문제를 그대로 방치.

### 3.1.3 병렬 실행과 부분 실패

코디네이터가 서브에이전트 여러 개를 **병렬(parallel)** 로 돌리는 경우가 많습니다.
예: 경쟁사 3곳의 가격 페이지를 각각 다른 서브에이전트가 수집.

이때 **일부만 실패하는 상황(partial failure, 부분 실패)** 이 반드시 생깁니다. 2개는 성공, 1개는 실패.
설계는 이 상황을 예외가 아니라 기본값으로 가정해야 합니다.

### 3.1.4 실행 재개(Resume)와 결과 캐싱

대규모 멀티 에이전트 실행을 중간에 일시 정지(pause)했다가 **같은 세션 안에서** 재개(resume)하면,
오케스트레이션 엔진은 **이미 완료되어 결과를 반환한 에이전트의 결과를 캐시에서 재사용**하고,
아직 끝나지 않은 에이전트만 실제로 다시 실행합니다.

- 이유: 이미 성공한 작업을 다시 돌리는 것은 API 토큰과 시간의 순수 낭비이기 때문입니다.
- 이를 **상태 지속성(state persistence)** 과 **결과 캐싱(result caching)** 이라고 합니다.
- 즉, 일시 정지가 곧 결과 폐기를 의미하지 않으며, 재개를 위해 애플리케이션을 재설치하거나 새로 시작할 필요도 없습니다.

## 3.2 위임 판단 기준

### 3.2.1 위임의 방향 규칙

이것이 이 주제에서 가장 중요한 설계 원칙 중 하나입니다.

> **토큰을 많이 소모하지만 결론이 짧은 작업 → 서브에이전트에게 위임**
> **전체 맥락을 알아야 하는 고수준 판단·종합 → 메인 에이전트가 직접 수행**

**서브에이전트에 적합한 일**

- 여러 디렉터리를 전수 검색(exhaustive search)
- 대량 로그 파싱
- 문서 수십 건 훑어서 관련 부분만 추출
- 즉, **verbose output(장황한 출력)을 만들어내는 저수준 탐색**

**메인 에이전트가 직접 해야 하는 일**

- 마이그레이션 전략 수립
- 아키텍처 판단
- 상충되는 정보 사이의 최종 결정
- 즉, **전체 그림을 봐야 하는 고수준 종합(synthesis)**

이 방향이 **거꾸로** 되면(탐색을 메인이 하고 종합을 서브에게 위임) 최악입니다.
메인 컨텍스트는 쓰레기 토큰으로 가득 차고, 정작 종합을 맡은 서브에이전트는 전체 맥락을 못 봅니다.

### 3.2.2 좋은 위임 프롬프트의 조건

1. **범위가 명확할 것 (bounded)**: 무엇을 조사할지, 어디를 볼지 구체적으로.
2. **목적이 명시될 것**: 왜 필요한지 알면 관련성 판단이 정확해집니다.
3. **요약 반환을 지시할 것**: 원문 전량 반환을 금지합니다.

좋은 예:

> "payments, ledger, notifications 세 서비스에 걸친 환불 흐름의 의존 관계를 추적하고,
> 발견한 내용을 요약해서 보고하라."

나쁜 예와 그 이유:

- "코드베이스를 좀 둘러보고 흥미로운 걸 아무거나 보고해라"
  → 범위가 없어 서브에이전트가 무관한 곳을 헤매고 토큰만 소모합니다.
- "아무 지시도 주지 않고 git status만 보고 목표를 추론하게 한다"
  → 목표 추측은 실패 확률이 높습니다.
- "조사 중에 연 모든 파일의 전체 내용을 요약 없이 그대로 보고해라"
  → 위임의 목적 자체를 파괴합니다. 원문이 그대로 메인 컨텍스트로 쏟아지면
     직접 읽은 것과 똑같아지고, 전달 비용만 추가됩니다.

### 3.2.3 위임하지 말아야 할 때 — 조정 오버헤드

위임은 공짜가 아닙니다. **조정 오버헤드(coordination overhead)** 가 있습니다.

- 서브에이전트 생성(spawn) 비용
- 프롬프트와 필요한 컨텍스트를 전달하는 토큰 비용
- 결과를 되받아 해석하는 비용
- 왕복으로 인한 지연 시간

**판단 기준:**

| 상황 | 선택 |
|---|---|
| 범위가 넓고, 여러 파일/서비스를 훑어야 하고, 원문이 많이 발생 | 위임 |
| 작고 목표가 명확한 단일 조회/수정 (예: 작은 모듈 안의 함수 하나 찾아 고치기) | 메인 에이전트가 직접 수행 |

작은 작업까지 무조건 위임하면 오버헤드가 작업 자체보다 커집니다.
반대로 "모든 직접 도구 사용을 금지하고 무조건 위임"하는 정책도 비효율적입니다.
또 같은 작업을 여러 서브에이전트에게 중복 실행시켜 교차 검증하는 것은
확실성이 필요한 특수한 경우가 아니면 낭비입니다.

원칙: **위임은 도구이지 규칙이 아니다. 컨텍스트 절약 이득이 조정 비용보다 클 때만 쓴다.**

### 3.2.4 위임을 아예 안 하는 것도 답이 아니다

"전부 하나의 에이전트 컨텍스트 안에서 처리한다"는 선택은 소규모에서는 단순해서 좋지만,
20만 줄 코드베이스 같은 규모에서는 컨텍스트 예산을 금방 초과하고 정보 손실이 발생합니다.

### 3.2.5 단계 간 핸드오프(phase handoff)

작업을 phase 1 → phase 2로 나눠 진행할 때, phase 2 에이전트가 phase 1 결과를 알아야 합니다.
이때 선택지는 세 가지이고, 정답은 항상 가운데입니다.

| 방식 | 결과 |
|---|---|
| 원본 대화록(raw transcript) 전부 전달 | 토큰 폭발, 비용 증가, 주의 분산. 격리의 이점이 사라짐 |
| **핵심 발견을 간결한 요약으로 종합해 초기 프롬프트에 주입** | ✅ 토큰 절약 + 맥락 유지 |
| 아무것도 전달 안 함 | phase 2가 phase 1 작업을 중복 재발견. 자원 낭비 |

**grounded(기반을 둔)** 라는 표현은 "후속 에이전트가 앞 단계의 사실 위에서 작업하는 상태"를 뜻합니다.
근거 없이 시작하면 에이전트는 가정을 지어내고, 그것이 곧 **환각(hallucination)** 으로 이어집니다.

또한 "서브에이전트가 질문할 때까지 기다린다"는 수동적 방식은 나쁩니다.
에이전트는 모르는 걸 모른다고 인지하지 못한 채 그냥 진행해 버리는 경향이 있기 때문입니다.
**필요한 맥락은 처음부터 밀어 넣는(push) 것이 원칙입니다.**

## 3.3 서브에이전트 출력 설계 — 무엇을 돌려줄 것인가

서브에이전트가 "무엇을, 어떤 형태로" 반환하는지가 시스템 전체 품질을 결정합니다.

### 3.3.1 출력 계약(Output Contract)

**출력 계약**이란 서브에이전트가 반환해야 할 데이터의 **형식과 필수 항목을 사전에 규정한 약속**입니다.
인터페이스, 출력 스키마(Output Schema), 데이터 계약(Data Contract)이라고도 부릅니다.

**왜 필요한가**: 자유 형식 문단(free-form paragraph)으로 결과를 주고받으면 상위 에이전트가
프로그램적으로 파싱·비교·검증할 수 없습니다. 계약을 정하고 구조화된 형식(예: JSON)으로 반환하게 하면
코디네이터가 날짜를 비교하고, 출처를 추적하고, 충돌을 판별할 수 있습니다.

> 멀티 에이전트 시스템의 대부분의 문제는 "모델을 바꿔서"가 아니라 **"출력 계약을 고쳐서"** 해결됩니다.

### 3.3.2 추론 서술을 빼고 결론과 근거만

서브에이전트에게 자유 서술을 허용하면 대개 이런 걸 반환합니다.

> "먼저 A 디렉터리를 살펴봤습니다. 거기에서 몇 가지 흥미로운 패턴을 발견했는데, 이는
> B와 관련이 있어 보였고, 그래서 다시 C를 확인했더니… (단락 5개 더)"

이 **추론 서술(reasoning narrative)** 은 대부분 상위 에이전트에게 불필요합니다.
상위 에이전트가 필요한 건 **결론과 근거**뿐입니다.

권장 출력 형태:

```json
{
  "key_facts": ["2023년 개정으로 X 조항이 적용 제외됨"],
  "citations": [
    {"source": "Smith v. Jones, 2023", "locator": "p.14"}
  ],
  "relevance_score": 0.82,
  "conflicts": []
}
```

- **key facts**: 핵심 사실만
- **citations**: 인용/출처
- **relevance score**: 관련성 점수 — 상위 단계가 정렬·필터링에 사용
- 추론 과정은 **제외**

이렇게 하면 서브에이전트 8개의 출력을 합쳐도 컨텍스트 예산 안에 들어옵니다.

**잘못된 대안들**

- **먼저 도착한 것만 쓰고 나머지 버리기** — 정보 유실. 도착 순서는 중요도와 무관.
- **에이전트 수를 늘려 주제를 잘게 나누기(단, 여전히 전체 추론을 반환)** — 총 토큰은 줄지 않고 오히려 늘어남.
- **소비자가 두 번에 나눠 읽기(two passes)** — 한 번 호출의 입력 한계 자체는 그대로. 구조적 해결이 아님.

**원칙: 출력량 문제는 출력을 만드는 쪽에서 줄여야 한다.**

### 3.3.3 인용 근거 부착(citation grounding)

후속 에이전트가 **원본 문서를 다시 읽지 않고도** 각 주장을 검증하고 재인용할 수 있으려면,
서브에이전트의 구조화된 출력에 다음 세 가지가 들어가야 합니다.

1. **주장 텍스트(claim text)** — 무엇을 알아냈는가
2. **출처 식별자(source URL 또는 문서명)** — 어디서 나왔는가
3. **주장을 뒷받침하는 관련 발췌문(relevant excerpt)** — 원문에 실제로 뭐라고 쓰여 있는가

```json
{
  "claim": "회사는 2025년 1월에 데이터 유출 사고를 공시했다.",
  "source": "https://sec.gov/.../10-K-2025.htm",
  "excerpt": "In January 2025, the Company identified unauthorized access to ..."
}
```

**부족한 대안들**:

- 출처 문서를 명시하지 않고 주변 문단을 요약만 하면 → 검증도 인용도 불가능.
- 어느 서브에이전트가 만들었는지만 적으면 → 그 서브에이전트는 이미 종료됐고 컨텍스트도 사라졌으므로
  재질의할 대상이 없습니다. **출처는 문서이지 에이전트가 아닙니다.**
- 서브에이전트가 스스로 매긴 신뢰도 점수만 붙이면 → 그 점수 자체가 검증되지 않은 자기 평가입니다.
  검증에 쓸 원문 근거가 없습니다.

### 3.3.4 출처 메타데이터(source metadata)를 함께 실어라

숫자 하나만 넘기면 상위 단계가 그것을 판단할 수 없습니다.

나쁜 출력:
```
TAM: 480억 달러
```

좋은 출력:
```
TAM: 480억 달러
  - 출처: Gartner "Industry X Market Sizing"
  - 발행일: 2021-03
  - 방법론: 하향식(top-down), 상위 20개사 매출 기반 추정
  - 지역 범위: 북미만
```

왜 필요한가:

- **발행일(publication date)** — 어느 수치가 최신인지 판단하려면 필수. 없으면 오래된 수치(outdated figure)를 인용하는 사고가 납니다.
- **방법론(methodology)** — 하향식 추정치와 상향식 실측치는 애초에 **비교 가능(comparable)** 하지 않습니다.
  방법이 다르면 숫자 차이는 오류가 아니라 정의 차이일 수 있습니다.
- **범위/정의** — 지역, 기간, 포함 항목.

여기서 나오는 개념이 **TAM(Total Addressable Market, 총 유효 시장)** 입니다.
어떤 제품이 이론상 도달 가능한 시장 전체 규모를 뜻하며, 정의와 방법론에 따라 몇 배씩 달라지는
대표적인 "맥락 없이는 무의미한 숫자"입니다.

잘못된 대안:

- 여러 출처를 **평균 내기** — 서로 다른 시점·방법의 수치를 평균하면 의미 없는 숫자가 되고, 최신성도 사라집니다.
- **가장 큰 값을 고르기** — 정확성과 무관한 편향된 규칙.
- **검색 과정을 더 자세히 설명하기** — 필요한 건 에이전트가 어떻게 찾았는지가 아니라,
  **찾아낸 데이터 원본의 속성**입니다.

## 3.4 결과 종합(Synthesis)

### 3.4.1 출처 추적성(Provenance / Traceability)

**Provenance(출처 내력, 데이터 프로버넌스)** 는 "이 주장이 어디서, 언제, 누구를 통해 왔는가"를
추적할 수 있는 성질이며, 각 값이 어디서·언제 나왔는지를 **끝까지 유지하는 것**입니다.

합성 에이전트에게 "모든 서브에이전트 결과를 간결하게 통합 요약하라"고만 지시하면,
문장은 매끄러워지지만 다음이 사라집니다.

- 어떤 서브에이전트가 찾은 정보인지
- 어떤 문서/URL에 근거하는지
- 언제 기준 데이터인지

검토자는 보고서를 검증할 수 없게 되고, 보고서는 사실상 신뢰할 수 없는 산문이 됩니다.

**해결책은 프롬프트에 메타데이터 유지(carry forward)를 명시적으로 지시하는 것입니다.**

```
각 주장을 보고서에 옮길 때, 해당 주장에 붙어 있던
source(출처 문서/URL), date(자료 기준일), agent(수집 서브에이전트)
메타데이터를 반드시 함께 유지하라. 메타데이터가 없는 주장은 포함하지 마라.
```

결과 예시:

> 경쟁사 A의 2025년 매출은 4억 2천만 달러다. [출처: 2026-01-14 자사 보도자료, 수집: revenue-agent-1]

주의할 점: **문체를 격식 있게 바꾸거나, 보고서를 더 짧게 만들거나, 말미에 "출처는 요청 시 제공" 같은
일반 면책 조항을 붙이는 것은 추적성 문제를 전혀 해결하지 못합니다.**
추적성은 각 주장 옆에 메타데이터가 실제로 붙어 있어야 성립합니다. 오히려 더 짧게 만들면 손실이 심해집니다.

### 3.4.2 증거 가치(Evidentiary Weight)의 차등 표현

여러 출처를 합성할 때 각 주장의 **근거 강도가 다르다는 사실 자체가 정보**입니다.
그런데 요약을 거치면 모든 문장이 같은 어조로 평평해집니다.

법률 리서치 예시:

- 주장 X: 검토한 **모든 항소법원이 긍정적으로 인용**한 확립된 판례 → 근거 매우 강함
- 주장 Y: **단 하나의 하급심 판결에만** 등장하고 다른 곳에서 검증되지 않은 주장 → 근거 매우 약함

이 둘이 같은 단락에 똑같은 문구로 나열되면, 독자는 두 주장이 같은 무게라고 오해합니다.
법률·의료·금융처럼 판단의 결과가 무거운 도메인에서 이는 심각한 결함입니다.

**올바른 수정: 증거 가치별로 섹션을 분리하고, 서술 방식을 다르게 하기**

```
## 확립된 판례 (Well-Settled Authority)
- 판례 X: 이 원칙을 검토한 모든 항소법원이 일관되게 지지함.

## 검증되지 않은 단일 판결 주장 (Untested / Single-Opinion)
- 주장 Y: 하급심 1건에서만 제시되었으며, 상급심 검증 이력 없음. 인용 시 주의 필요.
```

잘못된 대안들:

- 약한 주장을 아무 설명 없이 부록으로 치우기 → 왜 부록인지 알 수 없어 오히려 오해를 유발
- 각주 번호만 붙이고 서술의 확신 수준은 그대로 두기 → 독자는 여전히 같은 무게로 읽음
- 둘 다 "법원들이 시사한 바 있다" 같은 동일한 완곡 표현(hedging language)으로 통일
  → 강한 근거의 신뢰도를 인위적으로 깎아내리는 반대 방향의 왜곡

원칙: **평평하게 만드는 것(flattening)은 중립이 아니라 왜곡입니다. 차이가 있으면 차이가 보이게 써야 합니다.**

## 3.5 상충하는 결과 처리

### 3.5.1 서브에이전트의 역할은 판단이 아니라 보고

서브에이전트가 서로 모순되는 데이터를 발견했을 때(예: 같은 분기 영업비용이 두 스프레드시트에서 다름),
서브에이전트가 해야 할 일은 **판단이 아니라 보고**입니다.

**옳은 처리:**
```
영업비용 (2024 Q2)
  - 값 A: 1,240,000 (출처: FY24_ops_final.xlsx, 시트 "Summary")
  - 값 B: 1,187,500 (출처: Q2_close_v3.xlsx, 시트 "Actuals")
  - 상태: 불일치. 조정(reconciliation)은 코디네이터가 수행할 것.
```

**하면 안 되는 일:**

- **누락(omit)** — 불일치한다는 이유로 항목을 빼면, 상위 단계는 문제가 있다는 사실조차 모릅니다. 가장 나쁜 선택.
- **자체 재계산(recompute from first principles)** — 서브에이전트에게 부여되지 않은 권한 행사. 환각과 왜곡의 원천.
- **파일 수정 시각(timestamp)만 보고 한쪽 버리기** — 검증되지 않은 가정.
  최근에 열어 저장만 한 파일이 최신 수치라는 보장은 없습니다.

여기 깔린 원칙이 **관심사의 분리(separation of concerns)** 입니다.

> 서브에이전트: 수집 · 1차 분석 · 출처 기록 · **투명한 보고**
> 코디네이터: 조정(reconciliation) · 우선순위 결정 · 최종 종합

**침묵으로 문제를 숨기지 말고, 불확실성을 위로 올려라(surface uncertainty upward).**

### 3.5.2 코디네이터의 충돌 처리: 병렬 제시 + 출처 명기 + 충돌 사실 명시

서로 다른 서브에이전트가 같은 항목에 대해 다른 값을 가져오는 일은 흔합니다.

- 서브에이전트 1: 보도자료 인용 → 연매출 $420M
- 서브에이전트 2: 애널리스트 리포트 인용 → 연매출 $460M
- 두 출처 모두 신뢰할 만함

이때 합성 에이전트가 해서는 **안 되는** 일:

- 한쪽을 임의로 골라 채택하고 다른 쪽을 숨기기 → 편향과 정보 은폐.
  "애널리스트가 항상 더 엄밀하다", "회사 발표가 항상 더 정확하다"는 일반 규칙은 성립하지 않습니다.
- 두 값을 평균 내어 $440M으로 제시하기 → **어떤 출처에도 존재하지 않는 숫자를 창작하는 것**입니다.
  이것은 데이터 왜곡이자 환각의 일종이며, 단일 숫자로 보이기 때문에 더 위험합니다.

**올바른 처리:**

> 연매출 추정치는 출처에 따라 상이함:
> - $420M — 회사 보도자료(2026-01-14)
> - $460M — XYZ증권 애널리스트 리포트(2026-02-02)
>
> 두 수치는 서로 상충하며, 회계 기준 또는 집계 범위 차이일 가능성이 있음.

원칙: **불확실성은 해소된 척 감추는 것이 아니라, 사용자에게 그대로 전달되어야 합니다.**
판단에 필요한 정보를 가진 것은 최종 의사결정자입니다.

### 3.5.3 "소수 의견"이 사실은 다른 시점의 정당한 데이터인 경우

사례: 서브에이전트 5개가 같은 회사의 서로 다른 규제 제출 서류를 검토.
4개는 "부채비율 안정적"이라고 보고, 1개는 **다른 회계 분기의 서류를 사용해서** 훨씬 높은 비율을 보고.

여기서 그 1개는 **이상치(outlier)가 아닙니다.** 시점(fiscal quarter)이 다른, 별개의 정당한 데이터 포인트입니다.

올바른 처리: **안정적 비율은 여러 출처로 잘 뒷받침되는 값으로 제시하고,
높은 비율은 시점이 명시된 별개의 데이터 포인트로 함께 제시한다.**

```markdown
- 부채비율: 1.2 (FY2025 Q1~Q3 제출서류 4건에서 일관되게 확인)
- 참고: FY2024 Q2 제출서류에서는 2.8로 보고됨 (분기가 다름, 폐기하지 않고 별도 표기)
```

**잘못된 처리들**:

- **5개 값의 평균 내기**: 서로 다른 시점의 데이터를 평균 내면 존재한 적 없는 숫자가 만들어집니다.
- **높은 값을 최신이라고 추정해서 채택**: 근거 없는 추정입니다.
- **다수결로 소수 의견을 잡음으로 폐기**: 실제로는 유효한 다른 시점 정보를 버리는 것입니다.

## 3.6 종합 시 흔한 실패 정리

| 실패 | 무엇이 문제인가 | 올바른 대응 |
|---|---|---|
| 서로 다른 값을 **평균 내기** | 어떤 출처에도 존재하지 않는 숫자를 창작 = 환각. 단일 숫자로 보여 더 위험 | 병렬 제시 + 출처·시점 명기 |
| **다수결로 소수 의견 폐기** | 다른 시점·다른 정의의 유효한 데이터를 잡음 취급 | 잘 뒷받침된 값 + 별개 데이터 포인트로 병기 |
| **한쪽을 임의 채택하고 은폐** | 편향, 정보 은폐. "출처 유형별 우열" 같은 일반 규칙은 없음 | 충돌 사실 자체를 명시 |
| **가장 큰 값 / 최신처럼 보이는 값 고르기** | 정확성과 무관한 편향 규칙, 근거 없는 추정 | 메타데이터(발행일·방법론)로 판단, 불가하면 병기 |
| 불일치 항목 **누락** | 상위 단계가 문제 존재조차 모름. 최악 | 불확실성을 위로 올린다 |
| 서브에이전트의 **자체 재계산** | 부여되지 않은 권한 행사, 환각의 원천 | 보고만 하고 조정은 코디네이터 |
| **간결한 통합 요약만 지시** | source/date/agent 메타데이터 소실 → 검증 불가능한 산문 | carry forward를 프롬프트에 명시 |
| **문체 격식화 / 더 짧게 / 일반 면책 조항 추가** | 추적성 문제를 전혀 해결하지 못함, 짧게 만들면 손실 심화 | 각 주장 옆에 실제 메타데이터 부착 |
| **증거 강도 평평화(flattening)** | 강한 근거와 약한 근거가 같은 무게로 읽힘 | 섹션 분리 + 서술 방식 차등 |
| 약한 주장을 **설명 없이 부록으로** | 왜 부록인지 몰라 오해 유발 | 근거 수준을 라벨로 명시 |
| **동일한 완곡 표현으로 통일** | 강한 근거의 신뢰도를 인위적으로 깎는 반대 방향 왜곡 | 확신 수준을 서술에 반영 |
| **출처를 "에이전트 이름"으로 적기** | 그 에이전트는 이미 종료, 재질의 불가. 출처는 문서다 | 문서/URL + 발췌문 |
| **자기 신뢰도 점수만 첨부** | 검증되지 않은 자기 평가, 원문 근거 없음 | 발췌문 기반 인용 근거 |
| **먼저 도착한 결과만 채택** | 도착 순서는 중요도와 무관, 정보 유실 | 전부 수집 후 구조화 비교 |

핵심 한 줄: **종합은 정보를 매끄럽게 지우는 작업이 아니라, 출처와 차이를 보존한 채 하나로 배열하는 작업이다.**
