# 4. 워크플로: Plan 모드 · 테스트 주도 반복 · 피드백

## 이 장에서 다루는 것

- **작업 규모에 맞는 방식 고르기** — 직접 실행 / 플랜 모드 / 서브에이전트 위임 / 인터뷰(AskUserQuestion) / 세션 분리
- **Plan 모드 vs 직접 실행** — 정의, 존재 이유, 판단 기준, 판단 기준이 *아닌* 것들, 흔한 오해
- **테스트 주도 반복(TDD)** — AI 에이전트와 결합했을 때의 메커니즘, 레이트 리미터 예제, 열등한 대안들
- **피드백을 구조화해 전달하는 법** — 결합도 기반 그룹핑, 테스트 실패 보고 루프, 피해야 할 패턴들

---

## 1. 작업 규모에 맞는 방식 고르기

Claude Code에서 같은 일을 하는 방법은 여러 가지입니다. 핵심은 **작업 규모와 절차의 무게를 맞추는 것**입니다.
절차 자체에도 비용이 있습니다 — 계획 수립, 탐색, 승인 대기, 세션 분리는 모두 시간과 토큰을 씁니다.
한 줄 고치는 데 다단계 계획을 세우는 것은 순수한 낭비입니다.

> **원칙:** 절차의 무게는 **작업의 불확실성과 되돌리기 비용**에 비례해야 합니다.

### 1.1 네 가지 방식

#### (a) 직접 실행 (Direct Execution)

별도 계획·위임 없이 그냥 시키는 것. "이 파일 이 함수에 null 체크 추가해줘."

**언제:**
- 원인이 이미 특정됨 (예: 스택 트레이스가 파일·함수·줄을 정확히 가리킴)
- 범위가 단일 파일 / 소수 파일
- 수정 내용이 자명함 (한 줄 조건문 추가 등)
- 대상 코드와 주변 파일이 이미 팀에게 잘 파악되어 있음
- 요구사항에 모호함이 없음 (well-scoped requirement)

예: "이 폼 검증 함수에 만료일이 오늘보다 이전이면 거부하는 검사를 추가해줘."
→ 함수 하나, 요구사항 명확, 파일 이해됨 → 곧바로 실행하는 것이 가장 빠르고 효율적입니다.

#### (b) 플랜 모드 (Plan Mode)

큰 설계 결정이 필요할 때. 자세한 내용은 2절.

#### (c) 서브에이전트 위임 (Subagent Delegation)

별도의 격리된 AI 인스턴스를 띄워 하위 작업을 시키고, **결과 요약만** 메인 대화로 가져오는 것.
`Explore`가 대표적인 읽기 전용 탐색 에이전트입니다.

**왜 있는가 — 컨텍스트 오염 방지.** "이 기능이 어디에 구현돼 있지?"를 알아내려고 파일 50개를 뒤지면
그 50개 파일 내용이 전부 메인 대화 컨텍스트를 잡아먹습니다. 서브에이전트에게 시키면 서브에이전트
쪽에서만 그 50개를 읽고, 메인에는 "여기 있습니다: src/foo.ts:120" 한 줄만 돌아옵니다.

**적합한 경우:** 어디를 봐야 할지 모르는 광범위한 탐색, 여러 독립 조사를 병렬로 돌릴 때,
중간 과정의 파일 내용이 아니라 결론만 필요할 때.

**부적합한 경우:** 이미 위치와 원인을 아는 작업. 탐색할 게 없는데 탐색 에이전트를 부르는 것은
순수한 오버헤드입니다.

##### 서브에이전트의 컨텍스트 격리 (매우 중요)

서브에이전트는 **메인 대화의 히스토리를 물려받지 않습니다.** 독립된 컨텍스트에서 새로 시작합니다.
이건 버그가 아니라 설계 의도입니다 — 메인 컨텍스트를 아끼기 위한 것입니다.

따라서 아래와 같은 스킬 본문은 실패합니다.

```markdown
<!-- .claude/skills/migration-plan/SKILL.md -->
---
name: migration-plan
description: 결제 서비스 마이그레이션 계획을 작성한다
---

우리가 앞서 논의했던 방식대로 결제 서비스를 옮기는 계획을 세워라.
```

"우리가 앞서 논의했던(we discussed)"은 메인 대화에만 존재합니다. 서브에이전트는 그 대화를 본 적이
없으므로 참조할 게 없어 **일반론적이고 쓸모없는 계획**을 내놓습니다.

**올바른 작성법:** 필요한 구체적 정보를 스킬 본문 안에 직접 다 적거나, 파일 경로로 명시해
서브에이전트가 스스로 읽게 합니다.

```markdown
결제 서비스를 모놀리스에서 분리하는 계획을 세워라.

합의된 제약:
- Strangler Fig 패턴 사용, 빅뱅 전환 금지
- 기존 `/api/v1/billing/*` 엔드포인트는 6개월간 프록시로 유지
- 데이터는 이중 쓰기(dual-write) 후 검증 → 읽기 전환 순서
- 상세 현황은 `docs/billing-architecture.md` 를 읽고 반영할 것
```

참고로, 서브에이전트가 결과 텍스트를 메인 대화로 반환하지 못한다는 건 사실이 아닙니다. 정상적으로
반환합니다. 그리고 `arguments` 같은 필드가 없다고 본문이 무시되지도 않습니다.

#### (d) `AskUserQuestion` — 대화형 요구사항 도출

Claude가 사용자에게 구조화된 선택형 질문을 던져 답을 받는 도구입니다. 방향을 뒤집어, Claude가
사용자를 **인터뷰**할 수 있게 해 줍니다.

**왜 필요한가:** 익숙하지 않은 도메인에서는 사용자 자신도 무엇을 결정해야 하는지 모릅니다.
예를 들어 실시간 협업 문서 편집기를 처음 만든다면 다음 같은 질문들이 사전에 떠오르지 않습니다.

- **캐시 무효화(cache invalidation) 전략**: 여러 클라이언트가 같은 문서를 캐싱하고 있을 때, 변경이 생기면 낡은 캐시를 언제 어떻게 버릴 것인가. 무효화 시점을 잘못 잡으면 사용자가 남의 편집을 못 보거나, 반대로 캐시가 무의미해집니다.
- **충돌 해결(conflict resolution) 접근**: 두 사용자가 같은 문단을 동시에 고칠 때 어떻게 병합할 것인가. OT(Operational Transformation), CRDT, last-write-wins 등 서로 다른 복잡도와 보장을 갖는 선택지들이 있으며, 이 선택은 시스템 전체 구조를 결정합니다.
- **실패 처리(failure handling)**: 네트워크가 끊겼을 때 오프라인 편집을 허용할지, 재연결 시 어떻게 동기화할지, 서버가 죽으면 편집 내용이 어디까지 보존되는지.

이런 항목은 **구현 전에 표면화(surface)** 되어야 합니다. 구현 후에 발견하면 아키텍처를 갈아엎어야
하기 때문입니다.

**올바른 기법:** 기능을 간단히 설명한 뒤, Claude에게 `AskUserQuestion`으로 나를 인터뷰하면서
기술적 구현, 엣지 케이스, 트레이드오프를 함께 탐색한 다음 명세서(spec)를 쓰게 합니다.
도메인 패턴을 아는 쪽(Claude)이 질문하고, 결정권과 맥락을 가진 쪽(아키텍트)이 답하는 구조입니다.
지식과 권한이 분리되어 있을 때 가장 효율적인 형태입니다.

**대안들이 부적합한 이유:**

| 대안 | 왜 안 되는가 |
|---|---|
| 오픈소스 프로젝트 아키텍처를 그대로 복제 | 그 프로젝트의 전제 조건이 내 요구사항과 같다는 보장이 없고, 디자인 패턴을 따른다고 내 프로젝트 고유의 숨은 고려사항이 드러나지도 않음 |
| 아키텍트가 혼자 완전한 명세서를 먼저 작성 | 목표가 "본인이 모르는 것을 발견한다"인데 혼자 쓰면 아는 것만 쓰게 되어 목표와 정면 모순. 상호작용의 이점도 사라짐 |
| 일단 최소 구현을 하고 버그로 발견 | 사전 설계로 리스크를 예방하려는 요구와 정반대. 발견 시점이 가장 비싼 시점으로 미뤄짐 |

#### (e) 다단계 계획 / 세션 분리

리서치 세션과 구현 세션을 나누는 방식. 정말 큰 프로젝트에서만 의미가 있고, 작은 수정에 적용하면
순전한 관료주의입니다.

### 1.2 규모 매칭 원칙 요약

```
변경 범위 작음 + 원인 명확        → 직접 실행
변경 범위 큼   + 선택지 여럿      → 계획 모드
탐색 범위 큼   + 위치 모름        → 서브에이전트 위임
요구사항 자체가 불명확            → 인터뷰(AskUserQuestion)
```

| 작업 성격 | 적절한 방식 |
|---|---|
| 명확하고 국소적인 변경, 코드 이미 파악됨 | 직접 실행 |
| 다중 파일에 걸친 재구조화, 되돌리기 비용 큼 | 계획 모드 → 승인 → 편집 모드 전환 |
| 어디에 있는지 모르는 것을 광범위하게 조사 | 서브에이전트 위임 |
| 요구사항 자체가 불명확한 미지의 도메인 | 인터뷰(AskUserQuestion) |

### 1.3 과잉 대응(over-engineering)의 전형

잘 아는 단일 함수 하나를 고치는 상황에서:

- `Explore` 서브에이전트를 붙여 저장소 전체의 날짜 처리 함수를 목록화한다 → 이미 파악된 코드에 불필요한 탐색 비용.
- 계획 모드에 들어가 다른 검증 함수들까지 재구조화할지 검토한다 → 요청 범위를 벗어난 확장.
- 한 함수 변경을 전 애플리케이션 폼을 아우르는 다단계 마이그레이션 계획으로 취급한다 → 명백한 과장.

## 2. Plan 모드 vs 직접 실행

### 2.1 두 모드의 정의

- **플랜 모드(Plan Mode)**: Claude가 코드를 수정하지 않고 **읽기와 검색만 하면서** 코드베이스를 조사한 뒤, "무엇을 어떻게 바꿀 것인지" 실행 계획을 제시하고 **사용자 승인을 받는** 읽기 전용 모드입니다. 승인 전까지는 파일이 변경되지 않습니다. Claude Code에서는 보통 **Shift+Tab**으로 모드를 전환합니다.
- **직접 실행(Direct Execution)**: Claude가 요청받자마자 곧바로 파일을 편집하고 명령을 실행하는 일반 모드입니다.

### 2.2 왜 존재하는가

**되돌리기 비용.** 잘못된 전제로 시작한 대규모 변경은 되돌리는 비용이 큽니다. 예컨대 12개 서비스가
함께 쓰는 공유 유틸리티 패키지를 재구조화한다면, 잘못된 설계로 전부 뜯어고친 뒤 되돌리는 것은
재앙입니다. 계획 모드는 실제 편집 전에 사람이 설계를 검토하고 합의할 지점을 만들어 줍니다.

핵심 가치는 두 가지입니다.

1. **안전성** — 계획 단계에서는 파일이 바뀌지 않으므로 마음껏 조사해도 위험이 없습니다.
2. **일관성** — 작업을 시작하기 **전에** 하나의 표준 패턴을 확정할 수 있습니다.

### 2.3 일관성 문제는 왜 생기는가 (핵심 메커니즘)

Claude는 컨텍스트에 있는 것을 근거로 판단합니다. 사전 조사 없이 곧바로 파일 1번부터 고치기
시작하면 이런 일이 벌어집니다.

- 파일 1~10을 볼 때는 A 패턴이 자연스러워 보여서 A 방식으로 변환합니다.
- 작업이 진행되며 컨텍스트가 바뀌고, 파일 40~60에서 다른 형태의 코드를 만나 B 방식이 더 자연스럽다고 판단합니다.
- 결과: **한 마이그레이션 안에서 앞부분과 뒷부분이 서로 호환되지 않는 두 패턴으로 갈립니다.**
- 이를 맞추기 위해 전체를 다시 훑는 **2차 작업(second pass)** 이 강제됩니다.

이 불일치의 근본 원인은 "모델이 나쁘다"가 아니라 **작업 시작 전에 하나의 패턴을 확정하지 않았다**는
절차상의 결정입니다. 플랜 모드에서 먼저 전수 조사를 하면 "이런 호출 패턴이 3종류 있고, 각각의
대체 관용구는 이것이다"를 미리 못 박을 수 있습니다.

### 2.4 표준 흐름 — 계획 후 편집 모드로 전환

1. 계획 모드로 들어간다.
2. Claude가 조사하고 계획을 제시한다.
3. 사용자가 계획을 검토한다.
4. **계획을 승인하고, 세션을 편집 모드(editing mode)로 전환하는 옵션을 선택한다.**
5. Claude가 승인된 계획대로 곧바로 파일 수정을 진행한다.

```
[플랜 모드] 대안 비교 · 트레이드오프 분석 · 전략 확정
        ↓  승인 → 플랜 모드 종료
[직접 실행] 확정된 변경을 적용
```

4번이 핵심입니다. 승인 시점에 제시되는 선택지 중 편집을 허용하는 모드로 전환하는 것을 고르면,
**이미 합의된 설계가 컨텍스트에 그대로 살아 있는 상태로** 구현이 이어집니다. 각 파일 편집의 근거를
다시 설명할 필요가 없고, 지연 없이 구현 단계로 넘어갑니다. 계획 후 실행으로 전환하는 것 자체는
지극히 정상적이며 권장되는 흐름입니다.

**피해야 할 대안들:**

| 대안 | 왜 안 되는가 |
|---|---|
| 계획 모드에 무기한 머무르기 | 편집이 절대 일어나지 않고 채팅으로 설명만 반복됨. 계획 모드는 정의상 코드를 수정하지 않는 모드 |
| 새 세션을 처음부터 시작해 전부 다시 설명 | 이미 완성된 계획과 축적된 컨텍스트를 버리는 순수한 중복 작업 |
| 승인 없이 종료하고 손으로 직접 작업 | 자동화의 이점을 통째로 포기하는 비효율적 선택 |

### 2.5 판단 기준 (이것이 핵심)

Plan mode는 공짜가 아닙니다. 탐색·계획·검토 단계만큼 **시간과 토큰을 소비**합니다. 따라서
"언제나 안전하니까 항상 쓰자"는 잘못된 판단이며 오버헤드를 만듭니다.

**판단 축 = 범위(scope) × 모호성(ambiguity) × 파급효과(blast radius)**

| Plan 모드가 적합한 신호 | 직접 실행이 적합한 신호 |
|---|---|
| 여러 파일 / 여러 모듈에 걸친 변경 (예: 5개 서비스 엔트리 포인트 수정) | 변경이 단일 파일 / 소수 파일에 국한 |
| 아키텍처적 결정이 필요함, 실질적 기술 선택·트레이드오프 존재 (경쟁하는 두 라이브러리 중 택일) | 명확한 단일 구현 경로가 있음 (특히 같은 파일 내 기존 패턴을 그대로 따르는 경우) |
| 구현 경로가 여러 개이거나 모호함 | 다른 모듈에 영향이 없음 |
| **아직 결정되지 않은(open) 설계 사안**이 남아 있음 | 미결 설계 사안이 없음 |
| 파급 효과(side effect)를 사전에 파악해야 함 | 계획 비용이 작업 자체보다 큰 경우 |
| 핵심 시스템 동작을 직접 건드림 (세션 처리 로직, 토큰 저장 방식) | 오탈자 수정 등 자명한 변경 |
| 낯선 코드베이스 구조를 먼저 파악해야 할 때 | 이미 결정이 끝났고 변경이 작고 국소적 |
| 되돌리기 어려운 작업(마이그레이션, 대규모 리팩터링) | 비대화형(CI 등) 환경 + 완전 명세된 작업 |

**플랜 모드를 써야 할 대표 사례**

- **다중 파일 마이그레이션/리팩터링.** 예: 60개 파일에서 ORM 라이브러리를 교체하는데, 호출 지점마다 쿼리 패턴이 제각각이고 패턴별로 올바른 대체 관용구가 다르다. → 먼저 패턴을 전부 조사·분류하고 마이그레이션 방식을 초안으로 작성한 뒤, 승인받고 플랜 모드를 나가 실행한다.
- **아키텍처 선택이 아직 안 끝났을 때.** 예: 새 결제 연동을 (a) 메시지 큐 + 비동기 워커 방식으로 갈지, (b) 기존 서비스에서 동기 호출 + 재시도 로직으로 갈지 미정이다. 각각 인프라와 운영상의 트레이드오프가 다르다. → 구현 전에 플랜 모드로 양쪽을 탐색하고 트레이드오프를 드러내게 한 뒤 결정한다.
- **여러 설계 대안 비교** (예: 캐싱 전략 3가지 중 택일).

**직접 실행 대표 사례**

- "`config/server.yaml`의 `timeout: 30`을 `timeout: 60`으로 바꿔라." 탐색할 것도, 설계 선택지도 없습니다. 특히 CI 같은 **비대화형(non-interactive)** 환경에서는 사람이 중간에 승인해 줄 수 없으므로, 이런 완전 명세된 작업은 직접 실행이 정답입니다.
- 한 모듈 안의 내부 헬퍼 함수 하나의 이름을 바꾸고, 그 호출 지점 몇 개를 고친다. 호출 지점이 전부 지금 열려 있는 파일 안에서 눈으로 확인된다.

플랜 모드가 정당하게 생략되는 조건은 하나로 요약됩니다:
**변경의 전체 범위가 이미 알려져 있고, 탐색하거나 설계 결정할 것이 남아 있지 않을 때.**

### 2.6 판단 기준이 **아닌** 것들 (오해 모음)

- **누가 코드를 썼는가** — 기존 패턴을 다른 엔지니어가 작성했다는 사실은 인적 요소일 뿐 기술적 판단 기준이 아닙니다.
- **"최근에 작성된 코드니까 검토 없이 맞다고 가정한다"** — 생략의 근거가 아닙니다. 코드의 나이는 정확성의 보증이 아닙니다.
- **요청 문장의 길이** — 한 문장으로 설명된다고 범위가 작은 것이 아닙니다. "인증을 OAuth로 바꿔줘"는 짧지만 수십 파일을 건드립니다. 실제로 몇 개 모듈을 만지게 되는지가 기준입니다.
- **"요구사항이 다 적혀 있으면 직접 실행해도 된다"** — 요구사항 기술의 명확성과 작업의 구조적 복잡성은 별개입니다. 다중 파일 + 아키텍처 결정이 걸려 있으면 여전히 계획이 필요합니다.
- **비즈니스 중요도만으로** — 결제·체크아웃 모듈이 중요하다는 이유로 사소한 변경까지 항상 동일한 고정 프로세스를 강제하면 불필요한 오버헤드입니다. 중요도는 리뷰 강도의 근거는 되어도, 계획 단계 필요 여부의 자동 기준은 아닙니다.
- **"인증/보안 코드는 정책상 항상 플랜 모드"** — 그런 무조건적 정책 규칙은 없습니다. 인증 작업이 플랜 모드에 적합한 이유는 주제가 "보안"이라서가 아니라 대개 다중 파일 + 핵심 동작 변경이라는 **구조적 특성** 때문입니다.
- **"모든 설정 파일 변경에는 Plan 모드가 필수"** — 그런 규칙은 존재하지 않습니다. 값 하나 바꾸는 작업에 승인 대기를 넣으면 파이프라인만 막고 얻는 것이 없습니다.
- **"DB 스키마를 건드리면 무조건 플랜 모드"** — 사실이 아닙니다. *한 테이블에 nullable 컬럼 하나 추가 + 이를 읽는 모델 파일 하나 수정, 다른 파일 영향 없음, 남은 설계 결정 없음*이라면 명백히 직접 실행 대상입니다. 반대로 "테이블을 쪼갤지 말지 아직 안 정했다"면 미결 사안이 있으므로 플랜 모드입니다.
- **"스키마 변경은 플랜 모드도 직접 실행도 건너뛰고 마이그레이션 툴로 직행"** — 그런 규칙은 없습니다. 마이그레이션 파일 작성도 결국 코드 작업입니다.
- **"직접 실행은 한 번에 한 파일만 수정 가능"** — 사실이 아닙니다. 직접 실행도 여러 파일을 수정할 수 있습니다. 플랜 모드는 기술적 제약이 아니라 안전성과 체계성을 위한 선택입니다.
- **"이름 변경에는 플랜 모드를 쓸 수 없다"** — 사실이 아닙니다. 저장소 전체에 걸친 대규모 이름 변경이라면 플랜 모드가 오히려 유용합니다.
- **"이름 변경은 호출 지점 검증이 전혀 필요 없고 위험도가 0이다"** — 사실이 아닙니다. 호출 지점 검증은 항상 필요합니다. 앞의 헬퍼 함수 예시가 안전한 이유는 그 검증이 **이미 눈앞에서 끝나 있기 때문**이지, 이름 변경이 본질적으로 안전해서가 아닙니다.

### 2.7 좋은 워크플로와 나쁜 워크플로

**좋은 패턴**

- 플랜 모드로 탐색 → 계획 승인 → 플랜 모드 종료 → 승인된 계획을 직접 실행.
- 탐색 전용 서브에이전트(Explore)로 코드베이스 전반의 사용 패턴 목록을 먼저 만들기.
- 마이그레이션 범위를 **하나의 라이브러리로 좁히기.** 무관한 프레임워크 업그레이드를 같은 작업에 섞으면 실패 원인 파악이 어려워집니다. 범위를 좁히는 것은 위험 감소 기법입니다.

**나쁜 패턴**

- 첫 번째 파일에서 본 대체 관용구를 나머지 전부에 확인 없이 일괄 적용.
- 조사를 생략한 채 한 번에 전부 고쳐 놓고 테스트 스위트가 잡아 주기를 기대. (60개 파일 규모에서는 회귀 버그와 수동 수정이 폭증합니다. **테스트는 안전망이지 설계 대체재가 아닙니다.**)
- 사전 평가 없이 두 아키텍처를 **둘 다 끝까지 구현**해서 PR로 비교. (계획 단계 비교로 충분히 결정할 수 있는 것을 두 배의 시간·토큰으로 사는 낭비. "세 전략을 전부 구현해 보고 두 개를 지운다"도 같은 문제입니다.)
- 비교 자체를 건너뛰고 바로 구현 — 사전 분석 요구를 무시하는 것.
- 아직 결정되지 않은 아키텍처를 "인프라 작업이 더 중요하니까" 같은 근거 없는 규칙으로 임의 확정.
- 파일 생성 개수 같은 피상적 지표만으로 기술 아키텍처를 선택.
- 두 모드의 목적을 뒤집기: 비교 분석을 직접 실행으로, 확정된 소규모 수정을 플랜 모드로.

## 3. 테스트 주도 반복 (Test-Driven Iteration)

### 3.1 TDD 기본

**TDD(Test-Driven Development)** 는 "테스트를 먼저 쓰고, 그 테스트를 통과시키는 코드를 나중에 쓴다"는
개발 방식입니다.

순서: **실패하는 테스트 작성 → 최소 구현 → 테스트 통과 → 리팩터링**

1. 원하는 동작을 검증하는 테스트를 작성한다 (당연히 실패한다).
2. 그 테스트를 통과시키는 최소 구현을 작성한다.
3. 테스트가 통과할 때까지 다듬는다.

### 3.2 왜 AI 에이전트와 특히 잘 맞는가

AI에게 "레이트 리미터 만들어줘"라고만 하면 AI는 **요구사항을 추측**합니다. 초당 몇 개? 버스트는
허용? 윈도우 리셋은 언제? 추측이 틀리면 사람이 보고 지적하고, 다시 고치고 — 이
**수정 주기(correction cycle)** 가 반복됩니다.

테스트를 먼저 쓰면:

- 요구사항이 **실행 가능한 명세**로 고정됩니다. 자연어 설명은 해석이 흔들리지만, **테스트 코드는 모호하지 않은 기계 검증 가능한 명세**입니다.
- AI가 **스스로 채점**할 수 있습니다 (테스트 돌려보고 실패하면 자기가 고침).
- 테스트 실패 메시지는 **자동으로 생성되는 정확한 피드백**입니다. 사람이 "이거 틀렸어"라고 매번 설명할 필요 없이 **실패 출력을 그대로 붙여넣으면** 됩니다.

결과적으로 사람이 개입하는 수정 주기 횟수가 크게 줄어듭니다. 이것이 TDD가 수정 주기를 줄이는
핵심 메커니즘입니다.

### 3.3 구체적 예 — 레이트 리미터(rate limiter)

내부 API용 속도 제한기를 만든다고 합시다. 테스트가 다뤄야 할 축은 셋입니다.

- **스로틀링 동작(throttle)**: 정해진 시간당 요청 수를 넘으면 거부/지연시키는가 (예: HTTP 429)
- **버스트 제한(burst limit)**: 순간적으로 몰린 요청을 몇 개까지 허용하는가
- **리셋 타이밍(reset window)**: 카운터가 초기화되어 다시 허용되는 시간 구간은 언제인가

권장 흐름:

1. Claude에게 **먼저 테스트 스위트를 작성**하게 한다 — 스로틀 동작, 버스트 제한, 리셋 타이밍을 모두 커버.
2. 그 다음 rate limiter 구현을 요청한다.
3. 테스트를 실행하고, **실패 결과를 그대로 공유하며 반복(iterate)** 한다.

```python
def test_allows_up_to_limit():
    rl = RateLimiter(limit=5, window=1.0)
    assert all(rl.allow("user1") for _ in range(5))

def test_blocks_over_limit():
    rl = RateLimiter(limit=5, window=1.0)
    for _ in range(5):
        rl.allow("user1")
    assert not rl.allow("user1")

def test_resets_after_window():
    rl = RateLimiter(limit=5, window=1.0)
    for _ in range(5):
        rl.allow("user1")
    time.sleep(1.1)
    assert rl.allow("user1")
```

### 3.4 열등한 대안들과 그 이유

| 대안 | 왜 열등한가 |
|---|---|
| **설계 문서만 쓰고 구현** | 문서는 실행되지 않습니다. 구현이 문서를 따랐는지 검증할 자동 수단이 없어 수정 주기가 늘어납니다 |
| **구현 먼저, 테스트 나중(test-last)** | 이미 만들어진 동작을 사후 문서화할 뿐, 요구사항을 사전에 고정하지 못합니다. 잘못 구현된 동작도 그대로 "정답"으로 굳습니다. TDD가 아닙니다 |
| **터미널 수동 검증만** (curl로 몇 번 찔러보고 헤더 확인) | 반복 실행이 번거롭고, 재현성이 없으며, 회귀(regression)를 잡지 못합니다. 수정 주기 단축에 기여하지 않습니다 |

## 4. 피드백을 구조화해 전달하는 법

AI 에이전트는 **컨텍스트 안에서 인과관계를 추론**합니다. 그래서 무엇을 어떻게 묶어서 전달하느냐가
결과 품질을 바꿉니다.

### 4.1 기본 루프

```
① 요청 → ② Claude가 코드 작성 → ③ 테스트 실행 →
④ 실패 로그를 Claude에게 전달 → ⑤ 수정 → ⑥ 전체 테스트 재실행으로 검증
```

⑥이 중요합니다. **전체 스위트를 다시 돌려야** 수정이 다른 부분을 깨뜨리지 않았는지(회귀,
regression) 확인할 수 있습니다. 고친 테스트 하나만 돌리는 것은 부족합니다.

### 4.2 핵심 원칙 — 그룹 경계는 "기술적 의존 관계"를 따라 그린다

한마디로: **결합된 것은 묶고, 무관한 것은 분리한다.**

두 코드 조각이 같은 자원을 공유하거나 서로의 동작에 영향을 주면 **결합되어 있다(coupled)** 고
말합니다.

예: 재시도 백오프(retry backoff) 로직과 작업 잠금(job-locking) 로직이 **같은 타이머 인스턴스를
공유**한다면, 한쪽을 고치면 다른 쪽 동작이 바뀝니다.

- **retry backoff**: 실패한 작업을 재시도할 때 대기 시간을 점점 늘리는 기법.
- **job locking**: 같은 작업이 동시에 두 번 실행되지 않도록 잠그는 기법.
- 둘이 같은 타이머를 쓰면, 백오프 간격을 늘리는 순간 잠금 유효 시간도 함께 흔들립니다.

**결합된 문제들은 한 메시지에 함께, 결합 관계를 명시해서** 설명합니다. 모델이 두 로직의 상호작용을
한 번에 보고 근본 원인(공유 타이머)을 다룰 수 있게 하기 위함입니다.

**무관한 문제는 별도 항목으로 분리**해 전달합니다. 로그 레벨 한 단어를 고치는 일은 타이머와 아무
관계가 없습니다. 이것을 결합된 문제와 한 덩어리로 묶어 "분리 불가능한 하나의 변경"이라고 지시하면,
모델은 존재하지 않는 관계를 있다고 가정하고 엉뚱한 리팩터링을 할 수 있습니다.

### 4.3 케이스 A — 서로 무관한 버그들이 한꺼번에 나온 경우

세 개의 실패가 있고 각각 원인이 완전히 별개라고 합시다.

- 소수점 수량의 **반올림 오차(rounding error)**
- 반복문 경계의 **off-by-one 오류** — `<` 를 써야 하는데 `<=` 를 써서 마지막 요소를 한 번 더 돌거나 빠뜨리는 고전적 버그
- 단종 상품 필드에 대한 **null 체크 누락** — 값이 없을 수 있는 필드를 검사 없이 접근해 런타임 크래시로 이어짐

이 경우 **전체 테스트 출력을 한 메시지에 다 담아 주는 것**이 좋습니다.

- 모델이 함수 전체 구조를 한 번에 파악해 세 곳을 동시에 고칩니다.
- 대화 턴(turn)이 줄어들어 토큰과 시간이 절약됩니다.
- 뒤에 나올 정보를 감추면 모델은 반쪽 정보로 작업하고, 첫 수정이 나머지와 충돌할 수 있습니다.

다만 서로 무관한 결함이 **각각 다른 파일·다른 계층에 흩어져 있고 검증 단위도 다르다면**, 하나씩
순차 처리하는 편이 나을 수 있습니다. 예: ① 요약 합계의 **통화 서식(currency formatting) 불일치**,
② Windows 경로에서 **파일 확장자 누락**. 이 둘은 완전히 독립적이므로 각각 별도 메시지로 순차
처리해도 좋습니다. 그 이유는:

- AI가 한 번에 하나의 문제에만 집중 → 수정 정확도 상승
- 각 수정의 결과를 개별적으로 검증 가능 → 어떤 변경이 무엇을 고쳤는지 명확
- 여러 변경이 섞이면 회귀가 생겨도 원인 추적이 어려워짐

> 정리: 판단 축은 "한 번에 몇 개냐"가 아니라 **결합 여부**입니다. 무관한 것들을 한 메시지에 넣더라도
> **각각을 독립된 항목으로 명시**해야 하며, "이것들은 하나의 상호작용하는 결함"이라고 묶어서는 안 됩니다.

### 4.4 케이스 B — 연관된 버그와 무관한 버그가 섞인 경우

앞의 원칙은 "무조건 다 몰아서 주라"는 뜻이 아닙니다. 진짜 원칙은 **논리적 그룹핑(logical grouping)** 입니다.

예: 웹훅 수집 서비스에서 세 개가 실패.

1. 멱등성 키(idempotency key)로 중복 배달을 걸러내지 못함
2. 중복 제거 윈도우가 만료돼도 오래된 키가 해제되지 않음
3. 잘못된 JSON 페이로드에 400을 반환하지 않음

1번과 2번은 **같은 중복 제거 스토어(dedup store) 로직**에서 나옵니다. 3번은 파싱 계층의 별개 문제입니다.

→ **1·2번은 한 메시지에 묶어서**, 3번은 별도로 전달합니다.

- 묶는 이유: 같은 로직을 건드리는 두 문제를 따로 고치게 하면, 첫 수정이 두 번째 문제의 전제를 바꿔 재작업·충돌이 생깁니다. 함께 보면 스토어 설계를 한 번에 올바르게 잡습니다.
- 분리하는 이유: 무관한 문제를 섞으면 디버깅 범위가 흐려지고 모델이 억지로 공통 원인을 찾으려 합니다.

**관련 용어**

- **멱등성(idempotency)**: 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질. 웹훅은 네트워크 재시도로 중복 배달이 흔해서, 요청마다 고유한 **멱등성 키**를 붙이고 이미 처리한 키인지 저장소에서 확인합니다.
- **중복 제거 윈도우(dedup window)**: 멱등성 키를 영원히 저장할 수 없으므로 일정 시간(예: 24시간)만 보관하고 만료시킵니다.

### 4.5 피해야 할 패턴 모음

**(a) 과잉 결합(over-coupling) — 무관한 버그를 "하나의 상호작용하는 결함"으로 묶어 전달**
→ AI가 존재하지 않는 인과관계를 추론합니다. "통화 포맷터가 파일명 생성기에 영향을 준다"고 잘못
가정하고, 멀쩡한 공통 코드를 건드리는 식의 잘못된 수정이 나옵니다.

**(b) 원인 은폐(context stripping) — 증상만 나열하고 결합 관계를 빼먹기**
→ "재시도 백오프", "작업 잠금", "로그 레벨"이라고만 나열하고 **앞의 둘이 공유 타이머로 결합되어
있다는 사실**을 빼면, 모델은 각각을 독립 증상으로 보고 표면만 고칩니다. 근본 원인은 그대로 남습니다.

**(c) 일부 실패를 숨기고 나중으로 미루기**
→ 정보를 감출 이유가 없습니다. 알고 있는 결함은 전달하되 순서만 조절하면 됩니다. 숨기면 나중에
불필요한 왕복만 늘어납니다.

**(d) 불필요한 직렬화(sequential blocking)**
→ 사소한 수정을 먼저 처리하고 완료를 확인할 때까지 나머지 피드백을 미루는 것. 의존 관계가 없는
일을 순서로 묶을 이유가 없습니다.

**(e) 구체적 정보 없이 "알아서 심각한 것부터 고쳐" / "원인이 뭘 것 같아?"**
→ 정확한 증상(어떤 값이 기대되었고 실제로 무엇이 나왔는지)을 빼면 AI는 추측할 수밖에 없습니다.
근거 없는 추측은 **할루시네이션(hallucination, 그럴듯하지만 사실이 아닌 출력)** 을 유발합니다.
항상 실제 **에러 메시지, 스택 트레이스, 실패한 어서션의 기대값·실제값을 그대로 붙여넣으세요.**
이것이 가장 좋은 피드백입니다.

**(f) 결과 확정을 미루기**
→ 이미 명확한 실패 결과가 나왔다면, "플레이키(flaky, 간헐적 실패)인지 확인하려고 여러 번 더
돌려보고 나중에 보고" 하는 식으로 미루지 마세요. 진행만 지연됩니다.

### 4.6 좋은 피드백 메시지 형태 (예시)

```
전체 테스트 스위트를 돌린 결과입니다. 두 그룹으로 나눠 전달합니다.

[그룹 1 — 결합됨: dedup store 로직 공유]
FAILED test_webhook::test_duplicate_delivery_filtered
  expected: 1 processed event
  actual:   2 processed events
FAILED test_webhook::test_expired_key_released
  expected: key "evt_9f2" absent after 24h
  actual:   key still present
※ 두 테스트는 같은 dedup store를 씁니다. 만료 정책과 조회 경로가
   같은 자료구조를 공유하므로 함께 봐 주세요.

[그룹 2 — 위와 무관: JSON 파싱 계층]
FAILED test_webhook::test_malformed_payload_returns_400
  expected: 400
  actual:   500 (JSONDecodeError 미처리)
```

핵심은 세 가지입니다. **① 기대값과 실제값을 원문 그대로**, **② 그룹 경계를 기술적 의존 관계로**,
**③ 결합 관계는 말로 명시**.
