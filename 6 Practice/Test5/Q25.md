SCENARIO: You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

QUESTION: Your customer support agent calls get_customer once at the start of every session. The tool returns the complete customer profile, dozens of attributes including full address history, marketing preferences, and loyalty transaction records, although the agent only ever uses the customer ID, contact email, and account status. Telemetry shows that in long multi-issue sessions **the profile payload is resent as part of the message history on every request**, later requests carry **steadily larger input token counts**, and some sessions **approach the context window limit**. Which design change best addresses this while preserving the customer facts the agent needs?

**선택지**:

1. Reduce each get_customer result to the **few fields the session needs** before appending it to the message history => 정답
2. Mark the verbose profile payload with **cache_control** so its tokens are served from cache rather than occupying context on later turns
3. Summarize the full conversation **after every turn** so the **profile payload is compressed before the next** request is sent
4. **Increase max_tokens** on **every request** so the model can restate the customer fields it needs within each response

**설명**:
클로드는 요청할 때마다, 지금까지의 대화 전체를 다시 읽어들이는 구조이다.
수십 개의 프로필 정보가 모두 담긴 결과를 매번 보내면, 이게 계속 토큰 수를 늘리고, 결국 한계에 도달한다.

**문제 구분 포인트, 어려운 표현**:
- the message history on every request
- approach the context window limit
- few fields the session needs
