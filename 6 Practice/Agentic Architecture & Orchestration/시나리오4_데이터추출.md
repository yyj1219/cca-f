## 질문 1

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : A coordinator delegates reconciliation to a subagent with the prompt 'Reconcile the extracted invoice fields against the source document.' The output contains values matching neither the extractions nor the document. What change should you make?

**A.** Enforce a strict JSON output schema on the reconciliation subagent so its returned field values stay tied to real data.

**설명**

이 보기는 옳지 않다. 출력 스키마는 응답의 형태(shape)를 제약할 뿐 값의 사실적 근거(factual grounding)를 보장하지 않기 때문이다. 서브에이전트가 실제 추출 결과에 접근할 수 없는 상황이라면, 엄격하게 강제된 스키마라도 조작된 값으로 채워질 뿐이다.

**B.** Move the reconciliation subagent to a model tier with a larger context window so both inputs fit during processing.

**설명**

이 보기는 옳지 않다. 문제는 컨텍스트 용량이 문제가 되기도 전에 이미 발생한다. 추출 결과와 문서 자체가 서브에이전트의 컨텍스트에 전혀 전달되지 않았기 때문이다. 위임 프롬프트에 데이터 자체가 아니라 데이터에 대한 참조만 담겨 있다면, 컨텍스트 창이 더 크다고 해서 도움이 되지 않는다.

**C.** Instruct the subagent to read the extractions from the coordinator's conversation history before performing the reconciliation.

**설명**

이 보기는 옳지 않다. 서브에이전트는 코디네이터의 대화 히스토리에 어떤 형태로도 접근할 수 없으며, 지시를 내려도 이 사실은 바뀌지 않는다. 위임 프롬프트 문자열만이 경계를 넘어 전달되는 유일한 콘텐츠이므로, 다른 곳을 참조하라고 지시해도 서브에이전트가 찾을 수 있는 것은 아무것도 없다.

**D(정답).** Embed the complete extracted field values and the relevant source document content directly in the delegation prompt.

**설명**

이 보기가 정답이다. 서브에이전트는 코디네이터의 대화 히스토리를 물려받지 않는다. 서브에이전트의 컨텍스트에는 위임 프롬프트가 제공하는 내용만 존재한다. '추출된 인보이스 필드'라는 표현만 언급하고 실제 추출 결과와 문서 내용을 함께 담지 않은 프롬프트는 서브에이전트에게 대조할 실제 데이터를 아무것도 남기지 않는다. 따라서 전체 데이터를 프롬프트에 담아 전달하는 것이 이 실패를 해결하는 방법이다.

### 전반적인 설명

Claude Agent SDK에서 서브에이전트를 정의하는 핵심 속성은 컨텍스트 격리(context isolation)이다. 각 서브에이전트는 대화가 처음부터 새로 시작되는 별도의 에이전트 인스턴스이다. 부모의 히스토리를 물려받지 않으며, 코디네이터에서 서브에이전트로 넘어가는 유일한 콘텐츠는 위임 프롬프트 문자열 그 자체이다. 이 설계는 의도적인 것이다. 격리 덕분에 서브에이전트는 메인 대화를 오염시키지 않고도 방대한 자료를 탐색할 수 있으며, 병렬 위임도 저렴하게 수행할 수 있다. 그 대가로 컨텍스트 전달에 대한 책임 전체를 코디네이터가 지게 된다. '추출된 인보이스 필드'와 같은 표현은 서브에이전트의 세계 안에서는 지시 대상이 없는 포인터일 뿐이며, 능력 있는 모델이라도 근거로 삼을 수 없는 지시를 받으면 유창하고 그럴듯하지만 근거 없는 출력을 만들어낸다. 이것이 바로 여기서 관찰된 실패이다.

올바른 사고 모델은, 모든 위임에서 발견 사항이 명시적으로 전달되어야 한다는 것이다. 코디네이터는 전체 추출 출력(값과 메타데이터를 구분한 구조화된 데이터 형태가 이상적이다)과 관련 문서 내용을 대조(reconciliation) 프롬프트에 직접 담아야 한다. 다른 대안들은 이 점을 놓치고 있다. 서브에이전트에게 부모의 히스토리를 참조하라고 지시하는 방법은 작동할 수 없다. 요약본이든 원본이든 그 히스토리의 어떤 버전도 서브에이전트에게 보이지 않기 때문이다. 엄격한 JSON 스키마는 출력의 형태를 관리할 뿐 진실성을 관리하지 않는다. 조작된 값을 유효한 구조에 억지로 채워 넣을 뿐이다. 그리고 데이터가 애초에 컨텍스트에 들어가지 않았다면 컨텍스트 창의 크기는 무관하다. 서브에이전트 컨텍스트 격리가 작동하는 방식과, 서브에이전트가 필요로 하는 파일 경로·발견 사항·결정 사항을 Agent 도구의 프롬프트에 직접 포함해야 한다는 내용은 SDK의 Subagents 문서를 참고하라.

## 질문 2

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : The coordinator delegates section-level extraction to subagents and an assembly agent produces the final JSON. Outputs are always schema-valid, yet nullable fields are frequently null even though the source document contains those values. Which orchestration change fixes this?

**A.** Run every extraction subagent twice on each document and merge the two result sets, keeping whichever pass returned a non-null value for each output field.

**설명**

무작정 중복 실행하면 첫 번째 패스에 누락이 있었는지 여부와 무관하게 모든 문서에서 비용이 두 배가 되며, 두 번째 패스도 특정 누락 필드를 겨냥하지 않는다. 누락 탐지(gap detection) 없이는 반복 실행이 첫 번째 실행에서 놓친 부분을 실제로 찾아낸다는 보장도, 언제 멈춰야 하는지에 대한 신호도 없다.

**B(정답).** Have the coordinator detect null fields in the assembled output, re-delegate targeted extraction for them, and re-assemble until coverage is sufficient.

**설명**

이는 반복적 정제 루프(iterative refinement loop)를 구현한 것이다. 코디네이터가 조립된 결과를 커버리지 기준과 비교 평가하고, 비어 있는 필드에 대해서만 집중적인 후속 추출을 위임한 뒤, 출력이 기준을 충족할 때까지 조립을 다시 실행한다. 단순히 결함을 기록만 하는 것이 아니라 실제로 격차를 복구하며, 첫 번째 패스가 부족했던 부분에 노력을 집중시킨다.

**C.** Append a completeness score and a list of missing fields to each output so downstream consumers know which values were not captured.

**설명**

이는 결함을 측정만 하고 그대로 내보내는 방식이다. 복구 루프 없는 탐지는 널 값을 그대로 남겨두며, 원본 문서나 추출 서브에이전트에 접근할 수 없는 다운스트림 시스템에 시정 부담을 떠넘긴다.

**D.** Change the schema to mark the frequently null fields as required so the extraction subagents are forced to populate them on the first pass.

**설명**

필드를 필수(required)로 지정한다고 해서 근본 데이터를 더 쉽게 찾을 수 있게 되는 것은 아니다. 오히려 모델이 누락을 정직하게 보고할 방법을 없애는 셈이다. 필드가 필수인데 추출기가 값을 찾지 못했다면, 가능성이 높은 결과는 여전히 스키마를 통과하는 조작된 값이며, 이는 널 값보다 더 나쁘다.

### 전반적인 설명

이 문제가 검증하는 패턴은 반복적 정제 루프(때로는 evaluator-optimizer라고도 불린다)이다. 코디네이터는 처음 조립된 출력을 최종본으로 취급하지 않고, 명시적인 품질 기준에 대비해 평가한 뒤, 부족했던 부분에 대해 표적화된 작업을 재위임하고, 기준이 충족될 때까지 조립 단계를 다시 호출한다. 핵심 요소는 검증 가능한 '충분히 좋음'의 정의(여기서는 원본에 실제로 값이 있을 때 nullable 필드가 채워져 있어야 한다는 것), 출력을 그 정의와 비교하는 누락 탐지 단계, 그리고 후속 패스가 전체를 다시 하지 않고 구체적인 누락만을 공격하도록 하는 표적화된 재위임이다.

여기서의 사고 모델은 스키마 검증과 추출 커버리지가 서로 직교(orthogonal)한다는 것이다. JSON 스키마는 형태를 보장한다. 중괄호가 닫히고, 필수 필드가 존재하며, 타입이 일치한다. 하지만 nullable 필드가 실제로 값을 가져야 했는지에 대해서는 아무것도 말해주지 않는다. 그래서 이 시스템의 실패는 검증 과정에서는 보이지 않으며, 코디네이터가 직접 실행하는 평가 단계에서 잡아내야 한다. 서브에이전트가 격리된 컨텍스트에서 동작하기 때문에, 코디네이터만이 섹션 간 조립된 결과를 비교하고 해당 패스에 필요한 문서 컨텍스트를 담아 후속 추출을 위임할 수 있는 위치에 있다.

각 대안은 특징적인 방식으로 무너진다. 필드를 필수로 지정해 스키마를 더 엄격하게 만드는 것은 이미 알려진 안티패턴이다. 필드는 실제로 항상 존재하는 경우에만 필수로 지정해야 한다. 그렇지 않으면 모델은 스키마를 만족시키기 위해 값을 지어내는 경향을 보이며, 이는 탐지 가능한 널 값을 자신 있는 오답으로 바꿔버린다. 모든 서브에이전트를 두 번 실행하는 것은 무작정 중복이다. 누락이 없던 문서에도 두 배의 비용을 치르면서, 실제로 누락이 있던 필드는 전혀 겨냥하지 않는다. 완전성 리포트를 덧붙이는 것은 복구 없는 탐지이다. 관찰 가능성(observability) 자체는 가치가 있지만, 최종적으로 전달되는 출력 자체는 전혀 바뀌지 않는다.

evaluator-optimizer 워크플로에 대한 Anthropic의 가이드는 Building Effective Agents를, 코디네이터-서브에이전트 컨텍스트에 대해서는 Create custom subagents를 참고하라.

## 질문 3

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : The coordinator delegates three independent extraction passes (parties, financial terms, key dates) to dedicated subagents, dispatching one Task call per turn and waiting for each result. What change makes the passes run concurrently?

**A.** Merge the three specialized subagents into a single AgentDefinition that performs all extraction passes in one delegation.

**설명**

세 패스를 하나의 서브에이전트로 통합하면 전문화가 사라질 뿐 동시성이 생기지는 않는다. 단일 에이전트는 여전히 자기 컨텍스트 안에서 세 가지 추출을 하나씩 차례로 수행한다. 또한 세 작업의 출력을 모두 하나의 컨텍스트 창에 집중시키게 되는데, 이는 원래 분리를 통해 피하고자 했던 상황이다.

**B(정답).** Have the coordinator emit the three Task tool calls together in one response instead of one per turn.

**설명**

Claude는 하나의 응답에 여러 tool_use 블록을 포함할 수 있으며, 하니스는 이런 요청들을 동시에 실행할 수 있다. 세 개의 Task 호출을 코디네이터의 한 턴에 모두 내보내는 것이 병렬 서브에이전트 실행을 위해 문서화된 메커니즘이며, 이렇게 하면 세 개의 독립적인 패스가 가장 느린 패스 하나 정도의 시간 안에 끝난다.

**C.** Assign each extraction subagent a lower-latency model so every individual pass completes more quickly.

**설명**

더 빠른 모델은 각 패스의 소요 시간을 줄이지만 디스패치 패턴 자체는 바꾸지 못한다. 코디네이터는 여전히 턴마다 하나의 Task 호출만 내보내고 그 결과를 기다린다. 세 패스는 여전히 완전히 순차적이므로, 전체 지연 시간은 가장 느린 패스 하나의 시간이 아니라 세 패스 시간의 합이 된다.

**D.** Return each subagent's tool result in its own user message immediately, letting the coordinator start the next pass sooner.

**설명**

이는 결과가 되돌아오는 방식을 바꿀 뿐 호출이 발생하는 방식을 바꾸지 않으므로, 패스는 여전히 순차적으로 유지된다. Anthropic의 가이드도 오히려 반대 방향을 권장한다. 한 턴에서 여러 도구 호출이 이루어졌다면 모든 tool_result 블록을 하나의 user 메시지에 함께 담아 반환해야 하며, 이를 여러 메시지로 나누면 모델이 병렬 호출을 하지 않도록 학습시키는 결과를 낳는다.

### 전반적인 설명

코디네이터-서브에이전트 시스템에서 동시성을 만드는 지렛대는 런타임 설정이 아니라 코디네이터 자신의 응답 형태(shape)이다. Claude는 stop_reason: "tool_use"인 하나의 assistant 메시지에 여러 tool_use 블록을 반환할 수 있으며, 그렇게 할 경우 API가 실행 순서를 규정하지 않기 때문에 하니스는 해당 요청들을 자유롭게 병렬로 실행할 수 있다. 따라서 올바른 방법은 코디네이터가 세 개의 추출 패스를 한꺼번에 요청하도록 만드는 것이다. 즉 한 턴에 세 개의 Task 호출을 내보내면 세 개의 서브에이전트가 나란히 실행된다. 세 패스가 동일한 계약(contract)에 대한 독립적인 읽기 전용 추출이므로, 순차 실행을 강제할 순서 제약이 존재하지 않는다. (현재 SDK 버전에서 서브에이전트 도구의 이름은 Agent이며, Task는 별칭으로 유지된다.)

결과 처리 측면도 마찬가지로 중요하다. 각 tool_use 블록에 대해 하니스는 tool_use_id로 매칭되는 tool_result를 정확히 하나씩 반환해야 하며, 이 결과들은 모두 같은 다음 user 메시지에 함께 담겨야 한다. 각 결과를 별도의 메시지로 보내는 것은 명시적으로 안티패턴으로 지적된다. 시간이 지나면 이것이 모델에게 도구 호출을 일괄로 묶지 않도록 학습시키게 되어, 만들고자 했던 병렬성을 오히려 무너뜨린다.

오답들은 각각 병목이 실제로 어디에 있는지를 놓치고 있다. 지연 시간이 더 낮은 모델은 각 패스를 개별적으로 단축시키지만 전체적인 패턴은 여전히 순차적으로 남아있어, 전체 시간은 여전히 세 패스의 합이다. 세 서브에이전트를 하나의 AgentDefinition으로 병합하면 작업이 하나의 컨텍스트 안에서 직렬화되며 전문화와 컨텍스트 격리를 모두 포기하게 된다. 그리고 결과 전달 방식을 재구성하는 것은 지연을 유발하는 디스패치 패턴에 아무런 영향을 주지 않는다. Parallel tool use와 SDK의 Subagents 문서를 참고하라.

## 질문 4

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : The extraction pipeline defines a lookup_reference tool that Claude calls mid-extraction to resolve entity codes found in a document. Claude returns stop_reason "tool_use" and the application executes the lookup. How should the result be delivered so Claude can continue?

**A.** Send the output back as a plain text block in the next user message so Claude reads the lookup result as ordinary conversational input rather than a tool_result.

**설명**

일반 텍스트 user 메시지로 보내면 대기 중인 tool_use 블록이 응답받지 못한 상태로 남는다. API는 모든 tool_use 뒤에 다음 메시지에서 즉시 매칭되는 tool_result가 와야 한다고 요구한다. 이 요청은 tool_result 블록 없이 tool_use id만 발견되었다는 오류로 실패하게 되므로, 텍스트는 결국 모델에게 전달되지 않는다.

**B(정답).** Append the assistant message containing the tool_use block, then a user message with a tool_result block carrying the matching tool_use_id, and call the API again.

**설명**

이는 문서화된 표준 패턴이다. tool_use 블록을 담은 assistant 메시지와, tool_result(tool_use_id로 식별됨)를 담은 user 메시지가 모두 메시지 히스토리에 추가되고, 다음 API 호출에서 Claude가 그 출력을 바탕으로 추론할 수 있게 된다. 계속 누적되는 대화 히스토리가 모델이 도구 출력을 확인할 수 있는 유일한 통로이다.

**C.** Append a user message that opens with a text block explaining the lookup outcome, followed by the tool_result block carrying the matching tool_use_id.

**설명**

여기서 tool_result의 내용과 tool_use_id는 올바르지만, 배치 순서가 옳지 않다. user 메시지 안에서는 모든 tool_result 블록이 어떤 텍스트 블록보다도 앞에 와야 한다. 이 순서 규칙을 위반하면 API가 요청을 거부할 수 있으므로, 이 전달 방식은 신뢰할 수 없다.

**D.** Attach the output to the lookup_reference tool definition so the model re-reads the updated definition and result on its next inference pass.

**설명**

도구 정의(tool definition)는 도구의 이름, 설명, 입력 스키마를 정적으로 선언한 것이며, 런타임 결과를 전달하는 채널이 아니다. 모델은 오직 메시지 히스토리 안의 tool_result 블록을 통해서만 실행 출력을 확인할 수 있다.

### 전반적인 설명

Claude는 클라이언트가 정의한 도구를 스스로 실행하는 일이 결코 없다. 도구가 필요하다고 판단하면 stop_reason: "tool_use"로 생성을 멈추고 호출 내용을 기술하는 tool_use 블록을 내보낸다. 그러면 애플리케이션(하니스)이 실제 작업을 수행한다. 그 결과를 모델에게 다시 전달하는 일은 전적으로 하니스의 몫이며, 그 방법은 정확히 하나뿐이다. 바로 대화 히스토리이다. 하니스는 tool_use 블록을 담은 assistant 메시지를 추가한 뒤, 원래 호출의 id와 일치하는 tool_use_id를 가진 tool_result 블록을 담은 user 메시지를 추가하고, 다음 요청에서 전체 히스토리를 전송한다. How tool use works와 Build a tool-using agent를 참고하라.

API의 배치 규칙을 알면 오답들이 왜 실패하는지 설명된다. 각 tool_result는 메시지 히스토리에서 대응하는 tool_use 바로 다음에 와야 하며, user 메시지 안에서는 모든 tool_result 블록이 어떤 텍스트보다도 앞서야 한다(Handle tool calls 참고). 출력을 일반 텍스트로 보내면 대기 중인 tool_use가 응답받지 못한 채 남아 "tool_use ids were found without tool_result blocks immediately after"와 같은 오류를 유발한다. 같은 user 메시지 안에서 텍스트 블록을 tool_result보다 앞에 두는 것은 메시지 내부 순서 규칙을 위반한다. 한편 도구 정의는 이름, 설명, 입력 스키마로 구성된 정적 계약(contract)이며 모델이 호출을 선택하고 구성하는 방식을 형성할 뿐, 런타임 데이터를 담지 않는다.

이런 추출 파이프라인에 대해 가져야 할 올바른 사고 모델은, 메시지 히스토리가 곧 에이전트의 기억이라는 것이다. 루프의 매 반복마다 누적된 히스토리가 다시 전송되며, 새로 추가되는 각 tool_result는 모델이 다음 추론 단계에서 반영하는 새로운 증거가 된다. 이러한 상태 유지(statefulness)는 하니스가 구성해내는 일종의 환상이며, 바로 이 점이 개발자에게 모델이 무엇을 보고 무엇을 보지 못하는지에 대한 완전한 통제권을 부여한다.

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : Compliance mandates that national ID numbers, all of which match your team's validated regex detector, must never appear in extraction output sent downstream. System prompt instructions to omit them still leak occasionally in testing. Which design guarantees compliance?

**A.** Set sampling temperature to zero so the model applies the omission instruction identically on every extraction run.

**설명**

온도(temperature)를 0으로 설정하면 토큰 선택이 결정론적이 되지만, 지시가 반드시 지켜지는 것은 아니다. 모델이 가장 가능성 높은 출력으로 ID 번호를 포함하기로 정했다면, 그 유출은 매번 동일하게 재현될 것이다. 컴플라이언스 요구사항은 샘플링 문제가 아니다.

**B(정답).** Run the validated detector in code on the final extraction JSON, stripping any matches before the output is sent downstream.

**설명**

이 보기가 정답이다. 코드 수준의 검사는 매 실행마다 실행되며, 요구사항이 규제하는 대상, 즉 다운스트림으로 전송되는 출력 자체를 정확히 스캔한다. 문제 지문에서 모든 규제 대상 ID가 검증된 탐지기와 일치한다고 명시했으므로, 이 스캔은 전수적이고 결정론적이다. 따라서 ID가 어디서 들어왔든, 모델이 무엇을 생성했든 관계없이 경계를 통과할 수 없다.

**C.** Add a prompt-based hook that has a small Claude model review each extraction result and reject any output containing ID numbers.

**설명**

프롬프트 기반 훅은 모델이 판단을 내리도록 하는 방식이며, 본질적으로 확률적이다. 검토를 담당하는 모델도 추출 모델이 ID를 유출할 수 있는 것과 마찬가지로 ID를 놓칠 수 있다. Anthropic은 프롬프트 훅을 판단이 필요한 결정에 사용하도록 권장하며, 매번 반드시 지켜져야 하는 규칙에는 적합하지 않다고 명시한다.

**D.** Restate the redaction rule prominently in the system prompt and exclude ID number fields from the extraction JSON schema.

**설명**

시스템 프롬프트 지시는 확률적인 준수만을 제공하며, 이는 시나리오에서 이미 실패하고 있다는 것으로 드러난다. JSON 스키마는 pattern과 같은 검증기를 사용해 문자열 내용을 제약할 수 있지만, ID 필드를 단순히 제외하는 것만으로는 스키마가 허용하는 다른 자유 텍스트 필드 안에 ID 번호가 나타나는 것을 막을 수 없다.

### 전반적인 설명

이 문제가 검증하는 경계선은 결정론적 강제(deterministic enforcement)와 확률적 준수(probabilistic compliance) 사이의 구분이다. 시스템 프롬프트, 스키마 설명, 검토 모델의 평가 기준 등 모델에게 지시로 표현된 것은 무엇이든 높은 확률로는 지켜지지만 완벽하게 지켜지지는 않는다. 규제상의 결과가 걸려 있는 규칙이라면, 강제는 모델의 결정과 무관하게 매 실행마다 동작하는 코드에 존재해야 한다. 훅과 코드 수준의 게이트가 바로 이러한 보장을 제공하기 위해 존재한다. Claude Code 훅 가이드는 훅을 모델이 선택하도록 맡기는 대신 특정 동작이 실제로 일어나도록 보장하는 결정론적 통제로 설명한다.

강제 지점의 위치도 결정론만큼 중요하다. 이 요구사항은 출력 경계를 규제하므로, 강제 지점도 그곳에 있어야 한다. 최종 추출 JSON에 대해 검증된 탐지기를 실행하는 코드 검사는, ID가 도구 결과를 통해 들어왔든, 원본 문서를 통해 들어왔든, 모델 자체의 생성 과정에서 나왔든 관계없이 출력으로 들어가는 모든 경로를 커버한다. 도구 결과에 대한 PostToolUse 훅과 같은 입력 측 변환도 유용하지만, 그것은 그 한 채널을 통해 흐르는 데이터의 깨끗함만을 보장할 뿐, 그것만으로 시스템을 떠나는 것 전체를 인증할 수는 없다. 지문에서 모든 규제 대상 ID가 탐지기와 일치한다고 명시했으므로, 출력 아티팩트를 스캔하면 삭제(redaction) 작업이 전수적이 되어 확률적 지시를 확실한 게이트로 전환시킨다.

오답들은 각각 결정론이라는 축에서 실패한다. 프롬프트 훅은 강제 경로에 다시 모델의 판단을 끌어들인다. 훅 관련 문서는 Claude 모델을 이용해 단일 턴 평가를 수행하는 prompt 핸들러와, 코드를 실행하는 command 핸들러를 구분하며, Anthropic은 프로덕션 강제에는 후자를 권장한다. ID 필드를 스키마에서 제외한다고 해서 summary나 notes 같은 허용된 자유 텍스트 필드 안에 ID가 나타나는 것을 막지는 못한다. pattern과 같은 검증기가 적용된 경우 JSON Schema가 문자열 내용을 제약할 수 있다는 사실과는 별개의 문제이다. 그리고 온도를 0으로 설정하는 것은 샘플링에서 무작위성만 제거할 뿐이다. ID 번호를 포함하기로 결정한 결정론적 모델은 매번 그 번호를 포함할 것이다.

## 질문 6

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : The team resumes an extraction-tuning session with fork_session enabled to trial an alternative schema-guidance prompt from the established baseline. Which two practices should guide how they work with the resulting fork? (Choose two.)

**A(정답).** Resume either branch independently later, since the original session's ID and history are unchanged by the fork.

**설명**

이 보기가 정답이다. 포크(fork)는 원본 세션을 변경하지 않는다. 원본은 자신의 ID와 히스토리를 그대로 유지하며, 두 브랜치 모두 독립적으로 재개(resume)할 수 있다. 이것이 바로 분기 탐색을 안전하게 만드는 요소이다.

**B(정답).** Track the fork by its own session ID, a new session that begins from a copy of the original's conversation history.

**설명**

이 보기가 정답이다. 포크는 원본 세션의 누적된 히스토리 복사본에서 시작하는 새로운 세션을 만들며, 이 새 세션은 자신만의 별도 세션 ID를 부여받아 독립적으로 추적하고 재개할 수 있다.

**C.** Expect findings produced in the fork to merge back into the original session's history automatically on completion.

**설명**

이 보기는 옳지 않다. 포크된 세션은 분기점 이후 영구적으로 갈라진다. 원본 히스토리로 자동으로 되돌아 합쳐지는 것은 없다. 포크에서 얻은 발견 사항을 원래의 작업 흐름에 전달해야 한다면, 명시적으로 전달해야 한다.

**D.** Rely on the fork to snapshot the filesystem at the branch point so file edits stay isolated between the two branches.

**설명**

이 보기는 옳지 않다. 세션은 누적된 대화 히스토리일 뿐 파일시스템 상태가 아니므로, 포크는 대화 기록(transcript)만 복사한다. 파일 변경 사항을 격리하거나 되돌리려면 파일 체크포인팅(file checkpointing)과 같은 별도의 메커니즘이 필요하다.

### 전반적인 설명

Claude Agent SDK에서 세션(session)은 누적된 대화, 즉 프롬프트, 도구 호출, 도구 결과, 응답이다. 재개(resume) 시 fork_session을 설정하는 것은 그 히스토리를 그 자리에서 이어가는 것이 아니다. 원본 히스토리의 복사본에서 시작하여 자신만의 세션 ID를 부여받는 새로운 세션을 만드는 것이다. 원본 세션의 ID와 대화 기록은 그대로 유지되며, 그 지점 이후 두 브랜치는 각각 독립적으로 재개될 수 있다. 이는 정확히 설계 의도에 부합한다. 비용이 많이 드는 기준선(baseline)(여기서는 문서 집합과 스키마에 대한 정교화된 이해)을 각 브랜치가 물려받으면서, 어느 쪽도 서로를 오염시키거나 원본을 오염시키지 않는 '다른 접근 방식을 시도해보는' 워크플로가 바로 이것이다.

포크가 하지 않는 일에 해당하는 두 가지 경계를 내면화해두는 것이 중요하다. 첫째, 포크는 파일시스템 상태를 스냅샷하거나 격리하지 않는다. 세션은 오직 대화 히스토리만을 담고 있으므로, 한 브랜치에서 이루어진 파일 편집은 같은 작업 트리에서 동작하는 다른 어떤 것에도 그대로 보인다. 파일시스템 롤백은 세션 메커니즘이 아닌 파일 체크포인팅이 담당한다. 둘째, 되돌려 합쳐지는 일(merge-back)은 없다. 분기는 영구적이므로, 팀이 계속 이어가고자 하는 포크의 결론이 있다면 명시적으로 전달해야 한다(예를 들어 요약해서 새 프롬프트에 담는 방식). 이는 컨텍스트가 여러분이 직접 넣어줄 때만 에이전트 컨텍스트 간에 이동한다는 일반 원칙과도 일관된다.

포크와 재개(resume)에 대해 문서화된 동작은 Claude Agent SDK의 Sessions 문서를 참고하라.

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : A developer spent yesterday iterating on validation prompts for the extraction pipeline in a Claude Code session they named extraction-edge-cases. Several unrelated sessions have since run in the same directory. What should the developer run to continue that specific work?

**A.** claude -p "continue refining the extraction validation prompts" to pick up the prior work.

**설명**

-p 플래그는 세션 메모리가 전혀 없는 새로운 비대화형(non-interactive) 쿼리를 실행한다. 프롬프트 텍스트는 이어서 진행할 것을 요청하지만, Claude가 이어갈 수 있는 이전 컨텍스트는 전혀 로드되어 있지 않다.

**B(정답).** claude --resume extraction-edge-cases, restoring that session's conversation and state.

**설명**

--resume 플래그는 이름이나 ID를 통해 특정한 이전 세션을 목표로 지정하며, 도구 호출과 결과를 포함한 전체 대화 히스토리를 복원한다. 정확한 이름을 해석해내기 때문에, 그 이후 실행된 다른 세션들의 영향을 받지 않는다.

**C.** claude --continue, which reopens the most recent Claude Code session in the current directory.

**설명**

--continue 플래그는 현재 디렉터리에서 가장 최근에 실행된 대화형 세션만 재개한다. 그 이후 여러 관련 없는 세션들이 실행되었으므로, 이름이 지정된 추출 세션이 아니라 그중 하나를 다시 열게 된다.

**D.** A new interactive session in the same directory, relying on CLAUDE.md to restore the prior context.

**설명**

CLAUDE.md는 프로젝트 관례와 상시 지시사항을 담고 있을 뿐, 특정 조사 과정에서 발견된 사실과 대화 상태를 담고 있지 않다. 새로 시작한 세션은 어제 알아낸 내용을 전혀 알지 못한다.

### 전반적인 설명

Claude Code는 세션을 영속적으로 저장하며, --resume 플래그(짧은 별칭 -r)는 특정한 이전 대화를 이어가기 위한 메커니즘이다. 이 플래그는 세션 ID나 이름(실행 시 --name으로 지정하거나 세션 중 /rename으로 지정)을 받아, 도구 호출 및 결과의 전체 히스토리와 모델·권한 모드 같은 상태까지 포함한 저장된 대화를 복원한다. 세션에 이름을 붙이는 것이 바로 여러 날에 걸친 조사를 실용적으로 만들어주는 요소이다. 이름은 그 사이에 다른 세션이 얼마나 많이 실행되었든 살아남는 안정적인 손잡이(handle)이다.

이것이 --continue와의 핵심적인 차이점이다. --continue는 현재 디렉터리에서 가장 최근이었던 대화형 세션을 다시 여는 편의 기능이다. 두 명령은 서로 다른 질문에 답한다. "방금 멈췄던 곳에서 이어가기"와 "특정한 작업 흐름을 이어가기"이다. 이 상황에서는 어제 이후 관련 없는 세션들이 실행되었으므로, --continue는 잘못된 대화로 이동하게 된다. 또한 알아두면 좋은 점은, claude --resume <이름>이 저장소와 그 워크트리 전체에서 정확한 이름 일치를 해석하며, 이름이 모호할 경우 그 이름이 미리 채워진 세션 선택기를 연다는 것이다.

나머지 접근 방식들은 공통된 결함을 가지고 있다. 빈 컨텍스트에서 시작한다는 점이다. -p 호출은 세션 메모리가 없는 일회성 비대화형 실행이며, 새로운 대화형 세션은 CLAUDE.md를 로드하는데 이는 어제 프롬프트 튜닝 작업 중 축적된 구체적인 추론, 도구 결과, 결론이 아니라 지속적인 프로젝트 가이드를 담고 있다. "계속하라"는 지시를 다시 말한다고 해서 누락된 컨텍스트가 생겨나지는 않는다. 전체 재개 동작에 대해서는 Claude Code CLI 레퍼런스와 세션 문서를 참고하라.

## 질문 8

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : A session has produced a detailed analysis of why extraction fails on edge-case invoices. The team now wants to trial a strict-schema fix and a lenient-schema fix separately, with each attempt building on that analysis but neither influencing the other. What should they do?

**A.** Start two new sessions and paste a written summary of the failure analysis into each one as its opening message.

**설명**

수동으로 작성한 요약은 정보가 손실된다. 실패 분석의 세밀한 뉘앙스, 구체적인 문서 예시, 중간 관찰 내용이 압축되거나 빠지게 된다. 포크는 완전한 분석 컨텍스트를 어떤 수동 재요약 없이도 두 브랜치에 모두 전달하므로, 이 접근 방식은 불필요한 정보 손실 비용을 치르게 된다.

**B.** Test both fixes in one session sequentially, instructing Claude to disregard the first fix before evaluating the second.

**설명**

컨텍스트는 지시만으로 선택적으로 잊혀지지 않는다. 첫 번째 수정에 관한 모든 것이 대화에 남아 있으며, 두 번째 수정에 대한 평가에 영향을 줄 수 있다. 하나의 세션에서 순차적으로 테스트하는 것은 어느 쪽 탐색도 서로에게 영향을 주어서는 안 된다는 요구사항을 직접적으로 위반한다.

**C.** Run /compact after the analysis so the condensed context can support evaluating both schema fixes in the same session.

**설명**

압축(compaction)은 단일 세션 내의 히스토리를 압축할 뿐, 별도의 작업 흐름을 만들어내지 않는다. 두 수정 모두 여전히 하나의 공유 컨텍스트에서 평가될 것이므로, 두 번째 평가는 첫 번째 평가에 오염되며, 분석의 세부 사항도 요약 과정에서 손실될 수 있다.

**D(정답).** Create two branches from the analysis session with fork_session and develop each schema fix in its own branch.

**설명**

포크는 분기점까지의 전체 분석을 모두 물려받은 뒤 이후로는 아무것도 공유하지 않고 갈라지는 독립적인 브랜치를 만들어낸다. 이렇게 하면 각 스키마 수정이 완전한 실패 분석을 기준선으로 갖게 되면서, 동시에 두 탐색이 서로 격리된 상태로 유지된다는 것도 보장된다.

### 전반적인 설명

fork_session은 정확히 이러한 패턴, 즉 공유된 기준선에서 시작하는 분기 탐색을 위해 존재한다. 포크는 분기점까지의 전체 대화(실패 분석에서 얻은 모든 발견 사항 포함)를 각각 물려받은 뒤 독립적으로 진화하는 브랜치를 만들어낸다. 어느 브랜치도 다른 브랜치에서 일어나는 일을 절대 보지 못하므로, 엄격한 스키마와 느슨한 스키마 시도를 깔끔하게 비교할 수 있으며, 비용이 많이 드는 분석 작업은 각 시도마다 다시 하거나 재요약하는 것이 아니라 정확히 한 번만 수행하면 된다.

여기서의 사고 모델은 테이프가 아니라 나무(tree)이다. 단일 세션은 선형적인 테이프이다. 모든 것이 컨텍스트에 남아 있으며, 이전 내용을 "무시하라"는 지시는 그것을 제거하지 못한다. 모델은 여전히 그 토큰들에 주의를 기울이기 때문이다. /compact도 같은 테이프 위에서 동작하며 히스토리를 요약해 대체한다. 토큰 사용량은 줄어들지만 첫 번째 실험의 영향을 제거하지도, 두 번째 작업 흐름을 만들어내지도 못하며, 그 요약 과정에서 실패를 유발한 구체적인 인보이스 패턴 같은 정밀한 세부 사항이 빠질 수 있다. 완전히 새로운 두 세션에 붙여넣은 요약을 시딩하는 방법은 격리 자체는 달성하지만, 실제 분석을 손실이 있는 수동 작성 근사치로 대체하는 대가를 치르며, 그 기준선을 두 번 세팅해야 한다. 포크는 두 가지 속성을 동시에 얻는다. 완전한 정보 손실 없는 공유 컨텍스트와, 분기 이후의 엄격한 격리이다.

세션이 어떻게 재개되고 포크되는지는 Claude Agent SDK의 Session Management 문서를, 관련된 컨텍스트 격리 메커니즘은 Create custom subagents를 참고하라.

### 전반적인 설명

이 문제는 코디네이터 프롬프트 설계의 핵심 원칙을 검증한다. 절차가 아니라 성공을 정의하라는 것이다. 코디네이터-서브에이전트 아키텍처에서 각 서브에이전트는 자신만의 격리된 컨텍스트에서 실행되며, 코디네이터의 대화 히스토리나 이전 도구 결과를 자동으로 물려받지 않는다. 서브에이전트는 AgentDefinition의 시스템 프롬프트처럼 자체적으로 구성된 지시사항을 가질 수 있지만, 작업별 콘텐츠(연구나 추출 목표, 필요한 컨텍스트, 품질 기준)는 위임 프롬프트 자체에 포함되어야 한다. 위임된 작업이 경직된 절차적 스크립트로 작성되면, 눈앞의 문서에 대해 추론할 수 있는 서브에이전트의 능력이 낭비된다. 문서를 보기도 전에 작성된 경로를 강제로 따라가게 되기 때문이다. 결정론적 파서 대신 에이전트를 추출에 사용하는 이유 자체가 문서가 다양하기 때문이다. 위임 프롬프트는 목표(이 문서에서 이 필드들을 추출하라)와 품질 기준(출력이 JSON 스키마를 검증하며, 필수 필드가 채워져 있고, 값이 원본 텍스트에 근거하고 있다)을 명시하고 서브에이전트가 헤더, 표, 특이한 레이아웃을 어떻게 탐색할지 스스로 결정하도록 함으로써 그 적응성을 보존해야 한다.

Anthropic의 프롬프팅 가이드는 이를 명시적으로 설명한다. 단계가 아니라 결과를 기술하고, 모델에게 자신의 작업을 확인할 방법을 제공하며, 순서나 완전성이 실제로 중요한 경우에만 경직된 번호 매기기 시퀀스를 사용하라는 것이다. 품질 기준은 서브에이전트의 자기 검증 목표로 작동하며, 이것이 바로 목표 지향적 프롬프트를 단순히 허용적인 것을 넘어 신뢰할 수 있게 만드는 요소이다. 한 보기처럼 기준을 완전히 없애버리면 '완료'의 정의 자체가 사라져 불완전하거나 검증되지 않은 출력을 초래한다. 스크립트를 더 많은 레이아웃을 커버하도록 확장하는 것은 취약성을 더 깊게 만들 뿐이며, 특이한 문서를 코디네이터로 돌려보내 맞춤 스크립트를 작성하게 하는 것은 동일한 절차적 경직성을 위치만 옮기면서 왕복까지 추가하는 셈이다.

서브에이전트가 무엇을 물려받는지와 위임 프롬프트가 왜 작업별 컨텍스트를 담아야 하는지는 SDK의 Subagents 문서를, 단계별 절차 대신 결과와 측정 가능한 목표를 기술하는 방법에 대해서는 Claude Code의 프롬프트 가이드를 참고하라.

## 질문 10

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : A new intake adds complex contract packets whose relevant sections, amendments, and cross-references vary unpredictably from document to document; the extraction work needed only becomes clear after an initial read. Which decomposition approach fits this intake?

**A(정답).** Have the model analyze each document first, then generate the extraction subtasks dynamically based on what that analysis reveals.

**설명**

이는 동적 적응 분해(dynamic adaptive decomposition)이며, 필요한 하위 작업을 사전에 예측할 수 없을 때 문서화된 적합한 방식이다. 초기 분석 패스를 거치면 시스템은 각 문서의 구조가 알려지기 전에 설계된 단계를 모든 문서에 강제로 적용하는 대신, 그 특정 문서가 실제로 필요로 하는 추출 단계를 선택할 수 있다.

**B.** Enumerate every document structure seen so far and build a fixed chain with a dedicated extraction step per structural variant.

**설명**

고정된 체인은 하위 작업이 사전에 알려져 있다고 가정하는데, 이는 인테이크의 예측 불가능한 구조와 모순된다. 변형들을 열거하는 것은 아무도 예상하지 못한 구조를 가진 패킷이 도착하는 순간 파이프라인이 패배하게 되는 경쟁이다.

**C.** Send packets with unpredictable structure to human reviewers, keeping automated extraction only for documents that match known templates.

**설명**

모든 불규칙한 문서를 에스컬레이션하는 것은 시스템이 처리하도록 만들어진 바로 그 작업량에 대해 자동화를 포기하는 것이다. 적응 분해는 모델이 구조적 다양성을 자율적으로 처리할 수 있게 한다. 인간 리뷰는 일상적인 변동성이 아니라 진정한 판단이 필요한 경우를 위해 남겨두어야 한다.

**D.** Extract each packet in one comprehensive request so every field is captured with the entire document in view at once.

**설명**

단일한 통합 패스는 하나의 호출에 구조 발견과 데이터 추출을 동시에 요구하며, 이는 길고 이질적인 콘텐츠 전체에 주의를 분산시킨다. 분해(decomposition)는 정확히 이것을 피하기 위해 존재한다. 문제는 단지 그 단계들이 고정되어 있는지 적응적인지 뿐이다.

### 전반적인 설명

에이전트 설계에 대한 Anthropic의 가이드는 제어 흐름이 사전에 얼마나 결정되어 있는지에 따라 접근 방식을 구분한다. 프롬프트 체이닝(prompt chaining)은 고정된 순차 파이프라인이다. 작업을 "고정된 하위 작업들로 쉽고 깔끔하게 분해할 수 있을 때" 효과적이며, 각 호출이 이전 호출의 출력을 소비하고 단계 사이에 선택적으로 프로그래밍적 게이트를 둘 수 있다. 이 방식의 가치 전체는 입력이 도착하기 전에 단계들을 알고 있다는 전제에 기대고 있다. 필요한 하위 작업이 각 특정 문서가 담고 있는 내용에 의존할 때는 이 전제가 무너지며, 문서화된 대안은 동적 분해(dynamic decomposition)이다. 초기 패스가 입력을 살펴보고 시스템이 실제로 필요한 하위 작업을 생성하는 것으로, Anthropic이 오케스트레이터-워커(orchestrator-workers)라고 부르는 패턴이다. 여기서 하위 작업은 미리 정의되는 것이 아니라 특정 입력에 근거해 선택된다.

아키텍트가 가져야 할 사고 모델은 예측 가능성의 스펙트럼이다. 완전히 예측 가능한 단계는 고정된 체인으로 처리하는 것이 더 저렴하고 빠르며 회귀 테스트도 쉽다. 중간 발견 사항에서 생겨나는 단계는 적응 분해로 처리하며, 사전에 작성된 파이프라인이 예상하지 못한 입력을 처리하는 대가로 추가적인 비용과 지연을 받아들인다. 모든 구조적 변형을 끊임없이 커지는 고정 체인에 열거해 넣는 방식은 유지보수 노력으로 적응성을 사는 시도이며, 그럼에도 다음에 등장하는 새로운 패킷에서는 여전히 무너진다. 단일한 통합 추출 요청은 분해 자체를 피하면서 구조 발견과 추출을 한 호출에 과부하시킨다. 모든 불규칙한 문서를 인간에게 넘기는 것은 핵심 작업량을 포기하는 것이다. 인간 리뷰는 구조적 다양성이 아니라 판단이 걸림돌이 되는 곳에 있어야 한다.

프롬프트 체이닝, 오케스트레이터-워커의 전체 비교와 언제 에이전트형 복잡성을 받아들여야 하는지는 Building Effective Agents를 참고하라.

**SCENARIO** : You are building a structured data extraction system using Claude. **QUESTION** : The system routes documents it cannot extract confidently to human reviewers, and those reviewers have no access to the model's processing transcript. What should each escalation record contain so a reviewer can resolve the case without redoing the work?

**A.** Send only the document identifier and the original source file, so reviewers form an independent judgment without anchoring on the system's prior analysis.

**설명**

이 방식은 '새로운 시선'이라는 명목으로 완료된 작업 전체를 폐기하고, 리뷰어가 문서를 처음부터 다시 추출하도록 강제한다. 에스컬레이션의 목적은 사건 상태(case state)를 전달하는 것이지, 조사를 다시 시작하는 것이 아니다.

**B.** Forward the complete raw model output from every extraction pass, so reviewers can inspect all the evidence the system gathered.

**설명**

### 전반적인 설명

에스컬레이션 핸드오프(handoff)는 문제가 발생했다는 사실을 알리는 것뿐만 아니라 사건 상태를 전달하기 위해 존재한다. 받는 쪽 인간이 모델의 세션을 전혀 들여다볼 수 없을 때, 에스컬레이션 기록은 완료된 작업이 핸드오프를 거쳐 살아남을 수 있는 유일한 채널이다. 따라서 잘 설계된 기록은 네 가지를 담아야 한다. 원본 문서로 연결되는 식별자, 이미 만들어진 부분 결과(지금까지 추출되고 검증된 필드), 시스템이 왜 멈췄는지를 정확히 설명하는 근본 원인 진술(예를 들어 원본에서 두 개의 총액이 충돌한다거나, 필수 필드가 실제로 존재하지 않는다는 것), 그리고 리뷰어가 수락하거나 재정의할 수 있는 권장 조치이다. 이는 상담 에이전트가 결제 분쟁을 에스컬레이션할 때와 동일한 구조화된 핸드오프 규율이다. 인간이 처음부터 다시 시작할 필요는 절대 없어야 한다.

실무에서 팀들은 에스컬레이션 자체를 명시적인 JSON 스키마를 가진 도구나 구조화된 출력으로 모델링함으로써, 모델이 자유 텍스트로 사과문을 내놓는 대신 모든 필드를 채우도록 강제한다. Anthropic의 도구 사용 가이드는 도구의 input_schema가 모델이 반드시 제공해야 할 정확한 파라미터를 정의하며, 도구를 언제 어떻게 사용할지에 대한 상세한 설명이 신뢰할 수 있는 호출을 이끄는 가장 큰 요인이라고 강조한다. How to implement tool use를 참고하라. document_id, extracted_fields, escalation_reason, recommended_resolution과 같은 필드를 정의하면 핸드오프를 기계적으로 검증 가능하게 만들고 사건마다 일관성을 유지할 수 있다.

각 대안은 자기완결성(self-containment) 테스트에서 실패한다. 식별자와 원본 파일만 보내는 방식은 앵커링(anchoring)을 피하려고 추출 작업 전체를 버리는 것이며, 작은 편향 위험을 확실한 중복 작업으로 바꾸는 셈이다. 모든 원본 모델 출력을 전달하는 것은 통찰이 아니라 분량을 전달하며 종합의 부담을 인간에게 떠넘긴다. 신뢰도와 긴급도 점수는 유용한 라우팅 메타데이터이지만, 사건에 대한 메타데이터가 사건 그 자체는 아니다. 리뷰어는 여전히 행동하기 위해 발견 사항, 충돌, 그리고 제안된 다음 단계를 필요로 한다.

### 전반적인 설명

Messages API에서의 클라이언트 측 도구 사용은 두 번의 요청으로 이루어진 루프이다. Claude가 도구가 필요하다고 판단하면 stop_reason: "tool_use"와 하나 이상의 tool_use 콘텐츠 블록으로 자신의 턴을 마친다. 각 블록은 고유한 id, 도구 이름, 입력 인자를 담고 있다. API는 스스로 아무것도 실행하지 않는다. 여러분의 하니스가 도구를 실행하고 결과를 되돌려 보내어 모델이 추론을 계속할 수 있게 한다.

이 왕복 과정을 지배하는 구조적 규칙은 두 가지이다. 첫째, 도구 출력은 user 역할 메시지 안의 tool_result 콘텐츠 블록으로 돌아간다. 다른 일부 LLM API와 달리 Claude의 Messages API에는 별도의 tool이나 function 역할이 없으므로, 도구 사용은 기존의 user/assistant 교대 구조 안에 짜여 들어간다. 둘째, 각 tool_result는 자신이 응답하는 tool_use 블록의 id를 tool_use_id로 설정해야 한다. 이 명시적인 연결이 병렬 도구 호출을 안전하게 만드는 요소이다. 모델이 한 턴에서 두 개의 조회를 요청했을 때, 블록의 순서가 아니라 ID가 어떤 출력이 어떤 요청에 속하는지 알려준다. 여러 결과가 반환될 때는 여러 턴에 나눠지는 것이 아니라 하나의 user 메시지 안에 함께 속해야 한다.

여기서 가져야 할 사고 모델은, 계속 늘어나는 메시지 히스토리가 모델의 유일한 기억이라는 것이다. tool_use 블록을 담은 assistant 메시지와 그에 대응하는 tool_result 블록을 담은 user 메시지는 둘 다 다음 요청에 나타나야 한다. 모델은 매 추론 단계마다 전체 기록을 다시 읽기 때문이다. 결과를 assistant 메시지로 보내거나, 매칭을 위치 순서에 의존하는 것은 API가 정의하는 계약을 어기는 것이다. 문서화된 메시지 구조는 Tool use overview와 Handle tool calls를 참고하라.

여기서 가져야 할 사고 모델은, 도구 결과가 자유로운 형태의 서술이 아니라 일반적인 메시지 교대 구조 안에 내재된 요청-응답 계약의 구조화된 연속이라는 것이다. 그래서 수정 방법은 순전히 순서 재배열이다. 요약 텍스트가 유용하다면 유지하되, 결과 다음에 배치하면 된다. 이는 왜 다른 접근 방식들이 실패하는지도 설명해준다. Anthropic은 (일부 다른 API와 달리) 별도의 tool 역할을 의도적으로 피하고 모든 것을 user와 assistant 메시지 안에 유지한다. 하나로 합쳐진 tool_result는 두 개의 id를 참조할 수 없으므로 한쪽 호출은 응답받지 못한 채로 남는다. 그리고 결과를 두 개의 user 메시지로 나누는 것은 두 번째 결과에 대한 인접성 요구사항을 위반한다.

**QUESTION** : You fork a session after a completed baseline document analysis so two branches can each develop a candidate extraction schema, writing schema files into the project directory. How do you keep the branches from interfering with each other?

**A.** Fork the session and rely on the fork to snapshot the project files at the branch point, keeping each branch's schema edits separate.

**설명**

포크는 파일을 스냅샷하거나 복사하지 않는다. 대화 컨텍스트만 복제하므로, 분석이 다룬 파일은 여전히 두 브랜치 모두가 수정하고 관찰할 수 있는 단일한 공유 복사본으로 남는다.

**B.** Fork the session and let each fork's automatically created git worktree give it an independent copy of the project's file tree.

**설명**

워크트리(worktree)는 병렬 작업을 위한 독립적인 파일 트리를 제공하는 것이 맞지만, 이는 여러분이 직접 설정해야 하는 별개의 메커니즘이다. 세션을 포크한다고 해서 워크트리가 자동으로 생성되지는 않는다. 포크만으로는 두 브랜치 모두 같은 작업 디렉터리에 남는다.

**C(정답).** Fork the session for the shared analysis context, and give each branch its own worktree or output path for its schema files.

**설명**

이 보기가 정답이다. 포크는 분기점에서의 세션 대화 히스토리를 복제하지만, 세션은 대화 히스토리를 영속화할 뿐 파일시스템 상태를 영속화하지 않는다. 기본적으로 두 브랜치는 동일한 프로젝트 파일을 읽고 쓰게 되므로, 워크트리나 별도의 출력 경로 같은 메커니즘을 이용해 파일 출력을 직접 분리해야 한다.

**D.** Fork the session and use its file checkpoint at the branch point to roll back schema edits the other branch makes when needed.

**설명**

파일 롤백은 파일 체크포인팅(file checkpointing)의 역할이며, 세션 포크와는 별개이다. 포크는 파일 상태에 대한 체크포인트를 전혀 가지고 있지 않으므로, 어느 브랜치도 다른 브랜치의 수정을 되돌릴 능력을 얻지 못한다.

### 전반적인 설명

여기서 가져야 할 사고 모델은, 세션이 누적된 대화 히스토리, 즉 원래의 프롬프트, 도구 호출, 도구 결과, 응답이며, SDK가 이를 나중에 재개하거나 포크할 수 있도록 디스크에 기록해둔다는 것이다. 포크를 하면 두 브랜치 모두 분기점까지의 히스토리를 물려받은 뒤 독립적인 대화로 갈라진다. 포크가 결코 하지 않는 일은 파일시스템을 복제하거나 샌드박스화하는 것이다. 세션은 대화 히스토리를 영속화할 뿐 파일시스템 상태를 영속화하지 않으므로, 같은 프로젝트 디렉터리에 스키마 파일을 쓰는 두 개의 포크된 브랜치는 하나의 공유된 파일 집합을 편집하는 셈이며, 각 브랜치는 다른 쪽의 변경 사항을 보게 되고(그로 인해 혼란스러워질 수 있다).

이러한 역할 분담은 의도적인 것이다. 포크는 추론의 분기를 저렴하게 만들기 위해 존재한다. 기준선 분석에 대한 비용을 한 번만 치르고, 동일한 컨텍스트에서 두 가지 추출 스키마 설계를 탐색하는 것이다. 파일을 서로 다르게 유지하는 것은 다른 도구가 필요한 다른 문제이다. 파일 체크포인팅은 파일을 되돌리는 것을 지원하고, 워크트리는 병렬 세션에 진짜로 독립적인 파일 트리를 제공한다. 따라서 파일을 만들어내는 두 가지 스키마 접근 방식을 비교하는 아키텍트는 공유 컨텍스트를 위해 세션을 포크하고, 각 브랜치에 아티팩트용 별도의 워크트리나 출력 경로를 짝지어야 한다.

## 질문 15

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : A developer's extraction loop terminates as soon as a response contains a text block. Runs that mix explanatory text with tool calls end prematurely, leaving tool requests unexecuted. Which termination logic fixes this?

**A.** Stop only when a response contains no tool_use blocks and its text includes a phrase confirming the extraction is finished.

**설명**

완료를 나타내는 문구를 자연어에서 파싱하는 것은 이미 알려진 안티패턴이다. 모델이 예상된 문구를 내보내지 않고 끝낼 수도 있고, 작업 중간에 비슷한 표현을 내보낼 수도 있다. tool_use 블록의 부재는 이미 stop_reason을 통해 신뢰성 있게 전달되고 있다.

**B.** Run the loop for a fixed iteration count matching the expected number of tool calls per document, then take the last response as final.

**설명**

반복 횟수 제한은 폭주하는 루프에 대한 안전장치일 뿐, 주된 정지 메커니즘이 아니다. 더 적은 호출이 필요한 문서는 반복 횟수를 낭비하고, 더 많은 호출이 필요한 문서는 도구 요청이 실행되지 않은 채로 작업 중간에 끊기게 되는데, 이는 지금 고치려는 것과 동일한 실패이다.

**C(정답).** Keep executing requested tools and returning tool_result blocks while stop_reason is "tool_use", ending the loop when stop_reason is "end_turn".

**설명**

이는 문서화된 에이전트 루프 계약이다. stop_reason은 API가 명시적으로 제공하는 구조화된 신호이다. "tool_use"는 Claude가 마치기 전에 도구 결과를 돌려받기를 기대한다는 뜻이고, "end_turn"은 텍스트 블록이 중간에 등장했는지 여부와 무관하게 Claude가 응답을 완료했다는 뜻이다.

**D.** Terminate once the accumulated assistant text parses as JSON that validates against the extraction schema, treating validation success as completion.

**설명**

이는 API의 구조화된 신호를 콘텐츠 검사로 대체하는 방식이다. Claude가 도구 지원 작업을 마치기 전에도 중간 텍스트가 우연히 검증을 통과할 수 있으며, 출력을 검증하는 것과 모델이 더 취할 행동이 있는지 판단하는 것은 별개의 관심사이다.

### 전반적인 설명

Claude Messages API는 루프 상태를 응답 콘텐츠의 형태나 표현이 아니라 stop_reason 필드를 통해 전달한다. 하나의 assistant 메시지는 텍스트 블록(추론, 해설)과 tool_use 블록을 정당하게 동시에 포함할 수 있다. 바로 이 때문에 "응답에 텍스트가 포함되어 있다"에 근거한 어떤 종료 규칙도 실패한다. 텍스트의 존재 여부는 Claude가 끝났는지에 대해 아무것도 말해주지 않는다. 설계된 계약은 단순하다. stop_reason이 "tool_use"인 동안에는 요청된 각 도구를 실행하고, (tool_use_id로 매칭되는) tool_result 블록을 새 user 메시지에 추가하여 API를 다시 호출한다. stop_reason이 "end_turn"이면 Claude가 완료된 것이고 루프를 종료한다.

여기서 가져야 할 사고 모델은, 이것이 모델 주도(model-driven) 제어 흐름이라는 것이다. Claude는 매 단계마다 도구가 더 필요한지 아니면 답변할 준비가 되었는지를 결정하고, 그 결정을 여러분의 코드가 결정론적으로 분기할 수 있는 구조화된 필드를 통해 신호로 알린다. 완료 문구를 파싱하거나, 출력이 스키마에 검증되는지 확인하거나, 반복 횟수를 세는 등 콘텐츠를 검사하는 휴리스틱은 모두 API가 이미 명시적으로 답을 제공하는 결정에 다시 추측을 끌어들인다. 반복 횟수 제한도 여전히 쓰일 곳이 있지만, 오직 멈춰버린 루프에 대한 안전망으로서일 뿐이며, 결코 주된 종료 조건이 되어서는 안 된다. '예상되는' 도구 호출 횟수에 맞춰진 제한은 정당하게 더 많은 조회가 필요한 문서를 잘라버린다.

추출 파이프라인에서는 이것이 이중으로 중요하다. 스키마 검증은 루프가 완료된 이후, 최종 출력에 대한 품질 게이트로서 이루어져야 하며, stop_reason은 최종 출력이 아직 존재하는지를 관리한다. 이 둘을 혼동하면 정확히 설명된 조기 종료 버그가 발생한다. 표준 루프는 How tool use works를, tool_result 형식 요구사항은 Handle tool calls를 참고하라.

## 질문 16

**SCENARIO** : You are building a structured data extraction system using Claude. The system extracts information from unstructured documents, validates the output using JavaScript Object Notation (JSON) schemas, and maintains high accuracy. It must handle edge cases gracefully and integrate with downstream systems.

**QUESTION** : The team is structuring the extraction pipeline as a coordinator with specialized subagents for metadata extraction, table parsing, and schema validation. Which two responsibilities belong to the coordinator in this hub-and-spoke design? (Select two.)

**A.** Maintain a shared conversation history that all subagents read, so each one automatically sees what earlier extraction steps produced.

**설명**

서브에이전트는 격리된 컨텍스트에서 동작하며 대화 히스토리를 공유하지 않는다. 유지해야 할 공유 메모리는 존재하지 않으며, 서브에이전트가 필요로 하는 것은 코디네이터가 위임할 때 보내는 프롬프트에 명시적으로 담아야 한다.

**B(정답).** Aggregate the outputs returned by the subagents and validate the combined result before emitting the final structured record.

**설명**

결과 집계와 검증은 코디네이터의 책임이다. 모든 서브에이전트가 자신의 출력을 허브(hub)로 반환하기 때문에, 코디네이터는 부분 결과들을 결합하고 일관성을 점검하며 최종 기록으로 조립할 수 있는 유일한 지점이다.

**C(정답).** Decompose each incoming document into subtasks and dynamically select which subagents to invoke based on the document's characteristics.

**설명**

작업 분해(task decomposition)와 동적 서브에이전트 선택은 허브-스포크(hub-and-spoke) 설계에서 코디네이터의 핵심 임무이다. 코디네이터는 들어오는 작업을 살펴 집중된 하위 작업으로 나누고, 각각에 어떤 전문화된 워커가 필요한지 결정한다.

**D.** Allow each subagent to decide which peer subagent should process its output next, so routing adapts dynamically to document content.

**설명**

허브-스포크 토폴로지에서 서브에이전트들은 서로에게 작업을 넘기지 않는다. 모든 통신은 코디네이터를 거쳐 흐른다. 워커가 자신의 후속 작업자를 스스로 선택하도록 허용하면, 설계가 통제되지 않는 피어투피어(peer-to-peer) 흐름으로 바뀌어 허브가 파이프라인에 대해 갖는 통제력을 없애버린다.

### 전반적인 설명

허브-스포크 멀티 에이전트 아키텍처에서 코디네이터는 단순한 디스패처가 아니라 작업의 전체 생명주기를 소유한다. 들어오는 쪽에서는 문서를 집중된 하위 작업으로 나누는 작업 분해와, 이 특정 입력에 대해 어떤 전문가를 호출할지 선택하는 동적 서브에이전트 선택을 수행한다(스캔된 인보이스는 표 파싱이 필요할 수 있지만 계약서는 그렇지 않을 수 있다). 나가는 쪽에서는 결과 집계와 검증을 수행한다. 모든 워커가 허브로 결과를 보고하기 때문에, 코디네이터는 모든 부분 결과를 볼 수 있고 다운스트림 시스템에 도달하기 전에 이를 하나의 검증된 기록으로 조정할 수 있는 유일한 구성요소이다.

이 설계를 작동시키는 사고 모델은, 서브에이전트가 격리된 워커라는 것이다. 각 서브에이전트는 자신만의 컨텍스트 창에서 실행되며, 자신의 위임 프롬프트에 담긴 내용만을 받고, 최종 메시지만을 부모에게 반환한다. 피어들이 읽을 수 있는 공유 대화 히스토리는 없으며, 한 서브에이전트가 다른 서브에이전트에게 직접 작업을 넘기는 채널도 없다. 이러한 격리는 이 아키텍처가 의도적으로 취하는 트레이드오프이다. 명시적인 컨텍스트 전달이라는 비용을 치르지만, 그 대가로 깨끗한 컨텍스트 창, 병렬화 가능한 하위 작업, 그리고 전체 흐름을 관찰하고 통제할 수 있는 하나의 지점을 얻는다.

오답들은 정확히 이러한 보장을 무너뜨린다. 서브에이전트가 자신의 후속 작업자를 선택하는 피어투피어 라우팅은 허브의 순서 제어권을 없애고 파이프라인을 하나의 지점에서 관찰하거나 디버깅하는 것을 불가능하게 만든다. 서브에이전트가 "자동으로 보게 되는" 공유 히스토리는 실제로 존재하지 않는다. 이를 가정하면 빈 입력에 대해 동작하는 종합이나 검증 단계로 이어진다. 서브에이전트 컨텍스트 격리와 위임이 어떻게 작동하는지는 Create custom subagents와 SDK의 Subagents 문서를 참고하라.
