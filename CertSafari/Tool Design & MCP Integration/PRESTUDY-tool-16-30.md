# 사전 학습 노트: 도구 설계와 MCP 통합 (Tool Design & MCP Integration)

이 문서는 이 주제를 처음 접하는 학습자를 위한 개념 정리입니다. MCP가 무엇인지, Claude Code가 도구를 어떻게 다루는지, 좋은 도구를 어떻게 설계하는지, 에러를 어떻게 구분해서 반환해야 하는지를 밑바닥부터 설명합니다.

---

## 1. 기초: LLM 에이전트와 "도구(Tool)"

### 1.1 도구란 무엇인가
LLM(대규모 언어 모델)은 본래 텍스트를 생성할 뿐, 파일을 읽거나 DB를 조회하거나 Slack에 글을 올릴 수 없습니다. **도구(Tool)** 는 모델이 외부 세계에 작용할 수 있도록 노출된 "호출 가능한 함수"입니다.

도구 하나는 보통 세 가지로 구성됩니다.

| 구성 요소 | 역할 |
|---|---|
| 이름(name) | `search_tickets`처럼 도구를 식별하는 문자열 |
| 설명(description) | 이 도구가 무엇을 하고 언제 쓰는지를 적은 자연어. **모델이 읽는 유일한 사용 설명서** |
| 입력 스키마(input schema) | 인자의 이름·타입·필수 여부를 JSON Schema로 정의한 것 |

예시:

```json
{
  "name": "search_tickets",
  "description": "지원 DB에서 필터 조건에 맞는 티켓 목록을 조회한다. 고객 ID, 상태, 기간으로 필터링할 수 있다.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "customer_id": { "type": "string" },
      "status": { "type": "string", "enum": ["open", "closed"] }
    },
    "required": ["customer_id"]
  }
}
```

### 1.2 모델은 어떻게 도구를 고르는가
모델은 실행 코드를 보지 못합니다. **이름과 설명, 스키마만 읽고** "지금 상황에 어떤 도구가 맞는가"를 확률적으로 판단합니다. 그래서 도구 설계에서 이름과 설명은 UI 문구가 아니라 **모델을 향한 프롬프트**입니다. 여기서 이 주제의 핵심 원리가 나옵니다.

> 도구 선택이 틀리면, 대개 모델이 아니라 **이름·설명·도구 집합**의 문제다.

## 2. MCP (Model Context Protocol) 기초

### 2.1 MCP가 무엇이고 왜 존재하는가
**MCP(Model Context Protocol)** 는 AI 클라이언트(예: Claude Code)와 외부 기능 제공자(서버)를 연결하는 **표준 프로토콜**입니다.

MCP 이전에는 "Claude에 Postgres를 붙이는 코드", "Slack을 붙이는 코드"를 각 도구·각 클라이언트마다 따로 만들어야 했습니다. MCP는 이 연결 방식을 하나의 규격으로 통일합니다. 한 번 만든 MCP 서버는 규격을 지키는 어떤 클라이언트에서도 재사용됩니다.

- **MCP 서버**: 도구(그리고 리소스, 프롬프트)를 노출하는 프로그램. 예: Postgres 서버, Sentry 서버, Slack 서버, 사내 코드 인덱스 서버
- **MCP 클라이언트**: 서버에 접속해 도구 목록을 받아 모델에 제공하고, 모델의 호출을 서버로 중계하는 쪽. Claude Code가 여기에 해당

### 2.2 통신 방식: JSON-RPC
MCP는 **JSON-RPC 2.0** 메시지를 주고받습니다. 요청/응답 쌍과, 응답이 필요 없는 단방향 **알림(Notification)** 이 있습니다. 대표적인 메서드는 다음과 같습니다.

- `tools/list` — 서버가 제공하는 도구 목록을 달라는 요청
- `tools/call` — 특정 도구를 인자와 함께 실행해 달라는 요청
- `notifications/tools/list_changed` — 서버가 클라이언트에게 "내 도구 목록이 바뀌었다"고 알리는 알림

### 2.3 전송 방식(transport): stdio와 원격
- **stdio 서버**: 클라이언트가 서버를 **자식 프로세스로 직접 실행(spawn)** 하고, 표준 입출력으로 JSON-RPC 메시지를 주고받습니다. 로컬 도구에 적합합니다. 실행 명령과 인자(`command`, `args`), 환경 변수(`env`)를 설정에 씁니다.
- **원격 서버(HTTP/SSE 계열)**: 네트워크 엔드포인트 URL로 접속합니다. 팀 공용 서비스에 적합합니다.

## 3. 도구 목록의 동적 갱신 (`list_changed`)

### 3.1 문제 상황
세션은 몇 시간씩 지속될 수 있습니다. 그 사이 서버 백엔드 상태가 바뀌어(예: 새 DB가 붙거나, 사용자 권한이 올라가서) **새 도구가 생길 수 있습니다.** 세션 시작 때 한 번 받은 도구 목록만 고집한다면 새 도구는 영영 쓸 수 없습니다.

### 3.2 MCP의 해법
MCP는 이를 위해 **이벤트 기반 알림 체계**를 규격에 넣었습니다.

1. 서버가 도구 목록을 변경한다.
2. 서버가 클라이언트에 `notifications/tools/list_changed` 알림을 보낸다.
3. 클라이언트는 **연결을 유지한 채** 다시 `tools/list`를 호출해 최신 목록을 받아온다.
4. 새 도구가 즉시 사용 가능해진다.

### 3.3 중요한 성질
- **재연결이 필요 없습니다.** 연결을 끊었다 다시 붙는 방식이 아니므로, 진행 중인 도구 호출(in-flight call)을 폐기할 이유도 없습니다.
- **사용자 수동 개입이 필요 없습니다.** 서버가 알림을 정상적으로 보냈다면 클라이언트가 알아서 갱신합니다. (`/mcp` 화면에서 수동으로 다시 연결하는 것은 서버가 알림을 보내지 않는 등 비정상 상황의 대응책입니다.)
- 이 동작은 **서버가 알림을 보냈을 때** 성립합니다. 알림을 구현하지 않은 서버라면 클라이언트는 변경 사실을 알 수 없습니다.

## 4. 여러 MCP 서버의 동시 사용

MCP 클라이언트는 **여러 서버와 동시에 세션을 유지**할 수 있습니다. 개수 제한이나 "한 번에 하나만 연결" 같은 제약은 없습니다.

동작 방식:
- 연결된 모든 서버의 도구가 **하나의 통합된 도구 목록**으로 모델에게 동시에 노출됩니다.
- 모델은 **같은 턴(하나의 사용자 요청) 안에서** 서버를 넘나들며 도구를 호출할 수 있습니다.
- 프롬프트의 단어와 서버 이름이 얼마나 닮았는지에 따라 도구가 선택적으로 로드되는 일은 **없습니다.** 모두 처음부터 로드되어 있습니다.
- 어떤 서버의 호출이 끝나야 다른 서버의 도구가 "선택 가능해지는" 블로킹 구조도 **없습니다.** 턴 시작 시점부터 모든 도구가 선택 가능합니다.

예: "DB 스키마를 뽑아 → 최근 Sentry 에러와 대조해 → 요약을 Slack에 올려줘"라는 한 번의 요청은, Postgres·Sentry·Slack 세 서버의 도구를 한 턴 안에서 순차적으로 호출해 처리됩니다.

> 다만 서버를 많이 붙일수록 도구 수가 늘어 선택 정확도가 떨어질 수 있다는 별개의 문제가 있습니다(8장 참조).

## 5. MCP 서버 설정: 스코프와 변수 확장

### 5.1 설정 스코프(Scope)
MCP 서버 설정은 "어디에 저장되어 누구에게 적용되는가"에 따라 스코프가 나뉩니다.

| 스코프 | 저장 위치 | 적용 범위 | 성격 |
|---|---|---|---|
| **Local (로컬)** | 개인 머신의 사용자 설정 | 그 사용자, 해당 프로젝트 | 개인 전용, 공유 안 됨 |
| **Project (프로젝트)** | 저장소의 `.mcp.json` | 저장소를 체크아웃한 모든 팀원 | 버전 관리에 커밋되어 팀 공유 |
| **User (사용자 전역)** | 개인 머신의 전역 설정 | 그 사용자의 모든 프로젝트 | 개인 전용 |

`.mcp.json` 예시(프로젝트 스코프):

```json
{
  "mcpServers": {
    "analytics": {
      "command": "node",
      "args": ["./tools/analytics-server.js", "--root", "${CLAUDE_PROJECT_DIR}"],
      "env": { "ANALYTICS_ENDPOINT": "https://internal.example.com" }
    }
  }
}
```

### 5.2 이름 충돌 시 우선순위
같은 서버 이름이 여러 스코프에 정의되면 **더 좁고 개인적인 스코프가 이깁니다: 로컬 > 프로젝트 > 사용자 전역.**

핵심 규칙:

1. **로컬 스코프가 프로젝트 스코프를 이깁니다.** 개발자가 팀 기본 설정을 자기 환경에 맞게 덮어쓸 수 있도록 의도된 설계입니다. `.mcp.json`이 Git에 들어 있다는 사실은 우선순위를 높여주지 않습니다.
2. **병합되지 않습니다.** 필드 단위로 섞이지 않고, 이긴 스코프의 **엔트리 전체가 통째로** 채택됩니다. 프로젝트 정의의 `env`가 로컬 정의에 스며드는 일은 없습니다.
3. 중복 이름은 **오류가 아닙니다.** 둘 다 차단되는 게 아니라, 우선순위에 따라 하나가 선택되어 정상 동작합니다.

실무적 함의: 팀원 한 명만 "나는 다른 엔드포인트에 붙는다"고 하면, 그 사람의 로컬 스코프에 같은 이름의 서버가 남아 있는지 의심해야 합니다.

### 5.3 변수 확장과 `CLAUDE_PROJECT_DIR`
`.mcp.json`의 `command`, `args`, `env`, `url` 같은 값에는 `${VAR}` 형태의 **환경 변수 확장**을 쓸 수 있고, 셸과 같은 **기본값 문법 `${VAR:-기본값}`** 도 지원됩니다.

여기서 중요한 개념이 **주입되는 내장 변수(injected built-in variable)** 입니다.

- `CLAUDE_PROJECT_DIR`는 프로젝트 루트의 절대 경로를 담는 변수로, **Claude Code가 자식 프로세스(MCP 서버 등)를 실행할 때 그 프로세스의 환경에 스스로 주입합니다.**
- 따라서 팀원의 셸 환경(`~/.bashrc` 등)에 이 변수가 정의되어 있지 않아도 `${CLAUDE_PROJECT_DIR}`는 **정상적으로 확장됩니다.** 빈 문자열이 되거나 확장이 실패하지 않습니다.
- 값이 없을 때 자동으로 홈 디렉터리(`~`)로 대체되는 **암묵적 기본값 같은 것은 존재하지 않습니다.** 기본값을 원하면 직접 써야 합니다.
- 그럼에도 `${CLAUDE_PROJECT_DIR:-.}`처럼 기본값을 적어두는 것이 **더 안전한 관행**입니다. 다른 실행 경로나 도구에서 설정을 재사용할 때 방어가 되기 때문입니다.

정리: **동작한다. 다만 기본값을 쓰는 편이 낫다.**

## 6. 좋은 도구 설명 쓰기 (Tool Description)

도구 설명은 모델이 도구를 고르는 근거의 대부분입니다. 설명이 부실할 때 나타나는 전형적 실패와 해법을 봅니다.

### 6.1 실패 유형 A: 커스텀 도구가 무시되고 내장 도구만 쓰인다
상황: 정밀한 커스텀 MCP 도구 `find_symbol_usages`를 만들었는데, 에이전트는 계속 내장 `Grep`만 쓴다. 설명은 `"Finds symbol usages."` 한 줄뿐이다.

원인: 설명이 **무엇을 반환하는지**, **언제 텍스트 검색보다 나은지**를 말해주지 않습니다. 모델 입장에서는 익숙하고 검증된 `Grep`을 쓰는 편이 안전해 보입니다.

해법: **설명을 다시 씁니다.** 반환값의 구체적 형태와 차별화된 사용 시점을 명시합니다.

```
find_symbol_usages: 프로젝트의 심볼 인덱스를 이용해 특정 심볼의 모든 사용처를
파일 경로·행 번호·사용 종류(호출/임포트/재export)와 함께 반환한다.
이름이 바뀐 임포트(import { a as b })를 거친 사용처, 빌드로 생성된 코드 등
텍스트 검색으로는 문자열이 일치하지 않아 놓치는 경우까지 찾아낸다.
심볼 단위의 정확한 참조 추적이 필요할 때 Grep 대신 사용한다.
```

**효과가 없는 대응들:**
- 도구 이름을 내장 도구와 같은 `grep`으로 바꾸기 → 이름 충돌과 혼란만 유발합니다.
- 내장 `Grep`을 아예 제거하기 → 범용 텍스트 검색 능력을 통째로 잃습니다.
- 매 호출마다 수동 승인 요구하기 → 사람의 부담만 늘 뿐, 모델의 판단 근거는 하나도 개선되지 않습니다.

### 6.2 실패 유형 B: 비슷한 두 도구를 구분하지 못한다
상황: `run_linter`와 `run_type_checker`의 설명이 둘 다 `"Checks code for issues."`다. 사용자가 "코드 문제 좀 봐줘"라고 하면 늘 린터만 실행된다.

원인: 두 설명이 **동일**하므로 구분할 정보가 0입니다. 모델은 사실상 임의로 고릅니다.

해법: 각 설명에 **감지하는 문제의 정확한 범주**와 **연관되는 예시 문구**를 적습니다.

```
run_linter: 코드 스타일과 구문 관례 위반(포매팅, 미사용 변수, 네이밍 규칙,
import 정렬 등)을 검사한다. "린트 돌려줘", "스타일 정리해줘"에 해당.

run_type_checker: 정적 타입 검사를 수행해 타입 불일치, 잘못된 인자 타입,
null 가능성 오류 등 타입 오류를 검출한다. "타입 에러 있는지 봐줘",
"타입 체크해줘"에 해당.
```

**효과가 없는 대응들:**
- 도구를 하나로 줄이기 → 린트든 타입 검사든 한 기능을 포기하는 것입니다.
- 사용자에게 매번 정확한 용어를 쓰라고 강요하기 → 설명은 모델 판단에 결정적 영향을 줍니다. 고칠 수 있는 것을 사용자에게 떠넘기는 셈입니다.
- 항상 둘 다 실행하고 결과를 합치기 → 불필요한 연산·시간 낭비이며 의도 파악 문제를 회피할 뿐입니다.

### 6.3 실패 유형 C: 설명 복붙으로 인한 역할 중첩
상황: 붙여넣은 텍스트 요약용으로 만든 `analyze_content`의 설명을, 업로드된 PDF 처리용 신규 도구 `analyze_document`에 거의 그대로 복사했다.

원인: 두 도구의 이름과 설명이 겹쳐 **경계가 사라졌습니다.**

해법(중첩 제거 패턴): 기존 도구의 **이름을 더 구체적으로 바꾸고, 설명의 적용 범위를 좁힙니다.**
- `analyze_content` → `summarize_pasted_text`, 설명은 "대화에 붙여넣은 평문 텍스트만" 처리한다고 한정
- `analyze_document`는 "업로드된 PDF 파일"을 담당한다고 명시

**효과가 없는 대응들:**
- 설명은 똑같이 두고 내부 함수 이름만 다르게 하기 → 모델은 내부 함수 이름을 보지 못합니다. 백엔드 라우팅은 모델의 선택 문제를 해결하지 못합니다.
- 한쪽 도구를 지우고 사용자에게 PDF 내용을 직접 붙여넣게 하기 → 기능 후퇴입니다.

### 6.4 좋은 설명의 체크리스트
1. **무엇을 하는가** (동작)
2. **무엇을 반환하는가** (반환값의 형태와 내용)
3. **언제 이 도구를 쓰는가 / 어떤 상황에는 다른 도구가 나은가** (선택 기준)
4. **인접 도구와의 경계** (겹치는 도구가 있다면 명시적으로 구분)
5. 가능하면 **사용자 발화 예시**를 붙인다

## 7. 범용 도구 대신 제약된 도구 (Constrained / Scoped Tools)

### 7.1 범용 도구의 위험
`fetch_url(url)`처럼 **임의의 URL**을 받아 무엇이든 가져오는 도구를 생각해 봅시다. 모델은 다음과 같은 URL을 넣을 수 있습니다.

- 모델이 **환각(hallucination)** 으로 지어낸, 존재하지 않는 URL
- 처리 중인 문서 안에 박혀 있던 **신뢰할 수 없는 출처의 URL** (프롬프트 인젝션 경로가 되기도 합니다)

결과는 형식이 깨진 페이지, 무관한 페이지, 최악의 경우 외부로의 원치 않는 요청입니다.

### 7.2 원칙: 범용 도구를 제약된 대안으로 교체한다
입력 공간을 **모델이 실수해도 위험한 곳에 갈 수 없도록** 좁힙니다. 대표적 수단이 **허용 목록(allowlist) 검증**입니다.

```
load_document(document_id 또는 url):
  1. 주어진 값이 허용된 문서 출처(사내 문서 저장소 도메인, 등록된 소스 목록)에
     속하는지 검증한다.
  2. 검증에 실패하면 가져오지 않고, 왜 거부되었는지 설명하는 에러를 반환한다.
  3. 검증에 성공한 경우에만 콘텐츠를 가져온다.
```

즉 `fetch_url`을 **제거하고** `load_document`로 **교체**합니다.

### 7.3 효과가 없는 대안들
- **이름만 바꾸기** (`fetch_url` → `get_document`): 접근 제어와 입력 검증이 없으므로 임의 URL 문제가 그대로 남습니다.
- **똑같은 도구를 하나 더 추가하기** (`fetch_url_v2`를 폴백으로): 제약이 하나도 추가되지 않고 도구 선택 공간만 복잡해집니다.
- **기능을 통째로 없애고 사람이 붙여넣게 하기**: 안전하긴 하나 자동화를 포기하는 것이며, "제약된 도구 도입"이라는 지침과 다릅니다.

## 8. 도구 범위 제한과 서브에이전트 아키텍처

### 8.1 최소 권한의 원칙 (Principle of Least Privilege)
보안의 고전 원칙으로, **주체에게 자기 역할 수행에 꼭 필요한 최소한의 권한만 부여**하라는 것입니다. 에이전트 설계에서는 "역할에 필요한 최소한의 도구만 노출하라"로 번역됩니다.

전형적 사고: 코드 리뷰 서브에이전트를 `Read`, `Grep`, `Glob`(읽기 전용)으로 만들어 두었는데, 리팩터링 중 "있으면 편하겠지" 하며 `Bash`와 `deploy_service`를 추가합니다. 그 직후 리뷰 에이전트가 **승인되지 않은 브랜치에 배포를 실행**하기 시작합니다.

원리: **에이전트의 전문 범위를 벗어난 도구는, 사용 가능한 이상 언젠가 오용됩니다.** 모델은 확률적으로 도구를 고르므로, 목록에 있는 위험한 도구는 결국 선택될 수 있습니다.

올바른 해법: **`Bash`와 `deploy_service`를 도구 집합에서 제거하고, 역할이 요구하는 읽기 전용 도구로 되돌립니다.**

### 8.2 왜 다른 해법들은 부족한가
- **시스템 프롬프트에 "절대 배포하지 마"라고 강하게 쓰기**: 프롬프트는 확률적 제약일 뿐입니다. 오해·환각·긴 컨텍스트에서의 지시 희석으로 뚫립니다. **도구를 주지 않는 것이 유일하게 확정적인 제약입니다.**
- **입력 스키마 검증을 강화하기**: 스키마는 "인자의 형태가 올바른가"만 봅니다. "지금 이 도구를 호출하는 것 자체가 부적절한가"나 호출 타이밍은 판단하지 못합니다.
- **도구를 더 추가해 위험한 도구를 희석하기**: 선택 공간이 복잡해져 오선택과 환각 가능성이 오히려 **높아집니다.**

### 8.3 도구 개수와 선택 정확도 — 서브에이전트로 분할
단일 에이전트에 도구가 많아지면(대략 **10~20개를 넘어서면**) 다음이 나타납니다.

- 컨텍스트 혼잡 — 도구 정의만으로 컨텍스트를 크게 차지
- **그럴듯하지만 틀린 도구 선택**(plausible-but-wrong selection)
- 비슷한 옵션 사이에서 망설이는 추론 지연

예: 리서치·초안 작성·팩트체크·포매팅을 모두 하는 리포트 생성 파이프라인 에이전트에 **18개 도구**를 전부 준 경우. 개별 도구는 각각 정상 작동하는데도 선택 정확도가 무너집니다.

해법: **역할별 서브에이전트로 분할하고, 각 서브에이전트에 그 역할에 필요한 최소한의 도구(대략 4~5개)만 노출합니다.**

```
research-agent    : 검색, 문서 로드, 인용 수집 도구만
drafting-agent    : 초안 작성/편집 도구만
fact-check-agent  : 출처 조회, 대조 도구만 (읽기 전용)
formatting-agent  : 렌더링/포매팅 도구만
```

효과: 각 에이전트가 마주하는 선택지가 줄어 정확도와 속도가 함께 올라가고, 위험한 도구가 무관한 역할에 노출되지 않아 안전성도 올라갑니다.

**설명을 더 짧게 쓰는 것은 해법이 아닙니다.** 6장에서 보았듯 설명이 짧아지면 구분 정보가 줄어 오선택이 더 늘어납니다. 문제는 설명 길이가 아니라 **도구 개수와 역할 혼재**입니다.

## 9. Claude Code 내장 도구의 역할 구분

MCP 도구를 설계할 때도, 에이전트를 운용할 때도 내장 도구의 정확한 동작을 알아야 합니다.

### 9.1 Read / Write / Edit
| 도구 | 용도 | 선행 `Read` 필요 여부 |
|---|---|---|
| `Read` | 파일 내용 읽기 | — |
| `Write` | **새 파일 생성** 또는 파일 전체 덮어쓰기 | 완전히 새 파일이면 **불필요** |
| `Edit` | 기존 파일의 일부를 정확히 치환 | **필요** (기존 내용을 알아야 치환 가능) |

핵심: 저장소 어디에도 존재하지 않는 새 파일(예: `config/feature-flags.json`)을 만들고 내용이 이미 전부 정해져 있다면, **전체 파일 경로와 전체 내용을 `Write`에 넘기는 한 번의 호출로 끝납니다.** 존재하지 않는 파일을 먼저 `Read`할 이유가 없고, 부분 치환용인 `Edit`을 쓸 대상도 없습니다. "`Write`는 언제나 선행 `Read`를 요구한다"는 것은 사실이 아닙니다(이미 존재하는 파일을 덮어쓸 때에 한해 안전장치가 걸립니다).

### 9.2 Grep vs Glob — 무엇을 검색하는 도구인가
이 둘은 자주 혼동되지만 검색 대상이 완전히 다릅니다.

- **`Glob`**: **파일 이름과 경로 패턴**을 찾습니다. 예: `**/*.js`, `src/**/invoice*.ts`. 파일 **내용은 전혀 보지 않습니다.**
- **`Grep`**: **파일 내용(텍스트)** 을 정규식으로 검색합니다. ripgrep 기반입니다.

따라서 "`parseInvoice` 함수를 호출하는 모든 위치"처럼 **코드 내용**을 찾는 작업은 `Grep`의 일입니다.
- `Glob`으로 `**/*parseInvoice*`를 돌려 파일명에 함수명이 들어간 파일만 모으는 것은 잘못입니다. 호출자 파일의 이름이 `parseInvoice`를 포함할 이유가 없습니다.
- `Glob`으로 모든 `.js`를 나열한 뒤 파일명만 보고 추측하는 것도 잘못입니다. 실제 내용을 보지 않으므로 누락과 오탐이 발생합니다.

### 9.3 `Grep`과 `.gitignore` — 반드시 알아야 할 동작
`Grep`은 ripgrep 기반이라 **기본적으로 `.gitignore` 규칙을 존중해, 무시된 파일과 디렉터리(`node_modules/`, `dist/`, `build/`, 빌드 산출물 번들 등)를 전체 검색 대상에서 제외합니다.**

그러나 중요한 예외가 있습니다.

> **`.gitignore`에 등록된 경로라도, 그 경로를 검색 명령에 직접(명시적으로) 지정하면 검색됩니다.**

그래서 "gitignore된 minified 번들 안의 호출까지 포함해 모든 호출 위치를 찾아라"라는 요구는 **두 단계**로 처리합니다.

1. 저장소 전체에 대해 `Grep`으로 `parseInvoice` 검색 (기본 무시 규칙이 적용됨)
2. gitignore된 번들 파일의 **경로를 직접 지정해** 한 번 더 `Grep`

주의: `multiline` 플래그는 **여러 줄에 걸친 패턴 매칭**을 켜는 옵션일 뿐, `.gitignore` 규칙을 무시하거나 우회하는 효과가 전혀 없습니다. 두 기능은 서로 무관합니다.

## 10. 에러 설계: MCP에서 실패를 표현하는 법

이 영역은 실무에서 가장 자주 틀리는 부분입니다. **에러에는 계층이 있고, 계층마다 표현 방법과 에이전트의 반응이 다릅니다.**

### 10.1 두 계층: 프로토콜 에러 vs 도구 실행 결과 에러

**(1) 프로토콜 수준 에러 — JSON-RPC Error**
- **언제**: 도구의 핸들러 로직이 **실행되기 전**, 요청 자체가 잘못되었을 때
- **원인 예**: 입력 스키마 위반(타입 불일치, 필수 필드 누락), JSON 파싱 실패, 존재하지 않는 메서드/도구
- **표현**: JSON-RPC 에러 응답. 대표적으로 `-32602 Invalid params`, `-32700 Parse error`, `-32601 Method not found`
- **핵심**: **핸들러 코드는 한 줄도 실행되지 않습니다.** 프로토콜/스키마 계층에서 걸러집니다.

예: `charge_card`의 스키마가 `amount`를 숫자(number)로 정의했는데 `"$45.00"`이라는 문자열이 들어온 경우 → 결제 로직이 돌기도 전에 스키마 검증 단계에서 JSON-RPC 프로토콜 에러가 납니다.

**(2) 도구 실행 결과 에러 — `isError: true`**
- **언제**: 요청은 유효해서 **핸들러가 정상 실행되었지만**, 그 결과가 실패인 경우
- **원인 예**: 카드 결제 거절(declined), DB 연결 실패, 권한 부족, 외부 API가 500 반환
- **표현**: `tools/call`이 정상 응답하되, 결과 객체 안에 `isError: true`와 사람이 읽을 수 있는 설명을 담습니다.
- **핵심**: 프로토콜은 성공, **도메인 결과가 실패**입니다.

```json
{
  "content": [{ "type": "text", "text": "카드가 거절되었습니다: 잔액 부족 (code: insufficient_funds)" }],
  "isError": true
}
```

**요약 비교**

| | 프로토콜 에러 | 도구 실행 결과 에러 |
|---|---|---|
| 발생 시점 | 핸들러 실행 **전** | 핸들러 실행 **후** |
| 원인 | 스키마/형식 위반 | 도메인·시스템 실패 |
| 표현 | JSON-RPC error (`-32602` 등) | 결과 안의 `isError: true` |
| 에이전트의 올바른 반응 | **인자를 고쳐** 다시 호출 | 결과를 읽고 사용자에게 설명하거나 대안 시도 |

같은 `charge_card` 도구에서 "금액이 문자열로 들어옴"은 프로토콜 에러, "정상 요청이었으나 카드가 거절됨"은 `isError: true`인 실행 결과 에러입니다. 두 실패는 계층이 다릅니다.

### 10.2 에러 분류와 재시도 (`errorCategory`, `isRetryable`)
많은 도구 설계에서 에러에 메타데이터를 붙여 에이전트의 재시도 판단을 돕습니다.

- **일시적 에러 (transient)**: 네트워크 타임아웃, 일시적 서비스 중단, 레이트 리밋, 일시적 락 충돌. **똑같은 요청을 다시 보내면 성공할 수 있습니다.** → `isRetryable: true` (보통 지수 백오프와 함께)
- **영구적/유효성 에러 (validation / permanent)**: 필수 필드 누락, 잘못된 형식, 존재하지 않는 리소스, 권한 없음. **입력이나 상태가 바뀌지 않는 한 몇 번을 다시 보내도 결과가 같습니다.** → `isRetryable: false`

**전형적 버그**: `update_inventory`가 필수 필드 `sku` 누락에 대해 `errorCategory: "transient"`, `isRetryable: true`를 반환하도록 잘못 분류한 경우. 에이전트는 "일시적이라니 다시 보내면 되겠지" 하고 **똑같이 잘못된 요청을 무한히 재시도**합니다. 영원히 성공하지 않으며 시간·토큰·API 호출 한도를 태웁니다. "나중에 다른 요청이 그 필드를 채워줄 것"이라는 기대는 성립하지 않습니다. 각 호출은 독립적이고, 누락된 필드는 **이 요청**에 들어 있어야 합니다.

**올바른 수정**: 이것은 유효성(영구) 에러이므로 `isRetryable: false`로 분류하고, 에러 메시지에 **무엇이 잘못되었고 어떻게 고쳐야 하는지**를 명시합니다.

```json
{
  "content": [{ "type": "text",
    "text": "필수 필드 'sku'가 누락되었습니다. sku는 문자열이며 예: \"ABC-1234\". 요청에 sku를 추가한 뒤 다시 호출하세요." }],
  "isError": true,
  "errorCategory": "validation",
  "isRetryable": false
}
```

이렇게 하면 에이전트는 맹목적 재시도 대신 **인자를 고쳐 재호출**하는, 실제로 성공 가능한 행동을 택합니다.

> 판별 기준: **"입력을 하나도 바꾸지 않고 그대로 다시 보냈을 때 성공할 가능성이 있는가?"** 있으면 transient, 없으면 permanent/validation.

### 10.3 "결과 없음"은 에러가 아니다
가장 흔하고 파급이 큰 실수입니다.

상황: `search_tickets`가 특정 고객에 대해 쿼리를 **정상 실행**했고 조건에 맞는 티켓이 **0건**이었다. 도구가 `isError: true`와 함께 `"No tickets found"`를 반환한다. 조정 에이전트는 이를 시스템 장애로 이해하고 사용자에게 "시스템 오류가 발생했습니다"라고 사과한다.

원인: **0건은 성공적인 실행 결과입니다.** DB는 잘 붙었고, 쿼리는 잘 돌았고, 답이 "없음"일 뿐입니다. 이를 에러로 표시하면 에이전트가 사실을 오해하고 사용자에게 잘못된 정보를 전달합니다.

**올바른 수정**: `isError: false`(성공)로 반환하고, **빈 배열 형태의 구조화된 데이터(structured content)** 를 함께 줍니다.

```json
{
  "content": [{ "type": "text", "text": "조건에 맞는 티켓이 0건입니다." }],
  "structuredContent": { "tickets": [], "count": 0 },
  "isError": false
}
```

에이전트는 이제 "검색은 정상 수행되었고 해당 고객의 티켓은 없습니다"라고 정확히 안내할 수 있습니다.

**효과가 없거나 더 나쁜 대응들:**
- `isError: true`를 유지한 채 `errorCategory`만 `transient`로 바꾸기 → 에이전트가 "언젠가 티켓이 생기겠지" 하며 동일 검색을 무한 재시도합니다. 상황이 더 나빠집니다.
- 에러 문구만 부드럽게 다듬기 → 여전히 에러 플래그가 켜져 있으므로 에이전트의 오해는 그대로입니다.

**규칙**: `isError: true`는 **도구 수행 자체가 실패했을 때만** 씁니다. 연결 실패, 권한 오류, 구문 오류, 외부 시스템 장애 등. **정상 실행 + 빈 결과 = 성공**입니다.

## 11. 전체 원칙 요약

1. **모델은 이름과 설명만 본다.** 도구 선택 문제는 대개 이름·설명·도구 집합을 고쳐서 해결한다.
2. **설명에는 반환값과 사용 시점을 쓴다.** 비슷한 도구끼리는 감지 범주와 예시 문구로 경계를 명확히 한다.
3. **중첩되는 도구는 이름을 구체화하고 범위를 한정**해 겹침을 제거한다.
4. **범용 도구는 허용 목록 검증이 붙은 제약된 도구로 교체**한다. 이름만 바꾸거나 복제 도구를 더하는 것은 무의미하다.
5. **최소 권한.** 역할 밖의 도구는 프롬프트로 막지 말고 **아예 주지 않는다.**
6. **도구가 10~20개를 넘으면 역할별 서브에이전트로 쪼개고** 각각 4~5개만 노출한다.
7. **MCP 클라이언트는 여러 서버에 동시 연결**되며, 모든 도구를 한 턴 안에서 교차 호출할 수 있다.
8. **`list_changed` 알림을 받으면 연결 유지한 채 `tools/list`를 재요청**해 도구 목록을 자동 갱신한다.
9. **설정 스코프 충돌 시 로컬이 프로젝트를 이기고, 병합 없이 통째로 대체**된다.
10. **`CLAUDE_PROJECT_DIR`는 Claude Code가 자식 프로세스 환경에 주입**하므로 셸에 없어도 확장된다. 그래도 기본값을 쓰는 편이 안전하다.
11. **`Glob`은 파일명, `Grep`은 파일 내용.** `Grep`은 `.gitignore`를 존중하지만 **경로를 직접 지정하면 무시된 파일도 검색**한다.
12. **새 파일 생성은 `Write` 한 번.** 선행 `Read` 불필요.
13. **에러는 두 계층.** 스키마 위반은 핸들러 실행 전 JSON-RPC 프로토콜 에러, 도메인 실패는 결과 안의 `isError: true`.
14. **재시도 가능 여부는 "입력을 안 바꾸고 다시 보내면 성공할 수 있는가"로 판단.** 유효성 에러를 transient로 분류하면 무한 재시도 루프가 생긴다.
15. **빈 결과는 에러가 아니다.** `isError: false` + 빈 배열로 반환한다.

## 12. 용어 사전 (Glossary)

| 영어 용어 | 한국어 설명 |
|---|---|
| **MCP (Model Context Protocol)** | AI 클라이언트와 외부 기능 제공 서버를 잇는 표준 프로토콜. JSON-RPC 2.0 기반 |
| **MCP Server** | 도구·리소스·프롬프트를 노출하는 프로그램 (예: Postgres, Sentry, Slack 서버) |
| **MCP Client** | 서버에 접속해 도구 목록을 받아 모델에 제공하고 호출을 중계하는 쪽. Claude Code가 해당 |
| **JSON-RPC 2.0** | 요청/응답과 단방향 알림을 정의한 원격 호출 규격. MCP의 메시지 형식 |
| **stdio server** | 클라이언트가 자식 프로세스로 실행하고 표준 입출력으로 통신하는 로컬 MCP 서버 |
| **spawned process / environment** | 클라이언트가 새로 띄운 자식 프로세스와 그 프로세스에 주어지는 환경 변수 집합 |
| **`tools/list`** | 서버의 도구 목록을 요청하는 MCP 메서드 |
| **`tools/call`** | 특정 도구를 인자와 함께 실행 요청하는 MCP 메서드 |
| **`notifications/tools/list_changed`** | 도구 목록이 변경되었음을 서버가 클라이언트에 알리는 MCP 알림. 받은 클라이언트는 연결 유지 상태로 `tools/list`를 재요청 |
| **Notification** | 응답을 기대하지 않는 단방향 JSON-RPC 메시지 |
| **in-flight tool call** | 이미 전송되어 아직 결과가 오지 않은, 진행 중인 도구 호출 |
| **Tool Description** | 도구가 무엇을 하고 언제 쓰이는지 적은 자연어 설명. 모델의 도구 선택 근거 |
| **Input Schema** | 도구 인자의 이름·타입·필수 여부를 정의한 JSON Schema |
| **Tool Selection** | 모델이 여러 도구 중 하나를 고르는 행위 |
| **Plausible-but-wrong selection** | 그럴듯해 보이지만 의도와 다른 도구를 고르는 실패 |
| **Tool Disambiguation** | 이름·설명을 구체화해 비슷한 도구들의 경계를 분명히 하는 작업 |
| **Generic Tool** | `fetch_url`처럼 입력 범위가 넓고 무엇이든 할 수 있는 범용 도구 |
| **Constrained / Scoped Tool** | 입력과 대상 범위를 좁히고 검증을 붙인 전용 도구 |
| **Allowlist** | 허용된 값(도메인, 출처 등)만 통과시키는 목록 기반 검증 방식 |
| **Hallucination (환각)** | 모델이 존재하지 않는 정보(예: 가짜 URL)를 사실처럼 생성하는 현상 |
| **Principle of Least Privilege** | 최소 권한의 원칙. 역할 수행에 꼭 필요한 최소한의 권한(도구)만 부여 |
| **Tool Scoping** | 에이전트가 사용할 수 있는 도구 집합을 역할에 맞게 제한하는 것 |
| **Read-only tools** | 상태를 바꾸지 않는 도구들 (Read, Grep, Glob 등) |
| **Subagent** | 특정 역할에 특화되어 자기만의 축소된 도구 집합을 갖는 하위 에이전트 |
| **Turn (턴)** | 사용자 요청 하나에 대응하는 에이전트의 처리 단위. 한 턴 안에 여러 도구 호출이 들어갈 수 있음 |
| **Scope (설정 스코프)** | 설정이 저장·적용되는 범위. Local / Project / User |
| **Local scope** | 개인 머신에만 저장되는 설정. 이름 충돌 시 가장 높은 우선순위 |
| **Project scope** | 저장소의 `.mcp.json`에 담겨 팀과 공유되는 설정 |
| **`.mcp.json`** | 프로젝트 스코프 MCP 서버 정의를 담는, 버전 관리에 커밋되는 설정 파일 |
| **Name collision** | 여러 스코프에 같은 서버 이름이 정의되어 충돌하는 상황. 우선순위가 높은 쪽 엔트리가 통째로 채택되며 병합되지 않음 |
| **Field-by-field merge** | 설정을 필드 단위로 섞는 방식. MCP 스코프 충돌에서는 **일어나지 않음** |
| **Variable expansion** | 설정 값 안의 `${VAR}`를 실제 값으로 치환하는 것 |
| **Fallback syntax `${VAR:-default}`** | 변수가 없을 때 쓸 기본값을 지정하는 셸식 문법 |
| **`CLAUDE_PROJECT_DIR`** | 프로젝트 루트 절대 경로를 담는 내장 변수. Claude Code가 자식 프로세스 환경에 자동 주입 |
| **Environment injection** | 클라이언트가 자식 프로세스 환경에 변수를 스스로 넣어 주는 것 |
| **Grep** | 파일 **내용**을 정규식으로 검색하는 도구. ripgrep 기반 |
| **Glob** | 파일 **이름/경로 패턴**을 찾는 도구. 내용은 보지 않음 |
| **ripgrep** | 빠른 재귀 텍스트 검색기. 기본적으로 `.gitignore`를 존중 |
| **`.gitignore`** | Git이 무시할 경로 목록. Grep의 기본 검색에서도 제외되지만, 경로를 직접 지정하면 검색됨 |
| **multiline flag** | 여러 줄에 걸친 패턴 매칭을 켜는 검색 옵션. `.gitignore` 동작과는 무관 |
| **minified bundle** | 빌드로 압축·난독화된 산출물 파일. 보통 gitignore 대상 |
| **Read / Write / Edit** | 각각 파일 읽기 / 새 파일 생성·전체 덮어쓰기 / 기존 파일 부분 치환 도구 |
| **Protocol Error** | 핸들러 실행 **전** 스키마·형식 위반으로 발생하는 JSON-RPC 에러 |
| **`-32602 Invalid params`** | 잘못된 인자에 대한 표준 JSON-RPC 에러 코드 |
| **`-32700 Parse error`** | JSON 파싱 실패에 대한 표준 JSON-RPC 에러 코드 |
| **Tool Execution Error** | 핸들러가 실행된 뒤 도메인·시스템 실패로 발생하는 에러. 결과 안 `isError: true`로 표현 |
| **`isError`** | 도구 실행 결과가 실패인지 나타내는 불리언 플래그 |
| **`errorCategory`** | 에러 성격 분류 값 (`transient`, `validation`/`permanent` 등) |
| **`isRetryable`** | 동일 요청 재시도가 의미 있는지 나타내는 플래그 |
| **Transient error** | 타임아웃·레이트 리밋 등, 그대로 다시 보내면 성공할 수 있는 일시적 에러 |
| **Validation / Permanent error** | 필수 필드 누락·형식 오류 등, 입력을 고치지 않으면 영원히 실패하는 에러 |
| **Retry loop (무한 재시도 루프)** | 유효성 에러를 transient로 잘못 분류해 동일 요청을 끝없이 재시도하는 실패 패턴 |
| **Empty result** | 정상 실행되었으나 조건에 맞는 데이터가 0건인 상태. **에러가 아님** |
| **Structured content** | 텍스트 외에 기계가 파싱할 수 있는 구조화된 결과 데이터 (예: 빈 배열 `[]`) |
| **Declined charge** | 결제가 정상 처리 시도 후 거절된 도메인 실패. 프로토콜 에러가 아니라 `isError: true`로 보고 |
