# 3. 훅(Hooks)과 권한 제어

## 이 장에서 다루는 것

- 훅이란 무엇이며 왜 프롬프트보다 강한가 (결정론 vs 확률론, 관심사의 분리)
- 훅 생애주기 이벤트 전체 목록과 각 이벤트의 시점·능력
- `PreToolUse`의 판정 구조: `permissionDecision`(`allow`/`deny`/`ask`), `permissionDecisionReason`, `updatedInput`, `additionalContext`, `async`/`asyncTimeout`
- `PostToolUse`의 출력 가공 필드: `updatedToolOutput`, `updatedMCPToolOutput`, `additionalContext`, `systemMessage`
- 매처(Matcher): 정규표현식 앵커링, 오버매칭, 교대(`|`), MCP 네임스페이스 규칙(`mcp__<서버>__<도구>`)
- 여러 훅의 충돌 해결(가장 제한적인 결과 적용)과 훅 체이닝
- 하드 게이팅, Fail-Closed, 재시도 루프 차단, 상태 결합도 저하
- 권한과 설정 계층: 서브에이전트 `tools` 필드와 deny 규칙 상속
- 각 절의 흔한 함정과 오해

---

## 3.1 훅이란 무엇이고 왜 필요한가

**훅(Hook)** 은 에이전트 실행 생애주기의 특정 시점에 자동으로 실행되도록 등록해 두는 **내 코드**(콜백)입니다. LLM이 만들어내는 것이 아니라 **런타임이 호출**하므로, 모델의 판단과 무관하게 **반드시 실행됩니다.**

핵심은 이것입니다: **훅은 모델의 생성 과정 바깥(outside of model generation)에서 동작합니다.**

시스템 프롬프트에 "500달러 넘는 환불은 하지 마", "업무 시간 외에는 삭제하지 마"라고 아무리 강하게 써도, LLM은 **확률적(probabilistic)** 으로 동작합니다. 대부분 따르지만 100%는 아닙니다. 훅은 코드이므로 `if amount > 500:` 은 매번 똑같이 동작합니다 — **결정론적(deterministic)** 입니다.

| | 시스템 프롬프트 | 훅 |
|---|---|---|
| 성격 | 확률적 — 준수 **가능성**에 영향 | 결정론적 — 매번 강제 실행 |
| 작동 위치 | 모델의 생성 과정 | 코드 런타임 |
| 보장 수준 | "대체로" | "항상" |
| 적합 용도 | 스타일, 어조, 선호 방침 | 보안, 컴플라이언스, 순서 강제 |

훅으로 강제한 규칙은 다음에도 뚫리지 않습니다.

- 사용자가 이상하고 낯선 표현(unusual phrasing)으로 요청해도 우회되지 않음
- 도구 결과 안에 숨겨진 **프롬프트 주입(Prompt Injection)** 공격으로도 우회되지 않음
- 모델이 복잡한 지시를 단순히 잘못 적용(misapply)해도 뚫리지 않음

> **프롬프트 주입(Prompt Injection)**: 외부 데이터(웹페이지 내용, 도구 반환값, 사용자 입력 등) 안에 "이전 지시를 무시하고 ~하라" 같은 악의적 문장을 심어두어, LLM이 그것을 개발자의 지시로 착각하게 만드는 공격. LLM은 지시와 데이터를 근본적으로 구분하지 못하기 때문에 프롬프트만으로는 완전히 막을 수 없습니다.

### 판단 기준: 되돌릴 수 없음(irreversibility)과 피해 규모

금전 이동, 데이터 삭제, 외부 전송, 규정 준수 사안처럼 **되돌릴 수 없는(irreversible / hard to reverse)** 작업은 단 한 번의 누락만으로도 복구 불가능한 컴플라이언스 결함이 됩니다. 반대로 문장 다듬기처럼 실패해도 영향이 작은 일은 프롬프트 지시로 충분합니다.

"시스템 프롬프트에 이미 써 뒀으니 훅은 낭비"라는 생각이 위험한 이유가 이것입니다.

### 관심사의 분리(Separation of Concerns) — 훅이 근본적으로 강한 이유

시나리오: 환불 정책을 모르는 다른 팀원이 나중에 시스템 프롬프트를 수정하다가 "환불은 500달러까지"라는 문장을 지웠다고 합시다.

- 규칙이 **프롬프트 문장으로만** 존재했다면 → 그 순간 규제가 **조용히 사라집니다.** 아무도 모르게, 아무 오류도 없이.
- 규칙이 **훅으로** 존재한다면 → 훅은 프롬프트와 **분리된 애플리케이션 코드**에 등록되어 있으므로 프롬프트를 어떻게 고치든 그대로 작동합니다. 이 규제를 없애려면 코드를 고쳐야 하고, 코드 변경은 리뷰·버전 관리·테스트를 거칩니다.

### 흔한 오해 모음

**"프롬프트를 더 강하게 쓰면 되지 않나?" 계열**

- **"같은 규칙을 3번 반복해서 쓰면?"** → 눈에 더 잘 띄게(salient) 만들어 위반 확률을 낮출 수는 있지만 0으로 만들지는 못합니다. 확률적 시스템은 반복 강조로 결정론이 되지 않습니다.
- **"`temperature`를 0.1로 낮추면?"** → `temperature`는 생성의 무작위성(randomness)을 줄이는 파라미터입니다. 출력이 더 일관되게는 되지만, 모델이 지시를 애초에 **잘못 해석**하고 있다면 그 잘못된 해석을 더 일관되게 반복할 뿐입니다.
- **"컨텍스트 윈도우를 키우면?"** → 지시를 기억하느냐의 문제가 아니라 준수 보장의 문제입니다.
- **"매 티켓마다 순서를 상기시키는 메시지를 주입하면?"** → 역시 확률 조정일 뿐 하드 차단이 아닙니다.
- **"프롬프트에는 금액 같은 숫자를 쓸 수 없나?"** → 그렇지 않습니다. 시스템 프롬프트에 달러 임계값이든 어떤 숫자든 자유롭게 쓸 수 있습니다. 훅을 쓰는 이유는 "숫자를 쓸 수 없어서"가 아니라 **"프롬프트는 강제력이 없어서"** 입니다.
- **"훅이 프롬프트보다 쓰기 빨라서?"** → 아닙니다. 훅은 오히려 조건 로직을 코드로 정확히 구현해야 하므로 더 엄밀한 작업입니다. 훅의 가치는 속도가 아니라 **보장성**입니다.

**훅의 정체에 대한 오해**

- 훅은 샘플링 파라미터(temperature 등)를 조절해 모델의 "신뢰도 점수"를 높이는 장치가 **아닙니다.** 훅은 도구 호출을 가로채는 코드 레벨 인터셉터입니다.
- 훅이 시스템 프롬프트와 같은 설정 파일에 저장되어 프롬프트 저장 시 자동 검증해 주는 구조가 **아닙니다.**
- 훅이 매 세션 시작마다 템플릿에서 프롬프트를 재생성해 주는 것도 **아닙니다.**
- SDK 런타임이 시스템 프롬프트의 자연어 규칙을 자동으로 권한 검사 코드로 번역해 주지 **않습니다.** 두 방식은 기능적으로 전혀 다릅니다.
- 훅이 `deny`를 반환하면 **실제 도구 실행 자체가 차단됩니다.** 화면 표시만 바뀌고 뒤에서 실행되는 것이 아닙니다.
- 훅은 Python SDK 전용이 **아닙니다.** TypeScript SDK 등 주요 SDK가 공통으로 훅 등록을 지원합니다.

## 3.2 훅 생애주기 이벤트

에이전트 루프의 흐름 위에 훅이 어디에 붙는지 보면 이해가 쉽습니다.

```
모델이 도구 호출 요청 생성
        ↓
   [ PreToolUse 훅 ]   ← 도구가 실행되기 "전". 입력(tool_input)을 보고 허용/거부/수정
        ↓
   실제 도구 실행 (MCP 서버 호출, 파일 읽기 등)
        ↓
   [ PostToolUse 훅 ]  ← 도구가 실행된 "후", 결과가 모델에게 가기 "전". 출력을 보고 가공
        ↓
   모델이 결과를 받아 다음 판단
```

전체 이벤트 목록:

| 훅 이벤트 | 실행 시점 | 차단 가능? | 대표 용도 |
|---|---|---|---|
| `SessionStart` | 세션이 시작될 때 한 번 | ❌ | 초기 컨텍스트 주입, 환경 정보 안내 |
| `UserPromptSubmit` | 사용자가 프롬프트를 제출할 때마다 | — | 입력 검증, 컨텍스트 주입, 참고 정보 덧붙이기 |
| `PreToolUse` | 도구가 실행되기 **직전** | ✅ 가능 | 권한 검사, 인자 검증·수정, 실행 차단 |
| `PostToolUse` | 도구 실행 **직후, 결과가 모델에 가기 전** | ❌ (이미 실행됨) | 출력 정규화·잘라내기·마스킹, 로깅, 후처리 |
| `SubagentStop` | 서브에이전트가 작업을 마칠 때 | ❌ | 결과 집계, 완료 감지, 로깅 |
| `Stop` | 메인 에이전트가 턴을 마칠 때 | ❌ | 최종 검증, 마무리 처리 |
| `Notification` | 권한 요청 등 알림 이벤트 발생 시 | ❌ | 상태 메시지 전달, 사용자 알림, 로깅 |

**시점을 헷갈리지 않는 요령**: 이름의 `Pre`/`Post`/`Stop`이 그대로 시점입니다.

- **`PreToolUse`는 실행 전이므로 결과를 미리 볼 수 없고**, **`PostToolUse`는 실행 후이므로 실행을 막을 수 없습니다.**
- **입력을 검사/차단/수정 → `PreToolUse`**
- **출력을 가공/정규화 → `PostToolUse` + `updatedToolOutput`**
- **사후 감사 로그만 남기기** → `PostToolUse`로 가능하지만, 이미 실행된 뒤이므로 **사고를 예방하지는 못합니다.** 무단 고액 환불을 "막고 싶다"면 `PostToolUse`는 답이 아닙니다.

### PostToolUse는 사후약방문

환불이 이미 나간 뒤에 플래그를 다시 검사해 봐야, 되돌릴 수 없는 작업은 이미 부작용(side-effect)을 남겼습니다. 되돌리기 자체가 실패할 수도 있습니다.

### Notification 훅의 한계와 오해

`Notification` 훅은 **상태 메시지·로깅·관찰(observability) 전용**입니다. 특정 도구 이름에 매처를 걸 수는 있지만(그건 가능합니다), **`permissionDecision`을 반환할 수 없어 호출을 막지 못합니다.** "검증 없이 환불이 호출되면 경고 로그를 남긴다"는 설계는, 경고가 남을 때쯤이면 환불이 이미 실행된 뒤입니다.

또한 `Notification`은 모델이 실제로 수신하는 도구 결과를 치환하는 표준적인 수단이 **아닙니다.**

`Notification`에 대한 흔한 오해 (모두 사실 아님):

- 도구 이름 매칭이 아예 불가능해서 모든 도구 호출마다 발동한다 ✗
- 도구 호출 **전**에 실행되며 사람이 매번 클릭해야 진행된다 ✗
- Python SDK에서만 쓸 수 있고 TypeScript SDK에는 훅 등록 기능이 없다 ✗

### SubagentStop: 병렬 서브에이전트 결과 집계

여러 서브에이전트를 병렬로 띄웠을 때, "각자 정말 끝났는가"와 "각자 무엇을 찾았는가"를 알아야 최종 종합을 할 수 있습니다. 이를 위한 전용 훅이 `SubagentStop`입니다. 각 서브에이전트가 자기 작업을 마치는 시점에 발화하므로, 완료 시점마다 결과를 로깅하거나 공용 저장소에 모을 수 있습니다.

다른 훅이 왜 안 되는지도 시점으로 설명됩니다.

- `Notification` — 권한 요청 같은 알림 이벤트용이며 조사 결과 데이터를 나르지 않습니다.
- `PreToolUse` — 실행 **전**이므로 아직 존재하지 않는 결과를 미리 볼 수 없습니다.
- `UserPromptSubmit` — 최초 프롬프트 제출 시점이므로 아직 서브에이전트가 시작도 하지 않았습니다.

## 3.3 `PreToolUse` — 판정 구조

`PreToolUse` 훅은 세 가지 일을 할 수 있습니다.

1. **통과(allow)** — 그대로 실행하게 둔다
2. **수정(updatedInput)** — 도구에 전달될 입력을 바꿔서 실행하게 한다
3. **거부(deny)** — 실행 자체를 막고, 사유를 모델에게 알려준다

**받는 것**: `tool_input` — 모델이 그 도구에 넘기려는 인자 객체. 예를 들어 `refund_customer` 도구라면 `tool_input.amount`, `tool_input.customer_id` 같은 필드가 들어 있습니다.

**반환하는 것**: `hookSpecificOutput` 안에 담긴 판정. 핵심 필드가 **`permissionDecision`** 입니다.

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Use the sandboxed low-privilege wrapper script instead"
  }
}
```

### `permissionDecision`의 세 가지 값

| 값 | 동작 | 언제 쓰나 |
|---|---|---|
| `allow` | 사람 확인 없이 도구를 그대로 실행 (사용자에게 묻지 않음) | 안전하다고 판정된 호출을 자동 승인 |
| `deny` | 도구 호출을 **취소(cancel)**. 실행 자체가 일어나지 않고, 모델에게 거부 사실이 전달됨 | 절대 허용하면 안 되는 호출 |
| `ask` | 실행을 일시 정지하고 **사람에게 대화형 승인 프롬프트**를 띄움 | 사람의 판단이 필요한 회색지대 |

`deny`를 반환하면 도구는 **아예 실행되지 않습니다.** 환불 예시로 말하면, 돈이 나가는 일이 애초에 발생하지 않습니다.

> `permissionDecision`에 `"defer"`(무기한 보류) 같은 값은 **표준 동작이 아닙니다.** 정상적으로 검증이 끝난 상황에서 시스템을 무기한 멈추는 것은 설계로서도 잘못입니다.

### 관련 필드들

- **`permissionDecisionReason`**: 거부/질의 사유 문자열. `deny`와 `ask` 모두에서 유효하며, 세션을 에러로 종료시키지 않습니다.
- **`updatedInput`**: 도구에 전달될 **입력 인자를 훅이 바꿔치기**할 수 있는 필드. 즉 훅은 통과/차단만이 아니라 **입력 변환(Input Rewriting)** 도 할 수 있습니다.
- **`additionalContext`**: 모델에게 추가 정보를 덧붙여 주는 필드(강제력은 없는 참고 정보).
- **`async` / `asyncTimeout`**: 훅 실행을 비동기로 돌리거나 타임아웃(밀리초)을 조절하는 설정. **주의: 이것들은 실행 타이밍/시간 제어일 뿐, 사람에게 승인을 요청하는 기능이 전혀 아닙니다.** 사람 승인은 오직 `permissionDecision: "ask"`가 담당합니다.

### `permissionDecisionReason`은 단순 사유가 아니라 유도 통로

`deny`일 때 이 사유 문자열이 **모델에게 피드백으로 전달**됩니다. 모델은 왜 거부됐는지 이해하고, 위 JSON 예시처럼 "그럼 샌드박스된 저권한 래퍼 스크립트를 쓰자"는 **대안 행동(subsequent action)** 을 스스로 취할 수 있습니다. 에스컬레이션(사람 검토자에게 전달) 같은 다른 경로로 흐름을 전환하는 것도 마찬가지입니다.

즉 `deny`는 단순 차단이 아니라 **모델을 올바른 방향으로 유도하는 통로**입니다.

### 기본 예시

```python
def pre_tool_use(tool_name, tool_input, session_state):
    if tool_name == "refund_customer" and tool_input["amount"] > 500:
        return {
            "permissionDecision": "deny",
            "reason": "500달러를 초과하는 환불은 사람 검토자에게 전달되어야 합니다."
        }
    return {"permissionDecision": "allow"}
```

### 콜백이 받는 데이터: `input_data`

콜백에는 `input_data`(딕셔너리)가 전달되며, 그 안의 `tool_input`에 도구로 넘어갈 인자가 그대로 들어 있습니다.

```python
async def block_restricted_refund(input_data, tool_use_id, context):
    args = input_data["tool_input"]
    if args.get("amount", 0) > 500 and args.get("category") == "restricted":
        return {
            "hookSpecificOutput": {
                "hookEventName": "PreToolUse",
                "permissionDecision": "deny",
                "permissionDecisionReason": "제한 카테고리의 $500 초과 환불은 차단됩니다.",
            }
        }
    return {}   # 아무것도 반환하지 않으면 그대로 진행
```

> `PreToolUse` 훅이 도구 인자를 볼 수 없다는 말은 **사실이 아닙니다** — `input_data["tool_input"]`으로 전부 볼 수 있습니다.

## 3.4 `ask`: 사람 개입(Human-in-the-Loop)과 위험 기반 차등 적용

정책이 "일정 금액 구간(예: $500~$1000)의 환불은 **완전 차단도 아니고 자동 실행도 아니고**, 사람 검토자가 승인/거절하게 하라"고 요구한다면 정답은 `permissionDecision: "ask"` 하나뿐입니다.

`ask`를 쓰면 도구 호출이 대기 상태가 되고 검토자에게 노출(surface)되며, 사람이 승인하면 실행되고 거절하면 실행되지 않습니다. 되돌릴 수 없는 작업에 대한 **표준 감독 장치**입니다.

효과 없는 대안들:

- `deny` + 사유 문구로 "사람에게 연락해 보라"고 모델에게 시키기 → **승인 인터페이스를 띄우는 것이 아닙니다.** 그냥 차단입니다.
- `allow` + `additionalContext`로 "나중에 금액을 언급해 달라" → **이미 환불이 실행된 뒤**입니다. 사전 승인 정책 위반입니다.
- `async: true`, `asyncTimeout: 60000` → 시간만 벌 뿐 승인 UI를 만들지 않습니다.

### 위험 기반 차등 적용(Risk-based permission)

도구마다 위험도와 **가역성(reversibility)** 이 다르므로 결정을 달리 줍니다.

| 작업 | 성격 | 적절한 결정 |
|---|---|---|
| 마스킹된 주문 내역 조회 | 읽기 전용, 민감정보 마스킹, 저위험 | `allow` (자동 허용) |
| 환불 처리 | 금전적, **되돌릴 수 없음** | `ask` (사람 확인 후 진행) |

잘못된 조합들:

- 둘 다 `allow` → 신원 미검증 상태에서 되돌릴 수 없는 금전 작업까지 자동 허용. 심각한 보안·재무 위험.
- 둘 다 `deny` → 위험도 무관 일괄 차단. 위험 기반 제어의 취지에 어긋나고 UX를 파괴함.
- 읽기에 `ask`, 환불에 `deny` → 저위험 작업을 불필요하게 지연시키고, "확인 후 실행"이라는 `ask`의 용도를 엉뚱한 곳에 배치.

## 3.5 `updatedInput` — 인자 정규화·강제 덮어쓰기

`PreToolUse` 훅은 단순히 허용/거부만 하는 것이 아니라, **모델이 만든 인자를 안전한 값으로 교체**할 수 있습니다. `permissionDecision: "allow"` 와 함께 `updatedInput`을 반환하면 됩니다.

**왜 필요한가**: 모델은 대화 맥락에서 값을 "다시 타이핑(retype)"할 때 오타를 내거나, 다른 값과 혼동하거나, 환각(Hallucination)으로 없는 값을 만들어낼 수 있습니다. 특히 고객 ID, 계좌 번호 같은 식별자는 한 글자만 틀려도 엉뚱한 사람에게 처리가 나갑니다.

### 패턴 A: 정규화 + 임계값 검사 (같은 훅 안에서)

```python
def pre_tool_use(tool_name, tool_input):
    if tool_name != "process_payment":
        return {"permissionDecision": "allow"}

    # 1) 정규화: "$1,250.00" 도 1250.0 도 모두 float 로
    raw = tool_input["amount"]
    amount = float(str(raw).replace("$", "").replace(",", "")) if isinstance(raw, str) else float(raw)

    # 2) 정규화된 값으로 임계값 검사
    if amount > COMPLIANCE_THRESHOLD:
        return {
            "permissionDecision": "deny",
            "permissionDecisionReason": f"금액 {amount}이(가) 컴플라이언스 한도를 초과했습니다.",
        }

    # 3) 통과: 정규화된 입력으로 갱신
    return {
        "permissionDecision": "allow",
        "updatedInput": {**tool_input, "amount": amount},
    }
```

**설계 원칙: 정규화와 그 정규화된 값에 대한 검증은 같은 훅 안에서 한다.**

왜 나누면 안 될까요?

- 정규화는 `PreToolUse`, 검증은 `PostToolUse`로 나누면 — 검증 시점에는 **이미 결제가 실행된 뒤**입니다. 사후 확인은 사전 차단이 아닙니다.
- `PreToolUse` 훅 두 개로 나누면 — 훅 간 실행 순서와 `updatedInput`의 전파 시점에 의존하게 됩니다. 두 번째 훅이 정규화 이전 값을 보게 될 위험이 있으므로, 순서에 의존하지 않는 단일 훅이 더 안전하고 결정론적입니다.

일반화하면: **판단에 필요한 값의 생성과 그 값에 대한 판단은 같은 원자적 단위 안에 두어라.**

### 패턴 B: "검증된 값만 사용하기"

1. 앞선 단계에서 `get_customer` 같은 검증 도구가 성공적으로 실행됨
2. 검증된 `customer_id`를 **세션 상태(session state)** 에 저장해 둠
3. 이후 `process_refund` 호출 시 `PreToolUse` 훅이 개입:
   - 세션 상태에 검증된 ID가 **없으면** → `deny`
   - **있으면** → `allow` + `updatedInput`으로 `customer_id`를 세션의 검증된 값으로 덮어씀

```python
def pre_tool_use(tool_name, tool_input, session_state):
    if tool_name == "process_refund":
        verified_id = session_state.get("verified_customer_id")
        if not verified_id:
            return {"permissionDecision": "deny", "reason": "고객 검증이 선행되어야 합니다."}
        return {
            "permissionDecision": "allow",
            "updatedInput": {**tool_input, "customer_id": verified_id},
        }
    return {}
```

이 방식의 장점은 **자동화를 유지하면서 안전성을 확보**한다는 것입니다. 대안들이 왜 열등한지:

- 빈 객체를 반환해 그냥 통과시키기 → 세션에 올바른 ID가 있어도 모델이 넘긴 잘못된 값이 그대로 실행됩니다. **검증의 존재가 사용을 보장하지 않습니다.**
- 매번 `"ask"`로 사람에게 재입력 요청 → 이미 검증이 성공한 상황인데도 사람이 매번 개입해야 하므로 자동화 가치가 사라집니다.

## 3.6 `PostToolUse` — 출력 정규화와 반환 필드

**언제 쓰는가**: 도구가 반환한 **결과(출력)** 가 지저분하거나 형식이 제각각이어서, 모델이 그것을 보기 **전에** 정리해야 할 때.

### 반환 필드 비교

| 필드 | 역할 | 적용 범위 |
|---|---|---|
| `updatedToolOutput` | 도구 출력을 **교체(replace)** | **내장 도구 + MCP 도구 모두** — 표준·범용 필드 |
| `updatedMCPToolOutput` | 도구 출력을 교체 | **MCP 도구 전용**, 레거시 필드 |
| `additionalContext` | 기존 출력에 **정보를 덧붙임** (교체 아님) | — |
| `systemMessage` | 사용자 UI에 안내 메시지 표시 | 모델에게 가는 도구 출력이 아님 |

따라서 MCP 도구와 내장 도구를 **한 훅으로 함께 처리**하려면 `updatedToolOutput`을 씁니다. `updatedMCPToolOutput`은 MCP 도구에만 적용되므로 내장 도구 출력을 바꾸지 못합니다.

`additionalContext`와 `systemMessage`는 "덮어쓰기"가 아니라는 점이 중요합니다. **원래 출력은 그대로 남습니다.**

### 예시 1: 타임스탬프 형식 통일

서로 다른 세 개의 도구가 시간 값을 각각 다른 형식으로 반환합니다.

- Unix epoch 정수: `1717027200`
- ISO 8601 문자열: `"2024-05-30T00:00:00Z"`
- 숫자 상태 코드와 날짜가 뒤섞인 값: `"200|30-05-2024"`

모델은 이런 불일치를 자주 **오독(misread)** 합니다. 특히 시간 순서를 따져야 하는 추론에서 틀립니다.

해결: `PostToolUse` 훅을 세 도구에 매칭시켜, 각 응답을 파싱한 뒤 `hookSpecificOutput.updatedToolOutput`에 **하나의 일관된 형식으로 재작성한 값**을 담아 반환합니다. 그러면 모델은 원본의 뒤죽박죽한 데이터를 **아예 보지 못하고**, 정규화된 데이터만 받습니다.

```python
def post_tool_use(tool_name, tool_response):
    normalized = normalize_timestamps(tool_response)  # 전부 ISO 8601로
    return {
        "hookSpecificOutput": {
            "updatedToolOutput": normalized
        }
    }
```

### 예시 2: 재고 상태 어휘 통일

- `inventory_lookup` → 숫자 코드 `0 / 1 / 2` (재고 있음 / 부족 / 없음)
- `warehouse_lookup` → 문자열 `"in-stock" / "low-stock" / "out-of-stock"`

모델이 어느 도구가 답했든 **하나의 일관된 어휘**로 추론하게 하려면, 두 도구 모두에 매칭되는 `PostToolUse` 훅에서 결과를 같은 문자열 레이블 집합으로 매핑한 뒤 `updatedToolOutput`으로 돌려주면 됩니다.

```python
LABELS = {0: "in-stock", 1: "low-stock", 2: "out-of-stock"}

async def normalize_stock(input_data, tool_use_id, context):
    raw = input_data["tool_response"]
    normalized = LABELS.get(raw, raw)  # 숫자면 변환, 문자열이면 그대로
    return {"hookSpecificOutput": {
        "hookEventName": "PostToolUse",
        "updatedToolOutput": normalized,
    }}
```

### 왜 다른 방법은 안 되는가

- **`PreToolUse` 훅으로 하려는 시도** → `PreToolUse`는 도구로 **들어가는 입력**을 다룹니다. 문제는 도구가 **내보내는 출력**의 형식이므로 시점이 맞지 않습니다.
- **`Notification` 훅으로 하려는 시도** → 알림·관찰용 훅이며, 모델이 실제로 수신하는 도구 출력을 치환하는 확정적 경로가 아닙니다.
- **시스템 프롬프트로 "네가 알아서 ISO 8601로 변환해서 읽어라"** → 이것은 모델이 **불일치 데이터를 직접 읽고** 변환하는 것입니다. "모델이 보기 전에 정규화"라는 요구를 만족하지 못하고, 오독 위험도 그대로 남습니다. 세션 시작 시 매핑표를 안내하거나 매 턴 변환하라고 상기시키는 것도 마찬가지로 확률적 통제입니다.

## 3.7 매처(Matcher) — 훅을 어떤 도구에 걸 것인가

훅을 등록할 때 **매처(matcher)** 를 지정해서 "이 훅이 어떤 도구 호출에 대해 실행될지"를 정합니다. 매처는 문자열 패턴 또는 정규표현식(Regex)입니다.

```json
{
  "PreToolUse": [
    {
      "matcher": "process_refund",
      "hooks": [{ "type": "command", "command": "./check_refund.sh" }]
    }
  ]
}
```

```python
HookMatcher(matcher="refund_customer", hooks=[my_callback])
```

### 매처는 오직 "도구 이름"만 매칭한다

핵심 규칙: **`matcher`는 도구 이름만 거릅니다.**

- 도구의 **인자 값**(예: `category`가 특정 값일 때만)으로 필터링하는 기능은 matcher에 **없습니다.**
- `refund_customer.*category=restricted` 같은 정규식을 써도 인자를 걸러주지 않습니다.
- `argument_matcher` 같은 별도 필드도 **존재하지 않습니다.**

그럼 인자 조건은 어디에? → **콜백 함수 안에서 직접 검사**합니다(3.3의 `block_restricted_refund` 예시).

정리: **"어느 도구인가"는 matcher가, "그 도구의 인자가 어떤 값인가"는 콜백 내부 조건문이** 담당합니다.

### 정규표현식 앵커링(Regex Anchoring)과 오버매칭

정규표현식의 기본 동작은 **부분 문자열(substring) 매칭**입니다. 즉 패턴이 대상 문자열 안 어디에든 나타나면 일치로 봅니다.

```
매처: /refund/
의도: refund 라는 도구 하나만 게이트
실제: 이름에 "refund" 가 들어간 모든 도구에 매칭
```

`/refund/`는 다음 모두와 일치합니다.

- `refund` ✔ (의도한 것)
- `issue_refund_note` ✔ (의도하지 않음 — 내부 메모만 쓰는 도구)
- `refund_user` ✔
- `refund_all` ✔
- `process_refund` ✔

이것을 **오버매칭(Over-matching)** 이라고 합니다. 훅이 걸리면 안 되는 무해한 도구까지 차단되어 워크플로가 깨집니다.

**해결책은 앵커(Anchor)** 입니다.

- `^` : 문자열의 **시작**을 의미
- `$` : 문자열의 **끝**을 의미

| 매처 | `refund` | `issue_refund_note` | `refund_all` |
| --- | --- | --- | --- |
| `/refund/` (앵커 없음) | 일치 | **일치 (의도치 않음)** | **일치 (의도치 않음)** |
| `/^refund$/` (앵커 있음) | 일치 | 불일치 | 불일치 |

`/^refund$/`는 "시작하자마자 refund가 나오고 그걸로 끝나는" 이름, 즉 정확히 `refund`인 도구에만 매칭됩니다. `issue_refund_note`는 앞에 `issue_`가 있으므로 `^` 조건에서 탈락합니다.

### 부수적으로 알아둘 사실

- 훅의 정규표현식 매처는 **자동으로 앵커링되지 않습니다.** 개발자가 직접 `^`와 `$`를 써야 합니다.
- 매처는 `mcp__` 접두사가 붙은 MCP 서버 도구뿐 아니라 **일반 인-프로세스 커스텀 도구 이름도 자유롭게 대상으로 삼을 수 있습니다.** 접두사를 붙이려고 도구 이름을 바꿀 필요가 없습니다.
- 훅의 **타임아웃(timeout)** 설정은 훅이 얼마나 오래 실행될 수 있는지를 정하는 값일 뿐, **어떤 도구에 매칭되는지와는 아무 관계가 없습니다.** 매칭 문제는 정규표현식으로 고쳐야 합니다.

## 3.8 MCP 도구 이름 네임스페이스와 매처 작성

### MCP란

**MCP(Model Context Protocol)** 는 에이전트가 외부 시스템의 기능을 **도구로 노출**받기 위한 표준 프로토콜입니다. 사내 청구 시스템을 감싼 **MCP 서버**를 띄우면, 에이전트는 그 서버가 제공하는 도구(청구 조회, 환불 처리 등)를 쓸 수 있게 됩니다. 한 에이전트가 동시에 여러 MCP 서버(`billing`, `inventory` 등)에 연결될 수 있습니다.

### 네임스페이스 규칙

여러 서버가 우연히 같은 이름의 도구(`search`, `list` 등)를 노출하면 충돌합니다. 이를 막기 위해 MCP 도구 이름은 다음 규칙으로 **네임스페이스화**됩니다.

```
mcp__<서버이름>__<도구이름>
```

구분자는 **밑줄 두 개(`__`)** 입니다. 예:

- `mcp__billing__get_invoice`
- `mcp__billing__issue_refund`
- `mcp__billing__void_authorization`
- `mcp__billing__apply_credit`
- `mcp__inventory__check_stock`

반면 `Bash`, `Read`, `Grep`, `Glob` 같은 **내장 도구(built-in tool)** 는 이 접두사가 **없습니다.**

### 목표 A: 특정 서버의 모든 도구에만 적용

"`billing` 서버가 노출하는 모든 도구에만 훅을 걸고, `inventory` 서버 도구와 `Bash`/`Read` 같은 내장 도구는 제외"하려면:

```
mcp__billing__.*      (또는 mcp__billing__* 형태의 와일드카드 매처)
```

각 부분의 역할:

- `mcp__` : MCP 도구임을 한정 → 내장 도구(`Bash`, `Read`) 배제
- `billing__` : 서버를 한정 → `inventory` 배제
- `.*` / `*` : 그 서버의 모든 도구 이름을 포괄

| 매처 | 결과 |
| --- | --- |
| `mcp__billing__.*` | billing 서버의 모든 도구만 매칭 (**정답**) |
| `mcp__billing` | 도구 이름 부분(`__<tool>`)을 받는 `__.*`가 빠져 실제 도구 이름과 맞지 않음 |
| `billing` | `mcp__` 접두사가 없어 네임스페이스 규칙·실제 노출 이름과 불일치 |
| `^mcp__` | **모든** MCP 서버의 모든 도구가 매칭됨 (`inventory`까지 포함) — 너무 넓음 |

### 목표 B: 같은 서버 안에서 특정 몇 개 도구에만 적용

예: `billing` 서버에 `issue_refund`, `void_authorization`, `apply_credit`(모두 돈을 움직임)과 여러 읽기 전용 도구가 있을 때, 앞의 셋에만 신원 검증 훅을 걸고 싶다.

세 개의 거의 똑같은 훅을 따로 등록하면 **중복(duplication)** 이 생기고 유지보수가 나빠집니다. 정규식의 **교대(alternation, `|`)** 를 쓰면 한 번의 등록으로 해결됩니다:

```
mcp__billing__(issue_refund|void_authorization|apply_credit)
```

왜 다른 접근은 틀린가:

- **매처를 아예 안 쓰기** → 매처가 없으면 대상이 좁혀지지 않습니다. 훅이 "돈 움직이는 도구를 알아서 알아본다"는 것은 성립하지 않습니다.
- **`"*"` 매처 + 짧은 타임아웃** → 타임아웃(예: 5초)은 **훅이 얼마나 오래 실행될 수 있는지**를 정하는 값이지, **어떤 도구에 적용되는지**를 좁히는 값이 전혀 아닙니다. 서로 무관한 개념입니다.
- **`mcp__billing` 단독** → 도구명을 정확히 식별하지 못할뿐더러, 목표와 반대로 읽기 전용 도구까지 걸리게 됩니다.

## 3.9 여러 훅의 충돌 해결과 체이닝

### PreToolUse 충돌: 가장 제한적인 결과 적용(Most Restrictive Principle)

같은 도구에 여러 개의 `PreToolUse` 훅을 독립적으로 등록할 수 있습니다. 예를 들어 `charge_card` 도구에 대해:

1. 사기 신호 검사 훅
2. 일일 지출 한도 검사 훅
3. 계정 상태 검사 훅

이때 **매칭되는 모든 훅이 평가됩니다.** (첫 번째만 평가하고 나머지를 건너뛰지 않습니다.)

결과가 서로 다르면 **가장 제한적인 결과 적용 원칙**이 적용됩니다. 이것은 **거부권(veto)** 모델입니다.

> 단 하나의 훅이라도 `"deny"` 를 반환하면, 나머지가 모두 `"allow"` 여도 최종 결정은 **차단(blocked)** 이다.

위 예시에서 사기 신호 훅만 `deny`, 나머지 둘이 `allow`라면 → **도구 호출은 차단됩니다.**

설계 이유는 명확합니다. 각 훅은 서로 다른 위험 축을 담당하는 독립적인 안전장치입니다. 한 축에서 위험이 감지되었는데 다른 축이 괜찮다고 해서 통과시키면 안전장치의 의미가 없습니다.

잘못된 통념들:

- "다수결(simple vote)로 결정한다" → 아니다. 보안 판단을 다수결로 하면 **검사기를 늘리는 것만으로 거부를 무력화**할 수 있어 허점이 된다.
- "첫 번째 훅만 평가되고 나머지는 스킵된다" → 아니다. 매칭된 훅은 모두 평가된다.
- "충돌하면 설정 오류가 나고 세션이 중단된다" → 아니다. 서로 다른 결과가 나오는 것은 정상적인 보안 검사 시나리오다.

### PostToolUse 체이닝(Chaining)

같은 도구에 `PostToolUse` 훅을 둘 이상 걸었다고 합시다. 예: (a) 결과 행 수를 잘라내는 훅, (b) 타임스탬프를 ISO 8601로 바꾸는 훅. 최종 출력은 "잘렸고 **또한** 정규화된" 상태여야 합니다.

여기서 반드시 확인할 것은 **두 번째 훅이 첫 번째 훅의 `updatedToolOutput`을 입력으로 받아 이어서 작업하는 구조인가**입니다.

- 파이프라인처럼 이어지면: `원본 → 훅A → 훅B → 최종` 으로 두 변환이 모두 살아남습니다.
- 두 훅이 각각 **원본만** 보고 독립적으로 돌면, 마지막에 반환된 값만 채택되어 **앞선 변환이 유실**됩니다.

혼동하기 쉬운 오해들:

- **타임아웃 값이 훅 충돌을 해결하지 않습니다.** 늦게 끝난 훅의 출력을 무시하는 규칙 같은 것은 없습니다.
- **훅 이름의 알파벳 순서로 실행 순서가 정해지지 않습니다.**
- `tool_use_id`를 맞춰야 훅이 합성되는 것도 아닙니다.

## 3.10 하드 게이팅 — 호출 순서 강제하기

"환불하기 전에 반드시 고객 신원을 확인하라" 같은 순서 규칙을 100% 보장하려면, 프롬프트가 아니라 **하드 게이트(hard gate)** 가 필요합니다.

```python
def pre_tool_use(tool_name, tool_input, session_state):
    if tool_name == "process_refund" and not session_state.get("verified_customer_id"):
        return {
            "permissionDecision": "deny",
            "permissionDecisionReason": "get_customer로 신원 확인을 먼저 수행하세요.",
        }
    return {"permissionDecision": "allow"}
```

핵심 아이디어는 **선행 단계의 성공을 상태에 기록해 두고, 후행 도구의 훅에서 그 상태를 확인**하는 것입니다. 상태가 없으면 거부하고, 거부 사유를 모델에게 알려 주면 모델은 스스로 순서를 바로잡아 다시 시도합니다.

### 함정: 훅 사이 파일 통신으로 "선행 도구 강제"를 구현하기

**결정적으로 중요한 성질**: `PreToolUse` 훅은 **매칭된 그 도구가 실제로 호출되는 순간에만** 실행됩니다. 등록만 해 두면 알아서 도는 것이 아닙니다.

여기서 나오는 잘못된 설계:

```
get_customer 훅   →  세션 파일에 "verified" 마커를 쓴다
process_refund 훅 →  그 파일을 읽어 검증한다
```

이 설계는 **안전하지 않습니다.** 이유:

- 각 훅은 자기 매처에 해당하는 도구가 호출될 때만 돕니다.
- 모델이 `get_customer`를 **아예 건너뛰고** `process_refund`를 바로 부를 수 있습니다. LLM의 도구 호출 순서는 런타임이 보장하지 않습니다(**비결정성, nondeterminism**).
- 그러면 마커 파일은 쓰인 적이 없고, `process_refund` 훅은 존재하지 않는 파일이나 유효하지 않은 데이터를 읽게 됩니다.

부수적으로 정확히 알아 둘 사실:

- 훅들끼리 **로컬 파일 시스템이나 동일 세션 환경을 통해 상태를 공유하는 것 자체는 가능**합니다. 문제는 "순서 보장"이지 "공유 불가"가 아닙니다.
- 런타임이 도구 이름을 **알파벳 순으로 정렬해 훅 실행 순서를 보장하는 메커니즘은 존재하지 않습니다.**
- 등록된 모든 `PreToolUse` 훅이 매처와 무관하게 매번 병렬 실행되는 것도 **아닙니다.** 해당 도구가 트리거될 때 선행 실행됩니다.

올바른 해법 방향: 순서를 "다른 훅이 남긴 흔적"이 아니라, **후행 도구의 훅 자신이 호출 시점에 직접 검증할 수 있는 근거**로 확인하게 만드는 것(3.11 참조).

### 효과 없는 대안들

- 프롬프트에 "must"를 넣고 두 번 반복하기 — 여전히 확률적입니다.
- 컨텍스트 윈도우 키우기 — 지시를 기억하느냐의 문제가 아니라 준수 보장의 문제입니다.
- 매 티켓마다 순서를 상기시키는 메시지 주입 — 역시 확률 조정일 뿐 하드 차단이 아닙니다.

## 3.11 상태 결합도 저하(Decoupling State Failure) — 신뢰할 수 있는 검증 데이터

에이전트 보안에서 반복되는 실패 유형이 있습니다: **간접적인 공유 상태(플래그)에 의존한 검증.**

문제 사례:

- `process_refund`를 게이트하는 `PreToolUse` 훅이 `is_verified`라는 불리언 플래그만 봅니다.
- 이 플래그는 별도의 `mark_verified` 도구가 세팅합니다.
- 사람 검토자가 신분증을 **거부**했는데, 소프트웨어 버그로 `is_verified`가 `true`가 되었습니다.
- 훅은 `true`를 믿고 환불을 통과시킵니다 → 무단 환불.

**교훈**: 잘못 쓰일 수 있는 제3의 상태 변수에 의존하지 말고, **도구 호출 파라미터에 포함된 명시적 검증 결과(원천 데이터)를 훅이 직접 검사(inspect)** 하게 만드십시오. "사람 검토가 명시적으로 통과되었음(expressly passed)"을 나타내는 값이 호출 인자에 실려 오고, 훅이 그것을 확인하는 구조입니다. 검증 근거와 검증 대상이 같은 호출에 묶이므로, 중간에 오염될 창구 자체가 사라집니다.

효과 없는 대안들:

- **`PostToolUse`로 사후 검증 후 거래 되돌리기** → 이미 부작용 발생. 게다가 똑같이 오염된 플래그를 다시 보는 것이라 근본 해결이 아님.
- **더 크고 유능한 모델로 교체** → 결정론적 소프트웨어 상태 버그와 입력 검증 문제는 모델 크기로 풀리지 않습니다. 비싸고 비효율적입니다.
- **훅 타임아웃을 늘려 플래그를 주기적으로 재확인** → 플래그를 쓴 코드가 애초에 틀린 값을 썼다면, 몇 번을 다시 읽어도 같은 틀린 값입니다.

## 3.12 훅의 예외 처리와 Fail-Closed 원칙

훅은 내 코드이므로 예외를 던질 수 있습니다. 훅이 외부 검증 서비스를 호출하는데 그 서비스가 타임아웃되어 예외가 처리되지 않은 채 밖으로 전파되면, **에이전트 세션 전체가 죽습니다.** 깔끔한 거부 대신 크래시가 나는 것입니다.

두 가지를 함께 지켜야 합니다.

1. **방어적 훅 작성**: 훅 내부에서 예외를 `catch`하여 절대 밖으로 전파시키지 않는다.
2. **Fail-Closed**: 검증을 수행할 수 없는 상태라면 **거부(`deny`)** 한다.

```python
def pre_tool_use(tool_name, tool_input):
    if tool_name != "process_refund":
        return {"permissionDecision": "allow"}
    try:
        ok = verification_service.check(tool_input, timeout=5)
    except TimeoutError:
        return {
            "permissionDecision": "deny",
            "permissionDecisionReason": "검증 서비스 장애로 확인할 수 없어 환불을 보류합니다.",
        }
    return {"permissionDecision": "allow" if ok else "deny"}
```

**Fail-Closed vs Fail-Open**

- **Fail-Closed(실패 시 차단)**: 검증 불가 → 거부. 보안·컴플라이언스의 기본값. 가용성은 조금 잃지만 안전성은 지킵니다.
- **Fail-Open(실패 시 허용)**: 검증 불가 → 허용. 서비스 장애 시간 동안 **모든 검증이 우회**됩니다. 공격자에게는 "검증 서비스를 죽이면 게이트가 열린다"는 뜻이 됩니다.

같은 맥락에서 나쁜 대응들:

- **타임아웃을 몇 시간으로 늘리기** — 예외는 안 나지만 에이전트가 무기한 대기(hang)합니다. 빠른 실패 + 명확한 거부가 낫습니다.
- **장애 동안 훅을 아예 제거하기** — 무검증 실행을 허용하는 것으로, 통제를 포기하는 것과 같습니다.

## 3.13 `deny`의 부작용: 에이전트 재시도 루프 끊기

실무에서 자주 만나는 함정입니다.

LLM은 도구 호출이 `deny`로 실패하면 그것을 **"해결 가능한 오류"** 로 받아들이는 경향이 있습니다. 그래서 인자를 살짝 바꾸거나 그냥 똑같이, 계속해서 재시도합니다. 사용자 입장에서는 "왜 같은 걸 다섯 번씩 시도하지" 하는 나쁜 경험이 됩니다.

**해결 조건이 "사람을 부르지 않고, 훅 코드 자체가 자동으로 결정론적 제어를 유지한 채 재시도를 끊는 것"일 때**의 패턴:

> `permissionDecision: "allow"` 를 반환하되, `updatedInput` 으로 실제 실행될 명령을 **무해한 no-op**(예: `echo` 같은 아무 일도 하지 않는 명령)으로 바꿔치기한다.

작동 원리:

- 에이전트 입장에서는 도구 호출이 **성공**했으므로 재시도할 이유가 없어져 루프가 즉시 끝납니다.
- 실제로는 환불이 수행되지 않았으므로 훅이 완전한 통제권을 유지합니다.

각 대안이 왜 요구사항에 안 맞는지:

- **`PostToolUse`로 옮겨 실행 후 되돌리기** → 환불이 **이미 나갔습니다.** 사전 차단이 아니며 되돌리기가 실패할 수도 있습니다.
- **`permissionDecisionReason` 문자열을 지워 짧게 만들기** → 문구 몇 개를 손보는 프롬프트 튜닝으로는 LLM의 재시도 성향을 결정론적으로 통제할 수 없습니다.
- **`ask`로 바꾸기** → 재시도 루프는 멈추지만 **결정을 사람에게 넘기는 것**이므로 "훅이 자동으로 처리하라"는 요구와 어긋나고, 매번 물으면 사용자 피로도가 올라갑니다.

> **요구 조건에 따라 답이 갈립니다.** 요구사항이 "사람 승인"이면 `ask`가 정답이고, "자동 결정론적 처리"면 `allow` + `updatedInput`(no-op)이 정답입니다.

## 3.14 비동기 훅(`async`) — 넌블로킹 감사

모든 도구 호출의 인자를 외부 감사(audit) 서비스로 보내야 하는데, 이 감사는 **허용/거부 판단과 무관**하고 **응답 시간을 늦추면 안 되는** 경우가 있습니다.

이때 `PreToolUse` 훅에서 감사 요청을 쏘고 다음을 반환합니다.

```json
{ "async": true, "asyncTimeout": 30000 }
```

런타임은 이 훅의 완료를 **기다리지 않고** 즉시 도구 실행과 다음 단계를 진행합니다(넌블로킹, non-blocking). `asyncTimeout`은 백그라운드 작업에 허용하는 최대 시간(ms)입니다.

부적절한 대안들:

- `permissionDecision: "ask"` → 매번 사람 확인 프롬프트가 뜨므로 응답 시간이 크게 늘고 불필요한 사용자 개입이 발생.
- `updatedInput`에 감사 페이로드를 끼워 넣기 → `updatedInput`은 원래 **도구 인자를 수정**할 때 쓰는 필드입니다. 감사 데이터를 넣으면 도구 본래의 스키마와 인자를 오염시키고, 백그라운드 외부 전송이라는 목적에도 맞지 않습니다.
- `permissionDecision: "defer"` → 감사 서비스 응답이 올 때까지 세션을 일시 정지(pause)시키므로 "지연시키지 말 것"이라는 핵심 조건 위반.

## 3.15 권한(Permission)과 설정 계층

### 서브에이전트의 `tools` 필드

서브에이전트를 정의할 때 그 에이전트가 쓸 수 있는 도구 목록을 지정합니다.

```
name: test-runner
tools: ["Bash", "Read", "Grep"]
```

여기서 중요한 오해가 있습니다. **이 `tools` 목록은 "권한 부여"가 아니라 "권한 축소"에 가깝습니다.** 즉 "이 에이전트에게는 이 도구들만 보이게 하라"는 화이트리스트일 뿐, **상위에서 금지한 것을 되살리는 힘은 없습니다.**

### 권한 상속(Permission Inheritance)

`settings.local.json` 같은 설정 파일에는 **deny 규칙**(특정 도구/명령 사용 차단)을 쓸 수 있습니다.

핵심 규칙:

> **서브에이전트는 코디네이터(상위) 레벨의 보안 설정과 deny 규칙을 상속받습니다. 하위 설정으로 상위 금지를 우회할 수 없습니다.**

구체적 상황:

- `test-runner` 서브에이전트는 자기 정의에 `Bash`를 포함하고 있다.
- 그런데 이 서브에이전트를 부르는 코디네이터의 `settings.local.json`에는 `Bash`를 막는 deny 규칙이 있다.
- 결과: **`Bash`는 실행되지 않습니다. 첫 번째 호출부터 즉시 차단됩니다.**

왜 이렇게 설계되었는가: 만약 하위 정의가 상위 정책을 뚫을 수 있다면, 보안 설정이 무의미해집니다. 누구든 서브에이전트를 하나 정의해서 금지된 도구를 쓸 수 있게 되기 때문입니다. 그래서 **deny는 항상 위에서부터 강하게 적용되는 상위 가드레일**입니다.

틀린 통념:

- 서브에이전트의 `tools` 필드가 독립적으로 접근 권한을 준다 → **아닙니다.**
- `Task`(에이전트 호출 도구)를 `tools`에 넣어야 다른 도구들이 활성화된다 → 그런 규칙은 없습니다. 차단 원인은 상속된 deny 규칙입니다.
- 첫 호출만 허용되고 이후가 막힌다 → 아닙니다. **횟수와 무관하게 처음부터 차단됩니다.**

## 3.16 한눈에 보는 결정 요령

| 요구사항 | 정답 |
|---|---|
| 도구 실행을 사전에 막아야 함 | `PreToolUse` + `permissionDecision: "deny"` |
| 사람 승인을 받아야 함 | `PreToolUse` + `permissionDecision: "ask"` |
| 인자를 안전한 값으로 바꿔 실행 | `PreToolUse` + `allow` + `updatedInput` |
| 재시도 루프를 자동으로 끊기 | `PreToolUse` + `allow` + `updatedInput`(no-op) |
| 도구 출력 형식 통일 | `PostToolUse` + `updatedToolOutput` |
| 내장 도구와 MCP 도구를 한 훅으로 | `updatedToolOutput` (`updatedMCPToolOutput` 아님) |
| 출력에 정보만 덧붙이기 | `additionalContext` |
| 응답 지연 없이 외부 감사 전송 | `async: true` + `asyncTimeout` |
| 정확히 한 도구만 매칭 | `/^tool_name$/` (앵커 필수) |
| 특정 MCP 서버 전체 매칭 | `mcp__<서버>__.*` |
| 서버 내 일부 도구만 매칭 | 정규식 교대(`\|`) 사용: `mcp__billing__(issue_refund\|apply_credit)` |
| 인자 값 조건으로 분기 | 매처가 아니라 **콜백 내부 조건문** |
| 서브에이전트 도구 제한 | 상위 deny 규칙이 항상 우선 (상속) |
