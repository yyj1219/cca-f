# 사전 학습 노트: 에이전트 아키텍처와 오케스트레이션 (41~60 범위)

이 문서는 배경 지식이 전혀 없는 상태에서 읽어도 이해할 수 있도록, 이 범위에서 다루는 개념을 밑바닥부터 설명합니다. 주제는 크게 다섯 덩어리입니다.

1. 작업 분해(Task Decomposition)와 오케스트레이션 패턴
2. 서브에이전트(Subagent)와 AgentDefinition 설정
3. 컨텍스트 격리와 세션(Session) 관리
4. 훅(Hooks)과 권한 제어
5. MCP와 Messages API의 기본 동작

---

## 0. 먼저 알아야 할 기본 그림

### 0.1 LLM 에이전트란 무엇인가

**LLM(대규모 언어 모델)** 은 텍스트를 입력받아 텍스트를 출력하는 모델입니다. 그 자체로는 파일을 읽거나 API를 호출할 수 없습니다.

**에이전트(Agent)** 는 여기에 두 가지를 붙인 것입니다.

- **도구(Tools)**: 모델이 "이 도구를 이런 인자로 실행해줘"라고 텍스트로 요청하면, 바깥의 프로그램(런타임)이 실제로 실행하고 결과를 모델에게 돌려줍니다. 예: 파일 읽기(`Read`), 문자열 검색(`Grep`), 셸 실행(`Bash`), 파일 수정(`Edit`), 파일 생성(`Write`).
- **루프(Loop)**: 모델 → 도구 호출 → 결과 회신 → 모델 → ... 를 목표를 달성할 때까지 반복하는 구조.

즉 에이전트 = 모델 + 도구 + 반복 루프입니다.

### 0.2 컨텍스트(Context)란 무엇인가

모델은 기억 장치가 없습니다. 매 호출마다 "지금까지의 대화 전체"를 통째로 입력으로 다시 받아야만 이전 내용을 압니다. 이 입력 뭉치를 **컨텍스트(context)** 라고 하고, 담을 수 있는 최대 크기를 **컨텍스트 윈도우(context window)** 라고 합니다.

여기서 파생되는 두 가지 사실이 이 범위 전체를 관통합니다.

- 전달하지 않은 정보는 모델이 절대 알 수 없다. (기억이 아니라 "매번 다시 보여주기"다)
- 컨텍스트는 유한하고 비용(토큰)이 든다. 그래서 무엇을 넣고 무엇을 뺄지가 아키텍처 설계 문제가 된다.

## 1. 작업 분해(Task Decomposition)

### 1.1 왜 분해하는가

하나의 요청 안에 서로 다른 성격의 일이 섞여 있거나, 한 번에 처리하기엔 너무 큰 일이 있을 때, 이를 **하위 작업(subtask)** 으로 쪼개는 것을 작업 분해라고 합니다. 분해하면 각 하위 작업이 단순해져 모델의 정확도가 올라가고, 서로 독립적인 하위 작업은 동시에 처리할 수 있습니다.

### 1.2 다중 의도(Multi-intent) 요청 처리

하나의 사용자 발화 안에 독립적인 요구가 둘 이상 들어 있는 경우가 흔합니다.

> "구독료가 이중 청구됐어요. 그리고 다음 배송 전에 배송지 주소도 바꿔주세요."

여기에는 (a) 청구 조회/환불, (b) 주소 변경이라는 서로 무관한 두 의도가 있습니다. 권장되는 처리 흐름은 다음 3단계입니다.

1. **분해(Decompose)**: 요청을 "청구 문제"와 "주소 문제"로 나눈다.
2. **병렬 조사(Parallel investigation with shared context)**: 두 하위 작업은 서로 의존하지 않으므로 동시에 진행한다. 이때 원본 티켓 내용, 고객 정보 같은 공통 정보는 **공유 컨텍스트(shared context)** 로 한 번만 준비해 양쪽이 함께 쓴다. 티켓을 두 번 다시 읽어 토큰을 두 배로 쓰는 낭비를 피할 수 있다.
3. **합성(Synthesize)**: 두 결과를 하나의 통합 응답으로 합쳐 고객에게 전달한다.

이렇게 하면 응답 지연(latency)과 토큰 소모가 줄고, 사용자 입장에서는 한 번의 답변으로 모든 문제가 해결됩니다.

반대로 피해야 할 방식은 다음과 같습니다.

- 사용자에게 "티켓을 두 개로 나눠 다시 제출하세요"라고 되돌려 보내기 → 시스템의 한계를 사용자에게 전가하는 나쁜 UX.
- 한쪽 요구를 조용히 무시하기 → 요청 미해결. 우선순위 판단을 임의로 하는 것도 위험.
- 첫 문제를 처리한 뒤 **기억이 전혀 없는 새 세션**으로 두 번째 문제를 다시 시작하기 → 이미 확보한 컨텍스트를 버리는 정보 손실.

### 1.3 개방형(Open-ended) 과제의 적응적 분해

탐색 범위를 미리 알 수 없는 과제도 있습니다. 예를 들어 "테스트가 전혀 없고 모듈 경계도 문서화되지 않은 20만 줄짜리 레거시 코드베이스에 테스트를 추가하라" 같은 과제입니다.

이런 과제에서는 **적응적(adaptive) 전략**이 필요합니다. 전형적인 순서는 이렇습니다.

1. **매핑(Mapping)**: 먼저 코드베이스 구조를 훑어 모듈과 의존 관계를 파악한다. (무엇이 있는지도 모르는 상태에서 계획을 세울 수 없으므로 탐색이 먼저다.)
2. **우선순위 지정**: 영향도가 큰(high-impact) 공백부터 고른다. 모든 함수를 똑같이 취급하지 않는다.
3. **계획을 진행하며 조정**: 작업 중에 새로 드러나는 숨은 의존성에 맞춰 계획을 수정한다.

피해야 할 방식은 **빅뱅(Big Bang) 접근**입니다.

- 테스트를 한 번도 실행해보지 않고 모든 함수의 테스트를 한 번에 작성 → 피드백 루프가 없어 잘못된 가정이 끝까지 누적됨.
- 중간 점검(intermediate checkpoint) 없이 단일 세션에 전부 위임 → 컨텍스트 한계 초과, 오류 누적.
- 모듈 관계를 보지 않고 알파벳순 등 임의 순서로 진행 → 의존성이 얽혀 비효율.

핵심 원칙: **불확실성이 클수록 계획은 고정이 아니라 갱신 가능해야 한다.**

## 2. 오케스트레이션 패턴

에이전트 워크플로를 조직하는 대표적인 두 가지 패턴이 있습니다. 시험 범위 전체에서 반복적으로 비교됩니다.

### 2.1 프롬프트 체이닝 (Prompt Chaining)

**정의**: 미리 정해진 단계들을 고정된 순서로 실행하고, 각 단계의 출력을 다음 단계의 입력으로 넘기는 구조.

```
[1단계] PDF → JSON 변환
   ↓ (출력이 그대로 다음 입력)
[2단계] 필수 필드 검증
   ↓
[3단계] 레코드 저장
```

**적합한 조건**

- 단계의 수와 순서가 **절대 변하지 않는다** (never branch, number of stages never varies).
- 각 단계의 출력 형태가 다음 단계가 요구하는 입력과 **항상 정확히 일치한다**.
- 스키마가 고정되어 있다. (예: 모든 송장이 동일한 3개 필드 스키마)

**장점**

- **예측 가능성(predictability)**: 실행 경로가 하나뿐이므로 디버깅·테스트·비용 예측이 쉽다.
- **위임 오버헤드(delegation overhead)가 없다**: "다음에 뭘 할지" 판단하는 중앙 관리자를 둘 필요가 없으므로, 그 판단에 드는 LLM 호출·토큰·지연이 통째로 사라진다.

**체크포인트(Checkpoint) / 게이트키퍼(Gatekeeper) 패턴**

체이닝의 위험은 앞 단계가 이상한 출력을 내면 그 오류가 뒤 단계로 전파된다는 점입니다. 그래서 단계 사이에 **검증 지점(checkpoint)** 을 둡니다.

```
개요 생성 → [개요가 형식에 맞는가? 섹션이 있는가?] → 본문 작성 → [본문 길이/구조 검증] → 문법 교정
```

검증에 실패하면 다음 단계로 넘기지 않고 재시도하거나 중단합니다. 이 검증은 LLM이 아니라 코드(스키마 검증, 정규식, 필드 존재 확인)로 하는 것이 저렴하고 확실합니다.

### 2.2 오케스트레이터-워커 (Orchestrator-Workers)

**정의**: 중앙의 **오케스트레이터(orchestrator)** 가 상황을 보고 하위 작업을 **동적으로 생성**하여 **워커(worker)** 에게 위임하고, 결과를 받아 다음 하위 작업을 다시 결정하는 구조.

```
        오케스트레이터
      (다음에 뭘 조사할지 매번 결정)
       /      |       \
   워커1    워커2     워커3
       \      |       /
        결과 취합 → 새 하위 작업 생성 → 반복
```

**적합한 조건**

- **탐색 공간을 사전에 알 수 없다**. 몇 개의 로그, 몇 개의 서비스, 몇 개의 코드 경로를 봐야 하는지 미리 셀 수 없다.
- **다음 행동이 이전 결과에 의존한다**. 발견한 단서에 따라 조사 방향이 달라져야 한다.
- 분기(branching)와 우선순위 재조정이 필요하다.

**전형적 사례: 장애 원인 조사(Incident Investigation)**

모호한 알림 메시지 하나만 주어지고 어느 서비스가 문제인지 모르는 상황. 이때는 동적 오케스트레이터가 적합합니다. 첫 단계에서 로그를 보고 특정 서비스가 의심되면 그 서비스의 코드 경로를 조사하는 새 하위 작업을 만들고, 아니면 다른 방향으로 우선순위를 옮깁니다.

이 상황에서 부적절한 대안들:

- **하드코딩된 5단계 체인**: 무엇이 발견되든 5단계 전부 실행 → 불필요한 단계에 토큰과 시간 낭비, 예상 밖 원인에는 대응 불가.
- **고정 순서 점검(DB → 캐시 → 로드밸런서)**: 원인이 외부 API나 애플리케이션 코드에 있으면 영원히 찾지 못함.
- **단일 프롬프트로 즉시 근본 원인 지목**: 근거 없이 추측하므로 **환각(hallucination)** 을 유발. 조사 없는 단정은 위험.

### 2.3 선택 기준 요약

| 상황 | 적합한 패턴 |
| --- | --- |
| 단계 수/순서 고정, 스키마 고정, 분기 없음 | 프롬프트 체이닝 (+ 체크포인트) |
| 탐색 범위 미지, 다음 단계가 발견에 의존 | 오케스트레이터-워커 (동적) |

주의할 점: "체이닝이 항상 더 정확하다", "2단계 이상이면 무조건 체이닝이 필요하다", "오케스트레이터는 PDF를 못 다룬다" 같은 절대적 서술은 모두 사실이 아닙니다. 패턴 선택은 **작업의 성격**(고정성 대 동적성)으로 결정되며, 특정 데이터 형식을 처리할 수 있느냐는 패턴이 아니라 모델과 도구의 문제입니다.

또한 반대 방향의 과잉도 문제입니다. 고정 3단계 파이프라인에 동적 오케스트레이터를 쓰면 필요 없는 판단 오버헤드만 늘어납니다. 반대로 모든 단계를 하나의 프롬프트/서브에이전트 안에서 암묵적으로 처리하면 단계별 검증과 실패 복구가 불가능해집니다.

## 3. 서브에이전트(Subagent)와 AgentDefinition

### 3.1 서브에이전트란

**코디네이터(coordinator)** 또는 메인 에이전트가, 특정 목적을 가진 별도의 에이전트에게 작업을 위임할 수 있습니다. 이 위임받는 쪽을 **서브에이전트(subagent)** 라고 합니다. 위임은 보통 `Agent`(또는 `Task`) 도구를 호출하는 형태로 이루어집니다.

서브에이전트를 쓰는 이유:

- **컨텍스트 절약**: 서브에이전트가 수백 개 파일을 뒤져도, 코디네이터에게는 최종 요약만 돌아온다. 코디네이터의 컨텍스트 윈도우가 오염되지 않는다.
- **전문화**: 역할별로 다른 프롬프트, 다른 도구, 다른 모델을 줄 수 있다.
- **권한 격리**: 위험한 도구를 특정 서브에이전트에게만 주거나, 반대로 뺏을 수 있다.

### 3.2 AgentDefinition의 주요 필드

서브에이전트는 보통 **AgentDefinition** 이라는 정의 객체(혹은 정의 파일)로 선언합니다. 핵심 필드는 다음과 같습니다.

```jsonc
{
  "name": "doc-reviewer",
  // 언제 이 에이전트를 부를지 — 라우팅 트리거
  "description": "문서와 README의 정확성·명확성을 검토할 때 사용. 문서 리뷰, 오탈자 점검, 설명 누락 확인 요청 시 호출.",
  // 호출된 뒤 어떻게 행동할지 — 시스템 프롬프트
  "prompt": "당신은 기술 문서 리뷰어입니다. 각 문단의 정확성을 확인하고 ...",
  // 사용 가능한 도구 화이트리스트 — 하드 제약
  "tools": ["Read", "Grep"],
  // 이 에이전트가 사용할 모델
  "model": "opus"
}
```

각 필드의 의미를 하나씩 봅니다.

#### `description` — 언제 부를지 (라우팅 트리거)

코디네이터가 "이 요청을 내가 직접 처리할까, 어떤 서브에이전트에게 넘길까"를 판단할 때 보는 필드입니다. 즉 **라우팅(routing) 트리거 신호**입니다.

이 필드가 모호하거나 비어 있으면, 코디네이터는 이 서브에이전트가 언제 적용되는지 알 수 없어 **그냥 자기가 직접 처리해버립니다**. 자동 위임이 안 되는 가장 흔한 원인이 바로 이것입니다.

예를 들어 `performance-optimizer`라는 서브에이전트의 `prompt`가 아무리 상세하고 기술적으로 정확해도, `description`이 "성능 관련 도우미" 정도로 모호하면 사용자가 "쿼리가 느려요"라고 물었을 때 코디네이터는 위임하지 않습니다. 고쳐야 할 곳은 `prompt`가 아니라 `description`입니다.

좋은 `description`은 **트리거 조건을 구체적으로 명시**합니다.

```
"느린 데이터베이스 쿼리, 인덱스 누락, N+1 쿼리, 쿼리 실행 계획 분석이 필요할 때 사용."
```

참고로, 코디네이터의 시스템 프롬프트에 서브에이전트 이름을 하드코딩할 필요는 없습니다. 런타임이 등록된 정의들을 읽어 동적으로 라우팅합니다.

#### `prompt` — 호출된 뒤 어떻게 행동할지

서브에이전트가 실제로 실행될 때 받는 시스템 프롬프트입니다. 작업 절차, 출력 형식, 주의사항을 담습니다. `description`과 역할이 완전히 다릅니다.

- `description` = **언제 부르는가** (코디네이터가 읽음)
- `prompt` = **불려온 뒤 무엇을 하는가** (서브에이전트가 읽음)

참고로 프롬프트를 1인칭으로 쓰든 2인칭으로 쓰든, 그것이 위임 여부를 결정하지는 않습니다.

#### `tools` — 무엇을 할 수 있는가 (하드 제약)

이 서브에이전트에게 실제로 전달되는 도구 목록입니다. 여기 없는 도구는 모델에게 아예 노출되지 않으므로, 모델이 호출하고 싶어도 **호출할 수단 자체가 없습니다**.

#### `model` — 어떤 모델로 실행할 것인가

서브에이전트별로 독립적인 모델을 지정할 수 있습니다. 이 필드를 설정해도 **코디네이터 자신의 모델 설정은 전혀 바뀌지 않습니다**.

예: 일상적인 보안 리뷰는 저렴한 모델로, "엄격한(strict)" 변형 리뷰만 더 강력한 모델로 실행하고 싶다면 — 그 엄격 변형용 `AgentDefinition`의 `model` 필드만 강력한 모델로 지정하면 끝입니다.

이때 다음과 같은 우회 방법들은 잘못되었습니다.

- 코디네이터 세션을 다른 모델 인자로 재개(resume)하기 → 코디네이터 자신의 모델까지 바뀌므로 조건 위반.
- 모델 이름을 `tools` 배열에 넣기 → `tools`는 도구 목록이지 모델 지정 수단이 아니다.
- 세션을 포크해서 기본 모델을 바꾸기 → 필드 하나로 될 일에 불필요한 세션 조작.

### 3.3 최소 권한의 원칙 (Principle of Least Privilege)

**정의**: 어떤 주체에게든 자기 임무 수행에 꼭 필요한 최소한의 권한만 부여한다는 보안 원칙.

에이전트 세계에서 이것은 곧 **`tools` 목록을 좁히는 것**입니다.

여기서 반드시 구분해야 할 두 종류의 제약이 있습니다.

| 구분 | 수단 | 성격 |
| --- | --- | --- |
| **소프트 제약 (Soft Limit)** | 프롬프트에 "파일을 수정하지 마세요"라고 적기 | 모델이 지시를 어길 수 있음. 환각·오판으로 무너짐. **보장 없음** |
| **하드 제약 (Hard Limit)** | `tools`에서 `Edit`, `Write`를 제외 | 도구 자체가 없으므로 물리적으로 불가능. **보장됨** |

"절대로 ~해서는 안 된다(must never, even accidentally)"는 요구가 나오면 답은 항상 하드 제약, 즉 도구 목록 제한입니다.

**예시**: 문서를 읽고 코멘트만 해야 하는 `doc-reviewer`가 실수로 파일을 수정하는 것을 막고 싶다.

```jsonc
{
  "name": "doc-reviewer",
  "description": "문서를 읽고 검토 의견을 제시할 때 사용.",
  "prompt": "...",
  "tools": ["Read", "Grep"]   // Edit, Write 없음 → 수정 불가능
}
```

여기서 중요한 성질: **서브에이전트는 `tools`에 나열된 것만 받으며, 코디네이터가 무엇을 가지고 있든 상관없습니다.** 코디네이터가 `Read, Edit, Write, Grep, Glob`을 전부 가지고 있어도, 서브에이전트의 `tools`가 `["Read", "Grep"]`이면 그 서브에이전트에는 `Edit`/`Write`가 전달되지 않습니다.

잘못된 대안들:

- **`description` 필드에 "읽기 전용"이라고 적기**: `description`은 라우팅용 메타데이터일 뿐 실행 권한을 통제하지 않습니다.
- **`tools`를 비워두고 프롬프트로만 금지**: 소프트 제약이므로 보장이 없습니다. (또한 `tools`를 지정하지 않으면 상위의 도구를 상속받게 되어 오히려 위험합니다.)
- **코디네이터 자신의 `allowedTools`를 좁히기**: 코디네이터가 본래 해야 할 편집 작업까지 막히고, 서브에이전트 권한을 정의하는 표준 방식도 아닙니다.
- **모델 티어를 낮추기**: 성능이 낮은 모델은 오히려 지시를 더 잘 어깁니다. 능력 저하는 제약 장치가 아닙니다.
- **서브에이전트에게서 모든 도구를 뺏기**: 문서를 읽어야 하는데 `Read`조차 없으면 본연의 임무를 못 합니다. 최소 권한은 "0 권한"이 아니라 "필요한 만큼만"입니다.

## 4. 컨텍스트 격리와 세션 관리

### 4.1 서브에이전트 컨텍스트 격리 (Context Isolation)

**핵심 규칙: 서브에이전트를 호출할 때마다 그 서브에이전트의 컨텍스트는 완전히 새로(fresh) 시작됩니다.**

여기서 파생되는 두 가지 중요한 결과가 있습니다.

#### (1) 메인 대화 이력은 자동으로 전달되지 않는다

사용자가 3턴 전에 "인증 제공자는 A를 쓰기로 하자"고 결정했더라도, 서브에이전트는 그 대화를 보지 못합니다. 서브에이전트가 엉뚱하게 다른 제공자를 제안한다면, 그것은 버그도 캐시 문제도 권한 문제도 아니라 **설계된 동작**입니다.

**해결책**: 필요한 결정 사항·제약·배경을 `Agent` 도구를 호출할 때의 **프롬프트 텍스트 안에 직접 써서 넘겨야** 합니다.

```
Agent(
  subagent_type="auth-designer",
  prompt="""사용자는 이미 인증 제공자로 A를 쓰기로 결정했다. 이 결정은 변경 대상이 아니다.
            A를 전제로 로그인 흐름을 설계하라."""
)
```

이것을 **컨텍스트 주입(context injection)** 이라고 부를 수 있습니다. "필요한 것은 명시적으로 넘긴다"가 원칙입니다.

#### (2) 같은 서브에이전트를 두 번 불러도 서로를 모른다

`endpoint-finder`라는 같은 종류의 서브에이전트를 청구 서비스용으로 한 번, 알림 서비스용으로 한 번, 별개의 두 호출로 실행하면, 두 번째 호출은 첫 번째 호출이 있었다는 사실조차 모릅니다. 이미 설명했던 기본 규칙을 다시 설명하는 것도 정상입니다.

이것은 **예상된 동작(expected behavior)** 이며, 이유는 다음과 같습니다.

- 각 호출은 독립된 실행 환경에서 시작한다.
- 이전 실행의 상태를 이어받으려면 **특정 에이전트 ID를 지정해 명시적으로 재개(resume)** 해야 한다.
- 모든 서브에이전트 호출이 하나의 컨텍스트를 공유한다면 컨텍스트 윈도우가 폭발한다. 격리는 그것을 막는 설계다.

잘못된 통념들:

- "같은 코디네이터 세션 안의 서브에이전트들은 하나의 결합된 컨텍스트 윈도우를 공유한다" → 아니다.
- "같은 대상에 대해 두 번 부르면 메모리가 자동 공유된다" → 아니다. 대상이 같아도 무관하다.
- "AgentDefinition 수준에서 추론 결과를 자동 캐싱한다" → 그런 기능은 없다.

### 4.2 세션(Session)의 개념

**세션(session)** 은 하나의 대화 이력 단위이며, 고유한 **세션 ID**를 가지고 디스크에 저장됩니다. 세션을 다루는 기본 연산은 네 가지입니다.

| 연산 | 의미 |
| --- | --- |
| **새 세션 시작** | 아무 이력 없이 처음부터 시작 |
| **재개(Resume)** | 특정 세션 ID의 이력을 불러와 **그 세션에 이어서** 대화. 원본 세션이 계속 자란다 |
| **이어가기(Continue)** | 작업 디렉터리의 **가장 최근** 세션을 자동으로 이어감 (ID 지정 불필요) |
| **포크(Fork)** | 현재까지의 이력을 복사해 **새 세션 ID**를 만들고 거기서 진행. 원본은 그대로 보존 |

### 4.3 세션 포크(Session Forking)

포크는 "누적된 컨텍스트는 그대로 쓰되, 원본은 오염시키지 않고 대안을 탐색"하고 싶을 때 쓰는 도구입니다. git의 브랜치와 비슷한 개념입니다.

**전형적 시나리오**: 어떤 세션이 인증 모듈을 깊이 분석해서 JWT 기반 재설계안을 만들었다. 이제 같은 분석 결과를 출발점으로 OAuth2 기반 설계도 탐색해보고 싶다. 단, 나중에 JWT 스레드를 **변경 없이 그대로** 재개할 수 있어야 한다.

→ **포크를 활성화해서 세션을 재개**합니다. 현재 이력이 새 세션 ID로 복사되고, OAuth2 탐색은 그 새 세션에 쌓입니다. 원본 JWT 세션은 손대지 않은 채 남습니다.

부적절한 대안들:

- **완전히 새 세션에 요약본만 붙여넣기**: 누적된 깊은 분석 컨텍스트(왜 그런 결론에 이르렀는지, 어떤 코드를 봤는지)를 잃습니다.
- **원본 세션에서 그냥 OAuth2를 물어본 뒤 나중에 "무시해줘"라고 하기**: 이미 컨텍스트가 오염되었습니다. 대화 이력은 되돌릴 수 없고, "무시하라"는 지시가 완벽히 지켜진다는 보장도 없습니다.
- **그냥 최근 세션을 이어가면서 알아서 브랜치가 갈릴 것이라 기대하기**: 새 주제가 나왔다고 시스템이 자동으로 브랜치를 만들지 않습니다. 포크는 **명시적으로** 요청해야 합니다.

### 4.4 세션 범위 권한(Session-scoped Permissions)과 포크

에이전트가 위험한 도구를 쓰려 할 때 사용자에게 승인을 요청하는 **권한 프롬프트**가 뜹니다. 여기서 흔히 "이 세션 동안 허용(allow for this session)"을 고를 수 있습니다.

이 승인은 이름 그대로 **특정 세션 ID에 묶인 승인**입니다. 따라서 포크로 새 세션(새 세션 ID)이 만들어지면 **그 승인은 따라오지 않고, 새 브랜치에서 다시 물어봅니다.**

이유는 보안입니다. 포크는 보통 "더 위험한 접근을 시험해보기 위해" 만드는 분기인데, 원본에서 준 임시 승인이 자동으로 따라온다면 사용자가 의도하지 않은 권한 확대가 일어납니다. 그래서 이력만 복사하고 임시 권한 상태는 복사하지 않습니다.

혼동하기 쉬운 오해들:

- "권한 승인은 정해진 턴 수 후에 만료된다" → 그런 규칙 때문이 아니다. 원인은 세션이 갈라진 것.
- "`--fork-session`은 `--continue`와 같이 쓰면 안 된다" → 함께 쓸 수 있는 정상 조합이다.
- "포크는 작업 디렉터리를 초기화해서 권한이 무효화된다" → 그렇지 않다.

### 4.5 세션 관리의 적정량 — 과잉 설계 피하기

세션 기능이 있다고 해서 항상 써야 하는 것은 아닙니다.

**빌드 파이프라인 안의 원샷(one-shot) 작업** — 프롬프트 하나를 실행하고 끝이며 이후 후속 질문이 없는 경우 — 에는 **단일 `query()` 호출 외에 아무 세션 처리도 추가하지 않는 것**이 올바릅니다. 이후에 컨텍스트를 공유할 프롬프트 자체가 없기 때문입니다.

다음은 모두 불필요한 오버헤드입니다.

- 혹시 몰라 세션 ID를 저장하고 즉시 재개하기 → 상태가 필요 없는(stateless) 작업에 상태 관리를 도입.
- 나중을 대비해 `continue_conversation=True`를 켜두기 → 쓰지 않을 기능을 켜둠.
- 후속 작업이 예상되지 않는데 `fork_session`을 켜기 → 쓰지 않을 병렬 분기.

원칙: **필요가 실제로 존재할 때만 상태 관리를 도입한다.**

### 4.6 세션 조회 API

SDK는 디스크에 저장된 세션을 프로그램에서 직접 다룰 수 있는 함수를 제공합니다. 대화형 CLI 선택기를 외부 프로세스로 띄우지 않고 자체 UI(커스텀 세션 선택기)를 만들 때 사용합니다.

| 함수 | 역할 |
| --- | --- |
| `listSessions()` | 특정 프로젝트/리포지토리에 존재하는 **세션 목록을 열거** |
| `getSessionMessages()` | 지정한 세션의 **전체 메시지 이력을 읽기** |

비슷해 보이지만 역할이 다른 것들:

- `getSessionInfo()`: 단일 세션의 **메타데이터**만 조회. 전체 목록 열거용이 아니다.
- `resume()`: 세션을 **다시 이어서 실행**하는 연산. 단순 읽기용이 아니다.
- `fork_session()`: 세션을 **분기**하는 연산. 열거용이 아니다.
- `continue()`: 세션을 이어가는 연산.
- `renameSession()` / `tagSession()`: 세션의 **이름 변경 / 태그 부착** 같은 메타데이터 수정. 조회와 무관.

전형적인 사용 흐름:

```
sessions = listSessions(projectPath)      # 목록 만들기 → UI에 표시
messages = getSessionMessages(chosen_id)  # 사용자가 고른 세션의 내용 미리보기
```

## 5. CLI 플래그: 비대화형 실행과 세션 재개

Claude Code CLI에는 대화형 터미널 UI를 띄우는 기본 모드와, 스크립트에서 쓰기 위한 비대화형 모드가 있습니다. 주요 플래그는 다음과 같습니다.

| 플래그 | 의미 |
| --- | --- |
| `-p` / `--print` | **대화형 UI를 열지 않고** 프롬프트를 한 번 실행하고 결과를 표준 출력으로 내보냄 (원샷/비대화형) |
| `--resume <session-id>` | 지정한 세션 ID의 이력과 컨텍스트를 불러와 이어감 |
| `--continue` | 작업 디렉터리의 가장 최근 세션을 이어감 |
| `--fork-session` | 이어받되 새 세션 ID로 분기 (원본 보존) |
| `--output-format json` | 결과를 스크립트가 파싱할 수 있는 **구조화된 JSON**으로 출력 |
| `--from-pr <number>` | Pull Request를 기점으로 시작 (세션 ID 기반 재개와는 다른 기능) |

이 플래그들은 **조합**해서 씁니다. 요구사항을 하나씩 플래그로 매핑하는 습관을 들이면 됩니다.

**예시**: "이미 완료된 비대화형 세션에 후속 질문 하나를 던지고, 답변을 스크립트가 파싱할 구조화된 데이터로 받고 싶다. 대화형 터미널 UI는 열지 않는다."

- 대화형 UI 열지 않음 → `-p`
- 이전 세션 컨텍스트 이어받기 → `--resume <session-id>`
- 스크립트 파싱용 구조화 출력 → `--output-format json`

```bash
claude -p --resume <session-id> --output-format json "summarize what we changed"
```

주의: `-p` 없이 `--resume`만 쓰면 대화형 UI가 열립니다. 또한 `--output-format json`을 지정하지 않으면 출력이 사람이 읽는 자유 형식 텍스트라 안정적인 파싱이 불가능합니다. (뒤에 파이프로 JSON 파서를 붙인다고 출력이 JSON이 되지는 않습니다.)

## 6. 훅(Hooks)

### 6.1 훅이란

**훅(Hook)** 은 에이전트 실행 과정의 특정 시점에 자동으로 실행되는 사용자 정의 로직입니다. 모델의 판단에 의존하지 않고 런타임이 **결정론적으로(deterministically)** 실행하므로, 정책 강제·감사 로그·안전장치에 적합합니다.

**`PreToolUse`** 훅은 이름 그대로 **도구가 실행되기 직전**에 동작합니다. 도구 이름과 인자를 보고 실행을 허용할지 막을지 결정할 수 있습니다.

훅은 보통 다음을 반환합니다.

- `permissionDecision: "allow"` — 이 도구 호출을 허용
- `permissionDecision: "deny"` — 이 도구 호출을 차단

### 6.2 매처(Matcher) — 어떤 도구에 훅을 걸 것인가

훅에는 **매처(matcher)** 를 지정해 "어떤 도구 이름에 이 훅을 적용할지" 정합니다. 매처는 문자열 패턴 또는 정규표현식입니다.

#### 정규표현식 앵커링 (Regex Anchoring)

정규표현식의 기본 동작은 **부분 문자열 매칭(substring matching)** 입니다. 즉 패턴이 대상 문자열 안 어디에든 나타나면 일치로 봅니다.

- `^` : 문자열의 **시작** 을 의미하는 앵커
- `$` : 문자열의 **끝** 을 의미하는 앵커

따라서:

| 매처 | `refund` | `issue_refund_note` | `refund_all` |
| --- | --- | --- | --- |
| `/refund/` (앵커 없음) | 일치 | **일치 (의도치 않음)** | **일치 (의도치 않음)** |
| `/^refund$/` (앵커 있음) | 일치 | 불일치 | 불일치 |

**실무 함의**: `refund`라는 결제 도구만 게이트하려고 `/refund/`를 썼다면, 내부 코멘트만 남기는 `issue_refund_note` 같은 무해한 도구까지 차단되어 워크플로가 깨집니다. 정확히 하나의 도구만 대상으로 하려면 반드시 `/^refund$/`처럼 앵커를 명시해야 합니다.

훅의 정규표현식 매처는 **자동으로 앵커링되지 않습니다.** 개발자가 직접 `^`와 `$`를 써야 합니다.

또한 알아둘 것:

- 매처가 `mcp__` 접두사를 가진 도구만 대상으로 할 수 있다는 제약은 없습니다. 커스텀 인프로세스 도구도 이름으로 매칭됩니다.
- 훅의 **타임아웃(timeout)** 설정은 훅이 얼마나 오래 실행될 수 있는지를 정하는 값일 뿐, **어떤 도구에 매칭되는지와는 아무 관계가 없습니다.**

### 6.3 여러 훅의 충돌 해결 — 가장 제한적인 결과 적용

같은 도구에 여러 개의 `PreToolUse` 훅을 독립적으로 등록할 수 있습니다. 예를 들어 `charge_card` 도구에 대해:

1. 사기 신호 검사 훅
2. 일일 지출 한도 검사 훅
3. 계정 상태 검사 훅

이때 **매칭되는 모든 훅이 평가됩니다.** (첫 번째만 평가하고 나머지를 건너뛰지 않습니다.)

결과가 서로 다르면 **가장 제한적인 결과 적용 원칙(Most Restrictive Principle)** 이 적용됩니다. 이것은 **거부권(veto)** 모델입니다.

> 단 하나의 훅이라도 `"deny"` 를 반환하면, 나머지가 모두 `"allow"` 여도 최종 결정은 **차단(blocked)** 이다.

위 예시에서 사기 신호 훅만 `deny`, 나머지 둘이 `allow`라면 → **도구 호출은 차단됩니다.**

이 설계 이유는 명확합니다. 각 훅은 서로 다른 위험 축을 담당하는 독립적인 안전장치입니다. 한 축에서 위험이 감지되었는데 다른 축이 괜찮다고 해서 통과시키면 안전장치의 의미가 없습니다.

잘못된 통념들:

- "다수결(simple vote)로 결정한다" → 아니다. 보안 판단을 다수결로 하면 검사기를 늘리는 것만으로 거부를 무력화할 수 있어 허점이 된다.
- "첫 번째 훅만 평가되고 나머지는 스킵된다" → 아니다. 매칭된 훅은 모두 평가된다.
- "충돌하면 설정 오류가 나고 세션이 중단된다" → 아니다. 서로 다른 결과가 나오는 것은 정상적인 보안 검사 시나리오다.

## 7. MCP (Model Context Protocol)

### 7.1 MCP란

**MCP(Model Context Protocol)** 는 외부 시스템의 기능을 에이전트에게 **도구로 노출**하기 위한 표준 프로토콜입니다. 예를 들어 사내 청구 시스템을 감싼 **MCP 서버**를 띄우면, 에이전트는 그 서버가 제공하는 도구(청구 조회, 환불 처리 등)를 쓸 수 있게 됩니다.

한 에이전트가 동시에 여러 MCP 서버에 연결될 수 있습니다. 예: `billing` 서버와 `inventory` 서버.

### 7.2 도구 이름 네임스페이스 규칙

여러 서버가 우연히 같은 이름의 도구(`search`, `list` 등)를 노출하면 충돌합니다. 이를 막기 위해 MCP 도구 이름은 다음 규칙으로 **네임스페이스화**됩니다.

```
mcp__<서버이름>__<도구이름>
```

구분자는 **밑줄 두 개(`__`)** 입니다. 예:

- `mcp__billing__get_invoice`
- `mcp__billing__issue_refund`
- `mcp__inventory__check_stock`

반면 내장(built-in) 도구는 이 접두사가 없습니다. 예: `Bash`, `Read`, `Grep`.

### 7.3 특정 MCP 서버의 도구만 매칭하기

이 규칙을 알면 매처를 정확히 쓸 수 있습니다. "`billing` 서버가 노출하는 모든 도구에만 훅을 걸고, `inventory` 서버 도구와 `Bash`/`Read` 같은 내장 도구는 제외"하려면:

```
mcp__billing__*
```

각 부분의 역할:

- `mcp__` : MCP 도구임을 한정 → 내장 도구(`Bash`, `Read`) 배제
- `billing__` : 서버를 한정 → `inventory` 배제
- `*` : 그 서버의 모든 도구 이름을 포괄

비교:

| 매처 | 결과 |
| --- | --- |
| `mcp__billing__*` | billing 서버의 모든 도구만 매칭 (정답) |
| `mcp__billing` | 도구 이름 부분(`__<tool>`)이 빠져 실제 도구 이름과 맞지 않음 |
| `billing` | `mcp__` 접두사가 없어 실제 노출 이름과 불일치 |
| `^mcp__` | 모든 MCP 서버의 모든 도구가 매칭됨 (`inventory`까지 포함) |

## 8. Messages API와 에이전트 루프

### 8.1 Messages API는 무상태(Stateless)다

Claude의 **Messages API**는 **무상태(stateless)** 입니다. 서버는 이전 대화를 저장하지 않습니다. 매 요청마다 클라이언트가 **지금까지의 전체 `messages` 배열**을 보내야 하며, 보내지 않은 것은 모델이 알 수 없습니다.

(앞서 4.1에서 본 서브에이전트 컨텍스트 격리와 동일한 원리가 API 층에서도 적용되는 것입니다.)

### 8.2 도구 사용 루프의 메시지 구조

도구를 쓰는 대화는 다음 순서로 `messages` 배열에 **누적**됩니다.

```
[1] user       : "지난 1시간 CPU 메트릭 좀 가져와줘"
[2] assistant  : tool_use  (name="fetch_metrics", input={...})   ← 모델이 도구 호출을 요청
[3] user       : tool_result (tool_use_id=..., content="cpu: 87%") ← 실행 결과를 되돌려줌
[4] assistant  : "CPU가 87%로 높습니다. ..."                      ← 결과를 해석한 답변
```

여기서 핵심은 **[3]단계에서 `tool_result`를 배열에 "추가(append)"해야 한다는 것**입니다.

### 8.3 흔한 실수: 이력을 덮어쓰기

에이전트 루프를 직접 구현할 때 흔한 버그는, 도구 실행 결과를 돌려줄 때 기존 `messages` 배열을 **`tool_result` 하나로 대체(replace)** 해버리는 것입니다.

```python
# 잘못됨 — 이력을 통째로 날림
messages = [{"role": "user", "content": [tool_result]}]

# 올바름 — 기존 이력에 덧붙임
messages.append({"role": "user", "content": [tool_result]})
```

이력을 덮어쓰면 무슨 일이 생기는가:

- 원래 사용자의 질문([1])이 사라진다 → 무엇을 위한 결과인지 모른다.
- 모델이 왜 그 도구를 호출했는지 담긴 `tool_use`([2])가 사라진다 → 결과의 의도와 맥락을 잃는다.
- 결국 모델은 **이 결과가 무엇에 대한 답인지 해석할 수 없어** 엉뚱하거나 무의미한 응답을 내놓는다.

그리고 API가 무상태이므로, **서버가 알아서 이전 대화를 다시 불러와 채워주는 일은 없습니다.** 다음과 같은 오해도 사실이 아닙니다.

- `tool_result` 블록에 첫 호출의 세션 토큰이 필요해서 인증 오류가 난다 → 그런 메커니즘 없음.
- `tool_result`가 자동으로 시스템 프롬프트로 변환되어 이후 턴의 지침을 영구히 바꾼다 → 그런 동작 없음.
- 서버 측 저장소에서 전체 대화를 자동으로 다시 가져온다 → 무상태이므로 불가능.

## 9. 전체를 관통하는 설계 원칙 정리

1. **전달하지 않은 것은 모델이 모른다.** 서브에이전트든 API 호출이든, 필요한 맥락은 명시적으로 넣어야 한다.
2. **작업의 성격이 패턴을 결정한다.** 고정·예측 가능 → 체이닝. 미지·동적 → 오케스트레이터.
3. **보장이 필요하면 하드 제약을 쓴다.** 프롬프트 지시는 소프트 제약이며 절대 보장이 아니다. 권한은 `tools`로 끊는다.
4. **최소 권한.** 필요한 것만 주되, 임무 수행에 필요한 것은 뺏지 않는다.
5. **안전 판단은 가장 보수적인 쪽으로 수렴한다.** 하나의 `deny`가 모든 `allow`를 이긴다.
6. **필요할 때만 상태를 도입한다.** 원샷 작업에 세션 관리를 붙이는 것은 오버헤드다.
7. **원본을 오염시키지 않고 실험하려면 포크한다.** 그리고 포크는 새 세션이므로 세션 범위 권한은 따라오지 않는다.
8. **매칭 패턴은 명시적으로 좁힌다.** 앵커 없는 정규식과 네임스페이스 없는 이름은 의도치 않은 대상을 잡는다.

## 10. 용어 사전 (Glossary)

### 분해와 오케스트레이션

| 영문 용어 | 설명 |
| --- | --- |
| **Task Decomposition** | 작업 분해. 큰 요청을 독립적인 하위 작업으로 쪼개는 것 |
| **Multi-intent Resolution** | 다중 의도 해결. 한 발화에 든 여러 요구를 각각 처리하고 하나로 합치는 것 |
| **Decompose / Synthesize** | 분해 / 합성. 요청을 나누고, 각 결과를 하나의 통합 응답으로 묶는 두 단계 |
| **Shared Context** | 공유 컨텍스트. 여러 하위 작업이 함께 참조하는 공통 정보. 중복 재읽기를 없앰 |
| **Prompt Chaining** | 프롬프트 체이닝. 고정된 순서의 단계를 이어 붙이고 출력을 다음 입력으로 넘기는 패턴 |
| **Orchestrator-Workers** | 오케스트레이터-워커. 중앙 조정자가 하위 작업을 동적으로 만들어 워커에게 위임하는 패턴 |
| **Dynamic Orchestrator** | 동적 오케스트레이터. 이전 단계의 발견에 따라 다음 하위 작업을 생성·우선순위화하는 조정자 |
| **Delegation Overhead** | 위임 오버헤드. 중앙 조정자가 "다음에 뭘 할지" 판단하는 데 드는 추가 호출·토큰·지연 |
| **Branching** | 분기. 조건에 따라 실행 경로가 갈리는 것 |
| **Checkpoint / Gatekeeper** | 체크포인트/게이트키퍼. 단계 사이에서 출력이 올바른지 검증하고, 잘못되면 다음 단계로 넘기지 않는 지점 |
| **Adaptive Strategy** | 적응형 전략. 새 정보가 드러나면 계획을 수정해 나가는 접근 |
| **Big Bang Approach** | 빅뱅 방식. 중간 피드백 없이 한 번에 전부 처리하려는 접근. 개방형 과제에서 실패 위험이 큼 |
| **Open-ended Task** | 개방형 과제. 범위·단계 수를 사전에 확정할 수 없는 작업 |
| **High-impact Gap** | 영향도가 큰 공백. 우선적으로 다뤄야 할 취약 영역 |
| **Hallucination** | 환각. 모델이 근거 없이 그럴듯한 내용을 만들어내는 현상 |

### 에이전트와 설정

| 영문 용어 | 설명 |
| --- | --- |
| **Agent** | 에이전트. 모델 + 도구 + 반복 루프로 구성된 자율 실행 단위 |
| **Coordinator** | 코디네이터. 서브에이전트에게 작업을 위임하는 상위 에이전트 |
| **Subagent** | 서브에이전트. 코디네이터가 특정 목적으로 위임하는 하위 에이전트 |
| **AgentDefinition** | 에이전트 정의 객체. `name`, `description`, `prompt`, `tools`, `model` 등을 담음 |
| **`description` 필드** | "언제 이 에이전트를 부를지"를 코디네이터에게 알리는 라우팅 트리거. 모호하면 자동 위임이 안 됨 |
| **`prompt` 필드** | 호출된 서브에이전트가 받는 시스템 프롬프트. "어떻게 행동할지"를 정의 |
| **`tools` 필드** | 이 에이전트에게 실제 전달되는 도구 화이트리스트. 여기 없는 도구는 호출 불가 |
| **`model` 필드** | 이 에이전트가 사용할 모델. 코디네이터의 모델 설정과 독립적 |
| **Subagent Routing / Description Matching** | 서브에이전트 라우팅. `description`을 근거로 위임 여부를 판단하는 과정 |
| **Tool Scoping** | 도구 범위 제어. 에이전트가 쓸 수 있는 도구를 명시적으로 좁히는 것 |
| **Principle of Least Privilege** | 최소 권한의 원칙. 임무 수행에 필요한 최소한의 권한만 부여 |
| **Hard Limit / Hard Constraint** | 하드 제약. 도구 미부여처럼 물리적으로 불가능하게 만드는 통제. 보장됨 |
| **Soft Limit / Soft Prompting** | 소프트 제약. 프롬프트 지시에만 의존하는 통제. 모델이 어길 수 있음 |
| **Guardrail** | 가드레일. 에이전트의 위험 행동을 막는 안전장치 전반 |
| **`allowedTools`** | 특정 에이전트/세션에 허용되는 도구 목록 설정 |
| **Built-in Tool** | 내장 도구. `Read`, `Write`, `Edit`, `Grep`, `Glob`, `Bash` 등 런타임이 기본 제공하는 도구 |

### 컨텍스트와 세션

| 영문 용어 | 설명 |
| --- | --- |
| **Context** | 컨텍스트. 모델이 이번 호출에서 보는 입력 전체. 여기 없으면 모델은 모름 |
| **Context Window** | 컨텍스트 윈도우. 한 번에 담을 수 있는 최대 크기 |
| **Context Isolation** | 컨텍스트 격리. 서브에이전트 호출마다 새 컨텍스트로 시작하는 설계 |
| **Fresh Context** | 새 컨텍스트. 이전 이력이 전혀 없는 초기 상태 |
| **Expected Behavior** | 예상된 동작. 버그가 아니라 설계된 정상 동작 |
| **Session** | 세션. 고유 ID를 갖고 디스크에 저장되는 대화 이력 단위 |
| **Session ID** | 세션 식별자 |
| **Resume** | 재개. 특정 세션 ID의 이력을 불러와 그 세션에 이어서 진행 |
| **Continue** | 이어가기. 작업 디렉터리의 가장 최근 세션을 ID 지정 없이 이어감 |
| **Fork / Session Forking** | 포크. 현재 이력을 복사해 새 세션 ID를 만들고 거기서 진행. 원본은 보존됨 |
| **Session-scoped Permission** | 세션 범위 권한. "이 세션 동안 허용"으로 부여된 승인. 포크된 새 세션으로 이전되지 않음 |
| **One-shot Task** | 원샷 작업. 후속 질문 없이 한 번 실행하고 끝나는 작업. 세션 관리 불필요 |
| **Stateless** | 무상태. 서버가 이전 상태를 보관하지 않는 성질 |
| **`query()`** | SDK의 단일 프롬프트 실행 호출 |
| **`continue_conversation`** | 대화를 이어갈지 여부를 지정하는 옵션 |
| **`fork_session`** | 세션 분기를 활성화하는 옵션 |
| **`listSessions()`** | 리포지토리/프로젝트의 세션 목록을 열거하는 SDK 함수 |
| **`getSessionMessages()`** | 특정 세션의 전체 메시지 이력을 읽는 SDK 함수 |
| **`getSessionInfo()`** | 단일 세션의 메타데이터를 조회하는 함수 (목록 열거용 아님) |
| **`renameSession()` / `tagSession()`** | 세션 이름 변경 / 태그 부착. 메타데이터 수정용 |

### CLI 플래그

| 영문 용어 | 설명 |
| --- | --- |
| **`-p` / `--print`** | 대화형 UI 없이 단발 실행하고 표준 출력으로 결과 반환 |
| **`--resume <session-id>`** | 지정 세션 ID를 이어받음 |
| **`--continue`** | 최근 세션을 이어받음 |
| **`--fork-session`** | 이어받되 새 세션 ID로 분기 |
| **`--output-format json`** | 결과를 구조화된 JSON으로 출력해 스크립트가 파싱 가능하게 함 |
| **`--from-pr <number>`** | Pull Request를 기점으로 시작. 세션 ID 재개와는 다른 기능 |

### 훅과 권한

| 영문 용어 | 설명 |
| --- | --- |
| **Hook** | 훅. 실행 흐름의 특정 시점에 런타임이 결정론적으로 실행하는 사용자 정의 로직 |
| **PreToolUse Hook** | 도구 실행 직전에 동작해 허용/차단을 결정하는 훅 |
| **Matcher** | 매처. 훅을 어떤 도구 이름에 적용할지 정하는 패턴 |
| **`permissionDecision`** | 훅이 반환하는 권한 결정값. `"allow"` 또는 `"deny"` |
| **Most Restrictive Principle** | 가장 제한적인 결과 적용 원칙. 여러 훅이 충돌하면 가장 보수적인 결정이 이김 |
| **Veto** | 거부권. 단 하나의 `deny`가 모든 `allow`를 무력화하는 구조 |
| **Regex Anchoring** | 정규표현식 앵커링. `^`(시작)과 `$`(끝)로 정확히 일치하도록 범위를 고정하는 것 |
| **Unanchored Regex** | 앵커 없는 정규식. 부분 문자열만 포함해도 일치하므로 의도치 않은 대상을 잡음 |
| **Substring Matching** | 부분 문자열 일치. 정규식의 기본 동작 |
| **Exact Match** | 정확 일치. 앵커를 써야 얻어짐 |
| **Timeout** | 훅 실행 제한 시간. 매칭 대상과는 무관 |

### MCP와 API

| 영문 용어 | 설명 |
| --- | --- |
| **MCP (Model Context Protocol)** | 외부 시스템 기능을 에이전트에게 도구로 노출하는 표준 프로토콜 |
| **MCP Server** | MCP 서버. 도구 묶음을 제공하는 외부 프로세스 |
| **Tool Naming Convention** | MCP 도구 이름 규칙. `mcp__<서버이름>__<도구이름>` |
| **Namespace** | 네임스페이스. 서버 이름을 접두사로 붙여 도구 이름 충돌을 막는 방식 |
| **Wildcard (`*`)** | 와일드카드. 임의의 나머지 문자열을 포괄하는 패턴 |
| **Messages API** | Claude에 메시지를 보내 응답을 받는 무상태 API |
| **`messages` array** | 대화 전체를 순서대로 담는 배열. 매 요청마다 누적된 전체를 보내야 함 |
| **`tool_use`** | 모델이 도구 호출을 요청하는 메시지 블록 |
| **`tool_result`** | 도구 실행 결과를 모델에게 되돌려주는 메시지 블록. 기존 이력에 **append** 해야 함 |
| **Append vs. Replace** | 덧붙이기 대 덮어쓰기. `tool_result`는 덧붙여야 하며, 덮어쓰면 원본 질문과 호출 의도를 잃음 |
| **Multimodal** | 멀티모달. 텍스트 외에 이미지·PDF 등도 입력으로 다루는 모델 능력 |
