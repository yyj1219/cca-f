# 4. tool_choice와 재시도·오류 복구

## 이 장에서 다루는 것

- 도구 사용(Tool Use)의 기본 흐름과, 그것이 구조화된 출력의 표준 방법인 이유
- `tool_choice`의 네 가지 값(`auto` / `any` / `tool` / `none`)과 각각의 용도
- `tool_choice`를 둘러싼 흔한 오해와 제약(강제 사용 시 자연어 억제, Extended Thinking 비호환)
- 재시도로 고칠 수 있는 오류와 절대 고칠 수 없는 오류의 분류
- 타깃 피드백 재시도(Retry with Targeted Feedback)의 3요소와 실패 패턴
- 재시도 한도, 대응 사다리, 사람 검토로의 에스컬레이션

## 1. 도구 사용(Tool Use)의 기본 흐름

### 1.1 왜 도구 사용인가

모델의 기본 출력은 자유 형식 텍스트입니다. 하지만 애플리케이션은 파싱 가능한 데이터를 원합니다. "청구서에서 총액과 품목을 뽑아 DB에 넣어라" 같은 작업에서 자유 텍스트를 정규식으로 파싱하는 것은 매우 취약합니다.

**도구 사용(Tool Use / Function Calling)** 은 개발자가 "이런 이름과 입력 스키마를 가진 함수가 있다"고 모델에게 알려주고, 모델이 그 함수를 호출하는 형태로 응답하게 하는 기능입니다. 도구의 입력 형식을 **JSON Schema**(`input_schema`)로 선언하면, 모델은 그 스키마를 만족하는 JSON을 만들어 도구를 "호출"합니다.

여기서 중요한 점: **실제로 도구를 실행할 필요조차 없습니다.** 스키마에 맞는 JSON을 얻는 것 자체가 목적일 수 있습니다. 이 용법을 **구조화된 데이터 추출(Structured Data Extraction)** 이라고 부릅니다. 즉 "이 스키마대로 JSON을 뽑아라"를 도구 하나로 표현하면, API가 스키마 준수를 프롬프트 지시보다 훨씬 강하게 뒷받침합니다.

### 1.2 흐름

```
개발자: tools=[...도구 명세...] + tool_choice=... 로 요청
   ↓
모델: 문맥을 읽고 도구를 호출하는 형태로 응답
   ↓
응답에 tool_use 블록이 담김 → 그 안의 input이 곧 스키마를 만족하는 구조화 데이터
```

### 1.3 도구 정의 예시

```python
tools = [
    {
        "name": "extract_invoice",
        "description": "송장에서 구조화된 필드를 추출합니다.",
        "input_schema": {
            "type": "object",
            "properties": {
                "invoice_number": {"type": "string"},
                "total_amount":   {"type": "number"},
            },
            "required": ["invoice_number"]
        }
    },
    # extract_resume, extract_contract ...
]
```

조금 더 구조가 있는 스키마 예시(JSON):

```json
{
  "name": "extract_invoice",
  "description": "청구서에서 품목과 총액을 추출한다",
  "input_schema": {
    "type": "object",
    "properties": {
      "line_items": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "description": { "type": "string" },
            "amount": { "type": "number" }
          },
          "required": ["description", "amount"]
        }
      },
      "order_total": { "type": "number" },
      "phone_number": { "type": ["string", "null"] }
    },
    "required": ["line_items", "order_total"]
  }
}
```

주요 JSON Schema 키워드:

| 키워드 | 의미 |
|---|---|
| `type` | 값의 자료형 (`string`, `number`, `integer`, `boolean`, `object`, `array`, `null`) |
| `properties` | 객체가 가질 수 있는 필드 정의 |
| `required` | **반드시 존재해야 하는** 필드 이름 목록 |
| `enum` | 값이 지정된 후보 중 하나여야 함 (예: `"enum": ["P1","P2","P3","P4"]`) |
| `items` | 배열 원소의 스키마 |
| `type: ["string", "null"]` | 문자열 **또는** null 허용 (nullable) |

### 1.4 스키마가 보장하는 것 vs 보장하지 못하는 것

이 구분이 도구 사용 전체에서 가장 중요한 개념입니다.

**구문적 유효성(Syntactic Validity)** — 스키마가 보장함

- JSON 문법이 깨지지 않음
- 필드 타입이 맞음 (`amount`가 문자열이 아니라 숫자임)
- `required` 필드가 빠지지 않음
- `enum` 값이 후보 밖으로 나가지 않음

**의미적 정확성(Semantic Correctness)** — 스키마가 **보장하지 못함**

- 값이 원본 문서에 실제로 있던 값인가 (사실성)
- 필드들끼리 **논리적/산술적으로 앞뒤가 맞는가**
- 비즈니스 규칙을 지키는가 (예: 할인율은 총액보다 클 수 없다, 종료일은 시작일보다 뒤여야 한다)

구체적인 예:

```json
{
  "line_items": [
    {"description": "위젯 A", "amount": 500},
    {"description": "위젯 B", "amount": 440}
  ],
  "order_total": 980
}
```

품목 합계는 940인데 `order_total`은 980입니다. 그런데 이 JSON은 **스키마 검증을 완벽히 통과합니다.** 두 값 모두 유효한 `number`이고, 필수 필드도 다 있기 때문입니다.

이 불일치가 왜 다른 수단으로 해결되지 않는지:

- 구문 오류(syntax error)가 **아닙니다.** 문법도 타입도 정상입니다.
- `required` 제약을 더한다고 막히지 **않습니다.** `required`는 "있느냐 없느냐"만 볼 뿐 값들 사이의 계산 관계를 보지 않습니다.
- **`tool_choice` 설정을 바꾼다고 해결되지 않습니다.** 도구 선택 방식과 산술 검증은 무관합니다.
- 일시적인 샘플링 잡음이라 무시해도 되는 것도 **아닙니다.** LLM은 원래 산술에 약하고 문서에서 잘못된 숫자를 집어올 수 있으므로 반복적으로 발생합니다.

### 1.5 다운스트림 검증(Downstream Validation)

그러므로 의미적 검증은 **모델 밖, 애플리케이션 코드에서** 해야 합니다. "다운스트림"은 모델의 응답을 받은 이후 단계라는 뜻입니다.

```python
def validate_invoice(data, tolerance=0.01):
    calculated_total = sum(item["amount"] for item in data["line_items"])
    if abs(calculated_total - data["order_total"]) > tolerance:
        return {
            "ok": False,
            "reason": "total_mismatch",
            "calculated_total": calculated_total,
            "stated_total": data["order_total"],
        }
    return {"ok": True}
```

이런 검증에 실패한 레코드는 자동 통과시키지 말고 재시도하거나 사람 검토로 보냅니다.

> **설계 원칙: 스키마는 "형태"를 강제하고, 애플리케이션 코드는 "의미"를 검증한다.** 두 층은 서로를 대체할 수 없습니다.

### 1.6 required 필드가 환각을 유발하는 문제

원본 문서에 **없을 수도 있는 정보**를 `required`로 지정하면 심각한 부작용이 생깁니다.

상황: 지원 이메일에서 고객 전화번호를 뽑는 스키마인데, 오래된 이메일 상당수에는 전화번호가 아예 없습니다. 그런데 `phone_number`를 `required: string`으로 선언했습니다.

결과: 모델은 스키마를 만족시켜야 하므로 **그럴듯해 보이는 가짜 전화번호를 지어냅니다.** 이것이 **환각(hallucination)** 입니다. 스키마가 사실상 "빈칸을 채워라"라고 강요한 셈입니다.

**올바른 해법: 해당 필드를 선택적(optional)이고 nullable로 만든다.**

```json
{
  "properties": {
    "phone_number": {
      "type": ["string", "null"],
      "description": "문서에 전화번호가 명시된 경우에만 채운다. 없으면 null."
    }
  },
  "required": ["customer_name"]
}
```

- `required` 목록에서 빼면 → 필드를 아예 생략할 수 있습니다 (optional).
- `type`에 `"null"`을 함께 허용하면 → 명시적으로 `null`을 반환할 수 있습니다 (nullable).
- `description`에 "없으면 null"이라고 적어주면 모델이 의도를 더 정확히 이해합니다.

이러면 모델에게 **"모른다"고 말할 수 있는 합법적인 출구**가 생기고, 환각의 구조적 원인이 사라집니다.

잘못된 대안들과 그 이유:

| 잘못된 대안 | 왜 틀렸나 |
|---|---|
| 도구 정의를 통째로 없애고 산문으로 부탁하기 | 환각은 줄 수 있으나 출력이 다시 자유 텍스트가 되어 파싱 안정성과 추출 정밀도를 잃음. 구조화의 이점을 통째로 버리는 과잉 대응 |
| `required` 유지 + 타입을 지역번호 `enum`으로 변경 | 여전히 반드시 채워야 하므로 "후보 중에서 가짜 지역번호를 고르게" 될 뿐. 근본 원인(필수 제약)이 그대로 |
| `required` 유지 + `phone_number_confidence` 신뢰도 필드 추가 | 여전히 가짜 번호를 생성해야 하고 스키마만 복잡해짐. LLM이 스스로 매긴 신뢰도는 잘 보정(calibrate)되어 있지 않아 신뢰하기 어려움 |

> **일반 원칙: 스키마의 필수 제약은 "반드시 존재하는 정보"에만 건다. 부재 가능성이 있는 정보를 필수로 걸면 모델은 거짓말로 그 제약을 만족시킨다.**

### 1.7 원본 문서 내부의 충돌 처리

1.4는 모델이 계산을 틀린 경우였습니다. 이번에는 **원본 문서 자체가 서로 모순되는** 경우입니다.

상황: 임대차 계약서 1페이지 요약 조항에는 월세 $1,800, 4페이지 지급 일정표에는 $1,850. 둘 다 문서에 실제로 적혀 있고, 둘 다 깔끔하게 추출되는 유효한 숫자입니다.

이때 추출 시스템이 임의로 하나를 고르면 안 됩니다. 어느 쪽이 맞는지는 **법적/계약적 판단**이며 데이터 파이프라인이 내릴 결정이 아닙니다.

**모범 사례 — 충돌을 데이터로 표현하고 사람에게 넘긴다:**

```json
{
  "monthly_rent_candidates": [
    {"value": 1800, "source": "요약 조항, p.1"},
    {"value": 1850, "source": "지급 일정표, p.4"}
  ],
  "conflict_detected": true
}
```

그리고 `conflict_detected: true`인 레코드는 자동 처리 흐름에서 빼내 **사람이 확인/조정(human reconciliation)** 하도록 라우팅합니다. 이 패턴을 **Human-in-the-Loop(사람 개입)** 이라고 부릅니다.

해서는 안 되는 처리들:

- **더 상세해 보이는 섹션의 값을 택하기**: "상세한 섹션이 더 정확할 것"이라는 것은 시스템의 근거 없는 추측입니다.
- **두 값을 평균 내기 ($1,825)**: 문서 어디에도 없는 숫자를 만들어내는 것이므로 그 자체가 환각이며, 계약 금액으로는 명백히 틀린 값입니다.
- **먼저 나온 값만 취하고 뒤의 값을 조용히 버리기**: 충돌이 있었다는 사실 자체가 소실되어, 나중에 문제를 추적할 수도 없습니다. 데이터 손실이며 감사(audit) 불가능합니다.

> **원칙: 모호할 때 추측하지 말고, 모호하다는 사실을 출력에 명시적으로 표현하라(fail loudly, not silently).**

## 2. `tool_choice` — 네 가지 값과 각각의 용도

`tool_choice`는 **모델이 도구를 쓸지 말지, 쓴다면 어느 것을 쓸지**를 개발자가 통제하는 요청 파라미터입니다. 시험에서든 실무에서든 이 네 가지 구분이 핵심입니다.

| 값 | 동작 | 언제 쓰나 |
|---|---|---|
| `{"type": "auto"}` | **기본값.** 모델이 도구를 호출할지, 일반 텍스트로 답할지 스스로 결정 | 대화형 에이전트처럼 도구가 항상 필요하진 않은 경우 |
| `{"type": "any"}` | **등록된 도구 중 반드시 하나 이상을 호출.** 어느 것을 고를지는 모델이 문맥 보고 결정 | 여러 후보 중 모델이 분류해서 골라야 하고, 텍스트 응답으로 새는 것은 막아야 할 때 |
| `{"type": "tool", "name": "X"}` | **지정한 도구 X를 반드시 호출.** 다른 도구는 선택 불가 | 쓸 도구가 하나로 확정되어 있을 때 |
| `{"type": "none"}` | 도구를 전혀 호출하지 않음 | 도구를 잠시 끄고 싶을 때 |

`any`와 `{"type":"tool", ...}` 두 가지를 묶어 **강제 도구 선택(Forced Tool Selection)** 이라고 부릅니다.

**언제 강제하는가:** "모든 입력 문서는 반드시 태깅되어야 한다"처럼 **구조화된 출력이 필수 요구사항**일 때입니다. `auto`로 두면 모델이 도구를 호출하지 않고 일반 텍스트로 답해버릴 수 있고, 그러면 파이프라인이 깨집니다. 즉 `auto`와 강제 모드의 차이는 **출력 형식을 보장하느냐 마느냐**의 차이입니다.

### 2.1 텍스트 응답을 원천 차단해야 할 때

감사 추적(audit trail)처럼 "모든 문서가 반드시 구조화된 도구 호출을 만들어냈다"를 증명해야 하는 경우, `auto`로는 안 됩니다. 일부 요청이 `tool_use` 블록 없이 텍스트만 반환할 수 있기 때문입니다. 시스템 프롬프트로 아무리 강하게 경고해도 이는 **확률적 설득일 뿐 보장이 아닙니다.**

해결: `tool_choice`를 `{"type": "any"}` 또는 `{"type": "tool", "name": "extract_record"}` 로 바꿉니다.

참고로 다음은 이 문제와 무관합니다.

- `max_tokens`를 키우기 → 잘림(truncation) 문제이지 도구 호출 여부 문제가 아님
- `input_schema`의 필드를 optional → required로 바꾸기 → 도구를 **호출했을 때** 안의 필드 규칙일 뿐, 호출 자체를 강제하지 않음

### 2.2 `any`의 쓸모 (1): 모델을 라우터로 쓰기

문서 처리 서비스가 들어오는 파일이 송장/이력서/계약서 중 무엇인지 **사전에 모릅니다.** 요구사항은 두 가지입니다.

1. 반드시 셋 중 하나의 추출 도구가 실행되어야 한다 (일반 텍스트로 새면 안 됨)
2. 어느 도구인지는 문서 내용에 따라 달라야 한다

이 두 요구를 동시에 만족시키는 것이 정확히 `{"type": "any"}`입니다. 세 도구를 모두 `tools`에 등록하고 `any`로 강제하면, 모델이 문서를 읽고 적합한 도구를 스스로 고르되 반드시 하나는 호출합니다.

```python
response = client.messages.create(
    model="claude-sonnet-4-5",
    tools=[extract_invoice, extract_resume, extract_contract],
    tool_choice={"type": "any"},     # 셋 중 반드시 하나
    messages=[{"role": "user", "content": document_text}],
)
```

### 2.3 안티패턴: 외부 정규표현식 라우팅

지원 자동화 플랫폼이 티켓을 `bug_report` / `feature_request` / `billing_issue`로 분류해야 합니다. 흔한 초기 설계는 이렇습니다.

```
티켓 텍스트 → 정규표현식 키워드 매칭 → 분류 결정 → tool_choice: {"type":"tool", "name": 그 도구}
```

문제는 **정규표현식이 자연어 의미를 이해하지 못한다**는 것입니다. "결제가 안 되는 버그"처럼 키워드가 섞이면 오분류하고, 오분류된 채로 특정 도구가 강제되므로 잘못된 도구가 실행됩니다.

**더 나은 아키텍처**: 세 도구를 모두 한 요청에 등록하고 `tool_choice: {"type": "any"}`로 두어, 분류 판단 자체를 모델의 자연어 이해에 맡깁니다. 정규표현식 계층이 통째로 사라지고, 도구 실행 보장은 그대로 유지됩니다.

주의할 대안들:

| 대안 | 문제 |
|---|---|
| `{"type": "auto"}` | 모호한 티켓에서 모델이 도구를 건너뛰고 텍스트로 답할 수 있음. "항상 추출이 일어나야 하는" 파이프라인에는 부적합 |
| 도구별로 3번 병렬 호출 후 성공한 것만 취하기 | 토큰 비용과 컴퓨팅이 3배 |
| `tools` 파라미터를 아예 빼고 프롬프트로만 JSON 요구 | 도구 호출 기능의 형식 보장을 포기하는 것. 프롬프트 지시만으로는 형식 준수 보장 불가 |

### 2.4 `any`의 쓸모 (2): 여러 개의 작은 도구 = 스키마 모듈화

문서 종류(송장/영수증/발주서)가 업로드마다 다르고 한 번에 한 건씩 들어온다면, 두 가지 설계가 가능합니다.

- (a) 모든 종류를 한 스키마에 담은 거대한 `extract_document` 도구 하나
- (b) `extract_invoice`, `extract_receipt`, `extract_purchase_order` 세 개의 작은 도구 + `tool_choice: {"type":"any"}`

**(b)가 `any`의 의도된 사용법입니다.** `any`는 "반드시 도구를 호출하라(강제)" + "어떤 도구인지는 문서 내용 보고 네가 골라라(자율)"의 조합입니다. 각 도구는 해당 문서 유형에만 맞는 좁고 명확한 스키마를 가지므로:

- 관련 없는 필드가 프롬프트 노이즈로 섞이지 않습니다
- 어떤 유형으로 판정했는지가 **호출된 도구 이름 자체로** 드러납니다
- 유형별 필수 필드를 각각 엄격하게 강제할 수 있습니다

반면 (a)의 거대 통합 스키마는 대부분 비어 있는 필드가 많아 모델이 혼동하고, 유형별 required 제약을 걸기 어렵습니다.

### 2.5 여러 도구 중 특정 하나를 이번 턴에 강제해야 할 때

`translate_text`, `summarize_document`, `extract_metadata`가 모두 등록되어 있는데 이번 턴에는 반드시 `extract_metadata`가 먼저 실행되어야 한다면:

```json
"tool_choice": {"type": "tool", "name": "extract_metadata"}
```

`any`는 "아무 도구나 하나"이므로 다른 도구가 선택될 수 있어 보장이 안 됩니다. 즉 **`any` = 호출 보장 O / 도구 지정 X**, **`tool` = 호출 보장 O / 도구 지정 O** 입니다.

## 3. `tool_choice`를 둘러싼 흔한 오해

### 3.1 강제 도구 사용은 사전 자연어 텍스트를 억제한다

이력서 파싱 팀이 두 가지를 원한다고 합시다.

1. 이번 턴에 반드시 `parse_resume`가 호출될 것
2. 모호한 이력서 구간에 대한 자연어 설명도 도구 호출 **이전에** 함께 받을 것

특정 도구를 확실히 강제하는 문서화된 방법은 `tool_choice: {"type": "tool", "name": "parse_resume"}`입니다. 다만 **트레이드오프가 있습니다: 도구 사용이 강제되면 도구 호출 앞에 붙는 자연어 텍스트 생성이 억제(suppress)됩니다.** 즉 1번은 보장되지만 2번은 그 설정만으로는 얻을 수 없습니다.

실무적 함의와 오해 정리:

- 모델의 사고 과정을 텍스트로 보고 싶다면, 그 정보를 **도구 입력 스키마 안의 필드**로 만드는 편이 낫습니다. 예: `ambiguity_notes`, `reasoning` 같은 문자열 필드를 스키마에 추가.
- `{"type": "none"}`은 도구를 아예 호출하지 않으므로, "호출을 보장한다"는 요구와 정반대입니다.
- `{"type": "auto"}` + 프롬프트 지시는 호출을 **보장**하지 못합니다.
- `{"type": "any"}`가 강제 호출과 자연어 해설을 자유롭게 섞게 해준다는 것도 사실이 아닙니다. `any` 역시 강제 도구 사용에 해당합니다.

### 3.2 Extended Thinking과 `tool_choice`의 호환 제약

**Extended Thinking(확장 사고)** 은 모델이 최종 답을 내기 전에 내부적으로 길게 추론하도록 하는 기능입니다(요청에 `thinking` 파라미터로 켭니다). 어려운 판단이 필요할 때 정확도를 높입니다.

**제약: Extended Thinking은 `tool_choice`가 `auto` 또는 `none`일 때만 사용할 수 있습니다.** 강제 도구 선택(`{"type":"any"}` 또는 `{"type":"tool","name":...}`)과 동시에 쓰면 API가 유효성 검사 오류를 반환합니다.

즉 둘 중 하나를 골라야 합니다.

- 확장 사고를 쓰고 싶다 → `tool_choice`를 `auto`로 내린다 (도구를 부를지는 모델에 맡김)
- 도구 호출을 반드시 강제해야 한다 → 확장 사고를 끈다

`input_schema` 안에 `thinking_mode` 같은 필드를 넣어 우회할 수 있다는 것은 사실이 아닙니다. `input_schema`는 도구 인자의 형태를 기술할 뿐 API 동작을 바꾸지 않습니다.

### 3.3 기타 사실이 아닌 주장들

| 주장 | 사실 |
|---|---|
| `any`는 도구를 1개만 등록할 것을 요구한다 | 사실이 아님. `any`는 여러 도구를 등록해 두고 모델이 고르게 하는 것이 본래 용법 |
| `any`로 특정 도구를 기본값으로 고정할 수 있다 | 불가. 그건 `{"type":"tool","name":...}`의 역할 |
| `tool_choice`를 바꾸면 산술 불일치 같은 의미 오류가 잡힌다 | 무관. 도구 선택 방식과 의미 검증은 별개 층 |
| `input_schema`의 필드를 required로 바꾸면 도구 호출이 강제된다 | 무관. 호출됐을 때의 필드 규칙일 뿐 |

## 4. 재시도로 고칠 수 있는 오류 vs 없는 오류

### 4.1 재시도 루프란

검증에 실패하면 오류 내용을 모델에게 알려주고 다시 시도하게 하는 패턴입니다.

```python
for attempt in range(MAX_RETRIES):
    result = call_model(prompt)
    error = validate(result)
    if error is None:
        return result
    prompt += f"\n이전 시도의 오류: {error}. 수정해서 다시 출력하라."
raise ExtractionFailed()
```

이것을 **오류 피드백 재시도(Error-Feedback Retry)** 라고 부릅니다. 출력이 잘못되었을 때, **무엇이 왜 잘못되었는지를 알려주면서 다시 요청**하는 기법입니다.

```
1차 요청 → 출력 → 스키마 검증 실패
        → 오류 메시지를 프롬프트에 넣어 재요청 → 수정된 출력 → 검증 통과
```

같은 프롬프트를 그대로 다시 보내는 단순 재시도(blind retry)와는 다릅니다. 같은 입력에는 대체로 같은 실패가 반복되므로, **오류 정보를 되먹임(feedback)하는 것이 핵심**입니다.

### 4.2 형식 오류 vs 의미 오류

검증 실패를 만났을 때, 먼저 **어떤 종류의 오류인지 분류**하는 것이 대응 전략을 결정합니다.

| 종류 | 정의 | 예시 | 대응 |
|---|---|---|---|
| **형식 오류 (Formatting Error)** | 값 자체는 맞는데 표기 방식만 스키마와 다름 | 스키마는 `YYYY-MM-DD`인데 `14/03/2026`이 나옴 | 교정 재시도 |
| **의미 오류 (Semantic Error)** | 값 자체가 틀림. 잘못 읽었거나 계산이 틀림 | 총액이 항목 합계와 안 맞음 | 교차 검증, 필요시 사람 개입 |

형식 오류는 **가장 값싸게 고칠 수 있는 오류**입니다. 검증기가 낸 에러 메시지를 그대로 모델에게 되돌려주고 다시 요청하면 됩니다.

### 4.3 재시도가 고칠 수 있는 것

- 일시적인 형식 오류(JSON 문법 깨짐, 필드 누락)
- 모델의 우발적 실수, 부주의로 인한 오독
- 지시를 한 번 놓친 경우
- 정보는 문서에 있고 모델도 제대로 읽었으나 JSON 구조·키 위치·필드명이 틀린 경우

즉 **모델 측의 교정 가능한(correctable) 실수**입니다.

### 4.4 재시도가 절대 고칠 수 없는 것 — 재시도의 한계

#### (a) 원본에 정보가 존재하지 않는 경우 (Data Absence)

스캔된 서식에서 필요한 필드가 검은 마커로 가려져(**redacted**) 있다면, 모델은 그 값을 읽을 수 없습니다. 100번 재시도하며 상세한 오류 피드백을 줘도 빈 값만 반복됩니다. **없는 정보는 복구할 수 없습니다.** 억지로 채우게 만들면 그것은 환각(hallucination)이며 더 나쁩니다.

#### (b) 원본 데이터 자체가 모순된 경우 (Source Data Error)

은행 내역서의 개별 거래 합계와 명시된 총액이 안 맞는데, 조사해보니 **발급 은행이 실제로 산술 오류를 냈다**면, 모델은 원본에 적힌 숫자를 정확히 추출하고 있는 것입니다. 검증 규칙은 계속 실패하고, 재시도는 컴퓨팅 비용만 태웁니다. 계속 재시도하면 모델이 "합이 맞게" 숫자를 조작하도록 유도하는 셈이 되어 더 위험합니다.

### 4.5 실패 원인 분류표 — 이 실패는 어떤 종류인가

파이프라인 운영에서 가장 중요한 판단은 **"이 실패는 어떤 종류인가"** 입니다.

| 분류 | 설명 | 올바른 대응 |
|---|---|---|
| **처리/형식 오류 (processing / formatting error)** | 정보는 문서에 있고 모델도 제대로 읽었으나, JSON 구조·키 위치·필드명이 틀림 | **오류 피드백 재시도로 해결 가능.** 사람이나 새 문서 불필요 |
| **프롬프트 설계 미비** | 형식 변형에 대응하지 못하는 등 설계 문제 | 프롬프트/예시 개선 |
| **원본 데이터 부재 (source data absent)** | 필요한 정보가 그 문서 어디에도 없음 (예: 전화번호가 인쇄되어 있지 않음) | **재시도 중단.** 다른 원본 문서가 필요하거나, 필드를 `null`로 두고 사람 검토로 이관. 재시도는 무의미하고 오히려 환각을 유발 |
| **문서 미제공 (document not supplied)** | 정보가 다른 문서(예: 연례 서한)에만 있는데 그 문서를 넣지 않음 | **해당 문서를 파이프라인에 공급**해야 함 |
| **원본 데이터 모순 (source data error)** | 원본의 숫자끼리 앞뒤가 안 맞음 (발급처의 실제 오류) | **재시도 중단.** 원본 데이터 이슈로 플래그하고 사람에게 이관 |
| **의미/정책 모호성 (semantic ambiguity)** | 값은 있지만 그 값이 옳은지 판단하려면 정책·업무 기준이 필요 (예: 청구서에 주소가 하나뿐인데 그게 서비스 주소인지 우편 주소인지 알 수 없음) | **사람에게 에스컬레이션(human escalation)** 하거나 판정 규칙을 먼저 정의 |

> **핵심 직관: 모델은 존재하지 않는 정보를 만들어낼 수 없습니다(만들어내면 그게 환각입니다).** 따라서 재시도가 의미 있는 경우는 오직 "정보는 있는데 배치/형식만 틀린" 경우입니다.

### 4.6 절대 하면 안 되는 것

- **무한 재시도** — 비용 낭비 + 환각 유도
- **증상 숨기기** — 문제를 감지하는 검증 필드를 스키마에서 삭제 (예: 합계 불일치가 싫다고 `statement_total` 필드를 제거). 검증 파이프라인의 존재 이유를 무너뜨립니다
- **입력 거부(reject)** — 처리하기 어려운 입력 형식을 아예 거부해서 요구사항을 포기하기
- **구조화 포기** — 추출 자체를 포기하고 자유 텍스트로 저장하기. 파이프라인 설계를 무너뜨립니다

## 5. 타깃 피드백 재시도 (Retry with Targeted Feedback) 설계

추출이 실패했을 때 어떻게 다시 시도할 것인가도 설계 대상입니다.

### 5.1 대상화된 피드백(targeted feedback)의 3요소

API는 **무상태(stateless)** 입니다. 그러므로 후속 요청에는 **세 가지를 모두** 넣어야 합니다. 필수 필드 `invoice_number`가 누락된 JSON이 돌아온 경우를 예로 들면:

1. **원본 컨텍스트(원본 문서)** — 값을 찾아올 소스가 없으면 채울 수 없습니다. 이게 없으면 모델은 구조를 고치면서 값을 지어낼 수 있습니다.
2. **직전에 실패한 출력(JSON)** — 무엇을 고칠 대상인지 명시합니다. 모델이 자신이 만든 결과를 보고 나머지는 유지하고 빠진 것만 보완할 수 있습니다.
3. **구체적인 오류 지적 / 검증 오류 메시지** — 무엇이 왜 틀렸고 어떻게 되어야 하는지. "`invoice_number`가 필수인데 그 시도에서 누락되었다"처럼 **필드명을 명시**합니다.

이는 **멀티턴(multi-turn) 대화**로 구성합니다. 즉 대화 이력(`messages` 배열)에 이전 응답과 피드백을 쌓아 상태를 유지(stateful)하는 방식입니다.

### 5.2 요청 구성 예시

```
<original_document>
... 접수 문서 원문 ...
</original_document>

<previous_output>
{"guardian": {"date_of_birth": "1990-03-11"}, "patient": {...}}
</previous_output>

<validation_error>
date_of_birth는 guardian이 아니라 patient 객체 아래에 있어야 합니다.
</validation_error>

위 오류를 반영하여 스키마에 맞는 JSON을 다시 출력하세요.
```

코드로는 `messages` 배열에 직전 응답과 피드백을 쌓는 형태가 됩니다.

```python
try:
    validate(result, schema)
except ValidationError as e:
    messages.append({"role": "assistant", "content": raw_response})
    messages.append({"role": "user",
        "content": f"출력이 스키마 검증에 실패했습니다: {e.message}. "
                   f"start_date는 반드시 YYYY-MM-DD 형식이어야 합니다. 수정해서 다시 출력하세요."})
    result = call_claude(messages)   # 교정 재시도
```

핵심은 **에러 메시지에 "무엇이 왜 틀렸고 무엇을 원하는지"를 명시**하는 것입니다. 단순히 "다시 해봐"가 아니라 "형식은 `YYYY-MM-DD`여야 합니다"라고 요구 형식을 이름 붙여 알려줘야 모델이 정확히 고칩니다.

### 5.3 실패하는 재시도 패턴

3요소 중 무엇이 빠지면 어떻게 되는지 이해해 두는 것이 중요합니다.

| 실패 패턴 | 왜 실패하는가 |
|---|---|
| **오류 메시지(또는 오류 코드)만 단독 전송** | 모델이 이전 대화를 기억한다고 잘못 가정한 것. 무상태 환경에서는 문서도 이전 출력도 없어 아무것도 못 함. 게다가 코드만으로는 어떻게 고칠지 알 수 없음 |
| **원본 문서 없이 실패 JSON만 보내기** | 구조는 고칠 수 있어도 값의 근거가 없어 다른 필드를 유실하거나 값을 왜곡할 위험 |
| **원본 문서 없이 스키마만 새로 설명하기** | 추출 대상 데이터 자체가 사라지므로 작업이 불가능 |
| **똑같은 프롬프트를 그대로 재전송 (blind retry)** | 피드백이 0. 샘플링의 무작위성이 우연히 다른 결과를 내주기를 바라는 것뿐이라 같은 오류가 반복될 확률이 높음 |
| **시스템 프롬프트 문구만 바꿔서 재전송** | 어떤 필드가 빠졌는지 알려주지 않으면 모델은 같은 누락을 반복 |

## 6. 재시도 한도와 에스컬레이션

### 6.1 대응 사다리

비용이 낮은 순서로 시도합니다.

1. **피드백을 붙인 자동 재시도** — 형식 오류의 표준 해법
2. **스키마/프롬프트 조정** — 같은 오류가 반복되면 설계 문제
3. **사람 검토로 에스컬레이션(Human-in-the-loop)** — 자동 복구가 실패했거나 의미 오류일 때만

양쪽 극단이 모두 잘못입니다. 단순 형식 오류를 곧바로 사람에게 넘기는 것은 인적 자원 낭비이고, 반대로 사람이 판단해야 할 문제를 무한히 자동 재시도로 밀어붙이는 것은 비용 낭비이자 환각 유도입니다.

### 6.2 재시도 한도

재시도 루프에는 반드시 `MAX_RETRIES` 같은 상한이 있어야 합니다. 상한에 도달하면 예외를 던지고(`raise ExtractionFailed()`), 그 레코드는 자동 흐름에서 빠져나와 다음 경로로 갑니다.

- 필드를 `null`로 두고 사람 검토 큐로 이관
- 원본 데이터 이슈로 플래그(`conflict_detected: true` 등)
- 필요한 추가 문서를 요청

### 6.3 에스컬레이션은 실패가 아니다

자동화가 판단할 수 없거나 위험한 경우 사람에게 넘기는 것은 **실패가 아니라 설계된 안전장치**입니다. 콘텐츠 중재, 재무 대조, 개인정보 추출 등에서는 "판단 유보 → 사람"이 정답인 경로가 반드시 존재해야 합니다.

### 6.4 정리

| 상황 | 대응 |
|---|---|
| JSON 문법 깨짐 / 필드 누락 / 형식 불일치 | 타깃 피드백 재시도 |
| 같은 오류가 반복 | 프롬프트·스키마 설계 수정 |
| 원본에 정보 없음 | 재시도 중단, `null` + 사람 검토 |
| 원본이 서로 모순 | 충돌을 데이터로 표현(`conflict_detected`) + 사람 조정 |
| 정책·판단이 필요한 모호성 | 사람 에스컬레이션 또는 판정 규칙 정의 |
| 필요한 문서가 아예 없음 | 문서를 파이프라인에 공급 |
