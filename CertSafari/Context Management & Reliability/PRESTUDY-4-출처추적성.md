# 4. 출처 추적성과 근거 제시

이 장에서 다루는 것:

- **구조화된 출력 계약(스키마)** — 서브에이전트가 지켜야 할 형식 약속, 풍부한 에러 보고, 필수 메타데이터 필드, 이슈별 독립 레코드
- **데이터 형식과 표현 형식의 정합성** — 표로 쓸 것과 줄글로 쓸 것의 구분
- **출처 추적성(Provenance)** — 주장-출처 1:1 매핑, 메타데이터, 허위 모순, 중복 주장 병합, 정보 밀도
- **Claude 검색 결과 기능과 자동 인용** — RAG, 그라운딩, `search_results`, Citations, 신뢰도 점수와 캘리브레이션
- **근거 강도 구분** — 교차 검증된 발견 vs 단일 출처/미검증 발견
- **사용자 대면 출력 설계와 렌더링** — 공감·자동 해결, 콘텐츠 유형별 형식

## 1. 구조화된 출력 계약 (Output Contract / Schema)

### 1.1 출력 계약이란

서브에이전트가 코디네이터에게 결과를 돌려줄 때 지켜야 하는 **형식 약속**입니다.
JSON Schema 등으로 필드 이름, 타입, 필수 여부(`required`)를 명시합니다.

### 1.2 왜 단순 문자열 상태로는 부족한가

두 스키마를 비교해 봅시다.

**빈약한 스키마:**
```json
{ "status": "error" }
```

**풍부한 스키마 (Rich Error Reporting):**
```json
{
  "status": "error",
  "failure_type": "rate_limited_429",
  "attempted_query": "vector_search(index='kb-prod', q='refund policy')",
  "partial_results": [ { "doc_id": "POL-118", "score": 0.81 } ],
  "suggested_alternatives": ["keyword_search fallback", "retry after 60s"]
}
```

8개 서브에이전트 중 3개가 **서로 다른 이유로** 실패한 상황을 상상해 보세요.
빈약한 스키마에서는 세 개 모두 `"error"` 입니다. 코디네이터는 아무 판단도 할 수 없습니다.
재시도해야 할지, 다른 도구를 써야 할지, 그냥 진행해도 되는지 구분이 불가능합니다.

풍부한 스키마에서는 각 실패의 원인과 부분 진행 상황을 보고 **실패마다 다르게**
대응할 수 있습니다. 하나는 재시도, 하나는 대체 경로, 하나는 부분 결과로 진행.

**중요한 뉘앙스**: 구조화된 객체가 좋은 이유는 "구조화되었기 때문"이 아닙니다.
**그 안에 진단과 의사결정에 필요한 정보가 담겨 있기 때문**입니다.
필드만 많고 내용이 없는 객체는 문자열과 다를 바 없습니다.

또한 "에러 메시지를 단순화하면 서브에이전트가 알아서 해결하게 된다"는 것은
성립하지 않습니다. 보고 형식을 줄인다고 해결 능력이 생기지 않으며,
상위 전달 시 정보만 사라집니다.

### 1.3 필수 메타데이터 필드: 수치에는 시점을 붙인다

여러 서브에이전트의 결과를 코디네이터가 병합(merge)할 때, 값 자체만으로는
모순을 해석할 수 없는 경우가 많습니다.

예: 서브에이전트 A가 "해수면 상승 3.2mm/년", 서브에이전트 B가 "4.1mm/년"을 보고했습니다.
이것은 학계의 **실제 이견**일까요, 아니면 두 연구의 **측정 시기 차이**일까요?
출판 연도가 없으면 판단할 수 없습니다.

해결책은 스키마 수준의 수정입니다. 모든 추출된 수치 옆에
**출판일 또는 데이터 수집 시점**을 필수 필드로 요구합니다.

```json
{
  "type": "object",
  "required": ["figure", "unit", "source", "publication_date"],
  "properties": {
    "figure":           { "type": "number" },
    "unit":             { "type": "string" },
    "source":           { "type": "string" },
    "publication_date": { "type": "string", "format": "date" }
  }
}
```

일반 원칙: **어떤 사실을 다른 사실과 비교하거나 병합할 계획이라면,
비교에 필요한 메타데이터를 처음부터 필수 필드로 강제한다.**

함정:
- 단어 수, 자금 출처 같은 필드는 이 특정 모호성을 해소하지 못합니다.
  스키마에 필드를 추가할 때는 "이 필드가 실제로 어떤 판단을 가능하게 하는가"를 물어야 합니다.
- 모델에게 "값이 그 뒤로 어떻게 변했을지 추측하라"고 요구하는 것은
  사실 대신 환각을 필수 필드로 만드는 일입니다.

### 1.4 여러 이슈를 하나의 서술로 관리하지 않기

한 대화 세션에서 서로 다른 성격의 이슈가 동시에 진행되는 경우가 흔합니다.
예: 청구 분쟁(송장 #4821, $89.00 초과 청구)과 서비스 장애(오후 2:15 시작).

이것을 한 문장의 줄글 요약으로 관리하면 "the amount(그 금액)", "the time(그 시각)"
같은 표현이 **어느 이슈를 가리키는지 모호해집니다**. 이것을 참조 모호성이라고 합니다.

라벨을 붙이는 것("billing: $89.00", "outage: 2:15pm")은 완화책일 뿐이며,
여전히 하나의 텍스트 덩어리 안에서 관리됩니다.

올바른 방식은 **이슈별로 독립된 구조화 레코드를 유지**하는 것입니다.

```json
{
  "issues": [
    { "type": "billing_dispute",
      "invoice_number": "4821",
      "disputed_amount": 89.00,
      "status": "open" },
    { "type": "service_outage",
      "start_time": "2025-03-04T14:15:00Z",
      "status": "investigating" }
  ]
}
```

각 이슈 타입은 자기만의 필드 집합(스키마)을 갖습니다. 청구 분쟁에는 송장 번호와 금액,
장애에는 시작 시각과 상태. 이러면 어떤 값이 어느 이슈에 속하는지 구조적으로 확정됩니다.

또한 새 이슈가 등장했다고 이전 이슈를 자동으로 "해결됨" 처리하거나,
고객에게 "한 번에 하나씩만 말해달라"고 요구하는 것은 문제 해결이 아닙니다.
시스템이 여러 이슈를 동시에 추적할 수 있어야 합니다.

## 2. 데이터 형식과 표현 형식의 정합성

에이전트가 최종 보고서를 만들 때, **정보의 성격에 따라 서식을 다르게** 해야
가독성과 전달력이 올라갑니다.

| 정보 성격 | 예시 | 적합한 형식 | 이유 |
|---|---|---|---|
| 정량적, 시계열, 비교 가능, 반복 구조 | API 메서드/파라미터/반환값, 설정 항목, 벤치마크 수치, 주가·매출 추세 | 표(Table) 또는 구조화된 목록 | 값의 정렬·비교·스캔(Scannability)이 쉬움 |
| 정성적, 서사적, 맥락 의존 | 커뮤니티 여론, 정성 평가, 뉴스 요약, 배경 설명 | 줄글(Narrative Prose) | 흐름과 맥락이 자연스럽게 전달됨 |
| 병렬적 항목 나열 | 체크리스트, 후보군 | 목록(List) | 항목 간 독립성이 드러남 |

API 명세를 줄글로 풀어쓰면 독자가 메서드 이름과 파라미터를 문장 속에서 찾아내야 합니다.
반대로 여론 요약을 "메서드/파라미터" 표에 억지로 밀어 넣으면 뉘앙스가 파괴됩니다.

**피해야 할 방식:**
- 두 성격의 정보를 하나의 공통 표에 강제로 합치기.
- 하나의 문단으로 병합해 "통일된 서사"를 만들기 — 이것은 개선이 아닙니다.
- 모든 것을 하나의 형식(예: 전부 글머리 기호)으로 강제 통일 — 일관성이라는 이름의 가독성 저하.
- 숫자와 서술 문장을 하나의 목록 안에서 교대로 섞기 → 혼란 가중.
- 재무 수치를 서술형 문단으로 풀어쓰기 → 수치 비교가 매우 어려워짐.

각각을 자기에게 맞는 형식으로 유지한 채 **같은 보고서 안에 나란히 배치**하는 것이 올바른 구조입니다.

## 3. 출처 추적성 (Provenance)

### 3.1 Provenance란

**Provenance(출처 추적성)** 는 "이 정보가 어디서 왔는가"를 끝까지 따라갈 수 있는 성질입니다. 원래 미술품의 소장 이력을 뜻하는 단어로, 데이터 세계에서는 각 사실의 근거 문서를 추적하는 능력을 의미합니다.

Provenance가 없으면:
- 최종 보고서의 주장을 검증할 수 없습니다.
- 환각(Hallucination, 모델이 사실이 아닌 것을 지어내는 현상)을 걸러낼 수 없습니다.
- 상충하는 정보 중 무엇이 옳은지 판단할 수 없습니다.

### 3.2 주장-출처 매핑 (Claim-Source Mapping)

Provenance를 지키는 구체적 방법은 **모든 주장(Claim) 하나하나에 출처를 1:1로 짝지어(pair)** 두는 것입니다. 여기에 **뒷받침 발췌문(Supporting Excerpt)** 까지 함께 두면 검증이 쉬워집니다.

```json
{
  "claims": [
    {
      "claim": "경쟁사 A의 프로 요금제는 월 49달러다",
      "source": "https://competitor-a.com/pricing",
      "document_name": "Competitor A Pricing Page",
      "excerpt": "Pro plan — $49/month, billed annually",
      "retrieval_date": "2026-09-01",
      "publication_date": "2026-08-15"
    }
  ]
}
```

**문단 끝 참고문헌 목록(Bibliography)만으로는 부족합니다.** "이 문단을 쓰면서 이 문서 5개를 봤다"는 정보만으로는 문단 속 특정 주장 하나가 그 5개 중 어느 것에서 나왔는지 알 수 없습니다. 1:1 매핑이어야 추적이 성립합니다.

### 3.3 메타데이터 (Metadata)

메타데이터는 "데이터에 대한 데이터"입니다. 각 사실과 함께 반드시 실어야 할 대표 항목:

| 항목 | 의미 | 왜 필요한가 |
|---|---|---|
| source location / URL | 어디서 얻었는가 | 검증과 추적 |
| document name | 문서 이름 | 사람이 식별 |
| retrieval date | 언제 가져왔는가 | 데이터 신선도(Recency) 판단 |
| publication date | 원 자료 발행 시점 | 시점 차이 판별 |
| excerpt | 근거 원문 | 환각 검증 |

이 메타데이터가 있어야 코디네이터가 **프로그램적으로** 날짜를 비교해 최신 값을 고를 수 있습니다. 긴 서술문으로 추론 과정을 아무리 자세히 써도, 비구조화 텍스트에서는 날짜를 안정적으로 파싱·정렬할 수 없습니다.

### 3.4 허위 모순 (False Contradiction)

**허위 모순**이란 실제로는 모순이 아닌데 모순으로 오인되는 상황입니다.

예: 서브에이전트 A는 실업률 5.1%, 서브에이전트 B는 6.3%를 보고. 코디네이터는 충돌로 판단하지만, 사실은 **14개월 간격으로 발행된 서로 다른 시점의 보고서**에서 나온 값이었습니다. 시간에 따라 값이 변한 것이지 모순이 아닙니다.

**예방책**: 모든 수치에 **발행일 또는 데이터 수집 날짜**를 메타데이터로 붙이도록 출력 스키마를 강제합니다(1.3절의 스키마가 그대로 이 문제의 해법입니다).

하지 말아야 할 대응들:
- 수치를 대략적 범위로 바꾸기 → 정밀도만 잃고 시점 문제는 그대로.
- 6개월 지난 데이터를 무조건 폐기 → 시계열·추세 분석 자체가 불가능해지는 과잉 조치.
- 서브에이전트가 임의로 12개월 이동 평균으로 변환 → 원본 시점별 값이 사라지고 데이터가 왜곡됨.

### 3.5 중복 주장 병합 (Merging Near-Duplicates)

여러 서브에이전트가 같은 주제를 다른 각도에서 조사하면, **표현만 조금 다른 거의 동일한 주장**이 여러 개 생기고 각각의 출처는 서로 다릅니다.

**올바른 병합**: 중복 주장을 **하나의 엔트리로 통합(Consolidate)** 하되, 이를 뒷받침하는 **출처 인용 전체를 합집합으로 보존**합니다.

```json
{
  "claim": "해당 지역 실업률은 2026년 상반기에 하락 추세였다",
  "sources": [
    {"document": "BLS Report 2026-03", "excerpt": "...", "date": "2026-03-01"},
    {"document": "Regional Economic Review", "excerpt": "...", "date": "2026-05-20"},
    {"document": "State Labor Bulletin", "excerpt": "...", "date": "2026-06-10"}
  ]
}
```

여러 독립 출처가 같은 주장을 뒷받침한다는 사실 자체가 **신뢰도를 높이는 정보**입니다. 그러므로:
- 인용 없는 새 문장으로 다시 쓰기 → provenance 전멸.
- 가장 먼저 도착한 것만 남기고 나머지 폐기 → 다른 에이전트가 찾은 출처를 잃음.
- "이제 충분히 입증됐으니" 출처를 지우기 → 검증 불가능해짐. 치명적 오류.

### 3.6 컨텍스트 예산 안에서 정보 밀도 높이기

서브에이전트가 결론에 이르기까지의 **탐색적 추론(Exploratory Reasoning)** 을 여러 문단씩 그대로 반환하면, 상위 요약 에이전트의 컨텍스트 예산이 금방 소진되어 뒤쪽 서브에이전트 결과가 통째로 잘립니다.

**해결책**: 출력 계약을 바꿔 **탐색적 서술을 버리고(drop) 밀도 높은 핵심만** 반환하게 합니다.
- 핵심 사실(Key Facts)
- 뒷받침 인용(Supporting Citations)
- 연관성 점수(Relevance Score)

상위 취합 에이전트에게 필요한 것은 "어떻게 생각했는가"가 아니라 "무엇을 알아냈고 근거가 무엇인가"입니다.

효과 없는 대안들: 뒤 2개를 버리고 "분석 완료"라고 통보(정보 누락), 읽는 순서를 뒤집기(잘리는 대상만 바뀜), 에이전트 수를 늘리되 여전히 긴 서술 유지(총 토큰량이 오히려 증가).

## 4. Claude의 검색 결과 기능과 자동 인용

### 4.1 RAG란

**RAG (Retrieval-Augmented Generation, 검색 증강 생성)** 는
질문에 답하기 전에 외부 지식 베이스에서 관련 문서를 **검색(retrieve)** 해서
모델의 컨텍스트에 넣어주고, 그 근거 위에서 답을 **생성(generate)** 하게 하는 구조입니다.

목적: 모델이 학습하지 않은 사내 문서, 최신 정보에 대해 환각 없이 답하게 하는 것.

### 4.2 그라운딩과 출처 귀속

- **그라운딩(Grounding)**: 답변을 실제 제공된 자료에 근거하게 하는 것, 즉 생성 내용을 실제 근거에 묶어 두는 것.
- **출처 귀속(Source Attribution)**: 답변의 각 주장이 어느 문서, 어느 구절에서 왔는지 밝히는 것.

Claude의 웹 검색 기능은 답변에 자연스러운 인용(citation)을 붙여줍니다.
"이 문장은 이 출처에서 왔다"를 모델이 직접 표시합니다.

### 4.3 search_results 기능이 하는 일

**Search Results (검색 결과 블록)** 기능은, **자체 구축한 커스텀 지식 베이스**에서
검색한 결과를 `search_results` 형태의 컨텍스트 블록으로 Claude에 전달할 수 있게 합니다.

그 효과는 하나로 요약됩니다.

> **커스텀 지식 베이스의 내용에 대해서도, 웹 검색 인용과 동등한 품질의
> 자연스러운 인용과 정확한 출처 귀속을 얻는다.**

즉 "이 답변의 이 부분은 사내 정책 문서 POL-118의 이 구절에 근거한다"가
모델의 최종 종합(synthesis) 결과물에 자연스럽게 남습니다.
감사(audit) 가능성과 신뢰성이 필요한 내부 정책 Q&A 같은 곳에서 핵심적입니다.

### 4.4 Citations 기능

**Citations**는 모델이 답변을 생성할 때, 프롬프트로 제공된 문서 안의 **정확한 원문 구절(exact source passage)** 을 각 문장에 연결해 주는 기능입니다.

**일반 참고문헌과의 차이:**

| | 서브에이전트가 붙인 평문 참고문헌 | Citations 기능 |
|---|---|---|
| 단위 | 문서/출처 단위 목록 | 생성된 **문장(statement)** 단위 |
| 검증 | 사용자가 문서 전체를 뒤져야 함 | 해당 구절로 바로 이동(click-through) |
| 신뢰성 | 모델이 지어낸 출처일 수 있음 | 실제 제공된 문서의 위치를 가리킴 |

**언제 쓰는가:** 최종 사용자가 "이 문장의 근거가 어디냐"를 클릭해서 확인해야 하는 시스템(다중 출처 종합, 법률·의료·금융 리서치 등)에서 결정적입니다.

### 4.5 이 기능들이 해 주지 **않는** 일 (경계 이해 / 흔한 오해)

이것은 인용·귀속 기능이지 데이터 파이프라인 기능이 아닙니다. 다음은 하지 않습니다.

- 검색된 문서들을 하나의 **정규화된 포맷으로 자동 변환**해 주지 않습니다. (포맷팅 도구가 아님)
- 문서 간 **상충하는 내용을 자동으로 조정/해결(reconciliation)** 해 주지 않습니다.
  상충하는 통계를 하나의 합의값으로 합쳐 주지 않으며, 모순을 드러내 줄 뿐 판단은 여전히 설계자와 사용자의 몫입니다.
- 검색된 구절이 해당 문서의 **최신 버전임을 보장**하지 않습니다.
  버전 관리와 최신성 보장은 데이터베이스와 검색 인덱스의 책임입니다.
  낡은 문서를 색인에 넣어두면 낡은 내용이 인용될 뿐입니다.
- 각 문장에 **발행일 타임스탬프를 자동으로 붙여 주지 않습니다.** 시점 메타데이터는 3.3의 스키마로 직접 강제해야 합니다.
- **문서를 대신 검색해 오지 않습니다.** Citations는 **이미 프롬프트에 제공된 문서** 안에서 위치를 매핑할 뿐이며, RAG 검색이나 서브에이전트의 문서 읽기를 대체하지 않습니다.

### 4.6 신뢰도 점수(Confidence Score)와 캘리브레이션(Calibration)

**신뢰도 점수**란 모델이 추출한 각 값에 대해 "얼마나 확신하는가"를 함께 출력하게 하는 것입니다. 예: 이력서 파싱에서 "이름: 홍길동 (0.98), 졸업연도: 2019 (0.61)". 검토자는 점수가 낮은 필드부터 확인하면 되므로 한정된 시간을 효율적으로 씁니다.

**캘리브레이션(Calibration, 보정)** 이란: 모델이 0.9라고 말한 것들이 실제로 약 90% 정확한지를 **라벨링된 검증 세트(labeled validation set)**, 즉 정답이 붙어 있는 데이터와 비교해 검증하고, 어긋나면 점수를 보정하는 작업입니다. 검증 결과를 바탕으로 "0.85 미만은 사람이 검토"와 같은 **임계값(threshold)** 을 정할 수 있게 됩니다.

**캘리브레이션이 가능하려면 프롬프트 설계 단계에서 갖춰야 할 조건:**

1. **필드별(per-field) 점수** — 추출된 각 값 옆에 1:1로.
2. **일관된 수치 스케일(consistent numeric scale)** — 모든 필드, 모든 문서에서 동일하게(예: 0.0~1.0).
3. **빠짐없이 전 필드** — 일부만 출력하면 데이터셋이 불완전해집니다.

```json
{
  "name":            {"value": "홍길동", "confidence": 0.98},
  "email":           {"value": "hong@example.com", "confidence": 0.95},
  "graduation_year": {"value": 2019, "confidence": 0.61}
}
```

**부적합한 설계:**
- 숫자 대신 텍스트 설명만 출력 → 서술형은 정량적 통계 비교와 자동 임계값 판정이 불가능합니다.
- 문서 전체에 대한 단일 점수 → 어느 필드를 먼저 검토할지 알 수 없어 목적 자체를 달성하지 못합니다.
- 모델이 "어렵다"고 판단한 필드에만 점수 부여 → 데이터셋이 결측되어 통계적 평가 체계를 세울 수 없습니다. 게다가 무엇이 어려운지에 대한 모델의 판단 자체가 검증 대상입니다.

## 5. 근거 강도 구분: 교차 검증 vs 단일 출처

**교차 검증(Corroboration)** 은 서로 다른 독립적인 출처가 같은 사실을 뒷받침하는 것을 말합니다.

**시나리오:** 여러 서브에이전트가 어떤 치료법의 작용 기전(mechanism of action)에는 일치하지만, 장기 부작용에 대해서는 단 하나의 소규모 연구만이 시사하고 다른 어떤 출처도 뒷받침하지 않습니다.

**올바른 보고서 구조:** 잘 교차 검증된 발견과, 단일 출처이거나 이견이 있는(contested / uncorroborated) 발견을 **별도의 섹션으로 분리**하고, 각 출처가 스스로 어떻게 특성화했는지(연구 규모, 한계 등)를 그대로 보존합니다.

```markdown
## 잘 교차 검증된 발견 (다수 출처 일치)
- 작용 기전: ... (출처 A, B, C, D)

## 단일 출처 / 미검증 발견 (해석 주의)
- 장기 부작용 가능성: 소규모 연구 1건(n=42)에서만 시사됨. 타 출처의 확인 없음. (출처 E)
```

**하면 안 되는 것:**
- 신뢰도가 다른 정보를 하나의 매끄러운 서술로 뭉치기 → 확실성의 차이를 은폐해 독자를 오도합니다.
- 미검증 발견을 검증된 발견과 같은 확신 어조(confidence language)로 서술하기 → 어조의 일관성보다 정보 가치의 정확성이 우선입니다.
- 단일 출처라는 이유로 아예 삭제하기 → 특히 안전 관련 리스크 신호를 임의로 누락하는 것은 위험합니다. **불확실한 정보는 삭제 대상이 아니라 라벨링 대상입니다.**

이는 "결손을 감추지 말고 표기하라"와 같은 원칙의 다른 얼굴입니다: **불확실성은 숨기지 말고 구조로 드러낸다.**

## 6. 사용자 대면 출력 설계와 렌더링

### 6.1 공감과 자동 해결의 병행

고객 지원 AI 에이전트가 감정이 섞인 요청을 받았을 때의 원칙:

1. **감정 인정(Acknowledgement)**: 고객의 불만·좌절을 먼저 짧게 인정합니다. 감정적 표현을 "해결과 무관하다"며 무시하고 기계적으로 처리하면 불만이 악화됩니다.
2. **정책 범위 내라면 즉시 처리(Automated Resolution)**: 표준 규정(예: 30일 교환 정책) 안에서 해결 가능한 단순 건이라면 지체 없이 처리합니다.

### 6.2 불필요한 에스컬레이션과 마찰 피하기

- **감정적 어조 = 사람 상담원 이관 신호가 아닙니다.** 고객이 사람과 대화하겠다고 **명시적으로 요청하지 않았고** 요청이 규정 내에서 해결 가능하다면, 곧바로 사람에게 넘길 이유가 없습니다.
- **불필요한 확인 절차를 추가하지 않습니다.** "사람 상담원을 원하시는 게 아닌 거 맞죠?" 같은 되묻기는 처리를 지연시키고 마찰(Friction)을 늘려 불만을 키웁니다.

에스컬레이션은 **정책 밖의 건, 판단이 필요한 건, 고객이 명시적으로 요청한 경우**에 하는 것입니다.

### 6.3 출력 렌더링

최종 보고서를 만들 때 서로 성격이 다른 데이터를 하나의 형식으로 통일하면 가독성이 떨어집니다. **각 콘텐츠 유형을 그 유형의 자연스러운 형식에 맞춘다**는 원칙과 구체적 대응표는 2장을 그대로 적용합니다.

여기에 근거 제시가 결합되면 사용자 대면 출력의 최종 형태가 나옵니다:
- 정량 데이터는 표로, 정성 설명은 줄글로.
- 각 주장에는 클릭 가능한 문장 단위 인용(Citations)을.
- 교차 검증된 발견과 단일 출처 발견은 분리된 섹션으로.
