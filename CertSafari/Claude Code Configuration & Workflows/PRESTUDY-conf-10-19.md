# 사전 학습 노트 — Claude Code 설정과 워크플로우 (conf-10-19 범위)

이 문서는 해당 범위에서 다루는 개념을 아무 배경지식이 없는 상태에서 이해할 수 있도록 처음부터 설명합니다.

---

## 0. 큰 그림: Claude Code란 무엇인가

Claude Code는 터미널에서 동작하는 AI 코딩 도구입니다. 사용자가 자연어로 요청하면, Claude가 저장소의 파일을 읽고, 수정하고, 명령을 실행합니다.

핵심적으로 이해해야 할 세 가지 축이 있습니다.

1. **컨텍스트(Context)**: Claude가 한 번에 "볼 수 있는" 정보의 총량. 유한한 자원이며, 여기에 무엇을 넣을지가 품질과 비용을 좌우합니다.
2. **설정(Configuration)**: 저장소 안의 파일(`CLAUDE.md`, `.claude/rules/`, `SKILL.md` 등)로 Claude의 행동을 미리 규정하는 방법.
3. **워크플로우(Workflow)**: 요청의 성격에 따라 어떤 실행 방식(즉시 실행, 계획 모드, 서브에이전트 위임, 인터뷰)을 고르는가.

## 1. 프로젝트 지침 파일: CLAUDE.md

### 1.1 CLAUDE.md는 무엇인가

`CLAUDE.md`는 저장소에 두는 마크다운 파일로, "이 프로젝트에서 코드를 다룰 때 지켜야 할 규칙"을 적어 두는 곳입니다. 세션이 시작될 때 그 내용이 Claude의 컨텍스트에 자동으로 주입됩니다. 즉, 매번 "우리 팀은 탭 대신 스페이스를 씁니다"라고 말할 필요 없이 파일에 한 번 적어두면 됩니다.

전형적인 내용:

```markdown
# 프로젝트 규칙

- 패키지 매니저는 pnpm을 사용한다.
- 모든 공개 함수에는 JSDoc 주석을 붙인다.
- 테스트는 vitest로 작성하고 `*.test.ts` 이름을 쓴다.
```

### 1.2 위치에 따른 종류

- **저장소 루트의 `CLAUDE.md`**: 프로젝트 전체에 적용되는 지침.
- **디렉터리별 `CLAUDE.md`** (per-directory CLAUDE.md): 예를 들어 `src/db/CLAUDE.md`. 해당 디렉터리(및 그 하위)의 파일을 다룰 때 관련되는 지침. "이 폴더에 관한 설명은 이 폴더 안에 둔다"는 발상입니다.
- **`CLAUDE.local.md`**: 개인용/로컬 전용 지침. 보통 버전 관리에서 제외하고, 자기 머신에만 해당하는 내용을 적습니다. 팀 공용 규칙을 여기에 **복사해 두면 같은 내용이 두 번 로드되어 컨텍스트만 낭비**됩니다. 중복은 이득이 아니라 비용입니다.

### 1.3 CLAUDE.md가 비대해질 때 생기는 문제

`CLAUDE.md`가 커질수록(예: 300줄 초과) 두 가지 문제가 동시에 생깁니다.

1. **컨텍스트 사용량 증가(context usage)**: 세션을 시작하기만 해도 파일 전체가 컨텍스트에 들어갑니다. 실제로는 CSS만 만지는 세션에서도 GraphQL 규칙과 DB 마이그레이션 규칙이 함께 로드됩니다. 낭비이며, 남는 작업 공간이 줄어듭니다.
2. **준수율 하락(adherence drop)**: 지침이 길고 대부분이 지금 작업과 무관하면, 정작 중요한 몇 줄이 잡음에 묻힙니다. 지침은 많을수록 잘 지켜지는 것이 아니라, **관련성이 높을수록** 잘 지켜집니다.

이 문제의 정공법이 다음 절의 "경로 범위 규칙"입니다.

## 2. 규칙 시스템: `.claude/rules/`

### 2.1 개념

`.claude/rules/` 디렉터리는 지침을 **주제별로 쪼갠 파일들**을 담는 곳입니다. `CLAUDE.md` 하나에 모든 것을 몰아넣는 대신, 다음처럼 나눕니다.

```
.claude/rules/
  graphql.md
  migrations.md
  css-modules.md
  security.md
```

각 파일은 frontmatter(파일 맨 위 `---`로 감싼 YAML 메타데이터 블록)와 본문으로 구성됩니다.

```markdown
---
paths:
  - "src/api/**/*.ts"
---

# API 라우트 규칙

- 모든 핸들러는 입력값을 zod 스키마로 검증한다.
- 각 엔드포인트에 OpenAPI 주석을 단다.
```

### 2.2 `paths` 프론트매터 — 경로 범위 지정(path-scoped rules)

`paths`는 **이 규칙이 어떤 파일에 해당하는가**를 글로브(glob) 패턴 목록으로 지정합니다.

- `paths`가 **있으면**: Claude가 그 패턴에 매칭되는 파일을 실제로 다룰 때에만 해당 규칙이 컨텍스트에 들어옵니다. 이것이 "조건부 로딩"이며, 컨텍스트 절약과 준수율 향상의 핵심입니다.
- `paths`가 **없으면**: 조건 없는 전역 규칙이 되어, 매 세션마다 항상 로드됩니다. 즉 `CLAUDE.md`를 통째로 `.claude/rules/` 파일 하나로 옮기고 `paths`를 안 붙이면, 디스크상의 파일 이름만 바뀌었을 뿐 로딩 동작은 이전과 완전히 동일합니다. 문제는 해결되지 않습니다.

따라서 비대한 `CLAUDE.md` 해결법의 정석은:

> 주제별로 규칙 파일을 나누고, 각각에 그 주제와 관련된 파일 패턴을 `paths`로 지정한다.

```
.claude/rules/graphql.md      → paths: ["src/graphql/**/*.ts"]
.claude/rules/migrations.md   → paths: ["**/migrations/**"]
.claude/rules/css-modules.md  → paths: ["**/*.module.css"]
```

이렇게 하면 GraphQL 리졸버를 만질 때만 GraphQL 규칙이 들어오고, CSS 모듈을 만질 때만 CSS 규칙이 들어옵니다. 매 세션 전부를 싣지 않습니다.

### 2.3 글로브(glob) 패턴 문법

글로브는 파일 경로를 패턴으로 매칭하는 표기법입니다. 정규표현식보다 단순하며, 반드시 익혀야 할 것은 세 가지입니다.

| 기호 | 의미 |
|---|---|
| `*` | 경로 구분자(`/`)를 **넘지 않는** 임의의 문자열. 즉 한 단계 디렉터리 안에서만 매칭. |
| `**` | 경로 구분자를 **넘어서는** 임의의 깊이. 즉 재귀적으로 하위 디렉터리 전체. |
| `?` | 임의의 한 글자. |

구체적인 비교(핵심입니다):

| 패턴 | 매칭됨 | 매칭 안 됨 |
|---|---|---|
| `src/api/*.ts` | `src/api/index.ts` | `src/api/routes/user.ts` (한 단계 더 깊음) |
| `src/api/**/*.ts` | `src/api/index.ts`, `src/api/routes/v2/user.ts` | `src/utils/date.ts` |
| `src/**/*.ts` | `src/api/x.ts`, `src/utils/x.ts` (범위가 너무 넓음) | `lib/x.ts` |
| `**/migrations/**` | `src/db/migrations/001.sql`, `services/billing/migrations/002.sql` | `src/db/models/user.ts` |

또한 패턴은 보통 **저장소 루트를 기준**으로 해석됩니다. 따라서 실제 경로가 `src/api/...`인데 패턴을 `api/**/*.ts`라고 쓰면, 루트 바로 아래에 `api/` 디렉터리가 없으므로 의도한 파일이 잡히지 않습니다. 접두 경로를 정확히 맞추는 것이 중요합니다.

**요구사항 → 패턴 변환 연습**

"`src/api/` 안의 TypeScript 파일 전부, 아무리 깊이 중첩되어 있어도. 단 `src/utils/`나 `src/components/`는 제외."

→ `src/api/**/*.ts`

세 가지 실패 유형을 각각 이해해 두세요.
- 범위가 너무 넓음: `src/**/*.ts` — `src/` 아래 전부를 잡아 `utils`, `components`까지 포함.
- 범위가 너무 좁음: `src/api/*.ts` — `src/api/` 바로 아래 파일만 잡고 중첩 서브폴더를 놓침.
- 접두 경로 오류: `api/**/*.ts` — 루트 기준 `api/`를 찾으므로 `src/api/`와 어긋남.

### 2.4 디렉터리별 CLAUDE.md vs. 경로 범위 규칙 — 선택 기준

둘 다 "특정 파일에만 지침을 적용한다"는 목적을 갖지만, 적용 방식이 다릅니다.

- **디렉터리별 `CLAUDE.md`**: **위치(location)** 기준. 그 디렉터리 트리 안에 있는 파일에 적용됩니다. 대상이 한 곳에 모여 있을 때 자연스럽습니다.
- **`.claude/rules/` + `paths` 글로브**: **패턴(pattern)** 기준. 저장소 트리 전역(tree-wide)에서 패턴에 맞는 파일이라면 어디에 있든 적용됩니다.

따라서 판단 기준은 단순합니다.

> 대상 파일이 **한 디렉터리에 모여 있는가**, 아니면 **여러 무관한 서브시스템에 흩어져 있는가**?

예: 데이터베이스 마이그레이션 파일이 `src/db/migrations/`, `services/billing/migrations/`, `packages/auth/migrations/` 등 서로 무관한 여러 곳에 흩어져 있다고 합시다. `src/db/CLAUDE.md` 하나로는 나머지 두 곳을 덮을 수 없습니다. 이때는 `paths: ["**/migrations/**"]`인 경로 범위 규칙이 정확한 도구입니다.

흩어져 있다고 해서 같은 `CLAUDE.md`를 모든 디렉터리에 수동 복제할 필요는 없습니다. 복제본은 반드시 시간이 지나며 서로 어긋나고(드리프트), 유지보수 부채가 됩니다. 경로 범위 규칙이 재귀 글로브를 지원하므로 복제는 불필요합니다.

정리:

| 상황 | 적합한 구조 |
|---|---|
| 규칙 대상이 한 디렉터리 트리에 모여 있음 | 디렉터리별 `CLAUDE.md` |
| 규칙 대상이 여러 무관한 위치에 흩어져 있음 | `.claude/rules/` + `paths` 글로브 |
| 프로젝트 전체에 항상 적용 | 루트 `CLAUDE.md` 또는 `paths` 없는 규칙 파일 |

### 2.5 규칙 파일과 심볼릭 링크(symlink)

**심볼릭 링크란**: 파일시스템에서 "다른 경로를 가리키는 포인터 역할의 파일"입니다. 복사본이 아니라 참조이므로, 원본이 바뀌면 링크를 통해 읽는 내용도 즉시 바뀝니다.

```bash
# 저장소 안의 규칙 디렉터리에 중앙 규칙 파일을 링크로 연결
ln -s /shared/company-rules/security.md .claude/rules/security.md

# 디렉터리 전체를 링크할 수도 있다
ln -s /shared/company-rules .claude/rules/shared
```

**왜 필요한가**: 조직 내 여러 저장소가 동일한 코드리뷰 규칙을 **글자 그대로(verbatim) 재사용**해야 하고, 그 규칙이 **단일 진실 공급원(single source of truth)** 한 곳에서 관리되어, 바뀌면 모든 저장소에 자동 반영되기를 원할 때입니다. 물리적 복사본을 각 저장소에 두면 반드시 시간이 지나며 서로 달라집니다.

**동작 방식**: `.claude/rules/`의 규칙 탐색은 심볼릭 링크를 **정상적으로 해석(resolve)** 합니다. 구체적으로:

- 개별 파일 링크도, 디렉터리 전체 링크도 모두 처리됩니다. "디렉터리만 되고 파일 하나는 안 된다" 같은 제약은 없습니다.
- 링크 대상이 같은 git 저장소 안에 있을 필요가 없습니다. git 서브모듈이어야 할 필요도 없습니다. 저장소 바깥의 별도 폴더를 가리켜도 됩니다.
- 링크된 항목이 "일반 파일이 아니라서" 조용히 무시되는 일은 없습니다.

**순환 감지(circular detection)**: 링크가 링크를 가리키다 결국 자기 자신으로 되돌아오는 순환 구조(A → B → A)를 만들 수 있습니다. 순진하게 따라가면 무한 루프에 빠집니다. 규칙 탐색기는 이미 방문한 경로를 기억해 두었다가 순환을 감지하면 멈추므로, 이런 구조에서도 안전하게 종료됩니다.

**그래서 실무에서 확인할 것**: 심볼릭 링크가 지원되는지를 걱정할 게 아니라, **각 저장소의 링크가 올바른 공유 소스를 가리키고 있는지**를 검증하면 됩니다. 링크가 깨졌거나(대상 경로 없음) 잘못된 경로를 가리키면 규칙이 조용히 빠질 수 있습니다.

운영상 주의점:
- Windows에서는 심볼릭 링크 생성에 별도 권한이나 개발자 모드가 필요할 수 있습니다.
- git은 심볼릭 링크를 링크 자체로 저장하지만, 클론된 환경에서는 링크가 가리키는 대상 경로가 존재하지 않을 수 있습니다. 절대 경로와 상대 경로 중 무엇을 쓸지 신중히 결정해야 합니다.
- 참고로 git 서브모듈은 한 저장소 안에 다른 저장소를 포함시키는 별개의 기능이며, 규칙 공유를 위한 전제 조건이 아닙니다. 심볼릭 링크와 서브모듈은 각각 독립적인 선택지입니다.

## 3. 스킬(Skills)

### 3.1 스킬이란

스킬은 "특정 종류의 작업을 위한 사전 포장된 지시서"입니다. 배포 절차, 리뷰 체크리스트, PR 요약 방식처럼 반복되는 작업의 수행 방법을 문서로 만들어 두면, Claude가 그 작업을 만났을 때 해당 지시서를 불러와 따릅니다.

디렉터리 구조는 보통 이렇습니다.

```
.claude/skills/pr-summary/
  SKILL.md
```

`SKILL.md`는 frontmatter + 본문 구조입니다.

```markdown
---
name: pr-summary
description: PR 데이터를 가져와 요약한다. 사용자가 PR 요약을 요청할 때 사용.
allowed-tools: Read Grep
context: fork
agent: Explore
---

# 절차

1. `gh pr view`로 PR 정보를 가져온다.
2. 변경 파일 목록을 분류한다.
3. 3문단 이내로 요약한다.
```

### 3.2 `allowed-tools` — 가장 오해하기 쉬운 필드

이름이 "allowed(허용된) tools"이므로 직관적으로는 "여기 적힌 도구만 쓸 수 있다"는 **화이트리스트 제한**처럼 보입니다. 실제 동작은 다릅니다.

**실제 의미**: `allowed-tools`에 나열된 도구는 **사용자 권한 승인 프롬프트(permission prompt)를 건너뛰고 자동 허용**됩니다. 즉 이것은 "편의를 위한 사전 승인 목록"이지, "그 외 도구를 차단하는 보안 필터"가 아닙니다.

결과적으로 다음이 모두 성립합니다.

- `allowed-tools: Write Edit`이라고 써도 `Bash`는 여전히 호출될 수 있습니다. 단지 `Bash`는 호출될 때 사용자에게 승인 프롬프트가 뜰 뿐입니다.
- 자동으로 샌드박스(sandbox)가 걸리거나, 파일 작업 외 도구가 원천 비활성화되지 않습니다.
- 파일 삭제나 쉘 명령 실행 같은 파괴적 동작을 막아주지 못합니다.
- 따라서 **최소 권한 원칙(least privilege)을 구현하는 수단으로 `allowed-tools`를 쓰는 것은 잘못된 설계**입니다. 오히려 반대 방향으로 작동합니다 — 나열한 도구에 대해 승인 관문을 **없애는** 필드이기 때문입니다.

실제로 도구 사용을 제한하고 싶다면 별도의 권한 체계(permission mode / 권한 설정)를 사용해야 하며, `SKILL.md`의 이 필드 하나로 해결되지 않습니다. 어떤 설정 상황에서 "권한 모드는 바꾸지 않았다"는 조건이 붙는다면, 그것은 곧 실질적 제한 장치가 전혀 없다는 뜻입니다.

기억할 한 줄: **`allowed-tools`는 문을 잠그는 자물쇠가 아니라, 문을 열어두는 프리패스입니다.**

### 3.3 `context: fork` — 컨텍스트 분기

스킬을 실행하는 방식에는 크게 두 가지가 있습니다.

- **기본(인라인)**: 현재 대화 컨텍스트 안에서 스킬 지시서를 읽고 그대로 이어서 수행합니다. 지금까지의 대화 내용과 로드된 프로젝트 지침을 모두 공유합니다.
- **`context: fork`**: 스킬을 **별도의 서브에이전트**에서 실행합니다. 메인 대화와 분리된 자체 컨텍스트를 갖고, 작업이 끝나면 결과만 메인으로 돌아옵니다.

`fork`의 이점은 **컨텍스트 격리**입니다. 탐색 과정에서 읽은 대량의 파일 내용이 메인 대화를 오염시키지 않고, 최종 요약만 남습니다. 긴 조사·요약 작업에 적합합니다.

주의: `fork`는 컨텍스트를 **분기**하는 설정이지, "프로젝트 수준 파일을 전부 제거해 격리한다"는 의미가 아닙니다. 분기된 실행이 무엇을 보게 되는지는 다음 절에서 설명하는 **어떤 에이전트로 실행되는가**에 달려 있습니다.

### 3.4 `agent:` — 어떤 서브에이전트로 실행할 것인가

`agent:` 필드는 포크된 실행을 어떤 종류의 에이전트에 맡길지 지정합니다. 대표적으로 내장 **`Explore`** 에이전트가 있습니다.

`Explore`는 **읽기 전용 탐색 전용 에이전트**로, "코드베이스에서 무언가를 빠르고 가볍게 찾는다"는 한 가지 목적에 최적화되어 있습니다. 그 최적화의 일환으로, **시작 시 `CLAUDE.md` 같은 프로젝트 지침 파일을 로드하지 않습니다.** 컨텍스트를 최대한 작게 유지해 검색을 빠르고 저렴하게 만들기 위한 설계 선택입니다.

### 3.5 `context: fork` + `agent: Explore` 조합에서 생기는 함정

이 두 설정을 함께 쓴 스킬은, 결과적으로 다음만을 보게 됩니다.

- 스킬 자신의 내용(`SKILL.md` 본문)
- 그 에이전트 자체의 시스템 프롬프트
- 실행 중 스스로 명시적으로 읽어 들인 파일

**프로젝트의 `CLAUDE.md` 컨벤션은 여기에 포함되지 않습니다.**

그래서 예컨대 `pr-summary` 스킬을 `context: fork` + `agent: Explore`로 설정하면, 생성된 요약문이 프로젝트 `CLAUDE.md`에 적힌 문체·용어·형식 규칙을 전혀 반영하지 못합니다.

원인을 정확히 짚는 것이 중요합니다. 다음은 **원인이 아닙니다**:

- **`context: fork`가 프로젝트 파일을 일괄 제거해서** — 아닙니다. 포크는 컨텍스트를 분기할 뿐이며, 지침 로딩 여부는 어떤 에이전트로 실행되는가에 달려 있습니다.
- **`allowed-tools: Read` 권한이 없어서** — 아닙니다. 지침의 자동 로드는 도구 권한과 완전히 별개의 메커니즘입니다. `Read` 권한은 Claude가 명시적으로 파일을 읽을 때의 문제이지, 시작 시 자동 주입과는 무관합니다.
- **스킬에 인자(argument)를 넘겨서** — 아닙니다. 인자 유무는 `CLAUDE.md` 로딩에 아무 영향이 없습니다.

**진짜 원인은 `Explore` 에이전트가 컨텍스트를 작게 유지하려고 시작 시 `CLAUDE.md` 로딩을 건너뛴다는 설계 특성입니다.**

실무적 대응: 컨벤션이 반드시 반영되어야 하는 스킬이라면 (a) 필요한 규칙을 `SKILL.md` 본문에 직접 적어 두거나, (b) 스킬 절차에 `CLAUDE.md`를 명시적으로 읽는 단계를 넣거나, (c) 지침 로딩이 이루어지는 실행 방식/에이전트를 선택합니다.

## 4. 실행 모드와 작업 방식 선택

### 4.1 계획 모드(Plan Mode)

**무엇인가**: Claude가 코드를 수정하지 않고, 코드베이스를 조사한 뒤 "무엇을 어떻게 바꿀 것인지" 계획을 제시하는 읽기 전용 모드입니다.

**왜 존재하는가**: 큰 변경은 방향이 틀리면 되돌리는 비용이 큽니다. 예컨대 12개 서비스가 함께 쓰는 공유 유틸리티 패키지를 재구조화한다면, 잘못된 설계로 전부 뜯어고친 뒤 되돌리는 것은 재앙입니다. 계획 모드는 실제 편집 전에 사람이 설계를 검토하고 합의할 지점을 만들어 줍니다.

**흐름**:

1. 계획 모드로 들어간다.
2. Claude가 조사하고 계획을 제시한다.
3. 사용자가 계획을 검토한다.
4. **계획을 승인하고, 세션을 편집 모드(editing mode)로 전환하는 옵션을 선택한다.**
5. Claude가 승인된 계획대로 곧바로 파일 수정을 진행한다.

4번이 핵심입니다. 승인 시점에 제시되는 선택지 중 편집을 허용하는 모드로 전환하는 것을 고르면, **이미 합의된 설계가 컨텍스트에 그대로 살아 있는 상태로** 구현이 이어집니다. 각 파일 편집의 근거를 다시 설명할 필요가 없고, 지연 없이 구현 단계로 넘어갑니다.

피해야 할 대안들과 그 이유:

- **계획 모드에 무기한 머무르기** → 편집이 절대 일어나지 않고 채팅으로 설명만 반복됩니다. 계획 모드는 정의상 코드를 수정하지 않는 모드입니다.
- **새 세션을 처음부터 시작해 전부 다시 설명하기** → 이미 완성된 계획과 축적된 컨텍스트를 버리는 순수한 중복 작업입니다.
- **승인 없이 종료하고 손으로 직접 작업하기** → 자동화의 이점을 통째로 포기하는 비효율적 선택입니다.

### 4.2 직접 실행(Direct Execution)과 그 판단 기준

모든 요청에 계획 모드가 필요한 것은 아닙니다. 절차 자체에도 비용이 있습니다 — 계획 수립, 탐색, 검토는 시간과 컨텍스트를 소모합니다.

**직접 실행이 맞는 조건**:
- 변경 범위가 좁고 명확하다(예: 기존 함수 하나 안에 조건문 하나 추가).
- 대상 코드와 주변 파일이 이미 팀에게 잘 파악되어 있다.
- 요구사항에 모호함이 없다(well-scoped requirement).

예: "이 폼 검증 함수에 만료일이 오늘보다 이전이면 거부하는 검사를 추가해줘." 함수 하나, 요구사항 명확, 파일 이해됨 → 곧바로 실행하는 것이 가장 빠르고 효율적입니다.

**과잉 대응(over-engineering)의 전형**:

- 잘 아는 단일 함수 수정에 `Explore` 서브에이전트를 붙여 저장소 전체의 날짜 처리 함수를 목록화한다 → 이미 파악된 코드에 불필요한 탐색 비용.
- 계획 모드에 들어가 다른 검증 함수들까지 재구조화할지 검토한다 → 요청 범위를 벗어난 확장.
- 한 함수 변경을 전 애플리케이션 폼을 아우르는 다단계 마이그레이션 계획으로 취급한다 → 명백한 과장.

**정리하면**: 절차의 무게는 작업의 복잡도에 비례해야 합니다.

| 작업 성격 | 적절한 방식 |
|---|---|
| 명확하고 국소적인 변경, 코드 이미 파악됨 | 직접 실행 |
| 다중 파일에 걸친 재구조화, 되돌리기 비용 큼 | 계획 모드 → 승인 → 편집 모드 전환 |
| 어디에 있는지 모르는 것을 광범위하게 조사 | 서브에이전트 위임 |
| 요구사항 자체가 불명확한 미지의 도메인 | 인터뷰(AskUserQuestion) |

### 4.3 서브에이전트(Subagent) 위임

서브에이전트는 별도 컨텍스트를 가진 보조 에이전트에게 작업을 맡기는 방식입니다. `Explore`가 대표적인 읽기 전용 탐색 에이전트입니다.

**적합한 경우**: 어디에 있는지 모르는 것을 여러 디렉터리와 명명 규칙에 걸쳐 광범위하게 찾아야 하고, 중간 과정의 파일 내용이 아니라 결론만 필요할 때. 탐색 과정의 대량 텍스트가 메인 컨텍스트를 오염시키지 않습니다.

**부적합한 경우**: 대상 파일과 위치를 이미 알고 있을 때. 이 경우 위임 자체가 순수한 오버헤드입니다.

### 4.4 `AskUserQuestion` — 대화형 요구사항 도출

**무엇인가**: Claude가 사용자에게 구조화된 선택형 질문을 던져 답을 받는 도구입니다. 방향을 뒤집어, Claude가 사용자를 **인터뷰**할 수 있게 해 줍니다.

**왜 필요한가**: 익숙하지 않은 도메인에서는 사용자 자신도 무엇을 결정해야 하는지 모릅니다. 예를 들어 실시간 협업 문서 편집기를 처음 만든다면, 다음 같은 질문들이 사전에 떠오르지 않습니다.

- **캐시 무효화(cache invalidation) 전략**: 여러 클라이언트가 같은 문서를 캐싱하고 있을 때, 변경이 생기면 낡은 캐시를 언제 어떻게 버릴 것인가. 무효화 시점을 잘못 잡으면 사용자가 남의 편집을 못 보거나, 반대로 캐시가 무의미해집니다.
- **충돌 해결(conflict resolution) 접근**: 두 사용자가 같은 문단을 동시에 고칠 때 어떻게 병합할 것인가. OT(Operational Transformation), CRDT, last-write-wins 등 서로 다른 복잡도와 보장을 갖는 선택지들이 있으며, 이 선택은 시스템 전체 구조를 결정합니다.
- **실패 처리(failure handling)**: 네트워크가 끊겼을 때 오프라인 편집을 허용할지, 재연결 시 어떻게 동기화할지, 서버가 죽으면 편집 내용이 어디까지 보존되는지.

이런 항목은 **구현 전에 표면화(surface)** 되어야 합니다. 구현 후에 발견하면 아키텍처를 갈아엎어야 하기 때문입니다.

**올바른 기법**: 기능을 간단히 설명한 뒤, Claude에게 `AskUserQuestion`으로 나를 인터뷰하면서 기술적 구현, 엣지 케이스, 트레이드오프를 함께 탐색한 다음 명세서(spec)를 쓰게 합니다. 도메인 패턴을 아는 쪽(Claude)이 질문하고, 결정권과 맥락을 가진 쪽(아키텍트)이 답하는 구조입니다. 지식과 권한이 분리되어 있을 때 가장 효율적인 형태입니다.

**대안들이 부적합한 이유**:

- **오픈소스 프로젝트 아키텍처를 그대로 복제** → 그 프로젝트의 전제 조건이 내 요구사항과 같다는 보장이 없고, 디자인 패턴을 따른다고 해서 내 프로젝트 고유의 숨은 고려사항이 자동으로 드러나지도 않습니다.
- **아키텍트가 혼자 완전한 명세서를 먼저 작성** → 애초에 목표가 "본인이 모르는 것을 발견한다"인데, 혼자 쓰면 아는 것만 쓰게 되므로 목표와 정면으로 모순됩니다. 상호작용의 이점도 사라집니다.
- **일단 최소 구현을 하고 버그로 발견** → 사전 설계 단계에서 리스크를 예방하려는 요구와 정반대 방향입니다. 발견 시점이 가장 비싼 시점으로 미뤄집니다.

## 5. CI 통합: `claude-code-action`

### 5.1 무엇인가

`claude-code-action`은 GitHub Actions 워크플로우에서 Claude Code를 실행하는 액션입니다. PR이 열리거나 이슈에 코멘트가 달렸을 때 Claude가 자동으로 리뷰·수정·응답하도록 만들 수 있습니다.

### 5.2 베타에서 v1.0으로의 인터페이스 변화

베타 시절에는 목적별로 개별 입력 파라미터가 여러 개 있었습니다.

- `direct_prompt` — 직접 전달하는 프롬프트
- `custom_instructions` — 추가 지침
- `mode` — 실행 모드 지정
- `max_turns` — 대화 턴 수 제한

이 방식은 파라미터가 늘어날수록 액션 고유의 이름들을 계속 배워야 하고, CLI에서 쓰던 방식과 표기가 달라 혼란스러웠습니다. 같은 개념이 CLI와 액션에서 다른 이름을 갖는 상황이었습니다.

**v1.0의 설계 방향**은 세 가지로 요약됩니다.

1. **프롬프트 입력의 단일화(unify)**: 여러 프롬프트 관련 입력을 **단일 `prompt` 파라미터**로 통합했습니다.
2. **CLI와의 정렬(align)**: 나머지 세부 설정은 **`claude_args`** 에 담아 전달합니다. 이는 Claude Code CLI에 넘기는 인자와 같은 형태이므로, CLI에서 알던 지식이 그대로 재사용됩니다. 액션 전용 이름을 따로 외울 필요가 줄어듭니다.
3. **실행 모드 자동 감지(auto-detect)**: 이벤트 맥락(이슈 코멘트인지, PR 리뷰인지, 워크플로우 직접 실행인지 등)을 보고 실행 모드를 스스로 판단하므로 `mode`를 명시할 필요가 없어졌습니다.

개념적 형태:

```yaml
- uses: anthropics/claude-code-action@v1
  with:
    prompt: "이 PR을 리뷰하고 보안 문제를 지적해줘"
    claude_args: "--max-turns 10 --allowed-tools Read,Grep"
```

**오해하기 쉬운 지점들**:

- 커스텀 지침이나 턴 제한 기능이 **없어진 것이 아닙니다.** Anthropic API가 자동으로 관리하게 된 것도 아닙니다. 표현 위치가 `claude_args` 쪽으로 옮겨졌을 뿐, 기능 자체는 살아 있습니다.
- 단순한 **이름 변경(rename)이 아닙니다.** `prompt_text`, `instructions`, `execution_mode`, `max_steps` 같은 새 이름으로 1:1 대응된 것이 아니라, 구조 자체가 통합·재편되었습니다.
- 저장소 루트의 **단일 `config.yml`로 모든 설정을 강제하고 환경 변수를 대체하는 방식도 아닙니다.** 설정은 여전히 워크플로우 YAML 안의 액션 입력으로 전달됩니다.

**마이그레이션 시 사고방식**: "이 파라미터의 새 이름은 무엇인가?"가 아니라, **"이 설정은 통합된 `prompt`에 속하는가, 아니면 CLI 인자로서 `claude_args`에 속하는가?"** 를 묻는 것이 맞습니다.

## 6. 관통하는 원칙 정리

지금까지의 내용은 네 가지 원칙으로 압축됩니다.

1. **컨텍스트는 유한한 자원이다.** 항상 로드되는 지침은 최소화하고, 관련 있을 때만 들어오게 만든다(`paths`). 중복 로딩은 준수율을 높이지 않고 비용만 늘린다.
2. **필드 이름을 그 동작이라고 믿지 말라.** `allowed-tools`는 제한이 아니라 사전 승인이다. `context: fork`는 파일 제거가 아니라 컨텍스트 분기다. 이름의 직관과 실제 의미가 어긋나는 지점이 실무 사고의 원인이 된다.
3. **절차의 무게를 작업의 복잡도에 맞춰라.** 명확한 국소 변경은 직접 실행, 큰 재구조화는 계획 모드 후 승인·편집 모드 전환, 넓은 조사는 서브에이전트, 미지의 도메인은 인터뷰.
4. **단일 진실 공급원을 유지하라.** 복사본 대신 심볼릭 링크로 중앙 규칙을 참조하고, 흩어진 파일은 위치가 아니라 패턴으로 겨냥한다.

## 7. 용어 사전 (Glossary)

| 용어 | 설명 |
|---|---|
| **CLAUDE.md** | 프로젝트 규칙을 적어 세션 시작 시 Claude의 컨텍스트에 자동 주입되는 마크다운 파일. 저장소 루트 또는 디렉터리별로 둘 수 있다. |
| **per-directory CLAUDE.md** | 특정 디렉터리 안에 두는 CLAUDE.md. 그 디렉터리 트리, 즉 **위치** 기준으로 지침이 적용된다. |
| **CLAUDE.local.md** | 개인/로컬 전용 지침 파일. 팀 공용 규칙을 여기에 복사하면 중복 로딩으로 컨텍스트만 낭비된다. |
| **.claude/rules/** | 지침을 주제별 파일로 나누어 담는 디렉터리. 각 파일은 frontmatter로 적용 범위를 선언할 수 있다. |
| **frontmatter** | 마크다운 파일 맨 위에 `---`로 감싸 쓰는 YAML 메타데이터 블록. `paths`, `allowed-tools`, `context`, `agent` 등을 선언한다. |
| **paths (frontmatter)** | 규칙이 적용될 파일들을 글로브 패턴 목록으로 지정하는 필드. 지정 시 매칭 파일 작업 때만 규칙이 로드되고, 생략하면 항상 로드된다. |
| **path-scoped rule** | `paths`로 범위를 지정한 규칙. **위치**가 아닌 **패턴** 기준이라 저장소 전역에 흩어진 파일도 겨냥할 수 있다. |
| **glob** | 파일 경로 매칭 패턴 표기법. `*`는 한 디렉터리 단계 내, `**`는 재귀적 하위 전체, `?`는 한 글자. |
| **recursive glob wildcard (`**`)** | 디렉터리 경계를 넘어 임의 깊이를 매칭하는 와일드카드. `src/api/**/*.ts`가 깊은 중첩까지 포함하는 이유. |
| **tree-wide** | 저장소 디렉터리 트리 전역. 한 디렉터리에 국한되지 않음을 뜻한다. |
| **single source of truth** | 단일 진실 공급원. 같은 정보를 여러 곳에 복사하지 않고 한 곳에서만 관리해 불일치(드리프트)를 막는 원칙. |
| **verbatim** | 글자 그대로, 변형 없이. 여러 저장소가 동일 규칙을 그대로 재사용하는 상황을 가리킨다. |
| **symlink (symbolic link)** | 다른 경로를 가리키는 참조 파일. 복사본이 아니므로 원본 변경이 즉시 반영된다. `.claude/rules/`는 이를 정상 해석한다. |
| **resolve (심볼릭 링크 해석)** | 링크를 따라가 실제 대상 파일의 내용을 읽어내는 동작. |
| **circular detection** | 심볼릭 링크가 서로를 가리켜 순환할 때 무한 루프를 막기 위해 방문 경로를 추적해 감지·중단하는 안전장치. |
| **git submodule** | 한 git 저장소 안에 다른 저장소를 포함시키는 기능. 규칙 공유에 심볼릭 링크를 쓰기 위한 전제 조건은 아니다. |
| **Skill / SKILL.md** | 특정 작업 수행 방법을 담은 사전 포장된 지시서와 그 정의 파일. |
| **allowed-tools** | SKILL.md frontmatter 필드. 나열된 도구의 **사용자 승인 프롬프트를 생략(자동 허용)** 한다. 도구 사용을 차단하는 보안 제한이 **아니다**. |
| **permission prompt** | 도구를 실행하기 전 사용자에게 승인을 구하는 확인 절차. |
| **permission mode** | 도구 승인 정책을 결정하는 세션 수준 설정. 실제 도구 제한은 이쪽 영역이며 `allowed-tools`로 대체되지 않는다. |
| **least privilege** | 최소 권한 원칙. 필요한 최소한의 권한만 부여하는 보안 원칙. `allowed-tools`는 이를 구현하는 수단이 아니다. |
| **sandbox** | 실행을 격리해 외부 영향을 제한하는 환경. `allowed-tools` 설정만으로 자동 적용되지 않는다. |
| **context (컨텍스트)** | Claude가 한 번에 참조할 수 있는 정보 전체. 유한하며, 무엇을 넣느냐가 품질과 비용을 좌우한다. |
| **context usage** | 컨텍스트 사용량. 세션 시작 시점의 사용량이 높을수록 실제 작업에 쓸 여유가 줄어든다. |
| **context: fork** | 스킬을 메인 대화와 분리된 별도 컨텍스트의 서브에이전트에서 실행하는 설정. 결과만 메인으로 돌아온다. |
| **subagent (서브에이전트)** | 자체 컨텍스트를 가진 보조 에이전트. 작업을 위임하고 결론만 받아 메인 컨텍스트를 보호한다. |
| **Explore agent** | 내장 읽기 전용 탐색 에이전트. 컨텍스트를 작게 유지하기 위해 **시작 시 CLAUDE.md를 로드하지 않는다**. |
| **system prompt** | 에이전트에게 기본적으로 주어지는 역할·행동 지시문. 포크된 Explore 실행은 이것과 스킬 내용만 보게 된다. |
| **adherence** | 준수율. 지침이 실제로 지켜지는 정도. 지침이 길고 지금 작업과 무관할수록 떨어진다. |
| **Plan Mode (계획 모드)** | 코드를 수정하지 않고 조사 후 구현 계획을 제시하는 읽기 전용 모드. |
| **Editing Mode (편집 모드)** | 실제 파일 수정이 허용되는 모드. 계획 승인 시 이 모드로 전환해 승인된 설계를 곧바로 구현한다. |
| **Direct Execution (직접 실행)** | 계획이나 위임 없이 곧바로 변경을 수행하는 방식. 범위가 좁고 명확하며 코드가 잘 파악된 경우에 적합. |
| **well-scoped requirement** | 범위가 명확히 한정된 요구사항. 직접 실행이 정당화되는 조건. |
| **AskUserQuestion** | Claude가 사용자에게 구조화된 질문을 던져 요구사항·엣지 케이스·트레이드오프를 끌어내는 도구. |
| **surface (표면화)** | 사전에 명확하지 않던 설계 고려사항을 드러내 인지 가능하게 만드는 것. |
| **cache invalidation** | 캐시 무효화. 원본이 바뀌었을 때 낡은 캐시본을 언제 어떻게 폐기할지 결정하는 문제. |
| **conflict resolution** | 충돌 해결. 동시 편집 등으로 상충하는 변경이 발생했을 때 이를 병합·조정하는 전략(OT, CRDT 등). |
| **failure handling** | 실패 처리. 네트워크 단절, 서버 장애 등 비정상 상황에서의 동작과 복구 방식 설계. |
| **tradeoff** | 트레이드오프. 한 가지를 얻기 위해 다른 것을 포기해야 하는 설계 선택의 구조. |
| **claude-code-action** | GitHub Actions에서 Claude Code를 실행하는 액션. |
| **prompt (v1.0 파라미터)** | v1.0에서 여러 프롬프트 관련 입력을 통합한 단일 파라미터. |
| **claude_args** | v1.0에서 프롬프트 외 세부 설정을 담는 인자. Claude Code CLI 인자 형식과 정렬되어 있다. |
| **auto-detecting execution mode** | 이벤트 맥락을 보고 실행 모드를 자동 판별하는 v1.0 동작. 별도 `mode` 지정이 불필요해졌다. |
| **direct_prompt / custom_instructions / mode / max_turns** | 베타 시절의 개별 파라미터들. v1.0에서 기능이 제거된 것이 아니라 `prompt` 및 `claude_args` 구조로 통합·재편되었다. |
