# 시나리오3_리서치시스템

## 질문 1

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : The web search subagent sometimes experiences connection timeouts and sometimes runs queries that legitimately match nothing. Which TWO reporting behaviors let the coordinator respond correctly to each outcome? (Select TWO.)


**A(정답).** Return timeouts as errors carrying structured context (failure type, attempted query) so the coordinator can decide whether to retry.

**설명**

타임아웃은 검색이 완료되지 않았다는 뜻이므로 데이터가 여전히 존재할 수 있다. 구조화된 오류 컨텍스트가 있으면 코디네이터는 재시도, 쿼리 재구성, 커버리지 갭 표시 후 진행 중 어떤 것을 선택할지 판단할 수 있다.

**B(정답).** Return a query that completed with zero matches as a success carrying an empty result set, since no matches is a valid finding.

**설명**

성공적으로 실행되었지만 아무것도 찾지 못한 검색은 실제로 의미 있는 정보를 전달한다. 해당 주제에 대한 자료가 단순히 없을 수 있다는 뜻이다. 결과를 빈 결과 집합을 가진 성공으로 표시하면 코디네이터는 재시도 여부를 고민하는 데 노력을 낭비하지 않고 그 결과를 그대로 받아들일 수 있다.

**C.** Map both timeouts and zero-match queries to one uniform empty-response status so the coordinator's downstream handling stays simple.

**설명**

이는 의미적으로 서로 다른 두 결과를 뒤섞는다. 타임아웃이 정당한 빈 결과와 동일하게 보이면 코디네이터는 소스를 재시도해야 하는지, 데이터가 존재하지 않는다는 것을 받아들여야 하는지 알 수 없고, 실패가 사실처럼 조용히 은폐된다.

**D.** Treat any empty result set as a failure and have the subagent retry with broadened queries until at least one match is returned.

**설명**

이는 반대 방향의 혼동이다. 매칭이 0건인 성공적인 쿼리는 오류가 아니다. 무언가가 매칭될 때까지 재시도를 강제하면 리소스가 낭비되고, 재시도 루프를 충족시키기 위해 관련 없는 결과를 끌어들여 보고서 품질을 떨어뜨릴 수 있다.

### 전반적인 설명

여기서 핵심 구분은 접근 실패(검색이 끝까지 실행되지 않아 답을 알 수 없는 경우)와 유효한 빈 결과(검색이 완료되었고 실제로 "아무것도 매칭되지 않은" 경우) 사이의 차이다. 이 둘은 코디네이터로부터 정반대의 대응을 요구한다. 접근 실패는 백오프를 둔 재시도, 쿼리 수정, 커버리지 갭 표시 등 복구 판단을 필요로 하고, 빈 결과는 그 자체로 있는 그대로 합성 단계로 흘러가야 할 하나의 결과물이다.

Anthropic 자체 도구들도 이 구분을 명시적으로 모델링한다. Web search tool의 경우 실행 문제는 too_many_requests나 unavailable 같은 특정 코드를 가진 오류 객체를 콘텐츠로 담은 web_search_tool_result로 표면화되며, 매칭 없이 성공한 검색은 오류가 아니라 빈 콘텐츠 목록을 반환한다. 클라이언트 실행 도구의 경우도 마찬가지로, 실제로 실행이 실패했을 때만 is_error: true를 설정하고, 모델이나 코디네이터가 추측 없이 복구할 수 있도록 오류 메시지를 실행 가능하게 작성하라고 안내한다(예: "요청 한도를 초과했습니다. 60초 후 재시도하세요"). 두 결과를 하나의 일관된 상태로 뭉뚱그리면 복구 판단에 필요한 바로 그 신호가 사라지고, 모든 빈 결과를 실패로 취급하면 관련 없는 매칭을 끌어들여야만 "성공"할 수 있는 낭비적인 재시도 루프를 유발한다.

서브에이전트 설계를 위한 사고 모델: 실패를 성공으로 표시하지 말 것(조용한 은폐는 망가진 인프라를 숨긴다), 성공을 실패로 표시하지 말 것(실제 발견을 가짜 오류로 만든다). 각 결과를 코디네이터가 조치를 취할 수 있을 만큼 충분한 구조화된 컨텍스트와 함께 정직하게 전달하라. 문서화된 오류 및 빈 결과 형식은 Web search tool 문서와 Handling tool calls를 참고하라.

## 질문 2

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : A synthesis agent in a multi-agent research system frequently flags differing statistics as contradictions, yet reviewers find most flagged pairs are not genuine conflicts. Subagents currently output only each value and a source name. Which structured-output requirement best supports accurate reconciliation?


**A(정답).** Require subagents to include publication or data-collection dates and methodological context alongside each claim.

**설명**

신뢰할 수 있는 소스들 간의 표면적인 모순은 대개 실제 의견 충돌이 아니라 측정 시점이나 방법론이 다른 데서 비롯되는 경우가 많다. 날짜와 방법론적 맥락을 구조화된 메타데이터로 함께 전달하면 합성 에이전트가 시간적/방법론적 차이와 실제 충돌을 구별할 근거를 갖게 되어, 이 오류 유형 전체를 근본 원인에서 해결할 수 있다.

**B.** Instruct the synthesis agent to prefer the figure from whichever source it judges more authoritative and drop the other.

**설명**

이는 한쪽 값을 조용히 선택하고 정보를 버리는 것으로, 서로 다른 소스 데이터를 다루는 안티패턴이다. 또한 수치가 왜 다른지는 전혀 드러내지 않으므로 근본적인 오해석의 가능성이 그대로 남는다.

**C.** Add a synthesis prompt rule to interpret any pair of differing figures as a growth trend rather than a contradiction.

**설명**

이는 하나의 일괄적 가정을 다른 일괄적 가정으로 바꾸는 것일 뿐이다. 일부 수치 차이는 상충되는 방법론이나 오류로 인한 실제 모순일 수 있다. 데이터에 날짜나 방법론적 맥락이 없으면 합성 에이전트는 추세와 실제 충돌을 구별할 근거가 없다.

**D.** Have the coordinator average conflicting numeric values into a single figure before passing them to synthesis.

**설명**

평균을 내는 것은 어떤 소스도 보고한 적 없는 수치를 만들어내는 것으로, 출처가 명시되는 연구 산출물을 훼손한다. 또한 두 수치가 각자의 맥락에서 모두 정확할 수 있음에도, 모든 차이를 나눠서 해결해야 할 의견 불일치로 취급한다.

### 전반적인 설명

멀티 에이전트 연구 시스템은 각 핸드오프마다 정보를 압축하며, 구조화된 메타데이터로 전달되지 않는 것은 하위 에이전트에게 실질적으로 소실된다. 합성 에이전트는 상위 서브에이전트가 출력에 담아 준 것만 볼 수 있다. 주장이 단순한 값과 소스 이름만으로 도착하면, 에이전트는 한 수치가 다른 연도에 측정되었는지, 다른 방법론으로 측정되었는지 알 방법이 없다. 그 결과는 예측 가능한 실패 양상, 즉 시간적/방법론적 차이가 모순으로 위장되는 것이다. 서브에이전트가 각 주장과 함께 발행일 또는 데이터 수집일, 방법론적 맥락을 함께 내보내도록 요구하면 합성 단계가 올바르게 추론할 근거를 갖게 되어, 예를 들어 2023년 수치와 2024년 수치가 의견 불일치가 아니라 성장을 반영한다는 것을 알 수 있게 된다.

더 깊은 설계 원칙은 출처와 시간적 맥락이 나중에 지시나 휴리스틱으로 재구성되는 것이 아니라 데이터로서 함께 이동해야 한다는 것이다. 근거가 명확한 인용 응답에 대한 Anthropic의 가이드도 같은 사고 모델을 반영한다. 콘텐츠와 소스 메타데이터를 함께 묶어 하위의 추론이 정확하게 귀속시키고 조건을 달 수 있도록 하는 것이다(Citations 참고). 더 권위 있는 소스를 선택하거나, 값을 평균 내거나, 모든 차이를 일괄적으로 추세로 재해석하는 접근법은 모두 실제로 모호함을 해결해줄 정보 없이 모호함을 해결하려는 시도다. 조용한 선택과 평균화는 코디네이터가 신중한 조정을 위해 필요할 수도 있는 데이터를 파괴하며, 고정된 재해석 규칙은 방법론 차이나 오류에서 비롯된 실제 충돌을 은폐할 수 있다. 누락된 메타데이터를 추가하는 것만이 시스템이 그 사례들을 실질적으로 구별할 수 있게 해주는 유일한 변경이다.

## 질문 3

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : The web search subagent's queries to one news archive intermittently time out; an immediate retry usually succeeds, but occasionally the archive stays down for an entire task. How should the subagent handle these timeouts?

**A.** Keep retrying the archive inside the subagent until the request eventually succeeds, so the coordinator only ever receives complete result sets.

**설명**

무한 재시도는 문서화된 안티패턴이다. 아카이브가 작업 전체 동안 다운되어 있으면 서브에이전트는 지연 시간과 리소스를 소모하면서 워크플로를 정지시킨다. 소수의 로컬 시도 후에는 해결되지 않는 오류를 컨텍스트와 함께 코디네이터에게 전달해야 한다.

**B.** Forward every timeout to the coordinator as it occurs, keeping all retry and recovery decisions centralized so error handling stays uniform and fully observable.

**설명**

모든 일시적 실패를 에스컬레이션하면 코디네이터가 서브에이전트보다 더 잘 처리할 수도 없는 일상적인 복구 작업으로 넘쳐나게 된다. 시나리오에서는 즉시 재시도가 대개 성공한다고 명시했으므로, 이런 타임아웃은 로컬에서 해결해야 하며 해결되지 않는 실패만 전달해야 한다.

**C.** Return the results gathered from the other sources under a success status, letting synthesis proceed without interrupting the research workflow.

**설명**

실패한 소스를 성공으로 표시하는 것은 조용한 은폐다. 코디네이터와 합성 에이전트는 아카이브가 실제로는 다루어지지 않았음에도 다루어졌다고 믿게 되어, 보고서의 커버리지 갭이 표시되지 않은 채 넘어간다. 실패는 부분 결과와 함께라도 정직하게 보고되어야 한다.

**D(정답).** Retry timed-out queries locally with backoff, and if the archive stays down, escalate the failure to the coordinator with attempted queries and partial results.

**설명**

이것이 올바른 계층화 설계다. 일시적 타임아웃은 대개 로컬 재시도로 해결 가능하므로 서브에이전트가 코디네이터를 개입시키지 않고 직접 처리한다. 해결할 수 없는 실패만 전달되며, 이때 시도한 내용과 부분 결과를 함께 실어 코디네이터가 정보에 기반한 복구 판단을 내릴 수 있게 한다.

### 전반적인 설명

멀티 에이전트 시스템에서 오류 처리의 지도 원칙은 오류를 해결할 수 있는 가장 낮은 수준에서 처리하는 것이다. 타임아웃과 같은 일시적 실패는 정의상 재시도 시 성공할 가능성이 높으므로, 서브에이전트는 다른 누군가를 개입시키기 전에 로컬 복구(백오프를 둔 한두 번의 재시도)를 시도해야 한다. 이는 코디네이터가 일상적인 재시도의 디스패처 역할을 하지 않고, 자신만이 내릴 수 있는 판단에 집중하도록 해준다.

로컬 복구가 실패하면 전달되는 오류는 구조화되고 유용한 정보를 담아야 한다. 실패 유형, 시도된 쿼리, 실패 전 수집된 부분 결과, 그리고 가능하다면 대안적 접근법까지 포함해야 한다. 이런 컨텍스트가 있으면 코디네이터는 나중에 재시도할지, 다른 소스에 위임할지, 부분 결과로 진행하면서 최종 보고서에 커버리지 갭을 표시할지 선택할 수 있다. Claude Agent SDK에서는 이런 동작을 서브에이전트의 프롬프트와 도구 핸들러에 설계해 넣는다. 커스텀 도구의 경우 실패를 그대로 예외로 노출시키는 대신 포착하여 구성된 오류 결과를 반환하면, 에이전트 루프가 계속되는 동안 정확히 이런 실행 가능한 컨텍스트를 포함시킬 수 있다.

오답들은 잘 알려진 안티패턴에 대응한다. 모든 타임아웃을 에스컬레이션하는 것은 서브에이전트가 스스로 해결할 수 있는 작업을 중앙화하는 것이고, 무한 내부 재시도는 장애가 일시적이지 않을 때 워크플로를 정지시키며, 실패한 소스에 성공 상태를 반환하는 것은 조용한 은폐로서 코디네이터로부터 실패를 숨기고 아무도 볼 수 없는 커버리지 갭을 가진 보고서를 만들어낸다. 문서화된 오류 결과 및 서브에이전트 설계 패턴은 Agent SDK의 Custom Tools와 Subagents를 참고하라.

## 질문 4

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : The document analysis subagent attaches calibrated confidence scores to extracted claims, and high-confidence claims now bypass human fact-checking. How should the team continue detecting novel error patterns among the claims that skip review?

**A(정답).** Apply stratified random sampling to high-confidence claims and measure error rates in the sample on an ongoing basis.

**설명**

계층화 무작위 샘플링은 더 이상 검토를 받지 않는 정확히 그 모집단에 대해 측정을 계속 수행하기 때문에 정답이다. 이는 과거 데이터로 보정된 신뢰도 점수가 예측할 수 없는, 소스 형식 변경 등으로 도입되는 새로운 오류 패턴을 드러낸다.

**B.** Raise the confidence threshold for bypassing review so a smaller share of claims skips the fact-checking step.

**설명**

임계값을 높이면 자동 처리되는 모집단은 줄어들지만 여전히 검토를 우회하는 주장들에 대한 측정은 제공하지 못한다. 남아 있는 고신뢰도 집합의 새로운 오류 패턴은 여전히 보이지 않으며, 임계값 변경은 탐지력을 더하지 못하면서 효율성만 희생시킨다.

**C.** Track the aggregate accuracy metric across all claims and investigate only when it drops below the validated baseline.

**설명**

집계된 정확도는 특정 소스 유형이나 필드에 집중된 실패를 가려버릴 수 있어, 한 세그먼트의 새로운 오류 패턴이 전체 수치를 전혀 움직이지 않을 수 있다. 또한 문제가 평균을 흔들 만큼 커진 이후에야 문제를 감지한다.

**D.** Route only the claims the model itself flags as uncertain to human reviewers, since errors concentrate in those cases.

**설명**

모델이 스스로 표시하는 불확실성은 문제가 되는 바로 그 실패 양상, 즉 모델이 확신을 갖고 틀리는 주장을 놓친다. 새로운 오류 패턴은 대개 모델이 자신이 실패하고 있음을 모르는 고신뢰도 출력에서 나타나므로, 이런 라우팅은 그것들을 측정되지 않은 채로 남긴다.

### 전반적인 설명

신뢰도 보정은 "이전에 관찰한 오류들을 바탕으로, 이 추출이 맞을 가능성은 얼마인가?"라는 질문에 답한다. 검증 세트에 포함되지 않았던 오류에 대해서는 아무것도 말해주지 않는다. 고신뢰도 주장이 더 이상 인간 검토를 받지 않게 되면, 시스템은 새로운 소스 형식, 변화하는 문서 구조, 보정 데이터가 다루지 않은 엣지 케이스로 인한 새로운 오류 패턴을 발견할 유일한 채널을 잃는다. 사고 모델은, 자동화가 하나의 센서를 제거하는 것이므로 그것을 대체할 무언가가 있어야 한다는 것이다.

계층화 무작위 샘플링이 바로 그 대체물이다. 고신뢰도 모집단에서 무작위 샘플을 추출하고(가장 흔한 것만이 아니라 모든 소스 유형과 필드 세그먼트가 대표되도록 계층화하여) 이를 검토함으로써, 팀은 검토를 우회하는 바로 그 주장들에 대한 실제 오류율을 연속적이고 편향되지 않은 방식으로 추정할 수 있다. 샘플이 어떤 모델 신호에 의해 걸러지는 것이 아니라 무작위이기 때문에, 모델이 확신을 갖고 틀리는 오류를 잡아낼 수 있으며, 그곳이 바로 새로운 패턴이 숨는 곳이다. 계층화가 중요한 이유는 드문 소스 유형이 크게 실패하더라도 계층화되지 않은 샘플에서는 그 기여도가 너무 작아 결과를 움직이지 못할 수 있기 때문이다.

대안들은 각각 이 지점에서 무너진다. 집계된 정확도는 지연되고 희석된 신호다. 97%라는 전체 수치가 심하게 실패하는 세그먼트를 가릴 수 있고, 평균이 움직일 즈음에는 이미 피해가 발생한 뒤다. 자체 표시된 불확실한 주장만 라우팅하는 것은 모델이 자신이 틀렸다는 것을 안다고 신뢰하는 것인데, 이는 새로운 오류 패턴이 발생하는 동안 정확히 무너지는 가정이다. 우회 임계값을 높이는 것은 모니터링되지 않는 모집단을 측정 없이 줄이는 것일 뿐이며, 여전히 통과하는 것들은 사각지대로 남는다.

평가에 대한 Anthropic의 가이드는 모델의 자체 평가를 신뢰하기보다 대표성 있는 사례에 대한 지속적이고 경험적인 측정을 강조한다. Create strong empirical evaluations를 참고하라.

도구의 계약을 고치는 것이 다운스트림 완화책보다 나은 이유는 결정적이고 모든 호출에 적용되기 때문이다. 메타데이터를 무시하라는 프롬프트 지시는 토큰 소비에 아무 변화를 주지 못한다. 필드들은 여전히 윈도우를 차지하고 주의를 희석시킨다. 더 큰 컨텍스트 윈도우로 바꾸는 것은 실패를 제거하는 대신 미루는 것이며, 긴 노이즈 컨텍스트는 여전히 윈도우 중간 콘텐츠에 대한 회상 저하를 겪는다. 코디네이터 측 요약은 서브에이전트 자체의 윈도우가 이미 채워진 후에 작동하므로 한 계층 늦으며, 정확한 날짜와 수치, 귀속 정보를 보존하는 데 가치가 달려 있는 연구 시스템에서 손실 압축은 나쁜 거래다.

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : The coordinator currently retries every subagent report that contains no results, so queries that succeeded but matched nothing are re-run repeatedly alongside genuine timeouts. Which change stops the wasted retries without losing information?

**A.** Cap the coordinator at two retries per query for any no-result report, bounding the wasted cycles regardless of outcome type.

**설명**

재시도 상한은 버그의 비용을 제한할 뿐 고치지는 못한다. 유효한 빈 결과도 여전히 재시도를 유발하며, 접근 실패와 성공적인 매칭 0건 쿼리를 혼동하는 근본 문제는 그대로 남는다. 코디네이터는 여전히 쿼리가 아무것도 찾지 못한 것인지 검색 인프라가 실패한 것인지 구별할 수 없다.

**B.** Filter zero-result reports out before they reach the coordinator so they can never trigger the retry logic.

**설명**

이런 보고를 억제하는 것은 안티패턴이다. 코디네이터는 쿼리가 실행되어 정당하게 아무것도 찾지 못했다는 정보를 잃게 되어, 다루어지지 않은 하위 주제와 조사된 적이 없는 하위 주제를 구별할 수 없게 된다. 재시도 낭비는 멈추지만 정확한 커버리지 추적을 희생하는 대가를 치른다.

**C.** Have the subagent automatically broaden any query that returns zero matches until at least one result comes back.

**설명**

무언가가 매칭될 때까지 더 넓은 쿼리를 강제하는 것은 현실을 보고하기보다 관련성을 조작해내는 것이다. 매칭 0건 결과는 그 하위 주제에 대한 소스가 실제로 존재하지 않는다는 것을 정확하게 의미할 수 있다. 이런 동작은 부수적인 자료로 연구를 오염시키고 코디네이터로부터 진짜 커버리지 갭을 숨긴다.

**D(정답).** Retry only reports flagged as access failures, and record successful zero-match queries as findings that feed coverage annotations.

**설명**

타임아웃과 매칭 0건 결과는 의미적으로 다른 결과이기 때문에 이것이 정답이다. 접근 실패만이 재시도 판단을 요구하며, 매칭 없이 성공한 쿼리는 그 자체로 정보를 담은 결과물이다. 매칭 0건 결과를 기록해 두면, 시스템이 이미 답을 낸 쿼리를 끝없이 재실행하는 대신 합성 단계가 진짜 커버리지 갭을 표시할 수 있다.

### 전반적인 설명

여기서 시험하는 핵심 구분은 접근 실패(타임아웃이나 서비스 오류로 쿼리가 완료되지 않은 경우)와 유효한 빈 결과(쿼리가 성공적으로 완료되었지만 아무것도 매칭되지 않은 경우) 사이의 차이다. 이들은 서로 다른 대응을 요구하는 다른 결과다. 접근 실패는 데이터가 존재할 수도 있는데 시스템이 단순히 도달하지 못했을 뿐이므로 재시도 판단을 요구하지만, 매칭 0건 결과는 완료된 측정치다. 이를 재시도하는 것은 이미 답이 나온 질문을 다시 묻는 것이며, 이를 실패로 취급하는 것은 하위 단계로부터 유용한 정보를 숨기는 것이다.

Anthropic 자체 도구 인터페이스도 이 구분을 인코딩한다. Web search tool은 실행 오류를 도구 결과 안의 별도 오류 객체로 표현하는 반면, 매칭 없이 성공한 검색은 빈 콘텐츠 목록을 반환한다. 이 두 형태는 의도적으로 서로 바꿔 쓸 수 없게 되어 있다. 마찬가지로 클라이언트 도구의 경우 handling tool calls는 실제 실행 실패에 한해서만 is_error: true를 예약해 두어 빈 결과 형태와 분리해 둔다. 잘 설계된 코디네이터는 이 계약을 그대로 반영해야 한다. 오류로 표시된 보고는 재시도 또는 대안 접근 로직으로 라우팅하고, 성공적인 매칭 0건 보고는 연구 기록으로 라우팅하여 합성 단계가 어떤 하위 주제에 실제로 이용 가능한 소스가 없는지 표시할 수 있게 한다.

오답들은 각각 이 기준에서 실패한다. 재시도 상한을 두는 것은 잘못된 분류를 고치지 않고 낭비만 제한한다. 무언가가 매칭될 때까지 쿼리를 자동으로 넓히는 것은 관련성을 조작해내고 아무것도 존재하지 않는다는 발견을 지워버린다. 보고를 걸러내는 것은 조용한 은폐다. 낭비되는 재시도는 멈추지만, 코디네이터는 조사되었지만 비어 있는 하위 주제와 전혀 검색되지 않은 하위 주제를 더 이상 구별할 수 없게 되어 최종 인용 보고서의 정직성이 떨어진다.

**설명**

더 큰 윈도우는 토큰 수가 늘어남에 따라 정확도와 회상력이 여전히 떨어지므로, 같은 저하를 더 높은 비용으로 지연시킬 뿐이다. 걸러지지 않은 원본 출력이 코디네이터의 컨텍스트를 채우는 근본 문제는 고쳐지지 않는다.

### 전반적인 설명

여기서 설명하는 실패는 컨텍스트 부패다. 세션의 토큰 수가 늘어남에 따라 모델의 그 컨텍스트에 대한 정확도와 회상력이 저하되고, 실제로 주어진 구체적인 사실이 아니라 일반적인 사전 지식("일반적인 업계 수치")으로부터 답하기 시작한다. 핵심 설계 인사이트는 컨텍스트가 많다고 자동으로 더 좋아지는 것이 아니며, 중요한 것은 윈도우를 차지하는 내용을 정제하는 것이라는 점이다.

코디네이터-서브에이전트 아키텍처에서 코디네이터의 컨텍스트는 조율 수준의 상태, 즉 어떤 작업이 위임되었는지, 각 서브에이전트가 무엇을 결론지었는지, 무엇이 남아 있는지를 담아야 한다. 서브에이전트가 원본 출력 전체(페이지 콘텐츠, 추론 트레이스, 관련성 낮은 수십 개의 필드)를 코디네이터에 쏟아부으면, 그 윈도우는 관련성에 비례하지 않는 자료로 채워지고, 코디네이터가 나중에 필요로 하는 정밀한 통계는 잡음이 많은 입력 속의 약한 신호가 되어 버린다. 서브에이전트가 정제된 구조화 요약을 반환하도록 요구하면 이를 소스에서 고칠 수 있다. 장황한 탐색은 각 서브에이전트 자체의 컨텍스트에 고립되어 남고, 핵심 발견만 경계를 넘어간다.

대안들은 각기 특징적인 이유로 실패한다. 더 큰 컨텍스트 윈도우는 저하가 누적된 토큰의 함수이지 고정된 컷오프가 아니기 때문에 같은 부패를 더 높은 비용으로 미룰 뿐이다. 구체적인 수치를 인용하라는 프롬프트 지시는 이미 저하된 컨텍스트가 더 이상 지원할 수 없는 행동을 요구하는 것이다. 모델은 묻혀버린 세부사항에 신뢰성 있게 주의를 기울일 수 없다. 그리고 max_tokens는 응답 길이만 제어할 뿐 입력으로부터의 회상에는 영향이 없으며, 더 긴 응답은 늘어나는 히스토리에 부피만 더할 뿐이다.

에이전트 시스템에서 컨텍스트를 정제하는 근본 가이드는 Context windows와 AI 에이전트를 위한 효과적인 컨텍스트 엔지니어링을 참고하라.

## 질문 8

**SCENARIO** : You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

**QUESTION** : A multi-hour research run crashes after the web search and document analysis subagents complete but before synthesis starts. You want to resume without redoing finished work. Which recovery design should you implement?

**A.** Resume the coordinator under a named session with the resume flag, relying on the restored session context to make the completed subagents' outputs available to the synthesis agent.

**설명**

세션 재개는 단일 세션의 대화형 컨텍스트를 복원하지만, 코디네이터에게 어떤 단계가 완료되었는지에 대한 신뢰할 수 있는 기록이나 서브에이전트 발견 사항의 구조화된 저장소를 제공하지 않는다. 크래시 시점에 세션에 마침 있었던 내용에 의존하는 복구는 명시적 상태 내보내기와 매니페스트에 비해 취약하다.

**B.** Persist the coordinator's full conversation transcript to disk after every turn, then replay the entire message history on resume so all agents regain their prior working context.

**설명**

서브에이전트는 고립된 컨텍스트로 실행되며 코디네이터의 히스토리를 읽지 않으므로, 코디네이터의 대화 기록을 재생해도 그들의 상태는 복원되지 않는다. 또한 남은 에이전트들이 실제로 필요로 하는 정제된 발견 사항이 아니라 장황한 중간 출력을 통째로 다시 로드한다.

**C.** Configure each subagent to write its raw tool outputs in full to shared files, so on resume the synthesis agent can reconstruct all prior work by reading everything back into context.

**설명**

원본 도구 출력을 통째로 저장하면 데이터는 보존되지만 사용 가능한 상태는 보존되지 않는다. 합성 에이전트는 부피가 큰 검색 페이지와 분석 트레이스를 흡수하게 되어 관련성에 비례하지 않는 콘텐츠로 컨텍스트가 팽창된다. 또한 코디네이터에게 완료 기록을 제공하지 않으므로 무엇을 건너뛰고 무엇을 재실행할지 판단할 수 없다.

**D(정답).** Have each subagent export structured state to a known location; on resume, the coordinator loads a manifest to identify completed phases and injects those findings into remaining agents' prompts.

**설명**

이것이 크래시 복구를 위한 구조화된 상태 지속화 패턴이다. 각 에이전트는 자신의 상태와 핵심 발견을 알려진 위치에 기록하고, 매니페스트는 코디네이터에게 정확히 어떤 단계가 끝났는지 알려주어 완료된 작업을 건너뛰고 아직 실행해야 하는 에이전트들의 프롬프트에 이전 발견 사항을 명시적으로 전달할 수 있게 한다.

### 전반적인 설명

코디네이터-서브에이전트 시스템에서 크래시 복구가 작동하는 이유는 상태가 대화 히스토리에 암묵적으로 남겨지는 것이 아니라 명시적이고 구조화된 형태로 만들어지기 때문이다. 각 에이전트는 상태, 핵심 발견, 커버리지, 갭을 담은 상태 파일을 알려진 위치에 내보내고, 작은 매니페스트가 각 단계가 completed, in_progress, not_started 중 무엇인지 기록한다. 재개 시 코디네이터는 매니페스트를 읽고 완료된 단계를 건너뛰며, 내보내진 발견 사항을 아직 실행해야 하는 에이전트들의 프롬프트에 직접 주입한다. 이 마지막 단계가 중요한 이유는 서브에이전트가 고립된 컨텍스트를 갖기 때문이다. 프롬프트에 담기지 않으면 서브에이전트에게는 아무것도 존재하지 않으므로, 복구는 이전 발견 사항을 명시적으로 전달해야 한다.

대안들은 같은 사고 모델을 드러내는 이유로 실패한다. 코디네이터의 대화 기록을 재생하는 것은 대화를 복원할 뿐 에이전트 상태를 복원하지 못하며, 서브에이전트는 어차피 그 히스토리를 보지 않는다. 세션 재개는 다중 단계 파이프라인을 재구성하기 위한 것이 아니라 대화형 작업을 계속하기 위해 설계된 것이며, 완료 기록을 전혀 담지 않고 오래된 컨텍스트에 기반해 행동할 위험이 있다. 원본 도구 출력을 통째로 기록하는 것은 하나의 실패를 다른 실패로 바꿀 뿐이다. 데이터는 남지만 합성 에이전트는 수만 개의 걸러지지 않은 토큰을 삼켜야 하며, 구조화된 요약이 막으려는 컨텍스트 팽창을 그대로 재현한다.

여기서의 설계 트레이드오프는 각 단계 경계에서 약간의 노력(간결하고 구조화된 요약을 내보내는 것)을 들이는 대신, 크래시가 없을 때도 저비용의 결정적인 복구와 더 깔끔한 핸드오프를 얻는 것이다. Claude Agent SDK의 Subagents와, 장기 실행 에이전트 워크플로에서의 지속적 상태와 재개를 다루는 Anthropic의 멀티 에이전트 연구 시스템 구축 엔지니어링 글을 참고하라.

**QUESTION** : You are defining the conditions under which the coordinator should stop autonomous work and hand a research request to a human operator. Which TWO escalation rules are appropriate? (Select TWO.)

**A(정답).** Escalate when the request concerns a topic category the system's operating guidelines do not address or permit.

**설명**

정책 또는 가이드라인의 공백은 올바른 에스컬레이션 트리거다. 시스템을 규율하는 규칙이 특정 요청에 대해 침묵할 때 에이전트는 즉흥적으로 판단을 내려서는 안 되며, 진행 방향은 인간이 결정해야 한다.

**B(정답).** Escalate when retries, reformulated queries, and alternative sources have all failed to produce meaningful progress.

**설명**

합리적인 복구 시도 후에도 의미 있는 진전을 만들지 못하는 것은 최우선급 에스컬레이션 트리거다. 로컬 복구 옵션이 소진되면, 계속된 자율적 반복은 토큰을 낭비하고 인간만이 제공할 수 있는 해결을 지연시킨다.

**C.** Escalate when the synthesis agent's self-rated confidence in its draft findings falls below a preset numeric threshold.

**설명**

모델은 종종 어려운 사례에서 정확히 확신을 갖고 틀리기 때문에, 자체 보고된 신뢰도는 실제 사례 난이도에 대한 신뢰할 수 없는 대체 지표다. 이 신호에 임계값을 두면 누락된 에스컬레이션과 불필요한 에스컬레이션이 모두 발생한다.

**D.** Escalate when the research task requires coordinating all four specialized subagents at once, indicating unusual complexity.

**설명**

작업에 필요한 서브에이전트 수와 같은 구조적 복잡성은 이 시스템이 처리하도록 설계된 대상이며, 그 자체로 인간을 개입시킬 이유가 되지 않는다. 에스컬레이션은 진전 여부와 정책 커버리지에 따라 결정되어야 하며, 작업이 얼마나 많은 오케스트레이션을 요구하는지에 따라 결정되어서는 안 된다.

### 전반적인 설명

건전한 에스컬레이션 설계는 대체 지표가 아니라 관찰 가능한 규칙 기반 트리거에 의존한다. 신뢰할 수 있는 세 가지 트리거는 명시적인 인간의 요청, 정책 공백(해당 특정 요청에 대해 규율 규칙이 침묵하거나 모호한 경우), 그리고 합리적인 복구 시도 후에도 의미 있는 진전을 만들지 못하는 경우다. 뒤의 두 가지가 여기에 직접 적용된다. 코디네이터가 재시도, 쿼리 재구성, 대체 소스를 모두 소진하고도 연구를 진전시키지 못했다면 더 이상의 자율성은 토큰만 낭비할 뿐이며, 요청이 시스템 가이드라인이 전혀 다루지 않는 영역에 속한다면 자율 에이전트가 즉흥적으로 결정을 내리는 것은 인간에게 속하는 거버넌스 결정을 모델의 판단으로 대체하는 것이다.

여기서의 사고 모델은 에스컬레이션 트리거가 모델이 추정해야 하는 것이 아니라 하니스나 에이전트가 검증할 수 있는 것이어야 한다는 것이다. 자체 평가된 신뢰도는 이 기준을 통과하지 못한다. 모델의 신뢰도는 에스컬레이션이 가장 중요한 바로 그 사례들에서 잘못 보정되어 있어, 어려운 문제에서 확신을 갖고 틀리며, 그 신호에 대한 수치 임계값은 사실상 무작위로 사례를 라우팅한다. 마찬가지로 원시적인 구조적 복잡성(모든 서브에이전트가 필요하다거나, 도구 호출이 많다거나, 계획이 길다는 것)은 이 시스템이 수행하도록 설계된 작업 그 자체를 나타낸다. 이를 에스컬레이션 신호로 취급하면 일상적이고 범위 내에 있는 연구를 인간에게 밀어내어, 애초에 멀티 에이전트 시스템을 구축한 목적을 무너뜨리게 된다.

실무에서는 이런 트리거가 코디네이터의 시스템 프롬프트에 명시적인 기준으로 인코딩되며, 언제 에스컬레이션하고 언제 계속할지 보여주는 퓨샷 예시가 함께 제공되는 경우가 많다. 핸드오프 자체는 시도한 내용과 부분 결과에 대한 구조화된 요약을 담아, 인간이 처음부터 다시 시작하지 않도록 한다. Anthropic의 Building Effective Agents 가이드와 Claude Agent SDK 개요를 참고하라.

The system researches topics and produces comprehensive, cited reports.

**QUESTION** : Partway through a long research run, the coordinator starts investigating follow-up questions itself, loading full source documents into its own context; its later delegation and aggregation decisions become noticeably inconsistent. What should change?

**A.** Route follow-up questions to the synthesis agent directly, since it already processed the relevant documents during its analysis pass.

**설명**

**설명**

반복적인 즉석 압축은 점진적 요약의 함정이다. 매 단계마다 정밀한 발견 사항이 희석되며, 오케스트레이션 상태가 문서 콘텐츠와 함께 압축되어 버린다. 이는 팽창을 처음부터 막는 것이 아니라 이미 코디네이터의 컨텍스트에 들어온 이후에 관리하는 것이다.

**D.** Instruct the coordinator to trim each source document to relevant excerpts before loading it into its own context for investigation.

**설명**

다듬기는 문서당 부피를 줄이지만 코디네이터가 여전히 세부 수준의 조사를 직접 수행하게 두므로, 발췌문이 여러 후속 질문에 걸쳐 계속 누적된다. 근본 문제는 조사 콘텐츠와 오케스트레이션 상태가 하나의 컨텍스트를 공유한다는 것이며, 다듬기는 두 역할을 분리하기보다 저하 속도를 늦출 뿐이다.

### 전반적인 설명

코디네이터와 서브에이전트 아키텍처에서 코디네이터의 컨텍스트 윈도우는 오케스트레이션 상태, 즉 연구 계획, 무엇이 위임되었는지, 무엇이 돌아왔는지, 무엇이 남아 있는지를 담아야 하는 희소한 자원이다. 코디네이터가 스스로 조사를 수행하기 시작하면 장황한 소스 자료가 그 상태를 밀어내고, 모델은 일관되지 않은 위임 및 집계 판단을 내리기 시작하는데, 이는 컨텍스트 저하의 전형적인 증상이다.

구조적인 해결책은 위임이다. 좁고 구체적인 질문을 가진 서브에이전트를 생성하고 간결하고 구조화된 요약을 반환하도록 요구하는 것이다. 각 서브에이전트가 자체 고립된 컨텍스트에서 실행되므로, 그것이 읽는 전체 문서는 코디네이터의 윈도우에 전혀 들어오지 않으며 정제된 답변만 들어온다. 이것이 이 패턴이 확장 가능한 이유다. 코디네이터는 결과당 대략 한 줄의 컨텍스트만 유지하면서 많은 심층 조사를 위임할 수 있다. 트레이드오프는 서브에이전트가 아무것도 자동으로 물려받지 않으므로 코디네이터가 각 위임 프롬프트에 필요한 배경을 명시적으로 포함해야 한다는 것이다.

대안들은 모두 조사를 코디네이터 내부에 그대로 둔다. 문서를 발췌문으로 다듬는 것은 질문당 부피를 줄이지만 여전히 세부 작업과 오케스트레이션을 섞어 두며, 발췌문은 긴 실행에 걸쳐 누적된다. 코디네이터 자체의 히스토리를 반복적으로 압축하는 것은 점진적 요약이며, 매 단계마다 정밀한 발견과 오케스트레이션 상태를 갉아먹는다. 후속 질문을 합성 에이전트로 직접 보내는 것은 고립된 서브에이전트 컨텍스트 사이에 존재하지 않는 공유 메모리를 가정하는 것이고, 코디네이터를 우회하는 것은 허브-스포크 설계가 제공하는 중앙화된 관찰 가능성과 오류 처리를 희생시킨다.
