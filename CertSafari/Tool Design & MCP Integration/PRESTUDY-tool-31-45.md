# 사전학습 노트 — Tool Design & MCP Integration (31~45 범위)

이 문서는 이 주제를 처음 접하는 사람을 위한 **개념 선행 학습 자료**입니다.
"도구(Tool)를 어떻게 설계하고, 에러를 어떻게 표현하고, MCP 서버를 어떻게 붙이고,
모델이 도구를 언제 어떻게 고르게 만들 것인가"에 관한 모든 기초 개념을 0에서부터 설명합니다.

---

## 0. 큰 그림: LLM이 "도구"를 쓴다는 것

### 0.1 왜 도구가 필요한가
LLM(대형 언어 모델)은 본질적으로 **텍스트를 생성하는 함수**입니다. 스스로는
- 데이터베이스를 조회할 수 없고
- 파일을 읽거나 쓸 수 없고
- 외부 API를 호출할 수 없고
- 명령어를 실행할 수 없습니다.

그래서 "이런 일을 대신 해줄 수 있는 함수가 여기 있다"고 모델에게 **목록으로 알려주는** 방식이 도입되었습니다.
이것이 **Tool Use**(도구 사용), 다른 이름으로 **Function Calling**(함수 호출)입니다.

### 0.2 동작 흐름 (Tool Use Loop)
1. 애플리케이션이 모델에게 **도구 목록(tools)**을 함께 보냅니다. 각 도구는 이름, 설명, 입력 스키마를 가집니다.
2. 모델이 사용자의 요청을 읽고, "이건 `get_weather` 도구를 써야겠다"라고 판단하면
   일반 텍스트 대신 **tool_use 블록**(도구 이름 + 인자 JSON)을 출력합니다.
3. **모델은 도구를 직접 실행하지 않습니다.** 실행은 애플리케이션(클라이언트) 쪽 코드가 합니다.
4. 애플리케이션이 실행 결과를 **tool_result 블록**으로 다시 모델에게 돌려줍니다.
5. 모델이 그 결과를 읽고 최종 답변을 만들거나, 또 다른 도구를 호출합니다.

이 1~5의 반복을 **에이전트 루프(agent loop)**라고 부릅니다.

### 0.3 핵심 통찰: 모델은 "글"만 보고 도구를 고른다
모델이 어떤 도구를 고를지 결정할 때 참고하는 정보는 사실상 세 가지뿐입니다.

| 참고 정보 | 설명 |
| --- | --- |
| 도구 **이름**(name) | `get_user_profile`처럼 스네이크 케이스 식별자 |
| 도구 **설명**(description) | 자연어로 쓴 "이 도구는 무엇을 하는가" |
| 입력 **스키마**(input schema) | JSON Schema로 쓴 파라미터 정의 |

여기에 **시스템 프롬프트**가 얹혀서 전체 판단이 이뤄집니다.
그래서 도구 설계에서 가장 큰 영향력을 가진 것은 **코드가 아니라 텍스트**입니다.
이 사실이 이후 여러 절의 근본 원리가 됩니다.

## 1. 도구 이름과 설명 설계 (Tool Description Design)

### 1.1 설명은 모델을 향한 API 문서다
사람이 읽는 주석이 아니라, **모델이 라우팅 결정을 내리는 근거**입니다.
설명이 부실하면 모델은 잘못된 도구를 부릅니다. 이 현상을 **Misrouting**(오라우팅, 오호출)이라 부릅니다.

### 1.2 실패 사례 A — 설명이 서로 똑같을 때
같은 서버가 두 도구를 제공하는데 설명이 동일한 경우:

```json
{ "name": "get_user_profile",     "description": "Returns user account information." }
{ "name": "get_user_permissions", "description": "Returns user account information." }
```

사용자가 "이 사람 표시 이름 뭐야?"라고 묻든 "이 사람 권한 레벨 뭐야?"라고 묻든,
모델 입장에서 두 도구는 **문자 그대로 구별 불가능**합니다. 그래서 절반 확률로 틀립니다.

**해결 원리: 설명에 "무엇을 반환하는지 구체적 필드명"을 적는다.**

```json
{
  "name": "get_user_profile",
  "description": "Returns the user's profile fields: display name, email, avatar URL, timezone, and locale. Does NOT return roles or permissions."
},
{
  "name": "get_user_permissions",
  "description": "Returns the user's authorization data: assigned roles, access scopes, and permission flags. Does NOT return display name or contact details."
}
```

포인트 두 가지:
- **긍정 명세**: 반환하는 실제 필드를 나열한다.
- **부정 명세**: "이건 안 한다"를 명시하면 경계가 훨씬 선명해진다.

### 1.3 실패 사례 B — 설명이 낡았을 때 (Description Drift)
처음에 `analyze_content`라는 범용 도구가 있었고, 이메일·내부 메모·웹페이지 등
붙여넣은 모든 콘텐츠를 요약했습니다. 나중에 웹 전용 후속 도구(`analyze_web_page` 같은)가 추가됐지만
**기존 도구의 설명은 그대로 두었습니다.**

결과: 웹 전용 작업인데도 모델이 옛 범용 도구를 부릅니다.
이유는 단순합니다 — 옛 도구의 설명이 여전히 "웹 콘텐츠도 처리한다"고 광고하고 있기 때문입니다.

이 현상을 **설명 표류(description drift)** 또는 **도구 범위 중복(overlapping scope)**이라 부릅니다.

**해결 원리: 도구 카탈로그를 리팩터링한다.**
1. 남은 실제 역할을 반영하도록 **이름 변경** (예: `analyze_content` → `analyze_pasted_text`)
2. **설명 갱신**해서 새 도구가 담당하게 된 케이스를 명시적으로 **제외**
   (예: "For web pages and URLs, use `analyze_web_page` instead.")

### 1.4 하면 안 되는 대응들과 그 이유
| 잘못된 대응 | 왜 안 되는가 |
| --- | --- |
| 설명을 아예 지우기 | 모델이 도구의 역할·입력 규칙을 알 수 없게 되어 선택 정확도가 더 떨어짐 |
| 사용자에게 매번 도구 ID를 지정하게 하기 | 에이전트의 자율 도구 선택이라는 존재 이유 자체가 사라지고 UX가 붕괴 |
| 백엔드 라우팅 가중치만 조정 | 모호성은 **프롬프트 계층**에 있음. 백엔드 숫자는 모델의 판단 근거를 바꾸지 못함 |
| 클라이언트마다 어떤 도구를 부를지 하드코딩 | 서버 결함을 모든 소비자에게 떠넘기는 것. 서버 작성자가 설명을 고치는 게 근본 해결 |
| 도구 대신 리소스로 바꾸기 | 모호한 설명 문제는 리소스로 바꿔도 그대로 남음 |

**원칙: 도구 선택 문제의 근본 해결은 거의 항상 "이름과 설명을 명확히 하는 것"이다.**

## 2. 시스템 프롬프트가 도구 선택에 미치는 영향

### 2.1 시스템 프롬프트란
대화 전체에 걸쳐 모델의 역할·규칙·정책을 규정하는 최상위 지시문입니다.
사용자 메시지보다 강한 권위를 갖도록 학습되어 있습니다.

### 2.2 프롬프트 한 줄이 도구 선택을 뒤집는다
예를 들어 시스템 프롬프트에 이런 문장을 넣었다고 합시다.

> "If in doubt, use the search tool."  (확신이 없으면 검색 도구를 써라)

그러면 실제로는 사내 문서 검색(`lookup_internal_docs`)이 훨씬 적절한 질문에도
모델이 웹 검색(`search_web`)을 호출하기 시작합니다.

이것은 **모델의 결함이 아닙니다.** 모델은 지시를 충실히 따른 것입니다.
얻는 교훈은:

- 시스템 프롬프트의 명시적 지시는 **모델 자체의 적합성 판단을 덮어쓸(override) 수 있다.**
- 광범위한 기본 규칙("애매하면 X를 써라")은 강력하지만 **부작용이 크다.**
- 규칙을 쓸 거라면 조건을 좁혀야 한다.
  예: "For questions about internal policies, products, or runbooks, use `lookup_internal_docs` first. Use `search_web` only for public, external information."

### 2.3 함께 기억할 반례
- "도구 이름에 'search'가 들어가면 무조건 우선"이라는 규칙 같은 건 존재하지 않습니다.
  선택은 이름·설명·프롬프트 맥락의 종합 결과입니다.
- 도구가 선택되지 않는 이유가 항상 JSON 스키마 오류인 것도 아닙니다.
  스키마가 완벽해도 프롬프트 편향 때문에 밀려날 수 있습니다.

## 3. `tool_choice` — 도구 호출을 API 차원에서 강제하기

### 3.1 왜 필요한가
설명과 프롬프트로 "이렇게 해줘"라고 부탁하는 것은 **확률적**입니다. 대부분 맞지만 가끔 틀립니다.
반면 `tool_choice`는 **결정론적(deterministic)** 제어입니다. API가 강제합니다.

`tool_choice`는 Claude API의 요청 파라미터로, `tools`와 함께 보냅니다.

### 3.2 네 가지 값

| 값 | 의미 | 모델이 할 수 있는 것 |
| --- | --- | --- |
| `{"type": "auto"}` | 기본값. 모델이 알아서 판단 | 텍스트 응답 OR 아무 도구 호출 OR 호출 안 함 |
| `{"type": "any"}` | **반드시 도구를 하나 호출**해야 함 (어떤 도구인지는 모델이 선택) | 목록 중 하나 호출. 일반 텍스트만 응답하는 것은 **금지** |
| `{"type": "tool", "name": "X"}` | **반드시 도구 X를 호출**해야 함 | 오직 X만 호출 |
| `{"type": "none"}` | **어떤 도구도 호출 금지** | 오직 텍스트 응답만 |

예시 요청:

```json
{
  "model": "claude-...",
  "tools": [ {"name": "create_profile", "...": "..."} ],
  "tool_choice": {"type": "tool", "name": "create_profile"},
  "messages": [ ... ]
}
```

### 3.3 `any` vs `tool` 의 결정적 차이
- `any` = "**뭔가는** 반드시 도구를 불러라" — 어느 도구인지는 모델이 고름
- `tool` = "**바로 이** 도구를 불러라" — 도구까지 지정

따라서 "특정 도구를 첫 번째로 강제하고 싶다"면 `any`로는 불가능합니다. `tool`이어야 합니다.

### 3.4 전형적 활용 패턴 ① — 첫 턴 강제, 이후 자율
요구사항: 온보딩 에이전트가 대화의 **가장 첫 동작**으로 `create_profile`을 반드시 부르고,
그 다음부터는 `send_welcome_email`, `assign_default_settings` 중 상황에 맞게 자유롭게 고르길 원한다.

해법 — **턴에 따라 `tool_choice`를 동적으로 바꾼다.**

```python
# 1번째 턴
tool_choice = {"type": "tool", "name": "create_profile"}

# 2번째 턴 이후
tool_choice = {"type": "auto"}
```

왜 다른 방법은 안 되는가:
- `tools` 배열에서 순서를 앞에 두기 → **순서는 강제력이 전혀 없다.** 단순 나열 순서일 뿐.
- 첫 턴에 `none` → 오히려 도구 호출을 금지하므로 요구사항과 정반대.
- 전체 대화에 `any` → 특정 도구를 지정할 수 없고, 이후 턴에서 "도구를 안 쓰고 그냥 대답"하는 자유도 뺏김.

### 3.5 전형적 활용 패턴 ② — 선행 의존성 보장 (Ordering)
요구사항: `add_tags`, `link_related`, `generate_summary`(보강 도구들)는
`extract_metadata`가 만들어낸 필드에 의존한다. 그런데 모델이 가끔 값을 **추측(guess)**해서
보강 도구를 먼저 부른다.

해법: 메타데이터가 필요한 턴에 `tool_choice: {"type": "tool", "name": "extract_metadata"}`를 걸고,
그 결과가 돌아온 뒤부터 `auto` 또는 `any`로 풀어준다.

왜 설명 보강만으로는 부족한가:
- "이 도구는 extract_metadata의 출력이 필요합니다"라고 설명에 써두는 것은 **확률적 개선**입니다.
  대부분 잘 동작하지만 "guarantee(보장)"라는 요구는 충족하지 못합니다.
- 도구 목록을 턴마다 추가·제거하는 방법도 이론상 가능하지만, `tool_choice`가 훨씬 단순하고
  캐시·컨텍스트 안정성 면에서 유리합니다.

**규칙: "보장(guarantee)"이라는 단어가 요구사항에 있으면 프롬프트가 아니라 API 제어를 쓴다.**

### 3.6 전형적 활용 패턴 ③ — 자유 텍스트 응답 자체를 금지
요구사항: 하위 자동화 시스템이 **도구 호출만 파싱**할 수 있고 자유 텍스트는 처리 못 한다.
알림이 오면 `acknowledge_alert`, `escalate_alert`, `suppress_alert` 중 반드시 하나로 응답해야 한다.

해법: `tool_choice: {"type": "any"}`.
- 어느 도구인지는 모델이 판단해야 하므로 `tool`은 부적절.
- `auto`는 기본값일 뿐 강제력이 없음.
- `none`은 오히려 도구를 금지 — 정반대.
- 시스템 프롬프트에 "항상 도구로 응답하라"고 쓰는 것은 **강제가 아니라 부탁**이므로 100% 보장 아님.

## 4. 에러 설계 ① — 검증 에러 vs 비즈니스 에러

### 4.1 두 범주의 정의

**Validation Error (검증 에러)** — 입력 자체가 잘못됨
- 필수 필드 누락
- 타입 불일치 (숫자여야 하는데 문자열)
- 형식 위반 (날짜 포맷, 이메일 형식, enum 밖의 값)
- 스키마 구조 자체가 어긋남

핵심: **요청을 고쳐 쓰면(reformat) 통과할 수 있다.**

**Business Error / Domain Error (비즈니스 에러)** — 입력은 완벽하지만 규칙이 막음
- 계정이 정지(suspended) 상태
- 잔액 부족
- 법적 보류(legal hold) 중이라 삭제·취소 불가
- 이미 처리된 주문을 다시 취소하려 함

핵심: **요청 형식을 아무리 고쳐도 상태/정책이 바뀌지 않는 한 계속 실패한다.**

### 4.2 구별 기준 (외우기)
> 요청 자체가 **well-formed**(형식적으로 올바름)인가?
> - 아니다 → Validation Error
> - 그렇다. 그런데도 거부됐다 → Business Error

### 4.3 구체 예: 법적 보류(legal hold)
`cancel_subscription` 도구가 "이 계정은 법적 보류 중이라 취소 불가"로 거부했다.

- 요청 JSON은 완벽함 — account_id도 문자열이고 존재하는 값
- 거부 사유는 **계정의 상태에 대한 정책 규칙**
- 재시도·재구성해도 정책이 바뀌기 전엔 절대 성공 못 함

→ 따라서 **Business Error**입니다.

### 4.4 자주 나오는 잘못된 논리
- "스키마 검사 이후에 거부됐으니 전부 validation이다" → 아닙니다. 검사 **시점**이 아니라 **원인의 성질**이 기준입니다.
- "별도 서비스에서 검사했으니 business error다" → 결론은 맞아도 **이유가 틀렸습니다.**
  코드가 어디에서 실행되는지(아키텍처 위치)는 에러 분류 기준이 아닙니다.
- "account_id 필드가 원인이니 그 필드의 validation 실패다" → 아닙니다.
  **필드의 형식적 유효성**과 **그 필드가 가리키는 대상의 상태**는 엄격히 다른 층위입니다.

### 4.5 왜 이 구분이 중요한가
에이전트의 후속 행동이 달라지기 때문입니다.
- Validation Error → 인자를 고쳐서 **재시도**하면 성공 가능
- Business Error → 재시도해도 무의미. 사용자에게 **상황을 설명**하거나 다른 경로를 찾아야 함

## 5. 에러 설계 ② — MCP 도구 결과 형태와 `isError`

### 5.1 `isError` 필드
MCP 도구 호출 결과에는 `isError`라는 불리언 필드가 있습니다.
- `isError: false` → 호출이 **성공적으로 완수**됨
- `isError: true` → 호출이 **실패**함

### 5.2 가장 흔한 함정: "빈 결과 ≠ 에러"
반드시 구별해야 하는 두 상황이 있습니다.

**상황 A — 존재하는 고객인데 주문이 0건**
- 조회는 정상적으로 수행되었고, 답이 "없음"일 뿐입니다.
- **성공입니다.**

```json
{ "isError": false, "orders": [] }
```

**상황 B — 애초에 존재하지 않는 고객 ID**
- 조회 대상 리소스 자체가 없습니다. 요청 전제가 틀렸습니다.
- **에러입니다.**

```json
{
  "isError": true,
  "errorCategory": "not_found_error",
  "message": "Customer ID 'cus_99999' was not found."
}
```

### 5.3 왜 반드시 구별해야 하는가
- 둘 다 `isError: false` + 빈 배열로 처리하면 → **에러가 은폐**됩니다.
  에이전트는 "이 고객은 주문이 없구나"라고 잘못 결론 내리고, 오타난 ID를 영영 잡아내지 못합니다.
- 둘 다 `isError: true`로 처리하면 → 정상 상황을 실패로 취급해 불필요한 재시도·에러 핸들링이 발생합니다.
- 특히 빈 결과를 `transient`(일시적)로 분류하면 **의미 없는 주기적 재시도**가 반복됩니다.
  주문이 0건인 것은 시간이 지난다고 바뀌는 성질의 것이 아닙니다.

**규칙: "성공적으로 조회했는데 결과가 없다"는 성공. "조회 대상이 없다"는 에러.**

## 6. 에러 설계 ③ — 구조화된 에러 메타데이터와 재시도 전략

### 6.1 불투명한 에러의 문제
도구가 이렇게만 응답한다고 합시다.

```json
{ "isError": true, "content": [{ "type": "text", "text": "Operation failed." }] }
```

에이전트가 이 응답에서 얻을 수 있는 정보는 "실패했다"는 사실뿐입니다.
알 수 없는 것들:
- 이게 잠깐 뒤에 다시 하면 될 일인가? (배포 중 503)
- 아니면 영원히 안 될 일인가? (권한 없음, 존재하지 않는 리소스)
- 얼마나 기다렸다가 재시도해야 하나?

판단 근거가 없으면 에이전트는 **같은 호출을 무의미하게 반복**하다가 포기합니다.
토큰·시간·하위 API 부하가 낭비됩니다.

이때의 **가장 직접적인 원인**은 "에러를 구분할 구조화된 메타데이터가 없다"는 것입니다.
컨텍스트 윈도우 부족이나 `isError` 값 자체가 원인이 아닙니다.
(`isError: true`는 재시도를 무제한 허용하라는 신호가 아니라 단지 "실패"라는 표시일 뿐입니다.)

### 6.2 좋은 에러 응답의 형태

```json
{
  "isError": true,
  "errorCategory": "transient",
  "retryable": true,
  "retryAfterSeconds": 30,
  "httpStatus": 503,
  "message": "Billing API is temporarily unavailable (deployment in progress). Safe to retry in ~30s."
}
```

포함하면 좋은 것:
- **errorCategory**: 기계가 분기할 수 있는 범주 문자열
- **retryable**: 재시도가 의미 있는지 불리언
- **retryAfter**: 언제 다시 시도할지 힌트
- **message**: 사람과 모델이 읽을 수 있는 구체적 설명 ("무엇이" "왜" 실패했는지)

### 6.3 에러 카테고리 어휘 (자주 등장하는 것들)

| 카테고리 | 뜻 | 재시도? |
| --- | --- | --- |
| `validation_error` | 입력 형식/스키마 문제 | 인자를 고쳐서 재시도 |
| `not_found_error` | 대상 리소스 없음 | 같은 인자로는 무의미 |
| `permission_error` / `auth_error` | 권한·인증 실패 | 자격 증명 갱신 없이는 무의미 |
| `business_error` | 도메인 정책 위반 | 상태가 바뀌기 전엔 무의미 |
| `transient` | 일시적 장애 (503, 타임아웃, 연결 리셋) | **재시도 가치 있음** (백오프 권장) |
| `rate_limit` | 호출 한도 초과 | 대기 후 재시도 |

### 6.4 Transient(일시적) 오류란
시간이 지나면 저절로 해소될 가능성이 높은 실패입니다.
- HTTP 503 Service Unavailable (배포·재시작 중)
- 데이터베이스 커넥션 리셋
- 네트워크 타임아웃
- 일시적 락 경합

대응 방식은 **지수 백오프 재시도(exponential backoff)** — 1초, 2초, 4초... 간격을 늘려가며 재시도.

### 6.5 반대 개념: 영구(permanent / non-retryable) 오류
- 400 Bad Request, 401/403, 404, 422
- 도메인 정책 위반
- 재시도해도 결과가 동일하므로 즉시 상위에 보고하거나 사용자에게 설명해야 함

## 7. 계층적 에이전트 — 코디네이터와 서브에이전트

### 7.1 구조
- **코디네이터(coordinator) / 오케스트레이터**: 큰 작업을 쪼개서 위임하고 결과를 통합
- **서브에이전트(subagent)**: 위임받은 하위 작업을 **자기 컨텍스트 안에서 끝까지** 수행

이 구조의 장점은 **컨텍스트 격리**입니다. 서브에이전트의 시행착오·중간 로그가
코디네이터의 컨텍스트를 오염시키지 않습니다.

### 7.2 캡슐화(Encapsulation)와 결함 격리(Fault Containment)
서브에이전트의 책임은 **"결과"를 책임지는 것**이지 "과정을 중계하는 것"이 아닙니다.

예: ETL 3단계(extract → transform → load) 마이그레이션을 위임받았고,
load 단계에서 DB 커넥션 리셋(알려진 일시적 오류)으로 2번 실패했지만
서브에이전트 내부의 재시도 로직이 3번째 시도에서 성공했다고 합시다.

→ 코디네이터에게는 **성공 결과와 완료된 마이그레이션 요약**만 보고합니다.

이유:
- 일시적 실패는 **로컬에서 이미 해결**되었습니다. 최종 상태는 완전 성공입니다.
- 이런 실패는 코디네이터가 알아야 할 **의사결정 정보가 아닙니다.**
  코디네이터가 그걸 알아도 할 수 있는 일이 없습니다.

### 7.3 잘못된 보고 방식들
| 잘못된 보고 | 결과 |
| --- | --- |
| `isError: true`로 실패 보고 | 코디네이터가 이미 성공한 마이그레이션을 **또 재시도** → 중복 처리, 데이터 손상 위험 |
| "자격 증명이 만료된 것 같으니 새 크레덴셜을 달라"고 에스컬레이션 | 문제에 명시된 원인(transient)과 다른 **오진단**. 3번째에 성공했다는 사실 자체가 반증 |
| load 단계를 빼고 부분 결과만 보고 | 실제 DB 상태(적재 완료)와 보고 내용이 **불일치** |

### 7.4 그럼 언제 에스컬레이션하는가
- 재시도 예산을 다 쓰고도 **최종 실패**했을 때
- 서브에이전트 권한 밖의 결정이 필요할 때 (파괴적 작업 승인, 새 자격 증명 획득 등)
- 위임된 지시가 모호하거나 모순될 때

**요약: 안에서 해결된 문제는 안에서 끝낸다. 밖으로 올리는 것은 밖에서만 해결 가능한 것이다.**

## 8. Claude Code의 내장 도구들 — 무엇을 언제 쓰는가

Claude Code는 코드베이스 작업을 위한 내장 도구 세트를 가지고 있습니다.
각 도구는 **할 수 있는 일이 엄격히 정해져 있습니다.**

| 도구 | 하는 일 | 못 하는 일 |
| --- | --- | --- |
| **Read** | 파일 내용을 읽어서 보여줌 | 명령 실행, 파일 수정 |
| **Glob** | 파일명 **패턴**으로 파일 경로 목록 반환 (`**/*.test.ts`) | 파일 내용 검색, 실행 |
| **Grep** | 파일 **내용**을 정규식으로 검색 | 명령 실행 |
| **Bash** | 셸 명령을 **실제로 실행**하고 stdout/stderr 캡처 | — |
| **Edit** | 파일 내 문자열을 정확히 찾아 치환 | 정규식 매칭 |
| **Write** | 파일 전체를 새로 쓰거나 덮어씀 | 부분 수정 (Edit이 담당) |

### 8.1 "무언가를 실행해야 한다면 Bash다"
버그를 재현하려면 테스트 스위트를 **실제로 돌려야** 합니다.
`pytest`, `npm test`, `cargo test` 같은 명령을 실행하고
**stdout과 stderr**(스택 트레이스가 여기 나옵니다)를 받아오는 유일한 수단이 **Bash**입니다.

흔한 착각들:
- Grep으로 "test"라는 단어를 찾아서 테스트가 통과했다고 판단 → 검색은 실행이 아닙니다.
- Glob으로 테스트 **파일이 존재함**을 확인 → 파일 존재와 테스트 통과는 무관합니다.
- Read로 `jest.config.js` 같은 **설정 파일**을 읽고 성공/실패를 추론 → 설정은 실행 결과를 담지 않습니다.

**원칙: 정적 조회 도구로는 런타임 상태를 알 수 없다. 실행해야 알 수 있다.**

### 8.2 stdout / stderr / stack trace
- **stdout**(표준 출력): 프로그램의 정상 출력 스트림
- **stderr**(표준 에러): 에러 메시지 전용 스트림
- **스택 트레이스(stack trace)**: 예외 발생 시점의 함수 호출 경로.
  "어느 파일 몇 번째 줄에서, 어떤 함수 체인을 거쳐 터졌는가"를 알려줍니다.
  버그 재현·원인 분석의 1차 자료입니다.

## 9. Edit 도구와 고유 매칭 (Unique Match)

### 9.1 Edit의 동작 원리
Edit은 세 가지를 받습니다.
- `file_path` — 대상 파일
- `old_string` — 찾을 문자열
- `new_string` — 바꿔 넣을 문자열
- (선택) `replace_all` — 모든 출현을 바꿀지 여부

핵심 규칙 두 가지:
1. `old_string`은 **리터럴 텍스트**로 해석됩니다. **정규식이 아닙니다.**
   따옴표가 있든 없든 정규식으로 바뀌지 않습니다.
2. `old_string`은 파일 내에서 **유일해야** 합니다. 여러 곳에 매칭되면 에러가 나거나
   의도치 않은 위치가 바뀝니다. Edit은 "의미상 어느 쪽이 진짜인지" **추론하지 않습니다.**

### 9.2 문제 상황
`package.json`에서 버전 문자열 `1.4.2`를 바꾸고 싶은데,
우연히 어떤 의존성 이름 안에도 `1.4.2`가 부분 문자열로 들어 있습니다.

```json
{
  "version": "1.4.2",
  "dependencies": {
    "legacy-shim-1.4.2": "^3.0.0"
  }
}
```

`old_string: "1.4.2"`로 하면 어느 쪽이 바뀔지 알 수 없습니다.

### 9.3 해결책 — 주변 문맥을 포함시켜 유일하게 만든다

```
old_string:  "version": "1.4.2",
new_string:  "version": "1.5.0",
```

키 이름 `"version":`과 줄 전체 구조를 함께 넣음으로써 파일 전체에서 **단 한 곳**에만 매칭됩니다.
여전히 모호하면 앞뒤 줄을 더 붙여 문맥을 넓히면 됩니다.

### 9.4 `replace_all`은 언제 쓰나
"이 심볼을 파일 전체에서 일괄 개명한다" 같은 **의도적 전역 치환**에만 씁니다.
지금처럼 무관한 위치가 섞여 있는 상황에서 켜면 의존성 이름까지 망가지는 **사이드 이펙트**가 납니다.

**원칙: 모호함은 `replace_all`이 아니라 더 넓은 문맥으로 푼다.**

## 10. MCP (Model Context Protocol) 기초

### 10.1 MCP란 무엇인가
**Model Context Protocol**은 AI 애플리케이션이 외부 시스템(데이터베이스, SaaS, 사내 API,
파일 시스템 등)에 연결되는 방식을 **표준화한 개방형 프로토콜**입니다.

비유하자면 **AI 애플리케이션의 USB-C 포트**입니다.
연동 대상마다 제각각인 커스텀 통합 코드를 쓰는 대신, 한 가지 규격으로 붙입니다.

### 10.2 구성 요소
- **MCP 호스트/클라이언트**: Claude Code, Claude 데스크톱 앱 등 — 서버에 연결하는 쪽
- **MCP 서버**: 특정 시스템의 기능을 MCP 규격으로 노출하는 프로그램
  (예: Notion 서버, GitHub 서버, 사내 DB 서버)

### 10.3 MCP 서버가 노출하는 세 가지 원시 타입(primitives)

| 타입 | 성격 | 예 |
| --- | --- | --- |
| **Tools** | 모델이 **호출해서 행동**하는 함수 | `create_invoice`, `get_customer_orders` |
| **Resources** | 모델이 **읽어들이는 데이터/문서** | 인증 가이드 문서, 스키마 파일, 로그 |
| **Prompts** | 재사용 가능한 프롬프트 템플릿 | "이 코드 리뷰해줘" 워크플로 |

Tools는 "동사", Resources는 "명사"라고 기억하면 편합니다.

### 10.4 전송 방식 (transport)
- **stdio**: 로컬에서 서버 프로세스를 띄우고 표준 입출력으로 통신 (개인 로컬 서버에 흔함)
- **HTTP/SSE**: 원격 서버에 네트워크로 연결

## 11. MCP 설정 스코프 (Scope)

Claude Code에서 MCP 서버를 추가할 때 **어디에 저장하느냐**가 곧 **누가 그 서버를 보게 되느냐**를 결정합니다.

### 11.1 세 가지 스코프

| 스코프 | 저장 위치 | 적용 범위 | 공유 여부 |
| --- | --- | --- | --- |
| **local** | 해당 프로젝트에 대한 사용자 개인 설정 | **그 프로젝트에서만**, 나에게만 | 공유 안 됨 |
| **project** | 프로젝트 루트의 `.mcp.json` | 그 프로젝트 | **팀 공유** (git 커밋 대상) |
| **user** | 홈 디렉터리의 `~/.claude.json` | **그 머신의 모든 프로젝트** | 공유 안 됨 |

### 11.2 어떻게 고르는가 — 두 축으로 판단
1. **범위**: 한 프로젝트만인가, 이 머신의 모든 프로젝트인가?
2. **가시성**: 나만 볼 것인가, 팀과 공유할 것인가?

| 원하는 것 | 정답 스코프 |
| --- | --- |
| 팀 전체가 이 프로젝트에서 쓸 공용 서버 | **project** |
| 이 프로젝트에서 나만 쓸 실험적 서버 | **local** |
| 내 머신 어디서든, 나만 쓸 개인 서버 | **user** |

### 11.3 구체 사례
"개인 Notion 워크스페이스를 조회하는 실험적 로컬 MCP 서버를,
동료에게는 보이지 않게 하고, 내 머신에서 **어떤 프로젝트를 열든** 쓰고 싶다."

→ **user 스코프**. `~/.claude.json`에 기록되고, 모든 프로젝트에서 로드되며, git 리포지토리에 들어가지 않습니다.

왜 다른 답은 안 되는가:
- `.mcp.json` + `.gitignore` → `.mcp.json`은 **프로젝트 단위**입니다. 공유는 막을 수 있어도
  "모든 프로젝트에서 사용 가능"이라는 조건을 만족하지 못합니다. 프로젝트마다 다시 설정해야 합니다.
- project 스코프는 **애초에 공유용**입니다. "개인 전용으로 표시하는" 플래그 같은 건 없습니다.
- `.claude/settings.json`에 직접 넣는 것도 프로젝트 단위 범위에 묶입니다.

명령 형태(참고):
```bash
claude mcp add notion --scope user -- npx -y @modelcontextprotocol/server-notion
```

## 12. Tool Search와 `alwaysLoad`

### 12.1 문제: 도구가 너무 많다
MCP 서버를 10개쯤 붙이면 도구가 수백 개가 될 수 있습니다.
모든 도구의 이름·설명·스키마를 **매 요청마다 컨텍스트에 넣으면**:
- 토큰이 대량으로 낭비되고
- 선택지가 많아져 모델의 도구 선택 정확도가 떨어집니다.

### 12.2 해결: Tool Search (도구 탐색 / 지연 로딩)
그래서 도입된 것이 **Tool Search**입니다.
모든 도구 정의를 미리 넣지 않고, **필요할 때 검색해서 그 도구의 정의만 불러오는** 방식입니다.
이를 **deferred loading**(지연 로딩)이라 부릅니다.

- 장점: 컨텍스트 절약, 선택 정확도 향상
- 단점: 도구를 찾아 해석하는 **추가 단계**가 생겨 약간의 **지연(latency)**이 발생

### 12.3 예외 처리: `alwaysLoad: true`
어떤 서버의 도구를 **거의 매 턴마다** 쓴다면, 매번 탐색하는 것은 순수한 낭비입니다.
이럴 때 그 서버의 설정 항목에 `alwaysLoad: true`를 주면
**세션 시작 시점에 그 서버의 도구 정의가 컨텍스트에 즉시 로드**되어 탐색 단계를 건너뜁니다.

```json
{
  "mcpServers": {
    "internal-tools": {
      "command": "node",
      "args": ["./internal-mcp/server.js"],
      "alwaysLoad": true
    }
  }
}
```

핵심: **서버 단위로 개별 적용**할 수 있습니다. 그래서 "10개 중 그 1개 서버만" 같은 요구를 정확히 충족합니다.

### 12.4 혼동하기 쉬운 다른 설정들
| 설정 | 실제 의미 | 이 문제와의 관계 |
| --- | --- | --- |
| `MAX_MCP_OUTPUT_TOKENS` | 도구 **응답 결과**의 최대 토큰 수 제한 | 호출 **이후** 출력 크기 문제. 로딩 지연과 무관 |
| `ENABLE_TOOL_SEARCH=false` | 도구 탐색을 **전역으로** 비활성화 | 10개 서버 전부의 도구가 컨텍스트에 올라와 토큰 폭증. "한 서버만"이라는 요구와 어긋남 |
| 스코프 변경 (project→user) | 설정 파일 위치와 공유 범위 | 로딩 시점을 제어하는 옵션이 전혀 아님 |

## 13. MCP 리소스 참조 — `@` 멘션

### 13.1 리소스란
MCP 서버가 노출하는 **읽기 대상 데이터**입니다. 각 리소스는 **URI**로 식별됩니다.
예: `file://api/authentication`, `db://schema/users`

### 13.2 프롬프트 안에서 리소스를 직접 참조하기
Claude Code에서는 로컬 파일을 `@src/index.ts`처럼 `@`로 참조합니다.
MCP 리소스도 같은 감각으로, 다음 형태로 참조합니다.

```
@<server_name>:<resource_uri>
```

실제 예:

```
@docs:file://api/authentication 이 문서 기준으로 우리 로그인 플로우가 맞는지 검토해줘
```

이렇게 쓰면 해당 리소스의 내용이 **프롬프트 실행 시점에 컨텍스트로 직접 삽입**되어
Claude가 그 문서를 바로 분석할 수 있습니다.

### 13.3 왜 다른 방법은 부적절한가
- `.mcp.json`에 `resources` 필드를 넣어 **매 세션 자동 로드** → 그런 필드는 표준이 아니며,
  설령 있어도 필요 없을 때까지 컨텍스트를 낭비합니다. "이번 프롬프트에서 이 문서를"이라는 요구와 다릅니다.
- `list_resources`를 수동 호출해 **원시 JSON을 복붙** → 번거롭고, 리소스 참조 기능을 우회하는
  임시방편입니다. 형식도 깨지기 쉽습니다.
- "docs 서버 좀 열어봐"라고 **자연어로 막연히 요청** → 어느 리소스인지 특정되지 않아
  모델이 추측하게 됩니다. 명시적 참조 구문이 존재하는 이유가 바로 이 모호성을 없애기 위함입니다.

## 14. 전체를 관통하는 설계 원칙 정리

1. **모델은 텍스트로 판단한다.** 도구의 이름과 설명이 가장 강력한 제어 수단이다.
2. **모호성을 남기지 마라.** 두 도구의 설명이 겹치면 반드시 오호출이 난다. 반환 필드까지 구체적으로 써라.
3. **카탈로그를 유지보수하라.** 새 도구를 추가했으면 기존 도구의 이름·설명도 함께 갱신하라.
4. **"보장"이 필요하면 프롬프트가 아니라 API를 써라.** `tool_choice`는 결정론적이고 프롬프트는 확률적이다.
5. **에러는 원인의 성질로 분류하라.** 실행 위치나 검사 순서가 아니라 "요청이 well-formed인가"가 기준이다.
6. **빈 결과와 없는 리소스를 구별하라.** 전자는 성공, 후자는 에러다.
7. **에러에 구조화된 메타데이터를 실어라.** 재시도 가능 여부를 기계가 판단할 수 있어야 한다.
8. **일시적 오류는 가장 낮은 계층에서 흡수하라.** 안에서 해결됐으면 밖에는 성공만 보고한다.
9. **정적 조회로 런타임을 추론하지 마라.** 실행 결과가 필요하면 실제로 실행하라.
10. **치환은 유일성이 생명이다.** 문맥을 넓혀 유일하게 만들되, 전역 치환으로 도망가지 마라.
11. **설정의 저장 위치가 곧 공유 범위다.** 스코프는 "어디서 쓰나 × 누가 보나" 두 축으로 고른다.
12. **최적화는 표적 지향으로.** 한 서버가 문제면 그 서버만 고쳐라. 전역 스위치를 끄지 마라.

## 15. 용어 사전 (Glossary)

### 도구·모델 일반
| 용어 | 설명 |
| --- | --- |
| **Tool Use / Function Calling** | LLM에게 호출 가능한 함수 목록을 제공하고, 모델이 그중 하나를 호출하도록 하는 메커니즘 |
| **tool_use block** | 모델이 출력하는, "이 도구를 이 인자로 불러달라"는 구조화된 응답 블록 |
| **tool_result block** | 애플리케이션이 도구 실행 결과를 모델에게 되돌려주는 블록 |
| **Agent Loop** | 모델 호출 → 도구 실행 → 결과 반환을 반복하는 순환 구조 |
| **Tool Description** | 도구가 무엇을 하는지 자연어로 쓴 설명. 모델의 도구 선택에 가장 큰 영향을 미침 |
| **Input Schema** | 도구의 파라미터를 JSON Schema로 정의한 것 |
| **Tool Selection / Tool Routing** | 여러 도구 중 요청에 맞는 하나를 고르는 과정 |
| **Misrouting** | 부적절한 도구를 호출하는 오류. 주로 설명이 모호하거나 중복될 때 발생 |
| **Description Drift** | 기능 범위가 바뀌었는데 설명이 갱신되지 않아 생기는 불일치 |
| **Overlapping Scope** | 두 도구의 담당 영역이 겹쳐 모델이 구별하지 못하는 상태 |
| **Disambiguation** | 모호성 해소. 이름·설명을 구체화해 도구 경계를 분명히 하는 작업 |
| **System Prompt** | 대화 전체의 규칙·역할을 규정하는 최상위 지시문 |
| **Override** | 프롬프트의 명시적 지시가 모델 자체의 판단을 덮어쓰는 현상 |

### tool_choice 관련
| 용어 | 설명 |
| --- | --- |
| **tool_choice** | 모델의 도구 호출 동작을 API 차원에서 제어하는 요청 파라미터 |
| **`{"type":"auto"}`** | 기본값. 도구를 쓸지, 어떤 걸 쓸지 모두 모델이 자율 판단 |
| **`{"type":"any"}`** | 반드시 도구 중 하나를 호출해야 함. 일반 텍스트만으로 응답 불가 |
| **`{"type":"tool","name":"X"}`** | 반드시 도구 X를 호출해야 함. 특정 도구 강제 |
| **`{"type":"none"}`** | 어떤 도구도 호출 금지. 텍스트 응답만 |
| **Deterministic Control** | 확률적 유도가 아니라 시스템이 결과를 강제하는 제어 방식 |
| **Ordering / Prerequisite Tool** | 다른 도구보다 반드시 먼저 실행되어야 하는 선행 도구 |
| **Guessed Values** | 선행 도구를 부르지 않고 모델이 임의로 지어낸 인자 값 |
| **Structured Output** | 자유 텍스트가 아닌, 기계가 파싱 가능한 형태의 출력 |

### 에러 설계
| 용어 | 설명 |
| --- | --- |
| **Validation Error** | 입력의 형식·타입·구조 자체가 잘못된 에러. 요청을 고치면 통과 가능 |
| **Business Error / Domain Error** | 입력은 정상이나 도메인 정책·상태 때문에 거부되는 에러 |
| **Well-formed** | 요청이 형식적으로 올바른 상태 |
| **Malformed Input** | 형식이 깨진 입력 |
| **Legal Hold** | 법적 분쟁·조사 등을 이유로 데이터 변경·삭제를 금지하는 정책 상태 |
| **Policy Rule** | 계정·리소스 상태에 대한 비즈니스 규칙 |
| **isError** | MCP 도구 결과에서 성공(false)/실패(true)를 나타내는 불리언 필드 |
| **Empty Result** | 조회는 성공했으나 반환할 항목이 없는 정상 상태 (`[]`) |
| **not_found_error** | 조회 대상 리소스 자체가 존재하지 않을 때의 에러 카테고리 |
| **errorCategory** | 에러의 종류를 기계가 분기할 수 있게 표기한 필드 |
| **Structured Metadata** | 에러에 붙는 구조화된 부가 정보(카테고리, 재시도 가능 여부, 대기 시간 등) |
| **Opaque Error** | "Operation failed." 처럼 원인을 알 수 없는 불투명한 에러 메시지 |
| **Transient Error** | 시간이 지나면 해소될 가능성이 높은 일시적 장애 (503, 타임아웃, 커넥션 리셋) |
| **Non-retryable / Permanent Error** | 재시도해도 결과가 같은 영구적 실패 |
| **Retryability** | 재시도가 의미 있는지 여부 |
| **Exponential Backoff** | 재시도 간격을 1→2→4초처럼 지수적으로 늘리는 전략 |
| **503 Service Unavailable** | 서버가 일시적으로 요청을 처리할 수 없음을 뜻하는 HTTP 상태 코드 |
| **Connection Reset** | 네트워크 연결이 상대편에 의해 끊긴 상태. 대표적 일시적 오류 |
| **Rate Limit** | 단위 시간당 호출 한도 초과 |

### 에이전트 아키텍처
| 용어 | 설명 |
| --- | --- |
| **Coordinator / Orchestrator Agent** | 작업을 분할하고 위임하며 결과를 통합하는 상위 에이전트 |
| **Subagent** | 위임받은 하위 작업을 독립 컨텍스트에서 수행하는 에이전트 |
| **Delegation** | 상위 에이전트가 하위 에이전트에게 작업을 넘기는 것 |
| **Encapsulation** | 내부 처리 과정을 감추고 결과만 노출하는 설계 원칙 |
| **Fault Containment** | 장애를 발생 지점 계층에서 흡수해 상위로 전파하지 않는 원칙 |
| **Escalation** | 자체 해결 불가능한 사안을 상위로 올려 판단을 요청하는 것 |
| **Partial Results** | 일부 단계만 완료된 상태의 결과 보고 |
| **ETL (Extract–Transform–Load)** | 데이터를 추출·변환·적재하는 3단계 데이터 파이프라인 패턴 |
| **Context Isolation** | 서브에이전트의 중간 과정이 상위 컨텍스트를 오염시키지 않게 하는 것 |

| **Read** | 파일 내용을 읽는 도구 |

| **Surrounding Context** | 유일성 확보를 위해 `old_string`에 함께 포함시키는 주변 코드·키·줄 |
| **Literal Text** | 특수문자를 패턴으로 해석하지 않는 그대로의 문자열 |
| **stdout / stderr** | 표준 출력 / 표준 에러 스트림 |
| **Stack Trace** | 예외 발생 시점의 함수 호출 경로 기록 |
| **Test Runner** | 테스트를 실행하는 프로그램 (pytest, jest, cargo test 등) |
| **Reproduce** | 코드를 고치기 전에 버그를 실제로 재현해 확인하는 작업 |

### MCP
| 용어 | 설명 |
| --- | --- |
| **MCP (Model Context Protocol)** | AI 애플리케이션과 외부 시스템의 연결을 표준화한 개방형 프로토콜 |
| **MCP Server** | 특정 시스템의 기능을 MCP 규격으로 노출하는 프로그램 |
| **MCP Client / Host** | MCP 서버에 연결하는 AI 애플리케이션 (Claude Code 등) |
| **Tools (MCP)** | 모델이 호출해 행동을 수행하는 함수. "동사" |
| **Resources (MCP)** | 모델이 읽어들이는 데이터·문서. URI로 식별. "명사" |
| **Prompts (MCP)** | 재사용 가능한 프롬프트 템플릿 |
| **stdio transport** | 로컬 프로세스와 표준 입출력으로 통신하는 전송 방식 |
| **Resource URI** | 리소스를 식별하는 주소 (`file://api/authentication` 등) |
| **@ Mention** | 프롬프트에 리소스·파일을 인라인 참조하는 구문. MCP는 `@<server>:<uri>` 형태 |
| **`.mcp.json`** | 프로젝트 루트에 두는 MCP 설정 파일. project 스코프. git 공유 대상 |
| **`~/.claude.json`** | 홈 디렉터리의 사용자 설정 파일. user 스코프 저장 위치 |
| **User Scope** | 그 머신의 모든 프로젝트에 적용되며 공유되지 않는 설정 범위 |
| **Project Scope** | 특정 프로젝트에 적용되며 팀과 공유되는 설정 범위 |
| **Local Scope** | 특정 프로젝트에 대해 나에게만 적용되는 개인 설정 범위 |
| **Tool Search** | 도구가 많을 때 필요한 것만 검색해 불러오는 지연 로딩 메커니즘 |
| **Deferred Loading** | 도구 정의를 미리 넣지 않고 필요 시점에 로드하는 방식 |
| **`alwaysLoad: true`** | 특정 MCP 서버의 도구를 세션 시작 시 항상 컨텍스트에 로드하는 서버별 옵션 |
| **`ENABLE_TOOL_SEARCH`** | 도구 탐색 기능 전체를 켜고 끄는 전역 환경 변수 |
| **`MAX_MCP_OUTPUT_TOKENS`** | MCP 도구 응답 결과의 최대 토큰 수 제한 |
| **Context Window** | 모델이 한 번에 처리할 수 있는 토큰 총량 |
| **Latency** | 요청부터 응답까지의 지연 시간 |
