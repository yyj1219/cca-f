## 공통 기초

### LLM은 스스로 아무것도 실행하지 못한다

대규모 언어 모델(LLM, Large Language Model)은 텍스트를 입력받아 텍스트를 출력하는 함수입니다. Claude, GPT 같은 것들이 여기에 해당합니다. 파일을 읽거나, 데이터베이스를 지우거나, HTTP 요청을 보내거나, 결제를 하는 능력은 모델 자체에 없습니다. 모델이 할 수 있는 최선은 **"나는 이런 작업을 이런 인자로 하고 싶다"고 말하는 것**뿐이고, 실제 실행은 모델이 아니라 여러분의 애플리케이션 코드(런타임)가 합니다.

### 모델은 "기억"이 없다 — 컨텍스트

LLM은 요청 한 번마다 **그 요청에 담겨 온 텍스트만** 봅니다. 이전 요청에서 무슨 일이 있었는지 서버가 알아서 기억해 주지 않습니다. 대화가 이어지는 것처럼 보이는 이유는, 클라이언트(우리 코드)가 **지금까지의 대화 전체를 매번 다시 보내주기** 때문입니다.

- 이 "매번 다시 보내는 텍스트 뭉치"를 **컨텍스트(context)** 라고 합니다.
- 한 번에 담을 수 있는 최대 분량을 **컨텍스트 윈도우(context window)** 라고 합니다.

여기서 파생되는 두 가지 사실이 이 범위 전체를 관통합니다.

- **전달하지 않은 정보는 모델이 절대 알 수 없다.** 기억이 아니라 "매번 다시 보여주기"입니다.
- **컨텍스트는 유한하고 비용(토큰)이 든다.** 그래서 무엇을 넣고 무엇을 뺄지가 아키텍처 설계 문제가 됩니다.

이 한 문장이 전체를 관통합니다: **모델은 컨텍스트에 들어 있는 것만 안다.** 뒤에 나오는 "도구 결과가 사라져 같은 도구를 또 부른다", "서브에이전트가 형제 에이전트의 결과를 모른다", "서버리스 컨테이너에서 세션 재개가 안 된다" 같은 문제는 전부 이 원리의 다른 얼굴입니다.

### 도구(Tool)와 에이전트(Agent)

일반적인 챗봇은 사용자의 말을 받아 텍스트로 답하고 끝납니다. **에이전트**는 여기에 두 가지가 더해진 것입니다.

- **도구(Tool)**: 모델이 호출을 "요청"할 수 있는, 개발자가 정의한 외부 기능. 이름, 설명, 입력 스키마(JSON Schema)로 정의합니다. 예: `get_customer`, `process_refund`, `web_search`, 파일 읽기(`Read`), 문자열 검색(`Grep`), 셸 실행(`Bash`), 파일 수정(`Edit`), 파일 생성(`Write`).
- **루프(Loop)**: 모델이 도구를 요청하면 → 프로그램이 실행하고 → 결과를 다시 모델에게 돌려주고 → 모델이 그 결과를 보고 다음 판단을 하는 사이클을, 목표가 달성될 때까지 반복하는 구조.

```
사용자 요청
   ↓
LLM이 생각 → "파일을 읽어야겠다" → 도구 호출 요청
   ↓
프로그램이 실제로 파일을 읽음 → 결과를 LLM에게 돌려줌
   ↓
LLM이 결과를 보고 다시 생각 → 또 도구 호출하거나, 최종 답변
   ↓
(반복)
```

즉 **에이전트 = 모델 + 도구 실행 코드 + 반복 루프**이며, "에이전트"란 특별한 모델이 아닙니다. 이 반복 구조를 **에이전틱 루프(Agentic Loop)** 또는 **에이전트 루프**라고 부릅니다. 이 루프 덕분에 에이전트는 "한 번 답하고 끝"이 아니라 **여러 턴에 걸쳐 스스로 일을 진행하는 프로그램**이 됩니다.

그래서 이 학습노트가 다루는 주제들이 자연스럽게 따라 나옵니다.

- 여러 에이전트를 어떻게 조직할 것인가 (오케스트레이션)
- 루프를 언제 멈출 것인가 (정지 조건)
- 위험한 도구 호출을 어떻게 막을 것인가 (훅, 권한)
- 대화 기록(컨텍스트)을 어떻게 관리할 것인가 (세션, 격리)

### 확률적(Probabilistic) vs 결정론적(Deterministic)

이 구분이 주제 전체를 관통하는 가장 중요한 개념입니다.

| 구분 | 확률적 (Probabilistic) | 결정론적 (Deterministic) |
|---|---|---|
| 예시 | LLM의 텍스트 생성, 프롬프트 지시 준수 | if 문, 정규식 검사, 코드 로직 |
| 보장 수준 | "대체로" 지킨다 | 100% 지킨다 |
| 실패 원인 | 표현이 낯설거나, 지시가 복잡하거나, 공격을 당하면 어긋남 | 코드에 버그가 없으면 어긋나지 않음 |

LLM에게 "500달러 넘는 환불은 절대 승인하지 마"라고 시스템 프롬프트에 써도, 모델은 이를 **대체로** 지킬 뿐 **항상** 지키지는 않습니다. 이 차이가 보안·규정·금전 관련 규칙에서는 치명적입니다. 그래서 등장하는 것이 **훅(Hook)** 입니다.

### 서브에이전트가 존재하는 이유 — 컨텍스트 예산

컨텍스트가 유한하고 비용이 든다는 사실은 곧바로 아키텍처로 이어집니다. 하나의 대화에 모든 파일 내용과 모든 중간 결과를 쌓으면, 컨텍스트 윈도우가 차기도 하고 정작 중요한 디테일이 묻히기도 합니다(맥락 희석). 그래서 **서브에이전트**에 하위 작업을 위임하고, 탐색 과정의 잡음은 서브에이전트의 컨텍스트 안에 가둔 뒤 **결론만 상위로 올립니다**. 동시에 서브에이전트는 전문화, 병렬 실행, 그리고 도구 목록을 좁히는 권한 격리의 수단이기도 합니다. 다만 서브에이전트도 상태가 없으므로, 필요한 맥락은 위임할 때 **명시적으로 넣어 줘야** 합니다.

### 계층 구조 이해하기

이 주제 영역에는 세 가지 층위가 나오고, 자꾸 섞여서 헷갈리므로 먼저 구분해 둡시다.

| 층위 | 무엇인가 | 대표 개념 |
|---|---|---|
| **Messages API (저수준)** | Anthropic이 제공하는 HTTP API. 메시지 배열을 보내고 응답을 받습니다. 루프는 내가 직접 짭니다. | `messages`, `role`, `content` 블록, `tool_use`, `tool_result`, `stop_reason` |
| **Claude Agent SDK (중간)** | 루프, 훅, 서브에이전트, 권한 등을 대신 관리해 주는 라이브러리 | 훅(Hooks), 서브에이전트, `AgentDefinition`, `maxTurns` |
| **Claude Code CLI (최상위)** | 터미널에서 쓰는 대화형 도구 | 세션, `--resume`, `/fork`, `/clear`, `/compact`, `.claude/agents` |

## 전체를 관통하는 설계 원칙

여섯 원본이 각각 정리한 원칙 목록을 합치고 중복을 걷어낸 것입니다.

**통제와 보장**

1. **보장이 필요하면 모델 밖에 두어라.** 프롬프트는 영향을 줄 뿐이고(확률적, 소프트 제약), 코드(훅, 권한 설정, `tool_choice`, 서브에이전트 `tools`)가 강제합니다(결정론적, 하드 제약). 규정 준수·보안·순서 강제는 훅에게, 상황 적응은 모델에게 맡깁니다.
2. **시점이 곧 훅의 선택이다.** 막을 것은 실행 전(`PreToolUse`, 입력 통제), 다듬을 것은 실행 후(`PostToolUse`, 출력 통제). 되돌릴 수 없는 작업은 반드시 사전에 막습니다. 사후 로깅·사후 검증은 부작용을 되돌리지 못하므로 예방이 아닙니다.
3. **실패할 때는 닫히는 쪽으로 실패하라(Fail-Closed).** 그리고 그 실패가 세션 전체를 무너뜨리지 않게 하라.
4. **안전 판단은 가장 보수적인 쪽으로 수렴한다.** 하나의 `deny`가 모든 `allow`를 이깁니다.
5. **위험도와 가역성으로 권한을 차등한다.** 저위험 읽기는 `allow`, 되돌릴 수 없는 고위험 작업은 `ask`나 `deny`. **되돌릴 수 없는 작업에는 사람을 넣습니다**(`ask`를 통한 human-in-the-loop).
6. **최소 권한.** 필요한 것만 주되, 임무 수행에 필요한 것은 뺏지 않습니다.
7. **권한은 도구 목록으로, 예산은 `maxTurns`로.** 서로 대체할 수 없습니다.
8. **필터링의 층을 구분한다.** 도구 이름은 matcher로, 인자 값은 콜백 내부 로직으로 거릅니다.
9. **검증은 원천 데이터로.** 오염될 수 있는 간접 플래그 대신, 호출 인자에 실린 명시적 검증 결과를 직접 검사합니다.
10. **명시적으로 좁히기.** 정규표현식은 앵커로, 권한은 최소한으로, 이름은 네임스페이스를 붙여 사람이 읽을 수 있게. 앵커 없는 정규식과 네임스페이스 없는 이름은 의도치 않은 대상을 잡습니다.

**루프와 신호**

11. **명세된 신호를 쓰고, 부산물로 추측하지 마라.** 정지 조건은 `stop_reason`이지 "텍스트가 있느냐 없느냐"가 아닙니다.
12. **모든 `stop_reason`을 다루라.** 특히 `max_tokens`를 `end_turn`으로 흘려보내면 미완성 결과가 조용히 완성품으로 둔갑합니다.
13. **모델의 신호를 주 조건으로 삼되, 안전망은 따로 둔다.** 반복 상한은 서킷 브레이커입니다.
14. **오류는 종료 신호가 아니라 추론 재료다.** `is_error`로 돌려주면 모델이 스스로 복구합니다.
15. **모델 교체는 소프트웨어 버그의 해법이 아니다.**

**컨텍스트와 구조**

16. **모델은 컨텍스트에 있는 것만 안다.** 히스토리 누락, 서브에이전트 컨텍스트 미상속, 서버리스 상태 유실은 모두 같은 원리의 변주입니다. 필요한 맥락은 명시적으로 넣어야 합니다.
17. **컨텍스트는 자산이자 부채.** 필요한 정보만 넣고 오래된 정보는 적극적으로 버립니다. 격리가 기본값입니다.
18. **컨텍스트가 커질수록 나눠라.** 한 번에 다 넣으면 맥락이 희석되어 디테일이 사라집니다. Map으로 깊이 파고 Reduce로 합치며, 초대형 규모면 대화 밖 Workflow로 뺍니다.
19. **구조가 정확도를 만든다.** 메타데이터와 콘텐츠를 분리하면 모델이 추측할 필요가 없어집니다. 핸드오프든 검증이든 필수 필드를 못 박으면 누락을 구조적으로 막습니다. **구조화 > 자유 형식.**
20. **투명성 우선.** 모르는 것을 아는 척 정리하지 말고, 상충·불확실·미완료 상태를 그대로 위로 올립니다.

**분해와 오케스트레이션**

21. **제어 흐름의 성질에 맞는 분해 패턴을 골라라.** 고정+의존이면 체인, 고정+독립이면 병렬, 단계를 미리 모르면 오케스트레이터-워커(동적/적응형). 고정 작업에 동적 오케스트레이터를 쓰면 낭비이고, 가변 작업에 고정 체인을 쓰면 막힙니다.
22. **독립 작업은 병렬로.** 총 시간이 "합"에서 "최장 하나"로 줄어듭니다.
23. **복잡성은 필요할 때만 도입하라.** 필요한 만큼만 실행하고, 정적 전체 파이프라인보다 입력에 따라 경로를 고르는 동적 라우팅을 씁니다.
24. **분해는 범위 전체를 먼저 덮어라.** 하위 작업으로 지정되지 않은 영역은 결과에서 통째로 사라집니다.
25. **코디네이터는 취합자이자 평가자다.** 결과의 갭을 찾아 표적 재위임합니다.
26. **중앙 허브를 우회하는 통신은 가시성을 죽인다.**

**세션과 상태**

27. **세션은 대화를 기억하지, 파일을 기억하지 않는다.** 파일 되돌리기에는 별도의 체크포인팅이, 파일 변경 반영에는 명시적 재조회가 필요합니다.
28. **재개(resume)는 맥락 보존의 기본기.** 다만 로컬 디스크가 없으면 성립하지 않습니다.
29. **원본을 오염시키지 않고 실험하려면 포크한다.** 포크는 새 세션이므로 세션 범위 권한은 따라오지 않습니다.
30. **필요할 때만 상태를 도입한다.** 원샷 작업에 세션 관리를 붙이는 것은 오버헤드입니다.
