# 시나리오5_고객지원

## 질문 1

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : You add a coordinator that delegates support subtasks to specialized subagents. A customer reports a duplicate charge, a missing loyalty discount, and unwanted auto-renewal. Logs show the coordinator spawned two subtasks, both addressing the duplicate charge; all subagents succeeded, yet the reply ignores the other issues. Which change most effectively fixes this?

**A.** Restructure the synthesis input so findings for each concern appear at the start of the aggregated context with explicit section headings.

**설명**

위치 인식 입력 방식은 lost-in-the-middle 현상으로 모델이 컨텍스트 중간부의 내용에 충분히 주의를 기울이지 못할 때 도움이 되지만, 이 실패 유형은 먼저 조사 결과가 존재해야 발생한다. 어떤 서브에이전트도 할인이나 해지 문제를 조사한 적이 없으므로, 합성 단계에서 재배치하거나 놓칠 수 있는 조사 결과 자체가 존재하지 않는다.

**B(정답).** Revise the coordinator's decomposition instructions so it enumerates every stated concern and delegates one bounded subtask per concern.

**설명**

이것이 정답이다. 로그를 보면 두 서브태스크 모두 중복 청구 문제만을 대상으로 했으며, 이는 코디네이터의 작업 분해가 고객 메시지의 전체 범위를 다루지 못했음을 의미한다. 모든 서브에이전트가 할당된 작업을 정확히 완료했으므로, 수정은 작업 분해 단계에서 이루어져야 하며, 코디네이터가 위임 전에 언급된 각 문제를 모두 다루도록 지시받아야 한다.

**C.** Rewrite overlapping tool descriptions so discount and cancellation subtasks are routed to subagents capable of handling them.

**설명**

잘못된 라우팅을 고치는 접근은 해당 문제들에 대한 서브태스크가 생성되어 잘못된 작업자에게 전달되었다는 전제를 깔고 있다. 그러나 로그에는 중복 청구 관련 서브태스크만 생성된 것으로 나타나므로, 도구 설명을 명확히 하는 것으로는 빠진 범위를 복구할 수 없다.

**D.** Pass the coordinator's full conversation history into each subagent's prompt so workers can see all of the customer's stated concerns.

**설명**

컨텍스트 격리는 실제로 존재하는 문제이지만, 여기서의 실패 원인은 아니다. 서브에이전트는 코디네이터가 위임한 작업만 처리하도록 되어 있으며, 할인과 해지 문제는 애초에 서브태스크로 전환된 적이 없으므로, 더 풍부한 컨텍스트를 전달한다고 해서 어떤 서브에이전트도 이 문제들을 다루게 되지는 않는다.

### 전반적인 설명

허브-스포크(오케스트레이터-워커) 아키텍처에서는 코디네이터가 작업 분해를 담당한다. 전체 요청을 읽고 이를 서브태스크로 나누어 각각 위임한 뒤 결과를 합성한다. 이 구조에서는 코디네이터의 작업 분해가 시스템이 다룰 수 있는 범위의 상한선을 결정한다. 어떤 문제가 서브태스크로 전환되지 않으면, 이후 단계(서브에이전트 실행, 컨텍스트 전달, 합성) 중 어느 것도 이를 복구할 수 없다. 이 단계들은 실제로 위임된 작업에 대해서만 동작하기 때문이다. 바로 그래서 이 진단 신호가 의미 있는 것이다. 모든 서브에이전트가 성공했음에도 커버리지가 불완전하다는 사실은 문제가 위임 단계 자체에 있음을 가리킨다.

Anthropic은 멀티에이전트 리서치 시스템 관련 문서에서 정확히 이런 실패 유형을 다루고 있다. 리드 에이전트의 작업 설명이 모호하거나 분할이 부실하면 서브에이전트들이 작업을 중복 수행하거나 공백을 남기게 되므로, 각 위임에는 명확한 목표, 출력 형식, 그리고 명시적인 작업 범위가 포함되어야 한다. 이 사례에서는 두 서브태스크 모두 중복 청구 문제를 대상으로 했는데, 이는 작업을 중복시키면서도 고객이 언급한 세 가지 문제 중 두 가지를 빠뜨리는 비효율적인 업무 분배다. 효과적인 수정은 코디네이터 수준에서 이루어져야 한다. 즉, 여러 문제가 섞인 메시지를 위임하기 전에 언급된 모든 사안을 다루는 개별 항목으로 분해하도록 지시해야 한다.

오답 선택지들은 모두 작업 분해 이후 단계에 개입한다. 더 풍부한 컨텍스트 전달은 이미 존재하는 서브태스크에만 의미가 있고, 합성 입력의 순서를 바꾸는 것은 이미 수집된 조사 결과만 드러낼 수 있으며, 더 명확한 도구 설명은 실제로 생성된 서브태스크의 라우팅만 개선한다. 이 시나리오처럼 코디네이터의 작업 분해 로그를 확인하는 것이 커버리지 실패와 실행 실패를 구분하는 표준적인 방법이다. How we built our multi-agent research system과 Building effective agents를 참고하라.

## 질문 2

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : Compliance auditors find the agent occasionally processes refunds for orders older than 90 days, despite explicit system prompt instructions forbidding this. These refunds cannot be reversed. Which design guarantees the policy while preserving autonomous handling of in-policy refunds?

**A.** Add a PostToolUse hook that detects refunds on orders past 90 days after execution and automatically issues a compensating reversal transaction.

**설명**

PostToolUse 훅은 도구가 이미 실행된 후에만 실행되므로, 금지된 환불이 훅이 이를 감지하기 전에 이미 실행되어 버린다. 시나리오에서는 이런 환불이 되돌릴 수 없다고 명시하고 있으므로, 사후 감지 방식으로는 컴플라이언스 요구사항을 충족할 수 없다.

**B.** Remove the process_refund tool from the agent's configured MCP tools entirely and instruct it to route every refund request to a human agent.

**설명**

도구를 제거하면 위반은 막을 수 있지만, 에이전트가 어떤 환불도 처리할 수 없게 되므로 정책에 부합하는 환불조차 인간에게 넘겨야 한다. 위반 대상 호출만 선별적으로 차단할 수 있는 표적화된 메커니즘이 존재하는 상황에서, 이는 정책에 맞는 환불을 자율적으로 유지해야 한다는 요구사항을 충족하지 못한다.

**C(정답).** Add a PreToolUse hook that blocks process_refund calls for orders past 90 days and redirects those cases to the escalate_to_human workflow.

**설명**

PreToolUse 훅은 도구가 실행되기 전에 코드로 동작하므로, 위반하는 환불 호출을 매번 결정론적으로 막을 수 있다. 차단된 사례를 에스컬레이션으로 리다이렉트하면 고객 문제 해결은 유지되면서도 모델이 정책을 우회할 수 없게 되며, 90일 이내의 환불은 계속 자율적으로 처리된다.

**D.** Move the 90-day rule into the process_refund tool description and reinforce it with few-shot refusal examples in the system prompt.

**설명**

도구 설명과 퓨샷 예시는 모델이 규칙을 따를 확률을 높이지만, 준수는 여전히 확률적일 뿐 보장되지 않는다. 감사관들의 조사 결과는 지침 기반 접근이 이미 간헐적으로 실패하고 있음을 보여주는데, 이는 바로 이 선택지가 없앨 수 없는 실패 유형이다.

### 전반적인 설명

여기서 시험하는 핵심 구분은 프로그램적 강제와 프롬프트 기반 지침의 차이다. 시스템 프롬프트나 도구 설명 속 지침은 모델의 토큰 단위 의사결정에 영향을 미치므로 확률적일 수밖에 없다. 즉, 준수율을 높일 수는 있지만 100%에 도달할 수는 없다. PreToolUse 훅은 도구 호출이 실행되기 전에 이를 가로채는 일반 코드다. 인자를 검사하고 주문일을 90일 기준과 비교하여 호출을 거부하면서, escalate_to_human 쪽으로 에이전트를 유도하는 메시지를 되돌려줄 수 있다. 이 검사가 모델 바깥에 존재하기 때문에, 어떤 특이한 표현이나 컨텍스트 드리프트, 추론 오류로도 위반 호출이 빠져나갈 수 없다.

지녀야 할 사고 모델은 훅과 프롬프트가 서로 다른 계층에서 작동한다는 것이다. 프롬프트는 모델이 무엇을 시도할지를 형성하고, 훅은 시스템이 무엇을 허용할지를 제약한다. 실패가 금전적, 법적, 안전상의 결과를 낳고 되돌릴 수 없는 경우, 그 보장은 강제 계층에 있어야 한다. 프롬프트는 확실성보다 유연성이 중요한 선호와 뉘앙스에 적합한 도구로 남는다.

타이밍이 바로 PostToolUse 방식이 여기서 실패하는 이유다. 이는 실행 후 결과를 관찰하는 방식으로, 데이터를 정규화하거나 후속 작업을 트리거하는 데는 유용하지만 행동 자체를 막을 수는 없으며, 문제 설명에서는 이 환불이 되돌릴 수 없다고 명시하고 있다. 에이전트가 설정한 MCP 도구 목록에서 process_refund 도구를 완전히 제거하는 것은 반대 방향의 과잉 대응이다. 이는 기능 자체를 없애버림으로써 보장을 얻는 방식인데, 그 결과 정책에 맞는 환불까지 포함한 모든 환불을 인간에게 넘기게 되어, 정책에 맞는 환불은 자율적으로 유지해야 한다는 요구사항을 충족하지 못한다. 훅은 위반 대상 부분집합만 정확히 차단하면서 정상 운영은 그대로 유지하는 설계다.

PreToolUse의 가로채기 및 차단 결정이 어떻게 작동하는지는 Claude Code hooks reference와 Get started with hooks를 참고하라.

## 질문 3

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : Handling a billing dispute, the coordinator calls get_customer and lookup_order, then spawns an analysis subagent prompted "Assess refund eligibility for this dispute." The subagent responds that no customer or order data was provided. How should you fix this?

**A.** Reference the tool_use IDs of the coordinator's earlier calls in the delegation prompt so the subagent can retrieve those results.

**설명**

서브에이전트가 tool_use ID로 부모의 도구 결과를 조회할 수 있는 메커니즘은 존재하지 않는다. 이 ID는 단일 대화 내에서 도구 호출과 도구 결과를 연결하는 용도일 뿐, 부모와 서브에이전트 간의 컨텍스트 간 조회 채널을 만들지는 않는다.

**B.** Add get_customer and lookup_order to the subagent's AgentDefinition allowed tools so it can access the retrieved records.

**설명**

도구 접근 권한은 서브에이전트가 할 수 있는 일을 통제할 뿐, 이미 알고 있는 것을 통제하지는 않는다. 이 도구들을 부여해도 서브에이전트는 여전히 코디네이터의 이전 도구 결과를 볼 수 없으며, 모든 것을 처음부터 다시 가져와야 한다. 이는 기존 조사 결과를 전달하는 것이 아니라 작업을 중복시킬 뿐이다.

**C.** Spawn the analysis subagent in a subsequent turn so the coordinator's completed tool results are forwarded along with its history.

**설명**

이런 지연 전달 메커니즘은 존재하지 않는다. Agent 도구는 같은 턴이든 이후 턴이든 부모의 대화 기록을 일반 서브에이전트에게 전달하지 않는다. 위임 프롬프트가 유일하게 문서화된 전달 채널이다.

**D(정답).** Include the retrieved customer and order data directly in the subagent's delegation prompt.

**설명**

이것이 정답이다. 포크가 아닌 서브에이전트는 새로운 컨텍스트 윈도우로 시작하며 부모의 대화 기록이나 이전 도구 결과를 전혀 보지 못한다. Agent 도구의 프롬프트 문자열이 코디네이터의 조사 결과를 전달하는 유일한 채널이므로, 고객 및 주문 정보는 그 프롬프트에 기재되어야만 서브에이전트에게 존재하게 된다.

### 전반적인 설명

지녀야 할 사고 모델은 서브에이전트가 코디네이터 대화의 연속이 아니라 별도의 에이전트 인스턴스라는 점이다. 코디네이터가 Agent 도구 호출을 발생시키면, 생성된 서브에이전트의 컨텍스트 윈도우는 새롭게 시작한다. 자신만의 시스템 프롬프트, 도구 정의, 그리고 위임 프롬프트 문자열은 받지만, get_customer와 lookup_order의 결과를 포함한 부모의 메시지 기록은 전혀 받지 못한다. "이 분쟁에 대한 환불 자격을 평가하라"와 같은 프롬프트는 서브에이전트가 실제로 본 적이 없는 자료를 가리키므로, 데이터가 제공되지 않았다고 보고하는 것이 맞다.

이 격리는 우회해야 할 한계가 아니라 의도적인 트레이드오프다. 각 서브에이전트의 중간 도구 호출과 방대한 출력을 자체 컨텍스트 안에 가두어 두면 코디네이터의 윈도우가 원시 레코드로 가득 차는 것을 막을 수 있고, 인수인계를 명시적이고 검사 가능하게 만든다. 대가는 코디네이터가 각 서브에이전트가 필요로 하는 것을 선별하여 프롬프트에 직접 담아야 한다는 것이며, 모호한 역참조보다는 구조화된 데이터(고객 ID, 주문 상세, 분쟁 사실) 형태가 이상적이다. 유일하게 문서화된 예외는 포크된 서브에이전트로, 이는 분기 지점까지의 부모 대화를 상속받는다. 일반적인 호출은 그렇지 않다.

오답 선택지들은 모두 동일한 근본적 이유로 틀렸다. 각각 부모와 서브에이전트 사이에 존재하지 않는 숨겨진 채널을 상상하고 있다. 턴 종료 시나 다음 턴에 기록을 전달하는 방식은 없고, 컨텍스트 간 tool_use ID 조회도 없으며, 서브에이전트에 MCP 도구를 부여해도 추가 비용을 들여 데이터를 다시 가져올 수만 있을 뿐 코디네이터의 기존 조사 결과를 전달하지는 못한다. 전체 상속 규칙은 Subagents in the SDK와 Create custom subagents를 참고하라.

## 질문 4

**QUESTION** : The team adds a weekly quality audit: every resolved refund case is checked against the same four criteria (identity verification, policy compliance, amount limits, tone), then results are combined into a summary. Which decomposition approach fits?

**A.** Have a coordinator spawn a subagent per case that iterates until it finds no remaining issues, then merge the subagent reports.

**설명**

반복적 정제 루프는 열린 형태의 리서치처럼 품질 공백을 발견하고 보완해야 하는 작업에 적합하다. 고정된 체크리스트 기반 감사는 네 가지 점검이 끝나면 완료 조건이 명확하므로, 열린 형태의 반복 루프는 이득 없이 비용과 비결정성만 추가한다.

**B(정답).** Use prompt chaining: run each case through the four checks in sequence, then a final pass that aggregates findings into the summary.

**설명**

이 감사는 완전히 예측 가능한 구조를 가진다. 모든 사례에 동일한 네 가지 기준이 적용되고, 모든 단계가 사전에 알려져 있다. 고정된 순차 파이프라인은 각 점검에 집중된 주의를 기울이게 하고, 검사 가능한 중간 출력을 만들어내며, 전용 집계 단계로 마무리된다. 이것이 바로 prompt chaining이 설계된 목적이다.

**C.** Use dynamic adaptive decomposition, letting the agent decide at runtime which checks each case needs based on what earlier steps reveal.

**설명**

적응형 분해는 작업의 범위가 불확실하고 각 단계가 이전 발견에 의존할 때 올바른 선택이다. 이 감사에는 그런 불확실성이 없다. 네 가지 기준이 모든 사례에 고정되어 있으므로, 런타임 적응성은 아무런 이득 없이 변동성과 오버헤드만 추가한다.

**D.** Send all cases and criteria in a single comprehensive request so the model can judge every case with the full audit context in view.

**설명**

여러 사례를 여러 기준에 대해 한 번에 처리하면 주의력 희석이 발생한다. 일부 사례는 철저하게 처리되지만 다른 사례는 얕거나 일관되지 않은 판단을 받게 된다. 작업을 집중된 단계들로 나누면 이 잘 알려진 실패 유형을 피할 수 있다.

### 전반적인 설명

Prompt chaining이란 작업을 순차적인 호출들로 나누어 각 단계가 하나의 집중된 임무를 수행하고 그 출력이 다음 단계로 흘러가도록 하는 것을 말한다. Anthropic의 가이드에서는 중간 출력을 검사해야 하거나 특정 파이프라인 구조를 강제해야 할 때 chaining이 유용하다고 언급하는데, 이는 정확히 반복적인 컴플라이언스 감사의 특성과 일치한다. 모든 사례가 동일한 네 가지 점검을 통과하며, 감사관들은 최종 요약뿐 아니라 항목별 결과도 확인해야 할 수 있다. 이 패턴은 다단계 코드 리뷰 방식, 즉 개별 항목 단위의 로컬 분석을 먼저 하고 별도의 집계 또는 통합 단계를 거치는 방식과 유사하다.

내재화해야 할 선택 규칙은 워크플로의 불확실성 정도가 분해 전략을 결정한다는 것이다. 모든 단계가 사전에 알려져 있고 입력 전반에 동일하다면, 고정된 파이프라인이 재현성, 각 점검의 일관된 깊이, 그리고 각 단계에 대한 쉬운 회귀 테스트를 제공한다. 동적 적응형 분해는 다음 단계가 실제로 이전 단계에서 발견한 것에 의존할 때, 예를 들어 열린 형태의 조사에서만 그 오버헤드를 감수할 가치가 있다. 이를 여기에 적용하면 이 작업에서 전혀 쓰이지 않는 유연성을 얻는 대가로 결정성을 잃게 된다.

다른 접근들은 메커니즘 측면에서 실패한다. 많은 사례와 기준을 하나의 종합적인 요청으로 처리하면 주의력 희석이 발생한다. 모델이 일부 사례는 깊이 있게 다루고 다른 사례는 얕게 다루게 되며, 한 사례에서는 특정 패턴을 문제로 지적하면서 다른 사례에서는 동일한 행동을 승인할 수도 있다. 사례별로 "문제가 남지 않을 때까지" 반복하는 서브에이전트는 고정된 완료 조건을 가진 작업에 반복 정제 루프를 도입하는 것이다. 체크리스트 자체가 완료를 정의하므로, 이 루프는 비용과 불명확한 종료 조건 문제만 추가할 뿐이다. 구조화된 파이프라인에서 chaining의 역할에 대한 문서화된 내용은 Anthropic의 prompt engineering guidance를 참고하라.

## 질문 5

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : Your custom agent loop built on the Messages API receives a billing-dispute response with stop_reason "tool_use" containing two tool_use blocks: get_customer and lookup_order. How should the loop return the outputs so the next iteration proceeds correctly?

**A(정답).** Execute both tools, then send a single user message with one tool_result block per call, each matched by tool_use_id.

**설명**

이것이 병렬 도구 호출에 대해 문서화된 프로토콜이다. 모든 tool_use 블록은 대응하는 tool_result를 받아야 하며, 이들은 모두 다음 user 메시지에서 함께 반환되고 tool_use_id로 연결된다. 그러면 Claude는 두 출력을 한 번에 보고 다음 턴에서 결합된 데이터를 바탕으로 추론할 수 있다.

**B.** Execute only the first requested tool and return its result; Claude will re-request the remaining tool on the next iteration.

**설명**

응답 내의 모든 tool_use 블록은 대화가 이어지기 전에 응답을 받아야 한다. 결과를 하나만 반환하면 해결되지 않은 tool_use id가 남게 되어 프로토콜 오류가 발생한다. Claude는 빠진 호출을 자동으로 다시 요청하지 않는다.

**C.** Execute both tools, then return the results in an assistant message, since tool outputs belong to Claude's turn of the history.

**설명**

도구 결과는 항상 user 메시지로 전송된다. Messages API에는 별도의 tool 역할이 없으며, assistant 메시지는 tool_use 요청을 포함해 Claude 자신이 생성한 콘텐츠만을 위해 예약되어 있다. 결과를 assistant 메시지에 넣으면 누가 그 콘텐츠를 생성했는지가 왜곡되고 교대 구조가 깨진다.

**D.** Execute both tools, then send two consecutive user messages, each carrying one tool_result, in the order the calls appeared.

**설명**

결과를 별도의 user 메시지들로 나누어 보내는 것은 메시지 형식 규칙을 위반한다. tool_result 블록은 중간에 다른 메시지가 끼지 않고 해당 tool_use 블록 바로 다음에 와야 한다. tool_use id 바로 다음에 tool_result가 없는 기록은 API가 거부한다.

### 전반적인 설명

Claude는 하나의 assistant 턴에서 여러 도구를 요청할 수 있으며, 이는 기본 동작이다. stop_reason이 "tool_use"인 응답은 각각 고유한 id, name, input을 가진 여러 tool_use 블록을 담을 수 있다. Messages API 위에 직접 루프를 구축할 때 지녀야 할 사고 모델은 일종의 계약이다. Claude는 구조화된 요청을 발생시키고, 여러분의 하니스가 이를 실행하며, 모든 요청에 대한 응답이 이루어지기 전까지는 대화가 진행될 수 없다. 두 도구를 동시에 실행하든 순차적으로 실행하든 그것은 전적으로 구현자의 선택이며, 프로토콜은 오직 결과가 어떻게 돌아오는지만 제약한다.

반환 형식에는 세 가지 확고한 규칙이 있다. 첫째, 결과는 user 메시지로 돌아간다. Messages API는 전용 tool 역할 대신 일반적인 교대 역할로 도구 교환을 모델링하기 때문이다. 둘째, 각 tool_result 블록은 원래 호출의 id를 tool_use_id로 그대로 반영해야 하며, 이것이 두 결과가 함께 도착했을 때 Claude가 고객 레코드를 get_customer에, 주문 데이터를 lookup_order에 각각 매칭하는 방법이다. 셋째, 순서가 중요하다. 도구 결과는 해당 tool_use 블록 바로 다음에 와야 하며, 그 user 메시지 내의 모든 tool_result 블록은 어떤 텍스트보다도 앞에 위치해야 한다. 이를 위반하면 "tool_use ids were found without tool_result blocks immediately after"와 같은 오류가 발생한다.

이 설계 때문에 병렬 호출이 실제로 지연 시간을 절약한다. 독립적인 조회들이 두 번의 왕복이 아니라 한 번의 왕복으로 완료되고, Claude는 이후 단일 턴에서 결합된 증거를 바탕으로 추론한다. 호출 하나에만 응답하거나, 결과를 여러 메시지에 나누거나, assistant 메시지에 결과를 넣는 것은 모두 API가 용인하지 않고 감지해내는 방식으로 계약을 깨는 행위다. 전체 형식 요구사항은 Parallel tool use와 Handle tool calls를 참고하라.

## 질문 6

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : You define a billing-investigation subagent with an AgentDefinition. It needs to read customer and order data, but must be structurally unable to call process_refund. Which configuration achieves this guarantee?

**A.** State in the subagent's description that it is a read-only billing investigator so refund work is never routed to it.

**설명**

description 필드는 Claude가 언제 서브에이전트에 위임할지를 안내할 뿐, 호출된 이후 서브에이전트가 할 수 있는 일을 제약하지는 않는다. 라우팅이 정확하더라도, 서브에이전트는 여전히 도구 세트에 process_refund를 보유하고 있어 이를 호출할 수 있다.

**B(정답).** Set the subagent's tools field to list only get_customer and lookup_order, leaving process_refund out of its tool set.

**설명**

AgentDefinition의 tools 필드는 사용 가능성 자체를 제한한다. 이 필드가 지정되면 서브에이전트는 나열된 도구만 받게 된다. 목록에 없는 도구는 그 서브에이전트의 세션에 아예 존재하지 않으므로, 모델이 무엇을 시도하든 process_refund는 결코 호출될 수 없다.

**C.** Remove process_refund from the top-level allowedTools list so any attempt to invoke it is rejected automatically.

**설명**

allowedTools는 자동 승인을 통제할 뿐 사용 가능성을 통제하지 않는다. allowedTools에 없는 도구도 여전히 호출될 수 있으며, 그 요청은 단지 권한 모드나 canUseTool 핸들러로 넘어갈 뿐이다. 따라서 이는 구조적으로 호출을 막지 못한다.

**D.** Add an instruction to the subagent's prompt stating that it must never call process_refund under any circumstances.

**설명**

프롬프트 지침은 확률적 준수를 제공할 뿐 보장을 제공하지 않는다. 모델은 여전히 그 도구를 사용할 수 있고 지침에도 불구하고 이를 호출할 수 있는데, 이것이 바로 설정 수준의 제한이 없애고자 하는 실패 유형이다.

### 전반적인 설명

AgentDefinition에는 description과 prompt라는 두 개의 필수 필드와 tools 같은 선택적 설정이 있다. 이들은 각기 아키텍처에서 다른 역할을 한다. description은 라우팅을 좌우하고(Claude가 이를 바탕으로 언제 위임할지 결정한다), prompt는 행동을 좌우하며(서브에이전트가 작업에 접근하는 방식), tools 필드는 역량을 좌우한다(물리적으로 가능한 행동이 무엇인지). 이 중 마지막 것만이 강제 메커니즘이다. tools가 지정되면 서브에이전트는 정확히 그 도구들만 받고 그 외에는 아무것도 받지 않는다. 목록에서 빠진 도구는 서브에이전트의 세션에 전혀 존재하지 않으므로, 가로챌 호출도 없고 내려야 할 권한 결정도 없다. tools가 생략되면 서브에이전트는 서브에이전트가 사용할 수 있는 모든 도구를 상속받는데, 이것이 환불 처리처럼 금전적 결과가 따르는 작업에서 명시적 제한이 중요한 이유다.

흔한 혼동은 AgentDefinition.tools와 최상위 allowedTools 옵션 사이에서 발생한다. 이름은 비슷한 동작을 암시하지만, allowedTools는 자동 승인 목록이다. 일치하는 도구는 권한 프롬프트 없이 실행되지만, 목록에 없는 도구는 여전히 호출 가능하며 단지 권한 모드나 canUseTool 콜백으로 넘어갈 뿐이다. 이는 모델의 접근 범위에서 도구를 결코 제거하지 않는다. 프롬프트 지침과 description 문구는 그보다 더 약하다. 둘 다 모델이 대개는 따르지만 놓칠 수도 있는 자연어 지침이며, 시험 자료에서는 이를 설정과 코드의 결정론적 보장과 대비되는 확률적 준수로 규정한다. 지녀야 할 사고 모델은 이렇다. 규칙이 매번 반드시 지켜져야 한다면 그 역량을 없애거나 코드로 게이트를 걸어야 하고, 규칙이 선호 사항이라면 프롬프트에 넣으면 된다.

AgentDefinition 필드와 도구 상속에 대해서는 Subagents in the SDK를, 사용 가능성 제한과 자동 승인의 구분에 대해서는 SDK permissions를 참고하라.

PreToolUse 훅은 도구 호출이 실행되기 전에 실행되므로, 호출을 결정론적으로 거부하고 사건을 인간 에스컬레이션 워크플로로 리다이렉트할 수 있다. 이것이 정책을 위반하는 환불을 단순히 관찰하는 것이 아니라 실제로 막을 수 있는 유일한 생명주기 시점이다.

**D.** Keep the PostToolUse hook but have it return a blocking exit code so the refund transaction is cancelled once the violation is detected.

**설명**

PostToolUse 훅은 도구가 이미 실행된 후에만 실행되므로, 이 훅이 발동될 시점에는 환불이 이미 백엔드에서 처리되어 있다. 그 시점의 차단 신호는 모델에게 정보를 되돌려줄 수는 있지만, 완료된 행동을 되돌리거나 취소할 수는 없다.

### 전반적인 설명

여기서의 결함은 훅을 사용했다는 사실 자체가 아니라, 도구 생명주기에서 그 훅을 배치한 위치에 있다. Claude Agent SDK와 Claude Code의 훅은 도구 실행 전후의 고정된 지점에서 발동한다. PreToolUse 훅은 도구 호출이 전달되기 전에 실행되어 이를 허용, 거부, 또는 수정할 수 있으며, PostToolUse 훅은 도구가 이미 성공적으로 실행된 후에만 실행된다. 이 타이밍 차이가 각 훅이 무엇을 보장할 수 있는지를 결정한다. 실행 전 가로채기는 정책을 위반하는 process_refund 호출이 백엔드에 도달하는 것을 막고 사건을 escalate_to_human으로 리다이렉트할 수 있지만, 실행 후 훅은 결과를 변형하거나 주석을 달고 모델에 피드백을 되돌려줄 수는 있어도 이미 완료된 행동을 관찰하는 것일 뿐이다.

아키텍트가 지녀야 할 사고 모델은 강제가 되돌릴 수 없는 사건보다 앞선 지점에 있어야 한다는 것이다. 환불은 금융상의 부작용이다. 백엔드가 이를 커밋하고 나면, 어떤 종료 코드나 차단 신호, 재작성된 도구 결과로도 이를 되돌릴 수 없다. PostToolUse에서 차단 코드를 반환하거나 실패 결과를 가짜로 만드는 것은 모델이 다음에 보게 될 내용만 바꿀 뿐이며, 실패를 가짜로 만드는 것은 오히려 해롭다. 에이전트의 컨텍스트가 실제 시스템 상태와 모순되어, 두 번째 환불을 발생시킬 수도 있기 때문이다. 스키마와 설명 변경은 가장 약한 선택지다. 이들은 모델의 행동을 확률적으로만 형성하는데, 이는 선호나 형식 지정에는 적합하지만 단 한 번의 실수가 금전적 결과를 낳는 컴플라이언스 규칙에는 적합하지 않다.

이 문제가 다루는 일반 규칙은 이렇다. 결과의 관찰과 정규화에는 PostToolUse를 사용하고, 절대 일어나서는 안 되는 일에는 PreToolUse를 사용하라. 생명주기 이벤트와 차단 동작에 대해서는 Claude Code hooks reference와 hooks guide를 참고하라.

**D.** Add a PostToolUse hook on process_refund that checks whether a verified customer ID was obtained and flags any refund issued without one.

### 전반적인 설명

Anthropic 문서에서는 이를 결정론적 통제라고 부른다. 이 검사는 모델이 무엇을 결정했든 상관없이 모든 호출에서 실행된다. 반면 PostToolUse 훅은 도구가 완료된 후에만 발동하므로, 결과 정규화나 감사 로깅에는 적합한 자리이지만 방지에는 너무 늦다. 이미 실행된 금융 거래는 훅으로 실행 취소할 수 없다.

이는 틀렸다. 프롬프트 문구로는 새로운, 재개되지 않은 인스턴스가 이전 인스턴스의 조사 결과를 볼 수 있게 만들 수 없기 때문이다. 호출들 사이에서 서브에이전트의 기록을 유지하는 것은 해당 서브에이전트를 재개함으로써 이루어지는 것이지, 시스템 프롬프트에 적어 넣은 지침으로 이루어지지 않는다.

### 전반적인 설명

지녀야 할 사고 모델은 새로운, 재개되지 않은 서브에이전트 호출이 상태 없는(stateless) 워커라는 것이다. 이런 Agent 도구 호출은 매번 새로운 컨텍스트 윈도우를 가진 해당 서브에이전트 유형의 새 인스턴스를 생성한다. 경계를 넘어 들어가는 유일한 내용은 위임 프롬프트 문자열이며, 돌아오는 것은 서브에이전트의 최종 메시지와 나중에 재개에 사용할 수 있는 에이전트 ID 같은 메타데이터다. 이전 호출의 중간 도구 호출, 추론, 조사 결과는 새 인스턴스에 도달하지 않으므로, "시작했던 분석을 계속하라" 같은 프롬프트는 새 인스턴스가 전혀 담고 있지 않은 기록을 가리키게 된다.

이 설계는 의도적이다. 컨텍스트 격리는 서브에이전트가 코디네이터의 윈도우를 오염시키지 않으면서 방대한 조사를 처리할 수 있게 해 주며, 병렬 생성을 안전하게 만들어 주는 요소이기도 하다. 그 대가는 코디네이터가 인수인계를 책임져야 한다는 것이다. 새로운 호출이 첫 번째 호출의 결론을 필요로 한다면, 코디네이터는 그 결론을 자신의 대화 안에 담아 두었다가 다음 위임 프롬프트에 붙여넣어야 하며, 이상적으로는 조사 결과와 메타데이터를 분리한 구조화된 형태로 전달해야 한다. SDK는 두 번째 경로도 제공한다. 기존 서브에이전트를 재개하는 것으로, 이전 도구 호출과 추론을 포함한 전체 대화 기록을 복원한다. 다만 이 시나리오는 새로운, 재개되지 않은 위임을 명시하고 있으므로, 명시적인 컨텍스트 전달이 올바른 해결책이다.

오답 선택지들은 모두 여기에 적용되지 않는 메커니즘을 상상하고 있다. tool use ID는 살아있는 인스턴스에 호출을 다시 연결하는 것이 아니라 호출과 결과를 짝짓는 용도다. "기억하라"는 시스템 프롬프트 지침은 재개를 대체할 수 없으며, 두 호출이 윈도우를 전혀 공유하지 않을 때 더 큰 컨텍스트 윈도우는 무관하다. 서브에이전트 컨텍스트가 어떻게 구성되고 무엇을 상속받으며 재개가 어떻게 작동하는지는 Subagents in the SDK와 Create custom subagents를 참고하라.

**SCENARIO** : You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : A customer message raises a defective-item refund, a duplicate billing charge, and a shipping address change. Logs show the agent resolves each concern in a separate sequential pass, calling get_customer again at the start of every pass. Which redesign best reduces loop count while protecting first-contact resolution?

**A.** Add a caching layer inside the MCP server so repeated get_customer calls return instantly without hitting the backend systems.

**설명**

캐싱은 반복되는 조회를 백엔드 입장에서 더 저렴하게 만들지만, 반복되는 호출 하나하나가 여전히 에이전트 루프에서 도구 사용 왕복 한 번을 차지하므로 루프 횟수와 지연 시간은 거의 변하지 않는다. 이는 중복 조회라는 증상만 다룰 뿐, 그것을 유발하는 순차적 조사 구조 자체는 재구성하지 못한다.

**B(정답).** Fetch customer context once, split the message into three concerns, investigate them in parallel against that shared data, then reply with one combined resolution.

**설명**

이 재설계는 작업 분해를 적용한다. 요청을 개별 항목으로 나누고, 모든 조사에서 공유 고객 컨텍스트를 한 번만 조회하여 재사용하며, 독립적인 읽기 전용 조회들을 동시에 실행하고, 하나의 통합된 응답으로 합성한다. 이는 중복된 get_customer 호출과 루프 횟수를 늘리는 순차적 조사 단계를 모두 제거하면서도, 여전히 한 번의 접촉으로 모든 것을 해결한다. 환불이나 주소 변경 같은 상태 변경 행동은 병렬이 아니라 여전히 순차적으로 실행된다.

**C.** Resolve only the highest-priority concern in this session and ask the customer to open separate requests for the remaining two items.

**설명**

고객이 이미 언급한 문제들을 미루면 접촉 횟수가 늘어나고 최초 접촉 해결 목표에 직접적인 타격을 준다. 에이전트는 세 가지 항목을 모두 처리할 능력이 있으며, 그렇게 하지 않는 것은 워크플로 비효율성을 더 나쁜 고객 경험과 맞바꾸는 것이다.

**D.** Create a composite get_customer_with_history tool that bundles profile, order, and billing data so each sequential investigation completes in one backend call.

**설명**

복합 도구는 각 단계당 호출 수를 줄이지만 문제별 순차 처리 구조는 그대로 남겨두므로, 에이전트는 여전히 세 번의 조사 사이클을 처음부터 끝까지 실행하게 된다. 또한 대부분의 요청이 필요로 하는 것보다 훨씬 많은 데이터를 반환하는 비대한 도구를 만들어내어, 워크플로 형태를 고치지 못하면서 컨텍스트 노이즈만 추가한다.

### 전반적인 설명

이런 요청에 대한 사고 모델은 세 부분으로 이루어진다. 메시지를 개별 항목으로 분해하고, 모든 항목이 필요로 하는 컨텍스트를 공유하며(고객 레코드는 문제당 한 번이 아니라 전체에서 한 번만 조회한다), 하나의 통합된 답변으로 합성하기 전에 병렬로 조사한다. 각 부분은 서로 다른 비효율을 공격한다. 분해는 에이전트가 문제들을 뒤섞는 것을 방지하고, 공유 컨텍스트는 중복된 도구 호출을 없애며, 병렬성은 세 번의 순차적 조사 사이클을 겹치는 사이클로 축소하고, 합성은 고객 경험을 하나의 완결된 답변으로 유지하여 최초 접촉 해결을 보호한다. 이는 문서에서 하나의 이름이 붙은 패턴은 아니지만, 문서화된 작업 분해 개념 및 Agent SDK가 실제로 도구를 실행하는 방식과 일치한다.

병렬성에는 중요한 경계가 있다. Agent SDK 에이전트 루프 내에서 읽기 전용 도구들은 동시에 실행될 수 있으며, 하나의 assistant 턴이 여러 독립적인 조회를 한 번에 요청할 수 있으므로, 이미 조회해 둔 고객 컨텍스트를 대상으로 한 조사들은 실제로 시간상 겹치게 된다. 반면 상태를 변경하는 도구는 순차적으로 실행되므로, 환불 처리나 배송지 변경 같은 행동은 조사와 함께가 아니라 조사 이후에 이루어져야 한다. 더 큰 규모의 분해에서는 서브에이전트가 컨텍스트 격리를 더해 같은 아이디어를 확장하지만, 공유 데이터에 대한 세 번의 조회 정도라면 메인 루프 안에서의 병렬 도구 호출로 충분하다.

오답 선택지들은 각각 잘못된 계층을 고치고 있다. 복합 도구와 캐싱 계층 모두 중복된 조회의 비용을 최적화할 뿐, 문제별 순차 처리 구조와 그로 인한 루프 횟수는 그대로 남겨둔다. 캐싱된 호출도 여전히 루프를 거치는 왕복 전체를 소비한다. 세 가지 문제 중 두 가지를 이후 세션으로 미루는 것은 작업을 없앰으로써 비효율을 제거하는 것이며, 이는 시스템이 달성해야 할 해결 목표 자체를 희생시킨다.

Your target is 80%+ first-contact resolution while knowing when to escalate.

**QUESTION** : You add a refinement loop: the coordinator evaluates each draft resolution for completeness and re-delegates investigation for any flagged gaps. In testing, policy-ambiguous disputes cycle indefinitely because re-investigation never closes the evaluator's flagged gaps. How should you bound this loop?

**A.** Raise the tool-call budget for each re-delegated investigation so the subagents eventually surface the missing information.

**설명**

더 큰 도구 호출 예산은 정보가 존재하지만 아직 찾지 못했을 때만 도움이 된다. 문제 설명에서는 공백이 정책의 모호함에서 비롯된다고 명시하므로, 추가 검색으로는 이를 해결할 수 없고 루프는 계속 순환한다.

**B.** Relax the evaluator's completeness criteria on each pass so drafts eventually satisfy the check and the loop terminates.

**설명**

완결성의 정의를 점진적으로 완화하면 품질을 낮추는 방식으로 종료를 보장하게 되며, 이는 평가 단계의 목적 자체를 무력화한다. 루프는 불완전한 해결책을 해결하거나 에스컬레이션하는 것이 아니라 완전하다고 선언함으로써 끝나게 된다.

**C.** Disable the completeness evaluation for dispute cases and return the first draft resolution directly to the customer.

**설명**

평가 단계를 제거하면 불완전한 해결책을 잡아내는 품질 관리 자체를 없앰으로써 순환을 없앤다. 모호함이 높은 분쟁에서 초안 그대로의 답변은 문제를 놓치고 최초 접촉 해결에 해를 끼칠 가능성이 가장 높은 사례들이다.

**D(정답).** Cap refinement iterations, and if gaps persist at the cap, escalate to a human with a summary of the unresolved gaps.

**설명**

반복 횟수 상한은 무한한 평가-재위임 순환을 유한한 것으로 바꾸며, 그 공백이 어떤 재조사로도 해결할 수 없는 누락되거나 모호한 정책을 반영할 때 에스컬레이션이 올바른 탈출구가 된다. 미해결 상태로 남은 것에 대한 구조화된 요약을 전달하면 사건을 다시 시작하도록 강제하는 대신 인간에게 자기완결적인 인수인계를 제공하게 된다.

### 전반적인 설명

반복적 정제 루프는 품질 메커니즘이다. 평가자가 완결성 기준에 대해 출력을 검사하고, 발견된 구체적인 공백에 대해 작업이 재위임되며, 기준을 충족할 때까지 출력이 다시 생성된다. 핵심 에이전틱 루프와 마찬가지로 이 역시 원칙에 기반한 종료 설계가 필요하다. 정상 경로는 평가자가 커버리지가 충분하다고 확인할 때 종료되고, 비정상 경로는 유한한 탈출구가 필요하다. 일부 공백은 에이전트가 해결할 수 없기 때문이다. 회사 정책이 특정 분쟁에 대해 침묵하거나 모호할 때, 어떤 재위임 조사도 빠진 답을 만들어낼 수 없으므로, 상한 없는 루프는 동일한 조사 결과를 반복하며 토큰을 소모한 채 영원히 순환하게 된다.

올바른 설계는 반복 횟수 상한을 안전밸브로 취급하고 여기에 의미 있는 폴백을 짝지운다. 공백이 남은 채로 상한에 도달하는 것 자체가 에스컬레이션 트리거가 된다. 무엇이 해결되었고 무엇이 미해결로 남았는지에 대한 구조화된 요약과 함께 사건을 인간에게 넘기는 것은 완료된 조사를 보존하면서 언제 에스컬레이션해야 하는지 아는 것이라는 시스템의 명시된 목표와 부합한다. 이는 인수인계를 받는 인간이 전체 기록을 갖고 있지 않아 사건 상태에 대한 자기완결적인 설명이 필요한, 더 넓은 구조화된 인수인계 패턴과 맞닿아 있다.

오답 선택지들은 각각 루프의 잘못된 지점을 고치고 있다. 조사 예산을 늘리는 것은 공백이 정책 문제인데도 검색 문제라고 가정한다. 각 회차마다 기준을 완화하는 것은 평가자가 불완전한 작업을 승인하는 쪽으로 수렴하게 만들어, 루프가 품질에 대해 거짓말을 함으로써 종료되게 만든다. 평가를 완전히 제거하는 것은 정제 패턴 자체를 버리고 가장 어려운 사례들에 대해 검증되지 않은 초안을 그대로 내보내는 것이다. evaluator-optimizer 워크플로에 대한 Anthropic의 가이드는 Building Effective Agents를, 위임 메커니즘은 Agent SDK의 subagents 문서를 참고하라.

### 전반적인 설명

이 상황을 결정짓는 사고 모델은 세션이 실제로 무엇인가라는 것이다. Claude Agent SDK에서 세션은 지속된 대화 기록이다. 즉 프롬프트, 도구 호출, 도구 결과, 응답이 나중에 작업을 이어갈 수 있도록 디스크에 기록된 것이다. 문서에서는 세션이 대화를 지속시키는 것이지 파일시스템이나 백엔드 상태를 지속시키는 것이 아니라고 명시하고 있다. 따라서 재개란 세계가 현재 어떤 모습인지를 보여주는 스냅샷이 아니라 에이전트가 본 것을 재생하는 것이다. Agent SDK sessions를 참고하라.

여기에는 두 가지 실질적인 결과가 따른다. 첫째, 재개 시 이전 도구 결과를 재검증하는 절차가 없다. 어제 기록된 lookup_order 응답은 기록된 그대로 컨텍스트에 다시 들어오며, 모델은 이를 현재 사실로 취급한다. 둘째, 재개할지 새로 시작할지의 결정은 그 기록된 증거 중 얼마나 많은 부분이 여전히 유효한지에 달려 있다. 알려진 한정된 범위의 레코드만 변경되었을 때는 재개하여 무엇이 변경되었는지 명시적으로 언급하고 에이전트가 그 레코드들만 다시 가져오도록 지시하는 것이 효율적인 방법이다. 확인된 신원, 근본 원인 추론, 영향받지 않은 주문 데이터를 포함한 조사의 나머지 컨텍스트는 계속 그 가치를 유지한다. 광범위한 변경이 저장된 도구 결과 대부분을 무효화할 때만 신뢰할 수 있는 방법이 구조화된 요약으로 시작하는 새 세션으로 바뀐다.

오답 선택지들은 동일한 근본 메커니즘에서 실패한다. 여기서 새 세션을 시작하는 것은 대부분 유효한 조사를 폐기하고 단 두 개의 레코드를 위해 모든 것을 다시 발견하도록 에이전트에게 강요한다. 이는 잘못된 상황에 맞는 올바른 도구다. 그대로 재개하는 것은 존재하지 않는 자동 노후화 검사를 가정한다. 에이전트에게는 자신의 기록 속 두 항목이 더 이상 백엔드와 일치하지 않는다는 신호가 없으며, 그것들을 다시 다룰 일이 전혀 없을 수도 있다. 아키텍트의 임무는 복구 전략을 변경 범위에 맞추는 것이며, 두 레코드의 정정을 위해서는 재개된 세션에 이를 알리고 변경된 부분만 다시 분석하는 것이 그 방법이다.

고객 지원 해결책에서의 공백은 주문 상태나 결제 기록 같은 고객별 사실에 관한 것이며, 이는 반드시 백엔드 시스템에 대한 도구 호출에서 나와야 한다. 이를 일반 지식으로 채우면 근거가 없고 잠재적으로 잘못된 약속을 고객에게 하게 된다.

### 전반적인 설명

반복적 정제 루프에는 세 가지 움직이는 부분이 있다. 명시적인 완결성 기준에 대해 초안을 비교하는 평가자, 구체적인 공백을 표적으로 후속 작업을 발송하는 표적화된 재위임, 그리고 다시 평가하기 전에 새로운 조사 결과를 새 초안에 접어 넣는 재합성 단계다. 여기서 설명된 실패, 즉 일반적인 후속 조사 결과와 반복되는 누락은 두 번째와 세 번째 부분의 파손을 가리킨다.

재위임의 파손은 Claude Agent SDK의 서브에이전트가 가진 핵심 속성에서 비롯된다. 각 서브에이전트는 자체 격리된 컨텍스트에서 실행되며 코디네이터로부터는 부여된 프롬프트 외에 아무것도 받지 못한다. 도움이 되는 사고 모델은 이렇다. 코디네이터가 프롬프트에 넣지 않았다면, 그것은 그 서브에이전트에게 존재하지 않는 것이다. 따라서 재위임 프롬프트는 평가자의 구체적인 공백 설명과 이미 수집된 관련 조사 결과를 함께 담아야 하며, 그래야만 서브에이전트가 실제로 빠진 것을 향해 도구 호출을 조준할 수 있다. 이 격리는 의도적인 설계상의 트레이드오프로, 명시적인 인수인계를 요구하는 대가로 방대한 조사가 코디네이터의 컨텍스트 윈도우 밖에 머물게 한다. 코디네이터의 기록에 대한 공유 접근을 제안하는 오답 선택지는 이 아키텍처가 의도적으로 제공하지 않는 메커니즘을 상상하고 있다.

재합성의 파손은 더 미묘하다. 완벽한 후속 조사 결과라 할지라도, 코디네이터가 기존 자료와 새 자료를 합쳐 합성을 다시 호출하고 병합된 초안을 다시 검사하지 않는다면 아무것도 바뀌지 않는다. 수리와 재검사 순환 없는 탐지는 측정일 뿐 정제가 아니다. 평가자가 공백을 메우기 위해 내용을 지어내도록 하는 것은 더 나쁘다. 고객 지원 해결책은 오직 백엔드 도구만이 확인할 수 있는 고객별 사실(주문 상태, 결제 기록, 환불 자격)에 의존하기 때문이며, 조작된 정책 세부사항은 최초 접촉 해결 품질을 직접적으로 위협한다.

컨텍스트 격리 모델과 evaluator-optimizer 루프 패턴에 대해서는 Create custom subagents와 Anthropic의 Building effective agents를 참고하라.
