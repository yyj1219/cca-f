# 5. 세션 관리와 CLI 실행

이 장에서 다루는 것:

- 세션과 트랜스크립트: 무엇을 저장하고 무엇을 저장하지 않는가
- 세션을 되살리는 세 가지 방식 — Continue / Resume / Fork
- 재개가 실패하는 이유 (머신, 작업 디렉터리, 상태 비저장 환경)
- 스테일 컨텍스트와 컨텍스트 오염, 그리고 대응 전략
- 세션 범위 권한과 포크의 관계
- 서브에이전트 컨텍스트 격리
- 슬래시 명령어(`/fork`, `/resume`, `/clear`, `/compact`, `/rename`)
- CLI 플래그와 자주 나오는 설정 값
- 세션 조회 API와 다중 사용자 세션 관리
- 세션 관리의 적정량 — 과잉 설계 피하기

## 5.1 세션(Session)과 트랜스크립트(Transcript)

**세션(Session)** 은 하나의 대화 흐름 전체를 담는 단위입니다. 주고받은 메시지, 도구 호출과 그 결과, 읽은 파일 내용 등 누적된 컨텍스트가 모두 여기 들어갑니다. 각 세션에는 고유한 **세션 ID**가 부여되고, 그 대화의 전체 기록을 **트랜스크립트(transcript)** 라고 부릅니다.

**가장 중요한 사실: 트랜스크립트는 중앙 서버가 아니라 실행 머신의 로컬 디스크에 저장됩니다.** 일반적으로 `~/.claude/` 아래에 `.jsonl` 같은 파일로 놓입니다. 즉 세션 기록은 **그 머신에 묶인 파일**입니다. 이 한 문장이 뒤에 나오는 재개 실패 사례 대부분을 설명합니다.

세션이 있어서 "어제 하던 조사"를 오늘 이어서 할 수 있습니다.

### 세션이 보존하는 것과 보존하지 않는 것

여기 반드시 알아야 할 경계선이 있습니다.

> **세션은 "대화 이력(conversation history)"을 저장합니다. "파일 시스템의 스냅샷"을 저장하지 않습니다.**

세션 중간에 에이전트가 어떤 파일을 수정했다면, 그 파일의 **예전 내용은 어디에도 보관되지 않습니다**. 세션을 재개해서 "아까 그 상태로 파일을 되돌려줘"라고 요청해도, 에이전트가 볼 수 있는 것은 디스크에 있는 **현재의 수정된 내용**뿐입니다.

(대화 이력에 예전 Read 결과가 텍스트로 남아 있을 수는 있지만, 그것은 우연한 부산물이지 신뢰할 수 있는 복원 메커니즘이 아닙니다.)

**파일을 되돌리고 싶다면 별도의 체크포인팅(checkpointing) 메커니즘이 필요합니다** — Git 커밋/연동, 스냅샷, 전용 파일 체크포인터, 백업 복사본 등. 이것은 에이전트 프레임워크가 아니라 개발자가 직접 마련해야 하는 부분입니다.

**흔한 오해 정정:**

- "세션 ID를 올바르게 썼다면 파일 내용이 자동 복원됐을 것이다" → 아닙니다. ID가 맞아도 세션 저장 메커니즘에 파일 스냅샷 복원 기능 **자체가 없습니다**.
- "`fork_session`을 썼으면 파일 예전 상태가 보존됐을 것이다" → 아닙니다. fork는 **대화 맥락**을 분기하는 기능이지 파일 시스템을 캡처하는 도구가 아닙니다.
- "읽기 도구의 캐싱 범위 문제다" → 아닙니다. **세션 영속성의 범위가 애초에 '대화 이력'으로 한정**되어 있는 것입니다.

## 5.2 세션을 되살리는 세 가지 방식

| 방식 | 의미 | 특징 |
|---|---|---|
| **Continue** (`claude --continue`, `continue_conversation=True`) | **현재 작업 디렉터리의 가장 최근** 세션을 자동으로 이어감 | ID 몰라도 됨. 하지만 "최근"이 누구 것인지 특정 불가 |
| **Resume** (`claude --resume <id\|name>`, `resume=<id>`) | **지정한 그 세션**의 이력을 불러와 이어감 | 정확한 대상 지정. 여러 세션이 공존해도 안전. 원본 세션이 계속 자란다 |
| **Fork** (`--fork-session`, `fork_session=True`) | 현재까지의 이력을 **복사해 새 세션 ID**를 만들고 거기서 진행 | 원본은 그대로 보존. 갈래를 나눠 실험할 때 |

여기에 "새 세션 시작"(아무 이력 없이 처음부터)을 더하면 세션을 다루는 기본 연산 네 가지가 됩니다.

`claude --resume`을 인자 없이 실행하면 **세션 선택기(session picker)** 라는 대화형 UI가 떠서 사람이 목록에서 골라야 합니다. 반대로 `claude --resume payment-retry-bug`처럼 이름이나 ID를 인자로 주면 선택기를 거치지 않고 곧바로 그 세션이 열립니다. 세션 선택기는 **사람이 터미널에서 쓰는 UI**이므로, 자동화된 백엔드 서비스가 프로그래밍적으로 쓸 수단이 아닙니다.

### Resume vs Fork — 이력의 모양이 다르다

둘 다 "기존 세션에서 이어간다"는 점은 같지만, 결과로 만들어지는 이력의 모양이 다릅니다.

**Resume (재개)**: 같은 세션 ID에 계속 **이어 붙입니다**. 하나의 일직선 이력(single shared history)이 됩니다.

```
[원래 분석] → [탐색 1: 캐싱] → [탐색 2: 큐잉]
                                  ↑ 여기서는 탐색 1의 내용을 다 보고 있음
```

**Fork (분기)**: 지금까지의 이력을 복제해서 **독립된 새 갈래**를 만듭니다.

```
                ┌→ [탐색 A: 캐싱]     (서로를 보지 못함)
[원래 분석] ────┤
                └→ [탐색 B: 큐잉]
```

**전형적인 실수**: "같은 분석 세션을 두 번 resume해서 캐싱 접근법과 큐잉 접근법을 각각 독립적으로 탐색하자."

이것은 **독립적인 탐색이 되지 않습니다**. 두 탐색이 하나의 공유 이력에 순차적으로 쌓이므로, 두 번째 탐색(큐잉)은 첫 번째 탐색(캐싱)의 내용을 이미 보고 있고 그것에 오염(편향)됩니다. 진짜 독립적인 두 갈래를 원한다면 **fork** 를 써야 합니다.

**resume 관련 오해 정정:**

- "resume은 세션 ID당 한 번만 호출할 수 있다" → 아닙니다. 여러 번 호출 가능하며, 두 번째 호출이 에러로 실패하지 않습니다. 단지 같은 이력 라인 뒤에 계속 덧붙을 뿐입니다.
- "resume은 이전 도구 결과를 조용히 폐기한다" → 아닙니다. 이전 대화 이력과 도구 결과를 **모두 보존**해서 전달합니다.

## 5.3 세션 포크(Session Forking)

포크는 "누적된 컨텍스트는 그대로 쓰되, 원본은 오염시키지 않고 대안을 탐색"하고 싶을 때 쓰는 도구입니다. **git의 브랜치와 같은 개념**입니다.

```
[분석 세션: 테스트 스위트 분석 완료]   ← 원본 보존
        ├── fork → 브랜치 1: extract-service 전략 탐색
        └── fork → 브랜치 2: strangler-fig 전략 탐색
```

**전형적 시나리오**: 어떤 세션이 인증 모듈을 깊이 분석해서 JWT 기반 재설계안을 만들었다. 이제 같은 분석 결과를 출발점으로 OAuth2 기반 설계도 탐색해보고 싶다. 단, 나중에 JWT 스레드를 **변경 없이 그대로** 재개할 수 있어야 한다.

→ **포크를 활성화해서 세션을 재개**합니다. 현재 이력이 새 세션 ID로 복사되고, OAuth2 탐색은 그 새 세션에 쌓입니다. 원본 JWT 세션은 손대지 않은 채 남습니다.

**언제 쓰나**: 동일한 베이스라인 맥락에서 **서로 오염되면 안 되는 여러 갈래 실험**을 할 때. 같은 분석 세션을 `fork_session`을 켠 채로 두 번 재개하면, 공유 베이스라인을 가진 독립적인 두 브랜치가 생깁니다.

**부적절한 대안들:**

- **완전히 새 세션에 요약본만 붙여넣기** → 누적된 깊은 분석 컨텍스트(왜 그런 결론에 이르렀는지, 어떤 코드를 봤는지)를 잃습니다. 기억(수동 요약)에 의존하면 정교한 맥락과 데이터가 누락되고 비효율적입니다.
- **원본 세션에서 그냥 OAuth2를 물어본 뒤 나중에 "무시해줘"라고 하기** → 이미 컨텍스트가 오염되었습니다. 대화 이력은 되돌릴 수 없고, "무시하라"는 지시가 완벽히 지켜진다는 보장도 없습니다.
- **한 대화 안에서 두 전략 프롬프트를 번갈아 입력** → 맥락이 뒤섞이는 **교차 오염(cross-contamination)**.
- **재개 → 전략 1 완료 → `/clear` → 다시 재개** → `/clear`는 대화 맥락을 **초기화**하므로 같은 베이스라인에서 시작할 수 없습니다.
- **그냥 최근 세션을 이어가면서 알아서 브랜치가 갈릴 것이라 기대하기** → 새 주제가 나왔다고 시스템이 자동으로 브랜치를 만들지 않습니다. 포크는 **명시적으로** 요청해야 합니다.

## 5.4 재개가 실패하는 대표 원인

`claude --resume <session-id>`는 세션 ID에 해당하는 **로컬 트랜스크립트 파일을 찾아 읽어** 대화를 이어갑니다. 파일을 찾지 못하면 이전 기록 없이 새 세션처럼 동작합니다. 그래서 실패 원인은 거의 항상 "파일이 거기 없다"입니다.

**(1) 머신이 다르다 — 파일이 그 머신에 없다**

CI 환경에서 자주 겪는 문제입니다. 일회성(ephemeral) 빌드 머신에서 세션을 만들었다가 다른 워커에서 같은 세션 ID로 `--resume`을 하면 완전히 빈 세션이 나옵니다. 원본 머신의 트랜스크립트 파일이 새 워커로 복사된 적이 없기 때문입니다. 컨테이너·VM이 종료되면 그 디스크는 함께 사라지거나 분리됩니다.

해결하려면 **트랜스크립트 파일이나 세션 상태 아티팩트를 명시적으로 저장·전달**해야 합니다 (CI 아티팩트, 공유 볼륨 등).

**(2) 작업 디렉터리가 다르다**

같은 머신이라도, CLI는 **실행된 작업 디렉터리(working directory)를 기준으로 프로젝트 컨텍스트와 세션 기록을 관리**합니다. 세션 저장소가 프로젝트 경로별로 분리되어 있기 때문에, 다른 디렉터리에서 같은 세션 ID로 `--resume`을 하면 해당 경로 기준 저장소에서 기록을 못 찾아 빈 세션이 됩니다.

세션 ID가 확실히 맞는데도 기억이 없다면, **원래 세션을 시작했던 디렉터리에서 실행했는지 가장 먼저 확인**하십시오.

**재개 실패의 원인이 *아닌* 것들:**

- CI 환경이라 대화형 세션 재개가 금지된다 → 그런 정책은 없습니다.
- 세션 이름이 너무 길어 조회가 실패했다 → 조회 실패는 파일 부재가 원인입니다.
- 재개할 때 준 프롬프트가 원본과 달랐다 → 새 지시를 줘도 이전 기록은 유지되어야 정상입니다.
- 최대 턴 수나 예산 한도 초과로 끝났다 → 한도로 종료돼도 트랜스크립트는 남습니다. 기록이 통째로 없어지지 않습니다.
- 원래 실행자의 도구 권한이 부족했다 → 권한은 세션 기록의 저장·재개와 무관합니다.

### 상태 비저장(Stateless) 환경: 세션이 아예 안 통할 때

서버리스 파이프라인처럼 각 단계가 **매번 새로 뜨고 곧 사라지는 컨테이너**에서 실행되고 이전 컨테이너의 로컬 디스크에 접근할 수 없다면, 세션 재개의 전제 자체가 무너집니다. resume도 fork도 continue도 **모두 로컬 디스크에 트랜스크립트 파일이 존재해야** 동작합니다. 세션 ID만 들고 가봐야 읽을 파일이 없습니다.

이때의 해법은 세션 기능이 아니라 **애플리케이션 레벨 상태 전달**입니다.

1. 앞 단계가 끝나면 **핵심 결과·결론만 추출**해 외부 저장소나 파이프라인 변수(application state)에 저장한다.
2. 다음 컨테이너에서는 **새 세션을 시작**하고, 그 결과를 **첫 프롬프트에 함께 넣어** 준다.

이는 "모델은 컨텍스트에 있는 것만 안다"의 직접적 응용입니다. 전달 수단이 없으면 직접 텍스트로 넣어 주는 것이 유일한 방법입니다.

## 5.5 스테일(Stale) 컨텍스트와 컨텍스트 오염

**스테일(Stale)** 하다는 것은 저장된 정보가 **더 이상 현실과 맞지 않는다**는 뜻입니다.

전형적 상황: 이전 세션에서 대규모 코드베이스를 수십 턴에 걸쳐 읽고 상호 참조했는데, 그 이후에 코드가 대대적으로 리팩토링되었습니다. 세션 기록 속의 파일 내용, 함수 위치, 구조 파악은 전부 **옛날 코드**의 것입니다.

이 기록을 그대로 안고 작업을 재개하면 **컨텍스트 오염(Context Pollution)** 이 일어납니다. 모델은 대화 기록에 있는 내용을 사실로 간주하므로, 이미 사라진 함수를 호출하려 하거나 존재하지 않는 파일 경로를 참조하는 잘못된 전제 위에서 추론합니다.

더 좁은 형태로는 **캐시 오염**이 있습니다. 과거 세션에서 `CLAUDE.md`나 에이전트 정의 파일을 읽었다면, 그 **읽은 시점의 내용이 대화 이력 안에 텍스트로 박혀** 있습니다. 그 뒤 다른 엔지니어가 별도 브랜치에서 그 파일을 대폭 고쳐 머지했다면 —

- 디스크의 실제 파일: **새 내용**
- 세션 맥락 안의 내용: **며칠 전의 낡은 내용**

재개했다고 해서 이 낡은 텍스트가 자동으로 갱신되지 않습니다. 그대로 믿으면 환각과 잘못된 분석이 나옵니다.

### 대응 전략 — 상황에 따라 답이 다르다

핵심 판단 기준은 **"축적된 추론을 보존해야 하는가"** 입니다.

**상황 A: 일부 파일만 바뀌었고, 축적된 추론은 반드시 지켜야 한다**

세션을 재개하면 이전의 메시지, 도구 호출 이력, 그리고 그 위에 쌓인 **축적된 추론(accumulated reasoning)** 이 온전히 살아납니다. 이것이 resume의 최대 가치입니다.

→ **세션을 재개하되, 에이전트에게 그 파일이 변경되었음을 명시적으로 알려 다시 읽게(re-read) 합니다.** 그러면 축적된 추론은 보존한 채 해당 파일의 캐시만 최신화됩니다. 두 요구사항(추론 보존 + 변경 반영)을 동시에 만족하는 방법입니다.

효과 없는 대안:

- 그냥 재개하고 캐시된 이해를 믿는다 → 낡은 내용 기반 오작동·환각.
- 재개 후 `/compact` 실행 → `/compact`는 대화 이력을 **요약·압축**하는 기능일 뿐, 외부 파일의 최신 내용을 읽어오지 않습니다.
- 새 세션을 열고 이전 세션의 요약본을 넘긴다 → 요약 과정에서 상세한 추론 맥락이 **손실(context loss)** 됩니다. "축적된 추론 보존" 요구를 못 지킵니다.

**상황 B: 코드베이스가 대대적으로 바뀌어 옛 기록이 통째로 무의미하다**

이때는 이어가기 전략을 비교해 보아야 합니다.

| 전략 | 의미 | 이 상황에서의 문제 |
|---|---|---|
| **Resume** (재개) | 이전 세션을 그대로 열어 모든 기록을 물려받음 | 스테일한 도구 결과를 전부 상속 → 잘못된 답 생성 |
| **Fork** (분기) | 이전 세션을 복제해 별도 갈래로 진행 | 복제해도 스테일한 히스토리는 그대로 따라옴 |
| **Resume + `/clear`** | 재개한 뒤 컨텍스트 창을 비움 | 결과적으로 빈 상태가 되지만, 굳이 재개했다가 지우는 불필요한 우회. 세션 관리 오버헤드만 생김 |
| **Fresh Session + 요약 주입** | 새 세션을 열고 미리 정리해 둔 구조화 요약본을 첫 프롬프트로 넣음 | **가장 신뢰할 수 있는 방법** |

**Fresh Session Injection**이 표준인 이유:

- 스테일한 중간 도구 호출 기록이 애초에 들어오지 않으므로 오염 가능성이 0입니다.
- 필요한 것(검증된 결론)만 들어가므로 토큰도 절약됩니다.
- 모델이 최신·정제된 전제 위에서만 추론합니다.

전제 조건은 **최종 결론이 이미 구조화된 형태로 정리되어 있어야 한다**는 것입니다. 진행 상황 노트(progress notes)나 요약 문서(summary document)가 그 역할을 합니다. 그래서 긴 작업을 할 때는 중간중간 결론을 별도 문서에 남겨두는 습관이 중요합니다. 그 문서가 다음 세션의 "씨앗"이 됩니다.

> **상황 A와 B가 서로 모순되는 것이 아닙니다.** A는 "정교한 추론 맥락이 자산이고 일부만 낡았다", B는 "맥락 자체가 통째로 낡았다"입니다. 요약본으로 옮기면 반드시 맥락 손실이 생기므로, 그 손실을 감수할 가치가 있는지가 갈림길입니다.

## 5.6 max_turns와 error_max_turns

`max_turns`는 에이전트가 한 실행에서 돌 수 있는 **최대 대화 턴 수** 상한입니다. 폭주와 비용 폭발을 막는 안전장치입니다. 이 상한에 걸려 멈추면 `error_max_turns` 상태로 종료됩니다.

중요한 점: **`error_max_turns`는 "접근이 틀렸다"는 뜻이 아니라 단지 "예산이 떨어졌다"는 뜻**입니다. 이미 수행한 분석은 세션에 그대로 남아 있습니다.

그래서 올바른 대응은:

1. 그 세션의 ID로 **resume** 하고,
2. 후속 요청에 **더 큰 `max_turns`** 값을 준다.

이러면 읽은 파일과 중간 결론을 모두 보존한 채 남은 작업을 이어서 끝냅니다. 처음부터 다시 돌리거나(분석 폐기), 새 세션에 읽었던 파일 목록을 손으로 다시 적는 것은 낭비입니다. 단순히 이어 하면 되는 상황에서 fork까지 할 이유도 없습니다.

## 5.7 세션 범위 권한(Session-scoped Permissions)과 포크

에이전트가 위험한 도구를 쓰려 할 때 사용자에게 승인을 요청하는 **권한 프롬프트**가 뜹니다. 여기서 흔히 "이 세션 동안 허용(allow for this session)"을 고를 수 있습니다.

이 승인은 이름 그대로 **특정 세션 ID에 묶인 승인**입니다. 따라서 포크로 새 세션(새 세션 ID)이 만들어지면 **그 승인은 따라오지 않고, 새 브랜치에서 다시 물어봅니다.**

이유는 보안입니다. 포크는 보통 "더 위험한 접근을 시험해보기 위해" 만드는 분기인데, 원본에서 준 임시 승인이 자동으로 따라온다면 사용자가 의도하지 않은 권한 확대가 일어납니다. 그래서 **이력만 복사하고 임시 권한 상태는 복사하지 않습니다.**

혼동하기 쉬운 오해들:

- "권한 승인은 정해진 턴 수 후에 만료된다" → 그런 규칙 때문이 아닙니다. 원인은 세션이 갈라진 것.
- "`--fork-session`은 `--continue`와 같이 쓰면 안 된다" → **함께 쓸 수 있는 정상 조합**입니다.
- "포크는 작업 디렉터리를 초기화해서 권한이 무효화된다" → 그렇지 않습니다.

## 5.8 서브에이전트 컨텍스트 격리 (Context Isolation)

**핵심 규칙: 서브에이전트를 호출할 때마다 그 서브에이전트의 컨텍스트는 완전히 새로(fresh) 시작됩니다.**

여기서 파생되는 두 가지 중요한 결과가 있습니다.

### (1) 메인 대화 이력은 자동으로 전달되지 않는다

사용자가 3턴 전에 "인증 제공자는 A를 쓰기로 하자"고 결정했더라도, 서브에이전트는 그 대화를 보지 못합니다. 서브에이전트가 엉뚱하게 다른 제공자를 제안한다면, 그것은 버그도 캐시 문제도 권한 문제도 아니라 **설계된 동작**입니다.

**해결책**: 필요한 결정 사항·제약·배경을 `Agent` 도구를 호출할 때의 **프롬프트 텍스트 안에 직접 써서 넘겨야** 합니다.

```
Agent(
  subagent_type="auth-designer",
  prompt="""사용자는 이미 인증 제공자로 A를 쓰기로 결정했다. 이 결정은 변경 대상이 아니다.
            A를 전제로 로그인 흐름을 설계하라."""
)
```

이것을 **컨텍스트 주입(context injection)** 이라고 부를 수 있습니다. "필요한 것은 명시적으로 넘긴다"가 원칙입니다.

### (2) 같은 서브에이전트를 두 번 불러도 서로를 모른다

`endpoint-finder`라는 같은 종류의 서브에이전트를 청구 서비스용으로 한 번, 알림 서비스용으로 한 번, 별개의 두 호출로 실행하면, 두 번째 호출은 첫 번째 호출이 있었다는 사실조차 모릅니다. 이미 설명했던 기본 규칙을 다시 설명하는 것도 정상입니다.

이것은 **예상된 동작(expected behavior)** 이며, 이유는 다음과 같습니다.

- 각 호출은 독립된 실행 환경에서 시작한다.
- 이전 실행의 상태를 이어받으려면 **특정 에이전트 ID를 지정해 명시적으로 재개(resume)** 해야 한다.
- 모든 서브에이전트 호출이 하나의 컨텍스트를 공유한다면 컨텍스트 윈도우가 폭발한다. 격리는 그것을 막는 설계다.

잘못된 통념들:

- "같은 코디네이터 세션 안의 서브에이전트들은 하나의 결합된 컨텍스트 윈도우를 공유한다" → 아니다.
- "같은 대상에 대해 두 번 부르면 메모리가 자동 공유된다" → 아니다. 대상이 같아도 무관하다.
- "AgentDefinition 수준에서 추론 결과를 자동 캐싱한다" → 그런 기능은 없다.

## 5.9 대화형 세션의 슬래시 명령어

터미널 세션 안에서 대화 상태를 조작하는 명령들입니다. 이름이 비슷해 헷갈리므로 **무엇이 보존되고 무엇이 사라지는지**로 구분하세요.

| 명령 | 하는 일 | 원본 대화 |
|---|---|---|
| `/fork [name]` | 지금까지의 대화를 그대로 복사한 **분기 세션**을 만들고 그쪽으로 전환 | **그대로 보존됨** |
| `/resume` | 이전에 저장된 기존 세션을 선택해 다시 불러옴 | 현재 세션을 복제하지는 않음 |
| `/clear` | 컨텍스트를 완전히 비우고 처음부터 시작 | **추론 흐름이 사라짐** |
| `/compact` | 대화 기록을 요약으로 압축해 토큰 절약 | 원본 상세 내용이 요약으로 대체됨 |
| `/rename` | 세션에 사람이 읽을 수 있는 이름을 붙임 | 이력에는 영향 없음 |

**활용:** 버그를 조사하다가 "다른 가설도 한번 시험해 보고 싶은데 지금까지의 추론은 잃기 싫다"면 `/fork`가 정확히 그 용도입니다. 복사본에서 자유롭게 탐색하고, 아니면 원본으로 돌아오면 됩니다.

`/clear`나 `/compact`는 **탐색을 분기하는 도구가 아닙니다.** 전자는 맥락을 버리고, 후자는 압축할 뿐 별도의 복사본을 만들지 않습니다. `/resume`도 기존 세션을 다시 여는 것이지 현재 세션을 제자리에서 복제하지 않습니다.

`/clear`는 세션 도중 주제가 완전히 바뀔 때 유용합니다. 다만 "어차피 새로 시작할 것"이라면 굳이 재개했다가 지울 이유가 없습니다.

### 네 기능 한눈에 정리

| 기능 | 하는 일 | 맥락 보존 |
|---|---|---|
| `resume` | 기존 세션의 대화 이력을 이어 감 | 100% 보존 |
| `fork_session` | 맥락을 복사해 독립 브랜치 생성 | 베이스라인까지 보존, 이후 분리 |
| `/compact` | 대화 이력을 요약·압축 (토큰 절약) | 요약으로 축약, 세부 손실 |
| `/clear` | 대화 맥락을 초기화 | 전부 폐기 |

> **넷 중 어느 것도 디스크 파일 내용을 다시 읽어 오거나 파일 상태를 복원하지 않습니다.**

## 5.10 세션 이름 짓기

기본적으로 세션에는 자동 생성된 식별자가 붙습니다. 원시 **세션 ID**(긴 무작위 문자열)나 "디렉토리 이름 + 무작위 접미사" 형태의 표시 이름 같은 것들입니다. 문제는 같은 날 여러 조사 작업을 병렬로 돌리면 이런 이름으로는 어느 게 어느 작업인지 구분이 안 된다는 점입니다.

해결책은 **사람이 읽을 수 있는 이름(human-readable handle)을 직접 붙이는 것**입니다.

- 세션 **시작 시점**에 설명적인 이름을 지정하거나,
- 세션 도중 **`/rename`** 슬래시 명령으로 이름을 바꿉니다.

그 후에는 이름으로 바로 재개할 수 있습니다.

```
claude --resume <name>
```

(원시 세션 ID로도 재개는 됩니다: `claude --resume <session-id>`. 하지만 ID를 스프레드시트에 일일이 적어 관리하는 것은 번거롭고, "기억하기 쉬운 핸들"이라는 요구를 충족하지 못합니다.)

다른 대안들의 문제:

- 자동 생성 이름에 의존 → 병렬 작업 구분이 안 됩니다.
- 세션을 끄지 않고 계속 켜두기 → 리소스 낭비이고, 애초에 "종료 후 나중에 이름으로 재개"라는 목적과 맞지 않습니다.

## 5.11 다중 사용자 환경: 왜 continue가 아니라 resume인가

한 리포지토리 디렉터리에서 여러 사용자가 각자 장기 대화를 진행하고, 백엔드 서비스가 몇 시간 뒤 특정 사용자의 대화를 이어가야 하는 상황을 봅시다.

- `continue`(가장 최근 세션)를 쓰면, **다른 사용자가 방금 만든 세션**을 잘못 집어 대화가 섞입니다.
- `fork_session=True`를 매 요청마다 쓰면 매번 새 분기가 생겨 한 사용자의 대화가 이어지지 않고, "최신 세션"을 복사하는 것이라 역시 사용자 간 혼선이 납니다.
- **정답 구조**: 세션 생성 시 발급된 **세션 ID를 사용자별로 DB에 저장**해 두었다가, 그 사용자의 후속 요청이 오면 저장해 둔 ID로 **resume** 합니다.

즉 **세션 ID를 애플리케이션이 추적·소유**하는 것이 다중 사용자 세션 관리의 기본입니다.

## 5.12 세션 조회 API

SDK는 디스크에 저장된 세션을 프로그램에서 직접 다룰 수 있는 함수를 제공합니다. 대화형 CLI 선택기를 외부 프로세스로 띄우지 않고 자체 UI(커스텀 세션 선택기)를 만들 때 사용합니다.

| 함수 | 역할 |
| --- | --- |
| `listSessions()` | 특정 프로젝트/리포지토리에 존재하는 **세션 목록을 열거** |
| `getSessionMessages()` | 지정한 세션의 **전체 메시지 이력을 읽기** |

비슷해 보이지만 역할이 다른 것들:

- `getSessionInfo()`: 단일 세션의 **메타데이터**만 조회. 전체 목록 열거용이 아니다.
- `resume()`: 세션을 **다시 이어서 실행**하는 연산. 단순 읽기용이 아니다.
- `fork_session()`: 세션을 **분기**하는 연산. 열거용이 아니다.
- `continue()`: 세션을 이어가는 연산.
- `renameSession()` / `tagSession()`: 세션의 **이름 변경 / 태그 부착** 같은 메타데이터 수정. 조회와 무관.

전형적인 사용 흐름:

```
sessions = listSessions(projectPath)      # 목록 만들기 → UI에 표시
messages = getSessionMessages(chosen_id)  # 사용자가 고른 세션의 내용 미리보기
```

## 5.13 CLI 플래그: 비대화형 실행과 세션 재개

Claude Code CLI에는 대화형 터미널 UI를 띄우는 기본 모드와, 스크립트에서 쓰기 위한 비대화형 모드가 있습니다. 주요 플래그는 다음과 같습니다.

| 플래그 | 의미 |
| --- | --- |
| `-p` / `--print` | **대화형 UI를 열지 않고** 프롬프트를 한 번 실행하고 결과를 표준 출력으로 내보냄 (원샷/비대화형) |
| `--resume <session-id>` | 지정한 세션 ID의 이력과 컨텍스트를 불러와 이어감 |
| `--continue` | 작업 디렉터리의 가장 최근 세션을 이어감 |
| `--fork-session` | 이어받되 새 세션 ID로 분기 (원본 보존) |
| `--output-format json` | 결과를 스크립트가 파싱할 수 있는 **구조화된 JSON**으로 출력 |
| `--from-pr <number>` | Pull Request를 기점으로 시작 (세션 ID 기반 재개와는 다른 기능) |

이 플래그들은 **조합**해서 씁니다. 요구사항을 하나씩 플래그로 매핑하는 습관을 들이면 됩니다.

**예시**: "이미 완료된 비대화형 세션에 후속 질문 하나를 던지고, 답변을 스크립트가 파싱할 구조화된 데이터로 받고 싶다. 대화형 터미널 UI는 열지 않는다."

- 대화형 UI 열지 않음 → `-p`
- 이전 세션 컨텍스트 이어받기 → `--resume <session-id>`
- 스크립트 파싱용 구조화 출력 → `--output-format json`

```bash
claude -p --resume <session-id> --output-format json "summarize what we changed"
```

**주의**: `-p` 없이 `--resume`만 쓰면 대화형 UI가 열립니다. 또한 `--output-format json`을 지정하지 않으면 출력이 사람이 읽는 자유 형식 텍스트라 안정적인 파싱이 불가능합니다. (뒤에 파이프로 JSON 파서를 붙인다고 출력이 JSON이 되지는 않습니다.)

## 5.14 자주 나오는 설정 값 정리

| 설정 | 의미 | 하는 일 / 하지 않는 일 |
|---|---|---|
| `maxTurns` / `max_turns` | 에이전트가 돌 수 있는 최대 대화 턴 수 상한 | 폭주·비용 폭발 방지용 안전장치. **속도를 높이거나 병렬성을 만들지 않음** |
| `persistSession` | 세션 트랜스크립트를 디스크에 저장할지 여부 | 저장 여부만 결정. **호출 흐름의 직렬/병렬과 무관** |
| `fork_session` | 재개 시 원본을 복제해 분기 세션 생성 | 원본 보존용. **머신 간 재개를 막는 기능이 아니고, 파일 스냅샷도 아님** |
| `continue_conversation` | 작업 디렉터리의 최근 세션을 이어갈지 여부 | ID 없이 이어가기. 다중 사용자 환경에서는 위험 |
| `permissionDecision` | 훅이 반환하는 판정: `allow` / `deny` | `deny`면 실제 도구 실행이 차단됨 |
| `updatedInput` | 훅이 도구 입력을 수정해서 넘길 때 쓰는 필드 | `PreToolUse`에서 정규화된 값을 전달 |
| `stop_reason` | 모델이 왜 멈췄는지를 알려주는 응답 필드 | 루프 종료 판단의 공식 신호 |

## 5.15 세션 관리의 적정량 — 과잉 설계 피하기

세션 기능이 있다고 해서 항상 써야 하는 것은 아닙니다.

**빌드 파이프라인 안의 원샷(one-shot) 작업** — 프롬프트 하나를 실행하고 끝이며 이후 후속 질문이 없는 경우 — 에는 **단일 `query()` 호출 외에 아무 세션 처리도 추가하지 않는 것**이 올바릅니다. 이후에 컨텍스트를 공유할 프롬프트 자체가 없기 때문입니다.

다음은 모두 불필요한 오버헤드입니다.

- 혹시 몰라 세션 ID를 저장하고 즉시 재개하기 → 상태가 필요 없는(stateless) 작업에 상태 관리를 도입.
- 나중을 대비해 `continue_conversation=True`를 켜두기 → 쓰지 않을 기능을 켜둠.
- 후속 작업이 예상되지 않는데 `fork_session`을 켜기 → 쓰지 않을 병렬 분기.

**원칙: 필요가 실제로 존재할 때만 상태 관리를 도입한다.**

## 5.16 이 장의 핵심 요약

| 질문 | 답 |
|---|---|
| 트랜스크립트는 어디 있나? | **실행 머신의 로컬 디스크**, 작업 디렉터리별로 분리 |
| 세션이 저장하는 것은? | 대화 이력뿐. **파일 스냅샷 아님** → 되돌리려면 Git 등 체크포인팅 |
| 재개했는데 기억이 없다 | 머신이 다르거나 디렉터리가 다르다 (파일 부재) |
| 두 갈래를 독립 탐색하려면? | resume 두 번이 아니라 **fork** |
| 포크하면 세션 권한 승인은? | 따라오지 않는다. 새 세션 ID이므로 다시 묻는다 |
| 파일이 바뀐 채로 재개하려면? | 재개 후 **명시적으로 re-read 지시** |
| 옛 맥락이 통째로 낡았다면? | **새 세션 + 구조화 요약 주입** |
| `error_max_turns`로 끝났다면? | 분석은 남아 있다. **resume + 더 큰 max_turns** |
| 다중 사용자 백엔드는? | 사용자별 **세션 ID를 DB에 저장 → resume** |
| 컨테이너가 매번 새로 뜬다면? | 세션 아닌 **애플리케이션 레벨 상태 전달** |
| 원샷 작업이라면? | 세션 관리 **아무것도 하지 말 것** |
