# 사전 학습 노트 — Claude Code 설정과 워크플로 (conf-40-49 범위)

이 문서는 해당 범위에서 다루는 개념을 아무런 사전 지식이 없는 사람 기준으로 처음부터 설명합니다.
크게 다섯 덩어리입니다.

1. Claude Code가 무엇이고 "컨텍스트"란 무엇인가
2. 지시를 정확히 전달하는 방법 (프롬프트 설계, 예시, 테스트 우선)
3. 메모리 파일 체계 — `CLAUDE.md`와 임포트
4. 모듈형 규칙 체계 — `.claude/rules/`와 조건부 로드
5. 설정 파일 계층, 서브에이전트, CLI 실행 격리

---

## 0. 기초: Claude Code와 컨텍스트 윈도우

### Claude Code란
Claude Code는 터미널에서 실행되는 AI 코딩 에이전트입니다. 단순히 대화만 하는 챗봇이 아니라,
실제로 파일을 읽고(Read), 수정하고(Edit/Write), 검색하고(Grep/Glob), 셸 명령을 실행(Bash)할 수 있는
도구(tool)들을 손에 쥐고 있습니다. 사용자가 "이 함수를 리팩터링해줘"라고 하면 스스로 파일을 찾아
읽고 고치고 테스트를 돌립니다.

### 컨텍스트 윈도우 (Context Window)
LLM(대규모 언어 모델)은 한 번에 볼 수 있는 텍스트 양에 물리적 상한이 있습니다. 이 "한 번에 볼 수 있는
작업 기억 공간"을 컨텍스트 윈도우라고 합니다. 여기에는 다음이 전부 들어갑니다.

- 시스템 프롬프트(에이전트의 기본 행동 지침)
- 자동으로 로드된 메모리 파일(`CLAUDE.md` 등)의 내용
- 사용자와 주고받은 모든 대화
- 도구 실행 결과 (파일 내용, grep 출력, 테스트 로그 등)

측정 단위는 토큰(token)입니다. 대략 영어 단어 1개 ≈ 1~2토큰, 한글은 글자당 더 많이 듭니다.

**왜 중요한가**: 컨텍스트는 유한하고 비쌉니다. 두 가지 문제가 생깁니다.

1. **용량 문제** — 꽉 차면 오래된 대화가 요약(summarization)되거나 잘려나가 정보를 잃습니다.
2. **신호 대 잡음 문제** — 지금 하는 일과 무관한 내용이 잔뜩 들어 있으면 모델이 정말 중요한
   지시를 놓칩니다. 이걸 컨텍스트 오염(context pollution) 또는 clutter라고 부릅니다.

그래서 이 범위의 문제 대부분은 결국 하나의 질문으로 수렴합니다:
**"필요한 정보만, 필요한 순간에 컨텍스트에 들어오게 하려면 어떻게 설정하는가?"**

## 1. 지시를 정확히 전달하기 — 프롬프트 설계

### 1-1. 모호성(ambiguity)이라는 문제

자연어는 본질적으로 모호합니다. 대표적인 예가 날짜 형식입니다.

```
03/04/25
```

이것은 무엇일까요?

- 미국식(month-first, `MM/DD/YY`): 2025년 3월 4일
- 유럽식(day-first, `DD/MM/YY`): 2025년 4월 3일
- 일부 표기(`YY/MM/DD`): 2003년 4월 25일

사람도 문맥 없이는 못 정합니다. LLM은 더더욱 그렇습니다. 학습 데이터에 두 관습이 모두
들어 있으므로, 같은 프롬프트를 여러 번 줘도 **매번 다르게 해석**할 수 있습니다.
이것이 "일관성 없는 결과(inconsistent interpretation)"의 원인입니다.

관련 개념 **ISO 8601**: 국제 표준 날짜 표기법으로 `YYYY-MM-DD` 형태입니다. 예: `2025-03-04`.
연-월-일 순서가 고정이라 모호성이 없고, 문자열 정렬 순서가 곧 시간 순서라는 장점이 있어
데이터 교환 표준으로 널리 쓰입니다.

### 1-2. 퓨샷 프롬프팅 (Few-Shot Prompting)

**무엇인가**: 지시문에 "구체적인 입력 → 기대 출력" 쌍을 몇 개(few) 함께 보여주는 기법입니다.
예시가 0개면 제로샷(zero-shot), 1개면 원샷(one-shot), 2~5개 정도면 퓨샷입니다.

**왜 효과적인가**: LLM은 패턴 매칭에 강합니다. 추상적 규칙("월을 먼저 해석하라")은 여러 해석의
여지를 남기지만, 구체적 사례는 규칙을 **한 점으로 고정**시킵니다. 서술이 아무리 길어도
예시 한 줄이 주는 명확성을 이기기 어렵습니다.

**예시**:

```
자유 형식 날짜 문자열을 ISO 8601로 변환하는 함수를 작성해 줘.
숫자로만 된 모호한 입력은 MM/DD/YY(월 우선)로 해석해.

예시:
  "03/04/25"        -> "2025-03-04"
  "the 1st of March" -> "2025-03-01"
  "next Tuesday"     -> "2025-03-11"   (기준일 2025-03-06)
```

`03/04/25 -> 2025-03-04`라는 한 줄이 "월 우선"이라는 규칙을 실제 동작으로 증명합니다.
경계 사례(edge case)를 예시로 고르는 것이 핵심입니다. 헷갈릴 수 있는 것을 골라야 값어치가 있습니다.

### 1-3. 효과 없는 접근들 (그리고 왜 안 되는지)

이해를 위해 대비되는 접근들도 알아둘 가치가 있습니다.

- **강한 어조로 다시 말하기**: "이번엔 제대로 해!" 같은 표현은 **새로운 정보가 0비트**입니다.
  모델이 틀리는 이유는 의지 부족이 아니라 정보 부족입니다. 정보를 안 주면 결과도 안 바뀝니다.
- **"알아서 판단해(best judgment)"**: 모호성 해소의 책임을 모델에게 떠넘기는 것이므로,
  일관성이라는 목표와 정면으로 충돌합니다. 자율 판단은 곧 실행마다 달라질 수 있다는 뜻입니다.
- **모호하면 예외 던지기**: 기술적으로 안전하지만, "자유 형식 문자열을 자동 변환한다"는
  원래 요구사항 자체를 포기하는 것입니다. 요구사항을 축소해 문제를 회피하는 셈입니다.

교훈: **프롬프트 개선 = 정보 추가**. 어조나 강조가 아니라, 모델이 몰랐던 사실을 넣어야 합니다.

### 1-4. 테스트를 먼저 주기 (Test-First / TDD with AI)

**TDD란**: Test-Driven Development. 구현 코드보다 **테스트를 먼저** 쓰는 개발 방식입니다.
테스트가 곧 "무엇이 옳은가"에 대한 실행 가능한 명세(executable specification)가 됩니다.

**AI 에이전트에게 왜 특히 강력한가**: Claude Code는 셸을 실행할 수 있으므로 테스트를 직접
돌릴 수 있습니다. 그러면 다음 루프가 자동으로 돕니다.

```
코드 작성 → 테스트 실행 → 실패 확인 → 원인 분석 → 수정 → 다시 실행 → 전부 통과
```

이것을 **자율 피드백 루프(autonomous feedback loop)**라고 합니다. 사람이 "아니 그게 아니고..."
하며 매번 개입하는 왕복(back-and-forth) 횟수가 극적으로 줄어듭니다. 게다가 테스트는
자연어 명세와 달리 **해석의 여지가 없습니다.** 통과 아니면 실패, 둘 중 하나입니다.

**언제 특히 유용한가**: 도메인 규칙이 미묘하고 틀리기 쉬울 때.

#### 관련 도메인 개념 (1) — 뱅커스 라운딩 (Banker's Rounding)

정확히 0.5인 값을 어느 쪽으로 반올림할지에 대한 규칙입니다.

- **일반 반올림(half-up)**: 0.5는 항상 올림. `2.5 -> 3`, `3.5 -> 4`
- **뱅커스 라운딩(half-to-even, 오사오입)**: 0.5는 **가장 가까운 짝수** 쪽으로.
  `2.5 -> 2`, `3.5 -> 4`, `0.125 -> 0.12`, `0.135 -> 0.14`

**왜 존재하는가**: half-up은 항상 위로 올리므로 값을 많이 더할수록 총합이 계속 커지는
**체계적 편향(bias)**이 생깁니다. 금융/회계에서 수백만 건을 합산하면 무시할 수 없습니다.
짝수 쪽으로 번갈아 보내면 이 편향이 통계적으로 상쇄됩니다. IEEE 754 부동소수점 표준의
기본 반올림 방식이기도 하며, 파이썬 `round()`와 `decimal.ROUND_HALF_EVEN`이 이 방식입니다.

```python
round(2.5)   # 2   (파이썬3은 뱅커스 라운딩)
round(3.5)   # 4
```

이런 규칙은 줄글로 설명하면 반드시 오해가 생깁니다. 테스트 케이스로 못 박는 게 정답입니다.

```python
def test_bankers_rounding():
    assert round_cents(2.505) == 2.50
    assert round_cents(2.515) == 2.52
```

#### 관련 도메인 개념 (2) — 할인 중첩 순서 (Discount Stacking Order)

할인이 여러 개 겹칠 때 **적용 순서에 따라 최종 금액이 달라집니다**. 곱셈과 뺄셈은 교환법칙이
성립하지 않기 때문입니다.

정가 100, 쿠폰 -10(정액), 회원 할인 -20%(정률)라고 합시다.

- 정액 먼저: `(100 - 10) × 0.8 = 72`
- 정률 먼저: `100 × 0.8 - 10 = 70`

2원 차이입니다. 여기에 세금, 배송비, 최소 주문 금액 조건까지 얽히면 순서 규칙은 회사의
비즈니스 정책 문제가 됩니다. "일반적으로 이커머스에서 흔한 방식"으로 추측하게 두면 안 되는
전형적인 영역입니다. 마찬가지로 테스트로 고정합니다.

**정리**: 규칙이 미묘 → 예시로 보여준다(퓨샷). 규칙이 미묘 + 검증 가능 → 테스트로 못 박는다(TDD).

## 2. `CLAUDE.md` — 프로젝트 메모리 파일

### 2-1. 무엇인가

`CLAUDE.md`는 Claude Code가 세션을 시작할 때 자동으로 읽어서 컨텍스트에 넣는 마크다운 파일입니다.
"이 프로젝트에서 일할 때 알아야 할 것들"을 적어두는 곳입니다. 매번 같은 설명을 반복하지 않아도
되게 만드는 장치입니다.

전형적인 내용:

```markdown
# 프로젝트 개요
결제 백엔드 서비스. Node 20, TypeScript, PostgreSQL.

# 명령어
- 빌드: `npm run build`
- 테스트: `npm test`
- 린트: `npm run lint`

# 컨벤션
- 커밋 메시지는 Conventional Commits 형식을 따른다.
- 모든 API 핸들러는 zod 스키마로 입력을 검증한다.
```

### 2-2. 파일이 놓이는 위치와 로드 시점

| 위치 | 로드 시점 | 공유 범위 |
|---|---|---|
| 프로젝트 루트 `CLAUDE.md` | 세션 시작 시 **항상** | Git 커밋 → 팀 전체 |
| 하위 디렉터리 `some/dir/CLAUDE.md` | Claude가 그 디렉터리 **안의 파일을 읽을 때** | Git 커밋 → 팀 전체 |
| `CLAUDE.local.md` | 위와 같으나 개인용 | Git 제외 → 본인만 |
| `~/.claude/CLAUDE.md` | 모든 프로젝트에서 | 본인 기기 전체 |

**여기서 반드시 짚고 갈 두 가지 트레이드오프가 있습니다.**

**(가) 루트 `CLAUDE.md`는 항상 로드된다 = 항상 토큰을 먹는다**
테스트 컨벤션을 전부 루트에 넣으면, 테스트와 무관한 프론트엔드 작업 세션에서도 그 내용이
컨텍스트를 차지합니다. 상시 필요한 정보(빌드 명령, 프로젝트 성격)만 루트에 두는 게 원칙입니다.

**(나) 하위 디렉터리 `CLAUDE.md`는 "그 디렉터리를 건드릴 때만" 로드된다 = 놓치기 쉽다**
`src/api/tests/CLAUDE.md`에 테스트 규칙을 넣어두면, 나중에 누군가 `e2e/` 디렉터리를 새로 만들고
거기에 테스트를 추가했을 때 그 규칙은 **적용되지 않습니다.** 디렉터리 구조에 의존하기 때문입니다.
게다가 여러 테스트 디렉터리마다 같은 내용을 복붙하면 중복(duplication) 문제가 생기고,
하나를 고쳐도 나머지가 낡은 상태로 남습니다.

이 두 가지 한계가 뒤에 나오는 `.claude/rules/`가 존재하는 이유입니다.

### 2-3. 임포트 문법 `@path`

`CLAUDE.md` 안에서 `@` 뒤에 경로를 붙이면 그 파일의 내용을 **실제로 읽어서 컨텍스트에 삽입**합니다.
이걸 임포트(import)라고 합니다.

```markdown
See @README for project overview and @package.json for available npm commands.
```

이렇게 쓰면 `README`와 `package.json`의 **전체 내용**이 컨텍스트에 로드됩니다.
단순한 텍스트 링크가 아니라 실제 파일 삽입 명령입니다.

모노레포에서는 루트 `CLAUDE.md`가 하위 패키지 파일들을 임포트하는 패턴이 흔합니다.

```markdown
@packages/web/CLAUDE.md
@packages/admin-dashboard/CLAUDE.md
@packages/legacy-billing/CLAUDE.md
```

편리하지만, 이러면 `packages/web`만 담당하는 사람에게도 **모든 패키지의 내용이 강제 로드**됩니다.
이것이 뒤에 나오는 `claudeMdExcludes`가 필요한 상황입니다.

### 2-4. 임포트를 하지 않고 경로만 "언급"하기 — 백틱

문서에 파일 경로를 **사람이 읽으라고** 적고 싶은데, `@`를 그냥 쓰면 Claude가 그 파일을
통째로 읽어버립니다. 예를 들어 오래된 레거시 노트를 "참고로 이런 게 있다" 수준으로만
가리키고 싶을 때 원치 않는 토큰이 소모됩니다.

**해결: 인라인 코드 스팬(백틱)으로 감싼다.**

````markdown
자세한 배경은 `@docs/legacy-notes.md` 를 참고하세요. (사람용 안내)
````

임포트 파서는 **코드 스팬 내부를 건너뜁니다.** 백틱 안의 내용은 리터럴 텍스트로 취급되어
임포트가 발생하지 않습니다. 동시에 마크다운에서는 정상적으로 렌더링되어 사람 눈에는
잘 보이므로, "사람에게는 보이되 기계는 실행하지 않는다"는 목적을 정확히 만족합니다.

**작동하지 않는 방법들과 그 이유:**

- `<!-- @docs/legacy-notes.md -->` (HTML 주석) — 주석은 렌더링 시 **화면에 안 보입니다.**
  사람에게 보여주는 게 목적이었는데 그 목적 자체가 깨집니다.
- `@@docs/legacy-notes.md` (`@` 중복) — 그런 이스케이프 규칙은 존재하지 않습니다.
  일부 템플릿 엔진(Blade 등)의 관습이지만 여기 문법이 아닙니다.
- `@ docs/legacy-notes.md` (공백 삽입) — 임포트는 막힐지 몰라도 경로가 깨져 보이고,
  표준적인 이스케이프 방식이 아닙니다.

**일반 원리**: 마크다운 기반 지시 파일에서 "특수 문법을 문자 그대로 보여주고 싶다"면
코드 스팬/코드 블록이 표준 해법입니다.

## 3. `.claude/rules/` — 모듈형 조건부 규칙

### 3-1. 왜 생겼는가

앞서 본 `CLAUDE.md`의 두 한계를 다시 정리합니다.

- 루트에 두면 → 항상 로드 → 무관한 세션에서 토큰 낭비
- 하위 디렉터리에 두면 → 디렉터리 구조에 종속 → 중복 + 누락 위험

원하는 것은 **"디렉터리가 아니라 파일 종류를 기준으로, 필요할 때만"** 로드되는 규칙입니다.
`.claude/rules/`가 정확히 이걸 제공합니다.

### 3-2. 구조

프로젝트 루트의 `.claude/rules/` 디렉터리에 주제별 마크다운 파일을 둡니다.

```
.claude/
  rules/
    testing.md
    api-conventions.md
    security.md
  settings.json
  settings.local.json
```

각 규칙 파일은 맨 위에 **YAML 프론트매터(frontmatter)**를 가질 수 있습니다.
프론트매터란 파일 최상단에 `---` 세 줄 사이에 넣는 메타데이터 블록입니다.
정적 사이트 생성기(Jekyll, Hugo 등)에서 널리 쓰이는 관습을 그대로 차용했습니다.

```markdown
---
paths: ["**/*.test.ts"]
---

# 테스트 컨벤션

- 테스트 이름은 `describe`/`it`으로 행동을 서술한다.
- 외부 네트워크 호출은 반드시 목(mock) 처리한다.
- 하나의 `it` 블록에는 하나의 단언만 둔다.
```

### 3-3. `paths` — 조건부 로드의 핵심

`paths`는 **글로브 패턴(glob pattern)의 배열**입니다. Claude가 읽거나 작업하는 파일이 이 패턴에
일치할 때에만 해당 규칙이 컨텍스트로 로드됩니다. 일치하지 않으면 **토큰을 전혀 쓰지 않습니다.**

이것이 이 기능의 요점입니다: **필요한 순간에만 등장하는 규칙(just-in-time context)**.

### 3-4. 글로브 패턴 문법

글로브는 파일 경로를 매칭하는 간단한 와일드카드 문법입니다. 정규식보다 훨씬 단순합니다.

| 패턴 | 의미 |
|---|---|
| `*` | 경로 구분자(`/`)를 제외한 임의의 문자열 |
| `**` | 디렉터리 경계를 넘는 임의의 깊이 |
| `?` | 임의의 한 글자 |
| `{a,b}` | a 또는 b |

실전 예시:

| 패턴 | 매칭됨 | 매칭 안 됨 |
|---|---|---|
| `src/api/**/*` | `src/api/users.ts`, `src/api/v2/orders/handler.ts` | `src/web/app.ts` |
| `**/*.test.ts` | `src/a.test.ts`, `packages/x/tests/b.test.ts`, `e2e/c.test.ts` | `src/a.ts` |
| `**/*.test.*` | `a.test.ts`, `a.test.js`, `a.test.py` | `a.spec.ts` |
| `src/api` | 정확히 `src/api`라는 **그 항목 하나** | `src/api/users.ts` |

**마지막 줄이 아주 중요합니다.** 와일드카드 없는 리터럴 문자열 `"src/api"`는 하위 파일들에
재귀적으로 매칭되지 **않습니다.** 하위 전체를 잡으려면 반드시 `src/api/**/*`처럼 명시적으로
와일드카드를 써야 합니다. 글로브는 "디렉터리 이름을 쓰면 알아서 하위 포함"이라는 편의를
제공하지 않습니다.

### 3-5. 두 가지 대표 시나리오

**시나리오 A — 디렉터리 기준 스코핑**
"`src/api/` 밑에서 작업할 때만 입력 검증과 표준 에러 응답 규칙을 적용하고, 프론트엔드나
인프라 작업 때는 컨텍스트를 차지하지 않게 하라."

`.claude/rules/api-conventions.md`:
```markdown
---
paths: ["src/api/**/*"]
---

# API 컨벤션
- 모든 핸들러는 요청 본문을 스키마로 검증한 뒤 로직을 실행한다.
- 오류 응답은 `{ "error": { "code": ..., "message": ... } }` 형태로 통일한다.
```

**시나리오 B — 파일 유형 기준 스코핑**
"테스트 파일이 `src/`, `lib/`, `packages/*/tests/`, `e2e/` 등 여기저기 흩어져 있는데,
디렉터리마다 `CLAUDE.md`를 복붙하지 않고 한 곳에서 관리하고 싶다."

`.claude/rules/testing.md`:
```markdown
---
paths: ["**/*.test.ts"]
---

# 테스트 컨벤션
...
```

디렉터리 구조와 무관하게 파일 이름 패턴으로 걸리므로, 미래에 새 디렉터리가 생겨도
그 안의 `*.test.ts`에 규칙이 자동 적용됩니다. **중복 제거 + 누락 방지**를 동시에 달성합니다.

### 3-6. 스코핑에 대한 오해 정리

- **파일 이름으로 범위가 추론되지 않습니다.** `src-api-only.md`라고 이름 지어도 Claude Code가
  "아하 `src/api`용이구나"라고 해석하지 않습니다. 스코핑은 **오직 `paths` 프론트매터**로만
  선언합니다. 파일 이름은 사람이 알아보기 위한 것입니다.
- **규칙 파일을 하위 디렉터리에 넣는다고 자동 스코핑되지 않습니다.** `.claude/rules/`는
  프로젝트 루트에 두고 관리하는 것이 표준이며, 위치가 아니라 `paths`가 범위를 결정합니다.

### 3-7. 세 가지 배치의 비교 요약

| 방식 | 로드 조건 | 장점 | 단점 |
|---|---|---|---|
| 루트 `CLAUDE.md` | 항상 | 확실히 적용됨 | 무관한 세션에서도 토큰 소모 |
| 하위 `CLAUDE.md` | 그 디렉터리 파일을 읽을 때 | 지역적 맥락 | 구조 종속, 중복, 새 디렉터리 누락 |
| `.claude/rules/*.md` + `paths` | 패턴 일치 파일 작업 시 | 단일 소스, 구조 무관, 조건부 | 패턴을 정확히 써야 함 |

**설계 원칙**: 상시 필요한 소수의 정보는 루트 `CLAUDE.md`, 특정 작업 유형에만 필요한
세부 규칙은 `.claude/rules/`로 분리.

## 4. 설정 파일 계층과 스코프

### 4-1. 세 종류의 설정 파일

Claude Code의 동작은 JSON 설정 파일로 조정합니다. 위치에 따라 **적용 범위와 공유 여부**가 다릅니다.

| 파일 | 범위 | Git 추적 | 용도 |
|---|---|---|---|
| `~/.claude/settings.json` | 사용자 전역 (모든 프로젝트) | 아니오 | 개인 기본 취향 |
| `<project>/.claude/settings.json` | 그 프로젝트, **팀 전원** | **예 (커밋됨)** | 팀 공통 규칙 |
| `<project>/.claude/settings.local.json` | 그 프로젝트, **나만** | 아니오 (gitignore) | 개인 로컬 오버라이드 |

일반적으로 좁은 범위가 넓은 범위를 덮어씁니다(local > project > user).

**핵심 판단 기준**: "이 설정이 팀 전체에 적용되어야 하는가, 나에게만인가?"
팀 전체면 `settings.json`(커밋), 나만이면 `settings.local.json`.
개인 취향을 커밋된 파일에 넣으면 다른 팀원의 환경까지 바꿔버립니다.

### 4-2. `claudeMdExcludes`

**무엇인가**: 특정 경로 패턴의 `CLAUDE.md` 파일이 자동 로드되지 **않도록 차단**하는 설정입니다.
"제외 목록"이며, **로드를 유발하는 설정이 아닙니다.** (방향을 헷갈리기 쉬운 지점입니다.)

**언제 쓰는가**: 모노레포에서 루트 `CLAUDE.md`가 임포트로 모든 하위 패키지를 끌어오는데,
나는 `packages/web`만 담당해서 나머지가 전부 잡음일 때.

**개인만 적용하려면 `settings.local.json`에 넣습니다:**

`.claude/settings.local.json`
```json
{
  "claudeMdExcludes": [
    "packages/admin-dashboard/**",
    "packages/legacy-*/**"
  ]
}
```

이러면 내 기기의 세션에서만 그 패키지들의 `CLAUDE.md`가 로드되지 않습니다.
`admin-dashboard`를 담당하는 동료의 환경은 그대로입니다.

**하지 말아야 할 대안들과 그 이유:**

- **커밋된 `settings.json`에 넣기** → 팀 전원의 세션에서 차단됩니다. 그 패키지 담당자가
  필요한 컨텍스트를 잃습니다.
- **다른 패키지의 `CLAUDE.md` 파일 자체를 삭제** → 남의 작업 환경을 파괴하는 행위입니다.
  파일은 실제로 사용 중입니다.
- **팀에게 파일 구조를 바꿔달라고 요청** → 개인 환경 하나 정리하려고 조직 전체를 움직이는
  과잉 대응이며, "내 세션에서만"이라는 요구와 맞지 않습니다.

**원칙**: 개인 환경 문제는 개인 설정 파일로 푼다.

## 5. 컨텍스트 격리 — 서브에이전트

### 5-1. 서브에이전트란

메인 대화와 **별도의 독립된 컨텍스트 윈도우**를 가진 보조 에이전트입니다. 메인 세션이
"이 작업 좀 해와"라고 위임(delegate)하면, 서브에이전트가 자기 컨텍스트 안에서 도구를 실행하고,
**최종 결과 요약만** 메인에 돌려줍니다.

```
[메인 세션]  --- 작업 위임 --->  [서브에이전트: 독립 컨텍스트]
                                    grep 실행 (수천 줄 출력)
                                    파일 30개 읽기
                                    패턴 분석
[메인 세션]  <--- 요약만 반환 ---  "12개 파일 47곳에서 사용 중, 유형은 3가지..."
```

메인 세션에는 수천 줄의 원본(raw) 출력 대신 정리된 몇 문단만 들어옵니다.

**Explore 서브에이전트**는 이 목적에 특화된 읽기 전용 탐색 에이전트입니다. 코드베이스를
광범위하게 뒤져서 "어디에 무엇이 있는지"를 찾아 요약합니다.

### 5-2. 언제 쓰는가

전형적인 상황: 다단계 리팩터링에서 deprecated(더 이상 사용을 권장하지 않는) 헬퍼 함수가
수백 개 파일 중 어디에서 쓰이는지 전수 조사해야 할 때. `grep`을 메인에서 직접 돌리면
출력 수천 줄이 그대로 메인 컨텍스트를 삼킵니다. 이후 실제 리팩터링 작업에 쓸 공간이 사라지고,
잡음 때문에 판단 품질도 떨어집니다.

Explore 서브에이전트에 위임하면 탐색 비용이 서브에이전트 쪽에 격리됩니다.

### 5-3. 대안이 안 되는 이유

- **전체 출력을 붙여넣고 나중에 지우기** — 토큰은 **컨텍스트에 들어가는 순간 이미 소모**됩니다.
  트랜스크립트에서 줄을 지워도 이미 지불한 비용은 돌아오지 않으며, 수작업 자체가 비효율입니다.
- **플랜 모드(plan mode)로 전환** — 플랜 모드는 **코드를 변경하기 전에 계획을 세우고 승인받는**
  모드입니다. 파일 수정을 막는 안전장치이지, grep 출력을 가로채 요약해 주는 기능이 아닙니다.
  기능의 목적이 다릅니다.
- **컨텍스트 윈도우 한도를 올리기** — 비용이 늘어나고, 수천 줄의 잡음이 여전히 컨텍스트에
  남아 신호 대 잡음 비를 악화시킵니다. 근본 문제(불필요한 정보의 유입)를 해결하지 않습니다.

### 5-4. 자기 리뷰의 한계 — 왜 별도 세션에서 리뷰해야 하는가

**상황**: 하나의 긴 세션에서 기능을 구현하고, 같은 세션에서 자기 diff를 리뷰한 뒤 PR을 엽니다.
실제로 이렇게 하면 독립 리뷰어보다 버그를 훨씬 덜 잡아냅니다.

**이유**: LLM은 컨텍스트에 있는 내용을 기반으로 추론합니다. 코드를 작성하는 동안 세웠던
**추론 과정, 전제 조건, 가정**이 컨텍스트에 그대로 남아 있습니다. 리뷰 단계에 들어가도
이 전제들이 계속 살아 있으므로, 모델은 **처음에 놓친 것을 똑같이 놓칩니다.**
"내가 방금 이렇게 결정했으니 맞다"는 방향으로 확증 편향(confirmation bias)이 작동합니다.

사람도 똑같습니다. 자기가 쓴 글의 오타를 못 보는 것과 같은 현상입니다. 뇌가 "의도한 것"을
읽어버리기 때문입니다. 이런 인지적 사각지대를 **블라인드 스팟(blind spot)**이라고 합니다.

**해결**: 리뷰는 **신선한 컨텍스트(fresh session)** 또는 별도 서브에이전트에서 수행합니다.
작성 과정을 모르는 상태에서 결과물(diff)만 보고 판단하게 하면, 구현 의도가 아니라
실제로 쓰인 코드를 평가하게 됩니다.

**참고로, 원인이 아닌 것들**:
- 컨텍스트 부족으로 diff를 못 읽어서가 아닙니다. (짧은 diff에서도 같은 현상이 나타납니다)
- 도구 결과를 캐싱해서 낡은 파일 내용을 본다는 것도 사실이 아닙니다. 파일이 수정되면
  갱신된 내용을 참조합니다.
- `--print` 플래그가 Read 도구를 끄지도 않습니다. (아래 참조)

## 6. CLI 실행과 재현성

### 6-1. 인터랙티브 모드 vs 프린트 모드

- **인터랙티브 모드**: `claude`를 그냥 실행. 터미널에서 대화형으로 주고받습니다.
- **프린트 모드**: `claude -p "프롬프트"` 또는 `--print`. 한 번 실행하고 결과를 표준 출력에
  찍고 종료합니다. 스크립트, CI/CD 파이프라인, 크론 작업 등 **비대화형 자동화**용입니다.

```bash
claude -p "이 저장소의 보안 이슈를 점검해줘" > report.txt
```

`--print`는 단지 "대화형 UI 없이 출력하고 종료"를 의미할 뿐, 도구를 비활성화하지 않습니다.

### 6-2. 자주 쓰는 플래그들

| 플래그 | 의미 |
|---|---|
| `-p`, `--print` | 비대화형 실행, 결과 출력 후 종료 |
| `--output-format stream-json` | 결과를 JSON 이벤트 스트림으로 출력 (기계 처리용) |
| `--max-turns N` | 에이전트가 도는 최대 턴 수 제한 (폭주 방지용) |
| `--continue` | 이전 대화를 이어서 진행 |
| `--append-system-prompt` | 시스템 프롬프트에 지시문을 덧붙임 |
| `--settings <path>` | 사용할 설정 파일을 명시적으로 지정 |
| `--bare` | **자동 탐색(auto-discovery)을 전면 비활성화** |

### 6-3. 자동 탐색(auto-discovery)과 그 위험

기본적으로 Claude Code는 실행될 때 주변 환경을 스스로 뒤져서 설정을 끌어옵니다.

- 작업 디렉터리의 `CLAUDE.md`, `.claude/settings.json`, `.claude/rules/`
- 작업 디렉터리의 `.mcp.json` (MCP 서버 정의)
- 홈 디렉터리의 `~/.claude/` (전역 설정, 훅, 에이전트 정의)

대화형 개발에서는 편리합니다. 그런데 **CI/CD나 자동화 배치 작업에서는 이게 재앙**이 됩니다.

**MCP(Model Context Protocol)란**: Claude가 외부 시스템(DB, API, 파일 시스템, 사내 도구 등)에
접근할 수 있게 해주는 표준 프로토콜입니다. `.mcp.json`에 서버를 정의하면 그 도구들이
Claude에게 추가로 주어집니다.

**훅(Hook)이란**: 특정 이벤트(도구 실행 전후, 세션 시작/종료 등)에 자동으로 실행되는
사용자 정의 명령입니다. 예를 들어 "파일을 수정한 뒤에는 항상 포매터를 돌린다" 같은 자동화를
설정할 수 있습니다. 훅은 **도구 실행을 차단하거나 입력을 변형할 수도 있습니다.**

### 6-4. 재현성 문제

**상황**: 야간에 도는 보안 점검 작업이 여러 대의 자체 호스팅 러너(self-hosted runner) 중
아무 데서나 실행됩니다. 그런데 러너마다 환경이 미묘하게 다릅니다.

- 어떤 러너의 공유 작업 디렉터리에는 누가 남긴 `.mcp.json`이 있어 낯선 MCP 서버가 붙습니다.
- 어떤 러너의 `~/.claude`에는 동료가 예전에 설정한 훅이 남아 있어 도구 호출이 간섭받습니다.

결과: **같은 명령인데 러너마다 다른 결과.** 이것을 재현성(reproducibility)이 깨졌다고 합니다.
보안 점검처럼 결과를 신뢰해야 하는 작업에서는 치명적입니다.

### 6-5. 해결: `--bare` + 명시적 플래그

`--bare`는 작업 디렉터리와 홈 디렉터리로부터의 **모든 자동 탐색을 끕니다.**
설정도, 훅도, MCP 서버도, 프로젝트 규칙도 자동으로 로드되지 않습니다.

그 위에 **필요한 것만 명시적으로** 플래그로 주입합니다.

```bash
claude -p --bare \
  --settings ./ci/claude-settings.json \
  --append-system-prompt "보안 감사 모드로 동작하고 파일을 수정하지 마라." \
  "의존성의 알려진 취약점을 점검하고 요약해줘"
```

이제 이 명령은 러너 A에서 돌든 러너 B에서 돌든 **동일한 입력, 동일한 동작**을 갖습니다.
환경이 아니라 **명령 자체가 실행 조건을 완전히 서술**하기 때문입니다.

이것은 컨테이너 이미지를 고정 태그로 핀하거나, 패키지 lockfile을 쓰는 것과 같은 사고방식입니다:
**암묵적 환경 의존을 제거하고 모든 것을 명시한다.**

### 6-6. 재현성을 확보하지 못하는 접근들

- **`--output-format stream-json` + 출력 필터링** — 출력에서 훅/MCP 관련 이벤트를 걸러내도,
  그 훅과 MCP 서버는 **이미 실행 중에 동작했습니다.** 파일을 건드렸거나 도구 호출을
  변형했을 수 있습니다. 사후 필터링은 부작용(side effect)을 되돌리지 못합니다.
  로그를 지운다고 일어난 일이 사라지지 않습니다.
- **`--max-turns 2`로 턴 제한** — 턴 수를 줄여도 그 2턴 안에서 훅과 MCP는 정상 동작합니다.
  간섭의 **양**을 줄일 뿐 **원인**을 제거하지 못하며, 애초에 작업이 2턴에 안 끝날 수도 있습니다.
- **`--continue`로 깨끗한 환경의 세션 이어받기** — `--continue`는 **대화 기록**을 복원할 뿐입니다.
  현재 실행되는 러너의 훅과 MCP 자동 탐색은 그대로 일어납니다. 과거 상태를 불러온다고
  현재 환경이 격리되지 않습니다.

**원칙**: 오염은 **발생 전에 차단**해야지, 발생 후에 걸러낼 수 없습니다.

## 7. 전체 개념 지도

이 범위의 모든 내용은 세 가지 원칙으로 압축됩니다.

**원칙 1 — 모호성은 정보로만 해소된다.**
어조를 강하게 하거나 "알아서 해"라고 맡기는 것으로는 해결되지 않습니다.
구체적 예시(퓨샷)나 실행 가능한 테스트(TDD)처럼 **새로운 정보**를 넣어야 합니다.

**원칙 2 — 컨텍스트는 유한한 자원이며, 정밀하게 관리해야 한다.**
- 항상 필요한 것 → 루트 `CLAUDE.md`
- 특정 파일 종류에만 필요한 것 → `.claude/rules/` + `paths` 글로브
- 개인적으로 빼고 싶은 것 → `settings.local.json`의 `claudeMdExcludes`
- 대량의 탐색 출력 → 서브에이전트에 위임하여 격리
- 문서에 경로를 언급만 → 백틱으로 감싸 임포트 방지

**원칙 3 — 자동 편의성은 신뢰성과 상충한다.**
자동 탐색, 자동 임포트, 같은 세션 연속 작업은 편리하지만 각각 오염과 편향을 부릅니다.
신뢰성이 중요한 곳(자동화 파이프라인, 코드 리뷰)에서는 **명시성과 격리**를 택합니다.
`--bare` + 명시적 플래그, 그리고 별도 세션에서의 리뷰가 그 구현체입니다.

## 용어 사전 (Glossary)

**Context Window (컨텍스트 윈도우)** — 모델이 한 번에 다룰 수 있는 텍스트의 총량. 시스템 프롬프트,
메모리 파일, 대화, 도구 출력이 모두 여기에 들어가며 토큰 단위로 측정된다. 유한한 자원이다.

**Token (토큰)** — 텍스트를 모델이 처리하는 최소 단위. 대략 영어 단어 하나 정도의 크기.
비용과 컨텍스트 용량의 계산 단위.

**Few-Shot Prompting (퓨샷 프롬프팅)** — 지시문에 입력→출력 예시 몇 개를 함께 제시해 모델이
규칙을 패턴으로 파악하게 하는 기법. 추상적 서술보다 모호성 제거에 훨씬 효과적이다.

**ISO 8601** — 국제 날짜/시간 표준 표기법. 날짜는 `YYYY-MM-DD` 형식으로, 순서가 고정되어
모호성이 없고 문자열 정렬이 곧 시간 정렬이 된다.

**TDD (Test-Driven Development, 테스트 주도 개발)** — 구현보다 테스트를 먼저 작성하는 방식.
AI 에이전트에게는 실행 가능한 명세이자 스스로 검증·수정할 수 있는 피드백 루프를 제공한다.

**Banker's Rounding (뱅커스 라운딩, 오사오입, half-to-even)** — 정확히 0.5인 값을 가장 가까운
짝수 쪽으로 반올림하는 규칙. `2.5→2`, `3.5→4`. 대량 합산 시 생기는 체계적 상향 편향을 없앤다.

**Discount Stacking Order (할인 중첩 순서)** — 여러 할인을 겹쳐 적용할 때의 순서. 정액 할인과
정률 할인은 순서에 따라 최종 금액이 달라지므로 비즈니스 정책으로 명확히 정의해야 한다.

**CLAUDE.md** — Claude Code가 자동으로 읽어 컨텍스트에 넣는 프로젝트 메모리 마크다운 파일.
루트에 있으면 항상, 하위 디렉터리에 있으면 그 디렉터리의 파일을 다룰 때 로드된다.

**CLAUDE.local.md** — 버전 관리에서 제외되는 개인용 메모리 파일. 팀 공유 목적에는 부적합하다.

**Import (`@path` 임포트)** — `CLAUDE.md` 안에서 `@경로` 표기로 다른 파일의 내용을 실제로 읽어
컨텍스트에 삽입하는 문법. 단순 링크가 아니라 실제 로드다.

**Code Span (코드 스팬)** — 마크다운에서 백틱(`` ` ``)으로 감싼 인라인 코드. 임포트 파서가
내부를 건너뛰므로 `` `@path` ``로 쓰면 파일을 로드하지 않고 경로를 사람에게 보여줄 수 있다.

**`.claude/rules/`** — 주제별로 분리된 모듈형 규칙 파일들을 두는 디렉터리. 조건부 로드를 지원해
필요한 상황에만 컨텍스트를 차지한다.

**YAML Frontmatter (YAML 프론트매터)** — 마크다운 파일 최상단에 `---`로 감싸 넣는 메타데이터
블록. 규칙 파일에서는 여기에 `paths` 등을 선언한다.

**`paths`** — 규칙 파일의 프론트매터 필드. 글로브 패턴 배열로, 여기에 매칭되는 파일을 다룰 때만
그 규칙이 컨텍스트에 로드된다. 스코핑은 오직 이 필드로 선언되며 파일명이나 위치로 추론되지 않는다.

**Glob Pattern (글로브 패턴)** — 와일드카드로 파일 경로를 매칭하는 문법. `*`는 한 세그먼트 내
임의 문자열, `**`는 디렉터리 경계를 넘는 임의 깊이. 와일드카드 없는 리터럴 경로는 하위에
재귀 매칭되지 않는다.

**`settings.json`** — 프로젝트의 `.claude/`에 두는 팀 공유 설정 파일. Git에 커밋되어 팀원 전체에
적용된다.

**`settings.local.json`** — 같은 위치의 개인 전용 설정 파일. 버전 관리에서 제외되어 본인 기기에만
적용되며, 팀에 영향을 주지 않고 환경을 조정할 때 쓴다.

**`claudeMdExcludes`** — 지정한 경로 패턴의 `CLAUDE.md` 자동 로드를 차단하는 설정.
"제외" 기능이며 로드를 유발하는 설정이 아니다.

**Monorepo (모노레포)** — 여러 패키지/프로젝트를 하나의 저장소에서 관리하는 구조.
루트 메모리 파일이 하위 패키지를 모두 임포트하면 컨텍스트 오염이 생기기 쉽다.

**Subagent (서브에이전트)** — 메인 세션과 분리된 독립 컨텍스트에서 작업을 수행하고 요약만
반환하는 보조 에이전트. 대량 탐색의 토큰 비용을 메인에서 격리하는 수단.

**Explore Subagent** — 코드베이스 탐색/검색에 특화된 읽기 전용 서브에이전트. 수백 개 파일에 대한
grep 같은 작업을 자기 컨텍스트에서 처리하고 요약만 돌려준다.

**Context Isolation (컨텍스트 격리)** — 비용이 큰 작업의 중간 산출물을 메인 대화에 유입시키지 않고
분리된 공간에서 처리하는 설계.

**Blind Spot / Context Bias (사각지대 / 컨텍스트 편향)** — 코드를 작성할 때 세운 전제가 같은 세션에
남아 있어, 자기 결과물을 검토할 때 같은 실수를 다시 놓치는 현상. 독립된 신선한 세션에서 리뷰해야
완화된다.

**Plan Mode (플랜 모드)** — 코드를 변경하기 전에 계획을 수립·승인받는 동작 모드. 안전장치이며,
도구 출력을 자동 요약해 주는 기능이 아니다.

**`-p` / `--print` (프린트 모드)** — 대화형 UI 없이 한 번 실행하고 결과를 출력한 뒤 종료하는
비대화형 모드. CI/CD와 스크립트 자동화에 쓴다. 도구를 비활성화하지는 않는다.

**`--bare`** — 작업 디렉터리와 홈 디렉터리로부터의 설정·훅·MCP 서버 자동 탐색을 전면 비활성화하는
플래그. 실행 환경을 격리해 재현 가능한 실행을 만든다.

**`--settings`** — 사용할 설정 파일을 명시적으로 지정하는 플래그. `--bare`와 함께 필요한 설정만
주입할 때 쓴다.

**`--append-system-prompt`** — 시스템 프롬프트 뒤에 추가 지시문을 덧붙이는 플래그.

**`--max-turns`** — 에이전트가 도는 최대 턴 수를 제한하는 플래그. 폭주 방지용이며 환경 격리
수단은 아니다.

**`--continue`** — 이전 대화 상태를 이어받아 실행하는 플래그. 대화 기록만 복원할 뿐 현재 환경의
자동 탐색은 막지 않는다.

**`--output-format stream-json`** — 실행 결과를 기계가 처리하기 좋은 JSON 이벤트 스트림으로
출력하는 옵션. 사후 필터링은 이미 발생한 부작용을 되돌리지 못한다.

**Auto-discovery (자동 탐색)** — 실행 시 주변 디렉터리와 홈 디렉터리에서 설정, 규칙, 훅, MCP 서버를
스스로 찾아 로드하는 동작. 편리하지만 자동화 환경에서는 재현성을 해친다.

**MCP (Model Context Protocol)** — Claude가 외부 시스템(DB, API, 사내 도구 등)에 접근하게 해주는
표준 프로토콜. `.mcp.json`에 서버를 정의하면 해당 도구들이 에이전트에 추가된다.

**Hook (훅)** — 도구 실행 전후 등 특정 이벤트에 자동 실행되는 사용자 정의 명령. 도구 호출을
차단하거나 변형할 수 있어, 의도치 않게 남아 있으면 실행 결과를 오염시킨다.

**Self-hosted Runner (자체 호스팅 러너)** — CI/CD 작업을 실행하는, 조직이 직접 관리하는 머신.
머신마다 남은 설정이 다르면 같은 작업도 다른 결과를 낸다.

**Reproducibility (재현성)** — 언제 어디서 실행하든 같은 입력에 같은 결과가 나오는 성질.
암묵적 환경 의존을 제거하고 실행 조건을 명시함으로써 달성한다.

**Deprecated (더 이상 권장되지 않는)** — 아직 동작하지만 향후 제거 예정이라 새 코드에서 사용을
피해야 하는 API나 함수를 가리키는 표시.
