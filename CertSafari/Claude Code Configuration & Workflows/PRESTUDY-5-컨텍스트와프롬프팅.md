# 5. 컨텍스트 관리와 프롬프팅

## 이 장에서 다루는 것

- **컨텍스트 윈도우와 관리** — 컨텍스트란 무엇이고, 왜 유한하며, 압축(`/compact`)·초기화(`/clear`)·신선한 세션·서브에이전트로 어떻게 관리하는가
- **효과적인 프롬프트 작성** — 모호성 제거, 정보 추가로서의 프롬프트 개선, 얽힌 문제를 한 메시지에 묶기
- **예시 기반 지시(Few-shot)** — 입출력 쌍으로 명세하기, 테스트 우선(TDD)으로 못 박기
- **버그 수정 프롬프팅** — 증상이 아니라 원인, 예시로 정답 보여주기
- **요구사항 도출과 `AskUserQuestion`** — AI가 사람을 인터뷰하는 패턴, 스펙 기반 개발

---

## 1. 컨텍스트 윈도우와 그 관리

### 1.1 컨텍스트란 무엇인가

**컨텍스트(context)** 는 모델이 답을 생성할 때 "지금 눈앞에 보고 있는 모든 텍스트"입니다.
LLM은 매 요청마다 지금까지의 대화 전체를 다시 읽습니다. 이 전체를 담는 그릇이
**컨텍스트 윈도우(context window)** 이고, 크기는 토큰(token) 단위로 제한됩니다.

컨텍스트에 들어가는 것:

- 시스템 프롬프트(에이전트의 기본 행동 지침)
- 자동으로 주입된 프로젝트 지침 파일(`CLAUDE.md` 등)의 내용
- 사용자와 주고받은 모든 대화
- 도구 실행 결과 (파일 내용, grep 출력, 테스트 로그 등)

측정 단위는 토큰입니다. 대략 영어 단어 1개 ≈ 1~2토큰이고, 한글은 글자당 더 많이 듭니다.

그리고 이 장의 절반을 차지하는 핵심 문장:

> **컨텍스트에 없는 정보는 모델에게 존재하지 않는 것과 같습니다.**

파일이 디스크에 멀쩡히 있어도, 컨텍스트에 로드되지 않았다면 모델은 그 지침을 따를 수 없습니다.
모델이 게을러서가 아니라, 알 방법이 없어서입니다.

### 1.2 컨텍스트가 유한하기 때문에 생기는 문제

| 문제 | 내용 |
|---|---|
| **비용/지연** | 대화가 길수록 매 턴 처리할 토큰이 늘어나 요금과 지연시간이 커집니다. |
| **용량 초과** | 윈도우가 가득 차면 앞부분이 잘리거나 요약되면서 정보가 손실됩니다. |
| **오염(pollution / noise)** | 지금 작업과 무관한 옛 내용이 섞이면 모델이 정말 중요한 지시를 놓칩니다. 신호 대 잡음 문제이며, context pollution 또는 clutter라고 부릅니다. |

그래서 이 범위의 문제 대부분은 결국 하나의 질문으로 수렴합니다:
**"필요한 정보만, 필요한 순간에 컨텍스트에 들어오게 하려면 어떻게 설정하는가?"**

### 1.3 관련 있는 것은 반드시 넣어야 한다

예: Claude에게 "이 모듈의 단위 테스트를 새로 만들어줘"라고 하면서 **수정된 소스 코드만** 주면,
Claude는 이미 존재하는 테스트 파일을 볼 수 없습니다. 그러면 이미 커버된 시나리오를 또 만들어 냅니다.

```bash
# 나쁜 예: 소스만 준다
claude -p "src/inventory.ts 에 대한 단위 테스트를 작성해줘"

# 좋은 예: 이미 커버된 내용을 같이 준다
claude -p "src/inventory.ts 의 변경사항에 대해, tests/inventory.test.ts 에
아직 커버되지 않은 케이스만 추가해줘. 두 파일 모두 읽고 비교할 것."
```

일반 원칙: **"모델이 X를 고려하기를 원한다면, X를 컨텍스트에 넣어라."**

이걸 우회하려는 시도들은 대체로 실패합니다.

- **출력 형식을 바꾸고 후처리 스크립트로 중복 걸러내기** → 생성 자체는 여전히 낭비되고 파이프라인만 복잡해집니다. 중복 제거는 "생성 후 필터"가 아니라 **"생성 전 정보 제공"** 으로 푸는 게 맞습니다.
- **예산 상한을 올려 더 많이 생성하게 하기** → 중복이 더 늘어날 뿐입니다.
- **세션 기록 끄기** → 로컬 파일을 인식시키는 것과 무관합니다.

### 1.4 압축(Compaction)과 `/compact`

**Compaction(컨텍스트 압축)** 은 대화가 길어져 컨텍스트 윈도우가 가득 찰 때,
지금까지의 대화를 **요약본으로 대체**해 공간을 확보하는 동작입니다.
자동으로 일어나기도 하고 사용자가 `/compact`로 직접 유발할 수도 있습니다.

압축의 본질:

- 압축은 **메모리(컨텍스트) 상의 정리**입니다. **디스크의 실제 파일은 전혀 건드리지 않습니다.**
  압축이 파일을 손상시키거나 삭제하는 일은 없습니다.
- 압축 후에도 **프로젝트 루트의 `CLAUDE.md`는 자동으로 다시 읽혀 재주입(re-inject)** 됩니다.
  루트 지침은 세션 전체의 기본 규범이므로 항상 살아있도록 설계되어 있습니다.
- 반면 **하위 디렉터리의 중첩 `CLAUDE.md`는 압축 시 컨텍스트에서 빠집니다.**
  이 파일들은 "그 디렉터리 파일을 만질 때 로드되는" 성격이므로,
  압축 이후 Claude가 **다시 그 디렉터리의 파일을 읽는 시점에야 재로드**됩니다.

> **실무적 증상**: 긴 세션에서 압축이 일어난 뒤,
> 루트 지침은 잘 지켜지는데 특정 하위 폴더의 지침만 갑자기 무시되는 것처럼 보입니다.
> 이는 버그가 아니라 위 로딩 규칙의 정상 동작입니다.
> 그 폴더의 파일을 한 번 읽게 하면 지침이 되살아납니다.
>
> **오해**: "압축은 세션의 처음 200줄만 보존한다" 같은 규칙은 **존재하지 않습니다.**

### 1.5 신선한 세션(Fresh Session)과 `/clear`

세션(session)은 하나의 이어지는 대화 단위입니다. 새 세션을 시작하거나 `/clear`를 실행하면
컨텍스트가 비워집니다.

핵심 전략: **탐색/토론 단계와 구현 단계를 서로 다른 세션으로 나눈다.**

탐색 단계에서는 수십 번의 질의응답, 폐기된 아이디어, 읽다 만 파일 내용이 쌓입니다.
그 상태에서 구현을 시작하면 모델은 "이미 버려진 아이디어"까지 참조하며 흔들립니다.
대신 탐색 결과를 **문서로 고정**한 뒤, 새 세션에서 그 문서만 읽히면
컨텍스트는 깨끗하고 정보는 보존됩니다.

| 상황 | 도구 |
|---|---|
| 대화가 길어져 한계에 근접, 맥락은 이어가야 함 | `/compact` (요약으로 대체) |
| 작업이 끝났고 전혀 다른 일로 넘어감 | `/clear` 또는 새 세션 |
| 탐색 → 구현 전환 | 결과를 문서로 고정 후 새 세션 |

### 1.6 서브에이전트(Subagent)

서브에이전트는 **메인 대화와 분리된 컨텍스트를 가진 별도의 에이전트 인스턴스**입니다.
메인 에이전트가 작업을 위임하면, 서브에이전트가 자기만의 컨텍스트에서 일하고
**최종 결과만** 메인에게 돌려줍니다.

```
[메인 대화]  ── 위임 ──▶  [서브에이전트: 파일 40개 읽기, grep 20회 ...]
      ▲                                    │
      └──── "인증 설정은 config/auth.ts에 있음" (요약 결과만) ─────┘
```

메인 컨텍스트에 들어가는 것은 마지막 한 줄짜리 결론뿐입니다.
파일 40개의 원문은 서브에이전트 안에서 소모되고 사라집니다.

**Explore 서브에이전트**는 이 용도에 특화된 읽기 전용 탐색 에이전트입니다.
"이 기능이 어디 구현돼 있지?", "레거시 인증 흐름이 어떻게 돌아가지?" 같은
**넓은 범위의 조사**에 씁니다.

### 1.7 위임할 때와 직접 할 때

| 작업 성격 | 권장 방식 | 이유 |
|---|---|---|
| 넓은 조사 (파일 수십 개 읽기, 전체 탐색) | 서브에이전트 위임 | 산출물이 크고 대부분 버려짐 |
| 좁은 실행 (파일 1개에 필드 1개 추가) | 메인에서 직접 실행 | 위임 오버헤드가 작업보다 큼 |

전형적인 조합: **넓은 조사는 서브에이전트에 위임 → 결론만 받음 → 좁은 수정은 메인에서 직접 수행.**
이것이 "철저함"과 "컨텍스트 효율" 사이의 균형점입니다.

반대로, 조사 자체를 건너뛰고 "그럴듯해 보이는 파일"에 바로 손대는 것은 효율이 아니라 도박입니다.
**이해를 줄이는 것과 출력을 줄이는 것은 다릅니다.**

**함정 — 플랜 모드는 컨텍스트 절약 수단이 아니다.**
**플랜 모드(Plan Mode)** 는 파일을 바꾸기 전에 계획을 세워 검토받는 모드인데,
이것은 *컨텍스트 소모 문제를 해결해 주지 않습니다.*
조사 과정에서 읽은 파일 내용은 플랜 모드에서도 그대로 메인 컨텍스트에 쌓입니다.
게다가 설정 파일 한 줄 고치는 사소한 작업까지 플랜 모드로 감싸면 절차만 무거워집니다.
컨텍스트 절약 수단은 플랜 모드가 아니라 **서브에이전트**입니다.

## 2. 효과적인 프롬프트 작성

### 2.1 모호성(ambiguity)이라는 문제

자연어는 본질적으로 모호합니다. 대표적인 예가 날짜 형식입니다.

```
03/04/25
```

이것은 무엇일까요?

- 미국식(month-first, `MM/DD/YY`): 2025년 3월 4일
- 유럽식(day-first, `DD/MM/YY`): 2025년 4월 3일
- 일부 표기(`YY/MM/DD`): 2003년 4월 25일

사람도 문맥 없이는 못 정합니다. LLM은 더더욱 그렇습니다. 학습 데이터에 두 관습이 모두
들어 있으므로, 같은 프롬프트를 여러 번 줘도 **매번 다르게 해석**할 수 있습니다.
이것이 "일관성 없는 결과(inconsistent interpretation)"의 원인입니다.

> **관련 개념 — ISO 8601**: 국제 표준 날짜 표기법으로 `YYYY-MM-DD` 형태입니다. 예: `2025-03-04`.
> 연-월-일 순서가 고정이라 모호성이 없고, 문자열 정렬 순서가 곧 시간 순서라는 장점이 있어
> 데이터 교환 표준으로 널리 쓰입니다.

같은 함정이 추상적 지시어에도 있습니다. "간결하게 써(concise)", "깔끔하게 해줘",
"적당한 길이로", "주소를 표준 형식으로 정리해줘", "전화번호를 표준 형식으로 정규화해줘" —
사람에게는 자연스럽지만 모델에게는 해석 폭이 매우 넓습니다.
어떤 요청에는 한 문장, 어떤 요청에는 세 단락이 나옵니다.
특히 예외 케이스에서 해석이 갈립니다.

- 주소: 동/호수 누락, 사서함(PO Box), 시골 도로 주소(rural route)
- 전화번호: 내선번호(extension), 국가 코드(international code)

같은 지시를 여러 번 반복해도 매번 다른 결과가 나오는 이유는 지시가 부족해서가 아니라
**정답이 정의되지 않았기 때문**입니다.

### 2.2 프롬프트 개선 = 정보 추가

효과가 **없는** 접근들과 그 이유를 알아두면 방향이 분명해집니다.

| 잘못된 접근 | 왜 안 되는가 |
|---|---|
| 강한 어조로 다시 말하기 ("이번엔 제대로 해!") | **새로운 정보가 0비트**입니다. 모델이 틀리는 이유는 의지 부족이 아니라 정보 부족입니다. |
| `IMPORTANT`, `MUST` 같은 대문자 강조 반복 | 강조는 우선순위를 높일 뿐 "무엇이 정답인지"를 알려주지 않습니다. 모호함은 그대로 남습니다. |
| "알아서 판단해(best judgment)" | 모호성 해소 책임을 모델에게 떠넘기는 것이므로 일관성이라는 목표와 정면 충돌합니다. 자율 판단 = 실행마다 달라질 수 있음. |
| 지시를 아예 빼고 모델에게 맡기기 | 일관성이 더 나빠집니다. |
| 형용사 더 나열하기 ("short, tight, succinct, to the point") | 여전히 추상어입니다. 모호함의 양은 그대로입니다. |
| temperature/창의성 설정 올리기 | temperature는 출력의 무작위성 조절 값입니다. 높이면 **일관성이 더 나빠집니다.** 일관된 형식이 목표라면 정반대 방향입니다. |
| 모호하면 예외 던지기 | 기술적으로는 안전하지만 "자유 형식 문자열을 자동 변환한다"는 **원래 요구사항 자체를 포기**하는 것입니다. |
| 케이스별로 함수 쪼개기 | 같은 목적의 함수를 3개로 나누면 호출하는 쪽이 분기해야 합니다. 복잡도를 호출자에게 전가하는 나쁜 설계입니다. |
| 전체 팀 설계 회의 소집 | 몇 줄짜리 예시로 해결될 문제에 조직 프로세스를 붙이면 오버헤드가 과도합니다. |
| 라이브러리 여러 개 조사 후 다수결 | 시간이 많이 들면서도 사용자가 실제로 원하는 고유 포맷을 보장하지 못합니다. |

교훈: **프롬프트 개선 = 정보 추가.** 어조나 강조가 아니라, 모델이 몰랐던 사실을 넣어야 합니다.

> **stop sequence (중단 시퀀스)**
> 모델 API에는 "이 문자열이 나오면 생성을 즉시 멈춰라"라고 지정하는 `stop_sequences`
> 파라미터가 있습니다. 예를 들어 `["\n\n"]`을 주면 빈 줄이 나오는 순간 멈춥니다.
> 이건 **포맷 경계를 지키는 용도**(예: 다음 예시 블록으로 넘어가는 걸 막기)로 쓰는 것이지,
> **길이를 제어하는 용도가 아닙니다.** 길이 제어에 쓰면 문장이 중간에서 잘려
> 부자연스러운 결과가 나옵니다. 길이는 예시와 명시적 수치("2문장, 40단어 이내")로
> 제어하는 것이 옳습니다.

### 2.3 서로 얽힌 문제는 한 메시지에 함께 준다

Claude는 준 정보만으로 판단합니다. 따라서 **한 지점을 공유하는 여러 문제는 함께 설명해야 합니다.**

먼저 용어부터:

- **임계 영역(critical section)** — 여러 스레드가 동시에 들어가면 안 되는 코드 구간. 보통 락(lock)으로 보호합니다.
- **락킹 동작(locking behavior)** — 어떤 락을 언제 잡고 언제 푸는가. 이것이 바뀌면 그 구간에 의존하는 모든 코드의 전제가 바뀝니다.
- **stale read(오래된 값 읽기)** — 캐시가 제때 무효화되지 않아 낡은 데이터를 읽는 버그.
- **캐시 무효화(cache invalidation)** — 원본이 바뀌었을 때 캐시된 값을 버리는 처리.
- **동시성 버그(concurrency bug)** — 실행 순서/타이밍에 따라 결과가 달라지는 버그.
- **회귀(regression)** — 고치는 과정에서 이전에 잘 되던 것이 깨지는 현상.

**시나리오:** 캐시 무효화 로직의 stale-read 버그를 고치면 락킹 동작이 바뀌는데,
아직 열려 있는 별개의 동시성 버그가 **같은 임계 영역**을 건드린다.

**올바른 대응:** 두 버그를 **하나의 메시지에 함께 기술한다.**
공유 임계 영역을 고치면 다른 버그가 의존하고 있는 락킹 제약이 바뀌기 때문입니다.
전체 맥락을 함께 줘야 두 제약을 동시에 만족하는 통합 설계가 나옵니다.

**잘못된 대응들과 그 이유:**

- stale-read만 먼저 고쳐 머지하고, 나중에 동시성 버그를 **공유 임계 영역 언급 없이** 별도 제출
  → 1차 수정으로 락킹이 이미 바뀌었는데 그 사실을 모르는 상태에서 2차 수정을 하게 되어 회귀가 발생하거나 문제가 더 꼬입니다.
- 둘 중 하나를 무작위로 골라 고치고, 나머지는 CI가 실패할 때만 처리
  → 엔지니어링은 결정론적이어야 합니다. 무작위 선택과 "테스트가 잡아 주겠지"는 설계가 아닙니다.
- 발견 순서 같은 무관한 이유로 하나만 우선하고 다른 하나를 다음 스프린트로 미루기
  → 공유 임계 영역의 무결성이 깨진 채로 방치됩니다.

### 2.4 일반 원칙

- **제약 조건을 함께 준다.** "이 락은 X 순서를 보장해야 한다" 같은 불변식(invariant)을 명시합니다.
- **범위를 명확히 한다.** 어디까지 고쳐야 하고 어디는 건드리면 안 되는지.
- **관련 없는 작업은 섞지 않는다.** 기준은 하나입니다 — **의존 관계가 있으면 합치고, 없으면 나눈다.**

## 3. 예시 기반 지시 (Few-Shot Prompting)

### 3.1 무엇인가

지시문에 **"구체적인 입력 → 기대 출력" 쌍**을 몇 개(few) 함께 보여주는 기법입니다.
예시가 0개면 제로샷(zero-shot), 1개면 원샷(one-shot), 2~5개 정도면 퓨샷(few-shot)입니다.
**예시 기반 지시**, **테스트 주도 프롬프팅(test-driven prompting)** 이라고도 부릅니다.

**왜 효과적인가**: LLM은 패턴 매칭에 강합니다. 추상적 규칙("월을 먼저 해석하라")은
여러 해석의 여지를 남기지만, 구체적 사례는 규칙을 **한 점으로 고정(anchor)** 시킵니다.
산문은 아무리 길게 써도 해석 여지가 남고, 케이스가 늘수록 문장이 서로 충돌합니다.
**예시는 결과물 그 자체이므로 해석의 여지가 없습니다.**
게다가 예시는 나중에 그대로 **테스트 케이스로 재활용**할 수 있습니다.

**핵심 요령**: 경계 사례(edge case)를 예시로 고릅니다. 헷갈릴 수 있는 것을 골라야 값어치가 있습니다.

### 3.2 예시 (1) — 날짜 파싱

```
자유 형식 날짜 문자열을 ISO 8601로 변환하는 함수를 작성해 줘.
숫자로만 된 모호한 입력은 MM/DD/YY(월 우선)로 해석해.

예시:
  "03/04/25"         -> "2025-03-04"
  "the 1st of March" -> "2025-03-01"
  "next Tuesday"     -> "2025-03-11"   (기준일 2025-03-06)
```

`03/04/25 -> 2025-03-04`라는 한 줄이 "월 우선"이라는 규칙을 실제 동작으로 증명합니다.

### 3.3 예시 (2) — 전화번호 정규화

각 애매한 케이스마다 "이 입력이면 이 출력"을 하나씩 보여주면 모호성이 사라집니다.
2~3개면 충분한 경우가 많습니다.

```
입력: "02-123-4567 내선 89"      → 출력: "+82-2-123-4567 x89"
입력: "+1 (415) 555-0100"        → 출력: "+1-415-555-0100"
입력: "010 1234 5678"            → 출력: "+82-10-1234-5678"
```

모델은 구분자, 국가 코드 표기, 내선 표기 규칙을 예시에서 정확히 추론합니다.

### 3.4 예시 (3) — CSV → JSON 변환기

어떤 요구사항은 말로 정확히 기술하기가 어렵습니다. 예를 들어 CSV → JSON 변환기를 만들 때:

- 빈 셀(empty cell)은 `null`인가, 빈 문자열 `""`인가, 아예 키를 생략하는가?
- 따옴표 안의 쉼표(`"Seoul, Korea"`)는 필드 구분자가 아니라 데이터의 일부다 — 어떻게 파싱할 것인가?
- 중복된 헤더(같은 컬럼명이 두 번)는 어떻게 다룰 것인가? 뒤엣것으로 덮어쓰기? 배열로 묶기? 접미사 붙이기?

이런 것들은 산문으로 설명하면 길고 모호해집니다. 대신 **구현을 요청하기 전에**
엣지 케이스를 포함한 샘플 입력과 정확히 기대하는 출력을 짝지어 보여줍니다.

입력:
```csv
name,city,note
Alice,"Seoul, Korea",hello
Bob,,
```

기대 출력:
```json
[
  {"name": "Alice", "city": "Seoul, Korea", "note": "hello"},
  {"name": "Bob", "city": null, "note": null}
]
```

이 한 쌍이 "빈 셀은 null로", "따옴표 안 쉼표는 값의 일부로"라는 두 규칙을
모호함 없이 전달합니다. 산문 설명보다 짧고 정확합니다.

### 3.5 예시 (4) — 요약 스타일 고정

"간결하게"라는 형용사 대신 실제 예시를 넣으면 길이·톤·문장 구조·포맷이 한꺼번에 고정됩니다.

```
다음 형식으로 기사를 요약하라.

[예시 1]
기사: (원문 …)
요약: 국내 배터리 3사가 3분기 합산 영업이익 1.2조 원을 기록하며 전년 대비 18% 성장했다.

[예시 2]
기사: (원문 …)
요약: 미 연준이 기준금리를 0.25%p 인하했고, 시장은 연내 추가 인하 가능성에 무게를 두고 있다.

[실제 입력]
기사: {{article}}
요약:
```

여기서 "concise"라는 단어는 이제 **구체적 사례에 고정**됩니다.

### 3.6 반복적 개선 루프(iterative refinement loop)

예시를 먼저 주는 방식은 그 자체로 좋은 피드백 루프를 만듭니다.

```
1. 입출력 예시 제시   → 요구사항이 명확해짐
2. 구현
3. 예시가 곧 테스트 케이스 → 검증
4. 어긋나면 예시 추가/수정 → 다시 구현
```

**예시는 명세이자 동시에 테스트입니다.**

### 3.7 좋지 않은 대안들과 그 이유

- **예시 없이 먼저 다 짜게 하고 나중에 말로 고친다** — 잘못된 전제 위에 코드가 쌓입니다. 그리고 "말로 설명하기 어렵다"는 것이 애초의 문제였으므로, 사후에 말로 설명하는 것도 똑같이 어렵습니다.
- **인기 있는 라이브러리의 기본 동작에 맡긴다** — 기본값이 우리 도메인 요구와 일치한다는 보장이 없습니다. 특히 빈 셀/중복 헤더 처리는 라이브러리마다 다릅니다. 라이브러리를 쓰는 것 자체는 좋지만, **기대 동작을 명시하지 않고 기본값에 위임하는 것**이 문제입니다.
- **엣지 케이스는 TODO 주석으로 남기고 넘어간다** — 핵심 요구사항을 미해결로 남긴 채 완료 처리하는 것이고, 반복 개선 루프를 아예 만들지 않습니다.

### 3.8 한 단계 더 — 테스트를 먼저 주기 (Test-First / TDD with AI)

**TDD란**: Test-Driven Development. 구현 코드보다 **테스트를 먼저** 쓰는 개발 방식입니다.
테스트가 곧 "무엇이 옳은가"에 대한 실행 가능한 명세(executable specification)가 됩니다.

**AI 에이전트에게 왜 특히 강력한가**: Claude Code는 셸을 실행할 수 있으므로 테스트를 직접
돌릴 수 있습니다. 그러면 다음 루프가 자동으로 돕니다.

```
코드 작성 → 테스트 실행 → 실패 확인 → 원인 분석 → 수정 → 다시 실행 → 전부 통과
```

이것을 **자율 피드백 루프(autonomous feedback loop)** 라고 합니다.
사람이 "아니 그게 아니고..." 하며 매번 개입하는 왕복(back-and-forth) 횟수가 극적으로 줄어듭니다.
게다가 테스트는 자연어 명세와 달리 **해석의 여지가 없습니다.** 통과 아니면 실패, 둘 중 하나입니다.

**언제 특히 유용한가**: 도메인 규칙이 미묘하고 틀리기 쉬울 때.

#### 관련 도메인 개념 (1) — 뱅커스 라운딩 (Banker's Rounding)

정확히 0.5인 값을 어느 쪽으로 반올림할지에 대한 규칙입니다.

- **일반 반올림(half-up)**: 0.5는 항상 올림. `2.5 -> 3`, `3.5 -> 4`
- **뱅커스 라운딩(half-to-even, 오사오입)**: 0.5는 **가장 가까운 짝수** 쪽으로.
  `2.5 -> 2`, `3.5 -> 4`, `0.125 -> 0.12`, `0.135 -> 0.14`

**왜 존재하는가**: half-up은 항상 위로 올리므로 값을 많이 더할수록 총합이 계속 커지는
**체계적 편향(bias)** 이 생깁니다. 금융/회계에서 수백만 건을 합산하면 무시할 수 없습니다.
짝수 쪽으로 번갈아 보내면 이 편향이 통계적으로 상쇄됩니다.
IEEE 754 부동소수점 표준의 기본 반올림 방식이기도 하며,
파이썬 `round()`와 `decimal.ROUND_HALF_EVEN`이 이 방식입니다.

```python
round(2.5)   # 2   (파이썬3은 뱅커스 라운딩)
round(3.5)   # 4
```

이런 규칙은 줄글로 설명하면 반드시 오해가 생깁니다. 테스트 케이스로 못 박는 게 정답입니다.

```python
def test_bankers_rounding():
    assert round_cents(2.505) == 2.50
    assert round_cents(2.515) == 2.52
```

#### 관련 도메인 개념 (2) — 할인 중첩 순서 (Discount Stacking Order)

할인이 여러 개 겹칠 때 **적용 순서에 따라 최종 금액이 달라집니다.**
곱셈과 뺄셈은 교환법칙이 성립하지 않기 때문입니다.

정가 100, 쿠폰 -10(정액), 회원 할인 -20%(정률)라고 합시다.

- 정액 먼저: `(100 - 10) × 0.8 = 72`
- 정률 먼저: `100 × 0.8 - 10 = 70`

2원 차이입니다. 여기에 세금, 배송비, 최소 주문 금액 조건까지 얽히면 순서 규칙은 회사의
비즈니스 정책 문제가 됩니다. "일반적으로 이커머스에서 흔한 방식"으로 추측하게 두면 안 되는
전형적인 영역입니다. 마찬가지로 테스트로 고정합니다.

**정리**: 규칙이 미묘 → **예시로 보여준다(퓨샷)**. 규칙이 미묘 + 검증 가능 → **테스트로 못 박는다(TDD)**.

## 4. 효과적인 버그 수정 프롬프팅

### 4.1 에지 케이스(Edge Case)

정상 경로가 아닌 경계 조건에서만 나타나는 상황입니다.
예: 값이 `null`, 빈 리스트, 0, 음수, 아주 긴 문자열, 유니코드 문자.

예시 상황: 레거시 고객 데이터를 새 스키마로 옮기는 마이그레이션 스크립트에서,
`middle_name`이 `null`인 레코드가 **빈 문자열로 변환되어야 하는데 아예 누락**되고 있습니다.

### 4.2 구체적 예시로 지시하기

가장 효과적인 수정 요청은 **입력과 기대 출력을 나란히 보여주는 것**입니다.

```
입력:
  { "first_name": "Kim", "middle_name": null, "last_name": "Lee" }

기대 출력:
  { "first_name": "Kim", "middle_name": "", "last_name": "Lee" }

현재는 이 레코드가 결과에서 통째로 빠집니다.
```

이렇게 주면 모델은 (1) 어느 필드인지, (2) 어떤 조건인지, (3) 무엇이 정답인지를
추측 없이 알게 됩니다. 게다가 이 예시는 그대로 회귀 테스트로 굳힐 수 있습니다.

### 4.3 비효율적인 대안들과 그 이유

- **모호한 신고** ("null 관련 버그가 있어") — 어느 필드인지, 정답이 무엇인지 알 수 없어 엉뚱한 곳을 고칩니다.
- **전면 재작성 / 언어 교체** — 한 줄짜리 조건 분기 문제에 스크립트 전체를 다른 언어로 다시 쓰는 것은 비용만 크고 해결을 보장하지 못합니다.
- **광범위한 예외 삼키기** — 변환 함수 전체를 `try/except`로 감싸 오류 레코드를 조용히 건너뛰면, 증상(에러 로그)만 감추고 원인(데이터 유실)은 그대로입니다. 오히려 유실이 눈에 안 보이게 됩니다.

원칙: **증상이 아니라 원인을 고치고, 정확히 무엇이 정답인지 예시로 보여준다.**

## 5. 요구사항 도출과 `AskUserQuestion`

### 5.1 `AskUserQuestion` 도구

`AskUserQuestion`은 Claude Code가 **사용자에게 선택지가 있는 질문을 던지고 답을 받아오는** 도구입니다.
자유 서술로 되묻는 대신 구조화된 질문과 선택지 형태로 물어,
사용자가 빠르게 답하고 그 답이 그대로 설계 입력이 됩니다.

방향이 평소와 반대입니다 — **사람이 AI에게 묻는 게 아니라, AI가 사람을 인터뷰합니다.**
사용자가 "이 기능을 만들고 싶은데, AskUserQuestion으로 나를 상세히 인터뷰해 줘"라고 요청하면,
에이전트는 요구사항을 캐내는 **대화형 요구사항 도출(interactive requirements elicitation)** 진행자가 됩니다.

### 5.2 왜 인터뷰가 필요한가

복잡한 시스템 설계에서 가장 큰 실패 원인은 **"말해주지 않은 전제"** 입니다.
그리고 경험이 없는 도메인에서는 아키텍트 스스로도 **무엇을 모르는지조차 모릅니다.**

"지원 티켓 검색 기능을 만들어 줘" 같은 한 줄 요청에는 결정되지 않은 사항이 수십 개 숨어 있습니다.

- **랭킹(ranking)**: 결과를 어떤 순서로 보여줄 것인가? 최신순? 관련도순? 우선순위 가중치?
- **필터링(filtering)**: 상태·담당자·기간·태그 중 무엇으로 걸러낼 수 있어야 하는가?
- **실패 모드(failure mode)**: 검색 인덱스가 다운되면? 결과가 0건이면? 쿼리가 너무 길면? 타임아웃은?

이런 항목이 정해지지 않은 채 구현에 들어가면 에이전트는 "일반적인 관행"으로 빈칸을 채웁니다.
그럴듯하지만 실제 요구와 어긋난 코드가 나옵니다.
질문 두세 개만 답하고 나머지를 모델의 추정에 맡기는 것도 같은 결과를 낳습니다.

> **DB 스키마만 던져주면 되지 않나?** 안 됩니다.
> 스키마는 데이터의 *모양*(필드 이름, 타입, 관계)을 알려줄 뿐, *비즈니스 의도*는 담고 있지 않습니다.
> 필드 이름과 타입에서 "고객사 티켓을 우선 노출한다" 같은 규칙을 추론할 수는 없습니다.

핵심 가치: 모델은 그 도메인의 일반적 함정을 알고 있으므로,
**사용자가 질문할 줄 몰랐던 것을 질문해 줍니다.**
설계 결함을 코드 작성 전에 잡는 것이 가장 저렴합니다.

### 5.3 인터뷰에서 드러나는 전형적 함정들

**분산 시스템 계열**

- **실패 모드(failure mode)**: 정상 동작이 아니라 무언가 고장 났을 때의 동작. 예) 특정 리전이 통째로 다운되면?
- **네트워크 파티션(network partition)**: 시스템 일부가 서로 통신하지 못하도록 네트워크가 갈라진 상태.
- **스플릿 브레인(split-brain)**: 파티션 상황에서 양쪽이 각자 자기가 주인이라 믿고 따로 쓰기를 받아들여 데이터가 갈라지는 문제. 그래서 "어느 쪽이 권한(authoritative)을 갖는가"를 미리 정해야 합니다.
- **상태 조정(reconciliation)**: 파티션이 복구된 뒤 갈라졌던 데이터를 어떻게 합칠 것인가.
- **페일오버(failover)**: 장애 시 예비 자원으로 자동 전환하는 것.
- **일관성 트레이드오프**: 강한 일관성을 택하면 가용성과 지연이 나빠지고, 최종적 일관성을 택하면 일시적 불일치를 감수합니다.

**실시간 협업 문서 편집기 계열**

- **cache invalidation (캐시 무효화)**: 캐시에 저장된 데이터가 언제 낡은 것이 되는지, 어떻게 갱신·폐기할지. 분산 환경에서 가장 어려운 문제 중 하나입니다.
- **conflict resolution (충돌 해결)**: 두 사용자가 같은 문서의 같은 부분을 동시에 편집했을 때 결과를 어떻게 하나로 합칠지. (OT, CRDT 같은 접근법이 존재)
- **failure handling (실패 처리)**: 네트워크가 끊기거나 서버가 죽었을 때 편집 내용을 어떻게 보존·복구할지.

이런 항목들은 사용자가 먼저 떠올리기 어렵고,
Claude 입장에서는 코드만 봐서는 알 수 없는 **비즈니스 판단**입니다.

### 5.4 권장 인터뷰 패턴

1. Claude에게 만들려는 기능/목표를 **간략히** 설명한다.
2. **구현 전에**, `AskUserQuestion`을 사용해 나를 인터뷰해 달라고 요청한다
   — **뻔하지 않은 부분**(기술적 구현 방식, 엣지 케이스, 실패 모드, 트레이드오프, 제약)을 훑도록.
3. 그 문답을 통해 몰랐던 고려사항이 드러난다.
4. 확정된 답을 근거로 **명세(spec)를 작성**하고, 그 다음 구현에 들어간다.

### 5.5 명세서(Spec)와 스펙 기반 개발

**Spec-driven development**: 대화로 도출한 요구사항을 **독립적으로 완결된 명세 문서**로
먼저 고정하고, 그 문서를 기준으로 구현하는 방식입니다.

좋은 스펙의 요건:

| 요건 | 내용 |
|---|---|
| **자립적(self-contained)** | 이 문서만 읽으면 구현할 수 있어야 합니다. "아까 대화에서 말한 그거"에 의존하면 안 됩니다. |
| **구체적** | 관련 파일 경로와 인터페이스(함수 시그니처, 타입, 엔드포인트)를 명시합니다. |
| **결정 사항이 빠짐없이 기록됨** | 랭킹 규칙, 필터 목록, 에러 처리 정책까지. |

**왜 "대화 기록(transcript)"으로는 부족한가**: 대화 기록은 길고, 순서가 뒤섞이고,
중간에 뒤집힌 결정이 그대로 남아 있으며, 새 세션으로 옮길 수 없습니다.
스펙은 그 대화의 **정제된 결과물**입니다.

전체 흐름 (1장의 "신선한 세션" 전략과 정확히 맞물립니다):

```
한 줄 요청
  → AskUserQuestion 인터뷰 (랭킹·필터·실패 모드까지 전부 확정)
  → 자립형 스펙 문서 작성 (파일·인터페이스 명시)
  → 새 세션 시작 (컨텍스트 초기화)
  → 스펙만 읽히고 구현에 집중
```

### 5.6 열등한 대안들과 그 이유

- **검토 없이 바로 구현하고, 실제 운영 장애가 터지면 고친다** — 위험을 운영으로 전가하는 방식입니다.
- **일반 튜토리얼의 기본값을 서비스 제약 고려 없이 그대로 채택** — 우리 시스템의 제약과 무관한 선택이 굳어집니다.
- **사람이 혼자 모든 시나리오를 사전에 완벽히 문서화** — 공수가 과도하고, 경험 없는 도메인에서는 애초에 불가능하며 누락이 대량 발생합니다. 상호작용의 이점도 사라집니다.
- **오픈소스 프로젝트의 아키텍처를 그대로 복제** — 그 프로젝트의 제약과 우리 시스템의 제약이 다릅니다. 트레이드오프 검토 과정 자체가 생략되어, 왜 그렇게 만들어졌는지 모른 채 따라가게 됩니다.
- **일단 최소 구현 후 수동 테스트로 버그를 찾아 설계를 역산** — 아키텍처 결함을 구현 이후에 발견하면 **재작업(rework) 비용이 폭증**합니다. 선제적 설계 도출 전략이 아닙니다.

## 6. 이 장의 요약

| 상황 | 처방 |
|---|---|
| 모델이 기존 파일/테스트를 고려 안 함 | 그 파일을 컨텍스트에 넣어라 — "없으면 존재하지 않는 것" |
| 대화가 길어져 한계 근접 | `/compact` (파일은 안 건드림, 루트 `CLAUDE.md`는 재주입) |
| 하위 폴더 지침이 갑자기 무시됨 | 압축 후 정상 동작. 그 폴더 파일을 한 번 읽히면 되살아남 |
| 탐색 → 구현 전환 | 결과를 문서로 고정 후 `/clear` 또는 새 세션 |
| 넓은 조사로 컨텍스트가 폭발 | 서브에이전트(Explore)에 위임, 결론만 받기 (플랜 모드는 해결책이 아님) |
| 결과가 매번 다르게 나옴 | 어조·강조·temperature가 아니라 **정보 추가** — 퓨샷 예시 |
| 규칙이 미묘하고 검증 가능 | 테스트로 못 박기 (TDD) |
| 버그 신고 | 입력 / 기대 출력 / 현재 동작을 나란히 제시 |
| 얽힌 버그 여러 개 | 의존 관계가 있으면 한 메시지에, 없으면 나눠서 |
| 한 줄짜리 모호한 기능 요청 | `AskUserQuestion` 인터뷰 → 자립형 스펙 → 새 세션에서 구현 |
