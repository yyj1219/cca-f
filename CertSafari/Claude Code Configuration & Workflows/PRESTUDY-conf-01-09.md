# 사전 학습 노트 — Claude Code 설정과 워크플로 (conf-01-09)

이 문서는 Claude Code를 전혀 모르는 사람이 처음부터 읽고 이해할 수 있도록 쓴 개념 설명서입니다.
용어 하나하나를 "그게 뭔지 → 왜 있는지 → 어떻게 동작하는지 → 언제 쓰는지" 순서로 설명합니다.

---

## 0. 큰 그림: Claude Code란 무엇인가

**Claude Code**는 Anthropic이 만든 **CLI(명령줄) 기반 코딩 에이전트**입니다.
터미널에서 `claude` 명령으로 실행하면, AI가 여러분의 코드베이스를 직접 읽고(Read), 검색하고(Grep/Glob), 파일을 수정하고(Edit/Write), 명령을 실행(Bash)합니다.

일반 챗봇과 다른 핵심 차이는 세 가지입니다.

1. **파일시스템에 실제로 접근한다** — 그래서 "권한(permission)"이라는 개념이 필요합니다.
2. **여러 턴에 걸쳐 반복 작업한다** — 그래서 "워크플로 선택"과 "컨텍스트 관리"가 중요합니다.
3. **설정 파일로 행동을 조종할 수 있다** — 그래서 `CLAUDE.md`, `.claude/rules/`, `.claude/skills/` 같은 계층 구조가 있습니다.

이 노트는 이 세 축(권한/모드, 워크플로, 설정 계층)을 차례로 다룹니다.

## 1. 권한 모드 (Permission Modes)

### 1.1 왜 권한 모드가 필요한가

AI가 파일을 마음대로 지우거나 위험한 명령을 실행하면 곤란합니다.
그래서 Claude Code는 "어디까지 사람 확인 없이 진행해도 되는가"를 **모드**로 구분합니다.
모드는 위험도를 조절하는 다이얼이라고 생각하면 됩니다.

### 1.2 각 모드

| 모드 | 동작 | 쓰는 상황 |
|---|---|---|
| **default** | 파일 수정·명령 실행마다 사용자에게 승인 요청 | 가장 안전한 기본값 |
| **acceptEdits** (accept-edits) | 파일 편집은 자동 승인, 그 외(예: 위험한 Bash)는 여전히 확인 | 방향이 확실한 반복 편집 작업 |
| **plan** (계획 모드) | **파일을 전혀 수정하지 않음.** 읽기·검색만 하고 마지막에 "설계안"을 제출 | 큰 변경 전 설계 검토 |
| **bypassPermissions** | 모든 확인을 건너뜀 | 격리된 샌드박스/CI에서 매우 제한적으로만 |

### 1.3 계획 모드(Plan Mode) 상세

**무엇인가:** Claude가 코드베이스를 탐색해서 이해한 뒤, **수정하기 전에 사람에게 계획서를 제출**하는 모드입니다. 사람이 승인해야 비로소 실행 단계로 넘어갑니다.

**왜 있는가:** 큰 아키텍처 변경에서는 "어떻게 고칠지"보다 "어느 방향으로 나눌지"가 훨씬 중요합니다. 잘못된 방향으로 200개 파일을 고친 뒤에 되돌리는 비용은 막대합니다. 계획 모드는 그 되돌리기 비용을 **0으로** 만듭니다 — 아직 아무것도 안 고쳤으니까요.

**어떻게 동작하는가:**
1. Claude가 관련 파일을 읽고 구조를 파악
2. 여러 대안(예: 서비스 경계를 A/B/C로 나누는 세 가지 안)을 비교
3. 트레이드오프와 함께 설계안 제시
4. 사람이 승인 / 수정 요청 / 거부
5. 승인 시에만 편집 시작

**언제 쓰는가 (판단 기준):**
- 변경이 **여러 파일 / 여러 모듈**에 걸친다
- **정답이 여러 개**다 (설계 선택지가 경쟁 관계)
- 되돌리기 비용이 크다 (데이터 모델, 서비스 경계, 배포 구조 등)
- 예: 모놀리스를 마이크로서비스 3개로 쪼개는 작업 → 공유 데이터 모델, 서비스 경계, 배포 토폴로지가 모두 얽힘 → **계획 모드가 정석**

**언제 안 쓰는가:** 원인이 이미 명확하고 한 줄 고치면 되는 일. 계획 모드는 안전장치이지 의무적인 의식(ritual)이 아닙니다.

### 1.4 bypassPermissions 주의점

모든 승인 절차를 없애므로 사람의 검토 지점이 사라집니다.
아키텍처 수준의 의사결정을 이 모드로 CI에 맡기면, 잘못된 설계가 사람 눈을 거치지 않고 머지됩니다.
"자동화 = 좋음"이 아니라 **"검토가 필요 없는 일만 자동화"** 가 원칙입니다.

## 2. 작업 규모에 맞는 워크플로 고르기

Claude Code에서 같은 일을 하는 방법은 여러 가지입니다. 핵심은 **작업 규모와 절차의 무게를 맞추는 것**입니다.

### 2.1 직접 실행 (Direct Execution)

**무엇인가:** 별도 계획·위임 없이 그냥 시키는 것. "이 파일 이 함수에 null 체크 추가해줘."

**언제:**
- 원인이 이미 특정됨 (예: 스택 트레이스가 파일·함수·줄을 정확히 가리킴)
- 범위가 단일 파일 / 소수 파일
- 수정 내용이 자명함 (한 줄 조건문 추가 등)

**왜 이게 맞는가:** 절차 자체에도 비용이 있습니다. 계획서 작성, 승인 대기, 세션 분리는 모두 시간과 토큰을 씁니다. 한 줄 고치는 데 다단계 계획을 세우는 것은 순수한 낭비입니다.

### 2.2 계획 모드 (위 1.3 참조)

큰 설계 결정이 필요할 때.

### 2.3 서브에이전트 위임 (Subagent Delegation)

**무엇인가:** 별도의 격리된 AI 인스턴스를 띄워서 하위 작업을 시키고, **결과 요약만** 메인 대화로 가져오는 것. `Explore` 서브에이전트가 대표적입니다.

**왜 있는가:** **컨텍스트 오염 방지**. 예를 들어 "이 기능이 어디에 구현돼 있지?"를 알아내려고 파일 50개를 뒤지면, 그 50개 파일 내용이 전부 메인 대화 컨텍스트를 잡아먹습니다. 서브에이전트에게 시키면 서브에이전트 쪽에서만 그 50개를 읽고, 메인에는 "여기 있습니다: src/foo.ts:120" 한 줄만 돌아옵니다.

**언제:**
- 어디를 봐야 할지 모르는 **광범위한 탐색**
- 여러 독립 조사를 **병렬**로 돌리고 싶을 때

**언제 안 쓰는가:** 이미 위치와 원인을 아는 작업. 탐색할 게 없는데 탐색 에이전트를 부르는 것은 오버헤드입니다.

### 2.4 다단계 계획 / 세션 분리

리서치 세션과 구현 세션을 나누는 방식. 정말 큰 프로젝트에서만 의미가 있고, 작은 수정에 적용하면 순전한 관료주의입니다.

### 2.5 규모 매칭 원칙 요약

```
변경 범위 작음 + 원인 명확        → 직접 실행
변경 범위 큼   + 선택지 여럿      → 계획 모드
탐색 범위 큼   + 위치 모름        → 서브에이전트 위임
```

절차의 무게는 **작업의 불확실성과 되돌리기 비용**에 비례해야 합니다.

## 3. 테스트 주도 반복 (Test-Driven Iteration)

### 3.1 TDD 기본

**TDD(Test-Driven Development)** 는 "테스트를 먼저 쓰고, 그 테스트를 통과시키는 코드를 나중에 쓴다"는 개발 방식입니다.

순서: **실패하는 테스트 작성 → 구현 → 테스트 통과 → 리팩터링**

### 3.2 왜 AI 에이전트와 특히 잘 맞는가

AI에게 "레이트 리미터 만들어줘"라고만 하면, AI는 **요구사항을 추측**합니다. 초당 몇 개? 버스트는 허용? 윈도우 리셋은 언제? 추측이 틀리면 사람이 보고 지적하고, 다시 고치고 — 이 **수정 주기(correction cycle)** 가 반복됩니다.

테스트를 먼저 쓰면:
- 요구사항이 **실행 가능한 명세**로 고정됩니다 (모호함 제거)
- AI가 **스스로 채점**할 수 있습니다 (테스트 돌려보고 실패하면 자기가 고침)
- 사람은 "이거 틀렸어"라고 설명할 필요 없이 **테스트 실패 출력을 그대로 붙여넣으면** 됩니다

결과적으로 사람이 개입하는 수정 주기 횟수가 크게 줄어듭니다.

### 3.3 구체적 예 — 레이트 리미터

먼저 테스트 스위트를 요청합니다. 다뤄야 할 것:
- **스로틀링 동작(throttling behavior)**: 한도를 넘으면 거부(예: HTTP 429)하는가
- **버스트 제한(burst limit)**: 순간적으로 몰린 요청을 몇 개까지 허용하는가
- **리셋 타이밍(reset timing / window reset)**: 윈도우가 언제 초기화되어 다시 허용되는가

```python
def test_allows_up_to_limit():
    rl = RateLimiter(limit=5, window=1.0)
    assert all(rl.allow("user1") for _ in range(5))

def test_blocks_over_limit():
    rl = RateLimiter(limit=5, window=1.0)
    for _ in range(5):
        rl.allow("user1")
    assert not rl.allow("user1")

def test_resets_after_window():
    rl = RateLimiter(limit=5, window=1.0)
    for _ in range(5):
        rl.allow("user1")
    time.sleep(1.1)
    assert rl.allow("user1")
```

그 다음 구현을 요청하고, 실패한 테스트 출력을 그대로 공유하며 반복합니다.

### 3.4 대비되는(덜 좋은) 접근

- **수동 검증만**: 터미널에서 curl로 몇 번 찔러보고 헤더 확인 — 재현 불가능, 회귀 감지 불가
- **설계 문서만 쓰고 구현**: 문서는 실행되지 않으므로 자동 검증이 안 됨
- **구현 후 테스트 작성**: 이미 만들어진 동작을 사후 문서화하는 것이라, 잘못 구현된 동작도 그대로 "정답"으로 굳어짐

## 4. 피드백을 Claude에게 전달하는 방법

### 4.1 원칙: 구체적으로, 그리고 한 번에 하나씩

AI 에이전트는 **컨텍스트 안에서 인과관계를 추론**합니다. 그래서 무엇을 어떻게 묶어서 전달하느냐가 결과를 바꿉니다.

### 4.2 독립적인 여러 버그가 나왔을 때

예: 테스트 실행 결과 두 개가 실패
1. 요약 합계의 **통화 서식(currency formatting) 불일치**
2. Windows 경로에서 **파일 확장자 누락**

이 둘은 **서로 무관(independent)** 합니다.

**권장:** 각각 별도 메시지로 순차 처리. 첫 번째를 고치고 확인한 뒤 두 번째를 전달.

**왜:**
- AI가 한 번에 하나의 문제에만 집중 → 수정 정확도 상승
- 각 수정의 결과를 개별적으로 검증 가능 → 어떤 변경이 무엇을 고쳤는지 명확
- 여러 변경이 섞이면 회귀가 생겨도 원인 추적이 어려워짐

### 4.3 하지 말아야 할 세 가지 패턴

**(a) 무관한 버그를 "하나의 상호작용하는 결함"으로 묶어 전달**
→ AI가 존재하지 않는 인과관계를 추론합니다. "통화 포맷터가 파일명 생성기에 영향을 준다"고 잘못 가정하고, 멀쩡한 공통 코드를 건드리는 식의 잘못된 수정이 나옵니다.

**(b) 일부 실패를 숨기고 나중으로 미루기**
→ 정보를 감출 이유가 없습니다. 알고 있는 결함은 전달하되 순서만 조절하면 됩니다. 숨기면 나중에 불필요한 왕복만 늘어납니다.

**(c) 구체적 정보 없이 "알아서 심각한 것부터 고쳐"**
→ 정확한 증상(어떤 값이 기대되었고 실제로 무엇이 나왔는지)을 빼면 AI는 추측할 수밖에 없습니다. 결과가 모호하고 통제 불가능해집니다. **에러 메시지·기대값·실제값을 그대로 붙여넣는 것**이 가장 좋은 피드백입니다.

## 5. 설정 파일 계층 — CLAUDE.md

### 5.1 CLAUDE.md란

`CLAUDE.md`는 **Claude에게 주는 프로젝트 지침서**입니다. 마크다운 파일이고, Claude Code가 세션 시작 시 자동으로 읽어서 컨텍스트에 넣습니다.

담는 내용의 예:
- 빌드/테스트 명령어 (`npm run test:unit`)
- 코드 스타일 규칙
- 아키텍처 설명, 디렉터리 구조
- 하지 말아야 할 것들

### 5.2 위치별 종류

| 위치 | 범위 | 커밋 여부 |
|---|---|---|
| `~/.claude/CLAUDE.md` | **사용자(개인) 수준** — 그 머신의 모든 프로젝트에 적용 | 커밋 안 됨 (홈 디렉터리) |
| `<프로젝트루트>/CLAUDE.md` | **프로젝트 수준** — 팀 전체 공유 | 보통 커밋함 |
| `<하위디렉터리>/CLAUDE.md` | **디렉터리 수준** — 해당 하위 트리에서만 | 커밋함 |
| `CLAUDE.local.md` | 프로젝트 안의 개인용 (해당 프로젝트 한정) | 보통 `.gitignore` |
| 관리형 정책(managed policy) CLAUDE.md | **조직/엔터프라이즈 수준** — IT가 배포, 개인이 편집 불가 | 조직 관리 |

### 5.3 하위 디렉터리 CLAUDE.md — 모노레포의 핵심

**문제 상황:** 모노레포가 `packages/api`, `packages/web`, `packages/shared`로 구성돼 있습니다. api 팀은 자기네 DB 규칙과 테스트 규칙이 있는데, 이걸 루트 `CLAUDE.md`에 넣으면 web 작업 중에도 불필요하게 로드되어 컨텍스트를 낭비합니다.

**해결:** `packages/api/CLAUDE.md`를 만듭니다.

**로딩 방식 두 가지:**
1. **시작 시 로드(at launch)** — Claude를 `packages/api` 디렉터리에서 실행하면, 그 디렉터리의 `CLAUDE.md`가 자동으로 로드됩니다.
2. **온디맨드 로드(on demand)** — 루트에서 시작했더라도, Claude가 `packages/api/` 안의 파일을 읽는 순간 그 디렉터리의 `CLAUDE.md`를 함께 끌어옵니다.

이 두 가지 덕분에 "필요할 때만 로드"가 자동으로 성립합니다. 루트 파일을 오염시키지 않고, 중복도 없습니다.

### 5.4 임포트 문법 `@경로`

`CLAUDE.md` 안에서 다른 파일을 끌어올 수 있습니다.

```markdown
# 프로젝트 규칙
@docs/architecture.md
@packages/shared/CONVENTIONS.md
```

**주의점:**
- 루트 `CLAUDE.md`에서 `@packages/api/CLAUDE.md`를 임포트하면 **작업 디렉터리와 무관하게 항상 로드**됩니다. "api에서 작업할 때만"이라는 요구와는 정반대가 됩니다.
- 파일이 **자기 자신을 임포트**하는 것은 순환 참조라 무의미하며 유효하지 않습니다.
- 임포트는 "항상 필요한 공통 문서"에 쓰고, "특정 영역에서만 필요한 규칙"은 그 위치에 파일을 두는 방식(5.3)이 맞습니다.

## 6. 설정 파일 계층 — `.claude/rules/`

### 6.1 rules 디렉터리란

`.claude/rules/` 는 규칙 문서들을 **여러 개의 파일로 쪼개어** 관리하는 디렉터리입니다. `CLAUDE.md` 하나에 전부 몰아넣는 대신, 주제별로 분리합니다.

```
.claude/rules/
├── security.md
├── code-review.md
├── testing.md
└── style.md
```

Claude Code는 이 디렉터리를 스캔해서 안의 규칙 파일들을 읽어들입니다.

### 6.2 사용자 수준 rules — `~/.claude/rules/`

홈 디렉터리의 `~/.claude/rules/`에 둔 규칙은 **그 머신의 모든 프로젝트에 적용**되고, **어떤 프로젝트 저장소에도 커밋되지 않습니다.**

**전형적 용도:** 개인 편집기 취향, 서식 선호(들여쓰기, 따옴표 스타일 등), "설명은 한국어로" 같은 개인 습관.

**왜 여기인가:**
- 프로젝트 저장소를 오염시키지 않음 (다른 팀원에게 내 취향을 강요하지 않음)
- 모든 프로젝트에 자동 적용 (프로젝트마다 복붙할 필요 없음)
- **사용자 수준 규칙이 프로젝트 규칙보다 먼저 로드**됩니다

**대비되는 위치들:**
- 프로젝트 안 `.claude/rules/`에 복붙 → 저장소에 커밋되어야 하고, 저장소마다 중복 관리 필요
- `CLAUDE.local.md` → 그 **프로젝트 하나**에만 적용, 전역 적용 수단이 아님
- 관리형 정책 CLAUDE.md → 조직이 통제하는 파일이지 개인 취향용이 아님

### 6.3 심볼릭 링크(symlink) 지원

**심볼릭 링크란:** 실제 파일이 아니라 "다른 경로를 가리키는 바로가기" 파일입니다. 유닉스/리눅스/macOS의 기본 파일시스템 기능이고, Windows에도 있습니다.

```bash
ln -s /shared/org-rules/security.md .claude/rules/security.md
```

**왜 쓰는가 — 단일 진실 공급원(Single Source of Truth):**
조직 안 여러 저장소가 **동일한** 코드 리뷰 규칙을 써야 한다고 합시다. 각 저장소에 물리적으로 복사하면, 규칙이 바뀔 때마다 N개 저장소를 모두 고쳐야 하고 금방 어긋납니다. 중앙 폴더 하나를 두고 각 저장소에서 심볼릭 링크로 가리키면, **중앙 파일 하나만 고치면 모두가 자동으로 최신 상태**가 됩니다.

**Claude Code의 동작:**
- `.claude/rules/` 는 **심볼릭 링크를 정상적으로 따라갑니다(resolve)**. 조용히 무시하지 않습니다.
- **개별 파일 링크와 디렉터리 전체 링크 모두** 지원됩니다. `security.md` 하나만 링크해도 됩니다.
- **순환 감지(circular detection)** 가 내장되어 있습니다. A→B→A 처럼 링크가 자기 자신으로 되돌아오는 구조에서 무한 루프에 빠지지 않고 안전하게 중단합니다.
- 링크 대상이 **git 서브모듈일 필요는 없습니다.** 저장소 밖의 평범한 파일시스템 경로여도 됩니다.

**검증해야 할 것:** 각 저장소의 심볼릭 링크가 **실제로 그 공유 소스를 정확히 가리키는지** 확인하는 것. (링크가 깨져 있거나 엉뚱한 경로를 가리키면 규칙이 로드되지 않습니다.)

```bash
# 링크 대상 확인
ls -l .claude/rules/
readlink -f .claude/rules/security.md
```

## 7. Skills (스킬)

### 7.1 스킬이란

**스킬(Skill)** 은 특정 작업에 대한 **재사용 가능한 지침 묶음**입니다. `SKILL.md` 파일에 절차를 적어두면, Claude가 그 작업을 할 때 이 절차를 따릅니다. 슬래시 명령(`/review` 등)으로 직접 호출할 수도 있습니다.

디렉터리 구조:

```
.claude/skills/review/SKILL.md    ← 이름이 'review'인 스킬
```

스킬 이름은 **디렉터리 이름**으로 정해집니다. 위 예에서는 `review`이므로 `/review`로 호출됩니다.

### 7.2 스킬의 범위(scope)

| 위치 | 범위 |
|---|---|
| 엔터프라이즈/관리형 경로 | **Enterprise** — 조직 전체 |
| `~/.claude/skills/<이름>/SKILL.md` | **Personal** — 그 사용자의 모든 프로젝트 |
| `.claude/skills/<이름>/SKILL.md` | **Project** — 그 저장소, 팀 공유 (저장소에 커밋됨) |
| 플러그인이 제공하는 스킬 | **Plugins** |

### 7.3 이름 충돌 시 우선순위

같은 이름의 스킬이 여러 범위에 존재할 수 있습니다. 이때 **하나만 실행**되며, 우선순위는 다음과 같습니다.

```
Enterprise  >  Personal  >  Project  >  Plugins
```

**중요한 포인트:** **Personal(개인, `~/.claude/skills/`)이 Project(프로젝트, `.claude/skills/`)보다 우선합니다.**

**구체적 시나리오:**
- 저장소에 팀 공용 `.claude/skills/review/SKILL.md`가 커밋되어 있음
- 시니어 엔지니어의 노트북에 개인용 `~/.claude/skills/review/SKILL.md`가 있음 (같은 이름인 줄 모름)
- 이 엔지니어가 공유 저장소에서 `/review` 실행
- → **개인 스킬이 실행됩니다.** 프로젝트 스킬은 가려집니다(override).

**동작하지 않는 것들:**
- 두 스킬이 병합되거나 순차 실행되지 않습니다. 하나가 다른 하나를 **대체**합니다.
- 이름 충돌 에러가 나서 멈추지 않습니다. 우선순위 규칙에 따라 조용히 결정됩니다.

**실무적 함의:** 조용히 결정되기 때문에 **본인은 눈치채지 못한 채 팀 규칙을 안 따르고 있을 수 있습니다.** 그래서 개인 스킬은 이름을 구별되게(`my-review` 등) 짓는 것이 안전합니다.

## 8. 프로그래밍 방식 실행 — Headless / 비대화형 모드

### 8.1 `-p` 플래그 (print mode)

Claude Code는 대화형 화면뿐 아니라 **한 번 실행하고 끝나는 배치 모드**로도 쓸 수 있습니다.

```bash
claude -p "summarize the changes in this release"
```

`-p`(= `--print`)는 프롬프트를 주고, 응답을 표준 출력으로 뱉고, 종료합니다. CI 파이프라인, 릴리스 자동화, cron 잡 등에서 씁니다.

### 8.2 `--output-format` 옵션

출력 형식을 정합니다.

| 값 | 설명 |
|---|---|
| `text` | 사람이 읽는 평문 (기본값) |
| `json` | 하나의 JSON 객체로 반환. 스크립트가 파싱하기 좋음 |
| `stream-json` | 진행 중 이벤트를 줄 단위 JSON으로 스트리밍 |

### 8.3 JSON 응답 구조 — 여기에 비용 정보가 있다

```bash
claude -p --output-format json "summarize the changes in this release"
```

반환되는 JSON에는 **응답 텍스트만 들어있는 게 아닙니다.** 실행 메타데이터가 함께 들어옵니다.

대략 이런 형태입니다:

```json
{
  "type": "result",
  "subtype": "success",
  "is_error": false,
  "duration_ms": 12345,
  "num_turns": 3,
  "result": "이번 릴리스에서는 ...",
  "session_id": "abc-123",
  "total_cost_usd": 0.0432,
  "usage": {
    "input_tokens": 15234,
    "output_tokens": 892,
    "cache_read_input_tokens": 10000
  },
  "modelUsage": {
    "claude-opus-...": { "inputTokens": 1200, "outputTokens": 300, "costUSD": 0.031 },
    "claude-haiku-...": { "inputTokens": 14034, "outputTokens": 592, "costUSD": 0.012 }
  }
}
```

핵심 필드:
- **`result`** — 실제 응답 텍스트. 스크립트가 보통 이것만 꺼내 씀 (`jq -r '.result'`)
- **`total_cost_usd`** — 이번 호출의 **총 API 비용(달러)**
- **모델별 비용 내역(per-model cost breakdown)** — 여러 모델이 섞여 쓰인 경우(메인 모델 + 서브에이전트용 저렴한 모델 등) 모델마다 얼마 썼는지
- `usage` — 입력/출력/캐시 토큰 수
- `duration_ms`, `num_turns`, `session_id` — 실행 메타데이터

**핵심 이해:** 비용 정보를 얻으려고 **플래그를 추가할 필요가 없습니다.** `--output-format json`을 이미 쓰고 있다면 비용은 **이미 같은 응답 본문 안에** 들어 있습니다. `.result`를 읽던 스크립트에 `.total_cost_usd`를 읽는 줄 하나만 더하면 됩니다.

```bash
OUT=$(claude -p --output-format json "summarize the changes")
echo "$OUT" | jq -r '.result'          > summary.txt
echo "$OUT" | jq -r '.total_cost_usd' >> costs.log
echo "$OUT" | jq -c '.modelUsage'     >> costs.log
```

**오해하기 쉬운 점들:**
- `stream-json` + `--verbose` 조합이 있어야만 비용이 보이는 것이 **아닙니다.** 일반 `json`에도 들어 있습니다.
- 실행이 끝난 뒤 **웹 대시보드를 따로 조회해야만** 알 수 있는 것이 아닙니다. (대시보드도 있지만, 자동화 파이프라인에는 부적합합니다.)
- `.claude/usage.log` 같은 **로컬 로그 파일을 따로 파싱**해야 하는 구조가 아닙니다. 응답 본문 안에 있습니다.

### 8.4 `--verbose`

실행 중의 상세 로그(도구 호출 등)를 함께 출력합니다. 디버깅용이며, 비용 정보 획득의 필수 조건은 아닙니다.

## 9. 종합 판단 프레임

새로운 상황에서 무엇을 골라야 할지 헷갈릴 때 다음 순서로 생각하면 됩니다.

**1) 이 변경은 되돌리기 쉬운가?**
- 쉽다 → 직접 실행
- 어렵다 (아키텍처, 데이터 모델, 서비스 경계) → 계획 모드

**2) 정보가 어디 있는지 아는가?**
- 안다 → 직접 읽고 고치기
- 모른다, 그리고 탐색 범위가 넓다 → 서브에이전트 위임

**3) 이 설정은 누구에게 적용되어야 하는가?**
- 나만 / 내 모든 프로젝트 → `~/.claude/rules/`, `~/.claude/CLAUDE.md`
- 이 프로젝트 팀 전체 → 프로젝트 루트 `CLAUDE.md`, `.claude/rules/`
- 이 하위 디렉터리에서만 → 해당 디렉터리의 `CLAUDE.md`
- 여러 저장소가 공유, 중앙 관리 → 중앙 폴더 + 심볼릭 링크
- 조직 강제 정책 → 관리형 정책 파일

**4) 요구사항이 모호한가?**
- 그렇다 → 테스트를 먼저 써서 명세를 고정
- 아니다 → 바로 구현

**5) 피드백을 어떻게 줄까?**
- 독립적인 문제 여러 개 → 하나씩 순차적으로, 각각 구체적 증상과 함께

## 10. 용어 사전 (Glossary)

### 모드 · 권한

| 영어 용어 | 한국어 설명 |
|---|---|
| **Plan Mode** | 계획 모드. 파일을 수정하지 않고 코드베이스를 탐색·분석한 뒤 설계안을 제출하는 모드. 승인 후에만 실행 단계로 진입 |
| **accept-edits / acceptEdits** | 파일 편집을 매번 묻지 않고 자동 승인하는 모드. 방향이 확실한 반복 편집에 적합 |
| **default mode** | 기본 모드. 편집과 명령 실행마다 사용자 승인을 요청 |
| **bypassPermissions** | 모든 권한 확인을 건너뛰는 모드. 사람 검토 지점이 사라지므로 격리된 환경에서만 제한적으로 사용 |
| **Direct Execution** | 직접 실행. 계획·위임 없이 바로 시키는 것. 원인이 명확하고 범위가 좁은 수정에 적합 |

### 워크플로

| 영어 용어 | 한국어 설명 |
|---|---|
| **Subagent** | 서브에이전트. 격리된 별도 AI 인스턴스에 하위 작업을 위임하고 결과 요약만 받아오는 구조 |
| **Explore subagent** | 탐색 전용 서브에이전트. 위치를 모르는 코드를 넓게 찾을 때 사용. 메인 대화의 컨텍스트 오염을 막음 |
| **Context pollution** | 컨텍스트 오염. 불필요한 파일 내용이 대화 컨텍스트를 잠식해 성능이 떨어지는 현상 |
| **Correction cycle** | 수정 주기. AI 결과가 틀려서 사람이 지적하고 다시 고치는 왕복 횟수 |
| **TDD (Test-Driven Development)** | 테스트 주도 개발. 테스트를 먼저 작성하고 그것을 통과시키는 구현을 나중에 하는 방식 |
| **Test-driven iteration** | 테스트 주도 반복. 테스트 실패 출력을 AI에게 공유하며 반복 수정하는 워크플로 |

### 설정 파일

| 영어 용어 | 한국어 설명 |
|---|---|
| **CLAUDE.md** | Claude에게 주는 프로젝트 지침서 마크다운 파일. 세션 시작 시 자동 로드 |
| **CLAUDE.local.md** | 프로젝트 안의 개인용 지침 파일. 해당 프로젝트에만 적용되고 보통 gitignore 대상 |
| **User-level / Personal scope** | 사용자(개인) 수준. `~/.claude/` 아래. 그 머신의 모든 프로젝트에 적용, 저장소에 커밋 안 됨 |
| **Project scope** | 프로젝트 수준. 저장소 안 `.claude/` 아래. 팀 전체가 공유, 저장소에 커밋됨 |
| **Managed policy** | 관리형 정책. 조직/IT가 배포하고 개인이 편집할 수 없는 강제 설정 |
| **`.claude/rules/`** | 규칙 문서를 주제별 파일로 쪼개어 담는 디렉터리 |
| **Import (`@경로`)** | CLAUDE.md 안에서 다른 파일을 끌어오는 문법. 작업 디렉터리와 무관하게 항상 로드됨 |
| **Load at launch** | 시작 시 로드. Claude 실행 시점의 디렉터리 기준으로 해당 CLAUDE.md가 자동 로드되는 것 |
| **Load on demand** | 온디맨드 로드. Claude가 특정 디렉터리의 파일을 읽는 순간 그 디렉터리의 CLAUDE.md가 함께 로드되는 것 |
| **Monorepo** | 모노레포. 여러 패키지/서비스를 하나의 저장소에서 관리하는 구조 |

### 파일시스템

| 영어 용어 | 한국어 설명 |
|---|---|
| **Symlink (symbolic link)** | 심볼릭 링크. 다른 경로를 가리키는 바로가기 파일. `ln -s 대상 링크명` |
| **Resolve (a symlink)** | 심볼릭 링크를 따라가 실제 대상 파일에 도달하는 것 |
| **Circular detection** | 순환 감지. 링크가 자기 자신으로 되돌아오는 구조에서 무한 루프를 막는 기능 |
| **Single source of truth** | 단일 진실 공급원. 정보의 정본을 한 곳에만 두고 나머지는 그것을 참조하는 원칙 |
| **Git submodule** | 깃 서브모듈. 한 저장소 안에 다른 저장소를 중첩시키는 깃 기능. 심볼릭 링크와는 별개의 메커니즘 |

### 스킬

| 영어 용어 | 한국어 설명 |
|---|---|
| **Skill** | 스킬. 특정 작업 절차를 담은 재사용 가능한 지침. `SKILL.md`로 정의하고 슬래시 명령으로 호출 가능 |
| **SKILL.md** | 스킬 정의 파일. 스킬 이름은 이 파일이 든 디렉터리 이름으로 정해짐 |
| **Skill precedence** | 스킬 우선순위. 이름 충돌 시 `Enterprise > Personal > Project > Plugins` 순으로 하나만 선택됨 |
| **Override** | 오버라이드. 우선순위가 높은 쪽이 낮은 쪽을 가리고 대신 실행되는 것 |

### CLI · 출력

| 영어 용어 | 한국어 설명 |
|---|---|
| **`-p` / `--print`** | 비대화형(headless) 실행 플래그. 프롬프트 실행 후 결과를 출력하고 종료. CI 자동화용 |
| **`--output-format`** | 출력 형식 지정. `text` / `json` / `stream-json` |
| **`json` 출력** | 결과와 메타데이터를 하나의 JSON 객체로 반환. 스크립트 파싱용 |
| **`stream-json`** | 진행 이벤트를 줄 단위 JSON으로 실시간 스트리밍하는 형식 |
| **`--verbose`** | 도구 호출 등 실행 상세 로그를 함께 출력. 비용 정보 획득의 필수 조건은 아님 |
| **`result` (필드)** | JSON 응답에서 실제 답변 텍스트가 담기는 필드 |
| **`total_cost_usd`** | JSON 응답에 포함되는 이번 호출의 총 API 비용(달러) |
| **Per-model cost breakdown** | 모델별 비용 내역. 여러 모델이 사용된 경우 각각의 토큰 수와 비용 |
| **`usage`** | 입력/출력/캐시 토큰 사용량 정보 |
| **`session_id`** | 세션 식별자. 이후 세션 재개나 추적에 사용 |
| **`jq`** | 명령줄 JSON 처리 도구. `jq -r '.result'` 형태로 특정 필드를 추출 |

### 도메인 (예시에 등장한 개념)

| 영어 용어 | 한국어 설명 |
|---|---|
| **Monolith** | 모놀리스. 하나의 큰 덩어리로 배포되는 애플리케이션 구조 |
| **Microservices** | 마이크로서비스. 기능별로 독립 배포되는 작은 서비스들로 나눈 구조 |
| **Service boundary** | 서비스 경계. 어떤 기능·데이터가 어느 서비스에 속하는지의 분할선 |
| **Deployment topology** | 배포 토폴로지. 서비스들이 어떤 환경에 어떻게 배치·연결되는지의 구조 |
| **Rate limiter** | 속도 제한 장치. 일정 시간 안의 요청 수를 제한하는 컴포넌트 |
| **Throttling** | 스로틀링. 한도를 초과한 요청을 거부하거나 지연시키는 동작 |
| **Burst limit** | 버스트 제한. 짧은 순간에 몰린 요청을 얼마나 허용할지의 한계 |
| **Reset window / reset timing** | 리셋 윈도우. 카운터가 초기화되어 요청이 다시 허용되는 시간 구간 |
| **Stack trace** | 스택 트레이스. 예외 발생 시 호출 경로를 보여주는 출력. 원인 위치 특정에 사용 |
| **Null check** | 널 체크. 값이 비어 있는지 확인하는 방어 코드 |
| **CI pipeline** | CI 파이프라인. 코드 변경 시 자동으로 빌드·테스트·배포를 수행하는 자동화 흐름 |
