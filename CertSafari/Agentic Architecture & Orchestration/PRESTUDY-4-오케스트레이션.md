# 4. 작업 분해와 오케스트레이션 패턴

에이전트 시스템 설계의 핵심 결정은 하나입니다. **"이 일을 어떻게 쪼개고, 누가 그 순서를 정하는가."** 이 장은 그 결정을 다룹니다.

**이 장에서 다루는 것**

- 왜 분해하는가 — 다중 의도 요청, 개방형 과제
- 프롬프트 체이닝(고정 체인)과 체크포인트/게이트키퍼
- 병렬화(fan-out / fan-in)와 공유 컨텍스트
- 오케스트레이터-워커, 동적/적응형 분해
- Hub-and-Spoke 코디네이터와 갭 평가 → 타깃 재위임
- 맵-리듀스와 맥락 희석(attention dilution)
- 분해가 너무 좁을 때 생기는 누락 문제
- 초대형 스케일: 오케스트레이션을 대화 밖으로 (Workflow 도구)
- 에이전트 프롬프트 설계 — 과잉 명세 vs 목표 지향
- 사람 개입(HITL)과 구조화된 핸드오프

---

## 4.1 왜 분해하는가

하나의 요청 안에 서로 다른 성격의 일이 섞여 있거나, 한 번에 처리하기엔 너무 큰 일이 있을 때, 이를 **하위 작업(subtask)** 으로 쪼개는 것을 작업 분해(task decomposition)라고 합니다. 분해하면 각 하위 작업이 단순해져 모델의 정확도가 올라가고, 서로 독립적인 하위 작업은 동시에 처리할 수 있습니다.

패턴 선택의 기준은 결국 하나로 수렴합니다.

> **다음에 무엇을 할지가 이전 단계의 출력에 따라 달라지는가?**
> - 아니오 → 고정 프롬프트 체인 (의존까지 없으면 병렬화)
> - 예 → 동적 오케스트레이션 / 적응형 분해

---

## 4.2 다중 의도(Multi-intent) 요청 처리

하나의 사용자 발화 안에 독립적인 요구가 둘 이상 들어 있는 경우가 흔합니다.

> "구독료가 이중 청구됐어요. 그리고 다음 배송 전에 배송지 주소도 바꿔주세요."

여기에는 (a) 청구 조회/환불, (b) 주소 변경이라는 서로 무관한 두 의도가 있습니다. 권장 처리 흐름은 3단계입니다.

1. **분해(Decompose)**: 요청을 "청구 문제"와 "주소 문제"로 나눈다.
2. **병렬 조사(Parallel investigation with shared context)**: 두 하위 작업은 서로 의존하지 않으므로 동시에 진행한다. 이때 원본 티켓 내용, 고객 정보 같은 공통 정보는 **공유 컨텍스트(shared context)** 로 한 번만 준비해 양쪽이 함께 쓴다. 티켓을 두 번 다시 읽어 토큰을 두 배로 쓰는 낭비를 피할 수 있다.
3. **합성(Synthesize)**: 두 결과를 하나의 통합 응답으로 합쳐 전달한다.

관심사가 셋인 경우(예: "배송 지연", "쿠폰 미적용", "계정 해지"가 한 메시지에 섞여 있고 각각 별도 도구가 있는 경우)도 똑같습니다. 세 관심사로 분할 → 세 조사를 동시 실행 → 하나의 답변으로 종합하는 것이 가장 빠르면서도 일관됩니다.

이렇게 하면 응답 지연(latency)과 토큰 소모가 줄고, 사용자 입장에서는 한 번의 답변으로 모든 문제가 해결됩니다.

**피해야 할 방식**

- 사용자에게 "티켓을 두 개(세 개)로 나눠 다시 제출하세요"라고 되돌려 보내기 → 시스템의 한계를 사용자에게 전가하는 나쁜 UX이자, 자동화 능력의 포기.
- 한쪽 요구를 조용히 무시하기 → 요청 미해결. 다른 요청도 각각 원인 파악과 조치가 필요합니다. 우선순위를 임의로 판단하는 것도 위험.
- 하나를 처리하고 답한 뒤 후속 메시지를 기다리기 → 독립 작업을 직렬화해 불필요하게 느려집니다.
- 첫 문제를 처리한 뒤 **기억이 전혀 없는 새 세션**으로 두 번째 문제를 다시 시작하기 → 이미 확보한 컨텍스트를 버리는 정보 손실.

## 4.3 프롬프트 체이닝 (Prompt Chaining / 고정 프롬프트 체인)

**정의**: 미리 정해진 단계들을 고정된 순서로 실행하고, 각 단계의 출력을 다음 단계의 입력으로 넘기는 구조.

```
[1단계] PDF → JSON 변환
   ↓ (출력이 그대로 다음 입력)
[2단계] 필수 필드 검증
   ↓
[3단계] 레코드 저장
```

```
[개요 작성] → [본문 확장] → [문법 교정]
[대화록 수집] → [구조화된 요약] → [3개 언어 번역]
```

**적합 조건**

- 단계의 수와 순서가 **절대 변하지 않는다**(never branch, number of stages never varies). 순서가 런타임에 바뀔 일이 없다.
- 각 단계의 출력 형태가 다음 단계가 요구하는 입력과 **항상 정확히 일치한다**.
- 스키마가 고정되어 있다. (예: 모든 송장이 동일한 3개 필드 스키마)
- 단계 간에 **순차적 의존성**이 있다.

**장점**

- **예측 가능성(predictability)**: 실행 경로가 하나뿐이므로 디버깅·테스트·비용 예측이 쉽다. 결정론적이고 지연이 낮으며 오버헤드가 적다.
- **위임 오버헤드(delegation overhead)가 없다**: "다음에 뭘 할지" 판단하는 중앙 관리자를 둘 필요가 없으므로, 그 판단에 드는 LLM 호출·토큰·지연이 통째로 사라진다.

**단점**: 예측하지 못한 상황에 대응할 수 없다.

**예**: 신규 고객 온보딩 — 계정 레코드 생성 → 기본 권한 부여 → 환영 메일 발송. 어떤 계정이든 항상 같은 3단계입니다.

### 체크포인트(Checkpoint) / 게이트키퍼(Gatekeeper) 패턴

체이닝의 위험은 앞 단계가 이상한 출력을 내면 그 오류가 뒤 단계로 전파·증폭된다는 점입니다. 그래서 단계 사이에 **프로그래밍 방식의 검증 지점(programmatic check)** 을 둡니다. LLM 판단이 아니라 **코드**(스키마 검증, 정규식, 필드 존재 확인)로 확인하는 것이 포인트이며, 저렴하고 확실합니다.

```
개요 생성 → [개요가 형식에 맞는가? 섹션이 있는가?] → 본문 작성 → [본문 길이/구조 검증] → 문법 교정
```

```python
outline = run_stage("개요 작성", transcript)
assert_valid_outline(outline)      # 게이트: 형식이 깨졌으면 여기서 중단
prose = run_stage("본문 확장", outline)
```

검증에 실패하면 다음 단계로 넘기지 않고 재시도하거나 중단합니다. **"고정 파이프라인 + 단계 사이 프로그래밍 검증"은 결정론적 워크플로의 표준형입니다.**

### 고정 체인이 맞는 경우 — 사례와 잘못된 반론

**분기별 Terraform 컴플라이언스 검토**: 매 분기마다 정확히 같은 11개 규칙 체크리스트를 모든 파일에 적용하고, 어떤 규칙의 결과도 다른 규칙의 검사 여부를 바꾸지 않는다. → 하위 작업이 중간 발견 사항에 전혀 의존하지 않으므로 동적 계획 능력이 **불필요**합니다. 매 분기 같은 순서로 11개를 순회하는 고정 프롬프트 체인이 비용·일관성 면에서 최적입니다.

> 주의할 나쁜 변형: "고정 체인을 쓰되, 모델이 불필요하다고 판단하는 규칙은 조용히 건너뛰게(silently skip) 한다" → 컴플라이언스 검토에서 규칙을 임의로 누락하는 것은 검토의 완전성 자체를 무너뜨리는 위험한 설계입니다.

**콘텐츠 파이프라인**: 제품 설명 생성 → 항상 같은 브랜드 톤 검사기 → 항상 같은 비속어 필터. 내용과 무관하게 순서가 고정.

여기에 "내용에 따라 톤 검사기와 비속어 필터 중 무엇을 먼저 돌릴지 동적으로 정하는 오케스트레이터"를 도입하자는 제안이 나온다면, 가장 강한 비판은 이것입니다: **두 검사가 어차피 항상 같은 고정 순서로 모두 실행되므로 프롬프트 체인이 이미 예측 가능하게 처리하고 있고, 동적 오케스트레이터는 결과 개선 없이 불필요한 복잡성과 지연(latency)만 추가한다.**

흔히 나오는 잘못된 옹호 논리:

- "제품 설명 길이가 제각각이라 고정 체인으로는 감당 못 한다" → 틀렸습니다. 프롬프트 체인은 입력 텍스트 길이 변동을 자연스럽게 처리합니다.
- "동적 오케스트레이션이 언제나 더 좋은 결과를 낸다" → 근거 없는 주장이며, 이는 비판이 아니라 옹호입니다.
- "비속어 필터는 반드시 톤 검사기보다 먼저여야 한다" → 그런 절대적 제약은 없습니다.
- 같은 논리로 Terraform 예시에서 "파일 크기가 다양하니 고정 프로세스는 일관되게 적용될 수 없다"는 주장도 성립하지 않습니다. 크기 차이는 동적 오케스트레이터로 전환할 이유가 되지 못합니다.

## 4.4 병렬화 (Parallelization / Fan-out · Fan-in)

**정의**: 서로 의존하지 않는 하위 작업들을 **동시에** 실행하고, 결과를 모아 하나로 합치는 구조.

```
                ┌─→ [분류]     ─┐
입력 ──(fan-out)─┼─→ [감정 분석] ─┼─(fan-in)→ 종합 결과
                └─→ [요약]     ─┘
```

**적합 조건**: 하위 작업들이 **서로의 결과를 필요로 하지 않을 때**.

**예**: 지원 티켓 처리 — 카테고리 분류, 감정 추출, 요약 생성. 셋 중 어느 것도 다른 것의 결과를 기다릴 필요가 없습니다.

**핵심 논거**: 독립적인 작업을 순차 실행하면 지연 시간(latency)만 누적됩니다. 병렬 실행은 전체 소요 시간을 가장 느린 작업 하나의 시간으로 줄입니다.

**중요한 구분**: 고정된 3단계라고 해서 자동으로 "고정 프롬프트 체인"이 되는 것이 아닙니다. 체인은 **순차 의존**이 있을 때의 패턴입니다. 단계가 고정되어 있고 **의존이 없다면** 병렬화가 맞습니다.

**Fan-in의 중요성**: 병렬 실행 후 결과를 각각 따로 내보내면 사용자는 파편화된 답을 받습니다. 반드시 하나로 **종합(synthesis)** 해서 일관된 단일 응답을 만들어야 합니다.

## 4.5 오케스트레이터-워커 (Orchestrator-Workers) / 동적 오케스트레이션

**정의**: 중앙의 **오케스트레이터(orchestrator)** 가 상황을 보고 하위 작업을 **런타임에 동적으로 생성**하여 **워커(worker, 주로 서브에이전트)** 에게 위임하고, 결과를 받아 다음 하위 작업을 다시 결정하는 구조.

```
        오케스트레이터
      (다음에 뭘 조사할지 매번 결정)
       /      |       \
   워커1    워커2     워커3
       \      |       /
        결과 취합 → 새 하위 작업 생성 → 반복
```

**적합 조건**

- **탐색 공간을 사전에 알 수 없다**. 몇 개의 로그, 몇 개의 서비스, 몇 개의 코드 경로를 봐야 하는지 미리 셀 수 없다.
- **다음 행동이 이전 결과에 의존한다**. 발견한 단서에 따라 조사 방향이 달라져야 한다.
- 분기(branching)와 우선순위 재조정이 필요하다.
- 필요한 하위 작업의 **개수나 순서가 입력에 따라 달라진다**.

**장점**: 유연성, 탐색 능력. **단점**: 복잡, 비용 증가, 결과 편차(비결정성).

### 사례 1 — 장애 원인 조사(Incident Investigation)

모호한 알림 메시지 하나만 주어지고 어느 서비스가 문제인지 모르는 상황. 볼 로그·서비스·코드 경로의 수를 미리 정할 수 없습니다. 첫 단계에서 로그를 보고 특정 서비스가 의심되면 그 서비스의 코드 경로를 조사하는 새 하위 작업을 만들고, 아니면 다른 방향으로 우선순위를 옮깁니다. 각 단계에서 나온 단서(오류 코드, 로그 패턴)를 해석해 다음 조사 대상을 만들어 내야 합니다.

부적절한 대안들:

- **하드코딩된 5단계 체인**: 무엇이 발견되든 5단계 전부 실행 → 불필요한 단계에 토큰과 시간 낭비, 예상 밖 원인에는 대응 불가.
- **고정 순서 점검(DB → 캐시 → 로드밸런서)**: 원인이 그 목록 밖(서드파티 API, 인증 서비스, 애플리케이션 코드)에 있으면 영원히 찾지 못함.
- **단일 프롬프트로 즉시 근본 원인 지목**: 근거 없이 추측하므로 **환각(hallucination)** 을 유발. 조사 없는 단정은 위험.

### 사례 2 — 열린 결말(open-ended) 조사

"지난달 결제 이탈률(checkout abandonment)이 15% 증가한 원인은 무엇인가?" 확인해야 할 데이터 소스(로그, 분석 대시보드, 최근 배포 내역)가 사전에 정해져 있지 않고, 초기 조사 결과가 무엇을 시사하느냐에 따라 달라집니다.

올바른 분해:

1. **초기 조사 하위 작업**을 하나 생성해서 실행
2. 그 **결과(findings)를 평가**
3. 가장 유망한 단서(promising leads)를 추적하는 **후속 하위 작업을 동적으로 생성**
4. (필요한 만큼 반복)

이것이 **동적 작업 분해(Dynamic Task Decomposition)** 또는 **탐색적 계획(Exploratory Planning)** 입니다.

부적합한 대안들:

- "대시보드 → 서버 로그 → 최근 배포" 순서를 고정한 3단계 체인 → 초기 조사에서 배포가 유력한 단서로 지목돼도 무조건 정해진 순서를 강제하므로 유연성이 없습니다.
- 코드베이스를 파일별로 훑는 방식 → 원인이 로그·대시보드·배포 등 코드 밖에 있을 수 있는 문제의 성격과 맞지 않습니다.
- 어떤 데이터 소스도 보지 않고 문구만으로 즉시 원인을 단정 → **환각(Hallucination)** 을 유발하며 근거 없는 답이 나옵니다.

### 사례 3 — 취약점 도달 가능성 분석

"이 라이브러리 취약점이 대규모 애플리케이션 어딘가에서 실제로 악용 가능한가?" 시작 시점에 호출 지점(call sites)이 어디인지, 도달 가능한지(reachability), 이미 어떤 완화 조치가 있는지 **전부 미지**입니다. 검색을 한 번 돌려야 다음에 무엇을 조사할지 정해집니다. → Orchestrator-Workers가 맞습니다.

잘못된 선택들:

- Prompt Chaining으로 고정 3단계(스캔→패치→검증)를 박아 넣기 — 탐색 범위가 동적으로 변하는 상황에 대응 못 함. 단계 수를 고정한다고 모든 호출 지점을 찾는 게 보장되지도 않음.
- CVE 설명만 읽고 코드베이스를 보지 않은 채 단일 패스로 판단 — 특정 애플리케이션에서의 실제 악용 가능성은 코드를 봐야만 알 수 있음.

### 사례 4 — 사기 조사

플래그된 계정의 거래 내역을 조회하고, 거기서 발견되는 의심 패턴에 따라 다음에 볼 레코드가 달라집니다.

## 4.6 적응형 분해 (Adaptive Decomposition)

동적 오케스트레이션의 한 갈래로, 실행 도중 발견한 사실에 따라 **계획 자체에 없던 새 하위 작업을 추가**하는 방식입니다.

### 전형적 실패 사례 — DB 마이그레이션

5단계 고정 체인으로 DB 마이그레이션을 설계했습니다(스키마 추출 → 마이그레이션 스크립트 생성 → 문법 검증 → 마이그레이션 적용 → 행 수 확인). 그런데 테스트 중 "기본값 없는 새 컬럼"이 발견되어 **계획에 없던 백필(backfill) 단계**가 필요해졌습니다.

- **근본 결함**: 작업의 구조가 **발견되는 스키마 세부사항에 따라 가변적(variable structure)** 인데 고정 체인을 썼다는 것.
- **올바른 해법**: 런타임 분석 결과에 따라 백필 같은 하위 작업을 **동적으로 추가**할 수 있는 적응형 분해 / 동적 오케스트레이션.
- **잘못된 해법들**:
  - 체크포인트 하나 추가 → 문제를 *감지*할 뿐, 없던 단계를 *생성*하지는 못함.
  - 여섯 번째 백필 단계를 모든 마이그레이션에 하드코딩 → 백필이 불필요한 경우에도 매번 실행되어 불필요한 연산과 오류 유발.
  - "사전에 스키마를 완전히 알았어야 한다" → 런타임 스키마 추출 자체는 문제가 아님. 추출 결과에 유연히 대응하지 못한 설계가 문제.

### 개방형(Open-ended) 과제의 적응적 분해

"테스트가 전혀 없고 모듈 경계도 문서화되지 않은 20만 줄짜리 레거시 코드베이스에 테스트를 추가하라" 같은 과제에서는 **적응적(adaptive) 전략**이 필요합니다.

1. **매핑(Mapping)**: 먼저 코드베이스 구조를 훑어 모듈과 의존 관계를 파악한다. (무엇이 있는지도 모르는 상태에서 계획을 세울 수 없으므로 탐색이 먼저다.)
2. **우선순위 지정**: 영향도가 큰(high-impact) 공백부터 고른다. 모든 함수를 똑같이 취급하지 않는다.
3. **계획을 진행하며 조정**: 작업 중에 새로 드러나는 숨은 의존성에 맞춰 계획을 수정한다.

피해야 할 **빅뱅(Big Bang) 접근**:

- 테스트를 한 번도 실행해보지 않고 모든 함수의 테스트를 한 번에 작성 → 피드백 루프가 없어 잘못된 가정이 끝까지 누적됨.
- 중간 점검(intermediate checkpoint) 없이 단일 세션에 전부 위임 → 컨텍스트 한계 초과, 오류 누적.
- 모듈 관계를 보지 않고 알파벳순 등 임의 순서로 진행 → 의존성이 얽혀 비효율.

> 핵심 원칙: **불확실성이 클수록 계획은 고정이 아니라 갱신 가능해야 한다.**

## 4.7 패턴 선택 요약

| 패턴 | 구조 | 언제 쓰나 |
|---|---|---|
| **단일 패스(single-pass)** | 한 번의 프롬프트로 끝 | 작업이 작고 단순, 외부 탐색 불필요 |
| **프롬프트 체이닝** | 미리 정해진 고정 단계를 순차 실행 (A→B→C) | 단계 수·순서 불변, 스키마 고정, 분기 없음, 출력이 곧 다음 입력 (+ 단계 간 체크포인트) |
| **병렬화(fan-out/fan-in)** | 독립 하위 작업 동시 실행 후 종합 | 단계는 고정이지만 **의존이 없을 때** |
| **오케스트레이터-워커** | 오케스트레이터가 중간 결과를 보고 하위 작업을 동적 생성·분배 | 하위 작업 개수·순서가 입력에 따라 달라짐, 탐색 범위 미지 |
| **적응형 분해** | 실행 중 발견에 따라 계획에 새 작업을 추가 | 실행 중 발견에 따라 없던 단계가 생김 |
| **모델 중심 에이전트 루프** | 모델이 매 턴 도구를 선택 | 중간 결과에 따라 다음 도구를 골라야 함 |

### 흔한 오해와 함정

- **"동적 오케스트레이션이 더 안전한 기본값"이 아닙니다.** 예측 가능한 워크플로우에 동적 구조를 쓰면 계획 오버헤드, 비용, 비결정성만 늘어납니다. 반대로 탐색적 문제에 고정 체인을 쓰면 답을 아예 못 찾습니다. **제어 흐름의 성질에 맞는 패턴을 고르는 것**이 설계입니다.
- "체이닝이 항상 더 정확하다", "2단계 이상이면 무조건 체이닝이 필요하다", "오케스트레이터는 PDF를 못 다룬다" 같은 절대적 서술은 모두 사실이 아닙니다. 특정 데이터 형식을 처리할 수 있느냐는 패턴이 아니라 **모델과 도구**의 문제입니다.
- 반대 방향의 과잉도 문제입니다. 고정 3단계 파이프라인에 동적 오케스트레이터를 쓰면 필요 없는 판단 오버헤드만 늘어납니다.
- **단일 서브에이전트에 "알아서 다 해줘"라고 뭉뚱그려 맡기는 것**은 겉보기엔 간단하지만, 단계 경계가 암묵적(implicit)이 되어 중간 산출물을 검증할 수도, 실패 지점을 특정할 수도 없습니다. 명시적 단계와 중간 산출물이 필요한 작업에는 부적합합니다.

## 4.8 Hub-and-Spoke Coordinator 패턴

중앙의 **코디네이터(허브)** 가 모든 서브에이전트(스포크)와의 통신·상태·에러 처리를 중앙집중적으로 관장하는 구조입니다.

```
        ┌──────────────┐
        │ Coordinator  │  ← 로깅, 에러 처리, 결과 취합
        └──┬───┬───┬───┘
           │   │   │
        ┌──▼┐ ┌▼─┐ ┌▼──┐
        │ A │ │ B│ │ C │   ← 서로 직접 통신하지 않음
        └───┘ └──┘ └───┘
```

핵심 원칙: **스포크끼리 코디네이터를 우회해 직접 데이터를 주고받지 않는다.**

서브에이전트 둘이 공유 파일이나 공유 DB로 직접 결과를 주고받으면, 코디네이터는 무슨 일이 오갔는지 모르고, 한쪽이 실패해도 감지하지 못합니다. 이것이 **가시성(visibility) 상실**입니다. 공유 큐를 직접 폴링하고 완료 후에만 알리는 방식도 중간 실패에 대한 실시간 가시성을 떨어뜨립니다.

올바른 교정: **모든 에이전트 간 통신을 코디네이터를 경유하도록 라우팅**해서, 코디네이터가 중간 결과를 로깅하고 실패를 일관되게 처리하게 만듭니다.

(서브에이전트 둘을 하나로 합치고 에러 처리 책임까지 넘기는 것은 코디네이터의 본래 역할을 없애는 것이므로 이 패턴과 어긋납니다.)

### 코디네이터는 평가자이기도 하다 — 갭 평가와 타깃 재위임

코디네이터는 단순 전달자가 아닙니다. 취합된 결과가 **원래 요구 범위를 다 채웠는지 평가(evaluate for gaps)** 하는 책임이 있습니다.

예: '공급망 사이버 보안의 신종 위험' 보고서에 랜섬웨어는 충실한데 원래 범위였던 **제3자 공급업체 위험**이 빠졌다면?

올바른 흐름: **갭 식별 → 그 부분만 타깃 쿼리로 재위임 → 자료 보강 → synthesis 재실행.**

- 미완성인 채 최종본으로 발행 — 부적절.
- 새 자료 없이 어조만 고쳐 쓰기 — 빠진 정보는 채워지지 않음.
- 전체 파이프라인을 처음부터 재시작 — 잘 된 부분까지 버리는 토큰·시간 낭비.

이 **"생성 → 평가 → 부족분 보강 → 재생성"** 순환이 오케스트레이션의 품질을 만듭니다.

## 4.9 분해가 너무 좁으면 생기는 문제 (Over-narrow Decomposition)

코디네이터가 광범위한 요청을 하위 작업으로 쪼갤 때, 원래 요청의 **범위(scope)** 를 다 덮지 못하고 지나치게 구체적인 몇 가지 측면(facet)으로만 좁히면, 다뤄지지 않은 영역이 **최종 결과물에서 통째로 사라집니다**.

예시: "전기차 충전 네트워크의 **경쟁 환경 분석**"이라는 넓은 요청을 '충전기 커넥터 유형 찾기', '충전 속도 목록 작성' 같은 기술 사양 수준의 좁은 하위 작업으로만 분해 → 종합 보고서에서 가격 모델, 규제 인센티브, 주요 경쟁사가 **완전히 누락**됩니다.

근본 원인은 **하위 작업 정의 단계**에 있습니다. 헷갈리기 쉬운 다른 원인들과 구별하세요.

- 서브에이전트들이 서로 작업을 중복해서 시간이 부족했던 것이 아닙니다(각자 다른 작업을 수행했음).
- 종합 단계가 너무 일찍 실행되어 부분 결과만 모은 타이밍 문제가 아닙니다.
- 도구 접근 권한 부족은 **지정된 하위 작업 안에서의** 결과 부실을 설명할 수는 있어도, 주제 자체가 **작업 계획에서 배제된** 이유를 설명하지 못합니다.

**교훈**: 분해할 때는 원래 요청의 전체 범위를 먼저 축(axis)으로 나열하고(예: 기술 사양 / 가격 / 규제 / 경쟁사 / 시장 규모), 그 다음에 각 축을 하위 작업으로 내려야 합니다.

## 4.10 맵-리듀스(Map-Reduce)와 맥락 희석(Context Dilution / Attention Dilution)

**맥락 희석 / 주의력 분산**: 한 번의 프롬프트에 너무 많은 정보를 넣으면, 모델의 주의(attention)가 전체에 얕게 퍼지면서 개별 항목의 세부 사항을 놓치고 결과물이 뭉뚱그려집니다. 컨텍스트 윈도우에 **"들어가긴 한다"와 "잘 처리된다"는 다른 문제**입니다.

예시 상황: 모노레포에서 40개 파일을 건드린 PR을, 혹은 PR의 **모든 파일을 하나의 결합된 프롬프트**로 분석하고 두 번째 프롬프트에서 파일 간(cross-file) 이슈를 요약합니다. 그런데 파일을 직접 비교하면 보이는 실제 통합 버그를 이 요약이 자주 놓치고, 코멘트가 일반론이 됩니다.

**원인**: 첫 번째 패스가 이미 모든 파일에 주의를 분산시켜서 각 파일에 대한 발견이 얕습니다. 두 번째 패스는 그 얕은 결과 위에서 요약하므로, 원본에 없던 디테일을 되살릴 수 없습니다.

**해결 — 맵-리듀스 / 분할 정복(divide and conquer)**

1. **Map 단계**: 파일마다 **개별 분석 패스**를 돌려 각 파일에 대한 깊고 풍부한 발견(findings)을 만든다. 각 패스의 컨텍스트가 작아 세밀해집니다.
2. **Reduce / 통합 단계**: 원본 40개 파일이 아니라 **요약된 findings만** 입력으로 삼아 파일 간 통합 이슈를 분석·요약한다.

```
[파일1 분석] ┐
[파일2 분석] ├→ [교차 파일 통합 패스] → 최종 리뷰
[파일3 분석] ┘
```

**효과 없는 시도들**

- 전부를 하나의 프롬프트로 더 크게 합치기 → 주의력 분산과 맥락 오염이 더 심해집니다.
- 두 패스의 순서를 뒤집어 개별 분석 전에 교차 요약 먼저 → 요약할 재료가 없으므로 논리적으로 성립하지 않습니다.
- 시스템 프롬프트를 더 길고 정밀하게 써서 "통합 버그란 무엇인지" 정의하기 → 원인은 정의의 모호함이 아니라 정보 과부하로 인한 주의 분산입니다.
- 파일 순서 무작위화 → 여전히 40개를 한 컨텍스트에 넣으므로 근본 문제 그대로, 비결정성만 증가.
- 앞쪽 파일 우선순위 부여 → 뒤쪽 파일의 리뷰 품질이 무너짐.
- **Temperature 상향** → temperature는 토큰 선택의 무작위성(다양성/창의성)을 조절하는 샘플링 파라미터일 뿐, 컨텍스트 과부하나 주의력 분산과 무관하며 오히려 환각 위험을 키웁니다.

## 4.11 초대형 스케일: 오케스트레이션을 대화 밖으로 (Workflow 도구)

서브태스크가 수백 개(예: 파일 단위 200개 마이그레이션)라면, 코디네이터가 턴마다 몇 개씩 위임하는 방식으로는 감당이 안 됩니다.

- 대화 컨텍스트가 위임 기록으로 폭발하고,
- 턴 수 한계에 부딪히며,
- 지연 시간과 토큰 비용이 기하급수로 늘어납니다.

이때는 **Workflow 도구**를 써서 오케스트레이션 로직 자체를 **런타임이 대화 바깥에서 실행하는 스크립트**로 옮깁니다. 반복·배치 처리는 결정론적 스크립트가 돌리고, 대화에는 최종 결과만 돌아옵니다. 대화 컨텍스트 소비를 최소화하면서 대규모 자동화를 안정적으로 수행하는 방식입니다.

대안들이 부족한 이유:

- 서브에이전트 하나가 한 컨텍스트 윈도우 안에서 200개를 순차 처리 — 컨텍스트 오버플로와 주의력 분산으로 실패.
- `maxTurns`만 키워 턴 안에서 200번 위임 — 토큰 낭비와 지연, 컨텍스트 오버헤드 미해결.
- 코디네이터를 여러 개로 쪼개 각자 파이프라인 유지 — 코디네이터 간 상태 동기화·중복 작업이라는 새 복잡성 발생.

## 4.12 에이전트 프롬프트 설계

### 과잉 명세(Over-specification)의 함정

서브에이전트 프롬프트를 이렇게 쓰는 경우가 흔합니다.

> "1단계: 상위 5개 기사를 검색한다. 2단계: 각각을 연다. 3단계: 게시일을 추출한다. 4단계: 표로 반환한다."

문제가 생깁니다. 가장 유용한 출처에 게시일이 아예 없어도 억지로 표를 만들고, 6개 출처가 더 나은 답을 주는 상황에서도 5개에 갇힙니다. 에이전트가 **환경의 가변성에 적응할 수 없게** 되기 때문입니다.

여기서 단계를 10단계로 더 잘게 쪼개는 것은 상황을 **악화**시킵니다. 명세가 촘촘할수록 예외 상황에 대한 적응력은 더 떨어집니다. 숫자만 5에서 6으로 바꾸거나, "추출한 날짜를 재확인하라"는 단계를 하나 더 붙이는 것도 경직된 구조 자체를 그대로 두므로 근본 해결이 아닙니다.

### 목표 지향 프롬프팅 (Goal-Oriented Prompting)

대신 **목표(goal)와 품질 기준(quality bar)** 중심으로 씁니다.

> "이 질문에 답하는 데 필요한, 신뢰할 수 있고 관련성 높은 출처를 찾으세요. 각 주장에 대해 검증 가능한 내용만 보고하고, 확인할 수 없는 정보는 그렇다고 표시하세요. 출처가 몇 개여야 하는지는 질문의 성격에 따라 판단하세요."

이렇게 하면 에이전트가 상황에 맞게 5개든 6개든 고르고, 게시일이 없으면 다른 메타데이터로 신뢰도를 설명합니다.

### 언제 절차를 지시하고 언제 목표를 지시하는가

- **절차를 명시**: 순서가 정말 고정되어 있고, 벗어나면 안 되는 규정이 있는 경우
- **목표를 명시**: 최선의 경로가 상황에 따라 달라지고, 판단이 필요한 경우

다만 **"반드시 지켜져야 하는 규칙"은 프롬프트에 쓰는 것으로 끝내지 말고 훅으로 강제하십시오.** 프롬프트는 방향을 주는 도구이지 보증 장치가 아닙니다.

## 4.13 사람 개입과 핸드오프 설계

### Human-in-the-Loop (HITL)

에이전트가 되돌릴 수 없거나 고위험인 작업을 하기 전에 사람이 개입하도록 설계하는 것입니다. `permissionDecision: "ask"` 가 대표적 구현 수단입니다.

### 핸드오프(Handoff) 프로토콜

에이전트가 처리 도중 사람 관리자에게 **에스컬레이션(escalate)** 해야 할 때, 그 관리자는 대개 **대화 내용을 볼 수 없습니다.** 인계 문서의 품질이 곧 대응 품질입니다.

**나쁜 설계: 자유 형식(free-text) "노트" 상자 하나.** 에이전트가 매번 다른 양식으로 쓰고, 무엇을 빠뜨렸는지 알 수도 없습니다. 전달되는 정보의 일관성과 품질이 보장되지 않습니다.

**좋은 설계: 필수 구조화 필드(required structured fields).**

```
고객 상세 정보(customer details)  : 이름, 계정 ID, 연락처
원인 분석(root cause analysis)   : 지금까지 파악한 문제의 원인
권장 조치(recommended action)    : 에이전트가 제안하는 다음 행동
```

이렇게 하면 **모든 핸드오프가 동일한 필수 요소(same essentials)를 빠짐없이 담습니다.** 관리자는 매번 같은 자리에서 같은 정보를 찾을 수 있고, 필드가 비어 있으면 누락을 즉시 알 수 있습니다. "구조화된 명시적 데이터가 자유로운 텍스트나 간접 플래그보다 신뢰할 수 있다"는 원칙과 같은 맥락입니다.

효과 없는 개선들:

- **글자 수 제한만 늘리기** → 장황해질 뿐, 핵심 정보가 일관되게 포함된다는 보장이 없음.
- **시스템 프롬프트로 "고객 이름은 꼭 쓰라"고 지시** → 이름 외에도 원인 분석·조치 사항 등 필수 정보가 많고, 프롬프트 지시는 확률적이라 구조적 누락 문제를 해결하지 못함.
- **노트를 없애고 관리자가 고객에게 다시 전화해 처음부터 설명받기** → 고객 경험(CX)을 극단적으로 해치는 비효율.
