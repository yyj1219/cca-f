# 사전 학습 노트: 도구 설계와 MCP 통합 (tool 76-85 대비)

이 문서는 해당 범위가 다루는 개념을 **아무것도 모르는 상태에서** 이해할 수 있도록 처음부터 설명합니다.

---

## 1. LLM 에이전트와 "도구(Tool)"의 기본 개념

### 1.1 LLM은 왜 도구가 필요한가
대규모 언어 모델(LLM)은 텍스트를 생성할 뿐, 스스로 파일을 읽거나 API를 호출하거나 배포를 실행할 수 없습니다. 그래서 개발자가 **도구(tool, function)** 를 정의해 모델에게 "이런 기능을 쓸 수 있다"고 알려줍니다.

동작 흐름:
1. 개발자가 도구 목록(이름 + 설명 + 입력 스키마)을 모델에게 전달한다.
2. 사용자가 자연어로 요청한다. ("이 계정 보고서 좀 보여줘")
3. 모델이 도구 목록을 읽고 **어떤 도구를 어떤 인자로 부를지 스스로 결정**한다.
4. 실행 환경(에이전트 런타임)이 실제로 그 함수를 실행하고 결과를 모델에게 돌려준다.
5. 모델이 결과를 바탕으로 답변하거나 다음 도구를 호출한다.

### 1.2 결정적으로 중요한 사실
모델은 도구의 **소스 코드를 보지 못합니다.** 모델이 보는 것은 오직:
- 도구 **이름**
- 도구 **설명(description)**
- 입력 **JSON 스키마**(파라미터 이름, 타입, required 여부, 각 파라미터 설명)

따라서 모델이 도구를 잘못 고르거나 이상한 인자를 만들어내는 문제는 거의 항상 **이름/설명/스키마의 품질 문제**입니다. 모델을 탓하기 전에 도구 정의를 봐야 합니다. 이것이 이 단원 전체를 관통하는 원리입니다.

예시 (Anthropic API 스타일 도구 정의):

```json
{
  "name": "generate_summary_report",
  "description": "계정의 한 페이지 분량 요약 보고서를 생성한다. 총 잔액, 최근 5건 거래, 이상징후 여부만 포함한다(약 300단어). 예: '이 계정 간단히 훑어줘'. 거래 내역 전체나 월별 상세 분석이 필요하면 generate_detailed_report를 사용할 것.",
  "input_schema": {
    "type": "object",
    "properties": {
      "account_id": { "type": "string", "description": "계정 식별자, 예: 'ACCT-10293'" }
    },
    "required": ["account_id"]
  }
}
```

## 2. 도구 설계 원칙

### 2.1 단일 책임 원칙 (Single Responsibility)
하나의 도구는 **하나의 일**만 해야 합니다. 여러 기능을 한 도구에 몰아넣은 것을 **모놀리식 도구(monolithic tool)** 라고 부릅니다.

나쁜 예: `analyze_document` 하나가 (1) 데이터 포인트 추출, (2) 요약 생성, (3) 원문 대조 검증을 모두 수행.

무슨 일이 벌어지나: 사용자가 "이 문서 좀 분석해줘"처럼 모호하게 요청하면, 모델은 세 동작 중 무엇을 원하는지 알 수 없습니다. 도구 설명이 "문서를 분석한다"로 뭉뚱그려져 있으니 어떤 결과가 나올지 예측할 수 없고, 실행할 때마다 세 동작 중 하나만 골라 수행하는 일관성 없는 결과가 나옵니다.

올바른 재설계 — **좁은 계약(narrow contract)** 을 가진 도구로 분할:
- `extract_data_points` — 문서에서 구조화된 값만 뽑아 반환
- `summarize_content` — 요약문만 반환
- `verify_claim_against_source` — 주장 하나를 원문과 대조해 참/거짓과 근거를 반환

각 도구는 "언제 쓰는지"가 이름만 봐도 명확해집니다. 모델의 선택 문제가 애매한 추측에서 명확한 매칭으로 바뀝니다.

주의: `mode: "extract" | "summarize" | "verify"` 같은 **enum 파라미터를 추가하는 것만으로는 부족**합니다. 파라미터는 늘렸는데 도구 설명은 여전히 "문서를 분석한다"로 남아 있으면, 모델은 어떤 mode를 골라야 할지 판단할 근거를 여전히 못 얻습니다. enum을 쓸 거라면 각 enum 값의 의미와 선택 기준을 설명에 반드시 써야 합니다.

### 2.2 최소 권한 원칙 (Least Privilege)
에이전트에게는 **그 역할에 실제로 필요한 도구만** 줍니다. "나중에 필요할지도 모르니까" 미리 붙여두는 것은 사고의 원인입니다.

예시 상황: 고객 지원 티켓 **분류(triage)** 에이전트. 하는 일은 티켓을 읽고 빌링/기술/계정관리 큐 중 하나로 보내는 것뿐. 그런데 도구가 네 개 붙어 있음:
- `route_ticket` (본래 역할)
- `process_refund` (환불 실행)
- `reset_password` (비밀번호 초기화)
- `close_account` (계정 해지)

로그를 보니 에이전트가 환불 관련 티켓을 빌링 큐로 보내는 대신 **직접 `process_refund`를 호출**하고 있었습니다. 모델 입장에서는 자연스러운 행동입니다 — 사용자가 환불을 원하고, 환불 도구가 눈앞에 있으니 씁니다.

근본 해결: 분류 에이전트에서 실행 계열 도구 세 개를 **제거**하고 `route_ticket`만 남깁니다. 도구가 없으면 호출 자체가 불가능합니다. 이것이 확실한 구조적 차단이며, 에이전트의 단일 역할과도 정확히 일치합니다.

왜 다른 방법은 불충분한가:
- **시스템 프롬프트로 금지**: 프롬프트는 강한 권고일 뿐 강제가 아닙니다. LLM은 확률적으로 동작하므로 지시를 우회할 수 있고, 긴 대화나 특이한 입력에서 무시될 수 있습니다. 불필요한 도구가 계속 노출된다는 근본 원인도 그대로입니다.
- **사람 승인 단계 추가**: 유용한 안전장치이긴 하지만, 에이전트가 애초에 잘못된 도구를 호출하려 시도하는 설계 결함은 그대로 남습니다. 사람에게 불필요한 승인 요청이 계속 쏟아집니다.
- **도구 이름만 바꾸기**(`process_refund` → `billing_queue_helper`): 이름은 바뀌어도 하는 일은 여전히 환불 실행입니다. 실제 동작과 이름이 어긋나면 모델은 더 혼란스러워지고, 코드를 읽는 사람도 속게 됩니다. 전형적인 임시방편입니다.

핵심 격언: **없는 도구는 잘못 호출될 수 없다.**

### 2.3 관련 개념: 공격 표면(attack surface) 축소
최소 권한은 보안 원칙이기도 합니다. 에이전트가 프롬프트 인젝션(외부 데이터에 숨겨진 악의적 지시)에 노출되었을 때, 위험한 도구를 애초에 갖고 있지 않으면 피해 범위가 제한됩니다.

## 3. 도구 설명(Description) 작성법

### 3.1 왜 설명이 전부인가
모델의 도구 선택은 사실상 **자연어 요청과 도구 설명 간의 의미 매칭**입니다. 설명이 부실하거나 서로 겹치면 매칭이 실패합니다.

### 3.2 실패 유형 1 — 동일하거나 중복된 설명 (모호성)
예: `generate_summary_report`와 `generate_detailed_report`가 **둘 다** "Generates a report for the given account."라고만 설명됨.

사용자가 "간단한 개요만 줘"라고 하면 모델은 두 도구를 구분할 근거가 없어 종종 상세 보고서를 부릅니다. 이름의 summary/detailed 차이만으로 추론하기를 기대하는 것은 불안정합니다.

또 다른 예: `create_ticket`과 `escalate_ticket`이 **둘 다** "handles customer issues" 문구를 포함. 에스컬레이션해야 할 사안에도 모델이 그냥 티켓을 생성합니다.

해결: 각 설명에 **고유한 트리거 조건**과 **다른 도구를 써야 할 때**를 명시합니다.

```text
create_ticket:
  신규 고객 문의를 최초로 접수해 티켓을 만든다. 아직 티켓이 없는 사안에만 사용한다.
  이미 존재하는 티켓이 SLA를 초과했거나 고객이 상급자 대응을 요구하면
  create_ticket이 아니라 escalate_ticket을 사용할 것.

escalate_ticket:
  이미 존재하는 티켓을 상위 지원 등급으로 올린다. 기존 ticket_id가 반드시 필요하다.
  SLA 초과, 반복 실패, 고객의 명시적 에스컬레이션 요구 시에만 사용한다.
  아직 티켓이 없다면 먼저 create_ticket을 사용할 것.
```

이 "**A일 때는 나를, B일 때는 저쪽 도구를**"이라는 상호 참조가 모호성 해소의 핵심 기법입니다.

### 3.3 실패 유형 2 — 입력 형식과 경계 동작 누락
예: 설명이 "Updates a customer record with given fields."뿐. 그 결과:
- 모델이 스키마에 없는 필드를 지어내서 넘김 (허용 필드 목록이 없으므로)
- **부분 업데이트(partial update)** 가 되는지 불명확 — 일부 필드만 보내면 나머지는 유지되는가, 아니면 비워지는가?

여기서 **경계 동작(boundary behavior)** 이란 "정상 범위의 가장자리에서 어떻게 되는가"입니다. 예: 빈 값 처리, 존재하지 않는 ID, 최대 항목 수, 부분 입력 허용 여부, 멱등성(같은 호출을 두 번 하면?), 실패 시 반환 형태.

해결:
```text
update_customer_record:
  고객 레코드의 지정된 필드만 수정한다(부분 업데이트 지원 — 전달하지 않은 필드는 기존 값 유지).
  수정 가능한 필드: email, phone, billing_address, marketing_opt_in 뿐이다.
  그 외 필드(id, created_at, credit_score)는 읽기 전용이며 전달 시 요청 전체가 거부된다.
  존재하지 않는 customer_id면 404 오류를 반환하며 아무것도 변경하지 않는다.
```

주의할 오해:
- **모든 필드를 required로 강제하는 것은 해법이 아닙니다.** 그렇게 하면 부분 업데이트 기능 자체가 사라지고, 모델은 모르는 필드까지 억지로 채워 넣어야 해서 오히려 환각(hallucination)이 늘어납니다.
- **도구 선언 순서**는 스키마에 없는 필드를 지어내는 현상과 무관합니다.
- **camelCase / snake_case 명명 규칙** 차이도 "존재하지 않는 필드를 창작"하는 원인이 아닙니다. 스키마에 적힌 이름을 그대로 쓰면 되는 문제입니다.

### 3.4 근본 해결: 설명 템플릿 표준화
개별 도구를 하나씩 고치는 것은 **증상 치료**입니다. 새 도구가 추가될 때마다 같은 문제가 반복됩니다. 장기 해법은 팀 전체가 따르는 **도구 설명 템플릿**을 제정하는 것입니다.

권장 템플릿 항목:
1. **무엇을 하는가** — 한 문장 동작 정의
2. **출력 상세도(output granularity)** — 무엇이 얼마나 나오는가 (요약 300단어 / 전체 거래 내역 CSV 등)
3. **예시 쿼리(example query)** — 이 도구가 호출되어야 할 대표적인 사용자 발화
4. **유사 도구와의 차이** — 언제 저쪽 도구를 대신 써야 하는가
5. **입력 형식** — 유효한 필드/값 범위, 형식 예시
6. **경계 동작 및 오류** — 부분 입력, 빈 결과, 실패 시 반환

템플릿을 규범으로 만들면 앞으로 추가되는 모든 도구에 자동으로 적용되므로, 문제 재발을 구조적으로 막습니다.

### 3.5 하지 말아야 할 잘못된 처방들
- **이름을 똑같이 만들고 숫자 접미사로만 구분**(`report_v1`, `report_v2`): 의미 정보가 사라져 모델의 구분 능력이 오히려 악화됩니다.
- **도구 개수를 2개로 인위적 제한**: 선택은 쉬워지지만 실제 업무를 표현할 수 없어 확장성이 없습니다. 문제는 개수가 아니라 설명의 품질입니다.
- **사용자에게 내부 도구명을 직접 입력하게 요구**: 자연어 인터페이스를 도입한 목적 자체를 부정합니다.
- **실행 전 지연(delay) 삽입**: 모델은 "기다리며 재고"하지 않습니다. 의사결정은 이미 끝난 상태이므로 아무 효과가 없습니다.
- **항상 모든 도구를 동시 호출하게 지시**: 자원 낭비이며, 부작용이 있는 도구(환불, 계정 해지)에서는 실제 피해가 발생합니다.
- **설명 수정 없이 플래그만 추가**(`create_ticket(escalate=true)`): 모델은 플래그를 언제 true로 둘지 판단할 기준을 얻지 못합니다.

## 4. MCP (Model Context Protocol)

### 4.1 MCP란 무엇인가
**MCP(Model Context Protocol)** 는 AI 모델/에이전트가 외부 시스템(데이터베이스, SaaS API, 사내 서비스)과 통신하기 위한 **개방형 표준 프로토콜**입니다. Anthropic이 공개했고 누구나 구현할 수 있습니다.

문제 배경: 도구 통합을 애플리케이션마다 따로 구현하면 N개 앱 × M개 서비스 = N×M 개의 커넥터가 필요합니다. MCP는 그 사이에 표준 규격을 두어 N+M으로 줄입니다. 흔히 USB-C 포트에 비유됩니다.

구성 요소:
- **MCP 서버(server)**: 특정 외부 시스템(예: Jira, GitHub, Postgres)의 기능을 표준 형태의 도구/리소스로 노출하는 프로그램.
- **MCP 클라이언트(client)/호스트**: 서버에 연결해 그 도구를 모델에게 제공하는 쪽. Claude Code가 여기에 해당합니다.
- **전송 방식(transport)**: 로컬 프로세스와 표준입출력으로 통신하는 **stdio** 방식, 원격 HTTP 서버와 통신하는 **SSE / streamable HTTP** 방식이 있습니다.

### 4.2 기존 서버를 쓸 것인가, 직접 만들 것인가
이것은 전형적인 **build vs. adopt** 판단입니다. 기준은 단순합니다.

| 대상 시스템 | 판단 |
|---|---|
| Jira, GitHub, Slack, Google Drive, Postgres 등 **널리 쓰이는 표준 서비스** | 이미 커뮤니티/벤더가 만든 MCP 서버가 존재 → **채택(adopt)** |
| 사내 배포 파이프라인처럼 **외부에 동등물이 없는 고유 시스템** | 아무도 만들 수 없음 → **커스텀 서버 직접 구축** |

이유: 외부 개발자는 여러분의 사내 파이프라인의 존재조차 모릅니다. 반대로 Jira 같은 공개 API는 이미 여러 곳에서 잘 만들어 두었고 유지보수도 계속됩니다. 개발 공수와 유지보수 부담을 커스텀이 꼭 필요한 곳에만 집중시키는 것이 합리적입니다.

흔한 오해 반박:
- "사내에서 만든 서버만 프로덕션 자격증명을 맡길 수 있다" — 틀립니다. 신뢰성은 자체 제작 여부가 아니라 **코드 검토·감사·평판·권한 범위 제한**으로 확보합니다. 서드파티 서버 도입 시에는 버전 고정과 최소 권한 토큰 발급을 병행하면 됩니다.
- "서드파티 서버는 이미 내부 도구를 이해한다" — 명백히 틀립니다. 외부 서버가 사내 전용 파이프라인을 알 방법은 없습니다.

### 4.3 MCP를 건너뛰고 Bash + curl로 하면 안 되나
가능은 하지만 권장되지 않습니다. 에이전트에게 임의의 셸 명령 권한을 주면:
- 어떤 작업이 허용되는지 경계가 사라집니다(임의 명령 실행 = 사실상 무제한 권한).
- 자격증명이 명령줄·로그에 노출되기 쉽습니다.
- 도구별 스키마가 없어 모델이 URL과 파라미터를 창작하게 되어 신뢰성이 떨어집니다.
- 재사용·감사·에러 처리가 매번 즉흥적입니다.

MCP 서버는 "허용된 동작 목록"을 명시적 계약으로 만들어 줍니다.

## 5. Claude Code에서의 MCP 설정과 범위(Scope)

### 5.1 세 가지 설정 범위
Claude Code는 MCP 서버를 세 가지 범위로 등록할 수 있습니다.

| 범위 | 저장 위치 | 적용 대상 |
|---|---|---|
| **local** (기본) | 사용자 개인 설정 | 나만, 현재 프로젝트에서 |
| **user** (전역) | 사용자 홈 설정 | 나만, 모든 프로젝트에서 |
| **project** | 프로젝트 루트의 `.mcp.json` (git에 커밋됨) | 저장소를 클론한 모든 팀원 |

등록 명령 예:
```bash
claude mcp add deploy-tools --scope project -- node ./scripts/deploy-mcp-server.js
claude mcp list        # 등록된 서버와 연결 상태 확인
```

### 5.2 `.mcp.json` — 프로젝트 범위 파일
프로젝트 루트에 두고 버전 관리에 포함시켜 팀 전체가 같은 서버 설정을 공유합니다.

```json
{
  "mcpServers": {
    "deploy-tools": {
      "command": "node",
      "args": ["./scripts/deploy-mcp-server.js"],
      "env": { "DEPLOY_ENV": "staging" }
    }
  }
}
```

### 5.3 핵심 보안 동작: 승인 대기(pending approval)
`.mcp.json`은 저장소 안의 파일이므로, **저장소를 클론하기만 해도 임의의 명령이 실행되는 상황**이 생길 수 있습니다. 악의적인 PR이 `.mcp.json`에 위험한 서버를 심어 넣는 공격이 가능합니다.

그래서 Claude Code는 다음과 같이 동작합니다:

> 프로젝트 범위(`.mcp.json`)로 정의된 MCP 서버는, 그 저장소를 처음 여는 **각 사용자마다 명시적으로 승인하기 전까지 연결되지 않으며, 승인 대기(pending approval) 상태로 표시**됩니다.

따라서 팀 저장소를 클론한 기여자가 처음 `claude mcp list`를 실행하면 `deploy-tools`는 **pending approval**로 보입니다.

같이 정리해 둘 오해:
- 저장소에 체크인되어 있다는 사실은 **암묵적 승인이 아닙니다.** 조용히 자동 연결되지 않습니다.
- 이름 충돌을 가정해 숫자 접미사를 붙여 자동으로 개명하는 동작 같은 것은 없습니다.
- 최초 등록자만 쓸 수 있는 것도 아닙니다. 모든 팀원이 쓸 수 있고, 각자 한 번 승인만 하면 됩니다.

설계 철학: 안전하지 않은 기본값 대신 **명시적 사용자 동의**를 요구합니다.

## 6. MCP 서버 인증(Authentication)

원격 MCP 서버에 붙으려면 보통 인증이 필요합니다. Claude Code의 MCP 설정은 몇 가지 방식을 제공합니다.

### 6.1 정적 헤더 (`headers`)
값이 거의 변하지 않는 API 키에 적합합니다.

```json
{
  "mcpServers": {
    "internal-api": {
      "type": "http",
      "url": "https://mcp.internal.example.com",
      "headers": { "Authorization": "Bearer ${INTERNAL_API_TOKEN}" }
    }
  }
}
```
한계: 토큰이 짧은 주기로 만료되거나 **매 연결마다 새로 발급되어야 한다면** 쓸 수 없습니다. 사람이 설정 파일을 계속 갈아 끼우는 운영은 현실적으로 불가능합니다.

### 6.2 OAuth 블록 (`oauth`, `authServerMetadataUrl`)
표준 OAuth 2.0 인가 서버가 있을 때 사용합니다. `authServerMetadataUrl`은 인가 서버의 메타데이터 문서(엔드포인트 목록 등)를 가리키며, 클라이언트가 인증 흐름을 자동으로 발견하게 해줍니다.

전제 조건: **OAuth 인가 서버가 실제로 존재해야 합니다.** Kerberos처럼 OAuth가 아닌 인증 체계를 이 블록으로 처리할 수는 없습니다. Kerberos 렐름 주소를 `authServerMetadataUrl`에 넣는 것은 의미가 없습니다.

### 6.3 동적 헤더 헬퍼 (`headersHelper`) — 매 연결마다 갱신되는 토큰
**연결할 때마다 새 토큰을 발급받아야 하는** 인증 체계를 위한 기능입니다. 설정에 스크립트를 지정하면, Claude Code가 서버에 연결할 때마다 그 스크립트를 실행하고 **스크립트가 stdout으로 출력한 헤더 JSON**을 요청 헤더로 사용합니다.

```json
{
  "mcpServers": {
    "kerberos-service": {
      "type": "http",
      "url": "https://mcp.corp.internal",
      "headersHelper": "/usr/local/bin/mint-kerberos-header.sh"
    }
  }
}
```

스크립트는 헤더 객체를 JSON으로 stdout에 출력하면 됩니다:
```bash
#!/bin/bash
TOKEN=$(kinit-and-mint --service mcp.corp.internal)   # 매번 새 토큰 발급
printf '{"Authorization": "Negotiate %s"}\n' "$TOKEN"
```

이것이 Kerberos 파생 토큰, 단기 STS 자격증명, 서명 기반 인증 등 **OAuth가 아니면서 수명이 매우 짧은** 인증 방식을 다루는 표준적인 방법입니다.

관련 오해: "Claude Code가 지원하지 않으니 Kerberos로 인증하고 API 키를 발급해 주는 중개(intermediary) 서비스를 따로 세워야 한다"는 접근은, `headersHelper`가 있는 상황에서는 불필요한 추가 인프라입니다.

### 6.4 인증 방식 선택 요약
| 상황 | 사용할 설정 |
|---|---|
| 장기 고정 API 키 | `headers` (환경변수 참조 권장) |
| 표준 OAuth 인가 서버 존재 | `oauth` + `authServerMetadataUrl` |
| 매 연결마다 새 토큰 필요(Kerberos, STS 등) | `headersHelper` 스크립트 → stdout JSON |

## 7. Claude Code 내장 파일 도구의 안전장치

MCP 외에 Claude Code 자체가 제공하는 내장 도구들에도 설계 의도가 담긴 규칙이 있습니다.

### 7.1 Write와 사전 읽기 요구 (prior-access requirement)
**규칙: 이미 존재하는 파일을 `Write`로 덮어쓰려면, 현재 대화 세션 안에서 그 파일을 `Read`로 먼저 읽었어야 합니다.**

이유(안전장치, guardrail):
- 모델이 파일의 현재 내용을 모르는 상태에서 덮어쓰면 **기존 설정이나 코드가 통째로 소실**될 수 있습니다.
- 예를 들어 `settings.local.json`에 다른 사람이 추가해 둔 항목이 있는데, 모델이 자기가 생각한 버전으로 통째로 갈아엎으면 그 항목은 사라집니다.
- 먼저 읽게 강제하면 모델이 기존 내용을 파악한 뒤 **병합된 결과**를 쓰게 됩니다.

따라서 기존 `settings.local.json`을 갱신하려면 순서는:
1. `Read`로 `settings.local.json` 읽기
2. `Write`로 덮어쓰기 (부분 수정이면 `Edit`가 더 적절)

관련 오해 정리:
- **`Grep`으로 확인하면 되지 않나?** 안 됩니다. Grep은 매칭된 일부 라인만 보여줄 뿐 파일 전체 상태를 보장하지 않으므로, 사전 접근 요구 조건을 충족하지 못합니다. 요구되는 것은 `Read` 호출 자체입니다.
- **Bash로 파일을 지우고 새로 쓰면?** 우회는 안전장치를 무력화하는 나쁜 습관이며, 애초에 Write는 기존 파일 덮어쓰기를 정상 지원합니다. 삭제는 불필요하고 위험합니다.
- **아무 조건 없이 덮어쓸 수 있다?** 아닙니다. 그것이 바로 이 정책이 막으려는 상황입니다.

참고로 `Edit`(정확한 문자열 치환) 역시 같은 사전 읽기 요구를 따릅니다.

### 7.2 Grep — 코드 검색 도구
Claude Code의 `Grep`은 ripgrep 기반 검색 도구로, 주요 파라미터는 다음과 같습니다.

| 파라미터 | 의미 |
|---|---|
| `pattern` | 검색할 정규식 |
| `path` | 검색 시작 디렉터리/파일 |
| `type` | 언어별 파일 필터 (`py`, `js`, `rust`, `go` …) |
| `glob` | 파일명 패턴 필터 (`**/*.tsx`) |
| `output_mode` | `files_with_matches`(경로만) / `content`(매칭 줄) / `count`(개수) |
| `-i` | 대소문자 무시 |
| `-n` | 줄 번호 표시 |
| `-A` / `-B` / `-C` | 매칭 앞/뒤/양쪽 문맥 줄 수 |
| `multiline` | **줄바꿈을 넘어 매칭**하는 모드 |

### 7.3 멀티라인 검색이 필요한 이유
기본적으로 grep 계열 도구는 **한 줄 단위**로 패턴을 검사합니다. 패턴이 줄바꿈을 가로지르면 매칭되지 않습니다.

문제 상황: Python에서 기반 클래스 목록이 길면 이렇게 줄바꿈됩니다.
```python
class OrderHandler(
    BaseHandler, LoggingMixin
):
    ...
```
`class \w+\(BaseHandler` 같은 단일 행 패턴은 이 정의를 놓칩니다. 반면 한 줄로 쓰인 `class UserHandler(BaseHandler):`는 잡힙니다. 그래서 "일부만 검색된다"는 증상이 나타납니다.

해결: `multiline: true`를 켜면 `.`이 줄바꿈까지 포함해 매칭하므로, 줄이 나뉜 클래스 헤더도 잡힙니다. 동시에 `type: "py"`로 범위를 파이썬 파일로 좁히면 노이즈와 비용이 줄어듭니다.

```
Grep(
  pattern: "class\\s+\\w+\\([^)]*BaseHandler",
  type: "py",
  multiline: true,
  output_mode: "content"
)
```

잘못된 대안들:
- **Glob으로 모든 `.py`를 나열한 뒤 전부 읽어서 눈으로 확인**: 정확도는 얻을 수 있으나 토큰과 시간을 엄청나게 낭비합니다. 검색 도구가 있는데 수동 스캔을 하는 셈입니다.
- **`output_mode`를 `files_with_matches`로 바꾸기**: 이것은 **결과를 어떻게 보여줄지**만 바꾸는 옵션입니다. 검색의 철저함과는 무관하므로 멀티라인 누락은 그대로입니다.
- **Bash로 파일마다 grep을 개별 호출**: Grep은 이미 저장소 전체를 언어별로 필터링해 한 번에 검색할 수 있습니다. 파일별 반복 호출은 훨씬 느리고 불필요합니다.

### 7.4 도구 선택 감각 정리
| 하고 싶은 일 | 도구 |
|---|---|
| 파일 이름/경로 패턴으로 찾기 | `Glob` |
| 파일 **내용**으로 찾기 | `Grep` |
| 경로를 아는 파일의 내용 보기 | `Read` |
| 파일 일부 수정 | `Edit` (사전 Read 필요) |
| 파일 새로 만들기 / 전체 교체 | `Write` (기존 파일이면 사전 Read 필요) |

## 8. 전체를 관통하는 사고 틀

1. **모델의 오작동은 대개 설계 결함이다.** 프롬프트로 덧붙여 막기 전에, 도구 목록·설명·스키마를 먼저 고친다.
2. **구조적 차단 > 지시적 통제.** 도구를 제거하는 것이 "쓰지 마"라고 말하는 것보다 항상 강하다.
3. **좁고 명확한 계약.** 도구 하나에 역할 하나, 설명에 트리거 조건과 배제 조건.
4. **재발 방지는 표준화로.** 개별 수정이 아니라 팀 템플릿/규범을 만든다.
5. **안전한 기본값.** 클론한 설정은 승인 전까지 연결하지 않고, 덮어쓰기 전에는 읽게 한다.
6. **바퀴를 다시 만들지 않는다.** 표준 서비스는 기존 MCP 서버 채택, 커스텀은 사내 고유 시스템에만.

## 9. 용어 사전 (Glossary)

| 영어 용어 | 한국어 설명 |
|---|---|
| **Tool / Function** | LLM이 호출할 수 있도록 이름·설명·입력 스키마로 정의된 외부 기능. 모델은 코드가 아니라 이 정의만 본다. |
| **Tool description** | 도구 설명문. 모델의 도구 선택 판단 근거 대부분을 차지하는 자연어 텍스트. |
| **Input schema** | 도구의 입력 구조를 정의한 JSON Schema. 파라미터 이름·타입·required·설명 포함. |
| **Tool selection** | 사용자 요청에 대해 모델이 어떤 도구를 호출할지 고르는 과정. |
| **Ambiguity (모호성)** | 둘 이상의 도구 설명이 겹쳐 모델이 구분하지 못하는 상태. |
| **Trigger condition** | 이 도구가 호출되어야 하는 구체적 조건. 설명에 반드시 명시. |
| **Output granularity** | 도구가 내놓는 결과의 상세 수준(요약 300단어 vs 전체 내역 등). |
| **Boundary behavior (경계 동작)** | 빈 입력, 없는 ID, 부분 입력, 최대치 등 가장자리 상황에서의 동작 규정. |
| **Partial update (부분 업데이트)** | 일부 필드만 전달해도 나머지 필드는 기존 값이 유지되는 갱신 방식. |
| **Single Responsibility Principle** | 단일 책임 원칙. 하나의 도구/모듈은 하나의 명확한 역할만 갖는다. |
| **Least Privilege (최소 권한)** | 역할 수행에 꼭 필요한 최소한의 권한/도구만 부여하는 보안 원칙. |
| **Monolithic tool** | 여러 이질적 기능을 한 도구에 몰아넣은 비대한 도구. 오작동의 원인. |
| **Narrow contract** | 입력·출력·역할이 좁고 명확하게 한정된 도구 명세. |
| **Enum parameter** | 정해진 값 목록 중 하나만 받는 파라미터. 각 값의 선택 기준을 설명해야 유효하다. |
| **System prompt** | 모델에게 지속적으로 주어지는 지침 텍스트. 강한 권고이지 강제 실행 장치가 아니다. |
| **Human approval step** | 위험한 도구 실행 전 사람이 확인하는 단계. 유용하지만 설계 결함 자체를 없애지는 못한다. |
| **MCP (Model Context Protocol)** | AI 에이전트와 외부 시스템을 연결하기 위한 개방형 표준 프로토콜. |
| **MCP server** | 특정 외부 시스템의 기능을 MCP 규격의 도구로 노출하는 프로그램. |
| **MCP client / host** | MCP 서버에 연결해 모델에게 도구를 제공하는 쪽. Claude Code가 여기 해당. |
| **Community / vendor server** | 커뮤니티나 서비스 제공사가 이미 만들어 배포한 MCP 서버. 표준 서비스에는 이것을 채택. |
| **Custom MCP server** | 사내 고유 시스템처럼 외부에 동등물이 없는 대상을 위해 직접 구축하는 서버. |
| **stdio transport** | MCP 서버를 로컬 프로세스로 띄우고 표준입출력으로 통신하는 방식. |
| **HTTP / SSE transport** | 원격 MCP 서버와 HTTP 기반으로 통신하는 방식. |
| **`.mcp.json`** | 프로젝트 루트에 두고 git에 커밋하는 프로젝트 범위 MCP 서버 설정 파일. |
| **Scope: local / user / project** | MCP 서버 등록 범위. 내 프로젝트만 / 내 모든 프로젝트 / 저장소 공유. |
| **`claude mcp add --scope project`** | 프로젝트 범위로 MCP 서버를 등록하는 CLI 명령. |
| **`claude mcp list`** | 등록된 MCP 서버와 연결 상태를 확인하는 CLI 명령. |
| **Pending approval (승인 대기)** | `.mcp.json`의 프로젝트 범위 서버가 각 사용자의 명시적 승인 전까지 놓이는 상태. 자동 연결되지 않는다. |
| **`headers`** | MCP 서버 요청에 붙일 정적 HTTP 헤더 설정. 장기 고정 키에 적합. |
| **`headersHelper`** | 매 연결 시 지정 스크립트를 실행하고 그 **stdout의 JSON**을 헤더로 사용하는 설정. 매번 새 토큰이 필요한 인증에 사용. |
| **`oauth` block / `authServerMetadataUrl`** | OAuth 2.0 인가 서버 메타데이터 URL을 지정해 인증 흐름을 자동 발견하게 하는 설정. OAuth 서버가 존재할 때만 유효. |
| **Kerberos** | 티켓 기반의 기업용 인증 프로토콜. OAuth가 아니며 토큰 수명이 짧다. |
| **Kerberos realm** | Kerberos 인증 도메인 단위. OAuth 메타데이터 URL로 쓸 수 없다. |
| **Intermediary service** | Kerberos 등으로 인증한 뒤 다른 형태의 자격증명으로 변환해 주는 중개 서비스. |
| **`Write` tool** | 파일을 새로 만들거나 전체를 교체하는 도구. 기존 파일이면 같은 대화 내 사전 `Read` 필요. |
| **`Read` tool** | 파일 내용을 읽는 도구. 덮어쓰기 안전장치의 전제 조건. |
| **`Edit` tool** | 파일의 특정 문자열을 치환하는 부분 수정 도구. |
| **Prior-access requirement** | 덮어쓰기 전에 그 파일을 읽었어야 한다는 사전 접근 요구 조건. |
| **Guardrail (안전장치)** | 데이터 유실이나 위험한 동작을 구조적으로 막는 장치. |
| **`Grep` tool** | ripgrep 기반 파일 내용 검색 도구. |
| **`Glob` tool** | 파일 **이름/경로** 패턴으로 파일 목록을 찾는 도구. |
| **`type` parameter** | Grep에서 검색 대상을 언어별로 한정하는 파라미터(`py`, `js` 등). |
| **`glob` parameter** | Grep에서 파일명 패턴으로 대상을 한정하는 파라미터. |
| **`multiline` mode** | 줄바꿈을 가로지르는 패턴까지 매칭하게 하는 Grep 옵션. 줄이 나뉜 클래스 헤더 검색에 필요. |
| **`output_mode`** | Grep 결과 표시 방식: `files_with_matches`(경로만) / `content`(매칭 줄) / `count`(개수). 검색 철저함과는 무관. |
| **Attack surface (공격 표면)** | 공격자가 악용할 수 있는 진입점의 총합. 도구를 줄이면 함께 줄어든다. |
| **Prompt injection** | 외부 데이터에 숨겨진 악의적 지시가 모델의 행동을 조종하는 공격. |
