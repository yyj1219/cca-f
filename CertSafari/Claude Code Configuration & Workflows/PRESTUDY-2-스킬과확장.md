# 2. 스킬 · 슬래시 커맨드 · 훅 · 서브에이전트

이 장에서 다루는 것:

- **스킬(Skills)** — `SKILL.md`, 프론트매터 전 필드, 온디맨드 로딩, 스코프와 우선순위, 워크스페이스 신뢰
- **슬래시 커맨드(Slash Commands)** — `.claude/commands/`, 스코프, Git을 통한 팀 배포
- **훅(Hooks)** — 생명주기 이벤트, `PreToolUse` 차단, `InstructionsLoaded` 진단, 결정론적 강제
- **서브에이전트(Subagents)** — 컨텍스트 격리, Explore, 자기 리뷰의 한계
- **넷 중 무엇을 쓸 것인가** — 결정표

---

## 1. 스킬(Skills)

### 1.1 스킬이란

**스킬(Skill)** 은 "이런 종류의 작업은 이렇게 해라"를 담은 **재사용 가능한 절차 묶음**입니다. 배포 절차, 리뷰 체크리스트, PR 요약 방식처럼 반복되는 작업의 수행 방법을 문서로 고정해 두면, Claude가 그 작업을 만났을 때 해당 지시서를 불러와 따릅니다. 매번 같은 긴 지시를 타이핑하는 대신 파일로 고정해 팀 전체가 공유하는 것이 존재 이유입니다.

디렉터리 하나에 `SKILL.md` 파일을 두는 형태이고, **디렉터리 이름이 곧 스킬 이름**입니다.

```
.claude/skills/
  review/
    SKILL.md        ← 이름이 'review'인 스킬 → /review 로 호출
  commit/
    SKILL.md
  deploy-checklist/
    SKILL.md
```

호출 방식은 두 가지입니다.

- 사용자가 `/review` 같은 **슬래시 명령으로 명시 호출**
- Claude가 `description`을 보고 상황에 맞다고 판단해 **자동 호출**

필요하면 `SKILL.md` 옆에 보조 스크립트나 참조 문서를 함께 둘 수 있습니다.

### 1.2 왜 존재하는가 — 온디맨드 로딩(progressive disclosure)

스킬의 핵심 가치는 내용이 아니라 **로딩 방식**입니다.

- 평소에는 스킬의 **메타데이터(`name` + `description`)만** 컨텍스트에 상주합니다. 아주 작습니다.
- Claude나 사용자가 실제로 그 스킬을 **호출했을 때에만 본문(body)** 이 컨텍스트로 들어옵니다.

이를 **온디맨드(on-demand) 로딩** 또는 **점진적 공개(progressive disclosure)** 라고 합니다. CLAUDE.md와 정확히 대비됩니다.

| | CLAUDE.md | Skill |
|---|---|---|
| 로드 시점 | 매 세션, 무조건 | 호출될 때만 |
| 평소 비용 | 전체 내용의 토큰 | description 한 줄 정도 |
| 적합한 내용 | 짧고 항상 필요한 것 | 크고 가끔 필요한 것 |

따라서 **크고, 드물게 필요하고, 절차적인 것**은 스킬로 옮기는 게 정석입니다.

- 대용량 규정 준수(compliance) 참조 문서
- 8단계 배포 체크리스트
- 특정 마이그레이션 절차
- 매번 채팅에 붙여넣던 긴 지시문

### 1.3 중요한 부작용 — 한 번 로드되면 계속 남는다

스킬 본문은 **일단 로드되면 그 세션의 남은 시간 동안 컨텍스트에 계속 남습니다.** 즉 스킬이 절약해 주는 것은 "그 스킬을 쓰지 않는 세션들"의 비용입니다. 쓰는 세션에서는 여전히 자리를 차지합니다.

여기서 두 가지 결론이 나옵니다.

1. 그래도 **일반적인 세션당 비용**은 크게 줄어듭니다 — 대부분의 세션은 그 스킬을 안 쓰니까요.
2. 스킬 **실행 중에 생기는 긴 출력물**까지 세션에 남는 문제는 별도의 해법(`context: fork`)이 필요합니다.

## 2. SKILL.md 프론트매터

`SKILL.md`는 맨 위 `---` 사이에 들어가는 YAML **프론트매터** + 본문 구조입니다.

```markdown
---
name: pr-summary
description: PR 데이터를 가져와 요약한다. 사용자가 PR 요약을 요청할 때 사용.
allowed-tools: Read Grep
context: fork
agent: Explore
argument-hint: [pr-number]
---

# 절차

1. `gh pr view`로 PR 정보를 가져온다.
2. 변경 파일 목록을 분류한다.
3. 3문단 이내로 요약한다.
```

### 2.1 필드 요약표

| 필드 | 실제 효과 | 흔한 오해 |
|---|---|---|
| `name` | 스킬 이름 (슬래시 명령 이름) | — |
| `description` | 무슨 일을 하는지 설명. **모델이 자동 호출 여부를 판단하는 근거**이자 목록에 표시되는 설명문 | 실행 전에 사용자에게 읽어 준다(❌), 인자 플레이스홀더로 쓰인다(❌) |
| `allowed-tools` | 나열 도구를 **승인 없이** 실행 (사전 승인) | 다른 도구를 차단한다(❌) |
| `disallowed-tools` | 해당 도구를 **사용 가능 풀에서 제거** (진짜 금지) | — |
| `context: fork` | 격리 서브에이전트에서 실행, 요약만 반환 | 도구 샌드박싱/차단(❌), 프로젝트 파일 제거(❌) |
| `agent:` | 포크 실행을 어떤 종류의 에이전트에 맡길지 지정 (예: `Explore`) | — |
| `disable-model-invocation: true` | 모델의 자동 호출 금지, 사용자 수동 호출만 허용 | 출력 크기를 줄인다(❌), 스킬을 죽인다(❌), 규칙을 강제한다(❌) |
| `user-invocable: false` | 사용자가 직접(슬래시 명령 등) 호출하지 못하게 막음. 모델만 내부 사용 | 컨텍스트를 분리한다(❌) |
| `paths: **/*` | 어떤 파일 경로에서 이 스킬이 관련되는지 지정하는 매칭 패턴(활성화 조건) | 컨텍스트를 분리한다(❌) |
| `argument-hint: [issue-number]` | 자동완성 메뉴에 표시되는 **인자 플레이스홀더**. 순수 UI 힌트 | 인자를 강제·검증한다(❌), 스캔 범위를 제한한다(❌) |

축을 정리하면 이렇습니다.

- `user-invocable` / `disable-model-invocation` → **누가 호출할 수 있는가**
- `paths` → **언제 관련되는가**
- `context` / `agent` → **어디서 실행되는가**
- `allowed-tools` / `disallowed-tools` → **도구를 어떻게 다루는가**

네 축은 서로 독립입니다.

### 2.2 `allowed-tools` — 가장 오해하기 쉬운 필드

이름이 "allowed(허용된) tools"이므로 직관적으로는 "여기 적힌 도구만 쓸 수 있다"는 **화이트리스트 제한**처럼 보입니다. 실제 동작은 다릅니다.

**실제 의미**: `allowed-tools`에 나열된 도구는 **사용자 권한 승인 프롬프트를 건너뛰고 자동 허용**됩니다. 즉 "편의를 위한 사전 승인 목록"이지, "그 외 도구를 차단하는 보안 필터"가 아닙니다.

결과적으로 다음이 모두 성립합니다.

- `allowed-tools: Write Edit`이라고 써도 `Bash`는 여전히 호출될 수 있습니다. 단지 `Bash`는 호출될 때 승인 프롬프트가 뜰 뿐입니다.
- 나열되지 않은 도구가 사용 가능 목록(pool)에서 제거되지 않습니다.
- 자동으로 샌드박스가 걸리거나, 파일 작업 외 도구가 원천 비활성화되지 않습니다.
- 파일 삭제나 쉘 명령 실행 같은 파괴적 동작을 막아주지 못합니다.
- `Write*`처럼 뒤에 와일드카드를 붙여야 제한이 걸린다는 규칙도 **존재하지 않습니다.**
- 따라서 **최소 권한 원칙(least privilege)을 구현하는 수단으로 `allowed-tools`를 쓰는 것은 잘못된 설계**입니다. 오히려 반대 방향으로 작동합니다 — 나열한 도구에 대해 승인 관문을 **없애는** 필드이기 때문입니다.

패턴 문법도 쓸 수 있습니다. `allowed-tools: Bash(npm publish *)` 는 "`npm publish`로 시작하는 bash 명령"을 사전 승인한다는 뜻입니다.

기억할 한 줄: **`allowed-tools`는 문을 잠그는 자물쇠가 아니라, 문을 열어두는 프리패스입니다.**

### 2.3 `disallowed-tools` — 이쪽이 진짜 금지

```yaml
disallowed-tools: Bash
```

스킬이 활성화되어 있는 동안 해당 도구를 **아예 사용 가능 풀에서 제거**합니다. "Bash를 절대 못 쓰게 하고 싶다"면 이쪽을 써야 합니다.

기억법: **`allowed-tools` = 승인 생략, `disallowed-tools` = 사용 금지.**

그 외 실질적 도구 제한이 필요하면 권한 모드(permission mode)나 `.claude/settings.json`의 `permissions.allow` / `deny` 같은 별도 권한 체계를 씁니다. `SKILL.md` 필드 하나로 해결되지 않습니다. 어떤 문제 상황에 "권한 모드는 바꾸지 않았다"는 조건이 붙어 있다면, 그것은 곧 실질적 제한 장치가 전혀 없다는 뜻입니다.

### 2.4 `context: fork` — 스킬을 서브에이전트에서 실행하기

스킬을 실행하는 방식은 크게 두 가지입니다.

- **기본(인라인)**: 현재 대화 컨텍스트 안에서 스킬 지시서를 읽고 그대로 이어서 수행합니다. 지금까지의 대화 내용과 로드된 프로젝트 지침을 모두 공유합니다.
- **`context: fork`**: 스킬을 **별도의 서브에이전트**에서 실행합니다. 메인 대화와 분리된 자체 컨텍스트를 갖고, 작업이 끝나면 **최종 반환 결과만** 메인으로 돌아옵니다.

```yaml
context: fork
```

- 중간 과정(브레인스토밍, 후보 비교, 폐기된 안, 긴 탐색 대화, 방대한 중간 출력)은 **전부 서브에이전트 컨텍스트에 머무릅니다.**
- 메인 대화에는 요약된 결과만 올라옵니다.

**언제 쓰는가**: 스킬이 코드베이스 전체를 훑고 긴 분석 결과를 뱉어서, 스킬이 끝난 뒤에도 그 출력물이 메인 대화 컨텍스트를 계속 잡아먹을 때. 이것이 그 문제의 정확한 해법입니다. 탐색적이고 장황한 작업(대안 브레인스토밍, 대규모 조사, 리서치)에 적합합니다.

주의 두 가지:

- `fork`는 컨텍스트를 **분기**하는 설정이지, "프로젝트 수준 파일을 전부 제거해 격리한다"는 의미가 아닙니다. 분기된 실행이 무엇을 보게 되는지는 **어떤 에이전트로 실행되는가**에 달려 있습니다.
- `context: fork`는 `allowed-tools`가 동작하기 위한 전제 조건이 **아닙니다.** `allowed-tools`는 포크 여부와 무관하게 유효합니다.

### 2.5 `agent:` 와 `Explore` — 그리고 CLAUDE.md 로딩 함정

`agent:` 필드는 포크된 실행을 어떤 종류의 에이전트에 맡길지 지정합니다. 대표적으로 내장 **`Explore`** 에이전트가 있습니다.

`Explore`는 **읽기 전용 탐색 전용 에이전트**로, "코드베이스에서 무언가를 빠르고 가볍게 찾는다"는 한 가지 목적에 최적화되어 있습니다. 그 최적화의 일환으로 **시작 시 `CLAUDE.md` 같은 프로젝트 지침 파일을 로드하지 않습니다.** 컨텍스트를 최대한 작게 유지해 검색을 빠르고 저렴하게 만들기 위한 설계 선택입니다.

그래서 `context: fork` + `agent: Explore` 조합의 스킬은 결과적으로 다음만 보게 됩니다.

- 스킬 자신의 내용(`SKILL.md` 본문)
- 그 에이전트 자체의 시스템 프롬프트
- 실행 중 스스로 명시적으로 읽어 들인 파일

**프로젝트의 `CLAUDE.md` 컨벤션은 여기에 포함되지 않습니다.** 예컨대 `pr-summary` 스킬을 이 조합으로 설정하면, 생성된 요약문이 프로젝트 `CLAUDE.md`에 적힌 문체·용어·형식 규칙을 전혀 반영하지 못합니다.

원인을 정확히 짚는 것이 중요합니다. 다음은 **원인이 아닙니다**.

- **`context: fork`가 프로젝트 파일을 일괄 제거해서** — 아닙니다. 포크는 컨텍스트를 분기할 뿐이며, 지침 로딩 여부는 어떤 에이전트로 실행되는가에 달려 있습니다.
- **`allowed-tools: Read` 권한이 없어서** — 아닙니다. 지침의 자동 로드는 도구 권한과 완전히 별개의 메커니즘입니다. `Read` 권한은 Claude가 명시적으로 파일을 읽을 때의 문제이지, 시작 시 자동 주입과는 무관합니다.
- **스킬에 인자(argument)를 넘겨서** — 아닙니다. 인자 유무는 `CLAUDE.md` 로딩에 아무 영향이 없습니다.

**진짜 원인은 `Explore` 에이전트가 컨텍스트를 작게 유지하려고 시작 시 `CLAUDE.md` 로딩을 건너뛴다는 설계 특성입니다.**

실무적 대응: 컨벤션이 반드시 반영되어야 하는 스킬이라면 (a) 필요한 규칙을 `SKILL.md` 본문에 직접 적어 두거나, (b) 스킬 절차에 `CLAUDE.md`를 명시적으로 읽는 단계를 넣거나, (c) 지침 로딩이 이루어지는 실행 방식/에이전트를 선택합니다.

### 2.6 `argument-hint` 자세히

**해결하는 문제**: `/fix-issue`가 이슈 번호를 필요로 하는데, 팀원이 `/fix-issue`만 치고 무엇을 넣어야 할지 몰라 헤매는 상황.

**동작**: `argument-hint: [issue-number]`를 넣으면 CLI 자동완성 메뉴에서 명령 옆에 `[issue-number]`라는 안내 문구가 보입니다. `/fix-issue 482`처럼 입력해야 한다는 사실이 눈으로 전달됩니다.

**중요한 성질**: 이것은 **순수하게 표시(display)용**입니다.

- 스킬의 실행 방식을 바꾸지 않습니다.
- 인자를 **강제하거나 검증하지 않습니다.** 값을 안 넣어도 실행은 됩니다.
- 동작 범위를 제한하거나 컨텍스트를 분리하지 않습니다.

즉 문서화 장치이지 유효성 검사 장치가 아닙니다.

### 2.7 존재하지 않는 필드 — `arguments:`

`arguments:` 라는 이름으로 인자 타입/유효성 검사를 하는 표준 프론트매터 필드는 Claude Code `SKILL.md`에 **존재하지 않습니다.** 명령의 자동 승인은 `allowed-tools`에 적는 것이 올바른 문법이며, `arguments` 같은 필드에 명령을 적는 것은 유효한 문법이 아닙니다.

## 3. 스킬의 스코프와 우선순위

### 3.1 네 가지 범위(scope)

| 범위 | 위치 | 성격 |
|---|---|---|
| **Enterprise** | 엔터프라이즈/관리형 경로 | 조직 전체 강제 정책 |
| **Personal** (개인) | `~/.claude/skills/<이름>/SKILL.md` | 내 모든 프로젝트에서 사용, 개인 노트북, git에 올라가지 않음 |
| **Project** (프로젝트) | `.claude/skills/<이름>/SKILL.md` | 저장소에 커밋되어 팀 공유, clone 시 함께 들어옴 |
| **Plugins** | 설치한 플러그인 내부 | 외부 패키지가 제공 |

`~`(틸데)는 사용자 홈 디렉터리를 뜻합니다. 따라서 `~/.claude/`는 개인 전역 설정, `.claude/`(프로젝트 루트 기준)는 그 저장소 전용 설정이며, 개인 설정은 그 머신 밖으로 나가지 않습니다.

### 3.2 이름 충돌 시 우선순위

같은 이름의 스킬이 여러 범위에 존재할 수 있습니다. 이때 **가장 높은 우선순위 하나만 선택되어 실행**되고 나머지는 가려집니다(override).

```
Enterprise  >  Personal (~/.claude/skills/)  >  Project (.claude/skills/)  >  Plugins
```

**핵심 포인트: Personal(개인)이 Project(프로젝트)보다 우선합니다.**

**동작하지 않는 것들:**

- 두 스킬이 **병합되지 않습니다.**
- 여러 개가 **순차 실행되지 않습니다.** 하나가 다른 하나를 **대체**합니다.
- 이름 충돌 **에러가 나서 멈추지 않습니다.** 우선순위 규칙에 따라 조용히 결정됩니다.

**구체적 시나리오:**

- 저장소에 팀 공용 `.claude/skills/review/SKILL.md`가 커밋되어 있음
- 시니어 엔지니어의 노트북에 개인용 `~/.claude/skills/review/SKILL.md`가 있음 (같은 이름인 줄 모름)
- 이 엔지니어가 공유 저장소에서 `/review` 실행
- → **개인 스킬이 실행됩니다.** 프로젝트 스킬은 가려집니다.

**왜 Personal이 Project보다 높은가**: 개인의 로컬 맞춤 설정이 공유 설정에 의해 덮이지 않게 하기 위해서입니다. 개인 환경은 사용자 본인만 영향을 받으므로, 개인 취향을 우선 적용해도 팀에는 피해가 없습니다.

**실무적 함의**: 조용히 결정되기 때문에 **본인은 눈치채지 못한 채 팀 규칙을 안 따르고 있을 수 있습니다.** 팀 협업에서 조용한 사고의 원인이 되므로, 개인 스킬은 이름을 구별되게(`my-review` 등) 짓는 것이 안전합니다.

> **구분해 둘 것**: rules의 무조건 규칙 충돌은 비결정론적이지만, **skills 이름 충돌은 확정적 우선순위가 있습니다.** 두 규칙은 다릅니다.

### 3.3 이 규칙을 활용한 개인 오버라이드 패턴

팀 공유 스킬은 그대로 두고, 나만 다른 동작을 원할 때:

```
~/.claude/skills/commit/SKILL.md   ← 같은 이름으로 개인 사본 생성
```

이렇게 하면

- 나는 `/commit`을 그대로 입력해도 내 버전이 실행되고
- 저장소 파일은 손대지 않았으므로 팀원들은 원래 프로젝트 스킬을 계속 사용합니다.

비교되는 대안들과 그 단점:

| 대안 | 왜 나쁜가 |
|---|---|
| 저장소 파일을 고치고 커밋하지 않기 | 워킹 트리가 지저분해지고, 실수로 커밋되거나 `git clean`·브랜치 전환에서 날아갑니다. 개인 설정을 공유 저장소에 두는 것 자체가 잘못된 위치 선택입니다. |
| 다른 이름의 스킬 만들기(`commit-verbose`) | 동작은 하지만 호출 명령이 바뀝니다. "같은 명령어를 유지하고 싶다"는 요구를 만족시키지 못합니다. |
| 공유 파일에 비활성화 플래그 넣기 | 공유 파일 변경이므로 커밋되면 팀 전체에 영향이 갑니다. |
| `disable-model-invocation` 사용 | 자동 호출만 막는 옵션이며, 개인 오버라이드 수단이 아닙니다. |

## 4. 워크스페이스 신뢰(Workspace Trust) — 스킬 권한의 관문

여기가 스킬 권한에서 가장 중요한 보안 개념입니다.

**문제 상황을 먼저 생각해 봅시다.** 인터넷에서 아무 저장소나 clone 했는데, 그 저장소 안에 `.claude/skills/`가 들어 있고 위험한 명령이 `allowed-tools`로 사전 승인되어 있다면? 저장소를 여는 것만으로 악성 명령이 승인 없이 실행될 수 있습니다. 심각한 공급망 공격 경로입니다.

**Claude Code의 방어책**: 처음 보는 프로젝트를 열면 **워크스페이스 신뢰 대화상자**가 뜹니다. "이 폴더의 파일을 신뢰하고 실행을 허용하시겠습니까?"라고 묻습니다.

- 사용자가 **수락하기 전까지**, 저장소에 커밋되어 들어온 프로젝트 스킬의 `allowed-tools` 사전 승인 권한은 **효력이 없습니다.**
- 결과적으로 스킬을 호출해도 `npm publish` 같은 명령마다 **매번 수동 승인 창**이 뜹니다.
- 대화상자를 닫아 버렸거나 무시했다면, 사전 승인이 적용되지 않는 것이 **정상 동작이며 버그가 아닙니다.**

**따라서 "clone 한 프로젝트 스킬의 `allowed-tools`가 먹히지 않는다"의 1순위 원인은 신뢰 미수락입니다.**

부수적으로 정리해 둘 사실:

- `allowed-tools`는 개인 스킬(`~/.claude/skills/`)만의 기능이 아닙니다. 프로젝트 스킬에서도 쓸 수 있습니다. 다만 프로젝트 스킬은 워크스페이스 신뢰가 전제됩니다.
- 이 비대칭은 합리적입니다 — 개인 스킬은 내가 직접 쓴 것이고, 프로젝트 스킬은 남이 써서 저장소에 넣어 준 것이기 때문입니다.

### 4.1 관련 권한 개념

- **권한 모드(permission mode)**: Claude가 도구를 얼마나 자유롭게 쓸 수 있는지의 단계.
  - **기본(default)**: 파일 수정, 명령 실행마다 승인을 묻습니다.
  - **`acceptEdits`**: 파일 편집을 자동 수락합니다. 승인 클릭을 줄여 주지만 **"먼저 조사할 것인가"라는 문제를 해결해 주지는 않습니다.** 그저 더 빨리 고치기 시작할 뿐입니다.
  - **plan mode**: 코드를 변경하기 전에 계획을 세우고 승인받는 모드.
- `.claude/settings.json`의 `permissions.allow` / `deny`로 프로젝트 차원의 허용/차단 규칙을 정할 수 있습니다.

## 5. 슬래시 커맨드(Slash Commands)

### 5.1 개념

슬래시 명령어는 **자주 쓰는 프롬프트를 이름 붙여 저장해 둔 것**입니다. `.claude/commands/deploy.md`라는 파일을 만들면, 사용자가 `/deploy`라고 입력했을 때 그 파일의 내용이 프롬프트로 들어갑니다. **파일 이름이 곧 명령어 이름**입니다.

`.claude/commands/release-notes.md`:

```markdown
마지막 태그 이후의 커밋 로그를 읽고,
사용자 관점에서 릴리스 노트를 작성해줘.
Breaking change는 맨 위에 별도 섹션으로 분리할 것.
```

→ `/release-notes` 로 호출됩니다.

### 5.2 스코프: 프로젝트 vs 사용자

| 위치 | 스코프 | 누가 쓸 수 있나 |
|---|---|---|
| `<프로젝트>/.claude/commands/이름.md` | 프로젝트 | 저장소를 클론한 **모든 사람** |
| `~/.claude/commands/이름.md` | 사용자(전역) | **내 머신의 나만**, 대신 내 모든 프로젝트에서 |

### 5.3 팀 배포 — Git이 곧 배포 채널

"팀 전원이 `git pull`만 하면 자동으로 명령어를 갖게 하고 싶다"의 정답은 명확합니다.

**프로젝트의 `.claude/commands/release-notes.md`에 저장하고 그 파일을 저장소에 커밋한다.**

버전 관리 시스템이 배포 메커니즘 역할을 합니다. 팀원이 `git pull` 하면 파일이 함께 내려오고, 별도 설치 절차 없이 `/release-notes`가 즉시 동작합니다.

실패하는 대안들:

- 그 파일을 `.gitignore`에 넣으면 애초에 원격에 올라가지 않아 아무에게도 전달되지 않습니다.
- 팀 리드의 `~/.claude/`에 두면 팀 리드 개인 머신 안에만 존재합니다(그 사람의 모든 프로젝트에는 적용되지만, 남에게는 전달되지 않습니다).
- 팀원에게 파일을 각자 복사하라고 하는 것은 "수동 설치 없이"라는 요구 자체를 위반합니다.

### 5.4 중요한 특성 (오해 정리)

- **사용자가 직접 입력해야 실행됩니다.** 모든 사용자 메시지 앞에 자동으로 실행되는 것이 아닙니다.
- **자동으로 압축되지 않습니다.** 커맨드 파일이 "투명한 압축(transparent compression)"을 거쳐 CLAUDE.md보다 작은 컨텍스트를 쓴다는 동작은 존재하지 않습니다.
- **도구 실행을 감시하거나 차단하는 능력이 없습니다.** 강제력의 수단이 아닙니다.

### 5.5 슬래시 커맨드 vs 스킬

스킬은 슬래시 명령어보다 한 단계 더 **구조화된 재사용 절차 패키지**입니다. 커맨드는 "프롬프트 한 덩어리"이고, 스킬은 프론트매터로 실행 방식(포크 여부, 도구 사전 승인, 호출 주체, 활성화 경로)까지 선언할 수 있습니다. 스킬 역시 슬래시 명령으로 호출되므로 사용자 입장의 진입점은 비슷하지만, 제어 가능한 축의 수가 다릅니다.

## 6. 훅(Hooks) — 결정론적 강제 장치

### 6.1 훅이란

**훅(Hook)** 은 Claude Code가 동작하는 특정 **생명주기 시점(lifecycle event)** 에 자동으로 실행되는 **프로그램(셸 명령/스크립트)** 입니다. "이 사건이 일어나면 저것을 실행하라"는 이벤트-핸들러 구조이며, `.claude/settings.json`에 이벤트 이름과 실행할 명령을 짝지어 등록합니다.

핵심은 실행 주체입니다. **LLM이 실행하는 게 아니라 Claude Code 하네스(프로그램 자체)가 실행합니다.** 그래서 모델의 기억, 판단, 추론과 완전히 무관하게 작동합니다. 이것이 훅의 존재 이유 전부입니다.

훅에는 이벤트 정보가 **JSON 형태로 전달**되므로, 로그 파일에 그대로 쌓아두면 나중에 무슨 일이 있었는지 추적할 수 있습니다.

### 6.2 대표 이벤트

| 이벤트 | 발동 시점 | 대표 용도 |
|---|---|---|
| `PreToolUse` | Claude가 어떤 도구를 실행하기 **직전** | 입력 파라미터 검사 후 **실행 자체를 차단(block)** 하고 메시지 반환 |
| `PostToolUse` | 도구 실행 **직후** | 파일 편집 후 포매터 자동 실행 |
| `InstructionsLoaded` | 지침 파일이 컨텍스트에 로드되는 시점 | 어떤 지침이 언제 왜 로드됐는지 로깅·진단 |
| `SessionStart` | 세션 시작 | 초기화 작업 |
| `Stop` | 세션/턴 종료 | 마무리 작업, 알림 |

### 6.3 전형적인 사용 예 — main 브랜치 직접 커밋 차단

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": ".claude/hooks/block-main-commit.sh"
          }
        ]
      }
    ]
  }
}
```

스크립트는 Bash 도구에 전달된 명령 문자열을 받아, 현재 브랜치가 `main`인데 `git commit`을 하려 하는지 검사하고, 그렇다면 차단 신호와 함께 "main에 직접 커밋하지 말고 PR을 여세요"라는 메시지를 반환합니다.

### 6.4 `InstructionsLoaded` 훅 — 진단 도구

지침 파일(`CLAUDE.md`, `.claude/rules/*.md` 등)이 컨텍스트에 로드되는 시점에 발동합니다. **어떤 파일이**, **언제**, **왜(어떤 트리거로)** 로드되었는지를 기록할 수 있습니다.

```json
{
  "hooks": {
    "InstructionsLoaded": [
      {
        "hooks": [
          { "type": "command", "command": "cat >> ~/instructions.log" }
        ]
      }
    ]
  }
}
```

**언제 쓰는가**: "규칙을 분명히 써 뒀는데 Claude가 안 지킨다"는 상황에서 원인이 두 가지로 갈립니다.

1. 규칙이 **애초에 컨텍스트에 들어오지 않았다** (경로 패턴 오타, 트리거 미발생 등)
2. 규칙은 들어왔는데 **Claude가 따르지 않았다** (지침 문구가 모호함)

이 둘을 구분하는 정확한 진단 방법이 `InstructionsLoaded` 훅으로 로딩 사실 자체를 로그로 남겨 확인하는 것입니다. **로드 기록이 없으면 (1), 있으면 (2)** 입니다.

반면 규칙에서 `paths`를 지워 항상 로드되게 만드는 것은 **증상을 우회할 뿐 원인을 알려주지 않습니다.**

### 6.5 훅 vs 프롬프트 — 선택 기준

요구사항에 다음 표현이 나오면 훅(또는 `settings.json` 권한 규칙)이 답입니다.

- "**자동으로 강제**되어야 한다" (must be enforced automatically)
- "**Claude가 기억하거나 따르기로 선택하는 것에 의존하면 안 된다**" (must not depend on Claude remembering or choosing to follow)
- "**Claude가 건너뛰어도 된다고 판단해도 유지**되어야 한다" (must hold even if Claude decides skipping would be fine)

반대로 "이런 스타일로 작성해주면 좋겠다" 수준의 가이드라인은 CLAUDE.md나 rules로 충분합니다.

### 6.6 훅이 아닌 것

- 훅은 **"절차 지침을 로드하는" 수단이 아닙니다.** 배포 체크리스트 같은 **읽을 내용**을 훅에 넣는 것은 용도 오류입니다. 훅은 **검사하고 차단하는 코드**이고, 읽을 내용은 **스킬**로 갑니다.
- "`PreToolUse` 훅이 모든 도구 호출 전에 배포 단계를 실행한다" 같은 구성은 의미가 없습니다 — 매 도구 호출마다 배포를 시도하게 됩니다.

## 7. 서브에이전트(Subagents)

### 7.1 서브에이전트란

**서브에이전트(subagent)** 는 메인 대화와 **별도의 독립된 컨텍스트 윈도우**를 가진 보조 Claude 인스턴스입니다. `.claude/agents/` 아래에 정의합니다. 메인 세션이 "이 작업 좀 해와"라고 위임(delegate)하면, 서브에이전트가 자기 컨텍스트 안에서 도구를 실행하고 **최종 결과 요약만** 메인에 돌려줍니다.

```
[메인 세션]  --- 작업 위임 --->  [서브에이전트: 독립 컨텍스트]
                                    grep 실행 (수천 줄 출력)
                                    파일 30개 읽기
                                    패턴 분석
[메인 세션]  <--- 요약만 반환 ---  "12개 파일 47곳에서 사용 중, 유형은 3가지..."
```

메인 세션에는 수천 줄의 원본(raw) 출력 대신 정리된 몇 문단만 들어옵니다.

### 7.2 Explore 서브에이전트

**Explore**는 이 목적에 특화된 **읽기 전용 탐색 에이전트**입니다. 코드베이스를 광범위하게 뒤져 "어디에 무엇이 있는지"를 찾아 요약합니다.

- "이 코드베이스에서 옛 ORM이 어떻게 쓰이는지 패턴을 전부 목록화해 줘" 같은 광범위한 조사에 적합합니다.
- 결과 요약만 메인 컨텍스트로 돌아오므로 토큰이 절약됩니다.
- 마이그레이션 전에 Explore로 사용 패턴을 미리 카탈로그화하는 것은 **패턴 불일치를 예방하는 모범 사례**입니다. 문제의 원인이 아니라 해결책 쪽입니다.
- 앞서 본 대로 Explore는 컨텍스트를 작게 유지하려고 시작 시 `CLAUDE.md`를 로드하지 않습니다(2.5절).

### 7.3 언제 쓰는가

전형적인 상황: 다단계 리팩터링에서 deprecated 헬퍼 함수가 수백 개 파일 중 어디에서 쓰이는지 전수 조사해야 할 때. `grep`을 메인에서 직접 돌리면 출력 수천 줄이 그대로 메인 컨텍스트를 삼킵니다. 이후 실제 리팩터링에 쓸 공간이 사라지고, 잡음 때문에 판단 품질도 떨어집니다.

Explore 서브에이전트에 위임하면 **탐색 비용이 서브에이전트 쪽에 격리**됩니다.

### 7.4 대안이 안 되는 이유

| 대안 | 왜 안 되는가 |
|---|---|
| 전체 출력을 붙여넣고 나중에 지우기 | 토큰은 **컨텍스트에 들어가는 순간 이미 소모**됩니다. 트랜스크립트에서 줄을 지워도 이미 지불한 비용은 돌아오지 않으며, 수작업 자체가 비효율입니다. |
| 플랜 모드(plan mode)로 전환 | 플랜 모드는 **코드 변경 전에 계획을 세우고 승인받는** 모드입니다. 파일 수정을 막는 안전장치이지, grep 출력을 가로채 요약해 주는 기능이 아닙니다. 목적이 다릅니다. |
| 컨텍스트 윈도우 한도를 올리기 | 비용이 늘고, 수천 줄의 잡음이 여전히 남아 신호 대 잡음 비를 악화시킵니다. 근본 문제(불필요한 정보의 유입)를 해결하지 않습니다. |

### 7.5 자기 리뷰의 한계 — 왜 별도 세션에서 리뷰해야 하는가

**상황**: 하나의 긴 세션에서 기능을 구현하고, 같은 세션에서 자기 diff를 리뷰한 뒤 PR을 엽니다. 실제로 이렇게 하면 독립 리뷰어보다 버그를 훨씬 덜 잡아냅니다.

**이유**: LLM은 컨텍스트에 있는 내용을 기반으로 추론합니다. 코드를 작성하는 동안 세웠던 **추론 과정, 전제 조건, 가정**이 컨텍스트에 그대로 남아 있습니다. 리뷰 단계에 들어가도 이 전제들이 계속 살아 있으므로, 모델은 **처음에 놓친 것을 똑같이 놓칩니다.** "내가 방금 이렇게 결정했으니 맞다"는 방향으로 **확증 편향(confirmation bias)** 이 작동합니다.

사람도 똑같습니다. 자기가 쓴 글의 오타를 못 보는 것과 같은 현상입니다. 뇌가 "의도한 것"을 읽어버리기 때문입니다. 이런 인지적 사각지대를 **블라인드 스팟(blind spot)** 이라고 합니다.

**해결**: 리뷰는 **신선한 컨텍스트(fresh session)** 또는 **별도 서브에이전트**에서 수행합니다. 작성 과정을 모르는 상태에서 결과물(diff)만 보고 판단하게 하면, 구현 의도가 아니라 실제로 쓰인 코드를 평가하게 됩니다.

**원인이 아닌 것들**:

- 컨텍스트 부족으로 diff를 못 읽어서가 아닙니다. (짧은 diff에서도 같은 현상이 나타납니다)
- 도구 결과를 캐싱해서 낡은 파일 내용을 본다는 것도 사실이 아닙니다. 파일이 수정되면 갱신된 내용을 참조합니다.
- `--print` 플래그가 Read 도구를 끄지도 않습니다.

### 7.6 서브에이전트 vs 스킬

- **스킬**: "이 절차를 이렇게 수행하라"는 **지식/절차 문서**. 순차적 체크리스트 같은 참조 자료의 온디맨드 로딩에 적합.
- **서브에이전트**: 스스로 판단하며 여러 단계를 수행하는 **작업 수행 주체**. 컨텍스트 격리가 목적.

배포 체크리스트처럼 "필요할 때 읽고 따를 절차"는 서브에이전트가 아니라 **스킬**이 맞는 단위입니다. 반대로 긴 코드베이스 분석 같은 실행 작업의 컨텍스트 격리가 필요하면 **서브에이전트** 또는 **스킬의 `context: fork`** 가 맞습니다.

## 8. 넷 중 무엇을 쓸 것인가 — 결정표

### 8.1 요구사항 → 도구 매핑

| 요구사항의 표현 | 정답 | 이유 |
|---|---|---|
| "크고 가끔 필요한 절차·체크리스트를 두고 싶다" | **스킬** | 온디맨드 로딩. 안 쓰는 세션은 비용 0에 가까움 |
| "매번 치던 긴 프롬프트를 단축키로" | **슬래시 커맨드** | 프롬프트 템플릿 한 덩어리면 충분 |
| "팀 전원이 `git pull`만으로 갖게" | **프로젝트 스코프 + 커밋** | `.claude/commands/` 또는 `.claude/skills/` 를 저장소에 커밋 |
| "나만 다르게 동작시키고 명령 이름은 유지" | **개인 스킬 오버라이드** | `~/.claude/skills/<같은이름>/` (Personal > Project) |
| "Claude가 기억하든 말든 **무조건** 강제" | **훅** (또는 `permissions`) | 하네스가 실행하므로 모델 판단과 무관 |
| "위험한 도구 호출을 **차단**" | **훅 `PreToolUse`** / `disallowed-tools` | `allowed-tools`는 차단이 아님 |
| "편집 후 자동 포매팅" | **훅 `PostToolUse`** | 결정론적 후처리 |
| "규칙이 로드는 됐는지 확인" | **훅 `InstructionsLoaded`** | 로딩 사실 자체를 로깅해 원인 이분 |
| "긴 조사의 출력이 메인을 삼키지 않게" | **서브에이전트** 또는 **`context: fork`** | 컨텍스트 격리, 요약만 반환 |
| "편향 없는 코드 리뷰" | **별도 세션/서브에이전트** | 작성 컨텍스트가 없어야 블라인드 스팟이 사라짐 |
| "명령마다 승인 클릭을 줄이고 싶다" | **`allowed-tools`** (+ 워크스페이스 신뢰) | 사전 승인 목록 |

### 8.2 네 가지 요약 비교

| | 스킬 | 슬래시 커맨드 | 훅 | 서브에이전트 |
|---|---|---|---|---|
| 정의 위치 | `.claude/skills/<이름>/SKILL.md` | `.claude/commands/<이름>.md` | `.claude/settings.json` | `.claude/agents/` |
| 실행 주체 | Claude(모델) | Claude(모델) | **하네스(프로그램)** | 별도 Claude 인스턴스 |
| 발동 방식 | 슬래시 호출 + 모델 자동 호출 | **사용자 입력만** | 생명주기 이벤트 | 메인 세션의 위임 |
| 강제력 | 없음(지침) | 없음(지침) | **있음(차단 가능)** | 없음 |
| 컨텍스트 격리 | `context: fork` 시에만 | 없음 | 해당 없음 | **기본 제공** |
| 평소 비용 | description 한 줄 | 호출 시에만 | 없음 | 없음 |
| 팀 공유 | 프로젝트 스코프 커밋 | 프로젝트 스코프 커밋 | 프로젝트 settings 커밋 | 프로젝트 스코프 커밋 |

### 8.3 자주 틀리는 지점 모음

- `allowed-tools`를 **보안 장치**로 오해 → 실제로는 승인을 **없애는** 프리패스. 금지는 `disallowed-tools`.
- `context: fork`를 **샌드박스/도구 차단**으로 오해 → 컨텍스트 분기일 뿐.
- `disable-model-invocation`을 **출력 축소·규칙 강제·스킬 비활성화**로 오해 → 호출 주체만 제한.
- `argument-hint`를 **인자 검증**으로 오해 → 순수 표시용.
- `arguments:` 필드가 있다고 오해 → **존재하지 않음.**
- Project 스킬이 Personal보다 우선한다고 오해 → **반대**.
- clone한 프로젝트 스킬의 사전 승인이 바로 먹힌다고 오해 → **워크스페이스 신뢰 수락이 전제.**
- 훅에 **읽을 내용(체크리스트)** 을 넣음 → 훅은 검사·차단 코드. 읽을 내용은 스킬.
- 큰 출력 문제를 **컨텍스트 한도 상향·나중에 삭제**로 해결 시도 → 토큰은 들어오는 순간 소모됨.
