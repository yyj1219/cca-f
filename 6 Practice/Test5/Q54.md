SCENARIO: You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow with custom slash commands, CLAUDE.md configurations, and understand when to use plan mode vs direct execution.

QUESTION: Your team runs a custom MCP server that Claude Code uses to open tickets, check CI status, and trigger build jobs. The server currently reports every failure as **isError: true** with the **body "Request failed"**, regardless of whether the cause was a CI API timeout, a malformed branch name, or the developer lacking write access. In sessions, Claude retries permission denials repeatedly and abandons transient timeouts after one attempt. What **server-side** change best enables **correct recovery** behavior?

**선택지**:
1. Add a rule to CLAUDE.md instructing Claude to retry every failed MCP tool call twice with backoff before reporting the failure
2. Return the raw stack trace and upstream HTTP status code verbatim in the error text so no diagnostic detail is ever lost
3. Define a **server-side error contract: errorCategory** (transient, validation, permission), an **isRetryable flag**, and a readable message => 정답
4. Catch all failures inside the server and return a normal success result with an empty payload so sessions continue uninterrupted

**설명**:
에러 원인을 분류하는 errorCategory (일시적/검증/권한), 즉시 재시도할 수 있는지 알려주는 isRetryable 플래그, 그리고 원인을 나타내는 가독성 있는 메시지를 서버 응답으로 정의하면, Claude Code가 에러의 성격을 정확히 파악하여 "권한 문제 시 재시도 중단", "일시적 문제 시 재시도 진행", "입력값 오류 시 사용자에게 수정 요청" 등의 올바른 판단을 내릴 수 있게 됩니다.

**문제 구분 포인트, 어려운 표현**:
- permission denials: 권한 부족
- abandons transient timeouts: 일시적인 타임아웃은 포기한다
