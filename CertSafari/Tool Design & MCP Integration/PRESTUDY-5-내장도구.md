## 5.1 내장 도구 전체 지도

Claude Code는 코드베이스를 다루는 에이전트로, 다음 도구들을 씁니다. 각 도구는 **할 수 있는 일이 엄격히 정해져 있고**, 그 **역할 경계**를 정확히 아는 것이 핵심입니다.

| 도구 | 하는 일 | 하지 못하는 일 |
|---|---|---|
| `Read` | 파일 내용을 읽어 컨텍스트에 로드 (`offset`/`limit`로 구간 지정 가능) | 수정 불가, 명령 실행 불가, 탐색 도구 아님 |
| `Glob` | 파일 **이름/경로** 패턴으로 파일 목록 수집 (`**/*.test.ts`). 수정 시간순 정렬 결과 반환 | 파일 **내용**은 전혀 보지 않음. 수정·실행 불가 |
| `Grep` | 파일 **내용(content)** 을 정규식으로 검색 (ripgrep 기반) | **수정 불가 — 순수 읽기 전용 검색 도구.** 명령 실행 불가 |
| `Edit` | 파일 안의 `old_string`을 `new_string`으로 정확히 치환. 국소 수정용 | 정규식 매칭 아님. 대규모 전면 변경·재배치에는 부적합 |
| `Write` | 파일 전체를 주어진 content로 새로 쓰거나 통째로 덮어씀 | 부분 수정·부분 병합(merge) 불가 |
| `Bash` | 셸 명령을 **실제로 실행**하고 stdout/stderr 캡처 | 대화형(interactive) 에디터 부적합. 파일 검색/읽기/편집은 전용 도구가 나음 |

가장 흔한 혼동 두 가지를 먼저 못 박아 둡시다.

- **Grep은 검색만 한다.** 아무리 매치를 찾아도 파일을 고쳐 주지 않습니다. "줄을 가져오면서 동시에 제자리에서 다시 쓴다"는 동작은 존재하지 않습니다.
- **Glob은 파일 이름만 본다.** 변수명·함수명이 파일 *내용* 안에 있으면 Glob으로는 절대 찾을 수 없고, 파일 내부 공백을 정규화하는 기능도 없습니다.

이런 혼동은 도구 이름만 보고 기능을 추정할 때 생깁니다. 각 도구의 **부작용(side effect) 유무**를 정확히 알아 두는 것이 중요합니다.

### 도구 선택 감각 요약

| 하고 싶은 일 | 도구 |
|---|---|
| 파일 이름/경로 패턴으로 찾기 | `Glob` |
| 파일 **내용**으로 찾기 | `Grep` |
| 경로를 아는 파일의 내용 보기 | `Read` |
| 파일 일부 수정 (대상이 고유하게 식별됨) | `Edit` (사전 `Read` 필요) |
| 정말로 모든 occurrence를 동일하게 바꿈 | `Edit` + `replace_all: true` |
| 파일 구조 전체 재배치, 대량 이동 | `Read` → `Write` |
| 파일 새로 만들기 / 전체 교체 | `Write` (기존 파일이면 사전 `Read` 필요) |
| 빌드·테스트·git 등 무언가를 **실행** | `Bash` |

## 5.2 탐색 도구 — Glob · Grep · Read 선택 기준

세 도구는 "무엇을 근거로 찾는가"가 완전히 다릅니다. **Glob은 경로**, **Grep은 내용**, **Read는 이미 아는 경로의 전체 내용**입니다.

### 5.2.1 Glob — 파일 "이름/경로" 찾기

- **무엇인가**: 파일 경로 패턴으로 파일 목록을 얻는 도구입니다. 파일 안을 열어보지 않습니다.
- **왜 있는가**: "이런 이름의 파일들이 어디에 있지?"를 **가장 싸게** 답하기 위해서입니다. 결과가 경로 목록뿐이라 토큰을 거의 안 씁니다.
- **패턴 문법(글로브 패턴)**
  - `*` : 경로 구분자(`/`)를 제외한 임의의 문자열
  - `**` : 디렉토리 경계를 넘어 재귀적으로 매칭 (하위 폴더 전체)
  - `?` : 임의의 한 글자
  - `{a,b}` : a 또는 b

```
**/*.test.tsx     → 어느 깊이의 폴더든 .test.tsx로 끝나는 파일
**/*.spec.tsx     → .spec.tsx로 끝나는 파일
**/*Test.tsx      → 파일명이 Test.tsx로 끝나는 파일 (예: LoginTest.tsx)
src/**/*.{ts,tsx} → src 아래 모든 ts/tsx
src/components/**/*.tsx
```

- **언제 쓰나**: 명명 규칙(naming convention)이 신뢰할 만하고 여러 개로 섞여 있을 때(`.test.tsx`, `.spec.tsx`, `Test.tsx`), 폴더가 깊게 중첩되어 있을 때, **내용은 볼 필요 없이 파일의 존재/부재만** 판단하면 될 때. 패턴이 여러 개면 그냥 여러 번 호출하면 됩니다.
- **한계**: 파일 "안에 무엇이 들었는지"는 전혀 모릅니다. 그건 Grep의 일입니다.

**활용 예 — 테스트가 없는 컴포넌트 개수 세기**

1. `**/*.tsx`로 컴포넌트 목록 수집 (단, `.test.tsx` 제외)
2. `**/*.test.tsx`로 테스트 목록 수집
3. 두 경로 목록을 비교해 짝이 없는 것을 셈

파일을 하나도 열지 않으므로 I/O와 토큰 소모가 최소입니다. 반대로 각 파일을 Read로 다 열어 보거나, 파일 내용에 "test"라는 단어가 있는지 Grep하거나, 전체 테스트 스위트를 Bash로 돌리는 것은 모두 훨씬 무겁고 부정확합니다.

### 5.2.2 Grep — 파일 "내용" 검색

정규식으로 파일 내용을 검색하는 도구입니다. 내부적으로 ripgrep 기반이라 대형 저장소에서도 빠릅니다.

```
Grep(pattern="API_TIMEOUT_MS", output_mode="content", glob="**/*.ts")
```

| 파라미터 | 의미 |
|---|---|
| `pattern` | 검색할 정규식 |
| `path` | 검색 시작 디렉터리/파일 |
| `type` | 언어별 파일 필터 (`py`, `js`, `rust`, `go` …) |
| `glob` | 파일명 패턴 필터 (`**/*.tsx`) |
| `output_mode` | `files_with_matches`(기본, 경로만 — 가장 저렴) / `content`(매칭 줄 번호와 줄 내용) / `count`(파일별 매치 개수) |
| `-i` | 대소문자 무시 |
| `-n` | 줄 번호 표시 |
| `-A` / `-B` / `-C` | 매칭 뒤/앞/양쪽 문맥 줄 수 |
| `multiline` | **줄바꿈을 넘어 매칭**하는 모드 |

**쓰는 상황**: 코드베이스 전체에서 어떤 심볼/문자열이 어디에 쓰이는지 **영향 범위(scope)를 파악할 때.** 예를 들어 "`parseInvoice` 함수를 호출하는 모든 위치"처럼 **코드 내용**을 찾는 작업은 전적으로 Grep의 일입니다.

> **출력 모드는 "철저함"의 차이가 아니다.** `count`, `content`, `files_with_matches`는 **같은 검색 결과를 다른 형태로 보여줄 뿐**입니다. 모드를 바꾼다고 더 깊게/더 넓게 찾아주지 않습니다.

#### 멀티라인(multiline) 모드

기본적으로 grep 계열 도구는 **한 줄씩** 검사합니다. 패턴이 줄바꿈을 넘어가면 절대 매치되지 않습니다.

문제가 되는 전형적인 코드 — 문자열이 이어붙기로 쪼개진 경우:

```js
throw new Error("insufficient " +
                "permissions for this resource");
```

`insufficient permissions`는 소스 텍스트상 한 줄에 연속으로 존재하지 않습니다(`" +`와 줄바꿈, 공백이 끼어 있음). 그래서 단일 라인 패턴으로는 절대 안 잡힙니다.

```
pattern:  insufficient[\s"+]*permissions
multiline: true
```

같은 증상이 Python 클래스 헤더에서도 납니다.

```python
class OrderHandler(
    BaseHandler, LoggingMixin
):
    ...
```

`class \w+\(BaseHandler` 같은 단일 행 패턴은 이 정의를 놓칩니다. 반면 한 줄로 쓰인 `class UserHandler(BaseHandler):`는 잡히므로 **"일부만 검색된다"** 는 증상이 나타납니다. 해결은 `multiline: true`이고, 동시에 `type`으로 범위를 좁히면 노이즈와 비용이 줄어듭니다.

```
Grep(
  pattern: "class\s+\w+\([^)]*BaseHandler",
  type: "py",
  multiline: true,
  output_mode: "content"
)
```

기억할 것: **"찾았는데 일부가 안 잡힌다 + 문자열이 여러 줄로 쪼개져 있다" → 도구를 바꾸는 게 아니라 Grep의 multiline을 켠다.**

잘못된 대안들:

- **Glob으로 모든 `.py`를 나열한 뒤 전부 읽어서 눈으로 확인** → 정확도는 얻어도 토큰과 시간을 엄청나게 낭비합니다. 검색 도구가 있는데 수동 스캔을 하는 셈입니다.
- **`output_mode`를 바꾸기** → 결과 표현만 바뀔 뿐 멀티라인 누락은 그대로입니다.
- **Bash로 파일마다 grep을 개별 호출** → Grep은 이미 저장소 전체를 언어별로 필터링해 한 번에 검색합니다. 파일별 반복 호출은 훨씬 느리고 불필요합니다.
- **Glob(경로 검색)이나 파일 전체 Read로 전환** → 문제의 성격과 무관합니다.

#### Grep과 `.gitignore` — 반드시 알아야 할 동작

`Grep`은 ripgrep 기반이라 **기본적으로 `.gitignore` 규칙을 존중해, 무시된 파일과 디렉터리(`node_modules/`, `dist/`, `build/`, 빌드 산출물 번들 등)를 전체 검색 대상에서 제외합니다.**

그러나 중요한 예외가 있습니다.

> **`.gitignore`에 등록된 경로라도, 그 경로를 검색 명령에 직접(명시적으로) 지정하면 검색됩니다.**

그래서 "gitignore된 minified 번들 안의 호출까지 포함해 모든 호출 위치를 찾아라"라는 요구는 **두 단계**로 처리합니다.

1. 저장소 전체에 대해 `Grep`으로 `parseInvoice` 검색 (기본 무시 규칙이 적용됨)
2. gitignore된 번들 파일의 **경로를 직접 지정해** 한 번 더 `Grep`

주의: `multiline` 플래그는 **여러 줄 패턴 매칭**을 켜는 옵션일 뿐, `.gitignore` 규칙을 무시하거나 우회하는 효과가 전혀 없습니다. 두 기능은 서로 무관합니다.

### 5.2.3 Read — 파일 내용 읽기

- **무엇인가**: 특정 파일의 내용을 컨텍스트로 가져옵니다. `offset`/`limit`로 일부 구간만 읽을 수도 있습니다.
- **비용**: 가장 비쌉니다. 파일 전체가 토큰으로 들어옵니다.
- **원칙**: **어디를 읽어야 할지 이미 알 때만** 사용합니다. **탐색용이 아닙니다.** 디렉토리를 Read로 지정해 재귀 목록을 얻는 용도가 아니며(그건 Glob), 저장소 전체를 Read하는 것은 컨텍스트 낭비의 전형입니다.

### 5.2.4 점진적 탐색 전략 (Incremental Exploration)

처음 보는 코드베이스에서 "로그인 요청이 HTTP 라우트 핸들러부터 DB 호출까지 어떻게 흐르는가" 같은 **호출 체인 추적**을 해야 할 때의 표준 절차입니다.

1. **프로젝트 문서 먼저 읽기**: `CLAUDE.md`, `AGENTS.md`, `README.md` 등이 있으면 먼저 읽습니다. 아키텍처 개요, 폴더 구조, 관례가 압축적으로 적혀 있어 **적은 토큰으로 큰 지도**를 얻습니다.
   - `CLAUDE.md`: Claude Code가 세션 시작 시 자동으로 참고하는 프로젝트 지침 파일. 빌드 명령, 코딩 컨벤션, 아키텍처 설명 등을 적어둡니다.
   - `AGENTS.md`: 같은 목적의 도구 중립적 규약 파일.
2. **진입점 찾기**: Grep으로 `login`, `/auth/login`, 라우트 등록 코드 등을 검색해 라우트 핸들러 위치를 특정합니다.
3. **호출 체인 따라가기**: 찾은 파일의 import/require 문을 보고, 다음 계층(컨트롤러 → 서비스 → 리포지토리 → DB)의 파일만 **하나씩 순서대로** 읽습니다.
4. 목표에 도달할 때까지 2–3을 반복합니다.

핵심은 **"넓게 싸게 좁힌 뒤, 좁게 비싸게 읽는다"** 입니다.

반대로 하면 안 되는 것들:

- 저장소 전체/`src` 전체를 미리 Read → 컨텍스트를 다 소진하고, 정작 필요한 정보가 밀려납니다.
- 파일 크기(단어 수)가 큰 순서로 읽기 → 파일 크기와 관련성은 아무 상관이 없습니다. 큰 파일이 자동 생성 파일이거나 데이터 파일일 수도 있습니다.
- 최근 수정 시각 순으로 읽기 → 최근 수정과 "로그인 흐름"은 무관합니다. 최근에 만진 게 CSS일 수도 있습니다.

이런 접근들은 공통적으로 **근거 없는 가정(heuristic)** 위에 서 있고, 목표와 인과관계가 없습니다.

## 5.3 파일 편집 도구 — Read 선행 요건과 Edit vs Write

### 5.3.1 사전 읽기(prior-access) 요구

| 도구 | 용도 | 선행 `Read` 필요 여부 |
|---|---|---|
| `Read` | 파일 내용 읽기 | — |
| `Write` | **새 파일 생성** 또는 파일 전체 덮어쓰기 | 완전히 새 파일이면 **불필요**, 기존 파일 덮어쓰기면 **필요** |
| `Edit` | 기존 파일의 일부를 정확히 치환 | **필요** (기존 내용을 알아야 치환 가능) |

> **규칙: 이미 존재하는 파일을 `Write`로 덮어쓰거나 `Edit`으로 수정하려면, 현재 대화 세션 안에서 그 파일을 `Read`로 먼저 읽었어야 합니다.**

반대로, 저장소 어디에도 존재하지 않는 새 파일(예: `config/feature-flags.json`)을 만들고 내용이 이미 전부 정해져 있다면, **전체 파일 경로와 전체 내용을 `Write`에 넘기는 한 번의 호출로 끝납니다.** 존재하지 않는 파일을 먼저 `Read`할 이유가 없고, 부분 치환용인 `Edit`을 쓸 대상도 없습니다. **"`Write`는 언제나 선행 `Read`를 요구한다"는 것은 사실이 아닙니다** — 이미 존재하는 파일을 덮어쓸 때에 한해 안전장치가 걸립니다.

기존 `settings.local.json`을 갱신하는 순서는 따라서 이렇습니다.

1. `Read`로 `settings.local.json` 읽기
2. `Write`로 덮어쓰기 (부분 수정이면 `Edit`가 더 적절)

패턴 요약: **Read(최신 확인) → Write(전체 1회 호출).**

### 5.3.2 Write — 전체 덮어쓰기

`Write`는 지정한 경로의 파일을 **주어진 content로 통째로 교체**합니다. **부분 병합 개념이 없습니다.**

**Write가 적합한 상황**

- 파일 거의 전체가 바뀔 때 (전체 재들여쓰기, 전면 포매팅, 생성 파일 재생성)
- 파일 구조를 대대적으로 재배치할 때. 예: 파일 곳곳에 흩어진 여러 `export` 문을 상단의 한 블록으로 모으기
- 새 파일 생성

**올바른 순서: Read → Write**

1. `Read`로 파일 전체 내용을 로드
2. 재구성된 전체 파일을 만든 뒤
3. 같은 경로에 `Write`로 통째로 씀

**왜 여러 번의 Edit이 아닌가?** 각 export를 지우고 상단에 추가하는 작업을 연쇄적인 Edit으로 하면, 앞의 Edit이 파일을 바꾸면서 뒤의 Edit이 기대하던 `old_string`이 더 이상 유일하지 않거나 아예 존재하지 않게 되어 실패하거나 코드가 꼬입니다.

또 다른 예: 900줄짜리 파일의 거의 모든 줄에서 선행 공백이 제각각이라 들여쓰기를 표준화해야 하는 경우, 줄마다 `Edit`을 900번 호출하는 것은 토큰과 API 요청 면에서 극단적으로 비효율적입니다. 재정렬된 전체 내용을 담아 `Write`를 **한 번** 부르는 것이 맞습니다.

### 5.3.3 Edit vs Write 선택 기준

| 상황 | 도구 |
|---|---|
| 국소적인 몇 줄 수정, 대상이 고유하게 식별됨 | `Edit` (주변 맥락 유지, diff가 작음) |
| 정말로 모든 occurrence를 동일하게 바꿈 | `Edit` + `replace_all: true` |
| 파일 구조 전체 재배치, 대량 이동, 전면 포매팅 | `Read` → `Write` |
| 새 파일 생성 | `Write` |

부수적으로: 단일 파일의 존재 여부를 확인하려고 `Glob`을 부르는 것은 불필요하고, `Edit`의 `old_string`에 파일 전체 텍스트를 넣는 것은 Edit 도구의 취지에 맞지 않습니다 — 그 경우엔 그냥 `Write`를 쓰면 됩니다.

## 5.4 Edit의 고유 매칭(Unique Match) 규칙

### 5.4.1 Edit의 동작 원리

Edit은 다음을 받습니다.

- `file_path` — 대상 파일
- `old_string` — 찾을 문자열
- `new_string` — 바꿔 넣을 문자열
- (선택) `replace_all` — 모든 출현을 바꿀지 여부

**핵심 규칙 두 가지**

1. `old_string`은 **리터럴 텍스트**로 해석됩니다. **정규식이 아닙니다.** 따옴표가 있든 없든 정규식으로 바뀌지 않으며, 그래서 정규식 메타문자 이스케이프 같은 개념이 애초에 적용되지 않습니다.
2. `old_string`은 파일 안에서 **정확히 한 번만 등장해야** 합니다. 두 번 이상 등장하면 어느 것을 바꿔야 할지 알 수 없으므로 오작동을 막기 위해 호출이 **실패**합니다. Edit은 "의미상 어느 쪽이 진짜인지" **추론하지 않습니다.**

### 5.4.2 문제 상황 ①: 버전 문자열이 우연히 겹칠 때

`package.json`에서 버전 문자열 `1.4.2`를 바꾸고 싶은데, 우연히 어떤 의존성 이름 안에도 `1.4.2`가 부분 문자열로 들어 있습니다.

```json
{
  "version": "1.4.2",
  "dependencies": {
    "legacy-shim-1.4.2": "^3.0.0"
  }
}
```

`old_string: "1.4.2"`로 하면 어느 쪽이 바뀔지 알 수 없습니다.

**해결책 — 주변 문맥을 포함시켜 유일하게 만든다**

```
old_string:  "version": "1.4.2",
new_string:  "version": "1.5.0",
```

키 이름 `"version":`과 줄 전체 구조를 함께 넣음으로써 파일 전체에서 **단 한 곳**에만 매칭됩니다. 여전히 모호하면 앞뒤 줄을 더 붙여 문맥을 넓히면 됩니다.

### 5.4.3 문제 상황 ②: 같은 로그 줄이 두 함수에 있을 때

`logger.warn("legacy-path")`가 같은 파일의 서로 다른 두 함수에 있고, 그중 하나만 바꿔야 합니다.

**올바른 해결: `old_string`을 넓힌다(widen).** 대상 위치의 주변 코드 — 앞뒤 줄, 함수 선언부 등 — 를 함께 포함시켜 파일 내에서 유일하게 식별되게 만든 뒤 재시도합니다.

```
old_string:
function handleLegacyRequest() {
  logger.warn("legacy-path")
```

이렇게 하면 다른 함수 안의 동일한 로그 줄과 구분됩니다.

**잘못된 해결들**

- `replace_all: true`로 둘 다 바꾼 뒤 하나를 수동으로 되돌리기 → 의도와 어긋나는 비정상적 우회이며, 중간에 잘못된 상태를 만듭니다.
- `Write`에 새 로그 한 줄만 content로 넘기기 → **Write는 파일 전체를 덮어씁니다.** 한 줄만 넘기면 파일이 그 한 줄만 남고 나머지가 전부 사라집니다. Write는 병합하지 않습니다.
- `Grep`으로 고치기 → Grep은 파일을 수정할 수 없습니다.

### 5.4.4 `replace_all`은 언제 쓰나

"이 심볼을 파일 전체에서 일괄 개명한다" 같은 **의도적 전역 치환**에만 씁니다. 무관한 위치가 섞여 있는 상황에서 켜면 의존성 이름까지 망가지는 **사이드 이펙트**가 납니다.

> **원칙: 모호함은 `replace_all`이 아니라 더 넓은 문맥으로 푼다.**

## 5.5 안전장치 (Guardrails)

내장 도구의 제약은 불편을 위한 것이 아니라 **설계 의도가 담긴 안전장치**입니다.

### 5.5.1 사전 읽기 요구가 막는 사고

- 모델이 파일의 현재 내용을 모르는 상태에서 덮어쓰면 **기존 설정이나 코드가 통째로 소실**될 수 있습니다.
- 예를 들어 `settings.local.json`에 다른 사람이 추가해 둔 항목이 있는데, 모델이 자기가 생각한 버전으로 통째로 갈아엎으면 그 항목은 사라집니다.
- 먼저 읽게 강제하면 모델이 기존 내용을 파악한 뒤 **병합된 결과**를 쓰게 됩니다.

**관련 오해 정리**

- **`Grep`으로 확인하면 되지 않나?** 안 됩니다. Grep은 매칭된 일부 라인만 보여줄 뿐 파일 전체 상태를 보장하지 않으므로, 사전 접근 요구 조건을 충족하지 못합니다. 요구되는 것은 `Read` 호출 자체입니다.
- **Bash로 파일을 지우고 새로 쓰면?** 우회는 안전장치를 무력화하는 나쁜 습관이며, 애초에 Write는 기존 파일 덮어쓰기를 정상 지원합니다. 삭제는 불필요하고 위험합니다.
- **아무 조건 없이 덮어쓸 수 있다?** 아닙니다. 그것이 바로 이 정책이 막으려는 상황입니다.
- 이전에 한 번 읽었더라도, 그 사이 외부 도구나 다른 프로세스가 파일을 바꿨을 수 있으므로 덮어쓰기 직전에 다시 `Read`하는 것이 모범 사례입니다.

### 5.5.2 낙관적 동시성 제어 (Optimistic Concurrency Control)

데이터베이스에서 온 개념입니다. 잠금을 걸지 않고 일단 진행하되, **쓰기 시점에 "내가 읽은 이후로 바뀌었는가"를 검사**합니다. 바뀌었으면 실패시키고 다시 읽게 합니다.

Edit도 같습니다. 도구는 "내가 읽었을 때의 파일 상태"를 기억해 둡니다.

**시나리오**

1. Claude가 세션 초반에 `config.yaml`을 Read함.
2. 동료가 별도 에디터에서 그 파일을 손으로 수정하고 저장함(디스크 내용 변경).
3. Claude가 예전에 본 문자열을 `old_string`으로 삼아 Edit 호출 → **실패**.

원인은 "파일이 Claude의 마지막 읽기 이후 디스크에서 변경되었다"는 것이고, **정답 복구 절차는 파일을 다시 `Read`해서 최신 내용을 확인한 뒤, 갱신된 텍스트를 기준으로 Edit을 재시도**하는 것입니다.

**잘못된 대응들**

- `old_string`의 모든 문자를 이스케이프 → Edit은 리터럴 매칭이므로 무의미합니다.
- 파일을 버리고 Write로 처음부터 재생성 → **동료의 수정 사항을 파괴**합니다. 데이터 손실입니다.
- "세션 내 두 번째 Edit은 원래 실패한다"고 믿고 Bash 치환으로 전환 → 사실이 아닌 가정이고, 안전장치를 우회하는 나쁜 습관입니다.

## 5.6 Bash와의 역할 구분

### 5.6.1 "무언가를 실행해야 한다면 Bash다"

버그를 재현하려면 테스트 스위트를 **실제로 돌려야** 합니다. `pytest`, `npm test`, `cargo test` 같은 명령을 실행하고 **stdout과 stderr**(스택 트레이스가 여기 나옵니다)를 받아오는 유일한 수단이 **Bash**입니다.

**흔한 착각들**

- Grep으로 "test"라는 단어를 찾아서 테스트가 통과했다고 판단 → 검색은 실행이 아닙니다.
- Glob으로 테스트 **파일이 존재함**을 확인 → 파일 존재와 테스트 통과는 무관합니다.
- Read로 `jest.config.js` 같은 **설정 파일**을 읽고 성공/실패를 추론 → 설정은 실행 결과를 담지 않습니다.

> **원칙: 정적 조회 도구로는 런타임 상태를 알 수 없다. 실행해야 알 수 있다.**

### 5.6.2 stdout / stderr / stack trace

- **stdout**(표준 출력): 프로그램의 정상 출력 스트림
- **stderr**(표준 에러): 에러 메시지 전용 스트림
- **스택 트레이스(stack trace)**: 예외 발생 시점의 함수 호출 경로. "어느 파일 몇 번째 줄에서, 어떤 함수 체인을 거쳐 터졌는가"를 알려 줍니다. 버그 재현·원인 분석의 1차 자료입니다.

### 5.6.3 반대로, Bash를 쓰면 안 되는 일

파일 검색/읽기/편집에는 **전용 도구가 더 낫습니다.** `find`나 `ls -R`로 목록을 뽑고 하나씩 열어보는 방식은 느리고, 토큰을 쓰고, 결과가 구조화되지 않습니다. 파일마다 grep을 개별 호출하는 것도 마찬가지입니다. 또한 에이전트 환경에서 **대화형 에디터**를 Bash로 여는 것은 애초에 불가능합니다.

**Bash는 "전용 도구가 못 하는 일"에 씁니다.** 빌드, 테스트, git 등입니다.

## 5.7 흔한 오용과 함정

### 5.7.1 Glob으로 코드 내용을 찾으려는 시도

"`parseInvoice` 함수를 호출하는 모든 위치"를 찾을 때:

- `Glob("**/*parseInvoice*")`로 파일명에 함수명이 들어간 파일만 모으는 것 → **잘못**. 호출자 파일의 이름이 `parseInvoice`를 포함할 이유가 없습니다.
- `Glob("**/*.js")`로 모든 `.js`를 나열한 뒤 파일명만 보고 추측 → **잘못**. 실제 내용을 보지 않으므로 누락과 오탐이 발생합니다.
- `Glob("**/API_TIMEOUT_MS")` → **아무것도 찾지 못합니다.** Glob은 파일 **이름**을 찾습니다. 변수명은 파일 이름이 아니라 파일 내용 속에 있습니다.

### 5.7.2 대규모 변경 전 영향 범위 파악하기

수백 개 파일에 걸친 환경 변수 이름 변경(`API_TIMEOUT_MS` → `REQUEST_TIMEOUT_MS`) 같은 작업에서 **가장 먼저 할 일은 "어디를 고쳐야 하는지 전부 찾는 것"** 입니다.

```
Grep(pattern="API_TIMEOUT_MS", output_mode="content", glob="**/*")
```

이렇게 하면 참조하는 모든 파일과 정확한 줄이 나오고, 이 목록을 검토한 뒤 편집에 들어갑니다.

**잘못된 접근들**

- Bash로 대화형 에디터를 열어 눈으로 확인 → 에이전트 환경에서 불가능하고 비효율적입니다.
- 환경 설정 파일 하나만 먼저 고치고 나머지는 모델의 "추론"에 맡김 → 수백 파일 중 일부를 놓치는(missing reference) 치명적 결과를 낳습니다.

### 5.7.3 별칭(alias)과 re-export 때문에 놓치는 호출부

리팩토링에서 특히 위험한 함정입니다. 모듈이 함수를 **다른 이름으로 다시 내보내는** 경우가 있습니다.

```ts
// dateUtils.ts
export { formatDate as fmt, parseDate as pd }
```

이러면 외부 코드는 `formatDate`로도, `fmt`로도 이 함수를 부를 수 있습니다. `formatDate`만 Grep하면 `fmt` 호출부를 전부 놓치고, 이름을 바꾸는 순간 런타임 에러가 납니다.

**올바른 절차: Read → Grep (여러 번)**

1. `Read`로 `dateUtils.ts`를 읽어 **모든 export 이름과 별칭을 식별** (`formatDate`, `fmt`)
2. 식별된 **각 이름마다** `Grep`을 코드베이스 전체에 수행
3. 두 결과를 합쳐 완전한 호출부 목록을 얻음

**잘못된 접근**

- `Glob("**/dateUtils*")`로 파일만 찾고 호출자도 그 패턴 안에 있으리라 가정 → 호출자는 아무 파일에나 있을 수 있습니다.
- `export`라는 단어의 등장 횟수를 세어 임계값 넘는 파일만 읽기 → 호출부 탐색과 아무 관련이 없습니다.
- `formatDate` 단일 Grep만 수행 → 별칭 `fmt` 호출부를 전부 누락합니다.

> **일반 원칙: 심볼의 이름을 바꾸기 전에, 그 심볼이 코드베이스에서 불릴 수 있는 모든 이름을 먼저 확정하라.**
