# 2. 제약된 도구 설계와 도구 제어

## 이 장에서 다루는 것

- 도구 설계 원칙 — 단일 책임, 좁은 계약, 최소 권한, 공격 표면 축소
- 범용 도구 vs 제약된 도구(Constrained / Scoped Tools) — 실수를 구조적으로 불가능하게 만들기
- 도구 개수가 늘 때 생기는 문제 — 선택 정확도 붕괴와 그 진짜 원인
- `tool_choice` 네 가지 값과 전형적 활용 패턴
- 관련 Claude API 파라미터 — 확장 사고와 `tool_choice`의 비호환
- 코디네이터·서브에이전트 역할 분리와 도구 범위 제한
- 서브에이전트의 실패 보고, 에스컬레이션, 코디네이터의 후속 처리

---

## 1. 도구 설계 원칙

### 1.1 단일 책임 원칙 (Single Responsibility)

하나의 도구는 **하나의 일**만 해야 합니다. 여러 기능을 한 도구에 몰아넣은 것을 **모놀리식 도구(monolithic tool)** 라고 부릅니다.

나쁜 예: `analyze_document` 하나가 (1) 데이터 포인트 추출, (2) 요약 생성, (3) 원문 대조 검증을 모두 수행.

무슨 일이 벌어지나: 사용자가 "이 문서 좀 분석해줘"처럼 모호하게 요청하면, 모델은 세 동작 중 무엇을 원하는지 알 수 없습니다. 도구 설명이 "문서를 분석한다"로 뭉뚱그려져 있으니 어떤 결과가 나올지 예측할 수 없고, 실행할 때마다 세 동작 중 하나만 골라 수행하는 일관성 없는 결과가 나옵니다.

올바른 재설계 — **좁은 계약(narrow contract)** 을 가진 도구로 분할:

| 도구 | 책임 |
|---|---|
| `extract_data_points` | 문서에서 구조화된 값만 뽑아 반환 |
| `summarize_content` | 요약문만 반환 |
| `verify_claim_against_source` | 주장 하나를 원문과 대조해 참/거짓과 근거를 반환 |

각 도구는 "언제 쓰는지"가 이름만 봐도 명확해집니다. 모델의 선택 문제가 애매한 추측에서 명확한 매칭으로 바뀝니다.

**주의(흔한 함정):** `mode: "extract" | "summarize" | "verify"` 같은 **enum 파라미터를 추가하는 것만으로는 부족**합니다. 파라미터는 늘렸는데 도구 설명은 여전히 "문서를 분석한다"로 남아 있으면, 모델은 어떤 mode를 골라야 할지 판단할 근거를 여전히 못 얻습니다. enum을 쓸 거라면 각 enum 값의 의미와 선택 기준을 설명에 반드시 써야 합니다.

### 1.2 최소 권한 원칙 (Principle of Least Privilege)

보안의 고전 원칙으로, **주체에게 자기 역할 수행에 꼭 필요한 최소한의 권한만 부여**하라는 것입니다. 에이전트 설계에서는 "역할에 필요한 최소한의 도구만 노출하라"로 번역됩니다. "나중에 필요할지도 모르니까" 미리 붙여두는 것이 사고의 원인입니다.

**예시 A — 티켓 분류 에이전트.** 고객 지원 티켓 **분류(triage)** 에이전트가 하는 일은 티켓을 읽고 빌링/기술/계정관리 큐 중 하나로 보내는 것뿐입니다. 그런데 도구가 네 개 붙어 있습니다.

- `route_ticket` (본래 역할)
- `process_refund` (환불 실행)
- `reset_password` (비밀번호 초기화)
- `close_account` (계정 해지)

로그를 보니 에이전트가 환불 관련 티켓을 빌링 큐로 보내는 대신 **직접 `process_refund`를 호출**하고 있었습니다. 모델 입장에서는 자연스러운 행동입니다 — 사용자가 환불을 원하고, 환불 도구가 눈앞에 있으니 씁니다.

근본 해결: 분류 에이전트에서 실행 계열 도구 세 개를 **제거**하고 `route_ticket`만 남깁니다.

**예시 B — 코드 리뷰 서브에이전트.** `Read`, `Grep`, `Glob`(읽기 전용)으로 만들어 두었는데, 리팩터링 중 "있으면 편하겠지" 하며 `Bash`와 `deploy_service`를 추가합니다. 그 직후 리뷰 에이전트가 **승인되지 않은 브랜치에 배포를 실행**하기 시작합니다. 올바른 해법은 `Bash`와 `deploy_service`를 도구 집합에서 제거하고 역할이 요구하는 읽기 전용 도구로 되돌리는 것입니다.

원리: **에이전트의 전문 범위를 벗어난 도구는, 사용 가능한 이상 언젠가 오용됩니다.** 모델은 확률적으로 도구를 고르므로, 목록에 있는 위험한 도구는 결국 선택될 수 있습니다.

핵심 격언: **없는 도구는 잘못 호출될 수 없다.**

### 1.3 왜 다른 방법들은 불충분한가

| 대안 | 왜 부족한가 |
|---|---|
| 시스템 프롬프트로 금지 ("절대 배포하지 마") | 프롬프트는 강한 권고일 뿐 **확률적 제약**입니다. 오해·환각·긴 컨텍스트에서의 지시 희석으로 뚫립니다. 불필요한 도구가 계속 노출된다는 근본 원인도 그대로. **도구를 주지 않는 것이 유일하게 확정적인 제약입니다.** |
| 도구 설명에 "이 상황에서는 쓰지 마시오" 문구 추가 | 프롬프트 지시는 모델이 무시하거나 우회할 수 있습니다. 텍스트 지시보다 물리적 차단이 훨씬 견고합니다. |
| 입력 스키마 검증 강화 | 스키마는 "인자의 형태가 올바른가"만 봅니다. "지금 이 도구를 호출하는 것 자체가 부적절한가"나 호출 타이밍은 판단하지 못합니다. |
| temperature 낮추기(예: 0.2) | 확률적으로 호출 빈도를 줄일 뿐, 노출된 도구를 근본적으로 막지 못합니다. |
| 사람 승인 단계 추가 | 유용한 안전장치이긴 하지만, 에이전트가 애초에 잘못된 도구를 호출하려 시도하는 설계 결함은 그대로 남습니다. 불필요한 승인 요청이 계속 쏟아집니다. |
| 도구 이름만 바꾸기 (`process_refund` → `billing_queue_helper`) | 이름은 바뀌어도 하는 일은 여전히 환불 실행입니다. 실제 동작과 이름이 어긋나면 모델은 더 혼란스러워지고, 코드를 읽는 사람도 속게 됩니다. 전형적 임시방편. |
| 도구를 더 추가해 위험한 도구를 희석하기 | 선택 공간이 복잡해져 오선택과 환각 가능성이 오히려 **높아집니다.** |
| 상류 데이터 부실로 진단하기 | 원인 오진입니다. 자료가 충분해도 도구가 있으면 부르게 됩니다. |

### 1.4 관련 개념: 공격 표면(attack surface) 축소

최소 권한은 보안 원칙이기도 합니다. 에이전트가 프롬프트 인젝션(외부 데이터에 숨겨진 악의적 지시)에 노출되었을 때, 위험한 도구를 애초에 갖고 있지 않으면 피해 범위가 제한됩니다.

## 2. 범용 도구 vs 제약된 도구 (Constrained / Scoped Tools)

### 2.1 범용(Generic) 도구의 위험

범용 도구란 자유도가 매우 큰 인자를 받는 도구입니다.

- 임의의 URL (`fetch_url(url)`)
- 임의의 바이트 오프셋 범위 (`read_range(file, start=10234, end=10998)`)
- 자유 형식 SQL (`run_sql(query)`)
- 임의의 셸 명령 (`shell(cmd)`)

이런 도구는 강력하지만 두 종류의 문제를 만듭니다.

**① 값의 출처가 신뢰할 수 없는 경우.** `fetch_url(url)`에 모델은 다음과 같은 URL을 넣을 수 있습니다.

- 모델이 **환각(hallucination)** 으로 지어낸, 존재하지 않는 URL
- 처리 중인 문서 안에 박혀 있던 **신뢰할 수 없는 출처의 URL** (프롬프트 인젝션 경로가 되기도 합니다)

결과는 형식이 깨진 페이지, 무관한 페이지, 최악의 경우 외부로의 원치 않는 요청입니다.

**② 모델이 그 값을 정확히 계산하지 못하는 경우.** LLM은 정확한 숫자 계산이나 오프셋 산술에 약합니다. 결과적으로 무관한 구간을 가져오거나, 문장 중간이 잘린 깨진 텍스트(malformed span)를 가져오거나, 의도치 않은 데이터를 건드립니다.

### 2.2 원칙: 범용 도구를 제약된 대안으로 **교체**한다

핵심 패턴은 **모델이 실수할 수 있는 자유도 자체를 인터페이스에서 없애는 것**입니다. 추가가 아니라 교체입니다.

**수단 ① 허용 목록(allowlist) 검증.** `fetch_url`을 제거하고 `load_document`로 교체합니다.

```
load_document(document_id 또는 url):
  1. 주어진 값이 허용된 문서 출처(사내 문서 저장소 도메인, 등록된 소스 목록)에
     속하는지 검증한다.
  2. 검증에 실패하면 가져오지 않고, 왜 거부되었는지 설명하는 에러를 반환한다.
  3. 검증에 성공한 경우에만 콘텐츠를 가져온다.
```

**수단 ② 자유 인자를 식별자로 대체.** 오프셋 산술을 인터페이스에서 지워 버립니다.

Before (generic):

```json
{ "name": "retrieve_clause",
  "input_schema": { "properties": {
    "file": {"type": "string"},
    "start_byte": {"type": "integer"},
    "end_byte": {"type": "integer"} } } }
```

After (constrained):

```json
{ "name": "get_clause_by_id",
  "input_schema": { "properties": {
    "clause_id": { "type": "string",
      "description": "Clause identifier from the parsed clause index, e.g. 'S3.2'" } } } }
```

이때 문서는 사전에 파싱되어 **조항 인덱스(pre-parsed index)** 로 준비됩니다. 서버는 인덱스에 존재하는 유효한 ID만 받아들이고, 항상 완전한 조항 하나를 반환합니다. 모델은 오프셋을 계산할 기회 자체가 없으므로 그 종류의 실수가 **구조적으로 불가능**해집니다.

### 2.3 잘못된 대안들

| 대안 | 왜 나쁜가 |
|---|---|
| **이름만 바꾸기** (`fetch_url` → `get_document`) | 접근 제어와 입력 검증이 없으므로 임의 URL 문제가 그대로 남습니다. |
| **똑같은 도구를 하나 더 추가** (`fetch_url_v2`를 폴백으로) | 제약이 하나도 추가되지 않고 도구 선택 공간만 복잡해집니다. |
| **더 넓은 권한의 도구를 추가** (`raw_file_read`) | 제약을 거는 것과 정반대 방향입니다. |
| **검증용 2차 에이전트 추가** | 결함 있는 인터페이스는 그대로 두고 감시자만 붙이는 것. 토큰 비용과 복잡도만 늘고 근본 원인은 남습니다. |
| **설명에 예시(few-shot)를 더 넣기** | 모델의 산술 한계를 프롬프트로 완전히 통제할 수 없습니다. "제약된 도구로 교체"라는 패턴 자체가 아닙니다. |
| **기능을 통째로 없애고 사람이 붙여넣게 하기** | 안전하긴 하나 자동화를 포기하는 것이며, 제약된 도구 도입이라는 지침과 다릅니다. |

### 2.4 일반 원칙

> 모델이 특정 종류의 실수를 반복한다면, 그 실수를 "가능하게 만드는 인자"를 스키마에서 제거하라. 프롬프트로 부탁하지 말고 타입으로 막아라.

## 3. 도구 개수가 늘 때 생기는 문제

### 3.1 도구 개수와 선택 정확도의 관계

모델은 도구를 고를 때 **모든 도구의 이름·설명·스키마를 한꺼번에 비교**합니다. 도구가 늘어날수록:

- 컨텍스트에 들어가는 스키마 텍스트가 늘고 (**컨텍스트 혼잡**)
- 서로 의미가 겹치는 도구 쌍이 기하급수적으로 늘고
- 후보군(candidate set)에서 하나를 고르는 **의사결정 복잡성**이 커지고
- **그럴듯하지만 틀린 도구 선택**(plausible-but-wrong selection)이 나타나며
- 비슷한 옵션 사이에서 망설이는 **추론 지연**이 생깁니다.

경험적으로 도구가 대략 **10~20개**를 넘어가면 도구 선택 정확도와 인자 추출 정확도가 눈에 띄게 떨어집니다.

전형적 사례: 리서치·초안 작성·팩트체크·포매팅을 모두 하는 리포트 생성 파이프라인 에이전트에 **18개 도구**를 전부 준 경우. 개별 도구는 각각 정상 작동하는데도 선택 정확도가 무너집니다.

### 3.2 해결책: 역할별 전문 서브에이전트로 분할

20개 도구를 가진 단일 만능 에이전트를, 단계별로 나눈 서브에이전트(각각 약 4~5개 도구)와 가벼운 오케스트레이터(orchestrator)로 재설계합니다.

```
                 ┌─ research  agent  (4 tools)
                 ├─ outline   agent  (4 tools)
Orchestrator ────┼─ draft     agent  (4 tools)
                 ├─ edit      agent  (4 tools)
                 └─ publish   agent  (4 tools)
```

```
research-agent    : 검색, 문서 로드, 인용 수집 도구만
drafting-agent    : 초안 작성/편집 도구만
fact-check-agent  : 출처 조회, 대조 도구만 (읽기 전용)
formatting-agent  : 렌더링/포매팅 도구만
```

**신뢰성이 좋아지는 진짜 이유**는 하나입니다. 각 서브에이전트가 비교해야 하는 **후보군이 20개에서 4개로 줄어들어 의사결정 복잡성이 직접적으로 낮아지기 때문**입니다. 부수적으로 위험한 도구가 무관한 역할에 노출되지 않아 안전성도 올라가고, 선택지가 줄어 속도도 함께 올라갑니다.

### 3.3 흔한 오해들

- **"API 호출 수가 줄어서"** — 아닙니다. 오케스트레이터 ↔ 서브에이전트 통신이 추가되므로 총 호출 수는 오히려 늘거나 비슷합니다. 그리고 호출 수는 애초에 선택 오류의 원인이 아니었습니다.
- **"컨텍스트 윈도우가 작아져서 모델이 더 신중해져서"** — 컨텍스트 크기와 신중함은 인과관계가 없습니다.
- **"결과를 캐싱해서 도구 호출이 사라져서"** — 캐싱은 속도·비용 이야기이지 선택 정확도 이야기가 아닙니다.
- **"설명을 더 짧게 쓰면 된다"** — 해법이 아닙니다. 설명이 짧아지면 구분 정보가 줄어 오선택이 **더** 늘어납니다. 문제는 설명 길이가 아니라 **도구 개수와 역할 혼재**입니다.

## 4. `tool_choice` — 도구 호출을 API 차원에서 제어하기

### 4.1 왜 필요한가

설명과 프롬프트로 "이렇게 해줘"라고 부탁하는 것은 **확률적**입니다. 대부분 맞지만 가끔 틀립니다. 반면 `tool_choice`는 **결정론적(deterministic)** 제어입니다. API가 강제합니다.

`tool_choice`는 Anthropic Messages API의 요청 파라미터로, `tools`와 함께 요청마다 보냅니다. "이번 턴에 모델이 도구를 써야 하는가"를 제어합니다.

### 4.2 네 가지 값

| 값 | 동작 | 모델이 할 수 있는 것 | 언제 쓰나 |
|---|---|---|---|
| `{"type": "auto"}` | 기본값. 모델이 턴마다 스스로 판단 | 텍스트 응답 OR 아무 도구 호출 OR 호출 안 함 | 대부분의 대화형 에이전트. 행동할지(act) 말할지(respond)를 스스로 정하는 능력을 보존 |
| `{"type": "any"}` | **반드시 제공된 도구 중 최소 하나를 호출**해야 함 | 목록 중 하나 호출. 자유 텍스트만으로 응답하는 것은 **금지**. 어떤 도구인지는 모델이 선택 | 모든 요청이 실시간 데이터 조회나 실제 작업을 요구해서, 모델의 내부 지식만으로 답하면 안 되는 경우 |
| `{"type": "tool", "name": "X"}` | **반드시 지정한 도구 X를** 호출. 도구까지 고정 | 오직 X만 호출 | 출력 형식을 고정하고 싶을 때(구조화 추출 등), 특정 도구를 선행시켜야 할 때 |
| `{"type": "none"}` | 도구를 전혀 호출하지 못하게 함 | 오직 텍스트 응답만 | 도구 실행을 잠시 막고 계획만 말하게 할 때 |

`any` 와 `tool` 을 합쳐 **강제 도구 호출(forced tool calling)** 이라고 부릅니다.

```json
{
  "model": "claude-...",
  "tools": [ {"name": "create_profile", "...": "..."} ],
  "tool_choice": {"type": "tool", "name": "create_profile"},
  "messages": [ ... ]
}
```

**주의(오해 정리):**
- `{"type": "forced"}` 라는 값은 **존재하지 않습니다.**
- `any` 는 도구가 단 하나만 정의되어 있어도 정상 동작합니다(도구 개수 제한 없음).
- `any` 는 deprecated 되지 않았습니다.

### 4.3 `any` vs `tool` 의 결정적 차이

- `any` = "**뭔가는** 반드시 도구를 불러라" — 어느 도구인지는 모델이 고름
- `tool` = "**바로 이** 도구를 불러라" — 도구까지 지정

따라서 "특정 도구를 첫 번째로 강제하고 싶다"면 `any`로는 불가능합니다. `tool`이어야 합니다.

### 4.4 활용 패턴 ① — 첫 턴 강제, 이후 자율

요구사항: 온보딩 에이전트가 대화의 **가장 첫 동작**으로 `create_profile`을 반드시 부르고, 그 다음부터는 `send_welcome_email`, `assign_default_settings` 중 상황에 맞게 자유롭게 고르길 원한다.

해법 — **턴에 따라 `tool_choice`를 동적으로 바꾼다.**

```python
# 1번째 턴
tool_choice = {"type": "tool", "name": "create_profile"}

# 2번째 턴 이후
tool_choice = {"type": "auto"}
```

왜 다른 방법은 안 되는가:
- `tools` 배열에서 순서를 앞에 두기 → **순서는 강제력이 전혀 없습니다.** 단순 나열 순서일 뿐.
- 첫 턴에 `none` → 오히려 도구 호출을 금지하므로 요구사항과 정반대.
- 전체 대화에 `any` → 특정 도구를 지정할 수 없고, 이후 턴에서 "도구를 안 쓰고 그냥 대답"하는 자유도 뺏김.

### 4.5 활용 패턴 ② — 선행 의존성 보장 (Ordering)

요구사항: `add_tags`, `link_related`, `generate_summary`(보강 도구들)는 `extract_metadata`가 만들어낸 필드에 의존한다. 그런데 모델이 가끔 값을 **추측(guess)** 해서 보강 도구를 먼저 부른다.

해법: 메타데이터가 필요한 턴에 `tool_choice: {"type": "tool", "name": "extract_metadata"}`를 걸고, 그 결과가 돌아온 뒤부터 `auto` 또는 `any`로 풀어줍니다.

왜 설명 보강만으로는 부족한가:
- "이 도구는 extract_metadata의 출력이 필요합니다"라고 설명에 써두는 것은 **확률적 개선**입니다. 대부분 잘 동작하지만 "guarantee(보장)"라는 요구는 충족하지 못합니다.
- 도구 목록을 턴마다 추가·제거하는 방법도 이론상 가능하지만, `tool_choice`가 훨씬 단순하고 캐시·컨텍스트 안정성 면에서 유리합니다.

**규칙: "보장(guarantee)"이라는 단어가 요구사항에 있으면 프롬프트가 아니라 API 제어를 쓴다.**

### 4.6 활용 패턴 ③ — 자유 텍스트 응답 자체를 금지 / 구조화된 출력 강제

요구사항 A: 하위 자동화 시스템이 **도구 호출만 파싱**할 수 있고 자유 텍스트는 처리 못 한다. 알림이 오면 `acknowledge_alert`, `escalate_alert`, `suppress_alert` 중 반드시 하나로 응답해야 한다.

요구사항 B: 분류 서브에이전트가 `tag_urgent` / `tag_normal` / `tag_spam` 중 하나를 반드시 호출해야 하고, 절대 산문으로 답하면 안 되며, 어떤 태그인지는 메시지 내용에 따라 달라져야 한다.

두 경우 모두 해법은 `tool_choice: {"type": "any"}` 입니다.

```python
response = client.messages.create(
    model="claude-...",
    tools=[tag_urgent, tag_normal, tag_spam],
    tool_choice={"type": "any"},   # 도구 중 하나는 무조건 호출
    messages=[{"role": "user", "content": message_text}],
)
```

- `auto` 는 기본값일 뿐 강제력이 없고 텍스트 응답을 허용하므로 "항상 도구 호출"을 보장하지 못합니다.
- `none` 은 도구를 완전히 금지 — 정반대.
- `{"type":"tool","name":"tag_normal"}` 은 내용과 무관하게 항상 같은 도구를 강제하므로 상황별 선택이 필요한 유스케이스에는 부적합합니다(분류가 되지 않습니다).
- 시스템 프롬프트에 "항상 도구로 응답하라"고 쓰는 것은 **강제가 아니라 부탁**이므로 100% 보장이 아닙니다.

### 4.7 `tool_choice`로 풀면 안 되는 문제

설계 감각을 정리하면:

- "모델이 내부 지식으로 대충 답해 버리는 것"을 막고 싶다 → `any`.
- **"권한 밖의 도구를 쓰는 것"을 막고 싶다 → `tool_choice`가 아니라 도구 목록 자체를 줄이는 것이 정답입니다.** `any`나 특정 도구 강제는 오히려 자율성을 없애면서 오용 문제는 그대로 남깁니다.
- 에이전트가 "행동할지 말할지"를 스스로 정하는 능력을 유지하려면 반드시 `auto`여야 합니다.

## 5. 관련 API 파라미터 — 확장 사고와의 상호작용

### 5.1 확장 사고 (Extended Thinking)

**확장 사고**는 모델이 최종 답변을 내기 전에 내부적으로 더 긴 추론 과정을 거치도록 하는 기능입니다. 복잡한 다단계 문제에서 정확도를 높입니다.

두 가지 형태가 있습니다.

- **수동 확장 사고 (manual extended thinking)** — 요청에 `thinking: {"type": "enabled", "budget_tokens": N}` 을 명시적으로 켭니다.
- **적응형 사고 (adaptive thinking)** — 더 새로운 모델에서 지원되며, 모델이 필요에 따라 사고량을 스스로 조절합니다.

### 5.2 확장 사고와 `tool_choice` 의 비호환

> **수동 확장 사고(`thinking: {"type": "enabled"}`)가 켜져 있으면 `tool_choice` 로 `{"type": "any"}` 와 `{"type": "tool", ...}` 를 쓸 수 없습니다.** 이 경우 `auto` 또는 `none` 만 지원되며, 강제 옵션을 넣으면 API 요청 자체가 에러로 실패합니다.

이유를 직관적으로 이해하자면: 강제 도구 호출은 모델의 첫 출력이 반드시 도구 호출 블록이어야 한다는 제약인데, 수동 확장 사고는 첫 출력이 반드시 thinking 블록이어야 한다는 제약이기 때문에 서로 충돌합니다.

**해결 방법 (둘 다 필요할 때):**

1. **적응형 사고로 전환** — 더 새로운 모델에서 지원되며, 사고와 강제 도구 호출을 함께 쓸 수 있습니다.
2. **수동 확장 사고를 끈다** — 강제 도구 호출이 더 중요하다면 사고를 포기합니다.

기억해 둘 오해들:
- 확장 사고가 `tool_choice` **전부**를 막는 것은 아닙니다. `auto` 와 `none` 은 정상 동작합니다.
- 도구 개수와는 무관한 문제입니다.

## 6. 코디네이터·서브에이전트 역할 분리와 도구 범위 제한

### 6.1 기본 구조

복잡한 작업은 하나의 거대한 에이전트보다 역할별로 나눈 여러 에이전트로 처리하는 편이 안정적입니다.

- **코디네이터(Coordinator) / 오케스트레이터**: 큰 작업을 쪼개어 서브에이전트에게 위임하고, 결과를 모아 통합하며 다음 단계를 결정.
- **서브에이전트(Subagent)**: 좁은 역할 하나를 맡아, 위임받은 하위 작업을 **자기 컨텍스트 안에서 끝까지** 수행. 예: 리서치 / 코딩 / QA 에이전트, 또는 접수(intake)·처리(processing)·전달(delivery) 파이프라인.

서브에이전트들은 서로 다른 폴더·데이터 구간을 맡아 **병렬로** 실행될 수 있습니다.

이 구조의 이점은 **관심사의 분리**와 **컨텍스트 격리**입니다. 서브에이전트가 수십 개 파일을 뒤지며 만든 잡다한 중간 산출물과 시행착오 로그가 코디네이터의 컨텍스트를 오염시키지 않고, 결론만 위로 올라옵니다.

### 6.2 도구 스코핑 — 각 에이전트에게 자기 역할에 필요한 도구만

가장 중요한 설계 원칙입니다. 왜 중요한가: **모델은 손에 쥔 도구를 쓰고 싶어하는 경향이 있습니다. 접근 권한이 열려 있는 도구는 언젠가 호출됩니다.**

전형적 사례: 종합(synthesis) 에이전트는 리서치 에이전트가 이미 모아 준 자료를 정리해 최종 답변을 만드는 역할입니다. 그런데 두 에이전트가 **공용 도구 레지스트리**를 공유하는 바람에 종합 에이전트에게도 `web_search`가 노출되면, 종합 도중에 임의로 검색을 돌려 원래 자료에 없던 출처를 섞습니다. 결과적으로 인용이 일관되지 않게 됩니다.

근본 해법은 **종합 에이전트의 도구 목록에서 `web_search`를 아예 제거**하는 것입니다. (temperature 낮추기, 설명에 금지 문구 추가, 상류 데이터 탓하기가 왜 부족한지는 1.3절 표 참조.)

### 6.3 범위 제한 교차 역할 도구 (Scoped Cross-Role Tools)

멀티 에이전트로 나누면 새 문제가 생깁니다. 현실에서는 한 에이전트가 다른 역할의 기능 일부를 **자주(high-frequency)** 필요로 합니다.

- 예 A: 접수 에이전트가 처리 상태를 확인해야 하는 경우.
- 예 B: 종합 에이전트가 최종 답변을 쓰기 전에 인용된 통계 수치 하나를 확인하고 싶은 경우. 다만 출처 간 충돌을 해소하는 깊은 리서치 능력은 없습니다.

**올바른 설계:** 그 특정 목적만 수행하는 **좁은 도구 하나**만 부여합니다 — `check_status`, `verify_fact`(단일 주장의 빠른 확인 전용). 그리고 깊은 처리 작업이나 출처가 충돌하는 복잡한 케이스는 계속 담당 에이전트를 경유하거나 코디네이터에게 **에스컬레이션(refer)** 하도록 라우팅합니다.

**잘못된 설계들:**

| 접근 | 왜 나쁜가 |
|---|---|
| 다른 역할의 **전체 도구 세트를 통째로 부여** | 과도한 권한 부여(over-privileging). 상태 조회만 필요한데 데이터 변경 작업까지 실행 가능해집니다. 도구 개수 증가로 선택 정확도도 하락. |
| 그 기능을 파이프라인에서 **없앤다** | 필요한 기능을 삭제하는 것은 요구사항 회피이지 설계가 아닙니다. |
| 필요하지 않은 쪽 에이전트에 **도구를 복사** | 문제와 무관하고 권한만 넓힙니다. |
| 검증 도구를 아예 주지 않고 **모든 건을 코디네이터가 수동 검토** | 자주 발생하는 단순 작업이 병목이 됩니다. |
| 코디네이터만 도구를 갖고 **매번 요청·대기** | 불필요한 에이전트 간 통신 비용과 지연(latency). |

핵심 원칙 두 가지:

- **최소 권한 원칙** — 각 에이전트는 자기 역할에 필요한 최소한의 도구만 가진다.
- **빈도에 맞춘 범위 부여** — 자주 필요한 단순 기능은 직접 주고, 드물고 복잡한 기능은 담당 역할에 위임한다. 판단 기준은 "빈번하게 필요한가"와 "부작용 없는 읽기 전용에 가까운가"입니다.

### 6.4 도구 스코핑과 `tool_choice`를 함께 고려하기

"에이전트가 자기 소관 밖 도구를 건드린다"는 문제에 대한 옳은 조합은:

- **도구 세트**: 역할별로 축소 (리서치 에이전트엔 검색 도구만, QA 에이전트엔 테스트 도구만)
- **`tool_choice`**: `{"type": "auto"}` 유지 — 각 에이전트가 턴마다 도구를 쓸지 텍스트로 답할지 자율 판단하는 능력을 보존

`any`로 강제하면 도구가 필요 없는 턴에도 억지로 도구를 부르고, 15개 전체 세트를 그대로 두면 오용 문제도 남습니다. `none`으로 막으면 서브에이전트가 아무 일도 못 합니다. 단일 도구 강제는 상황별 유연성을 없앱니다.

## 7. 서브에이전트의 실패 보고와 코디네이터의 후속 처리

### 7.1 캡슐화(Encapsulation)와 결함 격리 — 로컬에서 해결된 문제는 올리지 않는다

서브에이전트의 책임은 **"결과"를 책임지는 것**이지 "과정을 중계하는 것"이 아닙니다.

예: ETL 3단계(extract → transform → load) 마이그레이션을 위임받았고, load 단계에서 DB 커넥션 리셋(알려진 일시적 오류)으로 2번 실패했지만 서브에이전트 내부의 재시도 로직이 3번째 시도에서 성공했다고 합시다.

→ 코디네이터에게는 **성공 결과와 완료된 마이그레이션 요약**만 보고합니다.

이유:
- 일시적 실패는 **로컬에서 이미 해결**되었고, 최종 상태는 완전 성공입니다.
- 이런 실패는 코디네이터가 알아야 할 **의사결정 정보가 아닙니다.** 알아도 할 수 있는 일이 없습니다.

잘못된 보고 방식들:

| 잘못된 보고 | 결과 |
| --- | --- |
| `isError: true`로 실패 보고 | **사실이 아닙니다.** 코디네이터가 이미 성공한 마이그레이션을 또 재시도 → 중복 처리, 롤백, 데이터 손상 위험 |
| "자격 증명이 만료된 것 같으니 새 크레덴셜을 달라"고 에스컬레이션 | 명시된 원인(transient)과 다른 **오진단**. 연결 리셋은 인증 실패가 아니고, 3번째에 성공했다는 사실 자체가 반증 |
| load 단계를 빼고 부분 결과만 보고 | 실제 DB 상태(적재 완료)와 보고 내용이 **불일치**하는 거짓 보고 |

물론 무조건 침묵하라는 뜻은 아닙니다. 재시도 사실을 **부가 정보로 간략히 덧붙이는 것**은 관측(observability)에 도움이 됩니다. 다만 **최종 상태는 성공**이어야 합니다.

**요약: 안에서 해결된 문제는 안에서 끝낸다. 밖으로 올리는 것은 밖에서만 해결 가능한 것이다.**

### 7.2 에스컬레이션 — 언제 위로 올릴 것인가

에스컬레이션은 **서브에이전트가 자기 권한과 재시도 한도 안에서 더 이상 할 수 있는 게 없을 때** 상위로 문제를 넘기는 행위입니다.

- 재시도 예산을 다 쓰고도 **최종 실패**했을 때
- 서브에이전트 **권한 밖의 결정**이 필요할 때 (파괴적 작업 승인, 새 자격 증명 획득 등)
- 위임된 지시가 **모호하거나 모순**될 때

예시: 문서 번역 서브에이전트가 `translate_text` 도구를 호출했는데 연결 타임아웃. 로컬 재시도 정책은 일시적 오류에 대해 최대 2회 자동 재시도 후 에스컬레이션. 두 번째 재시도도 타임아웃 → 재시도를 멈추고 코디네이터에게 실패를 전파합니다. 전파할 때는 코디네이터가 판단할 수 있도록 **충분한 정보를 함께** 보냅니다.

- `errorCategory` (여기서는 `transient`)
- 허용된 로컬 시도 전부에서 타임아웃이 지속되었다는 사실
- **어떤 텍스트가 번역되지 않은 채 남았는지** (부분 진행 상태)

세 번째 항목이 중요합니다. 코디네이터가 다른 도구로 우회하거나, 남은 부분만 다시 시도하거나, 사람에게 알릴 수 있으려면 **어디까지 됐는지**를 알아야 합니다.

잘못된 대응들:
- **조작된 결과 반환**: 이전 성공 호출의 캐시 응답을 진짜 번역인 척 조용히 반환 → 절대 안 됩니다. 워크플로 중단을 피하려다 **틀린 데이터를 시스템에 주입**합니다. 이런 오류는 나중에 훨씬 큰 비용으로 발견되고, 에이전트에 대한 신뢰 자체를 무너뜨립니다. **"조용히(silently)"라는 단어가 나오면 거의 항상 나쁜 설계입니다.**
- **무한 재시도 + 카운터 리셋**: 재시도 한도를 두는 이유(자원 낭비 방지, 장애 조기 감지) 자체를 무효화합니다. 서브에이전트가 영원히 멈춰 있고, 코디네이터는 이유도 모른 채 기다립니다.
- **오류 재분류**: 타임아웃을 권한 실패로 바꿔서 보고 → 코디네이터가 존재하지 않는 접근 제어 문제를 고치려 들게 만듭니다. 반복된 타임아웃은 네트워크/가용성 문제이지 접근 권한 문제가 아닙니다. **관측한 오류의 성격을 그대로 보고하는 것**이 원칙입니다.

### 7.3 로컬 처리 vs 에스컬레이션 판단표

| 상황 | 서브에이전트의 행동 |
|---|---|
| 일시적 오류, 재시도 한도 내 | 로컬 재시도 |
| 일시적 오류, 재시도로 결국 성공 | **성공 보고** (내부 재시도는 노출 불필요) |
| 일시적 오류, 재시도 한도 소진 | **에스컬레이션** — 카테고리 + 지속 사실 + 부분 진행 상태 포함 |
| 검증 오류 | 입력을 스스로 고칠 수 있으면 수정 후 재요청, 아니면 에스컬레이션 |
| 권한 오류 | 즉시 에스컬레이션 (재시도 무의미) |
| 어떤 경우든 | **거짓/조작된 결과 반환 금지** |

### 7.4 부분 결과(Partial Results)와 우아한 실패 보고

배치 작업 중 일부만 실패하는 상황은 흔합니다. 예: 50건 고객 레코드 보강 중 47건 성공, 3건은 자격 증명 부족(`permission`)으로 실패, 그리고 서브에이전트는 스스로 더 넓은 권한을 얻을 수 없음.

이때 서브에이전트가 코디네이터에게 돌려보내야 하는 것:

1. **성공한 47건의 결과 (부분 결과)** — 유효한 작업을 버리지 않습니다.
2. **미해결 3건의 식별 정보** — 누가 남았는지 명시.
3. **마주친 오류의 성격** — `errorCategory: "permission"` 등.
4. **시도한 내용** — 어떤 복구를 시도했고 왜 실패했는지.

이것을 **우아한 실패 보고(graceful failure reporting)** 라고 합니다. 코디네이터는 이 정보를 받아 더 높은 권한으로 재처리하거나 사람에게 에스컬레이션할 수 있습니다.

피해야 할 패턴:
- **전체를 `isError: true`로 처리하고 47건을 폐기** — 이미 쓴 비용을 버리는 낭비.
- **실패 3건을 조용히 누락(silently dropping)** — 상위에서 데이터 누락 사실을 알 수 없어 정합성이 깨집니다. 이것이 가장 위험합니다.
- **같은 자격 증명으로 무한 재시도 루프** — `permission` 오류는 자격 증명이 바뀌지 않는 한 절대 해결되지 않습니다. 무한 루프와 자원 낭비만 발생합니다.

### 7.5 "보고된 실패" vs "프로세스 크래시"의 결정적 차이

병렬로 세 서브에이전트를 돌렸다고 합시다.

- **서브에이전트 1**: 정상 완료 → 추가 조치 없음.
- **서브에이전트 2**: 일부 성공 + 특정 파일의 권한 오류를 **보고하며** 종료 → 부분 결과와 진단 정보가 모두 존재.
- **서브에이전트 3**: 프로세스가 **아무 출력 없이 크래시** → 결과물도, 오류 로그도, 어디까지 진행했는지도 알 수 없음.

코디네이터의 후속 처리는 달라야 합니다.

| | 서브에이전트 2 | 서브에이전트 3 |
|---|---|---|
| 가진 정보 | 부분 결과 + 구체적 실패 원인 | 아무것도 없음 |
| 조치 | 부분 결과를 그대로 활용하고, 보고된 그 한 파일의 권한 문제만 핀포인트로 해결(권한 부여 후 재시도) | 진행 상황을 판단할 근거가 없으므로 **폴더 전체를 미처리(unprocessed)로 간주**하고 처음부터 재작업 |

여기서 나오는 원칙:

1. **진단 정보의 유무가 처리 전략을 가른다.** 보고된 실패는 정밀 조치가 가능하고, 침묵한 크래시는 보수적 전량 재처리가 안전합니다.
2. **원인을 추측하지 말 것.** "크래시도 아마 권한 문제였겠지"라고 가정하고 처리하는 것은 위험한 자율성 설계입니다. 데이터 없이 내리는 추정은 잘못된 복구로 이어집니다.
3. **미완료를 완료로 표시하지 말 것.** "대부분 성공했으니 완료"나 "오류 보고가 없었으니 완료"는 조용한 데이터 누락을 만듭니다. 특히 크래시한 에이전트는 오류를 보고할 기회조차 없었다는 점이 중요합니다.
4. **유효한 부분 결과를 버리지 말 것.** 둘을 똑같이 취급해 서브에이전트 2의 결과까지 폐기하는 것은 비효율입니다.
